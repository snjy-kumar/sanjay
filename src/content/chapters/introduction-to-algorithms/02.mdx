This is the chapter where the book stops talking about algorithms and starts
doing them. It takes one familiar problem, putting numbers in order, and
uses it to teach three habits every later chapter assumes: saying exactly
what an algorithm does, proving it correct, and predicting its cost before
running it.

## Before you start

**After this chapter you will be able to:**

- write insertion sort and merge sort from memory, in TypeScript, and trace both by hand;
- state a loop invariant and prove a loop correct with initialization, maintenance and termination;
- count an algorithm's steps in the RAM model and derive its best and worst case;
- explain order of growth, and why Θ(n lg n) beats Θ(n²) for large inputs but not small ones;
- write a divide-and-conquer recurrence and solve it with a recursion tree.

## Chapter map

The chapter introduces two algorithms and the tools to judge them.
**Insertion sort** is the one you would invent yourself: take items one at
a time and slide each into place. **Merge sort** is the one you probably
would not: cut the list in half, sort each half, and zip the halves
together. The gap between them is the chapter's real lesson: how you
*design* an algorithm decides its cost far more than how cleverly you write it.

Along the way come the **loop invariant** (a way to prove a loop correct),
the **RAM model** (an imaginary computer simple enough to count steps on),
**worst-case analysis** and **order of growth** (ways to compare algorithms
without a stopwatch), **divide and conquer** (a design method), and the
**recurrence** (the equation for a recursive algorithm's cost).

## 2.1 Insertion sort

### In one sentence

Insertion sort keeps the front of the array sorted and grows it by one
element at a time, sliding each new element left until it sits in place.

### The idea

#### The sorting problem, stated precisely

Before writing any algorithm, say exactly what problem it solves. The
sorting problem has an **input**: a sequence of n numbers, call them
a₁, a₂, ..., aₙ. It has an **output**: a rearrangement of those same numbers,
a′₁, a′₂, ..., a′ₙ, such that each one is less than or equal to the next.

Two words in that definition carry weight. *Rearrangement* (the formal word
is permutation) means the output contains exactly the input's elements, the
same number of times each. An "algorithm" that returns `[1, 2, 3]` for every
input produces sorted output, but it does not solve the problem, because it
loses the input. *Less than or equal* means duplicates are allowed and the
order is non-decreasing rather than strictly increasing.

A particular input, say `[31, 41, 59, 26, 41, 58]`, is called an **instance**
of the problem. An algorithm is **correct** if, for every instance, it halts
with the right output. Not most instances, not the ones in the tests: every
one. That word "every" is why the chapter needs a proof technique, not just
examples.

In real programs the numbers are rarely alone. Each one is a **key** attached
to a record, the rest of which is **satellite data**: you sort orders by
their timestamp, and the order's id, total and customer ride along. The
algorithm compares keys and moves whole records. Everything in this chapter
works the same way with records; I use plain numbers to keep the traces
readable.

#### A hand of cards

Insertion sort is how most people sort a hand of playing cards. You start
with an empty left hand. You pick up one card at a time from the table and
insert it into the correct place in your left hand, scanning from right to
left past every card bigger than it. At every moment, the cards in your left
hand are sorted, and they are exactly the cards you have picked up so far.

That last sentence is the whole algorithm, and, as we will see, it is also
the proof that the algorithm works.

In an array, the "left hand" is the front of the array. The element just to
the right of the sorted part is the next card. To make room for it, every
larger element in the sorted part shifts one place right, and the card drops
into the gap.

### Worked example

#### The algorithm, in my own TypeScript

```ts
// insertion-sort.ts — sorts the array in place and returns it.
export function insertionSort(a: number[]): number[] {
  for (let j = 1; j < a.length; j++) {      // a[0..j-1] is the sorted hand
    const key = a[j];                        // the next card
    let i = j - 1;
    while (i >= 0 && a[i] > key) {           // scan right to left
      a[i + 1] = a[i];                       // shift the bigger one right
      i--;
    }
    a[i + 1] = key;                          // drop the card in the gap
  }
  return a;
}

console.log(insertionSort([5, 2, 4, 6, 1, 3]));
```

```text
[ 1, 2, 3, 4, 5, 6 ]
```

Read it line by line against the card picture. The outer loop picks up card
number `j`, starting from the second element because a single element is
already a sorted hand. `key` holds the card in the air, which is why the
shift in the inner loop is safe: overwriting `a[j]` on the first shift does
not lose anything. The inner loop walks left while it sees bigger elements,
moving each one right. It stops for one of two reasons: it fell off the left
end (`i` became `-1`, so the key is the smallest so far) or it found an
element not bigger than the key. Either way the gap is at `i + 1`.

Two details are easy to get wrong. The test order in `i >= 0 && a[i] > key`
matters: the left side guards the right side, so `a[-1]` is never read.
(In JavaScript `a[-1]` would quietly be `undefined` and the comparison would
be `false`, so the bug would hide; in C it would read memory before the
array.) And the comparison is strictly *greater than*. With *greater than or
equal* the algorithm still sorts, but it moves equal keys past each other,
which matters for stability (see the edge cases below).

### Step by step

#### Loop invariants: how to know it is correct

Running examples builds confidence, but six examples, or six thousand, do not
prove that insertion sort works on *every* input. For that, the chapter
introduces the **loop invariant**: a statement about the program's state that
is true at the start of every iteration of a loop.

For insertion sort's outer loop the invariant is the card-hand sentence,
made exact:

> At the start of each iteration with index `j`, the subarray `a[0..j-1]`
> consists of the elements originally in `a[0..j-1]`, in sorted order.

A loop invariant is useful only if you can show three things about it.

<Flow steps={["Initialization: true before the first iteration", "Maintenance: if true before an iteration, true before the next", "Termination: when the loop stops, the invariant gives the result"]} caption="The three obligations of a loop invariant argument. The first two make it true at every iteration; the third turns it into the answer." />

**Initialization.** Before the first iteration, `j = 1`, so the subarray is
`a[0..0]`: one element, the original first element. One element is sorted.
True.

**Maintenance.** Suppose the invariant holds when an iteration starts with
some `j`. The body lifts out `a[j]`, shifts every element of `a[0..j-1]` that
is bigger than it one place right, and drops it into the gap. The elements
that moved are still in their sorted order relative to each other, because
they all moved by the same one place. Everything left of the gap is not
bigger than the key, everything right of it is bigger, so putting the key in
the gap leaves `a[0..j]` sorted, and it holds exactly the original elements
of `a[0..j]`. When `j` increases for the next iteration, that is exactly the
invariant for the new `j`. (A fully formal proof would also state and prove
an invariant for the inner `while` loop; the informal argument above is the
one the chapter makes, and it is enough to trust the code.)

**Termination.** The loop stops when `j` equals `n`, the array's length.
Substitute `n` for `j` in the invariant: `a[0..n-1]`, the whole array, holds
the original elements in sorted order. That is the definition of a correct
sort. And the loop does stop, because `j` grows by one every iteration and
`n` is fixed.

If this feels like mathematical induction, it is. Initialization is the base
case, maintenance is the inductive step. The difference is termination:
induction usually goes on forever, while a loop invariant argument stops at
the moment the loop does, and uses the invariant at that moment to prove the
result. Choosing an invariant that is strong enough to give you the result
at termination, but true at initialization, is the skill. A weak invariant
like "`a[0..j-1]` is sorted" (without "and contains the original elements")
is true and useless: it cannot rule out an algorithm that overwrites the
array with zeros.

#### Writing the invariant into code

An invariant is not only for proofs. I can turn it into an assertion and
let the computer check it on thousands of random inputs. This is the habit
the chapter should leave behind: write down what must be true, then test
that, not just the final answer.

```ts
// insertion-sort.check.ts — the invariant as a runtime check.
function isSorted(xs: number[]): boolean {
  for (let k = 1; k < xs.length; k++) if (xs[k - 1] > xs[k]) return false;
  return true;
}
function sameElements(xs: number[], ys: number[]): boolean {
  const s = (v: number[]) => [...v].sort((p, q) => p - q).join(',');
  return s(xs) === s(ys);
}

export function insertionSortChecked(a: number[]): number[] {
  const original = [...a];
  for (let j = 1; j < a.length; j++) {
    // The invariant, at the start of every iteration:
    console.assert(isSorted(a.slice(0, j)), 'prefix not sorted', j);
    console.assert(sameElements(a.slice(0, j), original.slice(0, j)), 'prefix changed', j);
    const key = a[j];
    let i = j - 1;
    while (i >= 0 && a[i] > key) { a[i + 1] = a[i]; i--; }
    a[i + 1] = key;
  }
  return a;
}

// A small property test: random arrays, compared with a trusted sort.
for (let t = 0; t < 1000; t++) {
  const n = Math.floor(Math.random() * 20);
  const xs = Array.from({ length: n }, () => Math.floor(Math.random() * 10));
  const expected = [...xs].sort((p, q) => p - q);
  const got = insertionSortChecked([...xs]);
  if (got.join(',') !== expected.join(',')) throw new Error(`failed on ${xs}`);
}
console.log('1000 random arrays sorted, invariant held every time');
```

```text
1000 random arrays sorted, invariant held every time
```

The small value range (0 to 9) is deliberate: it forces many duplicates,
which is where sorting bugs hide. If I break the code, for example by
starting the inner loop at `i = j` instead of `j - 1`, the first assertion
fires within a few arrays and names the iteration where the invariant broke,
which is far more useful than a final "expected X, got Y".

### Common mistake

The most common mistake with insertion sort is not in the idea but in the
translation: porting the book's 1-indexed pseudocode to a 0-indexed
language and getting a bound wrong. Writing `while (i > 0 && ...)` instead
of `i >= 0` means the first element is never compared, so a key smaller
than everything stops one place too far right. The fix is mechanical: shift
every index by one, and test the smallest inputs (one and two elements)
first, because that is where an off-by-one bites.

The second mistake is using `>=` in the inner test. The result is still
sorted, but equal keys jump past each other, so the sort is no longer
stable, and an array of identical values becomes the worst case instead of
the best.

#### Pseudocode conventions worth knowing

The book's pseudocode is close to real code, with a few conventions that
trip people up when they translate it:

- **Indexing starts at 1**, and a subarray written with two dots includes
  both ends. In TypeScript every index drops by one and loop bounds change
  from "up to n" to "less than n".
- **Indentation is block structure.** There are no braces.
- **The loop variable keeps a value after the loop**: one past the last
  value it took. The termination step of a loop invariant argument uses that
  value, which is why it matters.
- **"and" and "or" short-circuit**, exactly like `&&` and `||`. The
  insertion sort loop depends on that.
- **Arrays and objects are passed by reference**: a procedure that changes
  an array's elements changes the caller's array. Sorting "in place" means
  exactly this.
- **Errors are not handled.** The pseudocode assumes valid input; real code
  has to decide what to do with `null`, `NaN` or a mixed-type array.

### In real systems

Insertion sort is not a classroom toy. Timsort, the sort behind Python and
V8's `Array.prototype.sort`, uses a binary insertion sort to extend short
runs before merging them, and many quicksort libraries switch to insertion
sort below a small size. Any time code keeps a short list sorted as items
arrive (a top-10 leaderboard, a list of the next few timers), it is running
insertion sort, whether or not it says so.

The loop invariant shows up in production as the assertion or the property
test. A team that writes "at the top of this loop, everything before the
cursor has been flushed" as a comment and a check catches bugs in batch
jobs, pagination cursors and migrations that example-based tests miss.

## 2.2 Analyzing algorithms

### In one sentence

Analysing an algorithm means counting the steps it takes in a simple model
machine, as a function of the input size, and keeping only how that count
grows.

### The idea

#### What analysing means

To **analyse** an algorithm is to predict the resources it needs: usually
running time, sometimes memory, network traffic or energy. The goal is to
compare algorithms before building them, and to know how a program will
behave on inputs much bigger than the ones on my laptop.

A stopwatch cannot do that on its own. A timing depends on the machine, the
language, the compiler, what else is running and the particular input. So
the chapter replaces the real machine with a model simple enough to count
on, and then counts.

#### The RAM model

The **random-access machine** (RAM) model imagines a computer where:

- instructions run one after another, never in parallel;
- each simple instruction (add, subtract, multiply, compare, load, store,
  branch, call, return) takes a **constant** amount of time;
- each piece of data (an integer, a float, a character) fits in one memory
  **word**, and any word can be read or written in constant time, no matter
  where it is.

The model is honest about what it leaves out. Real machines have caches, so
reading memory that is nearby is far cheaper than reading memory that is far
away. They have pipelines, branch predictors and vector units. They run
many things at once. The model ignores all of that.

It also has to forbid cheating. If a "simple instruction" could sort an
array, every algorithm would be constant time. So the model assumes the
instructions a real computer has, and words of a size that grows only
slowly with the input: big enough to hold an index into the input, not big
enough to hold the whole input in one word.

Why use a model this crude? Because it predicts the thing that matters most
for large inputs, the **shape** of the cost: whether doubling the input
doubles the time, quadruples it, or barely changes it. The constants it gets
wrong; the shape it usually gets right.

#### Input size and running time

The **size** of the input depends on the problem. For sorting it is the
number of items, n. For multiplying two numbers it is the number of bits.
For a graph it is two numbers, the vertices and the edges. Always say which.

The **running time** on a particular input is the number of primitive steps
executed. Since every line of pseudocode takes some constant time, each line
gets a cost, call them c₁, c₂ and so on, and the running time is the sum,
over lines, of the line's cost times the number of times it runs.

### Worked example

#### Counting insertion sort line by line

Here is my TypeScript again, with each line's cost and how many times it
runs. Let n be the array length, and for each outer iteration `j` let tⱼ be
the number of times the `while` test is evaluated in that iteration. (The
test always runs one more time than the loop body: the last test is the one
that fails.)

Add it up and the running time is:

`T(n) = c1·n + (c2 + c3 + c7)·(n − 1) + c4·Σtⱼ + (c5 + c6)·Σ(tⱼ − 1)`

Everything depends on the tⱼ, and they depend on the input. Two inputs of
the same size can take very different times. So the question "how long does
insertion sort take on n items?" has no single answer. It has a best, a
worst and an average.

**Best case: the array is already sorted.** Every inner test fails at once,
because the element to the left is never bigger than the key. So every tⱼ is
1, and every Σ(tⱼ − 1) is 0. The total becomes some constant times n plus
another constant: `T(n) = a·n + b`. The running time is a **linear
function** of n. On sorted input, insertion sort just checks each element
once and moves on.

**Worst case: the array is in reverse order.** Each key is smaller than
everything before it, so it walks all the way to the left end. In iteration
`j` the test runs j + 1 times (j shifts, then the test that fails at `i = -1`).
Summing j + 1 for j from 1 to n − 1 gives (2 + 3 + ... + n), which is
n(n + 1)/2 − 1. The shift lines run j times each, which sums to n(n − 1)/2.
Both sums are quadratic in n. Collecting terms, the running time has the
form `T(n) = a·n² + b·n + c` for constants a, b and c that depend on the
line costs. The running time is a **quadratic function** of n.

#### Inversions: what the work really counts

The trace in section 2.1 had 9 shifts in total. That number has a meaning.
An **inversion** is a pair of positions where the earlier element is bigger
than the later one. In `[5, 2, 4, 6, 1, 3]` they are (5,2), (5,4), (5,1),
(5,3), (2,1), (4,1), (4,3), (6,1) and (6,3): nine.

Every shift in insertion sort swaps one adjacent out-of-order pair, which
removes exactly one inversion and creates none. So the total number of
shifts equals the number of inversions in the input, and insertion sort's
running time is proportional to n plus the number of inversions. A sorted
array has zero inversions (the best case); a reversed one has the maximum,
n(n − 1)/2 (the worst case). An array that is "nearly sorted", with each
element a few places from home, has few inversions, and insertion sort is
nearly linear on it. That is why real sorting libraries still use insertion
sort on small or nearly sorted pieces.

### Step by step

#### Worst case, average case

The chapter focuses on the **worst-case** running time, the longest time on
any input of size n, and gives three reasons that are worth keeping:

1. It is a **guarantee**. If I know the worst case, I know the algorithm
   never takes longer, which is what an interactive system or a deadline
   needs.
2. For many algorithms the worst case **happens often**. A search for a
   record that is not there always does the maximum work, and absent records
   are common.
3. The **average case is often as bad as the worst**. For a random array,
   on average about half of the sorted prefix is bigger than the key, so tⱼ
   is about j/2. Halving a quadratic leaves a quadratic: the average case of
   insertion sort is still a quadratic function of n.

Average-case analysis needs an assumption about what "a typical input" is,
usually that every ordering is equally likely. Real inputs often break that
assumption: logs arrive nearly sorted, user lists are often sorted already.
When an average-case result matters, say what distribution it assumes.

#### Order of growth

The exact formula `a·n² + b·n + c` has constants that depend on the machine,
and the model already ignores the machine. So the chapter makes one more
simplification: keep only the **leading term** and drop its constant. For
large n the n² term dominates everything else, and the constant in front of
it is a property of the hardware, not of the algorithm.

What is left is the **order of growth**: insertion sort's worst case grows
like n². The notation for that is Θ(n²), read "theta of n squared". Chapter 3
of the book defines Θ precisely; for now it means "grows like this, up to
constant factors, for large n".

One algorithm is considered more efficient than another if its worst-case
running time has a lower order of growth. For small inputs that can be
wrong, because constants matter there. For large enough inputs it is always
right. The numbers below are plain arithmetic, not measurements:

### Common mistake

The common mistake is to measure once and call the number the complexity.
"It sorted 10,000 items in 40 ms" says nothing about 1,000,000 items. A
quadratic algorithm at 40 ms for ten thousand items takes about 400 seconds
for a million, while a linear one takes about 4 seconds. The fix is to
measure the *ratio* between sizes, as below, and to compare the ratio with
the count from the model.

A second mistake is to analyse only the input I happen to test with.
Insertion sort on sorted test data looks linear, and it ships, and then
real data arrives in reverse order. Always ask which input is the worst
case and test that one on purpose.

### In real systems

#### Measuring to check the model

A model is a prediction, so test it. The cheapest test of an order of growth
is the **doubling experiment**: time the algorithm at n, 2n, 4n and 8n, and
look at the ratio between consecutive timings.

```ts
// doubling.ts — does insertion sort's time grow like n²?
import { insertionSort } from './insertion-sort';

let previous = 0;
for (const n of [2_000, 4_000, 8_000, 16_000, 32_000]) {
  const a = Array.from({ length: n }, () => Math.random());
  const start = performance.now();
  insertionSort(a);
  const ms = performance.now() - start;
  const ratio = previous ? (ms / previous).toFixed(2) : '-';
  console.log(`n=${n}  ${ms.toFixed(1)} ms  ratio ${ratio}`);
  previous = ms;
}
```

For a quadratic algorithm each doubling of n should roughly **quadruple** the
time, so the ratio column should settle near 4. For a linear one it would
settle near 2, and for n lg n slightly above 2. The first rows are noisy:
the JIT compiler is still warming up and the arrays are small enough to sit
in cache. That noise is the part of the machine the RAM model drops. Run it
on an already sorted array instead and the ratio drops to about 2, which is
the best case showing itself.

In production, the same counting habit catches slow code before users
do. An API handler that, for each item in a request, searches a list of the
same length is doing n² work; it passes every test with 20 items and times
out with 20,000. Load tests at two or three sizes, with the ratio checked,
find this in minutes.

## 2.3 Designing algorithms

### In one sentence

Divide and conquer splits a problem into smaller copies of itself, solves
those recursively, and combines the answers; merge sort applies it to
sorting and gets Θ(n lg n).

### The idea

#### Incremental versus divide and conquer

Insertion sort is **incremental**: it builds the answer one element at a
time, keeping a correct partial answer (the sorted prefix) and extending it
by one. Many algorithms work this way, and the loop invariant is the natural
way to prove them.

The chapter's second design method is **divide and conquer**. Instead of
growing a solution, break the problem into smaller copies of itself, solve
those recursively, and combine their answers. Recursion does the heavy
lifting, and when it is applied well the total work drops dramatically.

#### The divide-and-conquer method

Every divide-and-conquer algorithm has three steps at each level of the
recursion:

<Flow steps={["Divide: split the problem into smaller subproblems", "Conquer: solve each subproblem recursively (tiny ones directly)", "Combine: merge the sub-answers into the answer"]} caption="The three steps of divide and conquer. Merge sort's divide is trivial and its combine does all the work; quicksort, in chapter 7, is the opposite." />

When a subproblem is small enough, the recursion **bottoms out**: it is
solved directly, without further splitting. That is the **base case**. For
merge sort, a subarray of one element is already sorted, so the base case
does nothing at all.

For sorting the subarray from index p to index r:

- **Divide**: find the midpoint q, halfway between p and r.
- **Conquer**: sort the two halves, p to q and q + 1 to r, recursively.
- **Combine**: merge the two sorted halves into one sorted run from p to r.

### Worked example

#### Merging two sorted halves

The combine step is where the algorithm's idea lives. Picture two face-up
piles of cards on the table, each sorted with its smallest card on top. To
merge them, look at the two top cards, take the smaller one and put it face
down on the output pile, and repeat. When one pile runs out, put the rest of
the other pile on the output. Each step is one comparison and one move, so
merging n cards in total takes time proportional to n.

```ts
// merge.ts — merge sorted a[p..q] and a[q+1..r] into sorted a[p..r].
export function merge(a: number[], p: number, q: number, r: number): void {
  const left = a.slice(p, q + 1);        // copy of the first sorted half
  const right = a.slice(q + 1, r + 1);   // copy of the second sorted half
  let i = 0;                             // next unused card in left
  let j = 0;                             // next unused card in right
  let k = p;                             // next slot to fill in a
  while (i < left.length && j < right.length) {
    if (left[i] <= right[j]) a[k++] = left[i++];   // ties go to the left
    else a[k++] = right[j++];
  }
  while (i < left.length) a[k++] = left[i++];      // one pile ran out:
  while (j < right.length) a[k++] = right[j++];    // copy the rest
}
```

The copies `left` and `right` exist because the output overwrites the same
slots the inputs came from. Without them, writing `a[k]` could destroy a
card not yet read. That extra memory, proportional to n, is merge sort's
main cost compared with insertion sort.

**Why merge is correct.** Its loop invariant: at the start of each iteration
of the main loop, `a[p..k-1]` holds the k − p smallest elements of `left` and
`right` together, in sorted order, and `left[i]` and `right[j]` are the
smallest elements of their piles not yet copied. Initially k = p, the output
is empty, and i = j = 0 point at the two smallest cards: true. Each iteration
copies the smaller of the two tops, which is the smallest element not yet
copied anywhere, onto the end of the output, so the output stays the
smallest elements in order: maintained. When one pile is empty the
remaining cards of the other pile are all at least as big as everything
output, and already sorted, so copying them finishes the job: termination.

**Why ties go left.** When `left[i]` equals `right[j]`, taking from the left
keeps equal elements in their original order, since every left element came
before every right element in the input. That property is called
**stability**, and it costs nothing here: it is the difference between
`<=` and `<` in one line.

#### Merge sort

```ts
// merge-sort.ts — sorts a[p..r] in place (using merge's temporary copies).
import { merge } from './merge';

export function mergeSort(a: number[], p = 0, r = a.length - 1): number[] {
  if (p < r) {                            // two or more elements
    const q = Math.floor((p + r) / 2);    // divide
    mergeSort(a, p, q);                   // conquer the left half
    mergeSort(a, q + 1, r);               // conquer the right half
    merge(a, p, q, r);                    // combine
  }
  return a;                               // zero or one element: done
}

console.log(mergeSort([12, 3, 7, 9, 14, 6, 11, 2]));
```

```text
[ 2, 3, 6, 7, 9, 11, 12, 14 ]
```

The base case is hidden in the `if`: a subarray with p equal to r has one
element and is returned untouched. An empty array has r = −1, so the test
fails and it is returned untouched too.

The recursion splits all the way down before any merging happens. Drawn as a
tree, the splitting goes down and the merging comes back up:

Correctness follows from merge's correctness by induction on the size of
the subarray. A subarray of size one is sorted. If merge sort correctly
sorts every subarray smaller than size m, then on a subarray of size m it
sorts both halves (each smaller than m) and merges two sorted halves, which
gives a sorted result.

### Step by step

#### Analysing divide and conquer: recurrences

A loop's cost is a sum. A recursive algorithm's cost is described by an
equation that refers to itself, a **recurrence**: the time on a problem of
size n, in terms of the time on smaller problems.

For a divide-and-conquer algorithm that splits a problem of size n into a
subproblems, each of size n/b, the recurrence has the general shape:

`T(n) = constant,  if n is small enough to solve directly`
`T(n) = a·T(n/b) + D(n) + C(n),  otherwise`

where D(n) is the time to divide and C(n) the time to combine.

For merge sort:

- **Divide** computes a midpoint: constant time, so D(n) is Θ(1).
- **Conquer** solves two subproblems of size n/2: that is 2·T(n/2).
- **Combine** merges n elements: C(n) is Θ(n).

Adding a constant to a linear term leaves a linear term, so:

`T(n) = c,  if n = 1`
`T(n) = 2·T(n/2) + c·n,  if n > 1`

(The halves are really the floor and ceiling of n/2 when n is odd. The
chapter, and this page, assume n is a power of two to keep the algebra
clean; the answer does not change.)

#### Solving it with a recursion tree

Expand the recurrence as a tree. The root costs c·n, the merge at the top.
It has two children, each a problem of size n/2 costing c·n/2 for its own
merge. Each of those has two children of size n/4, costing c·n/4. And so on,
until the subproblems have size 1 and cost c each.

<Figure art={`
  level      nodes     cost per node      cost of the level
  -----      -----     -------------      -----------------
    0          1         c·n                  c·n
    1          2         c·n/2                c·n
    2          4         c·n/4                c·n
    .          .           .                   .
    i         2^i        c·n/2^i              c·n
    .          .           .                   .
   lg n        n         c (base case)        c·n
                                           ----------------
                         (lg n + 1) levels × c·n each
                         total = c·n·lg n + c·n
`} caption="The recursion tree for merge sort. Each level halves the problem size and doubles the number of problems, so every level costs the same c·n, and there are lg n + 1 levels." />

Two facts make this work. First, every level costs the same: level i has
2ⁱ problems of size n/2ⁱ, and 2ⁱ times c·n/2ⁱ is c·n. Second, the number of
levels is lg n + 1, where lg means the base-2 logarithm: halving n repeatedly
reaches 1 after lg n halvings, and the tree has one level for each size from
n down to 1. (A tree for one element has one level, and lg 1 + 1 is 1; going
from n to 2n adds exactly one level. That is an induction you can check.)

So the total is c·n·(lg n + 1) = c·n·lg n + c·n. Drop the lower-order term
and the constant: merge sort runs in **Θ(n lg n)** time, in every case. It
does the same splitting and merging whether the input is sorted, reversed or
random.

To check the closed form directly, take the simplest version of the
recurrence: T(2) = 2 and T(n) = 2·T(n/2) + n for n a power of two greater
than 2. Claim: T(n) = n lg n. For n = 2: 2 · lg 2 = 2. True. Suppose it holds
for n/2, so T(n/2) = (n/2)·lg(n/2) = (n/2)(lg n − 1). Then T(n) = 2·(n/2)(lg n − 1)
+ n = n lg n − n + n = n lg n. True for all powers of two. Chapter 4 of the
book gives general methods, including the master method, for solving
recurrences like this without drawing the tree.

### Common mistake

The classic merge sort bug is a base case that never fires. If the split
for a two-element range produces a two-element half (for example by using
`Math.ceil` for the midpoint and recursing on p to q), the recursion never
shrinks and the stack overflows. The fix is to check that both halves are
strictly smaller than the whole for every size from 2 upward, and the
easiest check is a test on arrays of length 0, 1, 2 and 3.

The other classic is merging in place without copies: writing into `a[k]`
overwrites an element of the right half that has not been read yet. The
output then contains duplicates of some values and loses others. Copy the
halves first, as `merge` does, or use a separate output buffer.

### In real systems

#### Why n lg n beats n², and when it does not

lg n grows very slowly: it is about 10 at a thousand, 20 at a million and 30
at a billion. So n lg n is "n, times a small number", while n² is "n, times
n". For large inputs merge sort wins by an enormous margin, whatever the
constants.

For small inputs the constants decide, and they favour insertion sort: it
has no recursion, no temporary arrays and a very tight inner loop. Below
some size, which depends on the machine and is best found by measuring,
insertion sort is faster. The practical answer is a **hybrid**: merge sort
that switches to insertion sort when a subarray gets small. Production sorts
do exactly this. Timsort, the algorithm behind Python's sort and V8's
`Array.prototype.sort`, finds already sorted runs in the input, extends short
ones with a binary insertion sort, and merges the runs.

  ["online: can sort items as they arrive", "needs all the items before it starts"],

Merge itself is everywhere in production. Databases merge sorted runs
when a sort spills to disk, LSM-tree storage engines merge sorted files
during compaction, and a search service merges result lists that each shard
has already sorted by score. The system design level below walks through
these.

## From beginner to strategy

<Levels label="Chapter 2, Getting Started">
<Level name="Beginner" depth={3}>

At the smallest level this chapter is about two ways to put a list in
order, and about the habit of being exact. Insertion sort keeps a sorted
"hand" at the front of the array and inserts each new element into it. Merge
sort cuts the array in half, sorts each half, and merges them.

The smallest thing that works is insertion sort on five numbers, done on
paper. Write `4 1 3 5 2`. Pick up 1: it is smaller than 4, so 4 shifts and
you get `1 4 3 5 2`. Pick up 3: shift 4, stop at 1, `1 3 4 5 2`. Pick up 5:
nothing shifts. Pick up 2: shift 5, 4 and 3, stop at 1, `1 2 3 4 5`. Five
lines of paper, and you have run the algorithm and counted its work (1 + 1 +
0 + 3 = 5 shifts, which is the number of inversions in `4 1 3 5 2`).

The beginner's mistake is to think the code is the hard part. It is eight
lines. The hard part, and the part the chapter really teaches, is saying
precisely what the code guarantees ("the front of the array is the original
front, sorted") and checking that the guarantee survives every step. If I
can say that sentence, I understand insertion sort; if I can only recite the
code, I do not.

</Level>
<Level name="Intermediate" depth={3}>

In a real program I sort records, not numbers, and I sort them by a rule I
choose. That means a generic function with a comparator, which is also how
JavaScript's built-in sort works.

```ts
// A comparator returns a negative number, zero or a positive number.
type Cmp<T> = (x: T, y: T) => number;

export function insertionSortBy<T>(a: T[], cmp: Cmp<T>): T[] {
  for (let j = 1; j < a.length; j++) {
    const key = a[j];
    let i = j - 1;
    while (i >= 0 && cmp(a[i], key) > 0) { a[i + 1] = a[i]; i--; }
    a[i + 1] = key;
  }
  return a;
}

const orders = [
  { id: 'a', total: 30 }, { id: 'b', total: 10 },
  { id: 'c', total: 30 }, { id: 'd', total: 20 },
];
console.log(insertionSortBy(orders, (x, y) => x.total - y.total).map((o) => o.id).join(' '));
```

```text
b d a c
```

Orders a and c have the same total, and they come out in their original
order, a before c. That is stability, and it lets me sort by several keys:
sort by the secondary key first, then stably by the primary key, and ties on
the primary key stay ordered by the secondary.

The common mistake here is a comparator that returns a boolean, like
`(x, y) => x.total > y.total`. In a `> 0` test, `true` becomes 1 and `false`
becomes 0, so "less than" and "equal" look the same. My insertion sort
happens to survive that, but the built-in `Array.prototype.sort` does not:
it may never move an element left, and the result depends on the engine.
Always return a number: `x.total - y.total` for numbers, `a.localeCompare(b)`
for strings.

</Level>
<Level name="Advanced" depth={3}>

Underneath, the chapter rests on three exact results. Insertion sort's
running time is Θ(n + I), where I is the number of inversions, so its worst
case is Θ(n²) (I is at most n(n − 1)/2) and its best case Θ(n). Merge sort
satisfies T(n) = 2T(n/2) + Θ(n), whose solution is Θ(n lg n) in every case.
And both are correct by loop-invariant and induction arguments that hold for
every input, not just tested ones.

The inversion result explains a lot. Any algorithm that only ever swaps
*adjacent* elements removes at most one inversion per swap, so on a reversed
array it needs n(n − 1)/2 swaps: every such algorithm (bubble sort, insertion
sort, gnome sort) is quadratic in the worst case. To beat n², an algorithm
must move elements long distances in one step, which merge sort does when it
merges. Chapter 8 of the book proves a stronger fact: any sort that only
compares elements needs on the order of n lg n comparisons in the worst
case, so merge sort's order of growth is the best a comparison sort can do.

Precision about the model matters at this level. "Θ(n lg n)" counts RAM
steps, and it assumes comparing two keys is constant time. Comparing two
strings of length m takes up to m steps, so sorting n strings is really
about n lg n · m in the worst case. The analysis is only as good as the
model's assumptions about the primitive operations.

The common mistake: reading Θ(n lg n) as "always faster than Θ(n²)". It is a
statement about growth, for large enough n. On ten elements the quadratic
algorithm with small constants usually wins, which is why the hybrid exists.

</Level>
<Level name="Edge cases" depth={3}>

Each of these is one boundary, with what actually happens.

- **Empty array.** Insertion sort's outer loop never runs (1 is not less
  than 0). Merge sort is called with r = −1, the test `p < r` fails, and the
  empty array is returned. Both are correct; check that your own port is.
- **One element.** Same: nothing runs. A recursive sort that splits a
  one-element array into a one-element half and an empty half, instead of
  stopping, recurses forever.
- **All elements equal.** Insertion sort is in its best case: every inner
  test fails at once, linear time. Merge sort still does all its work. With
  `>=` instead of `>` insertion sort would shift every element every time
  and hit its worst case on an array of equal values.
- **Already sorted.** Insertion sort is linear; merge sort is n lg n.
- **Reverse sorted.** Insertion sort's worst case, n(n − 1)/2 shifts.
- **Two elements.** Merge sort's smallest real merge: one comparison. A good
  unit test, since off-by-one errors in the midpoint show up here first.
- **JavaScript's default sort.** `[10, 9, 1].sort()` returns `[1, 10, 9]`,
  because without a comparator the elements are compared as strings. Every
  number sort needs `(a, b) => a - b`.

The mistake to avoid is testing only random arrays. Random arrays almost
never contain these boundaries, and they are exactly where the bugs are.

</Level>
<Level name="Corner cases" depth={3}>

Corner cases are two boundaries at once, or a boundary plus a side effect.

**NaN in the input.** Every comparison with `NaN` is false. In insertion
sort, `a[i] > key` is false whenever either side is `NaN`, so a `NaN` acts
as a wall nothing can move past. Run `insertionSort([3, NaN, 1])`: the key
`NaN` does not move, then the key 1 stops at the wall, and the result is
`[3, NaN, 1]`, not sorted, with no error. The fix is to decide what `NaN`
means first (filter it out, or define it as largest) and enforce that in the
comparator.

**Duplicates plus a comparator that breaks stability.** Sorting by total
with a merge that uses `<` instead of `<=` sends ties to the right half, so
equal records swap order. On data without duplicates every test passes; on
real data, sorted twice for a two-key ordering, the result is subtly wrong.

**A huge array plus a fixed-width midpoint.** In languages with 32-bit
integers, `(p + r) / 2` overflows when p + r exceeds about two billion, and
the midpoint becomes negative. This bug sat for years in widely used binary
search code. JavaScript numbers are exact up to 2⁵³, so it does not bite in
TypeScript, but when porting to Java, C or Rust write `p + (r − p) / 2`.

**An inconsistent comparator plus a sort that trusts it.** A comparator that
uses random numbers, or says x before y and y before x, breaks the
invariants every sort relies on. Merge sort will still terminate, but the
output is garbage; some library sorts may produce different garbage on
different engines.

**Mutation during the sort.** A comparator that changes the array, or
another piece of code that changes it mid-sort (an event handler, in a UI),
breaks the "same elements" half of the invariant. Sort a copy when anything
else can touch the array.

</Level>
<Level name="Production level" depth={3}>

In production I almost never write either algorithm; I call the library
sort. What I need from this chapter is to know what that library sort does
and where it bites.

**What the built-in does.** Since ES2019 the language requires
`Array.prototype.sort` to be stable, and V8 implements it with Timsort, a
merge sort hybrid that exploits existing sorted runs and uses insertion sort
on short ones. So the chapter's two algorithms are both inside every
`.sort()` call I make in Node or Chrome.

**In-place mutation.** `sort()` sorts the array in place and returns the
same array. In React or any shared state, sorting a prop or a store value in
place mutates someone else's data. Use `toSorted()` (ES2023) or
`[...xs].sort(cmp)` to sort a copy.

**Memory.** Merge-based sorts need extra memory proportional to n. Sorting
a few million objects in a Node process means a few million extra
references during the sort. For data that does not fit in memory at all,
the answer is the chapter's merge, scaled up: an external merge sort (see
system design, below).

**Comparator cost.** The sort calls the comparator about n lg n times. A
comparator that creates objects, parses dates or calls `localeCompare`
without a shared `Intl.Collator` does that work n lg n times. Precompute the
key once per element, sort by the precomputed key, and drop it.

**Locale.** Sorting user-facing names with `<` sorts by UTF-16 code unit:
"Zoë" lands before "alex" because capitals come first. Use
`new Intl.Collator(locale).compare` as the comparator.

The production mistake is the quadratic algorithm hiding in "simple" code:
inserting into a sorted array one item at a time with `splice` inside a loop
is insertion sort, and it is quadratic. It is fine for a hundred items and
painful for a hundred thousand. Collect, then sort once.

</Level>
<Level name="Mindset" depth={3}>

The habit this chapter teaches is **state the guarantee, then check it
survives every step**. A loop invariant is not a ritual for textbooks. It is
the sentence I should be able to say about any loop I write: "at the top of
this loop, the accumulator holds the total of the rows seen so far", "at
the top of this loop, every item before the cursor has been sent". If I
cannot say it, I do not understand my loop, and a bug is likely.

The second habit is **count before you measure**. Before profiling, ask how
many times the inner line runs as a function of the input size. A nested
loop over the same list is a quadratic; a loop that halves its range is a
logarithm. That count tells me which inputs will hurt before any user finds
them.

The third is **design beats tuning**. No amount of micro-optimising insertion
sort's inner loop makes it n lg n. Changing the design does. When something
is slow, first ask whether the algorithm's shape is wrong.

The mindset mistake is treating correctness as "the tests pass". Tests check
the inputs I thought of. An invariant argument covers every input, and a
property test that checks the invariant on thousands of random and boundary
inputs is the practical middle ground.

</Level>
<Level name="System design" depth={3}>

Merge, the combine step of merge sort, is one of the most important
operations in real systems, because it works on data that arrives in sorted
pieces and never fits in memory at once.

**External sorting in databases.** When a query sorts more rows than its
memory budget allows, a database sorts chunks that fit in memory, writes each
sorted chunk to disk as a run, and then merges the runs. PostgreSQL reports
this in `EXPLAIN ANALYZE` as a sort method of "external merge" with the disk
space used. The chapter's merge, generalised from two piles to many, is
exactly that final step.

<Flow steps={["Rows arrive", "Sort chunks that fit in memory", "Write sorted runs to disk", "k-way merge of the runs", "Stream sorted rows out"]} caption="External merge sort: the shape a database uses when an ORDER BY does not fit in memory. Each run is sorted in memory; the merge reads every run once." />

**Log-structured storage.** LSM-tree databases and search engines keep data
in sorted files and periodically merge them (compaction). Each merge reads
the files in order and writes one sorted file, in time linear in the data,
which is why the storage engine can keep up with heavy writes.

**Distributed systems.** Batch frameworks sort data by key on each machine
and then merge sorted streams from many machines, so that all records with
the same key arrive together. A service that combines results from several
shards, each already sorted by score, does a k-way merge with a heap
(chapter 6) instead of re-sorting everything.

**Where insertion sort sits.** Insertion sort is the right tool when data
arrives one item at a time into an already sorted, small collection: a
leaderboard of the top 10, a short priority list in a UI. For large
collections the same "keep it sorted as items arrive" job belongs to a
balanced tree or a heap.

The design mistake is sorting at the wrong layer: pulling a million rows
into the application to sort them, when the database can sort with an index
or an external merge, or sorting a whole result to show the first page.
Ask for the top k, and let the layer that has the data do the merge.

</Level>
<Level name="Strategy" depth={3}>

No. Memorise the ideas: the sorted hand for insertion sort, the two piles

<details>
<summary>Why learn insertion sort if I will always call the library sort?</summary>

Because the library sort contains it, because the quadratic pattern shows
up in ordinary code (insert into a sorted list inside a loop), and because
it is the simplest place to learn invariants and step counting, which I use
on every loop I write.

</details>

<details>
<summary>Is the RAM model too unrealistic to be useful?</summary>

It is deliberately unrealistic about constants and memory, and realistic
about growth. It tells me whether doubling the input doubles or quadruples
the time, which is the question that decides whether a system survives
growth. The constants I get from measuring.

</details>

<details>
<summary>What does lg mean, and why base 2?</summary>

lg n is the base-2 logarithm: how many times n can be halved before it
reaches 1. It is base 2 because the algorithms halve. Logarithms in
different bases differ by a constant factor, so the order of growth is the
same.

</details>

## Key takeaways

- An algorithm is correct only if it halts with the right output on every input, not just the tested ones.
- A loop invariant is proved with initialization, maintenance and termination, and termination is where it yields the result.
- Insertion sort does one shift per inversion, so it is linear on sorted input and quadratic on reversed input.
- The RAM model counts steps; it predicts how cost grows, not how many milliseconds it takes.
- Worst-case analysis is a guarantee, and for insertion sort the average case is quadratic too.
- Order of growth keeps only the leading term, so Θ(n lg n) beats Θ(n²) for large enough n.
- Divide and conquer splits, recurses and combines; merge sort's recurrence T(n) = 2T(n/2) + Θ(n) solves to Θ(n lg n).
- Real sorts combine both algorithms, and merge is a building block of databases and storage engines.

## Glossary

- **Algorithm**: a well-defined procedure that turns an input into an output.
- **Instance**: one particular input to a problem.
- **Correct**: halts with the right output on every instance.
- **Key**: the value a sort compares; **satellite data** is the rest of the record that moves with it.
- **Permutation**: a rearrangement of the same elements.
- **Loop invariant**: a statement true at the start of every iteration of a loop.
- **Initialization, maintenance, termination**: the three steps of an invariant proof.
- **Stable sort**: a sort that keeps equal keys in their original order.
- **In place**: using only a constant amount of memory beyond the input.
- **RAM model**: an imaginary computer where each simple instruction and each memory access costs a constant.
- **Running time**: the number of primitive steps on a particular input.
- **Best, worst, average case**: the least, the most, and the expected running time over inputs of size n.
- **Inversion**: a pair of positions where the earlier element is bigger than the later one.
- **Order of growth**: the leading term of the running time with its constant dropped.
- **Θ (theta)**: "grows like", up to constant factors, for large n (made precise in chapter 3).
- **Incremental design**: building the answer one element at a time.
- **Divide and conquer**: split into subproblems, solve them recursively, combine.
- **Base case**: a subproblem small enough to solve directly.
- **Recurrence**: an equation giving a function's value in terms of its value on smaller inputs.
- **Recursion tree**: a drawing of a recurrence's expansion, used to add up its cost level by level.
- **lg n**: the base-2 logarithm of n.

## Exercises and self-check

These are my own exercises, in my own words. The book has its own at the end
of each section and the chapter's problems; do some of those too.

**Warm-up (by hand)**

1. Trace insertion sort on `31 41 59 26 41 58`, one row per pass, and count
   the shifts. Then count the inversions directly and check they match.
2. Merge `1 5 9` with `2 3 4 10 11` by hand. How many comparisons? Why is
   it fewer than the total number of elements?
3. Draw merge sort's recursion tree for 6 elements (not a power of two).
   Which levels are incomplete?

**Build (code and tests)**

4. Change `insertionSort` to sort in **non-increasing** order. Which single
   character changes? Write the new loop invariant.
5. Add counters to both sorts for comparisons and moves. Check: n − 1
   comparisons on sorted input for insertion sort; n(n − 1)/2 shifts on
   reversed input.
6. Write a hybrid merge sort that switches to insertion sort below a
   threshold. Measure thresholds of 4, 8, 16, 32 and 64 with the doubling
   script, and find the best one on your machine.
7. Write a function that counts inversions in Θ(n lg n) by modifying merge:
   when you take from the right half, every element still in the left half
   forms an inversion with it.

**Stretch (change the problem)**

8. Binary insertion sort finds the key's position with binary search. Does it
   change the worst-case running time? Count comparisons and moves
   separately before answering.
9. Write a bottom-up merge sort with no recursion: merge runs of size 1,
   then 2, then 4. Why does it do the same work as the recursive one?
10. Your merge sort must sort 50 GB of log lines on a machine with 2 GB of
    memory. Sketch the plan, and say how many times each line is read from
    disk.

**Self-check**

<details>
<summary>1. What are the three parts of a loop invariant argument, and which one uses the invariant to prove the result?</summary>

Initialization (true before the first iteration), maintenance (an iteration
keeps it true), termination (when the loop stops, the invariant plus the
stopping condition gives the result). Termination is where it proves the
result.

</details>

<details>
<summary>2. Why is "the prefix is sorted" too weak as insertion sort's invariant?</summary>

It does not say the prefix holds the original elements, so it cannot rule
out an algorithm that overwrites the array with sorted garbage, such as all
zeros. The invariant must also preserve the contents.

</details>

<details>
<summary>3. What is the best-case input for insertion sort, and its running time?</summary>

An already sorted array (or all equal elements, with a strict comparison).
Every inner test fails at once, so the running time is linear, Θ(n).

</details>

<details>
<summary>4. Why is insertion sort's average case still quadratic?</summary>

On a random array each key moves past about half of the sorted prefix, so
the work is about half the worst case. Half of a quadratic is still a
quadratic.

</details>

<details>
<summary>5. Write merge sort's recurrence and its solution.</summary>

T(n) = 2T(n/2) + Θ(n) for n greater than 1, with T(1) constant. The
recursion tree has lg n + 1 levels each costing about c·n, so T(n) is
Θ(n lg n).

</details>

<details>
<summary>6. Which one-character change makes merge sort unstable?</summary>

Using a strict comparison, `left[i] < right[j]`, in the merge. Ties then go
to the right half, so equal elements swap their original order.

</details>

<details>
<summary>7. Why do real sorting libraries still use insertion sort?</summary>

It has tiny constant factors and is linear on nearly sorted input, so it is
faster than merge sort on small pieces. Hybrids such as Timsort use it for
short runs and merge the runs.

</details>

<details>
<summary>8. What happens when you run my insertion sort on [3, NaN, 1]?</summary>

The result is `[3, NaN, 1]`, unchanged and unsorted. Every comparison with
NaN is false, so NaN blocks all shifting past it. Decide how to handle NaN
before sorting.

</details>
