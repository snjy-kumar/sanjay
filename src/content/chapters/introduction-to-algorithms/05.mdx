Chapters 2 to 4 measured algorithms by their worst case. This chapter
adds a second lens: the average over random inputs, and the expected cost
when the algorithm itself flips coins. It builds one small tool, the
indicator random variable, and shows how far that tool goes: from a toy
hiring problem to shared birthdays, hash collisions, the longest run of
heads and when to stop interviewing. Quicksort, hashing and selection in
later chapters all lean on this one.

A few probability words, defined once. A **random variable** is a number
determined by the outcome of a random experiment, such as the number of
hires. Its **expectation** E[X], or expected value, is the average of X
weighted by probability: the long-run average if you repeated the
experiment many times. Two events are **independent** if knowing one
happened does not change the probability of the other. And a **uniform
random permutation** is an ordering chosen so that every one of the n!
orderings is equally likely.

## 5.1 The hiring problem

### In one sentence

If you interview candidates in some order and hire each one who beats
everyone seen so far, the number of hires depends entirely on the order:
one in the best case, n in the worst, and about ln n on a random order.

### The idea

#### The setup

The book's running example is a hiring process. You need an office
assistant. An agency sends one candidate per day. You interview each
one, at a small cost, and if the candidate is better than your current
assistant, you fire the current one and hire the new one, at a large
cost. You want to always have the best person seen so far, and you want
to know what that policy costs.

The algorithm is a single loop: keep track of the best so far, and for
each candidate, if they beat the best, hire them and update the best. It
is the same loop as finding the maximum of an array, and the book uses
it for exactly that reason: the structure is trivial, so all the
interest is in counting how often the "hire" branch runs.

#### The cost model

Say interviewing costs c_i and hiring costs c_h, with c_h much bigger.
With n candidates and m hires, the total cost is c_i·n + c_h·m. The
interview part is fixed: everyone gets interviewed. The hiring part
depends on m, and m depends on the order. So the analysis is about m.

This cost model is a general pattern, not just a story: the loop always
reads every element (cheap, fixed) and occasionally does an expensive
update (costly, data-dependent). Updating a displayed maximum, writing a
new record to disk, or re-rendering a leaderboard when the top score
changes all fit it.

#### Worst case, best case, and the case in between

If the candidates arrive in strictly increasing order of quality, every
one beats the previous, and you hire all n: cost c_h·n. If the best
arrives first, you hire once. Neither tells you what to expect. To say
something about a typical run, you need an assumption about the order,
and the book introduces the two ways to get one.

**Probabilistic analysis** assumes a distribution on the inputs, here
that the candidates arrive in a uniformly random order, and computes the
expected cost over that distribution. The result is an **average-case
running time**. Its weakness is the assumption: if real inputs are not
random, the average does not apply.

A **randomized algorithm** removes the assumption by making the
randomness itself. Instead of trusting the agency to send candidates in a
random order, you get the whole list and shuffle it yourself. Now the
order is random by construction, whatever the agency does. The result is
an **expected running time**, and it holds for every input.

#### Ranks, and what "random order" means

To talk about order, give each candidate a **rank** from 1 to n, with
higher rank meaning better. The input is then a list of ranks, which is a
permutation of 1 to n. "The candidates arrive in random order" means
this list is a uniform random permutation: each of the n! orderings is
equally likely. Equivalently, each candidate is equally likely to be any
of the n ranks, and any subset of them is equally likely to be in any
relative order.

### Worked example

#### A simple example: five candidates

With ranks in the order 3, 1, 4, 2, 5: hire 3 (first is always hired),
skip 1, hire 4, skip 2, hire 5. Three hires. In the order 5, 4, 3, 2, 1:
one hire. In the order 1, 2, 3, 4, 5: five hires. Over all 120 orderings
of five candidates, the average turns out to be 1 + 1/2 + 1/3 + 1/4 + 1/5,
about 2.28, which section 5.2 proves.

#### A realistic example: simulating it

I simulated the policy on shuffled orders, using a seeded random number
generator so the output is reproducible:

```ts
// hiring.ts (excerpt): count hires on an order; average over shuffled orders.
function hires(order: number[]): number {
  let best = -Infinity, count = 0;
  for (const score of order) if (score > best) { best = score; count++; }
  return count;
}
const H = (n: number) => { let s = 0; for (let k = 1; k <= n; k++) s += 1 / k; return s; };
// for each n: average hires(shuffle(0..n-1)) over 2,000 trials
```

```text
n=10  average hires=2.951  H_n=2.929  ln n=2.303
n=100  average hires=5.192  H_n=5.187  ln n=4.605
n=1000  average hires=7.548  H_n=7.485  ln n=6.908
n=10000  average hires=9.722  H_n=9.788  ln n=9.210
sorted ascending, n=1000: 1000 hires
sorted descending, n=1000: 1 hire
```

The average matches the harmonic number H_n = 1 + 1/2 + ... + 1/n almost
exactly, and H_n is close to ln n (it is ln n plus about 0.58). Ten
thousand candidates, fewer than ten hires on average. But the last two
lines are the warning: a sorted input gives 1,000 hires. The average
says nothing about a specific adversarial input.

The last column's rule is the key observation for section 5.2:
candidate i is hired exactly when candidate i is the best among the first
i candidates. Whether that happens has nothing to do with candidates
after i.

### Common mistake

The common mistake is to quote the average as a guarantee: "hiring costs
about c_h·ln n". That is true only if the order is random. If the agency
sends candidates in increasing quality, perhaps because it saves the best
for last, the cost is c_h·n. The fix is either to state the assumption
explicitly or to remove it by shuffling (section 5.3).

A second mistake is in the simulation itself: averaging over orders made
with a broken shuffle. A biased shuffle produces a biased average, and
the mistake is invisible unless you test the shuffle separately, which
section 5.3 does.

### In real systems

The pattern "cheap scan, expensive update when a new best appears" is
everywhere. A monitoring dashboard that redraws when a new maximum
latency arrives; a game server that broadcasts when the high score
changes; a streaming job that writes a checkpoint when a new record value
is seen. On random-looking data these updates are rare, logarithmic in
the stream length. On a trending metric (latency creeping up) every
sample is a new maximum, and the "rare" path runs every time. Capacity
planning based on the average breaks exactly when the data trends.

## 5.2 Indicator random variables

### In one sentence

An indicator random variable is 1 when an event happens and 0 when it
does not, so its expectation is the event's probability, and because
expectations add, you can count anything by summing probabilities.

### The idea

#### The definition

For an event A, the **indicator random variable** I(A) is 1 if A occurs
and 0 if it does not. The book writes it with braces; I use parentheses
here. The one fact you need about it is the lemma that the expected value
of I(A) equals the probability of A. The proof is one line: E[I(A)] =
1·Pr(A) + 0·Pr(not A) = Pr(A).

That lemma looks too simple to matter. Its power comes from combining it
with the next fact.

#### Linearity of expectation

**Linearity of expectation** says that the expectation of a sum is the
sum of the expectations: E[X + Y] = E[X] + E[Y], for any random variables
X and Y, whether or not they are independent. This is the fact people
forget, because many probability rules (multiplying probabilities, for
example) need independence. Linearity does not.

Put the two together and you get a method. To find the expected value of
a count X, write X as a sum of indicators, X = X₁ + X₂ + ... + X_n, where
X_i is 1 when "thing i happens". Then E[X] is the sum of Pr(thing i
happens). You never need the full distribution of X, which is usually
hard; you only need n individual probabilities, which are usually easy.

#### Solving the hiring problem

Let X be the number of hires, and let X_i be the indicator that
candidate i is hired. Then X = X₁ + ... + X_n and E[X] is the sum of
Pr(candidate i is hired).

Candidate i is hired exactly when candidate i is the best of the first i.
In a uniform random order, each of those first i candidates is equally
likely to be the best of the group. So the probability is 1/i. Adding up,
E[X] = 1 + 1/2 + 1/3 + ... + 1/n = H_n, the n-th **harmonic number**,
which is ln n + O(1). The expected hiring cost is O(c_h·ln n), compared
with O(c_h·n) in the worst case.

Notice what did not happen. The events "candidate 3 is hired" and
"candidate 7 is hired" are not obviously independent, and we never had to
find out. Linearity did not care.

### Worked example

#### A simple example: two dice

What is the expected sum of two fair dice? Without indicators: average
over 36 outcomes. With linearity: the expected value of one die is
(1 + 2 + ... + 6)/6 = 3.5, so two dice give 7. My simulation of 100,000
rolls agrees (6.984). The point is how little work linearity needs.

#### A simple example: heads in n flips

The expected number of heads in n fair coin flips: let X_i be the
indicator that flip i is heads, with E[X_i] = 1/2. So the expected count
is n/2. The book uses this exact example to introduce the method,
because it shows that linearity gives the answer without the binomial
distribution.

#### A realistic example: fixed points and inversions of a shuffle

Two questions about a uniform random permutation p of 0 to n − 1. How
many positions i have p[i] = i (fixed points)? And how many pairs i, j
with i before j have p[i] greater than p[j] (inversions)?

Fixed points: let X_i be the indicator that p[i] = i. In a uniform
permutation, p[i] is equally likely to be any of the n values, so
Pr(p[i] = i) = 1/n. Summing n of them: expected fixed points = 1,
whatever n is.

Inversions: for each of the n(n − 1)/2 pairs, the indicator that the pair
is inverted has probability 1/2, by symmetry (swapping the two values
gives another permutation, equally likely). Expected inversions:
n(n − 1)/4. This is the number that matters for insertion sort from
chapter 2, whose shifts equal the number of inversions. So insertion
sort's average case is Θ(n²): about half the worst case.

```ts
// indicators.ts (excerpt): count fixed points and inversions over shuffles.
for (let i = 0; i < n; i++) if (p[i] === i) fixed++;
for (let i = 0; i < n; i++) for (let j = i + 1; j < n; j++) if (p[i] > p[j]) inv++;
```

```text
n=5  fixed points avg=0.975 (predict 1)  inversions avg=5.0 (predict 5.0)
n=50  fixed points avg=1.034 (predict 1)  inversions avg=614.2 (predict 612.5)
n=500  fixed points avg=0.994 (predict 1)  inversions avg=skipped (predict 62375.0)
two dice average sum=6.984 (predict 7)
```

The predictions came from one line of reasoning each, and the simulation
of 4,000 shuffles lands within sampling noise of them.

#### A realistic example: insertion sort's average case, exactly

Chapter 2 counted insertion sort's work in the worst case. Indicators
give the average just as quickly. Every shift in insertion sort moves one
larger element past a smaller one that started after it, so the number
of shifts equals the number of inversions in the input. On a uniform
random permutation that is n(n − 1)/4 on average, as computed above. Add
the n − 1 key comparisons that end each pass, and the expected number of
comparisons is about n²/4 + n.

The consequence matters more than the formula. Random input is not the
"easy" case for insertion sort; it costs half the worst case, still
Θ(n²). Only nearly sorted input, with few inversions, is fast. That is
why library sorts use insertion sort only for short runs or for data
already known to be almost in order.

Step 5 deserves one more sentence. "Random order" means every relative
ordering of any subset is equally likely. The first i candidates are a
subset; their best is equally likely to be in any of the i positions;
the chance it is the last of those positions is 1/i.

### Common mistake

The common mistake is to multiply where you should add, or to believe
linearity needs independence. Someone computing the expected number of
hires might try to find the probability of "exactly k hires", which is
hard, and give up. The fix is to remember that linearity works on any
sum, so you never need the joint distribution for an expectation.

The opposite mistake is to use linearity for something that is not an
expectation. Linearity gives E[X]; it does not give the probability that
X is large, or the variance. "Expected hires is ln n" does not mean
"hires are almost never more than 2 ln n"; that needs a different tool
(a tail bound). The fix is to say "in expectation" and stop there unless
you have proved a tail bound.

### In real systems

Indicators are the standard way to reason about expected load. Expected
number of cache misses: the sum over requests of the probability each
misses. Expected number of servers hit by a fan-out request: the sum over
servers of the probability each is touched. Expected number of hash
collisions: the sum over pairs of the probability the pair collides,
which section 5.4 and chapter 11 use. Each is one line once you think in
indicators.

## 5.3 Randomized algorithms

### In one sentence

Shuffle the input yourself before running the algorithm, and the
average-case analysis becomes an expected-case guarantee that holds for
every input.

### The idea

#### Moving the randomness inside

In section 5.2 the ln n result needed the candidates to arrive in random
order. A **randomized algorithm** is one whose behaviour depends on the
input and on values produced by a random-number generator. For hiring,
the randomized version first permutes the list of candidates randomly,
then runs the same loop. Now the expected number of hires is H_n for
every input, because the loop always sees a random order.

The book makes a careful distinction in wording. For the deterministic
algorithm on random inputs, we speak of the average-case cost. For the
randomized algorithm on any input, we speak of the expected cost. The
numbers are the same here; the guarantees are different. No particular
input makes the randomized algorithm slow. Only an unlucky sequence of
random numbers can.

#### Randomly permuting an array

The randomized hiring algorithm needs a way to produce a uniform random
permutation. The book gives the standard in-place method, often called
the **Fisher-Yates shuffle** (or Knuth shuffle): for each position from
the first to the last, swap the element there with an element chosen
uniformly from that position to the end. Its running time is Θ(n), and
each step uses one call to the random-number generator.

I write it walking from the end to the front, which is the same
algorithm mirrored: for i from n − 1 down to 1, pick j uniformly from 0 to
i inclusive and swap a[i] with a[j]. Position i is then final.

#### Why it is uniform: the loop invariant

The book proves uniformity with a loop invariant, the chapter 2 tool. To
state it, define a **k-permutation** of n elements as a sequence of k of
them in a particular order; there are n!/(n − k)! of them. The invariant,
in my backward version, is: after placing the last k positions, the
sequence in those k positions is equally likely to be any k-permutation
of the n elements.

- **Initialization.** Before any step, k = 0. The empty sequence is the
  only 0-permutation, so it has probability 1, which is 1 over the count
  of 0-permutations. True.
- **Maintenance.** Suppose the last k positions hold any particular
  k-permutation with probability (n − k)!/n!. The next step picks one of
  the n − k remaining elements uniformly, probability 1/(n − k), and puts
  it in the next position. The probability of any particular
  (k + 1)-permutation is the product, (n − k − 1)!/n!, which is exactly 1
  over the number of (k + 1)-permutations. True for k + 1.
- **Termination.** At k = n, every n-permutation, which is every full
  permutation, has probability 0!/n! = 1/n!. Uniform.

#### Generating random numbers

The book assumes a primitive that returns an integer chosen uniformly
from a range, with each call independent. Real code has to build that
from what the platform offers. `Math.random()` returns a float in the
range from 0 up to but not including 1, so `Math.floor(Math.random() * m)`
gives 0 to m − 1, with a tiny bias for huge m. For anything adversarial
(a lottery, a security token), `crypto.getRandomValues` is the right
source. For tests and simulations, a seeded generator makes runs
repeatable, which is why every simulation on this page uses one.

### Worked example

#### A simple example: shuffling three items

With three items there are 3! = 6 orders. A uniform shuffle produces each
one with probability 1/6. Fisher-Yates makes 3 choices for i = 2 and 2
for i = 1: 3 × 2 = 6 equally likely paths, one per permutation. That
counting argument is the invariant in miniature.

#### A realistic example: four shuffles, three of them broken

I ran four shuffles 600,000 times each on the list a, b, c, counting
each resulting order, with a chi-squared statistic measuring distance
from uniform (around 5 is normal for six categories; hundreds or more
means biased):

```ts
// shuffles.ts (excerpt): randInt(r, lo, hi) is inclusive at both ends.
const fisherYates = a => { for (let i = a.length - 1; i > 0; i--) { const j = randInt(r, 0, i); [a[i], a[j]] = [a[j], a[i]]; } return a; };
const offByOne    = a => { for (let i = a.length - 1; i > 0; i--) { const j = randInt(r, 0, i - 1); [a[i], a[j]] = [a[j], a[i]]; } return a; };
const swapAny     = a => { for (let i = 0; i < a.length; i++) { const j = randInt(r, 0, a.length - 1); [a[i], a[j]] = [a[j], a[i]]; } return a; };
const sortRandom  = a => a.sort(() => r() - 0.5);
```

Fisher-Yates is flat. The off-by-one version, which never lets an element
stay in place, produces only the two cyclic rotations; it is a known
algorithm (Sattolo's) for random cycles, but it is not a shuffle.
"Swap each position with any position" makes 3³ = 27 equally likely
paths, and 27 is not divisible by 6, so it cannot be uniform: three
orders come up about 11 percent more often. Sorting with a random
comparator is badly skewed, and the exact skew depends on the engine's
sort algorithm.

#### A realistic example: sampling a stream with a reservoir

The same uniformity argument solves a problem that comes up constantly in
logging and analytics: keep a uniform random sample of k items from a
stream whose length you do not know in advance, using only k slots of
memory. The method, usually called **reservoir sampling**, keeps the
first k items, then for the i-th item picks a random position from 0 to
i − 1 and, if it falls inside the reservoir, replaces that slot.

```ts
// reservoir.ts: a uniform sample of k items from a stream of unknown length.
function reservoir<T>(stream: Iterable<T>, k: number): T[] {
  const kept: T[] = []; let seen = 0;
  for (const item of stream) {
    seen++;
    if (kept.length < k) kept.push(item);
    else { const j = randInt(r, 0, seen - 1); if (j < k) kept[j] = item; }
  }
  return kept;
}
```

Running it 100,000 times with k = 3 on the stream 0 to 9, each item
should be kept 3/10 of the time, 30,000 times:

```text
times each of 0..9 was kept (expect 30000):
29775 30074 30010 29968 29955 30154 29889 30119 30002 30054
```

The proof is an invariant in the same style as Fisher-Yates: after seeing
i items, each of them is in the reservoir with probability k/i. The i-th
item enters with probability k/i. An item already in the reservoir
survives step i unless it is the slot chosen, which happens with
probability (k/i)·(1/k) = 1/i, so it stays with probability (i − 1)/i,
and k/(i − 1) times (i − 1)/i is k/i. The invariant holds for i + 1,
and at the end every item is kept with probability k/n.

### Common mistake

The mistakes are the three broken shuffles above: the off-by-one range,
the swap-with-anything loop and the random comparator. All three look
plausible and pass a casual eyeball test. The fix is to use Fisher-Yates
exactly (j ranges from the start of the pool to i inclusive) and to test
any shuffle with a frequency count on a small input, as I did.

A second mistake is randomizing an algorithm with a generator that an
adversary can predict. If an attacker knows the seed, the "random"
choices are fixed, and the worst case is back. The fix is a
non-deterministic seed for production and a fixed seed only for tests.

### In real systems

Randomization is the standard defence against adversarial inputs.
Language runtimes randomize hash seeds so attackers cannot craft keys
that all collide (hash flooding). Load balancers pick servers at random,
often choosing the less loaded of two random picks. Retry logic adds
random jitter so that clients that failed together do not retry
together. Card games, A/B test assignment and sampling for analytics
need a uniform shuffle or sample, and a biased one quietly corrupts every
result built on it.

## 5.4 Probabilistic analysis and further uses of indicator random variables

### In one sentence

The same indicator-and-linearity method answers four classic questions:
when do collisions appear, how long until every bin is hit, how long is
the longest run, and when should you stop looking and commit.

### The idea

This section is a set of four applications. Each one is famous on its
own, and each one turns up in real engineering under another name. I take
them in the book's order and give each its own heading.

#### The birthday paradox

How many people must be in a room before it is likely that two share a
birthday? Assume n = 365 equally likely birthdays, independent across
people. The answer, 23, surprises nearly everyone, which is why it is
called a paradox. The book gives two analyses.

The **exact analysis** computes the probability that all k birthdays are
distinct: the second person avoids the first with probability (n − 1)/n,
the third avoids both with (n − 2)/n, and so on. Multiply them. The
product drops below 1/2 at k = 23. A bound using 1 + x ≤ e^x shows the
product is at most e^(−k(k−1)/2n), so a shared birthday becomes likely
once k(k − 1) is about 2n ln 2, giving k close to √(2n ln 2).

The **indicator analysis** asks a different, easier question: the
expected number of pairs that share a birthday. For each of the
k(k − 1)/2 pairs, the indicator "this pair shares" has probability 1/n.
So the expected number of shared pairs is k(k − 1)/(2n). That reaches 1
when k is about √(2n), which for 365 is 28. The two answers differ a
little because they answer different questions, but both say the same
thing: collisions start around √n, not around n.

#### Balls and bins

Toss balls one at a time into b bins, each toss landing in a uniformly
random bin, independently. How many tosses until every bin has at least
one ball? This is also the **coupon collector's problem**: how many
cereal boxes until you have all b different coupons.

Split the process into stages. Stage i begins when i − 1 bins are
occupied and ends when a new bin is hit. During stage i, each toss hits a
new bin with probability (b − i + 1)/b. The number of tosses in the
stage is a geometric random variable, with expectation b/(b − i + 1).
Adding the stages by linearity: b/b + b/(b − 1) + ... + b/1 = b·H_b,
which is about b ln b. Filling the last few bins is slow, because almost
every toss lands in an already-full bin.

#### Streaks

Flip a fair coin n times. How long is the longest run of consecutive
heads? The answer is Θ(lg n), and the book proves both directions.

For the upper bound, a run of length k starting at a given position has
probability 2^(−k). With k = 2⌈lg n⌉ that is at most 1/n². There are at
most n starting positions, so by adding (a union bound, which is linearity
for probabilities), the chance of any such run is at most 1/n. So runs
longer than about 2 lg n are rare.

For the lower bound, cut the n flips into blocks of length about
(lg n)/2. Each block is all heads with probability about 1/√n, and there
are about 2n/lg n blocks, independent of each other. The chance that
every block fails is tiny, so a run of length about (lg n)/2 almost
certainly exists. Together: the longest streak is Θ(lg n). The finer
analysis puts the expected longest run close to lg n itself.

#### The online hiring problem

Back to hiring, with a new rule: you may hire only once, and you must
decide about each candidate right after the interview, with no going
back. You want to maximise the chance of hiring the very best candidate.
This is an **online problem**: decisions are made as the input arrives,
without seeing the future.

The strategy the book analyses: interview and reject the first k
candidates, remembering the best score among them. Then hire the first
later candidate who beats that score (or the last candidate, if none
does). What k maximises the chance of hiring the best?

The best candidate is at position i with probability 1/n. If i is at
most k, we rejected them: failure. If i is after k, we hire them exactly
when no candidate between k + 1 and i − 1 beat the first k's best; that
happens when the best of the first i − 1 is among the first k, which has
probability k/(i − 1). Summing over i from k + 1 to n gives
(k/n)·(1/k + 1/(k + 1) + ... + 1/(n − 1)), which is about (k/n)·ln(n/k).
Maximising over k by calculus gives k = n/e, and the success probability
is then about 1/e, roughly 0.37.

#### A simple example: the birthday numbers

Exact probabilities of a shared birthday among k people with 365 days:

```text

k=20  P(shared, n=365)=0.4114
k=23  P(shared, n=365)=0.5073
k=30  P(shared, n=365)=0.7063
```

The simulation of 100,000 rooms of 23 people agrees with the exact
product. At 70 people a shared birthday is close to certain.

#### A realistic example: hash collisions

Replace "365 days" with "n possible hash values" and "people" with
"items hashed". The birthday bound says collisions become likely around
√n items. I computed the 50 percent point for three hash widths, using
the exponential approximation:

```ts
// birthday.ts (excerpt): smallest k with 1 - exp(-k(k-1)/2n) >= 0.5, by binary search.
const n = 2 ** bits; let lo = 1, hi = 2 ** 40;
while (hi - lo > 1) {
  const mid = Math.floor((lo + hi) / 2);
  if (1 - Math.exp(-mid * (mid - 1) / (2 * n)) >= 0.5) hi = mid; else lo = mid;
}
```

```text
16-bit hashes: 50% collision chance at about 302 items (sqrt(n)=256)
32-bit hashes: 50% collision chance at about 77,164 items (sqrt(n)=65,536)
64-bit hashes: 50% collision chance at about 5,056,937,542 items (sqrt(n)=4,294,967,296)
```

A 32-bit hash used as a unique ID collides with even odds after only
about 77 thousand items, out of four billion possible values. That is
why unique identifiers use 128 bits, and why "the hash is 32 bits, so
collisions are one in four billion" is a dangerous sentence.

#### A realistic example: filling every bin

```text
b=10  average tosses=29.2  b*H_b=29.3  b ln b=23.0
b=100  average tosses=512.6  b*H_b=518.7  b ln b=460.5
b=1000  average tosses=7486.4  b*H_b=7485.5  b ln b=6907.8
```

The simulated average matches b·H_b, and b ln b is a slight
underestimate (H_b is ln b plus about 0.58). To have every one of 1,000
shards receive at least one random request takes about 7,500 requests
on average, not 1,000.

#### A realistic example: streaks and stopping

```text

n=1024  lg n=10  average longest streak=9.20  largest seen=17
n=16384  lg n=14  average longest streak=13.49  largest seen=23
n=262144  lg n=18  average longest streak=17.36  largest seen=26
```

#### The online hiring sum, line by line

1. Let S be the event of hiring the best, and S_i the event that the best
   is at position i and we hire them. S is the union of the S_i, which are
   disjoint, so Pr(S) is the sum of Pr(S_i).
2. For i at most k, Pr(S_i) = 0: the best was in the look-only phase.
3. For i after k, S_i needs two things: the best is at i (probability
   1/n), and nobody at positions k + 1 to i − 1 was hired. The second
   holds exactly when the best of positions 1 to i − 1 lies in the first
   k, probability k/(i − 1). These two events are independent, because
   where the overall best sits says nothing about the relative order of
   the others.
4. So Pr(S) is the sum over i from k + 1 to n of (1/n)·(k/(i − 1)) =
   (k/n)·(H_(n−1) − H_(k−1)).
5. Bounding the harmonic difference by integrals gives about
   (k/n)·(ln n − ln k).
6. Differentiate with respect to k and set to zero: (ln n − ln k − 1)/n
   = 0, so ln k = ln n − 1, k = n/e. Substituting back gives 1/e.

The bound in step 4 is the formula my hash-collision code used. It is an
upper bound on the chance of no collision, so it gives a lower bound on
the chance of a collision: at 23 people at least about 50 percent, which
the exact product (0.5073) confirms. The same three lines work for any
n, which is why "collisions at about √n" is safe to use as a rule.

### Common mistake

The common birthday mistake is to compare k with n instead of √n: "with
365 days, you need about 180 people for even odds". The pairs grow like
k², which is why collisions arrive at √n. The fix is to always count
pairs.

The common streak mistake is to see a run of 15 identical outcomes in a
log and conclude something is broken. In a few hundred thousand
independent events, runs of that length are normal; the longest run is
about lg n. The fix is to compare with lg n before raising an alarm.

The common online-hiring mistake is to read 1/e as "37 percent of the
time you get a good candidate". It is the chance of getting the single
best one. The strategy often gets a near-best candidate otherwise. And if
too few candidates are rejected (k = 1), success drops to about 5 percent
in my simulation.

### In real systems

Every one of these is an engineering tool. The birthday bound sets hash
and ID widths: 64-bit IDs for millions of items, 128 bits for global
uniqueness. Balls and bins describes random load balancing: with n
requests on n servers, the most loaded server gets about ln n / ln ln n
requests, which is why "pick the less loaded of two random servers"
helps so much. Streaks tell an on-call engineer how many failures in a
row are just bad luck. And the online hiring rule, often called the
secretary problem, is a model for any one-shot decision under uncertainty,
from accepting an offer to picking a moment to sell.

## From beginner to strategy

<Levels label="Chapter 5, Probabilistic Analysis and Randomized Algorithms">
<Level name="Beginner" depth={3}>

At the beginner level, this chapter is about averages. Instead of asking
"what is the slowest this can be?", you ask "what does it cost on a
typical input?" or "what does it cost on average when the algorithm makes
random choices?". Both questions need probability, and the chapter uses
only a little of it.

A smallest worked example: roll one die until you see a six. On average,
how many rolls? Each roll succeeds with probability 1/6, and a waiting
time with success chance p has expectation 1/p, so the answer is 6. That
"1/p" fact is the same one used for each stage of the coupon collector.

The beginner's mistake is to treat an average as a promise. Six rolls on
average does not mean six rolls every time; sometimes it takes twenty.
State averages as averages, and if you need a guarantee, ask a different
question: how likely is it to take more than twice the average?

</Level>
<Level name="Intermediate" depth={3}>

At the intermediate level, you can compute expectations with indicators
fluently. Given any "expected number of X", you write X as a sum of
0-or-1 variables, find each one's probability and add. The examples on
this page, hires, fixed points, inversions, shared birthday pairs, empty
bins, all took one paragraph each.

A worked example in code: the expected number of times a running maximum
changes as a stream arrives, which is the hiring problem in disguise. I
use it to size the write rate of a "new record" table:

```ts
// expected record-breaking events in a random stream of n values
const expectedRecords = (n: number) => { let s = 0; for (let i = 1; i <= n; i++) s += 1 / i; return s; };
console.log(expectedRecords(1_000_000).toFixed(2)); // 14.39
```

A million random readings, about 14 writes. The mistake is to trust this
for a trending series. The fix is to check the input really looks random,
or to accept that the write rate can be n.

</Level>
<Level name="Advanced" depth={3}>

At the advanced level, you can prove the results and you know their
limits. You can prove Fisher-Yates uniform with the k-permutation
invariant, prove that a shuffle with n^n equally likely paths cannot be
uniform, derive H_n for hiring and b·H_b for the coupon collector, and
carry out both directions of the streak bound.

A worked derivation: the probability that a specific run of k heads
starts at a given flip is 2^(−k). For the upper bound on streaks, take
k = 2⌈lg n⌉, so each start has probability at most 1/n². There are at
most n starts, and Boole's inequality (the probability of a union is at
most the sum of the probabilities) gives at most 1/n. This is the union
bound, the probability version of linearity, and it is the most-used tail
tool in algorithm analysis.

The advanced mistake is to apply linearity of expectation to a
non-linear function. E[X²] is not E[X]², and E[max(X, Y)] is not
max(E[X], E[Y]). The expected longest streak is not "the longest
expected streak". The fix is to use indicators only for counts, and
tail bounds for maxima.

</Level>
<Level name="Edge cases" depth={3}>

Edge cases are single boundaries. The first is n = 1. The hiring loop
hires once; H₁ = 1. Fisher-Yates on one element does nothing, which is
correct. The online hiring rule with k = 0 hires the first candidate,
success probability 1/n; with n = 1 that is certain.

The second is ties. The hiring analysis assumed distinct ranks. If scores
can tie and the rule is "hire if strictly better", ties never cause a
hire, and the expected count drops. If the rule is "at least as good",
equal scores each trigger a hire, and a stream of identical values
triggers n hires. The fix is to decide the tie rule explicitly, and to
break ties by a secondary key (arrival time) if you want the analysis to
hold.

The third is the random-number range. `Math.floor(Math.random() * (i + 1))`
gives 0 to i inclusive. Writing `i` instead of `i + 1` is the off-by-one
shuffle. Writing `Math.round` instead of `Math.floor` gives the two end
values half the probability of the others. Each is one character away from
correct, and only a frequency test catches it.

</Level>
<Level name="Corner cases" depth={3}>

Corner cases combine two boundaries. One: a randomized algorithm with a
fixed seed in production. Each run uses the same "random" sequence, so
an input that is bad for that sequence is bad every time, and an attacker
who learns the seed can construct it. The expected-cost guarantee is
gone. The fix is a fresh seed per process from a real entropy source,
with the seed logged so a failure can be replayed.

Two: shuffling a very large array with a weak generator. A generator
with a 32-bit state can produce at most about four billion distinct
sequences, but 13 items already have 13! (over six billion) orders, and a
deck of 52 cards has about 8 × 10^67. So most permutations of a large
array are simply unreachable. The shuffle code is correct; the
generator is too small. The fix, when uniformity really matters, is a
generator with a large state or the cryptographic source.

Three: the birthday bound with non-uniform values. If hash values are not
uniform (a poor hash, or keys with structure), collisions come earlier
than √n. Indicator analysis assumed each pair collides with probability
1/n; a skewed hash makes some pairs far more likely. The fix is to use a
well-mixed hash and to measure the collision rate on real keys.

</Level>
<Level name="Production level" depth={3}>

In production, randomization is a defence and a tool for load. Runtimes
randomize hash seeds per process so that keys crafted to collide on one
machine do not collide on another. Quicksort implementations pick random
or pseudo-random pivots so a sorted input is not the worst case. Retry
policies add random jitter so a thousand clients do not retry in the
same millisecond.

The second production concern is reproducibility. Randomness makes bugs
hard to replay. The working practice is: seed from entropy, log the
seed, and allow a seed override for debugging. Every simulation on this
page uses a fixed seed for exactly that reason, so the numbers above are
the numbers you get.

The third is monitoring with expectations. An expected count gives a
baseline: about ln n new maximums, about √n items before a collision,
about lg n for the longest streak of failures. When the observed number
is far above the expectation, something non-random is happening: a
trending input, a bad hash, correlated failures. Those are the alerts
worth having.

</Level>
<Level name="Mindset" depth={3}>

The habit this chapter teaches is: when a count is hard, break it into
yes-or-no pieces and add their probabilities. It turns many hard
questions into easy ones, and it works in planning and estimating, not
only in proofs. "How many of our 200 services will have an incident this
quarter?" is a sum of 200 indicators.

The second habit is to ask who controls the input. If an adversary does,
or if real data might be sorted, trending or structured, an average-case
result is weak. Moving the randomness into the algorithm turns it into a
guarantee. That question, "is the randomness mine or theirs?", is the
chapter's real lesson.

The mistake in mindset is to treat randomness as a substitute for
analysis: "we'll randomize it and it'll be fine". Randomization gives a
good expected cost only when you have proved it for the randomized
algorithm. The fix is to state what is random, what the expectation is
over, and what bound you proved.

</Level>
<Level name="System design" depth={3}>

In system design, these results set numbers. The birthday bound decides
ID and hash widths: a service that generates ten million IDs a day with
a 32-bit random ID will see collisions within the first hour. With
64-bit IDs, the 50 percent point is about five billion items, so a
long-lived high-volume system still needs collision handling or 128-bit
IDs.

Balls and bins decides sharding. Hashing keys to shards places them like
balls in bins, and the most loaded shard runs noticeably above the
average. A concrete example: a cache cluster of 100 nodes with random
key placement. Some node will hold noticeably more than 1 percent of
keys, and that node sets the cluster's capacity. Consistent hashing with
virtual nodes, or the power of two random choices, narrows the spread.

The design mistake is sizing from the average alone. The fix is to plan
for the expected maximum, not the expected mean, wherever the maximum
sets the limit: the hottest shard, the longest queue, the longest streak
of failures before a circuit breaker opens.

</Level>
<Level name="Strategy" depth={3}>

My strategy is to pair every derivation with a simulation. For each
result in the chapter, I write the one-paragraph indicator argument, then
a twenty-line simulation with a seeded generator, and I do not move on
until the two agree within sampling noise. When they disagree, either my
argument or my code is wrong, and finding which is the real learning.

I learn the four applications of 5.4 as tools with names and one-line
answers: collisions at √n, all bins at b ln b, longest streak lg n, stop
after n/e. Then I practise recognising them in disguise: hash IDs,
shards, failure runs and one-shot choices.

Done when I can, without notes: compute E[hires] = H_n with indicators,
prove Fisher-Yates uniform with the invariant, prove the swap-with-any
shuffle biased by counting, give the birthday bound both ways, derive
b·H_b for the coupon collector, and explain why k = n/e in the online
hiring problem, with a simulation to back each one.

</Level>
</Levels>

## Questions people ask

<details>
<summary>Is a randomized algorithm the same as a probabilistic analysis?</summary>

No. Probabilistic analysis studies a deterministic algorithm on random
inputs and gives an average-case cost that depends on the input
assumption. A randomized algorithm makes its own random choices and gives
an expected cost that holds for every input.

</details>

<details>
<summary>Why does the book care so much about the hiring problem?</summary>

Because it is the simplest loop whose cost depends on order, so all the
attention goes to the probability. The same analysis gives the number of
times a running maximum changes, which shows up in quicksort's and
selection's analyses later.

</details>

<details>
<summary>Is Math.random good enough for a shuffle?</summary>

For simulations, games and tests, yes, with Fisher-Yates. For anything
where someone benefits from predicting the order (lotteries, security
tokens, fair draws with money attached), use `crypto.getRandomValues`.
For reproducible tests, use a seeded generator.

</details>

<details>
<summary>What is wrong with sorting by a random comparator?</summary>

A comparator must be consistent: if a is less than b now, it must be
later. A random comparator breaks that contract, and the result depends
on the sort algorithm. My test of it on three items gave one order six
times as often as another.

</details>

<details>
<summary>Why is the expected number of fixed points 1 for every n?</summary>

There are n positions and each is a fixed point with probability 1/n.
By linearity, the expected count is n·(1/n) = 1. More positions, but each
less likely, exactly balancing.

</details>

paradox and balls and bins, because chapter 11's hashing analysis uses

</details>

## Key takeaways

- Probabilistic analysis averages over assumed random inputs; a randomized algorithm makes its own random choices and gives an expected cost for every input.
- An indicator random variable is 1 or 0, and its expectation is the probability of its event.
- Linearity of expectation holds for any random variables, independent or not, which makes indicators powerful.
- Hiring the best-so-far from a random order costs H_n, about ln n, hires in expectation, but n in the worst case.
- Fisher-Yates produces a uniform random permutation in Θ(n) time; its proof is a loop invariant over k-permutations.
- Off-by-one ranges, swap-with-any loops and random comparators all produce biased shuffles.
- Collisions appear around √n items among n values; filling all b bins takes about b ln b tosses.
- The longest run of heads in n flips is Θ(lg n); the best online-hiring rule looks at n/e candidates first and succeeds about 1/e of the time.

## Glossary

- **Probabilistic analysis**: analysing an algorithm's cost by assuming a probability distribution over its inputs.
- **Average-case running time**: the expected cost of a deterministic algorithm over a distribution of inputs.
- **Randomized algorithm**: an algorithm whose behaviour depends on random numbers it generates as well as on its input.
- **Expected running time**: the expected cost of a randomized algorithm on a given input, over its random choices.
- **Random variable**: a number determined by the outcome of a random experiment.
- **Expectation E[X]**: the probability-weighted average of a random variable.
- **Indicator random variable I(A)**: 1 if event A occurs, 0 otherwise; its expectation is Pr(A).
- **Linearity of expectation**: E[X + Y] = E[X] + E[Y] for any random variables.
- **Harmonic number H_n**: 1 + 1/2 + ... + 1/n, which is ln n + O(1).
- **Uniform random permutation**: an ordering where each of the n! orders is equally likely.
- **k-permutation**: an ordered sequence of k of the n elements; there are n!/(n − k)! of them.
- **Fisher-Yates shuffle**: swap each position with a uniformly chosen position from the remaining pool, inclusive.
- **Birthday paradox**: among n equally likely values, a repeat becomes likely after about √n draws.
- **Coupon collector's problem**: tossing balls into b bins until each has one takes about b ln b tosses.
- **Union bound (Boole's inequality)**: the probability of a union is at most the sum of the probabilities.
- **Online problem**: a problem where decisions must be made as the input arrives, without seeing the rest.

<summary>1. What is E[I(A)]?</summary>

Pr(A), because I(A) is 1 with probability Pr(A) and 0 otherwise.

<details>
<summary>2. Why is the probability that candidate i is hired equal to 1/i?</summary>

Candidate i is hired when they are the best of the first i, and in a

<details>
<summary>3. What does the randomized hiring algorithm do differently?</summary>

It shuffles the candidates first, so every input becomes a random order

It has 27 equally likely choice sequences, and 27 is not a multiple of 6,
