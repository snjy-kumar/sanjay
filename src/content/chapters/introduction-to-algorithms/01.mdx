This chapter answers two questions before the book teaches a single
algorithm: what exactly an algorithm is, and why anyone should care about
designing good ones when computers keep getting faster. The answers set up
the vocabulary and the attitude the other thirty-four chapters rely on.

## Before you start

**After this chapter you will be able to:**

- define an algorithm, a computational problem, an instance and a correct algorithm, in plain words and precisely;
- tell an algorithm from a heuristic, and an incorrect algorithm from a useful approximate one;
- name the main families of problems algorithms solve and the techniques the book uses for them;
- explain why a hard problem (one with no known efficient algorithm) changes what you build;
- compute, for two algorithms on two machines, the input size where the better algorithm overtakes the faster machine;
- argue why algorithms are a technology, as much as hardware, networks or databases.

**You should already know:** how to read a loop and a function in any
language, and what an array is. No maths beyond powers and logarithms. If
logarithms are rusty, read them as "how many times can I halve this
number before reaching 1".

**Reading time:** about 45 minutes to read, two sessions of an hour each
to run the code and do the exercises.

## 1.1 Algorithms

### In one sentence

An algorithm is a precisely defined procedure that takes any instance of a
problem as input and, after a finite number of steps, produces the correct
output for that instance.

### The idea

#### What counts as an algorithm

Informally, an **algorithm** is any well-defined computational procedure
that takes some value, or set of values, as **input** and produces some
value, or set of values, as **output**. It is a sequence of steps that
turns one into the other. A recipe is an algorithm for turning ingredients
into a meal; long division is an algorithm for turning two numbers into a
quotient and a remainder.

The phrase *well defined* is doing the work. Each step must be unambiguous:
two people (or two machines) following it on the same input must do the
same thing. "Add salt to taste" is not well defined. "Add 5 grams of salt"
is. Each step must also be something that can actually be carried out, and
the whole procedure must stop.

You can also see an algorithm as a tool for solving a well-specified
**computational problem**. The problem says, in general terms, what
relationship the output must have to the input. The algorithm describes a
specific procedure that achieves that relationship. The problem is the
*what*; the algorithm is the *how*. One problem usually has many
algorithms, and much of this book is about choosing between them.

#### Problems and instances

A problem is stated for all inputs at once. The **sorting problem**, for
example, says: given a sequence of n numbers, output a rearrangement of
them in non-decreasing order. Any particular input, such as the sequence
`31, 41, 59, 26, 41, 58`, is an **instance** of the problem. An instance is
everything needed to compute one answer.

This distinction matters because claims about algorithms are claims about
every instance. "My sort works" means it works on every sequence of
numbers: empty ones, single elements, sequences full of duplicates,
sequences of length ten million. Tests check instances. Proofs check the
problem.

What counts as "the input" also has to be decided. For sorting, it is the
numbers. For finding a route, it is the map plus the start and the end.
For multiplying two large numbers, it is the digits. Writing down the
input and output precisely, before writing any code, is the first step of
designing any algorithm.

#### Correctness

An algorithm is **correct** if, for every input instance, it **halts**
(finishes after a finite number of steps) with the correct output. A
correct algorithm **solves** the problem. Both halves of that definition
can fail on their own.

- It can halt with a **wrong answer** on some instance. Then it is
  incorrect, even if it is right on every instance in the test suite.
- It can **fail to halt** on some instance, looping forever. Then it is
  incorrect too, even if every answer it does produce is right.

An incorrect algorithm is not always useless. Some algorithms are wrong
with a small, controlled probability (a primality test that can be fooled
with probability less than one in a trillion), and others produce answers
that are close to optimal rather than optimal (chapter 35 is about them).
What matters is that the error is understood and bounded. An algorithm
that is wrong in ways nobody has characterised is just a bug.

#### What an algorithm can be written in

An algorithm can be written in English, as a program, or as a hardware
design. The only requirement is that the description is precise enough to
follow. The book uses pseudocode, which looks like a programming language
but skips the details (declarations, error handling, memory management)
that do not change the idea. A program is one concrete realisation of an
algorithm; the same algorithm can be written in TypeScript, C or as a
circuit.

#### What kinds of problems algorithms solve

Sorting is the book's first example, but it is far from the only problem.
The chapter surveys a range of real problems where algorithms are the core
of the solution. I group them by the kind of question they answer.

- **Matching and comparing sequences.** Biologists compare DNA strands,
  which are long strings over the four letters A, C, G and T, to find how
  related two organisms or genes are. One measure of similarity is the
  longest common subsequence: the longest sequence of letters that appears
  in both strands, in order, though not necessarily side by side. Trying
  every subsequence is hopeless; dynamic programming (chapter 14) does it
  in time proportional to the product of the lengths.
- **Finding routes.** Routers on the internet must find good paths for
  data, and a mapping service must find the shortest driving route. Both
  are shortest-path problems on graphs (chapters 22 and 23).
- **Finding information quickly.** Search engines must find the pages
  that contain a set of words among billions, which needs data structures
  such as hash tables (chapter 11) and string matching (chapter 32).
- **Keeping secrets.** Online payments rely on public-key cryptography and
  digital signatures, which rest on number theory (chapter 31).
- **Allocating scarce resources.** An airline assigning crews to flights,
  a company deciding where to place facilities, or an internet provider
  deciding where to add capacity all solve optimisation problems that can
  often be written as linear programs (chapter 29).
- **Ordering and scheduling.** Deciding the order of tasks with
  dependencies is topological sorting (chapter 20); allocating time on a
  shared resource is scheduling, often greedy (chapter 15).
- **Learning from data.** Clustering, prediction and recommendation rely
  on algorithms such as k-means and gradient descent (chapter 33).

Two characteristics are common to many of these problems. First, they have
a huge number of **candidate solutions**, most of which are not the
answer, and finding the right one without trying them all is the
challenge. Second, they have **practical applications**: the shortest path
matters because a delivery truck pays for every extra kilometre.

#### Data structures

A **data structure** is a way to store and organise data so that access
and modification are efficient. An algorithm often depends more on its
data structure than on its control flow. The duplicate check in the worked
example below is the same loop either way; what changes its cost from
quadratic to linear is storing the elements seen so far in a hash set
instead of scanning the array.

No single data structure works well for every purpose. A sorted array
gives fast search but slow insertion; a hash table gives fast insert and
lookup but no order; a balanced tree gives order and reasonably fast
everything. So it is important to know the strengths and limitations of
several, which is what Parts III and V of the book are for.

#### Technique

The book is not only a catalogue of algorithms. It teaches **techniques**
of algorithm design and analysis, so that when I meet a problem that is in
no book, I can design an algorithm for it, show that it is correct, and
understand its efficiency. The main techniques are divide and conquer
(chapters 2 and 4), randomisation (chapter 5), dynamic programming
(chapter 14), greedy choice (chapter 15) and amortised analysis (chapter
16), plus graph modelling throughout Part VI.

#### Hard problems

Most of the book is about **efficient** algorithms, which the book measures
by how long they take to produce a result. But there are problems for
which **no efficient algorithm is known**. The most famous family is the
**NP-complete** problems (chapter 34). Three facts make them interesting:

1. No efficient algorithm has ever been found for any of them, and nobody
   has proved that one cannot exist.
2. If an efficient algorithm exists for any one of them, then efficient
   algorithms exist for all of them. They stand or fall together.
3. Several of them look very similar to problems that do have efficient
   algorithms. A small change in the question moves it across the line.

Why should a working engineer care? Because if I can show that my problem
is NP-complete, I can stop searching for a fast exact algorithm and spend
my time on one that gives a good solution, not necessarily the best one.
The book's example is a delivery company planning routes for its trucks:
visiting every stop exactly once with the least total distance is the
**traveling-salesperson problem**, which is NP-complete. Real logistics
software uses approximation algorithms and heuristics (chapter 35) instead.

#### Alternative computing models

For many years processor clock speeds rose steadily, but physical limits
on power and heat stopped that. Instead of one faster core, chips now have
several cores, and programs get faster by running parts of the work in
parallel. Designing algorithms with **parallelism** in mind is the subject
of chapter 26.

There is also the question of when the input arrives. Most algorithms
assume the whole input is available at the start. **Online algorithms**
(chapter 27) receive their input over time and must make decisions
without knowing the future: a scheduler deciding which job to run next, or
a cache deciding which item to evict, does not know what requests will
come later.

### Worked example

#### A simple example: maximum of a list

Start with the smallest real problem: given a non-empty list of numbers,
return the largest. Input: a sequence of n numbers, n at least 1. Output: a
number m in the sequence such that no element is bigger than m.

Here is a procedure that looks right, and one that is right.

```ts
// max.ts — correct on the tests, wrong on an instance nobody tried.
function maxBuggy(xs: number[]): number {
  let best = 0;                         // assumes some element is >= 0
  for (const x of xs) if (x > best) best = x;
  return best;
}
function maxCorrect(xs: number[]): number {
  if (xs.length === 0) throw new RangeError('max of an empty list is undefined');
  let best = xs[0];                     // invariant: best = max of xs[0..i-1]
  for (let i = 1; i < xs.length; i++) if (xs[i] > best) best = xs[i];
  return best;
}
console.log(maxBuggy([3, 9, 4]), maxCorrect([3, 9, 4]));
console.log(maxBuggy([-5, -2, -8]), maxCorrect([-5, -2, -8]));
try { maxCorrect([]); } catch (e) { console.log((e as Error).message); }
```

```text
9 9
0 -2
max of an empty list is undefined
```

`maxBuggy` passes any test made of positive numbers. On the instance
`[-5, -2, -8]` it returns 0, which is not even in the input. By the
chapter's definition it is **incorrect**: there exists an instance where it
halts with the wrong output. The fix is to start from an element of the
input, which makes the claim "best is the largest element seen so far"
true from the first step.

The empty list is a separate question. The problem as stated excludes it
(n at least 1), so `maxCorrect` rejects it loudly instead of inventing an
answer. Deciding what the empty instance means is part of specifying the
problem, not an afterthought.

#### A realistic example: is there a duplicate?

A sign-up service must reject a batch of user ids if any id appears twice.
Input: a list of n ids. Output: true if some id occurs at least twice,
otherwise false. Two algorithms solve it, and both are correct.

```ts
// duplicates.ts — the same question, two algorithms, very different costs.
function hasDuplicateNaive(xs: number[]): { found: boolean; steps: number } {
  let steps = 0;
  for (let i = 0; i < xs.length; i++)
    for (let j = i + 1; j < xs.length; j++) {
      steps++;
      if (xs[i] === xs[j]) return { found: true, steps };
    }
  return { found: false, steps };
}
function hasDuplicateSet(xs: number[]): { found: boolean; steps: number } {
  const seen = new Set<number>();
  let steps = 0;
  for (const x of xs) {
    steps++;
    if (seen.has(x)) return { found: true, steps };
    seen.add(x);
  }
  return { found: false, steps };
}
```

The first compares every pair; the second remembers what it has seen in a
hash set. I count "steps" as comparisons for the first and set lookups for
the second, and run both on lists with no duplicates, which is the worst
case for both, because neither can stop early:

```ts
for (const n of [10, 1_000, 100_000]) {
  const xs = Array.from({ length: n }, (_, i) => i);   // no duplicates: worst case
  const a = hasDuplicateNaive(xs), b = hasDuplicateSet(xs);
  console.log(`n=${n}  naive steps=${a.steps}  set steps=${b.steps}`);
}
```

```text
n=10  naive steps=45  set steps=10
n=1000  naive steps=499500  set steps=1000
n=100000  naive steps=4999950000  set steps=100000
```

The naive version does n(n − 1)/2 comparisons: 45 for ten ids, about five
billion for a hundred thousand. On my machine that last line took about
ten seconds; the set version took a few milliseconds. Both are correct.
Only one is usable at scale. The difference is entirely a choice of data
structure.

#### A realistic example: fewest hops between routers

Routing is one of the chapter's headline applications. Here is the
smallest version: a network of routers, each connected to some
neighbours, and the question "what is the path from A to F with the
fewest hops?". Breadth-first search (chapter 20) answers it by exploring
the network in rings: everything one hop away, then two hops, and so on.

```ts
// hops.ts — fewest hops between routers, breadth-first.
type Graph = Record<string, string[]>;
function fewestHops(g: Graph, from: string, to: string): string[] | null {
  const prev = new Map<string, string | null>([[from, null]]);
  const queue = [from];
  for (let head = 0; head < queue.length; head++) {
    const u = queue[head];
    if (u === to) break;
    for (const v of g[u] ?? []) if (!prev.has(v)) { prev.set(v, u); queue.push(v); }
  }
  if (!prev.has(to)) return null;
  const path: string[] = [];
  for (let at: string | null = to; at !== null; at = prev.get(at)!) path.unshift(at);
  return path;
}
```

```ts
const net: Graph = { A: ['B', 'C'], B: ['A', 'D'], C: ['A', 'D', 'E'],
  D: ['B', 'C', 'F'], E: ['C', 'F'], F: ['D', 'E'] };
console.log(fewestHops(net, 'A', 'F'));
console.log(fewestHops({ A: ['B'], B: [], Z: [] }, 'A', 'Z'));
```


#### A realistic example: how alike are two DNA strands?

The longest common subsequence (LCS) is the similarity measure the chapter
mentions for genetics. For `GATTACA` and `GTCTAGCA`, a common subsequence
is any string you can get from both by deleting letters. The program below
fills a table where each cell holds the LCS length of two prefixes, then
walks back through the table to recover one longest subsequence. Chapter
14 explains why it works; here I only want to show that a problem with
astronomically many candidates has a fast algorithm.

```ts
// lcs.ts — length of the longest common subsequence, and one example of it.
function lcs(a: string, b: string): string {
  const m = a.length, n = b.length;
  const L = Array.from({ length: m + 1 }, () => new Array<number>(n + 1).fill(0));
  for (let i = 1; i <= m; i++)
    for (let j = 1; j <= n; j++)
      L[i][j] = a[i - 1] === b[j - 1] ? L[i - 1][j - 1] + 1 : Math.max(L[i - 1][j], L[i][j - 1]);
  let i = m, j = n, out = '';                 // walk back to recover one LCS
  while (i > 0 && j > 0) {
    if (a[i - 1] === b[j - 1]) { out = a[i - 1] + out; i--; j--; }
    else if (L[i - 1][j] >= L[i][j - 1]) i--; else j--;
  }
  return out;
}
const s = lcs('GATTACA', 'GTCTAGCA');
console.log(s, s.length);
```

```text
GTTACA 6
```

A strand of length m has 2 to the power m subsequences. For two strands of
a thousand letters each, checking every subsequence of one against the
other is beyond any computer that will ever exist. The table has about a
million cells and fills in well under a second. That gap, from impossible
to instant, is what the chapter means by an algorithm being a technology.

### Step by step

#### Walking the correctness argument for maximum

The chapter does not prove anything yet, but it asks for the attitude that
leads to proofs: *correct on every instance*. Here is what that means for
`maxCorrect`, walked line by line in plain words.

1. **The claim.** At the start of each pass of the loop with index `i`,
   `best` equals the largest of `xs[0]` through `xs[i − 1]`.
2. **Before the first pass**, `i` is 1 and `best` is `xs[0]`. The largest
   of a one-element list is that element. The claim holds.
3. **One pass.** Suppose the claim holds when a pass starts. The pass
   compares `xs[i]` with `best`. If `xs[i]` is bigger, it becomes `best`,
   which is now the largest of the first i + 1 elements. If not, `best`
   was already at least as large as `xs[i]`, so it is still the largest of
   the first i + 1 elements. Either way the claim holds for the next `i`.
4. **When the loop ends**, `i` equals n, so `best` is the largest of all n
   elements. That is exactly the required output.
5. **It halts**, because `i` increases by one per pass and stops at n.

This is the loop invariant method that chapter 2 formalises. The point
for now is that steps 2 to 4 cover every instance at once, which no
number of tests can do. `maxBuggy` fails at step 2: before the first pass,
`best` is 0, which is not the largest of anything in the input.

Why is this the fewest hops? Because the queue is first-in, first-out, the
search explores every router at distance 1 before any at distance 2, and
so on. The first time F is discovered, it is discovered from a router at
distance 2, so its distance is 3, and no shorter path can exist: a path of
two hops would have put F in the queue during ring 1. Chapter 20 turns
this into a proof.

#### Walking the duplicate-count formula

Why does the naive duplicate check do exactly n(n − 1)/2 comparisons when
there are no duplicates? The outer loop's first element is compared with
the n − 1 elements after it; the second with n − 2; and so on down to the
last-but-one, compared with 1. The total is (n − 1) + (n − 2) + ... + 1.
Write that sum forwards and backwards and add the two copies term by term:
each pair adds to n, there are n − 1 pairs, so twice the sum is n(n − 1),
and the sum is n(n − 1)/2. For n = 10 that is 45, which matches the
program's output exactly. The set version touches each element once, so n.

### Common mistake

The most common mistake is to treat "it passed my tests" as "it is
correct". `maxBuggy` passes every test written by someone who only thinks
of positive numbers. The fix is to think about the problem's instances,
not the program's tests: ask what the smallest, largest, emptiest,
most-repetitive and most-negative instances are, and check those on
purpose.

The second mistake is to confuse a problem with an algorithm. "Sorting is
n log n" is not true; *merge sort* is n log n, *insertion sort* is n² in
the worst case, and a sort that knows its keys are small integers can be
linear (chapter 8). A problem has a difficulty; each algorithm for it has
its own cost.

The third is to stop at the first algorithm that works. The duplicate
check works with nested loops. It also takes ten seconds on a hundred
thousand ids, which is a production incident waiting for a big batch.
Always ask whether a different data structure or technique changes the
cost.

### In real systems

In production, the definition of correctness becomes contracts and
property tests. A payment service's rounding function is checked not on
five amounts but on millions of generated ones, including zero, negative
refunds and the largest representable amount. Teams that adopt
property-based testing are, in effect, taking the chapter's "every
instance" seriously.

The problem families show up directly. Package managers resolve
dependencies with graph algorithms and, in the general case, with SAT
solvers, because dependency resolution with version constraints is
NP-complete. `git diff` computes a variant of the longest common
subsequence. Every TLS handshake runs number-theoretic algorithms. Ride
dispatch and delivery planning are matching and routing problems with
heuristics on top, because their exact forms are NP-hard.

Online and parallel models are the default, not the exception. A cache in
front of a database is an online algorithm: it decides what to evict
without knowing future requests. A batch job on a many-core server or a
cluster is a parallel algorithm, and its speed depends on how much of the
work can really run at once.

## 1.2 Algorithms as a technology

### In one sentence

Because computers are finite in speed and memory, the efficiency of an
algorithm is a resource like hardware, and choosing a better algorithm can
matter far more than buying a faster machine.

### The idea

#### If computers were infinitely fast

Suppose computers were infinitely fast and memory were free. Would there
be any reason to study algorithms? Yes, but a smaller one: I would still
want to show that my procedure terminates and gives the right answer. With
infinite speed any correct method would do, and I would pick the easiest
one to write.

Computers are fast, but not infinitely fast. Memory is cheap, but not
free. Network bandwidth, battery and money are limited too. Running time
and space are **bounded resources**, and algorithms that use them wisely
are worth more than ones that do not. That is the whole case for
studying efficiency.

#### Efficiency

Algorithms that solve the same problem often differ dramatically in their
efficiency. These differences can be far larger than the differences
caused by hardware or software. The chapter makes the point with the two
sorting algorithms of chapter 2:

- **Insertion sort** takes time roughly c₁·n² to sort n items, where c₁ is
  a constant that does not depend on n.
- **Merge sort** takes time roughly c₂·n·lg n, where lg n is the base-2
  logarithm and c₂ is another constant.

Insertion sort usually has a smaller constant: c₁ is less than c₂. But
constant factors matter far less than the **growth** of the other factor.
Write the two costs as c₁·n·n and c₂·n·lg n. Both share a factor of n; the
race is between n and lg n. For n = 1,000, lg n is about 10. For n equal
to a million, lg n is about 20. However large the ratio c₂ / c₁ is, once n
is big enough, n is bigger than (c₂ / c₁)·lg n, and merge sort wins.

#### The race: a fast machine against a good algorithm

The chapter stages a race between a fast computer running insertion sort
and a slow computer running merge sort. I run my own version of the race
with my own numbers, so you can check every step.

- **Machine F** (fast) executes ten billion steps per second. It runs a
  quadratic sort written by an excellent programmer in tight code: 3·n²
  steps.
- **Machine S** (slow) executes ten million steps per second, a thousand
  times slower. It runs an n lg n sort written carelessly, with a big
  constant: 60·n·lg n steps.

```ts
// crossover.ts — when does a better algorithm beat a faster machine?
const lg = (n: number) => Math.log2(n);
const fastMachine = 1e10;                  // steps per second
const slowMachine = 1e7;                   // 1,000 times slower
const quadratic = (n: number) => 3 * n * n;          // tight quadratic code
const nlogn = (n: number) => 60 * n * lg(n);         // sloppy n lg n code

for (const n of [1e3, 1e5, 1e6, 1e7, 1e8]) {
  const a = quadratic(n) / fastMachine;
  const b = nlogn(n) / slowMachine;
  console.log(`n=${n.toExponential(0)}  fast+n²: ${a.toPrecision(3)} s   slow+n lg n: ${b.toPrecision(3)} s`);
}
```

```text

n=1e+5  fast+n²: 3.00 s   slow+n lg n: 9.97 s
```

Read the rows top to bottom. For a thousand items, the fast machine wins

A machine a thousand times slower, running sloppier code, finishes in
hours what the fast machine needs a month for. No hardware upgrade closes
that gap, because the gap keeps growing with n.

#### Algorithms and other technologies

The race shows that total system performance depends on choosing
efficient algorithms as much as on choosing fast hardware. Algorithms are
a **technology** in the same sense: a thing engineers choose, compare and
invest in.

You might ask whether algorithms still matter when so much else has
improved: fast hardware with caches and pipelines, easy graphical
interfaces, object-oriented and functional languages, cloud services,
fast networks, machine learning. The chapter's answer is that every one of
those is built on algorithms. A web browser lays out a page with tree
algorithms; a compiler uses graph colouring for register allocation and
parsing algorithms for syntax; a network routes with shortest paths; a
machine-learning model is trained by gradient descent and served from
data structures. Even the design of the hardware itself used algorithms
for circuit layout and verification.

Machine learning deserves its own sentence, because it is sometimes
offered as a replacement for algorithms. It is itself a collection of
algorithms (chapter 33 covers some), and for problems that people
understand well, such as sorting, shortest paths or exact lookup, a
designed algorithm is both faster and correct by construction. Learning
helps when there is no clean specification, such as recognising images.

Finally, larger problems make the difference sharper. As computers get
faster, people use them to solve larger problems, and it is exactly at
large sizes that the difference between algorithms is most dramatic. A
solid base of algorithmic knowledge is one of the things that separates a
skilled programmer from a novice: with modern tools you can get things
done without it, but with it you can do much more.

### Worked example

#### A simple example: searching a sorted list

The simplest demonstration of algorithm as technology is search. Given a
sorted array of a million even numbers, find a target. **Linear search**
looks at each element in turn. **Binary search** looks at the middle,
discards the half that cannot contain the target, and repeats.

```ts
// search.ts — linear search versus binary search on a sorted array.
function linear(xs: number[], t: number) {
  let steps = 0;
  for (let i = 0; i < xs.length; i++) { steps++; if (xs[i] === t) return { i, steps }; }
  return { i: -1, steps };
}
function binary(xs: number[], t: number) {
  let lo = 0, hi = xs.length - 1, steps = 0;
  while (lo <= hi) {                         // t, if present, is in xs[lo..hi]
    steps++;
    const mid = lo + Math.floor((hi - lo) / 2);
    if (xs[mid] === t) return { i: mid, steps };
    if (xs[mid] < t) lo = mid + 1; else hi = mid - 1;
  }
  return { i: -1, steps };
}
```

```ts
const xs = Array.from({ length: 1_000_000 }, (_, i) => 2 * i);  // even numbers
for (const t of [0, 999_998, 1_999_998, 7]) {
  const a = linear(xs, t), b = binary(xs, t);
  console.log(`target ${t}: linear ${a.steps} steps, binary ${b.steps} steps, index ${b.i}`);
}
```

```text
target 0: linear 1 steps, binary 19 steps, index 0
target 999998: linear 500000 steps, binary 1 steps, index 499999
target 1999998: linear 1000000 steps, binary 20 steps, index 999999
target 7: linear 1000000 steps, binary 20 steps, index -1
```

Look at the first row: for the very first element, linear search wins, 1
step against 19. Look at the last row: for a missing target, linear search
must look at every element, a million steps, while binary search needs
20, because 2 to the 20th is just over a million. A million-fold larger
array would cost binary search only 20 more steps.

#### A realistic example: how big a problem fits in one second?

Turn the question around. Suppose a request handler has a budget of one
second and the machine does a billion simple steps per second. How large
an input can each kind of algorithm handle within the budget? I computed
it rather than guessed:

```ts
// budget.ts — largest n that fits in one second at 1e9 steps per second.
const budget = 1e9;

  ['n', (n) => n], ['n lg n', (n) => n * Math.log2(n)],
  ['n^2', (n) => n * n], ['n^3', (n) => n * n * n], ['2^n', (n) => 2 ** n],

  let lo = 1, hi = 1;
  while (f(hi) <= budget) hi *= 2;            // grow until over budget
  while (hi - lo > 1) { const m = Math.floor((lo + hi) / 2); if (f(m) <= budget) lo = m; else hi = m; }
  console.log(`${name.padEnd(7)} n = ${lo.toLocaleString('en-US')}`);
}
```

#### A realistic example: an exponential search

Subset sum is a good example of a problem whose obvious algorithm is
exponential. Given a list of numbers and a target, is there a subset that
adds up to the target? The brute-force algorithm tries every subset, and a
list of n numbers has 2ⁿ subsets.

```ts
// subset-sum.ts — brute force doubles its work with every extra item.
function subsetSum(xs: number[], target: number): { found: number[] | null; tried: number } {
  let tried = 0;
  const n = xs.length;
  for (let mask = 0; mask < 1 << n; mask++) {      // every subset, as a bit pattern
    tried++;
    let sum = 0;
    for (let i = 0; i < n; i++) if (mask & (1 << i)) sum += xs[i];
    if (sum === target) return { found: xs.filter((_, i) => mask & (1 << i)), tried };
  }
  return { found: null, tried };
}
console.log(subsetSum([8, 6, 7, 5, 3, 10, 9], 15));
```

```text
{ found: [ 8, 7 ], tried: 6 }
```

When the answer exists it may be found fast. When it does not, every
subset must be tried. I ran it with lists of even numbers and an odd
target, which can never be reached:

```text
n=10  subsets tried=1024  0 ms
n=15  subsets tried=32768  9 ms
n=20  subsets tried=1048576  75 ms
```

Each extra five items multiplies the work by 32. At 40 items it would be
about a trillion subsets, minutes or hours of work; at 60 items, longer
than anyone would wait. Subset sum is NP-complete (chapter 34), so no
known algorithm is fast on every instance, but chapter 35 shows how to get
within a chosen fraction of the best answer quickly.

### Step by step

#### Deriving the crossover point

When exactly does the slow machine start winning? The two times are equal
when 3·n² / 10¹⁰ equals 60·n·lg n / 10⁷. Walk the algebra line by line.

1. Multiply both sides by 10¹⁰: 3·n² equals 60,000·n·lg n.
2. Divide both sides by 3n (n is positive): n equals 20,000·lg n.
3. That equation has no closed-form answer in elementary functions, so
   solve it numerically. Try n = 300,000: lg n is about 18.19, and
   20,000 × 18.19 is about 363,800, which is bigger than n. The slow
   machine is still losing.
4. Try n = 400,000: lg n is about 18.61, and 20,000 × 18.61 is about
   372,200, which is smaller than n. The slow machine is winning.
5. The crossover is between them. A binary search pins it down.

```ts
// crossover-point.ts — find the smallest n where the slow machine wins.
const lg = (n: number) => Math.log2(n);
const fast = (n: number) => (3 * n * n) / 1e10;
const slow = (n: number) => (60 * n * lg(n)) / 1e7;
let lo = 2, hi = 1e9;               // slow loses at 2, wins at 1e9
while (hi - lo > 1) {               // invariant: slow(lo) >= fast(lo), slow(hi) < fast(hi)
  const mid = Math.floor((lo + hi) / 2);
  if (slow(mid) < fast(mid)) hi = mid; else lo = mid;
}
console.log(`the slow machine wins from n = ${hi}`);
```

```text
the slow machine wins from n = 369939
```

Binary search works here because, beyond a small n, the fast machine's
time minus the slow machine's time only grows: n / lg n is increasing, so
once n exceeds 20,000·lg n it stays above it. That is the same fact as
"growth beats constants", in a form a program can check.

#### Why growth beats constants, as an argument

The general claim is: for any positive constants a and b, a·n·lg n is
eventually smaller than b·n². Walk it in plain words.

1. Divide both by n: compare a·lg n with b·n.
2. Divide both by b: compare (a/b)·lg n with n.
3. lg n grows, but it grows by only 1 each time n doubles, while n itself
   doubles. So the ratio n / lg n grows without bound.
4. Therefore, however large a/b is, n / lg n eventually exceeds it, and
   from that n onward n is bigger than (a/b)·lg n.
5. Multiply back by b·n: b·n² is bigger than a·n·lg n from that point on.

Chapter 3 states this precisely with Θ, O and Ω notation. The idea is
already here: constants decide small inputs, growth decides large ones.

#### What a tenfold faster machine buys, derived

For an algorithm costing f(n) steps and a budget of B steps, the largest
input is the n where f(n) equals B. A machine ten times faster raises the
budget to 10B.

- **Linear**, f(n) = n: n goes from B to 10B. Ten times larger.
- **Quadratic**, f(n) = n²: n goes from the square root of B to the square
  root of 10B, which is the square root of 10, about 3.16, times larger.
- **Cubic**: the cube root of 10, about 2.15 times larger.
- **Exponential**, f(n) = 2ⁿ: n goes from lg B to lg(10B) = lg B + lg 10,
  which is lg B plus about 3.32. Three more items, whatever B was.

That last line is why exponential algorithms are hopeless for large
inputs. No amount of money makes them scale.

### Common mistake

The common mistake is to fix a slow system with hardware when the cause
is the algorithm. Doubling the instance size buys about 41% more input
for a quadratic hot path, and the bill doubles. If the data grows by ten
times next year, no instance size is enough. The fix is to measure how
cost grows with input size first (time it at n, 2n and 4n) and only buy
hardware when the growth is already near linear.

The opposite mistake is to optimise growth where n is small and fixed. A
settings page with twelve options does not need a balanced tree. For
small n, constants and simplicity win, as the first row of the race
shows. The fix is to know the realistic size of n, and to design for the
size it will reach, not for infinity.

### In real systems

The race is not hypothetical. A common production incident is a page that
loads in 200 milliseconds with a test account holding 50 items and times
out for a customer holding 50,000, because somewhere a list is searched
inside a loop over the same list. The fix is almost never a bigger
server; it is a hash map, an index or a join done by the database.

Databases make the algorithm-as-technology point every day. The same SQL
query can run as a nested-loop join (quadratic in the sizes of the two
tables), a hash join (linear) or a merge join (linear after sorting). The
query planner is an algorithm whose whole job is choosing algorithms, and
`EXPLAIN` shows which one it chose. Adding an index changes a full table
scan, linear in the table, into a B-tree lookup, logarithmic (chapter 18).

Cost in the cloud is literally the integral of the algorithm's cost over
all requests. A function that runs a million times a day at 300
milliseconds costs about thirty times more than one that runs in 10. An
algorithmic fix in a hot path often saves more money than any other
change a team can make, and it keeps saving as traffic grows.

## From beginner to strategy

<Levels label="Chapter 1, The Role of Algorithms in Computing">
<Level name="Beginner" depth={3}>

At the beginner level the chapter gives one sentence to hold on to: an
algorithm is a precise recipe that turns any valid input into the right
output and then stops. Everything else is detail on that sentence.

Try it on something you already do. Looking up a word in a paper
dictionary is an algorithm: open near the middle, decide whether the word
comes before or after the page you see, and repeat on the half that must
contain it. It works for every word that is in the dictionary, and it
stops with "not there" for every word that is not. That is binary search,
and with a thousand-page dictionary it never needs more than about ten
openings.

The beginner's mistake is to think an algorithm must be code. The
dictionary procedure is an algorithm written in English. The code comes
later, and a bug in the code is a different thing from a flaw in the
idea. Learn to say the idea in two sentences before writing a line.

</Level>
<Level name="Intermediate" depth={3}>

At the intermediate level the chapter's two ideas, correctness and
efficiency, meet in ordinary code. Every function I write solves a small
computational problem, and I can ask the chapter's two questions about it:
is it right on every instance, and how does its cost grow?

Take a function that merges two arrays of user ids and removes
duplicates. A first version uses `result.includes(id)` inside a loop over
both arrays. It is correct. It is also quadratic, because `includes`
scans the result each time. A second version keeps a `Set`:

```ts
function mergeUnique(a: string[], b: string[]): string[] {
  const seen = new Set<string>();
  const out: string[] = [];
  for (const id of [...a, ...b]) if (!seen.has(id)) { seen.add(id); out.push(id); }
  return out;
}
console.log(mergeUnique(['u1', 'u2'], ['u2', 'u3', 'u1']));
```

```text
[ 'u1', 'u2', 'u3' ]
```

The common intermediate mistake is to hide a linear scan inside a
convenient method (`includes`, `indexOf`, `find`, `filter`) inside a
loop. Each line looks cheap; together they are n². Read every method call
inside a loop as "how many elements does this touch?".

</Level>
<Level name="Advanced" depth={3}>

At the advanced level, the chapter's informal words get exact meanings
that the rest of the book develops. "Correct" becomes a proof obligation:
a loop invariant (chapter 2) or an induction. "Efficient" becomes a
statement about order of growth in a fixed cost model, written with Θ, O
and Ω (chapter 3). "Hard" becomes NP-completeness, a precise statement
about reductions between problems (chapter 34).

The precision matters because the informal versions mislead. "Merge sort
is faster than insertion sort" is false for small inputs. The exact claim
is: there is a constant n₀ such that for every n of at least n₀, merge
sort's worst-case cost is lower. The crossover derivation in section 1.2
is that claim with numbers attached.

Another exact rule: the size of the input must be measured honestly. An
algorithm that checks whether a number N is prime by trying every divisor
up to N is linear in N, but N is written in about lg N bits, so it is
exponential in the input size. That is why "linear time" for number
problems needs care, and why chapter 31 counts bits.

The advanced mistake is to quote a growth rate without its model. Say
what is counted (comparisons, memory accesses, bits), what the input size
is, and whether it is worst case, average case or expected.

</Level>
<Level name="Edge cases" depth={3}>

Edge cases test the "every instance" in the definition of correctness.
Each of these is one boundary, with what happens.

- **Empty input.** Maximum of an empty list has no answer. The problem
  must say so: return `undefined`, throw, or exclude it from the input
  domain. `Math.max()` in JavaScript returns `-Infinity`, which is a
  defined answer but a surprising one.
- **One element.** Many divide-and-conquer algorithms must treat it as the
  base case, or they recurse forever.
- **No solution.** The router example returns `null` for an unreachable
  router. A search that returns -1, an empty route or a "not found" must
  be part of the specification.
- **All equal values.** Duplicates break algorithms that assume distinct
  keys: a "find the second largest" that returns the largest again.
- **The largest allowed input.** If the problem allows n up to ten
  million, a quadratic algorithm that passed tests at a thousand is
  incorrect in practice: it does not halt in any useful time.

The mistake is to leave these to the tests. Write them into the problem
statement first; then the tests follow from it.

</Level>
<Level name="Corner cases" depth={3}>

Corner cases combine two boundaries, or a boundary and a side effect.

**Empty input plus a default.** `maxBuggy([])` returns 0 without
complaint, so the empty case and the "wrong initial value" bug hide each
other: a dashboard shows "maximum latency 0 ms" for a service that
received no requests. The fix is to make the empty case explicit.

**Large n plus small memory.** The LCS table for two strands of a
hundred thousand letters has ten billion cells; at 4 bytes each that is
40 GB. The algorithm is fast enough and still unusable. Chapter 14's
space-saving variant keeps only two rows when only the length is needed.

**Exponential worst case plus easy typical case.** Subset sum found its
answer after trying 6 subsets in my example. A system tested only on
inputs with answers looks fast; the first input with no answer hangs it.
Always test the "no solution" instance of an exponential search, and put
a time limit on it.

**A correct algorithm plus overflow.** Binary search's midpoint
`(lo + hi) / 2` overflows a 32-bit integer when the array has more than
about a billion elements. The algorithm is correct; the program is not.
Writing `lo + (hi - lo) / 2`, as my code does, fixes it.

</Level>
<Level name="Production level" depth={3}>

In production, the chapter's lesson becomes a habit of asking how cost
grows before it is a problem. Three practices put that into effect.

**Know the size of n.** For every hot path, know the largest realistic
input today and in a year: items in a cart, rows in a tenant's table,
nodes in a graph. A quadratic step over a list that will never pass 100
is fine. Over a list that grows with the customer base, it is a future
incident.

**Load test at several sizes.** Run the same request with 1,000, 10,000
and 100,000 items and compare the times. A tenfold step in input that
causes a hundredfold step in time is quadratic, whatever the profiler
says about individual lines.

**Prefer libraries for standard problems.** Sorting, hashing, search,
cryptography and shortest paths are solved problems with tested library
implementations. Write your own only to learn, or when the library's
assumptions do not fit, and then test against the library.

The production mistake is to answer a growth problem with capacity:
more replicas, a bigger instance. That buys a constant factor, and the
section 1.2 table shows how little a constant buys against n² or worse.

</Level>
<Level name="Mindset" depth={3}>

The mindset the chapter builds is that algorithms are **choices**, not
facts of nature. When code is slow, the question is not "how do I make
this faster?" but "is there a different procedure for this problem?".
The duplicate check, the search and the race all turned on changing the
procedure, not polishing it.

A second habit: **separate the problem from the solution.** Write down the
input, the output and the relationship between them before choosing a
method. Many slow systems are slow because they solve a harder problem
than needed: sorting everything to show the top ten, or computing exact
answers where a good approximation was acceptable.

A third: **respect hardness.** If a problem looks like scheduling with
constraints, routing through every stop, or packing items into bins, it
may be NP-hard. Recognising that early saves weeks of hunting for an
exact fast algorithm that probably does not exist.

The mindset mistake is to believe that modern hardware made all this
irrelevant. Hardware raised the ceiling on n, and people immediately
filled it with bigger n.

</Level>
<Level name="System design" depth={3}>

In system design, the chapter's ideas decide where work happens and how
it scales. Consider a product search for an online shop with ten million
items.

- **Naive design:** load all items, filter by the query string, sort by
  relevance, return the first 20. Linear in the catalogue per request, n
  lg n for the sort, and it gets slower every time the catalogue grows.
- **Algorithmic design:** an inverted index (a hash table from word to
  the list of items containing it) answers the filter in time
  proportional to the matches, and a heap of size 20 (chapter 6) keeps
  the top results without sorting all matches.

<Flow steps={["Query words", "Inverted index lookup: hash table per word", "Intersect posting lists: merge sorted lists", "Score matches", "Top-k with a heap of size k", "Return 20 results"]} caption="A product search pipeline. Each stage is a chapter of the book; none of them touches the whole catalogue per request." />

The same thinking places work in the right layer: let the database sort
with an index rather than sorting in the application; precompute
expensive results once at write time rather than at every read; push
filters to where the data lives. The system design mistake is to treat
every component as a black box with "enough capacity" and never ask what
algorithm it runs inside.

## Questions people ask

<details>
<summary>Is a heuristic an algorithm?</summary>

A heuristic is a procedure that usually gives a good answer without a
guarantee. If it is well defined and halts, it is an algorithm for some
problem, but not an algorithm that *solves* the original problem
correctly. Approximation algorithms are the middle ground: they come with
a proven bound on how far from optimal they can be.

</details>

<details>
<summary>Does every problem have an algorithm?</summary>

No. Some problems are undecidable: no algorithm solves every instance.
The classic is deciding whether an arbitrary program halts on an
arbitrary input. The book is about problems that do have algorithms, and
mostly about how efficient they can be.

</details>

<details>
<summary>If hardware keeps improving, why worry about efficiency?</summary>

Because improvement buys a constant factor and growth rates are not
constant. The table in section 1.2 shows that ten times the speed buys
ten times the input for a linear algorithm, about three times for a
quadratic one, and about three extra items for an exponential one.

</details>

<details>
<summary>Is this chapter worth reading if I already code every day?</summary>

Yes, briefly. It is short, and it names ideas I already use loosely. The
value is the precise vocabulary (instance, correct, efficient, hard) that
makes later proofs readable.

</details>

<details>
<summary>Does machine learning replace algorithm design?</summary>

No. Learning methods are algorithms themselves, and for problems with a
clear specification a designed algorithm is faster and provably correct.
Learning is the tool when no clean specification exists.

</details>

## Key takeaways

- An algorithm is a well-defined procedure that turns input into output; a program is one realisation of it.
- A problem is stated for all inputs; an instance is one input; a correct algorithm halts with the right output on every instance.
- Most real problems have huge numbers of candidate solutions, and an algorithm's job is to avoid trying them all.
- The data structure often decides the cost more than the control flow does.
- For NP-complete problems no efficient algorithm is known, so the practical answer is approximation or heuristics.
- Efficiency is a resource: a better growth rate beats a faster machine once the input is large enough.
- Faster hardware buys little against fast-growing costs: ten times the speed adds about three items to an exponential algorithm's reach.
- Every other technology, from compilers to machine learning, is built on algorithms.

## Glossary

- **Algorithm**: a well-defined procedure that takes input and produces output in a finite number of steps.
- **Computational problem**: a specification of the required relationship between input and output.
- **Instance**: one particular input to a problem.
- **Correct algorithm**: one that halts with the correct output on every instance; it solves the problem.
- **Halt**: finish after a finite number of steps.
- **Heuristic**: a procedure that usually works well but carries no guarantee.
- **Data structure**: a way to store and organise data to support efficient access and modification.
- **Technique**: a general method of algorithm design, such as divide and conquer or dynamic programming.
- **Efficient algorithm**: informally, one whose running time grows slowly with the input size; precisely, polynomial time (chapter 34).
- **NP-complete**: a family of problems with no known efficient algorithm, all of which are efficiently solvable if any one is.
- **Traveling-salesperson problem**: find the shortest tour visiting every location exactly once.
- **Longest common subsequence**: the longest sequence appearing in order, not necessarily contiguously, in two sequences.
- **Parallel algorithm**: an algorithm designed to run parts of its work at the same time on several processors.
- **Online algorithm**: an algorithm that receives its input over time and must act without knowing the future.
- **Order of growth**: how the running time increases with input size, ignoring constant factors.
- **Crossover point**: the input size beyond which one algorithm becomes cheaper than another.
- **lg n**: the base-2 logarithm of n, the number of halvings to reach 1.

## Exercises and self-check

My own exercises. The book has exercises at the end of each section and

**Build (code and tests)**

4. Change the race program so the fast machine runs 2·n² and the slow
   machine runs 100·n·lg n. Find the new crossover with the binary search
   program.
5. Write `secondLargest(xs)` and list five instances that break naive
   versions (duplicates, two elements, negatives, all equal, empty).
6. Add a time limit to the subset-sum search: stop after a given number of
   subsets and return "unknown". When is "unknown" an acceptable answer?

**Stretch (change the problem)**

7. An algorithm takes n³ steps. You can choose between a machine 8 times

8. Find a real function in code you maintain whose cost grows faster than
   linearly with an input that grows over time. Estimate when it will

**Self-check**

<details>
<summary>1. What two ways can an algorithm fail to be correct?</summary>

It can halt with a wrong output on some instance, or fail to halt on some
instance.

</details>

<details>
<summary>2. Why did the hash-set duplicate check beat the nested loop?</summary>

It remembers previously seen ids in a structure with constant-time
lookup, so it touches each element once (n steps) instead of comparing
every pair (n(n − 1)/2 steps).

</details>

<details>
<summary>3. Binary search needs at most how many steps on a million sorted items?</summary>

About 20, because 2 to the 20th is just over a million.

</details>

<details>
<summary>4. At what input size does merge sort on a slow machine overtake insertion sort on a fast one?</summary>

It depends on the constants and speeds. With my numbers it is 369,939.
The general fact is that such a crossover always exists, because n lg n
grows more slowly than n².

</details>

<details>
<summary>5. What does a tenfold faster machine do for an n² algorithm?</summary>

It lets it handle about 3.16 times larger inputs in the same time, the
square root of 10.

</details>

<details>
<summary>6. Why is knowing a problem is NP-complete useful?</summary>

It says no efficient exact algorithm is known, so the engineering effort
should go into approximations, heuristics or restricting the input.

</details>
