This chapter is about the tools every developer uses every day, whatever
the language: plain text, the shell, the editor, version control, the
debugger, small text-processing scripts and a notebook. Each topic argues
that fluency with a basic tool pays back every week for a whole career.
In my roadmap this chapter is the Phase 0 checklist itself.

## Before you start

After this chapter I will be able to:

- choose plain text for knowledge and configuration, and say when it is the wrong choice;
- combine shell commands into pipelines that answer real questions about logs and files;
- list the editor skills that save the most time, and practise them deliberately;
- use version control for everything, and find a breaking commit with `git bisect`;
- debug by method: reproduce, read, binary-search, explain, fix and test;
- write small scripts that transform text, and keep an engineering daybook.

What I should already know: how to open a terminal and run a command, and
basic JavaScript or TypeScript. The

## Topic 16. The Power of Plain Text

### In one sentence

Keep knowledge in plain, human-readable text, because every tool can read
it, diff it, search it and version it, for decades.

### The idea

Plain text means printable characters that a person can read directly:
source code, Markdown, JSON, YAML, CSV, log lines. Its opposite is a binary
format, where the bytes only make sense to the program that wrote them.
The book's argument is that knowledge, meaning configuration, data,
documentation and notes, belongs in plain text.

The reasons are practical. Plain text is insurance against obsolescence:
a file readable today will be readable in thirty years, while a binary
format dies with its program. It gives leverage, because every tool,
from `grep` to `git diff` to an editor, works on it. And it is easier to
test and debug, because I can see it, change it by hand and compare it.

The book's best advice is to make plain text self-describing. A line
reading `47` tells me nothing; `retry_limit=47` tells me what it is. A
format with field names, like JSON, survives even when the program that
wrote it is gone.

Plain text has costs. It can be larger than binary and slower to parse, and
some data, like images, has no sensible text form. The answer is usually
plain text for knowledge and configuration, and binary only where size or
speed truly demands it, with a text way to inspect it.

### Worked example

**Simple.** Two ways to store a retry setting.

<Compare left="Opaque" right="Self-describing plain text" caption="The same setting stored two ways. Look at the right column: a stranger can understand and safely edit it." rows={[
  ["A binary settings blob only the app can read", "retry_limit = 5 in a text config file"],
  ["A bare number 5 on line 7", "a named key with a comment saying why 5"],
  ["Diff shows 'binary files differ'", "Diff shows exactly which value changed"],
  ["Needs the app to inspect", "Readable with any viewer, searchable with grep"],
]} />

**Realistic.** A team stores feature flags in a database table edited
through an admin page. When a bad flag change causes an outage, nobody can
tell who changed what, or when. Moving the flags to a YAML file in the
repository, deployed through the pipeline, gives history, review and
rollback for free: `git log flags.yaml` answers the question in a second.

### Step by step

Choosing a storage format for a piece of knowledge:

1. **Ask who needs to read it.** If a person ever does, prefer text.
2. **Ask how long it lives.** The longer, the stronger the case for text.
3. **Name each field.** Self-describing beats positional.
4. **Check size and speed needs.** Only switch to binary with evidence.
5. **If binary, provide a text view.** A dump command, or a schema.

<Flow caption="The plain-text decision. Follow the questions; most knowledge ends at the third box." steps={[
  "Will a person read or edit it?",
  "Must it outlive this program?",
  "Use self-describing plain text",
  "Size or speed truly demand binary?",
  "Binary plus a text dump tool",
]} />

A second worked example shows the "lowest common denominator" argument.
Two services written in different languages, by different teams, must
share a list of supported currencies. A JSON file in a shared repository
is something both can read with their standard library, and a person can
review a change to it in a pull request. A binary format would need a
shared library in both languages and would make reviews impossible.

Testing also gets easier. If a program reads and writes plain text, a test
can be a pair of files: input and expected output. A failing test then
shows a readable diff, which points straight at the wrong line. That style
of test, sometimes called a golden-file or snapshot test, only works
because the format is text.

### Common mistake

The common mistake is plain text without self-description: CSV without a
header, a config of bare numbers in fixed positions. It is technically
text but practically opaque. The fix is named fields, a header row, or a
schema next to the file.

Another mistake is assuming all text is the same. Encodings (UTF-8 versus
others) and line endings (LF versus CRLF) break tools quietly. The fix is
to standardise on UTF-8 and LF, and enforce it in the repository.

### In real systems

Infrastructure as code, configuration in Git, structured JSON logs and
Markdown documentation are this topic in production. Even systems that use
binary protocols internally, such as protobuf, keep the schema in plain
text and offer text dumps for debugging.

### Check yourself

**Why is `retry_limit=5` better than a bare `5`?**

<details>
<summary>Answer</summary>

It is self-describing: a reader, a script or a future maintainer knows what
the value means without the program that wrote it.

</details>

**Name a case where binary is justified.**

<details>
<summary>Answer</summary>

Large media files, or hot data paths where size and parsing speed are
measured problems. Even then, keep a text schema or dump tool.

</details>

## Topic 17. Shell Games

### In one sentence

The shell is a workbench for combining small tools, and fluency with it
turns many manual chores into one-line commands.

### The idea

A graphical interface offers exactly the actions its designers imagined.
The shell offers small tools that each do one thing, and a way to join
them: the pipe, written `|`, which sends one command's output to the next
command's input. With that, I can answer questions no single tool was
built for.

The book's advice is to become comfortable in the shell and to make it
mine: customise the prompt, set up aliases for frequent commands, use
command completion, and learn the history search. Every keystroke saved
on something done a hundred times a day adds up.

The shell also brings automation. A sequence of commands I type twice
becomes a script, and a script can run in continuous integration, on a
schedule, or on someone else's machine. That turns my knowledge into
something repeatable.

The point is not to avoid graphical tools. It is to have both, and to
reach for the shell when the task is "do this to many things" or "answer
this question about many things".

### Worked example

**Simple.** Which endpoints are failing? A small access log has one request
per line: time, method, path, status and duration. One pipeline counts
server errors by path:

```bash
grep " 500 " access.log | awk '{print $3}' | sort | uniq -c | sort -rn
```

The output on my sample log:

```text
      2 /api/orders
      1 /api/cart
```

**Realistic.** What is the average latency per path? `awk` can keep running
totals per key and print a summary at the end:

```bash
awk '{gsub("ms","",$5); s[$3]+=$5; n[$3]++}
     END {for (k in s) printf "%-12s %3d requests  avg %5.1f ms\n", k, n[k], s[k]/n[k]}' access.log | sort
```

The output:

```text
/api/cart      2 requests  avg  62.5 ms
/api/orders    4 requests  avg  81.2 ms
/api/users     1 requests  avg  60.0 ms
/health        1 requests  avg   2.0 ms
```

On a real server log with millions of lines, the same command runs in
seconds, with no dashboard needed.

### Step by step

<Trace columns={["Stage", "Command", "What flows out"]} rows={[
  ["1", "grep \" 500 \" access.log", "the 3 lines whose status is 500"],
  ["2", "awk '{print $3}'", "just the path field: /api/orders, /api/cart, /api/orders"],
  ["3", "sort", "identical paths next to each other"],
  ["4", "uniq -c", "each distinct path with a count: 1 /api/cart, 2 /api/orders"],
  ["5", "sort -rn", "highest count first"],
]} caption="The error-count pipeline, one stage per row. Look at stage 3: uniq only merges adjacent lines, so the sort before it is essential." />

Building a pipeline is itself a method:

1. **Start with the data.** `head access.log` to see the shape.
2. **Add one stage at a time**, looking at the output after each.
3. **Name the fields** before using them; count the columns.
4. **When it works twice, save it** as a script or alias.

#### Making the shell mine

Fluency comes from small customisations that remove friction. A few I set
up on any new machine:

| Customisation | Example | What it saves |
|---|---|---|
| Prompt shows branch and exit code | a prompt plugin or a small function | Committing on the wrong branch; missing a failure |
| Aliases for frequent commands | `alias gs='git status -sb'` | Dozens of keystrokes a day |
| History search | Ctrl-R, then type part of an old command | Retyping long commands |
| Tab completion for Git and npm | the shell's completion package | Typos in branch and script names |
| A personal `bin` folder on the PATH | `~/bin/serve-here` | Remembering long one-off commands |

Each of these is small, and none is required. Together they make the shell
feel like a tool shaped to my hand, which is what makes me reach for it.

#### From pipeline to script

When a pipeline is worth keeping, it becomes a script with a name, a usage
line and safe defaults:

```bash
#!/usr/bin/env bash
# errors-by-path: count HTTP 500 responses per path in an access log.
set -euo pipefail
log="${1:?usage: errors-by-path ACCESS_LOG}"
grep " 500 " "$log" | awk '{print $3}' | sort | uniq -c | sort -rn
```

`set -euo pipefail` stops on the first failing command, on an unset
variable, and on a failure anywhere in a pipeline. The `${1:?...}` line
prints the usage message and exits if no file was given. The quotes around
`"$log"` keep a path with spaces in one piece.

### Common mistake

The classic mistake is `uniq -c` without `sort` first. `uniq` only merges
adjacent identical lines, so unsorted input gives wrong counts with no
error. The fix is to always sort before `uniq`.

Another is splitting on whitespace when fields can contain spaces, such as
user agents in a log. The fix is a structured log format, JSON, and a
tool that understands it, such as `jq`.

### In real systems

Shell scripts run builds, deployments, backups and incident
investigations everywhere. In production scripts, start with
`set -euo pipefail` so a failing command stops the script instead of
being ignored, quote every variable, and check exit codes. On-call
engineers who can slice a log in the shell find causes in minutes.

### Check yourself

**Why does `uniq -c` need `sort` before it?**

<details>
<summary>Answer</summary>

`uniq` only collapses identical lines that are next to each other. Sorting
brings equal lines together so each gets one correct count.

</details>

**When should a pipeline become a script?**

<details>
<summary>Answer</summary>

When I have typed it twice, or when someone else needs to run it. A script
makes it repeatable and reviewable.

</details>

## Topic 18. Power Editing

### In one sentence

The editor is the tool I use most, so I learn it until editing needs no
conscious thought.

### The idea

Developers spend much of their day editing text. If every edit requires
reaching for the mouse, hunting through menus or retyping, the friction
breaks concentration. The book's goal is fluency: being able to make the
change I am thinking about as fast as I think of it.

What does fluency mean concretely? Moving and selecting by character,
word, line, block and function without the mouse.

Indenting, commenting,
and reformatting code. Undoing and redoing. Splitting the window, jumping
to definitions, searching with regular expressions, and using multiple
cursors or macros to repeat an edit.

The book's method is gradual and deliberate. Notice when I do something
repetitive or slow.

Find out whether the editor has a faster way. Then
practise that one thing until it is automatic. One skill a week is enough;
over a year it changes everything.

Growing into the editor also means its extensions and its language
features: running tests from it, refactoring commands, and writing small
customisations when nothing existing fits.

### Worked example

**Simple.** I keep renaming a variable by hand, line by line. The faster
way is the editor's rename-symbol command, which uses the language server
to update every reference, including other files. I practise it for a
week on every rename until I never do it by hand again.

**Realistic.** I need to turn twenty lines of `key: value` settings into a
TypeScript object. With multiple cursors I select all twenty lines, jump
to the start of each, wrap the key in quotes, jump to the end and add a
comma. Thirty seconds instead of five minutes, and no typos.

### Step by step

<Timeline caption="A year of deliberate editor practice. Look at the size of each step: one skill at a time, until it is automatic." items={[
  { when: "Weeks 1 to 4", what: "Cursor movement by word, line and block; no arrow-key holding" },
  { when: "Weeks 5 to 8", what: "Go to definition, find references, rename symbol" },
  { when: "Weeks 9 to 12", what: "Multiple cursors and regex search-and-replace" },
  { when: "Months 4 to 6", what: "Run tests and debug from the editor; snippets for repeated code" },
  { when: "Months 7 to 12", what: "One small custom command or extension for my own workflow" },
]} />

1. **Notice friction.** Mark in the daybook any edit I did slowly.
2. **Look it up.** The editor's command palette or documentation.
3. **Practise it deliberately** for a week, on purpose, even when slower.
4. **Check that it is automatic**, then pick the next one.

A third example shows regular-expression replace, one of the highest-value
editor skills. A codebase calls `logger.info("...")` in 300 places, and the
team decides every call must include an event name as its first argument.
A regex search for `logger\.info\("` across the project lists every call;
a regex replace can insert a placeholder event name in each; and the
editor's multi-file preview lets me review every change before applying it.
What would be a day of careful manual editing becomes twenty minutes,
most of it reviewing.

The same applies to navigation. Jumping to a symbol by name, going back to
the previous location, and opening a file by typing part of its name are
each tiny, but I do them hundreds of times a day. Fluency there is the
difference between staying in the flow of a problem and losing it to the
mechanics of finding things.

### Common mistake

The mistake is trying to learn every shortcut at once. Nothing sticks, and
the effort feels pointless. The fix is one skill at a time, chosen from
real friction.

The other is switching editors constantly, never getting deep in any. The
fix is to pick one main editor and go deep, while knowing the basics of a
terminal editor for servers.

### In real systems

When an incident needs a config change on a server with only a terminal,
knowing a terminal editor's basics matters. Day to day, refactoring tools
in the editor make large changes safe, because they update references
precisely where search-and-replace might not.

### Check yourself

**What is the book's method for improving editor skill?**

<details>
<summary>Answer</summary>

Notice repetitive or slow edits, find the faster way the editor offers,
and practise it deliberately until it is automatic, one skill at a time.

</details>

## Topic 19. Version Control

### In one sentence

Put everything that matters under version control, and use it as a
time machine, a safety net and a collaboration tool.

### The idea

Version control records every change to a set of files: who made it, when,
and why. It lets me go back to any earlier state, compare versions, work on
branches in parallel and merge them. Git is the common choice today.

The book's first point is about scope: everything goes in. Not just source
code, but build scripts, configuration, documentation, tests, and even my
personal settings files. If something is needed to build or run the
project, it belongs under version control.

The second point is that a shared network folder is not version control.
Copying files to a shared drive loses history, lets people overwrite each
other's work, and gives no way to review changes. Real version control
gives each change an identity and a message.

The book also notes how version control enables everything else: reviews
through pull requests, automatic builds on every change, deployments from
known versions, and experiments on branches that cost nothing to abandon.

### Worked example

**Simple.** A test that used to pass now fails, and there are many commits
between the last good version and now. `git bisect` does a binary search
over history. I give it a good commit, a bad commit and a test script:

```bash
git bisect start HEAD HEAD~7     # bad is HEAD, good is 7 commits back
git bisect run sh test.sh        # test.sh exits 0 for good, 1 for bad
```

On a small demo repository with eight commits, where commit 6 broke an
`add` function, the run prints (trimmed):

```text
Bisecting: 3 revisions left to test after this (roughly 2 steps)
[25ebd16] change 4
Bisecting: 1 revision left to test after this (roughly 1 step)
[f7063e3] change 6
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[75458b6] change 5
f7063e363eae02fa4343bdcd41b7572d4df91bb7 is the first bad commit
```

Three test runs found the culprit among six candidates. With a thousand
commits it would take about ten.

**Realistic.** A production server's configuration was edited by hand
over months. When it is rebuilt, nobody can reproduce it. Putting the
configuration, and the script that applies it, under version control means
the next rebuild is a command, and every change has a reviewer and a
reason.

### Step by step

<Trace columns={["Step", "Range still suspect", "Commit tested", "Test result", "Conclusion"]} rows={[
  ["1", "changes 2 to 8", "change 4", "pass", "bug is after 4"],
  ["2", "changes 5 to 8", "change 6", "fail", "bug is at or before 6"],
  ["3", "changes 5 to 6", "change 5", "pass", "bug is after 5"],
  ["4", "change 6 only", "", "", "change 6 is the first bad commit"],
]} caption="git bisect as a binary search. Look at the second column: the suspect range halves with every test." />

The reason it works: each test splits the suspect range roughly in half,
so the number of tests grows with the logarithm of the number of commits.
That only holds if every commit builds and tests on its own, which is one
more reason for small, working commits.

#### Branches, and version control as the project's hub

Branches let me work on a change in isolation, then merge it when it is
ready. A short-lived branch per change, merged after review, keeps the
main branch always working. Long-lived branches drift away from main and
make merges painful, so the usual advice is to keep them short.

The book also points out that the repository becomes the hub of the
project. A push can trigger the build, the tests, the deployment to a test
environment and, after approval, to production. Once that is true, the
history of the repository is the history of the product: every release is
a tag, every change has a review, and every question about "what changed"
has an answer.

A good commit message is part of the tool. A useful shape is a short
summary line in the imperative ("Fix rounding of discounts in cart
totals"), a blank line, and then why the change was needed and anything
surprising about it. In a year, `git blame` on a strange line leads to that
message, and the why is the part nobody can reconstruct.

### Common mistake

The common mistake is large, mixed commits: "fix bug, rename things,
update deps". They are hard to review, hard to revert and make bisect
useless, because the bad commit contains five changes. The fix is one
logical change per commit, with a message that says why.

Another is leaving things out: the build script lives on one machine, the
config in someone's home folder. The fix is the rule that a fresh clone
plus one command must build the project.

### In real systems

In production, version control is the backbone of continuous integration
(every push is built and tested), deployment (every release is a known
commit), auditing (who changed this firewall rule, and why) and recovery
(revert the bad commit, redeploy). GitOps takes it furthest: the
repository is the source of truth for what runs.

### Check yourself

**Why does `git bisect` need every commit to build?**

<details>
<summary>Answer</summary>

It tests commits in the middle of the range. A commit that does not build
cannot be classified as good or bad, which breaks the binary search (it
must be skipped).

</details>

**Is a shared network drive with dated folders a form of version control?**

<details>
<summary>Answer</summary>

No. It lacks per-change history, messages, safe merging and review, and
people can overwrite each other's work.

</details>

## Topic 20. Debugging

### In one sentence

Debugging is problem solving with a method: stay calm, reproduce the bug,
read the evidence, narrow it down, explain it, then fix it with a test.

### The idea

#### The psychology

Nobody writes perfect code, so debugging is a normal part of the job, not
a failure. The book's first advice is about attitude. Fix the problem, not
the blame: it does not matter whose bug it is. And do not panic: deadlines
and pressure push us to guess, and guessing wastes time.

Another trap is "that can't happen". When the program does something
impossible, my belief is wrong, not the computer. The book's version is to
not assume anything but prove it. The bug is in what I am sure is fine.

#### Where to start

Start with a clean build, with all compiler and linter warnings on. Many
bugs are already reported as warnings.

Then reproduce the bug. Ideally
with a single command, so I can run it over and over as I narrow it down.
If the user's report is vague, gather the exact inputs and steps first.

A powerful step is to write a failing test that reproduces the bug before
fixing it. That proves I understand the trigger, and it keeps the bug from
returning.

#### Narrowing it down

Read the error message carefully, all of it. Stack traces say where the
program was; error text often says exactly what went wrong. Then narrow
the search with a binary chop: in the data (cut the failing input in half
until the smallest failing piece remains) or in the code or history
(bisect, or comment out half the logic).

Other techniques: add logging or tracing to see values over time. Use a
debugger to stop and inspect state. And explain the problem out loud, line
by line, to someone or something, the rubber duck. Explaining forces me to
state each assumption, and the wrong one often jumps out.

#### The usual suspects

The book points out that the bug is rarely in the operating system, the
compiler or a widely used library. It is far more likely in my code, or in
how I call the library. Check my own code first; suspect the platform only
with strong evidence.

After fixing, ask why the bug was not caught earlier, whether it exists
elsewhere, and what test now guards it.

### Worked example

**Simple.** A cart total looks strange. Prices come from a form, and the
sum is printed:

```ts
// Prices arrive from a form as strings. The sum looks plausible until it doesn't.
const prices: any[] = ['12.50', '250'];   // what the form actually sent
const total = prices.reduce((sum, p) => sum + p, 0);
console.log('total:', total, typeof total);
const fixed = prices.reduce((sum, p) => sum + Number(p), 0);
console.log('fixed:', fixed, typeof fixed);
```

The output:

```text
total: 012.50250 string
fixed: 262.5 number
```

Guessing would look at the reduce logic, which is fine. Reading the data
shows the cause: the values are strings, and `+` concatenates strings. The
fix converts at the boundary, where the form data enters, and a test pins
it.

**Realistic.** A pagination bug: users with exactly 11 items see only one
page. Reproducing with a table of inputs makes the pattern obvious:

```ts
// Off-by-one in a page calculation, then the fix.
const pages = (items: number, perPage: number) => Math.floor(items / perPage);
const fixedPages = (items: number, perPage: number) => Math.ceil(items / perPage);
for (const n of [0, 1, 10, 11, 25]) {
  console.log(`items ${String(n).padStart(2)}: buggy ${pages(n, 10)}, fixed ${fixedPages(n, 10)}`);
}
```

```text
items  0: buggy 0, fixed 0
items  1: buggy 0, fixed 1
items 10: buggy 1, fixed 1
items 11: buggy 1, fixed 2
items 25: buggy 2, fixed 3
```

The table shows that every partial page is dropped, not just the case that
was reported. Floor rounds down; a partial page still needs a page, so
ceiling is right. The boundary inputs 0, 1, 10 and 11 become the tests.

### Step by step

<Flow caption="The debugging method. Look at where the fix comes: after the explanation, never before." steps={[
  "Stay calm, drop the blame",
  "Clean build, warnings on",
  "Reproduce with one command",
  "Write a failing test",
  "Read the error and the data",
  "Binary-chop the input or history",
  "Explain it out loud",
  "Fix, test passes, look for siblings",
]} />

Binary chop on input, walked through. A JSON import fails on a 1,000-line
file with no useful error.

<Trace columns={["Try", "Lines kept", "Result", "Next"]} rows={[
  ["1", "1 to 500", "passes", "the problem is in 501 to 1,000"],
  ["2", "501 to 750", "fails", "keep 501 to 750"],
  ["3", "501 to 625", "passes", "the problem is in 626 to 750"],
  ["4", "626 to 688", "fails", "keep 626 to 688"],
  ["...", "...", "...", "about 10 tries in total"],
  ["10", "line 641", "fails", "line 641 has a tab inside a string"],
]} caption="Halving a failing input. Look at the second column: ten tries reach one line out of a thousand." />

The halving works because each try discards half of the suspects. A
thousand lines need about ten tries, a million about twenty.

### Common mistake

The worst mistake is changing code at random until the symptom goes away.
That often hides the bug, adds new ones, and teaches nothing. The fix is
the rule: no change until I can explain the cause, and a failing test
before the fix.

Another is fixing the symptom where it appears instead of where it
starts. The string-sum fix belongs where the form data enters, not in the
reduce. The fix is to trace the bad value back to its origin.

### In real systems

In production, reproducing may be impossible directly, so logs, traces and
metrics become the evidence. Good teams log enough context (request id,
inputs, versions) to reconstruct a failure, and every fixed incident gets a
regression test. Bugs that vanish under the debugger, often timing or
uninitialised memory, call for logs, sanitizers or core dumps instead.

### Check yourself

**Why write a failing test before fixing?**

<details>
<summary>Answer</summary>

It proves I can trigger the bug, tells me when the fix works, and keeps
the bug from coming back.

</details>

<details>

Explaining the code step by step forces me to state each assumption out

</details>

## Topic 21. Text Manipulation

### In one sentence

Learn a scripting language well enough to reshape text quickly, because
so much of development is turning one text into another.

### The idea

Developers constantly transform text: generating code from a schema,
extracting data from logs, converting formats, writing release notes from
commit messages, updating version numbers across files. Doing these by
hand is slow and error-prone. A scripting language turns each into a few
lines.

The book recommends learning a text-manipulation language well. Classic
choices are Python, Ruby or Perl, but for me JavaScript or TypeScript with
Node fits, because it is what I write daily. The point is that it is fast
to write, has good regular expressions, and can read and write files
easily.

This topic connects back to DRY. A script that generates documentation
from code, or code from a schema, keeps one source of truth. It also
connects to plain text: because my knowledge is in text, scripts can
operate on it.

The book also suggests using scripts to build the book itself: the
authors' own manuscript is plain text processed by scripts. That is a hint
about how far the idea goes.

### Worked example

**Simple.** Turn a changelog section into release-note bullets: keep only
features and fixes, rewrite each into plain words, and sort them.

```ts
// Text manipulation: turn a CHANGELOG section into release-note bullets.
const changelog = `## 2.4.0
- fix(cart): rounding of discounts (#412)
- feat(search): typo tolerance (#398)
- chore: bump deps
- feat(cart): save for later (#405)`;
const notes = changelog
  .split('\n')
  .filter((l) => /^- (feat|fix)/.test(l))
  .map((l) => l.replace(/^- (feat|fix)\((\w+)\): (.*) \(#(\d+)\)$/, (_, kind, area, text, pr) =>
    `${kind === 'feat' ? 'New' : 'Fixed'} in ${area}: ${text} (PR ${pr})`))
  .sort();
console.log(notes.join('\n'));
```

The output:

```text
Fixed in cart: rounding of discounts (PR 412)
New in cart: save for later (PR 405)
New in search: typo tolerance (PR 398)
```

**Realistic.** A database schema file is the source of truth for table
columns. A script reads it and generates the TypeScript types and the API
documentation table on every build. When a column is added, both update
automatically and cannot drift from the schema.

### Step by step

<Trace columns={["Stage", "Operation", "Lines remaining"]} rows={[
  ["1", "split on newlines", "5 lines, including the heading"],
  ["2", "keep lines starting with feat or fix", "3 lines; chore and heading dropped"],
  ["3", "regex capture: kind, area, text, PR number", "3 structured matches"],
  ["4", "rewrite each in plain words", "3 sentences"],
  ["5", "sort", "Fixed lines first, then New, alphabetically"],
]} caption="The changelog script as a pipeline. Look at stage 3: the regular expression turns loose text into named parts." />

### Common mistake

The mistake is a regular expression that works on the sample and silently
skips real lines that differ slightly, such as a missing PR number. The
line passes the filter but the replace does not match, so it comes out
unchanged. The fix is to count inputs and outputs, and report lines that
did not match instead of passing them through.

### In real systems

Code generators, migration scripts, log-processing jobs, release tooling
and documentation builds are all text manipulation in production. They are
usually small and owned by one person, so they need tests and version
control like any other code.

### Check yourself

**What happens in my script to a line like `- fix(cart): typo` with no PR number?**

<details>
<summary>Answer</summary>

It passes the filter but the replace pattern does not match, so it comes
out unchanged, in its raw form. The script should detect and report it.

</details>

## Topic 22. Engineering Daybooks

### In one sentence

Keep a dated notebook of what I did, tried, learned and wondered, because
it improves memory, thinking and debugging.

### The idea

An engineering daybook is a running log: notes from meetings, what I am
working on, values from debugging, ideas, reminders, sketches. The book
describes it as something engineers in other fields have long kept, and
recommends paper, though a plain-text file works for many people.

The book lists three benefits. It is more reliable than memory: I can look
up what I did last Tuesday. It gives a place to park ideas that are not
relevant right now, so I can return to the task. And it works like a
rubber duck: writing something down makes me reflect on it.

A daybook also shows patterns over time. Re-reading it, I see which bugs
keep recurring, which tasks always take longer than estimated, and which
ideas I never followed up.

It is private and informal, which is what makes it honest. It is not
documentation for others; it is thinking made visible.

### Worked example

**Simple.** A daybook entry for a debugging session, short and dated:

<Figure caption="One daybook entry from a debugging session. Look at the 'rule' line: the lesson is written down so it can be found again." art={`
2026-10-23  word counter crashes on empty file
  symptom   exit code 139, only when the input has 0 bytes
  repro     ./wordfreq empty.txt
  guess 1   open fails?  no: the file handle is valid
  bisect    crash is inside sort_words(), with n == 0
  cause     sort called with n - 1 items; n is unsigned, so 0 - 1 wraps
  fix       return early when n is under 2; test: empty file, exit 0
  rule      unsigned subtraction near zero wraps around
`} />

**Realistic.** Over a month, I tag each daybook entry with an estimate and
actual time. At the end of the month I find that every task touching the
payment module took about twice its estimate. That pattern, invisible day
to day, changes how I estimate the next one.

### Step by step

<Flow caption="The daybook loop. Look at the last step: re-reading turns notes into patterns." steps={[
  "Date the entry",
  "Write the question or task",
  "Log what I tried and what happened",
  "Write the rule or lesson",
  "Re-read weekly for patterns",
]} />

1. **Open the daybook at the start of the day** and write the date.
2. **Before starting a task, write what I expect.** Time, approach.
3. **During debugging, log every attempt and result.** Even the dead ends.
4. **Park unrelated ideas** with one line, and return to the task.
5. **Each week, re-read and pull out patterns** into a short summary.

A useful structure for a daybook page is a small, consistent set of
markers, so entries are fast to write and easy to scan later:

| Marker | Meaning | Example |
|---|---|---|
| `?` | an open question | `? why does the import skip the last row` |
| `!` | something learned | `! uniq only merges adjacent lines` |
| `->` | a decision made | `-> keep config in YAML, not the DB` |
| `todo` | a parked task | `todo: try the streaming parser` |
| `est / act` | an estimate and the actual | `est 2h / act 5h, payment module again` |

With markers like these, a weekly re-read can also be a search: every `!`
line from the month is a list of lessons, and every `est / act` pair is
calibration data for the next estimate.

### Common mistake

The mistake is turning the daybook into a polished document, which makes
writing slow, so it stops. The fix is to keep it informal: fragments,
sketches, values, whatever is fast.

The other mistake is writing and never reading. The fix is the weekly
re-read, ten minutes, with one pattern written at the end.

### In real systems

During incidents, a running log of times, actions and observations is
exactly a daybook, and it becomes the incident timeline. Many engineers
keep a work log that later feeds performance reviews, design documents and
postmortems.

### Check yourself

**Name the three benefits of a daybook the book gives.**

<details>
<summary>Answer</summary>

It is more reliable than memory, it is a place to park ideas so I can stay
focused, and writing in it works like a rubber duck for reflection.

</details>

## From beginner to strategy

<Levels label="Chapter 3, The Basic Tools">

<Level name="Beginner" depth={3}>

The smallest version of this chapter is a daily routine. I open a terminal
instead of a file browser.

I commit small changes with clear messages.
When something breaks, I reproduce it with one command before trying a
fix. And I write a dated line in my daybook for each thing I tried.

A worked example: my script prints the wrong total. I write `node
total.ts` in the terminal so I can re-run it in one keystroke. I add one
`console.log` showing the inputs and their types, see that the inputs are
strings, convert them at the boundary, add a test, and commit with the
message "Convert form prices to numbers where they enter".

The beginner mistake is debugging in my head instead of looking at the
data. Fix: print the actual values and their types before forming a
theory.

</Level>

<Level name="Intermediate" depth={3}>

At the intermediate level, the tools combine. A failing test points me to
a commit range; `git bisect run` finds the commit; the diff of that commit
plus a log pipeline over the test output shows the cause; a small script
generates the fixture that reproduces it; the daybook holds the story.

Concretely, after a dependency update the build gets slow. I time the
build at the old and new commits, bisect to the dependency bump, then use
`grep` and `sort` on the build's timing output to find the slow step. Total
time: twenty minutes, all in the terminal, all recorded.

The intermediate mistake is keeping useful one-liners only in shell
history, where they are lost. Fix: save anything I used twice into a
`scripts/` folder under version control.

</Level>

<Level name="Advanced" depth={3}>

Underneath, the chapter rests on two ideas. Plain text is a universal
interface, so every tool composes with every other. And debugging is
search: the bug is somewhere in a space of inputs, code and history, and
each experiment should cut that space as much as possible.

Binary search makes this precise. If each experiment halves the suspects,
then n suspects need about log₂ n experiments: 1,000 lines need 10, a
million need 20. Bisect relies on this, and on the assumption that the bug
appeared once and stayed, so history is "good, then bad". When a bug comes
and goes, that assumption fails, and the search needs a test that is
reliable first.

The advanced mistake is an experiment that does not split the space, such
as re-running the same failing case hoping to learn more. Fix: before each
experiment, say what each possible result would rule out.

</Level>

<Level name="Edge cases" depth={3}>

**An empty input.** Many tools behave oddly on zero-length data. My page
counter must return 0 pages for 0 items; the daybook example crashed on an
empty file. Always include the empty case in tests.

**A huge file.** Loading a 10 GB log into an editor fails. Streaming tools
such as `grep` and `awk` process it line by line and work.

**A commit that does not build.** Bisect cannot classify it; `git bisect
skip` marks it and moves on, at the cost of possibly ending with a range
instead of one commit.

**Non-UTF-8 text.** A file in another encoding breaks a script silently.
Check with the `file` command and convert first.

</Level>

<Level name="Corner cases" depth={3}>

**A flaky test meets bisect.** If the test fails randomly, bisect will
blame the wrong commit with confidence. The fix is to make the test reliable,
or run it several times per step and only call a commit good if all runs
pass.

**A bug that disappears under the debugger.** Stopping the program changes
timing, so a race or a reliance on uninitialised memory vanishes. The fix
is non-intrusive evidence: logs with timestamps, sanitizers, or a core dump
taken at the moment of failure.

**Plain-text config meets secrets.** Keeping config in the repository is
good; keeping passwords there is not. The fix is plain-text config with
references to secrets stored elsewhere.

</Level>

<Level name="Production level" depth={3}>

In production the tools grow up. Plain text becomes structured JSON logs,
which shell tools and log platforms can both read. Shell scripts get
`set -euo pipefail`, quoting and exit-code checks, and live in version
control with tests. Version control covers infrastructure, configuration
and dashboards, not only application code.

Debugging changes most. I usually cannot attach a debugger to a production
server, so the evidence must already exist: request ids carried through
every log line, traces that show where time went, metrics with labels, and
error reports with stack traces and versions. A team that adds this before
the incident finds causes in minutes rather than days.

The production mistake is logging too little context or too much noise.
Fix: log events with ids, inputs and outcomes, and keep a log level policy
so the important lines are not drowned out.

</Level>

<Level name="Mindset" depth={3}>

The habit of thought is that tools are leverage, and leverage compounds.
An hour learning `awk` or the debugger pays back every week. The same for
an editor skill, a bisect, a script.

Equally important is the evidence mindset: trust what I can observe over
what I believe. The computer is doing exactly what the code says. If I am
surprised, my model is wrong, and the way forward is to look.

The mindset mistake is pride in doing things the hard way, or fear of
looking slow while learning a tool. Fix: count the hours a tool saves, and
spend a small, fixed share of time on getting better at tools.

</Level>

<Level name="System design" depth={3}>

At system scale, these tools become platform decisions. Take an online
store's backend.

Its configuration is plain text in Git, reviewed and
deployed by the pipeline. Its logs are structured text with a request id
on every line, collected centrally. Its runbooks are Markdown next to the
code, with shell commands that on-call engineers can paste.

The same store's debugging story is designed in: every service propagates
the request id, errors include the commit hash of the running version, and
deploys are tagged so `git log` between two tags lists exactly what
changed. When checkout breaks, the path from alert to the guilty commit is
a few commands.

The design mistake is treating observability and tooling as something to
add later. Later is during the outage. Fix: the tracer bullet from chapter
2 includes logging, the request id and a deploy tag from day one.

</Level>

<Level name="Strategy" depth={3}>

This chapter is my Phase 0 checklist in the
<a href={withBase('/plans/traditional-software-developer/')}>traditional core</a>:
shell, editor, Git, debugger, scripts and the daybook. I learn them by
using them on the Phase 0 baseline programs, one tool at a time, and I
write each new trick into the daybook.

I know I have learned it when I can do each task without searching how:
slice a log, bisect a regression, script a transformation, step through a
program in the debugger, and find last week's decision in my daybook.

Done when, without looking anything up, I can bisect a planted bug in a
practice repository, answer three questions about a log file with shell
pipelines, write a text-transform script with tests, and show four weeks
of daybook entries.

</Level>

</Levels>

## Questions people ask

<details>
<summary>Do I need to learn Vim or Emacs?</summary>

The book's advice is to know one editor deeply, whichever it is. Knowing
the basics of a terminal editor is useful for servers, but fluency in my
main editor matters far more.

</details>

<details>
<summary>Is the shell still worth learning with good GUIs and IDEs?</summary>

Yes. GUIs do what their designers imagined; the shell combines tools for
questions nobody anticipated, and its commands can be saved, scripted and
run on any server.

</details>

<details>
<summary>Should the daybook be paper or digital?</summary>

The book favours paper for its freedom to sketch. A plain-text file works
too and is searchable. What matters is that it is fast to write in and
that I re-read it.

</details>

<details>
<summary>What if the bug really is in the library or the compiler?</summary>

It happens, but rarely. Prove it with a minimal reproduction that uses only
the library. If the reproduction still fails, report it with that case.

</details>

<details>
<summary>What belongs in version control besides code?</summary>

Build scripts, configuration, infrastructure definitions, documentation,
tests, database migrations and my own tool settings: anything needed to
build, run or understand the project.

</details>

## Key takeaways

- Keep knowledge in self-describing plain text, because every tool can work with it.
- Learn the shell well enough to combine small tools into pipelines, and save what I reuse.
- Practise one editor skill at a time until it is automatic.
- Put everything needed to build and run a project under version control, in small commits.
- Debug by method: reproduce, read, binary-chop, explain, then fix with a test.
- Assume the bug is in my code, and prove assumptions instead of trusting them.
- Write small scripts to reshape text, and give them tests.
- Keep a dated daybook and re-read it weekly for patterns.

## Glossary

- **Plain text**: human-readable characters, such as source code, JSON, CSV or Markdown.
- **Self-describing format**: text in which every value carries its name or meaning.
- **Shell**: the command-line program that runs commands and connects them.
- **Pipe**: the `|` operator that sends one command's output into the next command.
- **Alias**: a short name for a longer shell command.
- **Version control**: a system that records every change with author, time and message.
- **Commit**: one recorded change in version control.
- **git bisect**: a command that binary-searches history for the first bad commit.
- **Binary chop**: halving the suspect input, code or history at each step.
- **Rubber ducking**: explaining a problem out loud, step by step, to find a wrong assumption.
- **Regression test**: a test that keeps a fixed bug from returning.
- **Regular expression**: a pattern language for matching text.
- **Engineering daybook**: a dated, informal log of work, attempts and ideas.
- **Structured log**: log lines in a machine-readable format such as JSON.

   alias for each.

6. Extend the changelog script to report lines that did not match the

**Stretch (change the problem).**

7. My bisect test is flaky, failing one run in ten on good commits. Work out
   how many runs per step are needed to make a wrong answer unlikely, and
   change the script to do that.
8. Rewrite the access-log pipeline for JSON log lines using `jq`, and
   explain what changes in robustness.

About 10, because 2 to the power 10 is 1,024.
