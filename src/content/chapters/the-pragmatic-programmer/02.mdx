This chapter turns from attitude to design. Its eight topics are the ideas
that keep code cheap to change: one test for good design, one home for each
piece of knowledge, parts that do not affect each other, decisions that can
be undone, and ways to build, experiment and estimate under uncertainty.
They apply in every language, which is why the rest of the book keeps
pointing back to them.

## Before you start

After this chapter I will be able to:

- judge a design choice by asking whether it makes the code easier to change;
- find duplicated knowledge, which is different from duplicated text, and give it one home;
- spot coupling between modules and design them to be independent;
- hide a vendor or framework decision behind an interface so it can be reversed;
- build a thin end-to-end tracer bullet first, and know when a prototype must be thrown away;
- express rules in the domain's own vocabulary, and give estimates with units, a range and a model.

What I should already know: functions, modules and basic TypeScript or any
similar language. The
<a href={withBase('/books/the-pragmatic-programmer/01-a-pragmatic-philosophy/')}>previous chapter</a>
sets up the attitude, especially ownership and good-enough software, which
this chapter uses.

Reading time: about an hour for this page, plus two hours for the
exercises, most of them coding.

## Topic 8. The Essence of Good Design

### In one sentence

Good design is design that is easier to change, so every design choice is
judged by that one question.

### The idea

There are many design principles: decoupling, single responsibility, good
naming, information hiding. The book's observation is that almost all of
them serve one goal, making the code easier to change later. It calls this
the ETC principle, for Easier To Change.

Why change? Because requirements change, understanding grows, bugs are
found, and libraries move. Code that is hard to change becomes code people
are afraid to touch, and fear leads to workarounds, which leads to rot. A
design that is easy to change keeps all future options cheap.

ETC is a value, not a rule. That makes it useful as a tie-breaker. When two
designs both work, I ask which one will be easier to change, and I pick it.
I can check principles against it too: decoupling makes code easier to
change because a change touches fewer places.

Sometimes I genuinely do not know which way the code will change. The
book's advice for that case is to make the code replaceable: keep it small
and isolated, so whatever happens, swapping it is cheap. And to note the
guess in my daybook, so I can see later how good my instincts were.

### Worked example

**Simple.** A function formats prices for display. Version A hard-codes the
rupee symbol and two decimals inside a template in ten components. Version
B has one `formatPrice(amount, currency)` used by all ten. When the business
adds US dollars, A needs ten edits; B needs one. Both worked on day one; B
was easier to change.

**Realistic.** I am choosing how a notification service sends messages.
Design 1 calls the email provider's SDK directly from twenty places. Design
2 defines `notify(user, message)` with an email adapter behind it. ETC
picks design 2: adding SMS, swapping providers or batching messages each
touch one module. The cost is one small interface, written once.

### Step by step

Applying ETC to a decision, as a short routine:

1. **List the plausible changes.** New currency, new provider, new field,
   more traffic.
2. **For each design, count what each change touches.** Files, modules,
   teams.
3. **Prefer the design with fewer, more local touches**, unless it costs
   much more now.
4. **If unsure, make the piece replaceable** and write the guess in the
   daybook.

<Compare left="Hard to change" right="Easier to change" caption="The same feature built two ways. Look at the right column: each change lands in one place." rows={[
  ["Currency symbol in ten templates", "One formatPrice function"],
  ["Provider SDK called from twenty files", "One notify() with an adapter"],
  ["Magic numbers repeated in code", "Named constants or configuration"],
  ["One giant function doing five jobs", "Five small functions, each one job"],
]} />

### Common mistake

The mistake is using ETC to justify speculative generality: building plugin
systems and abstraction layers for changes that never come. Each layer is
itself something that must be changed. The fix is to design for the
changes I can name, keep the rest small and replaceable, and add
abstraction when a second real case appears.

### In real systems

In production code review, ETC is the most useful single question to ask
of a pull request: "if we needed to change X next month, how many files
would we touch?" It catches tight coupling, scattered constants and
leaked abstractions without needing a catalogue of principles.

### Check yourself

**Why can ETC act as a tie-breaker between two working designs?**

<details>
<summary>Answer</summary>

Because it gives one question that most design principles serve; the
design whose likely changes touch fewer places wins.

</details>

**What should I do when I cannot predict how code will change?**

<details>
<summary>Answer</summary>

Make it small and isolated so it is cheap to replace, and record my guess
to calibrate my judgment later.

</details>

## Topic 9. DRY: The Evils of Duplication

### In one sentence

Every piece of knowledge in a system should have one authoritative home,
so a change to that knowledge happens in exactly one place.

### The idea

DRY stands for Don't Repeat Yourself. It is often misread as "never write
the same lines twice". The book is explicit that DRY is about knowledge and
intent, not text. Two pieces of code that look identical but encode
different rules are not duplication; one rule written in two places, even
in different forms, is.

Why does duplicated knowledge hurt? Because when the rule changes, every
copy must change, and someone will miss one. The system then contradicts
itself. The bug is not in any single copy; it is in the gap between them.

The book lists where duplication creeps in. It appears in code, in
documentation that restates code, in data structures that store values
derivable from others, in representations (the same API described in a
client and a server), and between developers who each write the same
helper. Each has its own fix.

| Kind | Example | Usual fix |
|---|---|---|
| Code | The same validation in the form and the API | Share one validator |
| Documentation | A comment that restates what the code does | Delete it; comment the why |
| Data | Storing `start`, `end` and `length` together | Derive one from the other two |
| Representational | API shape written by hand in client and server | Generate both from one schema |
| Between developers | Two teams write the same date helper | Shared library, and talking |

### Worked example

**Simple.** A field list for exporting users. The header row and the
validator both need the field names and types. Written once, both are
derived from it:

```ts
// DRY: one description of a field list drives both validation and the CSV header.
const fields = [
  { name: 'id', type: 'number' },
  { name: 'email', type: 'string' },
  { name: 'plan', type: 'string' },
] as const;

function validate(row: Record<string, unknown>): string[] {
  return fields
    .filter((f) => typeof row[f.name] !== f.type)
    .map((f) => `${f.name}: expected ${f.type}, got ${typeof row[f.name]}`);
}
const header = fields.map((f) => f.name).join(',');

console.log(header);
console.log(validate({ id: 7, email: 'a@b.c', plan: 'pro' }));
console.log(validate({ id: '7', email: 'a@b.c' }));
```

The output:

```text
id,email,plan
[]
[
  'id: expected number, got string',
  'plan: expected string, got undefined'
]
```

Adding a field is now one line, and the header and the validator cannot
disagree.

**Realistic.** A team keeps the tax rate for each state in the database,
in a frontend constant for the price preview, and in a PDF invoice
template. When one state's rate changes, the database is updated and the
preview is not. Customers see one total at checkout and another on the
invoice. The fix is a single source, the database, with the preview asking
the API and the invoice reading the same row.

### Step by step

<Figure caption="Before and after giving a fact one home. Look at the arrows: after the fix, every reader points at the same source." art={`
 BEFORE                         AFTER
 +-----------+                  +-----------------+
 | DB: 18%   |                  | DB: tax_rate    |
 +-----------+                  +--------+--------+
 +-----------+                           |
 | UI: 0.18  |       ==>         +-------+-------+
 +-----------+                   |       |       |
 +-----------+                   v       v       v
 | PDF: 18%  |                  API     UI     PDF
 +-----------+                 (all read the one row)
`} />

Finding duplicated knowledge in a codebase:

1. **Pick a business rule.** "Orders over 50 ship free."
2. **Search for every place it is expressed.** The number 50, the word
   free, the shipping function.
3. **Ask whether each copy must change when the rule changes.** If yes, it
   is duplication.
4. **Choose the authoritative home**, then make the others read from it or
   be generated from it.
5. **Add a test** that fails if a copy reappears, where that is practical.

### Common mistake

The classic mistake is DRYing up text that is not shared knowledge. Two
validators both check "length at least 3", one for usernames and one for
product codes. Merging them couples two unrelated rules, so when product
codes change to length 5, the username rule changes by accident. The fix is
to ask "do these change for the same reason?" If not, leave them separate.

The other mistake is a comment that restates code. It is duplication that
will drift. The fix is to let the code say what, and the comment say why.

### In real systems

At scale, DRY is why teams generate API clients from OpenAPI or protobuf
schemas, derive TypeScript types from database schemas, and keep
configuration in one store. Representational duplication between services
is one of the most common sources of production bugs, and code generation
is the standard cure.

### Check yourself

**Two functions have identical bodies. Is that a DRY violation?**

<details>
<summary>Answer</summary>

Only if they express the same knowledge, meaning they must change together
for the same reason. Identical text for different rules should stay
separate.

</details>

**A record stores start, end and duration. What is wrong?**

<details>
<summary>Answer</summary>

One of the three can be derived from the other two, so they can disagree.
Store two and compute the third.

</details>

## Topic 10. Orthogonality

### In one sentence

Two parts of a system are orthogonal when changing one does not affect the
other, and building with orthogonal parts makes everything cheaper.

### The idea

Orthogonal is a geometry word for lines at right angles: moving along one
does not move you along the other. In software, two components are
orthogonal when they are independent, so a change to one has no effect on
the other. The database layer and the user interface should be orthogonal;
changing a button colour should not touch a SQL query.

The book's illustration is a helicopter's controls, where every control
affects the others. Push one lever and you must adjust the other three.
Non-orthogonal software feels the same: fix one thing and something
unrelated breaks.

Orthogonality gives two benefits. Productivity rises, because changes are
local, components are small and reusable, and they combine in more ways.
Risk falls, because a defect is contained in one module, testing is easier,
and I am less tied to any single vendor.

The book applies the idea at several scales: teams (clear ownership, few
overlapping responsibilities), design (layers, each using only the one
below), toolkits and libraries (do they force their choices on my code?),
coding (avoid global data and similar functions), testing (orthogonal code
is easy to unit test) and documentation (content separate from
presentation).

### Worked example

**Simple.** A word-frequency command-line program. Non-orthogonal version:
one function reads the file, splits words, counts them and prints a table.
Orthogonal version: `readText`, `tokenize`, `count`, `format`, each with one
job. Changing the output to JSON touches only `format`. Supporting stdin
touches only `readText`.

**Realistic.** An app logs events by calling the analytics vendor's SDK
from inside every UI component. The components are coupled to the vendor,
the network and the event schema at once. The orthogonal design emits
plain domain events (`cart.item_added`) to a small event bus, and one
subscriber translates them to the vendor. Swapping vendors, adding a second
one or disabling analytics in tests each touch one file.

### Step by step

<Layers caption="An orthogonal layering for the word-frequency tool. Each layer uses only the one below; a change inside a layer stays there." layers={[
  { name: "CLI", note: "parses flags, chooses the formatter" },
  { name: "format", note: "table or JSON, knows nothing about files" },
  { name: "count", note: "a Map of word to count, pure" },
  { name: "tokenize", note: "text to words, pure" },
  { name: "readText", note: "file or stdin to a string" },
]} />

A quick test for orthogonality, run on any pair of modules:

1. **Name a likely change to module A.**
2. **List every file that change touches.** If any belong to module B, A
   and B are coupled.
3. **Find what they share.** Global state, a data format, an assumption.
4. **Move the shared thing behind an interface** or into a third module
   both depend on.
5. **Re-run the test.** The change should now stay inside A.

### Common mistake

The common mistake is hidden coupling through global or shared mutable
state. Two modules that never call each other can still be coupled because
both read and write the same singleton. The fix is to pass what a function
needs as arguments, and to keep state owned by one module.

Another is letting a framework's types leak through every layer. When
every function takes the web framework's request object, the business
logic is coupled to the framework. The fix is to translate at the edge into
plain domain types.

### In real systems

Microservice boundaries, hexagonal architecture (ports and adapters) and
clean layering are all orthogonality at system scale. The practical signal
in production is the blast radius of a change: if a change to billing needs
a coordinated deploy of search, the two are not orthogonal, whatever the
diagram says.

### Check yourself

**Two modules never call each other but both use a global config object they modify. Are they orthogonal?**

<details>
<summary>Answer</summary>

No. They are coupled through shared mutable state; a change in one can
change the other's behaviour.

</details>

**How does orthogonality reduce risk?**

<details>
<summary>Answer</summary>

Defects stay inside one module, components are easier to test alone, and
replacing a vendor or library touches less code.

</details>

## Topic 11. Reversibility

### In one sentence

Decisions that look final rarely are, so I keep the cost of changing my
mind low.

### The idea

Projects make big decisions: which database, which cloud, which framework,
which architecture. It is tempting to treat them as fixed forever. The
book's point is that they are not. Requirements change, vendors change
prices, technologies fall out of favour, and today's best choice can be
tomorrow's mistake.

So the goal is flexible architecture, not perfect prediction. If a
decision is hidden behind an abstraction, changing it later costs a new
implementation of that abstraction, not a rewrite. The book's tip is that
there are no final decisions.

The book also warns about fashion. Architectures go in and out of style:
monoliths, then services, then serverless, then back. Rather than chasing
the current one, make the code able to move. Put third-party APIs behind my
own interfaces, and break code into components that could be deployed
together or apart.

Reversibility has a cost, so it is applied where the decision is both
likely to change and expensive to change. Not every decision needs it.

### Worked example

**Simple.** Invoice storage hidden behind an interface. Today it is memory
(or local disk); tomorrow it might be cloud object storage. The calling
code does not know:

```ts
// Reversibility: the code depends on a small interface, not on a vendor.
interface BlobStore {
  put(key: string, data: string): Promise<void>;
  get(key: string): Promise<string | undefined>;
}
class MemoryStore implements BlobStore {
  private m = new Map<string, string>();
  async put(k: string, d: string) { this.m.set(k, d); }
  async get(k: string) { return this.m.get(k); }
}
```

A logging decorator wraps any store, and the business function takes the
interface:

```ts
class LoggingStore implements BlobStore {
  private inner: BlobStore;
  constructor(inner: BlobStore) { this.inner = inner; }
  async put(k: string, d: string) { console.log(`put ${k} (${d.length} bytes)`); await this.inner.put(k, d); }
  async get(k: string) { console.log(`get ${k}`); return this.inner.get(k); }
}
async function saveInvoice(store: BlobStore, id: string, body: string) {
  await store.put(`invoices/${id}.txt`, body);
  return store.get(`invoices/${id}.txt`);
}
const store: BlobStore = new LoggingStore(new MemoryStore());
console.log(await saveInvoice(store, '42', 'total: 99'));
```

Run as an ES module with `node --experimental-strip-types store.mts`:

```text
put invoices/42.txt (9 bytes)
get invoices/42.txt
total: 99
```

Moving to a cloud store means writing one more class with `put` and `get`.
`saveInvoice` does not change.

**Realistic.** A startup builds on one cloud's proprietary queue, calling
it from forty handlers. Two years later costs push them to move. The forty
call sites, each with the vendor's retry and error semantics, make the move
a quarter-long project. With a thin `Queue` interface from the start, it
would have been one adapter and a test suite.

### Step by step

<Flow caption="Deciding whether to make a choice reversible. Follow the questions in order; only a yes to both earns an abstraction now." steps={[
  "Is this choice likely to change?",
  "Is changing it expensive without a seam?",
  "Yes to both: put it behind my own interface",
  "Otherwise: keep it simple and isolated",
  "Revisit when a second real case appears",
]} />

1. **List the decision and its alternatives.** Queue A, queue B, a database
   table.
2. **Estimate the change cost without a seam.** How many call sites, how
   much vendor-specific behaviour.
3. **Design the narrowest interface** that covers what my code needs, not
   everything the vendor offers.
4. **Write one adapter and one fake.** The fake proves the interface is not
   secretly vendor-shaped.
5. **Test the business code against the fake.**

### Common mistake

The mistake is the leaky abstraction: an interface that mirrors one
vendor's API so closely that a second implementation is impossible. The fix
is the fake: if I cannot write a simple in-memory version, the interface is
too vendor-shaped.

The opposite mistake is wrapping everything, including things that will
never change, which adds indirection everywhere. The fix is the two-question
test above.

### In real systems

Reversibility is behind feature flags (turn a decision off without a
deploy), database migration tools with down migrations, blue-green and
canary deploys (move traffic back in seconds), and multi-cloud abstractions
for storage and queues. Architecture decision records help too, because
knowing why a decision was made tells you what would justify reversing it.

### Check yourself

**How can I tell an interface is too vendor-shaped?**

<details>
<summary>Answer</summary>

Try writing a simple in-memory fake. If it is hard, the interface carries
vendor details and will not support a second implementation.

</details>

**Name a production practice that makes deploy decisions reversible?**

<details>
<summary>Answer</summary>

Feature flags, canary or blue-green deploys, or migrations with a working
rollback.

</details>

## Topic 12. Tracer Bullets

### In one sentence

When the target is uncertain, build a thin version that runs end to end
through every layer first, then thicken it, keeping it as the real
skeleton.

### The idea

Tracer bullets are ammunition that glows, so a gunner at night can see
where shots land and adjust aim in real time. The book uses them as a
metaphor for building software when requirements are vague and the
technology is new. Instead of specifying everything up front and hoping,
build something small that goes all the way through, and see where it
lands.

A tracer bullet in code is a thin slice that connects every major part of
the system: user interface, API, business logic, database, deployment. It
does very little, but it is real code, written to production standards
with tests and error handling. It is not thrown away; it becomes the
skeleton that the rest of the system is built on.

The benefits are concrete. Users see something working early and can
correct the aim.

Developers get a structure to work in. Integration
problems surface on day one instead of at the end. And progress is
visible, because each new feature is added to a system that already runs.

Tracer bullets do not always hit. When they miss, that is the point: I
learn it cheaply and adjust. Because the code is lean, moving it is cheap.

### Worked example

**Simple.** A word-frequency tool. The tracer bullet is: read one file,
split on spaces, count one word, print the count, exit 0, with one test
and a script that runs it in continuous integration. No flags, no Unicode,
no sorting. Day two adds tokenisation; day three adds sorting. The tool ran
end to end from day one.

**Realistic.** A team builds a new ordering system. The tracer bullet is
one product, one hard-coded customer, one button that places an order, an
API endpoint that writes one row, a background job that sends a fake
confirmation, all deployed to a staging environment with logging. It takes
a week. In that week they discover that the payment provider's sandbox
needs a public callback URL, which changes the network design. Discovering
that in month four would have cost far more.

### Step by step

<Figure caption="A tracer bullet versus building layer by layer. Look at week 1: the left side has one finished layer and nothing running; the right side runs end to end." art={`
 LAYER BY LAYER                 TRACER BULLET
 week 1: [ database     ]       week 1: UI -- API -- logic -- DB
 week 2: [ logic        ]               (thin, but it runs)
 week 3: [ API          ]       week 2: thicken logic, add 2nd screen
 week 4: [ UI           ]       week 3: thicken DB, add auth
 week 5: integrate, surprise    week 4: users already testing
`} />

1. **Name every layer** the finished system will cross.
2. **Pick the thinnest real feature** that crosses them all.
3. **Build it to production standards.** Tests, error handling, deployed.
4. **Show it to users.** Adjust the aim based on what they say.
5. **Thicken one layer or add one feature at a time**, keeping it running.

### Common mistake

The mistake is confusing a tracer bullet with a prototype. A prototype is
disposable code that answers one question; a tracer bullet is kept. Writing
a tracer bullet with prototype shortcuts (no tests, hard-coded secrets)
means the shortcuts ship. The fix is to decide which one I am building
before I start, and say so in the repository.

### In real systems

In industry this is called a walking skeleton: the smallest implementation
that exercises the whole architecture, deployed through the real pipeline.
Teams that start with one also get their deployment, monitoring and
continuous integration working in week one, which is when those are
cheapest to set up.

### Check yourself

**What is the key difference between a tracer bullet and a prototype?**

<details>
<summary>Answer</summary>

A tracer bullet is lean but production-quality code that is kept and grown.
A prototype is disposable code written to answer one question and then
thrown away.

</details>

**Why build through every layer instead of finishing one layer first?**

<details>
<summary>Answer</summary>

Integration problems and wrong assumptions surface immediately, users see
something working early, and every later feature lands in a system that
already runs.

</details>

## Topic 13. Prototypes and Post-it Notes

### In one sentence

A prototype is a cheap, disposable experiment built to answer one specific
question, and it is thrown away once it has answered it.

### The idea

Other industries prototype constantly. Car designers build clay models;
architects build cardboard ones. Each prototype is built to learn one thing
cheaply, the shape, the airflow, the light, while ignoring everything else.
Software can do the same.

What should be prototyped? Anything risky, untried or critical: the
architecture, a new feature, a third-party tool's performance, the user
interface, a data structure. The question decides the prototype's form.
A user-interface prototype might be drawn on a whiteboard or made in a
design tool; an architecture prototype might be Post-it notes on a wall.

Because a prototype exists only to answer a question, it can ignore what
does not matter for that question: correctness of unrelated parts,
completeness, robustness, style. That is why it is fast. It is also why it
must be thrown away; the shortcuts make it unfit for production.

The danger is that a working prototype looks like a nearly finished
product to people who do not know it is fake. The book warns to make it
clear to everyone that the code is disposable, and to use a tracer bullet
instead if the audience is likely to treat it as real.

### Worked example

**Simple.** I wonder whether a pure-JavaScript fuzzy search is fast enough
for 20,000 product names in the browser. The prototype is a single file:
generate 20,000 random names, run the library's search 100 times, print
the average time. One hour, one answer, then deleted. No UI, no real data,
no error handling, because none of that affects the question.

**Realistic.** A team is designing a dashboard and is unsure how users want
to filter data. They sketch five layouts on paper, show them to four
users, and learn that users always filter by date first and rarely use the
other filters. That changes the design and the database indexes. Nothing
from the sketches ships; the knowledge does.

### Step by step

<Compare left="Prototype" right="Tracer bullet" caption="Two kinds of early code. Look at the last row: the fate of the code is decided before writing it." rows={[
  ["Answers one question", "Builds the system's skeleton"],
  ["Ignores correctness and robustness on purpose", "Production quality from the start"],
  ["Can be paper, a diagram or throwaway code", "Always real, running code"],
  ["Shown with a clear 'this is fake' label", "Shown as the real system, thin"],
  ["Thrown away", "Kept and thickened"],
]} />

1. **Write the question in one sentence.** "Is search under 50 ms for 20,000
   items?"
2. **List what can be ignored.** Everything not affecting the answer.
3. **Pick the cheapest medium.** Paper, a spreadsheet, a script.
4. **Timebox it.** An hour, a day.
5. **Write down the answer**, then delete the prototype.

### Common mistake

The mistake is letting a prototype become production code. A manager sees
the demo, asks to ship it next week, and the shortcuts become the
foundation. The fix is to label prototypes clearly, keep them in a
separate folder or repository, and use paper or diagrams where possible,
because nobody tries to ship a whiteboard.

### In real systems

Spikes in agile teams are prototypes: timeboxed investigations that end
with knowledge, not code. Load-testing a candidate database with synthetic
data, trying a new framework on a toy app, or mocking a UI in a design tool
are all common examples.

### Check yourself

**Why is a prototype allowed to ignore correctness?**

<details>
<summary>Answer</summary>

It exists only to answer one question, and correctness in unrelated parts
does not affect the answer. Skipping it is what makes it cheap.

</details>

**What is the safest form of prototype when the audience might mistake it for the product?**

<details>
<summary>Answer</summary>

A non-code one, such as a sketch or a diagram, or else switch to a tracer
bullet, which is built to production standards.

</details>

## Topic 14. Domain Languages

### In one sentence

Program close to the problem domain, using its vocabulary, and sometimes
with a small language of its own.

### The idea

The language I write in shapes how I think about the problem. The book
suggests programming close to the domain: write code that uses the
vocabulary of the people the software serves. Sometimes that means a
mini-language, called a domain-specific language, or DSL.

There are two kinds. An internal DSL lives inside a host language, using
its syntax: testing libraries that read like "describe, it, expect" are
examples, as are route definitions in many web frameworks. An external DSL
is a separate language with its own parser: configuration formats, query
languages, or a rules file read by the program.

The trade-offs differ. Internal DSLs get the host language's power and
tools for free, but users must accept that syntax. External DSLs can look
exactly like the domain, but I must write and maintain a parser. A middle
ground is to use an existing data format such as YAML or JSON as the
syntax, and give it domain meaning.

The cost question matters. A DSL is code that must be designed, documented
and maintained. It pays off when non-programmers need to read or write the
rules, or when the rules change often and the language makes them clearer.

### Worked example

**Simple.** Shipping rules as an internal DSL. Each rule reads close to the
policy: a reason, a condition and a fee. The first matching rule wins.

```ts
// A tiny internal domain language for shipping rules, read like the policy.
type Order = { country: string; total: number; weightKg: number };
type Rule = { when: (o: Order) => boolean; fee: number; why: string };
const rule = (why: string, when: Rule['when'], fee: number): Rule => ({ why, when, fee });

const shipping: Rule[] = [
  rule('free over 50 in India', (o) => o.country === 'IN' && o.total >= 50, 0),
  rule('heavy parcels', (o) => o.weightKg > 10, 25),
  rule('domestic default', (o) => o.country === 'IN', 5),
  rule('international default', () => true, 15),
];
const quote = (o: Order) => shipping.find((r) => r.when(o))!;

for (const o of [
  { country: 'IN', total: 80, weightKg: 2 },
  { country: 'IN', total: 20, weightKg: 12 },
  { country: 'US', total: 20, weightKg: 1 },
]) {
  const r = quote(o);
  console.log(`${o.country} ${o.total} ${o.weightKg}kg -> ${r.fee} (${r.why})`);
}
```

The output:

```text
IN 80 2kg -> 0 (free over 50 in India)
IN 20 12kg -> 25 (heavy parcels)
US 20 1kg -> 15 (international default)
```

A product manager can read the rule list and say "the heavy rule should
come before the free rule", and that is a one-line change.

**Realistic.** An operations team describes deployments in YAML: service
name, replicas, health check, environment variables. The YAML is an
external DSL built on an existing format; a deploy tool reads it and
does the work. The team edits deployments without touching the tool's
code.

2. **Write example rules on paper** in those words.

### Common mistake

The mistake is building an external DSL with its own parser when a
function list or a JSON file would do. The parser becomes a project with
bugs and no tooling. The fix is to start internal or data-based, and only
write a parser when users truly need syntax that neither can give.

A subtler mistake is hiding rule order. In the example above, moving the
heavy rule first changes fees. The fix is to make order explicit and test
the cases where rules overlap.

### In real systems

SQL, regular expressions, CSS selectors, build files, infrastructure as
code, feature-flag targeting rules and testing frameworks are all domain
languages in daily production use. Each one lets people say what they mean
in the domain's terms and leaves the how to an engine.

### Check yourself

**What is the difference between an internal and an external DSL?**

<details>
<summary>Answer</summary>

An internal DSL uses a host language's syntax and runs inside it; an
external DSL has its own syntax and needs its own parser or a host data
format.

</details>

**In the shipping rules, why does rule order matter?**

<details>
<summary>Answer</summary>

The first matching rule wins, so overlapping rules give different fees
depending on which comes first. Order is part of the policy.

</details>

## Topic 15. Estimating

### In one sentence

Estimate by building a model of the work, give the answer in units that
show how sure I am, and improve by comparing estimates with actuals.

### The idea

Estimating is a skill, and the book treats it as one I can practise.
Estimation helps everywhere: how long a feature takes, how much memory a
data structure needs, whether a design will be fast enough. A quick
estimate often avoids building something that cannot work.

The first lesson is about accuracy and units. The unit I choose signals
precision. "About three months" and "65 working days" may mean the same
thing, but the second claims accuracy to the day. So I match units to my
confidence: days for days-scale work, weeks for weeks, months for longer.

The second lesson is where estimates come from. Ask someone who has done
it.

Understand what is being asked, including the scope. Build a model of
the system or the work, break it into parts, give each part a number, and
combine them. The model is often more valuable than the number, because it
shows what drives the cost.

The third lesson is about tracking. Record estimates and compare them with
what actually happened.

When I was wrong, I find out why. For project
schedules, the book recommends iterating the schedule with the code:
estimate the next iteration, build it, and refine the rest based on what
it took. When asked for an estimate on the spot, it is fine to say "I will
get back to you".

### Worked example

**Simple.** Will a list of 10 million user IDs fit in memory? Each ID is a
JavaScript number, which takes 8 bytes in a typed array. 10 million times 8
bytes is 80 MB. That fits on a laptop. Stored as an ordinary array of
strings it could be several times larger, so the model also tells me the
storage choice matters.

**Realistic.** A three-point estimate for three tasks: an optimistic, a
most-likely and a pessimistic number. The weighted formula, (O + 4M + P) /
6, is the classic PERT method, and the spread (P minus O) / 6 is a rough
standard deviation.

```ts
// Estimating with three points: optimistic, most likely, pessimistic.
type Task = { name: string; o: number; m: number; p: number };
const tasks: Task[] = [
  { name: 'login form', o: 1, m: 2, p: 5 },
  { name: 'password reset email', o: 0.5, m: 1, p: 4 },
  { name: 'rate limiting', o: 1, m: 3, p: 8 },
];
let mean = 0, variance = 0;
for (const t of tasks) {
  const e = (t.o + 4 * t.m + t.p) / 6;
  const sd = (t.p - t.o) / 6;
  mean += e; variance += sd * sd;
  console.log(`${t.name.padEnd(22)} expected ${e.toFixed(2)} days, spread ${sd.toFixed(2)}`);
}
const sd = Math.sqrt(variance);
console.log(`total ${mean.toFixed(1)} days, likely range ${(mean - sd).toFixed(1)} to ${(mean + sd).toFixed(1)}`);
```

The output:

```text
login form             expected 2.33 days, spread 0.67
password reset email   expected 1.42 days, spread 0.58
rate limiting          expected 3.50 days, spread 1.17
total 7.3 days, likely range 5.8 to 8.7
```

So the honest answer is "about a week and a half, possibly two", not "7.3
days". The decimals come from arithmetic, not from knowledge.

2. **Build a model.** Break the work into tasks small enough to picture.
3. **Estimate each part as a range**, not a point.
4. **Combine and round to honest units.**
5. **Record the estimate**, then the actual, and review the gap.

### Common mistake

The mistake is giving a single precise number under pressure, then
treating it as a promise. The fix is to answer with a range and its
assumptions, or to say "let me check and get back to you this afternoon".

Another is never comparing estimates with actuals, so I never get better.
The fix is a two-column log, estimate and actual, reviewed monthly.

### In real systems

Capacity planning (how many servers for next year's traffic), cost
estimates for cloud bills, and back-of-the-envelope latency calculations in
system design are all estimating. Teams that track estimate accuracy over
time are the ones whose release dates mean something.

### Check yourself

**Why is "65 working days" a riskier answer than "about three months"?**

<details>
<summary>Answer</summary>

The unit claims precision to the day, which the estimate does not have.
Listeners will hold me to that implied precision.

</details>

**What is the most valuable output of estimating, besides the number?**

<details>
<summary>Answer</summary>

The model of the work: it shows which parts drive the cost and the risk,
and what to watch.

</details>

## From beginner to strategy

<Levels label="Chapter 2, A Pragmatic Approach">

<Level name="Beginner" depth={3}>

The smallest version of this chapter is three questions I ask while
coding. Does this make the code easier to change?

Is this fact already
written somewhere else? Does this run end to end yet? Asking them every day
is most of the chapter.

A worked example: I am adding a discount code to a checkout. Before coding,
I search for where prices are computed and find one function, so I add the
discount there instead of in the UI. Then I wire the smallest version
through the form, the API and the database, and run it, before handling
expiry dates or limits.

The beginner mistake is building one layer perfectly before connecting
anything. Fix: connect first, perfect later.

</Level>

<Level name="Intermediate" depth={3}>

In a real program the principles combine. DRY gives each fact a home;
orthogonality keeps the homes independent; reversibility puts the risky
homes behind interfaces. A tracer bullet then proves the whole arrangement
runs.

Concretely, a word-frequency tool built this way has a `fields`-style
single source for its output columns (DRY), separate read, tokenize, count
and format modules (orthogonality), a `Reader` interface so stdin and files
are interchangeable (reversibility), and an end-to-end test written on the
first day (tracer bullet).

The intermediate mistake is applying DRY across module boundaries in a way
that creates coupling: a shared "utils" file every module imports. Fix:
share knowledge only when it truly changes for the same reason, and prefer
a small duplicate to a wide dependency.

</Level>

<Level name="Advanced" depth={3}>

Underneath, the chapter is about managing the cost of change under
uncertainty. ETC defines the goal.

DRY and orthogonality reduce how many
places a change touches. Reversibility reduces how expensive a wrong
decision is. Tracer bullets and prototypes reduce uncertainty itself, and
estimating makes the remaining uncertainty explicit.

There is a precise way to think about DRY versus orthogonality. DRY reduces
the number of places a single fact lives. Orthogonality reduces the number
of modules a single change touches. Removing duplication can add a
dependency, so the two can conflict, and the tie-breaker is ETC: which
version makes the likely changes cheaper?

The advanced mistake is treating these as laws rather than heuristics with
costs. Fix: for each abstraction, be able to say which likely change it
makes cheaper.

</Level>

<Level name="Edge cases" depth={3}>

**One implementation forever.** If a component will never be replaced, a
reversibility interface is pure cost. The fake test still helps for unit
tests, so the interface may earn its place there instead.

**Duplicated test data.** Tests often repeat values on purpose so each
test reads alone. That is acceptable duplication: the values are
examples, not shared knowledge.

**An estimate for something never done before.** There is no history to
draw on. The answer is a wide range plus a prototype to narrow it.

**A tracer bullet with no users yet.** The feedback comes from the system
itself, integration and deployment, until users can see it.

</Level>

<Level name="Corner cases" depth={3}>

**DRY meets orthogonality.** Two services both validate email addresses.
Sharing a library removes duplication but means a library release now
touches both deploys. If the rule truly must match, share it; if each
service can evolve its own rule, duplicate it.

**Prototype meets deadline.** The prototype worked and the date is close.
Shipping it combines throwaway quality with production traffic. The safe
version is to ship a tracer bullet built from what the prototype taught,
behind a flag.

**Domain language meets estimating.** A rules DSL makes rule changes fast,
which makes estimates for rule changes small, but a change to the DSL
itself is expensive. Estimate the two kinds of change separately.

</Level>

<Level name="Production level" depth={3}>

In production, the chapter turns into specific practices. DRY becomes
schema-first APIs with generated clients and types.

Orthogonality becomes
service boundaries and blast-radius limits. Reversibility becomes feature
flags, canary deploys and down migrations. Tracer bullets become a walking
skeleton deployed through the real pipeline in week one.

Estimating becomes capacity and cost planning. For example, a new feature
that writes one 2 KB row per user action, at 5 million actions a day, adds
about 10 GB a day, roughly 3.6 TB a year before indexes. That estimate
decides retention and partitioning before the first line is written.

The production mistake is a flag or adapter that is never removed. Each
one is a reversibility tool turned into a broken window. Fix: every flag
has an owner and a removal date.

</Level>

<Level name="Mindset" depth={3}>

The habit of thought is that every decision is a bet that can be
revisited, so I keep bets small and cheap to undo. I build to learn, I
measure, and I adjust.

It shows up outside code. A career move can be a tracer bullet (try a
project in the new area) rather than a leap. A big purchase can be
prototyped (rent before buying). A plan can be estimated as a range and
revised as information arrives.

The mindset mistake is mistaking confidence for knowledge: a precise
number or a firm architecture feels safer than a range and a seam, but it
only hides the uncertainty. Fix: say how sure I am, every time.

</Level>

<Level name="System design" depth={3}>

At system scale, take a food-delivery platform. ETC and orthogonality shape
the service split: orders, payments, dispatch and notifications, each
changeable without the others. DRY means the order schema lives in one
contract that every service generates code from.

Reversibility puts the mapping provider and the payment provider behind
interfaces, because both are likely to change for cost reasons. The first
release is a tracer bullet: one restaurant, one rider, one city, through
every service, deployed. The estimate for city two is then based on city
one's real numbers.

The mistake is splitting services before the domain is understood, which
makes boundaries wrong and expensive to move. Fix: start with orthogonal
modules in one deployable, and split along boundaries the tracer bullet
proved.

</Level>

<Level name="Strategy" depth={3}>

I apply this chapter to the Phase 1 command-line project in the
<a href={withBase('/plans/traditional-software-developer/')}>traditional core</a>:
tracer bullet on day one, one module per concern, one source for each
fact, and an estimate before every phase, logged against actuals.

I know I have learned it when my repository history shows it: the first
commit runs end to end, later commits each touch one module, and my
estimate log shows my accuracy improving over three phases.

Done when the project history shows a tracer bullet first, a later feature
that changed exactly one module, one vendor or I/O choice behind an
interface with a fake, and an estimate log with at least five estimate and
actual pairs.

</Level>

</Levels>

## Questions people ask

<details>
<summary>Is DRY the same as "never copy and paste"?</summary>

No. DRY is about knowledge. Copying code that expresses a different rule is
fine; writing one rule in two places, even in different forms, is the
problem.

</details>

<details>
<summary>How thin should a tracer bullet be?</summary>

As thin as possible while still crossing every layer the real system will
have, including deployment. If it skips a layer, that layer's surprises
are still waiting.

</details>

<details>
<summary>When is a domain-specific language worth building?</summary>

When non-programmers need to read or write the rules, or the rules change
often enough that clarity saves real time. Start with functions or a data
file before writing a parser.

</details>

<details>
<summary>What if my manager wants a single number, not a range?</summary>

Give the range and the assumptions, then the number I would commit to with
its confidence, for example "four weeks, with a real risk of six if the
vendor API is late".

</details>

<details>
<summary>Does reversibility mean wrapping every library?</summary>

No. Wrap the choices that are both likely to change and expensive to
change. Everything else, keep simple and isolated.

</details>

## Key takeaways

- Judge every design choice by whether it makes the code easier to change.
- DRY means one home per piece of knowledge, not "no repeated lines".
- Orthogonal components change independently, which raises productivity and contains defects.
- There are no final decisions, so put the risky ones behind narrow interfaces.
- Build a production-quality tracer bullet through every layer first, then thicken it.
- Prototypes answer one question and are thrown away; label them clearly.
- Write code in the domain's vocabulary, and make rule order explicit.
- Estimate with a model and a range, in honest units, and track estimates against actuals.

## Glossary

- **ETC (Easier To Change)**: the book's single test for good design.
- **DRY (Don't Repeat Yourself)**: every piece of knowledge has one authoritative representation.
- **Representational duplication**: the same knowledge described in two places, such as a client and a server.
- **Orthogonality**: independence of components, so a change in one does not affect the other.
- **Coupling**: the degree to which one part of a system depends on another.
- **Blast radius**: how much of a system a single change or failure affects.
- **Reversibility**: keeping the cost of changing a decision low.
- **Leaky abstraction**: an interface that exposes details of one implementation.
- **Fake**: a simple in-memory implementation of an interface, used in tests.
- **Tracer bullet (walking skeleton)**: a thin, kept, production-quality slice through every layer.
- **Prototype (spike)**: disposable code or material built to answer one question.
- **DSL (domain-specific language)**: a small language for one problem domain, internal or external.
- **PERT estimate**: a three-point estimate weighted as (optimistic + 4 × likely + pessimistic) / 6.
- **Velocity**: measured work completed per iteration, used to refine schedules.

## Exercises and self-check

The book has short exercises after several of these topics; do them in
writing too. These are my own.

**Warm-up (by hand).**

1. Take a small project of mine and list three facts that live in more
   than one place. Name the authoritative home for each.
2. Draw the layers of a web app I know and mark one change that crosses
   more layers than it should.
3. Estimate, with units and a range, how long it takes to read this
   chapter of the book, then time it.

**Build (code and test).**

4. Build the word-frequency tool as a tracer bullet: commit one, end to
   end with a test and a CI script; then four commits, each touching one
   module.
5. Put file reading behind a `Reader` interface with two implementations,
   file and string, and test the counter using the string one.
6. Extend the shipping DSL with a rule for "express" orders, and write tests
   for every pair of rules that overlap.

**Stretch (change the problem).**

7. Two services validate phone numbers the same way. Argue both for and
   against sharing a library, using ETC as the deciding question.
8. Rerun the three-point estimate with every pessimistic value doubled.
   How much does the total range move, and what does that say about where
   the risk sits?
