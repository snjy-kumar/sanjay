Coding is not just typing out a design; it is where most decisions are
really made. This chapter is about staying awake while I write code:
listening to doubt, knowing why the code works, estimating its speed,
reshaping it as I learn, letting tests shape it, keeping it safe, and
naming things so they say what they mean. It has eight topics, the most of
any chapter.

## Before you start

After this chapter I will be able to:

- treat hesitation while coding as a signal, and act on it;
- tell when code works by coincidence, and program deliberately instead;
- estimate an algorithm's order of growth and test the estimate;
- refactor in small, tested steps as a routine part of coding;
- use tests as a design tool, and write property-based tests that find edge cases I did not think of;
- apply basic security principles, and name things so the name reveals intent.

What I should already know: functions, arrays and loops in TypeScript or
JavaScript, and the contracts idea from
<a href={withBase('/books/the-pragmatic-programmer/04-pragmatic-paranoia/')}>chapter 4</a>.
The
<a href={withBase('/books/the-pragmatic-programmer/06-concurrency/')}>previous chapter</a>
covered concurrency; this one comes back to the code in front of me.

Reading time: about 80 minutes for this page, plus three hours for the
exercises.

## Topic 37. Listen to Your Lizard Brain

### In one sentence

When coding feels unusually hard or wrong, that feeling is my experience
noticing a problem before I can name it, so I stop and find out why.

### The idea

The book borrows from Gavin de Becker's writing about fear: instincts are
the brain recognising patterns below conscious thought. The "lizard brain"
is the book's name for that part. For a programmer, its signals are a
nagging doubt, a reluctance to start, code that keeps fighting back, or
each change seeming to need three more.

The tip is to listen to my inner lizard. Experience builds up a store of
patterns, such as designs that went badly, and the instinct fires when the
current situation matches one. Ignoring it means pushing on until the
problem becomes obvious, usually later and at greater cost.

#### Fear of the blank page

One form of hesitation is not wanting to start. The book suggests two
causes: my instincts sense a problem with the approach, or I am afraid of
making a mistake. For the first, I should look for the doubt. For the
second, the answer is to start with something explicitly disposable, a
prototype, so mistakes are cheap.

#### When code fights back

When code becomes hard to write, the book suggests stopping and giving the
instinct a chance to speak. Step away for a walk, sleep on it, or explain
the problem out loud, rubber-duck style.

If that does not help, write a
quick prototype of the troublesome part. Tell myself it is throwaway, then
write it. Often, partway through, the real problem becomes clear: a wrong
assumption, a missing abstraction, a design that does not fit.

#### Instinct with other people's code

The same applies to reading code. Patterns that feel strange in someone
else's code may be signs of a constraint I do not know about, or of a real
problem. The instinct is a prompt to ask, not a verdict.

### Worked example

**Simple.** I am adding a field to a form, and it needs changes in seven
files. Each change is easy, but I feel growing reluctance. I stop and ask
why. The answer: the field's name, type and validation are repeated in the
form, the API, the model, the database and two tests. The instinct was
pointing at a DRY problem, and the right next step is to centralise the
schema, not to make change number seven.

**Realistic.** I am integrating a payment provider and keep putting it
off. I write down what bothers me: I do not understand how their webhooks
handle retries. I spend an hour on a throwaway script that triggers a test
webhook and logs every retry. It turns out retries can arrive out of order,
which would have broken the design I was about to write.

### Step by step

<Flow caption="What to do when the lizard brain speaks. Look at the fourth step: the prototype is explicitly throwaway, which removes the fear of getting it wrong." steps={[
  "Notice the hesitation",
  "Stop typing",
  "Step away or explain it aloud",
  "Prototype the hard part, throwaway",
  "Name the problem and change course",
]} />

1. **Notice the signal.** Reluctance, repeated friction, a vague worry.
2. **Stop.** Pushing on makes the problem bigger.
3. **Give it room.** Walk, sleep, explain it to someone or something.
4. **Prototype the troublesome part** if it is still unclear.
5. **Write down what I learned** and adjust the plan.

### Common mistake

The common mistake is treating hesitation as laziness and forcing through
it. The fix is to give the feeling ten minutes of attention before
deciding it means nothing.

The opposite mistake is never starting because something feels off. The
fix is the throwaway prototype: it turns vague doubt into concrete
information quickly.

### In real systems

Teams build this into process with spikes, short time-boxed explorations
before committing to a design. Code review comments like "something feels
off here" are valued in good teams, and followed up with a question rather
than dismissed.

### Check yourself

**What does the book suggest when I am afraid to start?**

<details>
<summary>Answer</summary>

Start with something explicitly disposable, such as a prototype, so that
mistakes cost nothing and the real problems surface.

</details>

**What should I do when code keeps fighting back?**

<details>
<summary>Answer</summary>

Stop, step away or explain the problem aloud, and if needed prototype the
troublesome part to find the wrong assumption or missing piece.

</details>

## Topic 38. Programming by Coincidence

### In one sentence

Code that works without me knowing why is working by coincidence, and it
will stop working without warning, so I program deliberately.

### The idea

#### The minefield

The book's image is a soldier crossing a minefield who takes a few steps
and nothing explodes, so concludes the field is safe. Code can be like
that. I try something, it seems to work, so I keep it. But I do not know
why it works, so I do not know what will make it stop.

#### Kinds of coincidence

The book lists several. **Accidents of implementation** are cases where
code relies on behaviour that happens to be true today, such as an
undocumented ordering or a bug in a library that my code depends on.

**Accidents of context** are assumptions about the environment, such as a
time zone, a locale, a user being online or a screen size. **Implicit
assumptions** are beliefs that were never checked, such as "the list is
sorted" or "this will be called once". And **phantom patterns** are
coincidences that look like causes, such as a bug that seems to happen only
on Fridays.

The book's point is that "it works" is not the same as "it is correct",
and the gap between them is where the hardest bugs live. The tip: don't
program by coincidence.

#### Programming deliberately

The book's list for deliberate programming, in my words:

- always be aware of what I am doing;
- be able to explain the code to a more junior programmer;
- do not code blindfolded, in an unfamiliar technology, without learning it first;
- proceed from a plan, however small;
- rely only on reliable, documented behaviour;
- document assumptions, and test them, ideally with assertions;
- prioritise the important and hard parts first;
- do not be a slave to history: existing code can be changed if it no longer fits.

#### Phantom patterns and the history trap

Humans are built to see patterns, even in noise. A test that fails "only
when the build server is busy" or a crash "only for users in Pune" may be a
real clue or a coincidence of a few samples. The deliberate response is to
treat the pattern as a hypothesis and test it, as in chapter 3's
debugging, rather than building a fix around it.

The last item on the book's list deserves its own note. Code often stays
the way it is because it has always been that way.

A workaround for a
browser bug fixed years ago, a retry loop for a service that no longer
exists, a sleep added "because it made the test pass". Each is a
coincidence preserved by history. Programming deliberately includes asking
why old code is there, and removing it when the reason has gone.

### Worked example

**Simple.** Sorting numbers with JavaScript's default `sort`:

```ts
// Programming by coincidence: default sort "works" on the test data.
const tested = [3, 1, 2];
console.log('test data:', [...tested].sort());
const real = [10, 9, 1, 100];
console.log('real data:', [...real].sort());
console.log('deliberate:', [...real].sort((a, b) => a - b));
```

The output:

```text
test data: [ 1, 2, 3 ]
real data: [ 1, 10, 100, 9 ]
deliberate: [ 1, 9, 10, 100 ]
```

On single-digit test data, the default sort looks right. It is actually
sorting the numbers as strings, so "10" comes before "9". The code worked
by an accident of the test data. The deliberate version states the rule.

**Realistic.** A report job runs at 2 am and has always worked. The
company moves servers to a region where the clock is UTC. The job now
runs during the previous business day and includes half a day of data.
The code had relied on an accident of context, the server's time zone,
which nobody had written down. The deliberate fix is an explicit time zone
in the schedule and the date logic, plus a test that runs the date logic in
two zones.

### Step by step

<Compare left="By coincidence" right="Deliberately" caption="Two ways to reach working code. Look at the last row: only one of them knows what would break it." rows={[
  ["Tried things until it worked", "Followed a plan and understood each step"],
  ["Relies on whatever the runtime did", "Relies on documented behaviour"],
  ["Assumptions in the author's head", "Assumptions written and tested"],
  ["Cannot say what would break it", "Can list what would break it"],
]} />

1. **Ask why it works.** Can I explain each line?
2. **Check what I rely on** against documentation, not observation.
3. **List the assumptions**: order, environment, timing, input shape.
4. **Turn each assumption into a test or an assertion.**
5. **Fix code that only works by luck**, even if it currently passes.

### Common mistake

The common mistake is fixing a bug by changing things until the symptom
goes away, without understanding the cause. The bug often comes back in a
different form. The fix is to find the cause first, as in chapter 3's
debugging, and change only what the cause explains.

### In real systems

Upgrades expose coincidences: a new library version changes undocumented
ordering, and code that relied on it breaks. Teams that pin versions,
read changelogs, and test against documented behaviour see fewer
surprises.

### Check yourself

**Why does `[10, 9, 1, 100].sort()` give the wrong order?**

<details>
<summary>Answer</summary>

The default sort compares values as strings, so "10" sorts before "9". It
looks right on single-digit data by coincidence.

</details>

**What is an accident of context?**

<details>
<summary>Answer</summary>

Code relying on something about its environment, such as time zone,
locale or network, that was never stated or checked.

</details>

## Topic 39. Algorithm Speed

### In one sentence

Before writing code that processes data, I estimate how its running time
grows with the input, and then measure to check.

### The idea

#### Big-O in practice

The book uses **Big-O notation** as a way to describe how resource use,
usually time, grows as the input size n grows. It ignores constant factors
and smaller terms: an algorithm that takes 3n squared plus 2n steps is
order n squared. The point is not precision but shape. Doubling the input
roughly doubles an order-n algorithm's time and quadruples an order-n-squared
one.

#### Common-sense estimation

The book gives rules of thumb:

| Code shape | Order | Doubling n does this |
|---|---|---|
| A simple loop over the input | n | Doubles the time |
| A loop inside a loop | n squared | Quadruples the time |
| Halving the problem each step, as in binary search | log n | Adds one step |
| Split, solve halves, combine, as in merge sort | n log n | A little over double |
| Trying every combination | 2 to the n, or n factorial | Explodes |

The tip: estimate the order of your algorithms. A hidden loop inside a
loop, such as calling `indexOf` or `includes` on an array inside a
`filter`, is the most common source of surprise.

#### Test the estimate

The second tip is to test the estimate. Theory can be wrong about real
code: caches, memory allocation and library internals all matter. Timing
the code at a few sizes and checking how the time grows confirms the
order.

#### Best is not always best

The book adds that the fastest algorithm is not always the right one. For
small inputs, a simple order-n-squared approach may be faster than a clever
one with high constant costs, and is easier to get right. Premature
optimisation wastes time. The goal is to know the order, so I can choose
deliberately and avoid surprises when data grows.

### Worked example

**Simple.** Two ways to remove duplicates, timed at three sizes:

```ts
// Algorithm speed: O(n^2) versus O(n) duplicate removal.
const dedupeSlow = (xs: number[]) => xs.filter((x, i) => xs.indexOf(x) === i);
const dedupeFast = (xs: number[]) => [...new Set(xs)];
for (const n of [1_000, 10_000, 40_000]) {
  const xs = Array.from({ length: n }, (_, i) => i % (n / 2));
  let t = performance.now(); const a = dedupeSlow(xs); const slow = performance.now() - t;
  t = performance.now(); const b = dedupeFast(xs); const fast = performance.now() - t;
  console.log(`n=${String(n).padStart(6)}  slow ${slow.toFixed(1).padStart(7)} ms  fast ${fast.toFixed(2).padStart(5)} ms  same=${a.length === b.length}`);
}
```

The output on my machine:

```text
n=  1000  slow     0.4 ms  fast  0.06 ms  same=true
n= 10000  slow    28.1 ms  fast  1.22 ms  same=true
n= 40000  slow   391.9 ms  fast  2.81 ms  same=true
```

`indexOf` inside `filter` is a loop inside a loop. From 10,000 to 40,000
items, four times the input, the slow version takes about 14 times longer,
close to the 16 times order n squared predicts. The `Set` version grows
roughly in line with n. At a thousand items both are instant, so the slow
one would pass every small test.

**Realistic.** A page shows a user's notifications, checking for each one
whether it is in a "read" array. With fifty notifications nobody notices.
A power user with twenty thousand notifications and fifteen thousand read
ones makes the page freeze. Turning the read array into a `Set` makes the
check constant time and the page instant.

### Step by step

<Trace columns={["n", "Slow (ms)", "Ratio to previous", "Fast (ms)"]} rows={[
  ["1,000", "0.4", "", "0.06"],
  ["10,000", "28.1", "about 70x for 10x n", "1.22"],
  ["40,000", "391.9", "about 14x for 4x n", "2.81"],
]} caption="The measured times. Look at the ratio column: growth near n squared confirms the estimate from the code's shape." />

1. **Find the loops**, including hidden ones such as `indexOf`,
   `includes`, `find` and `filter` inside another loop.
2. **Estimate the order** from the nesting.
3. **Ask how big n will really get** in production.
4. **Measure at two or three sizes** and compare the ratio to the estimate.
5. **Change the algorithm or data structure** only if the real n needs it.

### Common mistake

The common mistake is testing only with small data, where every algorithm
is fast. The fix is a test or benchmark with realistic production sizes.

The opposite mistake is optimising code that runs on ten items. The fix is
to measure first.

### In real systems

Database queries have orders too: a missing index turns a lookup into a
full table scan. Query planners, profilers and load tests reveal these.
Many production slowdowns are a loop inside a loop that was invisible at
launch size.

### Check yourself

**What is the order of `xs.filter(x => ys.includes(x))`?**

<details>
<summary>Answer</summary>

About n times m, since `includes` loops over ys for each element of xs.
With both the same size, that is n squared.

</details>

**Why measure after estimating?**

<details>
<summary>Answer</summary>

Real performance depends on caches, memory and library internals, so
measurement confirms whether the estimate holds for the actual code.

</details>

## Topic 40. Refactoring

### In one sentence

Refactoring is restructuring code without changing its behaviour, done
continually in small tested steps, like tending a garden rather than
rebuilding a house.

### The idea

#### Gardening, not building

The book contrasts two metaphors. Building suggests a plan, construction,
then occasional maintenance. Software is more like a garden: things grow,
some plans fail, plants need moving and pruning. Code needs the same
ongoing care.

The book uses Martin Fowler's definition: **refactoring** is a disciplined
technique for restructuring an existing body of code, altering its
internal structure without changing its external behaviour. Two parts
matter: the behaviour does not change, and the technique is disciplined,
done in small steps, not a free-form rewrite.

#### When to refactor

The book lists triggers: duplication, a design that is not orthogonal,
knowledge that has become outdated, how the code is actually being used,
performance needs, and passing tests, which mark a good moment to clean up.
The tip: refactor early, refactor often. Small problems are cheap to fix;
left alone, they grow.

The book compares it to a tumour: delay makes removal harder. When the
schedule pressure argument comes up, the book suggests explaining it as
debt: not refactoring now borrows time that will be paid back with
interest.

#### How to refactor

Fowler's advice, as the book summarises it:

1. Do not refactor and add functionality at the same time.
2. Make sure there are good tests before refactoring, and run them often.
3. Take short, deliberate steps, such as moving a field, renaming a
   method, or extracting a function, testing after each.

Editors and IDEs automate many of these steps, such as rename and extract
function, which makes them safer.

#### Making the case for refactoring

Refactoring can be hard to justify to people who see only features. The
book's suggestion is to talk about it in terms they already understand.
Not refactoring is like not paying down debt: every new feature built on
messy code costs more, and the interest compounds. Another framing is
risk: a module nobody dares to change is a module that will cause the
next incident.

The easiest path, though, is to make refactoring too small to need
permission. A rename here, an extracted function there, done as part of
the feature that touches the code, takes minutes and never appears as a
separate line item. Large refactors still need planning, but most of the
value comes from the small, continuous kind.

### Worked example

**Simple.** A function computes a shipping price with nested conditions.
The tests for it pass. I extract "is this a remote area" into its own
named function, run the tests, then extract "weight band", run the tests,
then replace a chain of `if` statements with a lookup table, and run the
tests again. Behaviour is unchanged at each step; the function goes from
40 lines to 12, and the next change, adding a new band, is a single table
row.

**Realistic.** A team needs to add a second payment provider. The existing
code calls the first provider's SDK in twelve places. Before adding
anything, they refactor: introduce a `PaymentGateway` interface, move all
twelve calls behind it, with all tests passing and no behaviour change.
That is one pull request. Adding the second provider is then a separate
pull request that implements the interface. Mixing the two would have made
any bug impossible to attribute.

### Step by step

  "Tests pass",
  "Pick one small structural change",
  "Make it",
  "Run the tests",
  "Commit, then repeat",
]} />

<Timeline caption="Adding a payment provider in two phases. Look at the gap between phases: behaviour is unchanged until the second one starts." items={[
  { label: "Step 1", text: "Add tests around current payment behaviour." },
  { label: "Step 2", text: "Introduce PaymentGateway interface; one call moved; tests pass." },
  { label: "Step 3", text: "Move remaining eleven calls, one commit each; tests pass." },
  { label: "Step 4", text: "Separate change: implement the second provider." },
]} />

1. **Make sure tests cover the behaviour** I am about to touch.
2. **Choose one small change.** A rename, an extract, a move.
3. **Make it and run the tests.**
4. **Commit.** A green commit is a safe point to return to.
5. **Never mix with new behaviour.** New features go in separate commits.

### Common mistake

The common mistake is a "refactoring" that is really a rewrite, done in a
week-long branch with no tests passing until the end. The fix is to keep
the tests green after every small step and merge often.

Another mistake is refactoring without tests and hoping. The fix is to
write characterisation tests first, tests that pin down what the code does
today, even if it is odd.

### In real systems

Teams fold refactoring into normal work: leave code a little better than I
found it, the broken windows idea from chapter 1. Automated refactoring
tools, code review that welcomes cleanup, and fast test suites make it
cheap enough to do daily.

### Check yourself

**What are the two essential parts of the definition of refactoring?**

<details>
<summary>Answer</summary>

External behaviour does not change, and it is done as a disciplined series
of small steps.

</details>

**Why not refactor and add a feature in the same change?**

<details>
<summary>Answer</summary>

If something breaks, I cannot tell whether the structure change or the new
behaviour caused it, and reviewers cannot check either properly.

</details>

## Topic 41. Test to Code

### In one sentence

Testing is mainly a design activity, not a bug hunt: thinking about how to
test a piece of code makes me design it better.

### The idea

#### Tests as the first user

The book makes a claim that surprised me: the major benefit of testing
happens when I think about and write the test, not when I run it. A test is
the first user of my code. If it is awkward to set up, such as needing a
database, a network and a clock, the code is too coupled. Writing the test
gives that feedback while the design is still easy to change.

So the book's tip: a test is the first user of your code. And the
consequence: design to test. Code that is easy to test tends to be
decoupled, with clear inputs and outputs.

#### Test-driven development

The book discusses **test-driven development**, TDD, a cycle: decide on a
small piece of behaviour, write a test that fails, write the least code
that makes it pass, refactor, repeat. It values TDD as a way to keep
thinking about tests, but warns of traps: chasing 100 percent coverage,
writing redundant tests, and building bottom-up without a sense of the
whole. Its phrase: build end to end, not top-down or bottom-up. TDD works
best when I know where I am going.

#### What and how to test

The book lists kinds of testing worth knowing: **unit tests** for a module
in isolation, tested against its contract from chapter 4; integration
tests across modules; and ad hoc testing while debugging. When I find a bug
by hand, the book says to turn the check into an automated test so it
cannot return.

It also suggests building a test window into the code, such as log
messages, a diagnostic endpoint, or a hot key, so the running system can
be inspected.

#### A testing culture

The book's last word: all software is tested, if not by me then by my
users. The tip: test your software, or your users will. It suggests
thinking of tests as code like any other, kept in version control, run on
every change.

### Worked example

**Simple.** A `slugify` function for page addresses, with a table of
cases written while designing it. Writing the cases first made me decide
what to do with accents, punctuation and empty input before I coded it.

```ts
// Test to code: a small unit test with node:assert, written before the function was finished.
import assert from 'node:assert/strict';
function slugify(title: string): string {
  return title.toLowerCase().normalize('NFKD').replace(/[\u0300-\u036f]/g, '')
    .replace(/[^a-z0-9]+/g, '-').replace(/^-+|-+$/g, '');
}
const cases: [string, string][] = [
  ['Hello World', 'hello-world'],
  ['  Bend, or Break!  ', 'bend-or-break'],
  ['Café déjà vu', 'cafe-deja-vu'],
  ['', ''],
];
for (const [input, want] of cases) assert.equal(slugify(input), want, `slugify(${JSON.stringify(input)})`);
console.log(`${cases.length} slugify cases pass`);
```

The output:

```text
4 slugify cases pass
```

The accent case came from thinking about the test: the first draft of
`slugify` turned "Café" into "caf". Without the test, that would have
reached users as a broken link.

**Realistic.** A service that sends reminder emails reads the current time
inside the function. Writing a test for "sends a reminder 24 hours
before" is awkward: it needs to fake the clock. That awkwardness is the
design feedback. The fix is to pass the current time in as a parameter.
The test becomes one line, and the function can now also be used to
preview tomorrow's reminders.

### Step by step

<Flow caption="The test-driven cycle. Look at the last step: refactoring happens while the tests are green, which is what makes it safe." steps={[
  "Choose one small behaviour",
  "Write a failing test",
  "Write just enough code to pass",
  "Run all tests: green",
  "Refactor, then repeat",
]} />

1. **Before coding, write how I would test it.** Even as a list.
2. **If the test is awkward, change the design.** Pass dependencies in.
3. **Test against the contract**, including edge cases.
4. **Turn every bug found by hand into a test.**
5. **Run the tests on every change**, locally and in CI.

### Common mistake

The common mistake is writing tests after the code, only to raise
coverage, testing implementation details rather than behaviour. Those
tests break on every refactor and catch little. The fix is to test what the
code promises, through its public interface.

### In real systems

CI runs the full suite on every pull request; failing tests block merges.
Good teams track flaky tests and fix them, since a test that sometimes
fails teaches everyone to ignore failures.

### Check yourself

**Why does the book say most of testing's value comes before the test runs?**

<details>
<summary>Answer</summary>

Thinking about how to test the code reveals coupling and unclear
contracts while the design is still easy to change.

</details>

**What should I do after finding a bug by hand?**

<details>
<summary>Answer</summary>

Write an automated test that reproduces it, so it cannot come back
unnoticed.

</details>

## Topic 42. Property-Based Testing

### In one sentence

Instead of writing individual examples, I state properties that must hold
for every input and let a tool generate hundreds of random inputs to try to
break them.

### The idea

#### Our own assumptions

The book points out a weakness of hand-written tests: I write the code and
the tests, so both share my assumptions. If I did not think of an edge
case while coding, I will not think of it while testing. Something else
needs to choose the inputs.

#### Properties

A **property** is a statement that should be true for any valid input,
often a contract or invariant from chapter 4. For a sort function: the
output has the same length as the input, contains the same elements, and
each element is no greater than the next. A **property-based test**
generates many random inputs, checks the property on each, and reports a
failing input. Good tools also **shrink** the failing input to the
smallest one that still fails, which makes the bug easy to see.

The book's examples use the Hypothesis library in Python. In JavaScript
the common library is fast-check. The tip: use property-based tests to
validate your assumptions.

#### What they find

The book shows property tests finding bugs in a warehouse stock example
that example-based tests missed, because the random inputs included
combinations the author had not imagined. It also notes a side benefit:
properties document what the code is supposed to guarantee, more
generally than examples do.

### Worked example

**Simple.** A `chunk` function splits a list into groups of a given size.
A natural property is that flattening the chunks gives back the input.
This version has an off-by-one bug, and a small hand-rolled property test
with a seeded random generator finds it:

```ts
// Property-based testing by hand: random inputs, a property, and the first failing case.
function chunk<T>(xs: T[], size: number): T[][] {     // buggy: drops a short last chunk
  const out: T[][] = [];
  for (let i = 0; i + size <= xs.length; i += size) out.push(xs.slice(i, i + size));
  return out;
}
let seed = 7; const rand = (n: number) => (seed = (seed * 48271) % 2147483647) % n;
for (let run = 1; run <= 100; run++) {
  const xs = Array.from({ length: rand(10) }, () => rand(100)); const size = 1 + rand(4);
  const flat = chunk(xs, size).flat();
  if (flat.length !== xs.length) {
    console.log(`run ${run}: property "chunks flatten back to the input" fails`);
    console.log(`  xs=${JSON.stringify(xs)} size=${size} got ${JSON.stringify(chunk(xs, size))}`);
    break;
  }
}
```

The output:

```text
run 1: property "chunks flatten back to the input" fails
  xs=[58,14,77,5,34,86,41] size=3 got [[58,14,77],[5,34,86]]
```

Seven items in chunks of three leave one over, and the loop condition
drops it. My hand-written examples had used six items and size three,
which divide evenly. Changing the condition to `i < xs.length` fixes it,
and the same loop then completes all 100 runs without a failure. A real
library would also shrink the failing case to something like one item with
size two.

**Realistic.** A money-splitting function divides a bill among n people
in paise. Properties: the shares sum exactly to the total, and no two
shares differ by more than one paisa. A property test with random totals
and group sizes finds that rounding each share separately loses a paisa
for some inputs. The fix gives the leftover paise to the first few people.

### Step by step

<Compare left="Example-based test" right="Property-based test" caption="Two ways to test chunk. Look at the second row: who chooses the inputs is the key difference." rows={[
  ["Asserts chunk of 1 to 6 in threes gives two chunks", "Asserts flattening the chunks gives back the input"],
  ["Inputs chosen by me", "Inputs generated at random, hundreds of times"],
  ["Shares my blind spots", "Finds inputs I did not imagine"],
  ["Failing case is one I wrote", "Failing case is shrunk to the simplest"],
]} />

1. **State what must always be true**, not a specific result.
2. **Describe the valid inputs** to the generator.
3. **Run many cases**, with a fixed seed so failures reproduce.
4. **When it fails, shrink** to the smallest failing input.
5. **Fix the bug and keep the failing case** as an example test too.

### Common mistake

The common mistake is a property that restates the implementation, such
as computing the expected output with the same algorithm. It can never
fail. The fix is properties about relationships: round trips, invariants,
comparison with a simpler but slower reference version.

### In real systems

Property-based testing is common for parsers, serialisers, financial
calculations and data structures, where round trips and invariants are
natural. Fuzzing, which throws random or mutated inputs at programs to find
crashes and security holes, is its close relative.

### Check yourself

**Why do hand-written tests miss some bugs?**

<details>
<summary>Answer</summary>

The same person chooses the code and the test inputs, so both share the
same assumptions and blind spots.

</details>

**What is shrinking?**

<details>
<summary>Answer</summary>

Reducing a failing random input to the smallest input that still fails, to
make the cause obvious.

</details>

## Topic 43. Stay Safe Out There

### In one sentence

Anything exposed will be attacked, so I keep the attack surface small,
grant the least privilege, use secure defaults, encrypt sensitive data and
apply security updates quickly.

### The idea

The book starts with a warning: it is easy to think "nobody will bother
attacking this". Automated tools scan the whole internet constantly. Code
must assume hostile input from day one.

#### Basic principles

The book lists five:

1. **Minimise attack surface area.** The attack surface is everything an
   attacker can reach or influence. It grows with code complexity, input
   data, unauthenticated services, authenticated services with more users
   than needed, output data that reveals too much, and debugging
   information such as stack traces shown to users. The tip: keep it
   simple and minimise attack surfaces.
2. **Principle of least privilege.** Every component, user and process gets
   only the access it needs, for only as long as it needs it.
3. **Secure defaults.** The default settings should be the safe ones, such
   as passwords hidden as they are typed, with users opting in to less
   secure options.
4. **Encrypt sensitive data.** Personal information, financial data and
   passwords, in transit and at rest. Never commit secrets to version
   control.
5. **Maintain security updates.** Many large breaches came from systems
   that had not applied an available patch. The tip: apply security patches
   quickly.

#### Common sense and cryptography

The book is firm that I should not invent my own cryptography or security
schemes. Use well-reviewed libraries and standards. It also lists password
anti-patterns: limiting length, banning special characters, forced
periodic changes, and security questions, which make passwords weaker or
easier to guess. Current guidance favours long passphrases, checking
against lists of breached passwords, and multi-factor authentication.

#### Input is data, never code

The most common attacks put code where data belongs: SQL injection,
cross-site scripting and command injection all work by getting input
treated as instructions. The defence is to keep them separate, with
parameterised queries, output escaping and APIs that take arguments rather
than command strings.

#### Passwords, done sensibly

The book singles out password handling because so much of it is done
badly. On the storage side, passwords are never stored in plain text or
with fast hashes; they are hashed with a slow, salted algorithm designed
for passwords, such as bcrypt, scrypt or Argon2, from a well-known
library. On the policy side, the old rules of short maximum lengths,
mandatory symbols and monthly changes push people toward predictable
passwords. Allowing long passphrases, blocking passwords known from
breaches, and adding a second factor protect users far better.

### Worked example

**Simple.** A login lookup that builds SQL from the user's input, next to
one that passes the input as a parameter:

```ts
// Stay safe: building SQL from input versus passing parameters.
const name = "x' OR '1'='1";
const unsafe = `SELECT * FROM users WHERE name = '${name}'`;
const safe = { text: 'SELECT * FROM users WHERE name = $1', values: [name] };
console.log('unsafe:', unsafe);
console.log('safe:  ', safe.text, safe.values);
```

The output:

```text
unsafe: SELECT * FROM users WHERE name = 'x' OR '1'='1'
safe:   SELECT * FROM users WHERE name = $1 [ "x' OR '1'='1" ]
```

The unsafe query now matches every user, because the input changed the
query's structure. In the safe version, the database receives the query and
the value separately, so the input can only ever be a name.

**Realistic.** An internal admin dashboard was left reachable from the
internet "temporarily", with a default password, and showed full stack
traces on errors. Each was a separate surface: an unauthenticated service,
an insecure default, and debug output revealing library versions. Moving
it behind the company login, removing the default and showing generic
error pages closed all three.

### Step by step

<Layers caption="The five principles as layers of defence. Look at the bottom layer: even good design fails if known holes are left unpatched." layers={[
  "Minimise attack surface: less code, fewer inputs and services exposed",
  "Least privilege: each part gets only the access it needs",
  "Secure defaults: safe unless someone opts out",
  "Encrypt sensitive data: in transit and at rest, secrets out of the repository",
  "Apply security updates quickly",
]} />

1. **List what is exposed.** Endpoints, inputs, outputs, error messages.
2. **Remove what is not needed**, and authenticate the rest.
3. **Give each service and key the least access** that works.
4. **Keep input as data**: parameterised queries, escaped output.
5. **Automate dependency updates** and patch quickly.

### Common mistake

The common mistake is relying on obscurity, such as an unlisted URL or an
unusual port. Scanners find them quickly. The fix is real authentication
and authorisation on everything not meant to be public.

### In real systems

Dependency scanners, secret scanners in CI, web application firewalls,
regular penetration tests and the OWASP Top Ten list of common web risks
are standard tools. Cloud IAM policies are least privilege in practice.

### Check yourself

**Why is showing stack traces to users a security problem?**

<details>
<summary>Answer</summary>

They reveal internal details such as file paths and library versions,
which enlarge the attack surface by telling attackers what to target.

</details>

**What makes a parameterised query safe from SQL injection?**

<details>
<summary>Answer</summary>

The query and the values are sent separately, so input can never change
the structure of the query.

</details>

## Topic 44. Naming Things

### In one sentence

Names are how code explains itself, so I choose names that reveal intent,
follow the project's vocabulary, and rename when the meaning changes.

### The idea

#### Why names matter

The book notes that names are everywhere: variables, functions, modules,
services, branches, even projects. Readers form a picture of the code from
its names before they read the logic. A good name tells them what
something is for; a bad one misleads, which is worse than saying nothing.

The book illustrates with the Stroop effect, a psychology experiment where
people are slower to say the colour of a word when the word names a
different colour. Code with misleading names creates the same friction:
the name says one thing and the code does another, and the reader has to
fight their own reading.

#### What a good name does

The book suggests naming by role and intent, not by type or mechanism. A
variable called `list` says nothing; `pendingInvoices` says what it holds
and why it matters. A function called `process` hides what it does;
`chargeOverdueAccounts` explains it. The book's tip: name well, rename
when needed.

#### Culture and consistency

Names should respect the culture of the language and the project. Short
loop variables like `i` are idiomatic in many languages; long Java-style
names may look odd in a Unix tool. More importantly, a project should have
a consistent vocabulary: if the business says "customer", the code should
not mix "client", "user" and "account" for the same thing. The book
suggests a project glossary, which links back to domain languages in
chapter 2.

#### Renaming

Meanings drift. A `UserService` gains billing logic; a `temp` table becomes
permanent. The book says to rename when the name no longer fits, and that
if renaming is hard, that is itself a problem to fix, through tools,
tests and less coupling. Leaving a wrong name in place is a broken window.

### Worked example

**Simple.** A function in a codebase:

| Before | After | Why |
|---|---|---|
| `function calc(d, f)` | `function daysOverdue(dueDate, today)` | Says what it computes and what each input is |
| `let flag = true` | `let hasUnsavedChanges = true` | A boolean named as a question |
| `const data = await get()` | `const invoices = await fetchUnpaidInvoices()` | Names the content and the source |
| `class Manager` | `class InvoiceReminderScheduler` | Says what it manages |

None of these changes behaviour. Each removes a question a reader would
otherwise have to answer by reading the code.

**Realistic.** A team discovers that "account" means a login in one
service, a billing entity in another, and a company in a third. Bugs keep
arising where data from one meaning is used as another. They agree a
glossary: user for a login, billing account for the paying entity,
organisation for the company. Renaming takes a few weeks, done in small
refactoring steps, and a whole class of confusion disappears.

### Step by step

<Figure caption="How a name evolves. Look at the last line: the name grows more specific as my understanding grows." art={`
   first draft      x            "something"
   first pass       data         "some data"
   with context     orders       "orders"
   with intent      unpaidOrders "orders still owing money"
   as meaning moves overdueOrders "unpaid past the due date"
                     -> rename when the meaning changes
`} />

1. **Ask what the thing is for**, not what type it is.
2. **Use the project's vocabulary**, from the glossary.
3. **Name booleans as questions**, such as `isActive` or `hasAccess`.
4. **Read the code aloud**; names that need explaining need changing.
5. **Rename when the meaning changes**, with the editor's rename tool.

### Common mistake

The common mistake is abbreviations and placeholders that stay forever:
`tmp`, `obj`, `doStuff`, `mgr`. The fix is to treat naming as part of
finishing the code, and to rename in review.

### In real systems

Linters enforce naming conventions. API names, once public, are hard to
change, so teams review them carefully and version them. Domain-driven
design formalises the shared glossary as a ubiquitous language between
developers and the business.

### Check yourself

**What does the Stroop effect suggest about misleading names?**

<details>
<summary>Answer</summary>

When a name says one thing and the code does another, readers are slowed
and misled by their own reading, which is worse than a neutral name.

</details>

**What should I do if renaming something is too hard?**

<details>
<summary>Answer</summary>

Treat that difficulty as a problem in itself, and fix it with tooling,
tests and less coupling, rather than living with a wrong name.

</details>

## From beginner to strategy

<Levels label="Chapter 7, While You Are Coding">

<Level name="Beginner" depth={3}>

At the beginner level, the habits are small and concrete: run the code
after every change, read the documentation for any function I rely on,
write at least one test for each function, and give things names that say
what they are for.

Example: before using `sort`, I read its documentation and learn that it
sorts strings by default, so I pass a comparison for numbers.

Mistake: copying a snippet from the internet because it works, without
knowing why. Fix: before keeping it, explain each line to myself, and look
up anything I cannot explain.

</Level>

<Level name="Intermediate" depth={3}>

At the intermediate level, I estimate the order of any loop over data,
write tests before or alongside code, and refactor as I go in small steps
with tests passing. I notice hidden loops such as `includes` inside
`filter`.

Example: a code review comment on my own pull request, "this is n squared
for the number of products", leads me to change an array to a `Set`
before merging.

Mistake: refactoring and adding a feature in the same commit. Fix: two
commits, refactor first with tests green, then the feature.

</Level>

<Level name="Advanced" depth={3}>

At the advanced level, I use tests as a design tool, write property-based
tests for code with clear invariants, and think about security as part of
every feature, not a review at the end.

Example: a currency conversion module gets properties such as "converting
there and back stays within one minor unit" and "results are never
negative for positive input", which find a rounding bug on day one.

Mistake: property tests with an unseeded generator, so a failure cannot be
reproduced. Fix: log the seed on every run and allow re-running with it.

</Level>

<Level name="Edge cases" depth={3}>

Edge cases in this chapter are inputs at the boundaries: empty arrays,
one element, lengths that do not divide evenly, strings with accents or
emoji, very large n, and inputs containing quotes or control characters.

Example: the `chunk` bug appeared only when the length did not divide
evenly by the size, an edge case none of my examples covered.

Mistake: testing `slugify` only with plain English titles. Fix: include
accents, punctuation-only input, leading and trailing spaces, and the empty
string.

</Level>

<Level name="Corner cases" depth={3}>

Corner cases combine conditions: a refactor that changes behaviour only in
a time zone with daylight saving; a fast algorithm that becomes slow when
all keys collide; an input that is both very long and malicious.

Example: a regular expression used for validation is safe on normal input
but takes exponential time on a crafted string, a denial-of-service attack
known as ReDoS.

Mistake: assuming a validation regex is harmless because it is short. Fix:
test regexes with long adversarial inputs, or use linear-time regex engines
for untrusted input.

</Level>

<Level name="Production level" depth={3}>

In production, these habits become checks. CI runs unit, property and
integration tests on every change. Dependency and secret scanners run on
every commit. Performance tests at realistic sizes catch order-n-squared
surprises before release.

Example: a pipeline that fails the build if a dependency with a known
critical vulnerability is added.

Mistake: ignoring dependency update pull requests for months. Fix: a
weekly slot to merge them, since patches applied quickly are the cheapest
security there is.

</Level>

<Level name="Mindset" depth={3}>

The mindset is deliberate attention. I know why my code works, I listen
when something feels off, and I treat tests, names and structure as part of
the work, not decoration added afterwards.

Example: when a fix makes a bug disappear but I cannot explain why, I keep
investigating until I can.

Mistake: "it passed the tests, ship it" when I do not understand the
change. Fix: understanding is part of done; passing tests is necessary,
not sufficient.

</Level>

<Level name="System design" depth={3}>

At system design level, the same habits scale: algorithms are chosen with
data growth in mind, services are designed to be testable in isolation,
security boundaries follow least privilege, and the domain vocabulary is
consistent across service names, APIs and events.

Example: each service has its own database user with only the tables it
needs, so a compromised service cannot read the rest.

Mistake: one shared admin database credential used by every service. Fix:
per-service credentials with minimal grants, rotated automatically.

</Level>

<Level name="Strategy" depth={3}>

Strategically, a team's coding habits determine how fast it can go
safely. Investment in fast tests, refactoring time, security automation
and shared naming pays back in fewer incidents and easier change.

Example: a team reserves part of every sprint for refactoring and
dependency updates, and tracks incidents caused by old code going down
over two quarters.

Mistake: treating refactoring and tests as optional extras cut under
deadline pressure. Fix: build them into estimates as part of the work.

</Level>

</Levels>

## Questions people ask

<details>
<summary>Is the lizard brain advice just "trust your gut"?</summary>

Not quite. It says to treat the feeling as information worth
investigating, then find the concrete reason. The gut points; the
investigation decides.

</details>

<details>
<summary>Do I have to do test-driven development?</summary>

The book values the thinking TDD forces, but does not demand the ritual.
What matters is that I think about how to test code while designing it,
and that the tests exist and run.

</details>

<details>
<summary>Which property-based testing library should I use in JavaScript?</summary>

fast-check is the common choice, with generators for many types and
automatic shrinking. Hand-rolled tests like the one in this chapter are
fine for learning the idea.

</details>

<details>
<summary>How much should I worry about Big-O for web code?</summary>

Enough to spot loops inside loops over data that can grow, such as users,
orders or records. For fixed small inputs, clarity matters more than
order.

</details>

<details>
<summary>How do I keep up with security as a non-specialist?</summary>

Follow the OWASP Top Ten, use well-known libraries for authentication and
crypto, enable dependency and secret scanning, and patch quickly. Most
breaches exploit basics, not exotic attacks.

</details>

<details>
<summary>When is a name too long?</summary>

When the extra words do not add meaning in context. Inside a function
about invoices, `total` may be enough; at module level, `invoiceTotal` is
clearer. Scope decides how much the name must say.

</details>

## Key takeaways

- Hesitation while coding is information; stop and find its cause, prototyping if needed.
- Do not program by coincidence: know why code works and rely only on documented behaviour.
- Estimate an algorithm's order from its loops, then measure to confirm.
- Refactor early and often, in small tested steps, never mixed with new features.
- A test is the first user of my code; awkward tests mean awkward design.
- Property-based tests find the edge cases my own examples miss.
- Minimise attack surface, use least privilege and secure defaults, encrypt, and patch quickly.
- Name by intent, keep a shared vocabulary, and rename when meaning changes.

## Glossary

- **Lizard brain**: the book's term for instinct, pattern recognition below conscious thought.
- **Programming by coincidence**: relying on code that works without knowing why.
- **Accident of implementation**: behaviour that happens to be true but is not guaranteed.
- **Big-O notation**: a description of how resource use grows with input size.
- **Refactoring**: restructuring code without changing its external behaviour.
- **Characterisation test**: a test that records what existing code does today.
- **Test-driven development**: writing a failing test, then the code to pass it, then refactoring.
- **Property**: a statement that must hold for every valid input.
- **Shrinking**: reducing a failing random input to the smallest that still fails.
- **Attack surface**: everything an attacker can reach or influence.
- **Least privilege**: granting only the access needed, for only as long as needed.
- **SQL injection**: an attack where input changes the structure of a database query.
- **Stroop effect**: slowed reading when a word's meaning conflicts with what it describes.

## Exercises and self-check

**Warm-up.** Find three places in a codebase where a variable or function
name does not say what it is for. Rename them with the editor's rename
tool, run the tests, and commit each separately.

**Build.** Pick a function with a clear invariant, such as a splitter, a
parser or a formatter. Write one property-based test, by hand or with
fast-check, with a logged seed. Run it until it finds something, or until
I am confident it would.

**Stretch.** Take a slow piece of code and measure it at three input
sizes. Predict its order from the code, compare with the measurements,
then change the data structure or algorithm and measure again.

<details>
<summary>Self-check: what are Fowler's three rules for refactoring, as the book gives them?</summary>

Do not refactor and add functionality at the same time; have good tests
first and run them often; take short, deliberate steps.

</details>

<details>
<summary>Self-check: name three things that enlarge the attack surface.</summary>

Any three of: code complexity, input data, unauthenticated services,
authenticated services with too many users, verbose output data, and
debugging information shown to users.

</details>

<details>
<summary>Self-check: what was the real cause of the default sort "working" on the test data?</summary>

Single-digit numbers sort the same as strings and as numbers, so the test
data could not reveal that the sort compares strings.

</details>
