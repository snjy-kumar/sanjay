This chapter asks three questions about any procedure: is it really an algorithm, how fast does its cost
grow, and is the problem it solves even solvable quickly? It answers them with the first algorithms

its relatives, that the whole of computer science uses to compare them.

## 3.1 Algorithms

### In one sentence

An algorithm is a finite sequence of precise instructions for solving a problem, and the classic ones,
searching, sorting, matching and greedy choices, show both how to design one and how one can fail.

### The idea

#### What an algorithm is

An **algorithm** is a finite sequence of precise instructions for performing a computation or solving a
problem. The word comes from the name of the ninth-century mathematician al-Khwarizmi. Writing an
algorithm means writing steps a machine could follow without judgement.

The book lists the properties that separate an algorithm from a vague recipe:

| Property | Meaning |
|---|---|
| Input | it takes values from a specified set |
| Output | it produces values that are the solution |
| Definiteness | every step is defined precisely |
| Correctness | it produces the correct output for every input |
| Finiteness | it stops after a finite number of steps for every input |
| Effectiveness | each step can be done exactly, in finite time |
| Generality | it works for every input of the specified form, not just some |

A recipe that says "salt to taste" fails definiteness. A loop with no exit fails finiteness. A sort that
only works on arrays of length 3 fails generality.

#### Pseudocode

**Pseudocode** is an intermediate step between English and a programming language. It states each step
exactly without worrying about syntax. The book's appendix fixes its conventions; I write the same
algorithms in TypeScript, which is pseudocode I can run.

#### Finding the maximum

The first example: find the largest element of a finite sequence. Set a temporary maximum to the first
element; compare it with each next element and replace it whenever the next one is bigger; at the end
the temporary maximum is the answer. It has every property above, and it takes n minus 1 comparisons.

#### Linear search

The **searching problem** is: given x and a list a1 to an, find the position i with aᵢ equal to x, or
report that x is not present. **Linear search**, or sequential search, compares x with each element in
turn. It works on any list, sorted or not, and in the worst case compares with all n elements.

#### Binary search

If the list is sorted in increasing order, **binary search** does far better. Compare x with the middle
element. If x is bigger, the answer can only be in the right half; otherwise it is in the left half.
Repeat on that half until one element is left, then check it.

Each comparison halves the remaining list, so about log₂ n comparisons suffice. For a million elements
that is about 20 instead of a million. The price is the precondition: the list must be sorted.

#### Sorting

**Sorting** puts the elements of a list in increasing order. It matters because so much else, binary
search, finding duplicates, merging, depends on sorted data. Many algorithms exist because they trade
simplicity, speed and memory differently.

**Bubble sort** repeatedly walks the list, swapping adjacent elements that are out of order. After the
first pass the largest element has "bubbled" to the end; after pass i the last i elements are in place.
It takes n minus 1 passes at most.

**Insertion sort** takes the elements one at a time and inserts each into its correct place among the
ones already sorted, shifting bigger ones to the right. It is fast on nearly sorted input. The
<a href={withBase('/books/introduction-to-algorithms/02-getting-started/')}>CLRS chapter 2 page</a> covers
it in depth.

#### String matching

**String matching** finds every place a pattern p of length m occurs in a text t of length n. The
**naive string matcher** tries every shift s from 0 to n minus m and compares p with the text starting
at s, character by character. A shift where all m characters match is a **valid shift**.

Naive matching is simple and can be slow: on text "aaaa...a" and pattern "aaaab" it compares almost m
characters at every shift. Faster algorithms such as Knuth-Morris-Pratt and Boyer-Moore avoid repeating
work. String matching is the core of search tools, editors and DNA sequence analysis.

#### Greedy algorithms

An **optimisation problem** asks for the best solution by some measure: fewest coins, most talks,
shortest route. A **greedy algorithm** builds a solution by making the choice that looks best at each
step and never reconsidering it.

Greedy algorithms are fast and simple. They are only correct when the problem has a structure that makes
the locally best choice part of some globally best solution. So every greedy algorithm needs a proof, or
a counterexample.

The **cashier's algorithm** makes change for n cents by repeatedly taking the largest coin not more than
what remains. With US coins (quarters, dimes, nickels, pennies) it always uses the fewest coins. With
coins 1, 3 and 4 it does not: for 6 it takes 4, 1, 1, while 3, 3 is better.

**Scheduling talks** is the other example. Given talks with start and end times and one room, schedule
as many as possible without overlap. Greedy by earliest start fails, greedy by shortest fails, and
greedy by **earliest end** is optimal. The step-by-step section below proves it.

#### The halting problem

The **halting problem** asks: is there a procedure that, given any program and any input, decides
whether that program stops on that input? Alan Turing showed in 1936 that no such procedure exists. It
is an **unsolvable** problem.

The proof is a diagonal argument like the one in chapter 2. It is walked line by line below. The
practical meaning is that some questions about programs cannot be answered by any program in general,
and tools must approximate.

### Worked example

**Simple: linear versus binary search.**

```ts
function binarySearch(xs: number[], x: number): { idx: number; cmp: number } {
  let lo = 0, hi = xs.length - 1, cmp = 0;
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2);
    cmp++;
    if (x > xs[mid]) lo = mid + 1; else hi = mid;
  }
  cmp++;
  return { idx: xs.length && xs[lo] === x ? lo : -1, cmp };
}
const big = Array.from({ length: 1_000_000 }, (_, i) => 2 * i);
console.log('binary miss on 1e6:', binarySearch(big, 1).cmp);
```

```text
binary miss on 1e6: 21
```

A linear search for the same missing value makes 1,000,000 comparisons. The loop keeps the invariant
"if x is present, it is between lo and hi", and the final comparison checks the last candidate.

**Simple: greedy change, right and wrong.**

```ts
function cashier(amount: number, coins: number[]) {
  const used: number[] = [];
  for (const c of [...coins].sort((a, b) => b - a))
    while (amount >= c) { amount -= c; used.push(c); }
  return used;
}
console.log('greedy 67 with 25,10,5,1:', cashier(67, [25, 10, 5, 1]).join('+'));
console.log('greedy 6 with 4,3,1:', cashier(6, [4, 3, 1]).join('+'));
```

```text
greedy 67 with 25,10,5,1: 25+25+10+5+1+1
greedy 6 with 4,3,1: 4+1+1
```

A dynamic-programming check (chapter 8) gives 2 coins for 6 with coins 4, 3, 1, so greedy's 3 is not
optimal. The algorithm is correct only together with an assumption about the coin system.

**Realistic: scheduling, three greedy rules.**

```ts
type Talk = { name: string; start: number; end: number };
const pick = (ts: Talk[], key: (t: Talk) => number) => {
  const chosen: Talk[] = [];
  for (const t of [...ts].sort((a, b) => key(a) - key(b)))
    if (chosen.every(c => t.end <= c.start || t.start >= c.end)) chosen.push(t);
  return chosen.map(c => c.name).sort();
};
const tricky: Talk[] = [{ name: 'P', start: 9, end: 12 }, { name: 'Q', start: 11, end: 13 }, { name: 'R', start: 12, end: 15 }];
console.log('tricky shortest:', pick(tricky, t => t.end - t.start).join(','), '| earliest end:', pick(tricky, t => t.end).join(','));
```

```text
tricky shortest: Q | earliest end: P,R
```

`pick` sorts by the rule and keeps a talk if it overlaps nothing chosen so far. The short talk Q blocks
both long ones; earliest end keeps two. On a bigger six-talk example I tried, earliest start chose only
2 talks while earliest end chose 4.

**Realistic: string matching.** Searching "eceyeye" for "eye" gives valid shifts 2 and 4 with 10
character comparisons. Searching 20 a's for "aaaaab" takes 90 comparisons, close to the worst case of
(n minus m plus 1) times m.

### Common mistake

**Trusting a greedy rule because it worked on the examples.** The wrong way: shipping cashier's
algorithm for a currency with denominations 1, 3 and 4. Why it fails: greedy is only optimal under an
assumption about the input, here the coin system.

The fix is to either prove the greedy choice is safe (an exchange argument or greedy-stays-ahead, as
above) or search small cases against a brute-force optimum before trusting it.

**Binary search off by one.** `mid = (lo + hi) / 2` without floor, `hi = mid - 1` with a `lo < hi` loop,
or `(lo + hi)` overflowing in fixed-width languages are the classic bugs. The fix is to state the
invariant and check it on lists of length 0, 1 and 2.

### In real systems

Binary search runs inside database indexes, `git bisect`, sorted-array lookups and version resolution.
Sorting runs inside every `ORDER BY` and every merge. String matching runs inside `grep`, editors and
log search; production tools use smarter algorithms than the naive one for exactly the worst case above.

Greedy algorithms run schedulers, caches (evict the least recently used), Huffman compression (chapter
11) and Dijkstra's shortest paths (chapter 10). The halting problem is why linters and type checkers are
conservative: they cannot decide every property of every program, so they reject some correct programs.

## 3.2 The growth of functions

### In one sentence

Big-O, big-Omega and big-Theta compare how fast functions grow for large inputs while ignoring constant
factors, and each claim is proved by exhibiting two numbers called witnesses.

### The idea

#### Why ignore constants

The time an algorithm takes depends on the machine, the language and the compiler. Those change the
time by a constant factor. What does not change is how the time grows as the input grows. Big-O notation
captures that growth and deliberately throws away the constant.

It also throws away small inputs. For a handful of elements nearly any algorithm is fast. The question
that decides whether a system survives is what happens at a million or a billion.

#### Big-O

Let f and g be functions from integers or reals to reals. f(x) is **O(g(x))**, read "f is big-O of g",
if there are constants C and k such that the absolute value of f(x) is at most C times the absolute value
of g(x) whenever x is greater than k. C and k are the **witnesses**.

In words: from some point on, f is at most a constant multiple of g. g is an upper bound on f's growth.
Witnesses are never unique: if C and k work, so does any bigger C or bigger k.

To prove f is O(g), find one pair of witnesses and check the inequality for all x beyond k. To disprove
it, show that for every C and k there is some x beyond k where f exceeds C times g, usually by
contradiction.

#### Polynomials and other important estimates

If f is a polynomial of degree n, aₙxⁿ plus ... plus a0, then f is O(xⁿ). The proof bounds every term by
its absolute coefficient times xⁿ for x greater than 1.

Other estimates used constantly:

- 1 plus 2 plus ... plus n is O(n²), and n! is O(nⁿ). log n! is O(n log n).
- log n is O(n), and n is O(2ⁿ). More generally, for every b greater than 1 and d greater than 0, (log n)
  to any power is O(nᵈ), nᵈ is O(bⁿ), and bⁿ is O(cⁿ) for c greater than b.
- The base of a logarithm does not matter inside big-O, because log_a n is a constant times log_b n.

#### The usual order of growth

From slowest to fastest growing: 1, log n, n, n log n, n², n³, 2ⁿ, n!. Each is big-O of the next and not
the other way round.

#### Combining bounds

If f1 is O(g1) and f2 is O(g2), then f1 plus f2 is O(max of g1 and g2), and f1 times f2 is O(g1 times
g2). In code terms: two loops in sequence cost the bigger of the two, and a loop inside a loop costs the
product.

#### Big-Omega and big-Theta

f is **Ω(g)**, big-Omega, if there are C and k with absolute f at least C times absolute g for x greater
than k. It is a lower bound. f is Ω(g) exactly when g is O(f).

f is **Θ(g)**, big-Theta, if f is both O(g) and Ω(g). Then f and g are **of the same order**: each is
bounded by a constant multiple of the other from some point on. A polynomial of degree n with a non-zero
leading coefficient is Θ(xⁿ).

#### Proving one function is not big-O of another

The cleanest disproof is by contradiction with the witnesses. Assume witnesses C and k exist, rearrange
the inequality until one side is a growing function of n and the other is the constant C, then pick n
large enough to break it. n² not O(n) reduces to "n at most C", and 2ⁿ not O(n³) reduces to "2ⁿ divided
by n³ at most C", which fails because that ratio grows without bound.

A quick test that suggests the answer before you prove it: look at the ratio f(n)/g(n) for large n. If it
heads to 0, f is O(g) and not Θ(g). If it settles to a positive constant, f is Θ(g). If it grows without
bound, f is not O(g). The ratio test comes from calculus; the book mostly proves things with witnesses,
which needs no limits.

#### The sum 1 plus 2 plus ... plus n is Θ(n²)

Upper bound: each of the n terms is at most n, so the sum is at most n², witnesses C equal to 1 and k
equal to 1. Lower bound: the top half of the terms, from about n/2 to n, are each at least n/2, and there
are about n/2 of them, so the sum is at least about n²/4. Both bounds together give Θ(n²).

The exact value from chapter 2, n(n plus 1)/2, confirms it: for n equal to 100 the sum is 5,050, close to
n²/2, which is 5,000. This sum is the cost of every algorithm whose inner loop shrinks by one each pass.

#### Why logarithms lose to powers and powers lose to exponentials

log n is O(n) because n is less than 2ⁿ for every positive integer n (provable by induction in chapter 5),
and taking log base 2 of both sides gives log₂ n less than n. The same trick with a substitution shows log
n is O(n to any positive power).

nᵈ is O(bⁿ) for b greater than 1 because each step from n to n plus 1 multiplies bⁿ by b, a fixed factor,
while it multiplies nᵈ by ((n plus 1)/n)ᵈ, a factor that shrinks towards 1. Eventually the exponential's
fixed factor wins every step, and it never loses again.

#### Big-O with more than one variable

Functions of two inputs also get big-O bounds: f(m, n) is O(g(m, n)) if there are constants C, k1 and k2
with |f| at most C|g| whenever m is greater than k1 and n is greater than k2. String matching's cost
in text length n and pattern length m is the natural example: Θ(nm), and neither variable can be dropped.

### Worked example

**Simple: a witness pair.** Show 7n² plus 3n plus 5 is O(n²). For n at least 1, 3n is at most 3n² and 5
is at most 5n². So the sum is at most 15n², and C equal to 15, k equal to 1 are witnesses.

A tighter pair: C equal to 8. I asked Node for the smallest k that works.

```ts
let k = 1;
while (!(7 * k * k + 3 * k + 5 <= 8 * k * k)) k++;
console.log('witness k for C=8:', k);
let ok = true;
for (let n = k; n < 100000; n++) if (7 * n * n + 3 * n + 5 > 8 * n * n) ok = false;
console.log('holds up to 1e5:', ok);
```

```text
witness k for C=8: 5
holds up to 1e5: true
```

The loop only checks up to 100,000, which is not a proof. The proof: 8n² minus (7n² plus 3n plus 5) is
n² minus 3n minus 5, which is positive for n at least 5 and keeps growing. So C equal to 8, k equal to 4
(meaning n greater than 4) are witnesses.

**Simple: a disproof.** n² is not O(n). Suppose it were, with witnesses C and k. Then n² is at most Cn,
so n is at most C, for every n greater than k. Take n bigger than both C and k: contradiction.

**Realistic: reading code.** A function that sorts with merge sort (Θ(n log n)) and then scans once (Θ(n))
is Θ(n log n): the sum rule keeps the bigger term. A function that, for each of n users, runs a query
that scans all m orders is Θ(nm): the product rule.

### Common mistake

**Using big-O as if it meant Theta.** The wrong way: "this algorithm is O(n²), and that one is O(n³), so
the first is faster." Big-O is only an upper bound; a linear algorithm is also O(n³). Why it fails: two
upper bounds do not compare the actual costs.

The fix is to state Theta when you have matching upper and lower bounds, and to say "at most" when you
only have big-O.

**Treating "f equals O(g)" as an equation.** O(g) is a set of functions, and the equals sign is a
convention. O(n) equals O(n²) is fine read left to right, and nonsense read right to left.

### In real systems

Complexity classes tell you which part of a system falls over first as it grows. A Θ(n²) step that is
fast on 1,000 rows takes a million times longer on a million rows. Capacity planning is mostly finding
the term with the biggest growth.

Constants still matter in practice. An n log n algorithm with a huge constant can lose to an n² one for
the input sizes a system actually sees, which is why standard library sorts switch to insertion sort on
short runs. Big-O decides the shape; benchmarks decide the crossover.

## 3.3 Complexity of algorithms

### In one sentence

The time complexity of an algorithm is the number of basic operations it performs as a function of input
size, and comparing those functions, in the worst and average case, sorts problems into tractable,
intractable and unsolvable.

### The idea

#### Time and space complexity

The **time complexity** of an algorithm is the number of basic operations it performs, such as
comparisons or additions, expressed as a function of the input size. **Space complexity** is the memory
it needs. The book concentrates on time.

Counting operations instead of seconds makes the analysis independent of the machine. Big-O then
describes how that count grows.

#### Worst case and average case

**Worst-case complexity** is the largest number of operations over all inputs of size n. It is a
guarantee: no input of that size takes longer. **Average-case complexity** is the average over all
inputs of size n, under some assumption about how likely each input is. It is often harder to compute
and depends on that assumption.

Linear search makes n comparisons in the worst case and about n/2 on average if x is present and equally
likely to be anywhere. Both are Θ(n).

#### The standard counts

| Algorithm | Worst-case comparisons | Class |
|---|---|---|
| Finding the maximum | n minus 1 | Θ(n) |
| Linear search | n | Θ(n) |
| Binary search | about log₂ n plus 1 | Θ(log n) |
| Bubble sort | n(n minus 1)/2 | Θ(n²) |
| Insertion sort | n(n minus 1)/2 | Θ(n²) |
| Naive string matching | (n minus m plus 1) times m | Θ(nm) |
| Merge sort (chapter 5) | about n log₂ n | Θ(n log n) |

The bubble sort count comes from chapter 2's sum: pass i makes n minus i comparisons, and the sum of n
minus i for i from 1 to n minus 1 is n(n minus 1)/2.

#### Matrix multiplication

Multiplying two n × n matrices directly takes n³ multiplications and n²(n minus 1) additions, so Θ(n³).
Strassen's algorithm uses a clever split to do it in about n to the 2.81. Faster methods exist in theory.
The Boolean product has the same Θ(n³) direct count.

**Matrix-chain multiplication** asks for the cheapest order to multiply A1 A2 ... Aₙ. The answer is the
same for every order, by associativity, but the cost is not. Chapter 8's dynamic programming finds the
best order.

#### Insertion sort, counted

Insertion sort takes each element in turn and slides it left past larger elements into the sorted part.
The book's version scans from the front of the sorted part; the version below scans from the back, which
is what libraries use, and has the same worst case.

```ts
function insertion(xs: number[]) {
  const a = [...xs]; let cmp = 0;
  for (let j = 1; j < a.length; j++) {
    const key = a[j]; let i = j - 1;
    while (i >= 0) {
      cmp++;
      if (a[i] > key) { a[i + 1] = a[i]; i--; } else break;
    }
    a[i + 1] = key;
  }
  return { a, cmp };
}
console.log(insertion([3, 2, 4, 1, 5]));
```

```text
{ a: [ 1, 2, 3, 4, 5 ], cmp: 6 }
```

On already sorted input each element needs one comparison, so n minus 1 in total. On reversed input
element j is compared with all j elements before it, so 1 plus 2 plus ... plus (n minus 1), which is n(n
minus 1)/2. Node agreed at n equal to 1,000, 2,000 and 4,000: 999, 1,999 and 3,999 sorted, and 499,500,
1,999,000 and 7,998,000 reversed.

That gap is why insertion sort is still used: on nearly sorted data and short runs it is close to linear.
Its worst case is still quadratic.

#### Matrix multiplication, counted

```ts
function matmul(A: number[][], B: number[][]) {
  const n = A.length; let mul = 0, add = 0;
  const C = A.map(() => Array(n).fill(0));
  for (let i = 0; i < n; i++) for (let j = 0; j < n; j++) {
    let s = A[i][0] * B[0][j]; mul++;
    for (let q = 1; q < n; q++) { s += A[i][q] * B[q][j]; mul++; add++; }
    C[i][j] = s;
  }
  return { C, mul, add };
}
console.log(matmul([[1, 2], [3, 4]], [[5, 6], [7, 8]]));
```

```text
{ C: [ [ 19, 22 ], [ 43, 50 ] ], mul: 8, add: 4 }
```

Each of the n² entries takes n multiplications and n minus 1 additions. For n equal to 10 that is 1,000
and 900, and for 20 it is 8,000 and 7,600: doubling n multiplies the work by 8, the signature of Θ(n³).

#### Why the order of a matrix chain matters

Take A as 10 × 100, B as 100 × 5 and C as 5 × 50. Multiplying a p × q by a q × r matrix directly costs
pqr multiplications. (AB)C costs 10·100·5 plus 10·5·50, which is 7,500. A(BC) costs 100·5·50 plus
10·100·50, which is 75,000. Same answer, ten times the work.

#### Space complexity, briefly

Linear search and binary search use a constant amount of extra memory: a few indices. Bubble and
insertion sort work in place, so constant extra space too. The naive matcher keeps a list of matches,
which can be as long as the number of shifts. Recursive algorithms in chapter 5 use stack space that grows
with the recursion depth, which is how binary search written recursively uses Θ(log n) space.

#### The complexity of greedy algorithms

Greedy is usually fast. Cashier's algorithm with a fixed set of coins does work proportional to the
number of coins handed out. The talk scheduler is dominated by sorting the talks by end time, Θ(n log n),
followed by one linear pass. Speed is rarely the problem with greedy; correctness is.

#### The doubling experiment

To check an analysis against reality, run the code at n, 2n and 4n and look at the ratio of costs. A ratio
near 2 means linear, near 2.2 means n log n (Node gives 2.20 from 1,000 to 2,000), near 4 means
quadratic, near 8 means cubic. A ratio that keeps climbing suggests exponential.

#### Algorithmic paradigms

An **algorithmic paradigm** is a general approach that many algorithms follow. **Brute force** tries
every candidate: the naive matcher, checking every pair of points for the closest pair, trying every
route. It is simple and correct and often slow.

Greedy algorithms are another paradigm. Later chapters add divide and conquer (chapter 8), dynamic
programming (chapter 8), backtracking (chapter 11) and probabilistic algorithms (chapter 7).

#### Understanding complexity

The book's table of growth classes, in plain words:

| Complexity | Name |
|---|---|
| Θ(1) | constant |
| Θ(log n) | logarithmic |
| Θ(n) | linear |
| Θ(n log n) | linearithmic |
| Θ(nᵇ) | polynomial |
| Θ(bⁿ), b greater than 1 | exponential |
| Θ(n!) | factorial |

#### Tractable, intractable, unsolvable

A problem is **tractable** if some algorithm solves it in polynomial worst-case time, and
**intractable** if none does. Problems no algorithm solves at all, like the halting problem, are
**unsolvable**.

The class **P** is the set of tractable decision problems. The class **NP** is the set of problems whose
solutions can be *checked* in polynomial time once someone hands you one. Every problem in P is in NP.

A problem is **NP-complete** if it is in NP and every NP problem can be translated into it in polynomial
time. Satisfiability from chapter 1 was the first one proved NP-complete. If any NP-complete problem has
a polynomial algorithm, then P equals NP. Whether P equals NP is the most famous open problem in computer
science.

#### Real time versus counted steps

At a billion simple operations per second, a Θ(n²) algorithm on a million items takes about 1,000 seconds,
and a Θ(2ⁿ) algorithm on just 60 items would take about 37 years. That arithmetic, not the notation, is why
complexity matters.

### Worked example

**Simple: bubble sort's count.** I counted comparisons for three sizes.

```ts
for (const n of [1000, 2000, 4000]) console.log('bubble n=', n, 'cmp', n * (n - 1) / 2);
```

```text
bubble n= 1000 cmp 499500
bubble n= 2000 cmp 1999000
bubble n= 4000 cmp 7998000
```

Doubling n multiplies the count by about 4. That is what Θ(n²) predicts, and it is the "doubling
experiment" I use to check an analysis against real code.

**Realistic: closest pair.** Brute force over n points checks n(n minus 1)/2 pairs. For 100,000 points
that is about 5 billion distance computations. A divide-and-conquer algorithm does it in Θ(n log n): about 100,000 times 17,
under 2 million basic steps. Paradigm choice, not code tuning,
is the difference.

**Realistic: is it NP?** "Does this list of 50 package constraints have a consistent version choice?" is
satisfiability in disguise. Checking a proposed choice is fast, so it is in NP. Finding one may be hard in
the worst case, which is why package managers use SAT solvers with heuristics and sometimes time out.

### Common mistake

**Analysing only the best case.** The wrong way: "insertion sort is linear, because on sorted input it
makes n minus 1 comparisons." Why it fails: the guarantee users need is the worst case, which is
quadratic.

The fix is to state which case you mean, and to default to worst case for anything user-facing. When you
quote an average case, state the input distribution it assumes.

**"NP means not polynomial."** NP stands for nondeterministic polynomial time. Problems in P are also in
NP. The fix is the definition: NP means solutions are quick to check.

### In real systems

Performance incidents are usually a quadratic step meeting a bigger input than anyone tested: a nested
loop over users and permissions, an ORM issuing one query per row, a string built by repeated
concatenation. Measuring the input sizes you actually see, and running the doubling experiment, catches
them before production does.

NP-complete problems are everywhere in production in disguise: scheduling, routing, bin packing, register
allocation, dependency resolution. Systems solve them with heuristics, approximation, limits on input
size, or solvers that are fast on typical inputs.

## From beginner to strategy

<Levels label="Chapter 3, Algorithms">
<Level name="Beginner" depth={3}>

The smallest working version: an algorithm is a precise, finite list of steps, and we compare algorithms
by counting how many steps they take as the input grows. Binary search beats linear search because it
halves the problem every step instead of shrinking it by one.

Worked example: finding a name in a phone book of 1,000 pages. Reading page by page takes up to 1,000
looks. Opening in the middle and choosing a half takes about 10. That gap, n versus log n, is the
chapter's first lesson.

The beginner mistake is judging an algorithm by how short its code is. Bubble sort is shorter than merge
sort and far slower on big inputs. The fix is to count operations, not lines.

</Level>
<Level name="Intermediate" depth={3}>

At this level the pieces combine in a real program. You choose a search based on whether data is sorted,
a sort based on size and how sorted it already is, and you check whether a greedy shortcut is safe.

Example: deduplicating a list of emails. Brute force compares every pair, Θ(n²). Sorting then scanning
neighbours is Θ(n log n). A `Set` is Θ(n) on average.

```ts
const emails = ['a@x.in', 'b@x.in', 'a@x.in', 'c@x.in', 'b@x.in'];
const sorted = [...emails].sort();
const dupes = sorted.filter((e, i) => i > 0 && e === sorted[i - 1]);
console.log('dupes:', dupes, '| unique:', [...new Set(emails)].length);
```

```text
dupes: [ 'a@x.in', 'b@x.in' ] | unique: 3
```

The mistake is the hidden quadratic: `emails.filter((e, i) => emails.indexOf(e) !== i)` looks like one
pass but calls a linear `indexOf` inside, so it is Θ(n²). The fix is to know the cost of every library
call inside a loop.

</Level>
<Level name="Advanced" depth={3}>

Underneath are the exact definitions. Big-O is a statement with two quantified witnesses: there exist C
and k such that for all x greater than k, |f(x)| is at most C|g(x)|. Disproving it means negating that:
for all C and k there is an x beyond k where |f(x)| exceeds C|g(x)|, which is the nested-quantifier
negation from chapter 1.

Correctness of an algorithm is a theorem too. Binary search's correctness rests on the invariant "if x is
present, its index is between lo and hi", true at the start, kept by each step because the list is
sorted, and at the end it leaves one candidate. Greedy optimality is proved by greedy-stays-ahead or by an
exchange argument.

The mistake at this level is mixing up which quantifier you are fighting. To disprove big-O you must
handle every C, not just one. The fix is to write the negated statement out before starting.

</Level>
<Level name="Edge cases" depth={3}>

- **Empty list.** Linear search returns "not found" after 0 comparisons; binary search must not read
  index 0 of an empty array. My version guards with `xs.length &&`.
- **One element.** Binary search skips the loop and does one comparison.
- **All equal elements.** Bubble sort does all its comparisons and no swaps; binary search finds the
  leftmost copy with the version above.
- **Pattern longer than text.** The naive matcher has zero shifts and returns no matches.
- **Exact change.** Greedy change for 0 returns no coins.
- **Talks that touch.** A talk ending at 12 and one starting at 12 do not overlap if the rule uses "at
  most"; choose and document the rule.

Each needs a test. The mistake is assuming the general case code covers them.

</Level>
<Level name="Corner cases" depth={3}>

- **Binary search on unsorted data.** No error, just a wrong answer. Two problems at once: a violated
  precondition and a silent failure. Assert sortedness in development builds.
- **Duplicates plus binary search.** Different variants return the first, last or any copy. Code that
  assumes "first" breaks with a variant that returns "any".
- **Greedy with ties.** Two talks with the same end time: either choice is optimal for counting talks, but
  a test that expects a specific schedule fails.
- **Big-O claims at small n with large constants.** An O(n log n) sort with a slow comparator loses to an
  O(n²) one with a fast comparator on 20 elements.
- **Overflow in mid.** `(lo + hi) / 2` overflows in 32-bit languages for arrays near 2 billion; `lo +
  (hi - lo) / 2` does not. In JavaScript numbers this is safe up to 2 to the 53.

</Level>
<Level name="Production level" depth={3}>

In production, complexity meets real data. Inputs grow over time, so an O(n²) path that was fine at
launch becomes the slowest endpoint a year later. Tracking input sizes in metrics, not just latency,
shows the growth before it becomes an outage.

Libraries hide costs: `Array.prototype.includes`, `indexOf` and `splice` are linear, ORMs issue queries
per row, and regular expressions can take exponential time on crafted input. Profiling with realistic
data sizes and running doubling experiments in CI catch regressions.

The mistake is optimising constant factors before fixing the growth class. The fix is to find the
highest-order term first, change the algorithm or data structure there, and only then tune.

</Level>
<Level name="Mindset" depth={3}>

The habit is to ask "how does this grow?" before "how fast is this?" and to treat every greedy shortcut
as a claim that needs proof. Fast is a property of an input size; growth is a property of the algorithm.

The second habit is to recognise problem families. Many new problems are old ones in disguise:
scheduling, matching, shortest path, satisfiability. Recognising an NP-complete problem early saves weeks
of searching for an exact fast algorithm that probably does not exist.

Example outside code: planning a release with many dependent tasks is a scheduling problem. Knowing which
version is easy (one resource, earliest deadline) and which is hard (many resources, many constraints)
changes how you plan.

</Level>
<Level name="System design" depth={3}>

In a larger system, complexity decides architecture. A search feature over a million products cannot scan
linearly per keystroke; it needs an index, which is binary search or hashing built ahead of time. A
feed ranking millions of posts uses a greedy heap of the top k instead of sorting everything.

Concrete system: an autocomplete service. Precompute a sorted list or a trie of terms (chapter 11), binary
search the prefix range, and greedily keep the top results by score. The index build is Θ(n log n) once;
each query is Θ(log n plus k).

The mistake is designing for the demo's data size. The fix is to write down the expected n for each
operation a year out and choose algorithms whose growth fits it.

</Level>
<Level name="Strategy" depth={3}>

I learn this chapter by implementing every algorithm on the page with a counter for its basic operation,
then running each on sizes 1,000, 2,000 and 4,000 and checking the counts against the formulas. That

Then I prove three big-O facts with explicit witnesses, disprove one, and write the halting problem

</Level>

## Questions people ask

**why does the book count comparisons instead of measuring time?**

Comparisons are independent of the machine and dominate the cost of searching and sorting. Measuring
time is still useful, to check the analysis, but it mixes in constants that change between machines.

**does the base of the logarithm matter?**

Not inside big-O. Changing base multiplies by a constant. It matters for exact counts such as "about 20
comparisons for a million".

**if P versus NP is open, why do people say some problems are hard?**

Because no polynomial algorithm is known for NP-complete problems despite decades of effort, and finding
one for any of them would give one for all. "Hard" is a well-supported belief, not a proof.

**is the halting problem only theoretical?**

No. It is why no tool can perfectly detect infinite loops, dead code or every crash in arbitrary
programs. Real tools work by restricting the programs they analyse or by allowing false alarms.

## Key takeaways

- An algorithm has input, output, definiteness, correctness, finiteness, effectiveness and generality.
- Binary search needs sorted input and takes about log₂ n comparisons; linear search takes up to n.
- Greedy algorithms are only correct with a proof; one counterexample is enough to break one.
- No program can decide halting for every program and input; the proof is a diagonal argument.
- Big-O is an upper bound with witnesses C and k; Omega is a lower bound; Theta is both.
- Sum of costs takes the maximum class; nested costs multiply.
- Worst-case complexity is a guarantee; average case depends on an assumed input distribution.
- P is problems solvable in polynomial time, NP is problems checkable in polynomial time, and whether they
  are equal is open.

## Glossary

- **Algorithm**: a finite sequence of precise instructions for solving a problem.
- **Pseudocode**: a precise description of an algorithm without a real language's syntax.
- **Linear search**: comparing with each element in turn.
- **Binary search**: halving a sorted list at each comparison.
- **Bubble sort**: repeatedly swapping adjacent out-of-order elements.
- **Insertion sort**: inserting each element into the sorted part.
- **String matching, valid shift**: finding a pattern in a text; a position where it occurs.
- **Optimisation problem**: finding the best solution by some measure.
- **Greedy algorithm**: always taking the locally best choice.
- **Halting problem**: deciding whether a program stops on an input; unsolvable.
- **Big-O, witnesses**: an upper bound up to a constant from some point on; the constants C and k.
- **Big-Omega, big-Theta**: a lower bound; both bounds at once.
- **Time complexity, space complexity**: operations as a function of input size; memory needed.
- **Worst-case, average-case complexity**: the maximum over inputs of size n; the expected value under a
  distribution.
- **Algorithmic paradigm, brute force**: a general approach; trying every candidate.
- **Tractable, intractable, unsolvable**: polynomial-time solvable; not; no algorithm at all.
- **P, NP, NP-complete**: polynomial-time solvable; polynomial-time checkable; the hardest problems in NP.
