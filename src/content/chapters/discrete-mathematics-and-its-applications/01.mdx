This chapter builds the two tools every later chapter depends on: a precise language for statements,
called logic, and a precise set of rules for what counts as a reason, called proof. Every `if`, every
`filter`, every access rule and every code review question "are you sure this is right?" uses them.
Learn them here once, and the rest of the book reads like plain arguments instead of symbols.

## Before you start

After this chapter you will be able to:

- turn an English requirement into a logical formula, and spot the cases the English leaves undecided;
- build a truth table and use it to check equivalence, tautology and consistency;
- read, write and correctly negate statements with "for all" and "there exists", including nested ones;
- tell a valid argument from a fallacy, and name the rule each step uses;
- choose and write a direct proof, a proof by contrapositive, by contradiction, by cases, an existence
  proof, a uniqueness proof, or a counterexample.

read `every`, `some` and `filter`. Nothing from earlier in this book is needed; this is chapter 1.

Reading time: about two hours to read the page carefully, and two to three study sessions to do the
code and the exercises.

## 1.1 Propositional logic

### In one sentence

Propositional logic gives exact rules for combining true-or-false sentences with not, and, or, if-then
and if-and-only-if, so the truth of any combination can be computed from its parts.

### The idea

#### Propositions

A **proposition** is a declarative sentence that is either true or false, but not both. "7 is prime" is
a true proposition. "Delhi is the capital of Japan" is a false one.

"Close the door" is not a proposition, because a command has no truth value. "x plus 1 equals 2" is not
one either, yet, because its truth depends on x. Section 1.4 handles sentences like that.

Why insist on "true or false, not both"? Because everything that follows computes the truth of a
compound sentence from the truth of its parts. That only works if every part has exactly one value.

We name propositions with letters such as p, q, r, called **propositional variables**. True is written
T (or 1) and false F (or 0). A proposition that cannot be split further is **atomic**; one built from
others is **compound**.

#### Negation, and, or, exclusive or

**Logical operators**, also called connectives, build compound propositions. Each one is defined
completely by its **truth table**, a list of every combination of input values with the output for each.

**Negation**, ¬p ("not p"), is true exactly when p is false. **Conjunction**, p ∧ q ("p and q"), is true
exactly when both are true. **Disjunction**, p ∨ q ("p or q"), is true when at least one is true.

That last one is the **inclusive or**: it is true when both are true. The **exclusive or**, p ⊕ q, is
true when exactly one is true. English blurs the two; logic picks inclusive as the default and gives
exclusive its own symbol.

With n variables a truth table has 2 to the power n rows, because each variable doubles the
combinations. Two variables give 4 rows, ten give 1,024. That doubling is why truth tables are perfect
for small formulas and hopeless for big ones.

#### The conditional

The **conditional**, p → q ("if p then q", "p implies q"), is false in exactly one case: p true and q
false. p is the **hypothesis** and q is the **conclusion**. In every other row the conditional is true.

The rows where p is false surprise everyone. Think of p → q as a promise: "if you score 90 or more, you
get an A." The promise is broken only if you score 90 or more and do not get an A.

If you score 70, the promise says nothing about you, so it is not broken. A promise that is not broken
counts as kept. Logic calls the false-hypothesis rows **vacuously true**.

English says p → q in many ways, and requirements documents use all of them:

| English | Formula |
|---|---|
| if p, q; q if p; q when p; q whenever p | p → q |
| p only if q | p → q (not q → p) |
| p is sufficient for q; q is necessary for p | p → q |
| q unless ¬p | p → q |

#### Converse, contrapositive, inverse

From p → q you can build three relatives. The **converse** is q → p. The **contrapositive** is ¬q → ¬p.
The **inverse** is ¬p → ¬q.

Only the contrapositive always has the same truth value as the original. The converse and the inverse
agree with each other but can differ from the original. "If it is a square, it is a rectangle" is true;
its converse, "if it is a rectangle, it is a square", is false.

#### The biconditional

The **biconditional**, p ↔ q ("p if and only if q", often written "iff"), is true when p and q have the
same value. It means (p → q) ∧ (q → p). On booleans in code it is `p === q`.

#### Precedence

To save brackets there is a **precedence** order: ¬ binds tightest, then ∧, then ∨, then →, then ↔. So
p ∨ q ∧ r means p ∨ (q ∧ r), exactly as `p || q && r` does in TypeScript. I still write the brackets in
anything a person will read.

#### Bit operations

Computers store truth values as **bits**, 1 for true and 0 for false. A **bit string** is a sequence of
bits. The connectives extend to bit strings position by position as **bitwise** OR, AND and XOR, written
`|`, `&` and `^` in TypeScript.

### Worked example

**Simple: deciding what is a proposition.** "The deploy finished before 9 PM" is a proposition: on any
given day it is true or false. "n is even" is not, until n is fixed. Fix n to 4 and it is true; fix it
to 5 and it is false.

**Simple: the conditional table, checked in code.** I enumerated every row of p → q, its converse and
its contrapositive.

```ts
const implies = (p: boolean, q: boolean) => !p || q;
const T = (b: boolean) => (b ? 'T' : 'F');
console.log('p q | p->q  q->p  ~q->~p');
for (const [p, q] of [[true, true], [true, false], [false, true], [false, false]]) {
  console.log(`${T(p)} ${T(q)} |  ${T(implies(p, q))}     ${T(implies(q, p))}     ${T(implies(!q, !p))}`);
}
```

```text
p q | p->q  q->p  ~q->~p
T T |  T     T     T
T F |  F     T     F
F T |  T     F     T
F F |  T     T     T
```

The first and third result columns match in every row; the converse differs in two rows. The line `!p
|| q` is worth remembering: it is "implies" written with only not and or.

**Realistic: permission flags as bits.** Let read be bit 0 (value 1), write bit 1 (value 2), delete bit
2 (value 4). A user with read and write has flags `0b011`, which is 3.

- Does the user have write? `3 & 2` is 2, which is not zero, so yes.
- Grant delete: `3 | 4` is 7, which is `0b111`.
- Toggle write off: `7 ^ 2` is 5, which is `0b101`.

### Common mistake

**Affirming the converse.** The wrong way: "if the code is correct, the tests pass; the tests pass;
so the code is correct." That argues q → p from p → q.

Why it fails: in the row where p is false and q is true, p → q holds but the conclusion p is false.
Buggy code can pass weak tests.

The fix is mechanical. Write the statement as hypothesis → conclusion before arguing, and check that
the argument starts from the hypothesis, not from the conclusion.

**A precedence bug.** `flags & WRITE == WRITE` in JavaScript parses as `flags & (WRITE == WRITE)`,
because equality binds tighter than `&`. The fix is brackets: `(flags & WRITE) === WRITE`.

### In real systems

Every `if` condition is a compound proposition, and code review is often truth-table work: "what
happens when the user is logged in but the token is expired?" is asking about one row.

Vacuous truth shows up in tests. A test that says "if the user is an admin, the delete button shows"
passes on every non-admin without checking anything. If the fixture has no admin, the test checks
nothing and still goes green.

Bitwise operators carry permission masks, feature flags, file modes such as Unix `chmod 644`, and
network masks such as `192.168.1.0/24`. Each of those is propositional logic on a row of bits.

## 1.2 Applications of propositional logic

### In one sentence

Translating requirements, searches, puzzles and circuits into propositional logic makes their meaning
exact, exposes gaps, and lets a machine check whether they can all be true at once.

### The idea

#### Translation

To translate English into logic, find the atomic statements, give each a letter, and then decide which
operator each English connective is. Words like "but" usually mean and; "unless" and "only if" need the
table in 1.1.

Translation does more than record meaning. It shows which rows of the truth table the English does not
decide, and those rows are questions to ask, not gaps to fill with a guess.

#### System specifications and consistency

A spec is a list of propositions that should all hold at once. The list is **consistent** if at least
one assignment of truth values makes every statement true. An inconsistent spec cannot be built.

A program that searches for such an assignment is a **SAT solver**, short for satisfiability solver.
Package managers, configuration checkers and hardware verification tools use SAT solvers underneath.

#### Boolean searches

Search engines and database filters use the same connectives. AND narrows a result set, OR widens it, and
NOT removes items. The precedence rules of 1.1 apply, so brackets matter.

#### Logic puzzles

Puzzles such as knights and knaves are consistency problems. On the island, **knights** always tell the
truth and **knaves** always lie. Each speaker gives one biconditional: "the speaker is a knight" iff "the
statement is true".

#### Logic circuits

A **logic circuit** takes input bits and produces output bits. It is built from **gates**: an
**inverter** computes not, an **AND gate** computes and, and an **OR gate** computes or.

Any compound proposition can be built as a circuit by wiring gates the way the formula nests. Any
circuit can be read back into a formula by naming each gate's output.

### Worked example

**Simple: a campus rule.** "You can access the internet from campus only if you are a computer science
major or you are not a first-year." Let a be "can access", c be "CS major", f be "first-year". "Only if"
points at the conclusion, so the formula is a → (c ∨ ¬f).

**Realistic: a refund rule.** "A refund is issued if the order is cancelled within 24 hours, unless it
was already shipped." Let r be "refund issued", c be "cancelled within 24 hours", s be "already shipped".
The formula is (c ∧ ¬s) → r.

Now the gaps show. Does a shipped order never get a refund? The formula says nothing about that row.
The spec is silent, so I ask the product owner instead of guessing.

**Realistic: a search filter.** `status = 'open' OR status = 'pending' AND owner = 'me'` returns every
open item in the system, mine or not, because AND binds first. The intended filter is `(status = 'open'
OR status = 'pending') AND owner = 'me'`.

**Puzzle.** A says "B is a knave." B says "we are both knights." Let A mean "A is a knight" and B mean "B
is a knight". The two statements give A ↔ ¬B and B ↔ (A ∧ B). The brute-force search below tries every
assignment.

```ts
type Env = Record<string, boolean>;
function rows(vars: string[]): Env[] {
  const out: Env[] = [];
  for (let mask = 0; mask < 1 << vars.length; mask++) {
    const env: Env = {};
    vars.forEach((v, i) => { env[v] = ((mask >> (vars.length - 1 - i)) & 1) === 0; });
    out.push(env);
  }
  return out;
}
const iff = (p: boolean, q: boolean) => p === q;
const puzzle = (e: Env) => iff(e.A, !e.B) && iff(e.B, e.A && e.B);
console.log('puzzle solutions:', rows(['A', 'B']).filter(puzzle));
```

```text
puzzle solutions: [ { A: true, B: false } ]
```

`rows` builds all 2 to the n assignments by counting in binary. An empty result would mean the puzzle is
inconsistent; two results would mean it does not decide the answer.

**Circuit: the majority vote.** A motion passes if at least two of three members vote yes. The formula
is (p ∧ q) ∨ (p ∧ r) ∨ (q ∧ r). This is also the carry output of a full adder, so it is how a CPU adds.

### Common mistake

**Filling a gap while translating.** The wrong way is to read the refund rule and silently decide that
shipped orders never get refunds. It fails because the code then encodes an assumption nobody agreed to.

The fix is to translate literally, list every truth-table row the English does not decide, and get each
one answered in writing.

### In real systems

"Cannot resolve dependencies" from a package manager is a SAT solver reporting an inconsistent set of
version constraints. Feature-flag systems check that flag combinations are consistent the same way.

Query builders, search boxes and log filters are Boolean searches, and a missing bracket is one of the
commonest data bugs. Hardware design tools turn formulas into circuits and back, which chapter 12
covers.

## 1.3 Propositional equivalences

### In one sentence

Two formulas are logically equivalent when they have the same truth value in every row, and a small set
of laws lets you rewrite one into the other without building the table.

### The idea

#### Tautologies, contradictions, contingencies

A **tautology** is a compound proposition that is true in every row, such as p ∨ ¬p. A **contradiction**
is false in every row, such as p ∧ ¬p. A **contingency** is neither: true in some rows and false in
others.

These three words sort every formula. A valid argument, in 1.6, will turn out to be a conditional that
is a tautology.

#### Logical equivalence

p and q are **logically equivalent**, written p ≡ q, when p ↔ q is a tautology. In plain words, they
agree in every row. The symbol ≡ is not a connective; it is a statement about two formulas.

The direct way to check an equivalence is a truth table with one column for each side. The two columns
must match in every row.

#### De Morgan's laws

**De Morgan's laws** say how negation moves through and and or. ¬(p ∧ q) ≡ ¬p ∨ ¬q, and ¬(p ∨ q) ≡ ¬p ∧
¬q. Negating flips the connective and negates each part.

In words: "not both" means "at least one is not", and "not either" means "neither". The laws extend to
any number of terms.

#### The table of laws

These are the laws used most. Each one can be checked by a truth table, and once checked it can be used
as a rewrite rule.

| Name | Law |
|---|---|
| Identity | p ∧ T ≡ p; p ∨ F ≡ p |
| Domination | p ∨ T ≡ T; p ∧ F ≡ F |
| Idempotent | p ∨ p ≡ p; p ∧ p ≡ p |
| Double negation | ¬(¬p) ≡ p |
| Commutative | p ∨ q ≡ q ∨ p; p ∧ q ≡ q ∧ p |
| Associative | (p ∨ q) ∨ r ≡ p ∨ (q ∨ r); same for ∧ |
| Distributive | p ∨ (q ∧ r) ≡ (p ∨ q) ∧ (p ∨ r); p ∧ (q ∨ r) ≡ (p ∧ q) ∨ (p ∧ r) |
| De Morgan | ¬(p ∧ q) ≡ ¬p ∨ ¬q; ¬(p ∨ q) ≡ ¬p ∧ ¬q |
| Absorption | p ∨ (p ∧ q) ≡ p; p ∧ (p ∨ q) ≡ p |
| Negation | p ∨ ¬p ≡ T; p ∧ ¬p ≡ F |
| Conditional | p → q ≡ ¬p ∨ q; p → q ≡ ¬q → ¬p |
| Biconditional | p ↔ q ≡ (p → q) ∧ (q → p) |

Note that or distributes over and, which ordinary arithmetic does not do: addition does not distribute
over multiplication. That asymmetry trips people who reason by analogy with algebra.

#### Satisfiability

A formula is **satisfiable** if at least one assignment makes it true. It is **unsatisfiable** if none
does, which is the same as its negation being a tautology. A **solution** is a satisfying assignment.

Checking satisfiability by truth table costs 2 to the n rows. No known method is fast in the worst case
for every formula, and that question, chapter 3's P versus NP, is open. Real SAT solvers are fast on the
formulas people actually write.

#### Sudoku as satisfiability

The book's showcase encodes a Sudoku as one formula. Let p(i, j, n) mean "cell in row i, column j holds
n". Clauses say every cell holds some number, no row repeats a number, no column repeats one, and no box
repeats one. The givens are extra clauses.

The formula has 729 variables, so a truth table is out of the question. A SAT solver finds the
satisfying assignment, and reading off the true variables gives the filled grid.

### Worked example

**Simple: checking laws in code.** A generic checker compares two formulas on every row.

```ts
type Env = Record<string, boolean>;
type F = (e: Env) => boolean;
declare function rows(vars: string[]): Env[]; // from 1.2
const implies = (p: boolean, q: boolean) => !p || q;
const equivalent = (vars: string[], f: F, g: F) => rows(vars).every(e => f(e) === g(e));
const tautology = (vars: string[], f: F) => rows(vars).every(f);

console.log('De Morgan:', equivalent(['p', 'q'], e => !(e.p && e.q), e => !e.p || !e.q));
console.log('converse equal?', equivalent(['p', 'q'], e => implies(e.p, e.q), e => implies(e.q, e.p)));
console.log('contrapositive equal?', equivalent(['p', 'q'], e => implies(e.p, e.q), e => implies(!e.q, !e.p)));
console.log('excluded middle tautology?', tautology(['p'], e => e.p || !e.p));
console.log('distributive:', equivalent(['p', 'q', 'r'], e => e.p || (e.q && e.r), e => (e.p || e.q) && (e.p || e.r)));
```

```text
De Morgan: true
converse equal? false
contrapositive equal? true
excluded middle tautology? true
distributive: true
```

`equivalent` is the definition of ≡ turned into code: every row agrees. `tautology` is the special case
where the other side is always true.

**Realistic: simplifying a condition in review.** A pull request has `if (!(user.banned || !user.verified))`.
By De Morgan this is `!user.banned && user.verified`: "not banned and verified". The rewrite is the same
function and much easier to read.

### Step by step

Prove ¬(p ∨ (¬p ∧ q)) ≡ ¬p ∧ ¬q without a truth table, one law per line.

Line 2 pushes the outer negation inward and flips or to and. Line 3 does it again inside. Line 5 is the
only creative step: distributing so a contradiction appears and can be dropped.

A second derivation shows (p ∧ q) → (p ∨ q) is a tautology. Rewrite the conditional as ¬(p ∧ q) ∨ (p ∨
q). De Morgan gives (¬p ∨ ¬q) ∨ (p ∨ q). Regroup to (¬p ∨ p) ∨ (¬q ∨ q), which is T ∨ T, which is T.

### Common mistake

**Negating only the parts.** The wrong way: the negation of "the server is up and the disk is healthy"
written as "the server is down and the disk is unhealthy". That is ¬p ∧ ¬q, which says both failed.

Why it fails: the negation of p ∧ q is true when either one failed. An alert written the wrong way stays
silent when only one part fails.

The fix is De Morgan, every time: flip the connective as well as the parts. ¬(p ∧ q) is ¬p ∨ ¬q, "the
server is down or the disk is unhealthy".

### In real systems

Compilers apply these laws to simplify conditions, and linters flag `!(a && b)` patterns that read
better as `!a || !b`. Query planners rewrite `NOT (x AND y)` the same way before choosing indexes.

SAT solvers check hardware designs, find bugs in software through bounded model checking, and resolve
package versions. Equivalence checking is how a chip designer proves an optimised circuit computes the
same function as the original.

## 1.4 Predicates and quantifiers

### In one sentence

A predicate is a sentence with variables that becomes a proposition once the variables get values, and
the quantifiers "for all" and "there exists" turn it into a proposition about a whole domain.

### The idea

#### Predicates

"x is greater than 3" has two parts: the variable x and the property "is greater than 3". The property
is a **predicate**, written P(x). P(x) is a **propositional function**: give it a value of x and it
returns a proposition.

Predicates can take several variables. Q(x, y) might mean "x equals y plus 3". Then Q(5, 2) is true and
Q(1, 2) is false. In code, a predicate is a function returning boolean.

#### Preconditions and postconditions

A **precondition** is a predicate that must hold on a program's input. A **postcondition** is a
predicate that must hold on its output. Chapter 5 uses these to prove programs correct.

Example: for a swap of x and y, the precondition is "x is a and y is b" and the postcondition is "x is b
and y is a".

#### The domain

Every quantified statement has a **domain** (also called the domain of discourse, or universe): the set
of values the variable can take. "Every number is non-negative" is false over the integers and true over
the natural numbers.

The domain is part of the meaning. Leaving it unstated is how two people agree on words and disagree on
the claim.

#### The universal quantifier

The **universal quantification** of P(x), written ∀x P(x), says "P(x) is true for every x in the
domain". It is false if there is even one x for which P(x) is false. That x is a **counterexample**.

On a finite domain, ∀x P(x) is the conjunction P(x1) ∧ P(x2) ∧ ... ∧ P(xn). In TypeScript it is
`domain.every(P)`.

#### The existential quantifier

The **existential quantification**, ∃x P(x), says "there is at least one x in the domain with P(x)". It
is false only if P(x) is false for every x.

On a finite domain it is the disjunction P(x1) ∨ ... ∨ P(xn). In TypeScript it is `domain.some(P)`. The
**uniqueness quantifier**, ∃!x P(x), says there is exactly one such x.

#### The empty domain

Over an empty domain, ∀x P(x) is true and ∃x P(x) is false, whatever P is. The universal is vacuously
true because there is no counterexample. The existential is false because there is no witness.

#### Restricted domains, precedence and binding

"Every positive integer squared is positive" restricts the domain inside the statement. With a
universal, the restriction becomes a conditional: ∀x (x greater than 0 → x² greater than 0). With an
existential, it becomes a conjunction: ∃z (z greater than 0 ∧ z² equals 2).

Quantifiers bind tighter than every connective. ∀x P(x) ∨ Q(x) means (∀x P(x)) ∨ Q(x), and the last x
is not covered. A variable inside a quantifier's scope is **bound**; one outside every scope is **free**.
A statement with a free variable is not a proposition yet.

#### Negating quantifiers

De Morgan's laws for quantifiers: ¬∀x P(x) ≡ ∃x ¬P(x), and ¬∃x P(x) ≡ ∀x ¬P(x). "Not everyone passed"
means "someone failed". "Nobody failed" means "everyone did not fail".

On a finite domain these are exactly De Morgan's laws from 1.3 applied to a long and or a long or.

#### Translating and logic programming

Translating English with quantifiers means picking the domain, picking predicates, and choosing ∀ or ∃
with the right connective. **Logic programming** languages such as Prolog store facts and rules as
predicates and answer queries by searching for values that make them true. Datalog, a cousin, runs
inside some static analysers and databases.

### Worked example

**Simple: quantifiers as array methods.**

```ts
const users = [{ name: 'asha', roles: ['admin'] }, { name: 'ravi', roles: [] as string[] }];
console.log('forall has role:', users.every(u => u.roles.length > 0));
console.log('exists admin:', users.some(u => u.roles.includes('admin')));
console.log('empty every:', ([] as number[]).every(x => x > 100), 'empty some:', ([] as number[]).some(x => x > 100));
```

```text
forall has role: false
exists admin: true
empty every: true empty some: false
```

The first line is false because ravi is a counterexample. The last line is the empty-domain rule, and
JavaScript follows it exactly.

**Realistic: "every student in the class has taken a course in calculus".** With domain "students in
the class" and C(x) for "x has taken calculus", it is ∀x C(x). With domain "all people" and S(x) for "x
is in the class", it is ∀x (S(x) → C(x)). Both are right; the domain changed the formula.

**Realistic: a restricted existential.** "Some order is over ₹10,000 and unpaid" is ∃o (Big(o) ∧
Unpaid(o)). Writing ∃o (Big(o) → Unpaid(o)) is wrong: any small order makes the conditional true, so the
statement holds even if every big order is paid.

are quantifiers. Property-based testing tools such as fast-check search for a counterexample to a
universal statement.

The empty-domain rule matters in production. A dashboard that says "all checks passed" when zero checks
ran is reporting a vacuous truth. The fix is to assert the domain is non-empty first.

## 1.5 Nested quantifiers

### In one sentence

When one quantifier sits inside another, the order changes the meaning, and negation walks through the
whole chain flipping each quantifier in turn.

### The idea

#### Quantifiers inside quantifiers

**Nested quantifiers** are quantifiers within the scope of other quantifiers, as in ∀x ∃y (x plus y
equals 0). Read it from the left: "for every x, there is a y such that x plus y is 0". Over the integers
it is true, because y can be the negative of x.

A useful way to read nesting is as loops. ∀x ∃y P(x, y) is an outer loop over x with an inner search for
a y. The y found may depend on the x.

<Figure
  caption="∀x ∃y as nested loops. The inner search restarts for each x, so the y it finds can be different every time; that dependence is what the order of quantifiers encodes."
  art={`
  for every x in domain:          (forall x)
      found = false
      for each y in domain:       (exists y)
          if P(x, y): found = true
      if not found: return FALSE
  return TRUE
`}
/>

#### Order matters

Two quantifiers of the same kind can be swapped: ∀x ∀y P ≡ ∀y ∀x P, and the same for ∃. Mixed ones
cannot. ∀x ∃y P(x, y) says each x has its own y. ∃y ∀x P(x, y) says one single y works for every x.

The second is much stronger. If one y works for all x, then certainly each x has a y. The converse
fails.

| Statement | True when | False when |
|---|---|---|
| ∀x ∀y P(x, y) | P is true for every pair | some pair makes P false |
| ∀x ∃y P(x, y) | every x has some y with P | some x has no y at all |
| ∃x ∀y P(x, y) | one x works with every y | every x fails with some y |
| ∃x ∃y P(x, y) | some pair makes P true | every pair makes P false |

#### Translating mathematical statements

"The sum of two positive integers is positive" is ∀x ∀y ((x greater than 0 ∧ y greater than 0) → x plus
y greater than 0). "Every real number except zero has a multiplicative inverse" is ∀x (x ≠ 0 → ∃y (xy
equals 1)).

The definition of a limit is the famous example of three nested quantifiers: for every ε greater than 0
there exists δ greater than 0 such that for all x, if x is within δ of a then f(x) is within ε of L.

#### Translating English

Pick a domain and predicates, then build from the inside. "Everyone has exactly one best friend" becomes
∀x ∃y (B(x, y) ∧ ∀z ((z ≠ y) → ¬B(x, z))). The inner ∀z says nobody else is x's best friend.

#### Negating nested quantifiers

Apply the quantifier De Morgan law repeatedly from the outside in. Each step moves ¬ past one quantifier
and flips it. When ¬ reaches the predicate, simplify it with the laws from 1.3.

### Worked example

**Simple: request handlers.** "Every request has a handler" versus "one handler serves every request".

```ts
const reqs = ['GET /a', 'GET /b'];
const handlers = [{ id: 'h1', serves: ['GET /a'] }, { id: 'h2', serves: ['GET /b'] }];
const everyReqHasHandler = reqs.every(r => handlers.some(h => h.serves.includes(r)));
const oneHandlerForAll = handlers.some(h => reqs.every(r => h.serves.includes(r)));
console.log('forall r exists h:', everyReqHasHandler, '| exists h forall r:', oneHandlerForAll);
```

```text
forall r exists h: true | exists h forall r: false
```

The two lines differ only in which method is outside. Swapping `every` and `some` swapped the
quantifiers, and the answer changed.

**Realistic: a multi-tenant permission rule.** "Every tenant has an owner who can read every document of
that tenant." With T for tenants, U for users and D for documents: ∀t ∃u (Owner(u, t) ∧ ∀d (Of(d, t) →
CanRead(u, d))). Moving ∃u to the front would claim one user owns every tenant, which is a security
review finding, not a requirement.

### Common mistake

**Swapping the quantifiers while translating.** The wrong way: "there is a password that every account
uses" written for "every account has a password". The first is ∃p ∀a, a security disaster; the second
is ∀a ∃p.

The fix is to say the formula back in English with "the same one" or "its own". "Each account has its
own password" is ∀a ∃p; "the same password for all" is ∃p ∀a.

### In real systems

SQL's `NOT EXISTS` subqueries are negated nested quantifiers. "Customers who bought every product" is ∀p
∃order, and SQL writes it as "there is no product they did not buy", a double negation of nested
quantifiers.

Distributed-systems guarantees are nested quantifiers too. "Every write is eventually visible to every
reader" is ∀w ∀r ∃t (after time t, r sees w). Getting the order wrong changes which consistency model
you promised.

## 1.6 Rules of inference

### In one sentence

A rule of inference is a pattern of argument that always leads from true premises to a true conclusion,
and a valid proof is a chain of such steps.

### The idea

#### Arguments and validity

An **argument** is a list of propositions called **premises** followed by a **conclusion**. It is
**valid** if the conclusion must be true whenever all the premises are true. Validity is about the form,
not the subject matter.

An argument form with premises p1 to pn and conclusion q is valid exactly when (p1 ∧ ... ∧ pn) → q is a
tautology. That gives a mechanical test, but with many variables the truth table explodes. Rules of
inference are shortcuts: small argument forms already proved valid.

A valid argument can still have a false conclusion if a premise is false. Validity says the reasoning is
sound; it does not vouch for the starting facts.

#### The rules for propositions

| Rule | From | Conclude |
|---|---|---|
| Modus ponens | p, and p → q | q |
| Modus tollens | ¬q, and p → q | ¬p |
| Hypothetical syllogism | p → q, and q → r | p → r |
| Disjunctive syllogism | p ∨ q, and ¬p | q |
| Addition | p | p ∨ q |
| Simplification | p ∧ q | p |
| Conjunction | p, and q | p ∧ q |
| Resolution | p ∨ q, and ¬p ∨ r | q ∨ r |

**Resolution** deserves a note. The two premises are **clauses**, ors of variables or negations. One has
p and the other ¬p; the conclusion, the **resolvent**, keeps everything else. Computer theorem provers
and SAT solvers are built on resolution.

#### Fallacies

A **fallacy** is an invalid argument that looks valid. **Affirming the conclusion** argues from q and p
→ q to p. **Denying the hypothesis** argues from ¬p and p → q to ¬q. Both fail in the row where p is
false and q is true.

**Begging the question**, or circular reasoning, uses the conclusion as a premise. It is common in proofs
that "rewrite" the goal into itself.

#### Rules for quantified statements

| Rule | From | Conclude |
|---|---|---|
| Universal instantiation | ∀x P(x) | P(c) for any particular c |
| Universal generalisation | P(c) for an arbitrary c | ∀x P(x) |
| Existential instantiation | ∃x P(x) | P(c) for some new name c |
| Existential generalisation | P(c) for some particular c | ∃x P(x) |

"Arbitrary" in universal generalisation is strict. c must be a fresh name that nothing else assumed
anything about, so the reasoning works for every element. **Universal modus ponens** combines two rules:
from ∀x (P(x) → Q(x)) and P(a), conclude Q(a).

### Worked example

**Simple: checking rules by tautology in code.**

```ts
console.log('modus ponens valid?', tautology(['p', 'q'], e => implies(e.p && implies(e.p, e.q), e.q)));
console.log('affirming the consequent valid?', tautology(['p', 'q'], e => implies(e.q && implies(e.p, e.q), e.p)));
console.log('hypothetical syllogism valid?', tautology(['p', 'q', 'r'], e => implies(implies(e.p, e.q) && implies(e.q, e.r), implies(e.p, e.r))));
console.log('resolution valid?', tautology(['p', 'q', 'r'], e => implies((e.p || e.q) && (!e.p || e.r), e.q || e.r)));
```

```text
modus ponens valid? true
affirming the consequent valid? false
hypothetical syllogism valid? true
resolution valid? true
```

Each line is the definition of validity: "premises imply conclusion" is a tautology. The fallacy fails
because one row breaks it.

**Realistic: an on-call argument.** Premises: (1) if the deploy changed the config, the service
restarted; (2) if the service restarted, there is a restart event in the log; (3) there is no restart
event. Hypothetical syllogism on 1 and 2 gives "if the deploy changed the config, there is a restart
event". Modus tollens with 3 gives "the deploy did not change the config". The incident is somewhere else.

### Common mistake

meant the logged-in user.

assumption. The fix is to pick a fresh name every time you instantiate an existential.

### In real systems

Type checkers are inference engines: from "x is a string" and "if x is a string then x.length is a
number", they derive "x.length is a number". Rule engines and authorisation systems such as policy
languages run modus ponens all day.

Root-cause analysis is modus tollens. "If the database were down, the health check would fail; the
health check passes; so the database is not down." The trap in incidents is affirming the conclusion:
"the database being down causes errors; there are errors; so the database is down."

## 1.7 Introduction to proofs

### In one sentence

A proof is a sequence of justified steps from accepted facts to a claim, and the three basic shapes are
direct proof, proof by contrapositive, and proof by contradiction.

### The idea

#### The vocabulary of proof

A **theorem** is a statement that has been proved true. A **proposition**, in this sense, is a less
important theorem; a **lemma** is a small theorem used to prove a bigger one; a **corollary** follows
quickly from a theorem. A **conjecture** is a statement believed true but not yet proved.

**Axioms**, also called postulates, are statements accepted without proof, such as the rules of
arithmetic in the appendix. A **proof** uses axioms, definitions, earlier theorems and rules of inference.

#### What a theorem usually looks like

Most theorems are universal conditionals, ∀x (P(x) → Q(x)), even when the ∀ is left unwritten. "If n is
odd, n² is odd" means for every integer n. The proof takes an arbitrary n, assumes P(n) and shows Q(n);
universal generalisation then gives the ∀.

Informal proofs skip the rule names and combine steps. They are still chains of valid inferences, and a
reader should be able to fill in any skipped step.

#### Direct proof

A **direct proof** of p → q assumes p and derives q by a chain of steps. It is the first thing to try.

The key move is to unpack definitions. "n is even" means there is an integer k with n equal to 2k. "n is
odd" means there is an integer k with n equal to 2k plus 1. Once the definitions are written out, the
proof is usually algebra.

#### Proof by contrapositive

A **proof by contrapositive** proves p → q by proving ¬q → ¬p, which is equivalent. Use it when q is hard
to start from but ¬q gives you something concrete to work with.

It is an **indirect proof**: it does not go straight from hypothesis to conclusion.

#### Vacuous and trivial proofs

If p is false, p → q is true. Showing p is false is a **vacuous proof**. If q is true regardless of p, p
→ q is true; showing q alone is a **trivial proof**. Both turn up as base cases in induction.

#### Proof by contradiction

A **proof by contradiction** shows p by assuming ¬p and deriving a contradiction, some r ∧ ¬r. Since ¬p
leads to something impossible, ¬p is false and p is true.

To prove a conditional p → q by contradiction, assume p ∧ ¬q and derive a contradiction.

#### Proving an iff, and several equivalences

To prove p ↔ q, prove p → q and q → p. To prove that p1, p2, ..., pn are all equivalent, prove a cycle
p1 → p2 → ... → pn → p1. Each one then implies every other by hypothetical syllogism.

#### Counterexamples and mistakes in proofs

A single counterexample disproves a universal statement. No number of examples proves one.

The common mistakes in proofs are arithmetic errors, affirming the conclusion, dividing by something
that could be zero, assuming what is to be proved, and proving a special case and claiming the general
one.

### Worked example

**Simple: direct proof.** If n is odd, then n² is odd.

Assume n is odd. Then n is 2k plus 1 for some integer k. Squaring gives n² equal to 4k² plus 4k plus 1,
which is 2(2k² plus 2k) plus 1. The bracket is an integer, so n² has the form 2m plus 1 and is odd.

**Simple: contrapositive.** If 3n plus 2 is odd, then n is odd.

A direct start is awkward: knowing 3n plus 2 is 2k plus 1 does not give n easily. Try the contrapositive:
if n is even, then 3n plus 2 is even. Let n be 2k. Then 3n plus 2 is 6k plus 2, which is 2(3k plus 1),
which is even. The contrapositive is proved, so the original is too.

**Realistic: a code claim.** "If an array has a duplicate, sorting it puts two equal elements next to
each other." Direct proof: let x appear at two positions. After sorting, every element equal to x sits in
one contiguous block, because any element between two copies of x is at least x and at most x, so equals
x. The block has length at least 2, so two equal elements are adjacent. That is why the "sort then scan
neighbours" duplicate check is correct.

**Counterexample.** "n² plus n plus 41 is prime for every non-negative integer n." It holds for a long
time, which makes it look true. I searched for the first failure:

```ts
const isPrime = (n: number) => {
  if (n < 2) return false;
  for (let d = 2; d * d <= n; d++) if (n % d === 0) return false;
  return true;
};
let n = 0;
while (isPrime(n * n + n + 41)) n++;
console.log('first n where n^2+n+41 is not prime:', n, '->', n * n + n + 41, '=', 41, 'x', (n * n + n + 41) / 41);
```

```text
first n where n^2+n+41 is not prime: 40 -> 1681 = 41 x 41
```

Forty successes, then one failure, and the universal claim is false. That is the whole case against
"I tried a lot of examples".

it is exactly what the rest of the proof contradicts.

A proof of an iff, line by line: n is even iff n² is even.

1. (→) If n is even, n is 2k, so n² is 4k², which is 2(2k²), so n² is even. Direct proof.
2. (←) If n² is even, then n is even. Prove the contrapositive: if n is odd, n² is odd. Done above.
3. Both directions hold, so the biconditional holds.

### Common mistake

**Dividing by zero, or by something that might be zero.** The wrong "proof" that 1 equals 2: let a equal
b; then a² equals ab; subtract b²: a² minus b² equals ab minus b²; factor: (a plus b)(a minus b) equals
b(a minus b); divide by (a minus b): a plus b equals b; so 2b equals b, and 1 equals 2.

Why it fails: a minus b is 0, and dividing both sides by 0 is not a valid step. The fix: every time you
divide, cancel or take a square root, write down why the thing is not zero or negative.

**Circular reasoning.** The wrong way to prove "if n² is even then n is even": "n² is even, so n² is 2k;
then n must be 2l for some l, so n is even." The step "then n must be 2l" is the claim itself.

### In real systems

Code review is proof review. "This function never returns null because every branch returns a value
built by the constructor" is a direct proof by cases. "If the lock were not held, the counter would skip a
value; we never see a skipped value in the log" is a contrapositive argument, and it is only as strong as
the log.

Counterexamples are bug reports. One failing input disproves "this function handles all inputs", and a
property-based test framework is a machine for finding them, as the 41 search above was.

<summary>Answer</summary>

Contrapositive. Starting from n² odd gives no handle on n, but "if n is even then n² is even" is a
one-line direct proof.

</details>

<details>
<summary>Answer</summary>

## 1.8 Proof methods and strategy

### In one sentence

Beyond the three basic shapes, proofs split into cases, build or show the existence of an object, prove
it is unique, or disprove with a counterexample, and choosing among them is a skill with its own habits.

### The idea

#### Exhaustive proof and proof by cases

A **proof by cases** proves (p1 ∨ p2 ∨ ... ∨ pn) → q by proving each pi → q separately. The cases must
cover every possibility. An **exhaustive proof** is the special case where every possible input is
checked, which only works on a small finite set.

#### Without loss of generality

When two cases are the same up to renaming, a proof does one and says **without loss of generality**
(WLOG). It is only honest if the other case really follows by swapping names, so say what the swap is.

#### Existence proofs

An **existence proof** proves ∃x P(x). A **constructive** existence proof exhibits a particular x, called
a **witness**. A **nonconstructive** one shows an x must exist without saying which, often by
contradiction or by cases.

#### Uniqueness proofs

A **uniqueness proof** proves ∃!x P(x) in two parts. **Existence**: show some x has P. **Uniqueness**:
assume y also has P and show y equals x.

#### Proof strategies

**Forward reasoning** starts from the premises and moves toward the goal. **Backward reasoning** starts
from the goal and asks "what would be enough to prove this?" Most real proofs mix both.

**Adapting existing proofs** is a strategy too: a known proof of a similar fact often adapts. When
stuck, try a small case, draw a picture, or try to prove the opposite and see where it breaks.

#### Conjectures, tilings and open problems

A **conjecture** is formed from examples and then attacked with proof or counterexample. The book uses
tilings of checkerboards with dominoes as a playground: colouring arguments show some tilings are
impossible.

Some easy-to-state conjectures remain open. The **3x plus 1 conjecture** (Collatz) says that repeatedly
halving even numbers and replacing odd n with 3n plus 1 always reaches 1. Nobody has proved it.

### Worked example

**Simple: proof by cases.** Claim: for every integer n, n² is at least n. Test small values first: 0
gives 0, 1 gives 1, −3 gives 9. It holds, so try a proof by cases. Case n is 0 or more and
less than 1: n is 0, and 0 equals 0. Case n at least 1: multiply n at least 1 by n, which is positive, to
get n² at least n. Case n negative: n² is positive and n is negative, so n² is bigger.

**Simple: constructive existence.** There is a positive integer that can be written as a sum of two cubes
in two different ways. Witness: 1729 is 10³ plus 9³ and also 12³ plus 1³. Showing the witness and
checking the arithmetic is the whole proof.

**Nonconstructive existence.** There exist irrational numbers x and y with x to the power y rational.
Consider √2 to the power √2. If it is rational, take x and y both √2. If it is irrational, take x equal to
that number and y equal to √2; then x to the y is √2 to the power 2, which is 2. Either way a pair
exists, and we never learn which.

**Uniqueness.** If a and b are real with a not 0, there is exactly one r with ar plus b equal to 0.
Existence: r equal to −b/a works. Uniqueness: if as plus b is also 0, then ar plus b equals as plus b, so
ar equals as, and dividing by a, which is not 0, gives r equal to s.

**Realistic: a cases proof about code.** "`Math.abs(x) >= x` for every finite number x." Case x is 0 or
more: abs returns x, and x is at least x. Case x negative: abs returns −x, which is positive and so greater
than x. The proof also shows where it breaks: NaN is not covered by either case, and `Math.abs(NaN) >=
NaN` is false. The cases had to be exhaustive, and for floats they were not.

### Step by step

Tiling, walked line by line: a standard 8 by 8 board with two opposite corners removed cannot be tiled
by dominoes, each covering two adjacent squares.

The same shape, "find a quantity every move preserves and show the goal changes it", proves that some
puzzles have no solution and that some distributed protocols cannot reach some states.

### Common mistake

**Cases that do not cover everything.** The wrong way is the `Math.abs` proof without the NaN case, or a
proof about integers that forgets 0. Why it fails: the claim is universal, and the uncovered input is a
potential counterexample.

The fix is to write the case split as a disjunction and prove it is a tautology on the domain first: "x
is negative, zero, or positive" is exhaustive over the reals; "x is negative or positive" is not.

**Claiming WLOG when the cases are not symmetric.** If the two cases differ, because one involves a
boundary and the other does not, WLOG hides a real case. Write both.

### In real systems

TypeScript's exhaustive `switch` with a `never` check is proof by cases enforced by the compiler: forget a
case and the build fails. Existence proofs are what a test fixture is: a witness that a state is
reachable. Uniqueness is what a database `UNIQUE` constraint enforces and what an idempotency key relies on.

Invariant arguments like the domino colouring prove safety properties in distributed systems: a
quantity such as "at most one leader per term" is preserved by every step, so a bad state is never reached.

### Check yourself

**what are the two parts of a uniqueness proof?**

<details>
<summary>Answer</summary>

Existence: show some x has the property. Uniqueness: assume y also has it and show y equals x.

</details>

**is "√2 to the power √2 is either rational or irrational, so a pair exists" constructive?**

<details>
<summary>Answer</summary>

No. It proves a pair exists without saying which one. That is what makes it nonconstructive.

</details>

## From beginner to strategy

<Levels label="Chapter 1, The Foundations: Logic and Proofs">
<Level name="Beginner" depth={3}>

The smallest working version of this chapter is: a proposition is true or false, connectives combine
them, and a truth table tells you the result. If you can fill in the table for p → q without looking,
and say why the false-hypothesis rows are true, you have the core.

Worked example: "If it rains, the match is cancelled." It did not rain, and the match was cancelled
anyway for a power cut. Was the statement false? No. The hypothesis was false, so the promise was never
tested, and the conditional is true.

The common beginner mistake is reading "if" as "if and only if". The fix is to ask "does the sentence say
anything about what happens when the hypothesis is false?" Almost always, it does not.

</Level>
<Level name="Intermediate" depth={3}>

At this level the pieces combine in code. Conditions in `if` statements, `every` and `some` calls, and
SQL filters are formulas, and you can rewrite them with the laws of 1.3 to make them simpler or to find
the case they miss.

Example: a rate limiter allows a request when `!(overLimit && !isAdmin)`. De Morgan turns that into
`!overLimit || isAdmin`: allow if under the limit, or if an admin. The rewrite reveals the policy in one
reading, and a test for "admin over the limit" becomes obviously necessary.

```ts
const allowA = (over: boolean, admin: boolean) => !(over && !admin);
const allowB = (over: boolean, admin: boolean) => !over || admin;
const same = [[true, true], [true, false], [false, true], [false, false]]
  .every(([o, a]) => allowA(o, a) === allowB(o, a));
console.log('same policy:', same);
```

```text
same policy: true
```

The mistake here is rewriting by intuition and changing the function. The fix is the four-row check
above, which costs one line and catches every wrong rewrite.

</Level>
<Level name="Advanced" depth={3}>

Underneath, validity is a precise notion: an argument is valid exactly when the conjunction of its
premises implies its conclusion in every row. Rules of inference are pre-proved valid forms, and a proof
is a finite chain of them. Quantifier rules add the discipline of fresh names: universal generalisation
needs an arbitrary element, and existential instantiation needs a new name.

Example: from ∀x (P(x) → Q(x)) and ∃x P(x), conclude ∃x Q(x). Instantiate the existential with a fresh
c to get P(c). Instantiate the universal at the same c to get P(c) → Q(c). Modus ponens gives Q(c).
Existential generalisation gives ∃x Q(x). The order matters: instantiate the existential first, because
its name must be fresh.

The mistake is instantiating the universal first at some c and then claiming the existential's witness is
that same c. The fix is the rule above: existentials first, fresh names always.

</Level>
<Level name="Edge cases" depth={3}>

Single boundaries the chapter's rules decide, each with what happens:

- **Empty domain.** ∀x P(x) is true and ∃x P(x) is false. `[].every(f)` is true and `[].some(f)` is
  false. A "all checks passed" report with zero checks is vacuously true.
- **False hypothesis.** p → q with p false is true. A guard clause never triggered tells you nothing.
- **One-variable formula.** p ∨ ¬p is a tautology and p ∧ ¬p a contradiction; there is no contingency
  with only constants.
- **Zero in a proof.** Dividing by a quantity that is zero in one case breaks the proof only in that case.
  The 1 equals 2 "proof" is exactly this.
- **Duplicates in a uniqueness claim.** "There is exactly one admin" fails both when there are none and
  when there are two; test both.

The mistake with edge cases is treating them as rare. The fix is to put each one above into a test.

</Level>
<Level name="Corner cases" depth={3}>

Two boundaries at once:

- **Empty domain plus negation.** "Not every user is verified" over an empty user table: ∀x V(x) is true,
  so its negation is false. Code that checks `!users.every(verified)` to decide "send reminders" sends
  none, and that is correct; code that checks `users.some(u => !verified(u))` agrees. A hand-written loop
  that sets a flag inside the loop body and defaults it wrongly disagrees.
- **Quantifier order plus an empty inner domain.** ∀r ∃h Serves(h, r) with no handlers and no requests
  is true; with requests and no handlers it is false; with handlers and no requests it is true.
- **NaN plus a proof by cases.** `x >= 0` and `x < 0` are both false for NaN, so a two-case proof about
  numbers silently skips it. `Math.abs(NaN) >= NaN` is false.
- **Short-circuit plus side effects.** `a() || b()` skips `b()` when `a()` is true. Logically p ∨ q is
  symmetric, but in code the order changes which side effects run.

The fix in each case is to write the formula, list its boundaries, and test the combinations, not just
each boundary alone.

</Level>
<Level name="Production level" depth={3}>

In production the logic lives in conditions that grow over years. A feature flag check that started as
`enabled` becomes `enabled && (beta || plan === 'pro') && !region.blocked`. Each change adds a variable
and doubles the truth table, and the untested rows are where incidents come from.

Practical tools: write complex conditions as named predicates (`const canExport = ...`), test them with
a table of rows, and use property-based tests to search for counterexamples to the universal claims your
code makes. Observability helps too: logging which branch ran gives you the row of the truth table that
production actually hit.

The mistake is fixing a condition bug by adding another clause. The fix is to rewrite the whole condition
from the spec, check equivalence against the old one row by row, and look at the rows where they differ:
those are the behaviour change you are shipping.

</Level>
<Level name="Mindset" depth={3}>

The habit this chapter teaches is to translate before reasoning. When a requirement, a bug report or a
claim in a meeting is fuzzy, write it as a formula with an explicit domain, and the fuzziness turns into
specific questions.

The second habit is to look for the counterexample before the proof. If a claim is false, one input
shows it quickly; if the search fails, the place where it fails often suggests the proof.

Example outside maths: "every service has an on-call owner" in a reliability review. Written as ∀s ∃o
OnCall(o, s), it suggests the query that checks it and the negation that finds the gaps: ∃s ∀o
¬OnCall(o, s). The mistake is arguing about the English; the fix is to run the query.

</Level>
<Level name="System design" depth={3}>

In a larger system, logic sits in the policy layer. An authorisation service evaluates rules like "a user
can edit a document if they own it, or they are in a group that has edit rights on its folder, unless the
document is locked". That is a formula with quantifiers over groups and folders, evaluated on every
request.

Concrete design: keep the rules declarative, as data, so they can be checked for consistency with a
solver before deployment; evaluate them in one place so every service agrees; and log each decision with
the facts that produced it, which is a proof trace for audits.

The mistake is scattering the same rule across services as ad hoc `if` statements, so they drift and
disagree. The fix is a single policy engine whose inputs are facts and whose output is a decision with
its reasons.

</Level>
<Level name="Strategy" depth={3}>

I learn this chapter by doing three things in order: translation drills, a small truth-table and
equivalence checker in TypeScript, and writing short proofs by hand. Each feeds the next: the checker
verifies my translations, and the proofs use the laws the checker confirms.

Concrete plan: translate ten requirements from my own projects into predicate logic and negate each;
build the checker from this page and use it on every law in 1.3; write the direct, contrapositive,
contradiction, cases, existence and uniqueness proofs on this page from memory.

The mistake is reading the proofs and nodding. The fix is to close the page and rewrite each proof on
paper, then compare. Done when every negation I write, turned back into English, describes the real
failure case, and I can reproduce the √2 and domino proofs from a blank page.

</Level>
</Levels>

## Questions people ask

**why is "if false then anything" true? It feels like cheating.**

Because the conditional is a promise that is broken only when the hypothesis holds and the conclusion
fails. If the hypothesis never holds, nothing was promised. Choosing "true" here is also what makes
universal statements like "every even prime greater than 2 is odd" behave sensibly.

**do I need to learn the names of all the rules of inference?**

Learn the four you will use constantly: modus ponens, modus tollens, hypothetical syllogism and
resolution. The others are obvious once you see them. Names help when reviewing someone else's argument.

**how do I know which proof method to use?**

Try a counterexample search first, then a direct proof after unpacking definitions. If the conclusion
gives you nothing to work with, try the contrapositive; if the negation gives you a concrete object, try
contradiction. The flow diagram in 1.8 is the order I use.

**is a proof by contradiction weaker than a direct proof?**

No, it is equally valid. It is sometimes less informative, because a nonconstructive existence proof by
contradiction does not tell you the witness. When you can, prefer the constructive version.

**how is this different from the MIT text's first chapters?**

The MIT text goes faster and leans harder on proofs. Rosen spends more time on translation, applications
and worked examples. I use Rosen when I want more practice.

## Key takeaways

- A proposition is true or false, and a truth table computes any compound from its parts.
- p → q is false only when p is true and q is false; its contrapositive is equivalent, its converse is not.
- De Morgan's laws flip the connective as well as the parts, for propositions and for quantifiers.
- Universal statements pair with →, existential statements pair with ∧.
- The order of mixed quantifiers changes the meaning; same-kind quantifiers can swap.
- An argument is valid when its premises imply its conclusion in every row; rules of inference are the
  pre-checked shapes.
- One counterexample disproves a universal claim; no number of examples proves it.
- Choose a proof method deliberately: counterexample search, direct, contrapositive, contradiction, cases,
  construction.

## Glossary

- **Proposition**: a declarative sentence that is true or false, not both.
- **Propositional variable**: a letter that stands for a proposition.
- **Truth table**: every combination of input values with the output for each.
- **Negation, conjunction, disjunction**: not, and, inclusive or.
- **Exclusive or**: true when exactly one input is true.
- **Conditional**: p → q, false only when p is true and q false.
- **Hypothesis, conclusion**: the p and q of p → q.
- **Converse, inverse, contrapositive**: q → p, ¬p → ¬q, ¬q → ¬p.
- **Biconditional**: p ↔ q, true when p and q agree.
- **Bit string**: a sequence of 0s and 1s; bitwise operators act on each position.
- **Consistent**: a set of propositions that can all be true at once.
- **Tautology, contradiction, contingency**: always true, always false, neither.
- **Logically equivalent**: same truth value in every row.
- **Satisfiable**: true under at least one assignment.
- **Predicate**: a property of one or more variables; a function returning a proposition.
- **Domain**: the set of values a quantified variable ranges over.
- **Universal, existential, uniqueness quantifier**: for all, there exists, there exists exactly one.
- **Bound, free variable**: inside a quantifier's scope, or not.
- **Nested quantifiers**: quantifiers within the scope of others.
- **Argument, premise, conclusion, valid**: a list of premises and a conclusion that must be true when they are.
- **Rule of inference**: a valid argument form used as a step.
- **Resolution, resolvent**: from p ∨ q and ¬p ∨ r, conclude q ∨ r.
- **Fallacy**: an invalid argument that looks valid.
- **Theorem, lemma, corollary, conjecture, axiom**: proved, helper, quick consequence, unproved belief, accepted without proof.
- **Direct proof, contrapositive proof, proof by contradiction**: assume p and derive q; prove ¬q → ¬p; assume the negation and derive a contradiction.
- **Vacuous, trivial proof**: the hypothesis is false; the conclusion is true anyway.
- **Proof by cases, exhaustive proof**: prove each case of an exhaustive split; check every input.
- **Without loss of generality**: doing one of several cases that are the same up to renaming.
- **Constructive, nonconstructive existence proof**: exhibit a witness, or show one must exist.
- **Counterexample**: an element for which a universal claim fails.
