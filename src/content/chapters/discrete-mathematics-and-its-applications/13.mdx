What can a computer do, and what can't it do, no matter how fast it gets? To answer that you need precise
models of computation, and this last chapter builds three of them, each stronger than the one before.
Grammars describe languages by rules that generate strings. Finite-state machines read input one symbol at
a time with a fixed, finite memory. Turing machines add an unbounded tape and turn out to capture
everything any computer can do. Along the way the chapter connects machines to grammars and to regular
expressions, shows that some simple languages are beyond finite machines, and ends with problems that no
machine can solve. For a software developer this is the theory behind parsers, lexers, regex engines,
protocol state machines and the hard limits of program analysis.

## 13.1 Languages and grammars

### In one sentence

A grammar is a finite set of rewriting rules that generates a possibly infinite set of strings, the
language, by starting from a start symbol and repeatedly replacing nonterminals until only terminals remain;
restricting the shape of the rules gives the Chomsky hierarchy of types 0 to 3.

### The idea

#### Alphabets, strings and languages

An **alphabet** V, also called a vocabulary, is a finite nonempty set of symbols. A **string** (or word)
over V is a finite sequence of symbols; the **empty string**, written λ, has length 0. `V*` is the set of all
strings over V, and a **language** over V is any subset of `V*`. Languages can be finite (the reserved words of
a programming language) or infinite (all syntactically valid programs).

The **concatenation** of strings x and y, written xy, is x followed by y. For languages A and B, AB is the set
of all xy with x in A and y in B, and `A*` (the **Kleene star**) is the set of all concatenations of zero or
more strings from A, which always includes λ.

#### Phrase-structure grammars

A **phrase-structure grammar** G consists of:

- a vocabulary V;
- a subset T of V of **terminal** symbols, the symbols that appear in finished strings; the rest, N equal to
  V minus T, are **nonterminals**;
- a **start symbol** S in N;
- a finite set P of **productions**, rules written w₀ → w₁, where w₀ contains at least one nonterminal.

If z₀ is a string containing w₀ as a substring, replacing that occurrence by w₁ gives z₁, and we say z₁ is
**directly derivable** from z₀. A sequence of such steps is a **derivation**. The **language generated** by
G, L(G), is the set of terminal strings derivable from S.

Here, as a convention, uppercase letters are nonterminals and everything else is a terminal. A rule set
like S → (S)S and S → λ is written S → (S)S | λ, the bar separating alternatives.

#### Derivation trees

For grammars whose left-hand sides are single nonterminals, a derivation can be drawn as a **derivation
tree** (or parse tree): the root is S, each internal node is a nonterminal whose children are the symbols of
the right-hand side it was replaced by, and the leaves read left to right give the derived string. Many
derivations, differing only in the order of replacements, give the same tree. A **leftmost derivation**
always replaces the leftmost nonterminal, and there is one per tree.

A grammar is **ambiguous** if some string has two different derivation trees. Ambiguity matters because a
tree is a meaning: for arithmetic, the tree decides which operation happens first.

#### The Chomsky hierarchy

Grammars are classified by the shape of their productions:

| type | name | allowed productions | machine model |
|---|---|---|---|
| 0 | phrase-structure | any w₀ → w₁ | Turing machine |
| 1 | context-sensitive | lAr → lwr, w nonempty (and S → λ if S never appears on a right side) | linear bounded automaton |
| 2 | context-free | A → w, a single nonterminal on the left | pushdown automaton |
| 3 | regular | A → aB, A → a, and S → λ | finite-state automaton |

Each type is a special case of the one above it, and the language classes are strictly nested: there are
context-free languages that are not regular, context-sensitive ones that are not context-free, and so on.
"Context-free" means the nonterminal A can be replaced regardless of what surrounds it; in a
context-sensitive rule lAr → lwr, A may be replaced by w only between l and r.

#### Backus–Naur form

Programming-language syntax is usually given as a context-free grammar in **Backus–Naur form** (BNF):
nonterminals are written in angle brackets, the arrow is written ::=, and alternatives are separated by a
bar. Extended BNF adds notation for optional parts and repetition, so that a list of digits can be written
in one rule instead of a recursive pair.

The rule reads: a balanced string is either empty, or a pair of parentheses around a balanced string,
followed by another balanced string. That one sentence is also a recursive definition (chapter 5), and a
structural induction over it proves that every derived string has as many ( as ) and never has more ) than (
in any prefix.

**Realistic: generating a language mechanically.** A breadth-first search over sentential forms, always
expanding the leftmost nonterminal and discarding forms with too many terminals, lists every string up to
a given length.

```ts
type G = Record<string, string[]>; // nonterminals uppercase, '' = lambda
function generate(g: G, start: string, maxLen: number) {
  const out = new Set<string>(); const seen = new Set<string>(); const q = [start];
  while (q.length) {
    const s = q.shift()!; if (seen.has(s)) continue; seen.add(s);
    const i = [...s].findIndex(c => c >= 'A' && c <= 'Z');
    if (i < 0) { if (s.length <= maxLen) out.add(s); continue; }
    const terms = [...s].filter(c => !(c >= 'A' && c <= 'Z')).length;
    if (terms > maxLen) continue;
    for (const r of g[s[i]]) q.push(s.slice(0, i) + r + s.slice(i + 1));
  }
  return [...out].sort((a, b) => a.length - b.length || (a < b ? -1 : 1));
}
const b = generate({ S: ['(S)S', ''] }, 'S', 8);
console.log('balanced by length', [0, 2, 4, 6, 8].map(n => b.filter(s => s.length === n).length));
console.log(b.filter(s => s.length === 6).join(' '));
console.log('anbn', generate({ S: ['aSb', ''] }, 'S', 8).map(s => s || 'λ').join(' '));
const r = generate({ S: ['0S', '1A', ''], A: ['0S', ''] }, 'S', 6);
console.log('no 11 by length', [0, 1, 2, 3, 4, 5, 6].map(n => r.filter(s => s.length === n).length).join(' '));
```

Three languages, three lessons. The balanced strings come in Catalan numbers (1, 1, 2, 5, 14), the count of
chapter 8's recurrences. The grammar S → aSb | λ generates aⁿbⁿ, a context-free language that section 13.4
will prove is not regular. And the regular grammar S → 0S | 1A | λ, A → 0S | λ generates the binary strings
with no two consecutive 1s: after a 1 the grammar is in A, which forbids another 1. Their counts are the
Fibonacci numbers, as chapter 8 predicted. The two nonterminals S and A are really two states of memory,
"last symbol was not 1" and "last symbol was 1", which is a first look at the link between regular
grammars and finite machines.

**Realistic: a grammar that encodes precedence.** The obvious grammar for arithmetic, E → E plus E | E * E |
digit, is ambiguous. With n operands, the number of trees is the Catalan number of n minus 1:

```ts
const cat = (n: number): number => n <= 1 ? 1 :
  [...Array(n - 1).keys()].reduce((s, i) => s + cat(i + 1) * cat(n - 1 - i), 0);
console.log('trees for 1..6 operands', [1, 2, 3, 4, 5, 6].map(cat).join(' '));
function vals(t: (number | string)[]): number[] {
  if (t.length === 1) return [t[0] as number];
  const r: number[] = [];
  for (let i = 1; i < t.length; i += 2)
    for (const a of vals(t.slice(0, i))) for (const b of vals(t.slice(i + 1)))
      r.push(t[i] === '+' ? a + b : a * b);
  return r;
}
console.log('2+3*4', vals([2, '+', 3, '*', 4]).join(' '), ' 2*3+4*5', vals([2, '*', 3, '+', 4, '*', 5]).join(' '));
```

```text

```

So 2 plus 3 times 4 has two trees with two different values, and 2·3 plus 4·5 has five trees with four
different values; only one of them (26) is what everybody means. The fix is to build precedence into the
grammar with one nonterminal per level:

- E → T | E plus T | E minus T (an expression is a sum of terms);
- T → F | T * F (a term is a product of factors);
- F → digit | (E) (a factor is a number or a parenthesised expression).

This grammar is unambiguous, makes * bind tighter than plus, and makes minus left-associative because the
recursion is on the left. A **recursive-descent parser** turns each nonterminal into a function, with the
left recursion written as a loop:

```ts
function parse(src: string) {
  let p = 0;
  const E = (): any => { let t = T(); while (src[p] === '+' || src[p] === '-') { const op = src[p++]; t = [op, t, T()]; } return t; };
  const T = (): any => { let f = F(); while (src[p] === '*') { p++; f = ['*', f, F()]; } return f; };
  const F = (): any => {
    if (src[p] === '(') { p++; const e = E(); if (src[p++] !== ')') throw Error('expected )'); return e; }
    if (/[0-9]/.test(src[p])) return Number(src[p++]);
    throw Error(`unexpected ${src[p] ?? 'end'} at ${p}`);
  };
  const e = E(); if (p !== src.length) throw Error(`trailing input at ${p}`); return e;
}
const show = (t: any): string => Array.isArray(t) ? `(${t[0]} ${show(t[1])} ${show(t[2])})` : String(t);
const ev = (t: any): number => !Array.isArray(t) ? t : t[0] === '+' ? ev(t[1]) + ev(t[2]) : t[0] === '-' ? ev(t[1]) - ev(t[2]) : ev(t[1]) * ev(t[2]);
for (const s of ['2+3*4', '(2+3)*4', '8-3-2']) { const t = parse(s); console.log(s, show(t), ev(t)); }
for (const s of ['2+*3', '(2+3']) { try { parse(s); } catch (e: any) { console.log(s, 'error:', e.message); } }
```

```text
2+3*4 (+ 2 (* 3 4)) 14
(2+3)*4 (* (+ 2 3) 4) 20
8-3-2 (- (- 8 3) 2) 3
2+*3 error: unexpected * at 2
(2+3 error: expected )
```

The tree for 8 minus 3 minus 2 groups as (8 minus 3) minus 2, giving 3, not 8 minus (3 minus 2), which would
give 7. The grammar, not the evaluator, decided that.

### Common mistake

The common mistake is to write a grammar that generates the right strings but the wrong trees, or too
many strings. E → E plus E | E * E | digit generates exactly the right strings and is still wrong for a
compiler, because it does not fix the meaning. The opposite mistake is a grammar that is too generous, for
example S → (S) | SS | λ for balanced parentheses: it generates the right language, but the string `()()()`
has two trees (grouping the first two pairs or the last two), which harms nothing in a recogniser and
everything in a tool that attaches meaning to the tree. Always ask both questions: is the language right,
and is each string's tree unique and the intended one?

A second mistake is to write left-recursive rules directly as recursive-descent functions: E calling E
first, with no input consumed, recurses forever. Turn left recursion into a loop, as above.

### In real systems

Every compiler and interpreter starts with a grammar. Language specifications give their syntax in a BNF
variant, and parser generators read such a grammar and produce a parser automatically. Many production
compilers instead hand-write recursive-descent parsers like the one above, with precedence climbing for
operators, because it gives better error messages. JSON, SQL, HTTP headers, URLs and configuration file
formats are all specified by grammars, and data-validation libraries are, underneath, recognisers for
grammars. Ambiguity has caused real bugs: the "dangling else" problem, where `if a if b s1 else s2` could
attach the else to either if, is resolved in most languages by a rule outside the bare grammar.

## 13.2 Finite-state machines with output

### In one sentence

A finite-state machine with output reads an input string one symbol at a time, moves between a finite set
of states according to a transition function, and emits an output symbol at each step; its states are the
only memory it has, so it can remember only a bounded amount about the past.

### The idea

#### The definition

A **finite-state machine** M is a tuple (S, I, O, f, g, s₀):

- S is a finite set of **states**, with **initial state** s₀;
- I is the finite **input alphabet** and O the finite **output alphabet**;
- f is the **transition function**, giving for each state and input symbol the next state;
- g is the **output function**, giving for each state and input symbol an output symbol.

Given an input string x₁x₂…xₖ, the machine starts in s₀; at step i it is in state sᵢ₋₁, outputs
g(sᵢ₋₁, xᵢ) and moves to f(sᵢ₋₁, xᵢ). The result is an output string of the same length as the input.

A machine is drawn as a **state diagram**: a circle per state, an arrow from s to f(s, x) labelled "x, g(s,
x)" for each input x, and an arrow into the initial state. Or it is given as a **state table** with a row per
state and columns for f and g on each input.

#### Mealy and Moore machines

When the output depends on both the state and the current input, as above, the machine is a **Mealy
machine**. A **Moore machine** has an output that depends only on the state: each state is labelled with
an output, emitted on entering it (and the initial state's output is emitted before any input). The two
are equally powerful: any Mealy machine can be converted to a Moore machine by splitting each state by the
output it was entered with, at the cost of more states, and vice versa. Moore outputs are steady while the
machine sits in a state, which suits hardware outputs like lights; Mealy outputs react within the same step,
which needs fewer states.

#### Designing a machine: what must it remember?

The design question is always the same: what is the least information about the input so far that
determines all future behaviour? Each distinct answer becomes a state. For a machine that outputs 1
whenever the input so far ends with a given pattern, the state is "the longest suffix of the input that is
also a prefix of the pattern". For a machine that tracks a number read in binary modulo m, the state is the
remainder so far, and m states suffice.

Finite memory is the defining limit: a machine with k states cannot distinguish more than k different
pasts, which is why no finite-state machine can, for example, check that an arbitrarily long input has
as many 0s as 1s.

### Worked example

**Simple: a pattern detector.** Design a Mealy machine that outputs 1 exactly when the last four inputs
were 0110, with overlapping matches allowed, so 0110110 should produce two 1s.

The states record how much of 0110 is matched by the end of the input so far: s₀ (nothing), s₁ ("0"), s₂
("01"), s₃ ("011"). The transitions follow from asking, for each state and input, which is the longest
suffix of (matched prefix plus input) that is a prefix of 0110:

| state | input 0: next, output | input 1: next, output |
|---|---|---|
| s₀ (nothing) | s₁, 0 | s₀, 0 |
| s₁ (0) | s₁, 0 | s₂, 0 |
| s₂ (01) | s₁, 0 | s₃, 0 |
| s₃ (011) | s₁, 1 | s₀, 0 |

From s₃ on input 0 the machine has seen 0110, so it outputs 1, and the trailing 0 is itself the start of a new
match, so it moves to s₁, which is what makes overlapping matches work. From s₂ on 0, "010" ends in "0",
so it also goes to s₁, not back to s₀.

```ts
type Mealy = { start: string; f: Record<string, Record<string, string>>; g: Record<string, Record<string, string>> };
const det: Mealy = { start: 's0',
  f: { s0: { '0': 's1', '1': 's0' }, s1: { '0': 's1', '1': 's2' }, s2: { '0': 's1', '1': 's3' }, s3: { '0': 's1', '1': 's0' } },
  g: { s0: { '0': '0', '1': '0' }, s1: { '0': '0', '1': '0' }, s2: { '0': '0', '1': '0' }, s3: { '0': '1', '1': '0' } } };
function runMealy(m: Mealy, x: string) {
  let s = m.start, out = ''; const path = [s];
  for (const c of x) { out += m.g[s][c]; s = m.f[s][c]; path.push(s); }
  return { out, path: path.join(' ') };
}
console.log(runMealy(det, '0110110'));
console.log(runMealy(det, '1011001101'));
// compare with the definition on every input up to length 12
let bad = 0;
for (let n = 1; n <= 12; n++) for (let v = 0; v < 1 << n; v++) {
  const x = v.toString(2).padStart(n, '0'); const o = runMealy(det, x).out;
  for (let i = 0; i < n; i++) if ((o[i] === '1') !== (i >= 3 && x.slice(i - 3, i + 1) === '0110')) bad++;
}
console.log('mismatches', bad);
```

```text
{ out: '0001001', path: 's0 s1 s2 s3 s1 s2 s3 s1' }
{ out: '0000100010', path: 's0 s0 s1 s2 s3 s1 s1 s2 s3 s1 s2' }
mismatches 0
```

The exhaustive check covers all 8,190 inputs of length 1 to 12 and every position in them, so the four-state
table is right. This construction, the longest suffix that is a prefix, is the same failure-function idea
behind the Knuth–Morris–Pratt string-search algorithm, which finds a pattern of length m in a text in a
single pass with no backing up.

**Realistic: a running remainder.** A Mealy machine with five states can output, after each bit of a binary
number read from the most significant end, the remainder modulo 5 of the number read so far. Reading bit b
in state r moves to (2r plus b) mod 5, because appending a bit doubles the number and adds the bit.

```ts
function mod5(x: string) { let r = 0; const out: number[] = []; for (const c of x) { r = (2 * r + Number(c)) % 5; out.push(r); } return out.join(''); }
console.log('mod5 of prefixes of 1101011', mod5('1101011'), parseInt('1101011', 2), parseInt('1101011', 2) % 5);
```

```text
mod5 of prefixes of 1101011 1313132 107 2
```

The prefixes are 1, 3, 6, 13, 26, 53 and 107, with remainders 1, 3, 1, 3, 1, 3 and 2. The machine never stores
the number, which could have any length; five states are enough because the remainder is all that future
bits can depend on. This is the reason a checksum or hash can be computed over a stream of any length with
fixed memory.

**Realistic: a Moore machine for a traffic light.** A light at a side road stays green on the main road
until a car sensor reports a car (input c, otherwise n). The states G, Y and R output green, yellow and
red. G stays G on n and goes to Y on c; Y always goes to R (a fixed interval, modelled as one tick); R always
returns to G.

```ts
const out: Record<string, string> = { G: 'green', Y: 'yellow', R: 'red' };
```

### Common mistake

The most common design error is resetting to the initial state after a failed partial match. A detector
for 0110 that, in s₂ ("01"), returns to s₀ on input 0 misses the match in 010110, because the 0 that broke
the first attempt is the start of the real match. The longest-suffix rule avoids this. A second error is
mixing the Mealy and Moore conventions, for example labelling states with outputs and then also emitting
on transitions, or forgetting the Moore machine's extra initial output when comparing with expected
results.

### In real systems

Finite-state machines are everywhere in software. Network protocols are specified as state machines: a
TCP connection moves through states such as listening, established and closing, and each arriving segment
triggers a transition and possibly a response, which is a Mealy machine. User interfaces model a checkout
flow or a media player as states with allowed transitions, and libraries exist to make illegal transitions
impossible. Hardware controllers, from the traffic light to the control unit of a processor, are Moore or
Mealy machines built from flip-flops and the combinational logic of chapter 12. Lexers in compilers are
finite-state machines whose output is a stream of tokens. And workflow engines (an order is placed, paid,
shipped, delivered, or refunded) are state machines with persistence.

## 13.3 Finite-state machines with no output

### In one sentence

A finite-state automaton drops the output and instead marks some states as final, accepting exactly the
input strings that leave it in a final state; nondeterministic automata, which may have several moves or
none, recognise no more languages, because the subset construction turns any of them into a deterministic
one.

### The idea

#### Deterministic finite-state automata

A **finite-state automaton** M is (S, I, f, s₀, F): states S, input alphabet I, transition function f, initial
state s₀, and a set F of **final** (accepting) states. Extend f to strings: f(s, λ) is s, and f(s, xa) is f(f(s,
x), a). M **accepts** a string x if f(s₀, x) is in F, and the **language recognised** by M, L(M), is the set of
strings it accepts. Two automata are **equivalent** if they recognise the same language. In diagrams,
final states are drawn as double circles.

Because f is a function, every state has exactly one move on each symbol; such an automaton is
**deterministic** (a DFA). A missing transition in a diagram conventionally goes to a **dead state** that
loops on every symbol and is not final.

#### Designing automata

The design method is the one from 13.2: decide what must be remembered and make a state for each
possibility. Languages built from simpler ones often have simple automata:

- the **complement** of L(M), by making final states non-final and vice versa (in a DFA with every
  transition defined);
- the **intersection** or **union** of two languages, by the **product construction**: run both automata in
  parallel, with states that are pairs, and accept when both (or either) accept.

#### Nondeterministic automata

A **nondeterministic finite-state automaton** (NFA) has a transition function that gives a *set* of next
states, possibly empty. It accepts x if *some* sequence of choices ends in a final state. Think of it as
exploring all choices at once: after each symbol it is in a set of states. Nondeterminism makes design much
easier. For "the third symbol from the end is 1", an NFA guesses when it is three symbols from the end; a
DFA must remember the last three symbols.

#### The subset construction

**Theorem.** For every NFA there is an equivalent DFA.

Proof idea. Let the DFA's states be sets of NFA states. Its initial state is the set containing s₀. From a
set A on symbol a, move to the union of the NFA's moves from each state in A on a. A set is final if it
contains a final NFA state. By induction on the length of x, the DFA's state after x is exactly the set of
NFA states reachable on x, so the DFA accepts x precisely when some NFA run accepts it.

The price is size: an NFA with n states may need up to 2ⁿ DFA states, and the bound is reached.

#### Minimisation

Two states p and q of a DFA are **equivalent** if, for every string w, f(p, w) is final exactly when f(q, w)
is. This is an equivalence relation (chapter 9), and merging each class into one state gives the unique
smallest equivalent DFA. The classes are found by **partition refinement**: start with two blocks, final
and non-final; repeatedly split any block whose states move, on some symbol, into different blocks; stop
when nothing splits. The states that are split apart at round k are exactly those distinguished by a
string of length k.

### Common mistake

The classic mistake is complementing an NFA by swapping final and non-final states. For an NFA,
acceptance means some run accepts; after swapping, a string is accepted if some run ends in a formerly
non-final state, which many strings in the original language also satisfy. Determinise first, make the DFA
complete (with its dead state), and only then swap. A related mistake is forgetting the dead state in a
DFA you plan to complement: a string that falls off a missing transition was rejected, and it must become
accepted.

detection systems and antivirus scanners match thousands of patterns at once with combined automata.
Hardware verification and protocol model checkers explore products of automata to check that a system and
a property machine can never reach a bad pair of states. Input validation, such as checking a postal code
or a date format, is a DFA even when it is written as a regex.

## 13.4 Language recognition

### In one sentence

Kleene's theorem says that the languages recognised by finite-state automata are exactly the regular
sets, those described by regular expressions, and they are also exactly the languages of regular
grammars; and a pigeonhole argument shows that simple languages such as aⁿbⁿ are not among them.

### The idea

#### Regular expressions

**Regular expressions** over an alphabet I are defined recursively:

- ∅ is a regular expression (denoting the empty language), λ is one (denoting the set containing only the
  empty string), and each symbol a in I is one (denoting the set containing a);
- if A and B are regular expressions, so are AB (concatenation), A ∪ B (union, written A|B in most tools) and
  `A*` (Kleene star).

A **regular set** is a language denoted by a regular expression. For example, `(a|b)*abb` denotes the
strings over a and b ending in abb, and `a*b*` denotes any number of as followed by any number of bs.

#### Kleene's theorem

**Theorem (Kleene).** A set is regular if and only if it is recognised by a finite-state automaton.

From expression to automaton, by structural induction on the expression (this is **Thompson's
construction**, using λ-transitions, moves that consume no input):

- for ∅, λ and a single symbol, write down a two-state machine directly;
- for AB, join A's final state to B's start with a λ-move;
- for A|B, add a new start with λ-moves into both and λ-moves from both finals to a new final;
- for `A*`, add a new start and final, with λ-moves allowing A to be skipped or repeated.

λ-moves are removed afterwards, or handled by the subset construction, which then closes each set under
λ-moves. From automaton to expression, states are eliminated one at a time, with each removed state's
paths replaced by arrows labelled with regular expressions, until a single expression remains.

#### Regular grammars

**Theorem.** A set is generated by a regular grammar if and only if it is regular.

The translation is direct: a nonterminal is a state, A → aB is a transition from A to B on a, A → a is a
transition from A to a final state, and S → λ makes the start final. The no-11 grammar of 13.1 is the
two-state automaton "last symbol was not 1" and "last symbol was 1", both final.

#### Languages that are not regular

A DFA with k states can be in only k states after reading the k plus 1 strings λ, a, aa, …, aᵏ. By the
pigeonhole principle, two of them, aⁱ and aʲ with i less than j, lead to the same state. Then aⁱbⁱ and aʲbⁱ
also lead to the same state, so the machine accepts both or neither. But aⁱbⁱ is in L equal to the set of
aⁿbⁿ and aʲbⁱ is not. So no DFA with any finite number of states recognises L.

The general tool is the **pumping lemma**: if L is regular, there is an n such that every string in L of
length at least n splits as xyz with y nonempty and the length of xy at most n, such that xyᵏz is in L for
every k at least 0. Applying it to aⁿbⁿ: y lies inside the as, and pumping it changes the number of as but
not of bs.

A cleaner criterion, the **Myhill–Nerode theorem**, says L is regular exactly when the relation "x and y
have the same set of accepted continuations" has finitely many classes, and the number of classes is the
size of the minimal DFA. That is the minimisation of 13.3 seen from the language side.

#### Beyond regular

Context-free languages such as aⁿbⁿ and balanced parentheses are recognised by **pushdown automata**,
finite automata with a stack: push on a, pop on b. Even they have limits: aⁿbⁿcⁿ is not context-free.
Turing machines, next, recognise all of these.

### Worked example

**Simple: reading a regular expression.** Which strings does `(ab|b)*a` contain? It is any sequence of
the blocks ab and b, then a final a. So a, ba, aba, abba are in it (blocks: none; b; ab; ab, b). The string bab
is not: it ends in b. And abab is not, since it also ends in b. In words: strings ending in a in which every
a except the last is immediately followed by b.

**Realistic: Thompson's construction, tested exhaustively.** The compiler below parses a regular

argument works for any number of prefixes. By Myhill–Nerode, the language has infinitely many classes.

### Common mistake

The most frequent error is believing that "regex" in a programming language means regular. Modern regex
engines support backreferences, such as a pattern that matches a word followed by the same word again,
and that describes a non-regular language; matching with backreferences is NP-complete in general. Those
engines also use backtracking, and a pattern such as `(a|aa)*b` on a long string of as with no b can take
exponential time, the bug class known as catastrophic backtracking or regular-expression denial of service.
An automaton-based engine runs in time linear in the input for genuinely regular patterns.

The opposite mistake is trying to validate a nested format, such as balanced brackets or HTML, with a
regular expression. The pigeonhole proof says it cannot be done for unbounded nesting.

### In real systems

Regular expressions are the everyday interface to finite automata: in search tools, editors, log
filters, input validation and lexer generators. Some engines, designed to guarantee linear time, refuse
backreferences precisely so that they can compile to automata, and are used where untrusted users supply
patterns. The non-regularity result explains why compilers have two stages, a regular lexer for tokens and
a context-free parser for structure, and why configuration and data formats with nesting (JSON, XML) need
real parsers.

## 13.5 Turing machines

### In one sentence

A Turing machine is a finite-state control with a read–write head on an unbounded tape; this simple
device can compute everything any computer can (the Church–Turing thesis), and yet some precisely stated
problems, the halting problem first among them, cannot be solved by any Turing machine at all.

### The idea

#### The definition

A **Turing machine** T is (S, I, f, s₀): a finite set of states S, a tape alphabet I that includes a blank
symbol B, a start state s₀, and a **partial** transition function f that maps a pair (state, symbol) to a
triple (new state, symbol to write, direction L or R). The tape is infinite in both directions and is blank
except for finitely many cells. At each step the machine reads the symbol under the head, and if f is
defined there, it writes, moves one cell, and changes state. If f is undefined, the machine **halts**.

Conventions vary in small ways (some versions allow the head to stay put, some use one-way-infinite tapes,
some have explicit accept and reject states), and all are equivalent in power. Here a move S means "stay",
and h, acc and rej are halting states.

#### Recognising and deciding languages

T **recognises** a language L if it halts in a final state exactly on the inputs in L; on other inputs it may
halt elsewhere or run forever. T **decides** L if it also halts on every other input, rejecting. A language
recognised by some Turing machine is **recursively enumerable**; one decided by some Turing machine is
**decidable** (or recursive). These are the type 0 languages of the Chomsky hierarchy.

#### Computing functions

A Turing machine **computes** a function if, started with an encoding of the input on the tape, it halts
with an encoding of the output. A function computed by some Turing machine is **computable**. Numbers can
be encoded in unary (n as n plus 1 ones, in some books) or in binary; the class of computable functions does
not depend on the choice.

#### The Church–Turing thesis

The **Church–Turing thesis** says that any problem that can be solved by an effective procedure, an
algorithm in the intuitive sense, can be solved by a Turing machine. It is not a theorem, because
"effective procedure" is not a formal notion; it is supported by the fact that every proposed model of
computation (the lambda calculus, recursive functions, register machines, every real programming language)
has turned out to compute exactly the same functions.

#### The halting problem

**Theorem (Turing).** There is no Turing machine that, given the encoding of any Turing machine M and an
input x, always halts and correctly says whether M halts on x.

Proof by contradiction. Suppose H(M, x) is such a machine. Build D that, on input M, runs H(M, M) and then
does the opposite: if H says M halts on its own encoding, D loops forever; otherwise D halts. Now ask
whether D halts on its own encoding. If it does, H(D, D) said "halts", so D loops; if it does not, H(D, D)
said "loops", so D halts. Both are impossible, so H cannot exist.

This is the diagonal argument of chapter 2's uncountability proof applied to programs. Many other
problems reduce to it: whether a program ever prints a given line, whether two programs compute the same
function, whether a program is free of a given class of runtime error. **Rice's theorem** generalises: every
non-trivial property of the function a program computes is undecidable.

#### Complexity: P and NP

Among decidable problems, **P** is the class decidable in polynomial time by a deterministic Turing
machine, and **NP** the class decidable in polynomial time by a nondeterministic one, equivalently, those
whose yes answers can be checked in polynomial time given a certificate. Whether P equals NP is the most
famous open problem in computer science. **NP-complete** problems, such as satisfiability of Boolean
formulas (chapter 12) and the Hamilton circuit problem (chapter 10), are the hardest in NP: a polynomial
algorithm for one would give one for all.

### Worked example

**Simple: binary increment.** The machine starts on the leftmost bit. In state r it moves right over the
bits until it reaches a blank, then steps left into state c. In c, a 1 becomes 0 with the carry continuing
left; a 0 or a blank becomes 1 and the machine halts.

```ts
type Rule = [string, 'L' | 'R' | 'S', string]; // write, move, next state
type TM = { start: string; halt: Set<string>; d: Record<string, Record<string, Rule>> };
function run(m: TM, input: string, max = 10000, log = false) {
  const tape = new Map<number, string>(); [...input].forEach((c, i) => tape.set(i, c));
  let q = m.start, h = 0, steps = 0; const lines: string[] = [];
  const snap = () => { const ks = [...tape.keys(), h]; const lo = Math.min(...ks), hi = Math.max(...ks); let s = '';
    for (let i = lo; i <= hi; i++) s += (i === h ? '[' : '') + (tape.get(i) ?? 'B') + (i === h ? ']' : ''); return `${q.padEnd(3)} ${s}`; };
  while (!m.halt.has(q) && steps < max) {
    if (log) lines.push(snap());
    const r = m.d[q]?.[tape.get(h) ?? 'B']; if (!r) return { result: 'stuck', steps, lines, tape };
    tape.set(h, r[0]); h += r[1] === 'L' ? -1 : r[1] === 'R' ? 1 : 0; q = r[2]; steps++;
  }
  if (log) lines.push(snap());
  return { result: q, steps, lines, tape };
}
const read = (t: Map<number, string>) => [...t.keys()].sort((a, b) => a - b).map(k => t.get(k)).join('').replace(/^B+|B+$/g, '');
const inc: TM = { start: 'r', halt: new Set(['h']), d: {
  r: { '0': ['0', 'R', 'r'], '1': ['1', 'R', 'r'], B: ['B', 'L', 'c'] },
  c: { '1': ['0', 'L', 'c'], '0': ['1', 'S', 'h'], B: ['1', 'S', 'h'] } } };
for (const x of ['1011', '111', '0', '1001']) { const r = run(inc, x); console.log('inc', x, '->', read(r.tape), 'steps', r.steps); }
console.log(run(inc, '1011', 100, true).lines.join('\n'));
```

```text
inc 1011 -> 1100 steps 8
inc 111 -> 1000 steps 8
inc 0 -> 1 steps 3
inc 1001 -> 1010 steps 7
r   [1]011
r   1[0]11
r   10[1]1
r   101[1]
r   1011[B]
c   101[1]B
c   10[1]0B
c   1[0]00B
h   1[1]00B
```

Eleven plus one is twelve (1011 to 1100), and 111 plus 1 is 1000: the carry runs off the left end into a
blank cell, which the c state turns into a 1. Each configuration line shows the state, then the tape with
the head's cell in brackets. A configuration (state, tape contents, head position) is the complete
description of a Turing machine at an instant, which is what makes the model precise enough to reason
about.

**Realistic: deciding aⁿbⁿ.** The language that no finite automaton recognises is decided by a Turing
machine that uses its tape as memory. Repeatedly: cross off the leftmost a (write X), run right to the first
b and cross it off (write Y), run back left to the X, and step right. When no a remains, check that only Ys
are left.

**Realistic: how fast can a tiny machine grow?** The **busy beaver** question asks, for n-state machines on
a blank tape over symbols 0 and 1, how many 1s a halting machine can leave, and how many steps a halting
machine can run. Those numbers grow faster than any computable function, so they cannot be computed in
general, but small cases are known. Running known champion machines:

```ts
const bb = (spec: string) => {
  const d: any = {};

console.log('3 states', bb('A0=1RB A1=1RH B0=0RC B1=1RB C0=1LC C1=1LA'));
console.log('4 states', bb('A0=1RB A1=1LB B0=1LA B1=0LC C0=1RH C1=1LD D0=1RD D1=0RA'));
```


The 2-state machine leaves 4 ones in 6 steps, the most possible on both counts. The 3-state machine shown
leaves 6 ones, the maximum for 3 states (a different 3-state machine runs longer, 21 steps). The 4-state
machine runs 107 steps and leaves 13 ones, both maxima for 4 states. For 5 states the maximum running time,
47,176,870 steps, was confirmed by a collaborative computer-checked proof in 2024; for 6 states the
champions run for more steps than can be written in ordinary notation. Proving that no other small
machine runs longer requires settling, machine by machine, whether it halts, which is the halting problem
in miniature.

### Common mistake

The common mistake is to treat "undecidable" as "hard" or "unsolved". The halting problem is not
waiting for a clever algorithm; the proof shows that none can exist. Undecidability is also about *all*
inputs: for a particular program, halting is often easy to settle, and tools that analyse programs work
by answering "yes", "no" or "don't know", or by restricting the programs they accept. The reverse mistake is
to think the Church–Turing thesis is a theorem with a proof; it is a well-supported claim about what
"algorithm" means.

### In real systems

The halting problem is why no compiler can detect every infinite loop, why static analysers either
miss bugs or raise false alarms, and why antivirus software cannot decide in general whether a program is
malicious: all are non-trivial properties of program behaviour, covered by Rice's theorem. Type systems
stay decidable by rejecting some correct programs. Practical tools set timeouts or bounds instead: a test
runner kills a test after a time limit, a smart-contract platform charges for each step so that every run
ends, and a bounded model checker explores executions up to a fixed depth. On the complexity side,
SAT solvers, which tackle an NP-complete problem, are routine engineering tools in verification, scheduling
and package dependency resolution, because worst cases are rare in practice.

## From beginner to strategy

<Levels label="Chapter 13, Modeling Computation">
<Level name="Beginner" depth={3}>

The smallest working version of this chapter: a grammar generates strings by rewriting; a finite-state
machine reads input with a fixed number of states; a finite automaton accepts or rejects; a Turing machine
adds an unbounded tape and can compute anything computable.

Example: a light switch is a two-state machine. Input "press" moves on to off and off to on; output is the
state. Anything you can draw as circles and arrows with a fixed number of circles is a finite-state
machine.

The beginner mistake is to think more states means more power in kind. Any fixed number of states, however
large, is still finite memory; the jump in power comes from adding a stack or a tape.

</Level>
<Level name="Intermediate" depth={3}>

At this level you design: a DFA for a described language by deciding what to remember, an NFA when
guessing makes it simpler, a regular expression for a pattern, a grammar with precedence for an
expression language, and you convert between them with the subset construction and Thompson's
construction.

Example: "binary strings with an even number of 0s and ending in 1" is the product of a two-state parity
machine and a two-state "last symbol" machine, four states in all, and its regular expression is longer
than its automaton.

</Level>
<Level name="Advanced" depth={3}>

The advanced view is about limits and costs. Non-regularity by pigeonhole or Myhill–Nerode, the
exponential gap between NFA and DFA size, minimisation to a unique smallest DFA, the hierarchy of
language classes, undecidability by diagonalisation and reduction, and the difference between
computability and efficiency.

Example: the k-th-from-the-end language has an NFA of k plus 1 states and a minimal DFA of 2ᵏ states. For k
equal to 20 that is 21 against 1,048,576, which is exactly why lazy DFA construction exists.

</Level>
<Level name="Edge cases" depth={3}>

Edge cases are the empty string and the empty language. λ is accepted exactly when the start state is
final; the empty language has an automaton with no final states; ∅ and λ are different regular
expressions (`∅*` is λ). A grammar with S → λ needs care in the Chomsky definitions, which is why type 1
grammars allow it only when S never appears on a right-hand side.

Example: a validator for an optional field must accept the empty input, and an automaton designer who
forgets to make the start state final rejects it.

</Level>
<Level name="Corner cases" depth={3}>

Corner cases come from conventions. Mealy and Moore outputs differ by one symbol in length. Some books'
Turing machines halt on undefined moves, others need explicit halting states; some tapes are infinite in
one direction. Real regex dialects add anchors, lookaround and backreferences that change what is regular,
and differ on whether `.` matches a newline.

Example: the pattern `a|ab` matched as a search against "ab" reports "a" in a backtracking engine that takes
the first alternative, and "ab" in an engine that follows the leftmost-longest rule. Same expression, same
language, different match.

</Level>
<Level name="Production level" depth={3}>

In production, lexers are generated DFAs, parsers are hand-written recursive descent or generated from
grammars, regex engines are chosen for guarantees (linear-time engines for untrusted patterns), protocols
and workflows are explicit state machines with persisted state, and program analysers are designed around
undecidability with timeouts, bounds and sound approximations.

Example: a service that lets customers enter search patterns runs them on an automaton-based engine, so
a pattern like `(a|aa)*b` cannot pin a CPU, at the cost of not supporting backreferences.

</Level>
<Level name="Mindset" depth={3}>

The mindset is to ask "how much memory does this really need?" Bounded memory means a state machine and
linear-time streaming. A stack means nesting and a parser. Unbounded random access means general
computation, and with it the possibility of not halting.

Example: deciding whether a log stream has more errors than warnings over all time needs a counter, which
is unbounded, so it is not a finite-state problem; deciding whether the last 100 events contain an error is,
since a window of 100 is bounded.

</Level>
<Level name="System design" depth={3}>

In system design, making state machines explicit (an enumeration of states, a table of allowed
transitions, and a single place where transitions happen) turns a tangle of flags into something you can
draw, test exhaustively and reason about. Rejecting illegal transitions at the boundary prevents whole
classes of bugs.

Example: an order with flags paid, shipped and cancelled has 8 flag combinations, several meaningless
(shipped and not paid); an order state machine with states placed, paid, shipped, delivered and cancelled
has 5 states and a short list of legal moves, and the impossible combinations simply cannot be
represented.

</Level>
<Level name="Strategy" depth={3}>

The strategic view is to pick the weakest model that solves the problem. Weaker models are easier to
analyse, faster and safer: a regular language can be checked in linear time with constant memory, and
properties of finite automata (emptiness, equivalence) are decidable, while the same questions about
general programs are not.

Example: a configuration language that is deliberately not Turing-complete, with no unbounded loops or
recursion, guarantees that evaluating any configuration terminates, which a general-purpose scripting
language cannot promise.

</Level>
</Levels>

## Questions people ask

**do I need this chapter to write parsers?**

You can write one without it, but grammars, precedence levels and left recursion are exactly what makes a
parser correct, and the chapter explains why lexing and parsing are separate stages.

**are real computers finite-state machines, since memory is finite?**

Technically yes, with an astronomical number of states. In practice the Turing machine is the better
model, because programs are written for arbitrary input sizes and memory can always be added.

**why are regular expressions in my language more powerful than the ones here?**

Features such as backreferences go beyond regular languages. They are convenient, but they can make
matching slow in the worst case and they lose the guarantees of automata.

**if halting is undecidable, how do tools find infinite loops?**

They find some of them. Practical analysers detect common patterns, prove termination for restricted
classes of programs, or give up and say "unknown"; no tool is right on every program.

**what comes after this chapter?**

A course or book on automata and computability covers pushdown automata, the pumping lemma for
context-free languages, reductions and complexity classes in depth.

## Key takeaways

- A language is a set of strings; grammars generate languages by rewriting rules.
- Derivation trees give strings their structure; an ambiguous grammar gives some string two trees, and
  precedence is fixed by layering nonterminals.
- The Chomsky hierarchy, types 0 to 3, matches Turing machines, linear bounded automata, pushdown
  automata and finite automata.
- Mealy machines output on transitions and Moore machines on states; both have finite memory.
- A DFA has exactly one move per state and symbol; an NFA may have several or none, and the subset
  construction converts it, at a worst-case cost of 2ⁿ states.
- Every DFA has a unique minimal equivalent, found by partition refinement.
- Kleene's theorem: regular expressions, finite automata and regular grammars describe the same
  languages.
- The pigeonhole principle shows aⁿbⁿ, balanced parentheses and palindromes are not regular.
- Turing machines compute everything that is computable (the Church–Turing thesis).
- The halting problem is undecidable, and so is every non-trivial property of program behaviour.

## Glossary

- **Alphabet (vocabulary)**: a finite nonempty set of symbols.
- **String, empty string λ**: a finite sequence of symbols; the sequence of length 0.
- **Language**: a set of strings over an alphabet.
- **Concatenation, Kleene star**: joining strings or languages; all concatenations of zero or more strings.
- **Phrase-structure grammar**: vocabulary, terminals, start symbol and productions.
- **Terminal, nonterminal**: symbols of finished strings; placeholders to be rewritten.
- **Production**: a rewriting rule w₀ → w₁.
- **Derivation, leftmost derivation**: a sequence of rewritings; one always rewriting the leftmost nonterminal.
- **Derivation (parse) tree**: the tree recording which rule expanded each nonterminal.
- **Ambiguous grammar**: one in which some string has two derivation trees.
- **Context-free, context-sensitive, regular grammar**: types 2, 1 and 3.
- **Backus–Naur form**: a notation for context-free grammars.
- **Finite-state machine with output**: states, input and output alphabets, transition and output functions.
- **Mealy machine, Moore machine**: output on transitions; output on states.
- **Finite-state automaton (DFA)**: a machine with final states, accepting or rejecting strings.
- **Final (accepting) state, dead state**: states that accept; a non-final trap state.
- **Language recognised**: the set of strings an automaton accepts.
- **Nondeterministic automaton (NFA)**: one whose moves are sets of states.
- **Subset construction**: converting an NFA to a DFA whose states are sets.
- **Product construction**: running two automata in parallel on pairs of states.
- **Equivalent states, minimisation**: states with the same future; merging them.
- **Regular expression, regular set**: expressions built from ∅, λ, symbols, concatenation, union and star; the languages they denote.
- **Kleene's theorem**: regular sets are exactly the languages of finite automata.
- **Thompson's construction**: building a λ-NFA from a regular expression.
- **Pumping lemma, Myhill–Nerode theorem**: tools for proving languages non-regular.
- **Pushdown automaton**: a finite automaton with a stack.
- **Turing machine**: finite control, unbounded tape, read–write head.
- **Configuration**: state, tape contents and head position at one instant.
- **Recognise, decide**: halt and accept on the language; also always halt.
- **Computable function**: one computed by some Turing machine.
- **Church–Turing thesis**: effective procedures are exactly Turing machines.
- **Halting problem**: deciding whether a machine halts on an input; undecidable.
- **Rice's theorem**: non-trivial properties of computed functions are undecidable.
- **P, NP, NP-complete**: polynomial time; polynomial-time verifiable; the hardest problems in NP.
- **Busy beaver**: the maximum output or running time of halting n-state machines.

**Self-check.**

**1. Which type is the grammar S → 0S | 1A | λ, A → 0S | λ?**

<details>
<summary>Answer</summary>

Type 3, regular.

</details>

**2. What does a DFA state represent in the subset construction?**

<details>
<summary>Answer</summary>

The set of NFA states reachable on the input read so far.

</details>

**3. How many states has the minimal DFA for strings ending in ab?**

<details>
<summary>Answer</summary>

Three.

</details>

**4. Why must a Turing machine be able to write on its tape to recognise aⁿbⁿ?**

<details>
<summary>Answer</summary>

A read-only head moving both ways still has only finite memory, and such two-way automata recognise only
regular languages; writing turns the tape into unbounded memory.

</details>

**5. What is the key step in the halting problem proof?**

<details>
<summary>Answer</summary>

Building a machine that does the opposite of what the supposed decider predicts about it running on its
own encoding.

</details>

**6. Is every regular language context-free?**

<details>
<summary>Answer</summary>

Yes: a regular grammar is a special case of a context-free grammar.

</details>
