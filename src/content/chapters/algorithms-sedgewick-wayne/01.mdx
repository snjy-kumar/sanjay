## 1.1 Programming Model

### In one sentence

Every algorithm in the book can be written with a tiny part of any
language: primitive values, arrays, functions, recursion, and simple input
and output.

### The idea

A programming model is the set of language features you allow yourself.
The book deliberately picks a small one. The point is not that Java (or
TypeScript) lacks power; the point is that algorithms should not depend on
clever language tricks. If an idea needs only loops and arrays, it will
port to C, Go, Rust or Python in an afternoon.

The pieces are few. **Primitive types** are the values the machine handles
directly: integers, floating-point numbers, booleans and characters.
**Expressions** combine them with operators. **Statements** do things:
declarations, assignments, conditionals (`if`), loops (`while`, `for`),
calls and returns. **Arrays** store a fixed-length sequence of values of one
type, reached by an index in constant time. **Static methods**, which in
TypeScript are just plain functions, package a computation behind a name,
take arguments and return a value.

Two details of the model cause most bugs, so they deserve their own words.
The first is that numbers are finite. A Java `int` is 32 bits and silently
wraps around past about 2.1 billion; a JavaScript `number` is a 64-bit
float, exact for integers only up to 2^53, and wrong after that without
any warning. The second is that arrays are reached through **references**:
a variable holds the address of the array, not the array, so assigning one
array variable to another makes two names for the same data.

**Recursion** is a function that calls itself on a smaller input. Every
correct recursive function has three properties: a **base case** that
returns without recursing, recursive calls on **smaller** subproblems that
make progress towards the base case, and subproblems that **do not
overlap** wastefully. Break the first and the program never stops. Break
the second and it never reaches the base case. Break the third and it can
take exponential time, as the naive Fibonacci function famously does.

Finally, the model includes **input and output**: reading numbers or
strings from standard input, writing to standard output, and drawing. The
book ships small libraries for this. In Node I use `process.stdin`, files
and `console.log`; the idea is the same. Programs read a stream, process it,
and write a stream, which is what lets them be chained in a shell pipeline.

#### Binary search as the model's first real algorithm

The chapter's first real algorithm is **binary search**: given a sorted
array and a key, find the key's position or report that it is absent. It
keeps two indices, `lo` and `hi`, with the promise that if the key is
anywhere, it is between them. Each step looks at the middle element and
throws away the half that cannot contain the key. The interval halves every
time, so on a million elements it needs at most about 20 looks.

### Worked example

The simple example: Euclid's algorithm for the greatest common divisor, the
oldest algorithm still in daily use. The rule is that the gcd of `p` and `q`
equals the gcd of `q` and the remainder of `p` divided by `q`, and the gcd of
any number and zero is that number. Here it is with a printed call trace.

```ts
function gcd(p: number, q: number, depth = 0): number {
  console.log(`${'  '.repeat(depth)}gcd(${p}, ${q})`);
  if (q === 0) return p;                 // base case
  return gcd(q, p % q, depth + 1);       // smaller subproblem
}
console.log('=', gcd(1071, 462));
```

```text
gcd(1071, 462)
  gcd(462, 147)
    gcd(147, 21)
      gcd(21, 0)
= 21
```

All three properties of recursion are visible. `q === 0` is the base case.
The second argument shrinks every call (the remainder is always smaller
than the divisor). And each call makes exactly one recursive call, so there
is no overlap at all.

The realistic example: an **allowlist filter**, the client the book uses to
motivate binary search. A payments service has a sorted list of approved
account numbers and must check each incoming transaction against it. A
linear scan per transaction is fine for ten accounts and hopeless for ten
million. Binary search answers each lookup in about 24 steps for ten
million accounts.

```ts
export function rank(key: number, a: number[]): number {
  let lo = 0, hi = a.length - 1;
  while (lo <= hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (key < a[mid]) hi = mid - 1;
    else if (key > a[mid]) lo = mid + 1;
    else return mid;
  }
  return -1;
}
const allow = [10, 11, 12, 16, 18, 23, 29, 33, 48, 54, 57, 68, 77, 84, 98];
console.log(rank(23, allow), rank(50, allow), rank(10, allow), rank(98, allow));
```

```text
5 -1 0 14
```

The output covers the four interesting cases: a key in the middle (index
5), a key that is absent (−1), the first element and the last element.

Why is it correct? Use the same tool CLRS uses, a **loop invariant**: a
statement true at the start of every pass. The invariant is "if the key is
in the array, it is in `a[lo..hi]`". It holds at the start, because the
interval is the whole array. Each pass keeps it true, because the half we
discard is sorted and lies entirely on the wrong side of the key. When the
loop ends with `lo` greater than `hi`, the interval is empty, so by the
invariant the key is nowhere: returning −1 is right.

Why does it take about lg n looks? Each pass at least halves the interval
size. Starting at n, after k passes at most n / 2^k elements remain. The
loop must stop once that drops below one, which happens when k passes lg n.
For n = 15, lg 15 is about 3.9, so at most 4 looks, which is exactly what
the trace shows.

### Common mistake

The classic bug is computing the middle as `(lo + hi) / 2`. In Java with
32-bit ints, `lo + hi` overflows once the array passes about a billion
elements, and `mid` becomes negative. That bug sat in a widely used Java
library for years before anyone noticed. The fix is `lo + (hi - lo) / 2`,
which never exceeds `hi`.

In TypeScript the overflow is not the danger, because numbers are floats;
the danger is forgetting `Math.floor`. Then `mid` becomes 3.5, `a[3.5]` is
`undefined`, every comparison with `undefined` is false, and the loop
returns the wrong answer or never ends. If you write `(lo + hi) >>> 1` you
get both the floor and an unsigned shift, but only while indices fit in 31
bits.

The second classic bug is `while (lo < hi)` instead of `lo <= hi`. It skips
the last one-element interval, so a key sitting exactly where `lo` and `hi`
meet is reported absent. Searching for 98 in the trace above would fail.

### In real systems

Binary search is everywhere data is sorted: a database's B-tree page does a
binary search over its keys, `git bisect` binary-searches history for the
commit that broke a test, and log-structured storage engines binary-search
sorted string tables on disk. Language libraries expose it directly:
Java's `Arrays.binarySearch`, Python's `bisect`, C++'s `lower_bound`.

The programming-model lesson shows up in code reviews. Algorithm code that
uses only arrays, loops and functions is easy to port, to test and to
reason about. Code that leans on a framework's magic is not. When I write
the hot loop of a service, I write it in the small model.

## 1.2 Data Abstraction

### In one sentence

An abstract data type is a set of values plus the operations on them,
described by an API, so code can use it without knowing how it is built.

### The idea

A **data type** is a set of values and a set of operations on those values.
Numbers with `+` and `*` are a data type the language gives you. An
**abstract data type** (ADT) is one you define, whose representation is
hidden from its users. The users, called **clients**, see only the **API**:
the list of operations, each with a name, arguments, a return type and a
plain-language description of what it does.

Hiding the representation is called **encapsulation**. It buys three
things. You can change the implementation, say from an array to a linked
list, without touching any client. You can test the ADT on its own. And you
can reason about a big program one piece at a time, because each piece
promises only what its API says.

The API is a **contract** with two sides. Preconditions are what the client
must guarantee (do not `pop` an empty stack). Postconditions are what the
implementation guarantees in return (`pop` returns the most recently pushed
item still present). Invariants are what is always true of the object's
state between calls (the counter's count is never negative).

Objects have three properties worth separating. **State** is the value the
object holds right now. **Identity** is which object it is: in memory, its
address. **Behaviour** is what its operations do. Two objects can have equal
state and different identities, and confusing these is the root of most
equality bugs.

#### Immutability

An **immutable** data type is one whose values cannot change after
creation. Strings in Java and JavaScript are immutable; arrays are not. The
book makes many of its value types immutable on purpose: a `Date` or a
`Point` that never changes can be shared freely, used as a key in a hash
table, and passed between threads without locks.

The trap is that `final` in Java, or `readonly` in TypeScript, only freezes
the reference, not what it points to. A `readonly` field holding an array
still lets anyone change the array's contents. True immutability needs a
defensive copy on the way in and no mutators on the way out.

#### Equality

The book spends real time on what it means for two objects to be equal.
Reference equality (`===` in TypeScript, `==` on objects in Java) asks
whether two names point to the same object. Value equality asks whether they
represent the same value. A good `equals` is reflexive (x equals x),
symmetric, transitive, consistent over time, and false when compared with
null.

### Worked example

The simple example is the book's first ADT, a **counter**: a named tally
you can increment. The API is three operations.

```ts
export class Counter {
  readonly #name: string;
  #count = 0;
  constructor(name: string) { this.#name = name; }
  increment() { this.#count++; }
  tally() { return this.#count; }
  toString() { return `${this.#count} ${this.#name}`; }
}
const heads = new Counter('heads'), tails = new Counter('tails');
for (let i = 0; i < 1000; i++) (Math.random() < 0.5 ? heads : tails).increment();
console.log(String(heads), '|', String(tails));
```

```text
507 heads | 493 tails
```

(Your numbers will differ: it is a coin flip.) The `#` fields are truly
private in JavaScript, so no client can set the count to −5 and break the
invariant.

The realistic example is a **date-range** value type for a booking system,
immutable and with value equality, because two bookings for "3 to 7 March"
must compare equal even if they were created separately.

```ts
export class DateRange {
  readonly start: string; readonly end: string;     // ISO dates, inclusive
  constructor(start: string, end: string) {
    if (end < start) throw new RangeError(`end ${end} before start ${start}`);
    this.start = start; this.end = end;
    Object.freeze(this);
  }
  overlaps(o: DateRange) { return this.start <= o.end && o.start <= this.end; }
  equals(o: unknown) {
    return o instanceof DateRange && o.start === this.start && o.end === this.end;
  }
}
const a = new DateRange('2026-03-03', '2026-03-07');
const b = new DateRange('2026-03-03', '2026-03-07');
console.log(a === b, a.equals(b), a.overlaps(new DateRange('2026-03-07', '2026-03-09')));
```

```text
false true true
```

`a === b` is false because they are two objects (two identities). `equals`
is true because they hold the same value. The constructor enforces the
invariant once, so no method ever has to check it again.

Walk the counter through it. Values: a name and a non-negative count. API:
construct with a name, `increment`, `tally`, `toString`. Contract: the count
starts at zero and only grows by one per `increment`. Client: the coin-flip

a number. If one day the counter must be shared across processes, the
representation can become a database row and the coin-flip client does not
change.

### Common mistake

The common mistake is the leaky abstraction: an API that returns its
internal array. A `Bag` with a `getItems()` that returns `this.items` lets
any client push into it directly, bypassing the size counter. The next call
to `size()` is wrong, and the bug appears far from its cause.

```ts
class LeakyBag { items: number[] = []; n = 0;
  add(x: number) { this.items.push(x); this.n++; }
  getItems() { return this.items; } }
const bag = new LeakyBag(); bag.add(1); bag.getItems().push(2);
console.log(bag.n, bag.getItems().length);   // 1 2  -- the invariant is broken
```

The fix is to return a copy, a read-only view, or, best, an iterator, which
is what the book does: clients can look at every item but cannot change the
collection.

### In real systems

Every service boundary is an ADT. A payments API exposes `charge`,
`refund` and `getStatus`; the client never sees whether the ledger is
Postgres or a mainframe. Versioned REST and gRPC APIs are this section's
discipline at network scale: the contract is the API description, and the
representation can change between releases as long as the contract holds.

Immutable value types are the backbone of modern frontends and
concurrent backends. React's state model relies on replacing objects rather
than mutating them, so a change is detected by a cheap reference
comparison. Event-sourced systems store immutable events and rebuild state
from them.

## 1.3 Bags, Queues, and Stacks

The booksite calls this section "Stacks and Queues"; the printed book's
contents name all three collections.

### In one sentence

A bag, a queue and a stack all hold a collection of items; they differ only
in which item comes out next, and each can be built on a resizing array or
on a linked list with every operation in constant time.

### The idea

Many programs need to collect items and process them later. The three
classic collections share almost the same API: add an item, check whether
the collection is empty, ask its size, and iterate over its items. They
differ in removal.

- A **bag** has no removal at all. You add items and later iterate over
  them in no particular order. It is for "collect, then look at all of
  them", like gathering the numbers to compute an average.
- A **queue** removes in **first-in, first-out** (FIFO) order: `dequeue`
  returns the item that has waited longest. It models a line at a counter,
  a print queue, or jobs waiting for a worker.
- A **stack** removes in **last-in, first-out** (LIFO) order: `pop` returns
  the item added most recently. It models a pile of plates, the browser's
  back button, and the call stack of a running program.

Two more ideas make these collections useful in a real language.
**Generics** let one implementation hold any item type: `Stack<string>`,
`Stack<Order>`. **Iteration** lets a client write `for (const x of stack)`
without knowing the representation: the collection provides an iterator,
an object that hands out items one at a time.

#### Representation 1: the resizing array

An array has a fixed length, but a stack must grow. The trick is to keep an
array that is usually bigger than needed and a count `n` of how many slots
are in use. `push` writes at index `n` and increments it; `pop` decrements
`n` and reads that slot. When the array is full, allocate one **twice** as
big and copy everything across. When it falls to **one quarter** full,
shrink it to half.

Why double, not add ten slots? Adding a constant makes the total copying
for n pushes grow like n², because every few pushes copies the whole array.
Doubling makes the total copying for n pushes less than 2n, because the
copies cost 1 + 2 + 4 + ... up to n, which sums to under 2n. Spread across n
pushes, that is a constant per push. This is called **amortised** constant
time: one push can be expensive, but any sequence of n operations costs at
most a constant times n.

Why shrink at one quarter, not one half? Picture an array of capacity 8
holding exactly 4 items. If you shrink at half full, a `pop` takes you to 3
and shrinks to 4; a `push` takes you to 4, which is full, and grows to 8;
another `pop` shrinks again. Alternating push and pop at that boundary
copies the array every time, which is called **thrashing**. Shrinking at a
quarter leaves the half-full array with room on both sides, so the next
resize is at least a quarter of the capacity's worth of operations away.

#### Representation 2: the linked list

A **linked list** is a recursive structure: it is either empty (null) or a
**node** holding an item and a reference to a linked list. A stack keeps a
reference to the first node. `push` makes a new node whose `next` is the old
first node; `pop` reads the first node's item and moves `first` to its
`next`. Both are a few pointer assignments, constant time in the worst
case, with no copying ever.

A queue needs to add at one end and remove at the other, so it keeps two
references: `first` (where `dequeue` removes) and `last` (where `enqueue`
adds). The fiddly part is the empty case: when the queue becomes empty,
both must be null, and when an item is added to an empty queue, both must
point to it.

### Worked example

The simple example is the book's test input, a stream of words where `-`
means "remove one". Running it through a stack and through a queue shows
LIFO and FIFO on the same input.

```ts
export class ResizingArrayStack<T> implements Iterable<T> {
  private a: (T | undefined)[] = new Array(1);
  private n = 0;
  isEmpty() { return this.n === 0; }
  size() { return this.n; }
  private resize(cap: number) {
    const b = new Array<T | undefined>(cap);
    for (let i = 0; i < this.n; i++) b[i] = this.a[i];
    this.a = b;
  }
  push(item: T) {
    if (this.n === this.a.length) this.resize(2 * this.a.length);
    this.a[this.n++] = item;
  }
  pop(): T {
    if (this.n === 0) throw new Error('Stack underflow');
    const item = this.a[--this.n] as T;
    this.a[this.n] = undefined;             // avoid loitering
    if (this.n > 0 && this.n === this.a.length / 4) this.resize(this.a.length / 2);
    return item;
  }
  *[Symbol.iterator]() { for (let i = this.n - 1; i >= 0; i--) yield this.a[i] as T; }
}
```

The linked queue, with the empty-case handling called out:

```ts
type Node<T> = { item: T; next: Node<T> | null };
export class LinkedQueue<T> implements Iterable<T> {
  private first: Node<T> | null = null;
  private last: Node<T> | null = null;
  private n = 0;
  enqueue(item: T) {
    const old = this.last;
    this.last = { item, next: null };
    if (old) old.next = this.last; else this.first = this.last;  // was empty
    this.n++;
  }
  dequeue(): T {
    if (!this.first) throw new Error('Queue underflow');
    const { item } = this.first;
    this.first = this.first.next;
    if (!this.first) this.last = null;      // became empty
    this.n--;
    return item;
  }
  *[Symbol.iterator]() { for (let x = this.first; x; x = x.next) yield x.item; }
}
```

Feeding both the input `to be or not to - be - - that - - - is`, printing
the removed words and then what is left:

```ts
const input = 'to be or not to - be - - that - - - is'.split(' ');
const s = new ResizingArrayStack<string>(), q = new LinkedQueue<string>();
const fromS: string[] = [], fromQ: string[] = [];
for (const tok of input) {
  if (tok === '-') { fromS.push(s.pop()); fromQ.push(q.dequeue()); }
  else { s.push(tok); q.enqueue(tok); }
}
console.log(fromS.join(' '), '| left:', [...s].join(' '));
console.log(fromQ.join(' '), '| left:', [...q].join(' '));
```

The stack gives back the most recent word each time, so the order looks

original sentence.

The realistic example is the one the book uses to show stacks are more
than a toy: **Dijkstra's two-stack algorithm** for evaluating arithmetic
expressions. It is the idea inside every calculator and, in a more general
form, every compiler's expression parser. Keep one stack of operators and
one of values. Skip left parentheses, push operators and numbers, and on a
right parenthesis pop an operator and its operands, compute, and push the
result.

```ts
export function evaluate(expr: string): number {
  const ops: string[] = [], vals: number[] = [];
  for (const tok of expr.split(/\s+/).filter(Boolean)) {
    if (tok === '(') continue;
    else if ('+-*/'.includes(tok) || tok === 'sqrt') ops.push(tok);
    else if (tok === ')') {
      const op = ops.pop()!;
      let v = vals.pop()!;
      if (op === '+') v = vals.pop()! + v;
      else if (op === '-') v = vals.pop()! - v;
      else if (op === '*') v = vals.pop()! * v;
      else if (op === '/') v = vals.pop()! / v;
      else if (op === 'sqrt') v = Math.sqrt(v);
      vals.push(v);
    } else vals.push(Number(tok));
  }
  return vals.pop()!;
}
console.log(evaluate('( 1 + ( ( 2 + 3 ) * ( 4 * 5 ) ) )'));
console.log(evaluate('( ( 1 + sqrt ( 5.0 ) ) / 2.0 )'));
```


### Common mistake

The first mistake is **loitering**: popping an item but leaving its
reference in the array slot. The garbage collector sees a live reference
and cannot free the object. In a long-running server holding a stack of
request objects, each with a megabyte buffer, this leaks memory that no
profiler blames on the stack. The fix is the line `this.a[this.n] =
undefined` after every pop.

The second is the queue's empty case. Forget `if (!this.first) this.last =
null` in `dequeue`, and after the queue empties, `last` still points to the
removed node. The next `enqueue` links the new node onto that dead node,
`first` stays null, and the item vanishes. A test that empties the queue
and refills it catches this in one line.

The third is modifying a collection while iterating over it. The book's
iterators do not support it; Java's library iterators throw a
`ConcurrentModificationException`. A JavaScript generator will silently
produce confusing results. Pick one rule, fail fast or iterate over a
snapshot, and document it.

### In real systems

Stacks: the call stack of every program, undo and redo histories, the
browser back button, depth-first traversal of a file tree, and the parser
in every compiler and JSON library. The two-stack algorithm grows up into
the shunting-yard algorithm and operator-precedence parsing.

Queues: task queues like Sidekiq, Celery and BullMQ, message brokers like
Kafka and RabbitMQ (a durable, distributed queue), the event loop's task
queue in Node and the browser, and breadth-first search in chapter 4. In
production every queue needs a **bound**: an unbounded queue between a fast
producer and a slow consumer is a memory leak with a delay.

Resizing arrays: JavaScript arrays, Java's `ArrayList`, Python's `list` and
Go's slices all grow geometrically. Go grows by 2× while small and by a
smaller factor when large; Python by about 1.125×; the exact factor trades
memory waste against copy frequency, and any factor above 1 keeps the
amortised cost constant.

## 1.4 Analysis of Algorithms

### In one sentence

Treat running time as a scientific question: observe it, guess a model,
predict a bigger run, check the prediction, and back the model with a count
of the operations the code performs.

### The idea

Every programmer eventually asks: how long will my program take on a
bigger input, and why is it so slow? The book answers with the **scientific
method**, applied to code. **Observe** a feature of the running program.
**Hypothesise** a model that explains it. **Predict** an event using the
model. **Verify** the prediction by running the experiment. **Validate** by
repeating until the model and the measurements agree.

#### Observations and the doubling test

The cheapest observation is a stopwatch. Run the program on an input of
size n, then 2n, then 4n, and look at the **ratio** of each running time to
the previous one. If the running time is roughly `a · n^b` for some
constants, then doubling n multiplies the time by `2^b`, so the ratio
settles at `2^b` and the exponent is `lg` of the ratio. A ratio near 2
means linear, near 4 means quadratic, near 8 means cubic.

This is the **doubling test**, and it is powerful because it cancels the
constant `a`. The constant depends on the machine, the language and the
compiler; the exponent depends on the algorithm. A faster laptop shrinks `a`
and leaves `b` alone.

#### Mathematical models

Observation tells you *what*; a model tells you *why*. Knuth's insight,
which the book adopts, is that total running time is the sum over all
statements of (cost of the statement) times (how often it runs). The cost
depends on the machine; the frequency depends on the algorithm and the
input. Usually one statement, the **inner loop**, dominates, so you count
how often it runs.

**Tilde notation** keeps the leading term and its constant and drops the
rest. `n³/6 − n²/2 + n/3` is written `~n³/6`. Unlike big-O, tilde keeps the
constant, so it predicts actual counts, not just a growth class. That is
why the book prefers it: `~n²/2` and `~n²/4` are both "quadratic", but one
is twice as fast.

The **order of growth** is the leading term without its constant. The
book's short list covers nearly every algorithm you will meet: constant,
logarithmic (`lg n`), linear (`n`), linearithmic (`n lg n`), quadratic
(`n²`), cubic (`n³`) and exponential (`2^n`).

#### Memory

The book also models memory, for Java on a typical 64-bit machine: an
object has a 16-byte header, a reference is 8 bytes, an `int` 4, a `double`
8, and objects are padded to a multiple of 8 bytes. An array adds a header
of 24 bytes. So a linked-list node holding a reference to an item costs
about 40 bytes before the item itself, while a resizing array costs 8 to 32
bytes per item depending on how full it is. JavaScript engines differ in
details, but the lesson carries: per-object overhead dominates for small
items.

### Worked example

The simple example is counting the **3-sum** problem's work. Given n
integers, how many triples sum to exactly zero? The brute-force answer is a
triple loop.

```ts
export function countBrute(a: number[]): number {
  const n = a.length; let c = 0;
  for (let i = 0; i < n; i++)
    for (let j = i + 1; j < n; j++)
      for (let k = j + 1; k < n; k++)
        if (a[i] + a[j] + a[k] === 0) c++;
  return c;
}
```

The `if` runs once per triple with `i`, `j`, `k` strictly increasing, which
is "n choose 3" = `n(n−1)(n−2)/6`, so `~n³/6`. The model predicts a doubling
ratio of 8. Here is my doubling run (I added the header row), with random integers between minus
and plus one million, on the box I used.

```text
     n  count    time   ratio
   250      1   0.010s  -
   500     14   0.018s  1.8
  1000     66   0.138s  7.7
  2000    490   1.134s  8.2
  4000   4015   9.444s  8.3
```

The first ratios are noisy (small times, JIT warm-up), then the ratio
settles near 8, which is `2^3`. Prediction: n = 8000 will take about 8 ×
9.4 ≈ 75 seconds. That is the whole method in one table.

The realistic example: make it faster by changing the algorithm, not the
code. Sort the array, then for each pair `(a[i], a[j])` binary-search for
`−(a[i] + a[j])`. That is `~n²/2` pairs times `lg n` per search, so the
model predicts `n² lg n` and a ratio just above 4.

```ts
export function countFast(input: number[]): number {
  const a = [...input].sort((x, y) => x - y); let c = 0;
  for (let i = 0; i < a.length; i++)
    for (let j = i + 1; j < a.length; j++)
      if (rank(-a[i] - a[j], a) > j) c++;    // count each triple once
  return c;
}
```

At n = 4000 the fast version takes a quarter of a second against nine and

### Step by step

The derivation of the brute-force count, line by line in plain words.

1. The outer loop picks `i` from 0 to n − 1.
2. For each `i`, the middle loop picks `j` from `i + 1` to n − 1.
3. For each such pair, the inner loop picks `k` from `j + 1` to n − 1.
4. So the `if` runs once for every choice of three distinct positions in
   increasing order, and every set of three positions has exactly one
   increasing order.
5. The number of ways to choose 3 items from n is `n(n−1)(n−2)/6`.
6. Expanding: `n³/6 − n²/2 + n/3`.
7. For n = 1000 that is 166,166,000; the leading term alone gives
   166,666,667, within 0.3 percent. So `~n³/6`.

Why the ratio is `2^b`: if `T(n) = a · n^b`, then `T(2n) / T(n) = a · (2n)^b /
(a · n^b) = 2^b`. The `a` cancels, and so does `n`. Taking `lg` of both
sides, `b = lg(ratio)`. For the fast version, `lg 4.2` is about 2.07, a hair
above 2: the `lg n` factor shows up as a ratio slightly above 4.

### Common mistake

The fast 3-sum gave 4006 where the brute force gave 4015. The fast
version silently assumes the integers are **distinct**: binary search
returns one index for a value that appears several times, so triples using
the other copies are missed. My random generator produced a few
duplicates, and the count drifted. The fix is either to deduplicate the
input (if the problem allows it) or to count the run of equal values around
the found index. The general lesson: when you change the algorithm to get
a better order of growth, re-check the assumptions the new algorithm makes,
and keep the slow version as a test oracle.

The second mistake is trusting the first ratios. The first rows of both
tables are dominated by startup and just-in-time compilation. Discard runs
under a tenth of a second, repeat each size a few times, and only trust the
ratio once two or three in a row agree.

The third is reading big-O as a prediction. "O(n²)" is an upper bound; an
O(n²) algorithm can be linear on your input. Tilde notation with a
measured constant is what predicts.

### In real systems

The doubling test is the cheapest performance tool there is, and it scales
up to load testing: run a service at 1×, 2× and 4× traffic and look at how
latency and CPU grow. Linear growth is capacity planning; superlinear growth
is a bug waiting for Black Friday.

Order-of-growth surprises are behind many real outages: an accidental
quadratic loop (a `list.includes` inside a loop over the same list), a
regular expression that backtracks exponentially, a query that joins
without an index. Each was fast in testing on small data. Benchmarks in CI
that run at two sizes and alert on the ratio catch them early.

Memory models matter at scale too. A service holding ten million small
objects pays the per-object header ten million times; switching to a
packed array of numbers (a typed array in JavaScript, a struct-of-arrays
layout elsewhere) can cut memory several times over.

## 1.5 Case Study: Union-Find

### In one sentence

To answer "are p and q connected?" while connections keep arriving, keep
each group as a tree and name it by its root; link small trees under big
ones and flatten paths as you walk them, and every operation becomes
nearly constant time.

### The idea

The problem is **dynamic connectivity**. There are n **sites**, numbered 0
to n − 1. A stream of pairs arrives; each pair `p q` says "p is connected to
q". Connection is an **equivalence relation**: every site is connected to
itself (reflexive), if p is connected to q then q is connected to p
(symmetric), and connections chain (transitive). So the sites fall into
**components**, groups in which everyone is connected to everyone. We want
two operations: `union(p, q)` to merge the components of p and q, and
`find(p)` to name p's component, so that `connected(p, q)` is `find(p) ===
find(q)`.

The book solves this four times, and the sequence is the chapter's best
lesson in algorithm design: each version fixes the weak spot the previous
analysis revealed.

#### Quick-find

Keep an array `id` where `id[p]` is the name of p's component. Then `find`
is one array read: constant time. But `union(p, q)` must rename every site
in p's component, and the only way to find them is to scan the whole array.
So every union costs about n array accesses, and building one component
from n sites takes about n² accesses. With a million sites, that is a
trillion steps.

#### Quick-union

Flip the trade-off. Let `parent[p]` point to another site in the same
component, so each component is a **tree** of parent links, and its root
(the site whose parent is itself) is its name. `find(p)` follows parent
links up to the root. `union(p, q)` finds both roots and makes one point to
the other: one link, no scan. The danger is tall trees. If unions keep
adding to the bottom of a chain, the tree becomes a path of length n, and
`find` on its deepest site takes n steps.

#### Weighted quick-union

The fix is one comparison. Keep the **size** of every tree, and always link
the root of the **smaller** tree under the root of the larger. A site's
depth only increases when its tree is linked under a tree at least as big,
which at least doubles the size of the tree it belongs to. A tree can only
double lg n times before it holds all n sites, so no site is ever deeper
than lg n. `find` and `union` both become logarithmic.

#### Path compression

The last idea is almost free. While `find` walks from p to the root, it has
visited every site on the path. Point all of them directly at the root on
the way out. Later finds on any of them take one step. Combined with
weighting, the amortised cost per operation is bounded by a function that
grows so slowly (the inverse of Ackermann's function) that it is at most 4
for any n you could ever store. In practice: constant.

### Worked example

The simple example: ten sites and eleven pairs. I ran all three
implementations side by side and printed the array after every pair (`id`
for quick-find, `parent` for the others), one digit per site, site 0 first.
Here is the weighted version; quick-union is the same without the `size`
comparison, linking p's root under q's.

```ts
export class WeightedUF {
  parent: number[]; size: number[]; count: number;
  compress: boolean;
  constructor(n: number, compress = false) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.size = new Array(n).fill(1);
    this.count = n; this.compress = compress;
  }
  find(p: number) {
    let root = p;
    while (root !== this.parent[root]) root = this.parent[root];
    if (this.compress)
      while (p !== root) { const next = this.parent[p]; this.parent[p] = root; p = next; }
    return root;
  }
  union(p: number, q: number) {
    const rp = this.find(p), rq = this.find(q);
    if (rp === rq) return;                      // already connected
    if (this.size[rp] < this.size[rq]) { this.parent[rp] = rq; this.size[rq] += this.size[rp]; }
    else { this.parent[rq] = rp; this.size[rp] += this.size[rq]; }
    this.count--;
  }
}
```

(My benchmark copy also counts array accesses; I have left the counters out
here so the logic is easy to read.)

The realistic example is **account merging**. A sign-up service sees
records that share an email or a phone number and must group them into
people. Give every record a site number; for every shared email or phone,
union the two records. At the end, `find` on each record gives a person id.

```ts
  { id: 4, email: 'd@x.io', phone: '222' }, { id: 5, email: 'e@x.io', phone: '555' },

  const prev = firstSeen.get(key);

}
```

```text
80000  qf skipped  wqu 0.08s  wpc 0.02s
```

Quick-find's ratio is about 4 (quadratic); I skipped it at 80,000 because
the model already predicts about 11 seconds. The weighted versions are too
fast to time meaningfully at these sizes, which is the point.

#### The lg n height bound, line by line

1. Claim: in weighted quick-union, every site's depth is at most lg n.
2. A site starts at depth 0, in a tree of size 1.
3. Its depth changes only when its tree's root is linked under another
   root, and then it grows by exactly 1.
4. That happens only if its tree is the smaller (or equal) one, so the new
   tree is at least twice the size of its old tree.
5. So every time the depth grows by one, the size of the site's tree at
   least doubles.
6. A tree has at most n sites, so the size can double at most lg n times.
7. Therefore the depth is at most lg n, and find costs at most lg n steps.

### Common mistake

The most common bug is linking the sites instead of the roots:
`parent[p] = q` instead of `parent[find(p)] = find(q)`. If p is not a root,
this detaches p and its subtree from p's old tree, while p's old root keeps
the rest. One component splits in two, and `connected` starts giving wrong
answers for sites that were joined earlier. Always link roots.

The second is updating `size` on the wrong root, or forgetting it, which
quietly turns weighted quick-union back into plain quick-union with tall
trees. A test that checks the height stays under lg n after a million
random unions catches it.

The third is the quick-find loop that compares against `id[p]` while
changing it: if you write `if (id[i] === id[p]) id[i] = id[q]`, then once
the loop passes `i = p`, `id[p]` has changed and the rest of p's component
is left behind. Save `pid = id[p]` before the loop.

### In real systems

Union–find is how Kruskal's minimum-spanning-tree algorithm (chapter 4)
avoids cycles. It labels connected regions in images (connected-component
labelling), merges duplicate customer records as above, groups equivalent
type variables in type inference (unification), and detects when a
percolation system, the book's physics example, has a path from top to
bottom.

An entity-resolution job might run a hundred million unions. Quick-find
would never finish; weighted union with path compression finishes about as
fast as it can read the input. The one thing union–find cannot do is
**delete** a connection: splitting a component needs a different, much
harder data structure, so systems that must "unlink" accounts rebuild the
structure from the remaining links.

### Check yourself

<details>
<summary>1. Why does weighted quick-union need the size array, not just the parent array?</summary>

To decide which root goes under which, it must know which tree is smaller.
Without sizes it cannot tell, and it falls back to an arbitrary choice that
allows tall trees.

</details>

<details>
<summary>2. After union(p, q) on sites already connected, what must change?</summary>

Nothing. The roots are the same, the function must return early, and in
particular the component count must not drop.

</details>

<details>
<summary>3. Path compression alone, without weighting: still a good idea?</summary>

Yes, it helps a lot and its amortised bound is logarithmic. The
near-constant bound needs both together, so libraries use both.

</details>

## From beginner to strategy

<Levels label="Chapter 1, Fundamentals">
<Level name="Beginner" depth={3}>

At the smallest scale this chapter is about three collections and one
connectivity trick, and about being exact. A stack gives back the newest
item, a queue the oldest, and a bag does not give items back one at a time
at all; you just look at everything. Union–find answers "same group?" by
walking up to a tree's root.

The smallest thing that works is a stack used to reverse a word. Push the
letters of `stack` one by one, then pop until empty: you get `k c a t s`.
Five pushes and five pops, each one step. If you can predict that output
before running it, you understand LIFO.

```ts
const st = new ResizingArrayStack<string>();
for (const ch of 'stack') st.push(ch);
let out = ''; while (!st.isEmpty()) out += st.pop();
console.log(out);   // kcats
```

The beginner's mistake is to treat these as trivial and skip the
implementations. Writing a linked queue from memory, with the empty case
right, is a real test. Most people get it wrong the first time, and that
is the reason to do it now rather than in an interview.

</Level>
<Level name="Intermediate" depth={3}>

In a real program the pieces combine. A breadth-first web crawler is a
queue of URLs to visit plus a set of URLs already seen. A command-line
calculator is two stacks. A "group these photos by who appears in them"
feature is union–find over face matches. The skill is recognising which
access pattern the problem has: newest first, oldest first, or no order.

Here is a small, realistic combination: a bracket checker for a code
editor, which uses a stack to match openers and closers and reports the
position of the first error.

```ts
function checkBrackets(src: string): string {
  const pairs: Record<string, string> = { ')': '(', ']': '[', '}': '{' };
  const st: { ch: string; at: number }[] = [];
  for (let i = 0; i < src.length; i++) {
    const ch = src[i];
    if ('([{'.includes(ch)) st.push({ ch, at: i });
    else if (ch in pairs) {
      const top = st.pop();
      if (!top || top.ch !== pairs[ch]) return `mismatch at ${i}`;
    }
  }
  return st.length ? `unclosed at ${st[st.length - 1].at}` : 'ok';
}
console.log(checkBrackets('f(a[1], {b: 2})'), checkBrackets('f(a[1)]'), checkBrackets('(('));
```

```text
ok mismatch at 5 unclosed at 1
```

The intermediate mistake is reaching for an array and `shift()` as a queue.
`shift` moves every remaining element, so a queue of a million jobs drained
with `shift` is quadratic. Use a linked queue, a ring buffer, or two
indices into an array.

</Level>
<Level name="Advanced" depth={3}>

Underneath, the chapter rests on two precise claims. The first is
amortised cost. For the resizing stack, define a potential: think of each
push as paying three units, one for the write and two saved for a future
copy. When the array doubles from capacity c to 2c, the c/2 pushes since
the last doubling saved c units, exactly enough to pay for copying c items.
So the bank never goes negative, and any sequence of m operations costs at
most about 3m array writes. This is the accounting method, and it is a
worst-case guarantee over sequences, not an average over inputs.

The second is the union–find bound. Weighted quick-union gives lg n
height by the doubling argument above. With path compression added,
Tarjan proved that m operations on n sites take time proportional to m
times the inverse Ackermann function of n, and later work showed no
pointer-based structure can do better. The function is at most 4 for any
realistic n, which is why people call union–find "constant in practice"
while being careful never to call it constant in theory.

The cost model itself is the third advanced idea. Tilde notation counts a
chosen operation (array accesses, compares) and keeps the constant. That
makes it falsifiable: `~n³/6` predicts 166 million inner-loop runs at n =
1000, and you can count them with a counter. Big-O cannot be checked that
way. The advanced mistake is mixing the two, quoting an O-bound as if it
were a prediction.

</Level>
<Level name="Edge cases" depth={3}>

Single boundaries, each with what happens:

- **Pop or dequeue on empty.** My implementations throw "Stack underflow" or
  "Queue underflow". The alternative, returning `undefined`, pushes the
  check onto every caller. Decide once, document it, test it.
- **One element.** A queue with one item has `first === last`. Dequeue must
  set both to null. A stack of capacity 1 holding one item must grow on the
  next push.
- **Shrinking at size zero.** The guard `this.n > 0` stops the stack
  shrinking to capacity 0, from which doubling would stay at 0 forever.
- **Binary search on an empty array.** `hi` starts at −1, the loop never
  runs, the answer is −1. Correct, with no special case needed.
- **`union(p, p)`.** The roots are equal; return early; count unchanged.
- **A site index of n or −1.** The book validates and throws. Without the
  check, a JavaScript array silently returns `undefined` and `find` loops
  forever comparing `undefined` with itself's parent.

The mistake here is assuming the happy path covers these. Each one is a
one-line test, and each one has broken a real implementation.

</Level>
<Level name="Corner cases" depth={3}>

Two things at once:

- **Push after the stack shrank to its minimum, at a resize boundary.**
  Capacity 4, n = 1, pop to 0 (no shrink, guarded), push, push, push, push,
  push: the fifth push doubles from 4 to 8. Test exactly this sequence.
- **Dequeue to empty, then enqueue.** The `last = null` line and the
  `first = last` branch must both run correctly in sequence. This is the
  bug from section 1.3, and it needs both operations to show itself.
- **Iterating while popping.** A generator over the array stack reads
  `this.n` lazily; pop during the loop and the iterator skips or repeats
  items. Either snapshot before iterating or fail fast with a modification
  counter.
- **Duplicates plus the fast 3-sum.** Binary search plus repeated values
  gave a count of 4006 instead of 4015 in my run. Two separate features,
  sorting-based search and duplicate keys, combine into a wrong answer.
- **Weighted union with equal sizes plus path compression.** The tie-break
  is arbitrary, and compression changes tree shapes but never sizes at the
  root. Size is only maintained at roots, so reading `size[p]` for a
  non-root p gives a stale number. Only ever read sizes at roots.

</Level>
<Level name="Production level" depth={3}>

Real code uses library collections, so production concerns are about
bounds, memory and observability. A queue between a web tier and a worker
pool needs a maximum length and a policy when it is full: block the
producer, drop the newest, drop the oldest, or reject with a 429. Each
choice is a product decision. Expose the queue length as a metric; a
steadily growing queue is the earliest warning of an overloaded consumer.

Memory is the second concern. A JavaScript array of a million small
objects costs far more than a million numbers in a `Float64Array`. When a
stack or queue holds millions of items, consider a ring buffer over a typed
array, which never allocates after start-up and never triggers garbage
collection pauses.

Performance claims need the chapter's method. Before saying "this endpoint
is linear", run it at 1k, 2k and 4k records in a benchmark and keep the
ratios in the pull request. The production mistake is a benchmark at one
size, which cannot reveal an order of growth. The fix is two or three sizes
and a ratio.

</Level>
<Level name="Mindset" depth={3}>

The habit this chapter teaches is to separate *what* from *how*, and then
to measure *how much*. An API says what; the implementation says how; the
doubling test says how much. Keeping the three apart lets you change any
one without breaking the others.

The second habit is improving an algorithm by analysing its worst case.
Union–find did not get fast by tuning loops; each step looked at where the
previous version spent its time (scanning, then tall trees, then repeated
walks) and removed exactly that. The same habit applies to a slow web page:
profile, find the dominating cost, change the design that causes it.

The mistake is optimising before measuring. The fix is the order the
chapter uses: make it work with the simplest correct design, measure,
then improve the part the measurement points at.

</Level>
<Level name="System design" depth={3}>

Every distributed system is built from this chapter's parts at a larger
scale. A message broker is a durable queue; a request's call path through
microservices is a stack of contexts, visible in a distributed trace; a
cluster membership service answers a connectivity question. The choice
between a queue and a stack becomes a choice between fairness and freshness:
a support-ticket system processes FIFO for fairness, while a "show the
latest notifications" feed is LIFO for freshness.

Concrete example: a job system for sending emails. Producers enqueue jobs in
a bounded queue (Redis lists or Kafka). Workers dequeue. Failed jobs go to a
retry queue with a delay and then a dead-letter queue. The ADT boundary
means the producers call `enqueue(job)` and never know whether the queue is
Redis today and SQS tomorrow.

The system-design mistake is building a queue without back-pressure, so a
slow downstream service causes unbounded memory growth upstream. The fix is
bounded queues and an explicit full-queue policy at every boundary.

</Level>
<Level name="Strategy" depth={3}>

I learn this chapter by building, not reading. For each structure, I read
the section once, close the book, write the TypeScript from a blank file,
and test it against a built-in (`Array` for stacks, a reference model for
queues, a brute-force connectivity check by BFS for union–find). Then I
open the booksite's Java and note what they did differently.

For analysis, I run the doubling test on everything I write in this
chapter and keep a small table per structure in the README. The numbers
matter less than the habit of having them.

Done when, without notes, I can write a resizing-array stack and a linked
queue with every edge case right in under fifteen minutes, explain the
quarter-shrink rule, derive `~n³/6` for 3-sum, run a doubling test and read
its ratio, and implement weighted quick-union with path compression and
prove the lg n height bound in seven lines.

</Level>
</Levels>

## Questions people ask

**Why does a book about algorithms spend a section on a programming model?**
Because the algorithms should not depend on language features. If you can
express everything with arrays, loops and functions, the ideas travel to
any language, and the costs are easy to count.

**Do I need to learn Java?** No. Read the Java as pseudocode and write your
own version in a language you know. Rewriting is the learning.

**Is a linked list ever faster than an array in practice?** Rarely for
iteration, because arrays are cache-friendly. Linked lists win when you
need a worst-case constant-time operation, or when you splice in the middle
holding a reference to the node.

**Why not just use JavaScript's array as a queue?** `push` and `pop` are
fine for a stack, but `shift` for dequeue is linear in most engines, so
draining a long queue is quadratic.

**Is tilde notation the same as big-Theta?** No. Big-Theta keeps only the
order of growth and drops the constant; tilde keeps the constant. `~n²/2`
and `~3n²` are both Θ(n²).

**How many sizes do I need for a doubling test?** At least three that each
run longer than a fraction of a second, so you can see the ratio settle.

**Why is union–find in a fundamentals chapter?** Because it is the cleanest
complete example of the method: define an API, implement simply, analyse,
find the bottleneck, improve, and verify by experiment.

**Does path compression make find constant?** Amortised over a sequence,
very nearly; a single find can still walk a long path once, but then that
path is flat.

## Key takeaways

- A small programming model (arrays, loops, functions, recursion) is enough for every algorithm in the book.
- An abstract data type is an API plus a contract; clients depend on the API, never on the representation.
- Stacks, queues and bags differ only in removal order: newest, oldest, or none.
- Resizing arrays double when full and halve at one quarter full, giving amortised constant time without thrashing.
- Linked lists give worst-case constant time per operation at the cost of memory and cache locality.
- The doubling test turns a stopwatch into an exponent: the ratio is 2 to the power b.
- Tilde notation keeps the constant, so it predicts counts; big-O only bounds them.
- Changing the algorithm beats tuning the code: 3-sum went from `n³` to `n² lg n`.
- Weighted quick-union bounds tree height by lg n; path compression makes operations nearly constant.

## Glossary

- **Abstract data type (ADT):** a data type whose representation is hidden behind an API.
- **Amortised cost:** the total cost of a sequence of operations divided by its length, guaranteed for every sequence.
- **API:** the list of operations a type offers, with their arguments, results and contract.
- **Bag:** a collection you add to and iterate over, with no removal.
- **Component:** a maximal set of sites that are all connected to each other.
- **Doubling test:** timing a program at n, 2n, 4n and reading the exponent from the ratio.
- **Encapsulation:** keeping the representation private so only the API can change state.
- **Immutable:** a value that cannot change after it is created.
- **Linked list:** a node holding an item and a reference to the rest of the list, or null.
- **Loitering:** holding a reference to an object that is no longer needed, so it cannot be freed.
- **Order of growth:** the leading term of a cost function, without its constant.
- **Path compression:** pointing every site on a find's path directly at the root.
- **Queue:** a first-in, first-out collection.
- **Stack:** a last-in, first-out collection.
- **Tilde notation:** `~f(n)` means the ratio to `f(n)` goes to 1 as n grows.
- **Union–find:** a data type for dynamic connectivity with `union` and `find`.
- **Weighted quick-union:** quick-union that links the smaller tree under the larger.

<details>
<summary>1. What three properties must a correct recursive function have?</summary>

A base case, recursive calls on smaller problems that make progress towards
it, and no wasteful overlap between subproblems.

</details>

<details>
<summary>2. Why is the resizing stack's push only amortised constant?</summary>

Most pushes write one slot, but a push into a full array copies all n
items. Over any sequence the copies average out to a constant per push,
because each doubling is paid for by the pushes since the last one.

</details>

<details>
<summary>3. What does a doubling ratio of 2.1 suggest?</summary>

Roughly linear or linearithmic growth; `n lg n` gives ratios slightly above
2 that slowly approach 2 as n grows.

</details>

<details>
<summary>4. In quick-union, what is the cost of find?</summary>

The depth of the site in its tree, which can be as large as n − 1 when the
tree is a chain.

</details>

<details>
<summary>5. What is loitering and how do you prevent it in a stack?</summary>

Keeping a reference to a popped item in the array, so the garbage collector
cannot free it. Set the slot to null or undefined after popping.

</details>

<details>
<summary>6. Why is tilde notation more useful than big-O for prediction?</summary>

It keeps the leading constant, so it predicts actual counts and running
time ratios between algorithms of the same order.

</details>
