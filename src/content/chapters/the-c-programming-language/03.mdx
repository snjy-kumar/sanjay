Chapter 3 covers the statements that decide what runs next: blocks,
`if`-`else`, `else if` chains, `switch`, the three loops, `break`,
`continue` and `goto`. It matters because every algorithm is a shape of
control flow, and C's versions have a few sharp edges, like fall-through
and the dangling else, that other languages inherited.

## Before you start

After this chapter you will be able to:

- tell an expression from a statement, and use blocks to group statements and scope variables;
- write `if`-`else` correctly, including nested ones, and avoid the dangling-else trap;
- write a multi-way `else if` chain, and a binary search with a provable invariant;
- use `switch` with deliberate fall-through, and know when it is the wrong tool;
- choose between `while`, `for` and `do`-`while`, and use the comma operator in a loop header;
- use `break`, `continue` and the one good use of `goto`: leaving nested loops or cleaning up on error.

What you should already know: <a href={withBase('/books/the-c-programming-language/02-types-operators-and-expressions/')}>chapter 2</a>,
especially relational and logical operators and the fact that any non-zero
value is true.

Reading time: about 70 minutes, plus an evening for the programs. The book's
chapter is short; most of this page is the traps and the proofs.

## 3.1 Statements and Blocks

### In one sentence

An expression followed by a semicolon is a statement, and braces group
statements into a block that counts as one.

### The idea

An **expression** computes a value: `x = 0`, `i++`, `printf(...)`. Putting a
semicolon after it makes an **expression statement**, which evaluates it
for its side effects and throws the value away. In C the semicolon ends a
statement; it does not separate statements as in Pascal.

Braces `{` and `}` group declarations and statements into a **compound
statement**, or **block**. A block is syntactically one statement, so it can
go anywhere one statement is allowed: the body of an `if`, a loop, a
function. There is no semicolon after the closing brace.

A block also creates a **scope**. A variable declared inside it exists only
until the closing brace, and can hide a variable of the same name outside.
A lone semicolon is the **null statement**, which does nothing and is used
as an empty loop body.

### Worked example

```c
/* blocks.c */
#include <stdio.h>

int main(void)
{
    int x = 1;
    x + 1;                   /* legal, useless: value discarded */
    {
        int x = 10;          /* a new x, hides the outer one */
        printf("inner %d\n", x);
    }
    printf("outer %d\n", x);
    ;                        /* null statement */
    return 0;
}
```

```text
inner 10
outer 1
```

gcc warns "statement with no effect" on `x + 1;`, which is exactly the help
you want: an expression statement with no side effect is almost always a
typo for `x += 1`.

A realistic use of a block is limiting a temporary's lifetime, so a name
cannot be misused later in a long function:

```c
/* scoped_tmp.c */
#include <stdio.h>

int main(void)
{
    int a = 3, b = 7;
    {
        int tmp = a;         /* tmp exists only for the swap */
        a = b;
        b = tmp;
    }
    printf("%d %d\n", a, b);
    return 0;
}
```

```text
7 3
```

### Step by step

The compiler reads `if (x) a(); b();` as an `if` whose body is the single
statement `a();`, followed by an unconditional `b();`. Indentation is
ignored. Wrapping `a(); b();` in braces makes both the body.

### Common mistake

A semicolon right after a condition: `if (x > 0); y = 1;`. The body of the
`if` is the null statement, and `y = 1` always runs. gcc's `-Wempty-body`
(in `-Wextra`) warns "suggest braces around empty body in an 'if'
statement".

```c
/* empty_if.c */
#include <stdio.h>

int main(void)
{
    int x = -5, y = 0;
    if (x > 0);              /* bug: empty body */
        y = 1;
    printf("%d\n", y);
    return 0;
}
```

```text
1
```

### In real systems

Many style guides (Linux kernel for multi-line bodies, most corporate C
standards always) require braces on every `if` and loop body, because a line
added later under an unbraced `if` silently runs unconditionally. Apple's
2014 "goto fail" TLS bug was exactly that.

### Check yourself

**Is `{ int a = 1; }` followed by `printf("%d", a);` legal?**

<details>
<summary>Answer</summary>

No. `a` went out of scope at the closing brace, so the compiler reports
"'a' undeclared".

</details>

## 3.2 If-Else

### In one sentence

`if (expr) s1 else s2` runs `s1` when `expr` is non-zero and `s2` otherwise,
and an `else` always belongs to the nearest unmatched `if`.

### The idea

`if` evaluates its expression. If the value is non-zero, the first statement
runs; otherwise the `else` part, if there is one, runs. Because the test is
"non-zero", `if (n)` and `if (n != 0)` mean the same; the first is shorter,
the second clearer.

The `else` part is optional, which creates an ambiguity in nested `if`s:
which `if` does an `else` belong to? C's rule is that an `else` goes with
the **closest previous `else`-less `if`**. This is the **dangling else**.
Indentation does not change it; only braces do.

Every `if` body should be one statement or a block. Writing braces always
removes both the ambiguity and the added-line trap from 3.1.

### Worked example

```c
/* sign.c */
#include <stdio.h>

static const char *sign(int n)
{
    if (n > 0)
        return "positive";
    else if (n < 0)
        return "negative";
    else
        return "zero";
}

int main(void)
{
    printf("%s %s %s\n", sign(5), sign(-2), sign(0));
    return 0;
}
```

```text
positive negative zero
```

The realistic example is the dangling else itself. The indentation says the
`else` belongs to the outer `if`; the language says the inner one.

```c
/* dangling.c */
#include <stdio.h>

static int pick(int n, int a, int b)
{
    int z = 0;
    if (n > 0)
        if (a > b)
            z = a;
    else                      /* belongs to the inner if! */
        z = b;
    return z;
}

int main(void)
{
    printf("%d %d %d\n", pick(1, 5, 3), pick(1, 2, 3), pick(-1, 5, 3));
    return 0;
}
```

```text
5 3 0
```

For `n` of -1 the writer expected `z = b`, which is 3. The program returns 0,
because the `else` is attached to `if (a > b)`, which is never reached when
`n` is not positive. gcc's `-Wall` warns "suggest explicit braces to avoid
ambiguous 'else'" (`-Wdangling-else`).

### Step by step

The fix is braces around the inner `if`:

```c
/* dangling_fixed.c */
#include <stdio.h>

static int pick(int n, int a, int b)
{
    int z = 0;
    if (n > 0) {
        if (a > b)
            z = a;
    } else {
        z = b;
    }
    return z;
}

int main(void)
{
    printf("%d %d %d\n", pick(1, 5, 3), pick(1, 2, 3), pick(-1, 5, 3));
    return 0;
}
```

```text
5 0 3
```

<Figure art={`
  What the indentation says          What the compiler parses

  if (n > 0)                         if (n > 0)
      if (a > b)                     +-- if (a > b)
          z = a;                     |       z = a;
  else                               |   else
      z = b;                         |       z = b;   <- inner if's else
                                     +-- (no else for the outer if)
`} caption="The dangling else, drawn as the compiler sees it. An else binds to the nearest unmatched if; braces are the only way to say otherwise." />

### Common mistake

Writing `if (x = 0)` for `if (x == 0)`. The assignment makes `x` zero and
the condition false, every time. And testing floating values for exact
equality, `if (d == 0.3)`, which fails for computed values; compare with a
tolerance instead.

### In real systems

Security reviewers read every `if` around an authentication or bounds check
for exactly these patterns: an accidental assignment, a missing brace, a
dangling else. Compilers' `-Wall` warnings for all three are mandatory in
most serious builds, often with `-Werror`.

### Check yourself

**With no braces, which `if` does the `else` belong to in `if (a) if (b) x(); else y();`?**

<details>
<summary>Answer</summary>

The inner one, `if (b)`. An else binds to the nearest previous if that has
no else.

</details>

## 3.3 Else-If

### In one sentence

A chain of `else if`s tests conditions in order and runs the first one that
is true, which is how C writes a general multi-way decision.

### The idea

`if (e1) s1 else if (e2) s2 else if (e3) s3 else s4` is not a special
statement. It is nested `if`-`else`s, each `else`'s body being the next
`if`, written flat by convention. The conditions are tested top to bottom;
the first true one runs its statement, and the rest are skipped. The final
`else` handles "none of the above", and it is a good place to catch the
impossible case.

The book's example is **binary search**: find a value `x` in a sorted array
`v[0..n-1]`. Compare `x` with the middle element; if it is smaller, search
the lower half; if larger, the upper half; if equal, done. Each comparison
is a three-way decision, the natural use of an `else if` chain.

Binary search halves the remaining range on each step, so on a million
elements it needs at most 20 comparisons, against up to a million for a
linear scan. It works only on sorted data.

### Worked example

```c
/* binsearch.c */
#include <stdio.h>

/* find x in v[0] <= v[1] <= ... <= v[n-1]; return index or -1 */
static int binsearch(int x, const int v[], int n)
{
    int low = 0, high = n - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (x < v[mid])
            high = mid - 1;
        else if (x > v[mid])
            low = mid + 1;
        else
            return mid;          /* found */
    }
    return -1;                   /* not found */
}

int main(void)
{
    int v[] = {2, 3, 5, 7, 11, 13, 17};
    printf("%d %d %d %d\n", binsearch(11, v, 7), binsearch(2, v, 7),
           binsearch(4, v, 7), binsearch(1, v, 0));
    return 0;
}
```

```text
4 0 -1 -1
```

The last call searches an empty array: `high` starts at -1, the loop never
runs, and -1 comes back. A realistic second example is grading by ranges,
where the order of the tests carries meaning:

```c
/* grade.c */
#include <stdio.h>

static char grade(int score)
{
    if (score < 0 || score > 100) return '?';
    else if (score >= 90)         return 'A';
    else if (score >= 80)         return 'B';
    else if (score >= 70)         return 'C';
    else                          return 'F';
}

int main(void)
{
    int s[] = {95, 90, 85, 70, 12, 101};
    for (int i = 0; i < 6; i++)
        putchar(grade(s[i]));
    putchar('\n');
    return 0;
}
```

```text
AABCF?
```

Each `else if` only needs a lower bound because the earlier tests already
excluded everything above.

### Step by step

Search for 11 in `2 3 5 7 11 13 17`:

<Trace columns={["step", "low", "high", "mid", "v[mid]", "decision"]} rows={[
  ["1", "0", "6", "3", "7", "11 > 7: low = 4"],
  ["2", "4", "6", "5", "13", "11 < 13: high = 4"],
  ["3", "4", "4", "4", "11", "equal: return 4"],
]} caption="Binary search for 11. Each row halves the range low..high; the answer is found in three comparisons out of seven elements." />

Search for 4, which is missing: step 1 has mid 3 (7), so high becomes 2;
step 2 has mid 1 (3), so low becomes 2; step 3 has mid 2 (5), so high
becomes 1. Now low (2) is greater than high (1), the loop ends, and the
function returns -1.

Why is it correct? The **invariant**: if `x` is in the array at all, it is
in `v[low..high]`. It is true at the start (the whole array). Each step
keeps it, because the array is sorted: if `x < v[mid]`, it cannot be at
`mid` or above, so dropping them is safe, and symmetrically for the other
side. The range shrinks by at least one each step, so the loop ends. When it
ends with `low > high`, the range is empty, so by the invariant `x` is not in
the array.

### Common mistake

Computing the midpoint as `(low + high) / 2`. When `low` and `high` are both
large, the sum overflows `int`, which is undefined. This exact bug lived in
the JDK's binary search for nine years. `low + (high - low) / 2` cannot
overflow. The other classic is updating with `high = mid` or `low = mid`,
which can loop forever when the range has two elements.

### In real systems

Binary search is everywhere sorted data is: database index pages, `git
bisect` (over commits, not numbers), the C library's `bsearch`, and every
"lower bound" lookup in a sorted vector. The else-if chain is also how
request routers, parsers and validation code decide between cases.

### Check yourself

**Why must the loop condition be `low <= high` and not `low < high`?**

<details>
<summary>Answer</summary>

With `<`, a one-element range (low equal to high) is never examined, so a
value at that position is reported missing.

</details>

**How many comparisons, at most, does binary search need on 1,000 elements?**

<details>
<summary>Answer</summary>

About 10 iterations, since 2 to the 10 is 1,024. Each iteration does up to
two comparisons in this version.

</details>

## 3.4 Switch

### In one sentence

`switch` jumps to the `case` matching an integer value, falls through to
the following cases unless you `break`, and goes to `default` if nothing
matches.

### The idea

A `switch` statement evaluates an integer expression once and compares it
against a set of **case labels**, each a constant integer expression. Control
jumps to the matching label. If none matches, it jumps to `default`, if
present; otherwise nothing in the switch runs.

The case labels are just entry points. After control jumps to one, it runs
on through the following cases, which is called **fall-through**, until a
`break` (or `return`) leaves the switch. That allows several labels to share
one action, and it makes a forgotten `break` a bug.

Case values must be distinct, and must be integer constants: characters,
`enum` constants, `#define`d numbers. Strings and floating values are not
allowed. For those, use an `else if` chain.

### Worked example

The book counts digits, white space and other characters again, this time
with `switch`:

```c
/* switch_count.c */
#include <stdio.h>

int main(void)
{
    int c, nwhite = 0, nother = 0, ndigit[10] = {0};
    while ((c = getchar()) != EOF) {
        switch (c) {
        case '0': case '1': case '2': case '3': case '4':
        case '5': case '6': case '7': case '8': case '9':
            ndigit[c - '0']++;
            break;
        case ' ': case '\n': case '\t':
            nwhite++;
            break;
        default:
            nother++;
            break;
        }
    }
    printf("digits =");
    for (int i = 0; i < 10; i++)
        printf(" %d", ndigit[i]);
    printf(", white space = %d, other = %d\n", nwhite, nother);
    return 0;
}
```

```text
$ printf 'call 555-0199 now\n' | ./switch_count
digits = 1 1 0 0 0 3 0 0 0 2, white space = 3, other = 8
```

The output matches chapter 1's `if`-based version exactly, which is a useful
test. A realistic example is a command dispatcher with deliberate
fall-through, marked so readers and compilers know it is intended:

```c
/* dispatch.c */
#include <stdio.h>

enum level { DEBUG, INFO, WARN, ERROR };

static void report(enum level lv)
{
    switch (lv) {
    case ERROR:
        printf("page the on-call; ");
        /* fall through */
    case WARN:
        printf("write to alerts; ");
        /* fall through */
    case INFO:
    case DEBUG:
        printf("write to log\n");
        break;
    }
}
```

The rest of `dispatch.c`:

```c
/* dispatch.c, continued */
int main(void)
{
    report(INFO);
    report(WARN);
    report(ERROR);
    return 0;
}
```

```text
write to log
write to alerts; write to log
page the on-call; write to alerts; write to log
```


#### How a switch is compiled

A `switch` is not just a tidier `else if`. Because every case is an integer
constant, the compiler can choose how to implement it. For dense values,
such as 0 to 9, it typically builds a **jump table**: an array of code
addresses indexed by the value, so dispatch costs one bounds check and one
indirect jump no matter how many cases there are. For sparse values it
emits a binary search over the constants, or a chain of comparisons for a
handful of cases.

You can see the choice with `gcc -O2 -S`. On my x86-64 machine, a `switch`
over ten consecutive values that each do some work produces a table of
`.long` offsets followed by `jmp *%rax`; a `switch` over 1, 1000 and 1000000
produces three `cmpl` comparisons. When every case just returns a constant,
gcc goes further and replaces the code with a table of the values. The
semantics are the same either way, which is the point: you state the
decision, and the compiler picks the mechanism.

An `else if` chain has to be evaluated in order, because each test may have
side effects or depend on the ones before. The compiler can sometimes turn
a chain of equality tests on one variable into a jump table too, but it is
not obliged to, and readers cannot see at a glance that the tests are
exclusive. When the decision is one integer against constants, `switch`
says so.

Two rules follow from "constants only". The case expressions are evaluated
at compile time, so `case N + 1:` is fine when `N` is a `#define` or `enum`
constant, but not when it is a `const int` variable, which in C is not a
constant expression. And duplicate case values are a compile error, which
catches copy-paste mistakes in long switches.

### Common mistake

The forgotten `break`. This program meant to print one word per value:

```c
/* nobreak.c */
#include <stdio.h>

int main(void)
{
    for (int i = 1; i <= 3; i++) {
        switch (i) {
        case 1: printf("one ");
        case 2: printf("two ");
        default: printf("many ");
        }
        printf("| ");
    }
    printf("\n");
    return 0;
}
```

```text
one two many | two many | many | 
```

gcc's `-Wimplicit-fallthrough` (in `-Wextra`) warns on every unmarked
fall-through. Mark intentional ones with a `/* fall through */` comment or
C23's `[[fallthrough]];`, and put `break` after every other case, including
the last, so adding a case later is safe.

### In real systems

`switch` on an `enum` is the backbone of state machines, bytecode
interpreters (a big `switch` on the opcode) and protocol handlers. With
`-Wswitch` (in `-Wall`), the compiler warns when a `switch` on an enum
misses a value, so leaving out `default` there is a deliberate way to get a
compile error when a new state is added.

### Check yourself

**Can you `switch` on a string?**

<details>
<summary>Answer</summary>

No. Case labels must be integer constant expressions. Use `strcmp` in an
`else if` chain, or map the string to an enum first.

</details>

## 3.5 Loops—While and For

### In one sentence

`while` repeats a body as long as a test is true, and `for` is the same loop
with its initialisation, test and step written together in the header.

### The idea

`while (expr) statement` evaluates `expr`; if it is non-zero, the statement
runs and the test is evaluated again. When the test becomes zero, execution
continues after the loop. The test comes first, so the body may run zero
times.

`for (expr1; expr2; expr3) statement` is equivalent to:

```c
/* for_as_while.c */
#include <stdio.h>

int main(void)
{
    int i = 0;               /* expr1: once, before anything */
    while (i < 3) {          /* expr2: before every iteration */
        printf("%d ", i);    /* the body */
        i++;                 /* expr3: after every iteration */
    }
    printf("\n");
    return 0;
}
```

```text
0 1 2 
```

There is one difference: `continue` in a `for` loop jumps to `expr3`, while
in the hand-written `while` above it would skip the `i++`. Any of the three
expressions may be omitted; a missing test counts as true, so `for (;;)` is
an infinite loop, left with `break` or `return`.

Use `for` when there is a simple initialisation and step, such as counting
over an array, because it keeps the loop control in one visible place. Use
`while` when there is no natural step, as in "read until end of input".

<Flow steps={["expr1 (init, once)", "expr2 (test): zero? leave the loop", "body", "expr3 (step)", "back to the test"]} caption="The for loop's order of evaluation. The test runs before the first iteration, so a false test means the body never runs." />

#### The comma operator

A pair of expressions separated by a **comma operator** is evaluated left to
right, and the value is the right operand. It is mostly used in `for`
headers to drive two indices at once. The commas that separate function
arguments and declarations are not comma operators.


#### Loops that never end

An infinite loop is sometimes the goal (a server's main loop) and sometimes
a bug. C11 added a rule that surprises people: a loop whose controlling
expression is not a constant, and whose body does no I/O, no `volatile`
access and no synchronisation, may be **assumed to terminate**. The
compiler can delete such a loop if its result is unused, even when it would
in fact run forever.

That rule exists so compilers can optimise loops whose termination they
cannot prove, but it means a "spin until something changes" loop on an
ordinary variable is wrong twice over. Nothing tells the compiler that the
variable can change, so it may read it once, and the loop has no
observable effect, so it may be removed. Waiting on another thread or a
signal handler needs `volatile sig_atomic_t` or C11 atomics, from Appendix
B's territory.

The constant-condition loops, `for (;;)` and `while (1)`, are exempt from
the assumption, which is one more reason to write an intentional infinite
loop in one of those two forms with an explicit `break`.

### Worked example

The book converts a string to an integer, handling leading white space and
a sign. Here is my version, which also stops at the first non-digit:

```c
/* myatoi.c */
#include <ctype.h>
#include <stdio.h>

static int myatoi(const char s[])
{
    int i, n, sign;
    for (i = 0; isspace((unsigned char)s[i]); i++)
        ;                                   /* skip white space */
    sign = (s[i] == '-') ? -1 : 1;
    if (s[i] == '+' || s[i] == '-')
        i++;                                /* skip sign */
    for (n = 0; isdigit((unsigned char)s[i]); i++)
        n = 10 * n + (s[i] - '0');
    return sign * n;
}

int main(void)
{
    printf("%d %d %d %d\n", myatoi("  42"), myatoi("-17x"),
           myatoi("+8"), myatoi("abc"));
    return 0;
}
```

```text
42 -17 8 0
```

Three loops, three shapes: one with an empty body, one with no loop at all
(the sign), and one accumulating. A second example uses the comma operator
to reverse a string in place, with `i` and `j` walking towards each other:

```c
/* reverse.c */
#include <stdio.h>
#include <string.h>

static void reverse(char s[])
{
    for (size_t i = 0, j = strlen(s); i + 1 < j; i++, j--) {
        char c = s[i];
        s[i] = s[j - 1];
        s[j - 1] = c;
    }
}

int main(void)
{
    char a[] = "control", b[] = "", c[] = "x";
    reverse(a); reverse(b); reverse(c);
    printf("[%s] [%s] [%s]\n", a, b, c);
    return 0;
}
```

```text
[lortnoc] [] [x]
```

I keep `j` one past the element it points at, so an empty string never
needs `strlen(s) - 1`, which with `size_t` would wrap around to a huge
number.

#### Shell sort

The book's showcase for nested `for` loops is **Shell sort**: compare
elements far apart first, `gap` positions apart, then shrink the gap until
it is 1, at which point it is an ordinary insertion sort on data that is
already nearly sorted.

```c
/* shellsort.c */
#include <stdio.h>

static void shellsort(int v[], int n)
{
    for (int gap = n / 2; gap > 0; gap /= 2)
        for (int i = gap; i < n; i++)
            for (int j = i - gap; j >= 0 && v[j] > v[j + gap]; j -= gap) {
                int t = v[j];
                v[j] = v[j + gap];
                v[j + gap] = t;
            }
}

int main(void)
{
    int v[] = {9, 4, 7, 1, 8, 2, 6, 3};
    shellsort(v, 8);
    for (int i = 0; i < 8; i++)
        printf("%d ", v[i]);
    printf("\n");
    return 0;
}
```

```text
1 2 3 4 6 7 8 9 
```

The `j >= 0 &&` in the inner test relies on short-circuit evaluation from
chapter 2: when `j` becomes negative, `v[j]` is never read.

### Step by step

<Trace columns={["gap", "array after this gap", "what moved"]} rows={[
  ["start", "9 4 7 1 8 2 6 3", "-"],
  ["4", "8 2 6 1 9 4 7 3", "pairs 4 apart: 9 and 8, 4 and 2, 7 and 6 swapped"],
  ["2", "6 1 7 2 8 3 9 4", "elements 2 apart sorted among themselves"],

what that printed.

### Common mistake

Counting down with an unsigned index:
`for (size_t i = n - 1; i >= 0; i--)`. An unsigned value is always at least
0, so the test is always true; after 0 the index wraps to the maximum value
and the next `v[i]` reads far outside the array, which is undefined. gcc's
`-Wextra` says `comparison of unsigned expression in '>= 0' is always
true`. The safe idiom tests before decrementing:

```c
/* countdown.c */
#include <stdio.h>

int main(void)
{
    int v[] = {10, 20, 30};
    size_t n = 3;
    for (size_t i = n; i-- > 0; )      /* i is 2, 1, 0 in the body */
        printf("%d ", v[i]);
    printf("\n");
    return 0;
}
```

```text
30 20 10 
```

The other classic is the off-by-one, `i <= n` for an array of `n`, which
reads `v[n]`, one past the end. That is undefined behaviour that usually
reads a neighbouring variable and carries on, so it hides.

### In real systems

`for (;;)` with a `break` is the standard event loop: servers, game loops and
shells all read an event, handle it and go round. The Linux kernel's list
macros are `for` loops whose three parts are hidden in a macro, which is
the same equivalence as above put to work.

## 3.6 Loops—Do-while

### In one sentence

`do statement while (expr);` runs the body first and tests afterwards, so
the body always runs at least once.

### The idea

`while` and `for` test at the top. `do`-`while` tests at the bottom: the
statement runs, then the expression is evaluated; if it is non-zero the
statement runs again. The loop always executes at least once, and it ends
with a semicolon after the closing parenthesis.

It is the right loop when the first pass must happen regardless, such as
generating at least one digit of a number (zero still prints as "0"), or
prompting a user before checking their answer. It is less common than the
other two, and the book says so: most loops naturally test first.

<Compare left="while and for: test first" right="do-while: test last" caption="Where the test sits decides the minimum number of iterations." rows={[
  ["test, then body, then test again", "body, then test, then body again"],
  ["body may run zero times", "body runs at least once"],
  ["right for reading until EOF or walking an array that may be empty", "right for emitting at least one digit, retrying until success, and macro bodies"],
]} />

### Worked example

Converting an integer to characters produces digits in reverse order, least
significant first, so the book generates them and then reverses the string.
There is always at least one digit, which is why `do`-`while` fits:

```c
/* myitoa.c */
#include <stdio.h>
#include <string.h>

static void reverse(char s[])
{
    for (size_t i = 0, j = strlen(s); i + 1 < j; i++, j--) {
        char c = s[i]; s[i] = s[j - 1]; s[j - 1] = c;
    }
}

static void myitoa(int n, char s[])
{
    unsigned u = (n < 0) ? 0u - (unsigned)n : (unsigned)n;
    int i = 0;
    do {
        s[i++] = (char)('0' + u % 10);   /* next digit */
    } while ((u /= 10) > 0);
    if (n < 0)
        s[i++] = '-';
    s[i] = '\0';
    reverse(s);
}
```

The rest of `myitoa.c`:

```c
/* myitoa.c, continued */
int main(void)
{
    char buf[16];
    int tests[] = {0, 7, -45, 2147483647, -2147483647 - 1};
    for (int k = 0; k < 5; k++) {
        myitoa(tests[k], buf);
        printf("%s ", buf);
    }
    printf("\n");
    return 0;
}
```

```text
0 7 -45 2147483647 -2147483648 
```

The edge case is the most negative `int`. The obvious approach, `n = -n`
when `n` is negative, overflows for `INT_MIN`, because +2147483648 does not
fit in an `int`. That is undefined behaviour; in practice it leaves `n`
negative and the digit loop prints garbage. Converting to `unsigned` first
is defined: unsigned arithmetic wraps modulo 2 to the 32, so `0u - (unsigned)n`
is exactly the magnitude.

A second realistic use is a macro that must behave like one statement. A
`do { ... } while (0)` body runs once and swallows the following semicolon,
so the macro works inside an unbraced `if`-`else`:

```c
/* swap_macro.c */
#include <stdio.h>

#define SWAP(a, b) do { int t_ = (a); (a) = (b); (b) = t_; } while (0)

int main(void)
{
    int x = 1, y = 2;
    if (x < y)
        SWAP(x, y);
    else
        printf("already ordered\n");
    printf("%d %d\n", x, y);
    return 0;
}
```

```text
2 1
```

With plain braces instead, `SWAP(x, y);` would expand to `{ ... };`, the
extra semicolon would end the `if`, and the `else` would be a syntax error.

### Step by step

`myitoa(-45, buf)`: `u` becomes 45. First pass writes '5', then `u` becomes
4, which is greater than 0. Second pass writes '4', `u` becomes 0, the test
fails. The sign is appended: "54-". Reversing gives "-45".

For `n` of 0, the first pass writes '0' before any test, so the result is
"0". With a `while` loop testing first, zero would give an empty string.

### Common mistake

Forgetting the semicolon after `while (expr)`, which makes the next
statement part of a different construct, or writing `while (cond);` at the
top of a block thinking it is a `do`-`while`, which is an empty `while` loop
that may never end. The other mistake is negating `INT_MIN`, covered above;
`-fsanitize=undefined` reports it as "negation of -2147483648 cannot be
represented in type 'int'".

### In real systems

Retry loops are naturally test-last: try the operation, and repeat while it
failed with a temporary error such as `EINTR` or `EAGAIN`. Nearly every
multi-statement macro in large C codebases, the Linux kernel included, is
wrapped in `do { } while (0)`.

### Check yourself

**How many times does `do { n++; } while (0);` increment `n`?**

<details>
<summary>Answer</summary>

Once. The body runs before the test, and the test is false.

</details>

## 3.7 Break and Continue

### In one sentence

`break` leaves the innermost loop or `switch` at once, and `continue` skips
to the next iteration of the innermost loop.

### The idea

Sometimes the right place to leave a loop is in the middle, not at the test.
`break` exits the innermost enclosing `for`, `while`, `do` or `switch`
immediately. Execution continues with the statement after it.

`continue` applies only to loops, not `switch`. It skips the rest of the
body: in `while` and `do` it goes straight to the test; in `for` it goes to
the step expression and then the test. A `continue` inside a `switch` inside
a loop continues the loop.

Both act on the innermost construct only. To leave two nested loops, use a
flag, a `return` from a helper function, or the `goto` of the next section.

<Flow steps={["top of loop body", "continue: skip to the step (for) or test (while, do)", "break: leave the loop, go to the statement after it", "end of body: step, then test"]} caption="Where break and continue send control. Both affect only the innermost enclosing loop, and break also leaves a switch." />

### Worked example

The book trims trailing white space from a string by scanning backwards from
the end and breaking at the first non-blank. My version:

```c
/* trim.c */
#include <stdio.h>
#include <string.h>

static size_t trim(char s[])
{
    size_t n;
    for (n = strlen(s); n > 0; n--)
        if (s[n - 1] != ' ' && s[n - 1] != '\t' && s[n - 1] != '\n')
            break;
    s[n] = '\0';
    return n;
}

int main(void)
{
    char a[] = "hello \t\n", b[] = "   ", c[] = "x";
    size_t na = trim(a), nb = trim(b), nc = trim(c);
    printf("[%s]%zu [%s]%zu [%s]%zu\n", a, na, b, nb, c, nc);
    return 0;
}
```

```text
[hello]5 []0 [x]1
```

An all-blank string trims to empty, because the loop runs out at 0 without
breaking. A realistic `continue` skips records that should not be counted,
keeping the main path unindented:

```c
/* sum_valid.c */
#include <stdio.h>

int main(void)
{
    int readings[] = {12, -1, 15, 999, 9, -1, 14};
    int sum = 0, used = 0;
    for (int i = 0; i < 7; i++) {
        if (readings[i] < 0)          /* sensor offline */
            continue;
        if (readings[i] > 100)        /* obviously corrupt */
            continue;
        sum += readings[i];
        used++;
    }
    printf("%d readings, mean %.1f\n", used, (double)sum / used);
    return 0;
}
```

```text
4 readings, mean 12.5
```

### Step by step

`trim("hello \t\n")`: `strlen` is 8. At n 8, `s[7]` is newline, so keep
going. At n 7, tab. At n 6, space. At n 5, `s[4]` is 'o', not blank, so
`break`. `s[5]` gets the terminator and the length 5 is returned.

### Common mistake

Expecting `break` inside a `switch` inside a loop to leave the loop. It
leaves only the `switch`:

```c
/* break_switch.c */
#include <stdio.h>

int main(void)
{
    const char *cmds = "aaqaa";
    int handled = 0;
    for (int i = 0; cmds[i] != '\0'; i++) {
        switch (cmds[i]) {
        case 'q':
            break;               /* leaves the switch, not the loop */
        default:
            handled++;
        }
    }
    printf("handled %d\n", handled);
    return 0;
}
```

```text
handled 4
```

The writer wanted "quit at q" and 2. AT&T's 1990 long-distance network
outage traced back to a `break` that left a different construct from the
one its author intended.

### In real systems

"Guard clauses" with `continue` at the top of a loop, and early `return` at
the top of a function, are the standard way to keep the main path of C code
flat. Code reviewers prefer them to deep `if` nesting.

### Check yourself

**In a `for` loop, does `continue` run the step expression?**

<summary>Answer</summary>

Yes. It jumps to the step, then the test. In a `while` loop there is no
step, so it goes straight to the test.

</details>

## 3.8 Goto and Labels

### In one sentence

`goto label;` jumps to a labelled statement in the same function, and it is
rarely needed except to leave deeply nested loops or to share error cleanup.

### The idea

A **label** is a name followed by a colon, attached to a statement, and its
scope is the whole function. `goto name;` transfers control there. Labels
live in their own namespace, so a label can share a name with a variable.

The book's position is that `goto` is never necessary and almost always
makes code harder to follow, because a reader can no longer see the shape
of the control flow from the indentation. Any program with `goto` can be
written without it, using flags or extra tests. But there are a couple of
places where it is the clearest tool.

The first is breaking out of two or more nested loops at once, which
`break` cannot do. The second, very common in systems C, is **centralised
cleanup**: on an error deep in a function, jump to labels at the end that
release whatever was acquired, in reverse order.

### Worked example

Searching two arrays for a common element, leaving both loops when found:

```c
/* common.c */
#include <stdio.h>

int main(void)
{
    int a[] = {4, 8, 15, 16}, b[] = {23, 42, 16, 8};
    int i, j;
    for (i = 0; i < 4; i++)
        for (j = 0; j < 4; j++)
            if (a[i] == b[j])
                goto found;
    printf("no common element\n");
    return 0;
found:
    printf("a[%d] == b[%d] == %d\n", i, j, a[i]);
    return 0;
}
```

```text
a[1] == b[3] == 8
```

The same thing without `goto` needs a flag tested in both loop headers, or a
helper function that `return`s. The helper is usually the best choice; the
`goto` is fine when the function is short.

The realistic use is cleanup. Each resource acquired gets a label that
releases it, and the labels run in reverse order:

```c
/* cleanup.c */
#include <stdio.h>
#include <stdlib.h>

static int process(const char *path)
{
    int rc = -1;
    FILE *f = fopen(path, "r");
    if (f == NULL)
        goto out;
    char *buf = malloc(4096);
    if (buf == NULL)
        goto close_file;
    size_t n = fread(buf, 1, 4096, f);
    printf("%s: read %zu bytes\n", path, n);
    rc = 0;
    free(buf);
close_file:
    fclose(f);
out:
    return rc;
}
```

The rest of `cleanup.c`:

```c
/* cleanup.c, continued */
int main(void)
{
    int r1 = process("cleanup.c"), r2 = process("/no/such/file");
    printf("%d %d\n", r1, r2);
    return 0;
}
```

```text
...
0 -1
```

The first line is `cleanup.c: read N bytes`, where N depends on the file,
so the transcript leaves it open.

### Step by step

<Trace columns={["failure point", "jumps to", "cleanup that runs", "returns"]} rows={[
  ["fopen fails", "out", "nothing", "-1"],
  ["malloc fails", "close_file", "fclose", "-1"],
  ["no failure", "falls through", "free, then fclose", "0"],
]} caption="The cleanup ladder. Each failure jumps past the releases for things it never acquired, and every path leaves through the same exit." />

### Common mistake

Jumping forward past the declaration of a variable-length array, or
backwards in a way that creates a hidden loop. C forbids jumping into the
scope of a VLA. Jumping past an ordinary initialised declaration is legal
but leaves the variable uninitialised, so reading it is undefined. In the
cleanup example, `buf` is declared after the first `goto`; that is fine only
because nothing at `close_file` or `out` reads `buf`.

### In real systems

The Linux kernel uses `goto` cleanup ladders in thousands of functions; its
coding style document recommends exactly this pattern with labels named for
what they undo. Languages with destructors or `defer` (C++, Go, Zig) build
the same idea into the language.

### Check yourself

**Can `goto` jump to a label in a different function?**

<details>
<summary>Answer</summary>

No. A label's scope is the function it is in. For non-local jumps there is
`setjmp`/`longjmp` in the standard library, covered in Appendix B.

</details>

## From beginner to strategy

<Levels label="Chapter 3, Control Flow">
<Level name="Beginner" depth={3}>

The beginner's core is four shapes: a decision (`if`-`else`), a multi-way
decision (`else if` or `switch`), a loop that tests first (`while`, `for`)
and a loop that tests last (`do`-`while`). Every function you will write is
built from those, nested.

A beginner's worked example: print the numbers 1 to 15, but print "fizz"
for multiples of 3, "buzz" for multiples of 5, and "fizzbuzz" for both. It
needs one `for` and one `else if` chain, and the order of the tests matters:

```c
/* fizz.c */
#include <stdio.h>

int main(void)
{
    for (int i = 1; i <= 15; i++) {
        if (i % 15 == 0)     printf("fizzbuzz ");
        else if (i % 3 == 0) printf("fizz ");
        else if (i % 5 == 0) printf("buzz ");
        else                 printf("%d ", i);
    }
    printf("\n");
    return 0;
}
```

```text
1 2 fizz 4 buzz fizz 7 8 fizz buzz 11 fizz 13 14 fizzbuzz 
```

Put the `% 3` test first and 15 prints "fizz", because the chain stops at
the first true test. The beginner habit to build now: braces on every body,
and compile with `-Wall -Wextra` so the compiler catches the empty `if`, the
dangling else and the missing `break`.

</Level>
<Level name="Intermediate" depth={3}>

The intermediate skill is choosing the loop and its exit so the code reads
in the order a person thinks. Guard clauses with `continue` at the top, a
`for` when there is a counter, a `while` when there is a condition, and a
`break` when the natural exit is in the middle.

The "loop and a half" is the classic case where the exit belongs in the
middle: read a value, stop if it is the sentinel, otherwise process it.

```c
/* loop_half.c */
#include <stdio.h>

int main(void)
{
    int x, total = 0;
    for (;;) {
        if (scanf("%d", &x) != 1)   /* EOF or not a number */
            break;
        if (x == 0)                 /* sentinel */
            break;
        total += x;
    }
    printf("total %d\n", total);
    return 0;
}
```

```text
$ printf '5 10 -3 0 99\n' | ./loop_half
total 12
```

The alternative, priming a read before a `while` and repeating it at the
bottom, duplicates the read. The `for (;;)` with `break` states each exit
once.

</Level>
<Level name="Advanced" depth={3}>

At the advanced level you reason about loops with **invariants**: a
statement that is true before the loop, stays true after every iteration,
and together with the exit condition gives the result. Binary search in 3.3
is the model. You also count: how many iterations, and does every one make
progress so the loop must end?

A variant that is harder to get right is **lower bound**: the first index
whose element is at least `x`, or `n` if there is none. It works on arrays
with duplicates and is what sorted-vector libraries actually use.

```c
/* lower_bound.c */
#include <stdio.h>

/* invariant: v[0..lo-1] < x and v[hi..n-1] >= x */
static int lower_bound(const int v[], int n, int x)
{
    int lo = 0, hi = n;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (v[mid] < x) lo = mid + 1;
        else            hi = mid;
    }
    return lo;
}

int main(void)
{
    int v[] = {1, 3, 3, 3, 8};
    printf("%d %d %d %d\n", lower_bound(v, 5, 3), lower_bound(v, 5, 0),
           lower_bound(v, 5, 4), lower_bound(v, 5, 9));
    return 0;
}
```

```text
1 0 4 5
```

Here `hi = mid` is safe because `mid` is strictly less than `hi` whenever
`lo < hi`, so the range always shrinks. Writing down the invariant first is
what makes that obvious.

</Level>
<Level name="Edge cases" depth={3}>

Every loop has three edge inputs: zero iterations, one iteration and the
maximum. Test each. Binary search on an empty array, `reverse` on an empty
string, `trim` on an all-blank string and `myitoa` on 0 are all in this
page because each one is where a version of that code goes wrong.

The fourth edge is the type of the loop variable. With `int i` and a bound
`n` of type `size_t`, the comparison `i < n` converts `i` to unsigned, so a
negative `i` would compare as huge. With an `unsigned char` counter, a loop
to 256 never ends:

```c
/* uchar_loop.c */
#include <stdio.h>

int main(void)
{
    int iterations = 0;
    for (unsigned char c = 250; c != 0; c++)  /* wraps 255 -> 0 */
        iterations++;
    printf("%d\n", iterations);
    /* for (unsigned char c = 0; c < 256; c++) would never end */
    return 0;
}
```

```text
6
```

This loop ends only because it tests `c != 0` and relies on the wrap, which
is defined for unsigned types. The commented-out version is always true,
and gcc says so with `-Wextra`.

</Level>
<Level name="Corner cases" depth={3}>

Corner cases are where two rules meet. One is `switch` and declarations: a
`case` label is a jump target, so jumping into a `switch` skips any
initialisation written between labels. Declaring a variable directly after
a `case` label was a syntax error before C23, because a label must be
followed by a statement; wrapping the case body in braces fixes both
problems.

Another is the most famous corner of C control flow, **Duff's device**, in
which a `switch` jumps into the middle of a `do`-`while`. It is legal
because case labels can label any statement inside the switch body,
including one inside a loop:

```c
/* duff.c */
#include <stdio.h>

static void copy(char *to, const char *from, int count)
{
    int n = (count + 3) / 4;
    switch (count % 4) {
    case 0: do { *to++ = *from++;
    case 3:      *to++ = *from++;
    case 2:      *to++ = *from++;
    case 1:      *to++ = *from++;
            } while (--n > 0);
    }
}

int main(void)
{
    char dst[8] = {0};
    copy(dst, "abcdefg", 7);
    printf("%s\n", dst);
    return 0;
}
```

```text
abcdefg
```

It unrolls the copy by four and handles the remainder by jumping in part
way. With `count` of 0 it still copies four bytes, which is a bug, so the
real version guards against zero. Modern compilers unroll loops better on
their own; read it to understand labels, not to use it.

</Level>
<Level name="Production level" depth={3}>

In production C the control-flow rules are enforced by tools. `-Wall
-Wextra -Werror` makes the empty body, the dangling else, the implicit
fall-through and the always-true unsigned test into build failures.
`-Wswitch-enum` catches a missing enum case even when there is a `default`.
Static analysers (clang-tidy, cppcheck, Coverity) report unreachable code
and loops that cannot terminate.

Style is the other half. Production codebases standardise brace placement,
require braces everywhere, forbid `goto` except for the cleanup ladder,
and cap nesting depth (the Linux kernel's style guide says that more than
three levels of indentation means the function should be split).

Error paths are the production problem. Every call that can fail gets
checked, and the cleanup ladder from 3.8 ensures every failure releases
what was acquired, in reverse order. Test them by injecting failures, for
example a `malloc` wrapper that fails on the Nth call.

</Level>
<Level name="Mindset" depth={3}>

The mindset is that control flow is the shape of the argument the code
makes. When you can say, for each loop, what is true at the top of every
iteration and why the loop must end, the code is probably right. When you
cannot, the code is probably wrong, even if the tests pass.

The second habit is honesty about exits. Each `break`, `continue`, `return`
and `goto` is an exit; a reader has to find them all to know what the loop
does. Use them where they make the code shorter and clearer, and do not
scatter them.

</Level>
<Level name="System design" depth={3}>

At system scale, control flow becomes architecture. A server's main loop is
`for (;;)` around an event wait and a `switch` on the event type. An
interpreter is a loop around a `switch` on the opcode. A protocol
implementation is a state machine: an `enum` for the states, a `switch` on
the state, and transitions as assignments.

<Figure art={`
   +---------+   read event   +--------------+
   |  wait   | -------------> | switch(type) |
   +---------+                +--------------+
        ^                      |     |      |
        |                 accept  readable  timeout
        |                      |     |      |
        +----------------------+-----+------+
                 handle, then loop again
`} caption="An event loop is a for(;;) around a switch. The same three statements from this chapter are the skeleton of servers, GUIs and interpreters." />

The design questions are which state is explicit and which is implicit in
"where the program counter is". A state machine written as a `switch` makes
every state visible and testable; the same logic as nested loops hides
states in the call stack.

</Level>
<Level name="Strategy" depth={3}>

My strategy for this chapter is to practise until the traps are reflexes,
then spend the time on invariants. The traps (empty `if`, dangling else,
missing `break`, unsigned countdown, `(low + high) / 2`) are a short list
and the compiler catches most of them. Invariants are a lifelong skill.

I write each loop on this page from memory, state its invariant in a

## Questions people ask

**Is `for` faster than `while`?** No. They compile to the same machine code;
the choice is about readability.

**Should I always put a `default` in a `switch`?** On a `switch` over an
enum, leaving it out lets the compiler warn when a value is not handled. On
anything else, include it, even if it only reports an impossible value.

**Is `goto` really that bad?** Unstructured `goto` that jumps backwards and
forwards is. The two patterns in 3.8 are widely accepted, and the Linux
kernel uses the cleanup one everywhere.

**Why do C programmers write `for (;;)` instead of `while (1)`?** Habit, and
older compilers that warned about a constant condition in `while (1)`. They
mean the same thing.

**Can `break` leave an `if`?** No. It leaves the innermost loop or `switch`;
an `if` is not a loop.

**What does a semicolon after a `for` header do?** It makes the loop body
the null statement, so the loop runs to completion with nothing in it and
the next line runs once. Occasionally intended, for example in the
white-space skipping loop of `myatoi`, where the empty body is on its own
line to show it.

**Does the order of cases in a `switch` matter?** Not for which case is
chosen, since the values are distinct. It matters for fall-through, and for
readability: put the common cases first, or follow the order of the enum.

**Can a `case` label appear inside a nested block of the `switch`?** Yes.
Case labels may label any statement in the switch body, at any depth,
which is what makes Duff's device legal. It is almost never a good idea.

**Why is my `while (flag == 0) ;` loop hanging after I compile with `-O2`?**
Because nothing tells the compiler that `flag` can change, it may load it
once and loop forever. Make the flag `volatile sig_atomic_t` for a signal
handler, or `_Atomic` for another thread.

## Key takeaways

- A semicolon turns an expression into a statement; braces turn several statements into one block with its own scope.
- An `else` belongs to the nearest unmatched `if`; braces, not indentation, change that.
- An `else if` chain tests in order and stops at the first true condition, so order the tests deliberately.
- `switch` cases are jump targets and fall through; put `break` after each one and mark intended fall-through.
- `for` is a `while` with the control in one place; `continue` in a `for` still runs the step.
- `do`-`while` runs at least once, which suits "at least one digit" and the macro idiom `do { } while (0)`.
- `break` and `continue` act on the innermost loop only, and `break` in a `switch` does not leave the loop.
- `goto` is for leaving nested loops and for cleanup ladders, nothing else.
- Midpoints are `low + (high - low) / 2`, and negating `INT_MIN` is undefined; both are overflow traps.
- State a loop's invariant and test zero, one and maximum iterations.

## Glossary

- **Expression statement**: an expression followed by a semicolon, evaluated for its side effects.
- **Compound statement (block)**: declarations and statements in braces, treated as one statement.
- **Null statement**: a lone semicolon, which does nothing.
- **Dangling else**: the ambiguity of an `else` after nested `if`s, resolved to the nearest `if`.
- **Case label**: a constant integer value in a `switch`, marking where control enters.
- **Fall-through**: running on from one case into the next because no `break` intervenes.
- **Comma operator**: evaluates two expressions left to right and yields the second.
- **Loop invariant**: a statement true before and after every iteration of a loop.
- **Binary search**: repeatedly halving a sorted range to find a value.
- **Shell sort**: insertion sort over shrinking gaps, so far-apart elements move early.
- **Guard clause**: an early `continue` or `return` that handles a special case first.
- **Label**: a name and colon marking a statement as a `goto` target.
- **Cleanup ladder**: labels at a function's end that release resources in reverse order.
- **Sentinel**: a special input value that marks the end of the data.

<details>
<summary>1. What prints: `int y = 0; if (0) ; y = 1; printf("%d", y);`?</summary>

1. The `if` controls only the null statement, and `y = 1` always runs.

<details>
<summary>2. Why does `(low + high) / 2` sometimes fail?</summary>

When both are large the sum exceeds `INT_MAX`, which is undefined
behaviour. `low + (high - low) / 2` gives the same midpoint without
overflow.

</details>

<details>
<summary>3. What is the minimum number of times a do-while body runs?</summary>

Once. The test is at the bottom.

</details>

<details>
<summary>4. Inside a switch inside a loop, what does continue do?</summary>

It continues the loop. `continue` ignores `switch`, unlike `break`.

</details>

<details>
<summary>5. Why can't a switch case be a string?</summary>

Case labels must be integer constant expressions, so the compiler can turn
the switch into comparisons or a jump table.

`i >= 0` is always true for an unsigned type, so the loop never ends and
