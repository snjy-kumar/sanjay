This chapter is about the gap between an idea that sounds right and an
algorithm that is right. Skiena opens with two everyday problems, ordering a
robot's moves and picking which jobs to accept, and shows that the first
three ideas almost anyone has are wrong. The rest of the chapter gives the
tools for telling the difference: precise problem statements, counterexamples,
induction, contradiction, modelling and estimation.

## Before you start

**After this chapter you will be able to:**

- State a problem as an exact input and output, so that "correct" has a
  meaning you can check.
- Break a plausible heuristic with a small, specific counterexample, usually
  in under five minutes.
- Prove a recursive or incremental algorithm correct by induction, and prove
  something impossible by contradiction.
- Recognise the standard object hiding in a problem (a permutation, a subset,
  a tree, a graph, a set of points, a polygon or a string) and use that name
  to find known solutions.
- Make a quick, defensible estimate of a size or a running time before you
  build anything.

## 1.1 Robot Tour Optimization

### In one sentence

Ordering the points a robot must visit so the closed tour is as short as
possible looks like a job for a simple rule, but every simple rule fails on
some input, and the correct method is far too slow, because this is the
travelling salesman problem.

### The idea

Picture a robot arm that solders contact points on a circuit board. It must
visit every point once and come back to where it started, ready for the next
board. The arm moves at a fixed speed, so time is proportional to distance.
The problem, stated exactly, is: **input**, a set of n points in the plane;
**output**, the shortest closed tour (a cycle) that visits each point once.

An **algorithm** is a procedure that, for every possible input, finishes and
produces the correct output. A **heuristic** is a procedure that usually
produces a good answer but has no guarantee. The chapter's first lesson is
that these are different things, and that most first ideas are heuristics
wearing an algorithm's clothes.

The first idea almost everyone has is the **nearest-neighbour rule**: start
somewhere, go to the closest point not yet visited, repeat, and finally
return to the start. It is simple, fast and often decent. It is also wrong,
in the sense that some inputs make it produce a tour much longer than the
best one.

The second idea is the **closest-pair rule**: treat every point as a tiny
chain, and repeatedly join the two chain ends (from different chains) that
are closest together, until one chain remains; close it into a cycle. It
avoids the nearest-neighbour's habit of zig-zagging, and it is also wrong.

The third idea is **exhaustive search**: try every ordering and keep the
shortest. It is correct, because it literally checks every candidate. But n
points have n! orderings (fixing the start, (n − 1)!), and n! grows so fast
that 20 points already mean more than 10¹⁷ tours. Correct and useless
beyond tiny inputs.

The point Skiena draws is uncomfortable and important. For this problem
there is no known algorithm that is both correct and efficient. It is the
**travelling salesman problem** (TSP), the most famous of the hard problems
in chapter 11. A good designer recognises this early, stops hunting for a
perfect fast rule, and chooses deliberately between a slow exact method and
a fast heuristic with known weaknesses (chapter 12).

### Worked example

**Simple: points on a line.** Put six points on the x-axis at 0, 1, −2, 4,
−8 and 16, and start at 0. Nearest neighbour goes to 1 (distance 1), then
−2 (3), then 4 (6), then −8 (12), then 16 (24), then back to 0 (16). It
swings left and right across the start again and again, and each swing is
twice as long as the last.

```ts
// tour.ts: nearest neighbour against exhaustive search (excerpt)
type P = [number, number];
const d = (a: P, b: P) => Math.hypot(a[0] - b[0], a[1] - b[1]);
const tourLen = (t: P[]) =>
  t.reduce((s, p, i) => s + d(p, t[(i + 1) % t.length]), 0);

function nearestNeighbour(pts: P[], start = 0): P[] {
  const left = pts.slice();
  const tour = [left.splice(start, 1)[0]];
  while (left.length) {
    const cur = tour[tour.length - 1];
    let best = 0;
    for (let i = 1; i < left.length; i++)
      if (d(cur, left[i]) < d(cur, left[best])) best = i;
    tour.push(left.splice(best, 1)[0]);
  }
  return tour;
}
```

The exhaustive search fixes the first point and tries every permutation of
the rest with a generator (the full file has it; it is the swap-based
permutation generator from chapter 9). Running both on the line:

```text
NN order   : 0 1 -2 4 -8 16  length 62
best order : 0 1 4 16 -8 -2  length 48
```

The best tour simply walks right to the far end, then all the way left, then
home: any closed tour on a line must cover the span from −8 to 16 twice, so
48 is the minimum. Nearest neighbour pays 62 because it keeps crossing the
start. Move the points further out in the same doubling pattern and the
ratio gets worse.

**Realistic: two rows of components.** Many boards have components in neat
rows. Put three points on a bottom row and three on a top row, the rows one
unit apart and the points in each row 1.1 units apart. Every vertical pair
is slightly closer (1.0) than any horizontal neighbour (1.1). The
closest-pair rule greedily joins all three vertical pairs first, and then has
to connect the three short chains with long diagonal-ish links.

```text
closest-pair tour 2 5 4 1 0 3 length 7.617
rectangle tour    0 1 2 5 4 3 length 6.400
```

The obvious tour, round the rectangle, is 6.4. The closest-pair rule
produces 7.617, about 19 percent longer, on a perfectly ordinary layout. In
the real robot, that is 19 percent more time per board, forever.

The ties are not an accident of my example. I chose distances so that at
every step the two candidates are equally near; the rule, by scanning in
input order, picks the one on the opposite side. Change the tie-breaking and
you can build a different bad input. That is the general lesson: a
counterexample does not need to be natural, it only needs to exist.

The exhaustive search, by contrast, is easy to argue correct in one line:
every closed tour is some ordering of the points, the search examines every
ordering, and it keeps the shortest one it sees. The proof is trivial; the
cost is what kills it.

### Common mistake

**The mistake:** testing a heuristic on random inputs, seeing good tours,
and calling it correct. Random points scattered evenly in a square are
exactly where nearest neighbour does respectably, so a few random tests
build false confidence.

**Why it fails:** correctness is a statement about every input, and random
inputs almost never contain the structured cases that break a rule (points
on a line, regular rows, clusters far apart). Bad inputs are rare in a random
sample and common in real data, because real data has structure.

**The fix:** write down what kind of procedure you have. If it is exhaustive,
it is correct and you need to bound its size. If it is a heuristic, say so in
the code and the docs, test it on structured adversarial inputs, and compare
it with the exact answer on small cases.

### In real systems

Delivery route planners, warehouse picking robots, drilling and soldering
machines, and the order in which a printer head or a laser cutter visits its
targets are all versions of this problem. None of them run exhaustive search
on real sizes. They run a fast heuristic (nearest neighbour, or an insertion
rule) to get a start, then improve it with local search, such as repeatedly
reversing a segment of the tour when that shortens it (the 2-opt move, which
chapter 12 covers).

What production teams add, and what the chapter's lesson supports, is
**measurement against a bound**. You cannot know the optimum on a big
instance, but you can compute a lower bound (for example, the weight of a
minimum spanning tree, chapter 8) and report how far above it each tour is.
That turns "the heuristic seems fine" into a number someone can monitor.

<summary>Why is exhaustive search a correct algorithm for the robot tour, and why do we still not use it?</summary>

It examines every possible ordering, so the shortest one is among those it

</details>

<summary>Does a single bad input prove nearest neighbour is wrong?</summary>

Yes. Correctness means correct on every input, so one input where it returns
a longer tour than the best one is enough. It does not prove the rule is
useless; it proves the rule is a heuristic.

</details>

## 1.2 Selecting the Right Jobs

### In one sentence

Choosing the largest set of non-overlapping jobs looks just as tricky as the
robot tour, yet here one greedy rule, always take the job that finishes
first, is provably correct, while two other plausible rules fail.

### The idea

Imagine you are an actor offered film jobs. Each job occupies an interval of
days, from a start day to an end day, and you can work on only one film at a
time. Every job pays the same, so you want **as many jobs as possible**.
Stated exactly: **input**, a set of intervals on a line; **output**, the
largest subset in which no two intervals overlap.

This is the **interval scheduling** problem. A **greedy algorithm** builds an
answer one piece at a time, each time taking the choice that looks best right
now and never reconsidering it. Greedy algorithms are fast and simple, and
they are wrong far more often than they are right. This section shows both
outcomes on one problem.

**Rule A, earliest start first.** Sort jobs by start day, take each one that
does not clash with what you already have. It fails when one very long job
starts first and blocks several short ones.

**Rule B, shortest job first.** Take short jobs because they leave the most
room. It fails when a short job sits across the boundary of two long,
compatible jobs and blocks both.

**Rule C, earliest finish first.** Sort by end day, and take each job that
does not clash. This one is correct. The reason is an **exchange argument**:
the job that finishes first can always replace whatever job an optimal
solution starts with, without losing anything.

Exhaustive search (try all 2ⁿ subsets and keep the largest valid one) is
also correct here, and is the yardstick for testing the other rules on small
inputs. With 2ⁿ subsets it is hopeless past a few dozen jobs, but for 9 jobs
it is 512 subsets, instant.

### Worked example

**Simple: one long early job.** Jobs: "epic" from day 0 to 10, and three
short ones, a (1 to 3), b (4 to 6), c (7 to 9). Earliest start picks the
epic first, because it starts on day 0, and then every short job clashes.
One job. The best answer is the three short ones.

**Realistic: a short bridging job.** Jobs: "left" from 0 to 6, "right" from 7
to 13, and "bridge" from 5 to 8, which is only 3 days long but overlaps the
end of left and the start of right. Shortest first takes the bridge, and now
neither long job fits. One job, when two were possible.

I treat intervals as **half-open**, [start, end): a job ending on day 6 and
another starting on day 6 do not clash. That choice matters, and the edge
cases section returns to it.

```ts
// jobs.ts (excerpt): three greedy rules and a brute-force yardstick
type Job = { name: string; start: number; end: number };
const overlap = (a: Job, b: Job) => a.start < b.end && b.start < a.end;

function greedy(jobs: Job[], order: (a: Job, b: Job) => number): Job[] {
  const chosen: Job[] = [];
  for (const j of [...jobs].sort(order))
    if (chosen.every(c => !overlap(c, j))) chosen.push(j);
  return chosen;
}
const earliestStart = (a: Job, b: Job) => a.start - b.start;
const shortest = (a: Job, b: Job) => (a.end - a.start) - (b.end - b.start);
const earliestEnd = (a: Job, b: Job) => a.end - b.end;
```

The brute force loops `mask` from 0 to 2ⁿ − 1, keeps the jobs whose bit is
set, checks every pair for overlap, and records the largest valid size. Then
a property test throws 2,000 random job sets at earliest-finish-first and
compares it with the brute force:

```text
long early job | earliest start: 1 | shortest: 3 | earliest end: 3 | optimum: 3
short bridging job | earliest start: 2 | shortest: 1 | earliest end: 2 | optimum: 2
earliest-end vs brute force on 2000 random sets: failures = 0
```

Read the first two lines as a scoreboard. Each wrong rule loses on one of
the two inputs, and earliest end matches the optimum on both. The third line
is evidence, not proof: 2,000 random sets passing is how you gain confidence
before (or while) you write the proof below.

That last observation gives the efficient version. After sorting by end, a
job fits if and only if its start is at least the end of the last job taken,
so you do not need to compare with every chosen job:

```ts
function maxJobs(jobs: Job[]): Job[] {
  const out: Job[] = [];
  let lastEnd = -Infinity;
  for (const j of [...jobs].sort((x, y) => x.end - y.end))
    if (j.start >= lastEnd) { out.push(j); lastEnd = j.end; }
  return out;            // O(n log n) for the sort, O(n) for the scan
}
```

Now the proof, walked line by line in plain words. Call the greedy choice g,
the job with the earliest end of all. Take any optimal solution, and call its
earliest-ending job o.

1. g ends no later than o, because g ends earliest of all jobs.
2. Every other job in the optimal solution starts at or after o ends, since
   none of them overlaps o and o is the first to end among them.
3. Combine 1 and 2: every other job in the optimal solution also starts at or
   after g ends. So g overlaps none of them.
4. Therefore swapping o out and g in gives another valid solution of the same
   size. There is an optimal solution that contains g.
5. Remove g and every job that overlaps it. What remains is the same problem
   on fewer jobs, and an optimal solution for the whole is g plus an optimal
   solution of what remains (any better remainder plus g would beat the
   optimum).
6. The greedy rule does exactly this, recursively: take g, discard its
   clashes, repeat. By induction on the number of jobs (section 1.4), it is
   optimal.

### Common mistake

**The mistake:** believing a greedy rule because it is intuitive and passes
the examples you thought of. "Shortest first leaves the most room" sounds
almost like a proof. It is not one; the bridging job breaks it with three
intervals.

**Why it fails:** greedy rules commit early and never undo a choice. A rule
is correct only if the first choice can always be extended to an optimal
solution, and intuition is bad at checking "always".

**The fix:** for any greedy rule, do two things before trusting it. Spend
five minutes trying to break it with three or four items (try a long item, a
short item across a boundary, ties, nesting). Then either find the
counterexample or write the exchange argument: show the greedy first choice
can replace the optimum's first choice.

### In real systems

Interval scheduling is behind meeting-room booking, assigning one machine to
the most batch jobs in a time window, picking non-overlapping ad slots, and
choosing which of several overlapping maintenance windows to honour. The
earliest-end rule is what you implement when every job counts the same.

Production versions change the problem in ways that break the greedy rule,
and noticing that is the real skill. If jobs have **different pay**, maximise
total pay instead of count: earliest end is now wrong, and you need dynamic
programming (weighted interval scheduling, a sort plus a binary search per
job, chapter 10). If you have **several machines** (rooms, actors), the
question becomes how many rooms are needed for all jobs, which is solved by
sorting starts and ends and sweeping, a different greedy with a different
proof.

## 1.3 Reasoning about Correctness

### In one sentence

Before you can call an algorithm correct you need an exact problem, a clear
description of the procedure, and a way to hunt for the input that breaks
it; this section covers all three, in the book's three subsections.

### The idea

The first two sections showed ideas failing. This one asks what it would
take to know an idea succeeds. Skiena's answer has three parts, matching
the subsections 1.3.1 to 1.3.3: say precisely what problem you are solving,
write the algorithm down so that someone else can follow it, and actively
try to prove yourself wrong.

#### 1.3.1 Problems and properties

A **problem** has two halves: the set of allowed inputs, and the property
the output must have for each input. "Find the best route" is not yet a
problem: best by distance, by time, by number of turns, by toll cost? Each
choice is a different problem with a different algorithm. Until the property
is exact, no algorithm can be correct, because there is nothing for it to be
correct about.

Two traps come up again and again. The first is an **ill-defined goal**, like
"best", "fair" or "most relevant", with no measure attached. The second is a
**compound goal**, like "the shortest route that also uses the fewest turns".
Two objectives rarely agree, so either one must be primary (shortest, then
fewest turns among the ties) or you must combine them into one number (a
weighted sum). Write the tie-breaker down, or the problem stays ambiguous.

The input half matters as much. "A list of numbers" leaves open whether it
can be empty, contain duplicates, contain negative values, or be enormous.
Each of those is a decision about which inputs your algorithm promises to
handle. A correct algorithm for "non-empty lists of distinct integers" is
not a correct algorithm for "lists of numbers".

#### 1.3.2 Expressing algorithms

An algorithm can be written in English, in **pseudocode** (a structured,
language-neutral sketch with loops and conditions), or in a real programming
language. Each is a trade between precision and readability. English hides
details; real code buries the idea under syntax. Pseudocode is usually the
sweet spot for thinking, and real code is where you test.

Skiena's warning here is against **pseudocode that hides a non-algorithm**.
A line like "find the best next point" sounds like a step but contains the
whole problem. A good description has steps that are each obviously
doable: "for each unvisited point, compute its distance from the current
point; take the smallest". If a step is vague, the idea behind it is
usually vague too.

The practical rule is that the heart of the algorithm should be stateable in
one or two sentences of English. "Sort by end time, and take each job that
starts after the last one you took ends" is the whole of section 1.2's
correct rule. If you cannot say yours that briefly, you probably do not yet
understand it.

#### 1.3.3 Demonstrating incorrectness

The fastest way to show an algorithm is wrong is a **counterexample**: one
specific input where it returns a wrong answer. A good counterexample has two
properties. It is **verifiable**: you can compute both the algorithm's answer
and a better answer, and show they differ. And it is **simple**: it has as
few elements as possible, so that the reason for the failure is obvious.

The book gives a short list of hunting techniques, which I paraphrase and
expand:

- **Think small.** Most failures show up with two, three or four elements.
  Big random inputs hide the cause even when they expose the failure.
- **Think exhaustively.** For a tiny size there are only a few kinds of
  input. For two intervals: they overlap, they touch, or they are apart, and
  one may contain the other. Check each kind.
- **Hunt for the weakness.** Ask what the rule is greedy about. Shortest
  first is greedy about length, so build an input where length misleads.
- **Go for a tie.** A rule that compares values must do something when they
  are equal. Ties are where unstated assumptions live (the nearest-neighbour
  example above was built from ties).
- **Seek extremes.** Mix the huge with the tiny, the near with the far, the
  many with the few: one giant interval and many small ones, points that
  double in distance each time.

### Worked example

**Simple: a bad definition.** "Return the most popular item" for the input
`["tea", "coffee", "tea", "coffee"]`. Which is it? The problem says nothing
about ties, so two implementations can both be "correct" and disagree. The
fix is in the problem, not the code: "the most frequent item; on a tie, the
one that appears first".

```ts
function mostFrequent(xs: string[]): string | undefined {
  const count = new Map<string, number>();
  let best: string | undefined, bestCount = 0;
  for (const x of xs) {
    const c = (count.get(x) ?? 0) + 1;
    count.set(x, c);
    if (c > bestCount) { best = x; bestCount = c; } // strict: first to reach wins
  }
  return best;
}
```

### Common mistake

**The mistake:** writing a "counterexample" that is a big random input where
the outputs differ, and stopping there. It proves the rule is wrong, but
nobody, including you, learns why, and a fix cannot be designed from it.

**Why it fails:** a counterexample's value is the explanation it carries. A
100-element failure is a fact; a 3-element failure is an insight.

**The fix:** always shrink. Remove elements one at a time and keep any
removal that still fails. Property-testing libraries (fast-check for
TypeScript) do this automatically, and the step is called shrinking for
exactly this reason.

### In real systems

Precise problem statements are what a good ticket or design document is
for. "Make search better" becomes "for queries in this sample, the item the
user eventually clicked should be in the top three results at least this
often". The second version has an input set and an output property, so you
can tell whether a change helped.

Counterexample hunting is what property-based tests and fuzzers do at scale.
A fuzzer generates inputs, a property says what must hold, and the tool
shrinks failures to minimal cases. Teams that adopt this find bugs that
example-based tests never reach, for the reason this section gives: examples
are the inputs you already thought of.

## 1.4 Induction and Recursion

### In one sentence

Mathematical induction proves a statement for every size n by proving it
for the smallest size and showing each size follows from the one before, and
a recursive algorithm is that same structure turned into code, so induction
is the natural way to prove recursive and incremental algorithms correct.

### The idea

Counterexamples prove wrongness. To prove rightness for infinitely many
inputs, you need an argument that covers them all at once. **Induction** is
that argument. To prove a statement S(n) for every n from some starting
value:

1. **Base case:** prove S for the smallest n directly.
2. **Inductive step:** assume S holds for every size smaller than n (the
   **inductive hypothesis**), and use that to prove S(n).

If both hold, S holds for all n, like dominoes: the first falls, and each
falling domino knocks over the next.

A **recursive** algorithm solves a problem of size n by solving smaller
instances of the same problem and combining their answers, bottoming out at
a base case it solves directly. The match with induction is exact. The base
case of the recursion is the base case of the proof. The recursive call is
the inductive hypothesis: you may assume it returns the right answer for the
smaller input, because that is exactly what you are proving for smaller
sizes. The work around the call is the inductive step.

Skiena's framing is that this is why recursion is not magic. When you write
a recursive function you are already writing an inductive proof; you only
have to check that the base case is right and that the step from smaller to
larger is right. You never need to trace the whole recursion in your head.

Incremental algorithms, which build an answer one element at a time (like
insertion sort, or the greedy job rule), are proved the same way, with
induction on how many elements have been processed. This is the loop
invariant idea seen from another angle.

### Worked example

**Simple: the sum formula.** Claim: 1 + 2 + ... + n = n(n + 1)/2. Base case:
n = 0 gives an empty sum, 0, and the formula gives 0. Inductive step: assume
the formula for n − 1, so 1 + ... + (n − 1) = (n − 1)n/2. Add n to both sides:
(n − 1)n/2 + n = (n² − n + 2n)/2 = n(n + 1)/2. Done for all n.

The recursive function is the same argument as code, and running it is a
spot check of the proof (not a replacement for it):

```ts
const sum = (n: number): number => (n === 0 ? 0 : sum(n - 1) + n);
console.log([0, 1, 2, 10, 100]
  .map(n => `${n}:${sum(n)}=${n * (n + 1) / 2}`).join('  '));
```

```text
0:0=0  1:1=1  2:3=3  10:55=55  100:5050=5050
```

**Realistic: incrementing a binary number.** A counter is stored as a string
of bits (as in a big-number library, or a version vector). To add one: if
the last bit is 0, make it 1. If it is 1, make it 0 and add one to the rest,
which is the carry. If the string is empty, the carry has run off the top,
so the answer is "1".

```ts
function increment(bits: string): string {
  if (bits === '') return '1';                  // carry out of the top
  const last = bits[bits.length - 1], rest = bits.slice(0, -1);
  return last === '0' ? rest + '1' : increment(rest) + '0';
}
for (const b of ['0', '1', '1011', '111']) console.log(b, '->', increment(b));
let ok = true;
for (let n = 0; n < 5000; n++)
  if (parseInt(increment(n.toString(2)), 2) !== n + 1) ok = false;
console.log('increment correct for 0..4999:', ok);
```

```text
0 -> 1
1 -> 10
1011 -> 1100
111 -> 1000
increment correct for 0..4999: true
```

### Step by step

The proof for `increment`, by induction on the length of the string, walked
line by line. Write val(s) for the number a bit string s represents, with
val of the empty string being 0.

1. **Base case, empty string.** val is 0 and the function returns "1", whose
   value is 1 = 0 + 1. Correct.
2. **Inductive hypothesis.** Assume `increment` is correct on every string
   shorter than s.
3. **Case: s ends in 0.** Write s = r followed by 0, so val(s) = 2·val(r).
   The result is r followed by 1, whose value is 2·val(r) + 1 = val(s) + 1.
   Correct, with no recursion needed.
4. **Case: s ends in 1.** Now val(s) = 2·val(r) + 1. The function returns
   increment(r) followed by 0. By the hypothesis (r is shorter),
   val(increment(r)) = val(r) + 1. So the result's value is
   2·(val(r) + 1) = 2·val(r) + 2 = val(s) + 1. Correct.
5. Both cases are correct for s, given correctness on shorter strings, so by
   induction `increment` is correct for every bit string.

### Common mistake

**The mistake:** an inductive step that silently uses a case the base case
does not cover. The classic is a "proof" that all horses are the same colour,
whose step from n to n + 1 only works when the two overlapping groups share a
horse, which fails going from 1 to 2. In code, the same bug is a recursive
function whose base case is n = 1 when it can be called with n = 0, or whose
recursion skips past the base case (n − 2 from n = 1 reaches −1).

**Why it fails:** induction is only as strong as the link between the base
case and the step. A gap anywhere means some size is never proved, and in
code, some input never terminates or returns garbage.

**The fix:** for every recursive call, check two things. The argument is
strictly smaller in a measure that cannot go below the base (length, n,
interval width). And every value that measure can reach is either handled by
the step or by a base case. Write the base cases for the smallest legal
inputs, including empty ones.

### In real systems

Every tree walk in production is recursion with an inductive correctness
argument: rendering a component tree, evaluating an expression, walking a
JSON document, resolving a nested permission. When you review such code, the
inductive questions (is the base case right, is the recursive input
smaller, is the combine right) are exactly the review checklist.

The termination half matters most at scale. Recursion over data that might
contain a cycle (a symlink loop in a file system, a self-referencing record)
has no decreasing measure, so the induction fails and the program overflows
its stack or loops forever. Production walkers add a visited set or a depth
limit, which restores a decreasing measure: the number of unvisited nodes,
or the remaining depth.

## 1.5 Modeling the Problem

### In one sentence

Modelling means restating a messy real-world problem in terms of a small set
of standard objects (permutations, subsets, trees, graphs, points, polygons
and strings), because once a problem has that name, decades of known
algorithms apply to it.

### The idea

Real problems arrive in domain language: "plan the robot's soldering order",
"decide which films to accept", "find the shortest chain of friends between
two people". Algorithms are written for abstract objects. **Modelling** is
the translation between the two, and Skiena treats it as the most important
design skill in the book. Most of the catalogue in Part II is organised by
these objects for that reason.

#### 1.5.1 Combinatorial objects

These are the objects to try first, each with the words in a problem
statement that usually point to it:

| Object | What it is | Words that hint at it | Example |
|---|---|---|---|
| Permutation | an ordering of items | arrangement, tour, ordering, sequence | robot tour, playlist order |
| Subset | a selection from a set | cluster, collection, committee, group, selection | the jobs to accept |
| Tree | a hierarchy with no cycles | hierarchy, dominance, ancestor, taxonomy | an org chart, a file system |
| Graph | items plus pairwise relationships | network, circuit, web, relationship | road maps, friendships |
| Point | a location in space | sites, positions, data records, locations | soldering points, shops on a map |
| Polygon | a region in space | shapes, regions, configurations, boundaries | a building outline, a country |
| String | a sequence of characters | text, characters, patterns, labels | DNA, file contents, log lines |

The table is my own arrangement of the idea, not the book's figure. Use it
as a checklist: when a new problem lands, read the statement and ask which
row's words appear. Often two rows fit, and the problem is about the
relationship between them, like a permutation (tour) of points.

#### 1.5.2 Recursive objects

Each of those objects has a **recursive** structure: removing one piece
leaves a smaller object of the same kind. Delete one element from a
permutation and you have a permutation of the rest. Remove one element from
a subset and you have a subset. Delete the root of a tree and you have a
collection of smaller trees. Delete a vertex from a graph and you have a
smaller graph. Split a point set by a line and you have two point sets. Cut a
polygon along a diagonal between two of its corners and you get two smaller
polygons. Drop the first character of a string and you get a string.

This matters because recursive structure is what recursive algorithms
(section 1.4), divide and conquer (chapter 5), backtracking (chapter 9) and
dynamic programming (chapter 10) all exploit. If you can see how an object
shrinks, you can usually see how to solve the problem for it from the
solution for the smaller piece.

### Worked example

**Simple: counting the search space.** Naming the object tells you how big
an exhaustive search is, which is often the first design decision.

```ts

for (const n of [5, 10, 15, 20])
  console.log(`n=${n}  subsets 2^n=${2 ** n}  permutations n!=${
    fact(n).toLocaleString('en-US')}`);
```

```text

```

A subset problem on 20 items can be brute-forced (about a million cases); a
permutation problem on 20 items cannot (about 2.4 × 10¹⁸). The job
selection problem is about subsets and the robot tour about permutations,
and that alone tells you exhaustive search is viable for one and not the
other at that size.

**Realistic: modelling three product requests.**

1. "Suggest which features to put in the free plan so that most users get
   everything they use." The answer is a **subset** of features, and the
   quality depends on how users' sets of used features are covered: this is
   a set-cover style problem.
2. "Order the onboarding emails so that no email mentions a feature before
   the email that introduces it." The answer is a **permutation** with
   precedence constraints: a topological sort of a **graph** (chapter 7).
3. "Find the delivery depots nearest to each customer." Customers and depots
   are **points**, and the question is nearest-neighbour search (chapter 20
   of the catalogue).

None of the three requests uses those words. The modelling step found them.

### Common mistake

**The mistake:** modelling too literally, by keeping every domain detail in
the model. "A film has a title, a director, a pay rate, locations, a start
and end date..." Most of that is irrelevant to scheduling, and a model that
keeps it all hides the interval structure that solves the problem.

**Why it fails:** standard algorithms work on standard objects. Every extra
detail you keep is a reason the textbook algorithm "does not quite fit",
which leads to inventing a new, unproven one.

**The fix:** strip the problem to the smallest description that still
determines the answer (here: intervals and, maybe, a weight). Solve that.
Then check whether any dropped detail really changes the answer; if it does,
add it back as one extra feature of the model, such as weights, colours or
capacities.

### In real systems

The most valuable thing a senior engineer does in a design review is often
a modelling move: "this is just a topological sort", "this is a bipartite
matching", "this is interval scheduling with weights". It replaces a
fortnight of bespoke code with a well-known algorithm and its well-known
failure modes.

Databases and libraries are organised around these objects too. Graph
databases store graphs, search engines index strings, spatial indexes store
points and polygons. Choosing the right storage is the same modelling
question asked one level down: what object is this data, really?

## 1.6 Proof by Contradiction

### In one sentence

To prove something is true, assume it is false and show that this
assumption leads to an impossibility; in algorithm design this is the
standard way to show that a solution is optimal or that something cannot
exist.

### The idea

Some statements are hard to prove directly because they are about absence:
"there is no better solution", "there is no largest prime", "no comparison
sort can do better than this". **Proof by contradiction** handles them by
turning absence into presence. Assume the opposite (there is a better
solution), follow the consequences carefully, and reach a statement that is
plainly false (it is both better and not better). The assumption must have
been wrong, so the original statement is true.

The structure always has three parts. State the assumption exactly. Derive
consequences using only facts you know. Point to the contradiction, and say
which known fact it violates. If you cannot point to a precise
contradiction, you do not have a proof, only a feeling.

The standard example, which the book also uses, is Euclid's proof that there
are infinitely many primes. Assume there are finitely many, list them all,
multiply them together and add one. That new number leaves remainder 1 when
divided by every prime in the list, so none of them divides it. But every
whole number greater than 1 has some prime factor. So it has a prime factor
not in the list, which contradicts the list being complete.

### Worked example

**Simple: Euclid, computed.** A common misreading of the proof is that the
product plus one is itself prime. It is not necessarily prime; it only has a
prime factor outside the list. Running it shows both outcomes:

```ts
const isPrime = (n: number) => {
  if (n < 2) return false;
  for (let d = 2; d * d <= n; d++) if (n % d === 0) return false;
  return true;
};
const smallestFactor = (n: number) => {
  for (let d = 2; d * d <= n; d++) if (n % d === 0) return d;
  return n;
};
const primes: number[] = [];
for (let n = 2; primes.length < 7; n++) if (isPrime(n)) primes.push(n);
for (let k = 1; k <= 7; k++) {
  const p = primes.slice(0, k), m = p.reduce((a, b) => a * b, 1) + 1;
  console.log(`${p.join('*')} + 1 = ${m}  smallest prime factor ${smallestFactor(m)}`);
}
```

```text
2 + 1 = 3  smallest prime factor 3
2*3 + 1 = 7  smallest prime factor 7
2*3*5 + 1 = 31  smallest prime factor 31
2*3*5*7 + 1 = 211  smallest prime factor 211
2*3*5*7*11 + 1 = 2311  smallest prime factor 2311
2*3*5*7*11*13 + 1 = 30031  smallest prime factor 59
2*3*5*7*11*13*17 + 1 = 510511  smallest prime factor 19
```

The first five results are prime. The sixth, 30031, equals 59 × 509, and the
seventh has 19 as a factor. In every case the smallest prime factor is not
among the primes multiplied, which is exactly what the proof claims.

**Realistic: optimality of the job rule, by contradiction.** Suppose earliest
finish first (section 1.2) is not optimal on some input. Among all such
inputs, take one with the fewest jobs. On it, the greedy first pick g is in
some optimal solution (the exchange argument). After removing g and its
clashes, the greedy rule runs on a smaller input, which by our choice of a
smallest failing input it solves optimally. So greedy's total equals one
plus the optimum on the rest, which is the optimum overall. That contradicts
"greedy is not optimal on this input". This **smallest counterexample**
pattern is induction and contradiction combined, and it is how many greedy
proofs are written.

### Step by step

Euclid's argument as a chain, each line justified by the one before:

<Flow caption="Proof by contradiction as a chain of steps. The assumption is at the top; each arrow is a deduction using only known facts; the last box clashes with a known fact, so the first box must be false." steps={[
  "Assume: the primes are exactly p1, p2, ..., pk (finitely many)",
  "Let M = p1 × p2 × ... × pk + 1, a whole number bigger than 1",
  "Dividing M by any pi leaves remainder 1, so no pi divides M",
  "Every whole number bigger than 1 has at least one prime factor",
  "So M has a prime factor q that is not any of the pi",
  "Contradiction: q is prime but not in the 'complete' list",
]} />

Notice what each line uses. Line 3 uses only arithmetic: the product is a
multiple of each pᵢ, so adding one leaves remainder one. Line 4 is a known
fact about whole numbers (it follows by induction: a number is prime, or it
splits into two smaller factors, each of which has a prime factor). Line 5
combines them. Nothing in the chain is a guess.

### Common mistake

**The mistake:** assuming the wrong negation. To prove "every input has a
solution", the opposite is "some input has no solution", not "no input has a
solution". To prove "greedy is optimal", the opposite is "on some input,
some solution beats greedy". Getting the negation wrong proves something
else entirely.

**Why it fails:** the contradiction only refutes the statement you actually
assumed. If that was not the exact opposite of your claim, the claim is
still unproved.

**The fix:** write the claim with its quantifiers spelled out ("for every
input, for every valid solution, greedy's count is at least its count") and
negate mechanically: every becomes some, and the final condition flips.

### In real systems

Contradiction arguments appear wherever engineers need impossibility
results. A lower bound such as "no comparison sort beats n log n
comparisons" (chapter 4) tells a team not to waste time trying. The
argument that two replicas cannot both accept conflicting writes during a
network split and stay consistent is the same shape: assume a system that
does all three, derive the impossible state.

In debugging, the same move is "assume the invariant held, and derive the
state we observed". If that derivation reaches something impossible, the
invariant did not hold, and you now know where to look.

## 1.7 About the War Stories

### In one sentence

The war stories are short accounts of real problems Skiena worked on, and
they exist to show the design process (misunderstanding, modelling,
redesign) rather than a finished algorithm.

### The idea

Textbooks usually present algorithms as finished objects, already correct
and already the right tool. Real work is not like that. A client describes a
problem badly; the first model is wrong; the first algorithm is too slow;
the bottleneck turns out to be somewhere unexpected. The **war stories**
scattered through Part I are the book's way of showing that process
honestly.

Each one follows a similar arc. There is a problem from outside computer
science (biology, a client's business, a game, a manufacturing line). There
is a moment of modelling, where the problem is recognised as a standard
object or a known problem. There is usually a wrong turn, and then a
lesson that generalises. The algorithms in them are not the point; the
reasoning is.

The way I read them is as worked examples of section 1.5. For every war

## 1.8 War Story: Psychic Modeling

### In one sentence

A client who believed a psychic could partly predict lottery numbers wanted
the fewest tickets that would guarantee a prize, and the story shows how a
covering problem was modelled, solved, and then had to be reconsidered
because the requirement had been misunderstood.

### The idea

Here is the story in my own words, kept to its structure. A client came to
Skiena's group with a lottery scheme. A psychic would name a handful of
numbers, more than appear on one ticket, and some of the winning numbers
were supposed to be among them. The client wanted to buy a set of tickets,
each using only the psychic's numbers, such that if enough of the winning
numbers were in the psychic's list, at least one ticket would be guaranteed
to win a prize.

The modelling move is to see tickets and predictions as **subsets**. Let the
psychic's list have n numbers, a ticket hold k of them, and suppose a prize
needs some number l of matching numbers on one ticket. Then the client needs
a family of k-subsets (tickets) such that every l-subset of the n numbers
(every way the winning numbers could fall in the list) is contained in at
least one ticket. That is a **covering** problem, and covering problems of
this kind are known and hard in general; they are related to the set cover
problem in Part II.

The group built a search for small covers. The twist in the story, which is
its lesson, is that the requirement had to be checked again: what exactly
counted as a win, and how many of the predicted numbers were assumed to be
winners, changed what had to be covered. A slightly different reading of the
rules gives a different, and differently sized, covering problem. The design
was only as good as the understanding of that sentence.

I am paraphrasing from the book's structure rather than its details; the
point Skiena draws is the one that matters. Make sure you understand the
problem, in writing, before investing in the algorithm, and recognise that
"is a ticket set like this possible, and how small?" is a question about a
standard combinatorial object.

### Worked example

**Simple: the smallest version by hand.** Five predicted numbers, tickets of
three, and a prize needs two matching numbers. There are 10 pairs among 5
numbers, and each ticket of three covers 3 pairs. So at least 4 tickets are
needed (10 / 3 rounded up), which is a **counting lower bound**. Can 4 do
it? The program below finds four.

**Realistic: a greedy cover program.** At each step, pick the ticket that
covers the most still-uncovered pairs (or triples). This is the greedy set
cover heuristic from chapter 12: not always optimal, but provably within a
logarithmic factor.

```ts
function combos(items: number[], k: number): number[][] {
  if (k === 0) return [[]];
  if (items.length < k) return [];
  const [h, ...t] = items;
  return [...combos(t, k - 1).map(c => [h, ...c]), ...combos(t, k)];
}
const key = (c: number[]) => c.join(',');
function greedyCover(n: number, k: number, l: number): number[][] {
  const pool = Array.from({ length: n }, (_, i) => i + 1);
  const need = new Set(combos(pool, l).map(key));
  const tickets = combos(pool, k), chosen: number[][] = [];
  while (need.size) {
    let best = tickets[0], gain = -1;
    for (const t of tickets) {
      const g = combos(t, l).filter(c => need.has(key(c))).length;
      if (g > gain) { gain = g; best = t; }
    }
    combos(best, l).forEach(c => need.delete(key(c)));
    chosen.push(best);
  }
  return chosen;
}
```

```text
n=5 k=3 l=2: 4 tickets (all 10 possible)
n=7 k=3 l=2: 7 tickets (all 35 possible)
n=8 k=4 l=2: 6 tickets (all 70 possible)
n=10 k=5 l=3: 19 tickets (all 252 possible)
1-2-3  1-4-5  2-3-4  2-3-5
```

For n = 5 the greedy cover meets the lower bound of 4, so it is optimal
there. For n = 7, tickets of three, pairs: there are 21 pairs, each ticket
covers 3, so the bound is 7, and greedy hits it (this is the Fano plane, a
famous perfect design where every pair is covered exactly once). For bigger
cases greedy may use more than the true minimum, and you would not know
without a smarter search or a known design table.

### Common mistake

**The mistake:** building an algorithm for your first reading of the
requirement. The word "guarantee" in the client's request carries the whole
problem: guaranteed under which assumption about the winning numbers, and
for which prize level?

**Why it fails:** an elegant solution to the wrong problem is worth nothing,
and a covering problem with slightly different parameters can need a very
different number of tickets.

**The fix:** restate the problem back to the client in the precise form of
section 1.3 (input, output property), with a tiny worked instance, and get a
yes before writing code. Skiena's broader lesson is the same: modelling is
where projects are won or lost.

### In real systems

Covering problems are everywhere once you look: choosing the fewest test
cases that exercise every pair of configuration options (pairwise or
combinatorial testing), placing the fewest monitoring probes that observe
every link, choosing cache sites that cover every region. Pairwise testing
tools use exactly this kind of covering design. The engineering lesson
carries over too: the hard conversation is agreeing on what must be covered.

## 1.9 Estimation

### In one sentence

Estimation is principled guessing: combining a few known quantities to get
an answer within a factor of ten or so, and checking it a second, independent
way, so you can tell whether a design is feasible before you build it.

### The idea

Many design questions do not need an exact answer. They need to know
whether the answer is thousands or billions. How many records will this
table hold in a year? How long will this loop take on a million inputs? How
many servers does this service need? **Estimation** answers these with a
chain of rough multiplications, each step a number you know or can defend.

Skiena's advice has two parts. First, **break the quantity into factors**
you can estimate separately: total = count × size × rate. Second, **check it
by a different route**, using different factors. If two independent
estimates agree within a factor of a few, you can trust the order of
magnitude. If they disagree badly, one of your assumptions is wrong, and
finding which is itself useful.

The habit pairs with the analysis in chapter 2. Once you know an algorithm
does about n² steps, estimation tells you what n² means on your machine: a
modern core does on the order of 10⁸ to 10⁹ simple operations per second, so
n = 10⁴ (10⁸ steps) is a fraction of a second to a second, and n = 10⁶
(10¹² steps) is hours.

### Worked example

**Simple: how fast is a loop on my machine?** Measure the base rate once,
then estimate everything else from it.

```ts
let x = 0; const N = 200_000_000; const t0 = performance.now();
for (let i = 0; i < N; i++) x = (x + i) | 0;
const ms = performance.now() - t0;
console.log(`${N.toLocaleString('en-US')} additions in ${ms.toFixed(0)} ms  ->  about ${
  (N / ms / 1e6).toFixed(2)} x 10^9 per second (x=${x})`);
```

```text
200,000,000 additions in 109 ms  ->  about 1.84 x 10^9 per second (x=-645128448)
```

That is a tight loop of the simplest operation; real code with memory
access, branches and allocation runs slower, often ten times slower. So I
use about 10⁸ "real" operations per second as my planning number. Printing
`x` stops the engine from deleting the loop as dead code, a trap of its own.

**Realistic: storage for event logs.** A service gets 2,000 requests per
second at peak, about 500 on average. Each request writes one log line of
about 400 bytes.

1. Route one, by rate: 500 per second × 86,400 seconds per day is about
   4.3 × 10⁷ lines a day. Times 400 bytes is about 1.7 × 10¹⁰ bytes, roughly
   17 GB a day, so about 6 TB a year.
2. Route two, by users: say 50,000 daily users making about 900 requests
   each (pages, assets through the API, background polling). That is
   4.5 × 10⁷ requests, close to route one. The two routes agree within a few
   percent, so 15 to 20 GB a day is a sound planning figure.

Now the design follows: a year of raw logs on one disk is uncomfortable, so
plan rotation, compression (text logs often compress several-fold) and a
retention period.

### Common mistake

**The mistake:** estimating with the peak where the average belongs (or the
reverse), or multiplying a chain of optimistic guesses. Five factors each
off by a factor of two in the same direction give an answer off by 32.

**Why it fails:** errors in a product multiply. A single estimate has no
built-in check, so a bad assumption sails through.

**The fix:** use the average for totals (storage, cost) and the peak for
capacity (servers, bandwidth). Estimate the same quantity two independent
ways. Write each factor and its source in a table, as above, so a reviewer
can find the weak one.

### In real systems

Capacity planning, cloud cost forecasts, deciding whether a dataset fits in
memory, choosing between an in-memory index and a disk-based one, and
sizing a queue are all estimation first and measurement second. The
"back-of-the-envelope" section of a design document is this section of the
book: a few rows of factors that show the design is in the right order of
magnitude.

Estimation also guards algorithm choices. If n will be 10⁷ and the obvious
algorithm is n², the estimate says 10¹⁴ steps, about eleven days at 10⁸ per
second, before a line of code is written. That single sentence decides that
a better algorithm is needed.

## From beginner to strategy

<Levels label="Chapter 1, Introduction to Algorithm Design">
<Level name="Beginner" depth={3}>

At the smallest level, this chapter says one thing: an algorithm is a
procedure that is correct on every input, and an idea that works on your
examples has not earned that name yet. Everything else in the chapter is a
tool for earning it (proof) or for losing it quickly (counterexamples).

The smallest worked version is the job-selection problem with three jobs,
done on paper. Draw a line from day 0 to day 13. Mark "left" from 0 to 6,
"right" from 7 to 13 and "bridge" from 5 to 8. Ask each rule what it picks.
Shortest first picks the bridge and is stuck at one job. Earliest finish
first picks left (ends at 6), skips the bridge (starts at 5, before 6), and
picks right: two jobs, the best possible. Three intervals on a piece of
paper and you have seen a wrong rule, a right rule, and why the difference
is not obvious.

The beginner's mistake is to take away "earliest finish first" as the lesson.
It is the answer to one problem. The lesson is the five-minute hunt that
broke shortest-first, and it transfers to every greedy idea you will ever
have. If you can explain to a friend why shortest-first fails, with the
three intervals, you have the beginner level.

</Level>
<Level name="Intermediate" depth={3}>

In a real program the pieces of the chapter combine into a routine: state
the problem exactly, write the obvious slow algorithm, write the clever fast
one, and compare them on many small inputs. The slow one is your oracle, the
clever one is your candidate, and the comparison is a property test.

```ts
// A tiny property-test harness: candidate vs oracle on random small inputs.
function check<I, O>(gen: () => I, oracle: (i: I) => O,
                     candidate: (i: I) => O, runs = 2000): I | null {
  for (let r = 0; r < runs; r++) {
    const input = gen();
    if (JSON.stringify(oracle(input)) !== JSON.stringify(candidate(input)))
      return input;                         // first failing input
  }
  return null;                              // no counterexample found
}
```

With the job code from section 1.2, `check` with a generator of random job
sets, `bruteForce` as the oracle and the shortest-first count as the
candidate returns a failing job set within a few hundred runs. The same
harness with earliest-end as the candidate returns `null`, matching the run
shown earlier (0 failures in 2,000). Add a shrinking step (remove one job at
a time while it still fails) and the harness hands you the minimal
counterexample automatically.

The intermediate mistake is comparing outputs that are allowed to differ.
Two correct job selectors can return different sets of the same size, so
compare sizes (or a canonical form, such as sorted names), not the raw sets.
Decide what "the same answer" means before you test; that is section 1.3's
precise output property again.

</Level>
<Level name="Advanced" depth={3}>

Underneath, the chapter rests on two exact proof patterns. **Induction**:
prove a base case and a step from smaller to larger, and the statement holds
for every size. **Contradiction**: assume the negation, derive something
false, conclude the statement. Greedy proofs usually combine them as an
exchange argument plus induction on the input size, or as a "smallest
counterexample" contradiction, as shown for the job rule in section 1.6.

The precise shape of an exchange argument is worth stating, because it
recurs in chapters 8 and 12. Let G be the greedy solution and O any optimal
one. Find the first place they differ. Show you can change O at that place to
agree with G without making O worse or invalid. Repeat: O turns into G one
change at a time and never gets worse, so G is optimal. The work is always
in the middle sentence, and if you cannot write it, you probably have a
heuristic.

The cost side is the other exact rule. The search spaces of the standard
objects have sizes 2ⁿ (subsets), n! (permutations) and, for many tree and
graph counts, exponential in n too. Exhaustive search is correct and its
cost is that size times the cost of checking one candidate. For job
selection that is 2ⁿ times n² overlap checks; for the tour, (n − 1)! times n.
Those products, not intuition, say when brute force is acceptable.

The advanced mistake is an exchange step that breaks validity. Swapping g in
for o is only allowed because g ends no later than o; in the weighted
version, the swap can lose value, which is precisely why that version needs
dynamic programming instead.

</Level>
<Level name="Edge cases" depth={3}>

Each of these is one boundary, with what happens and why.

- **Zero jobs.** The greedy returns an empty set, and so does brute force
  (the empty subset is the only one). Make sure `lastEnd = -Infinity` does
  not cause a problem, and that the function's return type allows an empty
  array.
- **One job.** Always selected. A one-element test is the cheapest way to
  catch a loop that starts at index 1 by mistake.
- **Touching intervals.** A job ending on day 6 and one starting on day 6.
  With half-open intervals and `j.start >= lastEnd` they are compatible;
  with closed intervals they clash, and the code must use `>`. The rule
  itself is still correct either way; only the definition of overlap moves.
- **Identical jobs.** Ten copies of (2, 5). Exactly one is chosen, because
  the second starts at 2, before the first ends at 5.
- **Zero-length jobs.** A job (4, 4) is empty under half-open intervals and
  fits anywhere, even inside another job by the overlap test. Decide
  whether such jobs are valid input; if not, reject them at the boundary.
- **One point, two points in the robot tour.** One point: the tour has
  length 0. Two points: the tour goes there and back, twice the distance.
  Code that assumes at least three points to form a cycle will divide by
  zero or index out of range here.

The edge-case mistake is to let the test suite be all medium-sized random
inputs, which almost never contain any of the above. Write these six as
explicit unit tests.

</Level>
<Level name="Corner cases" depth={3}>

Corner cases are two boundaries at once, or a boundary plus a side effect.

**Ties in end time plus a touching start.** Jobs (0, 5), (3, 5) and (5, 8).
Two jobs end at 5. Either can be chosen first; both lead to taking (5, 8)
next under half-open intervals, so the count is 2 either way. But if the
output is a list of names and a test compares names, the tie-break (input
order, since the sort is stable in JavaScript) decides which name appears.
The answer is correct; the test is fragile. Compare counts or sort names.

**Nearest neighbour with exact ties.** My line example was built on ties.
With floating-point coordinates, "equal" distances may differ in the last
bit, so the tie-break becomes accidental and platform-dependent. The same
input can produce different tours on different machines, which makes bugs
impossible to reproduce. Use integer coordinates in tests, or break ties
explicitly by index.

**Estimation with peak traffic plus a long retention period.** Using the
peak rate (2,000 per second) for a year of storage, then multiplying by a
multi-year retention, can inflate a 6 TB answer to 75 TB or more. Each
choice alone looks cautious; together they buy hardware nobody needs. Use
the average for totals, and apply caution once, explicitly, at the end.

**Recursion on an empty string plus the carry.** `increment('')` returns
`'1'`, which is correct, but `increment('111')` relies on that same base
case being reached after three carries. If someone "optimises" the base case
to return `''` for empty input, every all-ones number silently loses its top
bit: '111' becomes '000'. One base case, two different paths through it.

The corner-case mistake is treating these as unlikely. They are exactly the
inputs that appear in real data: tie-heavy schedules, rounded coordinates,
and the maximum value of a counter.

</Level>
<Level name="Production level" depth={3}>

When this runs for real, for other people, three things change: sizes are
larger, inputs are adversarial or structured, and nobody reads the code
before trusting the result.

**Name what you have shipped.** If the routing service uses nearest
neighbour, the API documentation and the code should say "heuristic" and
give a measured quality figure, such as "on last month's routes, within 15
percent of a lower bound". Teams get into trouble when a heuristic is
silently treated as optimal and someone builds a billing rule on top of it.

**Keep the oracle.** The brute-force solver from development is a production
asset. Run it nightly on a sample of small real instances and alert when the
fast algorithm disagrees (for exact algorithms) or drifts in quality (for
heuristics). This is the property test from the intermediate level, moved
into monitoring.

**Watch the exponent.** Anything that enumerates subsets or permutations of
a user-controlled input is a denial-of-service risk: someone submits 40
items instead of 10, and the request takes years. Put a hard limit on n at
the boundary, and fall back to a heuristic above it.

**Estimate before deploying.** A one-line estimate (rate × size × time) in
the pull request description catches the n² loop over a table that will
have ten million rows next year. The production mistake is discovering that
from a paging alert instead.

</Level>
<Level name="Mindset" depth={3}>

The habit this chapter teaches is **adversarial doubt**: before trusting an
idea, spend a few minutes as its enemy. Ask what the rule is greedy about,
build the smallest input where that greed misleads it, and only then start
to believe it.

This shows up far outside algorithms. A caching rule ("cache everything for
an hour") has a counterexample (a price that changes every minute). A rate
limit ("100 requests per minute per user") has one (a shared office IP). A
product metric ("more clicks means more satisfaction") has one (a confusing
page that needs more clicks). The same five-minute hunt, using the same
techniques of ties and extremes, finds them.

The second habit is **naming**: ask which standard object a problem is
about before inventing anything. It is a humility move. Most problems have
been met before, and a name points straight to what is known, including
what is known to be hard.

The mindset mistake is to treat doubt as negativity. The point of breaking
your own idea is to do it in five minutes at a desk instead of in five weeks
in production; it is the cheapest form of progress there is.

</Level>
<Level name="System design" depth={3}>

Take a concrete system: a delivery company's daily route planner. Each
morning it receives a few thousand stops, assigns them to vans, and orders
each van's stops. This chapter's ideas sit at every layer.

**Problem statement.** "Good routes" must become a precise objective: total
driving time, subject to van capacity and delivery time windows, with a
stated tie-breaker. Without that, two teams will optimise different things.

**Modelling.** Assigning stops to vans is a partition of a set; ordering
each van's stops is a permutation of points: the robot tour, with
constraints. Recognising the tour as the travelling salesman problem means
nobody wastes a quarter searching for an exact fast method.

**Algorithm choice.** Exact search for small vans (a dozen stops), a
construction heuristic plus local improvement for larger ones, and a lower
bound for every route so quality is measurable.

**Estimation.** Three thousand stops, forty vans, two minutes of compute
budget: the estimate decides how many local-improvement passes fit, and
whether a single machine is enough.

The design mistake is to treat the solver as a black box and the constraints
as an afterthought. Time windows and capacities change which algorithms
apply; they belong in the model from day one.

</Level>
<Level name="Strategy" depth={3}>

How I learn this chapter, and how I know I have.

First, I re-run everything on this page and break things on purpose: swap
earliest-end for shortest-first and watch the property test find a failure;
change the half-open overlap test to a closed one and see which outputs
move. Second, I keep a **counterexample notebook**: every greedy idea I meet
during phase 4, with either its counterexample (smallest input, both
answers) or its exchange argument. Third, I take five real problems from my
own work and write each in the section 1.3 form, then name its object from
the section 1.5 table.

To check I have it, I give myself unseen greedy rules and a timer: "largest
coin first for coins 1, 7 and 10", "always take the cheapest edge out of the
current city", "schedule the job with the fewest conflicts first". For each
I either break it within five minutes or sketch why it holds. (The coins one
breaks at 14: greedy uses 10 and four 1s, five coins, against 7 + 7.)

Done when I can break three unseen greedy rules with minimal
counterexamples in under five minutes each, write the exchange proof for
earliest finish first from memory, and estimate a storage figure two
independent ways that agree within a factor of two.

</Level>

## Questions people ask

**If heuristics can be wrong, why does anyone use them?** Because for many
important problems (the robot tour among them) no algorithm is known that is
both correct and fast. A heuristic that is fast and usually good, with its
quality measured, beats an exact method that never finishes. The sin is not
using a heuristic; it is not knowing you are using one.

**How do I know when to stop looking for a counterexample and start a
proof?** When you have tried every input shape at sizes 2, 3 and 4, plus
ties and extremes, and nothing breaks, the rule is worth a proof attempt.
Often the proof attempt itself shows where a counterexample hides, at the
step you cannot justify.

**Is greedy ever optimal, or is it always a trap?** Greedy is optimal for a
specific set of problems: interval scheduling, minimum spanning trees
(chapter 8), Huffman coding and a few others. The common thread is an
exchange argument. Without one, assume greedy is a heuristic.

**Do I need formal proofs at work?** Rarely written out. But the habit of
asking "what is the invariant, and what is the counterexample?" is used in
every design review and code review, and it is what separates the engineers
whose systems do not surprise them.

**Why is the travelling salesman problem in the first chapter?** Because it
is the clearest example of a problem that looks easy, has tempting simple
rules, and is in fact hard. Meeting it first sets the expectation that
"obvious" is not evidence.

**What is the difference between modelling and abstraction?** Abstraction
is removing detail. Modelling is removing detail so that what remains is a
known object with known algorithms. The second is the useful one.

**How accurate does an estimate need to be?** Within a factor of about ten
is usually enough to choose between designs. If two options differ by less
than that, the estimate cannot decide between them, and you measure instead.

## Key takeaways

- An algorithm is correct on every input; an idea that works on your
  examples is a heuristic until proven.
- The robot tour is the travelling salesman problem: simple rules fail, and
  the correct method is exponential.
- For interval scheduling, earliest finish first is optimal, proved by an
  exchange argument, while earliest start and shortest first are not.
- A good counterexample is small and verifiable; find it by thinking small,
  exhaustively, at the weakness, at ties and at extremes.
- Induction proves recursive and incremental algorithms: check the base
  case, trust the recursive call, check the combine.
- Proof by contradiction proves optimality and impossibility; negate the
  claim carefully.
- Model every problem as a permutation, subset, tree, graph, point set,
  polygon or string, and use the name to find known solutions.
- Each standard object shrinks recursively, which is what most design
  techniques exploit.
- Confirm the exact requirement before building, as the psychic war story
  shows.
- Estimate by multiplying defensible factors, and check by an independent
  route.

## Glossary

- **Algorithm:** a procedure that halts with the correct output on every
  valid input.
- **Heuristic:** a procedure that usually gives a good answer, with no
  guarantee.
- **Instance:** one particular input to a problem.
- **Counterexample:** an instance on which a procedure gives a wrong answer.
- **Greedy algorithm:** builds a solution by repeatedly taking the choice
  that looks best now, never undoing it.
- **Exchange argument:** a proof that a greedy choice can replace part of an
  optimal solution without making it worse.
- **Exhaustive search:** trying every candidate solution; correct but often
  exponentially slow.
- **Travelling salesman problem (TSP):** find the shortest closed tour
  visiting every point once.
- **Interval scheduling:** choose the most non-overlapping intervals.
- **Half-open interval:** [start, end), including the start and excluding
  the end, so touching intervals do not overlap.
- **Induction:** proving a statement for all sizes from a base case and a
  step from smaller to larger.
- **Inductive hypothesis:** the assumption, in the step, that the statement
  holds for smaller sizes.
- **Proof by contradiction:** assuming the opposite of a claim and deriving
  something impossible.
- **Modelling:** restating a problem in terms of a standard object.
- **Permutation:** an ordering of items.
- **Subset:** a selection of items from a set.
- **Covering problem:** choosing sets so that every required element is in
  at least one of them.
- **Lower bound:** a value the answer provably cannot go below.
- **Estimation:** combining rough known quantities to get an
  order-of-magnitude answer.
- **Oracle:** a slow but trusted implementation used to check a fast one.

**Self-check**

<details>
<summary>1. What is the difference between an algorithm and a heuristic?</summary>

An algorithm is correct on every input. A heuristic usually gives good
answers but has no guarantee; one counterexample does not refute it as a
heuristic, but it does show it is not an algorithm for the problem.

</details>

<details>
<summary>2. Why does nearest neighbour do badly on points that double in distance on a line?</summary>

Each step's nearest unvisited point is on the opposite side of the start, so
the tour crosses back and forth with ever longer swings, instead of sweeping
once each way.

</details>

<details>
<summary>3. State the greedy rule that is optimal for interval scheduling, and the key step of its proof.</summary>

Take jobs in order of earliest end, skipping any that clash. Key step: the
earliest-ending job can replace the first job of any optimal solution,
because it ends no later and so clashes with none of the rest.

</details>

<details>
<summary>4. Give five counterexample-hunting techniques.</summary>

Think small, think exhaustively, hunt for the weakness, go for a tie, seek
extremes.

</details>

<details>
<summary>5. What are the two parts of an induction proof, and what do they correspond to in a recursive function?</summary>

The base case (the function's base case) and the inductive step (the work
around the recursive call, assuming the call on a smaller input is correct).

</details>

<details>
<summary>6. Name the seven standard objects of section 1.5.</summary>

Permutations, subsets, trees, graphs, points, polygons and strings.

</details>

<details>
<summary>7. Brute force over subsets is fine for 20 items; why not brute force over permutations?</summary>

2²⁰ is about a million subsets, which is instant. 20! is about 2.4 × 10¹⁸
permutations, which would take decades.

</details>

<details>
<summary>8. Why should two estimates of the same quantity use different routes?</summary>

So that their errors are independent. Agreement then means the order of
magnitude is right; disagreement exposes a bad assumption.

</details>
