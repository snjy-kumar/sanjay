This chapter answers one question: what does it take to know that a
statement is true for every case, not just the ones you tried? It builds the
vocabulary (propositions, predicates, axioms) and the four proof shapes that
every later chapter of the book uses. If you write software, this is the
difference between "the tests pass" and "it cannot go wrong".

## Before you start

**After this chapter you will be able to:**

- Tell a proposition (a statement that is true or false) from a statement that is not one, and say why the difference matters.
- Turn an English claim with "for all" or "there exists" into a precise predicate statement you can check or prove.
- Prove an implication directly, prove its contrapositive, and prove an "if and only if" in both directions.
- Split a proof into cases without leaving a gap, and run a proof by contradiction without fooling yourself.
- Read a proof critically and spot the step where a bogus proof cheats.

**What you should already know:** school algebra (expanding brackets,
moving terms across an equals sign), what an integer and a prime are, and

## 1.1 Propositions

### In one sentence

A proposition is a statement that is definitely either true or false, and
mathematics only tries to prove propositions.

### The idea

Start with what we want: a way to be certain. Certainty only makes sense for
statements that have a fixed truth value. "2 + 3 = 5" is true. "1 + 1 = 3"
is false. Both are **propositions**: statements that are either true or
false, with no third option.

Plenty of sentences are not propositions. A question ("Is it raining?") is
neither true nor false. A command ("Close the door") is neither. A statement
whose truth changes with the moment ("It is five o'clock") is not a single
proposition either, because it is true at five and false at six. Proof is
the tool for statements that stay put.

The hard part is that being a proposition does not tell you *which* truth
value it has. "Every even number greater than 2 is a sum of two primes" is a
proposition (it is either true or false), and nobody has managed to prove or
refute it. Knowing the type of a statement is step one; finding its value is
the work.

The chapter's first warning is the most useful one in the whole book:
**checking many cases does not prove a statement about infinitely many.**
A claim that holds for the first forty integers can fail at the forty-first.
Experiments suggest; proofs decide.

### Worked example

**Simple: a polynomial that looks prime-producing.** Take p(n) = n² + n + 41.
For n = 0 it gives 41, prime. For n = 1, 43, prime. For n = 2, 47, prime.
Keep going and every value up to n = 39 is prime. It is very tempting to
claim "p(n) is prime for every non-negative integer n".

The claim is false, and the first counterexample is easy to find by machine:

```ts
const isPrime = (n: number): boolean => {
  if (n < 2) return false;
  for (let d = 2; d * d <= n; d++) if (n % d === 0) return false;
  return true;
};
const p = (n: number) => n * n + n + 41;
let n = 0;
while (isPrime(p(n))) n++;
console.log(`first failure at n = ${n}, p(n) = ${p(n)} = 41 * ${p(n) / 41}`);
```

```text
first failure at n = 40, p(n) = 1681 = 41 * 41
```

You could have seen it without a computer: at n = 40, p(40) = 40² + 40 + 41
= 40 × (40 + 1) + 41 = 40 × 41 + 41 = 41 × 41. The structure of the formula
hands you the factor. Forty successes told you nothing about case forty-one.

**Realistic: a claim about a cache.** Suppose a teammate says "our cache key
function never collides; I hashed a million random user ids and got a
million distinct keys". That is a proposition about every possible id, and a
million samples cannot settle it. If the key is a 32-bit hash, the
pigeonhole principle (chapter 14) says collisions *must* exist once there are
more than about four billion ids. The sample was evidence, not proof.

### Step by step

Here is the reasoning that p(40) is composite, one line at a time, so you
can see that every step is forced.

  ["1", "p(40) = 40² + 40 + 41", "the definition of p, with n replaced by 40"],

Notice that a single counterexample is a complete proof that the universal
claim is false. Refuting "for all" takes one witness. Establishing it takes
an argument that covers every case at once.

### Common mistake

**The wrong way:** "I checked it for n = 1 to 1000 and it held, so it is
true." This fails because a property can hold for a long run and then stop.
The polynomial above holds for forty values. There are famous claims in
number theory that hold for every value anyone has ever computed and are
known to fail eventually.

**The fix:** treat case-checking as a search for counterexamples. If the
search finds one, you are done: the claim is false. If it finds none, you
have a conjecture, and you still owe a proof. Write the word "conjecture" in
your notes until you have one.

### In real systems

This is the gap between testing and verification. A test suite checks
chosen inputs; a type checker, a model checker or a proof assistant checks
every input of a given shape. Teams that ship distributed databases often
model-check their protocols for exactly this reason: the bug that matters
lives in the interleaving nobody thought to test.

Property-based testing tools such as fast-check sit in between. They state a
proposition ("for every list, sorting twice equals sorting once") and search
hard for a counterexample. Finding one is a proof the property is false;
finding none is evidence, which is why such tools print how many cases they
tried.

### Check yourself

1. Is "x + 1 = 5" a proposition?
2. Is "There are infinitely many primes" a proposition, even before you know a proof?

<details>
<summary>Answer</summary>

1. Not on its own. Its truth depends on x, so it is a predicate (next section). It becomes a proposition once x is fixed, or once it is wrapped in "for all x" or "there exists x".
2. Yes. It is definitely true or false; being a proposition is about having a truth value, not about our knowing it. (It is true, and chapter 8's ideas prove it.)

</details>

## 1.2 Predicates

### In one sentence

A predicate is a proposition with a blank in it, and filling the blank, or
quantifying over it, turns it back into a proposition.

### The idea

Most interesting statements are about a variable. "n is prime" is neither
true nor false until you say which n. Such a statement is a **predicate**: a
function from values to truth values. Writing it P(n) makes the blank
explicit. P(7) is true; P(8) is false.

You turn a predicate into a proposition in two ways. You can **substitute** a
value, as above. Or you can **quantify** it. "For all n, P(n)" claims P holds
for every n in some domain. "There exists an n such that P(n)" claims at
least one n works. The symbols are ∀ ("for all") and ∃ ("there exists").

The **domain** (the set of values the variable ranges over) is part of the
statement. "For all x, x² ≥ 0" is true over the real numbers and false over
the complex numbers, where i² = −1. Leaving the domain unstated is one of the
most common sources of confused proofs.

In code you already use predicates daily. Any function that returns a
boolean is one. `Array.prototype.every` is the universal quantifier over a
finite domain, and `Array.prototype.some` is the existential one.

### Worked example

**Simple:** let P(n) mean "n² + n + 41 is prime", over the non-negative
integers. Then P(0) is true, P(40) is false, "∃n. P(n)" is true (n = 0 is a
witness) and "∀n. P(n)" is false (n = 40 is a counterexample).

```ts
const P = (n: number) => isPrime(n * n + n + 41);
const domain = [...Array(100).keys()];   // 0..99, a finite stand-in
console.log(domain.some(P), domain.every(P));
```

```text
true false
```

**Realistic: an access-control rule.** "Every admin can delete any post"
reads as ∀u. ∀p. (Admin(u) → CanDelete(u, p)). Written that way, three
questions jump out that the English hid. What is the domain of u (all users,
or only active ones)? Does "any post" include posts in archived workspaces?
And is the rule claiming more than the code enforces? Writing the predicate
is how you find the ambiguity before a security review does.

<Figure art={`
   predicate            substitute a value         quantify the variable
  +-----------+         +---------------+         +----------------------+
  |  P(n)     |  n=7    |  P(7)  true   |   or    | for all n: P(n)      |
  | "n is     | ------> +---------------+ ------> | there is n: P(n)     |
  |  prime"   |                                   +----------------------+
  +-----------+      both results are propositions: true or false
`} caption="A predicate is not yet true or false. Follow either arrow, substituting or quantifying, and you get a proposition." />

### Step by step

How to negate a quantified statement, which you will do in every proof by
contradiction. Take "every request finishes within 2 seconds":
∀r. Fast(r).

<Trace columns={["step", "statement", "reason"]} rows={[
  ["1", "not (for all r, Fast(r))", "we want the claim to be false"],
  ["2", "there is an r with not Fast(r)", "'not all are fast' means 'some one is not fast'"],
  ["3", "there is an r that takes longer than 2 s", "unfold the meaning of not Fast"],
]} caption="Negation swaps the quantifier and pushes 'not' inside. The same rule turns 'not (there exists)' into 'for all ... not'." />

The general rule: ¬∀x. P(x) is the same as ∃x. ¬P(x), and ¬∃x. P(x) is the
same as ∀x. ¬P(x). Chapter 3 proves these; for now, check them against the
English and they will feel obvious.

### Common mistake

**The wrong way:** swapping the order of mixed quantifiers. "For every
request there is a server that can handle it" (∀r. ∃s. Handles(s, r)) is not
the same as "there is a server that can handle every request"
(∃s. ∀r. Handles(s, r)). The first allows a different server per request;
the second demands one super-server.

**The fix:** read the quantifiers left to right as a game. The "for all"
player picks first and the "there exists" player responds. Swapping their
order changes who has to commit first, and therefore what is claimed.

### In real systems

Database queries are predicates over a domain of rows. `WHERE` is a
predicate, `EXISTS` is ∃, and "for all" is usually written as
`NOT EXISTS (... NOT ...)`, which is exactly the negation rule above. SQL
also has a third truth value, NULL, which is why `WHERE x <> 5` silently
drops rows where x is NULL: the predicate is neither true nor false there,
and only true rows survive.

### Check yourself

1. Negate "there is a test that every build passes".
2. Over the domain of integers, is ∃x. x + 1 = x true?

<details>
<summary>Answer</summary>

1. "For every test, some build fails it": ∀t. ∃b. ¬Passes(b, t).
2. False. Subtracting x from both sides gives 1 = 0, so no integer is a witness.

</details>

## 1.3 The Axiomatic Method

### In one sentence

A proof starts from a small set of statements accepted without proof, the
axioms, and every other truth is derived from them by logical steps.

### The idea

If every claim needed a proof, and every proof used earlier claims, you
would go backwards forever. Something has to come first. The **axiomatic
method**, which goes back to Euclid's geometry, picks a handful of
statements, the **axioms**, and accepts them as the starting point.
Everything else must be derived.

A **proof** is then a sequence of statements in which each one is an axiom,
an earlier proved statement, or follows from earlier lines by a **logical
deduction** (an inference rule that cannot turn truths into falsehoods). The
last statement is the thing proved.

Proved statements get names by their role. A **theorem** is an important
one. A **lemma** is a stepping stone toward a theorem. A **corollary**
follows quickly from a theorem. These are labels for readers, not different
kinds of truth.

Two properties of an axiom system matter. **Consistency** means you cannot
prove both a statement and its negation. **Completeness** means every true
statement can be proved. You want both, and the twentieth century's big
surprise (Gödel) was that rich enough systems cannot have both. For daily
mathematics this does not bite, but it is worth knowing that "provable" and
"true" are not literally the same word.

### Worked example

**Simple:** from the axioms of arithmetic you derive "a × 0 = 0". You do not
assume it; you get it from distributivity: a × 0 = a × (0 + 0) = a × 0 +
a × 0, and subtracting a × 0 from both sides leaves 0 = a × 0. Every step
used an accepted rule.

**Realistic: a type system is an axiom system.** TypeScript's checker starts
from rules (a number literal has type `number`; if `f` takes `string` and
returns `boolean`, then `f(s)` has type `boolean` when `s` is a `string`) and
derives the type of every expression. When it rejects your program, it
failed to find a derivation. When `as any` appears, someone added an axiom,
and like any extra axiom it can make the system inconsistent: you can now
"prove" that a number is a string.

  { name: "Lemmas", note: "proved stepping stones" },
  { name: "Logical deductions", note: "rules that preserve truth, such as modus ponens" },

### Step by step

The most used inference rule is **modus ponens**: from P, and from "if P
then Q", conclude Q. Here is a derivation using only it.

### Common mistake

**The wrong way:** affirming the consequent. From "if P then Q" and "Q",
concluding "P". If it rained, the street is wet; the street is wet; so it
rained. But a burst pipe also wets streets. This is not a valid deduction:
it can lead from true premises to a false conclusion.

**The fix:** before using a step, ask "could the premises be true and the
conclusion false?" If yes, the step is not a deduction. The only valid
moves are the ones where that is impossible.

### In real systems

Proof assistants such as Lean, Coq and Isabelle are the axiomatic method run
by a machine. They accept a small trusted kernel of rules and check that
every step of a proof uses one of them. Verified software, such as the
CompCert C compiler and the seL4 microkernel, was built this way: the proof
is a long chain of steps each checked against the kernel.

### Check yourself

1. Why can't every statement be proved from earlier statements, with no axioms?
2. From "if the cache is warm, the request is fast" and "the request is slow", what can you validly conclude?

<details>
<summary>Answer</summary>

1. The chain would have to go back forever or loop. Axioms are where it stops.
2. That the cache is not warm. This is modus tollens: from "if P then Q" and "not Q", conclude "not P". It is valid because if P were true, Q would be too.

</details>

## 1.4 Our Axioms

### In one sentence

Instead of a tiny formal axiom list, the book lets you assume all familiar
facts about numbers and logic, and asks you to be precise about everything
else.

### The idea

A fully formal axiom system for arithmetic exists (the Peano axioms, and set
theory below them), but proofs from it are long and unreadable. The book
makes a practical choice: **you may assume the ordinary facts of algebra and
arithmetic** about integers, rationals and reals, plus the usual rules of
logical reasoning. What you may not do is assume the thing you are trying to
prove, or a fact that is just as hard.

This is a judgement call, and the judgement is "would a careful reader
accept this step without further argument?" Expanding (a + b)² is fine.
"Every even number above 2 is a sum of two primes" is not, because that is an
open problem.

The book names one rule of logic explicitly. If P implies Q, and Q implies
R, then P implies R. This is **transitivity of implication**, and chained
implications are the backbone of almost every proof.

### Worked example

**Simple:** to prove "if n is even, n + 2 is even", you may use without
comment that an even number is 2k for an integer k, that 2k + 2 = 2(k + 1),
and that k + 1 is an integer. Those are familiar facts.

**Realistic:** you are proving a rate limiter never lets through more than
100 requests per minute. You may assume integer addition does not overflow
*in the mathematics*, but your code runs in 64-bit floats or 32-bit ints.
The proof's axioms and the machine's arithmetic differ, and the honest proof
states that assumption: "counts stay below 2⁵³, so floating-point addition
is exact". Choosing your axioms includes choosing what the machine
guarantees.

### Step by step

Using transitivity to chain three facts about a deploy:

  ["1", "if the schema migration ran, the column exists", "migration semantics"],

### Common mistake

**The wrong way:** "assuming" a fact that is really the theorem in disguise.
Asked to prove that the square root of 2 is irrational, someone writes "√2 =
1.41421356... which does not repeat, so it is irrational". Non-repeating
decimals *are* the definition of irrational; the step assumed the answer.

**The fix:** when you lean on a "familiar fact", ask whether it is easier than
the claim. If it is the claim restated, it is not allowed.

### In real systems

Every system design document has axioms, usually unwritten: "the clock is
roughly synchronised", "the network eventually delivers", "disks do not lie
about fsync". Outages often trace back to an axiom that was false in
production. Writing them down, in a section called "Assumptions", is the
engineering version of this section.

### Check yourself

1. May you assume "if a × b = 0 then a = 0 or b = 0" for integers?

1. Yes: it is a standard fact of integer arithmetic. (It fails in some other number systems, such as arithmetic modulo 6, where 2 × 3 = 0. Chapter 8 returns to this.)
2. Because every guarantee you prove rests on them; if one is false in production, the guarantee is void, and you want to know which ones to monitor.

</details>

## 1.5 Proving an Implication

### In one sentence

To prove "if P then Q", either assume P and derive Q, or assume Q is false
and derive that P is false.

### The idea

An **implication** "P implies Q" (written P → Q) makes a promise: whenever P
holds, Q holds too. It promises nothing when P is false. So the only way it
can be false is P true and Q false. The truth table makes this concrete:

```ts
const implies = (p: boolean, q: boolean): boolean => !p || q;
for (const p of [true, false])
  for (const q of [true, false])
    console.log(`P=${p ? 'T' : 'F'} Q=${q ? 'T' : 'F'}  P->Q=${implies(p, q) ? 'T' : 'F'}`);
```

```text
P=T Q=T  P->Q=T
P=T Q=F  P->Q=F
P=F Q=T  P->Q=T
P=F Q=F  P->Q=T
```

The last two rows surprise people. "If pigs fly, then 1 = 2" is true,
because pigs do not fly, so the promise is never tested. A broken promise
needs P to happen and Q to fail.

That gives the first method. **Method 1, the direct proof:** write "Assume
P." Then reason, step by step, until you reach Q. Because you only need to
rule out the one bad row (P true, Q false), you may take P as given.

The second method uses the **contrapositive**. The statement "if not Q, then
not P" is logically the same as "if P, then Q": both are false in exactly
the row P true, Q false. **Method 2, prove the contrapositive:** write
"Assume not Q", and derive "not P". Use it when "not Q" gives you more to
work with than P does.

Do not confuse the contrapositive with the **converse**, "if Q then P". The
converse is a different statement and can be false when the original is
true.

<Compare caption="The original and its contrapositive always agree. The converse and the inverse agree with each other, but not necessarily with the original." left="Same meaning as P → Q" right="Different meaning" rows={[
  ["P → Q (original)", "Q → P (converse)"],
  ["¬Q → ¬P (contrapositive)", "¬P → ¬Q (inverse)"],
  ["'if it is a square, it is a rectangle'", "'if it is a rectangle, it is a square' (false)"],
]} />

### Worked example

**Simple, direct proof.** Claim: if n is an odd integer, then n² is odd.

Assume n is odd. Then n = 2k + 1 for some integer k. So n² = 4k² + 4k + 1 =
2(2k² + 2k) + 1. The number 2k² + 2k is an integer, call it m, so n² = 2m +
1, which is odd. Done.

**Simple, contrapositive.** Claim: if n² is even, then n is even. A direct
attack is awkward: "n² = 2k" does not obviously tell you about n. The
contrapositive is "if n is not even (so odd), then n² is not even (so odd)",
which is exactly what we just proved. So the claim is proved too.

**Realistic: an inequality from the book's style of problem.** Claim: for
every real x with 0 ≤ x ≤ 2, the quantity −x³ + 4x + 1 is positive. A direct
proof factors the main part: −x³ + 4x = x(2 − x)(2 + x). Each factor is
non-negative when x is between 0 and 2: x is at least 0, 2 − x is at least
0, and 2 + x is positive. A product of non-negative numbers is
non-negative, so −x³ + 4x ≥ 0, and adding 1 makes it at least 1, which is
positive.

You can sanity-check with code, and seeing the minimum land at the ends is a
useful confirmation that the boundaries were the risky points:

```ts
let min = Infinity, at = 0;
for (let i = 0; i <= 2000; i++) {
  const x = i / 1000, v = -(x ** 3) + 4 * x + 1;
  if (v < min) { min = v; at = x; }
}
console.log(min, at);
```

```text
1 0
```

The minimum value 1 appears at x = 0 (and again at x = 2), exactly where a
factor of the product becomes zero.

### Step by step

The direct proof that n odd implies n² odd, one line at a time.

<Trace columns={["line", "statement", "why"]} rows={[
  ["1", "assume n is odd", "Method 1: take P as given"],
  ["2", "n = 2k + 1 for some integer k", "definition of odd"],
  ["3", "n² = (2k + 1)²", "square both sides of line 2"],
  ["4", "n² = 4k² + 4k + 1", "expand the square"],
  ["5", "n² = 2(2k² + 2k) + 1", "factor 2 out of the first two terms"],
  ["6", "m = 2k² + 2k is an integer", "integers are closed under + and ×"],
  ["7", "n² = 2m + 1, so n² is odd", "definition of odd, read backwards"],
]} caption="Line 1 assumes P, line 7 reaches Q. Lines 2 and 7 both use the definition of 'odd', once to unpack it and once to pack it back up." />

That unpack, compute, repack rhythm is the shape of most direct proofs:
replace each defined word by its definition, do algebra, and recognise the
definition of the goal at the end.

### Common mistake

**The wrong way:** proving the converse by accident. Asked to show "if n² is
even then n is even", someone writes "assume n is even, n = 2k, so n² = 4k²
is even". That proves "n even implies n² even", the converse. It is true,
but it is not what was asked.

**The fix:** before writing anything, copy the claim into the form "Assume
____. Show ____." Then check that your first line matches the first blank
and your last line matches the second.

### In real systems

Guard clauses are contrapositive reasoning in code. A function that must
return a valid user "if the token is valid" is usually written as "if the
token is not valid, return an error early". Each early return handles ¬Q
paths, so the main path can rely on P. Code review questions like "what
happens if this is null?" are requests to prove an implication's
contrapositive.

## 1.6 Proving an "If and Only If"

### In one sentence

"P if and only if Q" means P and Q are always both true or both false, and
you usually prove it as two implications, one each way.

### The idea

"P if and only if Q" (written P ↔ Q, and often "iff") says the two
statements are **equivalent**: knowing either one tells you the other. It is
the same as "P implies Q, and Q implies P". So the first method is simply
**prove each direction separately**, each as an implication.

The second method is a **chain of iffs**. If you can rewrite P into an
equivalent statement, then into another, and so on until you reach Q, with
every link an equivalence, then P ↔ Q. This is elegant but dangerous: every
single link must be reversible. One step that only works forwards breaks the
whole chain.

Definitions are almost always iffs, even when written "if". "A number is
even if it is divisible by 2" means *if and only if*. This convention is
worth knowing because it explains why you can unpack a definition in either
direction.

### Worked example

**Simple: two directions.** Claim: an integer n is even iff n² is even.

- (→) If n is even, n = 2k, so n² = 4k² = 2(2k²), which is even.
- (←) If n² is even, then n is even. This is the contrapositive result from
  section 1.5.

Both directions are proved, so the iff is proved. Checking numerically is a
good habit, and so is checking an iff that should *fail*:

```ts
const even = (n: number) => n % 2 === 0;
let agree = 0;
for (let n = -1000; n <= 1000; n++) if (even(n * n) === even(n)) agree++;
console.log(`n*n even <=> n even held for ${agree} of 2001 integers`);
const counter = [...Array(50).keys()].find((n) => (n % 4 === 0) !== (n % 2 === 0));
console.log(`n divisible by 4 <=> n even fails first at n = ${counter}`);
```

```text
n*n even <=> n even held for 2001 of 2001 integers
n divisible by 4 <=> n even fails first at n = 2
```

The second line shows a one-way implication: divisible by 4 implies even,
but 2 is even and not divisible by 4.

**Realistic: a chain of iffs about the standard deviation.** The book uses a
chain like this: the standard deviation of a list of numbers is zero iff
every number equals the mean. Here is the chain in my words. The standard
deviation is zero iff its square, the variance, is zero (square roots of
non-negative numbers are zero only at zero). The variance is the average of
the squared distances from the mean; an average of non-negative numbers is
zero iff each of them is zero; a square is zero iff the number squared is
zero; and a distance from the mean is zero iff the value equals the mean.
Every link works in both directions, so the chain proves the iff.

  "standard deviation = 0",
  "variance = 0",
  "average of squared gaps = 0",
  "every squared gap = 0",
  "every value = the mean",
]} />

### Common mistake

**The wrong way:** a chain where one step is one-way. "x = 2 iff x² = 4
iff ..." The first link is false backwards: x² = 4 also when x = −2. Any
chain through squaring, dividing by something that could be zero, or taking
absolute values is suspect.

**The fix:** at each "iff", ask "does the step reverse?" If you are not sure,
prove the two directions separately instead. It is longer and safer.

### In real systems

Iffs are what make a cache or an index correct. A cache is correct iff
"key in cache" exactly matches "value computed and still valid". A one-way
version (everything in the cache is valid, but valid values may be missing)
is fine for performance. The other one-way version (everything valid is in
the cache, but some entries are stale) is a correctness bug. Knowing which
direction your system guarantees is the difference.

## 1.7 Proof by Cases

### In one sentence

Split all possibilities into a few groups that together cover everything,
prove the claim in each group, and the claim holds everywhere.

### The idea

Some claims resist one uniform argument but become easy once you know a
little more. "n² + n is even" for every integer n is a good example: if you
knew whether n was even or odd, it would be a one-liner. **Proof by cases**
makes that knowledge free. You list cases that are **exhaustive** (every
possibility falls into at least one) and prove the claim in each.

The cases need not be exclusive, but they must be exhaustive. Overlap only
costs you duplicate work; a missing case is a hole in the proof. The most
reliable splits come from a definition with exactly two outcomes: even or
odd, zero or not zero, P or not P.

A good case split also uses what each case gives you. In the "n even" case
you get n = 2k; in the "n odd" case you get n = 2k + 1. If a case does not
give you new information you use, it was probably not the right split.

### Worked example

**Simple:** Claim: n² + n is even for every integer n.

- Case 1, n even: n = 2k, so n² + n = 4k² + 2k = 2(2k² + k), even.
- Case 2, n odd: n = 2k + 1, so n² + n = (2k + 1)(2k + 2) = 2(2k + 1)(k + 1), even.

Every integer is even or odd, so the cases are exhaustive and the claim is
proved. (A slicker proof: n² + n = n(n + 1), a product of two consecutive
integers, one of which is even. That is itself a case argument, folded
into a sentence.)

**Realistic: the party problem.** Claim: among any six people, there are
three who all know each other or three who are all strangers to each other.
Model each pair as an edge coloured "know" or "strangers". Pick one person,
A. A has five relationships, so by counting at least three of them have the
same colour (five things into two colours cannot all be at most two).

- Case 1: A knows at least three people, say B, C, D. If any two of B, C, D
  know each other, they and A form a "know" triangle. If none do, B, C, D
  are three mutual strangers.
- Case 2: A is a stranger to at least three people. The same argument with
  the colours swapped gives the conclusion.

The cases are exhaustive by the counting step. Code can confirm the claim
the brute-force way, and that six is the smallest size where it holds:

```ts
// Colour the 15 pairs of 6 people in every possible way (2^15 ways).
const edges: [number, number][] = [];
for (let i = 0; i < 6; i++) for (let j = i + 1; j < 6; j++) edges.push([i, j]);
const bit = (m: number, i: number, j: number) =>
  (m >> edges.findIndex(([a, b]) => a === i && b === j)) & 1;
const mono = (m: number, n: number) => {
  for (let a = 0; a < n; a++) for (let b = a + 1; b < n; b++)
    for (let c = b + 1; c < n; c++)
      if (bit(m, a, b) === bit(m, a, c) && bit(m, a, c) === bit(m, b, c)) return true;
  return false;
};
let bad = 0;
for (let m = 0; m < 1 << 15; m++) if (!mono(m, 6)) bad++;
console.log(`colourings of 6 people with no triangle: ${bad}`);
```

```text
colourings of 6 people with no triangle: 0
```

Running the same search for five people finds 12 colourings with no
one-colour triangle (the pentagon pattern and its relabellings), so five
people are not enough. The proof explains *why* six works; the search only
confirms *that* it does.

### Common mistake

**The wrong way:** "x is positive or x is negative". This misses x = 0, and
zero is very often where the formula does something strange, such as
dividing by x. The proof looks complete and has a hole exactly where the
danger is.

**The fix:** derive cases from a two-outcome definition (x = 0 or x ≠ 0;
then split x ≠ 0 into positive or negative). Or write, before the cases,
one sentence proving they are exhaustive.

### In real systems

Exhaustive case analysis is what a `switch` over a TypeScript union with a
`never` check gives you. If you add a new variant to the union, the compiler
flags every switch that no longer covers every case. That is the type
checker enforcing "the cases are exhaustive" for you:

```ts
type Event = { kind: 'created' } | { kind: 'deleted' } | { kind: 'renamed' };
function label(e: Event): string {
  switch (e.kind) {
    case 'created': return 'new';
    case 'deleted': return 'gone';
    case 'renamed': return 'moved';
    default: { const unreachable: never = e; return unreachable; }
  }
}
```

Delete the `renamed` case and the compiler reports that type
`{ kind: 'renamed' }` is not assignable to type `never`: the missing case,
caught before it ships.

2. A number in two cases is proved twice, which is wasteful but still correct. Only a number in no case escapes the proof.

</details>

## 1.8 Proof by Contradiction

### In one sentence

To prove P, assume P is false and derive something impossible; since the
assumption led to nonsense, P must be true.

### The idea

Sometimes the direct route is blocked but the negation is easy to work with.
**Proof by contradiction** (also called indirect proof) says: suppose not P.
Reason from that supposition. If you reach a statement known to be false, a
**contradiction** such as "1 = 0" or "q is even and q is odd", then the
supposition cannot hold, so P is true.

Why it works: if "not P" implies something false, then by the truth table of
implication, "not P" must itself be false. And if "not P" is false, P is
true. The method rests on the rule that every proposition is true or false,
with no third option.

The method is strongest when P is a "there is no ..." or "it is impossible
to ..." statement. Assuming the opposite hands you a concrete object (a
fraction, a largest prime, a fast algorithm) that you can then poke at until
it breaks.

### Worked example

**Simple: √2 is irrational.** A number is **rational** if it equals a
fraction of integers p/q with q not zero. Suppose, for contradiction, that
√2 is rational. Then √2 = p/q, and we may take the fraction in **lowest
terms** (p and q share no factor above 1). Square both sides: 2 = p²/q², so
p² = 2q². So p² is even, and by section 1.5 p is even: p = 2r. Then 4r² =
2q², so q² = 2r², so q² is even and q is even. Now p and q are both even,
which contradicts "lowest terms". So √2 is not rational.

A search will not find a fraction, and it shows how close you can get:

```ts
let found = 0;
for (let q = 1; q <= 100000; q++) {
  const p = Math.round(Math.SQRT2 * q);
  if (p * p === 2 * q * q) found++;
}
console.log(`fractions p/q with p*p = 2*q*q and q up to 100000: ${found}`);
console.log(`closest miss: 99/70 squared = ${(99 / 70) ** 2}`);
```

```text
fractions p/q with p*p = 2*q*q and q up to 100000: 0
closest miss: 99/70 squared = 2.000204081632653
```

The search finds nothing up to 100,000, which is evidence. The proof covers
every q, which is certainty.

**Realistic: there is no universal compressor.** Claim: no lossless
compressor makes every file shorter. Suppose one did. Apply it to all 2ⁿ
files of exactly n bits. Each output is shorter, so it has fewer than n
bits, and there are only 2⁰ + 2¹ + ... + 2ⁿ⁻¹ = 2ⁿ − 1 such strings. So two
different files compress to the same output, and decompression cannot
recover both. That contradicts "lossless". So every lossless compressor
makes some file the same size or bigger, which is why zipping a JPEG often
makes it slightly larger.

### Common mistake

**The wrong way:** reaching a contradiction that comes from a mistake rather
than from the assumption. If your algebra divides by zero in line 4, the
"contradiction" in line 7 is your error, not a theorem. A second mistake is
writing a contradiction proof that is really a direct proof in disguise:
"assume P is false ... [never use it] ... so P is true".

**The fix:** mark the line where the assumption is used. If it is never
used, rewrite as a direct proof. If it is used, check that the contradiction
depends on it.

### In real systems

Impossibility results in distributed systems are proofs by contradiction.
The FLP result (no deterministic protocol can guarantee consensus with even
one crashing process in a fully asynchronous network) assumes such a
protocol exists and builds an execution where it never decides. Knowing the
theorem saves you from trying to build what cannot exist, and tells you
which assumption (timeouts, randomness) real systems such as Raft relax to
escape it.

### Check yourself

1. To prove "there are infinitely many primes" by contradiction, what do you assume?
2. What makes "lowest terms" the right choice in the √2 proof?

<details>
<summary>Answer</summary>

1. That there are finitely many, so there is a complete list p₁, ..., pₖ. Then p₁ × ... × pₖ + 1 leaves remainder 1 when divided by each, so its prime factors are not on the list: contradiction.
2. It gives the proof a property to violate. Any fraction can be reduced, so assuming lowest terms costs nothing, and showing both parts are even breaks it.

</details>

## 1.9 Good Proofs in Practice

### In one sentence

A proof is a piece of writing meant to convince a careful reader, so
structure it, define your terms, and make every step checkable.

### The idea

A correct argument that nobody can follow is not useful. The book closes the
chapter with practical advice, and it reduces to a few habits.

**State your game plan.** Begin with "We use proof by contradiction" or "We
prove both directions", so the reader knows the shape before the detail.
**Keep a linear flow.** Each step should follow from the ones before, not
from something three paragraphs later. **Write in sentences, not symbol
soup.** "Since n is odd, n = 2k + 1 for some integer k" beats "n = 2k + 1,
k ∈ ℤ" on its own.

**Avoid excessive symbolism, and introduce notation with care.** Every
symbol you define is a thing the reader must hold in memory. **Structure long
proofs** with lemmas, the way you structure long code with functions. **Be
wary of "obviously"**: it is where errors hide. And **finish**: say what has
been proved, so the reader knows you are done.

One more habit the book stresses in its exercises: learn to find the error in
a bogus proof. The same skill finds the bug in a bogus program.

### Worked example

**Simple: a bogus proof that 1 = 2.** Let a = b. Then a² = ab, so a² − b² =
ab − b², so (a + b)(a − b) = b(a − b). Divide both sides by (a − b): a + b =
b. Since a = b, 2b = b, so 2 = 1. The error is the division: a − b is zero,
and dividing by zero is not an allowed step. Every other line is fine, which
is why the proof looks convincing.

**Realistic: a design argument written as a proof.** "Claim: our idempotent
retry cannot double-charge a card. Game plan: we show each charge request
carries a key, the server stores the key before charging, and a second
request with the same key returns the stored result. Lemma 1: the key is
generated once per checkout, before the first attempt. Lemma 2: the
key-store write and the charge commit in one transaction. Then any retry
either finds the key, and returns the stored result, or finds no key, which
by Lemma 2 means no charge happened." This is a proof by cases, written as
a proof, and the lemmas are exactly the things a reviewer should check.

  "Steps, each justified, lemmas for big chunks",
  "Say what was proved",
]} />

### Step by step

Debugging the bogus 1 = 2 proof line by line, the way you would bisect a

The technique generalises: substitute a small concrete case into each line
of a suspicious argument and find the first line that becomes false. The
step into that line is the error.

### Common mistake

**The wrong way:** writing a proof as a pile of equations with no words, or
jumping from the claim to "and therefore it is true" with "clearly" in the
middle. Readers cannot check what they cannot follow, and you cannot either
when you reread it a week later.

**The fix:** after writing, read your proof as a sceptic who wants it to be
wrong. Every step should survive the question "why?" with an answer that is
already on the page.

### In real systems

Good design documents and good code reviews are good proofs in practice. A
design doc states the claim (what the system guarantees), the game plan (the
approach), the lemmas (the components and their contracts), and the
assumptions. A pull request description that says "this cannot deadlock,
because locks are always taken in id order" is a proof sketch a reviewer can
check, which is much stronger than "I tested it".

## From beginner to strategy

<Levels label="Chapter 1, What is a Proof?">
<Level name="Beginner" depth={3}>

The smallest working version of the chapter is this: a proof is a list of
steps, each one obviously allowed, that starts from things everyone accepts
and ends at the claim. You have done this since school algebra. What is new
is the demand that *every* step be allowed, and that the claim cover
*every* case.

Try it on "the sum of two even numbers is even". Unpack the definitions: the
numbers are 2a and 2b for some integers a and b. Compute: 2a + 2b = 2(a +
b). Repack: a + b is an integer, so the sum is 2 times an integer, which is
the definition of even. Three moves (unpack, compute, repack) and you have
proved it for all of the infinitely many pairs of even numbers at once.

The beginner's mistake is to "prove" by example: 2 + 4 = 6, 10 + 12 = 22,
so it works. The fix is to name the numbers with letters, so your argument
does not depend on which numbers they are.

</Level>

<Level name="Intermediate" depth={3}>

In real proofs the methods combine. A typical proof of an iff proves one
direction directly and the other by contrapositive; a contradiction proof
often contains a case split inside it. The skill is choosing the method by
looking at the claim's shape.

A useful rule of thumb, written as code you could actually keep in a notes
file:

```ts
type Claim = 'implication' | 'iff' | 'no-such-thing' | 'for-all-integers';
const firstTry = (c: Claim): string => ({
  'implication': 'assume P, derive Q; if stuck, assume not Q, derive not P',
  'iff': 'prove both directions; chain of iffs only if every step reverses',
  'no-such-thing': 'contradiction: assume one exists, break it',
  'for-all-integers': 'cases on parity or remainder; later, induction (chapter 5)',
})[c];
console.log(firstTry('no-such-thing'));
```

```text
contradiction: assume one exists, break it
```

The mistake at this level is sticking with the first method when it stalls.
If "assume P" gives you nothing to compute with, switch to the
contrapositive or to contradiction; the negation often hands you a concrete
object to work on.

</Level>

<Level name="Advanced" depth={3}>

Underneath, every method is justified by the truth table of the logical
connectives. A direct proof works because P → Q is false only when P is true
and Q false, so assuming P and reaching Q rules out the only bad row. The
contrapositive works because ¬Q → ¬P has exactly the same truth table.
Contradiction works because if ¬P → false is true, ¬P must be false.

There is a subtlety here. Proof by contradiction and "P or not P" (the law of
the excluded middle) are axioms of classical logic. Constructive logic, used
by some proof assistants, rejects them for existence claims: to prove
"there exists x" you must produce x. A classical proof can show a solution
exists without telling you what it is. In computing, the constructive kind
is often worth more, because a constructive proof is an algorithm.

The mistake at this level is treating "provable" and "true" as identical in
every system. For the arithmetic of this book they match closely enough, but
the precise statement belongs to logic, and chapter 7 shows a place where
naive reasoning about sets really does break.

</Level>

<Level name="Edge cases" depth={3}>

**Empty domain.** "Every element of the empty set is purple" is true,
because there is no element to be a counterexample. In code,
`[].every(x => x > 100)` returns `true`. This is right, but it surprises
people writing validation: an empty list of permissions passes "every
permission is valid".

**False hypothesis.** An implication with a false hypothesis is true. A
function contract "if the input is sorted, output the median" says nothing
about unsorted input. Callers who pass unsorted data get no promise.

**Zero.** The value zero breaks division, logarithms and "positive or
negative" case splits. Any proof that divides must show the divisor is not
zero.

**One counterexample.** A single counterexample is a complete disproof of a
"for all" claim, however many cases it held for before.

</Level>

<Level name="Corner cases" depth={3}>

**Empty domain plus existence.** "∀x. P(x)" is true on an empty domain, but
"∃x. P(x)" is false there. So "all admins have 2FA, therefore some admin has
2FA" fails when there are no admins. Two boundaries (empty set, and moving
from "all" to "some") combine into a wrong conclusion.

**Chain of iffs through squaring at zero.** "x = y iff x² = y²" fails for
negative values, and "x/z = y/z iff x = y" fails at z = 0. A chain that does
both is wrong in two places, and a numeric spot-check with positive values
misses both.

**Case split plus a missing boundary.** "If x is positive, use 1/x; if x is
negative, use −1/x" misses x = 0, and zero is exactly where 1/x is
undefined. The hole and the danger coincide.

</Level>

<Level name="Production level" depth={3}>

In real systems, a proof's value is that it covers inputs nobody tested. The
practical forms are: types (proofs of "no type errors"), assertions and
invariants checked at runtime (cheap partial proofs), property-based tests
(searches for counterexamples), and model checking or formal verification for
the parts where a bug is very expensive (consensus, payments, permissions).

Here is the property-based style in plain TypeScript, without a library:

```ts
const sortNums = (a: number[]) => [...a].sort((x, y) => x - y);
let failures = 0;
for (let t = 0; t < 10000; t++) {
  const a = Array.from({ length: t % 20 }, () => Math.floor(Math.random() * 50));
  const once = sortNums(a), twice = sortNums(once);
  if (once.join() !== twice.join()) failures++;
}
console.log(`idempotence failures in 10000 random lists: ${failures}`);
```

```text
idempotence failures in 10000 random lists: 0
```

The common production mistake is calling such a run a proof. It is a
search; it found no counterexample. The fix is to say which it is in the
pull request: "verified by type" or "proved in the design doc" versus "10,000
random cases found no counterexample".

</Level>

<Level name="Mindset" depth={3}>

The habit this chapter builds is asking "how do I know?" of every claim,
including your own. It shows up far outside mathematics: in debugging ("I
know the cache is the problem" versus "I have evidence the cache is
involved"), in incident reviews, and in code review.

A second habit is respecting the counterexample. One failing case refutes a
universal claim, so when a user reports a bug that "cannot happen", the
right first move is to believe the report and look for the hole in the
argument. The bogus-proof debugging technique from section 1.9 (plug in
concrete values, find the first false line) works on design arguments as
well as on algebra.

The mistake is letting confidence substitute for an argument. The fix is to
write the argument down; vague confidence rarely survives being written.

</Level>

<Level name="System design" depth={3}>

Every system makes claims: "exactly once delivery", "no lost writes", "at
most 100 requests per minute per user". Each is a proposition over all
possible executions, and each rests on assumptions (the axioms of section
1.4). A good design doc lists both.

Take a payment service with idempotency keys. The claim is "a card is
charged at most once per checkout". The axioms are "the key store is
durable" and "the key is generated before the first attempt". The proof is
a case split (key found or not found) with a lemma (the key write and charge
commit together). Each piece points to something to build or monitor: a
transaction boundary, an alert on key-store errors, a test that retries
after a crash mid-request.

The system-level mistake is proving the happy path only. The fix is the
case analysis of section 1.7 applied to failures: for each step, what if it
fails, times out, or runs twice?

</Level>

<Level name="Strategy" depth={3}>

I learn this chapter by doing, not reading. For each method I write three
proofs of my own from memory, then compare with a careful source. I keep a
proof notebook with one page per method and the "assume ____, show ____"
template at the top.

I also keep a counterexample habit: before trying to prove anything, I
spend two minutes trying to break it, by hand or with a ten-line script. If
I find a counterexample, I saved an hour. If I do not, I usually understand
why the claim is true, which is the start of the proof.

**Done when** I can, without notes, prove "n² even implies n even" by
contrapositive, "√2 is irrational" by contradiction, and "n² + n is even" by
cases, each in under five minutes, and find the error in a bogus proof
someone hands me.

</Level>

## Questions people ask

**Why is an implication with a false hypothesis true? It feels like
cheating.** Think of an implication as a promise. "If you finish the report,
I will buy lunch" is only broken if you finish and I do not buy. If you do
not finish, I have not broken anything, whatever I do. Calling the promise
"true" in that case is just saying it was not broken.

**Is proof by contradiction less trustworthy than a direct proof?** No, it
is equally valid in classical logic. It is sometimes less informative: a
contradiction proof that something exists may not tell you what it is. When
a direct or constructive proof is available, it often teaches more.

**How much detail is enough?** Enough that a careful reader at your level
could check every step without inventing anything. In a course, that means
more detail than in a research paper. In a design doc, it means every
assumption written down.

**Do I need to learn formal logic notation?** You need to read it, because
chapter 3 uses it and many sources do. You do not need to write proofs in
it. The book itself prefers clear sentences.

**Can a computer check my proofs?** Yes, with a proof assistant such as Lean
or Coq, but it is a separate skill with a steep start. For this book, a
careful friend or your own sceptical rereading is the checker.

**What is the difference between a theorem and a lemma?** Only emphasis. A
lemma is a result proved mainly to help prove something else; a theorem is
the result you care about.

## Key takeaways

- A proposition is a statement that is definitely true or false; only propositions can be proved.
- Checking finitely many cases can refute a universal claim but can never prove one.
- An implication is false only when its hypothesis is true and its conclusion false.
- A statement and its contrapositive are equivalent; a statement and its converse are not.
- Prove an iff as two implications, or as a chain of equivalences in which every step reverses.
- Case splits must be exhaustive; a missing case is a hole, often at zero or at the empty set.
- Proof by contradiction assumes the negation and derives the impossible; check that the assumption is actually used.
- A good proof states its method, defines its terms and justifies every step so it can be checked.

## Glossary

- **Proposition:** a statement that is either true or false.
- **Predicate:** a statement with a variable, true or false once the variable is fixed.
- **Domain:** the set of values a variable may take.
- **Universal quantifier (∀):** "for all"; the statement holds for every value in the domain.
- **Existential quantifier (∃):** "there exists"; the statement holds for at least one value.
- **Counterexample:** a value for which a universal claim fails.
- **Axiom:** a statement accepted without proof as a starting point.
- **Proof:** a chain of logical deductions from axioms and proved facts to a claim.
- **Theorem, lemma, corollary:** an important proved statement, a stepping-stone result, and a quick consequence.
- **Implication (P → Q):** "if P then Q"; false only when P is true and Q is false.
- **Contrapositive:** ¬Q → ¬P, equivalent to P → Q.
- **Converse:** Q → P, not equivalent to P → Q in general.
- **If and only if (↔):** both implications hold; the statements are equivalent.
- **Modus ponens:** from P and P → Q, conclude Q.
- **Vacuous truth:** an implication or "for all" claim that is true because there is nothing to check.
- **Proof by cases:** prove the claim in each of several exhaustive cases.
- **Proof by contradiction:** assume the claim is false and derive an impossibility.
- **Rational number:** a number equal to p/q for integers p and q with q not zero.
- **Lowest terms:** a fraction whose numerator and denominator share no factor greater than 1.

## Exercises and self-check

**Warm-up (by hand).**

1. Prove directly: if m and n are odd, then m × n is odd.
2. Prove by contrapositive: if 3n + 2 is odd, then n is odd.
3. Prove by cases on the remainder when dividing by 3: n² leaves remainder 0 or 1 when divided by 3.
4. Prove by contradiction that √3 is irrational, using the fact that if 3 divides p² then 3 divides p.

**Build (code and test).**

5. Write `truthTable(f, names)` that prints the truth table of any boolean function of up to four variables, and use it to confirm that P → Q and ¬Q → ¬P have the same column.
6. Write a counterexample searcher: given a predicate over integers and a range, it returns the first failing value or reports "none found in range". Run it on n² + n + 41 being prime, and on n² − n + 41.
7. Extend the party-problem search to report one colouring of five people with no one-colour triangle, and draw it.

**Stretch (change the problem).**

8. The party proof used "five edges, two colours, so three of one colour". What changes if there are three colours? How many people do you think are needed for a one-colour triangle, and how would a search confirm it?
9. Find the bug in this argument: "every horse in a set of one horse has the same colour; if every set of n horses is one colour, then in a set of n + 1, the first n and the last n are each one colour, so all are." (Chapter 5 returns to it.)

**Self-check.**

<details>
<summary>1. Can you prove "for all integers n, P(n)" by checking a billion values?</summary>

No. You can only refute it that way, by finding a counterexample. A proof needs an argument that covers every integer at once.

</details>

<details>
<summary>2. Which row of the truth table does a direct proof of P → Q rule out?</summary>

The row with P true and Q false, the only row where the implication is false.

</details>

<details>
<summary>3. What is the contrapositive of "if the request is authenticated, it has a user id"?</summary>

"If the request has no user id, it is not authenticated."

</details>

<details>
<summary>4. What do you need to check about every step in a chain of iffs?</summary>

That it is reversible, so the step holds in both directions. Squaring, dividing by a variable and taking absolute values are the usual one-way steps.

</details>

<details>
<summary>5. What is wrong with the cases "x greater than 0" and "x less than 0"?</summary>

They are not exhaustive; they miss x = 0.

</details>

<details>
<summary>6. In a proof by contradiction, how do you know the contradiction is real?</summary>

Find the line where the assumption is used and check that the contradiction depends on it, and that no step has an error such as division by zero.

</details>

<details>
<summary>7. Is `[].every(x => x > 0)` true or false in JavaScript, and why?</summary>

True. A universal statement over an empty domain has no counterexample, so it is vacuously true.

</details>
