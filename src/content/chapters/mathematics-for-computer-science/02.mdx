This chapter gives you a proof method that looks almost too simple to be
useful: every non-empty set of non-negative integers has a smallest member.
From that one fact you can prove claims about all integers, show that every
number factors into primes, and prove that a loop or a recursion must
eventually stop. It is the quiet engine behind induction (chapter 5) and
behind every termination argument in computer science.

## Before you start

**After this chapter you will be able to:**

- State the Well Ordering Principle and say exactly which sets it applies to and which it does not.
- Run the five-step well ordering template to prove that a property holds for every non-negative integer.
- Prove that every integer greater than 1 is a product of primes, and turn that proof into a working factoring function.
- Tell a well ordered set from a set that merely has a minimum, with concrete examples of each.
- Prove that a loop or a recursive function terminates by finding a quantity that strictly decreases in a well ordered set.

**What you should already know:** proof by contradiction and the
contrapositive from
<a href={withBase('/books/mathematics-for-computer-science/01-what-is-a-proof/')}>chapter 1</a>,
and what a prime is. A little TypeScript to read the code.

**Reading time:** about 60 minutes to read, plus an evening for the
exercises.

## 2.1 Well Ordering Proofs

### In one sentence

Every non-empty set of non-negative integers has a smallest element, and a
proof can exploit that by picking the smallest counterexample and breaking
it.

### The idea

Here is the principle in plain words. Take any collection of whole numbers
0, 1, 2, ... that has at least one number in it. Then one of those numbers is
the smallest. That is the **Well Ordering Principle**, often shortened to
WOP. The set of non-negative integers is written ℕ (the natural numbers,
which in this book include 0).

It sounds too obvious to need saying. Two words carry the weight.
**Non-empty**: the empty set has no smallest element, because it has no
elements. **Non-negative integers**: the principle fails for other number
systems. The integers including negatives have no smallest element (−1, −2,
−3, ... goes on forever). The positive fractions have no smallest element
either (halve any fraction and you get a smaller one).

Why can you not just keep going down forever in ℕ? Because every number in
ℕ is a finite distance above 0. Starting at any n, a strictly decreasing
chain n, then something smaller, then smaller again, can take at most n
steps before it hits 0 and stops. That intuition is what the principle
captures, and the book takes it as an axiom.

The proof method follows immediately. Suppose you want to show that some
property holds for every natural number, and suppose it does not. Then the
set of **counterexamples** (numbers where the property fails) is non-empty,
so it has a smallest member. Now work on that smallest counterexample. If you
can show either that the property holds for it after all, or that there is
an even smaller counterexample, you have a contradiction. So there are no
counterexamples.

### Worked example

**Simple: every fraction can be written in lowest terms.** In chapter 1's
proof that √2 is irrational, we assumed we could write any fraction m/n in
**lowest terms**, meaning numerator and denominator share no prime factor.
Why is that always possible? Well ordering answers it.

Suppose some fractions with positive parts cannot be put in lowest terms.
Collect the numerators of all such fractions into a set C. The set is
non-empty, so it has a smallest member, m₀, belonging to some fraction m₀/n₀
that cannot be put in lowest terms. That fraction is not already in lowest
terms, so m₀ and n₀ share a prime factor p. Divide both by p. The fraction
(m₀/p)/(n₀/p) is equal to m₀/n₀, so it cannot be put in lowest terms either
(if it could, the same lowest form would work for m₀/n₀). So m₀/p is in C.
But m₀/p is smaller than m₀, the smallest member of C. Contradiction. So C is
empty, and every fraction can be reduced.

In code, reducing a fraction is dividing by the greatest common divisor,
which chapter 8 develops:

```ts
const gcd = (x: number, y: number): number => (y === 0 ? x : gcd(y, x % y));
const reduce = (p: number, q: number) => { const d = gcd(p, q); return [p / d, q / d]; };
console.log(reduce(84, 126), reduce(17, 51));
```

```text
[ 2, 3 ] [ 1, 3 ]
```

**Realistic: the smallest failing input.** When a test fails on a large
generated input, property-based testing tools *shrink* it to a smaller one
that still fails, and keep shrinking until nothing smaller fails. They are
searching for the smallest counterexample, exactly the object a well
ordering proof reasons about. The smallest failing case is the one where
the bug is easiest to see, and it exists because input sizes are natural
numbers.

### Common mistake

**The wrong way:** applying the principle to a set that is not of
non-negative integers. "Let x be the smallest positive real number with
property P" is not justified: the positive reals have no smallest member,
and a set of them may not either. Proofs that do this can "prove" false
things.

**The fix:** before writing "let c be the smallest", say which well ordered
set C sits inside. If the objects are not integers, attach a natural-number
*measure* to them (a length, a numerator, a count) and take the object with
the smallest measure.

### In real systems

Delta debugging and test-case shrinking (in fast-check, Hypothesis and
QuickCheck) produce minimal failing inputs, and git's `bisect` finds the
*first* bad commit in a history. Both rely on the fact that a non-empty set
of positions has a first member. When you report a bug with "the smallest
input that fails is `[0, -1]`", you have done a well ordering argument's
first three steps by machine.

### Check yourself

1. Does the set of even negative integers have a smallest element?
2. In the lowest-terms proof, why does m₀/p count as smaller?

<details>
<summary>Answer</summary>

1. No. For any even negative number, subtracting 2 gives a smaller one. The principle only covers sets of non-negative integers (or, as 2.4 shows, sets bounded below).
2. Because p is a prime, so p is at least 2, and dividing a positive integer by at least 2 makes it strictly smaller.

</details>

## 2.2 Template for Well Ordering Proofs

### In one sentence

To prove P(n) for every natural number n, define the set of counterexamples,
assume it is non-empty, take its smallest member, derive a contradiction,
and conclude there are no counterexamples.

### The idea

The lowest-terms proof had a shape, and the shape is reusable. Here is the
template, in my words:

1. **Define the counterexamples.** Let C be the set of natural numbers n for
   which P(n) is false.
2. **Assume, for contradiction, that C is non-empty.**
3. **Take the smallest.** By well ordering, C has a smallest member; call
   it c. Now you know P fails at c and holds at every natural number below c.
4. **Contradict.** Use that knowledge to show P(c) holds after all, or that
   some number smaller than c is also in C. This is the creative step.
5. **Conclude** that C is empty, so P(n) holds for all n.

Steps 1, 2, 3 and 5 are bookkeeping; you write them the same way every
time. Step 4 is the real work. The extra power you get, compared with a
plain contradiction proof, is the knowledge in step 3 that *everything below
c works*. That knowledge is what lets you reach back to c − 1 or to a
factor of c.

There is usually a **base check** hidden in step 4. To reach back to c − 1,
you need c − 1 to exist, which needs c to be at least 1, which you get by
showing P(0) holds directly. Forgetting it is the most common way the
template goes wrong.

<Flow caption="The template as a pipeline. Every box except 'contradict' is the same in every proof; the contradict box is where you think." steps={[
  "C = the n where P(n) fails",
  "assume C is non-empty",
  "c = smallest member of C",
  "P holds below c; P fails at c",
  "contradict: P(c) holds, or a smaller member of C exists",
  "C is empty: P holds for all n",
]} />

#### Summing the integers

The book's first use of the template is the formula for the sum of the
first n positive integers: 1 + 2 + ... + n = n(n + 1)/2. Before proving it,
pin down the notation, because the three dots hide two traps.

When n = 1 the sum is just 1; the "+ 2 + 3" in the notation is not there.
When n = 0 the sum has no terms, and by convention a sum of no terms is 0
(and a product of no terms is 1). Summation notation, Σ with i running from
1 to n, makes both cases unambiguous. The formula gives 0 × 1/2 = 0 for n = 0
and 1 × 2/2 = 1 for n = 1, so both edge cases agree with it.

Now the proof. Let C be the set of n where the formula fails. Suppose C is
non-empty, and let c be its smallest member. The formula holds at 0, so c is
not 0, so c is at least 1 and c − 1 is a natural number. Since c − 1 is less
than c, it is not a counterexample, so 1 + ... + (c − 1) = (c − 1)c/2. Add c
to both sides: 1 + ... + c = (c − 1)c/2 + c = (c² − c + 2c)/2 = c(c + 1)/2.
So the formula holds at c after all. Contradiction; C is empty.

### Worked example

**Simple: the sum formula, checked and proved.** Checking first, because it
costs nothing and catches typos in the formula:

```ts
function smallestCounterexample(P: (n: number) => boolean, limit: number): number | null {
  for (let n = 0; n <= limit; n++) if (!P(n)) return n;
  return null;
}
const sumTo = (n: number) => { let s = 0; for (let i = 1; i <= n; i++) s += i; return s; };
console.log(smallestCounterexample((n) => sumTo(n) === (n * (n + 1)) / 2, 10000));
```

```text
null
```

The function returns the smallest counterexample in a range, which is
exactly the c of the template, computed. Here there is none, which is
evidence; the proof above is the certainty. Point the same function at a
false claim and it hands you the c that breaks it: for "n² − n + 41 is
prime" it returns 41, since 41² − 41 + 41 = 41².

**Realistic: stamps.** Claim: every amount of postage of 8 cents or more can
be made from 3-cent and 5-cent stamps. This is the kind of claim that shows
up as "every batch size above some threshold can be packed into crates of
sizes 3 and 5".

The property is P(n): "n + 8 cents can be made" (shifting so the claim is
about every natural number). Let C be the counterexamples and c the smallest.

- If c is 0, 1 or 2, the amount is 8, 9 or 10, which are 3 + 5, 3 + 3 + 3 and
  5 + 5. None of these fail, so c is at least 3.
- Then c − 3 is a natural number below c, so the amount c − 3 + 8 can be
  made. Add one 3-cent stamp and you have c + 8. So c is not a
  counterexample after all. Contradiction.

Notice that the base check here is three values, not one, because the
reach-back is by 3. A search confirms the threshold, and shows that 7 really
is impossible:

```ts
function stamps(n: number): [number, number] | null {
  for (let b = 0; 5 * b <= n; b++) if ((n - 5 * b) % 3 === 0) return [(n - 5 * b) / 3, b];
  return null;
}
for (const n of [7, 8, 9, 10, 11, 23]) console.log(n, JSON.stringify(stamps(n)));
```

```text
7 null
8 [1,1]
9 [3,0]
10 [0,2]
11 [2,1]
23 [6,1]
```

Each pair is (number of 3-cent stamps, number of 5-cent stamps).

### Common mistake

**The wrong way:** skipping the base check. In the stamp proof, if you only
check 8 and then reach back by 3, the argument would "prove" that 9 and 10
can be made from smaller amounts, but 6 and 7 are below the threshold and
7 cannot be made at all. The reach-back lands outside the region where you
know anything.

**The fix:** for a reach-back of k, check the first k values directly. Then
write the sentence "so c is at least k, and c − k is a natural number below
c" explicitly. If you cannot write that sentence, the proof is not done.

### In real systems

The template is how you prove a **retry or backoff policy** reaches a goal,
how you prove a **batching rule** covers every size above a threshold, and
how you show a **migration script** handles every row: assume a first row
it mishandles, and show the rows before it set up a state that handles it.
Engineers do this informally when they ask "what is the first request where
this breaks?". The template is the formal version of that question.

## 2.3 Factoring into Primes

### In one sentence

Every integer greater than 1 is a product of primes, because a smallest
number that is not would have to split into two smaller numbers that are.

### The idea

A **prime** is an integer greater than 1 whose only positive divisors are 1
and itself: 2, 3, 5, 7, 11, .... An integer greater than 1 that is not prime
is **composite**: it can be written as a × b with both a and b strictly
between 1 and itself. The claim is that every integer above 1 is a product
of primes, where a single prime counts as a product of length one.

This fact is so familiar that it feels like it needs no proof. It does need
one, and it has two halves. **Existence** says some factorisation exists.
**Uniqueness** says it is the only one, up to the order of the factors (the
Fundamental Theorem of Arithmetic). This chapter proves existence with well
ordering; uniqueness is harder and waits for chapter 8.

The proof follows the template. Let C be the integers above 1 that are not
products of primes, and suppose C is non-empty, with smallest member n. Then
n is not prime (a prime is a product of primes). So n = a × b with both a
and b between 1 and n. Both are smaller than n, so neither is in C, so each
is a product of primes. Multiply the two products together and n is a
product of primes. Contradiction.

This proof uses the template's step 3 more strongly than the sum formula
did. There we reached back to c − 1. Here we reach back to *any* smaller
number (a and b could be anywhere below n). That stronger reach-back is
exactly what chapter 5 will call **strong induction**.

### Worked example

**Simple: 360.** It is not prime: 360 = 2 × 180. Factor each part. 2 is
prime. 180 = 2 × 90 = 2 × 2 × 45 = 2 × 2 × 3 × 15 = 2 × 2 × 3 × 3 × 5. So
360 = 2³ × 3² × 5. The splits are not unique (you could start with 360 = 12
× 30), but the final multiset of primes is the same, which is what chapter
8's uniqueness proof guarantees.

**Realistic: the proof as code.** The existence proof is an algorithm:
try to split n; if you cannot, n is prime; if you can, factor each part.

```ts
function factor(n: number): number[] {
  for (let a = 2; a * a <= n; a++)
    if (n % a === 0) return [...factor(a), ...factor(n / a)];
  return [n]; // no divisor up to the square root: n is prime
}
console.log(factor(360), factor(97), factor(1001));
```

```text
[ 2, 2, 2, 3, 3, 5 ] [ 97 ] [ 7, 11, 13 ]
```

Two details link the code to the math. First, the loop only tries divisors
up to √n, because if n = a × b with both factors above √n, their product
would exceed n. Second, the recursion terminates because each call is on a
strictly smaller integer above 1, and a decreasing chain of natural numbers
cannot go on forever. That is well ordering again, used for termination
instead of for truth, and it is the subject of section 2.4.

### Common mistake

**The wrong way:** "proving" uniqueness with this argument. The template
shows that *some* factorisation exists. It says nothing about whether a
different split could lead to different primes. In some number systems
beyond the integers, factorisations really are not unique (in numbers of
the form a + b√−5, the number 6 is both 2 × 3 and (1 + √−5)(1 − √−5)), so
uniqueness is a real theorem, not a free bonus.

**The fix:** keep existence and uniqueness as two separate claims, with two
separate proofs. When a proof gives you one, say which.

### In real systems

Factoring is the reason RSA works (chapter 8): multiplying two large primes
is fast, and no one knows a fast way to factor the product back. The
trial-division function above is fine for numbers up to around 10¹² and
hopeless for the 2,048-bit numbers in RSA keys. The proof is the same at any
size; the cost is what changes, and that gap between "exists" and "can be
found quickly" is the foundation of public-key cryptography.

### Check yourself

1. Why does a prime count as a product of primes?
2. Why can `factor` stop trying divisors at the square root of n?

<details>
<summary>Answer</summary>

1. A product of length one is still a product. Without this convention the theorem would be false for every prime, and the proof's line 3 would not work.
2. If n = a × b and both a and b were greater than √n, then a × b would be greater than n. So any composite n has a divisor at most √n; if none is found, n is prime.

</details>

## 2.4 Well Ordered Sets

### In one sentence

A set of numbers is well ordered when every non-empty subset has a smallest
member, and any process whose measure strictly decreases in such a set must
stop.

### The idea

Well ordering is a property of a set, not just of ℕ. A set S of numbers is
**well ordered** if every non-empty subset of S has a minimum. The Well
Ordering Principle says ℕ is well ordered. Many other sets are too: every
finite set (just compare all the members), the integers from 5 upward, and
the multiples of any positive number r (0, r, 2r, 3r, ...).

Having a minimum is not enough. The non-negative rational numbers have a
minimum, 0. But the subset of *positive* rationals has no minimum: for any
positive fraction, half of it is a smaller positive fraction. So the
non-negative rationals are not well ordered. The definition is about every
non-empty subset, and one subset without a minimum is enough to break it.

The idea that matters most for programming is the **termination
argument**. Attach a number, a **measure** (also called a ranking function
or variant), to each state of a computation, chosen so that every step
strictly decreases it. If the measures come from a well ordered set, the
computation cannot run forever: the measures of an infinite run would form a
non-empty set with no minimum, because each one is followed by a smaller
one. Chapter 5 uses this on state machines.

#### Bounds, and the corollaries

The book proves a small generalisation: the integers greater than or equal
to a fixed n are well ordered. The proof is a shift. Take a non-empty set S
of integers, each at least n. Subtract n from every member: the result is a
non-empty set of non-negative integers, so it has a minimum m. Shift back,
and m + n is the minimum of S. It would be harmless to accept this as an
extra axiom, but it is worth noticing that it can be proved from the one we
already have.

A **lower bound** of a set S is a number b with b at most every member of S;
an **upper bound** is a number at least every member. A bound does not need
to be in the set. Two corollaries follow, and both are used constantly:

- **Any set of integers with a lower bound is well ordered.** If b is a real
  lower bound, then the floor of b (b rounded down to an integer) is an
  integer lower bound, and the shifted theorem applies.
- **Any non-empty set of integers with an upper bound has a maximum.**
  Negate every member. The upper bound becomes a lower bound, so the negated
  set has a minimum, and negating that minimum gives the maximum of the
  original set.

The second corollary is the one that justifies "let k be the largest integer
such that ..." in later proofs, for example the largest power of 2 dividing
a number, or the largest index where a loop invariant held.

#### A different well ordered set

The book's optional subsection builds an exotic well ordered set, and it is
worth a few minutes because it breaks a common intuition. Let F be the
fractions n/(n + 1): 0, 1/2, 2/3, 3/4, .... They creep up towards 1 and never
reach it. F is well ordered: any non-empty subset has the member with the
smallest numerator as its minimum.

Now add natural numbers: N + F is every number of the form n + f with n in
ℕ and f in F. Picture copies of F stacked one after another: the 0-copy
creeping towards 1, then the 1-copy starting at 1 and creeping towards 2, and
so on. This set is still well ordered. To find the minimum of a subset, first
take the smallest whole part n that appears (well ordering on ℕ), then among
members with that whole part take the smallest fraction (well ordering on F).

What makes it exotic: in ℕ, every member has only finitely many members
below it. In N + F, the number 1 has infinitely many members below it (all
of F). Yet there is still no infinite *decreasing* chain. Well ordered does
not mean "finitely many below"; it means "no endless descent".

### Worked example

**Simple: Euclid's algorithm halts.** Euclid's algorithm computes the
greatest common divisor by replacing (a, b) with (b, a mod b) until b is 0.
The measure is b. Each step replaces b by a mod b, the remainder of a divided
by b, which is strictly less than b and at least 0. A strictly decreasing
sequence of natural numbers is finite, so the loop stops.

```ts
function gcdTrace(a: number, b: number): string[] {
  const rows: string[] = [];
  while (b !== 0) { rows.push(`a=${a} b=${b} measure=${b}`); [a, b] = [b, a % b]; }
  rows.push(`a=${a} b=0 -> gcd ${a}`);
  return rows;
}
console.log(gcdTrace(1071, 462).join('\n'));
```

```text
a=1071 b=462 measure=462
a=462 b=147 measure=147
a=147 b=21 measure=21
a=21 b=0 -> gcd 21
```

**Realistic: a recursion with two arguments.** The Ackermann function
recurses on (m, n) in a way where neither argument alone always decreases:
ack(m, n) calls ack(m − 1, ack(m, n − 1)), and the inner result can be huge.
The measure that works is the *pair* (m, n) compared **lexicographically**:
first by m, and by n only when the m values tie, like words in a
dictionary. Every recursive call either lowers m (with any n) or keeps m and
lowers n. The pairs of natural numbers in dictionary order form a well
ordered set (it looks just like N + F: infinitely many pairs (0, n) sit
below (1, 0)), so the recursion halts, even though it can take an enormous
number of calls.

```ts
let calls = 0;
function ack(m: number, n: number): number {
  calls++;
  if (m === 0) return n + 1;
  if (n === 0) return ack(m - 1, 1);
  return ack(m - 1, ack(m, n - 1));
}
for (const [m, n] of [[1, 2], [2, 3], [3, 3]]) {
  calls = 0; const v = ack(m, n);
  console.log(`ack(${m},${n}) = ${v} after ${calls} calls`);
}
```

```text
ack(1,2) = 4 after 6 calls
ack(2,3) = 9 after 44 calls
ack(3,3) = 61 after 2432 calls
```

Termination says the call count is finite. It says nothing about it being
small. ack(4, 2) also halts, and its result has nearly twenty thousand
digits.

### Step by step

The termination argument as a recipe, applied to a loop that drains a work
queue where each job may enqueue smaller jobs.

<Trace columns={["step", "what you do", "for the queue loop"]} rows={[
  ["1", "write down the state", "the multiset of job sizes in the queue"],
  ["2", "choose a measure into a well ordered set", "the sorted list of sizes, compared largest first"],
  ["3", "show each step strictly decreases it", "one job of size s is replaced by jobs all smaller than s"],
  ["4", "show the measure stays in the set", "sizes are natural numbers"],
  ["5", "conclude the loop halts", "an infinite run would be an endless descent"],
]} caption="Step 2 is the creative one. A plain count of jobs does not work here, because a job can enqueue many smaller ones; the measure must capture 'bigger jobs are replaced by smaller ones'." />

The queue example uses the **multiset ordering**: replacing one element by
any finite number of smaller ones always decreases the multiset. That
ordering is well ordered when the elements are natural numbers, and it is
the standard tool for proving termination of rewriting systems and
work-stealing loops.

### Common mistake

**The wrong way:** using a measure that decreases but lives in a set that is
not well ordered. A loop that halves a positive real number "decreases every
step", but the positive reals allow an endless descent, so this proves
nothing. In the mathematics, x = 1, 1/2, 1/4, ... never reaches 0.

Floating point adds a twist that shows the difference between the
mathematics and the machine:

```ts
let r = 1, steps = 0;
while (r > 0) { r = r / 2; steps++; }
console.log(`halving 1 reached ${r} after ${steps} steps`);
```

```text
halving 1 reached 0 after 1075 steps
```

The loop halts on a real computer only because floats are a *finite* set,
and the value eventually underflows to 0. Run the same loop with an exact
rational-number type and it never ends. The halting came from the machine,
not from the argument, which is a fragile thing to rely on.

**The fix:** always name the well ordered set the measure lives in. If the
values are reals, map them to natural numbers (for example, the number of
halvings left before a tolerance is reached) and argue about that.

### In real systems

Termination arguments are everywhere you need a guarantee that something
finishes. A garbage collector's mark phase terminates because the set of
unmarked objects only shrinks. A TCP connection's state machine is designed
so that retransmission counters bound the work. A database's query planner
uses depth limits. Language tools build on this directly: Lean, Coq and
Agda reject a recursive function unless they can find a decreasing measure,
and Dafny asks you to write one with a `decreases` clause.

The Collatz problem is the cautionary tale: the loop "if n is even halve it,
else replace it by 3n + 1, until n is 1" has halted for every starting value
anyone has tried, and nobody has found a measure that proves it always does.

1. Is the set of integers at most 100 well ordered? Does it have a maximum?

3. What is the measure that shows Euclid's algorithm halts?

## From beginner to strategy

<Levels label="Chapter 2, The Well Ordering Principle">
<Level name="Beginner" depth={3}>

The smallest working version of the idea: if a claim about whole numbers
ever fails, there is a *first* place it fails. Find out what that first
failure would have to look like, and show it cannot exist.

Try it on "every natural number is either even or odd". Suppose not, and let
c be the first number that is neither. It is not 0, because 0 is even. So c −
1 is a natural number, and it is even or odd (it comes before c). If c − 1 is
even, c is odd; if c − 1 is odd, c is even. Either way c is even or odd.
Contradiction, so there is no first failure, so there is no failure.

The beginner's mistake is forgetting that "the first failure" must be
checked against the start of the line. If you never showed 0 works, then c
might be 0, and "c − 1" would be −1, outside the numbers you know about. The
fix is a habit: always check the smallest case directly before reaching
back.

</Level>

<Level name="Intermediate" depth={3}>

In real use, the template combines with other tools. The reach-back can be
by one (the sum formula), by a fixed amount (the stamps), or to any smaller
number (factoring). The contradiction can come from showing P(c) holds, or
from building a smaller counterexample (lowest terms). Choosing the reach
is the main design decision.

The same idea in a program: a function that finds the smallest
counterexample is a tiny, honest test harness. Point it at a claim and it
either returns null (evidence) or the smallest failure (a disproof, and the
best possible bug report).

```ts
const smallest = (P: (n: number) => boolean, limit: number) => {
  for (let n = 0; n <= limit; n++) if (!P(n)) return n;
  return null;
};
// Claim: n² + n is always divisible by 6. Is it?
console.log(smallest((n) => (n * n + n) % 6 === 0, 100));
```

```text
1
```

It fails at n = 1 (1 + 1 = 2). The intermediate mistake is to then "fix" the
claim by excluding 1 and trying again without thinking. n² + n is always
divisible by 2 (chapter 1), but not by 6; the search tells you which claim
to try to prove.

</Level>

<Level name="Advanced" depth={3}>

Underneath, the Well Ordering Principle, ordinary induction and strong
induction are three faces of one property of ℕ. Chapter 5 proves each from
the others. Well ordering is the most convenient when the natural argument
is "a smallest bad case would let me build a smaller one", which is common
in number theory (lowest terms, infinite descent) and in termination.

The precise definition is about every non-empty subset having a minimum.
Equivalently, there is no infinite strictly decreasing sequence. These two
are the same: an infinite descent is a subset with no minimum, and a subset
with no minimum lets you build an infinite descent by repeatedly picking a
smaller member. Termination proofs use the second form.

Well ordered sets can be much longer than ℕ while still forbidding descent.
N + F and the pairs of naturals in dictionary order are both "longer" than
ℕ: they have members with infinitely many predecessors. Set theory calls
these order types **ordinals**, and they are what make termination proofs
work for nested loops, lexicographic measures and programs like Ackermann.
The advanced mistake is assuming "every element has finitely many below it"
is required; it is not, only the absence of descent is.

</Level>

<Level name="Edge cases" depth={3}>

**The empty set.** The principle says nothing about it; it has no minimum.
Every template proof needs the assumption "C is non-empty" for that reason.

**The value 0 in a loop measure.** A loop that divides n by 2 while n is
even never stops when n is 0, because 0 is even and 0 / 2 is 0. The measure
n does not decrease at 0.

```ts
function twoAdic(n: number): number { let k = 0; while (n % 2 === 0) { n /= 2; k++; } return k; }
console.log(twoAdic(96), twoAdic(7)); // twoAdic(0) would never return
```

```text
5 0
```

**One element.** A one-element set is well ordered trivially. A recursion
on a list of length 1 must still reach a base case; if the split is
"first half and second half", a length-1 list can split into lengths 0 and
1, and the second call is on the same size. Measure must strictly decrease.

**The maximum.** "Let k be the largest such that ..." needs the set to be
non-empty *and* bounded above. Missing either and there is no largest.

</Level>

<Level name="Corner cases" depth={3}>

**A measure that decreases by zero at a boundary, plus an off-by-one
update.** The classic is binary search. With `lo = mid` instead of `lo =
mid + 1`, the gap hi − lo stops shrinking when hi = lo + 1, because mid then
equals lo. Two things at once: a two-element range, and an update that does
not move.

```ts
let lo = 3, hi = 4;
const mid = Math.floor((lo + hi) / 2);  // 3, which is lo
console.log(mid === lo);                // the buggy update lo = mid changes nothing
```

```text
true
```

**Reach-back plus too few base cases.** The stamp proof reaches back by 3.
If you check only 8 and 9, the case c + 8 = 10 reaches back to 7, which is
impossible, and the "proof" is broken right where the threshold sits.

**Negative numbers plus a remainder.** Euclid's measure argument assumes the
remainder lies between 0 and b − 1. In JavaScript, `-7 % 3` is `-1`, so
with negative inputs the "measure" can go negative and the argument no
longer applies. Take absolute values first.

</Level>

<Level name="Production level" depth={3}>

In production, the failure mode this chapter prevents is the hang: a retry
loop, a pagination loop or a recursive walk that never ends. Each needs a
measure. Pagination over an API halts because the number of unseen items
decreases with each page, *provided* the cursor always moves forward. If a
server returns the same cursor twice (a real bug in real APIs), the measure
stops decreasing and the client loops forever.

The engineering fixes mirror the proof. Make the measure explicit and check
it at runtime: store the previous cursor and fail loudly if it repeats. Add
a hard bound as a safety net (a maximum page count), and alert when it is
hit, because hitting it means the proof's assumptions were false.

```ts
function drain(fetchPage: (c: string | null) => { items: number[]; next: string | null }) {
  const seen = new Set<string>(); let cursor: string | null = null; let total = 0;
  do {
    const page = fetchPage(cursor); total += page.items.length;
    if (page.next !== null && seen.has(page.next)) throw new Error('cursor repeated');
    if (page.next !== null) seen.add(page.next);
    cursor = page.next;
  } while (cursor !== null);
  return total;
}
```

The mistake is relying on "it always finished in testing". The fix is a
measure you can name in the code review, plus a guard that turns a silent
hang into a visible error.

</Level>

<Level name="Mindset" depth={3}>

The habit is asking "what is the first thing that goes wrong?". It is a
debugging habit (find the first bad commit, the first bad log line, the
first request that failed) and a proof habit at once. The first failure
carries the most information because everything before it was fine.

The second habit is asking "what gets smaller?" of every loop and every
recursion before you trust it. If you cannot name the quantity, you do not
yet know the loop halts. This takes ten seconds per loop and catches a real
class of bugs.

The mindset mistake is treating termination as obvious. Most hangs in
production were "obviously" finite to their authors. The fix is to say the
measure out loud, even when it is obvious; the time it is not obvious is
the time it matters.

</Level>

<Level name="System design" depth={3}>

In a larger system, well ordering is how you argue that background work
finishes and that recovery converges. Take a job queue where failed jobs
are retried. The system-level claim is "every job eventually reaches a
final state". The measure is the pair (retries left, steps left in the job),
in dictionary order: a retry lowers the first part, progress lowers the
second. Design follows from the proof: retries must be bounded, and
progress must be recorded so a retry does not restart from zero.

Distributed protocols use the same tool. Raft's leader election is
argued to settle because terms only increase and randomised timeouts
eventually give one candidate a clean win; the proof is a measure argument
plus a probability argument (chapter 20). Garbage collection, compaction in
log-structured stores, and topological builds (chapter 9) all halt because
some well ordered quantity strictly decreases.

The design mistake is a retry policy with no measure: "on failure, re-enqueue"
with no counter. A poison message then loops forever and burns capacity. The
fix is a retry budget in the message, decremented on each attempt, and a
dead-letter queue for when it reaches 0.

</Level>

<Level name="Strategy" depth={3}>

I learn this chapter by writing the five-step template from memory until it
is automatic, then using it on six claims of my own: two sums, two
divisibility claims, one factoring-style claim with a strong reach-back, and
one termination proof for a loop from my own code.

I also go through one real codebase and write the measure for every

bug or add a guard. That exercise turns the chapter into a review skill.

</Level>

## Questions people ask

**Is the Well Ordering Principle an axiom or a theorem?** In this book it is
taken as an axiom about ℕ. In a formal development of arithmetic it can be
derived from the induction axiom, and induction can be derived from it.
Which one you start with is a choice; they are equivalent.

**Why not just use induction for everything?** You can, and chapter 5 shows
how. Well ordering is often the more natural phrasing when the argument is
"a smallest bad case would let me build a smaller one", as in the
lowest-terms proof. Pick whichever makes the proof shortest and clearest.

**Does well ordering work for the real numbers?** Not with the usual order:
the positive reals have no smallest member. (Set theory can well order any
set with a strange order, using the axiom of choice, but that order is not
"less than", and it is of no use for computing.)

**How do I find the measure for a termination proof?** Look at what the
loop is making progress on: a remaining count, the size of a range, the
length of an unprocessed list. If no single number works, try a pair in
dictionary order, or the multiset of sizes.

**Does this prove Collatz terminates?** No. Nobody has found a measure that
always decreases for the Collatz loop. It halts for every number tried, for
example 111 steps from 27, but that is evidence, not proof.

**What is the difference between "has a minimum" and "well ordered"?** A
minimum is a property of one set. Well ordered is a property of *every*
non-empty subset. The non-negative rationals have a minimum (0) but are not
well ordered.

## Key takeaways

- Every non-empty set of non-negative integers has a smallest member; that is the Well Ordering Principle.
- To prove P(n) for all n, assume a smallest counterexample c, use that P holds below c, and contradict.
- Check the starting cases directly before reaching back, one base case per step of reach-back.
- Every integer above 1 is a product of primes; this proves existence only, not uniqueness.
- A set is well ordered when every non-empty subset has a minimum, which is stronger than having a minimum.
- Integers with a lower bound are well ordered, and a non-empty set of integers with an upper bound has a maximum.
- A loop halts if some measure in a well ordered set strictly decreases every step; name the measure.
- Pairs compared in dictionary order are well ordered, which proves halting for nested or two-argument recursions.

## Glossary

- **Well Ordering Principle (WOP):** every non-empty set of non-negative integers has a smallest member.
- **ℕ:** the natural numbers 0, 1, 2, ... in this book.
- **Counterexample set:** the set of values for which the claim fails.
- **Smallest counterexample:** the minimum of the counterexample set, if it is non-empty.
- **Lowest terms:** a fraction whose numerator and denominator share no prime factor.
- **Prime:** an integer greater than 1 whose only positive divisors are 1 and itself.
- **Composite:** an integer greater than 1 that is a product of two smaller integers greater than 1.
- **Prime factorisation:** a way of writing an integer as a product of primes.
- **Well ordered set:** a set in which every non-empty subset has a minimum.
- **Lower bound, upper bound:** a number at most (or at least) every member of a set; not necessarily in the set.
- **Floor:** a real number rounded down to the nearest integer.
- **Measure (ranking function, variant):** a value attached to each state that strictly decreases each step.
- **Lexicographic (dictionary) order:** compare first components, and use later ones only to break ties.
- **Infinite descent:** an infinite strictly decreasing sequence; impossible in a well ordered set.
- **Ellipsis:** the "..." in a sum, which hides edge cases at n = 0 and n = 1.
