Number theory is the study of the integers, and for most of its history it
was admired for being useless. That changed when it became the engine of
public-key cryptography: every HTTPS connection, signed software update and
SSH login leans on the facts in this chapter. The book tells the story
through Alan Turing's attempts at number-theoretic codes, which are broken
as fast as they are built, and ends with RSA, which has survived for
decades. Along the way come the tools that do the real work: remainders,
the greatest common divisor, Euclid's algorithm and its extended form, the
Pulverizer, unique factorisation, modular arithmetic, inverses and Euler's
theorem.

## 8.1 Divisibility

### In one sentence

a divides b when b is an integer multiple of a, and a handful of simple
facts about divisibility, plus division with remainder, are the base of
everything else in the chapter.

### The idea

#### Facts about divisibility

Write a | b ("a divides b") when b = ka for some integer k. So 3 | 12, 7 |
0 (every number divides 0), and 1 divides everything. The book collects
the facts that get used constantly. For all integers a, b, c:

- If a | b and b | c, then a | c (transitivity).
- If a | b and a | c, then a | sb + tc for all integers s and t: a divisor
  of two numbers divides every **integer linear combination** of them.
- For c not zero, a | b iff ca | cb.

Each proof is one line of algebra: write b = ka and c = ja, then sb + tc
= (sk + tj)a. The linear-combination fact is the one that will matter
most, because the gcd turns out to be exactly the smallest positive linear
combination.

#### When divisibility goes bad

When a does not divide b, there is a remainder. The **Division Theorem**:
for integers n and d with d positive, there is exactly one pair q, r with
n = qd + r and 0 ≤ r less than d. The book writes q = qcnt(n, d) and r =
rem(n, d). So rem(2716, 10) = 6, and rem(−11, 7) = 3, because −11 = −2 · 7
+ 3.

The book warns about programming languages: many treat negative operands
differently. JavaScript's `%` takes the sign of the left operand, so −11 %
7 is −4, which is not the Division Theorem's remainder. Code that relies on
remainders being in the range 0 to d − 1 must normalise them.

#### Die Hard

The book's running puzzle: you have a 3-gallon jug and a 5-gallon jug, a
fountain, and you must measure exactly 4 gallons. You can fill a jug,
empty it, or pour one into the other until one is empty or the other is
full. (It is from an action film, hence the name.)

Model it as a state machine (chapter 5): the state is the pair of amounts.
The key invariant is that **every amount in either jug is always a linear
combination of 3 and 5**. It starts true (0 = 0 · 3 + 0 · 5), and each move
either sets a jug to 0 or full, or moves an amount between jugs, all of
which keep it true. So with jugs of size a and b, any amount you measure
is a linear combination of a and b, and therefore divisible by every
common divisor of a and b. With a 6 and a 15 jug, only multiples of 3 can
ever appear, so 4 gallons is impossible. With 3 and 5 every amount from 0
to 5 is reachable, as 8.2.3 will explain.

### Worked example

**Simple: remainders done right.** Define rem and qcnt to follow the
Division Theorem, and compare with JavaScript's operator:

```ts
const rem = (n: number, d: number) => ((n % d) + d) % d;
const qcnt = (n: number, d: number) => (n - rem(n, d)) / d;
console.log('JS -11 % 7 =', -11 % 7, ' rem(-11,7) =', rem(-11, 7), ' qcnt(-11,7) =', qcnt(-11, 7));
```

```text
JS -11 % 7 = -4  rem(-11,7) = 3  qcnt(-11,7) = -2
```

**Realistic: every reachable amount, by search.** A breadth-first search
over jug states, trying all six moves from each state, lists every amount
that ever appears:

```ts
function reachable(a: number, b: number): number[] {
  const seen = new Set<string>(); const amounts = new Set<number>(); const queue: [number, number][] = [[0, 0]];
  while (queue.length) {
    const [x, y] = queue.shift()!; const key = `${x},${y}`; if (seen.has(key)) continue; seen.add(key);
    amounts.add(x); amounts.add(y);
    const pourXY = Math.min(x, b - y), pourYX = Math.min(y, a - x);
    queue.push([a, y], [x, b], [0, y], [x, 0], [x - pourXY, y + pourXY], [x + pourYX, y - pourYX]);
  }
  return [...amounts].sort((p, q) => p - q);
}
console.log('jugs 3,5:', reachable(3, 5).join(' '));
console.log('jugs 6,15:', reachable(6, 15).join(' '));
```

```text
jugs 3,5: 0 1 2 3 4 5
jugs 6,15: 0 3 6 9 12 15
```

The search agrees with the invariant: with 6 and 15, only multiples of
their common divisor 3 appear. The search proves it for these sizes; the
invariant proves it for all sizes at once.

### Common mistake

**The wrong way:** using `n % d` as "n mod d" in code that can see negative
n, for example to index a circular buffer with `(i - 1) % size`.

**Why it fails:** for i = 0 this gives −1, an invalid index. The language's
remainder is not the mathematical one for negatives.

**The right way:** normalise with `((n % d) + d) % d`, or keep values
non-negative.

### In real systems

- **Circular buffers and hash tables** map an integer into a range with remainders; negative hash codes are a classic bug.
- **Calendars and clocks** compute weekdays and times with remainders, with the same sign pitfalls for dates before an epoch.
- **Invariant reasoning** like the jug argument is how model checkers prove that bad states are unreachable without enumerating them.

## 8.2 The Greatest Common Divisor

### In one sentence

The gcd of a and b is the largest number dividing both, Euclid's algorithm
finds it fast, and the Pulverizer also writes it as an integer combination
of a and b.

### The idea

gcd(a, b) is the greatest integer dividing both a and b (for a and b not
both zero). gcd(12, 18) = 6, and gcd(a, 0) = a. Two numbers are
**relatively prime** if their gcd is 1.

#### Euclid's algorithm

The key lemma: for b not zero, gcd(a, b) = gcd(b, rem(a, b)). Proof:
since a = qb + r, any number dividing a and b divides r = a − qb, and any
number dividing b and r divides a = qb + r. So the two pairs have exactly
the same common divisors, and therefore the same greatest one.

Euclid's algorithm applies the lemma until the second number is 0, then
returns the first. As a state machine, the state is the pair (x, y), the
transition is (x, y) to (y, rem(x, y)), and the invariant is that gcd(x, y)
stays equal to the original gcd. It terminates because y strictly
decreases. It is also fast: the book shows the first number at least
halves every two steps, so the number of steps is at most about twice the
number of bits of the inputs.

#### The Pulverizer

The book's central theorem: **gcd(a, b) is the smallest positive integer
linear combination of a and b.** Any common divisor divides every
combination, so the gcd is at most the smallest positive one; and the
smallest positive combination divides both a and b (its remainder when
dividing a is a smaller non-negative combination, so must be 0), so it is
at most the gcd.

The **Pulverizer**, an ancient Indian method also known as the extended
Euclidean algorithm, computes the coefficients. Run Euclid, and keep track
of how each remainder is a combination of the original a and b. Each new
remainder is the previous one minus a multiple of the one before, so its
coefficients are computed from the previous coefficients the same way.

#### One solution for all water jug problems

Now the jug puzzle has a complete answer. If gcd(a, b) = g, any amount you
can hold is a multiple of g; and conversely, every multiple of g up to b
is reachable. The book gives a simple strategy, with a less than b: to get
an amount equal to s·a plus a multiple of b, repeatedly fill the small jug
and pour it into the big one, emptying the big one whenever it is full.
After s fills you have poured s·a gallons in total, minus whatever was
emptied in multiples of b. Choose s from the Pulverizer so that s·a ≡ target
modulo b.

### Worked example

**Simple: Euclid with a trace.** gcd(1147, 899), recording each pair:

```ts
function euclid(a: number, b: number, trace: string[] = []): number {
  trace.push(`gcd(${a}, ${b})`); return b === 0 ? a : euclid(b, rem(a, b), trace);
}
const t: string[] = []; console.log(euclid(1147, 899, t), '←', t.join(' = '));
```

```text
31 ← gcd(1147, 899) = gcd(899, 248) = gcd(248, 155) = gcd(155, 93) = gcd(93, 62) = gcd(62, 31) = gcd(31, 0)
```

**Realistic: the Pulverizer, and 4 gallons from 3 and 5.** The recursive
form returns the gcd and its coefficients. On the way back up, if s·b + t·r
= g with r = a − qb, then t·a + (s − qt)·b = g:

```ts
function pulverize(a: number, b: number): [number, number, number] { // returns [g, s, t] with s*a + t*b = g
  if (b === 0) return [a, 1, 0];
  const [g, s, t2] = pulverize(b, rem(a, b));
  return [g, t2, s - qcnt(a, b) * t2];
}
const [g, s, tt] = pulverize(1147, 899); console.log(`${s}·1147 + ${tt}·899 = ${s * 1147 + tt * 899} = gcd ${g}`);
const [, s35, t35] = pulverize(3, 5); console.log(`${s35}·3 + ${t35}·5 = 1, so 4 = ${4 * s35}·3 + ${4 * t35}·5`);
```

```text
11·1147 + -14·899 = 31 = gcd 31
2·3 + -1·5 = 1, so 4 = 8·3 + -4·5
```

The last line reads as a recipe: fill the 3-gallon jug 8
times, pouring into the 5-gallon jug, and empty the big jug 4 times along
the way; what is left is 4 gallons.

### Common mistake

**The wrong way:** computing the gcd by factoring both numbers.

**Why it fails:** for large numbers factoring is believed to be very hard
(8.3), while Euclid needs a number of steps proportional to the number of
digits. Cryptography depends on exactly this gap.

**The right way:** use Euclid for gcds and the Pulverizer for
coefficients and inverses; never factor unless you must.

### In real systems

- **Modular inverses in cryptography** (RSA keys, elliptic curve arithmetic) are computed with the extended Euclidean algorithm.
- **Fraction libraries** reduce a/b by dividing by gcd(a, b) after each operation.
- **Scheduling and graphics:** the gcd of periods tells you when cycles realign, and gcd-based steps generate full cycles through a range, as in some shuffling and hashing schemes.

## 8.3 Prime Mysteries

### In one sentence

Primes are the atoms of the integers, and some of the simplest questions
about them are still unanswered, while one hard-looking problem about them,
factoring, is believed hard enough to protect the internet.

### The idea

A **prime** is an integer greater than 1 whose only positive divisors are 1
and itself. A number greater than 1 that is not prime is **composite**. The
book lists famous questions to show how much is unknown:

- **Infinitely many primes:** proved by Euclid. If there were finitely many,
  multiply them all and add 1; the result is divisible by none of them, but
  it has some prime factor, a contradiction.
- **Goldbach's conjecture:** every even integer greater than 2 is a sum of
  two primes. Checked by computer to enormous bounds, never proved.
- **Twin prime conjecture:** there are infinitely many primes p with p + 2
  also prime. Open, though there has been striking partial progress.
- **Primality testing:** deciding whether a number is prime can be done
  efficiently. Fast randomised tests have been used for decades, and a
  deterministic polynomial-time test was found in 2002.
- **Factoring:** given n = pq for two large primes, no efficient procedure
  is known to find p and q. This conjectured hardness is what RSA relies
  on.

#### The Prime Number Theorem

Primes thin out, but in a precise way. Let π(n) be the number of primes up
to n. The **Prime Number Theorem** says π(n) divided by n / ln n tends to 1
as n grows. As a rule of thumb, around a number n, about one integer in
every ln n is prime. For 300-digit numbers, ln n is roughly 700, so a
random odd number of that size is prime with probability about 1 in 350,
which is why generating RSA primes by "pick random odd numbers and test"
is quick. The proof is well beyond the book.

### Worked example

**Simple: watching π(n) approach n / ln n.** Sieve of Eratosthenes up to
a million, then compare:

```ts
function sieve(n: number): boolean[] {
  const p = new Array(n + 1).fill(true); p[0] = p[1] = false;
  for (let i = 2; i * i <= n; i++) if (p[i]) for (let j = i * i; j <= n; j += i) p[j] = false;
  return p;
}
const isP = sieve(1_000_000);
for (const n of [1000, 10000, 100000, 1000000]) {
  let c = 0; for (let i = 2; i <= n; i++) if (isP[i]) c++;
  console.log(`pi(${n}) = ${c}  n/ln n ≈ ${Math.round(n / Math.log(n))}  ratio ${(c / (n / Math.log(n))).toFixed(3)}`);
}
```

```text
pi(1000) = 168  n/ln n ≈ 145  ratio 1.161
pi(10000) = 1229  n/ln n ≈ 1086  ratio 1.132
pi(100000) = 9592  n/ln n ≈ 8686  ratio 1.104
pi(1000000) = 78498  n/ln n ≈ 72382  ratio 1.084
```

The ratio creeps toward 1, slowly. The theorem says it gets there; it does
not say quickly.

**Realistic: testing the conjectures on small numbers.** Using the same
sieve:

```ts
let goldbachOk = true;
for (let n = 4; n <= 10000; n += 2) { let found = false; for (let p = 2; p <= n / 2; p++) if (isP[p] && isP[n - p]) { found = true; break; } if (!found) goldbachOk = false; }
let twins = 0; for (let p = 2; p + 2 <= 1000000; p++) if (isP[p] && isP[p + 2]) twins++;
console.log('Goldbach holds for every even n from 4 to 10000:', goldbachOk, ' twin prime pairs below a million:', twins);
```

```text
Goldbach holds for every even n from 4 to 10000: true  twin prime pairs below a million: 8169
```

Evidence, not proof. Chapter 1 showed how claims checked on many cases can
still fail; that is why these remain conjectures.

### Common mistake

**The wrong way:** "N = p1 · ... · pk + 1 is always prime."

**Why it fails:** 2 · 3 · 5 · 7 · 11 · 13 + 1 = 30031 = 59 · 509. The
proof only needs N to have a prime factor missing from the list.

**The right way:** read the proof carefully: the new number gives a new
prime factor, not necessarily a new prime itself.

### In real systems

- **Key generation** for RSA picks random large odd numbers and runs fast probabilistic primality tests (Miller–Rabin) until one passes; the prime number theorem says this takes a few hundred tries.
- **Hash table sizes** are often chosen prime so that remainders spread keys evenly.
- **Factoring records** are tracked publicly, and key-size recommendations rise as they fall.

## 8.4 The Fundamental Theorem of Arithmetic

### In one sentence

Every integer greater than 1 can be written as a product of primes in
exactly one way, up to the order of the factors.

### The idea

Existence was proved in chapter 2 with well ordering: a smallest number
with no prime factorisation would be composite, so a product of two smaller
numbers, each of which has a factorisation. Uniqueness is the hard part,
and it is where the gcd pays off.

#### Proving unique factorisation

**Lemma.** If p is prime and p | ab, then p | a or p | b.

**Proof.** Suppose p does not divide a. Since p is prime, its only
divisors are 1 and p, so gcd(p, a) = 1. By 8.2, 1 = sp + ta for some
integers s and t. Multiply by b: b = spb + tab. p divides spb obviously,
and p divides tab because p | ab. So p divides their sum, b.

By induction, if p divides a product of many numbers, it divides one of
them.

**Theorem.** Factorisation into primes is unique, up to order.

**Proof.** By well ordering, suppose n is the smallest number with two
different factorisations, n = p1 · ... · pj = q1 · ... · qk. p1 divides the
right-hand product, so by the lemma it divides some qi, and since qi is
prime, p1 = qi. Cancel it from both sides: n / p1 then has two different
factorisations, and it is smaller than n. Contradiction.

The book notes that uniqueness is not automatic: in some number systems
that extend the integers, factorisation into "irreducible" elements is not
unique, and that is exactly where the lemma fails.

### Worked example

**Simple and realistic: factoring, and seeing uniqueness.** Trial division
gives the factorisation in increasing order, which is a canonical form
because the theorem says there is only one multiset of primes:

```ts
function factor(n: number): number[] { const f: number[] = []; for (let d = 2; d * d <= n; d++) while (n % d === 0) { f.push(d); n /= d; } if (n > 1) f.push(n); return f; }
console.log([360, 1001, 9973, 2 ** 20 - 1].map((n) => `${n} = ${factor(n).join('·')}`).join('  '));
```

```text
360 = 2·2·2·3·3·5  1001 = 7·11·13  9973 = 9973  1048575 = 3·5·5·11·31·41
```

Uniqueness is what makes this useful: gcd(a, b) is the product of the
common prime powers, lcm takes the larger powers, and a | b iff each prime
appears in a at most as often as in b. These all depend on there being one
factorisation to read from. Trial division is fine for six-digit numbers;
for 600-digit ones it is hopeless, which is 8.3's point about factoring.

### Common mistake

**The wrong way:** assuming "if d | ab then d | a or d | b" for any d.

**Why it fails:** it holds only for primes: 6 | 4 · 9 but 6 divides
neither.

**The right way:** for composite d, use the general rule: if d | ab and
gcd(d, a) = 1, then d | b (same proof as the lemma).

### In real systems

- **RSA moduli** are products of exactly two primes; uniqueness means the factorisation is the secret, and there is exactly one.
- **Canonical forms:** representing integers by their prime exponent vectors turns multiplication into addition, which some number-theory libraries use for gcd and lcm of many numbers.
- **Hashing and Gödel numbering:** encoding sequences as products of prime powers (2 to the a, times 3 to the b, ...) is decodable precisely because factorisation is unique.

## 8.5 Alan Turing

### In one sentence

Turing, who founded the theory of computation, also proposed a code built
on number theory, and its first version falls to a single gcd.

### The idea

The book pauses for Alan Turing. In 1936, at 24, he published the paper
that modelled computation mathematically and proved, as in chapter 7, that
some problems no computer can solve, a decade before electronic computers
existed. The book then looks at a less brilliant idea of his: a
number-theoretic code he considered around the start of the Second World
War. Since he never published it, the book reconstructs plausible versions.

#### Turing's code, version 1.0

- **Encoding:** turn the message into a number, for example two digits per
  letter (A = 01, B = 02, ...), then append a few digits so the number is
  prime. Call this m.
- **Key:** a large secret prime k, shared by sender and receiver.
- **Encryption:** send m* = m · k.
- **Decryption:** compute m*/k.

It looks safe: recovering m from m* seems to need factoring a product of
two large primes, and factoring is hard.

#### Breaking Turing's code, version 1.0

But the same key is used for many messages. Given two ciphertexts m1* =
m1·k and m2* = m2·k, their gcd is k (the messages are different primes, so
they share no factor but k). Euclid computes it instantly, and then every
message is readable. No factoring needed.

**Simple: encrypting two messages.** Using BigInt, a small "secret"

against the attacker's actual view (many messages, possibly some known
plaintexts), not against the single hard problem it was designed around.

## 8.6 Modular Arithmetic

### In one sentence

Two integers are congruent modulo n when n divides their difference, and
congruence behaves like equality for addition and multiplication.

### The idea

Gauss introduced the notation: a ≡ b (mod n) means n | (a − b). So 29 ≡ 15
(mod 7), since 7 divides 14, and every integer is congruent to its
remainder: a ≡ rem(a, n) (mod n).

The book's first lemma ties the two views together: **a ≡ b (mod n) iff
rem(a, n) = rem(b, n).** Two numbers are congruent exactly when they leave
the same remainder. That splits the integers into n classes, one per
remainder, so congruence mod n is an **equivalence relation** (reflexive,
symmetric and transitive, the relation properties from chapter 4).

The properties that make congruence useful: if a ≡ b and c ≡ d (mod n),
then

- a + c ≡ b + d (mod n),
- a · c ≡ b · d (mod n),
- and so, by induction, a^k ≡ b^k for every natural k.

Proof for multiplication: ac − bd = a(c − d) + d(a − b), and n divides
both terms. So in any expression built from + and ·, you may replace a
number by anything congruent to it, at any time, without changing the
answer mod n. That is the license to keep numbers small.

### Worked example

**Simple and realistic: random testing the congruence rules, then using
them.** Pick random a, b, and shift each by random multiples of n; sums and
products must keep the same remainders. Then compute the last digit of
7^2026 by tracking only remainders mod 10:

```ts
const rem = (n: number, d: number) => ((n % d) + d) % d;
let ok = true;
for (let trial = 0; trial < 100000; trial++) {
  const n = 2 + Math.floor(Math.random() * 50);
  const a = Math.floor(Math.random() * 2000) - 1000, b = Math.floor(Math.random() * 2000) - 1000;
  const a2 = a + n * (Math.floor(Math.random() * 20) - 10), b2 = b + n * (Math.floor(Math.random() * 20) - 10); // a2 ≡ a, b2 ≡ b
  if (rem(a + b, n) !== rem(a2 + b2, n) || rem(a * b, n) !== rem(a2 * b2, n)) ok = false;
}
console.log('congruence preserved by + and · in 100000 random trials:', ok);
let r = 1; const cycle: number[] = [];
for (let i = 1; i <= 8; i++) { r = rem(r * 7, 10); cycle.push(r); }
console.log('7^1..7^8 rem 10:', cycle.join(' '), ' so 7^2026 ends in', cycle[(2026 - 1) % 4]);
```

```text
congruence preserved by + and · in 100000 random trials: true
7^1..7^8 rem 10: 7 9 3 1 7 9 3 1  so 7^2026 ends in 9
```

The powers of 7 cycle with period 4 mod 10, because 7^4 ≡ 1. Since 2026 =
4 · 506 + 2, 7^2026 ≡ 7² = 49 ≡ 9. A number with about 1,700 digits, and
we never wrote it down.

**The wrong way:** reducing exponents mod n: "7^2026 mod 10 equals 7^(2026

**Why it fails:** congruence is preserved by + and · on the base, not on

wrong (2^10 = 1024 ends in 4, while 2^0 = 1).

**The right way:** reduce the base freely; reduce the exponent only modulo
the cycle length, which Euler's theorem (8.10) will pin down.

### In real systems

- **Checksums** (ISBN, Luhn for card numbers) are congruence checks: the weighted digit sum must be 0 mod 10 or mod 11.
- **Integer overflow** in fixed-width machine arithmetic is arithmetic mod 2^32 or 2^64; addition and multiplication results are still correct mod that power, which is why some hash functions rely on wraparound.
- **Cyclic schedules** (round-robin, rotating logs) reason about time mod a period.

## 8.7 Remainder Arithmetic

### In one sentence

Doing arithmetic on remainders directly, with + and · followed by taking
the remainder, gives a self-contained number system Z_n that obeys almost
all the usual algebra rules.

### The idea

Congruence says we can always replace a number by its remainder. So define
operations on the set from 0 to n − 1 directly:

- i +n j = rem(i + j, n),
- i ·n j = rem(i · j, n).

The **Remainder Lemma** says computing an expression with these operations
gives rem of the ordinary result. In practice, this means: compute with
remainders at every step and the final remainder is right.

#### The ring Z_n

The set of remainders with these operations is called **Z_n**, the
integers modulo n. The book lists the rules it satisfies, all inherited
from the integers: addition and multiplication are associative and
commutative, 0 and 1 are identities, every element has an additive
inverse (n − i), and multiplication distributes over addition. A system
with these rules is a **commutative ring**. The integers, rationals, reals
and integer polynomials are commutative rings too; truth values with OR
and AND are not (OR has no additive inverses), and square matrices are not
(multiplication is not commutative).

What Z_n can lack is the rule "every non-zero element has a multiplicative
inverse", which is where 8.9 picks up. In Z_7, multiplying by 3 shuffles
the remainders; in Z_6, multiplying by 3 collapses them.

**Realistic: arithmetic that never overflows.** To compute a big
expression mod n, like (123456789 · 987654321 + 555) mod 1000, reduce
first: 789 · 321 + 555 = 253269 + 555 = 253824, which is 824 mod 1000. The
true product has 18 digits, but nothing larger than six digits was needed.
Every cryptographic library does this constantly, with n hundreds of digits
long, using modular multiplication so intermediate numbers never grow
beyond twice the size of n.

- **Error-correcting codes** do arithmetic in finite rings and fields.

## 8.8 Turing's Code (Version 2.0)

### In one sentence

Turing's second code multiplies the message by a secret key modulo a
public prime, which fixes version 1.0's gcd leak but falls to an attacker
who knows a single plaintext.

### The idea

The book sets the scene: during the war, Atlantic convoys and German
submarines hunted each other, and information decided the outcome. The
Allies were reading Germany's naval Enigma traffic, thanks to methods first
developed by Polish cryptographers and then scaled up at Bletchley Park,
where Turing led much of the work. That secret was kept for decades.

The book's reconstruction of a second number-theoretic code:

- **Public:** a large prime p.
- **Secret key:** an integer k between 1 and p − 1.
- **Message:** an integer m in the range 0 to p − 1.
- **Encryption:** m* = rem(m · k, p).

Now ciphertexts are remainders, not products, so the gcd trick no longer
reveals k. But how does the receiver decrypt? Dividing by k is not
possible in ordinary integers after the remainder is taken. The answer is a
multiplicative inverse of k in Z_p, which is the subject of 8.9.

The working code for version 2.0 needs an inverse, so it appears in 8.9.

**Realistic:** for convoy traffic, many messages have predictable content:
standard headers, weather reports, sign-offs. Codebreakers call such

the plaintext of at least one message. 8.9.4 shows it does not.

- **Linear operations** are never enough on their own; real ciphers mix linear steps with non-linear ones (S-boxes) precisely so that algebra cannot be run backwards.

## 8.9 Multiplicative Inverses and Cancelling

### In one sentence

k has an inverse modulo n exactly when gcd(k, n) = 1, the Pulverizer
finds it, and you may cancel k from both sides of a congruence exactly
when it has one.

### The idea

A **multiplicative inverse** of k modulo n is a number k⁻¹ with k · k⁻¹ ≡ 1
(mod n). In the rationals every non-zero number has one; in Z_n some do and
some do not.

#### Relative primality

**Theorem.** k has an inverse modulo n iff gcd(k, n) = 1.

- If gcd(k, n) = 1, the Pulverizer gives s and t with sk + tn = 1, so sk ≡
  1 (mod n): s is the inverse.
- If an inverse exists, then sk + tn = 1 for some t, so every common
  divisor of k and n divides 1, and the gcd is 1.

When n is a prime p, every k from 1 to p − 1 is relatively prime to p, so
every non-zero element of Z_p has an inverse. That makes Z_p a **field**,
where division by non-zero elements works.

#### Cancellation

**Corollary.** If gcd(k, n) = 1, then ak ≡ bk (mod n) implies a ≡ b (mod
n). Multiply both sides by k⁻¹. Without relative primality, cancellation
fails: 2 · 3 ≡ 2 · 9 (mod 12), but 3 is not congruent to 9.

Cancellation also proves that multiplying by such a k permutes the
remainders: if k·a and k·b had the same remainder, cancelling gives a ≡ b.

#### Decrypting version 2.0

The receiver computes k⁻¹ in Z_p once with the Pulverizer and then
decrypts with rem(m* · k⁻¹, p) = rem(m · k · k⁻¹, p) = m.

#### Breaking version 2.0

Given one known pair (m, m*), the attacker computes m⁻¹ and then k =
rem(m* · m⁻¹, p). With k, every message is readable. This is the
known-plaintext attack.

#### Turing postscript

The book closes the story of Turing's life: after the war he worked on
early computers and on the question of machine intelligence, posing what
we now call the Turing test. In 1952 he was prosecuted for homosexuality,
then a crime in Britain, and subjected to hormone treatment. He died of
cyanide poisoning in 1954, officially ruled a suicide. Decades later, the
British government formally apologised. The book's point is the human
cost of a society that destroyed one of its greatest minds.

### Worked example

**Simple: units and failed cancellation in Z_12.** These snippets


## 8.10 Euler's Theorem

### In one sentence

For k relatively prime to n, raising k to the power φ(n) gives 1 modulo n,
where φ(n) counts the numbers from 1 to n relatively prime to n; for a
prime p this is Fermat's little theorem, k^(p−1) ≡ 1.

### The idea

**Euler's function** φ(n) is the number of integers in the range 0 to n −
1 that are relatively prime to n, which is the number of invertible
elements of Z_n. So φ(7) = 6, φ(12) = 4 (namely 1, 5, 7, 11), and for any
prime p, φ(p) = p − 1.

**Euler's theorem.** If gcd(k, n) = 1, then k^φ(n) ≡ 1 (mod n).

**Proof, in plain words.** Let the invertible elements of Z_n be r1, ...,
rφ. Multiply each by k (mod n). Because k is invertible, cancellation says
the results are all different, and each is still invertible (a product of
invertible elements is invertible). So multiplying by k just permutes the
list. Therefore the product of all the k·ri equals the product of all the
ri, mod n:

k^φ · (r1 · ... · rφ) ≡ r1 · ... · rφ (mod n).

The product of the ri is invertible, so cancel it: k^φ ≡ 1.

**Fermat's little theorem** is the case n = p prime: k^(p−1) ≡ 1 (mod p)
for k not divisible by p. A handy consequence: the inverse of k mod p is
k^(p−2), since k · k^(p−2) = k^(p−1) ≡ 1.

#### Why it matters for exponents

Euler's theorem answers 8.6's question about exponents: modulo n, exponents
of k may be reduced modulo φ(n) (for k relatively prime to n). That is
exactly the fact RSA decryption uses.

#### Fast exponentiation

To use these theorems on 600-digit numbers you need k^e mod n with e
itself hundreds of digits long. **Repeated squaring** does it: write e in
binary, square repeatedly, and multiply in the squares corresponding to
1 bits, reducing mod n after each step. The number of multiplications is
about twice the number of bits of e, so a 2048-bit exponent takes a few
thousand multiplications, not 2^2048.

#### Computing Euler's function

Counting directly is too slow for big n, but two rules give φ from the
factorisation:

- For a prime power, φ(p^k) = p^k − p^(k−1): out of p^k numbers, the
  multiples of p (there are p^(k−1) of them) are the ones sharing a factor.
- φ is **multiplicative**: if gcd(a, b) = 1, then φ(ab) = φ(a) · φ(b). One way
  to see it is the Chinese Remainder idea that a number mod ab
  corresponds to a pair of remainders mod a and mod b, and it is
  invertible iff both remainders are.

So φ(pq) = (p − 1)(q − 1) for distinct primes p and q, the formula RSA
needs. Note that computing φ(n) this way needs the factorisation of n; for
an RSA modulus, knowing φ(n) is as good as knowing the factors.

### Worked example

**Simple: φ, and Euler's theorem checked on every case up to 60.** With
repeated squaring as `powMod`:

```ts
const gcd = (a: number, b: number): number => (b === 0 ? a : gcd(b, a % b));
const phi = (n: number) => { let c = 0; for (let k = 1; k <= n; k++) if (gcd(k, n) === 1) c++; return c; };
function powMod(b: bigint, e: bigint, n: bigint): bigint { let r = 1n; b %= n; while (e > 0n) { if (e & 1n) r = (r * b) % n; b = (b * b) % n; e >>= 1n; } return r; }
console.log('phi(1..12):', Array.from({ length: 12 }, (_, i) => phi(i + 1)).join(' '));

console.log(`Euler's theorem checked on ${checks} pairs (n ≤ 60):`, eulerOk);
```


The formulas agree with brute force: φ(49) = 49 − 7 = 42, and φ(1000) =

**Realistic: Fermat as a primality test, and its blind spot.** If 2^(n−1)
is not 1 mod n, then n is certainly composite. The converse fails for
some composites:

```ts

```

even though it is 3 · 11 · 17: it is a Carmichael number, which passes the
Fermat test for every base relatively prime to it. Real primality tests
(Miller–Rabin) add an extra check on square roots of 1 that catches these.

## 8.11 RSA Public Key Encryption

### In one sentence

RSA lets anyone encrypt with a public key (n, e) while only the holder of
d, the inverse of e modulo (p − 1)(q − 1), can decrypt, and breaking it
appears to need factoring n.

### The idea

Turing's codes needed a shared secret. Public-key cryptography, proposed
by Diffie and Hellman and made concrete by Rivest, Shamir and Adleman in
the 1970s, removes that: the receiver publishes a key anyone may use to
encrypt, and keeps a matching secret key to decrypt.

**Beforehand, the receiver:**

1. Picks two distinct large primes p and q (hundreds of digits each) and
   computes n = pq.
2. Picks e relatively prime to (p − 1)(q − 1).
3. Computes d, the inverse of e modulo (p − 1)(q − 1), with the Pulverizer.
4. Publishes (e, n) as the public key and keeps d (and p, q) secret.

**Encrypting** a message m in the range 0 to n − 1: send m' = rem(m^e, n).

**Decrypting:** compute rem(m'^d, n), which equals m.

**Why decryption works.** e·d = 1 + t(p − 1)(q − 1) for some t. Look mod p
first. If p does not divide m, Fermat says m^(p−1) ≡ 1, so m^(ed) = m ·
(m^(p−1))^(t(q−1)) ≡ m (mod p). If p divides m, both sides are 0 mod p. So
m^(ed) ≡ m (mod p) always, and likewise mod q. A number congruent to m
mod both p and q differs from m by a multiple of p and of q, hence of pq
= n. So m^(ed) ≡ m (mod n).

**Why it seems secure.** To find d from (e, n), it is enough to know (p −
1)(q − 1) = φ(n), and knowing φ(n) lets you factor n. The best known ways
to recover messages without d amount to factoring n, which no one knows how
to do efficiently for well-chosen large primes. That is a belief backed by
decades of effort, not a theorem.

### Worked example

**Simple: RSA with toy primes.** The primes here are small enough to
factor instantly, so this is for understanding only:

```ts
const p = 104729n, q = 1299709n, n = p * q, ph = (p - 1n) * (q - 1n), e = 65537n;
function inv(a: bigint, m: bigint): bigint { let [r0, r1, s0, s1] = [a % m, m, 1n, 0n]; while (r1) { const t = r0 / r1; [r0, r1] = [r1, r0 - t * r1]; [s0, s1] = [s1, s0 - t * s1]; } return ((s0 % m) + m) % m; }
const d = inv(e, ph);
const msg = 805121215n; // "HELLO" as two-digit letters
const c = powMod(msg, e, n);
console.log(`n = ${n}, d = ${d}`);
console.log(`encrypt ${msg} → ${c}, decrypt → ${powMod(c, d, n)}`);
console.log('e·d rem phi(n) =', (e * d) % ph);
```

```text
n = 136117223861, d = 108704485601
encrypt 805121215 → 17803663500, decrypt → 805121215
e·d rem phi(n) = 1n
```

e = 65537 (2^16 + 1) is the value used by most real keys: it is prime,
and its binary form has only two 1 bits, so encryption is fast.

**Realistic: what real RSA adds.** Textbook RSA as above is deterministic
(the same message always gives the same ciphertext) and malleable
(multiplying ciphertexts multiplies messages). Real systems therefore pad
messages with randomness in a structured way (OAEP) before exponentiating,
use 2048-bit or larger n, and mostly use RSA only to protect a random
symmetric key or to sign a hash, not to encrypt bulk data. Many modern
protocols have moved to elliptic-curve key exchange, but the number theory
underneath is this chapter's.

### Common mistake

**The wrong way:** using a tiny e with no padding to send the same message
to several recipients, or encrypting a small m with e = 3 so that m³ is
less than n.

**Why it fails:** if m³ is less than n, no reduction happens and the cube
root of the ciphertext is the message. With three recipients, the Chinese
Remainder Theorem recovers m³ exactly.

**The right way:** always use randomised padding, and use vetted libraries
rather than textbook formulas.

### In real systems

- **TLS certificates** commonly carry RSA public keys; browsers verify RSA signatures on them for every HTTPS connection.
- **SSH and code signing** use RSA or elliptic-curve keys generated exactly as above, with primes from random search and Miller–Rabin.
- **Post-quantum migration:** Shor's algorithm would factor n on a large quantum computer, which is why standards bodies are moving to lattice-based schemes.

## 8.12 What has SAT got to do with it?

### In one sentence

A fast SAT solver would give a fast factoring algorithm, and with it a way
to break RSA, which is why P versus NP matters to everyone who uses
encryption.

### The idea

Chapter 3 claimed that an efficient SAT test would break secret codes.
The book cashes the claim here.

A multiplication-checking circuit is routine to build: inputs are the bits
of i, j and k, and the output is 1 iff i · j = k and both i and j are
greater than 1. It uses on the order of n² gates for n-bit numbers, and
like any circuit it can be written as a propositional formula of about the
same size.

To factor m, fix k = m in the inputs. Then ask the SAT solver: can the
remaining inputs be set to make the output 1? If not, m is prime. If yes,
fix the first bit of i to 1 and ask again; if still satisfiable keep it,
otherwise set it to 0. Repeat for every bit of i. After n questions,
i is fully determined and is a factor of m.

So if SAT could be solved in polynomial time, factoring would be
polynomial too (n times the SAT cost), and RSA would fall. The reverse is
not known: factoring might be easy even if SAT is hard. That is why RSA's
security rests on a belief about factoring specifically.

### Worked example

**Simple and realistic: factoring with a satisfiability oracle.** The
"oracle" below is brute force, so it is slow; what matters is that the
factoring procedure only asks it yes/no questions, one per bit:

```ts
let oracleCalls = 0;
function satisfiable(m: number, nBits: number, fixedPrefix: number[]): boolean {
  oracleCalls++;
  const free = nBits - fixedPrefix.length;
  for (let rest = 0; rest < 1 << free; rest++) {
    const i = fixedPrefix.reduce((acc, b) => acc * 2 + b, 0) * (1 << free) + rest;
    if (i > 1 && m % i === 0 && m / i > 1 && m / i < 1 << nBits) return true; // some j makes the circuit output 1
  }
  return false;
}
function factorWithOracle(m: number, nBits: number): [number, number] | null {
  oracleCalls = 0; const bits: number[] = [];
  if (!satisfiable(m, nBits, [])) return null; // m is prime (or too big)
  for (let k = 0; k < nBits; k++) bits.push(satisfiable(m, nBits, [...bits, 1]) ? 1 : 0);
  const i = bits.reduce((acc, b) => acc * 2 + b, 0); return [i, m / i];
}
for (const m of [221, 899, 3127, 65021, 65537]) {
  const r = factorWithOracle(m, 16);
  console.log(`${m}: ${r ? r.join(' × ') : 'no factorisation (prime)'} after ${oracleCalls} oracle calls`);
}
```

```text
221: 17 × 13 after 17 oracle calls
899: 31 × 29 after 17 oracle calls
3127: 59 × 53 after 17 oracle calls
65021: 5911 × 11 after 17 oracle calls
65537: no factorisation (prime) after 1 oracle calls
```

Every factorisation took 17 questions: one to check that a factor exists,
then one per bit of the 16-bit i. The greedy choice of 1 bits finds the
largest factor, which is why 65021 = 11 · 23 · 257 came out as 5911 × 11.
Replace the brute-force oracle with a polynomial-time SAT solver and this
loop would factor numbers of any size in polynomial time.

### Common mistake

**The wrong way:** "RSA is secure because factoring is NP-complete."

**Why it fails:** factoring is in NP, but it is not known (or widely
believed) to be NP-complete. It could be easy even if P is not NP.

**The right way:** RSA rests on the specific conjecture that factoring is
hard; SAT being hard is necessary for that, not sufficient.

### In real systems

- **SAT solvers** are used heavily in industry (hardware verification, package dependency resolution, scheduling) and solve huge practical instances, but nobody has a solver that is fast on all instances, including those encoding large factorisations.
- **Cryptanalysis** does use SAT solvers on reduced versions of hash functions and ciphers, which is part of how designers check their safety margins.

<Levels label="Chapter 8, Number Theory">
<Level name="Beginner" depth={3}>

The smallest working idea: integers divide each other or leave a
remainder, and doing arithmetic "mod n" means keeping only remainders. You
can add and multiply remainders and reduce at every step without changing
the final remainder.

Try it: compute the last two digits of 3^20 by multiplying by 3 twenty
times and keeping only the last two digits each time, then check with a
BigInt in Node.

The beginner's mistake is trusting the language's `%` with negative
numbers, or reducing an exponent mod n instead of the base.

</Level>
<Level name="Intermediate" depth={3}>

The working toolkit is the chain gcd → linear combination → inverse.
Euclid computes gcds fast; the Pulverizer writes the gcd as s·a + t·b;
when the gcd is 1, s is an inverse of a mod b. Inverses give cancellation
and division in Z_n, and with a prime modulus every non-zero element is
invertible.

Practise by solving linear congruences a·x ≡ c (mod n): check the gcd,
divide through if needed, multiply by an inverse. Then solve water jug
puzzles with the same tools.

</Level>
<Level name="Advanced" depth={3}>

Euler's theorem is the structural fact: the units of Z_n form a group of
size φ(n), and multiplying by a unit permutes them, which forces k^φ(n) ≡
1. RSA's correctness is Fermat applied modulo each prime and the two
results combined. Being able to rederive RSA from these three lemmas, on
paper, is the mark of having understood the chapter.

The advanced practical skill is exponentiation by repeated squaring with
all intermediate values reduced, and knowing that its running time is
proportional to the number of bits, not the size of the exponent.

</Level>
<Level name="Edge cases" depth={3}>

- **gcd(0, 0):** undefined by the "greatest divisor" definition, since every integer divides 0; libraries usually return 0 by convention.
- **Messages sharing a factor with n in RSA:** still decrypt correctly, by the argument mod p and mod q separately.
- **m = 0 or 1 in RSA:** encrypt to themselves; real padding avoids such fixed points.
- **Negative operands:** rem must be normalised to the range 0 to n − 1 before using it as an index or comparing remainders.

</Level>
<Level name="Corner cases" depth={3}>

- **Carmichael numbers** pass the Fermat test for every base relatively prime to them; a Fermat-only primality test is wrong on them.
- **p = q in RSA:** then n = p² and φ(n) = p(p − 1), not (p − 1)², and the key is trivially broken by a square root.
- **Composite moduli for "prime field" code:** if a supposed prime p is composite, some elements lack inverses and the inverse routine fails or silently returns garbage.
- **Number size:** `Number` in JavaScript is exact only up to 2^53; products of two numbers above about 94 million lose precision, which is why the cryptographic snippets use BigInt.

</Level>
<Level name="Production level" depth={3}>

In production, number theory lives inside vetted libraries. The engineer's
job is to choose parameters (key sizes, padding modes, exponent e), to
generate keys with a real source of randomness, to avoid textbook RSA,
and to use constant-time operations so timing does not leak secret bits.
The failures seen in practice are almost never wrong mathematics; they
are reused keys, bad randomness (shared primes across keys, as with
version 1.0), missing padding, and side channels.

For non-cryptographic code, the same tools show up in hashing (prime
moduli, multiplicative hashing), checksums, scheduling with periods and
gcds, and exact fraction arithmetic.

</Level>
<Level name="Mindset" depth={3}>

Two habits. First, think in remainders: if only a value mod n matters,
reduce early, and many big-number problems become small ones. Second,
think like an attacker: every code in this chapter looked secure against
the problem it was designed around and fell to a different, easier
question (a gcd, a single inverse). Ask what an adversary actually sees.

</Level>
<Level name="System design" depth={3}>

When designing a system that needs secrecy or authenticity, compose
standard primitives rather than inventing schemes: TLS for transport,
well-reviewed libraries for signatures and key exchange, key management
that rotates keys and never reuses nonces. Treat key sizes as parameters
that will change over time (as factoring improves, and as post-quantum
schemes replace RSA), and design so that algorithms can be swapped without
redesigning the protocol.

</Level>

Long-term, this chapter is the entry to cryptography, coding theory and

## Questions people ask

**Why does the Pulverizer have such an odd name?** The book uses the name
of an ancient Indian method, kuttak, which translates roughly as
"pulveriser". It is the same algorithm usually called the extended
Euclidean algorithm.

**Is RSA proven secure?** No. Its security rests on the belief that
factoring large numbers is infeasible. No proof exists, and a large
quantum computer would break it.

**Why is 65537 used as e so often?** It is prime and has only two 1 bits,
so encryption by repeated squaring needs very few multiplications, and it
is large enough to avoid the small-exponent pitfalls of e = 3.

**Do I need to know number theory to use HTTPS?** No; libraries handle
it. You need it to understand why parameters, padding and randomness
matter, and to read security advisories with judgement.

**What is the difference between rem and mod?** rem(n, d) is a number;
"a ≡ b (mod n)" is a relation between numbers. Many people also write "n
mod d" for the remainder, which is fine as long as negatives are handled.

**Why are primes so important?** Every integer factors uniquely into them,
Z_p has inverses for every non-zero element, and Fermat's theorem holds
mod a prime. Those three facts are all RSA needs.

## Key takeaways

- a | b means b is a multiple of a; a common divisor of a and b divides every combination s·a + t·b.
- The Division Theorem gives a unique quotient and remainder with 0 ≤ r less than d; program `%` may disagree for negatives.
- Euclid's algorithm computes gcd(a, b) in a number of steps proportional to the number of digits, and the Pulverizer writes the gcd as a combination.
- The gcd is the smallest positive linear combination, which settles the water jug puzzle: reachable amounts are exactly multiples of the gcd.
- Every integer greater than 1 factors uniquely into primes; the key lemma is that a prime dividing a product divides a factor.
- Congruence mod n respects + and ·, so you can reduce at every step; Z_n is a commutative ring.
- k has an inverse mod n iff gcd(k, n) = 1; cancellation is allowed exactly for such k.
- Euler: k^φ(n) ≡ 1 (mod n) for k relatively prime to n; Fermat is the prime case.
- RSA: public (e, n), secret d = e⁻¹ mod (p − 1)(q − 1); correctness from Fermat, security from the belief that factoring is hard.
- Turing's codes fell to a gcd and to one known plaintext: analyse ciphers against what attackers actually see.
- A fast SAT solver would factor numbers and break RSA.

## Glossary

- **a | b:** a divides b; b = ka for an integer k.
- **Linear combination:** s·a + t·b with integer s and t.
- **Division Theorem:** n = qd + r with a unique q and 0 ≤ r less than d.
- **qcnt(n, d), rem(n, d):** the quotient and remainder of the Division Theorem.
- **gcd(a, b):** the greatest common divisor.
- **Relatively prime:** having gcd 1.
- **Euclid's algorithm:** gcd(a, b) = gcd(b, rem(a, b)), repeated until the second number is 0.
- **Pulverizer:** the extended Euclidean algorithm, giving the gcd as a combination.
- **Prime:** an integer greater than 1 with no positive divisors except 1 and itself.
- **Composite:** an integer greater than 1 that is not prime.
- **Fundamental Theorem of Arithmetic:** unique factorisation into primes.
- **Prime Number Theorem:** π(n) is asymptotically n / ln n.
- **Congruence, a ≡ b (mod n):** n divides a − b.
- **Z_n:** the remainders 0 to n − 1 with + and · mod n.
- **Commutative ring:** a number system with the usual rules for +, · and additive inverses.
- **Multiplicative inverse, k⁻¹:** a number with k · k⁻¹ ≡ 1 (mod n).
- **Unit:** an element of Z_n with a multiplicative inverse.
- **Euler's function φ(n):** the number of units in Z_n.
- **Euler's theorem:** k^φ(n) ≡ 1 (mod n) for k relatively prime to n.
- **Fermat's little theorem:** k^(p−1) ≡ 1 (mod p) for prime p not dividing k.
- **Repeated squaring:** computing powers with about two multiplications per bit of the exponent.
- **RSA:** the public-key scheme with keys (e, n) and d.
- **Known-plaintext attack:** using a known message-ciphertext pair to recover the key.
- **Carmichael number:** a composite that passes the Fermat test for all relatively prime bases.
