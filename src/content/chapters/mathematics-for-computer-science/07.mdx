Chapter 4 compared the sizes of finite sets with arrows instead of
counting. This chapter keeps the arrows and drops the counting, because
infinite sets cannot be counted. The surprises come fast: an infinite set
can be the same size as a proper part of itself, the integers and the
rationals are no bigger than ℕ, and yet the subsets of ℕ, and the real
numbers, are strictly bigger. The same diagonal trick that proves this then
proves the result every programmer should know: no program can decide, for
every program, whether it halts. The chapter ends with the paradox that
forced mathematicians to put set theory on axioms, and a short, honest
answer to "does a programmer need any of this?".

## 7.1 Infinite Cardinality

### In one sentence

Two sets are the same size when there is a bijection between them, and
with that definition some infinite sets turn out to be strictly bigger than
others.

### The idea

Georg Cantor's idea, in the 1870s and after, was to take chapter 4's
mapping rules as definitions for infinite sets. A and B have the "same
size" when A bij B. A is "at least as big" as B when A surj B. And the book
defines **A strict B** ("A is strictly smaller than B") to mean NOT (A surj
B): there is no surjective function from A onto B.

For finite sets, A strict B is exactly |A| less than |B|, by the mapping
rules. For infinite sets it is a new definition, and the book warns that we
are only comparing sizes, never defining what "the size" of an infinite set
is.

Some finite-set facts carry over unchanged. For any sets:

- surj is transitive: if A surj B and B surj C, then A surj C (compose the surjections).
- bij is symmetric and transitive.
- A surj B iff B inj A, by reversing arrows, as in chapter 4.

And one fact that sounds obvious but is a real theorem, the
**Schröder–Bernstein theorem**: if A surj B and B surj A, then A bij B. For
finite sets this is just arithmetic. For infinite sets the bijection has
to be built by a clever argument, and the book does not prove it in the
text. From these, strict is transitive too: A strict B and B strict C
imply A strict C.

#### Infinity is different

The book's first surprise: if A is infinite and b is not in A, then A bij A
∪ `{b}`. Adding one element does not change the size. The proof builds
the bijection: since A is infinite, pick distinct elements a₀, a₁, a₂, ...
from it forever. Send b to a₀, each aₙ to aₙ₊₁, and every other element of
A to itself. Every element of A is hit exactly once.

In fact this characterises infinite sets: A is infinite iff it is the same
size as A plus one extra element. A finite set never is, since its count
goes up by one. This is the "hotel with infinitely many rooms" puzzle:
a full hotel can take a new guest by moving everyone from room n to room n
+ 1.

#### Countable sets

A set C is **countable** if its elements can be listed as c₀, c₁, c₂, ...
(possibly with repeats, possibly ending). Formally the book defines C to be
**countably infinite** if ℕ bij C, and **countable** if it is finite or
countably infinite. Equivalently, C is countable iff ℕ surj C: some list,
repeats allowed, covers every element.

Many sets that look bigger than ℕ are countable:

- **ℤ:** list 0, −1, 1, −2, 2, ... alternating signs.
- **ℕ × ℕ:** list the pairs diagonal by diagonal, by the sum a + b: (0, 0),
  then (1, 0), (0, 1), then (2, 0), (1, 1), (0, 2), and so on. Each diagonal
  is finite, so every pair appears.
- **The rationals:** every nonnegative rational is a/b for a pair, so
  listing ℕ × ℕ and skipping invalid or repeated fractions lists them all;
  interleave with negatives for ℚ.
- **Finite strings over a finite or countable alphabet,** and finite
  sequences of positive integers: list by length (or by length plus largest
  entry), finitely many per group.

The pattern: if you can break a set into countably many finite pieces, it
is countable.

#### Power sets are strictly bigger

**Cantor's theorem.** For every set A, A strict pow(A). No function from A
onto its power set exists.

The proof is short. Let g be any function from A to pow(A). Define the set
D of elements a of A such that a is not in g(a). D is a subset of A. If g
were onto, some element d would have g(d) = D. Ask whether d is in D:

- If d is in D, then by the definition of D, d is not in g(d) = D.
- If d is not in D, then d is not in g(d), so by definition d is in D.

Both cases contradict, so no d maps to D, and g is not onto. Since g was
arbitrary, no surjection exists.

Consequences the book draws:

- pow(ℕ) is uncountable.
- The set of infinite bit strings is uncountable, because infinite bit
  strings correspond to subsets of ℕ exactly as finite bit strings did to
  subsets in 4.5.
- ℝ is uncountable: map each real to the bits of its binary expansion (a
  partial function, but onto the bit strings that matter), so ℝ surj a set
  that is uncountable. A surjection from A onto an uncountable set makes A
  uncountable; a surjection from a countable set makes the target
  countable.
- Iterating gives an endless ladder: ℕ, pow(ℕ), pow(pow(ℕ)), ..., each
  strictly bigger than the last.

#### Diagonal argument

Cantor's proof is the first of the **diagonal arguments**. Picture any list
of infinite bit strings as an infinite table, row n being the n-th string.
Build a new string by going down the diagonal and flipping each bit: its
n-th bit is the opposite of row n's n-th bit. That string differs from row
n at position n, for every n, so it is not in the list. No list contains
all infinite bit strings.

The set D in Cantor's proof is exactly this diagonal: a is in D iff a is
not in g(a), "flip the bit at position (a, a)".

### Worked example

**Simple: explicit bijections for ℤ and ℕ × ℕ.** A bijection is best
shown with its inverse and a round-trip test:

```ts
const zOf = (n: number) => (n % 2 === 0 ? n / 2 : -(n + 1) / 2);
const nOf = (z: number) => (z >= 0 ? 2 * z : -2 * z - 1);
console.log(Array.from({ length: 9 }, (_, n) => zOf(n)).join(' '),
  [...Array(2001)].every((_, i) => nOf(zOf(i)) === i && zOf(nOf(i - 1000)) === i - 1000));
const pair = (a: number, b: number) => ((a + b) * (a + b + 1)) / 2 + b;
function unpair(n: number): [number, number] {
  const w = Math.floor((Math.sqrt(8 * n + 1) - 1) / 2); const t = (w * (w + 1)) / 2; const b = n - t;
  return [w - b, b];
}
console.log(Array.from({ length: 10 }, (_, n) => `${n}→(${unpair(n)})`).join(' '));
let okPair = true;
for (let a = 0; a < 300; a++) for (let b = 0; b < 300; b++) {
  const [x, y] = unpair(pair(a, b)); if (x !== a || y !== b) okPair = false;
}
console.log('pair/unpair round trip on 300×300:', okPair);
```

```text
0 -1 1 -2 2 -3 3 -4 4 true
0→(0,0) 1→(1,0) 2→(0,1) 3→(2,0) 4→(1,1) 5→(0,2) 6→(3,0) 7→(2,1) 8→(1,2) 9→(0,3)
pair/unpair round trip on 300×300: true
```

The pairing function walks the diagonals in order: diagonal w holds the w +
1 pairs with a + b = w, and the triangular number w(w + 1)/2 is where it
starts. This specific bijection is the Cantor pairing function.

**Realistic: listing the rationals, and checking Cantor on a small set.**
Walking ℕ × ℕ and keeping fractions in lowest terms lists every nonnegative
rational exactly once. Then, for A = `{0, 1, 2}`, try every one of the 8³ =
512 functions from A to pow(A) and check whether any reaches the diagonal
set D built from it:

```ts
const gcd = (a: number, b: number): number => (b === 0 ? a : gcd(b, a % b));
const rats: string[] = [];
for (let n = 0; rats.length < 12; n++) { const [a, b] = unpair(n); if (b > 0 && gcd(a, b) === 1) rats.push(`${a}/${b}`); }
console.log(rats.join(' '));
const A = [0, 1, 2];
const subsets = Array.from({ length: 8 }, (_, m) => A.filter((i) => (m >> i) & 1));
let functions = 0, hit = 0;
for (let code = 0; code < 512; code++) {
  const g = [code % 8, Math.floor(code / 8) % 8, Math.floor(code / 64)].map((m) => subsets[m]);
  const D = A.filter((a) => !g[a].includes(a));
  functions++;
  if (g.some((s) => s.length === D.length && s.every((x) => D.includes(x)))) hit++;
}
console.log('functions A → pow(A):', functions, 'that reach the diagonal set D:', hit);
```

```text
0/1 1/1 2/1 1/2 3/1 1/3 4/1 3/2 2/3 1/4 5/1 1/5
functions A → pow(A): 512 that reach the diagonal set D: 0
```

All 512 functions miss their own diagonal set, exactly as the proof says.
For a finite set this is no surprise (8 subsets, 3 elements), but the code
never used counting: it used only the diagonal construction, which is why
the same argument works for infinite sets.

### Common mistake

**The wrong way:** "ℕ is a proper subset of ℤ, so ℤ is bigger", or "between
any two rationals there are infinitely many more, so there must be more
rationals than naturals".

**Why it fails:** for infinite sets, a proper subset can be the same size
(that is what infinite means, per 7.1.1), and density says nothing about
size. Size is decided only by whether the right kind of function exists.

**The right way:** to show A and B are the same size, build a bijection
(or surjections both ways and invoke Schröder–Bernstein). To show A is
strictly smaller, show no surjection exists, usually by a diagonal argument.

### In real systems

- **Pairing functions** like the one above are used to encode pairs or tuples of integers as single integers, for example in hash keys, database sharding schemes and in theory to encode programs as numbers.
- **Enumerating search spaces fairly:** walking ℕ × ℕ diagonal by diagonal is how you interleave infinitely many infinite streams so every element appears, a technique used in logic programming and in property-based test generators.
- **Floating-point numbers** are a finite set standing in for the uncountable reals, which is the deepest reason rounding is unavoidable: almost all reals have no exact representation in any finite or even countable scheme.
- **Countability of programs:** every program is a finite string, so there are countably many programs, but uncountably many functions from ℕ to `{0, 1}`. Almost all such functions cannot be computed by any program.

## 7.2 The Halting Problem

### In one sentence

There is no program that can look at any program and its input and
correctly say whether it will eventually stop, and the proof is the
diagonal argument with programs in place of rows.

### The idea

#### Programs as strings

The book makes the setting concrete with **string procedures**: programs
that take a string as input and either halt with some result or run
forever. A program is itself a string (its source text), so a program can
be given another program, or itself, as input. Write P_s for the procedure
whose source text is s.

A set of strings R is **recognisable** if some procedure halts on exactly
the strings in R: given a member it eventually stops, given a non-member
it runs forever. That is a weak requirement. The procedure does not even
need to say "no"; it is allowed to hang.

Many sets are recognisable. "Strings that are valid TypeScript" is (run a
parser, halt if it parses, loop otherwise). "Programs that halt on the
empty input" is recognisable too: simulate the program, and halt when it
does. The question is whether every set we care about is.

#### The diagonal set

Define **No-halt** to be the set of strings s such that P_s does not halt
when given s itself as input. This is the flipped diagonal again: rows are
programs, columns are inputs, the entry (s, t) is "P_s halts on t", and
No-halt flips the diagonal entries.

**Theorem.** No-halt is not recognisable.

**Proof.** Suppose some procedure P_r recognises No-halt: for every string
s, P_r halts on s iff s is in No-halt. Now feed P_r its own text r:

- P_r halts on r iff r is in No-halt (because P_r recognises No-halt);
- r is in No-halt iff P_r does not halt on r (definition of No-halt).

Chaining: P_r halts on r iff P_r does not halt on r. Contradiction. So no
such r exists.

The proof is Cantor's, line for line: the set of strings recognised by
P_s plays the role of g(s), and No-halt plays the role of D. Every
recognisable set is the "row" of some procedure, and No-halt differs from
every row on the diagonal.

#### From No-halt to the halting problem

The set **Halt** of pairs (s, t) where P_s halts on t is recognisable:
simulate. But it is not **decidable**: no procedure always halts and
answers yes or no correctly. If such a decider existed, you could use it
to recognise No-halt: on input s, ask the decider about (s, s); if it says
"does not halt", halt; otherwise loop forever. That would recognise
No-halt, which is impossible. So no halting decider exists.

This is a **reduction**: we turned a hypothetical solution to one problem
into a solution to another we already know is impossible. It is the
standard way the impossibility spreads to other questions.

#### What it means for program checkers

The book draws the practical consequence. Many properties of programs
reduce to halting: "does this program ever divide by zero?", "does it ever
print the string 'error'?", "does it ever access an array out of bounds?".
Given a halting question about P on t, build a program that runs P on t
and then does the bad thing; the bad thing happens iff P halts on t. A
perfect checker for the bad thing would decide halting.

So no type checker or static analyser can, for every program, exactly
determine whether a run-time error happens. Every real tool makes one of
two compromises:

- **Sound but incomplete:** it rejects every program that could go wrong,
  and some that could not (a type checker rejecting code that would have
  worked).
- **Complete but unsound:** it only flags errors it is sure of, and misses
  some (a linter's heuristics).

Properties that only depend on a bounded amount of running ("halts within
100 steps", "uses at most a gigabyte in its first second") are decidable:
just run that far. The undecidable ones are about the unbounded future of
a program. The broad generalisation of this, that every non-trivial
property of what a program computes is undecidable, is known as Rice's
theorem; the book does not prove it, but the reduction above is its
essence.

### Worked example

**Simple: three would-be deciders, all defeated.** Model programs as
TypeScript generators: each `yield` is one step, and returning means
halting. A decider takes a program and an input and claims to predict
halting. From any decider, build the diagonal program: ask the decider
about itself on itself, then do the opposite.

```ts
type Program = (input: Program) => Generator<void, void, void>;
const run = (p: Program, x: Program, budget: number) => {
  const it = p(x); for (let i = 0; i < budget; i++) if (it.next().done) return `halted after ${i + 1} steps`;
  return `still running after ${budget} steps`;
};
type Decider = (p: Program, x: Program) => boolean; // claims: true = halts
const troll = (decide: Decider): Program => function* (p) {
  if (decide(p, p)) { while (true) yield; } // decider says p halts on itself: loop forever
  // decider says p loops on itself: halt at once
};
const candidates: Record<string, Decider> = {
  'always says halts': () => true,
  'always says loops': () => false,
  'simulate 1000 steps': (p, x) => { const it = p(x); for (let i = 0; i < 1000; i++) if (it.next().done) return true; return false; },
};
for (const [name, d] of Object.entries(candidates)) {
  const T = troll(d);
  try {
    console.log(`${name}: predicts T(T) ${d(T, T) ? 'halts' : 'loops'}; actually ${run(T, T, 100000)}`);
  } catch (e) {
    console.log(`${name}: never answers; asking it about T(T) recurses until ${(e as Error).name}`);
  }
}
```

```text
always says halts: predicts T(T) halts; actually still running after 100000 steps
always says loops: predicts T(T) loops; actually halted after 1 steps
simulate 1000 steps: never answers; asking it about T(T) recurses until RangeError
```

**Realistic: reading the three failures.** The first two deciders answer
and are wrong, in opposite directions, which is the theorem working as
designed. The third is the interesting one. A decider that simulates its
input has to simulate T running on T, and T's first act is to call the
decider on T, which simulates T again, without end. The would-be decider
never returns: it is not a decider at all, because it does not halt on
every input. Any real decider must fail in one of these two ways: give a
wrong answer, or never answer. Note that "still running after 100000
steps" in the first line is only evidence; we know it loops forever by
reading the code, not by running it, which is the whole point.

### Common mistake

**The wrong way:** "the halting problem means we can never tell whether a
program halts", so tools that detect infinite loops must be useless.

**Why it fails:** the theorem says no single procedure answers correctly
for every program. For particular programs, and for large useful classes
(loops with bounded counters, structurally recursive functions like
chapter 6's), halting is easy to prove. Termination checkers in proof
assistants accept huge numbers of real programs.

**The right way:** read the theorem as "every analysis will have cases it
cannot settle", and design tools that are sound for a useful class and
honest ("I cannot tell") outside it.

### In real systems

- **Type systems** are deliberately conservative: TypeScript's checker rejects some correct programs and, with `any` and casts, accepts some wrong ones; it cannot be both exact and automatic.
- **Timeouts** everywhere (HTTP request limits, CI job limits, watchdog timers) are the engineering answer to undecidable halting: replace "will it stop?" with "did it stop within N?", which is decidable.
- **Proof assistants and total languages** (Coq, Agda, Lean) restrict recursion to forms that provably terminate, giving up some programs to guarantee halting.
- **Antivirus and malware detection** cannot decide "does this program ever do something malicious?" in general, which is why they rely on signatures, sandboxes and heuristics.

## 7.3 The Logic of Sets

### In one sentence

Letting any property define a set leads to a contradiction, so modern
mathematics builds sets from a short list of axioms, ZFC, that allow the
useful constructions and block the paradoxical ones.

### The idea

#### Russell's paradox

Before about 1900, mathematicians used sets freely: any property P
defined the set of all things with property P. Bertrand Russell pointed
out what that allows. Let W be the set of all sets that are not members of
themselves. Is W a member of itself?

- If W ∈ W, then W has W's defining property, so W ∉ W.
- If W ∉ W, then W has the defining property, so W ∈ W.

Either way, a contradiction. This is the diagonal argument a third time:
W is the flipped diagonal of the "is a member of" table, and asking about
W's own row breaks it.

The conclusion is that "the set of all x with property P" cannot be
allowed for every P. Something in naive set theory has to go. The book
notes the cheap patch: only allow collecting elements from a set you
already have, "the elements of A with property P". Then the Russell
construction gives the subset of A of sets not containing themselves,
and the argument only proves that this subset is not an element of A,
which is no paradox. (It does prove there is no set of all sets.)

#### The ZFC axioms

The standard foundation is **Zermelo–Fraenkel set theory with the Axiom
of Choice (ZFC)**. The book lists the axioms; in plain words they say:

- **Extensionality:** two sets with the same elements are equal. A set is
  nothing but its members.
- **Pairing:** for any x and y there is a set `{x, y}`.
- **Union:** for any set of sets, there is a set containing all their
  elements.
- **Infinity:** there is an infinite set, built as the set containing the
  empty set and closed under "x goes to x ∪ `{x}`". This set is ℕ.
- **Subset (comprehension):** for any set A and property P, the elements of
  A with P form a set. Note the "of A": this is the patch.
- **Power set:** every set has a power set.
- **Replacement:** the image of a set under a function defined by a formula
  is a set.
- **Foundation:** every non-empty set has an element that shares no
  elements with it. Equivalently, there is no infinite chain going down by
  membership.
- **Choice:** for any collection of non-empty, pairwise disjoint sets,
  there is a set containing exactly one element of each.

Everything is built from the empty set. The natural number 0 is the empty
set, 1 is `{0}`, 2 is `{0, 1}`, and in general n + 1 is n ∪ `{n}`, so each
number is the set of the numbers below it. Pairs, functions, relations,
the integers, the rationals and the reals can all be encoded as sets on
top of that.

#### Avoiding Russell's paradox

Two axioms do the work. Comprehension is restricted to subsets of an
existing set, so the full Russell set cannot even be written down. And
Foundation rules out a set that contains itself: if x ∈ x, then the set
`{x}` is non-empty, and its only element x shares the element x with it,
breaking Foundation. So in ZFC, no set is a member of itself, and the
"set of sets not containing themselves" would be the set of all sets,
which does not exist.

Foundation also means membership is well founded, which is chapter 2's
well ordering and chapter 6's structural induction in another form: you
can do induction on sets by membership, the technique called
∈-induction.

### Worked example

**Simple: Russell's paradox as a program.** Model a naive set as a
membership predicate, a function that answers "is x in me?". Any predicate
is allowed, which is exactly naive comprehension:

```ts
type NaiveSet = (x: NaiveSet) => boolean;
const everything: NaiveSet = () => true;
const nothing: NaiveSet = () => false;
const R: NaiveSet = (s) => !s(s); // Russell: the sets that are not members of themselves
console.log('everything ∈ everything:', everything(everything), ' nothing ∈ nothing:', nothing(nothing));
console.log('so everything ∉ R:', R(everything), ' nothing ∈ R:', R(nothing));
try { console.log(R(R)); } catch (e) { console.log('R ∈ R ? no answer:', (e as Error).name); }
```

```text
everything ∈ everything: true  nothing ∈ nothing: false
so everything ∉ R: false  nothing ∈ R: true
R ∈ R ? no answer: RangeError
```

The program cannot crash with a contradiction, so it does the only thing
it can: it never settles. R(R) asks R(R), negated, forever. In logic the
same self-reference produces a statement that is true iff false. This is
also, again, the shape of the simulating halting decider in 7.2.

**Realistic: pure sets with Foundation.** Now model sets the ZFC way: a
set is a finite array of sets, built bottom-up from the empty set. Every
set must exist before it can be an element, so self-membership cannot be
built. The **rank** of a set (how deep the nesting goes) is always
defined:

```ts
type PureSet = PureSet[];
const empty: PureSet = [];
const succ = (n: PureSet): PureSet => [...n, n]; // n ∪ {n}
const nat = (k: number): PureSet => (k === 0 ? empty : succ(nat(k - 1)));
const rank = (s: PureSet): number => (s.length === 0 ? 0 : 1 + Math.max(...s.map(rank)));
const size = (s: PureSet) => s.length;
console.log([0, 1, 2, 3, 4, 5].map((k) => `${k}: size ${size(nat(k))} rank ${rank(nat(k))}`).join(' | '));
const pow = (s: PureSet): PureSet => s.reduce<PureSet[]>((acc, x) => acc.concat(acc.map((t) => [...t, x])), [[]]);
console.log('pow(3) size', pow(nat(3)).length, 'rank', rank(pow(nat(3))));
```

```text
0: size 0 rank 0 | 1: size 1 rank 1 | 2: size 2 rank 2 | 3: size 3 rank 3 | 4: size 4 rank 4 | 5: size 5 rank 5
pow(3) size 8 rank 4
```

The von Neumann number n has exactly n elements and rank n, so the
encoding really does count. The power set of 3 has 2³ = 8 elements and a
rank one higher, which is Cantor's theorem in miniature: the power set
always climbs a level. The rank function terminates because of the way the
data was built, which is Foundation as a program property: it is a
structural recursion in chapter 6's sense.

### Common mistake

**The wrong way:** "Russell's paradox is a word game, like 'this sentence
is false', and does not affect real mathematics."

**Why it fails:** it was a real flaw in the foundations people were using,
including a careful formal system by Gottlob Frege, and it is the same
argument that proves Cantor's theorem and the halting theorem. Ignoring it
means your foundation can prove anything (from a contradiction, everything
follows).

**The right way:** read it as a design lesson: unrestricted
self-reference plus negation produces contradiction. Systems stay sane by
restricting how things may refer to themselves, through axioms, types or
staging.

### In real systems

- **Type systems:** Russell's own fix was a theory of types, where a set can only contain things of a lower type. Modern typed languages and proof assistants inherit that idea; Lean and Coq have a hierarchy of universes so "the type of all types" is not itself a member of itself.
- **Immutable data built bottom-up** behaves like Foundation: you cannot create a cyclic structure without mutation or laziness, which is why structural recursion over JSON-like data always terminates.
- **Garbage collectors and serialisers** must handle cycles explicitly precisely because mutable object graphs do not obey Foundation; `JSON.stringify` throws on a cyclic object.
- **Configuration and query languages** that allow unrestricted self-reference (recursive includes, recursive views) need guards against the same infinite regress.

### Check yourself

3. Why does Foundation rule out a two-cycle x ∈ y ∈ x?

<summary>Answer</summary>

1. The subset of A of members that are not members of themselves is not an element of A. So no set contains every set.
2. 3 = `{0, 1, 2}`, where 0 is the empty set, 1 is the set holding only the empty set, and 2 is the set holding 0 and 1.
3. Apply Foundation to the set holding x and y: x shares y with it, y shares x with it, so no element is disjoint from the set.

## 7.4 Does All This Really Work?

### In one sentence

ZFC is the best foundation we have, but it cannot prove itself
consistent, it implies some strange theorems, and it leaves some natural
questions undecided; for computer science the payoff is the method, not
the large infinities.

### The idea

The book is candid about the state of things:

- **Consistency is not proven.** No one has derived a contradiction from
  ZFC, and mathematicians are confident. But Gödel's second incompleteness
  theorem shows that a consistent system like ZFC cannot prove its own
  consistency. The confidence is earned by experience, not proof.
- **Strange consequences.** The Axiom of Choice implies the Banach–Tarski
  theorem: a solid ball can be cut into finitely many pieces that
  reassemble, by rotations and shifts, into two balls the same size as the
  original. The pieces are so irregular they have no volume, so nothing
  physical is contradicted, but it shows how far the axioms stretch from
  intuition.
- **Undecided questions.** The Continuum Hypothesis says there is no set
  strictly between ℕ and ℝ in size. Gödel and Paul Cohen showed that ZFC
  can neither prove nor disprove it. The axioms simply do not settle it.

#### Large infinities in computer science

Does a programmer need pow(pow(ℕ))? Almost never. Computer science lives
mostly in the countable world: finite strings, programs, data structures,
countable state spaces. The book's point is that the reasoning developed
for infinite sets, the diagonal argument in particular, produced results
that matter enormously: the limits of computation (7.2), Gödel's
incompleteness, and the hierarchy of complexity classes (time hierarchy
theorems are diagonal arguments too). Even the uncountability of functions
from ℕ to `{0, 1}` compared with the countability of programs is a fact
you can use: most functions are not computable at all.

There is a second, quieter point. Computer science is also where
infinite objects are modelled with finite means: streams, lazily
evaluated lists, and infinite games or reactive systems that run forever.
Reasoning about them uses exactly the tools of this chapter: countability,
bijections and fair enumeration.

### Worked example

**Simple: counting programs versus counting functions.** Programs are
finite strings over a finite alphabet, so they can be listed: all strings
of length 1, then length 2, and so on. Map each program to the function
from ℕ to `{0, 1}` it computes (when it computes one). That is a function
from a countable set; its image is countable. But the set of all functions
from ℕ to `{0, 1}` is the set of infinite bit strings, which is
uncountable by the diagonal argument. So the image misses something:
there is an uncomputable function. In fact it misses "almost all" of them.

**Realistic: what this tells a tool builder.** Suppose you are asked for a
linter that flags every function in a codebase that can loop forever, with
no false alarms. Section 7.2 says this is impossible in general. The
practical plan is the one every real tool follows: accept the functions
you can prove terminating (structural recursion, bounded loops), flag the
ones you can prove looping (`while (true)` with no exits), and report the
rest as "could not determine", letting a person decide. The theory is not
a reason to give up; it tells you to budget for the third category from
the start.

### Common mistake

**The wrong way:** "if ZFC cannot prove its own consistency, mathematics
is built on sand, so none of these proofs can be trusted."

**Why it fails:** every result in this book is provable in far weaker
systems than full ZFC, and none of the exotic axioms (Choice in strong
forms, large infinities) is needed for the countable mathematics used in
computing. Unprovability of consistency is a limitation of formal systems
in general, not evidence of a flaw.

**The right way:** know which axioms a result depends on. For practical
computer science, the answer is usually "very few", and the proofs are as
reliable as anything in mathematics.

### In real systems

- **Complexity theory:** the time and space hierarchy theorems, which say more resources let you solve strictly more problems, are proved by diagonalisation.
- **Lazy streams** in Haskell, generators in TypeScript and infinite iterators in Python represent countably infinite sequences with finite code.
- **Formal verification** tools state which axioms they assume, and some proof assistants avoid Choice or excluded middle by default so proofs can run as programs.

## From beginner to strategy

<Levels label="Chapter 7, Infinite Sets">
<Level name="Beginner" depth={3}>

The smallest working idea: two sets are the same size when you can pair
their elements off exactly, with a bijection. For infinite sets you never
count; you build the pairing. A set is countable when you can write its
elements in one list that eventually reaches each of them.

Try it: write a list that eventually reaches every integer (0, −1, 1, −2,
2, ...), and then a list of every pair of naturals, diagonal by diagonal.
Convince yourself that any given integer or pair appears at a definite,
finite position.

The beginner's mistake is to treat "infinite" as one size, or to compare
infinite sets by inclusion ("the evens are half the naturals"). Inclusion
says nothing about size here; only the existence of a bijection does.

</Level>
<Level name="Intermediate" depth={3}>

The working toolkit: surj, inj and bij compare infinite sets, and most
finite rules carry over (transitivity, reversing arrows). The new
ingredient is Schröder–Bernstein: surjections both ways give a bijection.
To show a set countable, break it into countably many finite pieces and
list piece by piece. To show it uncountable, assume a list and build the
diagonal element it misses.

Practise both directions on the same kind of object: finite subsets of ℕ
are countable (list by largest element), all subsets of ℕ are not. The
contrast between those two is the whole chapter in one example.

</Level>
<Level name="Advanced" depth={3}>

The diagonal argument is one argument with many costumes: Cantor's
theorem, the uncountability of the reals, the halting theorem, Russell's
paradox, Gödel's incompleteness theorem and the hierarchy theorems in
complexity. The shared structure is a table indexed by the same set on
both axes, and an object defined to disagree with the table on its
diagonal. Spotting that structure lets you prove new impossibility results
quickly.

Reductions are the second advanced tool: once halting is impossible, show
a new problem would solve halting, and the new problem is impossible too.
This is how undecidability spreads to questions about program behaviour.

</Level>
<Level name="Edge cases" depth={3}>

- **The empty set:** pow of the empty set has one element, so Cantor's theorem holds even at size zero; there is no function from the empty set onto a non-empty set.
- **Finite sets:** "A bij A plus one element" fails for every finite A, which is why it characterises infinite sets.
- **Real numbers with two expansions:** 0.0111... and 0.1000... in binary are the same real, so the map from reals to bit strings needs care; the diagonal argument for reals handles it by avoiding strings ending in all ones, or by working with the bit strings directly.
- **Countable unions:** a countable union of countable sets is countable, but proving it in general quietly uses a weak form of the Axiom of Choice to pick a listing for each piece.

</Level>
<Level name="Corner cases" depth={3}>

- **Partial deciders:** a procedure that answers correctly whenever it answers, but sometimes runs forever, does not contradict the halting theorem; the simulator is one.
- **Bounded halting:** "does P halt on t within n steps?" is decidable for every fixed n; the undecidability lives only in the unbounded question.
- **Self-reference that is harmless:** a program can print its own source (a quine) without paradox; it is self-reference plus negation, asked of everything, that produces contradictions.
- **The set of all sets:** not a set in ZFC; set theorists handle such collections as "classes", which may not be members of anything.

</Level>
<Level name="Production level" depth={3}>

In real engineering the theorems show up as design constraints. Every
static analyser, type checker and linter makes a choice between false
alarms and missed bugs, and good ones document which. Every service that
runs user code (CI runners, serverless functions, query engines) enforces
time and memory limits, because it cannot know in advance whether the code
will stop. Every encoding of numbers is finite, so exact real arithmetic
is impossible and floating-point rounding is a permanent fact.

Fair enumeration is the constructive side: when merging infinitely many
streams, or generating test cases from an infinite space, walk the
diagonals so that every element appears at a finite position instead of
exhausting the first infinite stream forever.

</Level>
<Level name="Mindset" depth={3}>

The useful habit is to ask "is this question about the unbounded future
of a program?" before trying to build a perfect tool for it. If yes,
expect a three-way answer (yes, no, cannot tell) and design for the third
answer up front. The second habit is to be suspicious of any system that
lets a thing refer to the whole collection it belongs to, plus a negation:
that is the recipe for a paradox or an infinite loop.

</Level>
<Level name="System design" depth={3}>

When a system must evaluate user-supplied logic (rules engines, templates,
configuration languages, smart contracts), choose the language's power
deliberately. A language without unbounded loops or recursion (like many
template languages or SQL without recursive queries) can have termination
guaranteed and analysed exactly. A Turing-complete one gives power but
loses decidability, and then needs runtime limits (gas, timeouts, step
counts) as a substitute. Several smart-contract platforms meter every step
for exactly this reason.

</Level>
<Level name="Strategy" depth={3}>

Long-term, this chapter is the root of computability theory and much of
complexity theory. It pays to understand the diagonal argument so well that
you can write it from scratch, and to know the standard reductions, because
both come back in automata, compilers, verification and cryptography. My
plan is to keep a short list of undecidable properties next to the
decidable approximations that tools actually use, and to revisit this
chapter when I study type systems and program analysis.

</Level>
</Levels>

## Questions people ask

**Are there more real numbers between 0 and 1 than integers in total?**
Yes. The interval (0, 1) is uncountable, and in fact the same size as all
of ℝ (a bijection exists), while the integers are countable.

**Is the set of rationals bigger than the set of naturals, since there
are infinitely many rationals between any two naturals?** No. Both are
countable; the diagonal listing of pairs reaches every fraction.

**Does the halting theorem mean computers are less powerful than people?**
The theorem is about any procedure, and people reasoning by rule face the
same limit. It says nothing about which programs a person or a tool can
handle in particular cases.

**Do I need ZFC to write correct software?** No. It is useful to know that
the mathematics you rely on has a precise foundation and to recognise the
self-reference pattern; you will never need the axioms directly.

**What is the smallest uncountable size?** Whether it is the size of ℝ is
the Continuum Hypothesis, which ZFC cannot settle either way.

## Key takeaways

- Infinite sets are compared by bijections and surjections, not by counting or by inclusion.
- An infinite set is the same size as itself plus one element; this property defines infinity.
- ℤ, ℕ × ℕ, the rationals and all finite strings are countable: list them in finite blocks.
- Cantor's theorem: every set is strictly smaller than its power set, so there are endlessly many sizes of infinity, and the reals are uncountable.
- The diagonal argument builds an object that disagrees with every row of a table on the diagonal.
- No program can decide halting for all programs; any static checker must be either too strict or too lenient somewhere.
- Russell's paradox forced set theory onto axioms; ZFC restricts comprehension and adds Foundation so no set contains itself.
- ZFC cannot prove its own consistency and leaves the Continuum Hypothesis undecided, but none of that threatens the countable mathematics of computing.

## Glossary

- **Bijection, A bij B:** a function pairing every element of A with exactly one element of B; "same size".
- **A surj B:** there is a function from A onto B; "A is at least as big as B".
- **A strict B:** there is no surjection from A onto B; "A is strictly smaller than B".
- **Schröder–Bernstein theorem:** surjections both ways imply a bijection.
- **Countably infinite:** in bijection with ℕ.
- **Countable:** finite or countably infinite; equivalently, ℕ surj the set.
- **Uncountable:** not countable, like pow(ℕ) and ℝ.
- **Cantor's theorem:** every set is strictly smaller than its power set.
- **Diagonal argument:** building an object that differs from the n-th item at position n.
- **Pairing function:** a bijection between ℕ × ℕ and ℕ.
- **String procedure:** a program that takes a string and either halts or runs forever.
- **Recognisable set:** one for which some procedure halts on exactly its members.
- **Decidable set:** one for which some procedure always halts with the correct yes or no.
- **No-halt:** the strings s whose procedure P_s does not halt on s.
- **Reduction:** using a solution to one problem to solve another.
- **Russell's paradox:** the contradiction from the set of all sets not containing themselves.
- **ZFC:** Zermelo–Fraenkel set theory with the Axiom of Choice.
- **Foundation:** the axiom that membership has no infinite descending chains.
- **Continuum Hypothesis:** no set is strictly between ℕ and ℝ in size; independent of ZFC.
