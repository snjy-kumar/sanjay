This chapter is the measuring stick for the whole book. It defines precisely
what "this algorithm is O(n log n)" means, sets up a simple model of a
computer so that steps can be counted, and then teaches the craft of
reading a program and writing down its running time. The centrepiece is one
small problem, the maximum subsequence sum, solved four times with running
times from cubic to linear, so the payoff of analysis is visible in
milliseconds.

After this chapter you will be able to:

  prove a simple bound from the definition by finding the constants.

## 2.1 Mathematical background

### In one sentence

Big-O and its relatives compare how fast two functions grow, ignoring
constant factors and small inputs, so we can rank algorithms by how they
scale.

### The idea

Running time depends on the machine, the compiler, the language and the
input. If we tried to state exact times, every claim would be wrong on the
next laptop. What survives a change of machine is the *shape* of growth:
whether doubling the input doubles the time, quadruples it, or adds a
fixed amount. The notation of this section captures exactly that shape.

#### Big-O: an upper bound

We say **T(n) is O(f(n))** if there are positive constants c and n₀ such
that T(n) is at most c times f(n) for every n at least n₀. In words: past
some starting point, T never grows faster than f, up to a constant
multiple. Big-O is an upper bound. Saying an algorithm is O(n²) means its
time grows no faster than quadratically; it might grow slower.

The two constants carry the meaning. The constant c absorbs machine speed
and implementation details: if one computer is ten times faster, c changes
and the claim does not. The threshold n₀ lets us ignore small inputs, where
start-up costs dominate and nothing interesting is decided.

#### Big-Omega: a lower bound

**T(n) is Ω(g(n))** if there are positive constants c and n₀ such that
T(n) is at least c times g(n) for every n at least n₀. Past some point, T
grows at least as fast as g. Omega is how lower bounds are stated, such as
the comparison-sorting bound in chapter 7.

#### Big-Theta: a tight bound

**T(n) is Θ(h(n))** if it is both O(h(n)) and Ω(h(n)). Then T and h grow at
the same rate, up to constants. When people say "merge sort is n log n"
they mean Θ(n log n), even when they write O. The book is careful to say
that a big-O claim should be as tight as possible: saying a linear
algorithm is O(n²) is true and useless.

#### Little-o: strictly slower

**T(n) is o(p(n))** if T is O(p(n)) and not Θ(p(n)): T grows strictly
slower. Formally, for *every* positive constant c there is an n₀ beyond
which T(n) is less than c times p(n). n is o(n²); n² is not o(n²).

#### Three rules for combining bounds

The book gives rules that let me avoid proofs from scratch every time.

1. If T₁ is O(f) and T₂ is O(g), then T₁ + T₂ is O(f + g), which is the
   larger of the two. And T₁ × T₂ is O(f × g).
2. If T is a polynomial of degree k, T is Θ(nᵏ). Lower terms and the
   leading coefficient disappear.
3. logᵏ n is O(n) for any constant k. Any power of a logarithm grows
   slower than n.

From these follow the style conventions: never write constants or lower
order terms inside a big-O. Write O(n²), not O(2n² + 3n).

#### Comparing growth with a limit

To compare f and g, look at the ratio f(n) / g(n) as n grows without bound.
A **limit** is the value the ratio settles towards. If the limit is 0, f is
o(g). If it is a positive constant, f is Θ(g). If it grows without bound, g
is o(f). If the ratio oscillates, neither rule applies. When both functions
grow without bound, L'Hôpital's rule lets you compare their derivatives
instead, which is how one shows log n is o(n): the derivatives are 1/n and
1, whose ratio goes to 0.

### Worked example

Simple: prove from the definition that T(n) = 3n² + 10n + 7 is O(n²).

I need c and n₀ with 3n² + 10n + 7 at most c n² for all n at least n₀. For
n at least 1, 10n is at most 10n² and 7 is at most 7n². So T(n) is at most
3n² + 10n² + 7n², which is 20n². Choose c equal to 20 and n₀ equal to 1.
Done. Any larger c works too; the definition only needs one pair.

It is also Ω(n²): T(n) is at least 3n² for every n at least 1, so c equal
to 3 works. Both bounds hold, so T is Θ(n²).

Realistic: two implementations of a report. Version A does 100n steps;
version B does n² / 10 steps. For n equal to 100, A does 10,000 steps and B
does 1,000: B wins. They cross where 100n equals n²/10, at n equal to
1,000. For n equal to a million, A does 10⁸ steps and B does 10¹¹, a
thousand times more. Big-O says A is O(n) and B is O(n²), which predicts
the large-n winner correctly and says nothing about small n. That is
exactly what it is for.

Comparing by the limit: is n log n O(n^1.5)? The ratio is
n log n / n^1.5, which is log n / √n. Logarithms grow slower than any power
of n, so the ratio goes to 0, and n log n is o(n^1.5). Yes, and strictly.

### Common mistake

The first mistake is reading big-O as "exactly". O(n²) is an upper bound;
a linear algorithm is also O(n²). When you mean a tight bound, say Θ, or
at least give the tightest O you can prove.

The second is putting constants into the notation and drawing conclusions
from them: "O(2n) is twice as slow as O(n)". They are the same set of
functions. Constants matter for real time, and big-O deliberately throws
them away.

The third is comparing two algorithms at small n by their big-O. An O(n²)
algorithm with a tiny constant beats an O(n log n) one with a large
constant for small inputs. Library sorts switch to insertion sort below a
few dozen elements for exactly this reason.

### In real systems

Every capacity estimate is this section with real constants. "Our
dashboard query is linear in the number of events, and events grow 3× a
year" tells me next year's latency before it happens. Code review comments
like "this is quadratic in the number of line items" are big-O used as a
warning, and the useful follow-up is the real n: quadratic in a list that
never exceeds 20 is fine; quadratic in a customer's order history is not.

## 2.2 Model

### In one sentence

To count steps we pretend the computer does every simple instruction in one
unit of time, has unlimited memory, and works on fixed-size integers.

### The idea

Analysis needs something to count. Counting real machine cycles is
hopeless: caches, branch prediction and the compiler change them. So the
book adopts a simple model computer. It executes instructions one after
another. Every simple instruction (add, multiply, compare, assign, read an
array element, call a function) takes one time unit. Integers have a fixed
size, so arithmetic does not get slower as numbers grow. Memory is
infinite, so we never page to disk.

The model has known weaknesses, and the book names them. Real computers
do not make a disk read cost the same as an addition, and that difference
is the entire subject of B-trees (chapter 4) and external sorting
(chapter 7). Real caches make a linear scan of an array far faster than
following the same number of linked-list pointers. And arithmetic on huge
numbers is not constant time. The model is still the right one for
comparing algorithms in memory, because it is simple and it gets the
growth rate right in most cases.

### Worked example

Simple: in the model, `sum += a[i]` costs a read of `a[i]`, an addition and
an assignment: three units, or one "statement" if we are counting at that
granularity. Since big-O ignores constants, it does not matter which
granularity we pick, as long as each statement is constant work.

Realistic: summing a million numbers stored in an array and the same
million stored in a linked list. The model says both are about a million
steps, Θ(n). On real hardware the array is several times faster, because
consecutive elements share cache lines and the hardware prefetches them,
while each linked-list node is a separate memory access. The model predicts
the growth (both double when n doubles) correctly and misses the constant.
Both facts are useful.

### Common mistake

The mistake is treating the model as reality: "both are Θ(n), so the
linked list is as fast as the array". The model gives growth, not speed.
The fix is to use the model to choose among growth rates, then measure to
choose among algorithms with the same growth.

The opposite mistake is rejecting the model because it is unrealistic.
Without it there is no way to predict anything before running code. It is
wrong in the constants and right in the shape, which is what it promises.

### In real systems

The model breaks in three production situations worth knowing. When data
lives on disk or across a network, count I/Os or round trips instead of
instructions, which is how databases plan queries. When numbers are huge
(cryptography, BigInt), arithmetic costs grow with the number of digits.
When memory layout dominates (analytics over arrays of structs), count
cache misses. Each is the same idea with a different unit of cost.

## 2.3 What to analyze

### In one sentence

We usually analyse running time as a function of the input size, and we
usually mean the worst case, because it is a guarantee and it is the case
we can compute.

### The idea

Running time is the resource that matters most, so it is what the book
analyses. Running time depends on the input, so we express it as a
function T(n) of the **input size** n: the number of items to sort, the
number of vertices in a graph, the length of a string.

Inputs of the same size can take different times. Searching an array for a
value that sits in the first slot is fast; searching for one that is absent
reads everything. So there are three functions:

- **Worst case**, T_worst(n): the most time over all inputs of size n.
- **Average case**, T_avg(n): the expected time over some assumed
  distribution of inputs of size n.
- **Best case**: the least time. Rarely useful, because any algorithm can be
  made fast on one lucky input.

The book prefers the worst case for two reasons. It is a guarantee: no
input of size n will be slower. And it is usually easier to compute than
the average, which needs a probability model of inputs and often hard
mathematics. Average-case results appear where they are the honest
description, such as quicksort and binary search trees, and the book says
so when it uses them.

The chapter also separates the *algorithm's* cost from the cost of reading
the input. If the input arrives from disk, reading it is already linear, so
an algorithm faster than linear cannot be observed end to end. That is why
the maximum subsequence sum problem cannot be solved faster than linear: an
algorithm that does not look at every element can be fooled by the one it
skipped.

### Worked example

Simple: linear search in an array of n items.

```ts
function indexOf(a: readonly number[], x: number): number {
  for (let i = 0; i < a.length; i++) if (a[i] === x) return i;
  return -1;
}
```

Best case: x is at position 0, one comparison. Worst case: x is absent, n
comparisons. Average case, assuming x is present and equally likely to be
in any position: on average it sits halfway, so about n/2 comparisons. All
three are linear except the best case, but the constant differs.

Realistic: a login service checks a password against a list of revoked
tokens. Most requests are valid, so the token is *not* in the list. The
"average" request is the worst case of linear search. Assuming tokens are
usually found early would badly underestimate cost. The choice of input
distribution is a claim about the world, and it must match the world.

### Common mistake

The mistake is quoting a best case as if it described an algorithm:
"insertion sort is linear". It is linear on already sorted input and
quadratic in the worst and average case. The fix is to always say which
case.

The other mistake is assuming uniformly random inputs when real inputs are
not random. Quicksort with a first-element pivot is fast on random input
and quadratic on sorted input, and real data is often sorted or nearly so.
The fix is to state the distribution and check it against data, or to
randomise inside the algorithm so the input order stops mattering
(chapter 7).

### In real systems

Production latency targets are usually percentiles (p50, p99), which are
neither the worst case nor the average. The worst case bounds p100; the
average describes throughput. An algorithm whose worst case is triggered
by a specific input becomes a security issue when an attacker can choose
the input: hash flooding (chapter 5) and regular-expression backtracking
are both "the worst case, on purpose".

### Check yourself

1. Why is the worst case usually preferred?

<details>
<summary>Answer</summary>

It is a guarantee that holds for every input, and it is usually easier to
compute than an average, which needs an assumed input distribution.

</details>

2. Why can no algorithm for maximum subsequence sum be faster than linear?

<details>
<summary>Answer</summary>

It must read every element: if it skipped one, an adversary could make that
element huge and the answer would change.

</details>

## 2.4 Running-time calculations: a simple example and the general rules

### In one sentence

To find a program's running time, give each simple statement a cost of one,
then combine: loops multiply by their iteration count, sequences add,
branches take the larger side, and recursion becomes an equation.

### The idea

Section 2.4 opens by agreeing to be sloppy in a disciplined way. Since we
want big-O, we may throw away constants as we go, and we may overestimate
(an upper bound is still an upper bound) as long as we do not overestimate
so much that the answer becomes useless. With that licence, analysing code
becomes a set of local rules.

#### 2.4.1 A simple example

The book's first example sums the cubes of 1 to n. Counting every
operation exactly gives something like 6n + 4 units: a declaration, an
initialisation, a loop test and increment per iteration, and a few
operations in the body. The point of the exercise is that the exact count
is tedious and the answer is just "linear". Every constant in it is
discarded the moment we write O(n). So we count at the level of statements
and loops, not instructions.

#### 2.4.2 General rules

**Rule 1, for loops.** The running time of a loop is at most the running
time of its body times the number of iterations.

**Rule 2, nested loops.** Analyse from the inside out. The running time of
a statement inside a group of nested loops is the statement's cost times
the product of all the loop sizes. Two nested loops of n each around a
constant body cost Θ(n²).

**Rule 3, consecutive statements.** Add their costs. Since we keep only the
largest term, a linear loop followed by a quadratic loop costs Θ(n²).

**Rule 4, if/else.** The running time is at most the cost of the test plus
the larger of the two branches. This can overestimate (if the expensive
branch is rare) but never underestimates.

**Function calls** are analysed first, then substituted in. **Recursion**
needs care. If a function makes one recursive call and does constant work
otherwise, it is really a loop in disguise, and the analysis is linear in
the depth. If it makes two or more calls, write a **recurrence relation**:
an equation that expresses T(n) in terms of T on smaller inputs. Solving
recurrences is a tool used throughout the book; the chapter shows the
simplest cases.

### Worked example

Simple: apply the rules to this function.

```ts
function f(n: number): number {
  let total = 0;
  for (let i = 0; i < n; i++) total += i;          // loop A: n iterations, O(1) body
  for (let i = 0; i < n; i++)                       // loop B
    for (let j = 0; j < n; j++) total += i * j;    //   n × n iterations
  return total;
}
```

Loop A is O(n) by rule 1. Loop B is O(n²) by rule 2. They are consecutive,
so by rule 3 the total is O(n) + O(n²), which is O(n²).

A dependent inner loop:

```ts
for (let i = 0; i < n; i++)
  for (let j = i; j < n; j++) work();
```

The inner loop runs n − i times. Summing over i from 0 to n − 1 gives
n + (n − 1) + ... + 1, the arithmetic series, which is n(n + 1)/2. Still
Θ(n²), with constant one half. Rule 2's "product of the loop sizes" is an
upper bound here; the sum gives the exact count.

Realistic: an endpoint that, for each order (n of them), checks every
line item (up to m per order) against a list of k discounts by linear
search. The cost is O(n × m × k) by rule 2. If the discount list becomes a
`Set` (chapter 5), the inner search is O(1) on average and the cost drops
to O(n × m). The rules tell me which loop to attack.

Recursion that is really a loop:

```ts
function factorial(n: number): number { return n <= 1 ? 1 : n * factorial(n - 1); }
```

One call per level, constant work per level, n levels: O(n). And the
exponential trap from chapter 1, `fib(n - 1) + fib(n - 2)`, has the
recurrence T(n) = T(n − 1) + T(n − 2) + c, which grows like the Fibonacci
numbers themselves.

Solving the Fibonacci recurrence just enough to see it is exponential, in
plain words.

### Common mistake

The mistake is multiplying loops that are not nested, or adding loops that
are. Two loops one after the other over n items are O(n), not O(n²). One
loop over n containing a call to a function that loops over n is O(n²),
even though only one loop is visible. The fix is to inline mentally every
call inside a loop and ask what it costs. Hidden loops are everywhere in
JavaScript: `array.includes`, `indexOf`, `splice`, `shift`, spread
`[...xs]` and `Object.keys` are each linear.

```ts
// Looks linear, is quadratic: includes is a loop
const unique: number[] = [];
for (const x of input) if (!unique.includes(x)) unique.push(x);
```

The fix is a `Set`, which makes the check constant on average.

### In real systems

The classic production quadratic is `shift()` in a loop: using an array as
a queue and removing from the front, which moves every remaining element.
Another is string concatenation in some languages, where building a long
string with `+=` copies it each time (V8 avoids this with ropes, but
`Array.join` is the safe habit). A third is an ORM loading a list and then
querying once per item (the "N + 1 queries" problem): rule 1 with a network
round trip as the body.

## 2.4.3 Solutions for the maximum subsequence sum problem

### In one sentence

Given a list of integers, possibly negative, find the largest sum of any
contiguous run of them; four algorithms solve it in cubic, quadratic,
n log n and linear time, and the difference is decisive at scale.

### The idea

The **maximum subsequence sum** problem: given integers a₀ to aₙ₋₁, find the
largest value of aᵢ + aᵢ₊₁ + ... + aⱼ over all i at most j. In the book's
convention, if every number is negative the answer is 0, the sum of the
empty run. ("Subsequence" here means a contiguous slice, often called a
subarray elsewhere.) It is a good teaching problem because the obvious
solution is easy to write, obviously correct and very slow, and each
better solution comes from noticing work the previous one repeats.

Think of the numbers as daily profit and loss. The answer is the best
stretch of consecutive days to have held a position.

#### Algorithm 1: try every run, sum it from scratch (cubic)

Every run is a pair (i, j). For each pair, add up aᵢ through aⱼ. There are
about n² / 2 pairs and each sum takes up to n additions, so the total is
cubic. Precisely, the number of additions is the sum over all i at most j
of (j − i + 1), which works out to n(n + 1)(n + 2) / 6, which is Θ(n³).

#### Algorithm 2: reuse the running sum (quadratic)

Algorithm 1 recomputes the sum of aᵢ through aⱼ from scratch, even though
it just computed aᵢ through aⱼ₋₁. Keep a running sum as j advances and the
innermost loop disappears. Two nested loops remain: Θ(n²).

#### Algorithm 3: divide and conquer (n log n)

Split the array in half. The best run lies entirely in the left half,
entirely in the right half, or crosses the middle. The first two are found
by recursion. The crossing one must include the last element of the left
half and the first of the right, so it is the best suffix of the left half
(scan leftwards from the middle, tracking the largest running sum) plus
the best prefix of the right half (scan rightwards). Those two scans are
linear. The answer is the largest of the three.

The cost satisfies T(n) = 2T(n/2) + O(n): two half-size problems plus
linear work to combine. That recurrence solves to Θ(n log n), as the
step-by-step section shows.

#### Algorithm 4: one pass (linear)

The key observation: a run that starts with a negative-sum prefix can be
improved by dropping that prefix. So scan left to right keeping
`here`, the best sum of a run ending at the current position. When `here`
drops below zero, no future run should include anything so far, so reset
it to zero. Track the best `here` ever seen. One pass, constant work per
element: Θ(n). This idea is usually credited to Kadane. It is also an
**online algorithm**: it needs constant memory and can answer for the data
seen so far at any moment, without storing the input.

### Worked example

My example input is the eight days of profit and loss
`[4, -3, 5, -2, -1, 2, 6, -2]`. The best run is days 0 to 6:
4 − 3 + 5 − 2 − 1 + 2 + 6, which is 11.

All four, in my TypeScript:

```ts
function mss1(a: number[]): number {          // cubic
  let best = 0;
  for (let i = 0; i < a.length; i++)
    for (let j = i; j < a.length; j++) {
      let s = 0;
      for (let k = i; k <= j; k++) s += a[k];
      if (s > best) best = s;
    }
  return best;
}
function mss2(a: number[]): number {          // quadratic
  let best = 0;
  for (let i = 0; i < a.length; i++) {
    let s = 0;
    for (let j = i; j < a.length; j++) { s += a[j]; if (s > best) best = s; }
  }
  return best;
}
```

```ts
function mss3(a: number[], lo = 0, hi = a.length - 1): number {   // n log n
  if (lo > hi) return 0;
  if (lo === hi) return Math.max(0, a[lo]);
  const mid = (lo + hi) >> 1;
  const left = mss3(a, lo, mid), right = mss3(a, mid + 1, hi);
  let s = 0, bestL = 0;
  for (let i = mid; i >= lo; i--) { s += a[i]; bestL = Math.max(bestL, s); }
  s = 0; let bestR = 0;
  for (let i = mid + 1; i <= hi; i++) { s += a[i]; bestR = Math.max(bestR, s); }
  return Math.max(left, right, bestL + bestR);
}
function mss4(a: number[]): number {          // linear
  let best = 0, here = 0;
  for (const x of a) {
    here += x;
    if (here > best) best = here;
    else if (here < 0) here = 0;
  }
  return best;
}
```

```ts
const days = [4, -3, 5, -2, -1, 2, 6, -2];
console.log(mss1(days), mss2(days), mss3(days), mss4(days)); // 11 11 11 11
console.log(mss4([-3, -1, -2]));                            // 0: the empty run
```

Then I checked them against each other on 1,000 random arrays of length 0
to 29 with values from −10 to 10. All four agreed every time, which is the
cheapest correctness test there is: a slow obviously-correct version is
the oracle for the fast clever one.

The realistic part is timing. I ran each at three sizes, doubling each

Why it is correct, as a loop invariant (a statement true before every
iteration). Invariant: before processing position k, `best` is the
largest sum of any run within the first k elements (or 0), and `here` is
the largest sum of a run ending exactly at position k − 1 (or 0 if every
such run is negative).

1. **Initially** (k equal to 0), there are no elements, `best` and `here`
   are 0. True.
2. **Maintenance.** The best run ending at k either is just aₖ, or extends
   the best run ending at k − 1. So it is `here + aₖ` if `here` is
   positive, otherwise aₖ. The code computes `here + x`, and the earlier
   reset to 0 means a negative previous run was already dropped. If the
   result is negative, the best run ending at k that we will want to extend
   is the empty one, so the reset to 0 is right. `best` takes the max of
   its old value and the new `here`, so it covers runs ending at k too.
3. **Termination.** After the last element, `best` is the largest sum of
   any run in the whole array. That is the answer.

### Common mistake

The commonest bug in the linear algorithm is the all-negative case. Under
the book's convention the answer is 0, which the code gives. If your
problem requires a non-empty run (as many interview statements do), the
answer for `[-3, -1, -2]` should be −1, and the code must start `best` at
the first element and never reset `here` below the current element:
`here = Math.max(x, here + x)`.

In the divide-and-conquer version, the common bug is the crossing scans:
scanning the left half from its start instead of from the middle outwards.
The crossing run must touch the middle, so its left part is a *suffix* of
the left half.

In timing, the mistake is measuring once at one size. A single number says
nothing about growth; only the ratio between sizes does.

### In real systems

The linear scan is the template for streaming analytics: one pass,
constant memory, an answer at every moment. Best trading window, longest
streak of healthy health checks, worst stretch of an error-rate time
series (negate and run the same algorithm) all use it. The divide-and-
conquer shape (solve halves, combine with a linear crossing step) is how
merge sort, closest pair of points (chapter 10) and parallel reductions on
many cores work, because the halves can run independently.

## 2.4.4 Logarithms in the running time

### In one sentence

An algorithm runs in O(log n) time when it uses constant time to cut the
problem by a constant fraction, usually a half; binary search, Euclid's
algorithm and fast exponentiation are the three standard examples.

### The idea

Logarithms appear in running times for one reason: repeated division. If
each step costs O(1) and leaves a problem at most half as big, then after k
steps the size is at most n / 2ᵏ, which drops to 1 when k reaches log₂ n.
So the number of steps is O(log n). The same holds for any constant
fraction: cutting to two thirds each time takes log base 3/2 of n steps,
which is still O(log n) because bases differ by a constant factor.

The contrast matters. If each step only *subtracts* a constant (n − 1,
n − 2, ...), the count is linear. The difference between "halve" and
"subtract one" is the difference between 20 steps and a million.

A related point: an algorithm cannot be sub-linear if it must first read
its whole input. Binary search is O(log n) only because the sorted array is
already in memory. If the data arrives as a stream, reading it is
linear, and the logarithm is the cost of each query afterwards.

#### Binary search

Given a sorted array and a value x, find x's position or report that it is
absent. Compare x with the middle element. If equal, done. If x is larger,
it can only be in the right half; if smaller, the left. Each comparison
halves the range, so at most about log₂ n + 1 comparisons are needed. It
is the fastest way to search data that is sorted and does not change.
When the data changes, keeping it sorted costs linear time per insert, and
the tree structures of chapter 4 take over.

#### Euclid's algorithm

The greatest common divisor (gcd) of two numbers is the largest number that
divides both. Euclid's algorithm repeatedly replaces the pair (m, n) with
(n, m mod n) until n is 0; then m is the gcd. It works because any number
dividing both m and n also divides m mod n, which is m minus a multiple of
n, and vice versa; so the pair's common divisors never change.

Why logarithmic? The remainder does not always halve in one step, but it
does within two. The book proves: if m is greater than n, then m mod n is
less than m / 2. Two cases. If n is at most m / 2, the remainder is less
than n, so less than m / 2. If n is more than m / 2, then n goes into m
exactly once and the remainder is m − n, which is less than m / 2. So every
two iterations, the larger number at least halves, giving at most about
2 log₂ n iterations.

#### Exponentiation

Computing xⁿ by multiplying x by itself n − 1 times is linear. Instead:
if n is even, xⁿ is (x²)^(n/2); if n is odd, it is (x²)^((n−1)/2) times x.
Each step halves the exponent at the cost of one or two multiplications, so
the total is at most about 2 log₂ n multiplications. This is called
**exponentiation by squaring**, and it is the heart of the modular
exponentiation in cryptography and in the primality test of chapter 10.

### Worked example

Simple: binary search in my own sorted array.

```ts
function binarySearch(a: readonly number[], x: number): number {
  let lo = 0, hi = a.length - 1;
  while (lo <= hi) {
    const mid = lo + ((hi - lo) >> 1);   // avoids overflow in languages with fixed ints
    if (a[mid] < x) lo = mid + 1;
    else if (a[mid] > x) hi = mid - 1;
    else return mid;
  }
  return -1;                              // not found
}
const sorted = [-3, 1, 4, 7, 9, 12, 15, 20];
console.log(binarySearch(sorted, 12), binarySearch(sorted, 5)); // 5 -1
```

Euclid on my own pair, 2024 and 1150:

```ts
function gcd(m: number, n: number): number {
  while (n !== 0) { const r = m % n; m = n; n = r; }
  return m;
}
console.log(gcd(2024, 1150)); // 46
```

Fast exponentiation, with BigInt so the answer is exact:

```ts
function pow(x: bigint, n: number): bigint {
  if (n === 0) return 1n;
  if (n === 1) return x;
  const half = pow(x * x, Math.floor(n / 2));
  return n % 2 === 0 ? half : half * x;
}
console.log(pow(2n, 62).toString(), pow(3n, 13).toString());
// 4611686018427387904 1594323
```

Counting multiplications for n equal to 1,000 with a counter in the same
code gives 14, against 999 for the naive loop. log₂ 1000 is about 10, and
the odd steps add a few more, inside the bound of 2 log₂ n.

Realistic: "find the first bad deploy". Given 1,000 commits in order where
everything after some commit is broken, test the middle commit; if broken,
the first bad one is at or before it, otherwise after. About 10 test runs
find it. This is `git bisect`, binary search over history, and it works for
any monotone yes/no question, not just sorted numbers.

level, plus one extra on each odd level.

### Common mistake

Binary search is famous for off-by-one bugs. Three common ones: using
`while (lo < hi)` with `hi = mid - 1`, which skips the last candidate;
setting `lo = mid` instead of `mid + 1`, which loops forever when the range
has two elements; and computing `mid` as `(lo + hi) / 2` without flooring
in JavaScript, which gives a fractional index and reads `undefined`. The
fix is to pick one convention (inclusive `lo` and `hi`, as above), write
the invariant ("if x is present, it is in a[lo..hi]") and check every
update preserves it.

In C, C++ and Java, `(lo + hi) / 2` can overflow for huge arrays, which is
why `lo + (hi - lo) / 2` is the standard form. That bug sat in widely used
library code for years.

For exponentiation, the mistake is forgetting that the result overflows:
in JavaScript, `2 ** 62` as a Number is not exact past 2⁵³. Use BigInt, or
reduce modulo m at every step for modular exponentiation.

### In real systems

Binary search is inside every sorted-array index, database B-tree page
lookups (chapter 4), `git bisect`, finding a version boundary in a
changelog, and "binary search on the answer" for capacity questions (what
is the largest batch size that fits in memory?). Euclid's algorithm runs in
every rational-number library and in RSA key generation. Modular
exponentiation by squaring is how every TLS handshake computes its
public-key operations quickly.

## 2.4.5 Limitations of worst-case analysis

### In one sentence

The worst case can be far more pessimistic than what happens in practice,
and the average case, which would be more honest, is often too hard to
compute or depends on an input distribution that may not match reality.

### The idea

Analysis is a model, and the book closes the chapter by marking where it
can mislead. Sometimes the worst-case bound is far above observed
behaviour. That can happen because the worst case is rare (a specific
input order that real data never takes), or because the analysis
overestimated (the "take the larger branch" rule, for example, charges the
expensive branch every time even if it runs once).

The fix in principle is average-case analysis. But averages need a
distribution: "all input orders equally likely" is a mathematical
convenience, not a fact about your data. And average-case analyses are
much harder; for several algorithms in the book (Shellsort in chapter 7 is
the famous one) the exact average is still not known. So the worst case
remains the default, with the understanding that it is a ceiling, and
measurement fills the gap.

Two other ideas from later chapters address the same limitation.
**Amortised analysis** (chapter 11) bounds the total over a sequence of
operations, so that one occasional expensive operation does not dominate
the picture. **Randomised algorithms** (chapter 10) make the algorithm
itself random, so that no particular input is bad and the expected time is
a guarantee over the algorithm's coin flips rather than an assumption about
the input.

### Worked example

Simple: insertion sort is Θ(n²) in the worst case. On an array that is
already sorted except for three elements out of place, it does about n
plus a few times n steps, nearly linear. The worst-case label is correct
and useless for that input; the number of inversions (chapter 7) is the
honest measure.

Realistic: quicksort's worst case is quadratic, yet it is the default sort
in many C libraries and was in V8 for years. Its average is n log n with a
small constant, and with a random or median-of-three pivot the quadratic
case almost never happens. A team that ruled it out on worst-case grounds
alone would have chosen a slower sort. A team that used it on
attacker-supplied input without randomisation would be open to a
deliberate slowdown. Both lessons come from this section.

### Common mistake

The mistake is either extreme: rejecting an algorithm because its worst
case is bad when that case never occurs, or trusting an average when an
adversary chooses the input. The fix is to ask who chooses the input. If
it is nature, averages and measurement are fine. If it is a user who might
be hostile, the worst case is the one that matters.

### In real systems

Regular-expression engines that backtrack are exponential in the worst
case; most inputs are fast, and a crafted one (a "ReDoS") can stall a
server. Hash tables are constant on average and linear in the worst case,
and hash-flooding attacks choose keys that collide. Both are fixed by
changing the algorithm (linear-time regex engines, seeded hash functions),
not by hoping. Conversely, the simplex method for linear programming is
exponential in the worst case and used daily because real problems do not
look like the worst case.

## From beginner to strategy

<Levels label="Chapter 2, Algorithm Analysis">

<Level name="Beginner" depth={3}>

At the beginner level, the chapter teaches one question: when the input
doubles, what happens to the time? If it doubles, the algorithm is linear.
If it quadruples, quadratic. If it adds a constant, logarithmic. Big-O is
the notation for the answer.

A worked example: checking whether a list of n emails has a duplicate. The
obvious way compares every pair, about n² / 2 comparisons. For 1,000
emails that is half a million comparisons, instant. For a million emails
it is half a trillion, which takes a long time. Putting each email in a
`Set` and checking membership is one pass: a million operations.

```ts
const hasDupPairs = (xs: string[]) => xs.some((x, i) => xs.indexOf(x) !== i); // quadratic
const hasDupSet = (xs: string[]) => new Set(xs).size !== xs.length;          // linear
```

The beginner mistake is thinking the first version is linear because there
is only one visible loop. `indexOf` is a loop. Read every call inside a
loop as a loop.

</Level>

<Level name="Intermediate" depth={3}>

At the intermediate level the rules combine on real code. Take a function
that, for a sorted array of n prices, counts the pairs that sum to a
target.

```ts
function countPairs(prices: number[], target: number): number {
  let count = 0;
  for (let i = 0; i < prices.length; i++) {
    // binary search for target - prices[i] in the part after i
    let lo = i + 1, hi = prices.length - 1;
    while (lo <= hi) {
      const mid = lo + ((hi - lo) >> 1);
      if (prices[mid] < target - prices[i]) lo = mid + 1;
      else if (prices[mid] > target - prices[i]) hi = mid - 1;
      else { count++; break; }
    }
  }
  return count;
}
console.log(countPairs([1, 2, 3, 4, 5, 6], 7)); // 3: (1,6) (2,5) (3,4)
```

Rule 1: the outer loop runs n times. Inside it, binary search costs
O(log n). So the total is O(n log n), better than the O(n²) of checking
every pair. A two-pointer scan from both ends would be O(n). The rules
show the ladder: n², n log n, n.

The intermediate mistake is that this version counts at most one match per
i, so with duplicate prices it under-counts. Analysis and correctness are
separate checks; do both.

</Level>

<Level name="Advanced" depth={3}>

The advanced level is the precise mathematics. The formal definitions are
statements about all large n with explicit constants, so a bound is
proved by exhibiting c and n₀. The limit test is a shortcut that gives Θ,
o, or the reverse depending on whether f(n) / g(n) tends to a positive
constant, zero or infinity. Recurrences of the form T(n) = aT(n/b) + f(n)
are solved by the recursion tree (sum the work per level) or by the master
theorem, which chapter 10 states.

A precise example: prove log n is o(n^ε) for every ε greater than 0. By
L'Hôpital, the ratio (ln n) / n^ε has the same limit as
(1/n) / (ε n^(ε−1)), which is 1 / (ε n^ε), which tends to 0. So every
logarithm loses to every positive power, eventually. For ε equal to 0.1,
"eventually" is very large: log₂ n stays above n^0.1 until n is
about 2⁵⁹, roughly 6 × 10¹⁷. The advanced mistake is forgetting that asymptotic
statements can kick in only at absurd sizes; the constants and crossover
points decide what happens in practice.

</Level>

<Level name="Edge cases" depth={3}>

Each analysis has boundary inputs to check by hand.

- **Empty input.** All four maximum subsequence sum algorithms return 0.
  Binary search on `[]` has `hi` equal to −1, skips the loop and returns
  −1. Good; but `mid` computed before the loop would read `a[-1]`.
- **One element.** `mss4([-5])` returns 0 under the empty-run convention;
  `mss4([5])` returns 5.
- **All negative.** Convention decides: 0 (empty run allowed) or the
  largest element. State it in the function's name or docs.
- **Duplicates in binary search.** `binarySearch([2, 2, 2], 2)` returns 1,
  an arbitrary match. Finding the *first* match needs a different update
  (keep searching left after a hit).
- **gcd with a zero.** `gcd(0, 5)` is 5 after one step; `gcd(0, 0)` returns
  0, which is a convention, since every number divides 0.
- **Exponent zero.** `pow(x, 0)` must be 1, including `pow(0n, 0)`, by
  convention.

The mistake is not deciding these on purpose. Write the convention down
and make a test for each.

</Level>

<Level name="Corner cases" depth={3}>

Corner cases combine two conditions.

- **Large n and integer overflow together.** In Java or C,
  `(lo + hi) / 2` overflows when both are above about a billion. In
  JavaScript the sum is exact up to 2⁵³ but `>> 1` converts to a 32-bit
  integer, so `(lo + hi) >> 1` breaks above 2³¹. My `lo + ((hi - lo) >> 1)`
  keeps the shifted value small.
- **All-negative input and a "must be non-empty" requirement.** `mss4`
  silently returns 0, which looks like a valid answer. The fix is the
  non-empty variant, not a check afterwards.
- **Huge exponents and Number precision.** `powc(3, 40)` as a Number gives
  12157665459056929000, not the exact 12157665459056928801: the
  algorithm is right and the arithmetic is not. BigInt or modular
  reduction fixes it.
- **Timing small n with JIT warm-up.** Timing the cubic algorithm first and
  the linear one second at tiny sizes can rank them backwards, because the
  JIT compiler had not optimised the first function yet. Warm up, repeat,
  and time several sizes.

The mistake is testing each boundary separately; the pairs are where
production finds bugs.

</Level>

<Level name="Production level" depth={3}>

In production, analysis turns into three practices.

The first is **naming n**. In a multi-tenant service, the n that matters is
often the largest tenant, not the average one. A report that is quadratic
in a customer's orders is fine for the median customer with 50 orders and
an outage for the one with 200,000. I write the variable in the complexity
comment: "O(orders × lineItems) per request".

The second is **measuring growth, not points**. A benchmark at one size is
a number; a benchmark at doubling sizes is a growth rate, which can be
compared with the analysis. If doubling n multiplies time by 4 when I
expected 2, there is a hidden quadratic, often a `shift`, `includes` or
`splice` inside a loop.

The third is **guarding the worst case**. Inputs from users get size
limits (maximum page size, maximum JSON depth, maximum regex length)
precisely so that the worst case is bounded. The analysis tells me where
the limit has to be. The production mistake is setting limits by feel; set
them by the cost model.

</Level>

<Level name="Mindset" depth={3}>

The mindset is "what is the slow version recomputing?". Each step from
cubic to linear in the maximum subsequence sum came from noticing repeated
work: re-adding sums, then exploring runs that could not win. The same
question finds most real performance wins.

An example outside the chapter: a page renders a list of 5,000 items and
recomputes a filtered and sorted copy on every keystroke. The slow version
recomputes the sort even when only the filter changed. Caching the sorted
list and filtering it is the algorithm 1 to algorithm 2 move.

The second habit is keeping a slow correct version around. The cubic
algorithm is the oracle that caught bugs in the fast ones. In production
code I keep the simple version in the tests as the reference
implementation. The mistake is deleting it once the fast one "works".

</Level>

<Level name="System design" depth={3}>

At system scale, analysis is capacity planning. A concrete example: a
feed service ranks posts for each user. If ranking is O(p log p) in the
number of candidate posts p, and each user follows f accounts posting r
posts a day, then p is f × r and the work per refresh is
O(f r log(f r)). Doubling the average follow count slightly more than
doubles the ranking cost. That estimate decides whether to rank on read,
precompute on write (fan-out), or cap candidates.

The divide-and-conquer shape scales across machines: split the data,
solve each part on its own worker, combine with a linear step. MapReduce
and parallel aggregations in databases follow the same recurrence as
algorithm 3, with the combine step as the bottleneck to design.

The design mistake is optimising the component with the best big-O
instead of the one with the largest n. Profile by where n is large.

</Level>

<Level name="Strategy" depth={3}>

My strategy for this chapter is to make analysis a reflex by doing it on
code I wrote. First, the definitions: I prove three bounds from the
definition with explicit constants, and three with the limit test. Then
the rules: I take five functions from my own projects and write their
complexity in a comment, naming n.

Then the set piece: I implement all four maximum subsequence sum
algorithms, test them against each other on random arrays, and time them
at doubling sizes. I record the ratios and compare them with 8, 4, a bit
over 2, and 2. I do the same for binary search against linear search.

The mistake I avoid is reading the four algorithms without running them.
The timings are what make the abstraction stick.

Done when my four implementations agree on 1,000 random arrays, my timing
ratios match the predicted growth, and I can prove from the definition
that 3n² + 10n + 7 is Θ(n²) without notes.

</Level>

</Levels>

## Questions people ask

**Is O(n) always faster than O(n²)?** For large enough n, yes. For small
n, not necessarily: an O(n²) algorithm with a tiny constant can beat an
O(n) algorithm with a large one. Big-O predicts the winner as n grows, not
at every size.

**Why do people say O when they mean Θ?** Habit. O is easier to type and
in everyday speech "O(n log n)" usually means "grows like n log n". In a
proof or a lower bound, use the right symbol.

**Does the base of the logarithm matter?** Not inside big-O, since logs of
different bases differ by a constant factor. It matters for a real estimate
of steps: log₂ of a million is about 20, log₁₀ is 6.

**What is n for a graph or a string pair?** Whatever measures the input.
Graphs use two variables, V and E; string comparison uses both lengths.
An O(n + m) algorithm is not O(n) when m can be much larger.

**Is amortised the same as average?** No. Average-case assumes a
probability distribution over inputs. Amortised is a worst-case guarantee
over any sequence of operations. Chapter 11 covers it.

**Do I need the formal definitions day to day?** Rarely the constants, but
the definitions tell you what claims mean, which stops you making wrong
ones like "O(2n) is slower than O(n)".

**Why is the empty run allowed in the maximum subsequence sum?** It is the
book's convention, so the answer is never negative. Many problem
statements require a non-empty run; adjust the code and test both.

## Key takeaways

- Big-O is an upper bound, Ω a lower bound, Θ both, little-o strictly
  slower.
- A bound is proved by finding constants c and n₀, or by the limit of the
  ratio.
- The cost model counts simple steps as one; it gets growth right and
  constants wrong.
- Worst case is the default because it is a guarantee and computable.
- Loops multiply, sequences add, branches take the larger, recursion
  becomes a recurrence.
- Hidden loops (`includes`, `indexOf`, `shift`, `splice`) count.
- Maximum subsequence sum goes from cubic to linear by removing repeated
  work, and the timing ratios show it.
- Halving with constant work per step gives a logarithm: binary search,
  Euclid, fast exponentiation.
- T(n) = 2T(n/2) + Θ(n) is Θ(n log n).
- Worst-case bounds can be pessimistic; averages need a distribution; ask
  who chooses the input.

## Glossary

- **Big-O**: T is O(f) if T(n) is at most c f(n) for all n at least n₀.
- **Big-Omega**: T is Ω(g) if T(n) is at least c g(n) for all large n.
- **Big-Theta**: both O and Ω of the same function; a tight bound.
- **Little-o**: grows strictly slower; the ratio tends to 0.
- **Growth rate**: the shape of a function as n grows, ignoring constants.
- **Limit**: the value a ratio settles towards as n grows without bound.
- **L'Hôpital's rule**: compare two growing functions by their derivatives.
- **Cost model**: the imaginary machine used to count steps.
- **Input size**: the parameter n that the running time is a function of.
- **Worst case**: the maximum time over all inputs of size n.
- **Average case**: the expected time under an assumed input distribution.
- **Recurrence relation**: an equation giving T(n) in terms of T on smaller n.
- **Recursion tree**: a picture of a recurrence; sum the work per level.
- **Maximum subsequence sum**: the largest sum of a contiguous run.
- **Online algorithm**: one that processes input in a single pass and can
  answer at any time.
- **Loop invariant**: a statement true before every iteration of a loop.
- **Binary search**: halving search on a sorted array.
- **Greatest common divisor**: the largest number dividing both inputs.
- **Exponentiation by squaring**: computing xⁿ with about log n multiplications.

<details>
<summary>What do c and n₀ mean in the definition of big-O?</summary>

c is a constant multiplier that absorbs machine and implementation
differences; n₀ is the size beyond which the bound must hold.

</details>

<details>
<summary>What is the limit test result for f = n log n and g = n²?</summary>

The ratio (log n) / n tends to 0, so n log n is o(n²).

</details>

<details>
<summary>Why is `for (const x of a) if (!out.includes(x)) out.push(x)` quadratic?</summary>

`includes` scans `out`, which can grow to n, inside a loop of n iterations.

</details>

<details>
<summary>What invariant proves the linear maximum subsequence sum correct?</summary>

Before position k, best is the largest run sum in the first k elements and
here is the largest sum of a run ending at k − 1, or 0.

</details>

<details>
<summary>Why is Euclid's algorithm logarithmic?</summary>

After two iterations the larger number is at most half what it was, so the
number of iterations is at most about 2 log₂ n.

</details>

<details>
<summary>What does the cubic algorithm's time do when n doubles?</summary>

It multiplies by about 8, since (2n)³ is 8n³.

</details>

<details>
<summary>Give one reason a worst-case bound might be ignored, and one reason it must not be.</summary>

Ignored when the worst case is unreachable by real inputs; never ignored
when an adversary chooses the input.

</details>
