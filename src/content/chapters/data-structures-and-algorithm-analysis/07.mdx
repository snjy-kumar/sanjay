Sorting is the most studied problem in computing, and for good reason:
sorted data makes searching, merging, de-duplicating and reporting
cheap, and many algorithms start with "first, sort". This chapter builds
the main sorting algorithms in my own TypeScript, measures them on a
million numbers, and proves the limits: why any algorithm that swaps
neighbours is quadratic, and why any algorithm that only compares items
needs about n log n comparisons. Then it steps outside those limits with
bucket and radix sort, and outside main memory with external sorting.

## 7.1 Preliminaries

### In one sentence

This chapter sorts arrays in memory by comparing items, and counts the
cost in comparisons and moves.

### The idea

A **comparison-based sort** learns about the items only by comparing two
of them with `<` (or a comparator). It never looks at the bits of a key.
That makes it general: it can sort numbers, strings or records by any
order. It also makes a lower bound possible, because a comparison gives
at most one bit of information.

Most of the chapter assumes the input fits in memory and is in an array,
so any position can be read in O(1). Section 7.12 drops that assumption.
The cost model counts comparisons and data moves; in TypeScript, moving
a number is cheap, but comparing records through a comparator function
is not, so comparison counts predict time well.

Two properties matter beyond speed. A sort is **stable** if items with
equal keys keep their original order, which matters when sorting records
by one field after another. A sort is **in place** if it uses only O(1)
or O(log n) extra memory.

### Worked example

Every sort below has the same signature, with a counter for comparisons,
so I can compare them fairly:

```ts
let C = 0;                                  // comparisons made
const less = (a: number, b: number) => (C++, a < b);
// a sort: (a: number[]) => number[], sorting a in place and returning it
// test harness: a random array, a copy sorted with the built-in sort,
// and a check that both are equal element by element
```

The data for timings is a million random integers below 10⁹ from a
seeded generator, so every run sees the same input.

### Common mistake

The mistake in JavaScript is calling `array.sort()` with no comparator on
numbers. The default converts items to strings, so `[10, 9, 1].sort()`
gives `[1, 10, 9]`. Pass `(a, b) => a - b`, or use a typed array, whose
`sort` is numeric.

### In real systems

V8 (Node and Chrome) uses TimSort for `Array.prototype.sort`, which is
stable and adaptive. C++'s `std::sort` is introsort (quicksort that falls
back to heapsort), and `std::stable_sort` is a mergesort. Java sorts
primitives with a dual-pivot quicksort and objects with TimSort, because
objects need stability.

## 7.2 Insertion sort

### In one sentence

Insertion sort grows a sorted prefix one item at a time, sliding each new
item left until it is in place.

### The idea

#### 7.2.1 The algorithm

Insertion sort makes n − 1 passes. Before pass p, positions 0 to p − 1
are sorted. Pass p takes the item at position p, and moves larger items
in the prefix one place right until it finds the slot for the item. Like
the heap's percolation, it moves a hole rather than swapping, which
halves the writes.

#### 7.2.2 An STL-style implementation

The book writes insertion sort as a template over iterators, so that it
works on any random-access range and any comparator. The TypeScript
equivalent is a function over an array with a comparator and a range
`lo..hi`, which quicksort will reuse for small subarrays.

#### 7.2.3 Analysis

The inner loop runs at most p times in pass p, so the worst case is
1 + 2 + ... + (n − 1) = n(n − 1)/2 comparisons: O(n²). That happens on
reverse-sorted input. On sorted input each pass makes one comparison, so
the time is O(n). On random input, the average is about n²/4. Insertion
sort is fast when the input is nearly sorted, which is why it is used for
small or almost-ordered pieces inside faster sorts.

### Worked example

```ts
function insertionSort(a: number[], lo = 0, hi = a.length - 1) {
  for (let p = lo + 1; p <= hi; p++) {
    const t = a[p];
    let j = p;
    while (j > lo && a[j - 1] > t) { a[j] = a[j - 1]; j--; }  // shift right
    a[j] = t;                                                   // drop into the hole
  }
  return a;
}
```

On 2,000 random numbers, averaged over 20 runs, my counter showed
1,004,194 comparisons. The prediction n²/4 is exactly 1,000,000, and the
small extra is the one comparison per pass that ends the inner loop.

### Common mistake

The mistake is writing the inner loop as swaps (`[a[j], a[j-1]] =
[a[j-1], a[j]]`) instead of shifts. It is correct but does three times
the writes, and destructuring allocates in some engines. The other
mistake is using insertion sort as the main sort for large inputs because
"it was fast on my test", which was sorted.

### In real systems

TimSort and introsort both switch to insertion sort for short runs
(typically 16 to 64 items), and TimSort extends short natural runs with
binary insertion sort. Leaderboards and other nearly sorted lists that
change one item at a time are kept sorted by inserting the changed item,
which is one pass of insertion sort.

## 7.3 A lower bound for simple sorting algorithms

### In one sentence

Any sort that only swaps adjacent items removes at most one inversion
per swap, and a random array has about n²/4 inversions, so such sorts
are quadratic on average.

### The idea

An **inversion** in an array is a pair of positions i before j with
`a[i] > a[j]`. A sorted array has none; a reversed array has n(n − 1)/2,
the most possible. Swapping two adjacent items that are out of order
removes exactly one inversion and changes no other pair.

So insertion sort's running time is O(n + I), where I is the number of
inversions in the input. That explains both its O(n) best case and its
quadratic worst case in one formula.

The average number of inversions in a random permutation is
n(n − 1)/4. The argument pairs each permutation with its reverse: every
pair of values is an inversion in exactly one of the two, so the two
together have n(n − 1)/2 inversions, and on average one has half that.

Therefore **any** algorithm that sorts by exchanging adjacent items
(insertion sort, bubble sort, selection-by-swaps) takes Ω(n²) time on
average. To beat that, an algorithm must compare and exchange items that
are far apart, removing many inversions with one swap. Every faster sort
in this chapter does exactly that.

### Worked example

Counting inversions directly for 8 3 6 1 5: the pairs (8,3), (8,6),
(8,1), (8,5), (3,1), (6,1), (6,5). Seven, matching the seven shifts in
the trace above. My brute-force counter:

```ts
function inversions(a: number[]) {
  let c = 0;
  for (let i = 0; i < a.length; i++)
    for (let j = i + 1; j < a.length; j++)
      if (a[i] > a[j]) c++;
  return c;
}
console.log(inversions([8, 3, 6, 1, 5]));   // 7
```

This counter is quadratic; a modified mergesort counts inversions in
O(n log n), an exercise at the end.

### Common mistake

The mistake is reading the bound as "all sorts are Ω(n²)". It covers
only algorithms that remove inversions one adjacent swap at a time.
Shellsort, heapsort, mergesort and quicksort all move items long
distances and are not covered by it.

### In real systems

Inversion counts measure "how unsorted" data is. Adaptive sorts like
TimSort run fast on data with few inversions or long sorted runs, which
is common in practice (appending to sorted logs, re-sorting after small
edits). Inversion counts also measure ranking disagreement: Kendall's tau
distance between two rankings is the number of inversions between them.

## 7.4 Shellsort

### In one sentence

Shellsort runs insertion sort on items a fixed gap apart, for a
shrinking sequence of gaps ending at 1, so that items move long distances
early and the final pass has little left to do.

### The idea

Shellsort (named after Donald Shell) picks an **increment sequence**
h₁ = 1 < h₂ < ... < hₜ and, from the largest gap down, performs an
**hₖ-sort**: insertion sort on each of the subsequences of items hₖ
apart. After an hₖ-sort, the array is **hₖ-sorted**: `a[i] ≤ a[i + hₖ]`
for every i. A key fact proved in the book is that a later, smaller gap
does not undo the earlier ordering, so the array stays hₖ-sorted.

The final pass with gap 1 is plain insertion sort, so the result is
always sorted. The earlier passes are there to remove inversions in big
jumps, so the final pass finds few left.

#### 7.4.1 Worst-case analysis of Shellsort

The running time depends heavily on the gaps. Shell's original sequence
(n/2, n/4, ..., 1) has a Θ(n²) worst case: if all gaps are even until the
last, items in even positions are never compared with items in odd
positions until the final pass. **Hibbard's increments** (1, 3, 7, ...,
2ᵏ − 1) have no common factors between neighbours and give a Θ(n^(3/2))
worst case. **Sedgewick's increments** (1, 5, 19, 41, 109, ...) give
O(n^(4/3)) in the worst case and run well in practice. The exact average
case for good sequences is still an open problem.

### Worked example

My Shellsort takes the gap sequence as a parameter:

```ts
function shellsort(a: number[], gaps: number[]) {
  for (const g of gaps) {                      // largest gap first
    for (let i = g; i < a.length; i++) {
      const t = a[i];
      let j = i;
      while (j >= g && a[j - g] > t) { a[j] = a[j - g]; j -= g; }
      a[j] = t;
    }
  }
  return a;
}
```

On 100,000 random numbers, comparisons per item and time:

```text
gaps             comparisons per item   time     smallest gaps
Shell n/2^k      43.2                   ~28 ms   48, 24, 12, 6, 3, 1
Hibbard 2^k − 1  38.7                   ~40 ms   63, 31, 15, 7, 3, 1
Sedgewick        26.2                   ~27 ms   209, 109, 41, 19, 5, 1
```

Insertion sort on the same input would need about n/4 = 25,000
comparisons per item. Then the bad case: 4,096 items with the large half
in even positions and the small half in odd positions. Shell's gaps are
all even until 1, so the final pass faced about n²/8 inversions: my
counter showed 2,143,232 comparisons. Hibbard's odd gaps sorted the same
input with 50,192.

### Common mistake

The mistake is using Shell's halving gaps, which every textbook shows
first, in real code. They are the worst of the common choices. Use
Sedgewick's or a sequence like Ciura's (1, 4, 10, 23, 57, 132, 301, 701,
then multiply by about 2.25), found by experiment.

### In real systems

Shellsort is popular where code size and memory matter more than the
last few percent of speed: it needs no recursion, no extra memory and
only a dozen lines, so small C libraries and embedded firmware have used
it for their `qsort`. It is also a good default when you must hand-write
a sort in a language without a library one.

## 7.5 Heapsort

### In one sentence

Heapsort builds a max-heap in the array in linear time, then repeatedly
swaps the maximum to the end and restores the heap on the shrinking
front, sorting in place in O(n log n) worst case.

### The idea

Chapter 6 gives a sort for free: build a heap and deleteMin n times. The
naive version writes the outputs to a second array, doubling the memory.
The trick is that each deleteMin shrinks the heap by one slot, exactly
where the removed item can go. With a **max-heap**, the largest item goes
to the last slot, the next largest to the slot before, and the array ends
up ascending.

#### 7.5.1 Analysis

buildHeap costs at most 2n comparisons. Each of the n − 1 deleteMax
operations percolates down at most log₂ n levels with two comparisons per
level. So heapsort makes at most about 2n log₂ n comparisons in the worst
case, and the book shows the average is almost the same: heapsort's
running time is very consistent. It is in place but not stable, and its
memory access jumps around the array, which hurts cache performance.

### Worked example

```ts
function heapsort(a: number[]) {
  const down = (i: number, m: number) => {    // max-heap of the first m items
    const x = a[i];
    for (;;) {
      let c = 2 * i + 1;
      if (c >= m) break;
      if (c + 1 < m && a[c + 1] > a[c]) c++;  // larger child
      if (a[c] <= x) break;
      a[i] = a[c]; i = c;
    }
    a[i] = x;
  };
  for (let i = (a.length >> 1) - 1; i >= 0; i--) down(i, a.length);
  for (let m = a.length - 1; m > 0; m--) {
    [a[0], a[m]] = [a[m], a[0]];              // max to the end
    down(0, m);                                // fix the shrunken heap
  }
  return a;
}
```

On a million random integers, heapsort took about 176 ms and made 36.8
comparisons per item, close to 2 log₂ n = 39.9. Compare that with
mergesort's 18.7 below: heapsort does about twice the comparisons.

### Common mistake

The mistake is building a min-heap and then wondering where to put the
outputs. With a min-heap, in-place heapsort produces descending order.
Use a max-heap for ascending. A second mistake is passing the full array
length to `down` after shrinking: the heap must end at m, or the sorted
items get pulled back in.

### In real systems

Introsort (C++'s `std::sort`) switches from quicksort to heapsort when
recursion gets too deep, which guarantees O(n log n) worst case. The Linux
kernel's `sort()` is a heapsort, chosen for its guaranteed time and zero
extra memory, which matter more there than raw speed.

## 7.6 Mergesort

### In one sentence

Mergesort splits the array in half, sorts each half recursively, and
merges the two sorted halves in linear time, for O(n log n) in every case
with comparisons close to the theoretical minimum.

### The idea

The core is **merging**: given two sorted lists, repeatedly take the
smaller front item. Each comparison outputs one item, so merging lists of
total length n takes at most n − 1 comparisons. Mergesort is the classic
divide-and-conquer algorithm: split, solve both halves, combine.

Merging into the same array is hard, so mergesort uses a temporary array
of size n, allocated once and shared by all calls (allocating one per
call is a common performance bug). Mergesort is stable if ties take the
left item first.

#### 7.6.1 Analysis

The recurrence is T(1) = 1 and T(n) = 2T(n/2) + n. Dividing by n gives
T(n)/n = T(n/2)/(n/2) + 1; adding up log₂ n such equations telescopes to
T(n)/n = 1 + log₂ n, so T(n) = n log₂ n + n = O(n log n). The same result
comes from a recursion tree: log₂ n levels, each doing n work.

Mergesort does fewer comparisons than any other sort here. It does more
data movement (every item is copied twice per level), which is why it
loses to quicksort on primitive arrays but wins when comparisons are
expensive, such as sorting objects through a comparator.

### Worked example

```ts
function mergesort(a: number[]) {
  const tmp = new Array(a.length);            // one buffer for all calls
  const sort = (lo: number, hi: number) => {
    if (lo >= hi) return;
    const mid = (lo + hi) >> 1;
    sort(lo, mid); sort(mid + 1, hi);
    let i = lo, j = mid + 1, k = lo;
    while (i <= mid && j <= hi) tmp[k++] = a[i] <= a[j] ? a[i++] : a[j++];
    while (i <= mid) tmp[k++] = a[i++];
    while (j <= hi) tmp[k++] = a[j++];
    for (k = lo; k <= hi; k++) a[k] = tmp[k];
  };
  sort(0, a.length - 1);
  return a;
}
```

On a million random integers it took about 209 ms with 18.67 comparisons
per item. The lower bound of section 7.8 is log₂(n!)/n = 18.49 per item,
so mergesort is within 1% of the best possible comparison count.

The mistake is allocating new arrays in every recursive call
(`a.slice(0, mid)` and so on). It is the cleanest code and the slowest:
millions of small allocations. Allocate one buffer. The second mistake is
`a[i] < a[j]` in the merge, which takes the right item on ties and breaks
stability.

### In real systems

TimSort (Python, Java objects, V8) is a mergesort that first finds the
natural sorted runs in the data and merges them cleverly, so it is O(n)
on sorted input. Mergesort is also the basis of external sorting
(section 7.12), of sorting linked lists (no random access needed), and
of parallel sorting, because the two halves are independent.

## 7.7 Quicksort

### In one sentence

Quicksort picks a pivot, partitions the array into items smaller and
larger than the pivot in place, and sorts the two parts recursively; with
a good pivot it is the fastest comparison sort in practice.

### The idea

Quicksort is divide and conquer with the work done before the recursion,
not after. **Partitioning** rearranges the array so that every item left
of the pivot's final position is no larger than the pivot and every item
right of it is no smaller. The pivot is then in its final place, and the
two sides can be sorted independently, with no merge step and no extra
array.

The running time depends on how evenly the pivot splits the array. Even
splits give log₂ n levels of linear work, O(n log n). A pivot that is
always the smallest item gives n levels, O(n²). Everything in the details
below is about making bad splits unlikely and making each level cheap.

#### 7.7.1 Picking the pivot

Using the first item as pivot is a disaster on sorted or reverse-sorted
input, both common in practice: every split is 0 and n − 1. A random
pivot is safe on average but costs a random number per call.
**Median-of-three** takes the median of the first, middle and last items.
It fixes sorted input, costs three comparisons, and removes the need for
bounds checks in the partition loop, because the smallest of the three
ends up at the left end as a sentinel.

#### 7.7.2 Partitioning strategy

The book's partition hides the pivot at position hi − 1, then runs two
indexes towards each other: `i` from the left skips items smaller than
the pivot, `j` from the right skips items larger. When both stop, the two
items are on the wrong sides, so they are swapped. When the indexes
cross, the pivot is swapped into position `i`.

The subtle decision is what to do with items **equal** to the pivot. If
both indexes stop on equal items, an array of identical keys produces many
swaps but perfectly even splits, O(n log n). If neither stops, the
indexes run to the end and the splits are as uneven as possible, O(n²).
Stopping on equal keys is the right choice, because arrays with many
duplicates are common.

#### 7.7.3 Small arrays

For tiny subarrays, the recursion overhead outweighs quicksort's
advantage, and insertion sort is faster. A **cutoff** of about 10 (the
right value depends on the machine) switches to insertion sort for any
subarray smaller than that. This also avoids median-of-three on fewer
than three items.

#### 7.7.4 Actual quicksort routines

Put together: if the range is below the cutoff, insertion-sort it.
Otherwise take median-of-three, partition, and recurse on both sides.
Recursing on the smaller side first and looping on the larger one keeps
the stack depth at O(log n) even in bad cases.

#### 7.7.5 Analysis of quicksort

With i items left of the pivot, T(n) = T(i) + T(n − i − 1) + cn.

- **Worst case**: i = 0 every time, so T(n) = T(n − 1) + cn, which sums
  to O(n²).
- **Best case**: the pivot is always the median, so T(n) = 2T(n/2) + cn,
  O(n log n) like mergesort.
- **Average case**: if every split size is equally likely,
  T(n) = (2/n)(T(0) + ... + T(n − 1)) + cn. Multiplying by n, subtracting
  the same equation for n − 1 and telescoping gives T(n) = O(n log n),
  about 2n ln n ≈ 1.39 n log₂ n comparisons. Median-of-three lowers the
  constant to about 1.19.

#### 7.7.6 A linear-expected-time algorithm for selection

To find the k-th smallest item, partition as in quicksort, then recurse
into **only** the side that contains position k. This is
**quickselect**. On average each step halves the problem, so
T(n) = T(n/2) + cn = O(n). The worst case is still O(n²); section 10.2
shows a pivot rule that makes it O(n) in the worst case.

### Worked example

My quicksort, in two pieces. First the pivot choice and the partition:

```ts
function median3(a: number[], lo: number, hi: number) {
  const m = (lo + hi) >> 1;
  const sw = (i: number, j: number) => { const t = a[i]; a[i] = a[j]; a[j] = t; };
  if (a[m] < a[lo]) sw(lo, m);
  if (a[hi] < a[lo]) sw(lo, hi);
  if (a[hi] < a[m]) sw(m, hi);             // now a[lo] ≤ a[m] ≤ a[hi]
  sw(m, hi - 1);                           // hide the pivot at hi − 1
  return a[hi - 1];
}
```

Then the recursion, with the cutoff to insertion sort:

```ts
function quicksort(a: number[], lo = 0, hi = a.length - 1) {
  if (lo + 10 > hi) return insertionSort(a, lo, hi);
  const p = median3(a, lo, hi);
  let i = lo, j = hi - 1;
  for (;;) {
    while (a[++i] < p);                    // a[hi − 1] = p stops i
    while (p < a[--j]);                    // a[lo] ≤ p stops j
    if (i < j) { const t = a[i]; a[i] = a[j]; a[j] = t; } else break;
  }
  const t = a[i]; a[i] = a[hi - 1]; a[hi - 1] = t;   // pivot to its place
  quicksort(a, lo, i - 1);
  quicksort(a, i + 1, hi);
  return a;
}
```

On the same million random integers, my measurements:

```text

mergesort             209 ms    18.67
quicksort (median-3)  123 ms    22.62
Array.sort(cmp)       279 ms    –

```

Quicksort made 20% more comparisons than mergesort but finished in 60%
of the time, because its inner loops are tight and it touches memory
sequentially without copying. The typed-array sort wins overall because
it compares raw numbers in native code with no comparator calls.

### Common mistake

are equal. Always test quicksort on: sorted, reversed, all equal, two
distinct values, and arrays of length 0 to 3. A second mistake is
first-item pivots in code that will see sorted input, which in a server
becomes a denial-of-service vector.

### In real systems

pattern-defeating quicksort (pdqsort), which detects sorted runs and bad
pivots. Quickselect is `std::nth_element` in C++ and the core of
"median" and "percentile" functions in data libraries.

## 7.8 A general lower bound for sorting

### In one sentence

Any algorithm that sorts by comparisons alone must make at least
log₂(n!) ≈ n log₂ n − 1.44n comparisons in the worst case, so mergesort,
heapsort and quicksort are optimal up to constant factors.

### The idea

#### 7.8.1 Decision trees

A **decision tree** models a comparison sort on n items. Each internal
node is a comparison ("is a < b?"), its two children are the two possible
outcomes, and each leaf is the point where the algorithm has learned
enough to know the order. Any comparison sort, run on all n! possible
input orders, traces out such a tree; the number of comparisons on an
input is the depth of its leaf.

The tree must have at least n! leaves, one per possible order, because
two different orders must end at different leaves (otherwise the
algorithm would rearrange them the same way and get one of them wrong).
A binary tree of depth d has at most 2ᵈ leaves. So the worst-case depth
is at least log₂(n!).

Stirling's approximation turns log₂(n!) into n log₂ n − n log₂ e +
O(log n), about n log₂ n − 1.44n. The same argument bounds the average
depth too: a binary tree with L leaves has average leaf depth at least
log₂ L. So even on average, a comparison sort needs Ω(n log n)
comparisons.

### Worked example

The bound, computed:

```text
n            log2(n!)       comparisons needed (rounded up)
3            2.58           3
4            4.58           5
5            6.91           7
10           21.79          22
12           28.84          29
1,000,000    18.49 n        my mergesort: 18.67 n
```

For n = 5, the bound says 7 comparisons, and 7 is achievable (by a
clever hand-made method); simple insertion sort can need 10. For a
million items, the bound is 18.49 comparisons per item and my mergesort
used 18.67.

### Common mistake

The mistake is applying the bound to sorts that do not compare: radix
sort and counting sort look at the digits of keys and can be linear
(section 7.11). Another mistake is thinking the bound says quicksort's
worst case is fine; it says nothing about worst cases above n log n, only
that none can be below.

### In real systems

The bound explains why sorting libraries have converged: once a sort is
within a few percent of log₂(n!) comparisons, the remaining gains come
from memory access, branch prediction and adaptivity to existing order,
which is where TimSort, pdqsort and vectorised sorts compete.

## 7.9 Decision-tree lower bounds for selection problems

### In one sentence

Decision trees also bound selection: finding the smallest of n items
needs n − 1 comparisons, and finding the second smallest needs
n + ⌈log₂ n⌉ − 2.

### The idea

For selection, the leaves do not need to separate all n! orders, only the
answers, so the counting argument changes. The book's approach is to
count how many leaves a correct tree must have and to show that every
path must contain certain comparisons.

- **Smallest item.** Every item other than the answer must lose at least
  one comparison, or the algorithm cannot know it is not the minimum. Each
  comparison has one loser, so at least n − 1 comparisons are needed.
- **Second smallest.** A knockout **tournament** finds the smallest with
  n − 1 comparisons. The second smallest must have lost only to the
  smallest, so it is among the ⌈log₂ n⌉ items the winner beat. A second
  tournament among them costs ⌈log₂ n⌉ − 1, for n + ⌈log₂ n⌉ − 2 total,
  and the decision-tree argument shows no algorithm can do better.
- **Median.** The book shows that finding the median needs at least about
  3n/2 comparisons, more than the n − 1 for the minimum.

### Worked example

A tournament on 8 items: 14, 6, 11, 3, 9, 5, 12, 8. Round one: 6, 3, 5, 8
win; round two: 3 and 5; final: 3. That is 7 comparisons. The winner 3
beat 11, 6 and 5 on the way. The second smallest is among those three:
two more comparisons find 5. Total 9 = 8 + 3 − 2.

### Step by step

                          3

               3                     5
           /       \\             /       \\

### Common mistake

The mistake is finding the two smallest with two separate scans, which
costs about 2n comparisons, when a single scan that keeps the best two
costs about n plus a little on random input, and the tournament
guarantees n + log₂ n in the worst case.

### In real systems

Tournament trees are used in multiway merging (section 7.12): the
winner is output and replaced, and only its path to the root is replayed,
log₂ k comparisons per item. Sports brackets are the same structure, and
the "second place deserves a rematch" debate is this section's argument.

## 7.10 Adversary lower bounds

### In one sentence

An adversary argument proves a lower bound by imagining an opponent who
answers each comparison to keep the algorithm uninformed for as long as
possible, while staying consistent with some input.

### The idea

An **adversary** does not fix the input in advance. It answers each
comparison in whatever way reveals the least, under one rule: the
answers must always be consistent with at least one real input. If the
adversary can keep the algorithm from knowing the answer for k
comparisons, any algorithm needs more than k in the worst case.

The book's main example is finding both the **minimum and the maximum**.
Track each item's state: untested, won at least once (could be the max),
lost at least once (could be the min), or both (neither). The algorithm
must end with one item that never lost (the max), one that never won
(the min), and every other item having both won and lost. That needs
2n − 2 units of information. The adversary answers so that each
comparison provides at most 2 units only when comparing two untested
items, and 1 unit otherwise, giving a bound of ⌈3n/2⌉ − 2.

The matching algorithm pairs up items: compare each pair (n/2
comparisons), then find the minimum among the pair-losers and the
maximum among the pair-winners (n/2 − 1 each).

### Worked example

```ts
function minMax(a: number[]) {
  let mn = Infinity, mx = -Infinity, c = 0;
  for (let i = 0; i + 1 < a.length; i += 2) {
    const [s, b] = (c++, a[i] < a[i + 1]) ? [a[i], a[i + 1]] : [a[i + 1], a[i]];
    if ((c++, s < mn)) mn = s;               // losers compete for the minimum
    if ((c++, b > mx)) mx = b;               // winners compete for the maximum
  }
  return { mn, mx, c };
}
```

On 1,000 random items it made 1,500 comparisons. The bound is
⌈3n/2⌉ − 2 = 1,498; starting `mn` and `mx` from the first pair instead of
infinities saves exactly the two extra comparisons. Two separate scans
would make 1,998.

### Common mistake

The mistake is constructing an adversary that contradicts itself, for
example answering a < b, b < c and then c < a. An adversary argument is
only valid if some real input is consistent with every answer it gave.

### In real systems

Adversary thinking is how hash flooding and algorithmic-complexity
attacks work: the attacker chooses inputs that make the algorithm's
choices worst, as section 7.7 noted for first-item pivots. Randomisation
defeats a fixed adversary, which is why hash seeds and random pivots are
used in exposed code.

## 7.11 Linear-time sorts: bucket sort and radix sort

### In one sentence

When keys are small integers or strings over a small alphabet, sorting by
distributing items into buckets indexed by the key (or one digit at a
time) runs in linear time, beating the comparison bound.

### The idea

**Bucket sort** (in the book's sense, often called counting sort) applies
when keys are integers in 0..M − 1. Keep an array of M counters (or
lists), drop each item into the bucket for its key, then read the buckets
in order. That is O(n + M), linear when M is O(n). It does not violate
section 7.8, because it uses the key as an array index, which reveals
far more than one bit per step.

**Radix sort** extends this to large keys by sorting one digit at a time,
**least significant digit first**, with a stable bucket pass for each
digit. Stability is essential: after sorting by the last digit, a pass on
the next digit must keep ties in the order the previous pass produced.
With d digits in base b, the cost is O(d(n + b)). For 32-bit integers in
base 256, that is four linear passes.

The **uniform-distribution bucket sort** handles real numbers spread
evenly in [0, 1): n buckets, each covering an interval of width 1/n,
receive about one item each on average, and sorting each small bucket is
O(1) expected.

### Worked example

Counting sort of ages 34, 21, 34, 19, 45, 21, 34 into 50 counters gives
19, 21, 21, 34, 34, 34, 45. Then LSD radix sort, first on strings and
then on integers:

```ts
function radixSort32(a: Uint32Array) {
  let src = a, dst = new Uint32Array(a.length);
  for (let shift = 0; shift < 32; shift += 8) {       // 4 passes of 8 bits
    const cnt = new Uint32Array(257);
    for (const x of src) cnt[((x >>> shift) & 255) + 1]++;
    for (let i = 0; i < 256; i++) cnt[i + 1] += cnt[i];  // start positions
    for (const x of src) dst[cnt[(x >>> shift) & 255]++] = x;  // stable
    [src, dst] = [dst, src];
  }
  return src;
}
```

On a million random 32-bit integers, radix sort took about 39 ms against
66 ms for the native typed-array sort, and produced the same output.
The uniform bucket sort was a lesson in constants: with a million
JavaScript arrays as buckets it took 945 ms, though no bucket held more
than 9 items. The algorithm was linear; the allocation was not cheap.

The mistake is an unstable bucket pass inside radix sort (for example

radix-style partitioning for hash joins. Suffix array construction

## 7.12 External sorting

### In one sentence

When the data does not fit in memory, sort chunks that do fit into
**runs**, write them out, and merge the runs in as few passes over the
data as possible.

### The idea

#### 7.12.1 Why we need new algorithms

The sorts above assume O(1) access to any item. On disk or tape, random
access is very slow (a seek) while sequential reads are fast. Algorithms
must read and write data in long sequential streams, and the cost is the
number of **passes** over the data.

#### 7.12.2 Model for external sorting

The book uses the classic tape model: data on sequential tapes, memory
for M records, and a few tape drives. It is old-fashioned, but it is
exactly the right model for any storage where sequential access is cheap
and random access is not, which includes disks, SSDs at scale, and
networked object storage.

#### 7.12.3 The simple algorithm

Read M records, sort them in memory, write them as a sorted **run**,
alternating between two output tapes. That gives ⌈N/M⌉ runs. Then merge
runs pairwise onto two more tapes, doubling run length each pass, until
one run remains. With four tapes, that is ⌈log₂(N/M)⌉ merge passes after
the first.

#### 7.12.4 Multiway merge

With 2k tapes, a **k-way merge** combines k runs at once, using a heap of
the k current front items to pick the smallest in O(log k). The number of
passes falls to ⌈log_k(N/M)⌉. For 1,000 runs, 2-way merging needs 10
passes, 8-way needs 4, and 100-way needs 2.

#### 7.12.5 Polyphase merge

k-way merging with 2k tapes wastes half the drives as output.
**Polyphase merge** uses only k + 1 tapes by splitting the runs unevenly,
following Fibonacci numbers (for k = 2). Each phase merges until one input
tape runs out, which then becomes the next output tape.

#### 7.12.6 Replacement selection

Runs can be longer than M. **Replacement selection** keeps a heap of M
records: output the smallest, read the next input record, and if it is no
smaller than the record just output, it can join the current run;
otherwise, it waits in the heap for the next run. On random input, runs
average about 2M; on input that is already nearly sorted, a single run
can cover everything.

### Worked example

Replacement selection with M = 3 on 81 94 11 96 12 35 17 99 28 58 41 75
15 produced three runs:

```text
run 1: 11 81 94 96
run 2: 12 17 28 35 41 58 75 99
run 3: 15
```

The simple algorithm with M = 3 would produce five runs of at most 3.
On 100,000 random numbers with M = 1,000, my replacement selection made
51 runs averaging 1,961 records, against 100 runs for the simple method;
on sorted input it made exactly 1 run.

which turns sequential reads into random seeks.

### In real systems

larger than memory the same way, with temporary files and a multiway

continuous: memtables flush as sorted runs and compaction merges them.

At the beginner level, the chapter teaches that sorting has a few
standard answers and one trap. The answers: use the library sort, with
a comparator. The trap in JavaScript: `sort()` without a comparator sorts
numbers as strings.

A worked example: sorting a list of orders by total, then by date for
equal totals. The library sort in Node is stable, so sort by date first,
then by total, and orders with the same total stay in date order.

```ts
type Order = { id: string; total: number; date: string };
const orders: Order[] = [
  { id: 'a', total: 30, date: '2026-03-02' },
  { id: 'b', total: 12, date: '2026-01-15' },
  { id: 'c', total: 30, date: '2026-01-09' },
];
orders.sort((x, y) => x.date.localeCompare(y.date));   // secondary key first
orders.sort((x, y) => x.total - y.total);              // then primary, stably
console.log(orders.map((o) => o.id).join(' '));        // b c a
```

The beginner mistake is the default `sort()` on numbers; the second is a
comparator that returns a boolean, which some engines accept and
silently mis-sort.

</Level>

<Level name="Intermediate" depth={3}>

At the intermediate level, I can write insertion sort, mergesort,
heapsort and quicksort from memory and state their costs: n²/4 average
for insertion sort, n log₂ n comparisons for mergesort, about 2n log₂ n
for heapsort, about 1.19 n log₂ n for median-of-three quicksort. I
measured 18.7, 36.8 and 22.6 comparisons per item for a million items.

A worked example: choosing a sort for 10,000 records that arrive nearly
sorted, with a few late arrivals. Insertion sort costs O(n + I) and I is
small, so it beats an O(n log n) sort here, and TimSort would detect the
same thing automatically.

The intermediate mistake is choosing by Big-O alone. Mergesort has the
best comparison count and loses to quicksort on numbers; insertion sort
is quadratic and wins on nearly sorted data.

</Level>

<Level name="Advanced" depth={3}>

The advanced level is the lower bounds and the escapes from them. The
decision-tree argument proves log₂(n!) comparisons; adversary arguments
prove ⌈3n/2⌉ − 2 for min-and-max; inversions prove n²/4 for adjacent
swaps. Each bound says which kind of idea is needed to go faster: long
moves, or non-comparison operations like indexing by key.

A precise example: sorting a million 32-bit integers. The comparison
bound is 18.5 comparisons per item; radix sort with four passes of 8 bits
makes no comparisons, touching each item eight times (a count and a
placement per pass), and ran in 39 ms against 66 ms for the native sort.

The advanced mistake is assuming radix sort always wins. For short arrays
or wide keys (long strings), the passes and the counter arrays cost more
than comparison sorting.

</Level>

<Level name="Edge cases" depth={3}>

The boundary inputs every sort must be tested on:

- **Length 0, 1, 2 and 3**, which hit the base cases and the
  median-of-three corner.
- **Already sorted and reverse sorted**, which break first-item pivots.
- **All equal** and **two distinct values**, which break partitions that
  do not stop on equal keys.
- **Organ pipe** (ascending then descending) and **sawtooth**, which
  defeat some pivot rules.
- **Odd lengths** in mergesort, where `mid` must split correctly.

A worked example: my quicksort on 100,000 equal items made 14.8
comparisons per item and took 10 ms, because both indexes stop on equal
keys. A version that skipped equal keys would be quadratic there.

The mistake is testing only random input, where every reasonable sort
works.

</Level>

<Level name="Corner cases" depth={3}>

Corner cases come from comparators and keys.

- **Inconsistent comparators**: a comparator that is not transitive
  (random tie-breaking, or comparing floats with tolerance) can make
  quicksort run off the end of an array in unchecked languages and makes
  results undefined everywhere.
- **NaN**: `NaN - x` is NaN, which a comparator treats as "equal" to
  everything, so arrays with NaN do not sort into a consistent order.
- **Negative numbers in radix sort**: flip the sign bit first.
- **Locale-aware strings**: `localeCompare` and byte order differ for
  accents and case; choose one deliberately.
- **Stability across engines**: JavaScript's sort is guaranteed stable
  since ES2019; older code may rely on it being unstable or not.

The mistake is assuming the comparator is "obviously" a total order.
Write it so that it is: compare keys in sequence, and handle NaN and
null explicitly.

</Level>

<Level name="Production level" depth={3}>

At production level, sorting is rarely a function call on an array.
It is an `ORDER BY` that spills to disk, a top-k that should not have
been a full sort, or a sort of a million objects whose comparator
allocates.

A worked example: an API endpoint returns "top 20 products by score"
and sorts 2 million rows in memory on every request. The fix is
selection: a heap of 20 (chapter 6) or quickselect followed by sorting
20 items. My measurements give a sense of scale: quickselect found the
median of a million in 21 ms against 294 ms for a full sort.

Other production habits: sort keys, not objects (precompute a numeric
key so the comparator is a subtraction); push sorting into the database
with an index so it never happens at request time; watch for "external
merge" in query plans, which means the sort exceeded memory.

The production mistake is sorting to answer a question that only needs
the top, the median or a membership test.

</Level>

<Level name="Mindset" depth={3}>

The mindset is that sorting is a preprocessing step that makes other
problems easy, and that its cost is n log n once. Duplicate detection,
grouping, merging two lists, finding the closest pair of numbers, and
interval scheduling all become linear scans after a sort.

A worked example: finding whether any two meetings overlap among n
meetings. Comparing all pairs is O(n²). Sorting by start time and
checking each meeting against the previous end time is O(n log n).

The second habit is asking what the input looks like before choosing:
nearly sorted, many duplicates, small integers, larger than memory. Each
answer points to a different section of this chapter.

The mindset mistake is reimplementing sorts in application code. Write
them to learn; ship the library one unless measurement says otherwise.

</Level>

<Level name="System design" depth={3}>

In system design, sorting appears as external sorting and as sort-based
architecture. MapReduce's shuffle is a distributed sort: map outputs are
sorted into runs, then merged at reducers. LSM trees turn random writes
into sorted runs merged in the background. Search engines keep posting
lists sorted so intersections are merges.

A worked example: sorting 1 TB of records on machines with 10 GB of
memory each. Each machine sorts 10 GB chunks into runs; a single 100-way
merge (with buffered reads from each run) produces the output in one
merge pass, so the data is read and written twice in total. A 2-way
merge would need 7 passes.

The system design mistake is designing around random access to data
that lives on disk or across a network, when a sort followed by
sequential merges would do the same work at a fraction of the cost.

</Level>

<Level name="Strategy" depth={3}>

The strategy for this chapter is to own five sorts and two proofs. The
sorts are insertion, Shellsort, heapsort, mergesort and quicksort, with
quickselect. The proofs are the inversion bound and the decision-tree
bound. Everything else (radix, external) is applying those ideas.

The plan, in order: write each sort with a comparison counter and a
randomised test harness; run them all on the same million items and
reproduce the table; break quicksort on purpose with first-item pivots
and with non-stopping partitions; draw the decision tree for three items
by hand; write radix sort and an external sort with replacement
selection on a file.

The strategic mistake is stopping at "I know quicksort is n log n" without
the edge-case tests, which is exactly where real sorts fail.

Done when my sorts pass randomised and edge-case tests, my comparison
counts match the theory within a few percent, and I can prove the
log₂(n!) bound from a blank page.

</Level>

</Levels>

## Questions people ask

**Which sort should I use?**
The library sort, almost always. Write your own only for learning,
special keys (radix), selection (quickselect or a heap), or data larger
than memory.

**Why is quicksort faster than mergesort if it does more comparisons?**
It partitions in place with tight loops and sequential memory access,
and does not copy items into a buffer and back on every level.

**Is quicksort's worst case a real risk?**
With first-item pivots on sorted input, yes. With median-of-three it is
rare, and introsort removes it by switching to heapsort.

**How can radix sort be linear if sorting needs n log n?**
The bound is for comparison sorts. Radix sort uses digits of the key as
array indexes, which a comparison sort cannot do.

**What does stable mean, and does JavaScript guarantee it?**
Equal keys keep their input order. `Array.prototype.sort` has been
required to be stable since ES2019.

**When is insertion sort the right choice?**
For very small arrays and nearly sorted data, where its O(n + I) cost is
close to linear.

**Why sort externally rather than buy more memory?**
Sometimes you should. But data often grows faster than memory, and
external sorting with a large merge fan-in reads the data only twice.

## Key takeaways

- Insertion sort costs O(n + inversions): linear on nearly sorted data,
  n²/4 on random data.
- Removing one inversion per swap forces Ω(n²); fast sorts move items
  far.
- Shellsort's speed depends on its gaps; avoid halving gaps.
- Heapsort is in place and O(n log n) worst case; mergesort is stable and
  nearly optimal in comparisons; quicksort is fastest in practice.
- Quicksort needs median-of-three (or random) pivots, stopping on equal
  keys, and a small-array cutoff.
- Quickselect finds the k-th smallest in O(n) expected.
- Comparison sorts need log₂(n!) ≈ n log₂ n − 1.44n comparisons.
- Bucket and radix sort are linear for small keys.
- External sorting minimises passes: long runs and wide merges.

## Glossary

- **Comparison sort:** a sort that learns about items only by comparing
  pairs.
- **Stable sort:** a sort that keeps equal keys in input order.
- **In place:** using O(1) or O(log n) extra memory.
- **Inversion:** a pair of positions whose items are out of order.
- **Increment sequence:** the gaps used by Shellsort.
- **Partition:** rearranging around a pivot into smaller and larger
  sides.
- **Median-of-three:** choosing the median of the first, middle and last
  items as pivot.
- **Cutoff:** the size below which quicksort hands over to insertion
  sort.
- **Quickselect:** finding the k-th smallest by partitioning and
  recursing into one side.
- **Introsort:** quicksort that switches to heapsort when recursion is
  too deep.
- **Decision tree:** a binary tree modelling the comparisons of an
  algorithm.
- **Adversary argument:** a lower bound proof by an opponent answering
  comparisons as unhelpfully as possible.
- **Radix sort:** sorting digit by digit with stable bucket passes.
- **Run:** a sorted sequence written during external sorting.
- **Replacement selection:** forming runs with a heap, giving runs of
  about 2M on random input.
- **Polyphase merge:** merging with k + 1 tapes using an uneven,
  Fibonacci-like split of runs.

## Exercises and self-check

### Warm-up

2. Shellsort `[7, 3, 9, 1, 6, 2]` with gaps 3 and 1, and write the array
   after each pass.
3. Partition `[4, 8, 1, 7, 3, 6, 2, 5]` with median-of-three and my
   partition, and give the final array and the pivot's position.

### Build

4. Modify mergesort to count inversions in O(n log n), and check it
   against the brute-force counter on random arrays.
5. Write a three-way partition quicksort (less, equal, greater) and
   compare it with mine on arrays with 10 distinct values.
6. Write introsort: quicksort with a depth limit of 2 log₂ n that

   defeat median-of-three.

   memory limit, using runs on disk and a k-way merge with a heap.

8. Implement replacement selection and measure the average run length
