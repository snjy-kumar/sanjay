These sections do not belong to one phase. They are the rules I carry through all of them: a
checklist that defines what "a full app" means, a policy for how I use AI tools while learning, a
short list of things I never hand to a model, the habits that stop me forgetting what I learned, and
a concrete first month that gets something real deployed before any of the theory piles up. Each one
gets the same nine levels as a phase topic, because each one has its own beginner version and its
own way of going wrong at scale.

#### Across every phase: how I would use these sections

I read the checklist at the start of every phase and tick only what I can demonstrate. I reread the
AI policy and the do-not-delegate list whenever I open a new AI tool. Retention runs on a calendar,
not on mood. The first 30 days are the on-ramp; once they are done, the phase plan takes over.

#### Across every phase: the full-app checklist

The plan lists sixteen areas. A feature is not "done" because it works on my machine; an app is not
"full" until each area has evidence I can show. I group the sixteen into four bands so the checklist
is something I can actually hold in my head.

<Levels label="Across every phase, the full-app checklist">

<Level name="Beginner">

The first time I use the checklist I treat it as a vocabulary list. For each area I write one
sentence on what it means in my own words and one question I would ask about any app. Auth: who is
this? Authorization: are they allowed to do this to this thing? Data: what happens if the database
disappears tonight? Performance: how long does the main page take on a cheap phone? This turns
sixteen labels into sixteen questions, which is far easier to apply.

Then I take my hello-world app from the first 30 days and answer each question honestly. Most
answers on day one are "I don't know" or "nothing", and that is the point: the checklist shows where
the gaps are before a user finds them.

Worked example of the scoring I use, kept in `CHECKLIST.md` at the repo root:

```md
| Area          | Status | Evidence                                  | Next step                 |
|---------------|--------|-------------------------------------------|---------------------------|
| Auth          | 1/3    | login works; no expiry test               | add session expiry test   |
| Authorization | 0/3    | none                                      | ownership check on /notes |
| Performance   | 1/3    | Lighthouse LCP 3.9 s on mobile emulation  | compress hero image       |
```

Scores are 0 (nothing), 1 (exists), 2 (tested), 3 (tested and monitored in production).

Common mistake: ticking an area because the framework "handles it". Fix: evidence must be something I
ran or can point to: a test name, a dashboard, a command and its output.

</Level>

<Level name="Intermediate">

At this level each area gets an automated check where one is possible, so the checklist is enforced
by CI rather than by memory. A sketch of the script that gathers the easy evidence:

```ts
// scripts/checklist.ts — run in CI, prints a table, fails on regressions
import { execSync } from 'node:child_process';

type Check = { area: string; cmd: string };
const checks: Check[] = [
  { area: 'Security',      cmd: 'npm audit --omit=dev --audit-level=high' },
  { area: 'Security',      cmd: 'gitleaks detect --redact --no-banner' },
  { area: 'Accessibility', cmd: 'npx playwright test tests/a11y.spec.ts' },
  { area: 'Authorization', cmd: 'npx vitest run tests/tenancy' },
  { area: 'Performance',   cmd: 'npx lhci autorun' },
];

let failed = 0;
for (const c of checks) {
  try { execSync(c.cmd, { stdio: 'pipe' }); console.log(`PASS  ${c.area.padEnd(14)} ${c.cmd}`); }
  catch { failed++; console.log(`FAIL  ${c.area.padEnd(14)} ${c.cmd}`); }
}
process.exit(failed ? 1 : 0);
```

What I see when something regresses:

```text
PASS  Security       npm audit --omit=dev --audit-level=high
FAIL  Security       gitleaks detect --redact --no-banner
PASS  Accessibility  npx playwright test tests/a11y.spec.ts
...
Error: Process completed with exit code 1.
```

Not every area automates. Product and Docs stay human: a person follows the README; I can state the
metric. That is fine; the checklist marks them as manual reviews with a date.

Common mistake: making one giant check that fails for unclear reasons. Fix: one command per area, with
its own line in the output, so a failure names its area.

</Level>

<Level name="Advanced">

Areas interact, and the advanced skill is spotting trade-offs between them. Some I have hit or
expect to hit:

- **Performance vs Observability:** heavy client-side tracing adds bundle weight and main-thread work.
  I sample traces and load the error tracker after first paint.
- **SEO vs Auth:** pages behind login must not be indexed, but their marketing counterparts must be.
  `noindex` on app routes, canonical on public ones, and a sitemap that lists only public pages.
- **AI vs Privacy:** sending documents to a model provider is a data transfer. The privacy inventory
  lists which fields leave the system and under which terms.
- **Reliability vs Cost:** retries on a paid model call multiply spend. Retries are bounded and count
  against the budget.

I keep these in the checklist as "tensions" with the decision I made, which often becomes an ADR.

</Level>

<Level name="Edge cases">

- **A static page in a mostly dynamic app:** some areas (Authorization) do not apply. I mark them
  "n/a, because …" instead of leaving them blank, so a reviewer knows it was considered.
- **A third-party widget fails an accessibility scan:** I cannot fix their code, but I can wrap it,
  provide an accessible alternative path, or replace it. The checklist records which.
- **Performance budget passes in the lab but fails in the field:** lab Lighthouse runs on fixed
  hardware; real users have slow phones. The field number (from real-user monitoring) wins.

</Level>

<Level name="Corner cases">

- **Two areas give contradictory evidence:** the API p95 meets budget, but users report slowness. The
  usual cause is that p95 hides a slow tail for one tenant with large data. I add per-tenant p95 for
  the top tenants.
- **A check that always passes:** an a11y test that loads a page with no content. I add a deliberate
  failure once (remove a label) to prove the check can fail. A check that cannot fail is not evidence.

</Level>

<Level name="Production level">

In production the checklist becomes a release gate and a quarterly review. Areas at level 3 have a
dashboard or alert. Anything that drops a level (an alert deleted, a test skipped) shows up as a diff
in `CHECKLIST.md` in a PR, so regressions are visible in review. I date every manual review; anything
older than a quarter is treated as unknown.

</Level>

<Level name="Mindset">

The checklist protects me from the comfortable feeling that the hard part is the feature. For most
apps the feature is a fraction of the work; the rest is making it safe, fast, observable and
understandable. I would rather have a small app at 2 across all sixteen areas than a clever one at 3
in AI and 0 in authorization.

</Level>

<Level name="System design">

In a design review, I walk the sixteen areas over the architecture diagram: for each box and arrow,
which areas does it touch? A queue touches Reliability (retries, dead letters), Observability (depth,
age) and Authorization (tenant in the message). This turns the checklist into a design tool, not just
an audit at the end.

</Level>

<Level name="Strategy">

Each phase, I pick the three weakest areas and raise each by one level with evidence. Over twelve
phases, that compounds into a full app without a big-bang hardening sprint. Done when every area is at
2 or better for the capstone, the sub-2 exceptions have a written reason, and CI enforces the
automatable ones.

</Level>

</Levels>

#### Across every phase: the AI policy

The plan's policy has six points. I read them as a contract between me and the tools: what I use
them for, what I keep, and how I prove the result is mine.

<Levels label="Across every phase, the AI policy">

<Level name="Beginner">

The six points in my own words:

1. AI is good for first drafts, tests, refactors and showing me alternatives.
2. It does not own architecture, auth, payments, permissions, migrations or security-critical code.
3. I read every generated line before it goes in.
4. Fundamentals are learned closed-book: no assistant while I am learning how something works.
5. When I use AI inside the product, I measure before and after with evals.
6. I keep a delegation log of what I handed over and what happened.

A worked example of point 3. I ask for a function to group items by a key and get:

```ts
function groupBy<T>(items: T[], key: (t: T) => string) {
  return items.reduce((acc, item) => {
    (acc[key(item)] ||= []).push(item);
    return acc;
  }, {} as Record<string, T[]>);
}
```

Reading it line by line, I notice `{}` as a plain object: a key of `"__proto__"` behaves oddly. For
user-supplied keys I switch to a `Map`. Without reading, that bug ships.

Common mistake: "it compiled and the test passed, so it's fine". Fix: I must be able to explain each
line; if I can't, I don't accept it.

</Level>

<Level name="Intermediate">

The delegation log is a plain file. Each entry is short and honest:

```md
## 2026-11-04 groupBy helper
- asked: group search results by document id
- accepted: yes, after change (Map instead of object for untrusted keys)
- verified: unit tests for empty, one key, "__proto__" key
- time saved vs cost: ~10 min saved; caught one bug in review
- would delegate again: yes, utilities with clear tests
```

After a month I sort entries by "would delegate again" and see a pattern: utilities and tests, yes;
anything with state across requests, mostly no. The log turns gut feeling into data.

Closed-book (point 4) in practice: when I am learning a topic (for example, how a B-tree splits), the
assistant is off. I write it from my notes, run it, debug it. Only after it works do I ask for a
review or an alternative, and I log what it found.

Common mistake: closed-book for the first hour, then pasting the error into a chat. Fix: a timer;
I struggle for a set time and write down what I tried before asking anything.

</Level>

<Level name="Advanced">

Point 5, eval before and after, applies in two places. Inside the product, a prompt or model change
goes through the eval suite with a results table on the PR. For my own workflow, I can evaluate the
assistant too: I keep a handful of tasks with known good solutions and occasionally compare
assistant output against them, noting where it is reliably wrong. That tells me where to trust it
less.

```text
eval: prompt v7 -> v8   (40 cases)
  faithful:      34 -> 36
  cited:         38 -> 38
  refused-ok:     5 -> 6
  regressions:    case 17 (now omits the second clause)
decision: hold v8 until case 17 is fixed
```

</Level>

<Level name="Edge cases">

- **A suggestion pulls in a new dependency:** that is an architecture decision. I check
  maintenance, licence, size and whether a few lines of my own would do.
- **A suggestion is correct but uses an API I don't know:** I read the official docs for it before
  accepting; otherwise I accept something I can't maintain.
- **The assistant invents a function or flag that doesn't exist:** the type checker or a quick look
  at the docs catches it. I note it in the log as a hallucination so I see how often it happens.

</Level>

<Level name="Corner cases">

- **Generated tests that test the generated code's bugs:** if the same model writes the function and
  the test, the test can encode the same misunderstanding. I write the test cases (inputs and
  expected outputs) myself, and let the model write only the boilerplate around them.
- **A refactor that passes tests but changes behaviour the tests didn't cover:** before large
  refactors I add characterization tests for the current behaviour.

</Level>

<Level name="Production level">

In a team setting this policy becomes review rules: AI-assisted PRs are labelled, the author can
explain every line, security-critical paths get a second human reviewer, and no secret or customer
data goes into a tool whose terms I haven't checked.

</Level>

<Level name="Mindset">

The tools change every few months; the policy shouldn't. Speed from AI is real, but if the speed
comes from skipping understanding, I am borrowing against my future self. I want to be faster
and still the person who knows why.

</Level>

<Level name="System design">

When designing an AI feature, the same policy applies to the model inside the product: it drafts,
the system verifies. Generated output passes validation, permission checks and evals before it
affects anything. The architecture mirrors the personal policy.

</Level>

<Level name="Strategy">

I review the delegation log monthly and adjust: move a category from "delegate" to "keep" when it
burns me, and the reverse when it's consistently fine. Done when the log has entries for every week
of a phase and its patterns have changed at least one of my habits.

</Level>

</Levels>

#### Across every phase: what not to delegate

Nine things stay with me, whatever the tool. The plan's line sums it up: I can delegate the typing,
not the ownership.

<Levels label="Across every phase, what not to delegate">

<Level name="Beginner">

The nine items share one property: a mistake in them is expensive, often invisible at first, and hard
to undo. A wrong problem framing wastes months. A wrong data model is baked into every row. A
permissions bug leaks data. A bad migration loses it. A missing threat model means I don't know what
I didn't protect. Evals and acceptance criteria define what "correct" means, so whoever writes them
controls the quality bar. Incident command needs someone who understands the system. The final review
is where all of this is checked.

Example: I ask an assistant to "add a delete account button". The draft deletes the user row. It
does not delete their documents, embeddings, sessions, or files in storage, and it does not handle the
billing subscription. Deletion is a data-model decision; the code was the easy part.

Common mistake: delegating the design because the prompt sounded specific. Fix: I write the design
(what tables, what cascades, what happens to billing) first; then the typing can be delegated.

</Level>

<Level name="Intermediate">

For each item, I note what "owning" means concretely:

- **Framing and scope:** I write the problem statement and the not-doing list.
- **Architecture and data modeling:** I draw the diagram and write the schema by hand.
- **Auth and tenancy:** I write the policy module and its tests.
- **Payments:** I write the webhook handler and its idempotency logic.
- **Migrations and deletions:** I write and rehearse them on realistic data.
- **Security reviews:** I write the threat model rows.
- **Evals:** I write the cases and expected behaviour.
- **Incident command:** I lead, even in a game day of one.
- **Final review:** I read the diff as if someone else wrote it, because sometimes something else did.

</Level>

<Level name="Advanced">

Owning does not mean working alone. I can ask a model to attack my threat model ("what did I miss?")
or to propose alternative schemas. The difference: the model's output is input to my decision, and
the decision with its reasons is written by me in an ADR.

```md
ADR-007: Soft delete for documents, hard delete after 30 days
Decision: mine. Alternatives considered (two suggested by an assistant): immediate hard delete;
tombstone forever. Rejected because ... 
```

</Level>

<Level name="Edge cases">

- **A small change inside a protected area** (one line in the auth module): still mine to write
  and review. Size doesn't change ownership.
- **Generated SQL for a one-off data fix:** it's a migration in effect. It gets a dry run on a copy,
  a row count before and after, and a backup.

</Level>

<Level name="Corner cases">

- **An eval case generated by a model:** fine as a draft, but I decide the expected answer. If the
  model sets both question and expected answer, the eval measures agreement with itself.
- **A model-written postmortem:** it can draft the timeline from logs; the causes and actions are my
  analysis.

</Level>

<Level name="Production level">

In a team, these nine map to code owners and required reviewers. Paths like `src/auth/`,
`src/billing/`, `migrations/` and `evals/` need a human owner's approval, whatever produced the diff.

</Level>

<Level name="Mindset">

Ownership is being able to answer "why is it like this?" at 3 a.m. If I can't, I don't own it,
whatever the git blame says.

</Level>

<Level name="System design">

A design is reviewable only if its owner can defend each decision. I design so the risky decisions are
few and isolated (one auth module, one billing module, one migration path), which makes ownership
tractable.

</Level>

<Level name="Strategy">

Done when, for the capstone, I can point to each of the nine areas and show the artefact I wrote: the
problem statement, schema, policy module, webhook handler, migration rehearsal, threat model, eval
cases, game day timeline and review notes.

</Level>

</Levels>

#### Across every phase: retention

Learning that isn't revisited fades. The plan lists six practices. They take little time each week
but they decide whether phase 3 is still in my head by phase 12.

<Levels label="Across every phase, retention">

<Level name="Beginner">

Spaced repetition means reviewing a fact just before I would forget it, at growing intervals. I keep
cards small and about one thing:

```text
Q: Which isolation level prevents non-repeatable reads but allows phantoms (per the SQL standard)?
A: Repeatable read.
Q: What does HTTP 409 mean, and when do I use it?
A: Conflict; e.g. an optimistic-lock version mismatch on update.
```

Cards are for facts. Mechanisms don't fit on a card; those get re-implemented.

Common mistake: cards copied from somewhere else. Fix: I write every card from my own notes after
learning the thing; writing it is half the value.

</Level>

<Level name="Intermediate">

Quarterly re-implementation: from a blank file, no notes, I rebuild one of the five mechanisms. A
minimal token-bucket rate limiter is a good one-hour target:

```ts
export function tokenBucket(capacity: number, refillPerSec: number) {
  let tokens = capacity, last = Date.now();
  return function take(): boolean {
    const now = Date.now();
    tokens = Math.min(capacity, tokens + ((now - last) / 1000) * refillPerSec);
    last = now;
    if (tokens < 1) return false;
    tokens -= 1;
    return true;
  };
}
// const take = tokenBucket(5, 1); five calls -> true x5, sixth -> false, after 1 s -> true
```

What I compare afterwards: did I remember the refill clamp? Did I handle concurrent requests (here I
didn't; in a real server the state lives in Redis with an atomic script)? The gaps become cards or
notes.

</Level>

<Level name="Advanced">

Teach-back without vendor names: I explain a concept as if to a curious friend, without saying the
product. Not "Pinecone", but "an index that finds nearest vectors approximately, trading recall for
speed". If I can only explain it with the brand name, I know the product, not the idea.

Interleaving: practice sets mix types. Instead of five SQL problems in a row, one SQL, one caching,
one auth, one algorithm. It feels slower, and that difficulty is what makes it stick, because I must
first identify which kind of problem it is.

</Level>

<Level name="Edge cases">

- **A missed week:** I don't try to catch up on everything; I do today's review and move on. A
  backlog that feels impossible kills the habit.
- **A card I keep failing:** it's usually two facts in one, or a fact I never understood. Split it, or
  go back to the source.

</Level>

<Level name="Corner cases">

- **A fact that changed** (a framework default, a browser behaviour): cards carry a source and date,
  and I retire them when the fact moves.
- **Re-implementation that goes too smoothly:** I raise the bar next time (add concurrency, persistence
  or a test suite) so it keeps stretching me.

</Level>

<Level name="Production level">

The personal measurements dashboard is a page of numbers I measured myself: a Postgres point lookup on
my laptop, a cold start on my host, an embedding call's latency, tokens per page of my documents, my
app's LCP on a mid-range phone. When I estimate in a design review, I estimate from these, not
from guesses.

```text
my numbers (measured 2026-10, laptop + hosting tier)
  pg indexed lookup        ~ sub-millisecond locally
  API p95 (staging)        recorded weekly
  embedding batch of 100   recorded per provider
```

The values themselves live in the dashboard and are re-measured; I don't memorise them as truths.

</Level>

<Level name="Mindset">

Forgetting is normal; planning for it is the skill. Retention isn't extra work on top of learning;
it's the part of learning that makes the rest worth doing.

</Level>

<Level name="System design">

The retention system is itself a small system: inputs (notes, failures), schedules (daily, weekly,
monthly, quarterly), outputs (cards, re-implementations, dashboard). Keep it simple enough to keep
running when life is busy.

</Level>

<Level name="Strategy">

Done when I have run all six practices for a full quarter, rebuilt at least one mechanism from
scratch, and the failure log has changed how I work at least once.

</Level>

</Levels>

<Levels label="Across every phase, the first 30 days">

<Level name="Beginner">

Week 1 is deliberately boring: create the repo, deploy an empty app, connect a hosted Postgres, start
the study log. The goal is that every later change is a deploy away from users. A hello-world full
stack means one page that reads one row from the database through one API route.

```ts
// src/pages/api/health.ts
export async function GET() {
  const { rows } = await pool.query('select now() as now');
  return new Response(JSON.stringify({ ok: true, db: rows[0].now }), {
    headers: { 'content-type': 'application/json' },
  });
}
// curl https://my-app.example/api/health  ->  {"ok":true,"db":"2026-10-23T12:58:01.000Z"}
```

Common mistake: spending week 1 choosing the perfect stack. Fix: pick the stack the plan uses, deploy,
and write down any doubt as a question for later.

</Level>

<Level name="Intermediate">

Week 2: session auth with server-side sessions, a protected route, a form validated on the server,
and an integration test that runs against a real test database.

```ts
test('protected route redirects when signed out, renders when signed in', async () => {
  const anon = await fetch(`${base}/notes`, { redirect: 'manual' });
  expect(anon.status).toBe(302);
  const cookie = await signIn('a@example.test', 'correct horse');
  const ok = await fetch(`${base}/notes`, { headers: { cookie } });
  expect(ok.status).toBe(200);
});
```

Week 3: every page gets loading, error and empty states; I run Lighthouse and an axe scan, fix the
three worst issues, and complete one flow by keyboard only. I write down the before and after numbers.

<Level name="Advanced">

Week 4: a small AI feature, for example summarising a note. It has ten eval cases I wrote, a counter
that records tokens and estimated cost per call, a fallback when the provider errors or times out,
and measured latency.

```ts
async function summarise(note: string) {
  const t0 = performance.now();
  try {
    const r = await withTimeout(model.generate({ prompt: prompt(note) }), 8000);
    costCounter.add(r.usage);                     // tokens in/out -> estimated cost
    metrics.timing('ai.summarise.ms', performance.now() - t0);
    return { ok: true, text: r.text };
  } catch (e) {
    metrics.increment('ai.summarise.fallback');
    return { ok: false, text: firstSentences(note, 2) }; // honest fallback, labelled in the UI
  }
}
```

Then I review the model's errors across the ten cases: which were wrong, how, and is it the prompt,
the input or the task?

</Level>

<Level name="Edge cases">

- **Deploy fails on day 3 for a platform reason:** that's week 1 working as intended. Learn the
  platform's logs now, not during an incident.
- **An eval case with no clear right answer:** rewrite it until a second person would agree on pass or fail.

</Level>

<Level name="Corner cases">

- **The fallback is used so often it is the real feature:** that's a finding. Note the rate and the
  cause before adding more AI.
- **Cost counter shows near zero:** check the counter counts both input and output tokens, and retries.

</Level>
