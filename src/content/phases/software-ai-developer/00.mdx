phase is AI yet. It is the toolchain, the services, the deploy, the telemetry and the habit that every

<Levels label="Phase 0, TypeScript and Node as the core language">

<Level name="Beginner">

I pick TypeScript on Node for the core work because the frontend, the backend, the scripts and this
blog are all TypeScript already, and switching languages between layers costs attention I would rather
spend on the system. Python stays for model experiments later. The smallest thing that works is a
single file that Node runs directly.

```ts
// hello.ts
const name: string = process.argv[2] ?? 'world';
console.log(`hello, ${name}`);
```

```sh
$ node --version
v22.12.0
$ npx tsx hello.ts Sanjay
hello, Sanjay
```

The common mistake is to install Node from the operating system's package manager and end up on a
version years old. The fix is a version manager (`fnm`, `nvm` or `volta`) and an `.nvmrc` or
`engines` field in the repository so every machine, CI included, uses the same major version.

</Level>

<Level name="Intermediate">

A real project needs a `package.json`, a `tsconfig.json`, a way to run TypeScript in development and a
way to build it for production. I keep it boring: `tsx` to run during development, `tsc` to type-check,
and either `tsc` or a bundler to emit JavaScript.

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "outDir": "dist"
  }
}
```

`strict` turns on the checks that catch real bugs (`null` and `undefined` handling, implicit `any`).
`noUncheckedIndexedAccess` makes `arr[0]` have type `T | undefined`, which is the truth. The scripts:

```json
{ "scripts": { "dev": "tsx watch src/server.ts", "typecheck": "tsc --noEmit", "build": "tsc" } }
```

The mistake here is to rely on `tsx` alone. `tsx` strips types without checking them, so a type error
runs fine in development and only surfaces when someone runs `tsc`. The fix is `npm run typecheck` in
the pre-commit hook and in CI.

</Level>

<Level name="Advanced">

Underneath, Node is V8 (the JavaScript engine) plus libuv (the event loop and the thread pool for file
and DNS work) plus a standard library. TypeScript never runs: the compiler checks the types and erases
them, and what Node executes is plain JavaScript. Two consequences matter for this plan. First, a type
annotation is not a run-time check, so `const user = JSON.parse(body) as User` is a promise I made to
the compiler, not a fact. Second, module format is a real run-time concern. With `"type": "module"` in
`package.json`, `.js` files are ES modules, imports need file extensions under `NodeNext`, and
`require` is not defined.

```text
$ node dist/server.js
ReferenceError: require is not defined in ES module scope, you can use import instead
```

The fix is to choose one format for the project (ES modules) and write `import` everywhere, with the
`.js` extension on relative imports even in `.ts` files, because that is the path that will exist after
compilation.

</Level>

<Level name="Edge cases">

One boundary at a time. An empty `process.argv[2]` is `undefined`, not the empty string, so `??` falls
back but `||` would also replace a deliberate empty string. A `tsconfig` with `"strict": true` and an
existing codebase can produce hundreds of errors at once; turning it on file by file with
`// @ts-check` or a second config is how I migrate. Node's LTS line changes every October: a CI image
pinned to `node:20` keeps working, but `node:latest` silently jumps a major version. Windows line
endings in a shell script copied into a Linux container make the script fail with a confusing error.

```text
$ ./scripts/seed.sh
/usr/bin/env: 'bash\r': No such file or directory
```

The fix is a `.gitattributes` with `* text=auto eol=lf` and `*.sh text eol=lf`.

</Level>

<Level name="Corner cases">

Two boundaries at once. A package that ships only CommonJS, imported from an ES module project, on an
older Node version: the default import works but the named import fails, because Node can only detect
some CommonJS exports statically.

```text
SyntaxError: Named export 'parse' not found. The requested module 'legacy-lib'
is a CommonJS module, which may not support all module.exports as named exports.
```

The fix is `import lib from 'legacy-lib'; const { parse } = lib;`. Another one: `strict` mode plus a
JSON import plus `resolveJsonModule` off gives a type error locally but works in `tsx`, which does not
check. Each tool is right on its own; the pair disagrees, and the disagreement shows up in CI.

</Level>

<Level name="Production level">

In production the language choice becomes an operations choice. The build must be reproducible: the
same lockfile, the same Node major, `npm ci` rather than `npm install`. The process must start fast and
stop cleanly when the platform sends `SIGTERM`. Source maps must exist so a stack trace from production
points at my TypeScript line, not at line 1 of a minified bundle. And unhandled promise rejections must
crash loudly, which Node does by default since version 15, rather than leaving the process half alive.

```sh
node --enable-source-maps dist/server.js
```

The mistake is shipping `tsx` or `ts-node` as the production runner. It works, but it compiles on every
cold start and pulls dev dependencies into the image. Build once, run JavaScript.

</Level>

<Level name="Mindset">

The habit is "know what actually runs." Every layer I add (a compiler, a bundler, a framework) is a
translation, and bugs live in translations. When something behaves strangely I ask what JavaScript Node
is executing, which file, which version. The type checker is a colleague who reads my code before I
run it, not a guard who stops bad data at the door. That second job belongs to validation, which Phase 1
builds.

</Level>

<Level name="System design">

One language across the stack lets me share types and validators between the browser, the API and the
background workers: a `packages/shared` folder with Zod schemas imported by all three. That is a real
system-design benefit. The cost is coupling: a change to a shared type can break three deployables at
once, so the shared package needs its own tests and a clear rule about what belongs there (contracts,
not business logic). Python can still join later as a separate service behind an HTTP or queue
boundary, which is the right shape for model experiments.

</Level>

<Level name="Strategy">

I learn the runtime by writing three throwaway scripts on day one: read a file and count lines, fetch a
URL and print the status, and start an HTTP server that returns the time. Each one gets run with
`tsx`, type-checked with `tsc`, built and run as JavaScript. I write in the study log every flag I had
to look up. Done when a fresh clone on another machine runs `npm ci && npm run typecheck && npm run
build && node dist/server.js` with no edits, and I can say what each of the four commands does.

</Level>

</Levels>

#### Phase 0: The browser, its dev tools, the terminal, Git and the editor

<Levels label="Phase 0, browser dev tools, terminal, Git and editor">

<Level name="Beginner">

Four tools, each with one job. The editor writes and navigates code. The terminal runs programs and
shows their output and exit code. Git records what changed and why. The browser's dev tools show what
the page actually did: the DOM, the console, every network request and what is stored. The smallest
useful skill in each: in the editor, jump to definition; in the terminal, read the exit code with
`echo $?`; in Git, `git status` and `git diff` before every commit; in the browser, open the Network
tab before reloading.

```sh
$ node -e "process.exit(3)"; echo $?
3
```

The common mistake is debugging a page by adding `console.log` and reloading, when the Network tab
would have shown in one glance that the API returned 401.

</Level>

<Level name="Intermediate">

Combined, they form one loop. I change a file in the editor, the dev server reloads, the browser shows
the result, and the Network tab shows the request and response. When a test fails in the terminal, I
read the stack trace, jump to the line in the editor, fix it, and commit with a message that says why.

```sh
git switch -c fix/login-error-message
git add -p          # stage only the hunks that belong to this change
git commit -m "Show the server's error message when login fails"
```

`git add -p` is the habit that keeps commits small and readable, which matters because this plan wants
one commit per change. In the browser, "Preserve log" in the Network tab keeps requests across a
redirect, which is exactly when a login bug hides.

</Level>

<Level name="Advanced">

Underneath each tool there is a model worth knowing. Git stores snapshots, not diffs: a commit points to
a tree, a tree points to blobs, and a branch is a file containing a commit hash. That is why switching
branches is fast and why `git reflog` can recover a "lost" commit. The terminal runs a shell that
expands globs and variables before the program sees its arguments, so `rm *.log` passes a list of names,
and a file named `-rf` becomes a flag. The browser's Network tab shows timing phases (queueing, DNS,
connection, TLS, waiting for the first byte, download), which tells me whether slowness is the network
or my server.

```sh
$ git cat-file -p HEAD
tree 9f3a...
parent 6001487...
author Sanjay Kumar <sanjay17126@gmail.com> 1761222000 +0530
```

</Level>

<Level name="Edge cases">

A file with a space in its name breaks an unquoted shell loop: `for f in $(ls)` splits "my file.txt"
into two words. The fix is `for f in *; do echo "$f"; done` with the variable quoted. An empty commit
message aborts the commit. A detached HEAD after `git checkout <hash>` means new commits belong to no
branch; Git warns, and `git switch -c rescue` keeps them. In the browser, a request blocked by CORS shows
in the Network tab with no response body and a console error, even though the server did run and
return 200.

```text
Access to fetch at 'http://localhost:3000/api' from origin 'http://localhost:5173'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present.
```

</Level>

<Level name="Corner cases">

A rebase plus a pushed branch: rewriting commits that others have pulled forces them to reconcile two
histories. The rule I keep is never to rewrite pushed history, which this plan also requires. A cached
service worker plus a deploy: the browser keeps serving the old JavaScript after the server has the new
one, and the bug I fixed is still there for users. "Disable cache" in dev tools only applies while dev
tools are open, so I can fail to reproduce the user's bug precisely because I am looking. The fix is to
test in a fresh profile and to version asset URLs.

</Level>

<Level name="Production level">

In production these tools become how I investigate. I reproduce a user's report with dev tools
emulating a slow 4G network and a mid-range phone CPU. I find which commit introduced a regression with
`git bisect`, which runs a binary search over history.

```sh
git bisect start
git bisect bad HEAD
git bisect good v0.3.0
git bisect run npm test   # Git marks each commit by the test's exit code
```

The mistake is a history of commits named "wip" and "fix", which makes bisect land on a commit that
tells me nothing. Small commits with real messages are an operations tool.

</Level>

<Level name="Mindset">

The habit is "look before guessing." Each tool exists to replace a guess with an observation: the
exit code instead of "it seemed to work", the Network tab instead of "the API is probably fine", the
diff instead of "I only changed one thing." When I catch myself theorising for more than a minute, I
open the tool that would show me.

</Level>

<Level name="System design">

At system scale the same tools have bigger cousins: the Network tab becomes distributed tracing, the
terminal's exit code becomes a health check, Git history becomes the deploy log, and the editor's type
errors become CI's gate. Learning the small version first means the big version reads as familiar.

</Level>

<Level name="Strategy">

I work through Missing Semester's shell, editor, version control and debugging lectures, one a day,
and after each one I break something on purpose and find it with the tool: a script that exits 1, a
commit I lose and recover with reflog, a page whose API call fails. Done when I can find the failing
request, the failing commit and the failing line for a planted bug in under ten minutes each, without
searching the web.

</Level>

</Levels>

#### Phase 0: Docker, Postgres and Redis

<Figure art={`
  docker compose up
        |
        +--> app      (my code, port 3000)  --+
        |                                     | DATABASE_URL
        +--> postgres (port 5432) <-----------+
        |      volume: pgdata  (survives restarts)
        |                                     | REDIS_URL
        +--> redis    (port 6379) <-----------+
               no volume: a cache can be lost
`} caption="One compose file, three services. The volume is the line between data I keep and data I can lose." />

<Levels label="Phase 0, Docker, Postgres and Redis">

<Level name="Beginner">

Docker runs a program in a container: an isolated process with its own filesystem built from an image.
I use it so Postgres and Redis run the same way on my laptop, in CI and on the server. Postgres is the
relational database that holds the truth. Redis is an in-memory store for things I can afford to lose
or rebuild: caches, rate-limit counters, job queues. The smallest working setup:

```yaml
# compose.yaml
services:
  db:
    image: postgres:17
    environment: { POSTGRES_PASSWORD: dev, POSTGRES_DB: app }
    ports: ["5432:5432"]
    volumes: [pgdata:/var/lib/postgresql/data]
  cache:
    image: redis:7
    ports: ["6379:6379"]
volumes: { pgdata: {} }
```

```sh
$ docker compose up -d && docker compose exec db psql -U postgres -d app -c 'select 1'
 ?column?
----------
        1
```

The common mistake is leaving out the volume. Then `docker compose down` deletes every row.

</Level>

<Level name="Intermediate">

Connecting from code means configuration through environment variables, a connection pool and a
migration. I keep the URL in `.env` (not committed) and read it once at start-up.

```ts
import pg from 'pg';
import { createClient } from 'redis';

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 10 });
const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

const { rows } = await pool.query('select now() as t');
await redis.set('last-boot', rows[0].t.toISOString(), { EX: 3600 });
```

A first migration creates the one table the baseline needs. I write it as plain SQL in
`migrations/001_users.sql` so I can read exactly what runs. The mistake is creating the table by hand
in `psql` and forgetting; the next machine has no table and the app fails with
`relation "users" does not exist`.

</Level>

<Level name="Advanced">

An image is a stack of read-only layers; a container adds one writable layer on top. When the
container is removed, that layer goes, which is why data must live in a volume. Compose puts the
services on one private network where each service is reachable by its name, so from the app container
the database host is `db`, not `localhost`. Postgres creates one operating-system process per
connection, which is why the pool size matters: ten app instances with a pool of 20 each is 200
connections, and the default `max_connections` is 100. Redis is single-threaded for commands, so one
slow command (`KEYS *` on a large keyspace) blocks every other client.

```text
FATAL:  sorry, too many clients already
```

</Level>

<Level name="Edge cases">

The app starts before Postgres is ready to accept connections, and the first query fails with
`ECONNREFUSED`. `depends_on` alone waits for the container to start, not for the database to be ready.
The fix is a health check plus `condition: service_healthy`.

```yaml
db:
  healthcheck: { test: ["CMD", "pg_isready", "-U", "postgres"], interval: 2s, retries: 15 }
app:
  depends_on: { db: { condition: service_healthy } }
```

Other single boundaries: port 5432 already taken by a Postgres installed on the host; an image tag of
`latest` that changes major version under me; a Redis key with no TTL that lives forever.

</Level>

<Level name="Corner cases">

Changing `POSTGRES_PASSWORD` after the volume already exists has no effect, because the variable is
only read when the data directory is empty. The app now fails to log in with the new password and the
logs say nothing about the environment variable being ignored. Upgrading the image from `postgres:16`
to `postgres:17` with an existing volume fails to start because the on-disk format differs between
major versions; the fix is a dump and restore, or `pg_upgrade`, not a tag change. Both are a boundary
(the volume) meeting a change (a variable, a version).

</Level>

<Level name="Production level">

In production I would not run my own Postgres on day one. A managed database gives backups, upgrades
and failover. Redis may be managed too, or skipped until there is a measured need. What carries over
from the compose file is the contract: the app reads `DATABASE_URL` and `REDIS_URL`, runs migrations
on deploy, and survives Redis being empty or unreachable. If losing Redis loses data I care about, it
was the wrong store for that data.

</Level>

<Level name="Mindset">

The habit is "where does this data live, and what happens if that place disappears?" A container is
disposable; a volume is not; Redis is memory unless I configured otherwise. Asking the question early
is cheaper than discovering the answer during an incident.

</Level>

<Level name="System design">

This trio is the default shape of most web systems: an app tier that holds no state, a relational
store for the truth, and a fast store for derived or temporary state. Later phases add a queue (often
on Redis or Postgres), object storage and a vector index, and each one gets the same question: is it
the source of truth, or can it be rebuilt from the source of truth?

</Level>

<Level name="Strategy">

I bring the compose file up, insert a row, take it down without `-v`, bring it up and see the row;
then take it down with `-v` and see it gone. I kill Postgres while the app runs and read the error. I
fill Redis with keys that have and lack TTLs and watch which ones expire. Done when I can rebuild the
whole local environment from the README in under five minutes and explain what each line of the
compose file does.

</Level>

</Levels>

#### Phase 0: A deployment target

<Flow
  caption="From a commit on my machine to a URL a stranger can open. Each arrow is a place a deploy can fail."
  steps={["git push", "CI builds and tests", "Image or bundle built", "Platform starts the new version", "Health check passes", "Traffic moves to it", "Old version stopped"]}

<Levels label="Phase 0, a deployment target">

<Level name="Beginner">

A deployment target is wherever the app runs for someone who is not me: a small VPS, a platform that
runs my code from a Git push, or a container host. For Phase 0 I want the simplest one that gives me a
public HTTPS URL, a managed Postgres or a way to attach one, environment variables and logs. The
smallest thing that works is the baseline app answering `GET /health` with `200 ok` on a public URL.

```ts
app.get('/health', (_req, res) => res.status(200).send('ok'));
```

```sh
$ curl -i https://baseline.example.dev/health
HTTP/2 200
content-type: text/html; charset=utf-8

ok
```

The common mistake is binding the server to `localhost`. Inside a container that means only the
container itself can reach it, and the platform reports the app as unhealthy. Listen on `0.0.0.0` and
on the port the platform gives in `PORT`.

</Level>

<Level name="Intermediate">

A real deploy has three moving parts: the build (install, type-check, compile), the release (the build
plus this environment's configuration) and the run (the process started with that release). The
Twelve-Factor App names this split, and keeping it clean is what makes a rollback possible: rolling
back means running an older release, not rebuilding old code.

```sh
npm ci && npm run typecheck && npm run build   # build
# platform attaches DATABASE_URL, SESSION_SECRET  # release
node --enable-source-maps dist/server.js          # run
```

Migrations run as a separate release step before the new version takes traffic, not inside the
server's start-up, so two instances starting at once do not race to migrate.

</Level>

<Level name="Advanced">

Underneath, the platform does what Phase 5 will make me do by hand: it builds an image, starts a
container, waits for a health check, points a load balancer at it, and stops the old container by
sending `SIGTERM` and, after a grace period, `SIGKILL`. TLS is terminated at the platform's proxy, so my
app sees plain HTTP plus an `X-Forwarded-Proto` header. Knowing this explains odd behaviour: a redirect
to `http://` happens because the app thinks the request was not secure, and the fix is to trust the
proxy.

```ts
app.set('trust proxy', 1); // one proxy hop in front of the app
```

</Level>

<Level name="Edge cases">

The free tier sleeps after idle time, so the first request after a quiet hour takes many seconds and a
health check from a monitor reports an outage. The build succeeds locally and fails on the platform
because a dependency is in `devDependencies` but needed at run time. The app reads `PORT` as a string
and `app.listen('3000')` still works, but `Number(process.env.PORT)` of an unset variable is `NaN` and
the server listens on a random port.

```text
Error: listen EADDRINUSE: address already in use :::3000
```

That one appears locally when an old dev server is still running; `lsof -i :3000` finds it.

</Level>

<Level name="Corner cases">

A new release that needs a migration, plus an old instance still serving traffic during the rollout:
for a minute both versions run against the new schema. If the migration renamed a column, the old
version breaks. This is why Phase 4 teaches expand-and-contract migrations. Another one: a secret
rotated in the platform plus a running instance that read it at start-up. The new value is not used
until the process restarts, so the rotation looks done and is not.

</Level>

<Level name="Production level">

For real users I need three things from day one: a rollback I have tested, logs I can search, and an
alert if `/health` fails. I also need the health check to mean something. A health route that returns
200 without touching the database will say "healthy" while every real request fails. I split it: a
liveness check (the process is up) and a readiness check (it can reach Postgres).

```ts
app.get('/ready', async (_req, res) => {
  try { await pool.query('select 1'); res.send('ready'); }
  catch { res.status(503).send('db unreachable'); }
});
```

</Level>

<Level name="Mindset">

The habit is "a feature is not done until it is running somewhere I do not control." Deploying in week
one, when the app is tiny, is how I learn the deploy while mistakes are cheap. Every later phase
deploys continuously, so the pipeline has to be boring before the code becomes interesting.

</Level>

<Level name="System design">

The choice of target shapes the system: a platform gives speed and hides the network; a VPS gives
control and makes me own patching; a container host sits between. I choose the one that lets me move
later: the app is a container image that reads its configuration from the environment, so the same
image runs on any of the three.

</Level>

<Level name="Strategy">

I deploy the hello-world server on day one, then redeploy after every meaningful change that week. I
deliberately ship a broken build and watch the platform keep the old version, then roll back a working
but wrong release. Done when I can deploy, see the logs, and roll back from the command line or
dashboard without looking anything up, and the steps are in the README.

</Level>

</Levels>

#### Phase 0: An observability account: logs, metrics, traces and error tracking

<Layers

<Levels label="Phase 0, an observability account">

<Level name="Beginner">

Observability is being able to answer "what is the app doing right now, and what did it do when the
user complained" without adding code first. Logs are lines of text about events. Metrics are numbers
over time. Traces follow one request through every service. Error tracking groups exceptions so I see
each bug once with a count. In Phase 0 I sign up for one service that does at least logs and errors,
and I send it one structured log line per request.

```ts
console.log(JSON.stringify({ level: 'info', msg: 'request', method: req.method, path: req.path, status: res.statusCode, ms }));
```

```text
{"level":"info","msg":"request","method":"GET","path":"/health","status":200,"ms":2}
```

The common mistake is logging free text like "user logged in!!" which is impossible to search or
count. JSON with fixed field names is searchable.

</Level>

<Level name="Intermediate">

A real setup uses a logger library (`pino` is fast and writes JSON by default), a request ID added to
every log line so one request's lines can be grouped, and an error handler that sends unexpected errors
to the tracking service with that ID.

```ts
import pino from 'pino';
import { randomUUID } from 'node:crypto';
const log = pino();
app.use((req, res, next) => {
  req.id = req.headers['x-request-id']?.toString() ?? randomUUID();
  req.log = log.child({ reqId: req.id });
  res.setHeader('x-request-id', req.id);
  next();
});
```

The returned header means a user can send me the ID from their browser and I can find their request.

</Level>

<Level name="Advanced">

The standard underneath is OpenTelemetry: a vendor-neutral API and protocol (OTLP) for traces, metrics
and logs. A trace is a tree of spans; each span has a name, a start, a duration, attributes and a parent.
Auto-instrumentation wraps HTTP, `pg` and `redis` clients so the spans appear without hand-written code.
Using it from the start means changing vendors is a configuration change, not a rewrite.

```text
GET /notes            120 ms
 ├─ auth.session       4 ms
 ├─ pg.query select   95 ms   <- the slow part
 └─ render            18 ms
```

</Level>

<Level name="Edge cases">

A log line that includes the request body leaks passwords into the log store. A process that crashes
before the logger flushes loses the last lines, which are the ones I need; `pino` writes synchronously
to stdout by default for this reason. A free tier drops events past a monthly quota, so the dashboard
shows a quiet day that was actually busy. Logging an `Error` object with `JSON.stringify` gives `{}`
because its fields are not enumerable.

```ts
JSON.stringify(new Error('boom'))        // '{}'
log.error({ err: new Error('boom') })    // pino serialises message and stack
```

</Level>

<Level name="Corner cases">

High-cardinality labels plus metrics: adding `userId` as a metric label creates one time series per
user and either explodes the bill or gets dropped. User IDs belong in logs and traces, not metric
labels. Sampling plus a rare bug: keeping 10% of traces means the one failing request is likely not
kept. The fix is tail sampling that always keeps errors and slow requests.

</Level>

<Level name="Production level">

In production observability exists to shorten incidents. That means three dashboards I will look at
(request rate, error rate, latency percentiles), one alert that fires when users are affected, and a
retention period long enough to compare with last week. It also means a privacy rule: no secrets,
tokens, passwords or full prompts in logs, enforced with a redaction list in the logger.

```ts
const log = pino({ redact: ['req.headers.authorization', 'req.headers.cookie', '*.password'] });
```

</Level>

<Level name="Mindset">

The habit is "instrument before I need it." The question during an incident is always one I did not
think to ask in advance, so the data must already be there. If I cannot see it, I cannot fix it, and
I certainly cannot prove I fixed it.

</Level>

<Level name="System design">

Telemetry is a pipeline of its own: app, collector, storage, query, alert. Putting an OpenTelemetry
collector between the app and the vendor lets me redact, sample and route in one place. In later phases
the same pipeline carries AI-specific signals: tokens, cost, model version and eval scores per request.

</Level>

<Level name="Strategy">

I wire logs and error tracking on day ten, then throw a deliberate error from a route and find it in
the dashboard by its request ID. Done when, given only a request ID from a response header, I can find
that request's log lines and, if it failed, its stack trace, in under two minutes.

</Level>

</Levels>

#### Phase 0: A repository with a README, a study log and a project board

<Figure art={`
  baseline/

  |-- STUDY_LOG.md       date, hours, what I did, what I looked up, next
  |-- compose.yaml       local Postgres and Redis
  |-- .env.example       every variable, no real values
  |-- migrations/        plain SQL, numbered
  |-- src/               server, routes, db, views
  |-- test/              one integration test to start
  '-- .github/workflows/ ci.yml: typecheck, test, build
`} caption="The shape of the baseline repository. Every file in it is one I can explain at the gate." />

<Levels label="Phase 0, a repository with a README, a study log and a project board">

<Level name="Beginner">

The repository is the evidence. A README tells a stranger what the app is and how to run it. The study
log records each session: the date, the hours, what I built, what I had to look up, and what is next.
The project board lists the work as small cards. The smallest README that works has four headings.

```md
# Baseline
A small full-stack app: one table, one form, one signed-in page.
## Run it
cp .env.example .env && docker compose up -d && npm ci && npm run migrate && npm run dev
## Test it
npm test
## Deploy it
Push to main; CI deploys. Roll back from the platform dashboard.
```

The common mistake is a README written once and never run. I test it by following it on a clean clone.

</Level>

<Level name="Intermediate">

The log and the board work together. Each board card is a change small enough for one sitting and one
commit. Each log entry names the card it moved. Over two weeks the log becomes the honest record of
where time went, and the "looked up" column shows exactly what I have been avoiding.

```md
## 2026-10-23 (2.5 h)
- Did: session cookie on /account; integration test passes.
- Looked up: how to set SameSite on the cookie; what `trust proxy` does.
- Stuck: test leaked a DB connection; fixed by closing the pool in afterAll.
- Next: deploy, then error tracking.
```

</Level>

<Level name="Advanced">

The README is also where decisions go until there are enough for ADRs: "Postgres, not SQLite, because
the capstone needs concurrent writers." `.env.example` is the contract for configuration: every
variable the app reads appears there with a fake value and a comment, and a start-up check fails fast
when one is missing.

```ts
const required = ['DATABASE_URL', 'REDIS_URL', 'SESSION_SECRET'];
const missing = required.filter((k) => !process.env[k]);
if (missing.length) { console.error(`missing env: ${missing.join(', ')}`); process.exit(1); }
```

</Level>

<Level name="Edge cases">

`.env` committed by accident puts a real secret in history; deleting the file in a later commit does
not remove it. The fix is a `.gitignore` entry from the first commit and, if it happens, rotating the
secret (Phase 6 makes this a drill). A study log with a gap of a week is still honest; a log back-filled
from memory is not, and I do not do that. A board with fifty cards is a wish list, not a plan.

</Level>

<Level name="Corner cases">

A README that works on my machine because a tool is installed globally, on a clean machine where it is
not: the instructions pass for me and fail for everyone else. The fix is to put every tool in
`devDependencies` and call it through `npx` or a script. A public repository plus a study log that
mentions a real user's email in a bug note: the log is public evidence, so it must contain no personal
data.

</Level>

<Level name="Production level">

For a production repository the README grows sections a responder needs: how to see logs, how to roll
back, where the runbook is, who owns what. CI badges show whether main is green. A `CHANGELOG.md` records
user-visible changes. The test I apply is the one in the gate: someone who has never seen the project can
run it, test it and deploy it from the README alone.

</Level>

<Level name="Mindset">

The habit is "evidence over memory." I will not remember in month nine why I chose a session cookie in
week one. The log and the README remember for me, and writing them forces me to notice when I do not
actually know why something works.

</Level>

<Level name="System design">

Documentation is part of the system's interface. A README is the onboarding path, `.env.example` is the
configuration schema, the migrations folder is the data model's history and CI is the definition of
"works." Treating them as code means they are reviewed and kept true with the code.

</Level>

<Level name="Strategy">

I write the study log entry at the end of every session, before closing the editor, and I review the
week's entries every Sunday to pick next week's cards. Done when a clean clone on another machine
follows the README to a running, tested app, and the log has an entry for every session of the phase.

</Level>

</Levels>

#### Phase 0: the build, a baseline full-stack app

<Flow
  caption="The baseline's one critical path. Every box is a place I write a test or a log line."
  steps={["Sign-up form", "Validate input", "Hash password, insert user", "Set session cookie", "Redirect to /account", "Protected route reads the session", "Render the user's own rows"]}
/>

<Levels label="Phase 0, the baseline build">

<Level name="Beginner">

The baseline is one small app: a database table, a form, one authenticated route, one test and a
deploy. No AI. I keep the feature trivial so the work is in the plumbing: a "notes" app where a signed-in
user adds a short note and sees only their own notes. The smallest version is a server-rendered page with
a form that posts to the server and a table with a foreign key.

```sql
create table users (id bigserial primary key, email text unique not null, password_hash text not null);
create table notes (id bigserial primary key, user_id bigint not null references users(id), body text not null,
                    created_at timestamptz not null default now());
```

</Level>

<Level name="Intermediate">

The pieces combine as a request path. The form posts to `/notes`; the server checks the session,
validates the body, inserts with the session's user ID (never one from the form), and redirects. The
account page selects `where user_id = $1`. One integration test proves the critical rule: a user cannot
see someone else's notes.

```ts
test('a user sees only their own notes', async () => {
  const a = await signUp('a@example.com'); const b = await signUp('b@example.com');
  await a.post('/notes', { body: 'from a' });
  const page = await b.get('/account');
  expect(page.text).not.toContain('from a');
});
```

```text
 ✓ test/notes.test.ts (1)
   ✓ a user sees only their own notes 84ms
```

</Level>

<Level name="Advanced">

The exact rules underneath: passwords are hashed with a slow, salted function (`argon2id` or `bcrypt`),
never stored or logged. The session is a random ID in an `HttpOnly`, `Secure`, `SameSite=Lax` cookie,
mapped to a user on the server (in Postgres or Redis). Queries use parameters (`$1`), never string
concatenation. The form's POST is protected against cross-site requests by `SameSite` plus an origin
check. Each of these is a Phase 3 or Phase 6 topic; the baseline uses the safe default and the log notes
that I do not yet understand it fully.

</Level>

<Level name="Edge cases">

An empty note body; a body of a megabyte; an email with uppercase letters that duplicates an existing
lowercase one; a sign-up with an email already taken, which must give a useful error and not a 500.

```text
error: duplicate key value violates unique constraint "users_email_key"
```

The fix for the uppercase case is a lowercase normalisation before insert (or a `citext` column); for the
duplicate, catching the unique violation (`code === '23505'`) and returning a form error.

</Level>

<Level name="Corner cases">

A user double-clicks submit on a slow network: two identical notes. A session cookie set on
`localhost` in development and then the production domain: cookies are per host, so the test passes
locally with a cookie the deploy never sees if `Secure` is set and local is HTTP. A user deleted while
their session is alive: the protected route must treat a missing user as signed out, not crash.

</Level>

<Level name="Production level">

For real use the baseline needs the boring list: a 404 page, a 500 page that shows a request ID and no
stack trace, request logging, a readiness check, and migrations that run on deploy. I also measure: time
to first byte of `/account`, and how long the deploy takes. Those numbers are the baseline the plan's
name promises.

</Level>

<Level name="Mindset">

The baseline is a mirror. What took longest, what I copied without understanding, what I skipped
because it was boring: those are the real syllabus, and the study log is where I write them down
honestly.

</Level>

<Level name="System design">

Small as it is, the baseline already has the capstone's shape: a browser, a stateless app, a relational
store, a session store, a deploy pipeline and telemetry. Each later phase replaces one box with a
deeper version, so the capstone grows from this repository rather than starting over.

</Level>

<Level name="Strategy">

I build it in four sittings: schema and migration; form and validation; sessions and the protected
route; test, deploy and telemetry. I commit after each sitting. Done when the deployed app passes the
isolation test in CI, and I can explain every file in the repository, including the generated ones.

</Level>

</Levels>

#### Phase 0: exercises

- Run the three day-one scripts (count lines, fetch a URL, serve the time) with `tsx`, then built.
- Plant one bug for each tool: a failing request, a lost commit, a non-zero exit code, an undefined
  variable. Find each one with the tool and write down how.
- Bring the compose stack up and down with and without `-v`; kill Postgres mid-request and read the
  error the app gives.
- Deploy a broken build and watch the platform keep the old one; roll back a working but wrong release.
- Throw a deliberate error and find it by request ID in the observability dashboard.
- Follow the README on a clean clone and fix every step that fails.
- Read *The Pragmatic Programmer* chapters 1 to 3 and write one log entry each on what changes in how I
  work.

#### Phase 0: the gate

The plan's gate: a deployed app with a README, a database, a test and a study log, and I can explain
every file in the repository.

- **Deployed:** a public HTTPS URL, `/health` and `/ready` both return 200, and a rollback has been done
  once.
- **README:** a clean clone runs, tests and deploys from it with no extra knowledge.
- **Database:** a migration creates the schema, the isolation test proves ownership, and the volume
  survives a restart.
- **Test:** the integration test runs in CI against a real Postgres and blocks a merge when it fails.
- **Study log:** one entry per session, nothing back-filled, with the list of things I looked up.
- **Explain every file:** I walk an imagined reviewer through the repository top to bottom, out loud,
  with nothing open but the code. Any file I cannot explain becomes the first card of Phase 1.
