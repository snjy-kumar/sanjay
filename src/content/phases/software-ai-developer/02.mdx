also where AI-generated code most often looks finished and is not: the happy path renders, and the

*Refactoring UI* and *Inclusive Components*, with MDN, web.dev/learn, the React docs and Full Stack Open
as free references and *CSS: The Definitive Guide* for depth.

#### Phase 2: semantic HTML, landmarks, headings and document structure

<Figure art={`
  body
  |-- header      (banner)        site name, primary nav
  |   '-- nav     (navigation)    aria-label="Primary"
  |-- main        (main)          exactly one
  |   |-- h1                       one per page
  |   |-- section > h2
  |   |   '-- h3                   never skip a level going down
  |   '-- section > h2
  |-- aside       (complementary)
  '-- footer      (contentinfo)
`} caption="The landmark and heading tree a screen reader navigates: one main, one h1, headings in order." />

<Levels label="Phase 2, semantic HTML, landmarks and headings">

<Level name="Beginner">

Semantic HTML uses the element that means what the content is: a `button` for an action, an `a` for
navigation, `h1` to `h6` for headings, `ul` for lists. The browser gives these elements keyboard
behaviour, focus and accessible names for free.

```html
<!-- wrong: looks like a button, is not one -->
<div class="btn" onclick="save()">Save</div>
<!-- right: focusable, Enter and Space work, announced as a button -->
<button type="button" onclick="save()">Save</button>
```

Common mistake: a clickable `div`. Fix: if it does something, it is a `button`; if it goes somewhere,
it is a link.

</Level>

<Level name="Intermediate">

Landmarks (`header`, `nav`, `main`, `aside`, `footer`) let screen-reader users jump between regions.
Headings form an outline; users skim by heading level. One `h1` per page, then `h2` for sections, never
skipping down a level for visual size; size comes from CSS.

Two `nav` elements need distinct labels (`aria-label="Primary"` and `aria-label="Breadcrumb"`) or they
are announced identically.

</Level>

<Level name="Advanced">

The browser builds an accessibility tree from the DOM: each node has a role, a name, a state and a
value. The name is computed by a defined algorithm: `aria-labelledby`, then `aria-label`, then the
element's content or its `label`, then `title`. Chrome's dev tools show the tree under Accessibility.
ARIA changes that tree but adds no behaviour: `role="button"` on a `div` still needs `tabindex="0"`
and key handlers. The first rule of ARIA is to prefer the native element.

</Level>

<Level name="Edge cases">

- An icon-only button with no text has no accessible name; screen readers say "button". Add a visually
  hidden label or `aria-label`.
- A page with no `h1`, or two, confuses outline navigation.
- A `table` used for layout announces rows and columns that mean nothing.

</Level>

<Level name="Corner cases">

A link styled as a button that opens a modal: it is announced as a link, middle-click opens a new tab
with a `#` URL, and the back button does nothing useful. Semantics plus behaviour mismatch. If it opens a
modal, it is a button. Another: `aria-hidden="true"` on a container that holds a focusable element, so
the keyboard lands on something the screen reader says does not exist.

</Level>

<Level name="Production level">

Semantic structure is also SEO structure and the base for every automated accessibility check. A lint
rule (`jsx-a11y`) and an axe scan in CI catch the common regressions before review.

</Level>

<Level name="Mindset">

HTML is the API to the browser and to assistive technology. Choose elements for meaning first, then
style them.

</Level>

<Level name="System design">

Design-system primitives encode semantics once: a `Button` that always renders a `button`, a `Link`
that always renders an `a`, a `Heading` that takes a level. Then the whole app inherits the right
structure.

</Level>

<Level name="Strategy">

Write the app's three core pages in plain HTML with no CSS, then navigate them with VoiceOver or NVDA
using only the landmark and heading shortcuts. Done when every page has one main and one h1, headings
never skip, and I can reach every action by role.

</Level>

</Levels>

#### Phase 2: CSS: the box model, flexbox, grid, responsive design and container queries

<Figure art={`
  +-------------------------------------- margin ---+
  |  +------------------------------- border ----+  |
  |  |  +------------------------- padding ---+  |  |
  |  |  |        content (width x height)      |  |  |
  |  |  +--------------------------------------+  |  |
  |  +--------------------------------------------+  |
  +--------------------------------------------------+
  box-sizing: border-box  -> width includes padding and border
`} caption="The box model: content, padding, border and margin; border-box makes the declared width include padding and border." />

<Levels label="Phase 2, CSS layout from the box model to container queries">

<Level name="Beginner">

Every element is a box: content, padding, border, margin. With `box-sizing: border-box`, `width:
200px` means the whole visible box is 200 px. Flexbox lays out a row or a column; grid lays out rows
and columns together.

```css
*, *::before, *::after { box-sizing: border-box; }
.toolbar { display: flex; gap: 0.5rem; align-items: center; }
.dashboard { display: grid; grid-template-columns: 16rem 1fr; gap: 1rem; }
```

Common mistake: fixing layout with margins and fixed widths. Fix: let flex and grid distribute space,
and use `gap`.

</Level>

<Level name="Intermediate">

Responsive design starts mobile-first: base styles for narrow screens, `min-width` media queries for
wider. Intrinsic layouts reduce breakpoints: `repeat(auto-fit, minmax(16rem, 1fr))` makes a card grid
that reflows by itself. Container queries let a component respond to its container rather than the
viewport, so the same card works in a sidebar and a main column.

```css
.card-list { container-type: inline-size; }
@container (min-width: 30rem) { .card { display: grid; grid-template-columns: 8rem 1fr; } }
```

</Level>

<Level name="Advanced">

The cascade decides which rule wins: origin and importance, then cascade layers (`@layer`), then
specificity, then source order. Flex items have `min-width: auto`, so a long word or a wide child
refuses to shrink and overflows; `min-width: 0` fixes it. Percentage padding is relative to the
containing block's width, even vertical padding. Margins collapse vertically between block siblings
but never inside flex or grid containers.

</Level>

<Level name="Edge cases">

- A 60-character URL in a flex item overflows the screen: `overflow-wrap: anywhere` and `min-width: 0`.
- `100vh` on mobile includes the area behind the browser bar; `100dvh` tracks the visible height.
- An empty grid cell collapses unless rows have explicit sizes.

</Level>

<Level name="Corner cases">

A user sets the browser font size to 200% and the layout was built in px: text grows inside fixed-height
boxes and overlaps. Zoom plus fixed sizes. Using `rem` for type and spacing and avoiding fixed heights
fixes it. Another: a container query on an element that also sizes itself from its content creates a
loop, which is why `container-type: inline-size` only allows querying the inline size.

</Level>

<Level name="Production level">

Production CSS needs a structure that survives many contributors: tokens as custom properties, layers
for reset, base, components and utilities, and a rule against arbitrary values. Unused CSS is shipped
bytes; critical CSS inline for first paint.

</Level>

<Level name="Mindset">

Describe constraints and let the browser compute the layout. Pixel-pushing is fighting the engine.

</Level>

<Level name="System design">

Layout primitives (stack, cluster, sidebar, grid, as Every Layout names them) are a design-system layer
under components. Components compose primitives; pages compose components.

</Level>

<Level name="Strategy">

Rebuild the dashboard layout three ways (floats are skipped; flex only, grid only, grid with container
queries), then test at 320 px wide, at 200% zoom and with a long user name. Done when none of those
three tests produces horizontal scroll or overlap.

</Level>

</Levels>

#### Phase 2: accessibility: keyboard, focus, labels, contrast, screen readers and reduced motion

<Flow
  caption="A keyboard-only pass through one flow"
  steps={['Tab to the first control', 'Focus ring is visible', 'Enter or Space activates', 'Dialog traps focus inside', 'Escape closes it', 'Focus returns to the trigger']}
/>

<Levels label="Phase 2, accessibility from keyboard to reduced motion">

<Level name="Beginner">

Accessibility means people with different abilities and devices can use the app. The baseline: every
action works with a keyboard, focus is visible, every input has a label, text has enough contrast
(4.5 to 1 for body text under WCAG AA), and images that carry meaning have alt text.

```html
<label for="email">Email</label>
<input id="email" name="email" type="email" autocomplete="email" required>
```

Common mistake: `outline: none` with no replacement. Fix: style `:focus-visible` instead of removing
it.

</Level>

<Level name="Intermediate">

Focus management is where single-page apps break. When a dialog opens, focus moves into it and stays
there; when it closes, focus returns to the button that opened it. After a client-side route change,
focus moves to the new page's heading or main, and the change is announced. The native `dialog`
element with `showModal()` gives focus trapping and Escape for free.

```js
const dlg = document.querySelector('dialog');
openBtn.addEventListener('click', () => dlg.showModal());
dlg.addEventListener('close', () => openBtn.focus());
```

</Level>

<Level name="Advanced">

Live regions announce changes without moving focus: `aria-live="polite"` waits for a pause,
`assertive` interrupts. The region must exist in the DOM before its content changes, or nothing is
announced. Reduced motion: `@media (prefers-reduced-motion: reduce)` turns off parallax, auto-playing
animation and large transitions. Target size for pointer inputs should be at least 24 by 24 CSS px under
WCAG 2.2.

</Level>

<Level name="Edge cases">

- Placeholder used as a label disappears when typing and has low contrast.
- Disabled buttons are skipped by Tab, so a user cannot discover why they are disabled.
- Colour alone signals an error (a red border): users who cannot see the red get no message.

</Level>

<Level name="Corner cases">

A streaming AI response in a live region: every token triggers an announcement and the screen reader
reads fragments over and over. Live region plus high-frequency updates. Announce "Answer ready" once,
and let the user read the finished text, or announce sentence by sentence. Another: a toast that
disappears after three seconds while a screen reader is still reading something else.

</Level>

<Level name="Production level">

Automated tools catch about a third of issues; the rest need a manual keyboard pass and a screen-reader
pass on each critical flow. I put axe in the component and end-to-end tests and keep a short manual
checklist for releases.

</Level>

<Level name="Mindset">

Accessibility is correctness, not decoration. A flow a keyboard user cannot finish is a broken flow.

</Level>

<Level name="System design">

Accessible primitives in the design system (dialog, menu, tabs, combobox following the ARIA Authoring
Practices patterns) make every feature accessible by default. One correct combobox beats ten ad-hoc
ones.

</Level>

<Level name="Strategy">

Unplug the mouse for a day of using my own app. Log every place I get stuck. Done when the main flow
completes by keyboard alone, axe reports zero violations on core pages, and a screen-reader pass of the
chat surface is understandable.

</Level>

</Levels>

#### Phase 2: TypeScript at the boundary: props, events, API responses and error states

<Compare
  caption="Typing an API response so the states cannot be confused"
  left="Loose"
  right="Discriminated"
  rows={[
    ["data?: Note[]; error?: string; loading: boolean", "status: 'loading' | 'error' | 'empty' | 'ok'"],
    ["Loading and error can both be true", "Exactly one state at a time"],
    ["data may be undefined in the ok branch", "data is present only when status is ok"],
    ["Response cast with as Note[]", "Response parsed with a schema"],
  ]}
/>

<Levels label="Phase 2, TypeScript for props, events, responses and errors">

<Level name="Beginner">

Props get an explicit type, events get the DOM event type, and API responses are parsed rather than
cast.

```tsx
type NoteCardProps = { title: string; updatedAt: Date; onOpen: (id: string) => void; id: string };
function NoteCard({ title, updatedAt, onOpen, id }: NoteCardProps) {
  return <button onClick={() => onOpen(id)}>{title} · {updatedAt.toLocaleDateString()}</button>;
}
```

Common mistake: `any` on event handlers. Fix: `React.ChangeEvent<HTMLInputElement>` and friends.

</Level>

<Level name="Intermediate">

A discriminated union makes impossible states unrepresentable. The component switches on `status`, and
TypeScript narrows `data` only in the `ok` branch.

```ts
type Remote<T> =
  | { status: 'loading' }
  | { status: 'error'; message: string; retry: () => void }
  | { status: 'empty' }
  | { status: 'ok'; data: T; stale: boolean };
```

</Level>

<Level name="Advanced">

An exhaustive switch uses `never` so adding a state breaks the build where it is not handled.

```ts
function assertNever(x: never): never { throw new Error(`unhandled ${JSON.stringify(x)}`); }
switch (r.status) { case 'loading': ...; case 'error': ...; case 'empty': ...; case 'ok': ...; default: assertNever(r); }
```

Shared schemas between server and client (one Zod schema, imported by both) keep the boundary honest;
the type is inferred, the runtime check happens on the client after `fetch`.

</Level>

<Level name="Edge cases">

- Dates arrive as strings over JSON; the schema converts them (`z.coerce.date()`).
- An optional prop with a default: `{ size = 'md' }` and a type that says `size?: 'sm' | 'md'`.
- `children` typing: `React.ReactNode` allows `undefined`, which is fine; `JSX.Element` does not.

</Level>

<Level name="Corner cases">

The server adds a field and removes another in the same deploy; the client's schema rejects the response
and the whole page errors. Strictness plus versioning. Use `.passthrough()` or ignore unknown keys, and
treat removals as breaking changes with a deprecation period.

</Level>

<Level name="Production level">

Types are documentation that the compiler checks. In production, the runtime schema check on the client
turns a server bug into a visible error state instead of `undefined is not a function` deep in a
component.

</Level>

<Level name="Mindset">

Model the states the user can actually be in, then let the compiler prove I rendered each one.

</Level>

<Level name="System design">

The API contract is shared code or generated code (from OpenAPI in phase 3). Either way there is one
source of truth for the shape.

</Level>

<Level name="Strategy">

Convert the dashboard's data hooks to the `Remote` union and add `assertNever`. Done when removing a
state branch from any component fails `tsc`.

</Level>

</Levels>

#### Phase 2: React: components, state, effects, context, reducers and composition

<Flow
  caption="One React update, from event to screen"
  steps={['Event handler calls setState', 'React schedules a render', 'Component functions run again', 'New tree diffed against old', 'DOM updated', 'Effects run after paint']}
/>

<Levels label="Phase 2, React components, state, effects, context and reducers">

<Level name="Beginner">

A component is a function from props and state to UI. State changes trigger a re-render. Effects run
side effects after render.

```tsx
function Counter() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>Clicked {n} times</button>;
}
```

Common mistake: mutating state (`items.push(x); setItems(items)`) so React sees the same reference and
does not re-render. Fix: `setItems([...items, x])`.

</Level>

<Level name="Intermediate">

A component re-renders when its state changes, its parent re-renders, or a context it reads changes.
Derived values are computed during render, not stored in state. Effects are for synchronising with
something outside React (a subscription, a timer, a non-React widget), not for computing values.

```tsx
// wrong: derived state in an effect, renders twice, can go stale
const [full, setFull] = useState('');
useEffect(() => setFull(first + ' ' + last), [first, last]);
// right
const full = first + ' ' + last;
```

</Level>

<Level name="Advanced">

Each render captures its own props and state; a callback created in one render sees that render's
values. That is the stale closure: an interval set up once reads `n` from the first render forever.
The functional update form fixes it.

```tsx
useEffect(() => {
  const id = setInterval(() => setN(prev => prev + 1), 1000);
  return () => clearInterval(id);
}, []);
```

Reducers centralise transitions for complex state; context passes values down without props but
re-renders every consumer when the value changes, so a context value should be stable (`useMemo`) or
split by how often it changes.

</Level>

<Level name="Edge cases">

- Strict Mode in development mounts, unmounts and remounts components to surface missing cleanups, so
  an effect runs twice.
- A `key` equal to the array index: reordering a list moves state between items.
- `useState(expensive())` runs `expensive` every render; `useState(() => expensive())` runs it once.

</Level>

<Level name="Corner cases">

An effect that fetches on `id` change without cleanup: the user changes `id` from 1 to 2 quickly, the
response for 1 arrives last and overwrites 2. Effect plus race. The fix is an `AbortController` in the
cleanup or an `ignore` flag.

```tsx
useEffect(() => {
  const ac = new AbortController();
  fetch(`/api/notes/${id}`, { signal: ac.signal }).then(r => r.json()).then(setNote).catch(() => {});
  return () => ac.abort();
}, [id]);
```

</Level>

<Level name="Production level">

Re-render cost matters on large lists and on every keystroke. React's profiler shows what rendered and
why. Error boundaries keep one broken component from blanking the page. Server components and
server-side rendering move work off the client where the framework supports it.

</Level>

<Level name="Mindset">

UI is a function of state. If the screen is wrong, find the state that is wrong, not the DOM node.

</Level>

<Level name="System design">

State has homes: server state (cached fetches), URL state (filters, page), form state, and local UI
state. Putting each in its right home removes most state-management libraries.

</Level>

<Level name="Strategy">

Write the stale-interval bug and the derived-state bug on purpose, then fix them; profile the dashboard
list. Done when I can explain, for any re-render the profiler shows, which of the three causes triggered
it.

</Level>

</Levels>

#### Phase 2: data fetching: loading, error, empty, stale and optimistic states

<Figure art={`
           fetch
  idle ---------> loading ----ok, rows----> ok (fresh)
                     |  \                    |  time passes
                     |   '--ok, 0 rows--> empty
                   fail                      v
                     v                   ok (stale) --refetch--> loading
                   error --retry--> loading
  optimistic: ok --user edits--> ok (pending) --server ok--> ok
                                       '--server fails--> rollback + error
`} caption="The five states and their transitions, including the optimistic edit that rolls back on failure." />

<Levels label="Phase 2, loading, error, empty, stale and optimistic states">

<Level name="Beginner">

Every fetch has at least four outcomes the user can see: still loading, failed, succeeded with
nothing, succeeded with data. Each needs designed UI. The empty state is not a blank page; it says what
to do next.

Common mistake: only designing the "ok" state. Fix: for each list or panel, sketch all four before
coding.

</Level>

<Level name="Intermediate">

Stale data is data shown from cache while a refetch happens in the background (stale-while-revalidate).
A library such as TanStack Query manages caching, deduplication, retries and refetch on focus.

```tsx
const q = useQuery({ queryKey: ['notes', page], queryFn: () => getNotes(page), staleTime: 30_000 });
if (q.isPending) return <Skeleton />;
if (q.isError) return <ErrorPanel message={q.error.message} onRetry={q.refetch} />;
if (q.data.items.length === 0) return <Empty action="Create your first note" />;
```

</Level>

<Level name="Advanced">

Optimistic updates show the change before the server confirms, then roll back on failure. That needs a
snapshot of the previous cache and an invalidation after the server responds.

```ts
useMutation({
  mutationFn: renameNote,
  onMutate: async (v) => { await qc.cancelQueries({ queryKey: ['notes'] }); const prev = qc.getQueryData(['notes']);
    qc.setQueryData(['notes'], (old) => patch(old, v)); return { prev }; },
  onError: (_e, _v, ctx) => qc.setQueryData(['notes'], ctx.prev),
  onSettled: () => qc.invalidateQueries({ queryKey: ['notes'] }),
});
```

</Level>

<Level name="Edge cases">

- A fast response flashes the spinner for 50 ms: delay showing it by about 200 ms.
- An error on refetch while stale data is shown: keep the data and show a quiet error, do not blank it.
- A paginated list where the last page becomes empty after a deletion.

</Level>

<Level name="Corner cases">

An optimistic delete, then the user navigates away, then the server rejects it: the rollback happens on
a page the user no longer sees. Optimism plus navigation. A global toast with an undo or retry keeps the
user informed. Another: two optimistic edits to the same item where the first fails and its rollback
erases the second.

</Level>

<Level name="Production level">

Retries with backoff for idempotent reads only; no automatic retries for non-idempotent writes without
an idempotency key. Errors are reported with the request ID so support can find them.

</Level>

<Level name="Mindset">

The network is slow, flaky and sometimes wrong. Design for it as the normal case.

</Level>

<Level name="System design">

Client caching is a layer of the system's cache hierarchy, with its own invalidation problem. Keys and
invalidation rules mirror the API's resources.

</Level>

<Level name="Strategy">

Use dev tools to throttle to Slow 4G and to block the API, and screenshot every panel in every state.
Done when no panel ever shows a blank or a raw error, and an optimistic rename rolls back cleanly when I
force a 500.

</Level>

</Levels>

#### Phase 2: forms: validation, errors, disabled states and submission feedback

<Flow
  caption="A form submission that keeps the user oriented"
  steps={['Native constraints check', 'Submit disables the button and shows progress', 'Server validates', 'Field errors shown next to fields', 'Focus moves to the first error', 'Success message announced']}
/>

<Levels label="Phase 2, form validation, errors, disabled states and feedback">

<Level name="Beginner">

A form collects input and submits it. Use real `form`, `label`, `input` and `button type="submit"`
elements so Enter submits and the browser helps. Native constraints (`required`, `type="email"`,
`maxlength`) give fast feedback; the server still validates.

```html
<form method="post" action="/notes">
  <label for="t">Title</label>
  <input id="t" name="title" required maxlength="120" aria-describedby="t-err">
  <p id="t-err" class="field-error" hidden></p>
  <button type="submit">Save</button>
</form>
```

Common mistake: validating only on the client. Fix: the server is the authority; the client is a
convenience.

</Level>

<Level name="Intermediate">

Errors go next to the field, linked with `aria-describedby`, with `aria-invalid="true"` on the input.
On submit failure, focus moves to the first invalid field or to an error summary at the top. Validate
on blur or submit, not on every keystroke, so the user is not shouted at mid-typing.

</Level>

<Level name="Advanced">

Disabling the submit button during submission prevents double submits, but a disabled button loses
focus and its reason is invisible. A common pattern: keep it enabled, ignore clicks while pending and
show "Saving..." with `aria-busy`. The server-side error shape maps fields to messages so the client
can place them; phase 3 defines it.

```ts
type FormError = { error: 'invalid'; fields: Record<string, string> };
```

</Level>

<Level name="Edge cases">

- Leading and trailing spaces: "  " passes `required`; trim on the server.
- Paste of 10,000 characters into a 120-character field: `maxlength` truncates silently on paste.
- Autofill fills hidden fields or fires no input events in some browsers.

</Level>

<Level name="Corner cases">

The user submits, the network drops, the request actually reached the server, and they submit again:
two records. Network failure plus retry. An idempotency key generated when the form renders and sent
with each submit lets the server deduplicate. Another: a session expiry mid-form loses everything; save
a draft to local storage.

</Level>

<Level name="Production level">

Forms are where abuse arrives: spam, injection attempts, huge payloads. Server-side limits, rate limits
and validation, plus logging of validation failures (without values), are production basics.

</Level>

<Level name="Mindset">

A form is a conversation. The user should always know what is wrong, where, and what to do.

</Level>

<Level name="System design">

One schema shared by client and server validation removes drift; error messages are part of the API
contract.

</Level>

<Level name="Strategy">

Break the form deliberately with every edge case above and check each response. Done when every
invalid input produces a field-level message, focus lands on it, a screen reader announces it, and a
double submit creates one record.

</Level>

</Levels>

#### Phase 2: routing, code splitting and the cost of client-side JavaScript

<Levels label="Phase 2, routing, code splitting and JavaScript cost">

<Level name="Beginner">

A client router changes the URL and renders a new view without a full page load. Code splitting loads a
route's code only when it is visited.

```tsx
const Settings = lazy(() => import('./routes/Settings'));
<Suspense fallback={<Spinner />}><Settings /></Suspense>
```

Common mistake: one bundle for the whole app, so the login page downloads the chart library. Fix: split
by route, and check the bundle analyser.

</Level>

<Level name="Intermediate">

JavaScript is the most expensive byte on the web: it must be downloaded, parsed, compiled and executed
on the main thread, and on a mid-range phone that is several times slower than on my laptop. Routing
decisions affect this: server-rendered routes ship HTML that works before JavaScript loads; client-only
routes show nothing until it does.

</Level>

<Level name="Advanced">

Bundlers build a module graph and create chunks at dynamic `import()` boundaries; shared dependencies go
into common chunks. Tree-shaking removes unused exports only from side-effect-free ES modules. Prefetching
a route's chunk on hover or on viewport entry hides the split's latency.

</Level>

<Level name="Edge cases">

- A deep link to a client-only route returns 404 from the static host unless it falls back to the app
  shell.
- A chunk is deleted by a new deploy while an old tab is open: navigation fails with `ChunkLoadError`.
- Back button after a client route change should restore scroll position.

</Level>

<Level name="Corner cases">

A lazy route inside a modal plus a slow network: the modal opens with a spinner, the user closes it, the
chunk arrives and an effect runs on an unmounted tree. Lazy loading plus lifecycle. Keep the old deploy's
chunks for a while after release, and reload on `ChunkLoadError`.

</Level>

<Level name="Production level">

A bundle-size budget in CI fails the build when a route's JavaScript grows past a threshold. Third-party
scripts (analytics, chat widgets) count against the same budget.

</Level>

<Level name="Mindset">

Every dependency is paid for by every user on every visit. Ask whether the server could do it.

</Level>

<Level name="System design">

The rendering strategy (static, server-rendered, client-rendered, islands as this site uses) is an
architecture decision about where work happens and what the user waits for.

</Level>

<Level name="Strategy">

Measure the app's JavaScript per route, split the two largest, and compare total blocking time on a
throttled phone profile before and after. Done when each route has a budget in CI and the numbers are
in the study log.

</Level>

</Levels>

#### Phase 2: performance: Core Web Vitals, images, fonts, bundle size and hydration

<Compare
  caption="The three Core Web Vitals and what usually fixes each"
  left="Metric, good threshold"
  right="Usual fix"
  rows={[
    ["LCP, largest paint under 2.5 s", "Server-render the hero, preload its image, cut render-blocking CSS"],
    ["INP, interaction response under 200 ms", "Break long tasks, less JavaScript, defer non-urgent work"],
    ["CLS, layout shift under 0.1", "Width and height on media, reserved space for late content, font fallback metrics"],
  ]}
/>

<Levels label="Phase 2, Core Web Vitals, images, fonts, bundles and hydration">

<Level name="Beginner">

Core Web Vitals measure what users feel: how fast the main content appears (LCP), how fast the page
responds to input (INP) and how much it jumps around (CLS). Lighthouse measures them in a lab; real-user
data comes from the field.

```html
<img src="/hero.avif" width="1200" height="600" alt="Dashboard overview" fetchpriority="high">
```

Common mistake: images without dimensions, so text jumps when they load. Fix: always set width and
height, or `aspect-ratio`.

</Level>

<Level name="Intermediate">

Images: modern formats (AVIF, WebP), responsive `srcset`, lazy-loading below the fold, never
lazy-loading the LCP image. Fonts: `font-display: swap`, subset, self-host, preload the one used above
the fold. Bundles: split, tree-shake, drop heavy dependencies.

</Level>

<Level name="Advanced">

INP is measured from input to next paint, so a long task anywhere during the interaction counts. Breaking
work up with `await scheduler.yield()` (or a `setTimeout` fallback) lets the browser paint between
chunks. Hydration re-executes component code on the client to attach handlers; partial or progressive
hydration (islands) hydrates only interactive parts.

```js
for (const chunk of chunks(items, 100)) { render(chunk); await new Promise(r => setTimeout(r)); }
```

</Level>

<Level name="Edge cases">

- A font swap changes line heights and causes CLS: use `size-adjust` on the fallback.
- A cookie banner inserted at the top after load shifts everything.
- Lighthouse on a fast laptop scores 100 while a real low-end phone fails INP.

</Level>

<Level name="Corner cases">

A streaming AI response appends text and grows the container, which is user-initiated and so not
counted as CLS only if it happens within 500 ms of input; tokens arriving seconds later count. Streaming
plus layout shift. Reserve space, or append below the fold of the viewport the user is reading.

</Level>

<Level name="Production level">

Field data (the `web-vitals` library sending to my analytics) is the truth; lab data is for debugging.
Budgets in CI catch regressions before they reach users.

</Level>

<Level name="Mindset">

Performance is a feature that decays unless it is measured on every change.

</Level>

<Level name="System design">

Performance spans layers: CDN caching, server response time, rendering strategy, assets, and client
work. The waterfall in dev tools shows which layer dominates.

</Level>

<Level name="Strategy">

Record a performance profile of the dashboard on a throttled profile, fix the top three contributors,
and add Lighthouse CI with a budget. Done when the core pages score 95 or more on performance and the
budget blocks a deliberately large import.

</Level>

</Levels>

#### Phase 2: SEO: titles, descriptions, canonicals, structured data, sitemaps and server-rendered content

<Flow
  caption="How a page gets into search results"
  steps={['Crawler finds the URL in a link or sitemap', 'Fetches HTML', 'Reads title, canonical, robots', 'Renders JavaScript later if needed', 'Indexes the canonical', 'Ranks for queries']}
/>

<Levels label="Phase 2, SEO from titles to server-rendered content">

<Level name="Beginner">

Each page needs a unique `title`, a `meta name="description"` that summarises it, a canonical URL, and
content present in the HTML. A sitemap lists the pages; `robots.txt` says what not to crawl.

```html
<title>Notes · Dashboard</title>
<meta name="description" content="All your notes, searchable and sorted by last edit.">
<link rel="canonical" href="https://app.example/notes">
```

Common mistake: the same title on every page. Fix: generate it from the page's content.

</Level>

<Level name="Intermediate">

Structured data (JSON-LD with schema.org types) describes the page to search engines: an `Article`,
a `Product`, a `BreadcrumbList`. Canonical URLs consolidate duplicates (tracking parameters, trailing
slashes). Pages behind login should be `noindex`; marketing and docs pages should be server-rendered.

</Level>

<Level name="Advanced">

Search engines render JavaScript in a second, delayed pass, so client-only content is indexed later and
less reliably. Internal links must be real `a href` elements to be followed. Hreflang for languages,
pagination with distinct canonicals per page, and correct status codes (a real 404, not a 200 "not found"
page, which is a soft 404).

</Level>

<Level name="Edge cases">

- A canonical pointing at a URL that redirects or 404s is ignored.
- A sitemap listing `noindex` pages sends mixed signals.
- Query-string filters create thousands of near-duplicate URLs.

</Level>

<Level name="Corner cases">

A preview deploy is publicly reachable and indexable, and search shows the preview URL instead of
production. Environments plus crawlers. Preview deploys send `X-Robots-Tag: noindex`, and canonicals
always point at production.

</Level>

<Level name="Production level">

Search Console shows indexing errors and real queries. A build check that every page has one h1, a unique
title and description, a canonical and a sitemap entry (this site does exactly that) stops regressions.

</Level>

<Level name="Mindset">

SEO is mostly making the page honest and legible to a machine that is not running my JavaScript.

</Level>

<Level name="System design">

The rendering strategy, the URL design and the CDN cache all decide SEO. Public content and app content
often belong in different rendering modes.

</Level>

<Level name="Strategy">

Write the build check for titles, descriptions and canonicals, add JSON-LD to public pages and validate
it with Google's Rich Results Test. Done when Lighthouse SEO is 95 or more and the check fails on a
duplicate title.

</Level>

</Levels>

#### Phase 2: design systems: tokens, primitives, variants and documentation

<Layers
  caption="The layers of a design system"
  layers={[
    { name: 'Tokens', note: 'colour, space, type, radius as named values' },
    { name: 'Primitives', note: 'Button, Input, Stack, Text' },
    { name: 'Components', note: 'Card, Dialog, DataTable' },
    { name: 'Patterns', note: 'empty state, form layout, chat message' },
    { name: 'Docs', note: 'API, examples, do and do not' },
  ]}
/>

<Levels label="Phase 2, design-system tokens, primitives, variants and docs">

<Level name="Beginner">

Tokens are named design values: `--space-2`, `--color-ink`, `--font-size-body`. Components use tokens
instead of raw values so the whole UI changes consistently.

```css
:root { --space-1: 0.25rem; --space-2: 0.5rem; --color-ink: #111; --color-muted: #666; }
.button { padding: var(--space-2) var(--space-1); color: var(--color-ink); }
```

Common mistake: a "design system" that is a folder of unrelated components. Fix: start with tokens and
primitives, then build up.

</Level>

<Level name="Intermediate">

Variants are a component's documented options (`size`, `tone`, `variant`), typed as unions so invalid
combinations do not compile. Composition beats configuration: a `Card` with `Card.Header` and
`Card.Body` slots instead of twenty props.

```tsx
type ButtonProps = { variant?: 'primary' | 'secondary' | 'ghost'; size?: 'sm' | 'md' } & React.ButtonHTMLAttributes<HTMLButtonElement>;
```

</Level>

<Level name="Advanced">

A component's API is the contract: props, events, slots, accessibility guarantees and forwarded refs.
Breaking changes need versioning and a migration note. Documentation is generated where possible
(Storybook or a docs page with live examples) and includes the states (disabled, loading, error).

</Level>

<Level name="Edge cases">

- A button with a very long label: wrap or truncate, decided once.
- A component used inside a `form` with no `type` defaults to `submit`.
- Dark mode or high-contrast mode overriding tokens.

</Level>

<Level name="Corner cases">

A variant prop and a `className` override both set padding, and the override wins in one build and loses
in another because CSS order changed. Variants plus overrides. Cascade layers fix the order, and the
system decides whether overrides are allowed at all.

</Level>

<Level name="Production level">

Visual regression tests catch accidental changes; accessibility tests per component catch regressions at
the source. Adoption is measured by how many raw values remain in feature code.

</Level>

<Level name="Mindset">

A design system is a product for other developers. Its users are the team, and its docs are its UI.

</Level>

<Level name="System design">

The design system sits between design and features, owned by someone, versioned, with a changelog. AI
surfaces (message bubble, citation chip, streaming indicator) become patterns in it.

</Level>

<Level name="Strategy">

Extract tokens and three primitives from the app, then document one component fully. Done when the gate
item holds: one component with a documented API and tests for each variant and state.

</Level>

</Levels>

#### Phase 2: testing: component tests, accessibility checks and end-to-end flows

<Layers
  caption="Frontend tests, cheapest at the bottom"
  layers={[
    { name: 'Playwright end to end', note: 'sign in, create, chat: the critical flows' },
    { name: 'Accessibility scans', note: 'axe in components and pages' },
    { name: 'Component tests', note: 'render, interact by role, assert' },
    { name: 'Type check and lint', note: 'every save' },
  ]}
/>

<Levels label="Phase 2, component, accessibility and end-to-end tests">

<Level name="Beginner">

Component tests render a component and interact with it like a user: find by role and label, click,
type, assert on what is visible.

```tsx
test('shows an error for an empty title', async () => {
  render(<NoteForm onSubmit={vi.fn()} />);
  await userEvent.click(screen.getByRole('button', { name: 'Save' }));
  expect(screen.getByText('Title is required')).toBeVisible();
});
```

Common mistake: selecting by CSS class or test ID everywhere. Fix: query by role and accessible name;
it tests accessibility at the same time.

</Level>

<Level name="Intermediate">

Playwright drives a real browser through critical flows against a running app with a seeded database.

```ts
test('sign in and create a note', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('a@example.com');
  await page.getByLabel('Password').fill('correct horse');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.getByRole('link', { name: 'New note' }).click();
  await page.getByLabel('Title').fill('First');
  await page.getByRole('button', { name: 'Save' }).click();
  await expect(page.getByRole('heading', { name: 'First' })).toBeVisible();
});
```

</Level>

<Level name="Advanced">

`@axe-core/playwright` scans pages inside the same tests. Playwright's auto-waiting assertions remove
sleeps. Network mocking (`page.route`) tests error and slow states deterministically; a keyboard-only
test uses `page.keyboard.press('Tab')` and asserts on `:focus`.

</Level>

<Level name="Edge cases">

- A test that passes on a wide viewport fails on mobile: run both projects.
- Animations make screenshots flaky: disable them in tests.
- Tests that share one user account interfere with each other.

</Level>

<Level name="Corner cases">

The streaming chat test: tokens arrive over time, and asserting on the final text too early fails
intermittently. Streaming plus assertion timing. Assert on a "done" state the UI exposes (a button
changing from Stop to Regenerate), not on text length.

</Level>

<Level name="Production level">

End-to-end tests run on every pull request against a preview deploy, with traces and videos kept on
failure. They stay few and critical; the rest is lower in the pyramid.

</Level>

<Level name="Mindset">

Test what the user does and sees, not how the component is built.

</Level>

<Level name="System design">

Frontend tests depend on seed data, preview environments and stable selectors (roles), which are system
concerns as much as test concerns.

</Level>

<Level name="Strategy">

Write Playwright tests for sign-in, create-note, paginate and chat, including a keyboard-only version of
the main flow. Done when all run in CI on every push and a deliberate accessibility regression fails one.

</Level>

</Levels>

#### Phase 2: the build: a multi-page app with an AI chat surface

<Figure art={`
  user types --> POST /api/chat ---------> server --> model provider
                    |                           |   (tokens stream)
  UI states:        v                           v
  [idle] -> [sending] -> [streaming: Stop] -> [done: Regenerate, Copy]
                 |              |
                 v              v
             [error: Retry]  [stopped: partial answer kept]
  empty conversation: suggested prompts, not a blank box
`} caption="The chat surface as a state machine: every state has visible controls, and streaming can be stopped." />

<Levels label="Phase 2, the build: dashboard, form, pagination and AI chat">

<Level name="Beginner">

The app has sign-in, a dashboard, a form with validation, a paginated list and a chat surface. The chat
surface handles streaming, errors and empty states; the model itself is a placeholder service that
streams text, because the real AI work is phase 7.

```ts
const res = await fetch('/api/chat', { method: 'POST', body: JSON.stringify({ message }), signal: ac.signal });
const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader();
for (;;) { const { value, done } = await reader.read(); if (done) break; append(value); }
```

</Level>

<Level name="Intermediate">

The server streams with server-sent events or a chunked response. The client shows a Stop button that
calls `ac.abort()`, keeps the partial answer, and offers Regenerate. Errors mid-stream keep what arrived
and show Retry. The empty conversation shows example prompts.

```ts
// server: stream chunks as they arrive
res.writeHead(200, { 'content-type': 'text/event-stream', 'cache-control': 'no-cache' });
for await (const token of fakeModel(message)) res.write(`data: ${JSON.stringify(token)}\n\n`);
res.end('data: [DONE]\n\n');
```

</Level>

<Level name="Advanced">

Accessibility of the chat: the message list is a `log` region or announced once on completion, the input
keeps focus after sending, Stop is reachable by keyboard, and new messages do not steal scroll if the
user scrolled up. Pagination on the list uses cursor-based URLs so back and refresh keep the page.

</Level>

<Level name="Edge cases">

- An empty message: the send button is a no-op with a hint, not an error.
- A very long answer: virtualise or collapse old messages.
- Markdown in the answer: render safely; never inject model output as raw HTML.

</Level>

<Level name="Corner cases">

The user presses Stop exactly as the last chunk arrives: the client must not show both "stopped" and
"done". Abort plus completion. A single state machine with one transition winning fixes it. Another:
two tabs on the same conversation streaming at once.

</Level>

<Level name="Production level">

Proxies buffer streaming responses unless told not to (`X-Accel-Buffering: no` for nginx). Timeouts on
the server stop a stream that never ends. Every message has an ID for later feedback and evals.

</Level>

<Level name="Mindset">

The AI surface is a UI first. Its trustworthiness comes from states and controls, before any model.

</Level>

<Level name="System design">

The chat surface is the client end of phase 7 and 8's pipeline: it will show citations, uncertainty and
feedback buttons. Leave room for them in the message component now.

</Level>

<Level name="Strategy">

Build page by page with a Playwright test per flow, then the chat surface as a state machine with a
test per transition. Done when every flow has a test and the chat surface's states each have a visible,
keyboard-reachable control.

</Level>

</Levels>
