Six weeks on the layer where a user decides whether to trust the product. The frontend is also where
AI-generated code most often looks finished and is not: the happy path renders, and the loading state,
the keyboard path, the error message and the layout shift are missing. So this phase is about the
states nobody demos. The primary books are *Refactoring UI* for visual decisions and *Inclusive
Components* for accessible patterns, with MDN, web.dev/learn, the React docs and Full Stack Open as the
free references, and *CSS: The Definitive Guide* as optional depth. The same ground is covered from the
beginner side in <a href={withBase('/plans/software-developer/')}>the modern developer roadmap</a>; here
it ends with an AI chat surface that streams.

#### Phase 2: how I would learn it

Each topic follows one rule: build it without the framework first, then with it. A form is plain HTML
that posts to the server before it becomes a React component with client validation. A list is a
server-rendered table before it becomes a paginated, fetched, cached view. That order means I always
know what the framework is adding, and I always have a working fallback when JavaScript fails.

#### Phase 2: Semantic HTML, landmarks, headings and document structure

<Levels label="Phase 2, semantic HTML, landmarks, headings and document structure">

<Level name="Beginner">

Semantic HTML means choosing the element that says what a thing is, not what it looks like. A button is a
`button`, a link is an `a` with an `href`, a list is a `ul`, a heading is an `h1` to `h6`. The browser
gives each of those free behaviour: a button is focusable and fires on Enter and Space; a link opens in a
new tab with a middle click; a heading appears in a screen reader's headings list.

```html
<!-- wrong: looks like a button, is not one -->
<div class="btn" onclick="save()">Save</div>
<!-- right: focusable, keyboard-operable, announced as a button -->
<button type="button" onclick="save()">Save</button>
```

The common mistake is the `div` with a click handler. It cannot be reached with Tab, Enter does nothing,
and a screen reader announces it as plain text. The fix is not to add `tabindex` and key handlers by hand;
it is to use `button`.

</Level>

<Level name="Intermediate">

A real page has a structure: one `header`, one `nav` (or a few, each labelled), one `main`, sections with
headings, and a `footer`. Headings form an outline: one `h1` for the page, `h2` for its sections, `h3`
inside those, never skipping a level for visual size. Forms use `label` tied to each input; tables use
`th` with `scope` and a `caption`.

```html
<main>
  <h1>Dashboard</h1>
  <section aria-labelledby="recent">
    <h2 id="recent">Recent notes</h2>
    <ul>
      <li><article><h3>Standup</h3><p>Shipped the login fix.</p></article></li>
    </ul>
  </section>
</main>
```

The mistake is picking a heading level for its size: an `h4` because it looked right. Size is CSS; the
level is the outline. A screen-reader user navigating by headings sees a broken outline as a broken page.

</Level>

<Level name="Advanced">

Underneath, the browser builds two trees from the HTML: the DOM, and the accessibility tree that
assistive technology reads. Each node in the accessibility tree has a role (button, link, heading level
2), a name (the text or label), a state (expanded, checked, disabled) and a value. Native elements fill
these in correctly. ARIA attributes can change them, which is why the first rule of ARIA is to not use it
when a native element exists. The accessible name is computed in an order: `aria-labelledby`, then
`aria-label`, then the associated `label` or the element's content, then `title`.

```text
Chrome DevTools > Elements > Accessibility pane
  Role: button   Name: "Save"   Focusable: true
```

I open that pane on every custom component and check role, name and state, because that is what a
screen reader will say.

</Level>

<Level name="Edge cases">

An icon-only button has no text, so its accessible name is empty and a screen reader says "button". The
fix is visible text or `aria-label="Delete note"`. A page with two `nav` elements needs each labelled
(`aria-label="Primary"`, `aria-label="Pagination"`) or the landmark list shows two identical entries. A
`button` inside a `form` defaults to `type="submit"`, so a "Cancel" button submits the form unless it says
`type="button"`. An `a` without `href` is not focusable at all. A heading that is empty, because its text
loads later, appears as a blank entry in the headings list.

</Level>

<Level name="Corner cases">

A link styled as a button that also opens a modal: a link means "go somewhere", so a screen-reader user
expects navigation and gets a dialog, and a middle-click opens a broken tab. Decide by what it does: it
changes the URL, so it is a link; it acts on the page, so it is a button. A heading inside a clickable card
where the whole card is a link: the screen reader reads the entire card as the link's name, which can be a
paragraph long. The fix is the "stretched link" pattern: only the heading is the link, and CSS extends its
click area over the card.

```css
.card { position: relative; }
.card h3 a::after { content: ''; position: absolute; inset: 0; }
```

</Level>

<Level name="Production level">

In production semantics decide whether search engines, screen readers, browser reader modes and
automated tests can understand the page. Playwright's best locators (`getByRole('button', { name:
'Save' })`) only work on semantic markup, so semantic HTML also makes tests stable. I run axe in CI on
the core pages and fail the build on any violation, and I keep one rule in review: no `div` with an
`onClick`.

</Level>

<Level name="Mindset">

The habit is "say what it is, then style it." The document is a contract with every client that is not
my eyes: assistive technology, search crawlers, tests, and the user whose CSS failed to load. If the page
makes sense as plain HTML, every layer above it has something solid to stand on.

</Level>

<Level name="System design">

Structure is a shared interface between the design system, the content, the tests and SEO. A design
system's `Heading` component that takes a `level` prop separately from a `size` prop encodes the
outline-versus-style split once, for every page. Server-rendered semantic HTML is also the graceful
degradation path when the AI chat's JavaScript fails.

</Level>

<Level name="Strategy">

I build the app shell as plain HTML with no CSS and navigate it with a screen reader (VoiceOver or NVDA)
using only the landmarks and headings lists, then write down every place I got lost. Done when axe reports
zero violations on every core page, each page has exactly one `h1`, and I can complete the main flow with
the screen reader alone.

</Level>

</Levels>

#### Phase 2: CSS: the box model, flexbox, grid, responsive design and container queries

<Figure art={`
  +---------------- margin ----------------+
  |  +------------- border -------------+  |
  |  |  +---------- padding ---------+  |  |
  |  |  |                            |  |  |
  |  |  |   content  (width x height)|  |  |
  |  |  |                            |  |  |
  |  |  +----------------------------+  |  |
  |  +----------------------------------+  |
  +----------------------------------------+
  box-sizing: content-box -> width is the content only
  box-sizing: border-box  -> width includes padding and border
`} caption="Every element is this box. Most layout surprises are a misunderstanding of which box a width refers to." />

<Levels label="Phase 2, CSS: box model, flexbox, grid, responsive design and container queries">

<Level name="Beginner">

Every element is a rectangle with content, padding, a border and margin. Flexbox lays out items in one
direction (a row or a column) and distributes space between them. Grid lays out items in two dimensions
with rows and columns. Responsive design means the layout adapts to the space available. The smallest
useful setup: `border-box` everywhere, a flex row for a toolbar, a grid for a card list.

```css
*, *::before, *::after { box-sizing: border-box; }
.toolbar { display: flex; gap: 0.5rem; align-items: center; }
.cards { display: grid; grid-template-columns: repeat(auto-fill, minmax(16rem, 1fr)); gap: 1rem; }
```

The common mistake is setting `width: 100%` plus padding on a `content-box` element: it overflows its
parent by twice the padding. `border-box` fixes that globally.

</Level>

<Level name="Intermediate">

A real layout combines them: grid for the page skeleton, flexbox inside each region, and `gap` instead of
margins between siblings. Media queries change the layout at viewport widths; container queries change a
component based on the width of its container, which is what a reusable component actually needs.

```css
.app { display: grid; grid-template-columns: 16rem 1fr; min-height: 100dvh; }
@media (max-width: 48rem) { .app { grid-template-columns: 1fr; } }

.card-wrap { container-type: inline-size; }
@container (min-width: 30rem) { .card { display: flex; gap: 1rem; } }
```

The mistake is designing components around the viewport. A card in a narrow sidebar on a wide screen is
still narrow; only a container query knows that.

</Level>

<Level name="Advanced">

The exact rules underneath are the cascade and formatting contexts. The cascade picks a value by origin
and importance, then cascade layers, then specificity, then order. Flex items have `min-width: auto` by
default, which means a flex child will not shrink below its content's width, the cause of most "why is it
overflowing" bugs. Vertical margins between blocks collapse (the larger wins); they do not collapse inside
flex or grid containers. `fr` units distribute leftover space after fixed tracks and content minimums.

```css
.row > .title { min-width: 0; overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
```

Without `min-width: 0`, a long title pushes the row wider than the screen even with `overflow: hidden`.

</Level>

<Level name="Edge cases">

A single unbreakable string (a long URL, a hash) overflows any container; `overflow-wrap: anywhere` breaks
it. `100vh` on mobile includes the area behind the browser's address bar, so a full-height layout scrolls;
`100dvh` is the dynamic viewport. An empty grid shows nothing but still takes its gap if it has explicit
rows. Zero items in a `repeat(auto-fit, ...)` grid collapses the tracks; `auto-fill` keeps them. A user who
sets their browser font size to 200% breaks every layout built in pixels; `rem` respects it.

</Level>

<Level name="Corner cases">

A sticky header plus an `overflow: hidden` ancestor: `position: sticky` silently stops working because
sticky sticks to the nearest scrolling ancestor. A `z-index` that seems ignored: it only works within a
stacking context, and a `transform` or `opacity` below 1 on an ancestor creates a new one, so a dropdown
can never rise above a sibling container. A container query plus a component that sets the container's
own width by its content: `container-type: inline-size` makes the container ignore its children for
sizing, so a shrink-wrapped container collapses to zero.

</Level>

<Level name="Production level">

In production CSS problems are layout shift, unreadable text and broken flows on devices I did not test.
I reserve space for anything that loads late (images with `width` and `height`, skeletons with fixed
height), test at 320 pixels wide and at 200% zoom, and keep a small set of layout primitives (stack,
cluster, sidebar, grid) instead of one-off rules. Unused CSS is cheap; unpredictable CSS is expensive.

</Level>

<Level name="Mindset">

The habit is to work with the browser's layout algorithms, not against them. Instead of positioning
things at exact pixels, I describe the relationship (these items share a row with a gap; this column is
at least sixteen rem) and let the algorithm handle the sizes I did not think of.

</Level>

<Level name="System design">

CSS at scale is an architecture problem: naming, layering and ownership. Cascade layers (`@layer reset,
tokens, primitives, components, utilities`) make precedence explicit. Design tokens as custom properties
let a theme change in one place. Component-scoped styles keep one team's change from breaking another
page.

</Level>

<Level name="Strategy">

I rebuild three real layouts (an app shell with sidebar, a responsive card grid, a form with labels beside
inputs on wide screens and above them on narrow) with no framework, then break each at 320 pixels and
200% zoom and fix it. Done when every core page has no horizontal scroll at 320 pixels and no clipped text
at 200% zoom.

</Level>

</Levels>

#### Phase 2: Accessibility: keyboard, focus, labels, contrast, screen readers and reduced motion

<Flow
  caption="The keyboard path through a modal dialog. Every arrow must work without a mouse."
  steps={["Tab to 'Delete'", "Enter opens the dialog", "Focus moves into the dialog", "Tab cycles inside only", "Escape closes it", "Focus returns to 'Delete'"]}
/>

<Levels label="Phase 2, accessibility: keyboard, focus, labels, contrast, screen readers and reduced motion">

<Level name="Beginner">

Accessibility means people using a keyboard, a screen reader, zoom, voice control or reduced motion can
use the product. Four checks cover most of it: everything works with Tab, Enter, Space and Escape; there is
always a visible focus outline; every input has a label; text has enough contrast (4.5 to 1 for body text
under WCAG AA).

```css
:focus-visible { outline: 2px solid currentColor; outline-offset: 2px; }
```

The common mistake is `outline: none` to remove the "ugly" focus ring, which makes the page unusable by
keyboard. Style it; never delete it.

</Level>

<Level name="Intermediate">

In a real app, focus has to be managed when the page changes without a reload. When a modal opens, focus
moves into it; when it closes, focus returns to the button that opened it. When a client-side route
changes, focus moves to the new page's heading so a screen reader announces it. Status messages
("Saved", "3 results") use a live region so they are announced without moving focus.

```html
<dialog id="confirm"><h2>Delete note?</h2><button value="cancel">Cancel</button><button value="ok">Delete</button></dialog>
<p role="status" aria-live="polite" id="flash"></p>
```

The native `dialog` element with `showModal()` traps focus and closes on Escape for free. The mistake is a
hand-built modal `div` that lets Tab wander behind it into the page.

</Level>

<Level name="Advanced">

The exact rules come from WCAG 2.2: perceivable, operable, understandable, robust, with testable success
criteria. Some I check every time: 2.1.1 keyboard (everything operable), 2.4.7 focus visible, 2.4.11 focus
not obscured (a sticky footer must not hide the focused element), 1.4.3 contrast, 1.4.10 reflow at 320 CSS
pixels, 2.5.8 target size (at least 24 by 24 pixels), and 3.3.1 error identification. ARIA patterns for
widgets (tabs, combobox, menu) define the keys each must support, documented in the ARIA Authoring
Practices Guide.

```text
axe: "Elements must meet minimum color contrast ratio thresholds" (color-contrast)
  Expected contrast ratio of 4.5:1, found 3.2:1  (#8a8a8a on #ffffff)
```

</Level>

<Level name="Edge cases">

Placeholder text is not a label: it disappears on typing and usually fails contrast. A disabled button is
skipped by Tab, so a user never learns why they cannot submit; often an enabled button that shows the
errors is better. A `title` attribute is not announced reliably and never appears on touch. Text in a
monochrome palette at light grey fails contrast even though it looks elegant. `prefers-reduced-motion`
users still see an animation that was started by JavaScript unless the script checks the media query.

```ts
const reduce = matchMedia('(prefers-reduced-motion: reduce)').matches;
```

</Level>

<Level name="Corner cases">

A streaming AI response in a live region: each token update is announced, and a screen reader either
floods the user or drops updates. The fix is to announce "Answer ready" once when streaming ends, and let
the user read the full message, with `aria-busy="true"` on the message while it streams. A focus trap in a
modal plus a toast that appears outside it: the toast's "Undo" button is unreachable. A client-side route
change plus a scroll restoration: focus stays on a link that no longer exists, and the next Tab starts from
the top of the document.

</Level>

<Level name="Production level">

In production accessibility regressions arrive with every change, so it needs automated and manual
checks. Automated (axe in Playwright) catches about a third of issues: missing labels, contrast, roles.
The rest needs a person: a keyboard pass and a screen-reader pass of the critical flows before each
release. I add a "keyboard-only" Playwright test that completes sign-in and the main flow using only
`keyboard.press`.

</Level>

<Level name="Mindset">

The habit is to treat the keyboard and the screen reader as first-class clients of the UI, like a phone
screen. "Works for me with a mouse" is a test with one user. Accessibility also tends to be the same work
as quality: a labelled form is also a testable, clearer form.

</Level>

<Level name="System design">

Accessibility belongs in the design system: a `Dialog`, `Menu` or `Combobox` built once with the right
keyboard model and reused everywhere is far more reliable than each page getting it right. It also
belongs in the definition of done and in CI, so a regression blocks a merge like a failing test does.

</Level>

<Level name="Strategy">

I unplug the mouse for a full day of using my own app, then run VoiceOver or NVDA through sign-in, the
dashboard and the chat. I write every blocker as a card. Done when the gate's keyboard-only flow passes as
an automated test, axe is clean on every core page, and the screen-reader pass finds no blocker.

</Level>

</Levels>

#### Phase 2: TypeScript at the boundary: props, events, API responses and error states

<Figure art={`
   server JSON  --(unknown)-->  parse with schema  --(typed)-->  component props
        |                            |
        |                       fails? -> error state with message
        v
   the compiler cannot see across the network:
   'as User' is a promise, a schema is a check
`} caption="Types stop at the network. A schema at the boundary turns unknown data into a type I can trust." />

<Levels label="Phase 2, TypeScript at the boundary: props, events, API responses and error states">

<Level name="Beginner">

TypeScript describes the shape of data so the editor and compiler catch mistakes. In a frontend there are
four boundaries where data enters a component: its props, DOM events, API responses and errors. Typing
props is the easy one.

```tsx
type NoteCardProps = { title: string; body: string; onDelete: (id: string) => void; id: string };
function NoteCard({ title, body, onDelete, id }: NoteCardProps) {
  return <article><h3>{title}</h3><p>{body}</p><button onClick={() => onDelete(id)}>Delete</button></article>;
}
```

The common mistake is typing an API response with `as`: `const notes = (await res.json()) as Note[]`. It
compiles, and if the server changes a field the page crashes far from the cause.

</Level>

<Level name="Intermediate">

At the API boundary I validate with a schema and derive the type from it, so the check and the type cannot
drift. I model the request as a union of states rather than separate booleans.

```ts
import { z } from 'zod';
const Note = z.object({ id: z.string(), title: z.string(), body: z.string(), createdAt: z.coerce.date() });
type Note = z.infer<typeof Note>;

type Remote<T> = { status: 'idle' } | { status: 'loading' } | { status: 'error'; message: string } | { status: 'ok'; data: T };

async function getNotes(): Promise<Note[]> {
  const res = await fetch('/api/notes');
  if (!res.ok) throw new Error(`notes: ${res.status}`);
  return z.array(Note).parse(await res.json());
}
```

The mistake is `isLoading`, `isError` and `data` as three independent fields, which allows the impossible
"loading and error and data" combination. A discriminated union makes it unrepresentable.

</Level>

<Level name="Advanced">

Event types come from React's definitions: `React.ChangeEvent<HTMLInputElement>`,
`React.FormEvent<HTMLFormElement>`. `event.currentTarget` is typed as the element the handler is on;
`event.target` is whatever was clicked, typed loosely, because it may be a child. Exhaustive checks with
`never` make the compiler tell me when I add a state and forget to render it.

```ts
function render(s: Remote<Note[]>) {
  switch (s.status) {
    case 'idle': case 'loading': return 'Loading';
    case 'error': return s.message;
    case 'ok': return `${s.data.length} notes`;
    default: { const unreachable: never = s; return unreachable; }
  }
}
```

</Level>

<Level name="Edge cases">

A date arrives as a string in JSON; without `z.coerce.date()` it stays a string typed as `Date` and
`note.createdAt.getTime()` throws `getTime is not a function`. An optional field that the server sends as
`null` fails a schema that says `.optional()` (which allows `undefined` only); `.nullable()` or
`.nullish()` is the honest type. A `204 No Content` response makes `res.json()` throw
`Unexpected end of JSON input`. A number input's value is a string.

</Level>

<Level name="Corner cases">

A schema that strips unknown keys plus a form that round-trips the object back to the server: the server
added a field, my client never saw it, and my update silently deletes it. The fix is `PATCH` with only the
changed fields, or `.passthrough()` where round-tripping is intended. A shared type package plus a server
deployed before the client: the client's schema rejects a new enum value the server now sends, and the whole
list fails to render. The fix is to parse each item separately and degrade unknown ones, or to make the enum
open (`z.string()` with known values handled).

</Level>

<Level name="Production level">

In production a schema failure is a contract break between two deploys, and I want to hear about it. I
log the validation error with the endpoint and the path of the failing field, show a useful error state to
the user, and track the count as a metric. A spike after a deploy tells me which side broke the contract
within minutes.

</Level>

<Level name="Mindset">

The habit is to trust types inside the boundary and check data at it. Inside my code, types are facts;
at the edge, they are hopes until something checks them.

</Level>

<Level name="System design">

The boundary schema is the API contract in code. Generating it from OpenAPI (Phase 3), or sharing one Zod
package between server and client, gives one source of truth. The same pattern returns in Phase 7, where
the "server" is a model and structured output is validated with a schema before anything uses it.

</Level>

<Level name="Strategy">

I make the server return five broken responses on purpose (missing field, wrong type, null, 204, 500)
and check each produces a clear error state, not a crash. Done when no `as` cast on network data remains
in the codebase and every fetch passes through a schema.

</Level>

</Levels>

#### Phase 2: React: components, state, effects, context, reducers and composition

<Figure art={`
  event (click, input, response)
        |
        v
  setState / dispatch  ----->  React schedules a render
                                     |
                                     v
                        component functions run again (pure)
                                     |
                                     v
                        new JSX  --diff-->  minimal DOM updates
                                     |
                                     v
                        effects run after paint (sync with outside)
`} caption="React's loop. Rendering is a pure calculation from state; effects are for talking to things outside React." />

<Levels label="Phase 2, React: components, state, effects, context, reducers and composition">

<Level name="Beginner">

A React component is a function that takes props and returns a description of UI. State is data the
component remembers between renders; changing it with the setter makes React render again. That is the
whole model: UI is a function of state.

```tsx
function Counter() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>Clicked {n} times</button>;
}
```

The common mistake is mutating state: `items.push(x); setItems(items)`. React compares by reference, sees
the same array, and may skip the render. Create a new array: `setItems([...items, x])`.

</Level>

<Level name="Intermediate">

Real components combine state, derived values and composition. I keep state minimal and compute
everything else during render. Children and render props let a parent decide the content while a child
owns the behaviour. A reducer centralises related state transitions.

```tsx
type Action = { type: 'add'; note: Note } | { type: 'remove'; id: string };
function notesReducer(state: Note[], a: Action): Note[] {
  switch (a.type) {
    case 'add': return [a.note, ...state];
    case 'remove': return state.filter((n) => n.id !== a.id);
  }
}
const [notes, dispatch] = useReducer(notesReducer, []);
const visible = notes.filter((n) => n.title.includes(query)); // derived, not stored
```

The mistake is storing derived data in state (`const [visible, setVisible] = useState(...)` kept in sync by
an effect), which renders twice and drifts.

</Level>

<Level name="Advanced">

Underneath, each render is a snapshot: event handlers see the state values from the render that created
them. Updates are batched, so three `setN(n + 1)` calls in one handler give `n + 1`, not `n + 3`; the
updater form `setN((m) => m + 1)` queues correctly. Keys tell React which list item is which across
renders; changing a component's key resets its state. Effects run after the browser paints and exist to
synchronise with external systems (subscriptions, timers, imperative widgets); in development Strict Mode
mounts, unmounts and remounts each component to expose effects that lack cleanup.

```tsx
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id); // without this, Strict Mode shows two intervals
}, []);
```

</Level>

<Level name="Edge cases">

Using an array index as a key in a list that reorders: the state of row two moves to whatever item is now
second, so a half-typed comment jumps to another note. Use a stable ID. Rendering `{count && <Badge />}`
with `count` of 0 renders the digit `0`. An effect with an object in its dependency array that is
recreated every render runs every render. A state setter called during render causes an infinite loop:

```text
Error: Too many re-renders. React limits the number of renders to prevent an infinite loop.
```

</Level>

<Level name="Corner cases">

A stale closure plus an interval: `setInterval(() => setN(n + 1), 1000)` in an effect with an empty
dependency array always sees the first `n`, so the counter stops at 1. The updater form fixes it. A context
provider whose value is a new object every render plus many consumers: every consumer re-renders on every
parent render. The fix is `useMemo` on the value, or splitting the context so fast-changing and slow-changing
values live apart. A race in an effect that fetches by an ID that changes quickly: the older, slower
response arrives last and overwrites the newer one; an `ignore` flag or `AbortController` in the cleanup
stops it.

</Level>

<Level name="Production level">

In production React problems are performance and correctness under real data: long lists that render
thousands of rows (virtualise them), contexts that re-render the whole app on each keystroke, effects that
fetch in waterfalls, and errors that blank the whole page. An error boundary around each route section
keeps one broken widget from taking the dashboard down, and reports the error with the component stack.
The React DevTools profiler shows which components rendered and why.

</Level>

<Level name="Mindset">

The habit is "render is a calculation, effects are an escape hatch." Before writing `useEffect`, I ask
whether the thing is derived from props and state (compute it), triggered by an event (put it in the
handler), or truly a synchronisation with something outside React (then an effect with cleanup).

</Level>

<Level name="System design">

Where state lives is the architecture of a frontend: local component state, lifted to a shared parent,
in context for app-wide concerns (theme, the signed-in user), in the URL for anything shareable (filters,
page, tab), and in a server-cache library for data from the API. Putting server data in global client state
is the most common design mistake; it duplicates the database with worse consistency.

</Level>

<Level name="Strategy">

I rebuild the dashboard twice: once with `useState` everywhere, once with a reducer and the URL holding the
filters, and compare which is easier to test and to explain. I work through the React docs' "You Might Not
Need an Effect" page and remove every effect in my code that it covers. Done when every remaining effect
has a cleanup and a one-line reason, and the profiler shows no component rendering on keystrokes it does
not use.

</Level>

</Levels>

#### Phase 2: Data fetching: loading, error, empty, stale and optimistic states

<Figure art={`
              fetch starts
   idle ------------------> loading
                              |  \\
                       200 + []  200 + data         error
                              |      \\               |
                            empty    success <--- retry
                                       |
                        time passes -> stale (show it, refetch in background)
                                       |
                        user edits  -> optimistic (show now, confirm or roll back)
`} caption="Six states, not two. Every list and detail view renders each of them deliberately." />

<Levels label="Phase 2, data fetching: loading, error, empty, stale and optimistic states">

<Level name="Beginner">

Every piece of data from the network goes through states: not started, loading, failed, loaded but empty,
and loaded with data. A component that only renders the last state shows a blank page while loading and
crashes on failure. The smallest correct version handles all of them.

```tsx
if (state.status === 'loading') return <p>Loading notes…</p>;
if (state.status === 'error') return <p role="alert">Could not load notes. <button onClick={retry}>Try again</button></p>;
if (state.data.length === 0) return <p>No notes yet. <a href="/notes/new">Write the first one</a>.</p>;
return <ul>{state.data.map((n) => <li key={n.id}>{n.title}</li>)}</ul>;
```

The common mistake is the empty state: an empty list renders an empty `ul`, and the user thinks it is
broken.

</Level>

<Level name="Intermediate">

In a real app a server-cache library (TanStack Query, SWR, or a framework loader) handles caching,
deduplication, retries and refetching. Stale-while-revalidate shows cached data instantly and refreshes in
the background. Optimistic updates show the user's change at once and roll back if the server rejects it.

```tsx
const { data, status, error, refetch } = useQuery({ queryKey: ['notes', page], queryFn: () => getNotes(page), staleTime: 30_000 });
const add = useMutation({
  mutationFn: createNote,
  onMutate: async (draft) => {
    await qc.cancelQueries({ queryKey: ['notes'] });
    const prev = qc.getQueryData<Note[]>(['notes', page]);
    qc.setQueryData<Note[]>(['notes', page], (old = []) => [{ ...draft, id: 'temp' }, ...old]);
    return { prev };
  },
  onError: (_e, _d, ctx) => qc.setQueryData(['notes', page], ctx?.prev),
  onSettled: () => qc.invalidateQueries({ queryKey: ['notes'] }),
});
```

The mistake is an optimistic update with no rollback: the server says no and the screen keeps lying.

</Level>

<Level name="Advanced">

Underneath, the choices are when to fetch and what counts as fresh. Fetching in a `useEffect` starts only
after the component renders and its JavaScript has loaded, which creates waterfalls (parent loads, then
child starts). Loading on the server or in a route loader starts every request in parallel before
rendering. Freshness is a policy: `staleTime` says how long data is trusted, refetch on window focus
catches changes made elsewhere. A loading indicator that appears instantly flickers on fast responses;
delaying it by around 200 milliseconds avoids the flash.

</Level>

<Level name="Edge cases">

A request that succeeds with a `500`-shaped body; a request that never ends (no timeout, so "Loading"
forever); a list that loads and the user's filter matches nothing (this is "no results", a different
message from "no notes yet"); an error on page 3 of a paginated list while pages 1 and 2 are on screen,
which should show an inline error, not replace the whole list.

</Level>

<Level name="Corner cases">

Two optimistic mutations in flight plus the first one failing: rolling back to the snapshot from before the
first also erases the second's optimistic change, which may still succeed. The fix is invalidating and
refetching on settle rather than trusting snapshots alone. Stale data plus a deleted resource: the cached
detail page shows a note that another tab deleted, the refetch returns 404, and the view must switch to a
"this note was deleted" state rather than an error.

</Level>

<Level name="Production level">

In production every state is a user experience and a metric. I track how often users see the error state
per route, how long the loading state lasts at p75, and whether retries succeed. I make retries
exponential with a cap and never retry non-idempotent mutations automatically. I test the slow states with
dev tools throttling and with a fault-injection flag on the server that delays or fails a percentage of
requests.

</Level>

<Level name="Mindset">

The habit is to design the unhappy states first. The happy state is the one I will build anyway; the five
others are where trust is won or lost, and they are what AI-generated UI most often leaves out.

</Level>

<Level name="System design">

The fetching layer is a cache of the server's truth with a freshness policy, which is the same problem as a
CDN or Redis cache. Query keys are cache keys; invalidation is the hard part in both places. Moving data
loading to the server or the route removes waterfalls and is often the single largest performance win.

</Level>

<Level name="Strategy">

For each data view I write a Storybook-style fixture or test for all six states and look at each one.
Done when every list and detail view has a deliberate loading, error, empty and success state, a mutation
that the server rejects rolls back visibly, and nothing shows "Loading" for more than the request's timeout.

</Level>

</Levels>

#### Phase 2: Forms: validation, errors, disabled states and submission feedback

<Flow
  caption="A form submission, end to end. The server check is the only one that counts; the client check is for speed."
  steps={["User types", "Client validates on blur", "Submit: disable double-submit, show progress", "Server validates again", "Field errors mapped back to inputs", "Focus the first error", "Success message and next step"]}
/>

<Levels label="Phase 2, forms: validation, errors, disabled states and submission feedback">

<Level name="Beginner">

A form collects input and sends it. Each input needs a visible label, the right `type` (`email`,
`password`, `number`), and a clear error message next to it when something is wrong. HTML can already
validate basics with `required`, `type="email"` and `minlength`.

```html
<form method="post" action="/signup">
  <label for="email">Email</label>
  <input id="email" name="email" type="email" autocomplete="email" required>
  <label for="pw">Password</label>
  <input id="pw" name="password" type="password" autocomplete="new-password" minlength="12" required>
  <button>Create account</button>
</form>
```

The common mistake is validating only in the browser. Anyone can send a request without the form, so the
server must validate everything again.

</Level>

<Level name="Intermediate">

A real form validates on blur (not on every keystroke, which shouts at a user who has not finished
typing), shows errors next to fields and in a summary, prevents double submission, and maps server errors
back to the field they belong to. One schema shared by client and server keeps the rules identical.

```tsx
const Signup = z.object({ email: z.string().email('Enter a valid email'), password: z.string().min(12, 'At least 12 characters') });

async function onSubmit(e: React.FormEvent<HTMLFormElement>) {
  e.preventDefault();
  if (pending) return;
  const parsed = Signup.safeParse(Object.fromEntries(new FormData(e.currentTarget)));
  if (!parsed.success) return setErrors(parsed.error.flatten().fieldErrors);
  setPending(true);
  const res = await fetch('/api/signup', { method: 'POST', body: JSON.stringify(parsed.data), headers: { 'content-type': 'application/json' } });
  setPending(false);
  if (res.status === 422) setErrors((await res.json()).fieldErrors);
}
```

</Level>

<Level name="Advanced">

The exact accessibility rules: each error is tied to its input with `aria-describedby`, the input gets
`aria-invalid="true"`, and after a failed submit focus moves to the first invalid field (or to an error
summary with links to each field). `autocomplete` tokens let password managers and autofill work, which is
both accessibility and conversion. A form that works with JavaScript off (a plain POST that re-renders with
errors) is progressive enhancement: the JS version improves it but does not replace it.

```html
<input id="email" aria-invalid="true" aria-describedby="email-err">
<p id="email-err">Enter a valid email, like name@example.com</p>
```

</Level>

<Level name="Edge cases">

An email with a plus sign or a long top-level domain rejected by a homemade regex; a name field that
rejects apostrophes or non-Latin characters; leading and trailing spaces that make "a@x.io " fail a
uniqueness check; a password field with `maxlength` that silently truncates a pasted passphrase; a number
input where the user types "1e3". Each needs a decision: normalise (trim, lowercase email), or accept.

</Level>

<Level name="Corner cases">

The submit button disabled while pending plus a network error: the button never re-enables and the user is
stuck. The fix is `finally { setPending(false) }`. Client validation passes, server validation fails on a
rule the client does not know (email already taken): the error arrives after the user moved on, so it must
be shown at the field and announced. Browser autofill plus a React-controlled input that only updates on
`onChange`: some browsers fill the field without firing the event in the way React expects, and the form
submits empty values; reading `FormData` at submit avoids that.

</Level>

<Level name="Production level">

In production forms are where users give up. I measure field-level error rates and abandonment, keep the
message helpful ("At least 12 characters" beats "Invalid"), make the server idempotent for submissions (a
retried POST must not create two accounts, which Phase 3 solves with idempotency keys), and never clear the
user's input on an error.

</Level>

<Level name="Mindset">

The habit is to treat a form as a conversation with a person who will make every possible typo. The error
message is my side of the conversation, and the server is the only side that can be trusted to enforce
the rules.

</Level>

<Level name="System design">

Validation sits at three layers: the browser for speed, the API for correctness, the database (constraints)
for the last line of defence. A shared schema package spans the first two; constraints in Phase 4 cover the
third. The 422 response with field errors is part of the API contract.

</Level>

<Level name="Strategy">

I build the sign-up and note forms as plain HTML POST forms first, then enhance them, and test each with
JavaScript disabled, keyboard only, a screen reader, and a server that rejects the input. Done when every
field error is announced and focused, double-clicking submit creates one record, and the form works without
JavaScript.

</Level>

</Levels>

#### Phase 2: Routing, code splitting and the cost of client-side JavaScript

<Figure art={`
  bytes over the wire  ->  parse  ->  compile  ->  execute  ->  hydrate  ->  interactive
     (network)             (CPU)       (CPU)        (CPU)        (CPU)
  100 KB of gzipped JS is not 100 KB of image:
  the image decodes once; the JS blocks the main thread on a slow phone
`} caption="JavaScript costs twice: once to download, and again in CPU time before the page responds to a tap." />

<Levels label="Phase 2, routing, code splitting and the cost of client-side JavaScript">

<Level name="Beginner">

Routing maps a URL to a page. In a multi-page app, the server sends a new HTML page for each URL. In a
single-page app, JavaScript intercepts link clicks, changes the URL with the History API and renders the
new page without a reload. Code splitting means the browser downloads only the JavaScript a route needs,
instead of one bundle for the whole app.

```tsx
const Settings = lazy(() => import('./routes/Settings'));
<Suspense fallback={<p>Loading settings…</p>}><Settings /></Suspense>
```

The common mistake is a single bundle that ships the chart library and the markdown editor to a sign-in
page that uses neither.

</Level>

<Level name="Intermediate">

A real app splits by route and by heavy component, and keeps the URL as the source of truth for anything a
user may want to share or reload: the page, the filters, the open tab. Links remain real `a` elements with
`href`, so middle-click, copy link and no-JS all work.

```ts
const params = new URLSearchParams(location.search);
const page = Number(params.get('page') ?? '1');
// update: history.pushState(null, '', `?page=${page + 1}`)
```

I check the cost with the bundler's report (`vite build` prints chunk sizes; `rollup-plugin-visualizer`
draws them) and set a budget per route.

</Level>

<Level name="Advanced">

Underneath, client JavaScript costs network bytes and main-thread time: parsing, compiling and executing
scale with code size, and on a mid-range phone the CPU cost often exceeds the download. Hydration replays
the server-rendered page's components on the client to attach handlers, which costs as much as rendering
it. Islands (as in Astro, which this site uses) hydrate only the interactive parts, and server components
render on the server with zero client code. Dynamic `import()` creates a separate chunk that is fetched on
demand; preloading it on hover hides the latency.

```text
dist/assets/index-3f2a.js        142.31 kB │ gzip: 46.02 kB
dist/assets/Settings-9c1d.js      18.77 kB │ gzip:  6.40 kB
```

</Level>

<Level name="Edge cases">

A deep link opened directly on a single-page app served by a static host returns 404, because the server
has no file at that path; the host needs a fallback to `index.html`, or the app needs prerendering. The
back button after a client-side filter change must restore the filter, which only works if the filter is
in the URL. A lazy chunk that fails to load (a flaky network or a deploy that deleted the old chunk) throws
`Failed to fetch dynamically imported module`.

</Level>

<Level name="Corner cases">

A deploy plus a user with the old app open: the old app requests `Settings-9c1d.js`, which the new deploy
removed, and the route crashes. The fixes are keeping old chunks for a while, or catching the import error
and doing a full reload once. A client-side route change plus a page title that never updates: the tab,
history and screen reader all show the previous page's title. Every route sets `document.title` and moves
focus.

</Level>

<Level name="Production level">

In production I set a JavaScript budget per route (for example, under 100 KB gzipped for the dashboard)
and fail CI when a change exceeds it. I prefer server rendering for content pages, islands for
interactive widgets, and a single-page app only for the authenticated app area where it pays off. I watch
for dependency creep: one date library can double a bundle.

</Level>

<Level name="Mindset">

The habit is to treat every kilobyte of client JavaScript as a cost the user pays on their device. The
question is not "can I add this library?" but "what does a user on a slow phone pay for it, and on which
page?"

</Level>

<Level name="System design">

Rendering strategy is architecture: static generation, server rendering, streaming, islands, or a client
app. Each moves work between build time, the server and the device, and each changes caching, SEO and
failure behaviour. The AI chat surface is a good island: one interactive region in an otherwise static
page.

</Level>

<Level name="Strategy">

I build the same dashboard as a client-only app and as server-rendered pages with one island, and compare
bundle size, time to interactive on a throttled phone profile and the Lighthouse score. Done when every
route has a measured budget enforced in CI and every shareable state lives in the URL.

</Level>

</Levels>

#### Phase 2: Performance: Core Web Vitals, images, fonts, bundle size and hydration

<Compare
  left="Metric"
  right="What moves it"
  caption="The three Core Web Vitals and the fixes that matter most for each. Good thresholds are at the 75th percentile of real users."
  rows={[
    ["LCP, largest contentful paint, good under 2.5 s", "fast server response, preload the hero image or font, no render-blocking JS"],
    ["INP, interaction to next paint, good under 200 ms", "less main-thread work, split long tasks, smaller hydration"],
    ["CLS, cumulative layout shift, good under 0.1", "width and height on images, reserved space, font metric overrides"],
  ]}
/>

<Levels label="Phase 2, performance: Core Web Vitals, images, fonts, bundle size and hydration">

<Level name="Beginner">

Performance is how fast the page appears, how fast it responds, and how stable it is while loading. Google's
Core Web Vitals measure these three: LCP (when the main content appears), INP (how quickly the page
responds to a tap or key) and CLS (how much the layout jumps). Lighthouse in Chrome dev tools measures them
in a lab run.

```html
<img src="/hero.avif" width="1200" height="630" alt="Dashboard with three notes" fetchpriority="high">
```

The common mistake is an image without `width` and `height`: the browser does not know its size until it
downloads, so the text below jumps down, which is layout shift.

</Level>

<Level name="Intermediate">

A real page needs each resource handled on purpose. Images: modern formats (AVIF, WebP), `srcset` for
sizes, `loading="lazy"` below the fold, never lazy for the LCP image. Fonts: self-hosted, `woff2`, a
subset, `font-display: swap`, and the main font preloaded. JavaScript: split, deferred, and measured.

```html
<link rel="preload" href="/fonts/plex-sans-400.woff2" as="font" type="font/woff2" crossorigin>
<img srcset="/n-480.avif 480w, /n-960.avif 960w" sizes="(max-width: 600px) 480px, 960px" src="/n-960.avif" alt="" loading="lazy" width="960" height="540">
```

The mistake is optimising by guessing. Lighthouse's opportunities list and the Performance panel show what
actually blocks.

</Level>

<Level name="Advanced">

Underneath is the critical rendering path: HTML is parsed, CSS blocks rendering until it is loaded,
synchronous scripts block parsing, and the LCP element can only paint once its resource and the styles are
ready. INP measures the delay, processing and presentation time of interactions; any task over 50 ms on the
main thread is a "long task" that delays input. Splitting work with `await scheduler.yield()` (or a
`setTimeout` of 0) lets the browser respond between chunks. Font swaps cause shift unless the fallback font
is adjusted with `size-adjust` and `ascent-override` to match the web font's metrics.

```text
Lighthouse: Largest Contentful Paint element  ->  img.hero   4.1 s
  Resource load delay 2.2 s (discovered late: set in CSS background)
```

</Level>

<Level name="Edge cases">

A lab score of 100 on my laptop and a poor field score from real users on slow phones: lab and field data
differ, and the field (Chrome UX Report, or my own `web-vitals` beacon) is what users feel. A page that is
fast on first visit and slow on the second because a service worker serves a stale big bundle. A cookie
banner that appears late and pushes content down counts as layout shift. A carousel's LCP element changes as
slides rotate.

</Level>

<Level name="Corner cases">

A streaming AI answer plus layout shift: each new line pushes the content below it, and if the user is
scrolled to read it, the page jumps. Shifts within 500 ms of a user input are excluded from CLS, but a
stream that keeps growing seconds later is not. The fix is anchoring the scroll and growing the message in a
container that does not move other content. An expensive hydration plus an early tap: the user taps a button
before hydration finishes and nothing happens, which shows up as a poor INP.

</Level>

<Level name="Production level">

In production performance is a budget enforced in CI (Lighthouse CI with assertions) and a field metric
watched after each release. I send Web Vitals from real users with the `web-vitals` library to my analytics,
broken down by route and device class, and alert on a regression of the 75th percentile.

```ts
import { onLCP, onINP, onCLS } from 'web-vitals';
[onLCP, onINP, onCLS].forEach((f) => f((m) => navigator.sendBeacon('/vitals', JSON.stringify({ name: m.name, value: m.value, path: location.pathname }))));
```

</Level>

<Level name="Mindset">

The habit is "measure, change one thing, measure again." Performance folklore is everywhere; the profiler
shows which of it applies to my page today.

</Level>

<Level name="System design">

Performance is decided by architecture more than by tweaks: where rendering happens, how much JavaScript
ships, whether the server responds from a cache, where the CDN is. The server's time to first byte is often
the biggest part of LCP, which connects this phase to the database work in Phase 4.

</Level>

<Level name="Strategy">

I take the slowest core page, record a Performance trace on a throttled mobile profile, list every cost
in it, and fix the top three one at a time with before-and-after numbers in the study log. Done when the
gate's Lighthouse 95+ holds on every core page, CLS is zero on load, and field data is being collected.

</Level>

</Levels>

#### Phase 2: SEO: titles, descriptions, canonicals, structured data, sitemaps and server-rendered content

<Flow
  caption="How a page gets from my server into a search result"
  steps={["Crawler finds the URL (link or sitemap)", "Fetches HTML, checks robots and status", "Reads title, canonical, content", "Renders JS later, if at all", "Indexes the canonical version", "Shows title and description in results"]}
/>

<Levels label="Phase 2, SEO: titles, descriptions, canonicals, structured data, sitemaps and server-rendered content">

<Level name="Beginner">

SEO is making pages that search engines can find, understand and show well. The basics: each page has a
unique `title` and `meta description`, the content is in the HTML the server sends, links are real `a`
elements, and there is a sitemap listing the public pages.

```html
<title>Notes on React effects — Sanjay</title>
<meta name="description" content="When useEffect is the wrong tool, with four examples and the fix for each.">
<link rel="canonical" href="https://snjy-kumar.github.io/sanjay/react/03/">
```

The common mistake is the same title on every page ("My App"), which makes every result look identical.

</Level>

<Level name="Intermediate">

In a real site each page type gets metadata from its data: notes get their title and summary, list pages
get a descriptive title and a canonical that points to page 1 or to themselves. Structured data (JSON-LD)
describes the page type, such as an article with its date and author. Open Graph tags control the share
card. This blog's build does exactly this, and its check script fails on duplicate titles.

```html
<script type="application/ld+json">
{"@context":"https://schema.org","@type":"Article","headline":"Notes on React effects","datePublished":"2026-10-21","author":{"@type":"Person","name":"Sanjay Kumar"}}
</script>
```

</Level>

<Level name="Advanced">

Underneath, the canonical URL tells search engines which of several URLs with the same content is the real
one (with and without a trailing slash, with tracking parameters). `robots` meta and `robots.txt` differ:
`robots.txt` stops crawling, `noindex` stops indexing, and a page blocked by `robots.txt` cannot be seen to
be `noindex`. JavaScript-rendered content may be indexed, but later and less reliably than server HTML, so
content that matters is server-rendered. Status codes matter: a missing page must return 404, not a 200
"not found" page (a soft 404).

</Level>

<Level name="Edge cases">

A page with `noindex` that is also in the sitemap sends contradictory signals. A canonical that points to a
URL that redirects. A description longer than the display length gets cut mid-sentence. Pagination with
`?page=2` that canonicalises to page 1 hides page 2's items from search. The authenticated app area should
not be indexed at all: `noindex`, and no links to it from the sitemap.

</Level>

<Level name="Corner cases">

A preview deploy plus no `noindex`: the preview URL gets indexed and competes with production. Preview
environments send `X-Robots-Tag: noindex` from the platform. A base path (this site lives under `/sanjay`)
plus absolute links written without it: the sitemap and canonicals point to URLs that 404. That is why this
repository builds every link with `withBase`.

</Level>

<Level name="Production level">

In production SEO is checked like any other contract: the build verifies one `h1`, a unique title and
description, a canonical and a sitemap entry per page (this blog's `npm run check` does it). After launch,
Google Search Console shows which pages are indexed and why others are not, and I read it monthly.

</Level>

<Level name="Mindset">

The habit is to see search engines as one more client that reads HTML without a mouse, a lot like a
screen reader. Semantic, server-rendered, well-titled pages serve both.

</Level>

<Level name="System design">

SEO constrains rendering strategy and URL design: stable, readable URLs; one canonical per resource;
server-rendered public content; and a clean split between the public marketing and content site and the
private application. Changing URLs later needs redirects, which is a migration like any database change.

</Level>

<Level name="Strategy">

I audit five pages of this blog and five of my app with Lighthouse's SEO section and by reading the raw
HTML from `curl`, then fix every gap. Done when every public page passes the build check, Lighthouse SEO is
95 or more, and the app area is `noindex`.

</Level>

</Levels>

#### Phase 2: Design systems: tokens, primitives, variants and documentation

<Levels label="Phase 2, design systems: tokens, primitives, variants and documentation">

<Level name="Beginner">

A design system is the shared set of decisions and components a product is built from. Tokens are the
smallest decisions: colours, spacing steps, type sizes. Primitives are layout building blocks. Components
combine them into reusable pieces with a documented API. The point is that "the primary button" is one

```css
:root { --ink: #111; --muted: #6b6b6b; --line: #d4d4d4; --space-1: 0.25rem; --space-2: 0.5rem; --space-4: 1rem; --font: 'IBM Plex Sans', sans-serif; }
.btn { font: 500 1rem/1.2 var(--font); padding: var(--space-2) var(--space-4); border: 1px solid var(--ink); }
```

The common mistake is a component library with no tokens, where every component picks its own grey and
spacing, so the product drifts.

</Level>

<Level name="Intermediate">

Components get variants (primary, secondary, danger; small, medium) through a typed prop, not through
callers passing class names. The API is small and hard to misuse. *Refactoring UI* is the reference for the
visual decisions (hierarchy, spacing, contrast), *Inclusive Components* for the accessible behaviour.

```tsx
type ButtonProps = React.ButtonHTMLAttributes<HTMLButtonElement> & { variant?: 'primary' | 'secondary' | 'danger'; size?: 'sm' | 'md' };
export function Button({ variant = 'primary', size = 'md', type = 'button', ...rest }: ButtonProps) {
  return <button type={type} className={`btn btn-${variant} btn-${size}`} {...rest} />;
}
```

Defaulting `type` to `button` here prevents the accidental-submit bug from the semantic HTML topic, for
every caller at once.

</Level>

<Level name="Advanced">

The design questions underneath are API design questions. Composition (a `Dialog` with `Dialog.Title` and
`Dialog.Actions` children) scales better than a component with twenty props. Polymorphism (an `as` prop
that renders a `Button` as a link) needs care: a link styled as a button must still behave as a link. Ref
forwarding lets callers focus the underlying element. Variants should come from a closed set of tokens, so
a reviewer can say no to a new grey.

</Level>

<Level name="Edge cases">

A button label that is very long, in another language, or wraps to two lines; an icon-only variant that
needs an accessible name enforced by its type; a `disabled` and `loading` button at once; a dark-mode token
missing for one component. Each is a test or a story in the documentation.

</Level>

<Level name="Corner cases">

A component used inside another design system's container (a third-party widget, a markdown block) that
resets `font` or `box-sizing`: tokens defined on `:root` still apply, but primitives that assume
`border-box` break. Two versions of the design system loaded by two parts of the app: two copies of React
context, so the theme provider of one is invisible to the other's components.

</Level>

<Level name="Production level">

In production the design system needs versioning, a changelog and visual regression tests, because a
change to `Button` changes every page. I document each component with its props, its states, its keyboard
behaviour and a do and a don't, and I test the gate's component with unit tests and an axe check.

</Level>

<Level name="Mindset">

The habit is "decide once." Every repeated visual or behavioural decision is a candidate for a token or a
component, and every exception is a decision someone should make on purpose.

</Level>

<Level name="System design">

A design system is a product with internal users. It sits between design and engineering, and its API
stability matters like any library's. For this blog the system is small and strict: monochrome tokens, IBM
Plex, a Reference layout; that strictness is what lets every new page look like it belongs.

</Level>

<Level name="Strategy">

I extract tokens from the existing app, then build five components (Button, Field, Dialog, Table,
EmptyState) with documented APIs, stories for every state and tests. Done when the gate's documented,
tested component exists and no page in the app uses a raw colour or spacing value.

</Level>

</Levels>

#### Phase 2: Testing: component tests, accessibility checks and end-to-end flows

<Figure art={`
           /\\        end-to-end (Playwright): a few critical journeys
          /  \\       real browser, real server, real database
         /----\\
        /      \\     component tests (Testing Library + Vitest)
       /        \\    behaviour through roles and labels
      /----------\\
     /            \\  unit tests: pure functions, reducers, schemas
    /--------------\\
  plus axe in every layer that renders HTML
`} caption="More fast tests at the bottom, a few slow, high-value ones at the top. The shape is a heuristic, not a law." />

<Levels label="Phase 2, testing: component tests, accessibility checks and end-to-end flows">

<Level name="Beginner">

Frontend tests check that the UI behaves as a user expects. Unit tests check pure logic (a reducer, a
formatter). Component tests render a component and interact with it the way a user would. End-to-end tests
drive a real browser through a full flow. Accessibility checks scan rendered HTML for violations.

```ts
test('shows an error when the email is invalid', async () => {
  render(<SignupForm />);
  await userEvent.type(screen.getByLabelText('Email'), 'nope');
  await userEvent.click(screen.getByRole('button', { name: 'Create account' }));
  expect(screen.getByText('Enter a valid email')).toBeVisible();
});
```

The common mistake is testing implementation (a state variable's value, a CSS class) instead of what the
user sees. Those tests break on every refactor and catch nothing.

</Level>

<Level name="Intermediate">

End-to-end tests cover the critical journeys: sign up, sign in, create a note, use the chat. They run
against a real server and a seeded database, and they use role-based locators.

```ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('a user can sign in and add a note', async ({ page }) => {
  await page.goto('/signin');
  await page.getByLabel('Email').fill('demo@example.com');
  await page.getByLabel('Password').fill('correct horse battery');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page.getByRole('heading', { level: 1, name: 'Dashboard' })).toBeVisible();
  const a11y = await new AxeBuilder({ page }).analyze();
  expect(a11y.violations).toEqual([]);
});
```

</Level>

<Level name="Advanced">

Underneath, flaky tests come from timing. Playwright's assertions retry until a timeout, so
`await expect(locator).toBeVisible()` waits for the element; a bare `page.waitForTimeout(1000)` guesses.
Testing Library's `findBy` queries wait too. Network can be mocked at the browser level with
`page.route`, which is how I test the error and slow states deterministically. Tests should not share state:
each starts from a known database seed or a fresh user.

```ts
await page.route('**/api/notes', (r) => r.fulfill({ status: 500, body: '{}' }));
await expect(page.getByRole('alert')).toHaveText(/Could not load notes/);
```

</Level>

<Level name="Edge cases">

A test that passes alone and fails in the suite because an earlier test left a note behind; a test that
depends on the current date and fails at midnight or across a time zone (fix the clock with
`page.clock`); an animation that makes a click land on the wrong element; a test that uses text that the
copywriter changes next week.

</Level>

<Level name="Corner cases">

Mocking the network in a component test plus a changed API: the test passes against the old mock and
production breaks. A mock that no longer matches reality is a lie, which is the phrase the plan uses in
Phase 1. The fix is to validate mocks with the same schema the client uses, and to keep at least one
end-to-end test against the real API. Parallel end-to-end workers plus a shared test user: two workers
edit the same data and fail randomly; each worker gets its own user.

</Level>

<Level name="Production level">

In production tests are a gate. The CI pipeline runs unit and component tests on every push, Playwright on
every pull request with traces kept on failure, and Lighthouse CI on the core pages. A flaky test is fixed
or quarantined within a day, because a suite people rerun until green tests nothing.

</Level>

<Level name="Mindset">

The habit is "test what I would check by hand before a release." If I would click through sign-in before
shipping, a test should click through sign-in on every change, so I never have to remember.

</Level>

<Level name="System design">

The test suite is an executable specification of the product's critical paths. Its layers mirror the
architecture: pure logic, components, the integrated system. Seed data and test environments are part of
the system, and Phase 5's preview environments are where end-to-end tests run against each change.

</Level>

<Level name="Strategy">

I write the Playwright tests for the three critical flows first, then component tests for every state of
the data views and forms, then unit tests for reducers and schemas. Done when the critical flows run in CI
on every pull request, a deliberately broken label fails the axe check, and the suite has had no flaky
failure for two weeks.

</Level>

</Levels>

#### Phase 2: the build, a multi-page app with an AI chat surface

<Figure art={`
  browser                       server                      model provider
    | POST /api/chat {msg} ----> | check session, rate limit |
    |                            | build prompt ------------>|
    | <-- 200 text/event-stream  | <---- token, token, token |
    | render tokens as they come |                           |
    | [Stop] -> abort signal --> | abort upstream request -->|
    | <-- event: done            |                           |
    error at any step -> message with retry, input kept
`} caption="The chat surface's request. The frontend's job is the stream, the stop button and every failure state." />

<Levels label="Phase 2, the build: a multi-page app with an AI chat surface">

<Level name="Beginner">

The build is a multi-page app on top of the Phase 0 baseline: sign-in, a dashboard, a form with
validation, a list with pagination, and an AI chat surface. The chat is the new part. The smallest working
version sends the user's message to my server, which calls a model and returns the full answer.

```ts
const res = await fetch('/api/chat', { method: 'POST', headers: { 'content-type': 'application/json' }, body: JSON.stringify({ message }) });
const { answer } = await res.json();
```

The common mistake is calling the model provider directly from the browser with the API key in client
code. Anyone can read the key in the bundle; the call must go through my server.

</Level>

<Level name="Intermediate">

The real version streams. The server returns `text/event-stream` and forwards tokens as they arrive; the
client reads the stream and appends text, with a Stop button that aborts.

```ts
const ctrl = new AbortController();
const res = await fetch('/api/chat', { method: 'POST', body: JSON.stringify({ message }), signal: ctrl.signal, headers: { 'content-type': 'application/json' } });
const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader();
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  for (const line of value.split('\n')) if (line.startsWith('data: ')) append(line.slice(6));
}
// Stop button: ctrl.abort()
```

The list uses cursor pagination from the API; the form uses the shared schema; every view has its four
states.

</Level>

<Level name="Advanced">

The exact rules for streams: a chunk from `read()` is not a line, so an event can be split across two
chunks, and a correct parser keeps a buffer and splits on the blank line that ends each server-sent event.
Aborting the fetch closes the connection; the server must notice (`req.on('close')`) and abort its upstream
model call, or I keep paying for tokens nobody reads. Markdown in the answer is rendered with a sanitiser,
because model output is untrusted input (Phase 6).

```ts
let buf = '';
buf += value; const events = buf.split('\n\n'); buf = events.pop() ?? '';
for (const ev of events) handle(ev);
```

</Level>

<Level name="Edge cases">

An empty message (disable send, or show an inline hint); a very long message (limit and say so); the
model returns nothing; the stream ends without a `done` event (connection dropped); the user presses Stop
before the first token; the rate limit returns 429 (show "Too many requests, try again in 30 seconds" from
the `Retry-After` header).

</Level>

<Level name="Corner cases">

The user sends a second message while the first is still streaming: either queue it or abort the first, but
never interleave two streams into one bubble. The user navigates away mid-stream: the component unmounts,
the abort must fire in cleanup, and no state update must run after unmount. A screen-reader user and a
stream (covered in the accessibility topic): announce once when done, mark the message busy while it
streams.

</Level>

<Level name="Production level">

For real users the chat needs: a visible "AI-generated" label, the input kept on any error, a retry that
resends the same message, a cost guard on the server (a token limit per request), and a non-AI fallback
when the provider is down ("The assistant is unavailable; here are your recent notes"). Playwright tests
cover streaming, stop, error and empty, with the model mocked at the server boundary.

</Level>

<Level name="Mindset">

The habit is to treat the model as a slow, unreliable, expensive network dependency, because that is what
it is from the frontend's point of view. Everything I learned about loading and error states applies, plus
streaming and cancellation.

</Level>

<Level name="System design">

The chat surface is an island in a server-rendered page, it talks only to my API, and my API owns the key,
the rate limit, the prompt and the cost. That split is the plan's premise in miniature: the model is a
component behind my boundary, not the architecture.

</Level>

<Level name="Strategy">

I build the app page by page, finishing each with its states, keyboard pass and tests before moving on,
and leave the chat for last so it inherits every pattern. Done when the gate passes: keyboard-only main
flow, Lighthouse 95+ on core pages, zero layout shift, a documented and tested design-system component,
and a written list of every network request each page makes.

</Level>

</Levels>
