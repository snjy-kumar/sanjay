learn what the runtime is doing when the syntax succeeds. The primary book is *Eloquent JavaScript*
or *You Don't Know JS Yet*, with JavaScript.info and the TypeScript Handbook as the free references and
*Refactoring* for depth. The build is a CLI tool and an HTTP server with no framework, and the gate asks
for a router, a JSON parser and a rate limiter written from a blank file.

Eleven topics in four weeks is about three a week. Each one gets the same cycle: read the chapter or
the reference page, predict what a small program prints, run it, explain the difference, then use the
idea in the server. No AI in the first pass on any topic; afterwards I ask for a review and log what it
caught that I missed.

#### Phase 1: values, types, scope, lifetime and mutation

<Figure art={`
  stack (per call)            heap (shared, garbage collected)
  +----------------+          +---------------------------+
  | n      = 3     |          |  { tags: ['a','b'] }  <---+---- a
  | a  ----------- +--------->|                           |
  | b  ----------- +--------->|   (same object)           |
  +----------------+          +---------------------------+
  primitives are copied        objects are shared by reference
`} caption="Primitives live as values; objects live on the heap and variables hold references to them, so two names can point at the same object." />

<Levels label="Phase 1, values, types, scope, lifetime and mutation">

<Level name="Beginner">

JavaScript has seven primitive types (string, number, bigint, boolean, undefined, null, symbol) and
objects. Primitives are immutable values; objects are mutable and shared by reference. `const` stops
the name from being reassigned; it does not freeze the object.

```js
const a = { tags: ['x'] };
const b = a;
b.tags.push('y');
console.log(a.tags); // [ 'x', 'y' ]
```

Common mistake: thinking `const` means "cannot change". Fix: `const` is about the binding;
`Object.freeze` (shallow) or never mutating is about the value.

</Level>

<Level name="Intermediate">

Scope is where a name is visible; lifetime is how long the value stays reachable. `let` and `const`
are block-scoped; `var` is function-scoped and hoisted. A value lives as long as something references
it, which is why closures and caches extend lifetimes.

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));  // 3 3 3
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j));  // 0 1 2
```

`let` creates a fresh binding per loop iteration; `var` has one binding for the whole function. In
real code that shows up as every click handler reporting the last item.

</Level>

<Level name="Advanced">

The exact rules: `typeof null` is `'object'` (a historical bug kept for compatibility). Numbers are
IEEE 754 doubles, so integers are exact only up to `Number.MAX_SAFE_INTEGER` (2 to the 53 minus 1).
Equality: `===` compares type and value, except `NaN !== NaN` and `+0 === -0`; `Object.is` fixes both.
`let` has a temporal dead zone: reading it before the declaration runs throws
`ReferenceError: Cannot access 'x' before initialization`.

TypeScript adds a static layer: `string | undefined` makes the absence visible, and `readonly`
catches mutation at compile time but not at run time.

```ts
const xs: readonly number[] = [1, 2];
// xs.push(3);  // error TS2339: Property 'push' does not exist on type 'readonly number[]'
(xs as number[]).push(3); // compiles, mutates: the type was a promise, not a lock
```

</Level>

<Level name="Edge cases">

- `0.1 + 0.2 === 0.3` is `false` (it is `0.30000000000000004`). Money goes in integer cents or a
  decimal library.
- `9007199254740993` prints as `9007199254740992`: past the safe integer, IDs from a database must be
  strings or `bigint`.
- `[] == false` is `true` and `[] ? 1 : 2` is `1`: loose equality and truthiness disagree.

</Level>

<Level name="Corner cases">

Spread copies one level: `{ ...state }` creates a new outer object but the nested arrays are still
shared, so a "copy then mutate" updates the original's nested data. Shallow copy plus nested mutation is
exactly the React stale-state bug of phase 2. `structuredClone` deep-copies but throws
`DataCloneError` on functions and silently drops class prototypes.

</Level>

<Level name="Production level">

Mutation shared across requests is a production bug: a module-level object used as a per-request
scratch space leaks one user's data into another's response. Large IDs that pass through `JSON.parse`
lose precision silently. Memory leaks in a long-running Node process are lifetimes nobody ended: a
growing `Map` cache with no eviction.

</Level>

<Level name="Mindset">

For every value, ask three questions: who else holds a reference to it, who is allowed to change it,
and when does it stop being reachable.

</Level>

<Level name="System design">

Request-scoped, process-scoped and persisted state are lifetimes at system scale. Anything that must
survive a restart belongs in Postgres; anything per-request lives in a function call; anything shared
across requests in memory needs a size limit and an eviction rule.

</Level>

<Level name="Strategy">

Write twenty predict-then-run snippets covering equality, copying, closures in loops, number precision
and the dead zone. Done when I predict at least eighteen correctly and can explain the two I missed.

</Level>

</Levels>

#### Phase 1: functions, closures, recursion and the call stack

<Figure art={`
  call stack while fact(3) runs        after a closure is made
  +----------------+                   counter() returns inc
  | fact(1)  n=1   |  <- top           +-------------+
  | fact(2)  n=2   |                   | inc  ------ +---> env { n: 2 }
  | fact(3)  n=3   |                   +-------------+     kept alive
  | main           |                   frame of counter() is gone,
  +----------------+                   its variable n is not
`} caption="Each call pushes a frame; a closure keeps the variables it uses alive after its frame is popped." />

<Levels label="Phase 1, functions, closures, recursion and the call stack">

<Level name="Beginner">

A function is a value: it can be stored, passed and returned. A closure is a function together with
the variables it captured from where it was defined. Recursion is a function calling itself on a
smaller input until a base case stops it.

```js
function counter() {
  let n = 0;
  return () => ++n;
}
const inc = counter();
inc(); inc();
console.log(inc()); // 3
```

Common mistake: a recursive function without a reachable base case. The error is `RangeError: Maximum
call stack size exceeded`. Fix: write the base case first, and test the smallest input.

</Level>

<Level name="Intermediate">

Closures are how JavaScript does private state, memoisation, middleware and configuration. A
middleware chain is a list of functions each closing over `next`.

```js
const memo = (f) => { const seen = new Map(); return (x) => seen.has(x) ? seen.get(x) : (seen.set(x, f(x)), seen.get(x)); };
const slowSquare = (x) => { for (let i = 0; i < 1e7; i++); return x * x; };
const fast = memo(slowSquare);
fast(9); fast(9); // second call is instant
```

`this` is not captured by a normal function, only by arrow functions. Passing `obj.method` as a
callback loses `this`, and the error is `TypeError: Cannot read properties of undefined`.

</Level>

<Level name="Advanced">

Each call creates an execution context with its own environment record, linked to the environment
where the function was defined (lexical scoping). The stack holds frames; V8's default stack allows
roughly ten thousand frames for a simple function, depending on frame size. JavaScript engines in
practice do not do tail-call optimisation (only Safari implemented it), so deep recursion must become
a loop with an explicit stack.

```js
function depth(node) {              // iterative tree depth, no stack overflow
  let max = 0; const stack = [[node, 1]];
  while (stack.length) {
    const [n, d] = stack.pop(); max = Math.max(max, d);
    for (const c of n.children ?? []) stack.push([c, d + 1]);
  }
  return max;
}
```

</Level>

<Level name="Edge cases">

- A recursive JSON walker on a 100,000-deep nested array overflows the stack.
- A default parameter is evaluated per call: `f(x = [])` gives a fresh array each time, unlike Python.
- `arguments` does not exist in arrow functions.

</Level>

<Level name="Corner cases">

A closure captured in a long-lived event listener holds a reference to a large object, and removing the
DOM node does not free it because the listener is still registered elsewhere. Closure plus lifetime plus
a global registry: a memory leak. Another: recursion inside an `async` function does not grow the
synchronous stack across `await`, but it does keep every pending promise alive.

</Level>

<Level name="Production level">

Stack traces are the call stack at the moment of the error, so readable function names matter;
anonymous arrow functions show as `<anonymous>`. In a server, a closure-based cache created per request
is useless, and one created per process needs bounds.

</Level>

<Level name="Mindset">

When reading any function, find what it closes over. Hidden captured state is where surprising
behaviour lives.

</Level>

<Level name="System design">

Middleware, plugin systems and dependency injection are closures at architecture scale: a function
configured once, called many times. My router library in this phase's build is exactly that.

</Level>

<Level name="Strategy">

Implement `memo`, `once`, `debounce` and a middleware `compose` from scratch, then convert one recursive
tree walk to an iterative one. Done when all five pass tests including a 100,000-deep input for the
iterative walk.

</Level>

</Levels>

#### Phase 1: the event loop, promises, async/await and concurrency without threads

<Figure art={`
   +-------------------+
   |  call stack       |  runs one task to completion
   +---------+---------+
             | empty?
             v
   +-------------------+    drain ALL of these first
   |  microtasks       |    promise callbacks, queueMicrotask
   +---------+---------+
             v
   +-------------------+    then ONE of these
   |  macrotasks       |    timers, I/O callbacks, setImmediate
   +-------------------+
             ^
     libuv thread pool and the OS finish I/O and queue callbacks
`} caption="The event loop: run the current task, drain every microtask, then take the next macrotask. I/O happens outside the JavaScript thread." />

<Levels label="Phase 1, the event loop, promises and async/await">

<Level name="Beginner">

JavaScript runs on one thread. Slow work (network, disk, timers) is handed to the runtime, and a
callback runs later when it finishes. A promise is a value that will settle later; `await` pauses the
async function until it does, without blocking the thread.

```js
console.log('a');
setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('promise'));
console.log('b');
// a, b, promise, timeout
```

This is the concrete example the gate asks for: synchronous code first, then all microtasks (the
promise), then the next macrotask (the timer), even with a 0 ms delay.

Common mistake: forgetting `await`, so the function returns before the work is done and errors vanish.
Fix: lint with `no-floating-promises` and always return or await a promise.

</Level>

<Level name="Intermediate">

Concurrency without threads means many operations in flight while one runs at a time. `Promise.all`
runs things concurrently and fails fast; `Promise.allSettled` waits for all; `Promise.race` takes the
first. Sequential `await` in a loop is often an accidental slowdown.

```js
// sequential: 3 x 200 ms = ~600 ms
for (const id of ids) await fetchUser(id);
// concurrent: ~200 ms
await Promise.all(ids.map(fetchUser));
```

But unbounded concurrency is its own bug: 10,000 parallel requests exhaust sockets or get rate limited.
A small pool limits it.

```js
async function pool(items, limit, fn) {
  const out = []; let i = 0;
  const workers = Array.from({ length: limit }, async () => {
    while (i < items.length) { const k = i++; out[k] = await fn(items[k]); }
  });
  await Promise.all(workers); return out;
}
```

</Level>

<Level name="Advanced">

Node's loop has phases: timers, pending callbacks, poll (I/O), check (`setImmediate`), close callbacks.
`process.nextTick` runs before promise microtasks. File system work and DNS lookups use libuv's thread
pool (four threads by default), so many concurrent `fs` calls queue behind each other. `async`
functions are syntax over promises and generators: each `await` splits the function into microtask
continuations.

```js
setImmediate(() => console.log('immediate'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
// nextTick, promise, immediate
```

</Level>

<Level name="Edge cases">

- A CPU loop of two seconds blocks every request on the server: the event loop cannot run anything
  else. Health checks time out.
- A promise rejected with no handler: Node 15+ crashes the process with `UnhandledPromiseRejection`.
- `await` on a non-promise value still yields to the microtask queue once.

</Level>

<Level name="Corner cases">

A microtask that schedules another microtask forever starves the macrotask queue: timers and I/O never
run, and the process looks hung with zero CPU idle. Two rules (microtasks drain fully; I/O waits) meet.
Another: `Promise.all` rejects on the first failure but the other operations keep running, so a failed
batch can still write half its rows.

</Level>

<Level name="Production level">

I measure event-loop lag (`perf_hooks.monitorEventLoopDelay`) as a metric; a p99 lag over 100 ms means
something is blocking. CPU-heavy work moves to a worker thread or a queue. Every outbound call gets a
timeout with `AbortSignal.timeout(ms)`, because a promise that never settles is a leak.

</Level>

<Level name="Mindset">

Ask of every line: does this wait, and does anything else get to run while it waits?

</Level>

<Level name="System design">

The single-threaded model makes Node good at I/O-bound servers and poor at CPU-bound work. Model calls
in phase 7 are I/O-bound and slow, so concurrency limits, timeouts and cancellation are the design
concerns, not threads.

</Level>

<Level name="Strategy">

Write ten ordering puzzles mixing `nextTick`, promises, timers and `setImmediate`, predict, run, explain.
Then block the server with a CPU loop and watch the lag metric. Done when I can explain the gate's
example aloud and fix a starved timer.

</Level>

</Levels>

#### Phase 1: errors: values, exceptions, rejected promises and process exit codes

<Flow
  caption="Where an error can go, and where it must end up"
  steps={['Thrown or rejected', 'Caught at the right layer', 'Turned into a value or a response', 'Logged once with context', 'Exit code or status says what happened']}
/>

<Levels label="Phase 1, errors, exceptions, rejections and exit codes">

<Level name="Beginner">

An error can be thrown (synchronous), rejected (a promise), or returned as a value. A process ends with
an exit code: 0 for success, anything else for failure, and shell scripts and CI read that number.

```js
try { JSON.parse('{bad'); }
catch (e) { console.error(e.message); process.exitCode = 1; }
// Expected property name or '}' in JSON at position 1
```

Common mistake: `catch (e) {}` that swallows everything. Fix: catch only what I can handle, and rethrow
the rest.

</Level>

<Level name="Intermediate">

Expected failures (a user typed bad input) are values; unexpected ones (a bug, a broken connection) are
exceptions. A small result type makes expected failures visible in TypeScript.

```ts
type Result<T> = { ok: true; value: T } | { ok: false; error: string };
function parseAge(s: string): Result<number> {
  const n = Number(s);
  return Number.isInteger(n) && n >= 0 ? { ok: true, value: n } : { ok: false, error: 'age must be a whole number' };
}
```

Errors should carry a cause: `throw new Error('loading config failed', { cause: err })` keeps the
original stack.

</Level>

<Level name="Advanced">

In Node, an uncaught exception or unhandled rejection crashes the process by default. That is correct:
the state may be corrupt, so the right response is to log, exit non-zero and let the supervisor
restart. `process.exit()` stops immediately and can drop buffered output; setting `process.exitCode`
and letting the loop drain is safer. Signals have conventional codes: killed by SIGTERM shows as 143
(128 + 15).

</Level>

<Level name="Edge cases">

- `throw 'string'` has no stack trace.
- An error thrown inside a `setTimeout` callback is not caught by the `try` around the `setTimeout`.
- `finally` that returns a value overrides the thrown error.

</Level>

<Level name="Corner cases">

An error thrown inside a `catch` while logging the first error replaces it, so the logs show the
logging failure, not the cause. Two failures at once: use `cause` and keep logging code simple. Another:
an async error after the HTTP response was already sent cannot change the status code; it must be
logged, not returned.

</Level>

<Level name="Production level">

One error shape for the API, one log line per error with the request ID, and no stack traces sent to
users. CI depends on exit codes: a test runner that exits 0 on failure makes the pipeline lie.

</Level>

<Level name="Mindset">

Errors are part of the interface. Decide, for each function, which failures it reports and how.

</Level>

<Level name="System design">

Error boundaries map to system layers: validation errors become 400s, auth errors 401 or 403, missing
resources 404, dependency failures 502 or 503, and bugs 500. That mapping is designed once, in one
place.

</Level>

<Level name="Strategy">

Make the CLI tool exit with documented codes (0 ok, 1 bad input, 2 I/O failure), and test each with a
shell script that checks `$?`. Done when every failure path has a test and a code.

</Level>

</Levels>

#### Phase 1: data structures I use every day: arrays, maps, sets, queues and trees

<Compare

<Levels label="Phase 1, arrays, maps, sets, queues and trees">

<Level name="Beginner">

An array is an ordered list by index. A `Map` is key to value. A `Set` is unique values. A queue takes
from the front and adds to the back. A tree is nodes with children.

```js
const seen = new Set(['a', 'b', 'a']);
console.log(seen.size); // 2
const counts = new Map();
for (const w of 'to be or not to be'.split(' ')) counts.set(w, (counts.get(w) ?? 0) + 1);
console.log(counts.get('to')); // 2
```

Common mistake: using `array.includes` inside a loop to deduplicate. Fix: a `Set`.

</Level>

<Level name="Intermediate">

The gate asks why a `Map` is not an object. Concretely: an object used as a dictionary inherits from
`Object.prototype`, so `'constructor' in {}` is `true`, and a user-supplied key like `__proto__` can
change the object's prototype (prototype pollution). Object keys are coerced to strings, so `o[1]` and
`o['1']` are the same and an object key becomes `'[object Object]'`.

```js
const o = {}; const k1 = {}; const k2 = {};
o[k1] = 'a'; o[k2] = 'b';
console.log(o[k1]); // 'b' -- both keys became '[object Object]'
const m = new Map([[k1, 'a'], [k2, 'b']]);
console.log(m.get(k1)); // 'a'
```

</Level>

<Level name="Advanced">

`Array.prototype.shift` is O(n) because it reindexes, so a queue built on `shift` is quadratic over many
items. A ring buffer or two-stack queue is O(1) amortised. V8 stores arrays densely when they hold one
element kind and switches to a slower dictionary mode when they become sparse (`a[1e6] = 1`).

```js
class Queue { #a = []; #h = 0;
  push(x) { this.#a.push(x); }
  shift() { const x = this.#a[this.#h++]; if (this.#h * 2 > this.#a.length) { this.#a = this.#a.slice(this.#h); this.#h = 0; } return x; }
  get size() { return this.#a.length - this.#h; } }
```

</Level>

<Level name="Edge cases">

- `new Set([NaN, NaN]).size` is 1: Set uses SameValueZero, so `NaN` equals itself here.
- `[10, 9, 1].sort()` gives `[1, 10, 9]`: default sort is by string.
- An empty array's `reduce` with no initial value throws `TypeError: Reduce of empty array with no
  initial value`.

</Level>

<Level name="Corner cases">

Mutating a `Map` while iterating it: deleting the current key is safe, adding keys means the loop
visits them too, which can loop forever if each visit adds one. Iteration plus mutation. Another: a
`Set` of objects deduplicates by reference, so two equal-looking objects both stay.

</Level>

<Level name="Production level">

In a server, the choice shows up as latency: a lookup by ID inside a loop over a list is O(n squared)
and fine at 100 rows, painful at 100,000. Unbounded in-memory maps are leaks; an LRU with a size limit is
the production version.

</Level>

<Level name="Mindset">

Choose the structure from the operation I do most: look up, test membership, keep order, take the
oldest.

</Level>

<Level name="System design">

The same choices recur at system scale: Redis has lists (queues), sets and hashes; Postgres has B-tree
indexes (sorted trees). Knowing the in-memory version makes those legible.

</Level>

<Level name="Strategy">

Implement a queue, an LRU cache and a trie with tests, and measure the `shift` queue against mine at
100,000 items. Done when I can explain the Map answer from the gate without notes and my queue beats
`shift` by a measured factor.

</Level>

</Levels>

#### Phase 1: complexity: the cost of a loop, a lookup, a copy and a serialisation

<Figure art={`
  n        O(1)   O(log n)   O(n)       O(n log n)    O(n^2)
  10       1      3          10         33            100
  1,000    1      10         1,000      10,000        1,000,000
  100,000  1      17         100,000    1,700,000     10,000,000,000
`} caption="How operation counts grow: at a hundred thousand items, quadratic code does ten billion steps where linear code does a hundred thousand." />

<Levels label="Phase 1, complexity of loops, lookups, copies and serialisation">

<Level name="Beginner">

Complexity is how work grows with input size. A loop over n items is O(n); a loop inside a loop is O(n
squared); a `Map` lookup is O(1) on average.

```js
// O(n^2): find users who have orders
users.filter(u => orders.some(o => o.userId === u.id));
// O(n): build a set once
const ids = new Set(orders.map(o => o.userId));
users.filter(u => ids.has(u.id));
```

Common mistake: calling something O(1) because it is one line. Fix: count what the line does,
including what the library call hides.

</Level>

<Level name="Intermediate">

Copies and serialisation hide cost. Spreading an array in a reduce copies it every step, which makes a
linear-looking loop quadratic. `JSON.stringify` of a large object is O(size) and blocks the event loop.

```js
// quadratic: copies acc every iteration
items.reduce((acc, x) => [...acc, x * 2], []);
// linear
items.map(x => x * 2);
```

</Level>

<Level name="Advanced">

Big O hides constants and memory. An O(n) pass over a contiguous array can beat an O(log n) tree
because of CPU caches. Amortised cost matters: `push` is O(1) amortised even though resizing is O(n).
Hash maps are O(1) average and O(n) worst case under collisions.

```js
console.time('stringify'); JSON.stringify(Array.from({ length: 1e6 }, (_, i) => ({ i }))); console.timeEnd('stringify');
// stringify: ~150ms on my laptop -- every request waits that long
```

</Level>

<Level name="Edge cases">

- n = 0 and n = 1: many algorithms have different code paths; test them.
- String concatenation in a loop is usually fine in V8 (ropes), but repeated `slice` of large strings
  can retain the whole original.
- `Array.prototype.includes` on a 10-item array is faster than building a `Set`.

</Level>

<Level name="Corner cases">

A quadratic algorithm over user-controlled input is a denial-of-service vector: one request with a
large payload ties up the event loop for everyone. Complexity plus an attacker. Regex backtracking is
the classic case: `/(a+)+$/` on a long string of a's followed by one b takes exponential time.

</Level>

<Level name="Production level">

I put limits on input sizes (body size, array lengths, page size) so the worst case is bounded, and I
profile before optimising. The p99 is where complexity shows up, because the largest inputs land there.

</Level>

<Level name="Mindset">

Know the size of n in production, not in the test. Then decide whether the complexity matters.

</Level>

<Level name="System design">

The same reasoning sizes databases (index scans versus full scans), APIs (pagination) and AI calls
(tokens scale with context length; cost is per token). Every phase after this one has a "what is n"
question.

</Level>

<Level name="Strategy">

Take five functions from the server, annotate their complexity, benchmark each at 10, 10,000 and
1,000,000 items. Done when the benchmark confirms each annotation or I have explained why it did not.

</Level>

</Levels>

<Levels label="Phase 1, HTTP methods, headers, status codes, cookies, caching and CORS">

<Level name="Beginner">

HTTP is a request and a response. The method says what to do (GET read, POST create, PUT replace,
PATCH change, DELETE remove), the status says what happened (2xx ok, 3xx go elsewhere, 4xx client
error, 5xx server error), and headers carry metadata.

```sh
curl -i https://example.com/
# HTTP/2 200
# content-type: text/html; charset=UTF-8
# cache-control: max-age=604800
```

Common mistake: returning 200 with `{ "error": "not found" }`. Fix: the status code is the contract;
use 404.

</Level>

<Level name="Intermediate">

Cookies are how the browser remembers state: the server sends `Set-Cookie`, the browser sends `Cookie`
back on matching requests. Attributes matter: `HttpOnly` hides it from JavaScript, `Secure` sends it
only over HTTPS, `SameSite=Lax` stops most cross-site sends. Caching is controlled by `Cache-Control`
and validated with `ETag` and `If-None-Match`, which can turn a 200 into a cheap 304.

```http
Set-Cookie: sid=abc; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
```

</Level>

<Level name="Advanced">

CORS is the browser enforcing the same-origin policy and letting servers opt in. A "simple" request is
sent and its response is hidden unless `Access-Control-Allow-Origin` matches. A non-simple request (a
JSON content type, a custom header, PUT or DELETE) first sends an `OPTIONS` preflight. Credentials need
`Access-Control-Allow-Credentials: true` and an exact origin, never `*`. CORS does not protect the
server: curl ignores it entirely.

Safe methods (GET, HEAD) should not change state; idempotent methods (GET, PUT, DELETE) can be repeated
with the same effect. POST is neither, which is why phase 3 adds idempotency keys.

</Level>

<Level name="Edge cases">

- A 204 No Content must not have a body; some clients hang waiting for one.
- A redirect with 301 or 302 may turn a POST into a GET; 307 and 308 keep the method.
- A header value containing a newline is a header-injection bug.

</Level>

<Level name="Corner cases">

A cached personalised response: the server sends `Cache-Control: public` on a page that includes the
user's name, and a CDN serves it to everyone. Caching plus cookies. The fix is `private` or `no-store`,
plus `Vary: Cookie` if anything caches. Another: CORS preflight succeeds, the request fails with 500,
and the error response lacks CORS headers, so the browser reports a CORS error instead of the 500.

</Level>

<Level name="Production level">

In production, headers are security and performance controls: HSTS, a content security policy, cache
lifetimes for hashed assets, compression. I check every route's status codes, cache headers and cookie
attributes with `curl -i` before shipping.

</Level>

<Level name="Mindset">

HTTP is text I can read. When something is wrong, read the raw request and response before reading
code.

</Level>

<Level name="System design">

HTTP semantics drive architecture: GETs can be cached at the edge, idempotent methods can be retried by
proxies, and streaming responses (server-sent events) are how phase 2's AI chat surface receives tokens.

</Level>

<Level name="Strategy">

Write the raw request for ten scenarios by hand (login, cached asset, CORS preflight, redirect after
POST) and check each against the real server with `curl -v`. Done when I can explain every header in a
real response from my deployed app.

</Level>

</Levels>

#### Phase 1: JSON, validation and the boundary between untrusted input and my types

<Flow
  caption="Untrusted bytes become trusted types in exactly one place"
  steps={['Raw bytes', 'Size limit', 'JSON.parse', 'unknown', 'Schema check', 'Typed value', 'Business logic']}
/>

<Levels label="Phase 1, JSON, validation and the trust boundary">

<Level name="Beginner">

JSON is text with six kinds of values: object, array, string, number, boolean, null. `JSON.parse`
turns text into values and throws on bad syntax. Parsing is not validating: valid JSON can still be the
wrong shape.

```js
JSON.parse('{"age": "seven"}'); // parses fine, still wrong
```

Common mistake: `const body = JSON.parse(text) as CreateNote`. Fix: parse into `unknown`, then check
the shape before using it.

</Level>

<Level name="Intermediate">

A schema library (Zod, Valibot) or a hand-written check turns `unknown` into a typed value and gives
error messages for free. The type is derived from the schema so they cannot drift.

```ts
import { z } from 'zod';
const CreateNote = z.object({ body: z.string().min(1).max(10_000) });
type CreateNote = z.infer<typeof CreateNote>;
const r = CreateNote.safeParse(JSON.parse(text));
if (!r.success) return reply(400, { error: 'invalid', issues: r.error.issues });
```

</Level>

<Level name="Advanced">

The gate asks for a JSON parser from scratch. JSON's grammar is small enough for a recursive-descent
parser: one function per value kind, a position index, and precise errors.

```ts
function parse(s: string): unknown {
  let i = 0;
  const ws = () => { while (' \t\n\r'.includes(s[i])) i++; };
  const fail = (m: string) => { throw new SyntaxError(`${m} at ${i}`); };
  function value(): unknown {
    ws();
    const c = s[i];
    if (c === '{') return object();
    if (c === '[') return array();
    if (c === '"') return string();
    if (c === '-' || (c >= '0' && c <= '9')) return number();
    for (const [lit, v] of [['true', true], ['false', false], ['null', null]] as const)
      if (s.startsWith(lit, i)) { i += lit.length; return v; }
    return fail('unexpected token');
  }
  function object() { i++; const o: Record<string, unknown> = {}; ws();
    if (s[i] === '}') { i++; return o; }
    for (;;) { ws(); const k = string(); ws(); if (s[i++] !== ':') fail('expected :');
      o[k] = value(); ws(); if (s[i] === ',') { i++; continue; } if (s[i++] === '}') return o; fail('expected , or }'); } }
  function array() { i++; const a: unknown[] = []; ws();
    if (s[i] === ']') { i++; return a; }
    for (;;) { a.push(value()); ws(); if (s[i] === ',') { i++; continue; } if (s[i++] === ']') return a; fail('expected , or ]'); } }
  function string() { if (s[i++] !== '"') fail('expected string'); let out = '';
    while (s[i] !== '"') { if (i >= s.length) fail('unterminated string');
      if (s[i] === '\\') { const e = s[++i]; const map: Record<string, string> = { n: '\n', t: '\t', r: '\r', b: '\b', f: '\f', '"': '"', '\\': '\\', '/': '/' };
        if (e === 'u') { out += String.fromCharCode(parseInt(s.slice(i + 1, i + 5), 16)); i += 5; continue; }
        if (!(e in map)) fail('bad escape'); out += map[e]; i++; continue; }
      out += s[i++]; } i++; return out; }
  function number() { const m = /^-?(0|[1-9]\d*)(\.\d+)?([eE][+-]?\d+)?/.exec(s.slice(i)); if (!m) fail('bad number'); i += m![0].length; return Number(m![0]); }
  const v = value(); ws(); if (i !== s.length) fail('trailing data'); return v;
}
```

The `Record` object here is a plain object, so a key `__proto__` would hit the prototype setter; a
safe parser uses `Object.create(null)` or `Object.defineProperty`. That detail is the bridge to phase
6.

</Level>

<Level name="Edge cases">

- `JSON.parse('')` throws `Unexpected end of JSON input`.
- Duplicate keys: `{"a":1,"a":2}` parses to `{ a: 2 }` silently.
- `JSON.stringify(undefined)` returns `undefined`, not a string; `NaN` becomes `null`.
- Large integers lose precision (see the first topic).

</Level>

<Level name="Corner cases">

A valid payload nested 50,000 levels deep crashes a recursive parser with a stack overflow, and a 2 GB
body crashes the process with out-of-memory before validation even starts. Size plus depth: the fix is
a body size limit before parsing and a depth limit inside it. Another: a `Date` round-trips through
JSON as a string and comes back as a string, not a `Date`, so the type says `Date` and the value lies.

</Level>

<Level name="Production level">

Every boundary gets a schema: request bodies, query strings, environment variables, third-party
webhooks, database rows read with raw SQL, and, from phase 7, model output. Validation errors are logged
with the field path but not the value, in case it is sensitive.

</Level>

<Level name="Mindset">

Types are promises my code makes to itself. Input from outside has made no promises. Check once, at the
edge, then trust the type inside.

</Level>

<Level name="System design">

The trust boundary is an architectural line. Draw it on the diagram: browser to API, API to database,
API to model provider, webhook to API. Each crossing has a validator.

</Level>

<Level name="Strategy">

Write the parser, then fuzz it against `JSON.parse` with random inputs and compare results and error
behaviour. Done when it agrees with `JSON.parse` on a thousand random valid documents and rejects every
invalid one I generate.

</Level>

</Levels>

#### Phase 1: testing: unit, integration, and the difference between a mock and a lie

<Layers
  caption="What each kind of test proves"
  layers={[
    { name: 'End to end', note: 'a real browser drives the deployed flow' },
    { name: 'Integration', note: 'my code plus a real database or HTTP server' },
    { name: 'Unit', note: 'one function, no I/O, fast' },
  ]}
/>

<Levels label="Phase 1, unit tests, integration tests, mocks and lies">

<Level name="Beginner">

A test runs code and checks the result. Node has a built-in runner.

```js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { slugify } from '../src/slugify.js';
test('slugify lowercases and joins with dashes', () => {
  assert.equal(slugify('Hello World'), 'hello-world');
});
```

```sh
node --test
# tests 1  pass 1  fail 0
```

Common mistake: tests that only check that no error was thrown. Fix: assert on the actual output.

</Level>

<Level name="Intermediate">

A unit test isolates one function. An integration test exercises real collaborators: an HTTP request
into the server, a real Postgres in Docker. A mock replaces a collaborator with a fake that records
calls.

The plan's phrase "a mock and a lie": a mock that returns what I assume the real thing returns tests my
assumption, not the system. If the real database rejects my SQL, the mocked test still passes.

```js
// lie: passes even though the SQL has a typo
db.query = async () => ({ rows: [{ id: 1 }] });
// truth: runs the real query against a test database
const { rows } = await pool.query('select id from notes where user_id = $1', [user.id]);
```

</Level>

<Level name="Advanced">

Good tests are deterministic: they control time (fake clocks), randomness (seeds) and order (no shared
state between tests). A test database is reset per test with a transaction that rolls back, or a fresh
schema per file. Mocks are right at true boundaries I do not own and cannot run: a payment provider, a
model API. Even then, a contract test against a recorded real response keeps the mock honest.

</Level>

<Level name="Edge cases">

- A test that passes alone and fails in the suite: shared state.
- A test that depends on the current date fails on 29 February or at midnight UTC.
- A snapshot test that is updated without reading the diff tests nothing.

</Level>

<Level name="Corner cases">

A flaky async test that fails one run in twenty because two promises race; the tempting fix is a
`sleep(100)`, which slows every run and still fails under load. The gate asks to debug one without a
sleep. The real fix is to await the specific event: return the promise, use a fake timer, or wait on a
condition with a timeout.

```js
// flaky
startJob(); await sleep(100); assert.equal(status(), 'done');
// deterministic
await startJob(); assert.equal(status(), 'done');
```

</Level>

<Level name="Production level">

Tests are the gate in CI. They must be fast enough to run on every push (minutes, not hours) and
trustworthy enough that a red build stops the merge. A flaky test that everyone reruns is worse than no
test, because it teaches people to ignore red.

</Level>

<Level name="Mindset">

A test is a claim about behaviour. Ask what claim it makes and whether a broken implementation could
still pass it.

</Level>

<Level name="System design">

The test pyramid is a cost model: many cheap unit tests, fewer integration tests, a handful of
end-to-end flows. AI features add a fourth kind in phase 7: evals, which are tests with scores instead of
pass and fail.

</Level>

<Level name="Strategy">

For the server, write unit tests for the parser and router, integration tests for each route against
real Postgres, and break the code on purpose to check each test fails. Done when every route has an
integration test and a deliberate bug in each module turns at least one test red.

</Level>

</Levels>

#### Phase 1: debugging: stack traces, breakpoints, logging and reproducing a bug

<Flow
  caption="The debugging loop that does not guess"
  steps={['Reproduce reliably', 'Read the full stack trace', 'Form one hypothesis', 'Test it with a breakpoint or a log', 'Fix', 'Add a test that failed before']}
/>

<Levels label="Phase 1, stack traces, breakpoints, logging and reproduction">

<Level name="Beginner">

A stack trace lists the calls active when the error happened, newest first. The first line of my own
code in it is usually where to look.

```txt
TypeError: Cannot read properties of undefined (reading 'id')
    at handleCreate (src/routes/notes.ts:14:22)
    at route (src/router.ts:31:10)
```

Line 14, column 22 of notes.ts: something there is `undefined`. Common mistake: reading only the first
line. Fix: read every frame until the first one in my code, then inspect what was undefined.

</Level>

<Level name="Intermediate">

Breakpoints stop the program and let me inspect values. `node --inspect-brk src/main.ts` and open
`chrome://inspect`, or use the editor's debugger. A conditional breakpoint stops only when, say,
`req.url === '/api/notes'`. Logging is the fallback when I cannot attach a debugger, such as in
production.

</Level>

<Level name="Advanced">

Async stack traces: V8 stitches together frames across `await`, but not across callbacks scheduled by
some libraries, so a trace can end at `processTicksAndRejections`. Source maps translate compiled line
numbers back to TypeScript; without them the trace points at the wrong file. `git bisect` finds the
commit that introduced a bug by binary search.

```sh
git bisect start; git bisect bad; git bisect good v0.3.0
git bisect run npm test   # runs tests at each midpoint
```

</Level>

<Level name="Edge cases">

- A bug that disappears with the debugger attached: timing changes. Use logging with timestamps.
- `console.log(obj)` in the browser shows the object's state when expanded, not when logged.
- A minified production stack trace with no source map.

</Level>

<Level name="Corner cases">

A bug that only reproduces with production data and only under concurrency: two requests modifying
the same row. Data plus timing. The approach is to reproduce with a script that fires concurrent
requests at a copy of the data, then shrink the case until it is a test.

</Level>

<Level name="Production level">

In production I debug from logs, traces and error reports, so I plan for it: request IDs, structured
context and source maps uploaded to the error tracker. I never attach a debugger to a live production
process serving users.

</Level>

<Level name="Mindset">

Debugging is the scientific method. One hypothesis at a time, tested, then discarded or kept. Random
changes until it works means I have not learned the cause.

</Level>

<Level name="System design">

Debuggability is designed in: correlation IDs, deterministic replays, feature flags to isolate code
paths, and logs that capture inputs that caused failures (minus secrets). Phase 9's agent traces are
the same idea for AI behaviour.

</Level>

<Level name="Strategy">

Keep a bug journal for the phase: symptom, reproduction, hypothesis, cause, fix, test. Done when five
real bugs are written up and each has a test that failed before the fix.

</Level>

</Levels>

<Levels label="Phase 1, Git commits, branches and history">

<Level name="Beginner">

A commit is a snapshot with a message. A branch is a movable name for a line of commits. Small commits
make the history readable and make a bad change easy to find and revert.

```sh
git switch -c rate-limiter
git add src/limit.ts && git commit -m "Limit requests per IP with a token bucket"
git log --oneline --graph
```

Common mistake: one commit called "stuff" with five changes. Fix: `git add -p` to stage hunks
separately.

</Level>

<Level name="Intermediate">

A good message has a subject line in the imperative ("Add", "Fix", "Limit") and a body explaining why
when it is not obvious. `git revert` undoes a commit with a new one, which is safe on shared branches;
`git reset` moves the branch, which rewrites history and is only for local work.

</Level>

<Level name="Advanced">

Merge commits preserve the branch shape; rebase rewrites the branch onto a new base and produces linear
history. Either is fine if the team agrees; this site keeps merge commits and no squashing, so each
step stays visible. `git reflog` records where HEAD has been, so even a bad reset is recoverable for a
while.

</Level>

<Level name="Edge cases">

- A merge conflict in a lock file: regenerate it instead of hand-editing.
- An empty commit message aborts the commit.
- A detached HEAD: commits made there are lost when switching away unless a branch is created.

</Level>

<Level name="Corner cases">

Reverting a merge commit and later re-merging the same branch: Git thinks those commits are already in,
so the changes do not come back. Revert plus re-merge. The fix is to revert the revert. Another: a
secret committed and then deleted in the next commit is still in the history and still leaked.

</Level>

<Level name="Production level">

History is the audit trail for deploys, incident timelines and blame. Branch protection on main,
required CI, and commits that each pass the build make `git bisect` and rollbacks reliable.

</Level>

<Level name="Mindset">

Write history for the person reading it during an incident, who will be me.

</Level>

<Level name="System design">

The branching model decides deploy flow: trunk-based with short branches pairs with continuous deploy;
long-lived branches pair with release trains. Phase 5 builds on this choice.

</Level>

<Level name="Strategy">

For this phase's build, one commit per step in the build list, each passing the tests. Done when `git
log --oneline` reads as the story of the build and `git bisect run npm test` works across it.

</Level>

#### Phase 1: the build: a CLI tool and an HTTP server without a framework

<Figure art={`
  request --> logger --> rate limiter --> router --> handler --> response
                |            |              |           |
          JSON log line   429 + Retry-   404 / 405    validate body,
          with id, ms     After header   if no match  400 with issues
`} caption="The server's pipeline: each stage is a small function, and each one can end the request early with a clear status." />

<Levels label="Phase 1, the build: CLI, server, router, rate limiter and logger">

<Level name="Beginner">

The CLI tool reads a file of notes and prints counts; it uses `process.argv`, `fs`, exit codes and the
JSON parser. The server answers routes with `node:http` and no framework.

```ts
import { createServer } from 'node:http';
createServer((req, res) => {
  if (req.method === 'GET' && req.url === '/health') return void res.end('ok');
  res.writeHead(404, { 'content-type': 'application/json' }).end('{"error":"not found"}');
}).listen(3000);
```

</Level>

<Level name="Intermediate">

The router maps method and path pattern to a handler and extracts parameters. It returns 404 when no
path matches and 405 with an `Allow` header when the path matches but the method does not.

```ts
type Handler = (req: Req, params: Record<string, string>) => Promise<Res>;
const routes: { method: string; parts: string[]; h: Handler }[] = [];
export function add(method: string, path: string, h: Handler) { routes.push({ method, parts: path.split('/'), h }); }
export function match(method: string, path: string) {
  const segs = path.split('?')[0].split('/'); let allowed: string[] = [];
  for (const r of routes) {
    if (r.parts.length !== segs.length) continue;
    const params: Record<string, string> = {};
    const ok = r.parts.every((p, i) => p.startsWith(':') ? (params[p.slice(1)] = decodeURIComponent(segs[i]), true) : p === segs[i]);
    if (!ok) continue;
    if (r.method === method) return { h: r.h, params };
    allowed.push(r.method);
  }
  return allowed.length ? { status: 405, allowed } : { status: 404 };
}
```

</Level>

<Level name="Advanced">

The rate limiter is a token bucket per client: a bucket holds up to `capacity` tokens and refills at
`rate` per second; each request takes one; an empty bucket means 429 with `Retry-After`.

```ts
const buckets = new Map<string, { tokens: number; at: number }>();
export function allow(key: string, capacity = 10, rate = 5, now = Date.now()) {
  const b = buckets.get(key) ?? { tokens: capacity, at: now };
  b.tokens = Math.min(capacity, b.tokens + ((now - b.at) / 1000) * rate);
  b.at = now;
  const ok = b.tokens >= 1;
  if (ok) b.tokens -= 1;
  buckets.set(key, b);
  return { ok, retryAfter: ok ? 0 : Math.ceil((1 - b.tokens) / rate) };
}
```

Passing `now` in makes it testable without real time. The request logger writes one JSON line per
request with the method, path, status, duration and request ID. Finally the router moves into its own
package with a README documenting `add`, `match` and the 404 and 405 behaviour.

</Level>

<Level name="Edge cases">

- A path with a trailing slash: is `/notes/` the same as `/notes`? Decide and test it.
- An encoded path segment: `/notes/a%2Fb` must decode to `a/b` as one parameter, not two segments.
- A malformed percent-encoding makes `decodeURIComponent` throw `URIError`: catch it and return 400.

</Level>

<Level name="Corner cases">

The rate limiter's map grows forever with one entry per IP: a slow memory leak and, under attack with
spoofed headers, a fast one. Limit plus memory. The fix is evicting buckets that are full and idle.
Behind a proxy, every request has the proxy's IP, so one key limits everyone; trust `x-forwarded-for`
only from the known proxy.

</Level>

<Level name="Production level">

The in-memory limiter works for one process. With two instances, each has its own buckets, so the real
limit doubles. Production moves the bucket into Redis (phase 3). The logger must not log bodies or
auth headers.

</Level>

<Level name="Mindset">

Build the thing the framework hides once, then use the framework knowing what it does.

</Level>

<Level name="System design">

Router, middleware, limiter and logger are the same building blocks every web framework and API gateway
provides. Knowing their failure modes (ordering, shared state, proxies) is what lets me configure a
gateway correctly later.

</Level>

<Level name="Strategy">

Build in this order, one commit each: CLI, server, router, JSON errors, validation, logger, limiter,
tests, router as a library with a README. Done when every step has tests and the library's README is
enough for someone else to use it.

</Level>

</Levels>
