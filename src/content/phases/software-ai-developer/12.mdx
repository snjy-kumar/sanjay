#### Phase 12: Authentication, authorization and tenant isolation

Three different questions get confused all the time. Authentication asks who is making this request.
Authorization asks whether that identity can do this action. Tenant isolation asks whether this
resource even belongs to the world that identity lives in. In a multi-tenant product the third
question matters most, because a leak doesn't only hurt one user. It breaks the promise the whole
product makes to every customer.

<Levels label="Phase 12, authentication, authorization and tenant isolation">

<Level name="Beginner">

Authentication starts with sign-up and sign-in. The server checks a password against a stored slow
hash, creates a session row, and sends back a cookie that holds only a random session id. On each
request the server looks the id up. Sign-out deletes the row. Expiry is a column, so a stolen cookie
stops working.

```ts
export async function signIn(email: string, password: string) {
  const user = await db.users.findByEmail(email.toLowerCase());
  const ok = user && (await argon2.verify(user.passwordHash, password));
  if (!ok) throw httpError(401, 'invalid_credentials');      // same error for both cases
  const id = randomBytes(32).toString('base64url');
  await db.sessions.insert({ id: sha256(id), userId: user.id, expiresAt: addDays(new Date(), 14) });
  return cookie('sid', id, { httpOnly: true, secure: true, sameSite: 'lax', path: '/' });
}
```

The session id is hashed at rest, so a database leak doesn't hand out live sessions. The error is the
same whether the email exists or not, so nobody can use the form to list accounts.

Authorization in its first form is a role check: viewers read, editors write, owners manage billing
and members. Tenant isolation in its first form is a rule: every table that holds customer data has a
`tenant_id`, and every query filters on it.

Common mistake: checking the role but not ownership. An editor in tenant A changes the id in
`/documents/123/edit` and edits tenant B's document, because the code only asked "are you an
editor?". Fix: every resource load includes the tenant (and owner, where relevant) in the query.

</Level>

<Level name="Intermediate">

I put the rules in one module, so routes, workers and AI tools all ask the same question.

```ts
const policy = {
  viewer: ['documents:read', 'answers:ask'],
  editor: ['documents:read', 'documents:write', 'answers:ask'],
  owner:  ['documents:read', 'documents:write', 'answers:ask', 'members:manage', 'billing:manage'],
} as const;

export function can(role: Role, perm: Perm) { return (policy[role] as readonly string[]).includes(perm); }

export async function requireDoc(ctx: Ctx, docId: string, need: 'read' | 'write') {
  const doc = await db.documents.find({ id: docId, tenantId: ctx.tenantId });
  if (!doc) throw httpError(404);           // 404, not 403: don't reveal it exists elsewhere
  if (!can(ctx.role, need === 'write' ? 'documents:write' : 'documents:read')) throw httpError(403);
  return doc;
}
```

The test that matters most is the cross-tenant one. I seed two tenants and try everything across them:

```ts
test.each(routes)('%s refuses tenant B resources for tenant A', async (route) => {
  const res = await as(userA).request(route.method, route.path(tenantB.docId));
  expect([403, 404]).toContain(res.status);
});
// FAIL  PATCH /api/documents/:id  expected [403, 404] to contain 200
```

That failure line is the reason the suite exists. It names the exact route that forgot its check.

Password reset: the token is random and single-use, stored as a hash, expires within the hour, and
using it revokes every other session for that user.

</Level>

<Level name="Advanced">

Defence in depth means the database enforces tenancy too. With Postgres row-level security, the app
sets the tenant per transaction and the policy does the rest:

```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON documents
  USING (tenant_id = current_setting('app.tenant_id')::bigint);
-- in each request transaction:
SET LOCAL app.tenant_id = '42';
SELECT count(*) FROM documents;   -- only tenant 42's rows, even with no WHERE clause
```

The app connects as a role that doesn't own the tables (owners bypass RLS unless it is forced), and
migrations run as a separate role. Then I go through every derived store. Vector search filters on
tenant before ranking. Cache keys start with the tenant id. Queue messages take tenant from the
session at enqueue time, never from request bodies. AI tool calls run with the caller's context, not a
service account.

Admin and support access is a separate, audited path: who looked at which tenant, when, and why, with
a reason field that can't be empty.

</Level>

<Level name="Edge cases">

- **Session expires mid-form:** the client keeps the draft locally, the server returns 401, and after
  signing in again the draft is restored. Users shouldn't lose work to security.
- **Reset for an unknown email:** same message and roughly the same response time as a known one.
- **Email case and Unicode:** I normalise before lookup, otherwise `A@x.com` and `a@x.com` become two
  accounts.
- **Invitation accepted by a different signed-in user:** the invite is bound to an email. A mismatch
  asks them to switch accounts instead of silently joining.

</Level>

<Level name="Corner cases">

- **User removed from a tenant while signed in:** their membership-scoped sessions are revoked
  straight away, or each request re-checks membership. Otherwise they keep access until expiry.
- **One person in two tenants:** the active tenant is explicit in the session. Switching re-checks
  membership and rotates the session id.
- **Background job running after a role downgrade:** jobs re-check permission when they run, not only
  when they are queued.
- **Last owner leaves:** blocked. A tenant must always have an owner, otherwise billing and deletion
  have no one who can act.

</Level>

<Level name="Production level">

I watch failed logins per account and per IP, run rate limits on sign-in and reset, alert on spikes,
and keep an audit log of role changes and admin access. The cross-tenant suite runs on every PR. To
prove it can fail, I remove one check on a branch and watch the build go red. Session cookies are
rotated on privilege change. There is a documented way to revoke every session for a tenant if one
of their accounts is compromised.

</Level>

<Level name="Mindset">

Auth is the code I don't improvise and don't delegate. Boring, explicit and tested beats clever. When
I'm unsure, I deny by default and make allowing something a deliberate line of code.

</Level>

<Level name="System design">

One authorization module, one request context, and RLS underneath. Every entry point builds the same
context: HTTP routes, webhooks, workers and AI tool calls. If a new entry point can't build that
context, it can't touch data. That is a design property, not a code review habit.

</Level>

<Level name="Strategy">

Week 63 starts with the cross-tenant suite, red. Then I write auth and policy code until it goes
green, then add RLS and watch it catch a check I left out on purpose. Done when every route and job
is in the suite, RLS is on for every tenant table, and a removed check fails CI.

</Level>

</Levels>
#### Phase 12: A database with migrations, indexes and a backup/restore drill

The database is the one part of the capstone I can't redeploy my way out of. Code that's broken can
be rolled back in minutes. Data that's gone or corrupted stays that way unless a restore I've
practised brings it back.

<Flow
  caption="Expand, migrate, contract: renaming a column without downtime"
  steps={['expand: add new column, nullable', 'deploy app that writes both', 'backfill in batches', 'deploy app that reads new', 'contract: drop old column']}
/>

<Figure art={`
  backup drill
  1. take backup (nightly + WAL)        5. run smoke queries + row counts
  2. spin up empty Postgres             6. compare to production counts
  3. restore to a point in time         7. record: duration, data loss window
  4. point a staging app at it          8. destroy the restored copy

<Levels label="Phase 12, database, migrations, indexes, backup and restore">

<Level name="Beginner">

Constraints are the database's own tests. They run on every write, whatever code did the writing.

```sql
CREATE TABLE documents (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id  bigint NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  title      text   NOT NULL CHECK (length(title) BETWEEN 1 AND 200),
  status     text   NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','indexed','failed')),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
INSERT INTO documents (tenant_id, title) VALUES (42, '');
-- ERROR:  new row for relation "documents" violates check constraint "documents_title_check"
```

Migrations are numbered files in the repo that move the schema forward, applied by a tool in CI and
on deploy. Never by hand.

Common mistake: editing the production schema in a console "just this once". The next migration then
fails or drifts. Fix: every change, including a one-off index, is a migration file.

</Level>

<Level name="Intermediate">

Indexes come from real queries, not guesses. I take the top queries by total time (for example from
`pg_stat_statements`) and run each through `EXPLAIN ANALYZE`:

```sql
EXPLAIN ANALYZE SELECT id, title FROM documents
WHERE tenant_id = 42 ORDER BY updated_at DESC LIMIT 20;
-- before:
--   Limit -> Sort (Sort Key: updated_at DESC) -> Seq Scan on documents (Filter: tenant_id = 42)
CREATE INDEX CONCURRENTLY documents_tenant_updated ON documents (tenant_id, updated_at DESC);
-- after:
--   Limit -> Index Scan using documents_tenant_updated on documents (Index Cond: tenant_id = 42)
```

Column order follows the query: equality first (tenant_id), then the sort column. The sort step goes
away because the index already returns rows in order. I write the before and after timings into the
ADR for that index. I don't quote them from memory.

Backups: the managed host takes nightly snapshots plus continuous WAL archiving. That allows
point-in-time recovery. The drill in the figure proves it works.

</Level>

<Level name="Advanced">

Zero-downtime migrations follow expand and contract. During a deploy, the old and new versions of the
app run at the same time, so each migration must work with both. Dangerous operations get rewritten:

```sql
-- risky on a big table: takes a strong lock while it validates every row
ALTER TABLE documents ADD CONSTRAINT fk_owner FOREIGN KEY (owner_id) REFERENCES users(id);
-- safer: add without validating, then validate separately (lighter lock)
ALTER TABLE documents ADD CONSTRAINT fk_owner FOREIGN KEY (owner_id) REFERENCES users(id) NOT VALID;
ALTER TABLE documents VALIDATE CONSTRAINT fk_owner;
```

I set a `lock_timeout` in migrations, so a migration that can't get its lock fails fast instead of
queueing behind a long query and blocking everything after it. Backfills run in batches of a few
thousand rows with a pause between them, and they can restart from where they stopped.

</Level>

<Level name="Edge cases">

- **Migration passes on an empty test database, fails on production data:** for example, adding a
  NOT NULL column when old rows have nothing to put there. Fix: add it nullable, backfill, then add the
  constraint. Test migrations against a realistic copy.
- **Long-running transaction during a migration:** the ALTER waits on its lock, and everything queues
  behind it. `lock_timeout` plus a retry turns an outage into a failed deploy step.

</Level>

<Level name="Corner cases">

- **Restore and derived data:** the vector index and caches are built from rows. After a
  point-in-time restore they may hold chunks of documents that the restore removed. The drill
  includes a rebuild or a consistency check.
- **Restore across a migration:** restoring to before migration N means the running app must be one
  that works with that schema. The runbook pairs restore points with app versions.

</Level>

<Level name="Production level">

The runbook holds two measured numbers: restore time and the data-loss window (RTO and RPO). It also
lists the exact commands and who can run them. Slow-query logging is on. Index bloat and unused
indexes get reviewed every quarter. Connection pooling limits are written down, so a traffic spike
can't run Postgres out of connections.

</Level>

<Level name="Mindset">

Data outlives code. A schema change gets more care than a code change, and a deletion gets the most
care of all.

</Level>

<Level name="System design">

Postgres is the single source of truth for rows, full-text, vectors (pgvector) and the job queue.
That gives me one thing to back up and one transaction boundary. A specialised store gets added only
when a measured limit forces it, and that decision goes in an ADR.

</Level>

<Level name="Strategy">

I run the restore drill twice in week 63: once to learn it, once to time it. Done when the runbook has
the measured RTO and RPO, every schema change is a migration, and the top five queries have an
EXPLAIN plan on record.

</Level>

</Levels>

<Levels label="Phase 12, frontend core flows">

<Level name="Beginner">

Every view that waits on the network has four states. I write them as one component so none get
forgotten:

```tsx
function Answers({ q }: { q: Query }) {
  if (q.status === 'loading') return <AnswerSkeleton />;
  if (q.status === 'error')   return <ErrorBox message="Couldn't load answers." onRetry={q.retry} />;
  if (q.data.length === 0)    return <Empty>Upload a document to ask your first question.</Empty>;
  return <AnswerList items={q.data} />;
}
```

Accessibility at its most basic: real buttons and links, a label on every input, visible focus,
enough colour contrast, and headings in order.

Common mistake: testing components one at a time but never the whole flow, so the flow breaks
where they connect. Fix: one end-to-end test per core flow.

</Level>

<Level name="Intermediate">

```ts
test('ask a question and open a citation', async ({ page }) => {
  await page.goto('/app');
  await page.getByRole('textbox', { name: 'Ask about your documents' }).fill('termination notice?');
  await page.keyboard.press('Enter');
  await expect(page.getByRole('status')).toHaveText(/answer ready/i);
  await page.getByRole('link', { name: /\[1\]/ }).click();
  await expect(page.getByRole('heading', { level: 1 })).toContainText('Contract');
});
```

Role-based selectors do two jobs: they find elements the way assistive technology does, so an
unlabeled textbox fails the test. When it does, the error says so plainly:

```text
Error: locator.fill: Timeout 5000ms exceeded.
  waiting for getByRole('textbox', { name: 'Ask about your documents' })
```

I add an axe scan to each flow test and fail on serious or critical violations.

</Level>

<Level name="Advanced">

Performance has two sides. Lab budgets run in CI (Lighthouse CI asserting LCP, CLS and total JS).
Field numbers come from real-user monitoring (the `web-vitals` library sending LCP, INP and CLS with
the route and release). For the streamed answer, INP is the number to watch. Typing in the box and
pressing Enter must stay responsive while tokens stream in, so DOM updates are batched once per
animation frame, not once per token.

```ts
let buf = ''; let scheduled = false;
stream.on('token', (t) => {
  buf += t;
  if (!scheduled) { scheduled = true; requestAnimationFrame(() => { el.append(buf); buf = ''; scheduled = false; }); }
});
```

</Level>

<Level name="Edge cases">

- **Slow network:** uploads show real progress and can be cancelled. The streamed answer shows
  something within the first second.
- **320 px width and 200% zoom:** no horizontal scroll on core flows, and buttons stay reachable.
- **Answer finishes while focus is elsewhere:** a polite live region announces it without moving focus.

</Level>

<Level name="Corner cases">

- **Reduced motion:** the streaming cursor and skeleton shimmer respect `prefers-reduced-motion`.
- **Double submit:** the ask button is disabled while a request is in flight, and the server is
  idempotent anyway.
- **Back button mid-stream:** the request is aborted with an `AbortController`, so tokens aren't
  billed for a page nobody is looking at.

</Level>

<Level name="Production level">

Front-end errors go to error tracking with release version and route. Source maps are uploaded but
not served publicly. Field vitals are on the dashboard, split by device class.

</Level>

<Level name="Mindset">

A flow is done when someone using only a keyboard or a screen reader can finish it, on a slow phone.

</Level>

<Level name="System design">

The core flows are the contract between product and code. Their tests run on every deploy and against
staging after every deploy, so a broken flow blocks the release.

</Level>

<Level name="Strategy">

Week 64: the four flow tests come first, then the UI to make them pass. Done when they pass in CI with
axe clean, lab budgets are asserted, and field vitals are reporting.

</Level>

#### Phase 12: A backend with validation, rate limits, jobs and useful errors

The backend's job is to be predictable. Bad input gets a clear answer, abuse gets slowed down, slow
work moves to the background, and every failure leaves a trail I can follow.

<Levels label="Phase 12, backend validation, rate limits, jobs, errors">

<Level name="Beginner">

Validation happens at the boundary, before any handler logic runs. A schema library turns
"unknown JSON" into a typed value or a list of problems:

```ts
const CreateDoc = z.object({ title: z.string().trim().min(1).max(200), sourceUrl: z.string().url().optional() });

app.post('/api/documents', async (req, res) => {
  const parsed = CreateDoc.safeParse(req.body);
  if (!parsed.success) return sendError(res, 422, 'validation_failed', parsed.error.flatten().fieldErrors);
  const doc = await createDocument(req.ctx, parsed.data);
  res.status(201).json(doc);
});
```

Common mistake: returning the raw exception to the user, stack trace and SQL included. Fix: log the
full error with the request id, and return the standard shape with that id.

</Level>

<Level name="Intermediate">

Rate limits protect two things: availability and money. AI endpoints get a per-user limit and a
per-tenant limit. Sign-in gets per-account and per-IP limits. The response tells the client when to
retry:

```text
HTTP/1.1 429 Too Many Requests
Retry-After: 12
{"error":"rate_limited","message":"Too many questions. Try again in 12 seconds.","requestId":"req_91ab"}
```

Jobs: document ingest runs in a queue backed by Postgres (`SELECT ... FOR UPDATE SKIP LOCKED`). Each
job is idempotent, retried with exponential backoff and jitter, and dead-lettered after five
attempts. The user sees progress in the UI, for example "indexing 3 of 10".

```sql
UPDATE jobs SET locked_at = now(), attempts = attempts + 1
WHERE id = (SELECT id FROM jobs WHERE run_at <= now() AND locked_at IS NULL
            ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING *;
```

</Level>

<Level name="Advanced">

Idempotency keys make retries from clients safe. The client sends a key, the server stores the first
response under that key, and any repeat gets the stored response back:

```ts
const prior = await db.idem.find(ctx.tenantId, key);
if (prior) return res.status(prior.status).json(prior.body);   // replay, no second side effect
const result = await doUpload(ctx, body);
await db.idem.insert({ tenantId: ctx.tenantId, key, status: 201, body: result });
```

The insert and the side effect share a transaction where they can. Timeouts are set on every outbound
call, so one slow dependency can't hold every worker.

</Level>

<Level name="Edge cases">

- **Payload too large:** 413 with the limit in the message. Uploads go straight to object storage
  with a signed URL, so big files never pass through the app server.
- **Unknown fields in the body:** the schema strips or rejects them. It never passes them through to
  the database (mass assignment).
- **Client disconnects mid-request:** handlers check the abort signal before expensive steps.

</Level>

<Level name="Corner cases">

- **Job retried after its document was deleted:** the job loads the row first and exits cleanly if
  it's gone. That's a success, not a dead letter.
- **Poison message:** one malformed file fails every time. The dead-letter queue holds it with the
  error, and an alert fires on dead-letter count, not on each failure.

</Level>

<Level name="Production level">

Error rate per route, p95 per route, queue depth, oldest job age and dead-letter count are metrics
with alerts. Every 5xx has a request id that leads to the trace.

</Level>

<Level name="Mindset">

A useful error saves a support request, and a useful log saves an hour of an incident.

</Level>

<Level name="System design">

Validation, limits, context and error mapping live in middleware, so handlers stay small and look the
same. Workers use the same context and error types as HTTP.

</Level>

<Level name="Strategy">

Week 64: I fuzz every endpoint with invalid and oversized input. Done when all of them return the
standard shape, none returns a 500, and the job queue survives a killed worker with no lost or
duplicated work.

</Level>

</Levels>

<Levels label="Phase 12, the AI feature">

<Level name="Beginner">

The feature answers questions about a tenant's own documents. It cites the passages it used, and it
says "I can't find that in your documents" when nothing relevant comes back. Refusal is a feature,
not a failure. A confident wrong answer is worse than an honest "not found".

Common mistake: tuning by feel in the last week ("this answer looks better now"). Fix: every change
goes through the eval suite, and the PR shows the before and after table.

</Level>

<Level name="Intermediate">

The eval suite grows from use. Every thumbs-down is triaged into the taxonomy, and many become cases:

```ts
{ id: 'c-041', tenant: 'sample-legal', q: 'What is the termination notice period?',
  mustCite: ['contract.pdf#p3'], expect: 'states 30 days', kind: 'faithful' },
{ id: 'c-042', tenant: 'sample-legal', q: 'What is the CEO salary?',
  expect: 'refuses: not in documents', kind: 'refusal' },
```

CI output on a PR:

```text

  faithful   44 -> 46
  cited      50 -> 50
  refusal     6 -> 5   REGRESSION c-042 answered with an invented figure
  p95 ms      recorded per run
  cost/case   recorded per run

```

</Level>

<Level name="Advanced">

Citation enforcement is code, not trust in the prompt. After generation, every cited id is checked
against the retrieved set. An answer citing a chunk that wasn't retrieved is rejected and retried
once, or shown with that citation removed and a warning. Guardrails run on input (length,
prompt-injection markers in retrieved text kept as data, never as instructions) and on output (PII
patterns, no URLs that aren't in the sources).

I report quality through the taxonomy: what share of bad answers were retrieval, context or
generation failures this week, and which fix I made for the biggest class, with eval evidence.

</Level>

<Level name="Edge cases">

- **A tenant with one short document:** most questions should refuse. I check that the refusal UX
  suggests uploading more, instead of reading as an error.
- **A question in a different language from the documents:** retrieval quality drops. That's an eval
  case and a known limit in the user guide.

</Level>

<Level name="Corner cases">

- **Budget used up mid-month for one tenant:** the feature switches to search-only mode with a clear
  message. The tenant owner and I both get alerted. Other tenants aren't affected.
- **A document edited after an answer cited it:** the citation link points to the version it cited,
  or shows a "source has changed" note.

</Level>

<Level name="Production level">

Prompt and model versions live in a registry and get logged with every trace. Rollback to the previous
pair has been rehearsed. A provider outage drops the feature to search results after a timeout.
Cost per successful answer is a tracked metric, not a guess.

</Level>

<Level name="Mindset">

The AI feature is one component with numbers, like the database. It earns trust through evals and
traces, not through demos.

</Level>

<Level name="System design">

It uses the same auth context, tenancy, job queue, rate limits and observability as everything else.
There's no side door for AI.

</Level>

<Level name="Strategy">

Week 65. Done when the eval dashboard shows the trend across the capstone weeks, one improvement
backed by eval evidence, citation enforcement tested, and the budget cutover rehearsed.

</Level>

</Levels>

<Level name="Beginner">

<Level name="Intermediate">

<Level name="Advanced">

<Level name="Edge cases">

<Level name="Corner cases">

<Level name="Mindset">

Observability is how I learn what the system actually does, as opposed to what I designed it to do.

<Level name="System design">

<Levels label="Phase 12, security">

<Level name="Beginner">

A threat model starts with the architecture diagram and asks, at each boundary: what could go wrong
here, and what stops it? STRIDE is a handy prompt list: spoofing, tampering, repudiation, information
disclosure, denial of service, elevation of privilege. Each threat gets one row with a control and a
test.

Common mistake: writing it once and never coming back. Fix: any PR that adds a boundary (a new
provider, a new upload type) updates the threat model.

</Level>

<Level name="Intermediate">

The automated parts run in CI:

```bash
gitleaks detect --source . --redact        # secrets in the working tree and history
npm audit --omit=dev --audit-level=high    # known vulnerabilities in runtime deps
```

```text
Finding:     STRIPE_SECRET_KEY=sk_test_****
File:        scripts/seed.ts   Line: 4
Commit:      3e1a...           1 leak found
```

Even a test key gets rotated, because the habit matters more than the key. Response headers are set
once: a Content-Security-Policy that blocks inline scripts, HSTS, frame-ancestors none, and
`X-Content-Type-Options: nosniff`.

</Level>

<Level name="Advanced">

The AI section of the threat model has its own rows. Retrieved documents can contain instructions
(indirect prompt injection), so retrieved text is treated as data, the model has no write tools, and
anything with side effects needs my approval. Data sent to the provider is listed, along with the
provider's retention terms. Uploads get type-checked by content, not just extension, size-limited, and
parsed in a worker with no network access to internal services (to block SSRF through document URLs).

</Level>

<Level name="Edge cases">

- **A vulnerable package with no fix yet:** check whether the vulnerable path is actually reachable,
  write down the exposure and the mitigation, and set a date to check again. Never ignore it quietly.
- **A dev-only dependency flagged:** lower priority, but still tracked.

</Level>

<Level name="Corner cases">

- **A secret found in an old commit:** rotate it first, then clean history if needed. Cleaning
  history doesn't revoke a key that's already been cloned.
- **SVG upload:** it can carry scripts. I serve uploads from a separate origin with a
  `Content-Disposition` header, or convert them.

</Level>

<Level name="Production level">

Security findings are tracked like bugs, with severity, owner and date. Dependencies are updated on
a schedule, in small batches, with tests. Access to production is limited, logged, and needs 2FA.

</Level>

<Level name="Mindset">

Security is a property of the system I keep up, not a review I pass once.

</Level>

<Level name="System design">

The threat model follows the trust boundaries on the architecture diagram. New boundaries need a row
before the code can merge.

</Level>

<Level name="Strategy">

Week 66. Done when each row in the threat model has a tested control and CI blocks secrets and
high-severity vulnerabilities.

</Level>

</Levels>

<Levels label="Phase 12, billing or metering">

<Level name="Beginner">

Metering counts what each tenant uses, like questions answered and tokens spent, in an append-only
usage table. Billing turns plans and usage into charges through a payment provider. In test mode, no
real money moves, but the code paths are real.

Common mistake: trusting the redirect after checkout ("success page reached, so they paid"). Fix:
entitlements change only when a verified webhook arrives.

</Level>

<Level name="Intermediate">

```ts
export async function handleWebhook(rawBody: Buffer, signature: string) {
  const event = provider.verify(rawBody, signature, env.WEBHOOK_SECRET); // throws if forged
  if (await db.webhookEvents.exists(event.id)) return;                   // idempotent
  await db.tx(async (t) => {
    await t.webhookEvents.insert({ id: event.id, type: event.type });
    if (event.type === 'subscription.updated') await t.entitlements.sync(event.data);
  });
}
```

Features ask the billing module ("may tenant 42 ask another question?"). They never ask the provider
directly.

</Level>

<Level name="Advanced">

Allowances come from the phase 10 cost model. If a plan's allowance is used in full at the worst
realistic cost per answer, it still covers its price. I keep that calculation in an ADR and check it
against real cost per answer every month.

</Level>

<Level name="Edge cases">

- **Webhook arrives before my user record exists:** return an error so the provider retries later.
  The handler is idempotent, so retries are safe.
- **Webhooks out of order:** use the event's own timestamp or version. Never let an older event
  overwrite a newer state.

</Level>

<Level name="Corner cases">

- **Plan change mid-cycle after usage is consumed:** pick one rule (for example, new allowance from
  now on, no refund of usage), write it in the user guide, and test it.
- **Failed payment during heavy use:** grace period with a banner, then downgrade. Data is never
  deleted for non-payment without notice.

</Level>

<Level name="Production level">

A daily reconciliation job compares usage totals and subscription states with the provider and alerts
on any mismatch.

</Level>

<Level name="Mindset">

Money paths get the most tests per line in the codebase.

</Level>

<Level name="System design">

Billing is a module with its own tables, events and webhook endpoint, and one interface for
entitlements.

</Level>

<Level name="Strategy">
