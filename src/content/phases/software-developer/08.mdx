Months 14 to 18: turn the evidence from phases 0 to 7 into interviews, referrals, paid work or a product
with users. The goal is that a senior engineer can look at my work and say what I would be trusted with.
Nothing here is new technology. It is narrative, proof and practice. *The Pragmatic Programmer* is the
book I reread here, for judgment, and *Designing Data-Intensive Applications* goes with the system
design topic, read now that I have operated something.

#### Phase 8: how I would learn it

I work in two-week blocks, each ending with one visible artefact: a case study, a merged open-source pull
request, a mock interview recording I reviewed, a system design write-up. Applications run in parallel
from week 60, not after everything is "ready", because the market gives feedback faster than I can guess.
I keep a career log the same way I kept the bug log: what I tried, what happened, what I change.

<Levels label="Phase 8, portfolio narrative">

<Level name="Beginner">

A portfolio answers one question for a busy reader: what can this person do for us? I write one sentence
that answers it, then choose only the work that proves that sentence. Everything else goes or moves down.

```md
I build and operate full-stack TypeScript products: React, Node and Postgres,
with AI features that are measured (evals, cost, refusal) and agents that are bounded.
Evidence: [Logbook case study] [RAG over my notes] [Maintainer agent]
```

Common mistake: a portfolio of clones with no narrative. Fix: fewer projects, each with a reason it exists.

</Level>

<Level name="Intermediate">

Each project entry has the same shape: the problem in a sentence, my role, the hardest decision, a number,
and links (live, repo, case study). The reader should get the point in thirty seconds and the depth in
five minutes.

</Level>

<Level name="Advanced">

The narrative matches the roles I want. If I want backend-leaning roles, the backend and data evidence
leads. One portfolio can have two orderings for two kinds of application, with the same evidence.

</Level>

<Level name="Edge cases">

- A project that is private (paid work): describe the problem and decisions without code or names, with
  permission.

</Level>

<Level name="Corner cases">

- A strong project that does not fit the narrative: keep it lower down; do not bend the narrative around it.

</Level>

<Level name="Production level">

Every link works, every demo is up, every README runs. A broken demo costs more than a missing one. A
monthly link check, the same idea as this site's build check.

</Level>

<Level name="Mindset">

A portfolio is an argument with evidence, not a scrapbook.

</Level>

<Level name="System design">

  caption="How a reviewer reads, so how I order it"
  steps={['one sentence', 'first case study', 'a number', 'the live link', 'the repo, if still curious']}
/>

</Level>

<Level name="Strategy">

Write the sentence, cut everything that does not support it. Done when a stranger reads the page for one
minute and repeats the sentence back with one piece of evidence.

</Level>

</Levels>

#### Phase 8: Case studies

**Covers:** three one-page write-ups of real projects: problem, constraints, decisions, outcome, written so
a stranger can judge my thinking.

<Figure art={`
  +--------------------------------------------------------------+
  | Problem       who, when, cost, workaround           3 lines  |
  | Constraints   time, team, budget, tech              3 lines  |
  | Decisions     3-5 x (options, choice, why, cost)    the core |
  | Outcome       numbers, users, what changed          5 lines  |
  | Failure       what broke, what I changed            5 lines  |
  | Links         live, repo, trace, postmortem                  |
  +--------------------------------------------------------------+
`} caption="One page, the same shape every time" />

<Levels label="Phase 8, case studies">

<Level name="Beginner">

A case study is a project explained for someone deciding whether to trust me. It is not a tutorial and not
a feature list. Three is the plan's number: enough for a pattern, few enough to be good.

</Level>

<Level name="Intermediate">

My three candidates are already built: the full-stack app (isolation proven by a test), the RAG feature
(eval numbers, refusal), and the product with ten users (iterations, postmortem). The agent can replace
one if the role is about automation.

</Level>

<Level name="Advanced">

Decisions include the rejected option and the cost of my choice: "pgvector over a hosted vector store:
one database to operate, at the cost of tuning the index myself; measured recall was within noise".
Honest costs are what make the rest credible.

</Level>

<Level name="Edge cases">

- No impressive numbers: use honest small ones ("26 of 30 eval cases"), with context.

</Level>

<Level name="Corner cases">

- A team project: say exactly what I did and what others did. Overclaiming is found out in the first
  technical question.

</Level>

<Level name="Production level">

Each case study links to the trace, the postmortem, and the commit range, so a technical reviewer can
verify any claim.

</Level>

<Level name="Mindset">

Show the thinking, not just the result. Judgment is what is scarce.

</Level>

<Level name="System design">

The case studies are written from records kept in earlier phases (product log, ADRs, eval tables), which is
why those records mattered.

</Level>

<Level name="Strategy">

One case study per week for three weeks, each read by someone outside the project. Done when the plan's
gate is met: a stranger can explain what I would be trusted with.

</Level>

</Levels>

#### Phase 8: Open source

**Covers:** contributing five useful pull requests to projects I use: finding the right issue, following the
project's process, and getting code merged by strangers.

<Flow
  caption="A first contribution, start to merge"
  steps={['use the project', 'read CONTRIBUTING and recent merged PRs', 'pick a small, labelled issue', 'comment before starting', 'small PR with a test', 'respond to review', 'merged']}
/>

<Levels label="Phase 8, open source">

<Level name="Beginner">

Open source contributions show I can work in someone else's codebase, follow their rules and take review.
The best first PRs are small: a documentation fix I hit myself, a failing edge case with a test, a clearer
error message.

```bash
git clone https://github.com/<owner>/<project>.git && cd <project>
git checkout -b fix/clearer-error-on-empty-config
# read CONTRIBUTING.md, run the tests first, so I know they pass before I change anything
npm test
```

Common mistake: a large unrequested refactor as a first PR. It sits unreviewed. Fix: small, asked-for,
tested.

</Level>

<Level name="Intermediate">

I contribute to projects I actually use, because I understand the user side. I read a few recent merged PRs
to learn the style, commit message format and how maintainers review.

</Level>

<Level name="Advanced">

Over five PRs, I grow scope: docs, a test, a bug fix, a small feature, a review on someone else's PR. That
trail shows progression, which is more convincing than five typo fixes.

</Level>

<Level name="Edge cases">

- An issue someone else claimed months ago: ask politely before taking it.
- A PR that is never reviewed: a polite ping after a reasonable wait, then move on.

</Level>

<Level name="Corner cases">

- A PR rejected for design reasons after I did the work: that is why I comment first. Learn the reason;
  it is often a lesson about the project's constraints.

</Level>

<Level name="Production level">

Contributions follow licences, sign-off rules (some projects require a DCO sign-off), and AI-use policies
where projects have them. If a project asks contributors to disclose AI help, I disclose it.

</Level>

<Level name="Mindset">

Maintainers are volunteers or busy staff. Make my PR the easiest one they review this week.

</Level>

<Level name="System design">

Reading an unfamiliar repository is the same skill as joining a team: find the entry point, run the tests,
trace one request, then change one thing.

</Level>

<Level name="Strategy">

One PR every two weeks. Done when five are merged and one of them is a fix with a test.

</Level>

</Levels>

#### Phase 8: Code review

**Covers:** reviewing others' code and taking review on mine: what to look for, how to say it, and how to
respond.

<Compare
  left="Unhelpful review"
  right="Helpful review"
  caption="Same concern, two ways to raise it"
  rows={[
    ['"This is wrong."', '"If items is empty this returns undefined and the caller renders nothing. Could it return [] instead?"'],
    ['Twenty style nits', 'Linters for style; humans for behaviour, names, boundaries'],
    ['Approve without running it', 'Run it, read the test, check the edge case'],
    ['Silent approval', 'Say what was good and why'],
  ]}
/>

<Levels label="Phase 8, code review">

<Level name="Beginner">

A review checks that the change does what it says, does not break anything else, and will be clear to the
next reader. I read the description first, then the tests, then the code.

</Level>

<Level name="Intermediate">

My checklist: correctness on edge inputs, error handling, security (authorization, validation, output
encoding), tests that assert behaviour, names, and whether the change fits the existing design. Comments
say what, why, and a suggestion.

</Level>

<Level name="Advanced">

Reviewing AI-generated code is now a core skill: it compiles and looks plausible, so I check behaviour on
the inputs that matter, whether the tests assert anything (mutation testing from phase 4), and whether it
invented an API.

</Level>

<Level name="Edge cases">

- A huge PR: ask to split it, or review in passes (design, then details).

</Level>

<Level name="Corner cases">

- A reviewer and author disagree on taste with no correctness issue: the author decides, or the team's
  convention does. Not worth a week.

</Level>

<Level name="Production level">

Review latency matters: a PR waiting days blocks people. Small PRs and same-day reviews.

</Level>

<Level name="Mindset">

Review the code, not the person. Take review on my code as free teaching.

</Level>

<Level name="System design">

Review is one gate among CI, tests and approval. Each catches different things; none replaces the others.

</Level>

<Level name="Strategy">

Review two open-source PRs a month alongside my own. Done when a maintainer acted on one of my review
comments.

</Level>

</Levels>

#### Phase 8: System design

**Covers:** designing a system at the whiteboard level: requirements, data model, APIs, scaling, failure,
and the trade-offs, explained aloud.

<Flow
  caption="A system design answer, in order"
  steps={['clarify requirements and scale', 'core entities and data model', 'API', 'high-level components', 'one deep dive', 'failures and bottlenecks', 'trade-offs I chose']}
/>

<Levels label="Phase 8, system design">

<Level name="Beginner">

System design questions ask how I would build something like a URL shortener or a notification service. The
interviewer wants to hear my process and trade-offs, not a memorized diagram. I start by asking what it must
do and at what scale.

```md
URL shortener: requirements
- create short link, redirect; 100 writes/s, 10k reads/s (assumed, stated aloud)
- links never change; custom aliases optional
Data: link(code PK, url, owner_id, created_at)
API: POST /links -> {code}; GET /:code -> 301/302
```

</Level>

<Level name="Intermediate">

Back-of-the-envelope numbers decide the design: reads per second, storage per year, cache hit rates. I
state assumptions aloud and round generously.

</Level>

<Level name="Advanced">

The deep dive is where my own experience shows: caching and invalidation, a queue with retries and
dead-letter, idempotency, a read replica and its lag. I use what I built in phases 3 to 6, and say so.

</Level>

<Level name="Edge cases">

- Requirements that change mid-interview: that is the test. Revisit the earlier choice openly.

</Level>

<Level name="Corner cases">

- A design that scales but cannot be operated by the stated team: mention operational cost as a
  trade-off.

</Level>

<Level name="Production level">

Real system design is written: a design doc with goals, non-goals, alternatives and a failure matrix.
Interview design is the spoken version of the same thing.

</Level>

<Level name="Mindset">

There is no correct design, only defended trade-offs.

</Level>

<Level name="System design">

<Levels label="Phase 8, interviews">

<Level name="Beginner">

Interviews are a skill separate from the job, and they improve with practice. Mock interviews with a
friend or a peer, recorded and reviewed, are the fastest way to improve.

</Level>

<Level name="Intermediate">

Coding rounds: restate the problem, give examples including an edge case, say the brute force, improve it,
code it, test it by hand. Some practice problems help; LeetCode as a whole career plan does not.

```ts
// Think aloud, then test aloud:
// input [] -> 0 ; input [5] -> 5 ; input with negatives -> ?
function maxSubarray(nums: number[]): number {
  if (nums.length === 0) return 0;          // say the choice aloud: empty means 0 here
  let best = nums[0], cur = nums[0];
  for (let i = 1; i < nums.length; i++) { cur = Math.max(nums[i], cur + nums[i]); best = Math.max(best, cur); }
  return best;
}
console.log(maxSubarray([-2, 1, -3, 4, -1, 2, 1, -5, 4])); // 6
```

</Level>

<Level name="Advanced">

Behavioural stories use a clear shape (situation, task, action, result), each from my records: the stale
closure bug, the RAG refusal threshold, the agent that hit its budget. Real details beat polished
generalities.

</Level>

<Level name="Edge cases">

- A question I cannot answer: say what I know, how I would find out, and ask a clarifying question.

</Level>

<Level name="Corner cases">

- "How do you use AI?" asked as a trap: the plan's answer is the right one. "I let it write everything" is
  a red flag; "I use it for the first draft, then review the diff, add tests and measure the result" is a
  skill. And I have a failure story ready.

</Level>

<Level name="Production level">

A tracker for applications: company, role, stage, date, notes, next step. Patterns in rejections tell me
what to fix.

</Level>

<Level name="Mindset">

Optimize for the work, not just the interview. The interview should be a sample of the work.

</Level>

<Level name="Strategy">

<Level name="System design">

#### Phase 8: Negotiation

**Covers:** preparing for an offer: knowing what matters to me, researching the range, and asking clearly.

<Flow
  caption="Before, during and after an offer"
  steps={['write what matters (money, learning, team, remote)', 'research ranges for role and city', 'receive offer in writing', 'ask questions, then counter once with reasons', 'decide against my list']}
/>

<Levels label="Phase 8, negotiation">

<Level name="Beginner">

An offer is the start of a conversation. Asking politely for more, with reasons, is normal. I write down
what matters to me before any offer, so the decision is mine and not the moment's.

</Level>

<Level name="Intermediate">

I research ranges from several sources for the role, level and location, and look at the whole offer:
base, bonus, equity, leave, learning budget, remote, notice period.

</Level>

<Level name="Advanced">

A counter names a number and the reason (a competing offer, the evidence of scope I can own). One clear
counter beats many small ones.

</Level>

<Level name="Edge cases">

- An exploding offer with a very short deadline: ask for more time; a reasonable employer usually agrees.

</Level>

<Level name="Corner cases">

- Two offers with different structures (higher base versus equity): compare expected values with honest
  assumptions, and weigh the learning.

</Level>

<Level name="Production level">

Everything agreed is in writing before I resign anywhere or decline other options.

</Level>

<Level name="Mindset">

Negotiation is a normal professional conversation, not a confrontation.

</Level>

<Level name="System design">

My list of what matters is the decision function; the research is the input data; the offer is just one
evaluation.

</Level>

<Level name="Strategy">

Write the list and the ranges before the first final round. Done when I can state my walk-away point and
my target with reasons.

</Level>

</Levels>

#### Phase 8: The AI usage story

**Covers:** a concrete, honest account of how I use AI and how I verify it, with a failure story, because
companies now ask.

<Compare
  left="Red flag"
  right="A skill"
  caption="The plan's own contrast, as answers I would give"
  rows={[
    ['"I let it write everything."', '"I use it for the first draft, then review the diff, add tests and measure the result."'],
    ['"It is always right."', '"Here is when it was wrong and how my tests caught it."'],
    ['Hiding AI use', 'Saying exactly where it helps and where I do not use it'],
  ]}
/>

<Levels label="Phase 8, the AI usage story">

<Level name="Beginner">

I write my workflow down in a paragraph: where AI helps (first drafts, test scaffolding, explaining
errors), where I do not use it (the data model, auth boundaries, the final review), and how I verify.

</Level>

<Level name="Intermediate">

The failure story is specific: what it produced, why it looked right, how I caught it (a test, an eval, a
review), and the rule I keep now. My bug log has these.

</Level>

<Level name="Advanced">

My projects show the verification: eval sets, approval gates, traces. I can point to them while telling the
story.

</Level>

<Level name="Edge cases">

- A company that bans AI tools: I can work without them, and say so; phases 0 and 1 were typed by hand.

</Level>

<Level name="Corner cases">

- A company that expects heavy AI use: I describe the guardrails I bring, which is exactly what they need.

</Level>

<Level name="Production level">

I follow each employer's and project's AI policy, including on what code and data may be sent to a provider.

</Level>

<Level name="Mindset">

Lying about AI usage is a plan-named trap. Honesty about it is now part of professional trust.

</Level>

<Level name="System design">

The AI-era split (delegate, keep, verify) is my answer's structure, with examples from each column.

</Level>

<Level name="Strategy">

Write it, then say it aloud in a mock. Done when the answer takes two minutes and includes a real failure.

</Level>

</Levels>

#### Phase 8: the gate

Present three case studies. Pass: a stranger can explain what I would be trusted with. With it, the plan's
proof: interviews, referrals, paid work, or a launched product with users. Then the AI-assisted half:
every line in the case studies is mine to defend, including the parts AI helped me draft.
