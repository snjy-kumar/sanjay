Two weeks to stop being afraid of the three things every later phase assumes: the terminal, the
browser and the deploy. Nothing here is hard on its own. What makes it matter is that every bug I
will chase for the next eighteen months passes through one of these layers: a path that is wrong,
a commit that is missing, a request that came back 404, a DNS record that has not propagated, a
JSON body that does not parse. This phase builds the memory I debug against later.

The ship is small on purpose: one page of semantic HTML and one CSS file, in a repository with ten
real commits and a README, deployed to GitHub Pages at a public URL. The proof is that I can explain,
without notes, everything that happens between typing that URL and seeing the page.

#### Phase 0: how I would learn it

Every topic follows the same loop: do it by hand once, break it on purpose, read the error, then
write the rule down in the bug log. No video longer than the task it explains. The AI rule for this
phase is strict: a model may explain an error message or a Git command, but it does not write the
first page. I need one memory of doing it myself.

<Levels label="Phase 0, the terminal and file paths">

<Level name="Beginner">

The terminal is a text conversation with the operating system. I type a command, the shell finds a
program with that name, runs it with my arguments, and prints what the program prints. Five commands
cover the first day: `pwd` (where am I), `ls` (what is here), `cd` (go somewhere), `mkdir` (make a
folder) and `touch` or an editor (make a file).

```sh
$ pwd
/home/sanjay
$ mkdir -p projects/page && cd projects/page
$ touch index.html
$ ls
index.html
```

A path is the address of a file. If it starts with `/` it is absolute and means the same thing from
anywhere. If it does not, it is relative to the current directory, and `.` means here while `..`
means one level up. `~` is the shell's shorthand for my home directory.

The first common mistake is running a command in the wrong folder: `ls` shows nothing, or
`cat index.html` says `No such file or directory`. The fix is always the same two commands: `pwd` to
see where I am, `ls` to see what is actually there, before I assume anything.

</Level>

<Level name="Intermediate">

Commands become useful when they combine. Every program has three streams: standard input, standard
output and standard error. A pipe `|` connects one program's output to the next one's input; `>`
writes output to a file (replacing it) and `>>` appends.

```sh
$ ls -la                      # long listing, including hidden dotfiles
$ grep -rn "TODO" .           # search every file under here for TODO
./index.html:12:<!-- TODO: footer -->
$ grep -rn "TODO" . | wc -l   # how many TODOs
1
$ history | tail -n 5         # the last five commands I ran
```

Flags change behaviour (`-l` long, `-a` all, `-r` recursive, `-n` line numbers), and `man ls` or
`ls --help` lists them. Tab completion finishes names so I never type a long path by hand; pressing
Tab twice shows the choices. The up arrow brings back the last command and `Ctrl-R` searches history.

Mistake: `rm -r` with a typo, or with a variable that is empty. There is no recycle bin. The fix is
a habit: run `ls` on exactly the same path first, and only then replace `ls` with `rm`.

</Level>

<Level name="Advanced">

The shell is itself a program (bash or zsh) that parses the line before anything runs. It expands
`~`, variables like `$HOME`, globs like `*.html` and command substitution like `$(date)`, then splits
the result into words, then looks up the first word. Lookup checks aliases, shell functions,
built-ins (`cd` must be a built-in, because a child process cannot change its parent's directory),
and finally each folder in `$PATH`, in order.

```sh
$ echo $PATH
/home/sanjay/.local/bin:/usr/local/bin:/usr/bin:/bin
$ which node
/usr/local/bin/node
$ type cd
cd is a shell builtin
$ echo $?            # exit code of the last command: 0 means success
0
$ ls nope; echo $?
ls: cannot access 'nope': No such file or directory
2
```

Every program exits with a number. Zero means success and anything else is a failure, which is what
`&&` (run the next only on success) and `||` (run the next only on failure) test. That one convention
is how CI decides whether a build is green years from now.

Mistake: `command not found` after installing something. The program exists but its folder is not on
`$PATH`, or the shell has not reloaded its config. The fix is `which` to confirm, then adding the
folder to `PATH` in `~/.bashrc` or `~/.zshrc` and opening a new terminal.

</Level>

<Level name="Edge cases">

File names with spaces split into two arguments unless they are quoted: `cd My Site` tries to enter
a folder called `My`. Quote them (`cd "My Site"`) or, better, never create them in a project. A glob
that matches nothing is passed through literally in bash, so `rm *.tmp` in a folder with no `.tmp`
files tries to delete a file literally named `*.tmp` and prints an error rather than doing nothing.

Hidden files start with a dot and `ls` skips them: `.git`, `.env`, `.gitignore`. A repository that
"has no Git" may just have a `.git` folder I cannot see without `ls -a`. Case matters on Linux and on
GitHub Pages but not, by default, on macOS: `Index.html` and `index.html` are the same file on my
laptop and two different files on the server.

```sh
$ ls
Index.html
$ open http://localhost:8000/index.html   # works on macOS
# deployed: https://user.github.io/page/index.html -> 404
```

</Level>

<Level name="Corner cases">

Two boundaries at once: a relative path inside a script that is run from a different folder. The
script says `cat data/list.txt`, works when I run it from the project root, and fails from anywhere
else, because relative paths resolve against the current directory, not the script's location. The
fix is to resolve from the script's own folder (`"$(dirname "$0")/data/list.txt"` in a shell script,
`new URL('./data/list.txt', import.meta.url)` in a Node module).

Another: case-insensitivity plus Git. Renaming `Index.html` to `index.html` on macOS can leave Git
thinking nothing changed, so the server keeps the old capitalised name and the link breaks only in
production. The fix is `git mv Index.html index.html`, which records the rename explicitly.

</Level>

<Level name="Production level">

On a server there is no desktop, only the terminal, often over `ssh`, and often at the worst moment.
The commands that matter there are the same ones: `pwd`, `ls -la`, `cat`, `less`, `tail -f` on a log,
`grep` for an error, `df -h` for a full disk, `ps` and `kill` for a stuck process. Scripts run by CI
use `set -euo pipefail` so that an error, an unset variable or a failed stage of a pipe stops the
script instead of carrying on with bad data.

```sh
#!/usr/bin/env bash
set -euo pipefail
OUT="${OUT_DIR:?OUT_DIR must be set}"   # fails loudly instead of rm -rf "/"
rm -rf "$OUT"/*
```

The classic outage is a cleanup script that ran `rm -rf "$DIR/"*` with `DIR` empty. The fix is
the `:?` guard above, and the rule: destructive commands never trust an unchecked variable.

</Level>

<Level name="Mindset">

The terminal teaches me to state exactly what I want and to read exactly what came back. A GUI hides
the error; the terminal prints it. Most beginner frustration is skipping the output: the error message
almost always names the file, the line and the reason. I read the whole message, top line first,
before I search for anything.

</Level>

<Level name="System design">

Every larger system I build is a pipeline of small programs passing text or bytes, with exit codes
as the contract: the build calls the compiler, CI calls the build, the deploy calls CI's artefact.
Paths are configuration: a service that hard-codes `/home/sanjay/...` breaks in a container, so later
systems read paths from environment variables and resolve them relative to known roots. The habits
from day one, small composable commands, explicit paths, checked exit codes, are the same habits at
the scale of a deploy pipeline.

</Level>

<Level name="Strategy">

For two days I do everything from the terminal: create the page project, move files, search them,
delete the scratch folders. I keep a cheat sheet of only the commands I actually used. Then I break it
on purpose: run a script from the wrong folder, delete a file with a space in its name, call a program
that is not on `PATH`, and log each error with its fix.

Done when I can, without notes, create a project tree, move around it with relative and absolute paths,
find every occurrence of a word with `grep`, explain what `$PATH` and `$?` are, and recover from
`command not found` and `No such file or directory` in under a minute.

</Level>

</Levels>

<Levels label="Phase 0, an editor I can drive without the mouse">

<Level name="Beginner">

An editor is where I spend most of my working hours, so a little speed compounds. I pick one, VS Code
is the default for web work, and learn five moves: open a file by name, search the whole project,
go to a line, toggle the integrated terminal, and save. Nothing else on day one.

The first thing to configure is not a theme but formatting on save and showing whitespace, so that
the file I see is the file Git sees. Two settings in `settings.json` are enough:

```json
{
  "editor.formatOnSave": true,
  "editor.renderWhitespace": "boundary"
}
```

Mistake: installing thirty extensions in the first hour. Each one adds noise, popups and sometimes
conflicting formatters. The fix is to start with none and add one only when I can name the problem
it solves.

</Level>

<Level name="Intermediate">

The moves that pay most are multi-cursor and symbol navigation. `Ctrl/Cmd-D` selects the next
occurrence of the current word, so renaming a CSS class in five places is five key presses. `F2`
renames a symbol across files using the language server, which understands scope, so it renames the
variable `item` without touching the word `item` inside a string.

```js
// cursor on `total`, press F2, type `subtotal`
let total = 0;
for (const item of cart) total += item.price;
console.log("total:", total);   // the string is left alone; both variables change
```

Project-wide search (`Ctrl/Cmd-Shift-F`) with a regular expression finds patterns: `class="btn[^"]*"`
finds every button class. The command palette (`Ctrl/Cmd-Shift-P`) is the index of everything the
editor can do; when I forget a shortcut, I type what I want there.

</Level>

<Level name="Advanced">

Underneath, the editor runs language servers: separate processes that parse my code and answer
questions over the Language Server Protocol, such as where a symbol is defined, what type it has and
what is wrong with it. The red squiggle under a TypeScript error is the same compiler I run in the
terminal, run continuously. When the editor and the terminal disagree, it is usually because they use
different versions or different config files.

```sh
$ npx tsc --noEmit
src/app.ts:4:7 - error TS2322: Type 'string' is not assignable to type 'number'.
```

If the editor shows no error but `tsc` does, I check which TypeScript the editor uses (the status bar
or "TypeScript: Select TypeScript Version") and point it at the workspace's `node_modules`.

</Level>

<Level name="Edge cases">

Line endings: Windows writes CRLF, Linux and macOS write LF. A file with mixed endings shows every line
as changed in a diff. The fix is a `.gitattributes` with `* text=auto eol=lf` and the editor's line
ending setting at the bottom right. A file saved with a byte order mark breaks some parsers: a JSON
file that starts with an invisible BOM fails `JSON.parse` with `Unexpected token`.

Format on save with no formatter config formats differently on every machine. The fix is to commit a
formatter config (for example `.prettierrc`) so the project, not the editor, decides.

</Level>

<Level name="Corner cases">

Format on save plus a large existing file: I change one line, save, and the formatter rewrites
four hundred lines, so the commit diff hides my real change. The fix is to format the whole file in
its own commit first ("Format index.html, no content change") and make the real change in the next
commit. Reviewers can then skip the first and read the second.

Multi-cursor plus a regex search-and-replace across the project: a pattern that matches more than I
think replaces it in `node_modules` or a minified file too. I preview the matches, exclude folders,
and run Git's diff before saving all.

</Level>

<Level name="Production level">

On a shared project the editor's behaviour has to be the repository's behaviour. That means a
committed `.editorconfig` (indentation, final newline, line endings), a formatter config, a lint
config, and recommended extensions in `.vscode/extensions.json`. Then every contributor's editor
produces the same bytes, and CI runs the same formatter and linter to catch anyone whose editor does
not.

```ini
# .editorconfig
root = true
[*]
indent_style = space
indent_size = 2
end_of_line = lf
insert_final_newline = true
```

I also learn to edit over SSH or in a dev container, because some bugs only reproduce on the machine
where the code runs.

</Level>

<Level name="Mindset">

Tools should disappear. The goal is not to collect shortcuts but to remove the moments where moving
the mouse breaks my train of thought. I learn a shortcut only when I notice I have done the slow
version three times.

</Level>

<Level name="System design">

The editor is the first stage of the feedback loop that the rest of the system extends: squiggle in
the editor, then the type check and tests on save, then lint and tests in CI, then monitoring in
production. The cheaper and earlier a stage catches an error, the better. Configuring the editor to
run the same checks as CI is the first piece of that design.

</Level>

<Level name="Strategy">

Two days, one rule: no mouse inside the editor. I keep a sticky note of the ten moves above and
remove each one when it is automatic. I commit an `.editorconfig` and a formatter config to the page
repository on day one.

Done when I can open any file by name, jump to any symbol, rename across files, search the project with
a regex and run the build in the integrated terminal, all without touching the mouse, and when a fresh
clone formats identically on another machine.

</Level>

</Levels>

<Levels label="Phase 0, Git from init to a pull request">

<Level name="Beginner">

Git records snapshots of a folder over time. `git init` starts tracking a folder, `git add` chooses
which changes go into the next snapshot, and `git commit` saves that snapshot with a message. `git
status` tells me which of those three states each file is in, and `git log` shows the history.

```sh
$ git init
Initialized empty Git repository in /home/sanjay/projects/page/.git/
$ git add index.html
$ git commit -m "Add the first page with a heading and a paragraph"
[main (root-commit) 3f2a1c9] Add the first page with a heading and a paragraph
 1 file changed, 12 insertions(+)
$ git log --oneline
3f2a1c9 Add the first page with a heading and a paragraph
```

A good commit is one idea with a message that says what changed and why, in plain words. Mistake:
one giant commit called `update` at the end of the day. The fix is to commit each time one small thing
works; the plan asks for ten meaningful commits, and that number is the habit, not a quota.

</Level>

<Level name="Intermediate">

Branches let me try something without disturbing `main`. `git switch -c footer` creates a branch and
moves to it; commits land there. When it works I push it, and on GitHub I open a pull request, which
is a proposal to merge that branch into `main` with a place for review and checks.

```sh
$ git switch -c footer
$ git add index.html css/site.css
$ git commit -m "Add a footer with the source link"
$ git remote add origin git@github.com:snjy-kumar/page.git
$ git push -u origin footer
# GitHub prints a link: Create a pull request for 'footer'
```

`git diff` shows unstaged changes and `git diff --staged` shows what the next commit will contain; I
read the staged diff before every commit. A `.gitignore` keeps generated or secret files, like
`node_modules/` and `.env`, out of history.

Mistake: committing straight to `main` and then wanting to undo. The fix is the branch-per-change
habit, so `main` always matches what is deployed.

</Level>

<Level name="Advanced">

Underneath, Git is a content-addressed store. Every file version is a blob named by the hash of its
contents; a tree lists blobs and subtrees; a commit points to one tree, its parent commits, an author
and a message. A branch is a small file containing one commit hash, and `HEAD` says which branch I am
on. That is why branching is instant: it writes a forty-character hash, nothing more.

```sh
$ cat .git/HEAD
ref: refs/heads/footer
$ cat .git/refs/heads/footer
a91e0c4f7d...
$ git cat-file -p a91e0c4
tree 5b1d...
parent 3f2a1c9...
author Sanjay Kumar <sanjay17126@gmail.com> 1761206400 +0530
```

A merge either fast-forwards (moves the label, if `main` has not moved) or creates a merge commit with
two parents. A rebase replays my commits on top of a new base, producing new hashes, which is why
rebasing commits that others already have rewrites their history too.

</Level>

<Level name="Edge cases">

An empty folder cannot be committed, because Git tracks files, not directories; people add a
`.gitkeep` file. A file added to `.gitignore` after it was committed is still tracked; `.gitignore`
only affects untracked files, so it needs `git rm --cached file`. The very first commit has no parent,
so `git diff HEAD~1` fails on it with `unknown revision`.

A detached HEAD, after `git checkout 3f2a1c9`, means new commits belong to no branch:

```sh
$ git checkout 3f2a1c9
You are in 'detached HEAD' state...
```

The fix if I committed there is `git switch -c rescue` before switching away, so the commits get a
name.

</Level>

<Level name="Corner cases">

A secret committed and then deleted in the next commit is still in history, and pushing that history
publishes it. Two boundaries meet: Git never forgets, and a public remote never forgets either. The
only real fix is to rotate the secret (make the old one useless), then clean history if needed. Prevent
it with `.gitignore` for `.env` before the first commit.

A merge conflict in a file that both branches reformatted: every line conflicts, though the real
changes are two lines. The fix is to land the formatting change on its own first, then merge.

```text
<<<<<<< HEAD
<footer>Built by hand</footer>
=======
<footer>Source on GitHub</footer>
>>>>>>> footer
```

I resolve by choosing the intended text, deleting the markers, then `git add` and `git commit`.

</Level>

<Level name="Production level">

On a team, `main` is protected: no direct pushes, a pull request with at least one review, and green
checks before merge. History is a debugging tool, so small commits with clear messages let `git
bisect` find the commit that introduced a bug in a handful of steps, and `git blame` explain why a line
exists. Force-pushing a shared branch destroys teammates' work; the rule is never force-push what
someone else may have pulled, and use `--force-with-lease` on my own branches.

```sh
$ git bisect start
$ git bisect bad            # current commit is broken
$ git bisect good v1.0      # this tag was fine
# Git checks out the midpoint; I test and mark good or bad until it names the commit
```

</Level>

<Level name="Mindset">

A commit is a message to a future reader, often me at 2am. It should say what changed and why, in a
sentence a stranger understands. Small reversible steps beat one heroic change, because every small
step is something I can undo.

</Level>

<Level name="System design">

Git is the source of truth for everything later: CI runs on a push, a deploy is a commit hash, a
rollback is a revert to a known commit, an infrastructure change is a pull request. Choosing a branch
model (trunk-based with short-lived branches is the default for small teams) decides how often code
integrates and how big each merge risk is.

</Level>

<Level name="Strategy">

Ten commits on the page repository, each one change with a real message, done by typing commands,
not clicking. Then one pull request from a branch, read on GitHub, merged. Then break it: make a
conflict on purpose, detach HEAD, commit an ignored file, and recover each time.

Done when I can draw the working tree, staging area, local repo and remote from memory, explain what a
branch and a merge commit are, resolve a conflict without a GUI, and open and merge a pull request.

</Level>

</Levels>



#### Phase 0: The pull request

<Flow
  caption="A pull request's life, even when I am the only person on the repository"
  steps={['git switch -c add-footer', 'Small commits on the branch', 'git push -u origin add-footer', 'Open the PR: title, why, how to check', 'Checks run; I read my own diff', 'Fix with new commits', 'Merge, delete the branch, pull main']}

<Levels label="Phase 0, the pull request">

<Level name="Beginner">

A pull request (PR) is a request to merge one branch into another, usually a feature branch into `main`, with a page on
GitHub that shows the diff, a discussion, and the results of automatic checks. Git itself has no pull requests; they
are a GitHub feature built on top of branches.

The smallest real loop, on my one-page site:

```sh
$ git switch -c add-footer
Switched to a new branch 'add-footer'
$ # edit index.html, add a footer
$ git add index.html
$ git commit -m "Add a footer with the source link"
$ git push -u origin add-footer
remote: Create a pull request for 'add-footer' on GitHub by visiting:
remote:      https://github.com/USER/site/pull/new/add-footer
```

I open that link, write a title and a description, and press "Create pull request". When I am happy, "Merge pull
request", then "Delete branch", then locally:

```sh
$ git switch main
$ git pull
$ git branch -d add-footer
Deleted branch add-footer (was 3f2a1c9).
```

Mistake: working on `main` "because it is just me". PRs are a habit, and the habit is what every team I will join
expects. Practising alone costs nothing.

</Level>

<Level name="Intermediate">

A good PR description answers three questions: what changed, why, and how a reviewer can check it.

```text
Add a footer with the source link

Why: visitors had no way to find the repository.
What: a <footer> with a link to the repo and the year, styled in style.css.
How to check: open the preview, scroll to the bottom, follow the link; tab to it with the keyboard.
```

The "Files changed" tab is where review happens. I read my own diff there before anyone else does, line by line, and
I catch things I never see in the editor: a stray `console.log`, a file I did not mean to commit, trailing whitespace,
a commented-out block. Comments can be left on specific lines; "Suggest changes" lets a reviewer propose an exact edit.

Fixing review feedback means more commits on the same branch and another push; the PR updates automatically.

</Level>

<Level name="Advanced">

Merge options change history. "Create a merge commit" keeps every branch commit and adds a merge commit. "Squash and
merge" combines the branch into one commit on `main`, good when the branch's commits were messy. "Rebase and merge"
replays the commits on top of `main` with no merge commit. A repository picks one so history stays readable.

When `main` moved while my branch was open, GitHub shows "This branch is out-of-date" or a conflict. I update locally:

```sh
$ git switch add-footer
$ git fetch origin
$ git merge origin/main
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.
```

I open the file, find the markers, keep the right lines, remove the markers, then `git add index.html` and
`git commit`. Push, and the PR updates.

</Level>

<Level name="Edge cases">

A PR that is too big does not get reviewed; it gets approved. Keep PRs small enough to read in ten minutes, one idea
each. A PR opened from the wrong base branch shows dozens of unrelated commits; change the base with the "Edit" button
next to the title. Pushing a secret in a PR is a leak even if the PR is never merged, because the commit is on GitHub;
rotate the secret.

</Level>

<Level name="Corner cases">

Draft PRs signal "not ready, but look if you like" and do not request review. Closing a PR without merging leaves the
branch; delete it or it piles up. "Closes #12" in the description links an issue and closes it on merge, a small habit
that keeps the issue list honest.

</Level>

<Level name="Production level">

On teams, `main` is protected: PRs only, at least one approval, checks green (tests, lint, build), branch up to date.
A template (`.github/pull_request_template.md`) prompts the what, why and how-to-check sections. Preview deployments
let a reviewer click the change rather than imagine it.

</Level>

<Level name="Mindset">

A PR is a letter to a reviewer, including my future self. Make it easy to say yes to.

</Level>

<Level name="System design">

The PR is the gate where checks, review and deployment meet. Continuous integration in Phase 4 hangs everything off it:
nothing reaches `main`, and so production, without passing through one.

</Level>

<Level name="Strategy">

Every change to the one-page site from week 1 onward goes through a branch and a PR, including at least one I merge
with a conflict I resolved by hand, and one where I left myself a review comment and fixed it.

Done when the repository has at least five merged PRs with what, why and how-to-check descriptions, `main` has no direct
commits after the first, and I can resolve a conflict in the terminal without searching.

</Level>

</Levels>

#### Phase 0: HTTP requests and responses

<Figure art={`
  REQUEST (what the browser sends)              RESPONSE (what the server sends back)
  GET /about.html HTTP/1.1          <- line      HTTP/1.1 200 OK                 <- status line
  Host: user.github.io              <- headers   Content-Type: text/html; charset=utf-8
  User-Agent: Mozilla/5.0 ...                    Content-Length: 2310
  Accept: text/html                              Cache-Control: max-age=600
  Accept-Encoding: gzip, br                      Last-Modified: Thu, 22 Oct 2026 10:00:00 GMT
                                    <- blank     
                                    <- body      <!doctype html><html lang="en"> ...  <- body
                                       (none for GET)
`} caption="The shape of HTTP: a request line or status line, headers, a blank line, and an optional body. Everything on the web is this exchange." />

<Levels label="Phase 0, HTTP requests and responses">

<Level name="Beginner">

HTTP is the conversation between a browser (the client) and a server. The client sends a request: a method (what to do),
a path (what to do it to), headers (extra information) and sometimes a body. The server sends a response: a status code
(how it went), headers and usually a body.

I can see the raw exchange with `curl -v`:

```sh
$ curl -v https://example.com/
> GET / HTTP/2
> Host: example.com
> User-Agent: curl/8.5.0
> Accept: */*
>
< HTTP/2 200
< content-type: text/html; charset=UTF-8
< content-length: 1256
<
<!doctype html>
...
```

Lines with `>` went out; lines with `<` came back. Methods I will meet: `GET` (read), `POST` (create or submit), `PUT` and
`PATCH` (replace or change), `DELETE`. Status codes by first digit: 2xx success, 3xx go elsewhere, 4xx the client got
something wrong, 5xx the server failed.

Mistake: reading only the page and never the response. When something breaks, the status and headers usually say why.

</Level>

<Level name="Intermediate">

The status codes worth knowing by heart in week one: `200 OK`; `201 Created`; `204 No Content`; `301 Moved Permanently` and
`302 Found` (redirects, with a `Location` header); `304 Not Modified` (use your cached copy); `400 Bad Request`;
`401 Unauthorized` (not logged in); `403 Forbidden` (logged in, not allowed); `404 Not Found`; `429 Too Many Requests`;
`500 Internal Server Error`; `502 Bad Gateway` and `503 Service Unavailable` (something in front of the app could not reach it).

A redirect, traced:

```sh
$ curl -sI http://github.com
HTTP/1.1 301 Moved Permanently
Location: https://github.com/
$ curl -sIL http://github.com | grep -i '^http\|^location'
HTTP/1.1 301 Moved Permanently
Location: https://github.com/
HTTP/2 200
```

`-I` asks for headers only (a `HEAD` request), `-L` follows redirects. Headers that matter now: `Content-Type` (what the body
is), `Content-Length`, `Cache-Control` (how long it may be reused), `Location`, and `Set-Cookie` and `Cookie` later.

</Level>

<Level name="Advanced">

HTTP is stateless: each request stands alone, and the server remembers nothing between them unless something (a cookie, a
token) is sent again. HTTPS is HTTP inside TLS, which encrypts the exchange and proves the server's identity with a certificate;
the padlock means the certificate was valid for that domain. HTTP/2 and HTTP/3 change how bytes travel (many requests over one
connection, QUIC over UDP) but keep the same methods, headers and status codes, which is why `curl` shows the same shape.

Caching is part of HTTP. A response with `Cache-Control: max-age=600` can be reused for ten minutes without asking. After that the
browser revalidates with `If-Modified-Since` or `If-None-Match`, and a `304` with no body says "still good". This is why a deployed
change sometimes does not show up immediately: the old file is still fresh in a cache.

</Level>

<Level name="Edge cases">

A page can be `200` and still broken: an error message in a `200` body, or an HTML error page served where JSON was expected.
A `404` for `favicon.ico` in DevTools is harmless noise. Mixed content: an HTTPS page loading an `http://` script is blocked by
the browser.

</Level>

<Level name="Corner cases">

`HEAD` and `GET` can disagree on badly configured servers, so `curl -I` is a clue, not proof. Header names are case-insensitive
(`Content-Type` and `content-type` are the same), which is why HTTP/2 shows them lowercase. A trailing slash matters: `/about` and
`/about/` can be different resources, and GitHub Pages redirects one to the other.

</Level>

<Level name="Production level">

Status codes, response times and sizes are what monitoring watches; the HTTP layer is where most incidents first show up. Every
team member reads raw requests with `curl` or DevTools when debugging.

</Level>

<Level name="Mindset">

When a page misbehaves, look at the conversation, not the screen: what was asked, what was answered, and with which status.

</Level>

<Level name="System design">

Proxies, CDNs, load balancers and APIs all speak HTTP, which is why the same few concepts (methods, status, headers, caching) explain
every hop between a user and a database. Phase 3 builds an API on exactly this.

</Level>

<Level name="Strategy">

I `curl -v` my own deployed page, a redirecting URL, a missing page and a JSON API, and write down the status and three headers for each.

Done when I can name what each part of a raw request and response is, predict the status for a missing page and a redirect, and explain
why a deploy did not appear for a few minutes.

</Level>

</Levels>

#### Phase 0: DNS, at a high level

<Figure art={`
  browser: what is user.github.io?
     |
     v
  OS / browser cache  -- hit? --> 185.199.108.153
     | miss
     v
  recursive resolver (ISP, 1.1.1.1, 8.8.8.8)
     |  1. ask a root server ............ "ask the .io servers"
     |  2. ask the .io TLD server ......... "ask github.io's nameservers"
     |  3. ask github.io's nameserver ..... "user.github.io A 185.199.108.153, TTL 3600"
     v
  answer cached for TTL seconds, returned to the browser, which connects to that IP
`} caption="DNS turns a name into an address by asking a chain of servers, each pointing to the next, then caches the answer." />

<Levels label="Phase 0, DNS at a high level">

<Level name="Beginner">

Computers connect to IP addresses; people type names. DNS (the Domain Name System) is the global, distributed phone book that turns
`user.github.io` into an address like `185.199.108.153`. Every visit to a site by name starts with a DNS lookup, usually answered from a
cache in milliseconds.

```sh
$ dig +short example.com
93.184.215.14
$ nslookup example.com
Name:    example.com
Address: 93.184.215.14
```

The plan asks for DNS "at a high level": what a lookup is, what records are, why changes take time. Not running a DNS server.

Mistake: thinking a domain "is" a server. A domain is a name with records pointing at things; changing the record moves the name.

</Level>

<Level name="Intermediate">

Record types I will actually touch: `A` (name to IPv4 address), `AAAA` (to IPv6), `CNAME` (this name is an alias for another name),
`MX` (where email goes), `TXT` (text, used for verification and email security). Pointing a custom domain at GitHub Pages:

```text
www.example.com.   CNAME   user.github.io.
example.com.       A       185.199.108.153   (plus the other three GitHub Pages addresses)
```

```sh
$ dig www.example.com CNAME +short
user.github.io.
```

TTL (time to live) says how long resolvers may cache an answer. A record with TTL 3600 can keep the old answer for up to an hour after
I change it, which is what "DNS propagation" means: not a broadcast, just caches expiring.

</Level>

<Level name="Advanced">

The lookup in the figure: my computer asks a recursive resolver; the resolver asks a root server, which points to the top-level-domain
servers for `.io`; those point to the domain's authoritative nameservers; those give the answer. Each answer is cached at each level for
its TTL. `dig +trace example.com` shows the chain.

Before a planned change, lower the TTL (to 300 seconds) a day ahead, so the switch takes minutes, then raise it again after.

</Level>

<Level name="Edge cases">

A `CNAME` cannot sit at the bare domain (`example.com`) alongside other records under the classic rules, which is why apex domains use
`A` records or a provider's `ALIAS` or flattening feature. Typos in records (a missing trailing dot in some zone formats, the wrong
target) fail silently until someone visits.

</Level>

<Level name="Corner cases">

My laptop, my phone and a friend's machine can see different answers during a change, because each uses a different resolver with a
different cache. `dig @1.1.1.1 example.com` asks a specific resolver, useful for comparing. A negative answer ("no such name") is
cached too, so checking a domain before creating its record can delay it working.

</Level>

<Level name="Production level">

DNS is part of every outage checklist; certificate issuance (HTTPS for a custom domain) depends on the DNS record being correct first;
domain registration expiring takes a whole product offline. Records live in the registrar or DNS provider, ideally managed as code.

</Level>

<Level name="Mindset">

When "the site is down for some people", suspect caches, including DNS, before suspecting the server.

</Level>

<Level name="System design">

DNS is the first hop of every request and a lever for routing: CDNs answer with the nearest server's address, and failover can move a
name to a healthy region. It is also why TTLs are a design choice.

</Level>

<Level name="Strategy">

I run `dig` on my GitHub Pages URL, a big site and a domain with `MX` records, and trace one with `+trace`. If I own a domain, I point
it at the site and watch the change propagate.

Done when I can explain the lookup chain from the figure, name the five record types, and explain propagation as caching with a TTL.

</Level>

</Levels>

#### Phase 0: JSON

<Compare
  left="Valid JSON"
  right="Looks like JSON, is not"
  caption="JSON is a strict subset of JavaScript literal syntax. Most parse errors are one of these."
  rows={[
    ['{"name": "Ana", "age": 31}', "{name: 'Ana', age: 31}  (unquoted key, single quotes)"],
    ['[1, 2, 3]', '[1, 2, 3,]  (trailing comma)'],
    ['{"note": null}', '{"note": undefined}  (no undefined in JSON)'],
    ['{"when": "2026-10-23T10:00:00Z"}', '{"when": new Date()}  (no dates, only strings)'],
  ]}
/>

<Levels label="Phase 0, JSON">

<Level name="Beginner">

JSON (JavaScript Object Notation) is the text format almost every web API uses to send data. It has six kinds of value: objects
`{ }` with string keys, arrays `[ ]`, strings in double quotes, numbers, `true` and `false`, and `null`. Nothing else: no comments, no
functions, no dates, no `undefined`.

```json
{
  "title": "My first page",
  "published": true,
  "tags": ["html", "css"],
  "views": 42,
  "author": { "name": "Sanjay" },
  "draft": null
}
```

In the browser console, `JSON.parse` turns text into a value and `JSON.stringify` turns a value into text:

```js
JSON.parse('{"views": 42}').views        // 42
JSON.stringify({ a: 1, b: [true] })      // '{"a":1,"b":[true]}'
```

Mistake: hand-writing JSON with single quotes or a trailing comma, then seeing `Unexpected token`. Use a validator or `jq`.

</Level>

<Level name="Intermediate">

Parse errors, read properly:

```text
SyntaxError: Expected double-quoted property name in JSON at position 1 (line 1 column 2)
SyntaxError: Unexpected token '<', "<!doctype "... is not valid JSON
```

The first is a JSON mistake at a specific position. The second is the most common one on the web: I asked for JSON and got an HTML
page, usually a 404 or error page. The fix is to check the response status and `Content-Type` before parsing.

`jq` reads JSON in the terminal:

```sh
$ cat site.json
{"title": "My first page", "tags": ["html", "css"], "author": {"name": "Sanjay"}}
$ jq '.title, .author.name, .tags[0]' site.json
"My first page"
"Sanjay"
"html"
$ curl -s https://api.github.com/repos/OWNER/REPO | jq '.default_branch'
"main"
```

The filter syntax is `.field`, `.nested.field` and `.array[0]`; the same filters work on a file or on a live API response.

</Level>

<Level name="Advanced">

`JSON.stringify` has rules worth knowing: `undefined` values and functions in objects are dropped, `NaN` and `Infinity` become `null`,
`Date` objects become ISO strings (and do not come back as dates on parse), and `Map` and `Set` become `{}`. Pretty printing is
`JSON.stringify(value, null, 2)`. Big integers above `2^53` lose precision when parsed into JavaScript numbers, which is why APIs send
large IDs as strings.

</Level>

<Level name="Edge cases">

A UTF-8 byte order mark at the start of a file makes some parsers fail on the first character. An empty response body is not valid JSON;
`JSON.parse('')` throws. A top-level string or number is valid JSON (`"hi"`, `42`), which surprises code that expects an object.

</Level>

<Level name="Corner cases">

Duplicate keys (`{"a": 1, "a": 2}`) are allowed by most parsers, which keep the last one silently. Circular objects make
`JSON.stringify` throw `Converting circular structure to JSON`. Very deep nesting can hit recursion limits.

</Level>

<Level name="Production level">

APIs validate JSON against a schema at the boundary (Phase 3), send `Content-Type: application/json`, and treat parse failures as `400`
responses, not crashes.

</Level>

<Level name="Mindset">

JSON is a contract written as text. When it fails, read the exact error and position before guessing.

</Level>

<Level name="System design">

JSON's simplicity is why it won as the web's data format: every language can read it. Its gaps (no dates, no big integers, no schema)
are why schemas, validation and conventions exist around it.

</Level>

<Level name="Strategy">

I write a small JSON file describing my site (title, sections, links), validate it with `jq`, break it in each of the four ways in the
table and read each error, and fetch one public API with `curl` and `jq`.

Done when I can read a JSON parse error and find the problem in seconds, and explain the HTML-instead-of-JSON error from its first character.

</Level>

</Levels>

<Levels label="Phase 0, browser DevTools">

<Level name="Beginner">

DevTools is a debugger built into every browser. Open it with F12, or Cmd+Option+I on macOS, or right-click an element and choose
Inspect. The Elements panel shows the live DOM (the page as the browser built it, which can differ from my HTML file) and the CSS

The Console shows errors in red with a file and line number. A missing stylesheet looks like:

```text
GET https://user.github.io/site/styles.css 404 (Not Found)
```

That one line says what was requested, from where, and what came back, usually enough to spot a wrong path.

<Level name="Intermediate">

The Network panel, step by step. Open it, tick "Disable cache", reload. Each row is one request. Columns: name, status, type,

<Level name="Advanced">

The Elements panel's Computed tab shows the final value of every property and, when expanded, which rule set it. The box model diagram
shows content, padding, border and margin for the selected element. The Styles pane can force states (`:hover`, `:focus-visible`) to
debug styles that only appear on interaction.

The Console is a REPL in the page's context: `document.querySelectorAll('a').length`, `$0` for the currently selected element,
`copy(value)` to copy a value. Lighthouse runs an audit and produces scores with specific fixes, a useful first check of accessibility and
performance on the deployed page.

</Level>

<Level name="Edge cases">

The DOM shown in Elements is after the browser fixed my HTML: an unclosed tag, a `div` inside a `p`, or a missing `tbody` are silently
repaired. "View page source" (Ctrl+U) shows what the server actually sent. When the two differ, my HTML is invalid or a script changed it.

</Level>

<Level name="Corner cases">

A request that does not appear in Network may have been served from the memory cache before DevTools opened, or by a service worker;
reload with DevTools open and cache disabled. Browser extensions inject their own errors into the Console; test in a private window to
rule them out.

</Level>

<Level name="Production level">

<Level name="System design">

#### Phase 0: Deploying a static page

<Flow
  caption="GitHub Pages from a push to a public URL"
  steps={['git push to main', 'Pages build starts (Actions tab)', 'Files copied to the Pages servers and CDN', 'HTTPS certificate in place', 'https://USER.github.io/REPO/ serves index.html', 'Check with curl -I and a phone']}
/>

<Levels label="Phase 0, deploying a static page">

<Level name="Beginner">

A static page is files (HTML, CSS, images) served exactly as they are; no code runs on the server. Deploying it means putting those
files on a server that answers HTTP requests at a public URL. GitHub Pages does this from a repository.

Steps: push the site to a public repository with `index.html` at the root; on GitHub open Settings, Pages; under "Build and deployment"
choose "Deploy from a branch", branch `main`, folder `/ (root)`; save. After a minute or two the Actions tab shows a "pages build and
deployment" run, and the Pages settings show the URL.

```sh
$ curl -sI https://USER.github.io/site/ | head -3
HTTP/2 200
server: GitHub.com
content-type: text/html; charset=utf-8
```

Mistake: deploying once at the end. Deploy the empty page on day one; every later push is then just a change.

</Level>

<Level name="Intermediate">

Paths are the first thing that breaks. A project site lives under `/REPO/`, not at the domain root, so an absolute path in my HTML points
to the wrong place:

```html
<link rel="stylesheet" href="/styles.css">    <!-- requests https://USER.github.io/styles.css: 404 -->
<link rel="stylesheet" href="styles.css">     <!-- relative: https://USER.github.io/site/styles.css -->
```

File names are case-sensitive on the server even when they are not on my laptop: `Logo.svg` and `logo.svg` work locally on macOS and
404 in production. A missing `index.html` gives GitHub's 404 page.

</Level>

<Level name="Advanced">

Caching: GitHub Pages serves files with a short cache lifetime (minutes), so a push can take a little while to appear. I check with
`curl` (no browser cache) or a private window before deciding the deploy failed. A custom domain adds a `CNAME` file in the repository and
a DNS record, and Pages provisions an HTTPS certificate once DNS resolves; "Enforce HTTPS" redirects plain HTTP.

Deploying with an Actions workflow (the "GitHub Actions" source) instead of a branch makes the build explicit and is how sites with a
build step (Astro, Vite) are deployed.

</Level>

<Level name="Edge cases">

Files starting with an underscore are ignored by Pages' default Jekyll processing; a `.nojekyll` file at the root turns that off. A
`404.html` at the root becomes the custom not-found page. A private repository on a free plan cannot use Pages.

</Level>

<Level name="Corner cases">

Two pushes in quick succession can produce deployments that finish out of order on some hosts; check the commit SHA the live site serves
(a comment or meta tag with the SHA helps). A page that works at `/site/` may break at `/site` without the trailing slash, because relative
paths resolve against a different directory.

</Level>

<Level name="Production level">

Real deploys are automatic from `main`, reversible (redeploy the previous commit), and verified by a check after each deploy. Preview
deployments per pull request come with hosts like Netlify, Vercel or Cloudflare Pages.

</Level>

<Level name="Mindset">

Shipping is a habit, not an event. The earlier the first deploy, the smaller each later one.

</Level>

<Level name="System design">

A static site behind a CDN is the simplest, cheapest, most reliable architecture there is. Knowing when a page needs nothing more is a
design skill.

</Level>

<Level name="Strategy">

Deploy on day one, then break the deploy on purpose: an absolute path, a wrong-case file name, a missing `index.html`, and fix each from
DevTools and `curl` output.

Done when the site is live at a public URL over HTTPS, every asset loads with 200, it looks right on a phone, and I can explain each break I caused.

</Level>

</Levels>

#### Phase 0: Semantic HTML and one CSS file

<Figure art={`
  <body>
    <header>   site name, <nav> with 3 links          landmark: banner
    <main>                                            landmark: main (one per page)
      <h1>Who I am</h1>

<Levels label="Phase 0, semantic HTML and one CSS file">

<Level name="Beginner">

Semantic HTML means choosing elements by meaning, not looks. `h1` to `h6` are headings in a hierarchy, `p` is a paragraph, `a` goes
somewhere, `button` does something, `ul` and `li` are lists, `nav`, `header`, `main`, `footer` mark regions. Browsers, search engines and
screen readers use these meanings; a `div` has none.

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Sanjay · building in public</title>
  <link rel="stylesheet" href="styles.css">
</head>
<body>
  <header><a href="./">Sanjay</a><nav aria-label="Main"><a href="#work">Work</a></nav></header>
  <main>
    <h1>Hi, I build things for the web</h1>
    <section id="work" aria-labelledby="work-title"><h2 id="work-title">What I am building</h2></section>
  </main>
  <footer><a href="https://github.com/USER/site">Source</a></footer>
</body>
</html>
```

Mistake: picking headings by size (`h4` because it looked right). Headings are an outline; style them with CSS.

</Level>

<Level name="Intermediate">

One CSS file, organised so it stays readable: custom properties first, then a small base (box sizing, body font, links), then layout,
then components, then one media query.

```css
:root { --text: #111; --bg: #fff; --muted: #555; --space: 1rem; --max: 40rem; }
*, *::before, *::after { box-sizing: border-box; }
body { margin: 0; font: 1.0625rem/1.6 system-ui, sans-serif; color: var(--text); background: var(--bg); }
main { max-width: var(--max); margin-inline: auto; padding: var(--space); }
a { color: inherit; text-underline-offset: 0.2em; }
a:focus-visible { outline: 2px solid currentColor; outline-offset: 2px; }
@media (min-width: 48rem) { body { font-size: 1.125rem; } }
```

The cascade decides conflicts: more specific selectors win, and among equals the later rule wins. Keeping selectors simple (classes and
elements, no IDs, no `!important`) keeps the cascade predictable.

</Level>

<Level name="Advanced">

Every image has `alt` text describing its purpose (or `alt=""` if decorative); every link's text makes sense alone ("Source code", not
"click here"); `lang` is set; there is exactly one `h1`. The W3C validator (validator.w3.org) and Lighthouse's accessibility audit catch
mechanical errors. Open Graph tags (`og:title`, `og:description`) control how the link looks when shared.

</Level>

<Level name="Edge cases">

Nested interactive elements (a button inside a link) are invalid and behave differently across browsers. A `section` without a heading
is just a `div` to assistive tech. Margins between adjacent block elements collapse, which explains many mystery gaps.

</Level>

<Level name="Corner cases">

Default user-agent styles differ slightly between browsers; a small reset (box sizing, body margin) removes most surprises without wiping
useful defaults like focus rings. `rem` follows the user's browser font size; `px` font sizes ignore it, which breaks for users who enlarged
their default text.

</Level>

<Level name="Production level">

Valid HTML, landmarks, one `h1`, alt text, a sensible title and description per page, and a stylesheet small enough to read in one sitting,
with no unused rules.

</Level>

<Level name="Mindset">

Start with the content and its structure; style comes after. A page that reads well with CSS turned off is a well-built page.

</Level>

<Level name="System design">

HTML is the contract between content and every consumer of it: browsers, assistive technology, search engines, link previews. Getting it
right once serves all of them.

</Level>

<Level name="Strategy">

I write the page with CSS turned off first, check the heading outline and landmarks with a screen reader's rotor, then add the one stylesheet.

Done when the validator shows no errors, Lighthouse accessibility is at its best score, the page works with the keyboard and at 320px wide,
and the CSS fits in one readable file.

</Level>

</Levels>

<Levels label="Phase 0, ten meaningful commits and a README">

<Level name="Beginner">

The plan asks for a repository with ten meaningful commits. A meaningful commit is one logical change with a message that says what it does.
The convention: a short summary line in the imperative mood ("Add", "Fix", "Remove"), under about 72 characters, optionally a blank line and a
body explaining why.

```sh
$ git log --oneline
a91c2e7 Fix the stylesheet path for the project site
5d03b44 Add a footer with the source link
c2e19f0 Add the work section with two projects
...
```

Ten real commits means ten small steps of the build: the skeleton, the header, each section, the stylesheet, the deploy fix, the README. Not ten
typo fixes made to reach a number.

</Level>

<Level name="Intermediate">

Staging lets me split one messy session into clean commits. `git add -p` walks through each change and asks whether to include it:

```sh
$ git add -p styles.css
@@ -10,6 +10,9 @@ main { max-width: 40rem; }
+footer { padding: 1rem; color: var(--muted); }
Stage this hunk [y,n,q,a,d,s,e,?]? y
```

Then `git diff --staged` shows exactly what the commit will contain, a habit that catches stray files before they are committed.

The README answers: what is this, how do I run it, where is it live.

```md
# Sanjay's site

A one-page site built with plain HTML and one CSS file, as Phase 0 of my developer roadmap.

Live: https://USER.github.io/site/

## Run it locally
git clone https://github.com/USER/site && cd site
python3 -m http.server 8000   # then open http://localhost:8000
```

</Level>

<Level name="Advanced">

Good history is a debugging tool. `git log -p styles.css` shows every change to a file; `git blame` shows which commit last changed each line and
why; `git bisect` finds the commit that broke something by binary search. All of them work only when commits are small and messages are honest.
Amending the last unpushed commit (`git commit --amend`) fixes a message or a forgotten file; rewriting pushed history is a different matter, for
later.

</Level>

<Level name="Edge cases">

Committing generated or personal files (`.DS_Store`, editor folders, `node_modules` later): add a `.gitignore` in the first commit. A commit that
mixes a refactor and a behaviour change is hard to review and impossible to revert cleanly; split it.

</Level>

<Level name="Corner cases">

My commit author email decides whether GitHub links commits to my profile; set `git config --global user.email` to an address on my account, or
GitHub's no-reply address if I want it private. Line ending differences between Windows and Unix can make every line show as changed; a
`.gitattributes` file fixes it.

</Level>

<Level name="Production level">

Teams agree a commit style (sometimes Conventional Commits, `feat:` and `fix:` prefixes, which tools use to generate changelogs) and a README
template: purpose, setup, scripts, deploy, contact.

</Level>

<Level name="Mindset">

History is documentation that writes itself if I let it. Each commit should make sense to a stranger a year from now.

</Level>

<Level name="System design">

In larger systems, the repository is the single source of truth for code, configuration and infrastructure, and its history is the audit log.
The habits start with ten commits.

</Level>

<Level name="Strategy">

I plan the ten commits before writing the site (one per piece of the build), use `git add -p` at least twice to split work, and write the README
before the last commit.

Done when `git log --oneline` reads like a short story of the build, every commit is one change, and the README lets a stranger run the site in
two commands.

</Level>

</Levels>
#### Phase 0: The proof, from a typed URL to a painted page

<Figure art={`
  BROWSER                         NETWORK                              SERVER (GitHub Pages)
  1 parse URL: https, host,
    path /site/
  2 cache? service worker?
  3 ------------------------->  4 DNS: host -> 185.199.108.153
  5 ------------------------->  6 TCP connect (3-way handshake)
                                7 TLS handshake: certificate checked
  8 send GET /site/ HTTP/2 -->  9 travels via routers, CDN edge  -->  10 find /site/index.html
                                                                      11 200 + headers + HTML
  12 parse HTML -> DOM <------------------------------------------------+
  13 see <link styles.css> -> request it (steps 8-11 again, connection reused)
  14 CSS -> CSSOM; DOM + CSSOM -> render tree
  15 layout (sizes, positions) -> paint -> composite -> pixels
`} caption="The proof in one picture: which steps belong to the browser, which to the network, and which to the server." />

<Levels label="Phase 0, from a typed URL to a painted page">

<Level name="Beginner">

The plan's proof: a public URL, and being able to explain what happens between typing it and seeing the page, including which parts are the
browser, the network and the server. The short version, in my own words:

The browser reads the URL and works out the scheme (`https`), host and path. It asks DNS for the host's IP address. It opens a connection to that
address and does a TLS handshake so the conversation is encrypted and the server is verified. It sends an HTTP `GET` for the path. The server finds
the file and replies `200` with the HTML. The browser parses the HTML, requests the CSS and images it references, builds the page and paints it.

Mistake: memorising this as a list. The point is to be able to place a bug on it: a DNS error is step 4, a certificate warning step 7, a 404 step 11,
a broken layout step 14 or 15.

</Level>

<Level name="Intermediate">

Each step, observed rather than recited:

```sh
$ dig +short user.github.io                       # step 4: the address
185.199.108.153
$ curl -v https://user.github.io/site/ 2>&1 | grep -E '^\* (Connected|SSL|Server certificate)|^> GET|^< HTTP'
* Connected to user.github.io (185.199.108.153) port 443   # step 6
* SSL connection using TLSv1.3                              # step 7
> GET /site/ HTTP/2                                         # step 8
< HTTP/2 200                                                # step 11
```

The exact lines vary with the curl version; the order does not. In DevTools, the Network panel's Timing tab for the document request shows the same
phases as bars: DNS lookup, initial connection, SSL, waiting for the server (time to first byte), content download.

</Level>

<Level name="Advanced">

Rendering in more depth. HTML is parsed top to bottom into the DOM. CSS in the head blocks rendering until it is loaded, because painting without it
would flash unstyled content. A plain `script` tag blocks parsing until it has downloaded and run, which is why scripts go at the end or use `defer`.
The DOM and CSSOM combine into a render tree of visible elements; layout computes each box's size and position; paint fills in pixels; compositing
assembles layers. Changing layout properties (width) later costs more than changing composited ones (transform), which matters in Phase 4's
performance work.

</Level>

<Level name="Edge cases">

A second visit may skip most steps: DNS cached, connection reused, HTML and CSS served from the browser cache. That is why "it works for me" and
"it is slow for new users" can both be true.

</Level>

<Level name="Corner cases">

A redirect (`http` to `https`, or `/site` to `/site/`) repeats steps 8 to 11 before the real page. A CDN edge may answer step 10 itself from its
cache without reaching the origin server, so a deploy can be live at the origin and stale at the edge.

</Level>

<Level name="Production level">

Every performance metric and many incidents map to a step: slow DNS, slow TLS, slow server (time to first byte), heavy CSS (render blocking), large
images (paint). Monitoring tools report these phases separately for that reason.

</Level>

<Level name="Mindset">

A system I can draw end to end is a system I can debug. This picture is the first one.

</Level>

<Level name="System design">

Every later architecture adds boxes to this picture (an API server, a database, a cache, a queue) but never removes these steps. The proof is the
skeleton of every system diagram I will draw.

</Level>

<Level name="Strategy">

I draw the figure from memory on paper, then verify each step against `dig`, `curl -v` and the Network panel for my own URL, and explain it out loud
to someone, or to a recording, in under five minutes.

Done when I can explain the sequence without notes, say for each step whether it is browser, network or server, and place three real errors (DNS,
certificate, 404) on the diagram.

</Level>

</Levels>

#### Phase 0: The traps, and the AI-era note

  right="The habit that replaces it"

<Levels label="Phase 0, the traps and the AI-era note">

<Level name="Beginner">

The three traps share a cause: preparing instead of doing. Watching Git videos feels like progress, but Git is learned by committing, breaking
things and recovering. Installing extensions feels like setup, but each one adds noise before I know what problem it solves. A framework feels
modern, but it hides the HTML, CSS and HTTP this phase exists to make visible.

The fix for all three is the same: ship the small thing by hand, then learn what I needed while shipping it.

</Level>

<Level name="Intermediate">

The AI-era note: ask a model to explain an error or a Git command; do not ask it to write the first page. A good use looks like this:

```text
Prompt: I ran `git push` and got "rejected: non-fast-forward". Explain what this means
in terms of my local and remote branches, and what my safe options are. Do not run anything.
```

I then do the fix myself, and write one line in a notes file about what happened. The memory of doing it by hand is what I debug against later.

</Level>

<Level name="Advanced">

Explanations from a model can be confidently wrong about specific flags or platform details. I check each explanation against the actual
command output or the official docs (`git help push`, MDN) before acting, especially anything destructive (`reset --hard`, `push --force`).

</Level>

<Level name="Edge cases">

When the tutorial I am following uses a tool I do not have yet (a bundler, a framework), I skip that part or do it with plain files, rather than
installing the tool to keep up.

</Level>

<Level name="Corner cases">

Some extensions really are worth it on day one: a formatter, Git integration that ships with the editor, and maybe an HTML validator. The test is
whether I can name the problem each one solves.

</Level>

<Level name="Production level">

Teams value people who can work in a bare terminal on a server with no extensions and no AI help. This phase is where that comfort comes from.

</Level>

<Level name="Mindset">

Doing beats preparing. Every hour of this phase should end with something committed or deployed.

</Level>

<Level name="System design">

Understanding the layers by hand is what lets me judge abstractions later. A framework, a deploy platform or a model is a choice I can make well
only once I know what it is doing for me.

</Level>

<Level name="Strategy">

At the end of week 2 I audit the phase against the trap table, uninstall any extension I cannot justify, and check the repository's history and the
live URL.

Done when every trap has evidence in the repository, the page was written by hand, and I have a notes file of errors a model explained and I then fixed
myself.

</Level>

</Levels>
