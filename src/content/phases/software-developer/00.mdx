Two weeks to stop being afraid of the three things every later phase assumes: the terminal, the
browser and the deploy. Nothing here is hard on its own. What makes it matter is that every bug I
will chase for the next eighteen months passes through one of these layers: a path that is wrong,
a commit that is missing, a request that came back 404, a DNS record that has not propagated, a
JSON body that does not parse. This phase builds the memory I debug against later.

The ship is small on purpose: one page of semantic HTML and one CSS file, in a repository with ten
real commits and a README, deployed to GitHub Pages at a public URL. The proof is that I can explain,
without notes, everything that happens between typing that URL and seeing the page.

#### Phase 0: how I would learn it

Every topic follows the same loop: do it by hand once, break it on purpose, read the error, then
write the rule down in the bug log. No video longer than the task it explains. The AI rule for this
phase is strict: a model may explain an error message or a Git command, but it does not write the
first page. I need one memory of doing it myself.

#### Phase 0: The terminal and file paths

<Levels label="Phase 0, the terminal and file paths">

<Level name="Beginner">

The terminal is a text conversation with the operating system. I type a command, the shell finds a
program with that name, runs it with my arguments, and prints what the program prints. Five commands
cover the first day: `pwd` (where am I), `ls` (what is here), `cd` (go somewhere), `mkdir` (make a
folder) and `touch` or an editor (make a file).

```sh
$ pwd
/home/sanjay
$ mkdir -p projects/page && cd projects/page
$ touch index.html
$ ls
index.html
```

A path is the address of a file. If it starts with `/` it is absolute and means the same thing from
anywhere. If it does not, it is relative to the current directory, and `.` means here while `..`
means one level up. `~` is the shell's shorthand for my home directory.

The first common mistake is running a command in the wrong folder: `ls` shows nothing, or
`cat index.html` says `No such file or directory`. The fix is always the same two commands: `pwd` to
see where I am, `ls` to see what is actually there, before I assume anything.

</Level>

<Level name="Intermediate">

Commands become useful when they combine. Every program has three streams: standard input, standard
output and standard error. A pipe `|` connects one program's output to the next one's input; `>`
writes output to a file (replacing it) and `>>` appends.

```sh
$ ls -la                      # long listing, including hidden dotfiles
$ grep -rn "TODO" .           # search every file under here for TODO
./index.html:12:<!-- TODO: footer -->
$ grep -rn "TODO" . | wc -l   # how many TODOs
1
$ history | tail -n 5         # the last five commands I ran
```

Flags change behaviour (`-l` long, `-a` all, `-r` recursive, `-n` line numbers), and `man ls` or
`ls --help` lists them. Tab completion finishes names so I never type a long path by hand; pressing
Tab twice shows the choices. The up arrow brings back the last command and `Ctrl-R` searches history.

Mistake: `rm -r` with a typo, or with a variable that is empty. There is no recycle bin. The fix is
a habit: run `ls` on exactly the same path first, and only then replace `ls` with `rm`.

</Level>

<Level name="Advanced">

The shell is itself a program (bash or zsh) that parses the line before anything runs. It expands
`~`, variables like `$HOME`, globs like `*.html` and command substitution like `$(date)`, then splits
the result into words, then looks up the first word. Lookup checks aliases, shell functions,
built-ins (`cd` must be a built-in, because a child process cannot change its parent's directory),
and finally each folder in `$PATH`, in order.

```sh
$ echo $PATH
/home/sanjay/.local/bin:/usr/local/bin:/usr/bin:/bin
$ which node
/usr/local/bin/node
$ type cd
cd is a shell builtin
$ echo $?            # exit code of the last command: 0 means success
0
$ ls nope; echo $?
ls: cannot access 'nope': No such file or directory
2
```

Every program exits with a number. Zero means success and anything else is a failure, which is what
`&&` (run the next only on success) and `||` (run the next only on failure) test. That one convention
is how CI decides whether a build is green years from now.

Mistake: `command not found` after installing something. The program exists but its folder is not on
`$PATH`, or the shell has not reloaded its config. The fix is `which` to confirm, then adding the
folder to `PATH` in `~/.bashrc` or `~/.zshrc` and opening a new terminal.

</Level>

<Level name="Edge cases">

File names with spaces split into two arguments unless they are quoted: `cd My Site` tries to enter
a folder called `My`. Quote them (`cd "My Site"`) or, better, never create them in a project. A glob
that matches nothing is passed through literally in bash, so `rm *.tmp` in a folder with no `.tmp`
files tries to delete a file literally named `*.tmp` and prints an error rather than doing nothing.

Hidden files start with a dot and `ls` skips them: `.git`, `.env`, `.gitignore`. A repository that
"has no Git" may just have a `.git` folder I cannot see without `ls -a`. Case matters on Linux and on
GitHub Pages but not, by default, on macOS: `Index.html` and `index.html` are the same file on my
laptop and two different files on the server.

```sh
$ ls
Index.html
$ open http://localhost:8000/index.html   # works on macOS
# deployed: https://user.github.io/page/index.html -> 404
```

</Level>

<Level name="Corner cases">

Two boundaries at once: a relative path inside a script that is run from a different folder. The
script says `cat data/list.txt`, works when I run it from the project root, and fails from anywhere
else, because relative paths resolve against the current directory, not the script's location. The
fix is to resolve from the script's own folder (`"$(dirname "$0")/data/list.txt"` in a shell script,
`new URL('./data/list.txt', import.meta.url)` in a Node module).

Another: case-insensitivity plus Git. Renaming `Index.html` to `index.html` on macOS can leave Git
thinking nothing changed, so the server keeps the old capitalised name and the link breaks only in
production. The fix is `git mv Index.html index.html`, which records the rename explicitly.

</Level>

<Level name="Production level">

On a server there is no desktop, only the terminal, often over `ssh`, and often at the worst moment.
The commands that matter there are the same ones: `pwd`, `ls -la`, `cat`, `less`, `tail -f` on a log,
`grep` for an error, `df -h` for a full disk, `ps` and `kill` for a stuck process. Scripts run by CI
use `set -euo pipefail` so that an error, an unset variable or a failed stage of a pipe stops the
script instead of carrying on with bad data.

```sh
#!/usr/bin/env bash
set -euo pipefail
OUT="${OUT_DIR:?OUT_DIR must be set}"   # fails loudly instead of rm -rf "/"
rm -rf "$OUT"/*
```

The classic outage is a cleanup script that ran `rm -rf "$DIR/"*` with `DIR` empty. The fix is
the `:?` guard above, and the rule: destructive commands never trust an unchecked variable.

</Level>

<Level name="Mindset">

The terminal teaches me to state exactly what I want and to read exactly what came back. A GUI hides
the error; the terminal prints it. Most beginner frustration is skipping the output: the error message
almost always names the file, the line and the reason. I read the whole message, top line first,
before I search for anything.

</Level>

<Level name="System design">

Every larger system I build is a pipeline of small programs passing text or bytes, with exit codes
as the contract: the build calls the compiler, CI calls the build, the deploy calls CI's artefact.
Paths are configuration: a service that hard-codes `/home/sanjay/...` breaks in a container, so later
systems read paths from environment variables and resolve them relative to known roots. The habits
from day one, small composable commands, explicit paths, checked exit codes, are the same habits at
the scale of a deploy pipeline.

</Level>

<Level name="Strategy">

For two days I do everything from the terminal: create the page project, move files, search them,
delete the scratch folders. I keep a cheat sheet of only the commands I actually used. Then I break it
on purpose: run a script from the wrong folder, delete a file with a space in its name, call a program
that is not on `PATH`, and log each error with its fix.

Done when I can, without notes, create a project tree, move around it with relative and absolute paths,
find every occurrence of a word with `grep`, explain what `$PATH` and `$?` are, and recover from
`command not found` and `No such file or directory` in under a minute.

</Level>

</Levels>


#### Phase 0: Git, from init to push

<Figure art={`
  working tree  --git add-->  staging area  --git commit-->  local repo  --git push-->  remote
  (files I edit)              (the next snapshot)            (history)                  (GitHub)
       ^                                                        |
       +---------------------- git restore / git checkout ------+
`} caption="Git's three local places and the remote. A commit is a snapshot of the staging area, not of the folder." />

<Levels label="Phase 0, Git from init to push">

<Level name="Beginner">

Git records snapshots of a folder so I can see what changed, when, and why, and go back. `git init`
makes the folder a repository. `git status` says what is changed and what is staged. `git add` stages
a file for the next snapshot. `git commit -m "..."` records the snapshot with a message. `git log`
shows the history.

```sh
git init
echo "<h1>Hi</h1>" > index.html
git status            # Untracked files: index.html
git add index.html
git commit -m "Add the first page"
git log --oneline     # 3f2a1c9 Add the first page
```

Mistake: `git commit` without `-m` drops me into Vim and I panic. Fix: type the message, press Esc,
type `:wq` and Enter; or set `git config --global core.editor "code --wait"`.

</Level>

<Level name="Intermediate">

A branch is a movable name for a line of commits. I make one per change, commit small steps on it, and
merge it back. `git diff` shows unstaged changes, `git diff --staged` shows what will be committed.
Remotes: `git remote add origin <url>` then `git push -u origin main` publishes the branch and links it.

```sh
git switch -c add-footer
echo "<footer>Sanjay</footer>" >> index.html
git diff                       # + <footer>Sanjay</footer>
git commit -am "Add a footer with my name"
git switch main && git merge add-footer
git push
```

A good message says why, in the imperative, in one line: `Add a footer so every page has an owner`
beats `update`. Mistake: `git add .` that sweeps in `.DS_Store` and `node_modules`. Fix: a
`.gitignore` committed first, and `git status` read before every commit.

</Level>

<Level name="Advanced">

Underneath, Git is a content-addressed store. Each file version is a blob named by the hash of its
contents; a tree lists blobs and subtrees; a commit points at one tree, its parent commits, an author
and a message. A branch is a file containing one commit hash, and `HEAD` says which branch I am on.
That is why branches are cheap and why rewriting a commit changes its hash and every hash after it.

```sh
git cat-file -p HEAD          # tree 9c1e... parent 3f2a... author ...
cat .git/refs/heads/main      # 7d4b0e2...
```

A merge of two diverged branches makes a commit with two parents; a fast-forward just moves the name
when there is nothing to combine. Mistake: believing a branch is a copy of the files. Fix: it is a
pointer; the snapshots are shared.

</Level>

<Level name="Edge cases">

The first commit has no parent, so `git diff HEAD~1` fails with `unknown revision`. An empty folder
cannot be committed; Git tracks files, so people add a `.gitkeep`. A file that was committed before
being added to `.gitignore` stays tracked; `git rm --cached file` stops tracking it. A detached HEAD
after `git checkout <hash>`: commits made there belong to no branch and are easy to lose; `git switch
-c rescue` saves them.

</Level>

<Level name="Corner cases">

A secret committed and then deleted in the next commit is still in history and still in every clone;
deleting the line is not enough, the key must be rotated. A merge conflict in a file both branches
renamed: Git shows the conflict under the new name, and the markers `<<<<<<<`, `=======`, `>>>>>>>`
must all go before `git add`. Pushing after someone else pushed: `rejected (fetch first)`; `git pull
--rebase` replays my commits on top, but rebasing commits that others already pulled rewrites their
history.

</Level>

<Level name="Production level">

In a team, `main` is protected, every change arrives through a pull request, and history is the audit
trail for "when did this break". Small commits make `git bisect` useful: it binary-searches history
for the commit that introduced a bug, which only works if each commit builds. Secrets never enter the
repo; `.env` is ignored and a `.env.example` documents the names. Mistake: force-pushing a shared
branch. Fix: never force-push `main`, and use `--force-with-lease` on my own branches.

</Level>

<Level name="Mindset">

A commit is a note to my future self explaining a decision. Ten meaningful commits teach more than ten
hours of Git videos, the trap the plan names, because Git is learned by the mistakes it lets me undo.
The habit: commit when a small idea is complete, not when the day ends.

</Level>

<Level name="System design">

Git is the source of truth that CI, deploys, code review and releases hang off. A push triggers the
build; a tag can trigger a release; a merged pull request deploys. Later, migrations and infrastructure
also live in the repo, so the state of the system can be rebuilt from history.

</Level>

<Level name="Strategy">

A scratch repo where I deliberately make every mistake: a conflict, a detached HEAD, a committed
secret, an amended message, a revert. I log each recovery. Done when I can draw the three local areas
and the remote from memory, make and merge a branch, resolve a conflict, and recover a lost commit with
`git reflog`.

</Level>

</Levels>

#### Phase 0: The pull request

<Flow
  caption="A pull request's life. The review happens before the merge, and the branch dies after it."
  steps={['Branch from main', 'Small commits', 'Push the branch', 'Open PR: what, why, how to check', 'Checks run', 'Review and fix', 'Merge', 'Delete the branch']}
/>

<Levels label="Phase 0, the pull request">

<Level name="Beginner">

A pull request is a proposal on GitHub to merge one branch into another, with a page for the diff,
the discussion and the checks. Even working alone, I open one for each change: it gives me a place to
read my own diff as a reviewer would. After pushing a branch, GitHub prints a link to open it, or I run
`gh pr create`.

```sh
git push -u origin add-footer
gh pr create --title "Add a footer with my name" --body "Why: every page should say who owns it."
```

Mistake: one pull request containing the whole site. Fix: one idea per PR, small enough to read in
five minutes.

</Level>

<Level name="Intermediate">

A good description has three parts: what changed, why, and how to check it. Screenshots for visual
changes. Each review comment is either fixed with a new commit or answered. Draft PRs signal "not
ready"; checks (build, tests) appear at the bottom and can block the merge. The three merge styles:
a merge commit keeps every commit, squash makes one, rebase replays them in a line.

</Level>

<Level name="Advanced">

A PR compares the head branch against the merge base with the target, the latest commit both share.
If main moves on, the diff stays correct but conflicts may appear; updating the branch merges or
rebases main into it. Branch protection rules can require reviews, passing checks and an up-to-date
branch. `CODEOWNERS` routes review to the right people automatically.

</Level>

<Level name="Edge cases">

A PR from a fork cannot read the target repo's secrets in CI, so deploy previews may not run. A PR
with zero diff (the branch was already merged) shows "nothing to compare". A binary file change shows
no readable diff, so the description must say what changed.

</Level>

<Level name="Corner cases">

Two PRs that each pass alone but conflict in behaviour once both merge: each was tested against a main
that did not contain the other. A required check plus a PR that changes only docs: if the check is
path-filtered and never runs, the merge stays blocked forever waiting for it.

</Level>

<Level name="Production level">

Review is where knowledge spreads and where risky changes get a second pair of eyes. Size is the main
lever: review quality drops sharply as diffs grow. A PR that mixes a refactor with a behaviour change
hides the behaviour change; split them. The merged PR link is the record that incident reviews later
point at.

</Level>

<Level name="Mindset">

Reviewing my own PR before asking anyone else is the cheapest bug-finder I have. Read the diff on the
PR page, not in the editor; a different view shows different mistakes.

</Level>

<Level name="System design">

The PR is the gate in the delivery pipeline: checks run on it, previews deploy from it, and merge
triggers the real deploy. Phase 4's CI gate is a required check on exactly this page.

</Level>

<Level name="Strategy">

Every change in this phase goes through a PR, even alone. Done when my repo has at least five merged
PRs, each with a description that answers what, why and how to check.

</Level>

</Levels>

#### Phase 0: HTTP requests and responses

<Figure art={`
  REQUEST                                  RESPONSE
  GET /index.html HTTP/1.1                 HTTP/1.1 200 OK
  Host: snjy-kumar.github.io               Content-Type: text/html; charset=utf-8
  Accept: text/html                        Content-Length: 1834
  User-Agent: Mozilla/5.0 ...              Cache-Control: max-age=600
                                           ETag: "64f1-2a"
  (blank line, then an optional body)      (blank line)
                                           <!doctype html> ...
`} caption="HTTP is text in a fixed shape: a start line, headers, a blank line, a body. Method and path ask; status and headers answer." />

<Levels label="Phase 0, HTTP requests and responses">

<Level name="Beginner">

HTTP is the conversation between a browser (the client) and a server. The client sends a request: a
method (`GET` to read, `POST` to send), a path, and headers. The server sends a response: a status code,
headers, and a body. `curl` lets me see it raw.

```sh
curl -i https://example.com/
# HTTP/2 200
# content-type: text/html; charset=UTF-8
# ...
# <!doctype html>
```

Status code families: 2xx success, 3xx go elsewhere, 4xx the client asked wrongly, 5xx the server
failed. Mistake: reading only the body. Fix: always look at the status and headers first, with `-i`.

</Level>

<Level name="Intermediate">

The headers that matter early: `Content-Type` tells the client how to read the body, `Location` with a
301 or 302 says where to go, `Cache-Control` says how long to keep a copy, `Set-Cookie` and `Cookie`
carry state across requests, which HTTP itself does not keep. Following a redirect:

```sh
curl -I http://github.com           # HTTP/1.1 301 Moved Permanently  Location: https://github.com/
curl -IL http://github.com          # follows to the final 200
curl -s -o /dev/null -w "%{http_code}\n" https://example.com/missing   # 404
```

Mistake: serving CSS as `text/plain`, so the browser refuses to apply it with a console warning about
MIME type. Fix: let the host set types from file extensions, and check `Content-Type` in DevTools.

</Level>

<Level name="Advanced">

HTTP is stateless and layered on a connection: TCP (or QUIC for HTTP/3) plus TLS for HTTPS. HTTP/1.1
sends one request at a time per connection; HTTP/2 multiplexes many over one connection as binary
frames, with compressed headers; the meaning (methods, status, headers) is the same. Methods have
rules: `GET` and `HEAD` are safe (no side effects), and `GET`, `PUT` and `DELETE` are idempotent
(repeating them has the same effect as once), while `POST` is neither. Conditional requests use `ETag`
and `If-None-Match` to get a `304 Not Modified` with no body.

```sh
curl -I https://example.com/ -H 'If-None-Match: "<etag from the first response>"'   # 304 when unchanged
```

</Level>

<Level name="Edge cases">

A 200 with an error page body (some apps do this) fools any code that checks only the status. A 204
has no body, so parsing it as JSON throws. A redirect loop ends with `curl: (47) Maximum (50)
redirects followed` or the browser's "too many redirects". A 404 for a path that differs only in a
trailing slash: `/about` and `/about/` are different URLs to the server.

</Level>

<Level name="Corner cases">

A cached 301 plus a later fix on the server: browsers keep permanent redirects, so the old redirect
keeps happening on my machine after it is gone. Test redirects with `curl`, not the browser. HTTPS
page plus an `http://` image: mixed content, blocked silently in the page and reported in the console.

</Level>

<Level name="Production level">

Status codes are the language monitoring speaks: a rise in 5xx is an outage, a rise in 4xx may be a
broken client. Caching headers decide cost and speed; a wrong `Cache-Control` on HTML means users see a
stale site for hours after a deploy. Static assets get long cache lifetimes and content-hashed names;
HTML gets short ones.

</Level>

<Level name="Mindset">

The browser is not magic; it is an HTTP client with a renderer attached. When something on the web
fails, I ask the same three questions every time: what was requested, what came back, and what did the
client do with it.

</Level>

<Level name="System design">

Every later layer is HTTP: the React app fetching JSON in Phase 2, the API in Phase 3, the CDN in
front of it, the webhook from a payment provider, the LLM API in Phase 5. Proxies, load balancers and
CDNs all read the same headers, so getting them right once pays off everywhere.

</Level>

<Level name="Strategy">

I spend a session with `curl -i` against ten real sites, writing down one surprising header from each.
Done when I can write a request and response by hand from memory, name the status families, explain
safe and idempotent, and debug a wrong `Content-Type`.

</Level>

</Levels>

#### Phase 0: DNS, at a high level

<Flow
  caption="Resolving a name. Each step can answer from cache, which is why changes take time to spread."
  steps={['Browser cache', 'OS cache', 'Recursive resolver (ISP or 1.1.1.1)', 'Root: who runs .io?', 'TLD: who runs github.io?', 'Authoritative: the A record', 'IP address back to the browser']}
/>

<Levels label="Phase 0, DNS at a high level">

<Level name="Beginner">

Computers connect to IP addresses; people type names. DNS is the distributed phone book that turns
`snjy-kumar.github.io` into an address like `185.199.108.153`. I can ask it directly.

```sh
dig +short snjy-kumar.github.io      # one or more IPs
nslookup example.com
```

Mistake: thinking the website "is" the name. Fix: the name points at servers; the servers serve the
site, and the two can change independently.

</Level>

<Level name="Intermediate">

Record types: `A` maps to an IPv4 address, `AAAA` to IPv6, `CNAME` makes one name an alias for
another, `MX` says where mail goes, `TXT` holds text such as domain verification. For a custom domain
on GitHub Pages, the apex (`example.com`) uses `A` records to GitHub's addresses and `www` uses a
`CNAME` to `<user>.github.io`.

```sh
dig example.com A +noall +answer     # example.com. 3600 IN A 93.184.215.14
dig www.github.com CNAME +short
```

The number in the answer is the TTL in seconds: how long caches may keep it.

</Level>

<Level name="Advanced">

A recursive resolver walks the hierarchy from the root servers to the top-level domain to the domain's
authoritative servers, caching each answer for its TTL. Responses travel over UDP port 53 by default,
or over HTTPS and TLS in newer setups. `dig +trace` shows the walk.

```sh
dig +trace example.com
```

</Level>

<Level name="Edge cases">

A `CNAME` cannot sit at the apex alongside other records, which is why apex domains use `A` records or
a provider's flattening feature. `NXDOMAIN` means the name does not exist; a timeout means no one
answered, which is a different problem. A name that resolves on my laptop but not on my phone is often
a stale local cache or a `/etc/hosts` entry.

</Level>

<Level name="Corner cases">

A long TTL plus an urgent change: the old address lives in caches until the TTL expires, so the fix is
to lower the TTL a day before a planned move. A DNS change plus HTTPS: the new host must have a
certificate for the name, or users get a certificate warning even though DNS is right.

</Level>

<Level name="Production level">

DNS failures look like the whole site being down. Changes are scheduled, TTLs are lowered in advance,
and the registrar account has two-factor authentication, because whoever controls DNS controls where
users go.

</Level>

<Level name="Mindset">

Caching is a trade between speed and freshness. DNS is the first place I meet that trade; it comes back
in HTTP caches, CDNs and React Query.

</Level>

<Level name="System design">

DNS is also a routing tool: geographic answers send users to the nearest region, and failover swaps
addresses when a region dies. It sits in front of everything else in a system diagram.

</Level>

<Level name="Strategy">

Resolve five names with `dig`, trace one, and read the TTLs. Done when I can explain the resolution
walk, the four common record types, and why a DNS change is not instant.

</Level>

#### Phase 0: JSON

<Compare
  left="Valid JavaScript, invalid JSON"
  right="Valid JSON"
  rows={[
    ["{ name: 'Sanjay' }", '{ "name": "Sanjay" }'],
    ['{ "a": 1, }', '{ "a": 1 }'],
    ['{ "when": undefined }', '{ "when": null }'],

    ['NaN, Infinity', 'numbers only, or null'],
  ]}
  caption="JSON looks like a JavaScript object but is stricter: double-quoted keys and strings, no trailing commas, no comments, no undefined."

<Levels label="Phase 0, JSON">

<Level name="Beginner">

JSON is a text format for data: objects in braces, arrays in brackets, strings in double quotes,
numbers, `true`, `false` and `null`. APIs send it, config files use it, and `localStorage` stores it as
text. In JavaScript, `JSON.parse` turns text into a value and `JSON.stringify` turns a value into text.

```js
const text = '{"name":"Sanjay","tags":["ts","react"]}';
const data = JSON.parse(text);
console.log(data.tags[1]);                 // react
console.log(JSON.stringify(data, null, 2)); // pretty-printed
```

Mistake: single quotes inside JSON. `JSON.parse("{'a':1}")` throws `SyntaxError: Expected property
name or '}' in JSON at position 1`. Fix: double quotes, always.

</Level>

<Level name="Intermediate">

On the command line, `jq` reads JSON: `curl -s https://api.github.com/users/snjy-kumar | jq .name`.
In the browser, `fetch` gives `response.json()`. `JSON.stringify` drops functions and `undefined`
properties and turns `Date` into an ISO string, so a round trip is not lossless.

```js
JSON.stringify({ a: undefined, b: () => 1, c: new Date(0) });
// '{"c":"1970-01-01T00:00:00.000Z"}'
```

</Level>

<Level name="Advanced">

`JSON.parse` accepts a reviver and `stringify` a replacer, to convert values on the way in and out. A
class can define `toJSON`. Numbers are IEEE doubles in JavaScript, so integers above 2^53 lose
precision when parsed.

```js
JSON.parse('{"id": 9007199254740993}').id;   // 9007199254740992
JSON.parse('{"at":"2026-10-23T00:00:00Z"}', (k, v) => k === 'at' ? new Date(v) : v).at instanceof Date; // true
```

</Level>

<Level name="Edge cases">

`JSON.parse('')` throws `Unexpected end of JSON input`, which is what an empty 204 response produces
when code calls `.json()` on it. `JSON.stringify(undefined)` returns `undefined`, not a string.
`NaN` becomes `null`. A top-level string is valid JSON: `JSON.parse('"hi"')` is `hi`.

</Level>

<Level name="Corner cases">

A circular object plus `stringify`: `TypeError: Converting circular structure to JSON`. A database ID
stored as a 64-bit integer plus a JavaScript client: two different records end up with the same
rounded ID. Send big IDs as strings.

</Level>

<Level name="Production level">

JSON from outside is untrusted: it parses fine and still has the wrong shape. Phase 1 and Phase 3
validate it at the boundary. Log payloads carefully, since JSON bodies often carry personal data.

</Level>

<Level name="Mindset">

"It parsed" and "it is correct" are different claims. Parsing checks syntax; only validation checks
meaning.

</Level>

<Level name="System design">

JSON is the default contract between front end and back end. Its shape is an API, documented in Phase
3 with OpenAPI and enforced with a schema.

</Level>

<Level name="Strategy">

Hand-write five JSON files, break each one, and log the exact parse error. Done when I can spot
invalid JSON by eye and explain what a round trip through `stringify` loses.

</Level>

</Levels>

<Levels label="Phase 0, an editor I can drive without the mouse">

<Level name="Beginner">

An editor is where I spend most of my working hours, so a little speed compounds. I pick one, VS Code
is the default for web work, and learn five moves: open a file by name, search the whole project,
go to a line, toggle the integrated terminal, and save. Nothing else on day one.

The first thing to configure is not a theme but formatting on save and showing whitespace, so that
the file I see is the file Git sees. Two settings in `settings.json` are enough:

```json
{
  "editor.formatOnSave": true,
  "editor.renderWhitespace": "boundary"
}
```

Mistake: installing thirty extensions in the first hour. Each one adds noise, popups and sometimes
conflicting formatters. The fix is to start with none and add one only when I can name the problem
it solves.

</Level>

<Level name="Intermediate">

The moves that pay most are multi-cursor and symbol navigation. `Ctrl/Cmd-D` selects the next
occurrence of the current word, so renaming a CSS class in five places is five key presses. `F2`
renames a symbol across files using the language server, which understands scope, so it renames the
variable `item` without touching the word `item` inside a string.

```js
// cursor on `total`, press F2, type `subtotal`
let total = 0;
for (const item of cart) total += item.price;
console.log("total:", total);   // the string is left alone; both variables change
```

Project-wide search (`Ctrl/Cmd-Shift-F`) with a regular expression finds patterns: `class="btn[^"]*"`
finds every button class. The command palette (`Ctrl/Cmd-Shift-P`) is the index of everything the
editor can do; when I forget a shortcut, I type what I want there.

</Level>

<Level name="Advanced">

Underneath, the editor runs language servers: separate processes that parse my code and answer
questions over the Language Server Protocol, such as where a symbol is defined, what type it has and
what is wrong with it. The red squiggle under a TypeScript error is the same compiler I run in the
terminal, run continuously. When the editor and the terminal disagree, it is usually because they use
different versions or different config files.

```sh
$ npx tsc --noEmit
src/app.ts:4:7 - error TS2322: Type 'string' is not assignable to type 'number'.
```

If the editor shows no error but `tsc` does, I check which TypeScript the editor uses (the status bar
or "TypeScript: Select TypeScript Version") and point it at the workspace's `node_modules`.

</Level>

<Level name="Edge cases">

Line endings: Windows writes CRLF, Linux and macOS write LF. A file with mixed endings shows every line
as changed in a diff. The fix is a `.gitattributes` with `* text=auto eol=lf` and the editor's line
ending setting at the bottom right. A file saved with a byte order mark breaks some parsers: a JSON
file that starts with an invisible BOM fails `JSON.parse` with `Unexpected token`.

Format on save with no formatter config formats differently on every machine. The fix is to commit a
formatter config (for example `.prettierrc`) so the project, not the editor, decides.

</Level>

<Level name="Corner cases">

Format on save plus a large existing file: I change one line, save, and the formatter rewrites
four hundred lines, so the commit diff hides my real change. The fix is to format the whole file in
its own commit first ("Format index.html, no content change") and make the real change in the next
commit. Reviewers can then skip the first and read the second.

Multi-cursor plus a regex search-and-replace across the project: a pattern that matches more than I
think replaces it in `node_modules` or a minified file too. I preview the matches, exclude folders,
and run Git's diff before saving all.

</Level>

<Level name="Production level">

On a shared project the editor's behaviour has to be the repository's behaviour. That means a
committed `.editorconfig` (indentation, final newline, line endings), a formatter config, a lint
config, and recommended extensions in `.vscode/extensions.json`. Then every contributor's editor
produces the same bytes, and CI runs the same formatter and linter to catch anyone whose editor does
not.

```ini
# .editorconfig
root = true
[*]
indent_style = space
indent_size = 2
end_of_line = lf
insert_final_newline = true
```

I also learn to edit over SSH or in a dev container, because some bugs only reproduce on the machine
where the code runs.

</Level>

<Level name="Mindset">

Tools should disappear. The goal is not to collect shortcuts but to remove the moments where moving
the mouse breaks my train of thought. I learn a shortcut only when I notice I have done the slow
version three times.

</Level>

<Level name="System design">

The editor is the first stage of the feedback loop that the rest of the system extends: squiggle in
the editor, then the type check and tests on save, then lint and tests in CI, then monitoring in
production. The cheaper and earlier a stage catches an error, the better. Configuring the editor to
run the same checks as CI is the first piece of that design.

</Level>

<Level name="Strategy">

Two days, one rule: no mouse inside the editor. I keep a sticky note of the ten moves above and
remove each one when it is automatic. I commit an `.editorconfig` and a formatter config to the page
repository on day one.

Done when I can open any file by name, jump to any symbol, rename across files, search the project with
a regex and run the build in the integrated terminal, all without touching the mouse, and when a fresh
clone formats identically on another machine.

</Level>

</Levels>

#### Phase 0: Git, from init to a pull request

<Figure art={`
  working tree  --git add-->  staging area  --git commit-->  local repo
       ^                                                        |
       |                                                   git push
   git restore                                                  v
       |                                                   remote (GitHub)
       +---------------------- git pull <-----------------------+

  main:     A---B---C-----------M      M = merge commit
                     \\         /
  feature:            D---E---F        a branch is just a moving label
`} caption="Git has three local places and one remote. A commit moves changes from staging into history; a branch is a pointer that moves with each new commit." />

<Levels label="Phase 0, Git from init to a pull request">

<Level name="Beginner">

Git records snapshots of a folder over time. `git init` starts tracking a folder, `git add` chooses
which changes go into the next snapshot, and `git commit` saves that snapshot with a message. `git
status` tells me which of those three states each file is in, and `git log` shows the history.

```sh
$ git init
Initialized empty Git repository in /home/sanjay/projects/page/.git/
$ git add index.html
$ git commit -m "Add the first page with a heading and a paragraph"
[main (root-commit) 3f2a1c9] Add the first page with a heading and a paragraph
 1 file changed, 12 insertions(+)
$ git log --oneline
3f2a1c9 Add the first page with a heading and a paragraph
```

A good commit is one idea with a message that says what changed and why, in plain words. Mistake:
one giant commit called `update` at the end of the day. The fix is to commit each time one small thing
works; the plan asks for ten meaningful commits, and that number is the habit, not a quota.

</Level>

<Level name="Intermediate">

Branches let me try something without disturbing `main`. `git switch -c footer` creates a branch and
moves to it; commits land there. When it works I push it, and on GitHub I open a pull request, which
is a proposal to merge that branch into `main` with a place for review and checks.

```sh
$ git switch -c footer
$ git add index.html css/site.css
$ git commit -m "Add a footer with the source link"
$ git remote add origin git@github.com:snjy-kumar/page.git
$ git push -u origin footer
# GitHub prints a link: Create a pull request for 'footer'
```

`git diff` shows unstaged changes and `git diff --staged` shows what the next commit will contain; I
read the staged diff before every commit. A `.gitignore` keeps generated or secret files, like
`node_modules/` and `.env`, out of history.

Mistake: committing straight to `main` and then wanting to undo. The fix is the branch-per-change
habit, so `main` always matches what is deployed.

</Level>

<Level name="Advanced">

Underneath, Git is a content-addressed store. Every file version is a blob named by the hash of its
contents; a tree lists blobs and subtrees; a commit points to one tree, its parent commits, an author
and a message. A branch is a small file containing one commit hash, and `HEAD` says which branch I am
on. That is why branching is instant: it writes a forty-character hash, nothing more.

```sh
$ cat .git/HEAD
ref: refs/heads/footer
$ cat .git/refs/heads/footer
a91e0c4f7d...
$ git cat-file -p a91e0c4
tree 5b1d...
parent 3f2a1c9...
author Sanjay Kumar <sanjay17126@gmail.com> 1761206400 +0530
```

A merge either fast-forwards (moves the label, if `main` has not moved) or creates a merge commit with
two parents. A rebase replays my commits on top of a new base, producing new hashes, which is why
rebasing commits that others already have rewrites their history too.

</Level>

<Level name="Edge cases">

An empty folder cannot be committed, because Git tracks files, not directories; people add a
`.gitkeep` file. A file added to `.gitignore` after it was committed is still tracked; `.gitignore`
only affects untracked files, so it needs `git rm --cached file`. The very first commit has no parent,
so `git diff HEAD~1` fails on it with `unknown revision`.

A detached HEAD, after `git checkout 3f2a1c9`, means new commits belong to no branch:

```sh
$ git checkout 3f2a1c9
You are in 'detached HEAD' state...
```

The fix if I committed there is `git switch -c rescue` before switching away, so the commits get a
name.

</Level>

<Level name="Corner cases">

A secret committed and then deleted in the next commit is still in history, and pushing that history
publishes it. Two boundaries meet: Git never forgets, and a public remote never forgets either. The
only real fix is to rotate the secret (make the old one useless), then clean history if needed. Prevent
it with `.gitignore` for `.env` before the first commit.

A merge conflict in a file that both branches reformatted: every line conflicts, though the real
changes are two lines. The fix is to land the formatting change on its own first, then merge.

```text
<<<<<<< HEAD
<footer>Built by hand</footer>
=======
<footer>Source on GitHub</footer>
>>>>>>> footer
```

I resolve by choosing the intended text, deleting the markers, then `git add` and `git commit`.

</Level>

<Level name="Production level">

On a team, `main` is protected: no direct pushes, a pull request with at least one review, and green
checks before merge. History is a debugging tool, so small commits with clear messages let `git
bisect` find the commit that introduced a bug in a handful of steps, and `git blame` explain why a line
exists. Force-pushing a shared branch destroys teammates' work; the rule is never force-push what
someone else may have pulled, and use `--force-with-lease` on my own branches.

```sh
$ git bisect start
$ git bisect bad            # current commit is broken
$ git bisect good v1.0      # this tag was fine
# Git checks out the midpoint; I test and mark good or bad until it names the commit
```

</Level>

<Level name="Mindset">

A commit is a message to a future reader, often me at 2am. It should say what changed and why, in a
sentence a stranger understands. Small reversible steps beat one heroic change, because every small
step is something I can undo.

</Level>

<Level name="System design">

Git is the source of truth for everything later: CI runs on a push, a deploy is a commit hash, a
rollback is a revert to a known commit, an infrastructure change is a pull request. Choosing a branch
model (trunk-based with short-lived branches is the default for small teams) decides how often code
integrates and how big each merge risk is.

</Level>

<Level name="Strategy">

Ten commits on the page repository, each one change with a real message, done by typing commands,
not clicking. Then one pull request from a branch, read on GitHub, merged. Then break it: make a
conflict on purpose, detach HEAD, commit an ignored file, and recover each time.

Done when I can draw the working tree, staging area, local repo and remote from memory, explain what a
branch and a merge commit are, resolve a conflict without a GUI, and open and merge a pull request.

</Level>

</Levels>

DevTools (F12, or Cmd-Option-I on a Mac) shows what the browser actually received and built. Elements

Mistake: editing CSS in the Elements panel, liking it, then reloading and losing it. Fix: DevTools edits

</Level>

<Level name="Corner cases">

A browser extension injects scripts and errors into every page, so the console shows errors that are
not mine; check in a private window with extensions off. Disable cache only applies while DevTools is
open, so a bug that appears only for users with DevTools closed is often caching.

</Level>

<Level name="Production level">

Users send screenshots, not stack traces. Reproducing their environment (viewport, network speed,
logged-in state, browser) with DevTools is the first step of most front-end bug reports. Later, error

</Level>

<Level name="Mindset">

Look before guessing. DevTools turns "it does not work" into a specific failed request, a specific
overridden rule or a specific exception, and a specific fact is fixable.

</Level>

<Level name="System design">

DevTools is the client end of observability. The Network panel's timing (DNS, connect, TLS, waiting,

#### Phase 0: Deploying a static page

<Flow
  caption="From my laptop to a public URL on GitHub Pages."
  steps={['Commit index.html and style.css', 'Push to GitHub', 'Settings, Pages: source = main, root', 'GitHub builds and publishes', 'https://user.github.io/repo/', 'Check it on a phone']}
/>

<Levels label="Phase 0, deploying a static page">

<Level name="Beginner">

A static site is files served exactly as they are: HTML, CSS, images. Deploying it means putting the
files on a server that answers HTTP requests for them. GitHub Pages does this from a repository: in the
repo's Settings, under Pages, choose the branch and folder, save, and after a minute or two the site is
at `https://<user>.github.io/<repo>/`. Mistake: a page that works locally by double-click (`file://`)
and breaks online. Fix: test with a local server, `npx serve .` or `python3 -m http.server`, so paths
behave like they will in production.

</Level>

<Level name="Intermediate">

The base path is the classic break. On a project site, the site lives under `/<repo>/`, so a link to
`/style.css` asks for `https://<user>.github.io/style.css` and gets a 404. Relative paths
(`style.css`, `./css/style.css`) work under any base.

```html
<link rel="stylesheet" href="/style.css">   <!-- 404 on a project site -->
<link rel="stylesheet" href="style.css">    <!-- works -->
```

A deploy shows up under the repo's Actions or Deployments tab with a status, which is where to look
when the site does not update.

</Level>

<Level name="Advanced">

Behind the scenes, Pages builds the content (by default with Jekyll, which ignores files and folders
starting with underscore unless a `.nojekyll` file exists), uploads it to a CDN, and serves it with
HTTPS. Custom domains need a `CNAME` file and the DNS records from the previous topic. Modern setups use
a GitHub Actions workflow to build (for example an Astro site) and publish the output folder, which is
how this blog deploys.

</Level>

<Level name="Edge cases">

`Index.html` instead of `index.html`: Linux servers are case-sensitive, so the root returns 404.
A folder `_assets` vanishes because Jekyll skips it. The first deploy of a new repo can take several
minutes, and a 404 during that window is not a bug.

</Level>

<Level name="Corner cases">

A CDN cache plus a fast redeploy: users see the old CSS with the new HTML for a few minutes, and the
page looks broken only for them. Content-hashed filenames solve it later. A private repo plus Pages on a
free plan: the site may not publish at all.

</Level>

<Level name="Production level">

A deploy is not done until I have checked the live URL, on a phone, with the cache disabled. Keep the
deploy repeatable: the same push produces the same site, with no manual uploads. Rollback is `git
revert` and push.

</Level>

<Level name="Mindset">

Shipping early removes fear. A public URL on day ten makes every later deploy routine, and it is the
proof the plan asks for.

</Level>

<Level name="System design">

Static hosting plus a CDN is the cheapest, most reliable architecture there is: no server to crash.
Later phases add an API behind it, but the front end often stays exactly this shape.

</Level>

<Level name="Strategy">

Deploy on day one, even a single heading, then redeploy every day. Done when the site is public,
loads with no console errors on desktop and phone, and I can roll back a bad change.

</Level>

</Levels>

#### Phase 0: Semantic HTML and one CSS file

<Figure art={`
  <body>
  +--------------------------------------------------+
  | <header>  site name, <nav> with three links      |
  +--------------------------------------------------+
  | <main>                                           |
  |   <h1> one per page </h1>                        |
  |   <section> <h2> About </h2> ... </section>      |
  |   <section> <h2> Projects </h2> <ul>...</ul>     |
  +--------------------------------------------------+
  | <footer>  contact, source link                   |

`} caption="The page's landmarks. Screen readers and search engines navigate by these, not by how the page looks." />

<Levels label="Phase 0, semantic HTML and one CSS file">

<Level name="Beginner">

HTML says what things are; CSS says how they look. Semantic elements name their role: `header`,
`nav`, `main`, `section`, `article`, `footer`, headings `h1` to `h6` in order, `a` for links, `button`
for actions, `ul` and `li` for lists. One stylesheet linked from the head.

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Sanjay Kumar</title>
  <link rel="stylesheet" href="style.css">
</head>
<body>
  <header><nav><a href="./">Home</a></nav></header>
  <main><h1>Sanjay Kumar</h1><p>I build things for the web.</p></main>
  <footer><a href="https://github.com/snjy-kumar">GitHub</a></footer>
</body>
</html>
```

Mistake: a `div` with a click handler as a button. Fix: `button`, which is focusable and works with the
keyboard for free.

</Level>

<Level name="Intermediate">

CSS cascade basics: rules match by selector, and when two rules set the same property, the more
specific selector wins, then the later one. A small layout uses flexbox for rows and a max width for
readable lines.

```css
:root { --ink: #111; --paper: #fff; }
body { margin: 0; font: 1rem/1.6 system-ui, sans-serif; color: var(--ink); background: var(--paper); }
main { max-width: 65ch; margin: 0 auto; padding: 1rem; }
nav { display: flex; gap: 1rem; }
```

Images need `alt` text that says what the image means; decorative ones get `alt=""`.

</Level>

<Level name="Advanced">

The browser builds the DOM from HTML and the CSSOM from CSS, combines them, computes layout, then
paints. Specificity is counted as (ids, classes and attributes, elements): `#nav a` beats `.menu a`
beats `nav a`. The `viewport` meta tag stops phones rendering the page at desktop width and zooming
out. Accessibility comes from the accessibility tree the browser derives from semantic elements.

</Level>

<Level name="Edge cases">

Two `h1` elements, or skipping from `h1` to `h4`, breaks the heading outline screen-reader users
navigate by. A missing `lang` attribute makes a screen reader guess the pronunciation. Text over a
background image fails contrast on some parts of the image.

</Level>

<Level name="Corner cases">

`display: none` hides an element from screen readers too, while a visually hidden class hides it only
from sight; mixing them up removes a label or leaves a ghost one. A long unbroken URL inside a narrow
column overflows the page on a phone; `overflow-wrap: anywhere` fixes it.

</Level>

<Level name="Production level">

Semantic markup is SEO, accessibility and maintainability at once, for free. One CSS file with a few
custom properties is the seed of the design tokens in Phase 2. Validate HTML with the W3C validator and
run Lighthouse's accessibility audit before calling the page done.

</Level>

<Level name="Mindset">

Use the platform before adding to it. Starting with a framework because a tutorial did is the trap the
plan names; plain HTML shows what a framework is generating for me.

</Level>

<Level name="System design">

The same landmark structure carries into every React layout later; components render HTML, and
accessibility is decided by which HTML they render.

</Level>

<Level name="Strategy">

Write the page by hand, no generator, no copied template. Done when it has one `h1`, landmarks, alt
text, a valid document, a readable layout on a phone, and a Lighthouse accessibility score with no
failed checks I cannot explain.

</Level>

</Levels>

<Levels label="Phase 0, ten meaningful commits and a README">

<Level name="Beginner">

The build target: a repo with ten commits, each one change with a message that says what and why, and a
README that says what the project is and how to run it. A README is the front page of the repo, rendered
by GitHub.

```md
# sanjay-site
My one-page personal site, plain HTML and CSS.
## Run locally
npx serve .   then open http://localhost:3000
## Deploy
Pushed to main, published by GitHub Pages.
```

Mistake: ten commits made by splitting one change into arbitrary pieces. Fix: ten real decisions.

</Level>

<Level name="Intermediate">

Commit message shape: a subject under about 72 characters in the imperative ("Add", "Fix", "Remove"),
a blank line, then a body when the why needs more room. `git add -p` stages parts of a file, so one
messy session can still become several clean commits.

</Level>

<Level name="Advanced">

`git commit --amend` fixes the last message before pushing; interactive rebase reorders and rewrites
local commits. Once pushed and shared, history is public and I add new commits instead.

</Level>

<Level name="Edge cases">

A commit that only formats code clutters `git blame`; keep formatting commits separate and say so. An
empty README is worse than none, because it promises documentation.

</Level>

<Level name="Corner cases">

A README instruction that worked once but depends on a global tool I forgot I installed: a stranger
following it fails. Test the README in a fresh clone in a temporary folder.

</Level>

<Level name="Production level">

In teams, the README is onboarding, and commit history is the explanation for why code looks the way it
does. Good history shortens every incident investigation.

</Level>

<Level name="Mindset">

Write for the reader who arrives with no context, which is me in six months.

</Level>

<Level name="System design">

Docs live next to code and change in the same PR, so they cannot drift silently.

</Level>

<Level name="Strategy">

Done when a stranger can clone the repo, run the site from the README alone, and understand each of
the ten commits from its message.

</Level>

</Levels>

#### Phase 0: The proof, from a typed URL to a painted page

<Flow
  caption="What happens between typing a URL and seeing the page, split by who does the work."
  steps={['Browser: parse the URL', 'Network: DNS lookup', 'Network: TCP and TLS handshake', 'Server: receive GET, find the file', 'Network: response travels back', 'Browser: parse HTML, request CSS', 'Browser: style, layout, paint']}
/>

<Levels label="Phase 0, from a typed URL to a painted page">

<Level name="Beginner">

The plan's proof is explaining this chain, naming which part is the browser, the network and the
server. Browser: works out the scheme, host and path. Network: DNS turns the host into an IP, a
connection opens, TLS encrypts it. Server: reads the request and sends the file. Browser again: parses
the HTML, discovers the stylesheet, requests it, builds the page, paints. Mistake: "the server sends the
page and it appears". Fix: the HTML is only the first of several requests.

</Level>

<Level name="Intermediate">

The Network panel's waterfall shows the chain: the document first, then CSS, then images. The
Timing tab breaks one request into queueing, DNS, initial connection, SSL, waiting for the server, and
content download. A second visit reuses the connection and cache, so many steps vanish.

</Level>

<Level name="Advanced">

CSS blocks rendering (the browser waits for it to avoid a flash of unstyled content); classic scripts
in the head block parsing unless `defer` or `async` is set. TLS 1.3 needs one round trip; HTTP/2 lets
the CSS and images share the connection. The renderer then builds DOM and CSSOM, computes layout, paints
layers and composites them on the GPU.

</Level>

<Level name="Edge cases">

An offline device: DNS fails first, and the browser shows its own error page with a code like
`ERR_NAME_NOT_RESOLVED`. An expired certificate stops the chain at TLS with a full-page warning before
any HTTP happens.

</Level>

<Level name="Corner cases">

A service worker answers from cache before the network is touched, so the page loads offline, and also
keeps serving an old version after a deploy until it updates.

</Level>

<Level name="Production level">

Every performance metric in Phase 4 lives on this chain: time to first byte is the server and network,
largest contentful paint is the whole chain. Knowing the chain is knowing where to look.

</Level>

<Level name="Mindset">

Divide a system by responsibility, then ask which part failed. That habit is debugging.

</Level>

<Level name="System design">

CDNs shorten the network leg, caching removes legs, and server rendering moves work from the browser to
the server. Every architecture choice later moves work along this chain.

</Level>

<Level name="Strategy">

Explain the chain to a friend on a whiteboard without notes, then check it against DevTools. Done when
I can do it in three minutes and answer "which part is slow?" from a waterfall.

</Level>

</Levels>

#### Phase 0: The traps, and the AI-era note

<Compare
  left="The trap"
  right="What I do instead"
  rows={[

<Levels label="Phase 0, the traps and the AI-era note">

<Level name="Beginner">

The plan's AI rule for this phase: ask a model to explain an error or a Git command, do not ask it to
write the first page. Asking "what does `fatal: not a git repository` mean?" is learning; asking for a
finished site skips the memory I will later debug against.

</Level>

<Level name="Intermediate">

A useful prompt includes the exact error, the command, and what I expected. Then I verify the answer
by running it, not by trusting it. If the explanation and the machine disagree, the machine wins.

</Level>

<Level name="Advanced">

Models are confident about commands that changed between versions, flags that do not exist on my
platform (GNU against BSD `sed -i`), and destructive operations. Anything with `rm`, `reset --hard` or
`push --force` gets read twice.

</Level>

<Level name="Edge cases">

An error message containing a token or a path with my name gets pasted into a chat: redact before
pasting.

</Level>

<Level name="Corner cases">

A model's suggested fix works and hides the cause (for example `sudo` to get past a permission error,
leaving root-owned files in my project). It passes now and breaks the next command.

</Level>

<Level name="Production level">

The six AI rules in the plan start here: never run or merge what I cannot explain.

</Level>

<Level name="Mindset">

The first memory of doing it by hand is the reference I compare every later generated answer against.

</Level>

<Level name="System design">

AI is a tool in my workflow, like the terminal: it gets inputs, I verify its outputs.

</Level>

<Level name="Strategy">

Done when the page, the commits and the README are mine, my log has at least ten entries, and every AI
answer I used is linked to a command I ran to confirm it.

</Level>

</Levels>
