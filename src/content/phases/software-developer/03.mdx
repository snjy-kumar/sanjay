Eight weeks to own the whole request path, from the click to the row in the database and back. Every item
on the plan's list is here, in the order a request meets them: Node, Express or Fastify, routing and
middleware, validation, REST and status codes, Postgres, SQL with joins, indexes and transactions, schema
design, Prisma, migrations, authentication with sessions or short-lived tokens, password hashing,
cookies, CORS, file upload, email, structured logging and error handling. Then the build (a full-stack
app where a user signs up, logs in, manages their own records and uploads an image), the proof (a schema
diagram, API docs, an auth flow drawn from memory, integration tests, a seed script, and a test proving a
second user cannot read the first user's data) and Gate 3. *Designing Data-Intensive Applications*,
which the plan recommends after this first full-stack app rather than before, is the reading that
follows this phase.

#### Phase 3: how I would learn it

SQL first, in `psql`, before any ORM touches it, because the plan's first trap is skipping SQL because an
ORM hides it. Then a tiny HTTP server with only `node:http`, so I know what a framework adds, then
Fastify or Express for the real app. Each week adds one layer to the request path and one integration
test that exercises it end to end. I keep a running schema diagram and an API doc in the repo from day
one, updated in the same commit as the code.

<Levels label="Phase 3, Node">

<Level name="Beginner">

Node runs JavaScript outside the browser. No DOM, but files, network sockets, processes and environment
variables. A server with nothing but Node:

```js
import { createServer } from 'node:http';
createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ ok: true, path: req.url }));
}).listen(3000, () => console.log('http://localhost:3000'));
```

`curl -i localhost:3000/hello` prints `HTTP/1.1 200 OK` and `{"ok":true,"path":"/hello"}`. Mistake:
`EADDRINUSE: address already in use :::3000` from a server still running. Fix: stop it, or
`lsof -i :3000` to find it.

</Level>

<Level name="Intermediate">

`package.json` scripts, `"type": "module"`, environment variables via `process.env` and
`node --env-file=.env`, and `node --watch` for reloads. Reading a request body is a stream:

```js
const chunks = [];
for await (const chunk of req) chunks.push(chunk);
const body = JSON.parse(Buffer.concat(chunks).toString('utf8'));
```

</Level>

<Level name="Advanced">

Node's event loop serves many requests on one thread because I/O waits are handed to the OS or libuv's
thread pool. CPU-heavy work (hashing, image resizing, big JSON) blocks every request; use async APIs,
worker threads or a job queue. Streams handle large data without loading it into memory.

</Level>

<Level name="Edge cases">

A request body larger than memory, or an endless slow upload: set size limits and timeouts. A missing
environment variable is `undefined`, and `Number(undefined)` is `NaN`, so a `PORT` of `NaN` fails later
and confusingly. Validate config at startup.

</Level>

<Level name="Corner cases">

An unhandled promise rejection inside a handler crashes the whole process (Node's default), taking down
every other user's request. A synchronous `bcrypt.hashSync` under load plus a health check: the health
check times out and the platform restarts a healthy process.

</Level>

<Level name="Production level">

Run Node under a process manager or a platform that restarts it, use LTS versions, log to stdout, handle
`SIGTERM` to finish in-flight requests before exit, and pin the version in `.nvmrc` or `engines`.

</Level>

<Level name="Mindset">

Learn the primitive under the framework: one evening with `node:http` explains everything Express and
Fastify do for me.

</Level>

<Level name="System design">

A Node API is usually stateless, so several copies can run behind a load balancer; state lives in
Postgres and, later, a cache.

</Level>

<Level name="Strategy">

Done when I can build a JSON endpoint with `node:http` from memory, explain why blocking work hurts every
user, and the app validates its config at startup.

</Level>

</Levels>

#### Phase 3: Express or Fastify, routing and middleware

<Flow
  caption="Middleware is a pipeline. Each step can pass the request on, answer it, or fail it."

<Levels label="Phase 3, Express or Fastify, routing and middleware">

<Level name="Beginner">

A framework maps method and path to a handler, parses bodies, and composes middleware. Fastify:

```ts
import Fastify from 'fastify';
const app = Fastify({ logger: true });
app.get('/health', async () => ({ ok: true }));
app.get('/notes/:id', async (req) => {
  const { id } = req.params as { id: string };
  return { id };
});
await app.listen({ port: 3000 });
```

Express is the same shape with `(req, res, next)` handlers. I pick one and learn it well.

</Level>

<Level name="Intermediate">

Middleware (Express) or hooks and plugins (Fastify) run before handlers: authentication, logging, rate
limits. Group routes by resource.

```ts
// Express
app.use(express.json({ limit: '100kb' }));
app.use(requestId);
app.use('/api/notes', requireUser, notesRouter);
app.use(errorHandler); // last, four arguments: (err, req, res, next)
```

</Level>

<Level name="Advanced">

Order matters: middleware runs in registration order. Express 5 forwards rejected promises from async
handlers to the error handler; Express 4 does not, which left requests hanging. Fastify's schema-based
routes validate and serialise faster, and encapsulate plugins so a decorator in one scope does not leak
to another.

</Level>

<Level name="Edge cases">

Trailing slashes and case: `/notes/` and `/Notes` may not match `/notes`. A route `/notes/:id` registered
before `/notes/export` swallows "export" as an id. Register specific routes first, or rely on the
router's precedence rules.

</Level>

<Level name="Corner cases">

An auth middleware mounted after the router that it should protect: routes are public and nothing errors.
A test for an unauthenticated request catches it.

</Level>

<Level name="Production level">

Body size limits, timeouts, a request id on every log line, graceful shutdown, and security headers (via
`helmet` in Express or `@fastify/helmet`).

</Level>

<Level name="Mindset">

Each middleware is a decision applied to every request. Know the list and its order.

</Level>

<Level name="System design">

Cross-cutting concerns (auth, logging, limits) live in the pipeline, not in handlers; the same idea scales
to API gateways.

</Level>

<Level name="Strategy">

Done when I can draw my app's middleware order and a test proves protected routes reject anonymous
requests.

</Level>

</Levels>

<Levels label="Phase 3, validation">

<Level name="Beginner">

Anything from outside (body, query, params, headers) is untrusted. Validate its shape and limits before
using it. Zod defines the schema and the TypeScript type at once.

```ts
import { z } from 'zod';
const NoteInput = z.object({ title: z.string().trim().min(1).max(200), body: z.string().max(10_000).default('') });
type NoteInput = z.infer<typeof NoteInput>;
const result = NoteInput.safeParse(req.body);
if (!result.success) return reply.code(400).send({ error: 'invalid_input', issues: result.error.issues });
```

</Level>

<Level name="Intermediate">

Coerce query strings (`z.coerce.number().int().min(1).max(100)` for `?limit=`), validate ids
(`z.string().uuid()`), and return field-level errors the UI can show next to inputs.

</Level>

<Level name="Advanced">

Parse, don't validate: the function returns a typed value, so the rest of the code never sees raw input.
Strip unknown keys to stop mass assignment (a client sending `"role": "admin"`). Share schemas with the
front end for instant feedback.

</Level>

<Level name="Edge cases">

Empty strings, whitespace only, a number sent as a string, `null` against missing, unicode lookalikes,
very long strings, arrays where an object was expected, and `__proto__` keys.

</Level>

<Level name="Corner cases">

A schema with `.default()` plus a PATCH endpoint: the default fills fields the client never sent and
overwrites stored data. Use a separate partial schema for updates with no defaults.

</Level>

<Level name="Production level">

Validate on the server, always: the first line of the plan's security checklist. Log rejected input
counts, not contents.

</Level>

<Level name="Mindset">

The boundary is where trust is decided. Inside it, types are true.

</Level>

<Level name="System design">

Every boundary validates: HTTP input, queue messages, webhook payloads, and in Phase 5 model output.

</Level>

<Level name="Strategy">

Done when every route parses its input with a schema, and a test sends garbage to each and gets a 400.

</Level>

</Levels>

#### Phase 3: REST and status codes

<Figure art={`

<Levels label="Phase 3, REST and status codes">

<Level name="Beginner">

REST organises an API around resources (`/notes`) and uses HTTP methods for actions. Status codes tell
the client what happened, so it can react without parsing prose.

```sh
curl -i -X POST localhost:3000/notes -H 'content-type: application/json' -d '{"title":"First"}'
# HTTP/1.1 201 Created
# location: /notes/42
```

Mistake: `200 { "error": "not found" }`. Fix: 404 with an error body.

</Level>

<Level name="Intermediate">

One consistent error shape: `{ "error": "not_found", "message": "Note 42 does not exist" }`. Pagination
with `limit` and a cursor. Filtering and sorting via query parameters.

</Level>

<Level name="Advanced">

Idempotency from Phase 0 matters here: PUT and DELETE can be retried safely; POST cannot unless the
client sends an `Idempotency-Key` the server remembers. 401 means "who are you?", 403 means "I know who
you are, and no". Some APIs return 404 instead of 403 to avoid revealing that a record exists.

</Level>

<Level name="Edge cases">

DELETE on an already deleted record: 204 or 404, chosen and documented. An empty list is 200 with `[]`,
never 404. A page beyond the end returns an empty page.

</Level>

<Level name="Corner cases">

Offset pagination plus inserts during paging: items shift and the user sees duplicates or misses rows.
Cursor pagination (by id or created time) fixes it.

</Level>

<Level name="Production level">

Status codes drive dashboards and alerts: a spike in 5xx pages someone. Version the API or evolve it
additively so old clients keep working.

</Level>

<Level name="Mindset">

An API is a promise to clients I do not control. Be boring and consistent.

</Level>

<Level name="System design">

Monolith and REST first, as the plan's "what to ignore" list says; GraphQL and microservices only once
these are boring.

</Level>

<Level name="Strategy">

Done when every endpoint returns the right code for success and each failure, documented in the API docs.

</Level>

</Levels>

<Levels label="Phase 3, Postgres">

<Level name="Beginner">

Postgres is a relational database: data in tables of rows and typed columns, queried with SQL. Run it
locally with Docker and connect with `psql`.

```sh
docker run --name pg -e POSTGRES_PASSWORD=dev -p 5432:5432 -d postgres:17
psql postgres://postgres:dev@localhost:5432/postgres
```

```sql
CREATE TABLE notes (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, title text NOT NULL, created_at timestamptz NOT NULL DEFAULT now());
INSERT INTO notes (title) VALUES ('First') RETURNING *;
```

</Level>

<Level name="Intermediate">

Types that matter: `text`, `integer` and `bigint`, `numeric` for money, `boolean`, `timestamptz` (always
with time zone), `uuid`, `jsonb`. `psql` commands: `\dt` lists tables, `\d notes` describes one.

</Level>

<Level name="Advanced">

MVCC: each transaction sees a snapshot; updates write new row versions, and `VACUUM` cleans old ones.
Connections are expensive processes, so apps use a pool, and serverless platforms need a pooler.

</Level>

<Level name="Edge cases">

`timestamp` without time zone stores a wall-clock time with no zone, which shifts silently between servers;
use `timestamptz`. Text comparison is case-sensitive: `'A' = 'a'` is false.

</Level>

<Level name="Corner cases">

A pool of 10 per app instance plus 20 instances: 200 connections against a database that allows 100.
Requests time out waiting for connections while the database looks idle.

</Level>

<Level name="Production level">

Managed Postgres (Neon or Supabase, from the plan's cost table), backups enabled and a restore tested,
credentials in environment variables, TLS on.

</Level>

<Level name="Mindset">

The database outlives the code. Design it more carefully than anything else.

</Level>

<Level name="System design">

Postgres is enough for most apps far longer than people expect: queues, full-text search and JSON all fit
before adding another system.

</Level>

<Level name="Strategy">

Done when I can create, query and describe tables in `psql` without an ORM.

</Level>

</Levels>

`} caption="A join matches rows across tables by a key. LEFT JOIN keeps rows that have no match." />

<Levels label="Phase 3, SQL, joins and aggregates">

<Level name="Beginner">

`SELECT` reads, `WHERE` filters, `ORDER BY` sorts, `LIMIT` caps. `INSERT`, `UPDATE`, `DELETE` write.

```sql
SELECT id, title FROM notes WHERE user_id = 1 ORDER BY created_at DESC LIMIT 20;
UPDATE notes SET title = 'Renamed' WHERE id = 10 AND user_id = 1;
```

Mistake: `UPDATE notes SET title = 'x'` without `WHERE` updates every row. Fix: write the `WHERE` first,
and run a `SELECT` with it before the `UPDATE`.

</Level>

<Level name="Intermediate">

Joins and aggregates:

```sql
SELECT u.email, count(n.id) AS notes
FROM users u LEFT JOIN notes n ON n.user_id = u.id
GROUP BY u.email
HAVING count(n.id) < 5
ORDER BY notes DESC;
```

`count(n.id)` counts matches; `count(*)` would count the user's own row as 1 even with no notes.

</Level>

<Level name="Advanced">

CTEs (`WITH`) name intermediate results; window functions compute across rows without collapsing them,
like each user's latest note.

```sql
SELECT * FROM (
  SELECT n.*, row_number() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn FROM notes n
) t WHERE rn = 1;
```

</Level>

<Level name="Edge cases">

`NULL` is not equal to anything, including `NULL`: `WHERE x = NULL` returns nothing; use `IS NULL`.
`NOT IN` with a subquery containing a `NULL` returns no rows at all.

</Level>

<Level name="Corner cases">

A LEFT JOIN plus a `WHERE n.title = 'x'` on the right table turns it back into an inner join, because
`NULL` rows fail the filter. Put the condition in the `ON` clause.

</Level>

<Level name="Production level">

Always parameterised queries (`$1`), never string concatenation, or SQL injection follows. ORMs do this;
raw queries must too.

</Level>

<Level name="Mindset">

Ask the database the question in one query, instead of fetching everything and filtering in JavaScript.

</Level>

<Level name="System design">

The N+1 problem (one query per item in a list) is the most common ORM performance bug; a join or a
batched query fixes it.

</Level>

<Level name="Strategy">

Thirty queries in `psql` against my seed data, from simple selects to window functions. Done when I can
write the app's main queries by hand and explain each join.

</Level>

</Levels>

#### Phase 3: Indexes

<Figure art={`
  Seq Scan on notes  (rows read: 1,000,000)  ->  ~200 ms
  CREATE INDEX notes_user_created ON notes (user_id, created_at DESC);
  Index Scan using notes_user_created  (rows read: 20)  ->  ~0.1 ms
                 B-tree
              [ 500 | 900 ]
             /      |      \
     [..250..]  [..700..]  [..1200..]  -> leaf -> row
`} caption="An index is a sorted structure beside the table. EXPLAIN tells me whether a query uses it." />

<Levels label="Phase 3, indexes">

<Level name="Beginner">

An index lets the database find rows without reading the whole table, like a book's index. Primary keys
and unique constraints get one automatically. Foreign keys do not.

```sql
CREATE INDEX notes_user_id_idx ON notes (user_id);
```

</Level>

<Level name="Intermediate">

`EXPLAIN ANALYZE` runs the query and shows the plan and real timing. Read it for `Seq Scan` on a large
table filtered by a selective condition.

```sql
EXPLAIN ANALYZE SELECT * FROM notes WHERE user_id = 1 ORDER BY created_at DESC LIMIT 20;
```

</Level>

<Level name="Advanced">

A composite index `(user_id, created_at)` serves the filter and the sort together; column order matters,
because the index is sorted by the first column first. Partial indexes (`WHERE deleted_at IS NULL`) and
unique indexes enforce rules too.

</Level>

<Level name="Edge cases">

On a small table the planner rightly ignores the index; a sequential scan is cheaper. `WHERE lower(email)
= $1` does not use an index on `email`; it needs an expression index on `lower(email)`.

</Level>

<Level name="Corner cases">

`LIKE '%term'` with a leading wildcard cannot use a B-tree index. A composite index `(a, b)` does not help
a query filtering only on `b`.

</Level>

<Level name="Production level">

Every index slows writes and takes space. Index the queries the app actually runs; find them in slow
query logs. `CREATE INDEX CONCURRENTLY` avoids locking a busy table.

</Level>

<Level name="Mindset">

Measure, then index. Rule 10 again, at the database.

</Level>

<Level name="System design">

Access patterns drive schema and index design; Phase 4 returns to indexes as a performance tool.

</Level>

<Level name="Strategy">

Seed a million rows, find a slow query with `EXPLAIN ANALYZE`, add the right index, measure again. Done
when I can read a plan and explain the change.

</Level>

</Levels>

#### Phase 3: Transactions

<Flow
  caption="A transaction: all of it, or none of it."
  steps={['BEGIN', 'INSERT order', 'UPDATE stock - 1', 'any step fails?', 'yes: ROLLBACK, nothing happened', 'no: COMMIT, all visible at once']}
/>

<Levels label="Phase 3, transactions">

<Level name="Beginner">

A transaction groups statements so they all succeed or all fail. Without one, a crash between two writes
leaves half-done data.

```sql
BEGIN;
INSERT INTO orders (user_id, product_id) VALUES (1, 7);
UPDATE products SET stock = stock - 1 WHERE id = 7;
COMMIT;
```

</Level>

<Level name="Intermediate">

In Prisma, `prisma.$transaction(async (tx) => { ... })` runs a callback in one transaction; throwing rolls
it back.

</Level>

<Level name="Advanced">

Isolation levels decide what concurrent transactions see. Postgres defaults to Read Committed, where two
transactions can both read stock 1 and both sell it. Fix with an atomic update and a check
(`UPDATE ... SET stock = stock - 1 WHERE id = 7 AND stock > 0 RETURNING stock`), `SELECT ... FOR UPDATE`,
or the Serializable level with retries.

</Level>

<Level name="Edge cases">

A transaction left open (a forgotten `COMMIT`, an exception without rollback) holds locks and blocks
other writers. Statement timeouts and idle-in-transaction timeouts protect the database.

</Level>

<Level name="Corner cases">

A transaction that also sends an email: the email goes out, then the transaction rolls back. Send side
effects after commit, or through an outbox table processed later.

</Level>

<Level name="Production level">

Keep transactions short, never wait on a network call inside one, and handle serialization failures with
a retry.

</Level>

<Level name="Mindset">

Ask "what if two people do this at the same moment?" for every write.

</Level>

<Level name="System design">

The outbox pattern and idempotent handlers come back in the backend series and in Phase 6 agents.

</Level>

<Level name="Strategy">

Write a test that runs two purchases of the last item concurrently. Done when exactly one succeeds.

</Level>

</Levels>

<Levels label="Phase 3, schema design">

<Level name="Beginner">

A schema is the set of tables, columns and rules. One table per kind of thing, a primary key on each,
and foreign keys for relationships.

</Level>

<Level name="Intermediate">

Constraints make bad data impossible: `NOT NULL`, `UNIQUE`, `CHECK (length(title) <= 200)`, foreign keys
with a chosen `ON DELETE` behaviour. Many-to-many relationships use a join table.

</Level>

<Level name="Advanced">

Normalise to remove duplicated facts, then denormalise deliberately for read speed with a plan to keep
copies in sync. Tenant or owner columns on every owned table make authorization queries simple. Soft
delete (`deleted_at`) against hard delete is a product and privacy decision.

</Level>

<Level name="Edge cases">

Emails differing only by case collide in real life: store a normalised lowercase version with a unique
index. Unbounded text columns need app-level limits.

</Level>

<Level name="Corner cases">

A unique constraint plus soft delete: a deleted user's email blocks a new sign-up. Use a partial unique
index `WHERE deleted_at IS NULL`.

</Level>

<Level name="Production level">

Schema changes on live data are migrations (next topics), planned to avoid locks and downtime.

</Level>

<Level name="Mindset">

The plan's AI note: the schema, the boundaries and the failure modes are where my value is. AI can write
CRUD; it should not choose the schema.

</Level>

<Level name="System design">

Gate 3 is a multi-user schema. The ownership column is what makes isolation provable.

</Level>

<Level name="Strategy">

Design on paper, then in SQL, then in Prisma. Done when the diagram is in the README and every rule I
care about is a constraint, not a hope.

</Level>

</Levels>

#### Phase 3: Prisma

<Levels label="Phase 3, Prisma">

<Level name="Beginner">

Prisma is a TypeScript ORM: a schema file describes models, and a generated client gives typed queries.

```prisma
model User { id String @id @default(uuid()) email String @unique passwordHash String notes Note[] }
model Note { id String @id @default(uuid()) title String body String @default("") user User @relation(fields: [userId], references: [id], onDelete: Cascade) userId String createdAt DateTime @default(now()) @@index([userId, createdAt]) }
```

```ts
const notes = await prisma.note.findMany({ where: { userId }, orderBy: { createdAt: 'desc' }, take: 20 });
```

</Level>

<Level name="Intermediate">

`select` and `include` choose fields and relations; `update` and `delete` with a compound `where` enforce
ownership.

```ts
const { count } = await prisma.note.deleteMany({ where: { id, userId } }); // 0 means not yours or gone

```

</Level>

<Level name="Advanced">

SQL. `$queryRaw` with tagged templates is parameterised; `$queryRawUnsafe` is not.

</Level>

<Level name="Edge cases">

`findUnique` returns `null`, not an error; `findUniqueOrThrow` throws. A unique violation throws a known
error with code `P2002`, which should become a 409.

</Level>

<Level name="Corner cases">

`include` of a relation inside a list query plus a large list: Prisma batches it, but returning every
note's every tag can still send megabytes. Select only what the page shows.

</Level>

<Level name="Production level">

One Prisma client per process, a connection limit sized to the database, and generated code in CI.

</Level>

<Level name="Mindset">

An ORM is a convenience over SQL, not a replacement for knowing it.

</Level>

<Level name="System design">

The Prisma schema becomes the source type that the API's DTOs derive from, continuing the one-source idea
from Phase 1.

</Level>

<Level name="Strategy">

For every Prisma query in the app, read the SQL it logs once. Done when none of them surprise me.

#### Phase 3: Authentication with sessions or short-lived tokens

<Figure art={`
  POST /login {email, password}
     |  find user by email; verify(password, hash)
     |  ok -> create session row {id: random 32 bytes, user_id, expires_at}
     v
  Set-Cookie: sid=...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800
     |
  later: GET /notes  Cookie: sid=...
     |  look up session, not expired -> req.user
     v
  POST /logout -> delete session row, clear cookie

<Levels label="Phase 3, authentication with sessions or short-lived tokens">

<Level name="Beginner">

Authentication answers "who is this?". After a correct password, the server creates a session and gives
the browser a cookie with a random session id; each request sends it back.

```ts
const sid = crypto.randomBytes(32).toString('base64url');
await prisma.session.create({ data: { id: hash(sid), userId: user.id, expiresAt: addDays(new Date(), 7) } });
reply.setCookie('sid', sid, { httpOnly: true, secure: true, sameSite: 'lax', path: '/', maxAge: 7 * 86400 });
```

</Level>

<Level name="Intermediate">

Server sessions can be revoked instantly by deleting the row. Tokens (JWTs) are signed, self-contained
and verified without a lookup, so they cannot be revoked before expiry; keep them short-lived with a
refresh flow. For a single web app, sessions in `httpOnly` cookies are the simpler, safer default.

</Level>

<Level name="Advanced">

Store a hash of the session id, so a leaked database does not leak usable sessions. Rotate the session id
on login (prevents session fixation). Expire idle sessions. JWTs must check `alg`, issuer, audience and
expiry, and never put secrets in the payload, which is only encoded, not encrypted.

</Level>

<Level name="Edge cases">

Login error messages: "email or password is incorrect" for both cases, to avoid revealing which emails
exist. Expired sessions return 401 and the UI redirects to login while keeping the user's place.

</Level>

<Level name="Corner cases">

A password change plus other logged-in devices: their sessions must be revoked. With stateless JWTs that
cannot happen until expiry, which is why lifetimes stay short.

</Level>

<Level name="Production level">

Rate-limit login (from the security checklist), log sign-ins and failures without passwords, and offer a
"log out everywhere".

</Level>

<Level name="Mindset">

Authentication is not authorization: the plan's trap is checking one and not the other.

</Level>

<Level name="System design">

Managed auth providers exist and are fine; building it once by hand is how I learn what they promise.

</Level>

<Level name="Strategy">

Done when I can draw the flow from memory, and tests cover login, logout, expiry and a bad password.

</Level>

</Levels>

#### Phase 3: Password hashing

<Compare
  left="Wrong"
  right="Right"
  rows={[
    ['plain text', 'argon2id or bcrypt'],

    ['one global salt', 'a random salt per password, stored in the hash string'],
    ['compare with ===', 'the library verify function (constant time)'],

<Levels label="Phase 3, password hashing">

<Level name="Beginner">

Never store passwords. Store a hash from a password-hashing function, argon2 or bcrypt, as the plan's
checklist says, and verify on login.

```ts
import argon2 from 'argon2';
const passwordHash = await argon2.hash(password);          // $argon2id$v=19$m=65536,t=3,p=4$...
const ok = await argon2.verify(user.passwordHash, attempt); // true or false
```

</Level>

<Level name="Intermediate">

The hash string contains the algorithm, parameters and salt, so verification needs nothing else.
Enforce a minimum length (and allow long passphrases) rather than composition rules.

</Level>

<Level name="Advanced">

Slow hashes make guessing expensive: argon2id is memory-hard, which resists GPU attacks. Tune the cost so
hashing takes a noticeable fraction of a second on my server; re-hash on login when parameters change.

</Level>

<Level name="Edge cases">

bcrypt only uses the first 72 bytes of the input, so very long passwords are truncated. Unicode
passwords should be normalised (NFKC) before hashing, or the same password typed on two devices fails.

</Level>

<Level name="Corner cases">

A login endpoint that returns faster for unknown emails (no hash computed) leaks which emails exist
through timing. Hash a dummy value on that path.

</Level>

<Level name="Production level">

Hashing is CPU work that blocks Node's thread pool; rate limits protect both security and capacity.

</Level>

<Level name="Mindset">

Assume the database will leak one day. Design so that day is survivable.

</Level>

<Level name="System design">

The same thinking applies to API keys and session ids: store hashes, show the secret once.

</Level>

<Level name="Strategy">

Done when no plain password exists anywhere in code, logs or database, and the timing check passes.

</Level>

#### Phase 3: Cookies

<Layers
  caption="The cookie attributes that make a session cookie safe, each closing one attack."
  layers={[
    { name: 'HttpOnly', note: 'JavaScript cannot read it, so XSS cannot steal it' },
    { name: 'Secure', note: 'sent over HTTPS only' },
    { name: 'SameSite=Lax', note: 'not sent on cross-site POSTs: most CSRF blocked' },
    { name: 'Path and Domain', note: 'where it is sent; narrower is safer' },
    { name: 'Max-Age or Expires', note: 'when it dies; none means a session cookie' },
  ]}
/>

<Levels label="Phase 3, cookies">

<Level name="Beginner">

A cookie is a small value the server asks the browser to store and send back on later requests to the
same site. `Set-Cookie` sets it; the `Cookie` header returns it.

```http
Set-Cookie: sid=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800
```

</Level>

<Level name="Intermediate">

`httpOnly`, `secure` cookies are what the plan's checklist prefers over tokens in `localStorage`. In
DevTools' Application panel, I can see each attribute.

</Level>

<Level name="Advanced">

SameSite: `Strict` never sends on cross-site navigation, `Lax` sends on top-level GET navigations, `None`
always sends (requires `Secure`). Cookies prefixed `__Host-` must be Secure, have Path `/` and no Domain,
which stops subdomains from overwriting them.

</Level>

<Level name="Edge cases">

`Secure` cookies are not set over plain `http://localhost` in some browsers; use the framework's dev
settings rather than turning `Secure` off in production code.

</Level>

<Level name="Corner cases">

Front end on one domain, API on another, plus `SameSite=Lax`: the cookie is not sent on `fetch` calls,
so login "works" and every request is anonymous. Put both on the same site, or use `SameSite=None;
Secure` with CSRF protection.

</Level>

<Level name="Production level">

Browsers limit cookie size to about 4 KB; store an id, not data. Rotate on login, clear on logout.

</Level>

<Level name="Mindset">

Each attribute is a defence; leaving one out should be a decision, not a default.

</Level>

<Level name="System design">

Cookie scope (domain, path, SameSite) shapes where the front end and API can be deployed.

</Level>

<Level name="Strategy">

Done when the session cookie has all five attributes and I can say what each one prevents.

</Level>

</Levels>

#### Phase 3: CORS

<Flow
  caption="A cross-origin fetch with a JSON body: the browser asks permission first."
  steps={['fetch from app.example to api.example', 'Browser sends OPTIONS preflight', 'API answers Allow-Origin, Allow-Methods, Allow-Headers', 'Allowed? browser sends the real request', 'Response must also carry Allow-Origin', 'JS can read it']}

<Levels label="Phase 3, CORS">

<Level name="Beginner">

The browser blocks JavaScript from reading responses from another origin (scheme, host and port) unless
that server says it is allowed. CORS headers are how the server says so. The console error reads like
`has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present`.

</Level>

<Level name="Intermediate">

Allow exactly the front end's origin, not `*`, when cookies are involved.

```ts
await app.register(cors, { origin: ['https://snjy-kumar.github.io'], credentials: true });
```

</Level>

<Level name="Advanced">

Simple requests (GET, form POSTs) are sent without a preflight; others (JSON bodies, custom headers,
PUT, DELETE) trigger an `OPTIONS` preflight, cacheable with `Access-Control-Max-Age`. With credentials,
`Allow-Origin` cannot be `*` and `Allow-Credentials: true` is required.

</Level>

<Level name="Edge cases">

CORS is enforced by browsers only; `curl` ignores it, so CORS is not a security boundary for the API. A
dev server proxy avoids CORS locally but hides problems that appear in production.

</Level>

<Level name="Corner cases">

Reflecting any request `Origin` back with credentials allowed lets any website make authenticated calls
as the user. Use an allowlist.

</Level>

<Level name="Production level">

Serving the front end and API from the same origin (a path like `/api`) removes CORS entirely and is
often the simplest choice.

</Level>

<Level name="Mindset">

Read the browser's error literally: it says which header was missing.

</Level>

<Level name="System design">

Origin layout (same origin, subdomain, separate domain) is an architecture decision affecting cookies,
CORS and CSRF together.

</Level>

<Level name="Strategy">

Done when I can produce, read and fix a CORS error, and the allowlist is exact.

</Level>

</Levels>

#### Phase 3: Error handling

<Layers
  caption="Errors translated layer by layer, so the client gets a useful status and the logs get the cause."
  layers={[
    { name: 'Client response', note: '{ error: "not_found" } with 404; 500 shows only a request id' },

<Levels label="Phase 3, error handling">

<Level name="Beginner">

One central error handler turns thrown errors into responses. Handlers throw; they do not each format
errors.

```ts
class HttpError extends Error { constructor(public status: number, public code: string, message: string) { super(message); } }
app.setErrorHandler((err, req, reply) => {
  if (err instanceof HttpError) return reply.code(err.status).send({ error: err.code, message: err.message });
  req.log.error({ err }, 'unhandled');
  return reply.code(500).send({ error: 'internal', requestId: req.id });
});
```

</Level>

report can be matched to the log.

</Level>

<Level name="Advanced">

handlers log and exit on truly unexpected failures, letting the platform restart a clean process.

</Level>

<Level name="Edge cases">

An error thrown after the response started streaming cannot change the status; log it and close the
connection.

</Level>

<Level name="Corner cases">

An error inside the error handler: the framework falls back to a bare 500, and my log line is lost. Keep
the handler trivial.

</Level>

<Level name="Production level">

Error rates per route feed the alerts of Phase 4; a 500 is always my bug and gets a bug-log entry.

</Level>

<Level name="Mindset">

Expected failures (not found, invalid) are not errors to log loudly; unexpected ones are.

</Level>

<Level name="System design">

Error codes are part of the API contract and documented beside the endpoints.

</Level>

<Level name="Strategy">

Done when every route's failures return the documented code and a 500 never leaks internals.

<Level name="Beginner">

Authorization answers "may this user do this to this record?". Every query on owned data includes the
owner. The plan's trap is checking authentication but not authorization.

```ts
const note = await prisma.note.findFirst({ where: { id: req.params.id, userId: req.user.id } });

```

</Level>

<Level name="Intermediate">

The proof: a second user cannot read the first user's data, proven with a test.

```ts
it('does not let user B read user A note', async () => {
  const a = await signUp('a@test.dev'); const b = await signUp('b@test.dev');
  const note = await a.post('/notes', { title: 'private' });
  const res = await b.get(`/notes/${note.id}`);

  expect(await b.get('/notes').then((r) => r.json())).toEqual([]);
});
```

The same test runs for update, delete and the image URL.

</Level>

<Level name="Advanced">

control. Postgres row-level security can enforce ownership in the database itself as a second layer.

</Level>

<Level name="Edge cases">

List endpoints, search endpoints, counts and exports all need the owner filter, not just the detail
route. A search that returns "3 results" while hiding them still leaks.

</Level>

<Level name="Corner cases">

An update that checks ownership, then writes with only `id` in the `WHERE`, plus a concurrent ownership
change: a race. Put the owner in the write's own `WHERE`.

</Level>

<Level name="Production level">

Roles (admin, member) arrive later; a single `can(user, action, record)` function keeps rules in one
place and testable.

</Level>

<Level name="Mindset">

The plan's AI note: ask the model to attack the API, then write the test that proves the attack fails.

</Level>

<Level name="System design">

Tenant isolation in multi-tenant products is this rule at company scale; it gets its own note in the
backend series.

</Level>

<Level name="Strategy">

Done when every endpoint on owned data has a two-user test, and all pass.

</Level>

can do what, and tests must cover both users.
