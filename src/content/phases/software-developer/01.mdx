<Levels label="Phase 1, values and types">

<Level name="Beginner">

A value is a piece of data; its type says what I can do with it. `typeof` tells me the type at runtime.
Variables are names for values: `const` for names that will not be reassigned, `let` for ones that
will, and never `var` in new code.

```js
const name = 'Sanjay';
let count = 0;
count = count + 1;
console.log(typeof name, typeof count, typeof true, typeof undefined); // string number boolean undefined
```

Mistake: `const list = []; list = [1]` throws `TypeError: Assignment to constant variable.` Fix: `const`
stops reassignment, not change; `list.push(1)` is fine.

</Level>

<Level name="Intermediate">

Primitives are copied by value; objects by reference. Two variables can point at the same object, so
changing it through one changes it for both. Equality: `===` compares type and value with no
conversion; `==` converts first and has surprising rules, so I use `===` always.

```js
const a = { n: 1 }; const b = a; b.n = 2;
console.log(a.n);           // 2
console.log({} === {});     // false: two different objects
console.log('1' == 1, '1' === 1); // true false
```

Truthy and falsy: `false`, `0`, `-0`, `0n`, `''`, `null`, `undefined` and `NaN` are falsy; every
other value, including `'0'`, `[]` and `{}`, is truthy.

</Level>

<Level name="Advanced">

Numbers are IEEE 754 doubles, so decimal fractions are approximate and integers are exact only up to
`Number.MAX_SAFE_INTEGER`. Operators coerce: `+` concatenates when either side is a string, while `-`,
`*` and `/` convert to numbers. `typeof null` is `'object'`, a historical bug kept for compatibility.
Strings are UTF-16, so `length` counts code units, not characters.

```js
0.1 + 0.2;            // 0.30000000000000004
'5' + 1; '5' - 1;     // '51' 4
typeof null;          // 'object'
'👍'.length;          // 2
[...'👍'].length;     // 1
```

Mistake: comparing money with floats. Fix: store cents as integers.

</Level>

<Level name="Edge cases">

`NaN` is the only value not equal to itself: `NaN === NaN` is false; use `Number.isNaN`. `-0 === 0` is
true but `Object.is(-0, 0)` is false. `Number('')` is `0`, `Number(' ')` is `0`, `Number('12px')` is
`NaN`, while `parseInt('12px')` is `12`. `undefined` and `null` are both "nothing" but `null` is chosen
and `undefined` usually is not.

</Level>

<Level name="Corner cases">

A form input plus arithmetic: `input.value` is always a string, so `input.value + 1` gives `'41'` when
the user typed 4. An empty input plus `Number()` gives `0`, which silently passes a "required number"
check. `[] + {}` is `'[object Object]'` because both convert to strings. `null >= 0` is true while
`null == 0` is false.

</Level>

<Level name="Production level">

Most type bugs in real apps happen at the edges: form fields, query strings, JSON from an API, values
from `localStorage`, all of which arrive as strings or of unknown shape. Convert once, at the boundary,
and check the result (`Number.isFinite`). Prices are integers in the smallest unit; IDs are strings.

</Level>

<Level name="Mindset">

Know which values could be there, not which ones I expect. Most "JavaScript is weird" moments are
coercion I did not ask for, and `===` plus explicit conversion removes almost all of them.

</Level>

<Level name="System design">

The question "what type is this value at this point?" is exactly what TypeScript automates in week 8,
and what validation enforces at the API boundary in Phase 3. Learning the runtime types first is what
makes the static ones make sense.

</Level>

<Level name="Strategy">

Predict-then-run drills: twenty expressions, write my prediction, run them, log every miss. Done when I
can predict `typeof`, truthiness, `===` against `==` and the coercion of `+` and `-` for any common
value without running it.

</Level>

</Levels>

#### Phase 1: Functions and scope

<Levels label="Phase 1, functions and scope">

<Level name="Beginner">

A function is a named, reusable piece of work that takes inputs (parameters) and returns an output.
Three ways to write one: a declaration, a function expression and an arrow function.

```js
function add(a, b) { return a + b; }
const sub = function (a, b) { return a - b; };
const mul = (a, b) => a * b;
console.log(add(2, 3), sub(5, 1), mul(2, 4)); // 5 4 8
```

Scope is where a name is visible. `let` and `const` are visible inside the nearest braces. Mistake:
forgetting `return` in a function with braces, which returns `undefined`. Fix: arrows without braces
return automatically; with braces, write `return`.

</Level>

<Level name="Intermediate">

Default parameters, rest parameters and returning objects. Functions are values: I can pass them to
other functions (callbacks) and return them.

```js
const greet = (name = 'friend') => `Hi, ${name}`;
const sum = (...nums) => nums.reduce((t, n) => t + n, 0);
const point = (x, y) => ({ x, y });   // parentheses or the braces become a block
const twice = (f) => (x) => f(f(x));
console.log(greet(), sum(1, 2, 3), point(1, 2), twice((n) => n + 3)(1)); // Hi, friend 6 {x:1,y:2} 7
```

Mistake: `const point = (x, y) => { x, y }` returns `undefined`. Fix: wrap the object in parentheses.

</Level>

<Level name="Advanced">

Scope is lexical: decided by where code is written, not where it is called. Declarations are hoisted
(usable before their line); `let` and `const` exist from the start of their block but throw if touched
before their line, the temporal dead zone. Arguments are passed by value, but an object's value is a
reference, so a function can mutate the caller's object yet cannot replace it.

```js
console.log(hoisted()); function hoisted() { return 'ok'; } // ok
console.log(x); let x = 1; // ReferenceError: Cannot access 'x' before initialization
function rename(user) { user.name = 'B'; user = { name: 'C' }; }
const u = { name: 'A' }; rename(u); console.log(u.name); // B
```

</Level>

<Level name="Edge cases">

Calling with fewer arguments leaves the rest `undefined`; with more, the extras are ignored (but visible
in rest parameters). A default applies for `undefined` but not for `null`: `greet(null)` gives
`Hi, null`. A function with no `return` returns `undefined`. Shadowing: an inner `const items` hides
the outer one inside its block, a quiet source of "my update did nothing" bugs.

</Level>

<Level name="Corner cases">

`['1', '2', '3'].map(parseInt)` returns `[1, NaN, NaN]`, because `map` passes the index as the second
argument and `parseInt` reads it as the radix. Two boundaries meeting: a callback API and a function
with an optional parameter. Fix: `.map((s) => parseInt(s, 10))` or `.map(Number)`.

</Level>

<Level name="Production level">

Small pure functions (same input, same output, no side effects) are easy to test and reuse; side
effects (DOM writes, storage, network) go at the edges. Name functions for what they return or do:
`visibleTodos`, `saveTodos`. Long parameter lists become one options object.

</Level>

<Level name="Mindset">

A function is a promise about inputs and outputs. If I cannot say that promise in a sentence, the
function does too much.

</Level>

<Level name="System design">

The pure-core, effects-at-the-edge split here is the same shape as reducers in Redux, React components
that render from props, and request handlers that call a pure domain function. It is the main
architectural idea of the whole path, met in miniature.

</Level>

<Level name="Strategy">

Exercises 1–4: a temperature converter, a word counter, a function that returns a function, and a
scope puzzle I write myself. Done when I can explain hoisting, the temporal dead zone and lexical scope
with my own example, and every function in the app has a one-sentence promise.

</Level>

</Levels>

#### Phase 1: Closures

<Figure art={`
  makeCounter() runs once            counter() runs many times
  +---------------------------+      +--------------------------+
  | let count = 0   <---------+------+-- reads and writes count |
  | return function counter   |      |   count = count + 1      |
  +---------------------------+      +--------------------------+
  makeCounter has returned, but count stays alive,
  because counter still refers to it.
`} caption="A closure is a function plus the variables it captured. The variables outlive the call that made them." />

<Levels label="Phase 1, closures">

<Level name="Beginner">

A closure is a function that remembers the variables from where it was created, even after that outer
function has returned.

```js
function makeCounter() {
  let count = 0;
  return () => { count += 1; return count; };
}
const next = makeCounter();
console.log(next(), next(), next()); // 1 2 3
```

`count` is private: nothing outside can read or reset it. Mistake: thinking `count` resets on each
call. Fix: it resets only when `makeCounter` runs again, which makes a new, separate `count`.

</Level>

<Level name="Intermediate">

Every event handler and callback is a closure. In the todo app, a handler created inside a render
function captures that item's id.

```js
function renderItem(todo) {
  const li = document.createElement('li');
  const del = document.createElement('button');
  del.textContent = 'Delete';
  del.addEventListener('click', () => removeTodo(todo.id)); // captures todo
  li.append(todo.text, del);
  return li;
}
```

Closures also make factories (`makeCounter`), private state, and partially applied functions such as
`const addTax = (rate) => (price) => price * (1 + rate)`.

</Level>

<Level name="Advanced">

A closure captures variables, not values: it keeps a live reference to the binding, so it sees later
changes. `let` in a `for` loop creates a fresh binding per iteration; `var` creates one for the whole
function. That difference is the classic interview question and a real bug.

```js
const fs = [];
for (var i = 0; i < 3; i++) fs.push(() => i);
console.log(fs.map((f) => f())); // [3, 3, 3]
const gs = [];
for (let j = 0; j < 3; j++) gs.push(() => j);
console.log(gs.map((g) => g())); // [0, 1, 2]
```

</Level>

<Level name="Edge cases">

A closure over a large object keeps that whole object in memory as long as the closure lives, for
example a handler on a long-lived element. Removing the element but keeping the handler registered
elsewhere leaks it. A closure created in a loop over 10,000 items creates 10,000 functions; one
delegated listener is lighter.

</Level>

<Level name="Corner cases">

The stale closure: a callback captures a variable, the variable is later reassigned to a new value,
but the callback was registered once and holds the old binding's value, for example a `setInterval`
whose callback reads a settings object that was replaced, not mutated. In React this becomes the
<a href={withBase('/posts/react/06/')}>stale closure in a handler or effect</a>, the bug Gate 2 asks me
to fix.

```js
let settings = { step: 1 };
const read = ((s) => () => s.step)(settings); // captured the object at that moment
settings = { step: 5 };
console.log(read()); // 1
```

</Level>

<Level name="Production level">

Closures are how modules keep private state, how middleware gets configured, and how memoization
caches results. Their cost is memory and stale data: anything long-lived (timers, global listeners,
subscriptions) must be cleaned up, and its captured values must be fresh or read through a reference.

</Level>

<Level name="Mindset">

When a function runs, ask: which variables did it capture, and when? Most "it uses the old value" bugs
answer themselves.

</Level>

<Level name="System design">

React hooks are built on closures over each render's props and state. Understanding closures here is
what makes the dependency arrays and the stale-closure fixes of Phase 2 obvious rather than magical.

</Level>

<Level name="Strategy">

Write a counter, a once-only function, a memoizer and a rate limiter, each with closures. Then explain
the `var` loop out loud. Done when I can explain closures without notes, as the plan's proof requires,
and fix a stale closure on sight.

</Level>

</Levels>

#### Phase 1: `this`

<Figure art={`
  how was the function CALLED?                      this is ...
  -------------------------------------------------------------------------
  obj.method()                 (dot call)          obj
  fn()                         (plain call)        undefined in strict mode / modules
  new Fn()                     (constructor)       the new object
  fn.call(x) / fn.apply(x)     (explicit)          x
  const g = fn.bind(x); g()    (bound)             x, forever
  arrow function               (any call)          this of the surrounding code
  addEventListener(fn)         (DOM callback)      the element (not for arrows)
`} caption="this is decided by how a function is called, not where it is written, except for arrow functions, which have no this of their own." />

<Levels label="Phase 1, this">

<Level name="Beginner">

`this` is a hidden parameter every normal function gets, set by how the function is called. The most common case is a method call: in
`obj.method()`, `this` is `obj`.

```js
const counter = {
  count: 0,
  increment() { this.count++; return this.count; },
};
counter.increment();     // 1, this === counter
```

The proof asks me to explain `this` without notes; the table in the figure is the whole explanation, and the rest is examples of it.

Mistake: pulling a method off its object and calling it plainly:

```js
const inc = counter.increment;
inc();
```

```text
TypeError: Cannot read properties of undefined (reading 'count')
```

The call `inc()` has no dot, so `this` is `undefined` (in modules and strict code). Where the function was written does not matter; how it was
called does.

</Level>

<Level name="Intermediate">

Callbacks are where this bites, because I hand the function to someone else, who calls it plainly:

```js
class Timer {
  seconds = 0;
  start() {
    setInterval(function () { this.seconds++; }, 1000);   // this is not the Timer
  }
}
```

Three fixes, each a row of the table. An arrow function, which uses the `this` of `start`:

```js
start() { setInterval(() => { this.seconds++; }, 1000); }
```

`bind`, which returns a function with `this` fixed: `setInterval(this.tick.bind(this), 1000)`. Or a class field arrow, `tick = () => { this.seconds++; }`,
which is bound per instance. Arrows are the usual answer.

</Level>

<Level name="Advanced">

Arrows have no `this` of their own, so they are wrong where a dynamic `this` is wanted: as object methods and as DOM listeners that use the element.

```js
const obj = { name: 'A', hi: () => this?.name };
obj.hi();                         // undefined: the arrow took this from the module, not obj

button.addEventListener('click', function () { this.classList.toggle('on'); });   // this = button
button.addEventListener('click', (e) => { e.currentTarget.classList.toggle('on'); }); // arrow: use the event
```

`call` and `apply` set `this` for one call: `fn.call(obj, a, b)`, `fn.apply(obj, [a, b])`. `new` creates an object, sets `this` to it, runs the function and
returns it, which is all a constructor is.

</Level>

<Level name="Edge cases">

Outside strict mode and modules, a plain call sets `this` to the global object (`window`), so the inc example silently creates `window.count` as `NaN`
instead of throwing. Modules are always strict, one more reason to use them. `bind` twice does nothing the second time: the first binding wins.

</Level>

<Level name="Corner cases">

Destructuring a method loses its `this`: `const { increment } = counter; increment()` fails just like `inc`. Passing `obj.method` as a React prop or a
`.then` callback is the same mistake in disguise.

</Level>

<Level name="Production level">

Modern code avoids most `this` problems by using modules of functions instead of classes for logic, and arrows for callbacks. Where classes are used, methods
passed as callbacks are class field arrows or bound in the constructor.

</Level>

<Level name="Mindset">

Do not ask "where is this function?" Ask "how is it being called right now?"

</Level>

<Level name="System design">

Code that depends on implicit context (`this`, globals) is harder to move and test than code that receives everything as parameters. Prefer explicit inputs.

</Level>

<Level name="Strategy">

I write the figure's seven rows as seven runnable examples, predict each output, run them, and fix the Timer three ways.

Done when I can explain `this` for any call site from the table without notes, as the proof requires, and predict all seven examples correctly.

</Level>

</Levels>

<Levels label="Phase 1, arrays and objects">

<Level name="Beginner">

An array is an ordered list; an object is a set of named properties. The plan names a trap here:
avoiding array methods because `map` feels clever. They are the everyday tools.

```js
const todos = [
  { id: 1, text: 'Write README', done: true },
  { id: 2, text: 'Deploy', done: false },
];
const texts = todos.map((t) => t.text);          // ['Write README', 'Deploy']
const open = todos.filter((t) => !t.done);       // [{ id: 2, ... }]
const found = todos.find((t) => t.id === 2);     // { id: 2, ... }
const count = todos.reduce((n, t) => n + (t.done ? 1 : 0), 0); // 1
```

Mistake: a `for` loop with an index to build a new array, off by one. Fix: `map` and `filter`.

</Level>

<Level name="Intermediate">

Immutable updates: produce a new array or object instead of editing in place, so other code holding the
old one is not surprised, and so React can later detect the change.

```js
const toggled = todos.map((t) => (t.id === 2 ? { ...t, done: !t.done } : t));
const added = [...todos, { id: 3, text: 'Test', done: false }];
const removed = todos.filter((t) => t.id !== 1);
```

Objects: `Object.keys`, `Object.values`, `Object.entries`, and `Object.fromEntries` to rebuild. `some`
and `every` answer yes-or-no questions. `includes` checks membership.

</Level>

<Level name="Advanced">

Spread copies one level only (a shallow copy); nested objects are still shared. `structuredClone` makes
a deep copy of plain data. `sort` sorts as strings by default and mutates. Arrays are objects with
numeric keys and a `length`; holes exist. `Map` and `Set` are better than objects for dynamic keys and
uniqueness.

```js
[10, 9, 1].sort();                 // [1, 10, 9]
[10, 9, 1].toSorted((a, b) => a - b); // [1, 9, 10]
const a = { tags: ['x'] }; const b = { ...a }; b.tags.push('y'); console.log(a.tags); // ['x', 'y']
[...new Set([1, 1, 2])];           // [1, 2]
```

</Level>

<Level name="Edge cases">

`reduce` on an empty array with no initial value throws `TypeError: Reduce of empty array with no
initial value`. `find` returns `undefined` when nothing matches; `findIndex` returns `-1`. `[].every(f)`
is `true`. `indexOf(NaN)` is `-1` while `includes(NaN)` is `true`. An object key `'__proto__'` from user
input can change the prototype; use `Map` or `Object.create(null)` for user-keyed data.

</Level>

<Level name="Corner cases">

Sorting objects with a comparator that returns a boolean (`(a, b) => a.date > b.date`) appears to work
on small inputs and fails on others, because `sort` needs negative, zero or positive. Mutating an array
while iterating it with `forEach` (removing items) skips elements. Shallow copy plus nested update:
`{ ...state, user: state.user }` followed by `user.name = 'x'` mutates the original.

</Level>

<Level name="Production level">

Data work in apps is mostly map, filter, find, group and sort over API results. Choose the right
structure: an array for order, a `Map` keyed by id for lookups. Normalize nested API data into an object
by id when many parts of the UI read the same records.

</Level>

<Level name="Mindset">

Decide whether I am transforming or mutating, and say so. Treating data as values that produce new
values is the habit that makes React and Redux easy later.

</Level>

<Level name="System design">

The shape of in-memory data mirrors the database schema of Phase 3: lists of records with ids, grouped
and joined. `groupBy` in code is `GROUP BY` in SQL.

</Level>

<Level name="Strategy">

Exercises 5–7: group a list by a field, compute totals, deduplicate and sort without mutating. Done when
I can write add, toggle, delete and filter for the app as one-line immutable updates and explain
shallow copies.

</Level>

</Levels>

#### Phase 1: Destructuring

<Figure art={`
  const { id, text: title, tags = [], ...rest } = todo;

  todo = { id: 'a1', text: 'Buy milk', done: false, due: '2026-10-30' }
           |          |                |              |

  const [first, , third = 'none', ...others] = ['a', 'b'];
           'a'   skip   'none' (missing)      []
`} caption="Destructuring unpacks by name for objects and by position for arrays, with renames, defaults and a rest collector." />

<Levels label="Phase 1, destructuring">

<Level name="Beginner">

Destructuring pulls values out of objects and arrays into variables in one line.

```js
const todo = { id: 'a1', text: 'Buy milk', done: false };
const { id, text } = todo;               // by name
console.log(id, text);                   // a1 Buy milk

const [first, second] = ['a', 'b', 'c']; // by position
console.log(first, second);              // a b
```

It shines in function parameters, where it documents what a function uses:

```js
function label({ text, done }) { return done ? `✓ ${text}` : text; }
label(todo);    // 'Buy milk'
```

Mistake: destructuring something that might be `undefined`: `const { text } = undefined` throws
`Cannot destructure property 'text' of 'undefined' as it is undefined.` Give a default: `function f({ text } = {})`.

</Level>

<Level name="Intermediate">

Renames, defaults and rest:

```js
const { text: title, priority = 'normal', ...rest } = { text: 'Ship', done: true };
// title = 'Ship', priority = 'normal', rest = { done: true }
```

Swapping without a temporary: `[a, b] = [b, a]`. Entries in loops:

```js
for (const [key, value] of Object.entries({ all: 3, done: 1 })) console.log(key, value);
// all 3
// done 1
```

Rest in objects is the clean way to remove a field without mutating: `const { password, ...safeUser } = user;`.

</Level>

<Level name="Advanced">

Nested destructuring follows the shape:

```js
const { author: { name }, tags: [firstTag] } = { author: { name: 'Ana' }, tags: ['js', 'ts'] };
// name = 'Ana', firstTag = 'js'   (author and tags themselves are not variables)
```

Options objects with defaults are a common API pattern:

```js
function fetchTodos({ limit = 20, sort = 'created', signal } = {}) { /* ... */ }
fetchTodos({ sort: 'due' });
```

Named options are readable at the call site, can be added without breaking callers, and replace long positional argument lists.

</Level>

<Level name="Edge cases">

Defaults apply only for `undefined`, not `null`: `const { a = 1 } = { a: null }` gives `null`. Destructuring a missing nested object throws: `const { author: { name } } = {}`
fails because `author` is undefined; add a default, `{ author: { name } = {} }`.

</Level>

<Level name="Corner cases">

Destructuring assignment to existing variables needs parentheses around an object pattern, or the braces are read as a block:
`({ a, b } = obj);`. A line starting with `[` or `(` after a line with no semicolon can join the previous line; that is one place semicolons matter.

</Level>

<Level name="Production level">

Parameter destructuring with defaults for options, rest to omit sensitive fields before logging or returning, and shallow patterns only; deep patterns are hard
to read and fragile when data is missing.

</Level>

<Level name="Mindset">

Destructuring states what I need from a value. If the pattern is long, the function probably needs less.

</Level>

<Level name="System design">

Options objects with defaults are how stable APIs evolve: new options arrive without breaking anyone. The same idea appears in config files and HTTP query parameters.

</Level>

<Level name="Strategy">

I refactor the vanilla app's functions to destructure their parameters, use rest to strip fields, and convert one three-argument function to an options object.

Done when no function takes more than two positional arguments, defaults handle missing options, and I can predict the edge-case outputs above.

</Level>

</Levels>

#### Phase 1: Modules

  index.html
    <script type="module" src="./main.js">

                 |  import { render } from './view.js'

<Levels label="Phase 1, modules">

<Level name="Beginner">

A module is a file with its own scope. Nothing in it is visible outside unless it is exported, and nothing from outside is visible
inside unless it is imported. That fixes the oldest JavaScript problem: every script sharing one global scope, where two files that
both declare `count` overwrite each other.

```js
// util.js
export function escapeHtml(s) {
  return s.replace(/[&<>"']/g, c => ({ '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' })[c]);
}

// main.js
import { escapeHtml } from './util.js';
console.log(escapeHtml('<b>hi</b>'));     // &lt;b&gt;hi&lt;/b&gt;
```

In the browser, the entry script needs `type="module"`: `<script type="module" src="./main.js"></script>`. Module scripts are deferred
automatically (they run after the HTML is parsed) and always run in strict mode.

Mistake: opening `index.html` by double-clicking. The page loads from `file://`, and the browser blocks module imports:

```text
Access to script at 'file:///.../main.js' from origin 'null' has been blocked by CORS policy
```

Serve the folder instead: `python3 -m http.server 8000` or `npx serve`.

</Level>

<Level name="Intermediate">

Named exports versus a default export:

```js
// store.js
export const todos = [];
export function addTodo(text) { todos.push({ id: crypto.randomUUID(), text, done: false }); }
export default function createStore() { /* ... */ }

// main.js
import createStore, { addTodo, todos as allTodos } from './store.js';
import * as store from './store.js';     // namespace object: store.addTodo, store.todos
```

Named exports are easier to search for and rename, and editors auto-import them reliably; I prefer them. Browser import paths must be
full: `./util.js` with the extension. A bare name like `import { x } from 'lodash'` only works with a bundler or an import map.

</Level>

<Level name="Advanced">

Imports are live bindings, not copies. If `store.js` reassigns an exported `let`, importers see the new value; but importers cannot assign
to it:

```js
// counter.js
export let count = 0;
export function inc() { count++; }
// main.js
import { count, inc } from './counter.js';
inc();
console.log(count);     // 1, the live value
count = 5;              // TypeError: Assignment to constant variable.
```

Each module is evaluated once, the first time anything imports it; later imports get the same instance. That makes a module a natural
singleton (one store shared by every file), and it is why a module's top-level code should not do surprising work like network calls.

Dynamic `import()` loads a module on demand and returns a promise, the basis of code splitting:

```js
button.addEventListener('click', async () => {
  const { openEditor } = await import('./editor.js');
  openEditor();
});
```

</Level>

<Level name="Edge cases">

Circular imports (a imports b, b imports a) work, but one of them sees the other's exports before they are initialised:

```text
ReferenceError: Cannot access 'helper' before initialization
```

Move the shared piece into a third module both import. Top-level `this` in a module is `undefined`, not `window`.

</Level>

<Level name="Corner cases">

Node supports both ES modules and the older CommonJS (`require`, `module.exports`). A `.js` file is treated as ESM only if `package.json`
has `"type": "module"`, or the file is `.mjs`. Mixing them produces errors like `require is not defined in ES module scope` or
`Cannot use import statement outside a module`. Pick ESM for new code and set `"type": "module"`.

</Level>

<Level name="Production level">

Bundlers (Vite, esbuild) follow the import graph, drop unused exports (tree shaking) and split chunks at dynamic imports. That only works
when modules have no side effects at the top level and use named exports; both are habits worth having from the start.

</Level>

<Level name="Mindset">

A module's exports are its public API. Export as little as possible; everything else can change freely.

</Level>

<Level name="System design">

The import graph is the app's dependency structure. Arrows should point one way, from features toward shared utilities, never from
`util.js` back to a feature. A cycle in the graph is a design smell before it is a runtime error.

</Level>

<Level name="Strategy">

I split the vanilla app into `store.js`, `view.js`, `util.js` and `main.js`, serve it locally, draw its import graph, and make one feature
load with dynamic `import()`.

Done when no file uses a global, the graph has no cycles, the app runs from a local server, and I can explain live bindings with the counter
example.

</Level>

</Levels>

#### Phase 1: Promises and `async`/`await`

<Timeline
  caption="A promise's life. It settles once, and every then or await registered on it runs after settling."
  items={[
    { when: 'created', what: 'pending: the work (a timer, a request) has started' },
    { when: 'resolve(value)', what: 'fulfilled with value: then callbacks and awaiters resume with it' },
    { when: 'reject(error)', what: 'rejected with error: catch callbacks run; await throws it' },
    { when: 'afterwards', what: 'settled forever: later resolve or reject calls are ignored' },
  ]}
/>

<Levels label="Phase 1, promises and async/await">

<Level name="Beginner">

A promise is an object standing for a value that will exist later: the result of a request, a timer, a file read. `await` pauses an `async` function until
the promise settles and gives back its value, so asynchronous code reads top to bottom:

```js
const sleep = (ms) => new Promise(resolve => setTimeout(resolve, ms));

async function main() {
  console.log('start');
  await sleep(500);
  console.log('half a second later');
}
main();
console.log('main has returned a promise; this runs first');
```

```text
start
main has returned a promise; this runs first
half a second later
```

An `async` function always returns a promise. It runs synchronously until the first `await`, then gives control back to the caller.

Mistake: forgetting `await`. `const data = getJson(url)` gives a pending `Promise`, and `data.items` is `undefined`.

</Level>

<Level name="Intermediate">

Errors: a rejected promise makes `await` throw, so `try`/`catch` works:

```js
async function load() {
  try {
    const todos = await getJson('/api/todos');
    render(todos);
  } catch (err) {
    showError(err instanceof Error ? err.message : 'Unknown error');
  }
}
```

A rejection nobody handles shows up as `Uncaught (in promise) Error: ...` in the console, and in Node it crashes the process by default.

Sequential versus parallel: two independent awaits in a row take the sum of their times; started together they take the longer of the two:

```js
const a = await getJson('/a');     // 300 ms
const b = await getJson('/b');     // + 300 ms = 600 ms

const [c, d] = await Promise.all([getJson('/a'), getJson('/b')]);   // about 300 ms
```

</Level>

<Level name="Advanced">

The combinators: `Promise.all` (all succeed, or reject with the first error), `Promise.allSettled` (wait for all, report each outcome), `Promise.race` (first to
settle wins, used for timeouts), `Promise.any` (first success). A timeout with race:

```js
function withTimeout(promise, ms) {
  return Promise.race([promise, new Promise((_, reject) => setTimeout(() => reject(new Error(`Timed out after ${ms} ms`)), ms))]);
}
```

The race only stops waiting; the original work continues. Real cancellation needs an `AbortSignal` passed into the work.

`await` in a `for` loop runs iterations one after another, which is right when order or rate matters and slow otherwise; `items.forEach(async ...)` does not
wait at all, which is almost always a bug.

</Level>

<Level name="Edge cases">

`return await` inside `try` matters: `return promise` from inside a `try` block skips the `catch` if the promise rejects, because the rejection happens after the
function returned. `await` on a non-promise value just wraps it.

</Level>

<Level name="Corner cases">

`Promise.all` with one rejection does not cancel the others; they keep running and their results are ignored. An `async` event handler's rejection is unhandled
unless caught inside it, because the event system ignores the returned promise.

</Level>

<Level name="Production level">

Every promise chain ends in handling (a `catch`, a `try`, or a framework that reports it), independent work runs in parallel, loops over remote calls use a
concurrency limit, and a global `unhandledrejection` listener reports misses to error tracking.

</Level>

<Level name="Mindset">

`await` is a pause point where the rest of the program may run. Any state I read before it may have changed after it.

</Level>

<Level name="System design">

Concurrency is a design decision: what can run in parallel, what must be ordered, what limit protects the server. Promises make those decisions explicit in code.

</Level>

<Level name="Strategy">

I write `sleep`, `withTimeout`, a parallel loader and a sequential loader, time each with `performance.now()`, and convert one `forEach(async)` bug into a working
`for...of`.

Done when every async function in the app handles its errors, independent requests run in parallel, and I can predict the order and timing of logs in mixed
async code.

</Level>

</Levels>

#### Phase 1: The event loop

<Figure art={`
   CALL STACK            WEB APIs (browser)          QUEUES
  +-----------+        +------------------+        microtasks: [ then-callback ]
  | main()    | -----> | setTimeout 0ms   | ---->  tasks:      [ timeout-callback ]
  +-----------+        | fetch            |
                       | click listener   |
                       +------------------+
   loop, forever:
   1. run the current task until the stack is empty
   2. run ALL microtasks (promise callbacks, queueMicrotask), including new ones
   3. maybe render (style, layout, paint) about once per frame
   4. take the next task (timer, event, message) and go to 1
`} caption="One thread, one stack. Timers, network and events wait in queues; promise callbacks jump the line as microtasks after each task." />

<Levels label="Phase 1, the event loop">

<Level name="Beginner">

JavaScript in a page runs on one thread. It does one thing at a time, and while it is running, nothing else in the page runs: no clicks
are handled, no rendering happens. Slow work like timers and network requests is handed to the browser, which calls back later through a
queue. The event loop is the rule for when those callbacks run: only when the call stack is empty.

The classic first trace:

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
console.log('C');
```

```text
A
C
B
```

`setTimeout(..., 0)` does not mean "now"; it means "queue this as a task after at least 0 ms". `C` runs first because the current script
must finish before any queued task.

Mistake: a long loop in a click handler. While it runs, the page freezes; the browser cannot paint or respond. The proof asks me to explain
this without notes.

</Level>

<Level name="Intermediate">

Promises add a second queue. Promise callbacks (`then`, `catch`, code after `await`) are microtasks, and all microtasks run after the current
task, before the next task and before rendering:

```js
console.log('1 script');
setTimeout(() => console.log('5 timeout'), 0);
Promise.resolve().then(() => console.log('3 microtask'));
queueMicrotask(() => console.log('4 microtask'));
console.log('2 script');
```

```text
1 script
2 script
3 microtask
4 microtask
5 timeout
```

Step by step: the script is one task; it logs 1, schedules a timer task, queues two microtasks, logs 2. The stack empties, so all microtasks
run (3, 4). Only then does the loop take the timer task (5).

`await` splits a function: everything after it is a microtask that runs when the awaited promise settles.

```js
async function f() { console.log('b'); await null; console.log('d'); }
console.log('a'); f(); console.log('c');
// a b c d
```

</Level>

<Level name="Advanced">

Rendering happens between tasks, roughly once per display frame (about every 16 ms at 60 Hz), and only after microtasks are drained. So a DOM
change followed by a long computation in the same task is not visible until the computation ends:

```js
status.textContent = 'Working…';
heavyComputation();                   // 2 seconds
status.textContent = 'Done';          // the user never sees "Working…"
```

Fixes: yield to the loop so a frame can paint (`await new Promise(r => setTimeout(r, 0))` before the heavy work, or
`await scheduler.yield()` where supported), split work into chunks, or move it to a Web Worker, which has its own thread and event loop.
`requestAnimationFrame` schedules a callback just before the next paint, the right place for visual updates.

</Level>

<Level name="Edge cases">

Nested timers are clamped to at least about 4 ms after a few levels, and background tabs throttle timers to once a second or less, so
`setTimeout` is never a precise clock. Measure elapsed time with `performance.now()` instead of counting ticks.

</Level>

<Level name="Corner cases">

Because the loop drains all microtasks before moving on, a microtask that queues another microtask forever starves the page: no timers, no
events, no rendering, the tab hangs exactly like an infinite loop. A recursive `setTimeout` does not, because each round is a separate task with
rendering possible in between.

</Level>

<Level name="Production level">

Long tasks (over 50 ms) are what make pages feel sluggish, and the Interaction to Next Paint metric measures exactly that. The Performance panel
in DevTools shows long tasks as red-cornered blocks; finding and splitting them is Phase 4 work.

</Level>

<Level name="Mindset">

Asynchronous does not mean parallel. My code still runs one piece at a time; the loop only decides the order.

</Level>

<Level name="System design">

Node uses the same model on the server: one thread for JavaScript, a pool for I/O. That is why a CPU-heavy request in Phase 3 blocks every other
user's request, and why heavy work goes to workers or queues.

</Level>

<Level name="Strategy">

I predict the output of ten ordering puzzles (timers, promises, `await`, nested combinations) on paper, then run them, and record a long task in the
Performance panel and fix it by chunking.

Done when I can draw the figure and explain the 1-to-5 trace without notes, as the proof requires, and get the puzzles right before running them.

</Level>

</Levels>

#### Phase 1: The DOM and events

<Flow
  caption="A click on a delete button inside a list, traced through capture, target and bubble"
  steps={['Capture: window to document to ul', 'Target: the button', 'Bubble: button to li to ul', 'Listener on ul runs (delegation)', 'event.target.closest("[data-id]") finds the row', 'State updated, list re-rendered']}
/>

<Levels label="Phase 1, the DOM and events">

<Level name="Beginner">

The DOM (Document Object Model) is the page as a tree of objects that JavaScript can read and change. The browser builds it from the HTML;
changing it changes the screen.

```js
const list = document.querySelector('#todos');          // first match, or null
const items = document.querySelectorAll('#todos li');   // a static NodeList

const li = document.createElement('li');
li.textContent = 'Buy milk';
list.append(li);
```

Events are how the page tells my code something happened:

```js
const form = document.querySelector('#add-form');
form.addEventListener('submit', (event) => {
  event.preventDefault();                  // stop the full-page form submission
  const text = form.elements.text.value.trim();
  if (text) addTodo(text);
});
```

Mistake: building HTML with user text through `innerHTML`: `li.innerHTML = text`. A todo named `<img src=x onerror=alert(1)>` runs script.
Use `textContent` for text, and create elements for structure. The plan's trap here is reaching for React before I can do this by hand.

</Level>

<Level name="Intermediate">

Events travel: from the window down to the target (capture), then back up (bubble). Most listeners run in the bubble phase, so a single listener
on a parent can handle events from every child, including children added later. That is event delegation:

```js
list.addEventListener('click', (event) => {
  const button = event.target.closest('button[data-action]');
  if (!button) return;
  const id = button.closest('li').dataset.id;
  if (button.dataset.action === 'delete') removeTodo(id);
  if (button.dataset.action === 'toggle') toggleTodo(id);
});
```

```html
<li data-id="a1">Buy milk <button data-action="toggle">Done</button> <button data-action="delete">Delete</button></li>
```

`event.target` is the element actually clicked (maybe an icon inside the button); `event.currentTarget` is the element the listener is on.
`closest` walks up from the target to find what I care about.

</Level>

<Level name="Advanced">

Rendering from state: instead of patching the DOM in many places, keep the data in an array, and write one `render()` that rebuilds the list from
it. Every change updates the array, then calls `render()`. This is the idea React automates, and doing it by hand once makes React obvious later.

```js
function render() {
  const visible = todos.filter(t => matches(t, filter, query));
  list.replaceChildren(...visible.map(t => {
    const li = document.createElement('li');
    li.dataset.id = t.id;
    li.className = t.done ? 'done' : '';
    li.append(t.text, ' ', button('toggle', t.done ? 'Undo' : 'Done'), ' ', button('delete', 'Delete'));
    return li;
  }));
  count.textContent = `${visible.length} of ${todos.length}`;
}
```

Reading layout (`offsetHeight`, `getBoundingClientRect`) right after writing styles forces the browser to compute layout immediately; doing it in
a loop (write, read, write, read) causes layout thrashing. Batch reads, then writes.

</Level>

<Level name="Edge cases">

`querySelector` returns `null` when nothing matches, and the next line fails with `Cannot read properties of null (reading 'addEventListener')`,
usually because the script ran before the element existed (put scripts at the end, use `defer` or `type="module"`) or the selector has a typo.
`querySelectorAll` returns a static list; `getElementsByClassName` returns a live one that changes as the DOM changes, which surprises loops that
remove items.

</Level>

<Level name="Corner cases">

Adding a listener inside `render()` adds another one on every render, so one click deletes three items after three renders. Delegation on a parent
that is never re-rendered avoids it. `event.stopPropagation()` in one component silently breaks delegated listeners and analytics elsewhere; avoid it
unless there is no other way.

</Level>

<Level name="Production level">

Event handlers are cheap and few (delegation), user text is always inserted as text, forms work with Enter and without JavaScript where possible, and
focus is managed after changes (after deleting an item, move focus somewhere sensible).

</Level>

<Level name="Mindset">

The DOM is just a tree of objects. Everything a framework does to it, I can do by hand; frameworks only make it less tedious.

</Level>

<Level name="System design">

State, a render function from state to DOM, and events that update state: this loop is the architecture of every UI framework. Building it by hand is
the best preparation for Phase 2.

</Level>

<Level name="Strategy">

I build the vanilla app with one state array, one `render()`, one delegated click listener, a submit listener and a search input, with no `innerHTML`
for user data.

Done when adding, deleting, filtering and searching all go through state and `render()`, there is exactly one listener per event type, and a todo
containing HTML shows as literal text.

</Level>

</Levels>

#### Phase 1: `fetch`

<Figure art={`
  const res = await fetch(url)          resolves when HEADERS arrive
        |                               rejects ONLY on network failure
        v                               (offline, DNS, CORS, abort)
  res.ok? (status 200-299)
     no  --> throw new Error('HTTP ' + res.status)    404 and 500 do NOT reject
     yes
        |
  const data = await res.json()         reads the BODY; rejects if not valid JSON
        |
  validate the shape, then use it
`} caption="fetch has two awaits and two kinds of failure. Most bugs come from treating a 404 as success or parsing an HTML error page as JSON." />

<Levels label="Phase 1, fetch">

<Level name="Beginner">

`fetch` makes an HTTP request from JavaScript and returns a promise of a `Response`:

```js
const res = await fetch('https://jsonplaceholder.typicode.com/todos/1');
console.log(res.status, res.headers.get('content-type'));
const todo = await res.json();
console.log(todo);
```

```text
200 application/json; charset=utf-8
{ userId: 1, id: 1, title: 'delectus aut autem', completed: false }
```

Two awaits: the first waits for the response headers, the second reads and parses the body.

Mistake: assuming `fetch` rejects on errors. It only rejects when the request could not complete at all. A `404` or `500` resolves normally with
`res.ok === false`, so code that does not check carries on with an error body.

</Level>

<Level name="Intermediate">

A small helper I use everywhere, with the status check, a timeout and a clear error:

```js
export async function getJson(url, { timeout = 8000, ...options } = {}) {
  const res = await fetch(url, { ...options, signal: AbortSignal.timeout(timeout) });
  if (!res.ok) {
    const body = await res.text();
    throw new Error(`GET ${url} failed: ${res.status} ${res.statusText} ${body.slice(0, 200)}`);
  }
  return res.json();
}
```

Sending JSON needs a method, a header and a string body:

```js
await fetch('/api/todos', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ text: 'Buy milk' }),
});
```

Forgetting `JSON.stringify` sends the string `[object Object]`; forgetting the header makes many servers ignore the body.

</Level>

<Level name="Advanced">

Cancellation: an `AbortController` cancels a request, which matters for search-as-you-type, where an old slow response must not overwrite a newer one:

```js
let controller;
input.addEventListener('input', async () => {
  controller?.abort();
  controller = new AbortController();
  try {
    const results = await getJson(`/api/search?q=${encodeURIComponent(input.value)}`, { signal: controller.signal });
    renderResults(results);
  } catch (err) {
    if (err.name !== 'AbortError') showError(err);
  }
});
```

Parallel requests with `Promise.all` (fail fast if any fails) or `Promise.allSettled` (collect each result or error):

```js
const [user, todos] = await Promise.all([getJson('/api/me'), getJson('/api/todos')]);
```

</Level>

<Level name="Edge cases">

`res.json()` on an HTML error page throws `Unexpected token '<'`; check `res.ok` and the content type first. `res.json()` on a `204 No Content`
throws on the empty body. The body can be read only once; a second `res.json()` throws `body used already`; use `res.clone()` if two readers need it.
Query strings need `encodeURIComponent` or `URLSearchParams`, or a search for `a&b` breaks the URL.

</Level>

<Level name="Corner cases">

Cross-origin requests the server does not allow fail with a CORS error, which `fetch` reports as a generic `TypeError: Failed to fetch` with no status,
indistinguishable in code from being offline; the console shows the real reason. Cookies are only sent cross-origin with `credentials: 'include'` and a
server that allows it.

</Level>

<Level name="Production level">

Every request has a timeout, every response is checked and validated (TypeScript cannot see what a server sends at runtime; see `unknown` below),
retries happen only for safe requests with backoff, and the UI shows loading, error and empty states.

</Level>

<Level name="Mindset">

The network is unreliable and the server is someone else's code. Every `fetch` should answer: what if it is slow, fails, or returns something unexpected?

</Level>

<Level name="System design">

A thin, typed API client module (one place for base URL, headers, errors, timeouts) is the seam between the UI and the backend, and the place to add auth,
logging and caching later.

</Level>

<Level name="Strategy">

I add a public API to the vanilla app (fetching a quote or a list of tasks), write `getJson`, then break it: a wrong URL, offline mode in DevTools, a slow
network, a fast typist.

Done when a 404, a network failure, a timeout and an out-of-order response each produce the right UI, and no `fetch` in my code lacks a status check.

</Level>

</Levels>

<Levels label="Phase 1, errors">

<Level name="Beginner">

An error is an object with a `name`, a `message` and a `stack`. `throw` stops the current function and every caller until a `try`/`catch` handles it:

```js
function parsePrice(text) {
  const n = Number(text);
  if (Number.isNaN(n) || n < 0) throw new Error(`Invalid price: "${text}"`);
  return n;
}

try {
  parsePrice('abc');
} catch (err) {
  console.error(err.message);     // Invalid price: "abc"
} finally {
  console.log('runs either way');
}
```

The built-in types tell me what went wrong: `TypeError` (wrong kind of value, often `undefined`), `ReferenceError` (a name that does not exist), `SyntaxError`
(code or JSON that does not parse), `RangeError` (a number out of range).

Mistake: an empty `catch {}`. The error vanishes, the app does nothing, and nobody knows why.

</Level>

<Level name="Intermediate">

Catch only what I can handle, where I can handle it. A storage loader can recover (fall back to an empty list), so it catches. A function in the middle that
cannot do anything useful should let the error pass up. Throw `Error` objects, never strings, so there is a stack:

```js
throw 'not found';             // no stack, no name
throw new Error('Todo not found: a1');
```

Wrapping keeps the original with `cause`:

```js
try { await saveRemote(todos); }
catch (err) { throw new Error('Could not sync todos', { cause: err }); }
```

</Level>

<Level name="Advanced">

Custom error classes let callers handle kinds of failure:

```js
class ValidationError extends Error {
  constructor(field, message) { super(message); this.name = 'ValidationError'; this.field = field; }
}

try { validate(form); }
catch (err) {
  if (err instanceof ValidationError) showFieldError(err.field, err.message);
  else throw err;                          // not mine to handle
}
```

A global safety net reports what nobody caught:

```js
window.addEventListener('error', (e) => report(e.error));
window.addEventListener('unhandledrejection', (e) => report(e.reason));
```

An alternative style returns errors as values (`{ ok: false, error }`), which TypeScript can check; the typed `Result` from the generics topic is that pattern.

</Level>

<Level name="Edge cases">

`finally` runs even after `return` inside `try`, and a `return` inside `finally` overrides the original return or swallows the thrown error. Keep `finally` for cleanup
only. Errors thrown inside a `setTimeout` callback are not caught by a `try` around the `setTimeout` call, because the callback runs later in a different task.

</Level>

<Level name="Corner cases">

Anything can be thrown, including `null` or a number, so `err.message` in a `catch` can itself throw. In TypeScript the `catch` variable is `unknown` under strict mode;
narrow with `instanceof Error` first.

</Level>

<Level name="Production level">

User-facing messages say what happened and what to do; technical detail goes to logs and error tracking with the stack and context. Errors are never shown raw to users.

</Level>

<Level name="Mindset">

For every operation, decide in advance what failure looks like, who handles it, and what the user sees.

</Level>

<Level name="System design">

Error boundaries (where a failure stops spreading) are an architecture decision: a widget, a page, a request, a process. Phase 2 and Phase 3 each draw these lines.

</Level>

<Level name="Strategy">

I list every failure in the vanilla app by the four layers in the figure, add handling at the right layer for each, and add the global handlers.

Done when no `catch` is empty, every handled error shows a useful message, unhandled ones are reported by the global listener, and I can cause each failure on purpose.

</Level>

</Levels>

#### Phase 1: JSON and `localStorage`

<Flow
  caption="Persisting app state: serialise on every change, parse and validate once on load"
  steps={['State changes (add, delete, toggle)', 'JSON.stringify(todos)', 'localStorage.setItem("todos:v1", text)', 'Page reload', 'localStorage.getItem returns text or null', 'JSON.parse in try/catch, validate, fall back to []']}
/>

<Levels label="Phase 1, JSON and localStorage">

<Level name="Beginner">

`localStorage` stores strings by key in the browser, per origin, and keeps them across reloads and restarts. Since it only holds strings, objects go
through JSON:

```js
function save(todos) {
  localStorage.setItem('todos:v1', JSON.stringify(todos));
}
function load() {
  const raw = localStorage.getItem('todos:v1');
  return raw === null ? [] : JSON.parse(raw);
}
```

In DevTools, Application, Local Storage shows the stored value, which I can edit by hand to test odd data.

Mistake: `localStorage.setItem('todos', todos)` without stringify stores `"[object Object],[object Object]"`, and loading it fails.

</Level>

<Level name="Intermediate">

Loading must survive bad data, because stored data outlives code: an old format, a manual edit, a bug from last week.

```js
function load() {
  try {
    const raw = localStorage.getItem('todos:v1');
    if (raw === null) return [];
    const data = JSON.parse(raw);
    if (!Array.isArray(data)) return [];
    return data.filter(t => typeof t?.id === 'string' && typeof t?.text === 'string' && typeof t?.done === 'boolean');
  } catch {
    return [];
  }
}
```

The `:v1` in the key is a version. When the shape changes, `v2` can migrate `v1` data once and delete the old key.

</Level>

<Level name="Advanced">

What JSON loses: `Date` becomes a string, `undefined` properties vanish, `Map` and `Set` become `{}`, class instances lose their methods. Store plain
data (ISO date strings, arrays) and rebuild richer objects after parsing. `JSON.stringify(value, null, 2)` pretty-prints for debugging.

The `storage` event fires in other tabs of the same origin when one tab writes, which keeps two open tabs in sync:

```js
window.addEventListener('storage', (e) => { if (e.key === 'todos:v1') { todos = load(); render(); } });
```

</Level>

<Level name="Edge cases">

Storage is limited (around 5 MB per origin in most browsers); `setItem` throws `QuotaExceededError` when full, so wrap writes too. Private browsing
modes may clear it on close. `localStorage` is synchronous; writing large values on every keystroke can stutter.

</Level>

<Level name="Corner cases">

Anything in `localStorage` is readable by every script on the page, including a successful XSS payload or a compromised third-party script. Never store
tokens or secrets there; that is why Phase 3 uses httpOnly cookies. Two tabs writing at once can overwrite each other's changes (last write wins).

</Level>

<Level name="Production level">

Real apps keep durable data on a server; `localStorage` holds preferences, drafts and caches, always versioned and validated on load.

</Level>

<Level name="Mindset">

Data read back from storage is input, as untrusted as anything a user types.

</Level>

<Level name="System design">

Serialise, version, validate, migrate: the same four steps apply to every persisted format, from a browser key to a database schema to an API payload.

</Level>

<Level name="Strategy">

The vanilla app persists todos with a versioned key and a validating loader. I then corrupt the stored value three ways by hand in DevTools and check that
the app still loads.

Done when the app survives corrupted, missing and old-format data, writes are wrapped for quota errors, and two tabs stay in sync.

</Level>

</Levels>

#### Phase 1: TypeScript annotations

<Flow
  caption="Where TypeScript sits: it checks, then disappears. The browser never sees a type."
  steps={['app.ts with types', 'tsc or the editor checks', 'Errors shown before running', 'Types erased', 'app.js runs in the browser']}
/>

<Levels label="Phase 1, TypeScript annotations">

<Level name="Beginner">

TypeScript is JavaScript plus a type checker. An annotation says what type a variable, parameter or
return value is, and the checker reports code that breaks the promise before it runs.

```ts
function total(prices: number[]): number {
  return prices.reduce((sum, p) => sum + p, 0);
}
total(['3', 4]);
// error TS2322: Type 'string' is not assignable to type 'number'.
```

Mistake: thinking the types run in the browser. Fix: they are erased; validation at runtime is a
separate job (see `unknown` below).

</Level>

<Level name="Intermediate">

Describe object shapes with `type` or `interface`, optional properties with `?`, read-only ones with
`readonly`, and function types.

```ts
type Todo = { readonly id: number; text: string; done: boolean; due?: string };
type Filter = (todo: Todo) => boolean;
const open: Filter = (t) => !t.done;
```

The site's note on <a href={withBase('/posts/typescript/02/')}>interface against type</a> covers when
each fits; for this app either works.

</Level>

<Level name="Advanced">

TypeScript is structural: a value fits a type if it has the right shape, whatever it was called.
Excess property checks apply only to fresh object literals. Literal types (`'all'`) are narrower than
`string`; `as const` keeps literals narrow and readonly.

```ts
const point = { x: 1, y: 2, z: 3 };
const p: { x: number; y: number } = point;       // fine: structural
const q: { x: number; y: number } = { x: 1, y: 2, z: 3 };
// error TS2353: Object literal may only specify known properties, and 'z' does not exist
const filters = ['all', 'open', 'done'] as const; // readonly ['all', 'open', 'done']
```

</Level>

<Level name="Edge cases">

An empty array literal with no annotation is `any[]` evolving, or `never[]` in some positions, so
pushing into it later gives confusing errors; annotate `const items: Todo[] = []`. Optional `due?:
string` is `string | undefined`, and with `exactOptionalPropertyTypes` setting it to `undefined`
explicitly is an error.

</Level>

<Level name="Corner cases">

Structural typing plus two types with the same shape: a `UserId` and an `OrderId` that are both
`string` are interchangeable, so passing the wrong one compiles. A branded type
(`string & { readonly brand: 'UserId' }`) makes them distinct.

</Level>

<Level name="Production level">

Types are documentation that cannot go stale, and the safety net for refactors: rename a field and the
compiler lists every place to update. They do not replace tests, which check behaviour.

</Level>

<Level name="Mindset">

Write types for the boundaries (function signatures, data shapes) and let inference handle the inside.

</Level>

<Level name="System design">

Shared types between client and server (Phase 3) make the API contract checkable in both places.

</Level>

<Level name="Strategy">

Port `format.js` and `store.js` to TypeScript first. Done when `tsc --noEmit` passes and I can say what
each annotation protects against.

</Level>

</Levels>

#### Phase 1: Unions

<Figure art={`
  type Status = 'idle' | 'loading' | 'success' | 'error';

          idle --load--> loading --ok----> success
                            |
                            +--fail--> error --retry--> loading

  type State =
    | { status: 'loading' }
    | { status: 'success'; data: Todo[] }      data exists ONLY here
    | { status: 'error'; message: string }     message exists ONLY here
`} caption="A union lists every value a thing can be. A discriminated union attaches the right data to each state, so impossible combinations cannot be written." />

<Levels label="Phase 1, unions">

<Level name="Beginner">

A union type says a value is one of several types: `string | number`, or one of several exact strings. The site's note on
<a href={withBase('/posts/typescript/03/')}>union types</a> is the deep dive.

```ts
type Filter = 'all' | 'active' | 'done';
let filter: Filter = 'all';
filter = 'archived';
```

```text
error TS2322: Type '"archived"' is not assignable to type 'Filter'.
```

The compiler now knows every valid value, and the editor autocompletes them. Compare with `filter: string`, which accepts any typo.

Mistake: using a union value as if it were one specific member without checking. `function len(x: string | number) { return x.length; }` fails with
`Property 'length' does not exist on type 'number'`; I must narrow first (next topic).

</Level>

<Level name="Intermediate">

A discriminated union is a union of object types that share one literal field, the discriminant, so TypeScript can tell which member it has:

```ts
type State =
  | { status: 'loading' }
  | { status: 'success'; data: Todo[] }
  | { status: 'error'; message: string };

function view(s: State): string {
  switch (s.status) {
    case 'loading': return 'Loading…';
    case 'success': return `${s.data.length} todos`;     // data is available here
    case 'error':   return `Failed: ${s.message}`;       // message is available here
  }
}
```

Compare the loose version, `{ loading: boolean; data?: Todo[]; error?: string }`, which allows `loading: true` with an error and data at once, and
forces `?` checks everywhere.

</Level>

<Level name="Advanced">

Exhaustiveness: in a `switch` over the discriminant, assigning the leftover to `never` makes adding a new member a compile error everywhere it is not
handled. See the <a href={withBase('/posts/typescript/11/')}>discriminated unions</a> note.

```ts
function assertNever(x: never): never { throw new Error(`Unhandled: ${JSON.stringify(x)}`); }

function view(s: State): string {
  switch (s.status) {
    case 'loading': return 'Loading…';
    case 'success': return `${s.data.length} todos`;
    case 'error':   return `Failed: ${s.message}`;
    default:        return assertNever(s);
  }
}
```

Add `| { status: 'empty' }` to `State` and the compiler points at the `default`:

```text
error TS2345: Argument of type '{ status: "empty"; }' is not assignable to parameter of type 'never'.
```

</Level>

<Level name="Edge cases">

A literal assigned to a `const` keeps its literal type, but in an object it widens: `const f = { filter: 'all' }` has `filter: string`, which is not
assignable to `Filter`. Annotate the object, or use `as const` (`{ filter: 'all' } as const`) or `satisfies`.

</Level>

<Level name="Corner cases">

`string | 'all'` collapses to `string`, losing autocomplete; a union with a wide member absorbs the narrow ones. Optional properties already include
`undefined` in the union, which shows up in narrowing as a member to handle.

</Level>

<Level name="Production level">

Status fields, API results, events and actions are modelled as discriminated unions; every `switch` over them has an exhaustiveness check, so adding a
case is a guided change, not a hunt.

</Level>

<Level name="Mindset">

Make invalid states unrepresentable. If the type cannot express it, no code path can produce it.

</Level>

<Level name="System design">

Unions are how a type system models state machines and protocols. The same shapes reappear in reducers (Phase 2) and API responses (Phase 3).

</Level>

<Level name="Strategy">

I convert the vanilla app's filter and request status to unions, add exhaustiveness checks, then add a new member and follow the compiler's errors to
every place that needs it.

Done when no status is a plain string or a set of booleans, and adding a union member produces errors in exactly the places that must change.

</Level>

</Levels>

#### Phase 1: Narrowing

<Flow
  caption="How TypeScript narrows a value inside one function, step by step"
  steps={['x: string | number | null', 'if (x === null) return', 'x: string | number', 'if (typeof x === "number") ...', 'inside: x is number', 'after: x is string']}
/>

<Levels label="Phase 1, narrowing">

<Level name="Beginner">

Narrowing is how TypeScript works out a more specific type from checks I write. After a check, the type inside that branch is smaller. The
<a href={withBase('/posts/typescript/08/')}>narrowing note</a> walks the real bugs.

```ts
function format(x: string | number | null): string {
  if (x === null) return '-';
  // x: string | number
  if (typeof x === 'number') return x.toFixed(2);
  // x: string
  return x.trim();
}
```

Hovering over `x` in the editor at each line shows the narrowed type; doing that is the fastest way to learn it.

Mistake: reaching for `as` to silence an error (`(x as string).trim()`) instead of narrowing. `as` is a promise to the compiler with no check; if it
is wrong, the crash happens at runtime.

</Level>

<Level name="Intermediate">

The checks TypeScript understands: `typeof` for primitives (`'string'`, `'number'`, `'boolean'`, `'object'`, `'function'`, `'undefined'`),
`instanceof` for classes (`err instanceof Error`), `in` for properties (`'data' in result`), equality with literals (`s.status === 'error'`),
`Array.isArray`, and truthiness (`if (user)`).

```ts
function message(err: unknown): string {
  if (err instanceof Error) return err.message;
  if (typeof err === 'string') return err;
  return 'Unknown error';
}
```

Early returns narrow for the rest of the function, which keeps code flat:

```ts
function title(todo: Todo | undefined) {
  if (!todo) return 'Not found';
  return todo.text;            // todo: Todo
}
```

</Level>

<Level name="Advanced">

Custom type guards teach TypeScript a check it cannot infer:

```ts
type Todo = { id: string; text: string; done: boolean };

function isTodo(x: unknown): x is Todo {
  return typeof x === 'object' && x !== null
    && typeof (x as Record<string, unknown>).id === 'string'
    && typeof (x as Record<string, unknown>).text === 'string'
    && typeof (x as Record<string, unknown>).done === 'boolean';
}

const parsed: unknown = JSON.parse(raw);
const todos = Array.isArray(parsed) ? parsed.filter(isTodo) : [];   // Todo[]
```

The `x is Todo` return type is a promise: if the function returns true, `x` is a `Todo`. A wrong guard lies to the compiler, so guards need tests.
Assertion functions (`asserts x is Todo`) throw instead of returning false.

</Level>

<Level name="Edge cases">

`typeof null === 'object'`, so `typeof x === 'object'` does not exclude null; check `x !== null` too. Truthiness narrowing drops `0` and `''`:
`if (count)` treats zero as missing. Use `count !== undefined` when zero is valid.

</Level>

<Level name="Corner cases">

Narrowing does not survive callbacks: after `if (user)`, a `setTimeout(() => user.name)` may still be an error with a `let` variable, because the
callback runs later when `user` may have changed. Copy to a `const` first. Narrowing a property (`obj.x`) is lost after any function call that could
have mutated `obj`.

</Level>

<Level name="Production level">

Code has no unexplained `as` (part of the proof), external data is narrowed through guards or a schema library, and guards have unit tests with
both valid and invalid inputs.

</Level>

<Level name="Mindset">

The compiler is asking a question: how do you know? Answer it with a check, not with `as`.

</Level>

<Level name="System design">

Narrowing at the boundary (where data enters) means the inside of the program can trust its types. That one rule removes most runtime type errors.

</Level>

<Level name="Strategy">

I remove every `as` from the typed module, replacing each with a narrowing check or a guard with tests, and hover through three functions to watch the
types change.

Done when the code has no `as` without a comment explaining why it is safe, and each guard has tests for at least one valid and three invalid inputs.

</Level>

</Levels>

#### Phase 1: Generics

<Figure art={`
  function first<T>(items: T[]): T | undefined

  first([1, 2, 3])            T = number   ->  returns number | undefined
  first(['a', 'b'])           T = string   ->  returns string | undefined
  first(todos)                T = Todo     ->  returns Todo | undefined

  T is a type parameter: a blank the caller's argument fills in,
  linking the input type to the output type
`} caption="A generic is a function over types. The type parameter carries information from what goes in to what comes out." />

<Levels label="Phase 1, generics">

<Level name="Beginner">

A generic function works for many types while keeping track of which one it was given. The
<a href={withBase('/posts/typescript/09/')}>generics note</a> sticks to the ones I actually use.

```ts
function first<T>(items: T[]): T | undefined {
  return items[0];
}
const n = first([10, 20]);        // n: number | undefined
const t = first(todos);           // t: Todo | undefined
```

Without generics I would choose between `first(items: any[]): any`, which loses the type, and one function per type. `Array<T>`, `Promise<T>`
and `Map<K, V>` are generics I already use.

Mistake: writing `<T>` and then not using it to connect anything, like `function log<T>(x: T): void`. A type parameter that appears once is just a
complicated `unknown`.

</Level>

<Level name="Intermediate">

Constraints limit what `T` can be, so the function can use its properties:

```ts
function byId<T extends { id: string }>(items: T[], id: string): T | undefined {
  return items.find(item => item.id === id);
}
byId(todos, 'a1');              // Todo | undefined
byId([1, 2], 'x');
```

```text
error TS2322: Type 'number' is not assignable to type '{ id: string; }'.
```

`keyof` and indexed access link keys and values:

```ts
function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map(item => item[key]);
}
pluck(todos, 'text');           // string[]
pluck(todos, 'done');           // boolean[]
pluck(todos, 'colour');         // error: not a key of Todo
```

</Level>

<Level name="Advanced">

Generic types describe shapes with a blank:

```ts
type Result<T, E = string> = { ok: true; value: T } | { ok: false; error: E };

async function getJson<T>(url: string, isT: (x: unknown) => x is T): Promise<Result<T>> {
  const res = await fetch(url);
  if (!res.ok) return { ok: false, error: `HTTP ${res.status}` };
  const data: unknown = await res.json();
  return isT(data) ? { ok: true, value: data } : { ok: false, error: 'unexpected shape' };
}
```

The guard parameter is what makes `T` honest: the caller supplies proof that the data is a `T`, instead of the function claiming it with `as T`.

</Level>

<Level name="Edge cases">

Inference picks the best common type: `first([1, 'a'])` gives `string | number`. Passing an empty array gives `never[]` or `unknown`; specify the
type explicitly, `first<Todo>([])`. A generic that only appears in the return type (`function parse<T>(s: string): T`) is a disguised cast; avoid it.

</Level>

<Level name="Corner cases">

In `.tsx` files, an arrow function `<T>(x: T) => x` is read as a JSX tag; write `<T,>(x: T) => x` or use a `function`. Conditional types and
`infer` are powerful but rarely needed in app code; reach for them only after the simple version fails.

</Level>

<Level name="Production level">

Generics live mostly in shared utilities and API clients; application code uses them more than it defines them. Each generic has a test that checks
inferred types (with `expectTypeOf` in Vitest).

</Level>

<Level name="Mindset">

Use a generic when a type must flow from input to output. If nothing flows, I do not need one.

</Level>

<Level name="System design">

Generic building blocks (a typed fetch, a typed store, a `Result` type) let the rest of the codebase stay specific and simple.

</Level>

<Level name="Strategy">

I write `first`, `byId`, `pluck`, `groupBy` and a typed `getJson` in the utility module, with type tests for each.

Done when each generic's parameter links input to output, the type tests pass, and none of them uses `as` or `any` internally without a comment.

</Level>

</Levels>

#### Phase 1: Utility types

<Levels label="Phase 1, utility types">

<Level name="Beginner">

Utility types are built-in generics that transform one type into another. The point is a single source of truth: define `Todo` once and derive the
rest. The <a href={withBase('/posts/typescript/10/')}>Partial, Pick and Omit note</a> covers the three I use most.

```ts
type Todo = { id: string; text: string; done: boolean; createdAt: string };

type NewTodo = Omit<Todo, 'id' | 'createdAt'>;       // { text: string; done: boolean }
type TodoPatch = Partial<Pick<Todo, 'text' | 'done'>>; // { text?: string; done?: boolean }

function updateTodo(id: string, patch: TodoPatch) { /* ... */ }
updateTodo('a1', { done: true });                    // ok
updateTodo('a1', { id: 'b2' });                      // error: 'id' does not exist in type TodoPatch
```

Mistake: copying the fields into a second hand-written type. When `Todo` gains a field, the copy silently goes stale.

</Level>

<Level name="Intermediate">

`Record<K, V>` builds an object type with keys `K`; with a union of keys, the compiler requires every one:

```ts
type Filter = 'all' | 'active' | 'done';
const labels: Record<Filter, string> = { all: 'All', active: 'Active', done: 'Done' };
const missing: Record<Filter, string> = { all: 'All', active: 'Active' };
```

```text
error TS2741: Property 'done' is missing in type '{ all: string; active: string; }' but required in type 'Record<Filter, string>'.
```

`ReturnType` and `Parameters` read types from functions, and `Awaited` unwraps promises: `type Loaded = Awaited<ReturnType<typeof loadTodos>>`.

</Level>

<Level name="Advanced">

Utility types are mapped types underneath. `Partial<T>` is `{ [K in keyof T]?: T[K] }`. Writing my own is occasionally useful; the
<a href={withBase('/posts/typescript/13/')}>mapped types note</a> goes further.

```ts
type Nullable<T> = { [K in keyof T]: T[K] | null };
type FormErrors<T> = Partial<Record<keyof T, string>>;
const errors: FormErrors<NewTodo> = { text: 'Required' };
```

`satisfies` checks a value against a type without widening it, so literal types survive:

```ts
const routes = { home: '/', todos: '/todos' } satisfies Record<string, string>;
routes.home;      // type '/' kept, and typos in keys still error
```

</Level>

<Level name="Edge cases">

`Readonly` is shallow: `Readonly<{ tags: string[] }>` stops reassigning `tags` but not `tags.push`. Use `readonly string[]` or `ReadonlyArray` for the
inner array. `Omit` does not check that the omitted key exists, so a typo omits nothing.

</Level>

<Level name="Corner cases">

`Partial` on an update means `{}` is a valid patch, and `{ text: undefined }` is too, which might erase a field. Handle explicit `undefined` in the update
function, or enable `exactOptionalPropertyTypes` to distinguish missing from undefined.

</Level>

<Level name="Production level">

<Levels label="Phase 1, unknown">

<Level name="Beginner">

`unknown` is the type for "I do not know what this is yet". Any value can be assigned to it, but I cannot use it until I narrow it. The
<a href={withBase('/posts/typescript/07/')}>any trap</a> note is about the opposite type, `any`, which turns checking off.

```ts
const data: unknown = JSON.parse(raw);
data.length;
```

```text
error TS18046: 'data' is of type 'unknown'.
```

```ts
if (Array.isArray(data)) console.log(data.length);   // fine: narrowed to any[]
```

The proof asks for code with no `any`. `unknown` is what replaces it at every boundary: parsed JSON, `fetch` responses, `catch` variables, messages
from other windows.

</Level>

<Level name="Intermediate">

`any` spreads silently:

```ts
const data: any = JSON.parse('{"user": null}');
const name: string = data.user.name;      // compiles
```

```text
TypeError: Cannot read properties of null (reading 'name')
```

With `unknown`, the same code does not compile until each step is checked. In `catch` blocks, strict mode makes the error `unknown` too
(`useUnknownInCatchVariables`), because anything can be thrown:

```ts
try { risky(); } catch (err) {
  const msg = err instanceof Error ? err.message : String(err);
}
```

</Level>

<Level name="Advanced">

Hand-written guards work for small shapes; a schema library scales. The
<a href={withBase('/posts/typescript/12/')}>unknown and validation note</a> covers the library route:

```ts
import { z } from 'zod';
const TodoSchema = z.object({ id: z.string(), text: z.string().min(1), done: z.boolean() });
type Todo = z.infer<typeof TodoSchema>;

const result = z.array(TodoSchema).safeParse(JSON.parse(raw));
if (!result.success) console.warn(result.error.issues);
const todos: Todo[] = result.success ? result.data : [];
```

One schema gives both the runtime check and the static type, so they cannot disagree.

</Level>

<Level name="Edge cases">

`Array.isArray` narrows `unknown` to `any[]`, which reintroduces `any` for the elements; validate elements too. `res.json()` returns `Promise<any>`;
annotate the result as `unknown` immediately: `const data: unknown = await res.json()`.

</Level>

<Level name="Corner cases">

Libraries with poor types return `any` and it leaks into my code without any warning. The lint rules `@typescript-eslint/no-unsafe-assignment` and
`no-unsafe-member-access` catch `any` flowing in from outside.

</Level>

<Level name="Production level">

Every external input (HTTP, storage, messages, environment variables) enters as `unknown` and is validated once at the boundary; `any` is banned by lint
with rare, commented exceptions.

</Level>

<Level name="Mindset">

Types describe what I have proved, not what I hope. `unknown` is honest about the moment before proof.

</Level>

<Level name="System design">

Validation at the edges, trusted types inside: the same boundary pattern as Phase 3's API validation, applied to every input the program has.

</Level>

<Level name="Strategy">

I search the codebase for `any` (explicit and from `JSON.parse` and `res.json()`), replace each with `unknown` plus a guard or a schema, and turn on the
no-unsafe lint rules.

Done when `grep -rn "any" src` finds no `any` types, the lint rules pass, and corrupted input produces a handled error instead of a crash.

</Level>

</Levels>

#### Phase 1: Strict mode

<Layers
  caption="What strict: true turns on, and the bug each flag catches"
  layers={[
    { name: 'strictNullChecks', note: 'null and undefined are their own types: no more cannot read properties of undefined' },
    { name: 'noImplicitAny', note: 'an untyped parameter is an error, not a silent any' },
    { name: 'strictFunctionTypes', note: 'callbacks must accept what they will be given' },
    { name: 'useUnknownInCatchVariables', note: 'catch (err) gives unknown, not any' },
    { name: 'strictPropertyInitialization', note: 'class fields must be set in the constructor' },
    { name: 'Beyond strict', note: 'noUncheckedIndexedAccess: arr[i] may be undefined' },
  ]}
/>

<Levels label="Phase 1, strict mode">

<Level name="Beginner">

TypeScript's `strict` option turns on a family of checks that catch the most common runtime errors. Without it, TypeScript lets many unsafe things
through. Every new project starts strict:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noEmit": true
  }
}
```

The biggest single win is `strictNullChecks`:

```ts
const todo = todos.find(t => t.id === id);
todo.text;
```

```text
error TS18048: 'todo' is possibly 'undefined'.
```

Without strict mode this compiles and crashes at runtime when the ID is not found.

</Level>

<Level name="Intermediate">

`noImplicitAny` stops untyped parameters from silently becoming `any`:

```ts
function total(items) { return items.reduce((s, i) => s + i.price, 0); }
```

```text
error TS7006: Parameter 'items' implicitly has an 'any' type.
```

`noUncheckedIndexedAccess` (not part of `strict`, but worth it) makes `arr[0]` and `record[key]` include `undefined`, which matches reality: an index
may be out of range.

Running `npx tsc --noEmit` checks the whole project without producing files; it goes in a script (`"typecheck": "tsc --noEmit"`) and later in CI.

</Level>

<Level name="Advanced">

Turning strict on in an existing JavaScript-to-TypeScript project produces hundreds of errors at once. The path: enable flags one at a time, fix the errors
each one reports, commit, repeat. `strictNullChecks` first, since it catches the most real bugs. The non-null assertion `todo!.text` silences the null
check without a runtime check; each use needs a comment, or better, a narrowing check.

</Level>

<Level name="Edge cases">

`// @ts-ignore` suppresses the next line's error forever, even after it is fixed; `// @ts-expect-error` fails when there is no longer an error, so stale
suppressions get noticed. Prefer the second, with a reason.

</Level>

<Level name="Corner cases">

Strict mode in TypeScript is not the same as JavaScript's `'use strict'`. The JavaScript one changes runtime behaviour (no implicit globals, `this` undefined
in plain functions); modules and classes have it automatically. TypeScript's `strict` only changes type checking.

</Level>

<Level name="Production level">

Strict is on in every project, the typecheck runs in CI, and suppressions are counted and reviewed.

</Level>

<Level name="Mindset">

Each strict error is a runtime crash found early. I treat them as free bug reports, not obstacles.

</Level>

<Level name="System design">

The compiler is a teammate that checks every line on every change. Strict settings decide how much it is allowed to catch.

</Level>

<Level name="Strategy">

I convert the vanilla app to TypeScript with strict on from the start and `noUncheckedIndexedAccess` added, fixing each error with a real check, not `!` or `as`.

Done when `tsc --noEmit` passes with strict, there are no `ts-ignore` comments, and every `!` and `as` has a written reason.

</Level>

</Levels>

#### Phase 1: When not to annotate

<Compare
  left="Over-annotated"
  right="Annotate the boundaries, infer the rest"
  caption="Annotations belong where they add information the compiler cannot infer, or where they form a contract."
  rows={[
    ['const count: number = 0', 'const count = 0'],
    ['const names: string[] = todos.map((t: Todo): string => t.text)', 'const names = todos.map(t => t.text)'],
    ['export function load() { ... }  (return type inferred)', 'export function load(): Todo[] { ... }'],
    ['const filter = "all"  then reassigned to other values', 'let filter: Filter = "all"'],
  ]}
/>

<Levels label="Phase 1, when not to annotate">

<Level name="Beginner">

TypeScript infers types from values, so most local variables need no annotation. `const count = 0` is already `number`; writing `: number` adds noise and
nothing else. Callback parameters are inferred from context: in `todos.map(t => t.text)`, `t` is already `Todo`.

Annotate where inference cannot help or where a contract matters: function parameters (they have no value to infer from), exported function return types,
empty collections (`const todos: Todo[] = []`, or it becomes `never[]`), and variables that start as one value and will hold others of a union.

Mistake: annotating every line "to be safe". The noise hides the annotations that matter, and a wrong annotation can widen a type and lose information.

</Level>

<Level name="Intermediate">

Where an annotation loses information:

```ts
const config: Record<string, string> = { home: '/', todos: '/todos' };
config.hme;            // no error: any string key is allowed

const config2 = { home: '/', todos: '/todos' };
config2.hme;           // error: Property 'hme' does not exist
```

The inferred type is more precise. When I want a check against a type and the precise type, `satisfies` does both.

</Level>

<Level name="Advanced">

Return types on exported functions are worth writing even when inferable: they document the contract, speed up the compiler in big projects, and catch a
change inside the function that would silently alter what callers receive. Internal helpers can rely on inference.

</Level>

<Level name="Edge cases">

`let x = null` infers `any` in some settings or `null` in others; annotate when a variable starts empty. `const` with a literal infers the literal type
(`'all'`), `let` widens it (`string`), which matters for unions.

</Level>

<Level name="Corner cases">

An annotation on a destructured parameter goes on the whole pattern, not inside it: `function f({ id }: { id: string })`, not `function f({ id: string })`,
which renames `id` to a variable called `string`.

</Level>

<Level name="Production level">

Lint rules (`no-inferrable-types`, `explicit-module-boundary-types`) encode the policy: no redundant annotations on locals, explicit types on exports.

</Level>

<Level name="Mindset">

Types are for readers and the compiler. Write the ones that tell either of them something new.

</Level>

<Level name="System design">

Annotated boundaries and inferred interiors mirror the validate-at-the-edge rule: contracts where modules meet, freedom inside.

</Level>

<Level name="Strategy">

I review the utility module and delete every annotation the editor's hover shows is redundant, and add return types to every export.

Done when every annotation in my code either types a parameter, an export, an empty collection or a widened variable, and nothing else.

</Level>

</Levels>

Mistake: keeping state in the DOM (reading checkboxes to find what is done). Fix: the array is the

</Level>

<Level name="Intermediate">

Every state change goes through one function that updates, saves and renders, so no path forgets a

```js
function setState(change) {
  todos = change(todos);
  save(todos);
  render();
}
const addTodo = (text) => setState((ts) => [...ts, { id: Date.now(), text, done: false }]);
const removeTodo = (id) => setState((ts) => ts.filter((t) => t.id !== id));

```

</Level>

<Level name="Advanced">

</Level>

<Level name="Corner cases">

</Level>

<Level name="Production level">

It loads with no console errors, works with the keyboard alone, survives a corrupt `localStorage`,

</Level>

<Level name="Mindset">

</Level>

<Level name="System design">

This is a tiny architecture: state, pure logic, rendering, persistence, each in its own module. The

</Level>

<Level name="Strategy">

One feature a week, in the order add, delete, filter, search, persist, fetch seed data. Done when it is
deployed and I can explain every function in it.

</Level>

<Level name="Beginner">

Small exercises are reps: each takes under an hour and drills one idea. I write them in a `drills/` folder, one file each, with a comment at the
top saying what it practises and a few `console.assert` lines at the bottom so the file checks itself when run with `node`.

```js
// drills/06-once.js: closures. once(fn) runs fn the first time only, then returns the first result.
export function once(fn) {
  let called = false;
  let result;
  return (...args) => {
    if (!called) { called = true; result = fn(...args); }
    return result;
  };
}

let n = 0;
const init = once(() => ++n);
console.assert(init() === 1 && init() === 1 && n === 1, 'once should run fn exactly once');
```

```sh
$ node drills/06-once.js
$                     # silence means every assert passed
```

The plan's first trap is tutorial hell: watching someone else write code feels like learning, and the first blank file proves it was not. These
twenty files are the antidote.

</Level>

<Level name="Intermediate">

The method that makes them stick: read the one-line spec, write it from a blank file without looking anything up, run the asserts, and only then
compare with a reference or ask for a review. Where I got stuck goes in the bug log. A week later I delete the file and write it again from the
spec; if I cannot, the idea is not mine yet. That is the second trap, copy-pasting code I cannot rewrite.

A worked one, exercise 8, `groupBy`, drilling arrays and objects:

```js
// drills/08-group-by.js
export function groupBy(items, keyFn) {
  return items.reduce((groups, item) => {
    const key = keyFn(item);
    (groups[key] ??= []).push(item);
    return groups;
  }, {});
}

const todos = [{ text: 'a', done: true }, { text: 'b', done: false }, { text: 'c', done: true }];
console.log(groupBy(todos, t => (t.done ? 'done' : 'active')));
```

```text

```

</Level>

<Level name="Advanced">

Exercise 17, a concurrency-limited fetch, combines promises, closures and the event loop:

```js
// drills/17-limit.js: run at most `limit` async tasks at once, keep result order
export async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i], i);
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
```

`next++` is safe without locks because JavaScript runs one piece at a time; the increment and the read happen in the same synchronous step. Explaining
why is a good test of the event loop topic.

</Level>

<Level name="Edge cases">

Each drill gets asserts for an edge: `groupBy([])` returns `{}`; `once` with a function that throws (should the second call retry?); `mapLimit` with a
limit larger than the list, or zero. Deciding the behaviour is half the exercise.

</Level>

<Level name="Corner cases">

The proof asks me to debug a broken app from the console. The first habit is reading the error properly. Every error has a type, a message and a stack:

Writing `debugger;` in code pauses there when DevTools is open. Conditional breakpoints (right-click the line number) pause only when an expression is true,
for example `todo === undefined`.

The console itself has more than `log`: `console.table(todos)` shows an array of objects as a table, `console.dir(el)` shows an element's properties, and
`console.trace()` prints how the current line was reached.

</Level>

<Level name="Advanced">

Hard bugs have a method. Make the reproduction smaller until it is minimal. Bisect: comment out half, see which half has the bug, repeat (or `git bisect`
across commits). Check assumptions one at a time, writing each down: "I believe `todos` is an array here", then verify. Use the Network panel when data
comes from outside and the Application panel when it comes from storage.

Pause on exceptions (the stop-sign icon in Sources) stops at the throw, with all the state that caused it still in scope, even for errors that are caught.

</Level>

<Level name="Edge cases">

The error may come from a line far from the cause: a bad value written to storage on Monday crashes rendering on Tuesday. Follow the value back to where it
was created. Minified production code shows meaningless names; source maps map it back to my files.

</Level>

<Level name="Corner cases">

`console.log(obj)` shows the object live, not as it was when logged, so expanding it later shows the current state. Log `structuredClone(obj)` or
`JSON.stringify(obj)` to capture the moment. Bugs that disappear when DevTools is open often involve timing or focus.

</Level>

<Level name="Production level">

Error tracking (Phase 4) captures stacks from users' browsers with source maps; the bug log becomes postmortems and runbooks; the method stays the same.

</Level>

<Level name="Mindset">

A bug is a gap between what I believe the code does and what it does. Debugging is finding which belief is wrong.

</Level>

<Level name="System design">

Observable code is debuggable code: clear errors with context, small functions, state in one place. Design choices from earlier topics are what make this
topic easy or hard.

</Level>

<Level name="Strategy">

The AI-era note asks for a bug log: the error, the cause, the fix, and the rule I keep so it does not happen again. Mine is a Markdown file with one entry
per bug:

```md
## 2026-10-12: Cannot read properties of undefined (reading 'text')
Cause: delete used the index from the filtered list on the full list.
Fix: delete by id, not index.
Rule: never pass an index across a filter; pass ids.
```

Someone (or a model) plants five bugs in a copy of my app; I find each from the console with breakpoints, no reading the diff.

Done when I can find planted bugs from the console alone, the bug log has an entry for every real bug this phase, and the rules column has changed how I write code.

</Level>

</Levels>

<Levels label="Phase 1, the gate, the traps and the AI-era note">

<Level name="Beginner">

The proof for this phase has three parts: explain closures, `this` and the event loop without notes; debug a broken app from the console; ship code with no
`any` and no unexplained casts. I take it as a gate, cold: a blank page for the explanations, a planted-bug app, and `grep` plus lint on my repository.

For the explanations, each one gets a short written answer and a code example I can run: a counter factory for closures, the same method called four ways
for `this`, the 1-to-5 ordering trace for the event loop.

</Level>

<Level name="Intermediate">

The AI-era note: use AI for code review, not for the first draft of every function. A review prompt that teaches rather than replaces:

```text
Prompt: What is wrong with this function? List bugs, edge cases it mishandles, and
anything that would fail TypeScript strict mode. Do not rewrite it.
```

Then I fix the problems myself and add each real bug to the log. The model's review is a second pair of eyes; the fix stays mine.

</Level>

<Level name="Advanced">

I also use the model as an examiner: ask it for five event-loop ordering puzzles of increasing difficulty and five `this` puzzles, answer them on paper, then
run them. Wrong answers point to exactly which part of the model in my head is wrong.

</Level>

<Level name="Edge cases">

A model's explanation of `this` or the event loop can be subtly wrong (for example about when rendering happens). I check claims against running code or MDN,
not against another model answer.

</Level>

<Level name="Corner cases">

Passing the `any` check by hiding types behind `as unknown as T` is a cast in disguise; the gate counts those as unexplained casts unless commented.

</Level>

<Level name="Production level">

The checks that prove "no any" (lint rules, `tsc --noEmit`) stay in the repository's scripts, so the property holds after the gate.

</Level>

<Level name="Mindset">

The gate is not a test to pass once; it is a check that the model in my head matches the machine.

</Level>

<Level name="System design">

Everything later, React's renders, Node's request handling, async jobs, rests on closures, `this` and the event loop. A gap here shows up as mystery bugs in
every later phase.

</Level>

<Level name="Strategy">

At the end of week 10, take the gate cold: write the three explanations without notes, fix the planted-bug app from the console, and run the `any` and cast audit.

Done when all three explanations are correct on first writing, every planted bug is found from the console, the audit is clean, and each trap in the table has
evidence in the repository. If not, the plan's advice holds: go back, because the next phase will not fix it.

</Level>

</Levels>
