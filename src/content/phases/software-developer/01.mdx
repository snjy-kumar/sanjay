<Levels label="Phase 1, values and types">

<Level name="Beginner">

A value is a piece of data; its type says what I can do with it. `typeof` tells me the type at runtime.
Variables are names for values: `const` for names that will not be reassigned, `let` for ones that
will, and never `var` in new code.

```js
const name = 'Sanjay';
let count = 0;
count = count + 1;
console.log(typeof name, typeof count, typeof true, typeof undefined); // string number boolean undefined
```

Mistake: `const list = []; list = [1]` throws `TypeError: Assignment to constant variable.` Fix: `const`
stops reassignment, not change; `list.push(1)` is fine.

</Level>

<Level name="Intermediate">

Primitives are copied by value; objects by reference. Two variables can point at the same object, so
changing it through one changes it for both. Equality: `===` compares type and value with no
conversion; `==` converts first and has surprising rules, so I use `===` always.

```js
const a = { n: 1 }; const b = a; b.n = 2;
console.log(a.n);           // 2
console.log({} === {});     // false: two different objects
console.log('1' == 1, '1' === 1); // true false
```

Truthy and falsy: `false`, `0`, `-0`, `0n`, `''`, `null`, `undefined` and `NaN` are falsy; every
other value, including `'0'`, `[]` and `{}`, is truthy.

</Level>

<Level name="Advanced">

Numbers are IEEE 754 doubles, so decimal fractions are approximate and integers are exact only up to
`Number.MAX_SAFE_INTEGER`. Operators coerce: `+` concatenates when either side is a string, while `-`,
`*` and `/` convert to numbers. `typeof null` is `'object'`, a historical bug kept for compatibility.
Strings are UTF-16, so `length` counts code units, not characters.

```js
0.1 + 0.2;            // 0.30000000000000004
'5' + 1; '5' - 1;     // '51' 4
typeof null;          // 'object'
'👍'.length;          // 2
[...'👍'].length;     // 1
```

Mistake: comparing money with floats. Fix: store cents as integers.

</Level>

<Level name="Edge cases">

`NaN` is the only value not equal to itself: `NaN === NaN` is false; use `Number.isNaN`. `-0 === 0` is
true but `Object.is(-0, 0)` is false. `Number('')` is `0`, `Number(' ')` is `0`, `Number('12px')` is
`NaN`, while `parseInt('12px')` is `12`. `undefined` and `null` are both "nothing" but `null` is chosen
and `undefined` usually is not.

</Level>

<Level name="Corner cases">

A form input plus arithmetic: `input.value` is always a string, so `input.value + 1` gives `'41'` when
the user typed 4. An empty input plus `Number()` gives `0`, which silently passes a "required number"
check. `[] + {}` is `'[object Object]'` because both convert to strings. `null >= 0` is true while
`null == 0` is false.

</Level>

<Level name="Production level">

Most type bugs in real apps happen at the edges: form fields, query strings, JSON from an API, values
from `localStorage`, all of which arrive as strings or of unknown shape. Convert once, at the boundary,
and check the result (`Number.isFinite`). Prices are integers in the smallest unit; IDs are strings.

</Level>

<Level name="Mindset">

Know which values could be there, not which ones I expect. Most "JavaScript is weird" moments are
coercion I did not ask for, and `===` plus explicit conversion removes almost all of them.

</Level>

<Level name="System design">

The question "what type is this value at this point?" is exactly what TypeScript automates in week 8,
and what validation enforces at the API boundary in Phase 3. Learning the runtime types first is what
makes the static ones make sense.

</Level>

<Level name="Strategy">

Predict-then-run drills: twenty expressions, write my prediction, run them, log every miss. Done when I
can predict `typeof`, truthiness, `===` against `==` and the coercion of `+` and `-` for any common
value without running it.

</Level>

</Levels>

#### Phase 1: Functions and scope

<Levels label="Phase 1, functions and scope">

<Level name="Beginner">

A function is a named, reusable piece of work that takes inputs (parameters) and returns an output.
Three ways to write one: a declaration, a function expression and an arrow function.

```js
function add(a, b) { return a + b; }
const sub = function (a, b) { return a - b; };
const mul = (a, b) => a * b;
console.log(add(2, 3), sub(5, 1), mul(2, 4)); // 5 4 8
```

Scope is where a name is visible. `let` and `const` are visible inside the nearest braces. Mistake:
forgetting `return` in a function with braces, which returns `undefined`. Fix: arrows without braces
return automatically; with braces, write `return`.

</Level>

<Level name="Intermediate">

Default parameters, rest parameters and returning objects. Functions are values: I can pass them to
other functions (callbacks) and return them.

```js
const greet = (name = 'friend') => `Hi, ${name}`;
const sum = (...nums) => nums.reduce((t, n) => t + n, 0);
const point = (x, y) => ({ x, y });   // parentheses or the braces become a block
const twice = (f) => (x) => f(f(x));
console.log(greet(), sum(1, 2, 3), point(1, 2), twice((n) => n + 3)(1)); // Hi, friend 6 {x:1,y:2} 7
```

Mistake: `const point = (x, y) => { x, y }` returns `undefined`. Fix: wrap the object in parentheses.

</Level>

<Level name="Advanced">

Scope is lexical: decided by where code is written, not where it is called. Declarations are hoisted
(usable before their line); `let` and `const` exist from the start of their block but throw if touched
before their line, the temporal dead zone. Arguments are passed by value, but an object's value is a
reference, so a function can mutate the caller's object yet cannot replace it.

```js
console.log(hoisted()); function hoisted() { return 'ok'; } // ok
console.log(x); let x = 1; // ReferenceError: Cannot access 'x' before initialization
function rename(user) { user.name = 'B'; user = { name: 'C' }; }
const u = { name: 'A' }; rename(u); console.log(u.name); // B
```

</Level>

<Level name="Edge cases">

Calling with fewer arguments leaves the rest `undefined`; with more, the extras are ignored (but visible
in rest parameters). A default applies for `undefined` but not for `null`: `greet(null)` gives
`Hi, null`. A function with no `return` returns `undefined`. Shadowing: an inner `const items` hides
the outer one inside its block, a quiet source of "my update did nothing" bugs.

</Level>

<Level name="Corner cases">

`['1', '2', '3'].map(parseInt)` returns `[1, NaN, NaN]`, because `map` passes the index as the second
argument and `parseInt` reads it as the radix. Two boundaries meeting: a callback API and a function
with an optional parameter. Fix: `.map((s) => parseInt(s, 10))` or `.map(Number)`.

</Level>

<Level name="Production level">

Small pure functions (same input, same output, no side effects) are easy to test and reuse; side
effects (DOM writes, storage, network) go at the edges. Name functions for what they return or do:
`visibleTodos`, `saveTodos`. Long parameter lists become one options object.

</Level>

<Level name="Mindset">

A function is a promise about inputs and outputs. If I cannot say that promise in a sentence, the
function does too much.

</Level>

<Level name="System design">

The pure-core, effects-at-the-edge split here is the same shape as reducers in Redux, React components
that render from props, and request handlers that call a pure domain function. It is the main
architectural idea of the whole path, met in miniature.

</Level>

<Level name="Strategy">

Exercises 1–4: a temperature converter, a word counter, a function that returns a function, and a
scope puzzle I write myself. Done when I can explain hoisting, the temporal dead zone and lexical scope
with my own example, and every function in the app has a one-sentence promise.

</Level>

</Levels>

#### Phase 1: Closures

<Figure art={`
  makeCounter() runs once            counter() runs many times
  +---------------------------+      +--------------------------+
  | let count = 0   <---------+------+-- reads and writes count |
  | return function counter   |      |   count = count + 1      |
  +---------------------------+      +--------------------------+
  makeCounter has returned, but count stays alive,
  because counter still refers to it.
`} caption="A closure is a function plus the variables it captured. The variables outlive the call that made them." />

<Levels label="Phase 1, closures">

<Level name="Beginner">

A closure is a function that remembers the variables from where it was created, even after that outer
function has returned.

```js
function makeCounter() {
  let count = 0;
  return () => { count += 1; return count; };
}
const next = makeCounter();
console.log(next(), next(), next()); // 1 2 3
```

`count` is private: nothing outside can read or reset it. Mistake: thinking `count` resets on each
call. Fix: it resets only when `makeCounter` runs again, which makes a new, separate `count`.

</Level>

<Level name="Intermediate">

Every event handler and callback is a closure. In the todo app, a handler created inside a render
function captures that item's id.

```js
function renderItem(todo) {
  const li = document.createElement('li');
  const del = document.createElement('button');
  del.textContent = 'Delete';
  del.addEventListener('click', () => removeTodo(todo.id)); // captures todo
  li.append(todo.text, del);
  return li;
}
```

Closures also make factories (`makeCounter`), private state, and partially applied functions such as
`const addTax = (rate) => (price) => price * (1 + rate)`.

</Level>

<Level name="Advanced">

A closure captures variables, not values: it keeps a live reference to the binding, so it sees later
changes. `let` in a `for` loop creates a fresh binding per iteration; `var` creates one for the whole
function. That difference is the classic interview question and a real bug.

```js
const fs = [];
for (var i = 0; i < 3; i++) fs.push(() => i);
console.log(fs.map((f) => f())); // [3, 3, 3]
const gs = [];
for (let j = 0; j < 3; j++) gs.push(() => j);
console.log(gs.map((g) => g())); // [0, 1, 2]
```

</Level>

<Level name="Edge cases">

A closure over a large object keeps that whole object in memory as long as the closure lives, for
example a handler on a long-lived element. Removing the element but keeping the handler registered
elsewhere leaks it. A closure created in a loop over 10,000 items creates 10,000 functions; one
delegated listener is lighter.

</Level>

<Level name="Corner cases">

The stale closure: a callback captures a variable, the variable is later reassigned to a new value,
but the callback was registered once and holds the old binding's value, for example a `setInterval`
whose callback reads a settings object that was replaced, not mutated. In React this becomes the
<a href={withBase('/posts/react/06/')}>stale closure in a handler or effect</a>, the bug Gate 2 asks me
to fix.

```js
let settings = { step: 1 };
const read = ((s) => () => s.step)(settings); // captured the object at that moment
settings = { step: 5 };
console.log(read()); // 1
```

</Level>

<Level name="Production level">

Closures are how modules keep private state, how middleware gets configured, and how memoization
caches results. Their cost is memory and stale data: anything long-lived (timers, global listeners,
subscriptions) must be cleaned up, and its captured values must be fresh or read through a reference.

</Level>

<Level name="Mindset">

When a function runs, ask: which variables did it capture, and when? Most "it uses the old value" bugs
answer themselves.

</Level>

<Level name="System design">

React hooks are built on closures over each render's props and state. Understanding closures here is
what makes the dependency arrays and the stale-closure fixes of Phase 2 obvious rather than magical.

</Level>

<Level name="Strategy">

Write a counter, a once-only function, a memoizer and a rate limiter, each with closures. Then explain
the `var` loop out loud. Done when I can explain closures without notes, as the plan's proof requires,
and fix a stale closure on sight.

</Level>

</Levels>

#### Phase 1: `this`

<Flow
  caption="How JavaScript decides this for a normal function call. Arrow functions skip the chart and use the surrounding this."
  steps={['Called with new? the new object', 'Called with call, apply or bind? the given object', 'Called as obj.method()? obj', 'Otherwise: undefined in strict mode (window in sloppy scripts)']}
/>

<Levels label="Phase 1, this">

<Level name="Beginner">

`this` is a hidden parameter: for a regular function it is set by how the function is called, not where
it is written. Called as a method, `this` is the object before the dot.

```js
const user = { name: 'Sanjay', hi() { return `Hi, ${this.name}`; } };
console.log(user.hi()); // Hi, Sanjay
```

Mistake: expecting `this` to mean the function or the file. Fix: look at the call site.

</Level>

<Level name="Intermediate">

Pulling a method off its object loses `this`. Passing it as a callback does the same. Arrow functions
do not have their own `this`; they use the one from the code around them, which is why they fix the
callback case.

```js
const hi = user.hi;
hi(); // TypeError: Cannot read properties of undefined (reading 'name') in a module
setTimeout(user.hi, 0);          // same loss
setTimeout(() => user.hi(), 0);  // keeps the call site
const bound = user.hi.bind(user); bound(); // Hi, Sanjay
```

</Level>

<Level name="Advanced">

The rules in order of priority: `new` binds a fresh object; `call`, `apply` and `bind` set it
explicitly; a method call uses the receiver; a plain call gets `undefined` in strict mode (modules and
classes are strict). Class methods are not auto-bound. In DOM listeners, a regular function's `this` is
the element (`event.currentTarget`), an arrow's is not.

```js
class Timer { constructor() { this.ticks = 0; } tick() { this.ticks++; } }
const t = new Timer();
button.addEventListener('click', t.tick);          // this is the button, ticks is NaN on it
button.addEventListener('click', () => t.tick());   // correct
```

</Level>

<Level name="Edge cases">

An arrow function used as an object method: `{ name: 'A', hi: () => this.name }` reads the outer `this`,
usually `undefined` in a module, so the property read throws. `bind` is permanent: binding a bound
function again does nothing. Destructuring a method `const { hi } = user` loses `this` the same way
assignment does.

</Level>

<Level name="Corner cases">

`array.forEach(obj.method)` plus a method that uses `this`: `forEach` accepts a `thisArg` second
argument that most people never pass. `removeEventListener` with `fn.bind(obj)` fails silently because
each `bind` creates a new function, so the listener was never the same reference; store the bound
function once.

</Level>

<Level name="Production level">

Modern code uses `this` mostly inside classes, and passes methods as arrows or binds them in the
constructor. React function components avoid it entirely. Libraries that still use it (some DOM APIs,
older code) are where it bites, so the rule set matters for reading code more than writing it.

</Level>

<Level name="Mindset">

Hidden inputs are dangerous. `this` is an argument I did not write; when code behaves differently from
two call sites, look for hidden inputs.

</Level>

<Level name="System design">

Design APIs that do not depend on how they are called: plain functions and closures over explicit
arguments are easier to pass around than methods relying on `this`.

</Level>

<Level name="Strategy">

Ten call sites, predict `this` for each, run them. Done when I can explain the four rules and the
arrow exception without notes, as the plan's proof asks, and fix a lost-`this` callback in one line.

</Level>

</Levels>

<Levels label="Phase 1, arrays and objects">

<Level name="Beginner">

An array is an ordered list; an object is a set of named properties. The plan names a trap here:
avoiding array methods because `map` feels clever. They are the everyday tools.

```js
const todos = [
  { id: 1, text: 'Write README', done: true },
  { id: 2, text: 'Deploy', done: false },
];
const texts = todos.map((t) => t.text);          // ['Write README', 'Deploy']
const open = todos.filter((t) => !t.done);       // [{ id: 2, ... }]
const found = todos.find((t) => t.id === 2);     // { id: 2, ... }
const count = todos.reduce((n, t) => n + (t.done ? 1 : 0), 0); // 1
```

Mistake: a `for` loop with an index to build a new array, off by one. Fix: `map` and `filter`.

</Level>

<Level name="Intermediate">

Immutable updates: produce a new array or object instead of editing in place, so other code holding the
old one is not surprised, and so React can later detect the change.

```js
const toggled = todos.map((t) => (t.id === 2 ? { ...t, done: !t.done } : t));
const added = [...todos, { id: 3, text: 'Test', done: false }];
const removed = todos.filter((t) => t.id !== 1);
```

Objects: `Object.keys`, `Object.values`, `Object.entries`, and `Object.fromEntries` to rebuild. `some`
and `every` answer yes-or-no questions. `includes` checks membership.

</Level>

<Level name="Advanced">

Spread copies one level only (a shallow copy); nested objects are still shared. `structuredClone` makes
a deep copy of plain data. `sort` sorts as strings by default and mutates. Arrays are objects with
numeric keys and a `length`; holes exist. `Map` and `Set` are better than objects for dynamic keys and
uniqueness.

```js
[10, 9, 1].sort();                 // [1, 10, 9]
[10, 9, 1].toSorted((a, b) => a - b); // [1, 9, 10]
const a = { tags: ['x'] }; const b = { ...a }; b.tags.push('y'); console.log(a.tags); // ['x', 'y']
[...new Set([1, 1, 2])];           // [1, 2]
```

</Level>

<Level name="Edge cases">

`reduce` on an empty array with no initial value throws `TypeError: Reduce of empty array with no
initial value`. `find` returns `undefined` when nothing matches; `findIndex` returns `-1`. `[].every(f)`
is `true`. `indexOf(NaN)` is `-1` while `includes(NaN)` is `true`. An object key `'__proto__'` from user
input can change the prototype; use `Map` or `Object.create(null)` for user-keyed data.

</Level>

<Level name="Corner cases">

Sorting objects with a comparator that returns a boolean (`(a, b) => a.date > b.date`) appears to work
on small inputs and fails on others, because `sort` needs negative, zero or positive. Mutating an array
while iterating it with `forEach` (removing items) skips elements. Shallow copy plus nested update:
`{ ...state, user: state.user }` followed by `user.name = 'x'` mutates the original.

</Level>

<Level name="Production level">

Data work in apps is mostly map, filter, find, group and sort over API results. Choose the right
structure: an array for order, a `Map` keyed by id for lookups. Normalize nested API data into an object
by id when many parts of the UI read the same records.

</Level>

<Level name="Mindset">

Decide whether I am transforming or mutating, and say so. Treating data as values that produce new
values is the habit that makes React and Redux easy later.

</Level>

<Level name="System design">

The shape of in-memory data mirrors the database schema of Phase 3: lists of records with ids, grouped
and joined. `groupBy` in code is `GROUP BY` in SQL.

</Level>

<Level name="Strategy">

Exercises 5–7: group a list by a field, compute totals, deduplicate and sort without mutating. Done when
I can write add, toggle, delete and filter for the app as one-line immutable updates and explain
shallow copies.

</Level>

</Levels>

#### Phase 1: Destructuring

<Figure art={`
  const { id, text: label, done = false, ...rest } = todo;
            |     |            |              |
   todo.id -+     |            |              +-- every other property
   todo.text, renamed to label |
                  todo.done, or false when it is undefined
`} caption="Destructuring is pattern-matching on shape: pick fields, rename them, default them, gather the rest." />

<Levels label="Phase 1, destructuring">

<Level name="Beginner">

Destructuring unpacks values from arrays and objects into variables in one line.

```js
const todo = { id: 1, text: 'Deploy', done: false };
const { text, done } = todo;
const [first, second] = ['a', 'b'];
console.log(text, done, first); // Deploy false a
```

Mistake: destructuring a name that does not exist gives `undefined`, not an error. Fix: check the
spelling against the actual object, or add a default.

</Level>

<Level name="Intermediate">

Rename, default, nest, and use it in parameters. Swap two variables without a temporary.

```js
const { text: label, priority = 'normal' } = todo;
function render({ id, text, done = false }) { return `${id}:${text}:${done}`; }
let x = 1, y = 2; [x, y] = [y, x];
const { user: { name } } = { user: { name: 'S' } };
```

Rest gathers the remainder: `const { id, ...withoutId } = todo` is a clean way to drop a field.

</Level>

<Level name="Advanced">

Defaults apply only when the value is `undefined`, not `null`. Destructuring an object pattern runs
property gets, so getters run. Array destructuring works on any iterable (a `Map`'s entries, a
`Set`), which is why `for (const [key, value] of map)` works.

```js
const { a = 1 } = { a: null }; console.log(a); // null
for (const [k, v] of new Map([['x', 1]])) console.log(k, v); // x 1
```

</Level>

<Level name="Edge cases">

Destructuring `null` or `undefined` throws: `const { a } = null` gives `TypeError: Cannot destructure
property 'a' of 'null' as it is null.` Guard with `= {}` as a parameter default:
`function f({ a } = {})`.

</Level>

<Level name="Corner cases">

A parameter default `= {}` plus a caller passing `null`: the default does not apply (only `undefined`
triggers it), so the destructure still throws. Nested destructuring plus a missing middle object
(`{ user: { name } }` when `user` is absent) throws as well. Optional chaining reads safely where
destructuring cannot.

</Level>

<Level name="Production level">

Destructured parameters make function signatures self-documenting and are the standard way React

<Level name="System design">

<Levels label="Phase 1, modules">

<Level name="Beginner">

A module is a file with its own scope that exports what others may use and imports what it needs. In
the browser, `<script type="module">` turns them on.

```js
// format.js
export function plural(n, word) { return `${n} ${word}${n === 1 ? '' : 's'}`; }
// main.js
import { plural } from './format.js';

```

Mistake: opening the HTML by double-click gives a CORS error for modules on `file://`. Fix: serve it
with `npx serve .`.

</Level>

<Level name="Intermediate">

Named exports for most things, a default export rarely. Import paths in the browser need the extension
(`./format.js`). Modules are strict mode and deferred automatically. Split by responsibility: data,
rendering, helpers.

</Level>

<Level name="Advanced">

ES module imports are live bindings, read-only to the importer, resolved before any code runs (static),
and each module runs once no matter how many files import it. `import()` loads a module lazily and
returns a promise. CommonJS (`require`) is Node's older system: synchronous, copied values, and still
common in packages.

```js
const { heavy } = await import('./heavy.js'); // loaded only when needed
```

</Level>

<Level name="Edge cases">

`ReferenceError: Cannot access 'x' before initialization`. Mixing `require` and `import` in Node
depends on `"type": "module"` in `package.json` and file extensions `.mjs` and `.cjs`.

</Level>

<Level name="Corner cases">

A module with side effects at the top level (adding listeners) plus a test that imports it: the side
effect runs in the test. Keep top-level code to declarations, and do work in exported functions.

</Level>

<Level name="Production level">

only works when imports are static and modules have no hidden side effects.

</Level>

<Level name="Mindset">

A module boundary is a promise about what is public. Export less.

</Level>

<Level name="System design">

Module graphs become package boundaries, then service boundaries. Cycles at any level are the same
smell.

</Level>

<Level name="Strategy">

Split the app into four modules with no cycles. Done when each module's exports fit on one line and a
change to rendering touches only `render.js`.

</Level>

#### Phase 1: Promises and `async`/`await`

<Figure art={`
                 +-----------+
   new Promise ->|  pending  |
                 +-----+-----+
            resolve(v) |  reject(e)
             +---------+---------+
             v                   v
      +-------------+     +-------------+
      | fulfilled v |     | rejected e  |   settled: never changes again
      +------+------+     +------+------+
             |  .then(f)         |  .catch(g)   (await gives v, or throws e)
`} caption="A promise is a placeholder for one future result. It settles once, to a value or to an error." />

<Levels label="Phase 1, promises and async/await">

<Level name="Beginner">

Some work finishes later: a network request, a timer, reading a file. A promise represents that future
result. `await` pauses an `async` function until the promise settles and gives me the value.

```js
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
async function main() {
  console.log('start');
  await wait(500);
  console.log('half a second later');
}
main();
```

Mistake: forgetting `await`, so the variable holds `Promise { <pending> }` instead of the data. Fix:
`await` it, inside an `async` function.

</Level>

<Level name="Intermediate">

Errors: a rejected promise makes `await` throw, so `try`/`catch` works. Run independent work in
parallel with `Promise.all`; it rejects as soon as any one rejects. `Promise.allSettled` waits for all
and reports each outcome.

```js
async function loadBoth() {
  try {
    const [users, posts] = await Promise.all([getJSON('/users'), getJSON('/posts')]);
    return { users, posts };
  } catch (err) {
    console.error('load failed:', err.message);
    return { users: [], posts: [] };
  }
}
```

Mistake: `await` inside a loop for independent requests, making them sequential. Fix: build an array of
promises and `await Promise.all(...)`.

</Level>

<Level name="Advanced">

`then` callbacks always run asynchronously, as microtasks, even for an already-resolved promise.
Returning a promise from `then` chains it; throwing inside `then` rejects the chain. An `async` function
always returns a promise. `Promise.race` settles with the first to settle and `Promise.any` with the
first to fulfil. A promise that rejects with no handler triggers an `unhandledrejection` event in the
browser and crashes Node by default.

```js
Promise.resolve(1).then((v) => console.log('then', v));
console.log('sync');
// sync
// then 1
```

</Level>

<Level name="Edge cases">

`Promise.all([])` resolves immediately with `[]`. `await` on a non-promise just wraps it. A `forEach`
with an `async` callback does not wait for anything: the loop finishes and the function returns before
any callback completes. Use `for...of` with `await`, or `Promise.all` with `map`.

</Level>

<Level name="Corner cases">

A timeout race plus a slow request: `Promise.race([fetch(url), timeout(5000)])` returns on time, but the
fetch keeps running in the background; only an `AbortController` actually cancels it. Two rapid
searches plus out-of-order responses: the older, slower response arrives last and overwrites the newer
results. Track the latest request id, or abort the previous request.

</Level>

<Level name="Production level">

Every async call needs three states in the UI (loading, success, error), a timeout, and a decision on
retries. Unhandled rejections are monitored in production; a `.catch` that swallows errors silently is
worse than a crash because nobody knows.

</Level>

<Level name="Mindset">

Ask "what if this never comes back, comes back late, or comes back twice?" for every await.

</Level>

<Level name="System design">

Concurrency limits, retries with backoff and cancellation recur in the backend (Phase 3 jobs and email),
in Phase 4 timeouts, and in Phase 5 model calls. The promise is the unit they all compose.

</Level>

<Level name="Strategy">

Exercises 16–17: a sleep, a timeout wrapper with `AbortController`, and a concurrency-limited
downloader. Done when I can say the output order of mixed sync, promise and timer code, and the app
never shows stale search results.

</Level>

</Levels>

#### Phase 1: The event loop

<Figure art={`
   +---------------+     empty?     +--------------------+
   |  call stack   | -------------> | run ALL microtasks |  (promise callbacks,
   | (sync code)   |                | until queue empty  |   queueMicrotask)
   +---------------+                +---------+----------+
          ^                                   |
          |                                   v
          |                         +--------------------+
          +------ take ONE task ----|  render if needed  |
                 (timers, clicks,   +--------------------+
                  network events)
`} caption="The loop: run the stack to empty, drain every microtask, maybe render, then take one task. Repeat." />

<Levels label="Phase 1, the event loop">

<Level name="Beginner">

JavaScript in a page runs on one thread: one thing at a time. Slow work (timers, network) is handed to
the browser, and its callback is queued for later. The event loop runs queued callbacks when the
current code finishes.

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
console.log('C');
// A C B
```

Mistake: thinking `setTimeout(f, 0)` runs immediately. Fix: it runs after the current code and after
promise callbacks.

</Level>

<Level name="Intermediate">

Two queues matter: tasks (timers, events, messages) and microtasks (promise reactions). After each task,
all microtasks run before the next task.

```js
console.log(1);
setTimeout(() => console.log(2));
Promise.resolve().then(() => console.log(3));
queueMicrotask(() => console.log(4));
console.log(5);
// 1 5 3 4 2
```

A long loop blocks everything, including clicks and painting: the page freezes.

</Level>

<Level name="Advanced">

Rendering happens between tasks, at most once per frame (about every 16 ms at 60 Hz), and
`requestAnimationFrame` callbacks run just before it. Because microtasks drain fully, a microtask that
queues another microtask forever starves rendering just like an infinite loop. Node's loop has phases
(timers, I/O poll, check for `setImmediate`) with `process.nextTick` running even before promise
microtasks.

</Level>

<Level name="Edge cases">

Timers are clamped: nested timeouts get at least about 4 ms, and background tabs throttle timers to
once a second or less. A 0 ms delay is a minimum, not a promise.

</Level>

<Level name="Corner cases">

Updating the DOM in a loop and reading layout (`offsetHeight`) in the same loop forces a synchronous
layout every iteration (layout thrashing). Batch reads, then writes. A heavy JSON parse after a fetch
blocks input for that whole duration even though the fetch itself was async.

</Level>

<Level name="Production level">

Long tasks over 50 ms hurt responsiveness, which Phase 4 measures as Interaction to Next Paint. Split
work into chunks, defer non-urgent work, or move it to a Web Worker.

</Level>

<Level name="Mindset">

Async is not parallel. One thread, many waits; the skill is never holding the thread.

</Level>

<Level name="System design">

Node servers use the same model: one slow synchronous operation blocks every request on that process.
That is why Phase 3 uses async database drivers and pushes CPU work to jobs.

</Level>

<Level name="Strategy">

Write ten ordering puzzles mixing logs, timers, promises and `await`, predict, run. Done when I can
explain the event loop without notes, as the plan's proof requires, and draw the diagram above from
memory.

</Level>

</Levels>

#### Phase 1: The DOM and events

<Flow

<Levels label="Phase 1, the DOM and events">

<Level name="Beginner">

The DOM is the browser's live tree of the page, as objects JavaScript can read and change. Select
elements, change text, create new ones, and listen for events.

```js
const list = document.querySelector('#todos');
const li = document.createElement('li');
li.textContent = 'Write tests';
list.append(li);
document.querySelector('#add').addEventListener('click', () => console.log('clicked'));
```

Mistake: running the script before the element exists, so `querySelector` returns `null` and the next
line throws `Cannot read properties of null`. Fix: `type="module"` or `defer`, which run after parsing.

</Level>

<Level name="Intermediate">

Forms: listen to `submit` on the form, call `event.preventDefault()` to stop the page reload, and read
values from the form. Event delegation: one listener on the list handles clicks for all items,
including future ones.

```js
form.addEventListener('submit', (e) => {
  e.preventDefault();
  const text = new FormData(form).get('text').trim();
  if (text) addTodo(text);
  form.reset();
});

  const btn = e.target.closest('button[data-action="delete"]');
  if (btn) removeTodo(Number(btn.closest('li').dataset.id));
});
```

</Level>

<Level name="Advanced">

Events travel in three phases: capture down, target, bubble up. `event.target` is where it started,
`event.currentTarget` is the element whose listener is running. `stopPropagation` halts the journey;
`preventDefault` cancels the default action. Listener options: `{ once: true }`, `{ passive: true }`
for scroll performance, and `signal` from an `AbortController` to remove many listeners at once.
`textContent` sets text safely; `innerHTML` parses HTML.

</Level>

<Level name="Edge cases">

`focus` and `blur` do not bubble (use `focusin` and `focusout`). Pressing Enter in a single-input form
submits it. A `button` inside a form defaults to `type="submit"`, so a "Clear" button submits the form
unless it says `type="button"`.

</Level>

<Level name="Corner cases">

`innerHTML` plus user input is an XSS hole: a todo titled with an `img` tag carrying an `onerror`
attribute runs script. Use `textContent`, which Phase 4 returns to. Re-rendering the whole list with
`innerHTML` plus a focused input inside it destroys the input and the user's cursor position.

</Level>

<Level name="Production level">

Keep one source of truth (an array in memory), render the DOM from it, and never read state back from
the DOM. This is the core idea React automates. Accessible events: buttons, not clickable divs, so
keyboard users can act.

</Level>

<Level name="Mindset">

The DOM is a view of my data, not the data. When they disagree, the data is right.

</Level>

<Level name="System design">

State, then render, then events that change state: the loop of every UI framework. The plan's trap,
reaching for React before manipulating the DOM, skips learning the loop React hides.

</Level>

<Level name="Strategy">

Exercises 10–12: a counter, a tab widget, a delegated list. Done when the app renders entirely from
an array, uses one delegated listener, and contains no `innerHTML` with user data.

</Level>

<Levels label="Phase 1, fetch">

<Level name="Beginner">

`fetch` makes an HTTP request from JavaScript and returns a promise for the response. Read the body with

```js
const res = await fetch('https://jsonplaceholder.typicode.com/todos?_limit=3');
const todos = await res.json();
console.log(todos.length); // 3
```

Mistake: assuming `fetch` rejects on a 404. It does not; it resolves with `res.ok === false`. Fix: check

</Level>

<Level name="Intermediate">

A helper that handles status, JSON and errors in one place, with a POST example.

```js
async function getJSON(url, options = {}) {

}
await getJSON('/api/todos', {
```

<Level name="Corner cases">

A CORS failure plus a successful server: the server did the work (even wrote to the database), but the

</Level>

<Level name="Production level">

Every fetch has a timeout, a loading state, an error message a person can act on, and an empty state.

<Level name="Mindset">

The network is unreliable by default. Write the failure path first.

<Level name="System design">

A single API client module is where auth headers, base URLs, error mapping and retries live, so the
rest of the app calls functions, not URLs.

#### Phase 1: Errors

<Layers
  caption="Where an error should be handled: low layers throw with context, the top layer decides what the user sees."
  layers={[

    { name: 'Feature logic', note: 'catch what it can recover from, add context, rethrow the rest' },

<Levels label="Phase 1, errors">

<Level name="Beginner">

When something goes wrong, JavaScript throws an error object with a `name`, a `message` and a `stack`.
`try`/`catch` handles it. Reading the error is the first debugging skill.

```js
try {
  JSON.parse('{bad');
} catch (err) {
  console.log(err.name, '-', err.message);
  // SyntaxError - Expected property name or '}' in JSON at position 1
}
```

Mistake: `catch (e) {}` with nothing inside. Fix: handle, log, or rethrow; never swallow.

</Level>

<Level name="Intermediate">

Throw your own errors with useful messages, and use `finally` for cleanup that must always run. Custom
error classes let callers tell kinds apart.

```js
class ValidationError extends Error {
  constructor(field, message) { super(message); this.name = 'ValidationError'; this.field = field; }
}
function addTodo(text) {
  if (!text.trim()) throw new ValidationError('text', 'A todo needs some text');
}
try { addTodo('  '); } catch (e) { if (e instanceof ValidationError) showFieldError(e.field, e.message); else throw e; }
```

</Level>

<Level name="Advanced">

The stack trace lists the call chain, newest first; the top frame in my own file is usually where to
look. `new Error(msg, { cause })` wraps a lower error without losing it. Errors thrown in callbacks or
promises escape a surrounding synchronous `try`; they need their own handling.

```js
try { setTimeout(() => { throw new Error('later'); }); } catch { /* never runs */ }
```

</Level>

<Level name="Edge cases">

`throw 'oops'` throws a string with no stack; always throw `Error` objects. In TypeScript, a caught
value is `unknown`, because anything can be thrown. An error in `finally` replaces the original error.

</Level>

<Level name="Corner cases">

A `catch` that shows "Network error" for every failure, plus a bug in my own parsing code: the real
cause is hidden under a misleading message. Catch narrowly and include the original as `cause`.

</Level>

<Level name="Production level">

Users see a short, actionable message; logs get the full error with context. Global handlers
(`window.onerror`, `unhandledrejection`) catch the rest, and Phase 4's error tracking reports them.

</Level>

<Level name="Mindset">

An error message is a letter to the person debugging. Write it for them: what failed, with which
input, and what to try.

</Level>

<Level name="System design">

Decide per layer: recover, translate or propagate. The API in Phase 3 uses the same decision to map
domain errors to status codes.

</Level>

<Level name="Strategy">

The plan's proof asks me to debug a broken app from the console. Done when I can read any stack trace
to the line that caused it, and every error path in the app shows the user something and logs the
cause.

</Level>

```js
function load() {
```

<Levels label="Phase 1, TypeScript annotations">

<Level name="Beginner">

TypeScript is JavaScript plus a type checker. An annotation says what type a variable, parameter or
return value is, and the checker reports code that breaks the promise before it runs.

```ts
function total(prices: number[]): number {
  return prices.reduce((sum, p) => sum + p, 0);
}
total(['3', 4]);
// error TS2322: Type 'string' is not assignable to type 'number'.
```

Mistake: thinking the types run in the browser. Fix: they are erased; validation at runtime is a
separate job (see `unknown` below).

</Level>

<Level name="Intermediate">

Describe object shapes with `type` or `interface`, optional properties with `?`, read-only ones with
`readonly`, and function types.

```ts
type Todo = { readonly id: number; text: string; done: boolean; due?: string };
type Filter = (todo: Todo) => boolean;
const open: Filter = (t) => !t.done;
```

The site's note on <a href={withBase('/posts/typescript/02/')}>interface against type</a> covers when
each fits; for this app either works.

</Level>

<Level name="Advanced">

TypeScript is structural: a value fits a type if it has the right shape, whatever it was called.
Excess property checks apply only to fresh object literals. Literal types (`'all'`) are narrower than
`string`; `as const` keeps literals narrow and readonly.

```ts
const point = { x: 1, y: 2, z: 3 };
const p: { x: number; y: number } = point;       // fine: structural
const q: { x: number; y: number } = { x: 1, y: 2, z: 3 };
// error TS2353: Object literal may only specify known properties, and 'z' does not exist
const filters = ['all', 'open', 'done'] as const; // readonly ['all', 'open', 'done']
```

</Level>

<Level name="Edge cases">

An empty array literal with no annotation is `any[]` evolving, or `never[]` in some positions, so
pushing into it later gives confusing errors; annotate `const items: Todo[] = []`. Optional `due?:
string` is `string | undefined`, and with `exactOptionalPropertyTypes` setting it to `undefined`
explicitly is an error.

</Level>

<Level name="Corner cases">

Structural typing plus two types with the same shape: a `UserId` and an `OrderId` that are both
`string` are interchangeable, so passing the wrong one compiles. A branded type
(`string & { readonly brand: 'UserId' }`) makes them distinct.

</Level>

<Level name="Production level">

Types are documentation that cannot go stale, and the safety net for refactors: rename a field and the
compiler lists every place to update. They do not replace tests, which check behaviour.

</Level>

<Level name="Mindset">

Write types for the boundaries (function signatures, data shapes) and let inference handle the inside.

</Level>

<Level name="System design">

Shared types between client and server (Phase 3) make the API contract checkable in both places.

</Level>

each annotation protects against.

<Levels label="Phase 1, unions">

<Level name="Beginner">

A union type says a value is one of several types: `string | number`, or one of several exact strings.

</Level>

<Level name="Intermediate">

On a union, I can only use what every member has, until I narrow it. Discriminated unions put a shared
literal field on each member, which is the clean way to model fetch state.

```ts
type Load =
  | { status: 'loading' }
  | { status: 'error'; message: string }
  | { status: 'success'; todos: Todo[] };
function view(s: Load) {
  if (s.status === 'error') return s.message;   // message exists only here
  if (s.status === 'success') return s.todos.length;
  return 'Loading...';
}
```

</Level>

<Level name="Advanced">

Exhaustiveness: in a `switch` over the discriminant, assigning the leftover to `never` makes adding a
new member a compile error everywhere it is not handled. See the
<a href={withBase('/posts/typescript/11/')}>discriminated unions</a> note.

```ts
function assertNever(x: never): never { throw new Error(`Unhandled: ${JSON.stringify(x)}`); }
switch (s.status) { case 'loading': ...; case 'error': ...; case 'success': ...; default: assertNever(s); }
```

</Level>

<Level name="Edge cases">

`string | 'open'` collapses to `string`, losing autocompletion. A union of arrays `string[] | number[]`
is not the same as `(string | number)[]`; methods like `map` on the former can be awkward to call.

</Level>

<Level name="Corner cases">

Separate booleans `isLoading` and `isError` allow impossible combinations (both true, or loading with
stale data and an error). Two flags meeting is the corner; a single union removes it.

</Level>

<Level name="Production level">

Modelling states as unions removes a whole class of UI bugs, and the compiler points at every screen
that must handle a new state.

</Level>

<Level name="Mindset">

Make impossible states impossible to write.

</Level>

<Level name="System design">

The same unions describe API responses, event types in logs, and database enums. They are the
vocabulary of the domain.

</Level>

<Level name="Strategy">

Replace every boolean flag pair in the app with a union. Done when the fetch state is a discriminated
union and the `switch` is exhaustive.

</Level>

</Levels>

#### Phase 1: Narrowing

<Flow
  caption="Each check removes possibilities. After the last one, only one type is left."
  steps={['value: string | number | null', 'if value === null: return', 'typeof value === string?', 'yes: string here', 'else: number here']}
/>

<Levels label="Phase 1, narrowing">

<Level name="Beginner">

Narrowing is TypeScript following my checks: inside `if (typeof x === 'string')`, `x` is a string. The
<a href={withBase('/posts/typescript/08/')}>narrowing note</a> walks the real bugs.

```ts
function label(x: string | number) {
  if (typeof x === 'string') return x.toUpperCase();
  return x.toFixed(2);
}
```

Mistake: casting with `as string` instead of checking. Fix: check, and let the compiler narrow.

</Level>

<Level name="Intermediate">

Narrowing tools: `typeof`, `instanceof`, `in`, equality with literals, truthiness, `Array.isArray`, and
the discriminant of a union. Custom type guards return `x is T`.

```ts
function isTodo(v: unknown): v is Todo {
  return typeof v === 'object' && v !== null && 'id' in v && 'text' in v;
}
```

</Level>

<Level name="Advanced">

Control-flow analysis tracks assignments and early returns. Narrowing is reset across function
boundaries: a callback does not know that a `let` variable was checked outside, because it might run
later after a reassignment. `const` keeps narrowing in callbacks.

```ts
let current: Todo | undefined = find();
if (current) items.forEach(() => current.text);
// error TS18048: 'current' is possibly 'undefined'.
```

</Level>

<Level name="Edge cases">

Truthiness narrowing drops `0` and `''` along with `null`: `if (count)` skips a real zero. Use
`count !== undefined`. `typeof null === 'object'`, so an object check needs `&& v !== null`.

</Level>

<Level name="Corner cases">

A custom type guard that lies (returns true without checking every field) plus later code trusting it:
the compiler believes the guard, so the bug is invisible to it. Guards must be tested.

</Level>

<Level name="Production level">

Narrowing at the boundary, once, then passing a precise type inward keeps the rest of the code free of
defensive checks.

</Level>

<Level name="Mindset">

The compiler is a reader of my `if` statements. If it cannot follow my reasoning, a human reviewer
probably cannot either.

</Level>

<Level name="System design">

Validation libraries (Zod in Phase 3) are generated type guards; the boundary pattern scales from a
function to an API.

</Level>

<Level name="Strategy">

Remove every `as` cast from the ported app by adding checks. Done when I can name the narrowing tool for
any union I meet and explain the callback reset.

</Level>

</Levels>

#### Phase 1: Generics

<Figure art={`
  function first<T>(items: T[]): T | undefined

  first([1, 2, 3])        T = number   ->  number | undefined
  first(['a', 'b'])       T = string   ->  string | undefined
  first(todos)            T = Todo     ->  Todo | undefined
`} caption="A generic is a type parameter: the same function, with the type filled in at each call." />

<Levels label="Phase 1, generics">

<Level name="Beginner">

A generic lets a function or type work for many types while keeping the link between input and output.
The <a href={withBase('/posts/typescript/09/')}>generics note</a> sticks to the ones I actually use.

```ts
function first<T>(items: T[]): T | undefined { return items[0]; }
const n = first([1, 2]);   // number | undefined
```

Mistake: `function first(items: any[]): any`, which forgets everything. Fix: a type parameter.

</Level>

<Level name="Intermediate">

Constraints restrict what `T` can be; `keyof` links a key to its object.

```ts
function byId<T extends { id: number }>(items: T[], id: number): T | undefined {
  return items.find((i) => i.id === id);
}
function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map((i) => i[key]);
}
pluck(todos, 'text');  // string[]
pluck(todos, 'nope');  // error TS2345: Argument of type '"nope"' is not assignable to parameter of type 'keyof Todo'.
```

</Level>

<Level name="Advanced">

Generic types (`type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E }`),
defaults, inference from arguments, and generic React components later. TypeScript infers `T` from the
call; explicit `first<number>(...)` is rarely needed.

</Level>

<Level name="Edge cases">

A type parameter used only once is pointless: `function f<T>(x: T): void` is just `unknown`. Inference
from an empty array gives `never[]`, so `first([])` is `undefined`-typed oddly.

</Level>

<Level name="Corner cases">

`T extends object` plus a `null` argument fails, which is right; `T extends {}` allows primitives,
which surprises people. Two inferred candidates for `T` (`pair(1, 'a')`) produce `string | number` or an
error depending on positions.

</Level>

<Level name="Production level">

Use generics for containers and helpers (results, caches, API clients), not to show off. A generic
signature that needs a paragraph to read is a smell.

</Level>

<Level name="Mindset">

A generic preserves information the caller already has. If it is not preserving anything, remove it.

</Level>

<Level name="System design">

A typed API client `getJSON<T>(url)` is only as honest as the validation behind it; generics carry
types, they do not check data.

</Level>

<Level name="Strategy">

Write `groupBy`, `byId` and `pluck` generically, with tests. Done when each generic's parameters are
inferred at every call site.

</Level>

</Levels>

The plan's build: add, delete, filter, search and `localStorage`, no framework. Start with HTML for a
form and a list, then one array in memory and one `render()` that rebuilds the list from it.

```js
let todos = load();
let filter = 'all';
let query = '';
function render() {
  const visible = todos
    .filter((t) => filter === 'all' || (filter === 'done') === t.done)
    .filter((t) => t.text.toLowerCase().includes(query.toLowerCase()));
  list.replaceChildren(...visible.map(renderItem));

```

Mistake: keeping state in the DOM (reading checkboxes to find what is done). Fix: the array is the
truth; the DOM is drawn from it.

</Level>

<Level name="Intermediate">

Every state change goes through one function that updates, saves and renders, so no path forgets a
step.

```js
function setState(change) {
  todos = change(todos);
  save(todos);
  render();
}
const addTodo = (text) => setState((ts) => [...ts, { id: Date.now(), text, done: false }]);
const removeTodo = (id) => setState((ts) => ts.filter((t) => t.id !== id));
const toggleTodo = (id) => setState((ts) => ts.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
```

</Level>

render on every keystroke. Put pure logic (filtering, searching) in a module with no DOM, so it can be
tested.

</Level>

<Level name="Edge cases">

Empty text, only spaces, a 5,000-character todo, emoji, a search with regex characters like `(` or `.`
(using `includes` avoids the regex trap), zero todos, a filter that matches nothing (show "No done
tasks yet", not a blank).

</Level>

<Level name="Corner cases">

duplicate ids, so delete removes both. Use `crypto.randomUUID()`. Search active plus delete: the
deleted item vanishes and the empty state must reappear if it was the last match.

</Level>

<Level name="Production level">

and is deployed like the Phase 0 page. The README says how to run it and lists known limits.

</Level>

<Level name="Mindset">

</Level>

<Level name="System design">

This is a tiny architecture: state, pure logic, rendering, persistence, each in its own module. The

</Level>

<Level name="Strategy">

One feature a week, in the order add, delete, filter, search, persist, fetch seed data. Done when it is
deployed and I can explain every function in it.

</Level>

<Levels label="Phase 1, debugging from the console and the bug log">

<Level name="Beginner">

The proof says: debug a broken app from the console. Start with the red error, click the file and line,
and look at the values there. `console.log` with labels, `console.table` for arrays of objects.

```js
console.table(todos);
console.log({ filter, query, visibleCount: visible.length });
```

The bug log is one markdown file with four fields per bug.

```md
## 2026-10-23: deleting one todo deleted two
Error: no error; two items vanished.
Cause: ids from Date.now() collided on a double add.
Fix: crypto.randomUUID().
Rule: ids come from a generator meant for ids, never from time.
```

</Level>

<Level name="Intermediate">

Breakpoints beat logs for "why is this value wrong": add `debugger;` or click a line number in Sources,
then step over, into and out, and watch variables. Conditional breakpoints pause only when, say,
`id === 3`.

</Level>

<Level name="Advanced">

Bisect the cause: comment out half, or `git bisect` across commits, to find where it broke. Event
listener breakpoints pause on any click. "Pause on caught exceptions" finds errors swallowed by a
`catch`.

</Level>

<Level name="Edge cases">

A bug that disappears when DevTools is open (timing or cache). A bug only on the deployed site (base
path, case-sensitive file names, from Phase 0).

</Level>

<Level name="Corner cases">

`console.log(obj)` shows the object live: expanding it later shows current values, not values at log
time. Log `structuredClone(obj)` or `JSON.stringify(obj)` to freeze it.

</Level>

<Level name="Production level">

The log becomes the source of notes on this site, which is how this whole blog started.

</Level>

<Level name="Mindset">

Fix the cause, not the symptom: rule 6. The rule line in the log is the part that prevents the next bug.

</Level>

<Level name="System design">

The same loop runs on production incidents in Phase 4, with logs and traces instead of a console.

</Level>

<Level name="Strategy">

Have someone (or a script) break my app in three ways I do not know. Done when I find all three from the
console alone and the log has at least twenty entries.

</Level>

</Levels>

<Levels label="Phase 1, the gate">

<Level name="Beginner">

Gate 1: build a todo app from scratch, no framework. Pass: it works, persists, and I can explain every
function. Ship: a vanilla app, no framework. I start from an empty folder, with no notes open.

</Level>

<Level name="Intermediate">

Timebox it to one sitting. Afterwards I write a short explanation per function: what it takes, what it
returns, what side effects it has.

</Level>

<Level name="Advanced">

The AI-assisted half of the gate: ask a model "what is wrong with this function?" for each module, then
verify every point it raises and reject the wrong ones with a reason.

</Level>

<Level name="Edge cases">

The rebuilt app must handle the edge inputs from the build topic without looking them up.

</Level>

<Level name="Corner cases">

Explaining a function I wrote but cannot justify a line of means I copied it from memory without
understanding; that line goes in the bug log as a gap.

</Level>

<Level name="Production level">

The deployed app, the tested utility module and the strict TypeScript port are linked from the README.

</Level>

<Level name="Mindset">

If I cannot pass the gate, the next phase will not fix it. Go back.

</Level>

<Level name="System design">

Phase 2 rebuilds this app's ideas in React; anything shaky here becomes a React bug there.

</Level>

<Level name="Strategy">

Done when I pass the gate cold, explain closures, `this` and the event loop without notes, debug a
broken app from the console, and the code has no `any` and no unexplained casts.

</Level>

</Levels>
