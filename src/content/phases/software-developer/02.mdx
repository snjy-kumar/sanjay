One idea carries the whole phase: UI is a function of state. I write what the screen should look like for
a given state; React works out what changed and patches the DOM. Almost every bug in this phase, a stale
value, a double fetch, a list that scrambles, a re-render storm, comes from forgetting where a piece of state
lives or when a render happens. So each topic below starts from that loop and traces it with real output.

<Levels label="Phase 2, components and props">

<Level name="Beginner">

A component is a function that takes one object, its props, and returns JSX, a description of what to show.
JSX is not HTML; it compiles to function calls. This:

```tsx
<ProductCard title="Lamp" price={1299} />
```

becomes, roughly, `jsx(ProductCard, { title: 'Lamp', price: 1299 })`. React calls `ProductCard` with that object and
uses what it returns. That is why component names start with a capital letter: lowercase tags (`div`, `article`) are
treated as HTML elements, capitalised ones as my functions.

```tsx
type CardProps = { title: string; price: number };

export function ProductCard({ title, price }: CardProps) {
  return (
    <article className="card">
      <h3>{title}</h3>
      <p>₹{price.toLocaleString('en-IN')}</p>
    </article>
  );
}
```

Curly braces in JSX switch to JavaScript: `{title}` inserts a value, `{price.toLocaleString('en-IN')}` a computed one.
Rendered with `price={129900}`, the paragraph shows `₹1,29,900`.

Common mistake: changing a prop inside the component (`props.price = 0`). Props belong to the parent; the component
only reads them. If a value needs to change over time inside the component, that is state, the next topic.

</Level>

<Level name="Intermediate">

Children are a prop too. Whatever I put between the tags arrives as `children`, which makes wrapper components
simple:

```tsx
function Panel({ title, children }: { title: string; children: React.ReactNode }) {
  return (
    <section aria-labelledby="panel-title">
      <h2 id="panel-title">{title}</h2>
      {children}
    </section>
  );
}

<Panel title="Filters"><PriceFilter /><BrandFilter /></Panel>
```

Callbacks are how a child talks to its parent. The parent owns the data and passes down a function; the child calls it:

```tsx
function ProductCard({ product, onAdd }: { product: Product; onAdd: (id: string) => void }) {
  return <button onClick={() => onAdd(product.id)}>Add {product.title}</button>;
}
```

The child does not know what "add" does; it only reports the event. That separation is what lets the same card work in
the catalog and in search results.

Mistake: `onClick={onAdd(product.id)}`. That calls `onAdd` during render (adding every product to the cart on every
render) and passes its return value as the handler. Pass a function: `onClick={() => onAdd(product.id)}`.

</Level>

<Level name="Advanced">

A good component boundary follows a reason to change. I split when a piece has its own state, its own reuse, or is big
enough that reading it needs a scroll. I do not split just because JSX is long; a 60-line component that reads top to bottom
is easier than six 10-line ones that pass eight props each.

Prop design is API design. Prefer a few meaningful props over many booleans: `variant="danger"` instead of
`isRed isBold hasBorder`. Boolean props combine into impossible states (`isLoading` and `isError` both true); a union type
prevents them:

```tsx
type ButtonProps = React.ButtonHTMLAttributes<HTMLButtonElement> & { variant?: 'primary' | 'secondary' | 'danger' };

export function Button({ variant = 'primary', className, ...rest }: ButtonProps) {
  return <button className={`btn btn-${variant} ${className ?? ''}`} {...rest} />;
}
```

Spreading `...rest` onto the real element means `type`, `disabled`, `aria-*` and `onClick` all work without me listing
them, and TypeScript checks them.

</Level>

<Level name="Edge cases">

Conditional rendering with `&&` and a number: `{items.length && <List />}` renders `0` on screen when the list is empty,
because `0` is a valid React child. Use `{items.length > 0 && <List />}`. Returning `undefined` from a component was an
error in older React; return `null` to render nothing. A prop named `key` or `ref` is not passed to the component as a
normal prop (in older React `ref` needs `forwardRef`; in React 19 it can be a prop).

</Level>

<Level name="Corner cases">

Prop drilling: a value passed through four components that do not use it, only to reach the fifth. It is not a bug,
but every intermediate component now has to change when the value changes. Composition (pass the finished child down)
usually fixes it before context is needed; both topics come later. Default values in destructuring only apply to
`undefined`, not `null`: `({ size = 'md' })` with `size={null}` gives `null`.

</Level>

<Level name="Production level">

Components in a real codebase have typed props, sensible defaults, pass through native attributes where they wrap a
native element, and are exported from a folder with a story or gallery entry. Names say what they are in the product
(`ProductCard`), not how they look (`BlueBox`).

</Level>

<Level name="Mindset">

A component is a promise: given these props, I render this. The fewer and clearer the props, the easier the promise is
to keep.

</Level>

<Level name="System design">

The component tree is the architecture of the front end. Where I draw boundaries decides where state lives, what can be
reused, and what has to change together. I sketch the tree on paper for each page before coding it.

</Level>

<Level name="Strategy">

I port the Phase 1 todo app to React: one component per concern (input, list, item, filter bar), all typed, callbacks for
every event, no state yet beyond the top.

Done when I can sketch any screen as a tree, say what props each node gets and which callbacks go up, and the port runs
with no type errors and no prop mutated anywhere.

</Level>

</Levels>

#### Phase 2: State

<Flow
  caption="What happens when a setter runs: React does not change the variable, it schedules a new render with a new snapshot"
  steps={['Event handler calls setCount(count + 1)', 'React queues the update', 'Handler finishes; count is still the old value here', 'React re-renders Counter', 'useState returns the new value', 'New JSX committed to the DOM']}
/>

<Levels label="Phase 2, state">

<Level name="Beginner">

State is data a component remembers between renders and that changes the output when it changes. `useState` gives the
current value and a setter:

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Clicked {count} times</button>;
}
```

Why not a normal variable? A `let count = 0` inside the function is reset to 0 every time React calls the function, and
changing it does not tell React to render again. `useState` stores the value outside the function, keyed to this
component's position in the tree, and the setter asks for a re-render.

Mistake: mutating state directly.

```tsx
const [todos, setTodos] = useState<Todo[]>([]);
todos.push(newTodo);      // the array changed, but React was not told
setTodos(todos);          // same array reference: React sees no change and may skip the render
```

The fix is a new array: `setTodos([...todos, newTodo])`.

</Level>

<Level name="Intermediate">

State is a snapshot. Inside one render, `count` is a constant. This surprises everyone once:

```tsx
function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
  console.log(count);
}
```

```text
0          logged, because this render's count is 0
1          shown after the render, not 3
```

All three calls computed `0 + 1`. To build on the previous value, pass an updater function, which React runs with the
latest queued value:

```tsx
setCount(c => c + 1); setCount(c => c + 1); setCount(c => c + 1);   // 3
```

Updates for objects and arrays are immutable by convention: copy, then change the copy.

```tsx
setUser(u => ({ ...u, address: { ...u.address, city: 'Pune' } }));
setTodos(ts => ts.map(t => (t.id === id ? { ...t, done: !t.done } : t)));
setTodos(ts => ts.filter(t => t.id !== id));
```

</Level>

<Level name="Advanced">

Where state lives is the key decision. Put it in the lowest component that contains every component that reads it.
Two siblings that need the same value: lift it to their parent and pass it down. Lifting too high (everything in `App`)
makes every change re-render everything and makes components impossible to reuse; the
<a href={withBase('/posts/react/04/')}>lifting state too early</a> note is that mistake in detail.

When several values change together through named actions, `useReducer` makes the transitions explicit and testable
without rendering:

```tsx
type Action = { type: 'added'; text: string } | { type: 'toggled'; id: string } | { type: 'removed'; id: string };

function todosReducer(state: Todo[], action: Action): Todo[] {
  switch (action.type) {
    case 'added':   return [...state, { id: crypto.randomUUID(), text: action.text, done: false }];
    case 'toggled': return state.map(t => (t.id === action.id ? { ...t, done: !t.done } : t));
    case 'removed': return state.filter(t => t.id !== action.id);
  }
}

const [todos, dispatch] = useReducer(todosReducer, []);
dispatch({ type: 'added', text: 'Buy milk' });
```

The reducer is a pure function, so I can unit test it with plain inputs and outputs:
`todosReducer([], { type: 'added', text: 'x' })` returns a one-item array, no rendering needed.

</Level>

<Level name="Edge cases">

State resets when a component's position or type in the tree changes. Rendering `{isEdit ? <Form /> : <Form />}` keeps the
same state (same type, same position), which surprises people; rendering a different component, or giving a different `key`,
resets it. That is also the tool: `<ProfileForm key={userId} />` resets the form when the user changes.

</Level>

<Level name="Corner cases">

Initial state from a prop: `useState(props.initialName)` only uses the prop on the first render; later prop changes are
ignored. Name it `initialX` so the behaviour is obvious, or use a `key` to reset. An expensive initial value
(`useState(parseBigFile())`) recomputes on every render even though it is used once; pass a function,
`useState(() => parseBigFile())`.

</Level>

<Level name="Production level">

State is minimal (nothing that can be computed), typed, colocated with the component that uses it, and transitions with more
than two related values use a reducer with tests. Server data is not hand-managed with `useState` at all in larger apps; a
data library (TanStack Query, a router loader) owns caching and refetching.

</Level>

<Level name="Mindset">

Every piece of state is a question: what is the smallest set of facts from which the whole screen can be drawn?

</Level>

<Level name="System design">

There are kinds of state: UI state (is this menu open), form state, URL state (filters, page), server state (records), and
shared client state (the signed-in user). Each has a natural home: component, form library, URL, data cache, context. Putting
each in its home prevents most state bugs before they start.

</Level>

<Level name="Strategy">

In the todo port I write down every piece of state, where it lives and why, convert the todo list to a reducer with unit tests,
and trace the snapshot example in the console.

Done when I can predict the logged and shown values for the triple-setter example, every update is immutable, and the reducer
tests pass without rendering anything.

</Level>

</Levels>

<Levels label="Phase 2, derived state">

<Level name="Beginner">

Derived state is any value that can be computed from other state or props: the filtered list from the full list and the
search query, the cart total from the cart, "is the form valid" from the fields. The plan's first trap is storing it.
Compute it during render instead:

```tsx
function Catalog({ products }: { products: Product[] }) {
  const [query, setQuery] = useState('');
  const visible = products.filter(p => p.title.toLowerCase().includes(query.toLowerCase()));
  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} aria-label="Search" />
      <p>{visible.length} of {products.length}</p>
      <ProductList products={visible} />
    </>
  );
}
```

Typing "la" with products Lamp, Laptop and Chair renders `2 of 3`. There is no `visible` state to keep in sync.

</Level>

<Level name="Intermediate">

The broken version and its trace:

```tsx
const [query, setQuery] = useState('');
const [visible, setVisible] = useState(products);
useEffect(() => {
  setVisible(products.filter(p => p.title.toLowerCase().includes(query.toLowerCase())));
}, [query]);           // products missing from deps
```

```text
type "la"      render 1: visible = old list (wrong for one frame)
               effect: setVisible(filtered)
               render 2: visible = 2 items
products prop updates from the server
               render: visible still the old filtered list, because the effect only watches query
```

Two renders per keystroke, a flash of wrong data, and a stale list when the other input changes. The
<a href={withBase('/posts/react/01/')}>derived state note</a> walks this exact bug. The fix deletes the state and the effect.

</Level>

<Level name="Advanced">

If the computation is genuinely expensive (thousands of items, a sort with a heavy comparator) and measured as slow, memoise
it rather than storing it:

```tsx
const visible = useMemo(() => filterAndSort(products, query, sort), [products, query, sort]);
```

That is still derived: React recomputes when any input changes. The test is the Profiler, not intuition; most filters over a
few hundred items take well under a millisecond.

Derived state also covers "selected item": store `selectedId`, derive `selected = items.find(i => i.id === selectedId)`. Storing
the whole selected object goes stale when the item is edited in the list.

</Level>

<Level name="Edge cases">

When the derived value depends on a prop that should reset some state (a new product list should clear the selection), the
answer is usually a `key` on the component or storing an ID that naturally becomes invalid, not an effect that resets state
after the fact.

</Level>

<Level name="Corner cases">

Sometimes a value really is state even though it looks derived: a "draft" copy of a record the user edits before saving. It
starts from props but then diverges on purpose. Name it `draft`, initialise it once (or by key), and keep the original
separately so "discard changes" works.

</Level>

<Level name="Production level">

In code review I look for `useState` paired with a `useEffect` that only calls its setter: that pattern is almost always derived
state and gets flagged. Lint rules and the React docs' "You might not need an effect" page give the team a shared vocabulary.

</Level>

<Level name="Mindset">

A single source of truth is not a slogan; it is the reason the screen cannot disagree with itself.

</Level>

<Level name="System design">

The same rule holds at every scale: in databases (normalisation), in caches (derived from a source and invalidated), in URL
state (filters in the URL, results derived from it). Storing a copy is a decision to own the job of keeping it in sync.

</Level>

<Level name="Strategy">

I search the port and the dashboard for every state variable and ask "can this be computed?", delete the ones that can, and
time the remaining expensive computations before memoising any.

Done when no state can be computed from other state, the search, filter and totals all derive during render, and I can fix a
planted derived-state bug in minutes, which is part of Gate 2.

</Level>

</Levels>

#### Phase 2: Effects, and when not to use them

<Flow
  caption="An effect's life: it runs after the commit, cleans up before the next run, and cleans up for good on unmount"
  steps={['Render and commit', 'Browser paints', 'Effect runs (deps changed)', 'Next render with new deps', 'Cleanup of the previous effect', 'Effect runs again', 'Unmount: final cleanup']}
/>

<Levels label="Phase 2, effects and when not to use them">

<Level name="Beginner">

An effect synchronises a component with something outside React: a network request, a subscription, a timer, a browser API,
the document title. It runs after React has updated the screen.

```tsx
useEffect(() => {
  document.title = `${count} new messages`;
}, [count]);
```

The dependency array lists every value from the component the effect uses. React compares each one with the last render
(`Object.is`) and reruns the effect only if one changed. No array means "after every render"; an empty array means "after the
first render only".

The plan's trap is using `useEffect` as an event handler. If something happens because the user clicked, do it in the click
handler:

```tsx
// wrong: an effect watching state that the click set
useEffect(() => { if (submitted) { post(form); } }, [submitted]);
// right
async function handleSubmit() { await post(form); }
```

The <a href={withBase('/posts/react/02/')}>useEffect used as an event handler</a> note is the full story.

</Level>

<Level name="Intermediate">

Cleanup undoes what the effect did. It runs before the effect runs again and when the component unmounts:

```tsx
useEffect(() => {
  const id = setInterval(() => setNow(Date.now()), 1000);
  return () => clearInterval(id);
}, []);
```

Fetching in an effect needs cleanup too, or a slow response for an old query overwrites a fast response for the new one:

```tsx
useEffect(() => {
  const controller = new AbortController();
  setStatus('loading');
  fetch(`/api/products?q=${encodeURIComponent(q)}`, { signal: controller.signal })
    .then(r => (r.ok ? r.json() : Promise.reject(new Error(`HTTP ${r.status}`))))
    .then(data => { setProducts(data); setStatus('success'); })
    .catch(err => { if (err.name !== 'AbortError') setStatus('error'); });
  return () => controller.abort();
}, [q]);
```

```text
type "la" -> request A starts
type "lam" -> cleanup aborts A; request B starts
B resolves -> products for "lam"   (A can never overwrite it)
```

</Level>

<Level name="Advanced">

In development with Strict Mode, React mounts, unmounts and remounts each component once, so every effect runs, cleans up,
and runs again. It is deliberate: an effect that breaks when run twice (a double subscription, a double POST) has a missing
cleanup that would also bite in production. The fix is cleanup, never disabling Strict Mode.

The list of things that are not effects, from the React docs: computing values (derived state), handling user events
(handlers), resetting state when a prop changes (a `key`), notifying the parent (call its callback in the handler that caused the
change), and chains of effects that set state that triggers other effects (compute it all in one handler).

</Level>

<Level name="Edge cases">

Objects and functions in the dependency array are new on every render, so the effect reruns every render:

```tsx
const options = { q, limit: 20 };
useEffect(() => { search(options); }, [options]);     // runs every render
```

Depend on the primitives (`[q]`) and build the object inside the effect. Leaving a dependency out to stop the reruns creates a
stale closure instead; the lint rule `react-hooks/exhaustive-deps` catches both.

</Level>

<Level name="Corner cases">

An effect that sets state unconditionally with a dependency that the state change affects loops forever:

```text
Warning: Maximum update depth exceeded. This can happen when a component calls setState inside useEffect,
but useEffect either doesn't have a dependency array, or one of the dependencies changes on every render.
```

Reading the newest value of something inside an effect without making it a dependency (a callback prop used in a
subscription) is a real need; the pattern is to keep the latest callback in a ref, or React's `useEffectEvent` where available.

</Level>

<Level name="Production level">

Server data is fetched through a data library or the router's loaders, which handle caching, deduplication, cancellation and
refetching, so hand-written fetch effects are rare. The exhaustive-deps lint rule is an error, not a warning, and every
suppression has a comment explaining why.

</Level>

<Level name="Mindset">

Before writing `useEffect`, I ask what external system I am synchronising with. If the answer is "none", it is not an effect.

</Level>

<Level name="System design">

Effects are where a component touches the world, so they are where races, leaks and duplicates live. Keeping them few and at
the edges (custom hooks, data layers) keeps the rest of the UI pure and easy to test.

</Level>

<Level name="Strategy">

I list every effect in the port, classify each (external sync or not), delete the ones that are not, add cleanup to the rest, and
reproduce the fetch race with a throttled network in DevTools before fixing it.

Done when every remaining effect names its external system, has a cleanup where needed, runs correctly twice in Strict Mode, and
the race cannot be reproduced.

</Level>

</Levels>

#### Phase 2: The rules of hooks

<Figure art={`

<Levels label="Phase 2, the rules of hooks">

<Level name="Beginner">

Two rules. Call hooks only at the top level of a component or custom hook, never inside conditions, loops or nested functions.
Call them only from React function components or custom hooks, never from plain functions or class components.

```tsx
// wrong
if (user) { const [draft, setDraft] = useState(user.name); }
// right
const [draft, setDraft] = useState(user?.name ?? '');
if (!user) return <SignIn />;
```

The reason is in the figure: React stores each component's hook data in a list and hands it back by position. If the number or
order of calls changes between renders, values go to the wrong hooks. React detects some of this and throws:

```text
Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.
```

</Level>

<Level name="Intermediate">

An early return before a hook is the most common violation, because it looks harmless:

```tsx
function Profile({ user }) {
  if (!user) return null;               // hooks below run only sometimes
  const [tab, setTab] = useState('posts');
}
```

Move every hook above the first return. The ESLint plugin `eslint-plugin-react-hooks` enforces both rules; it is part of every
project from day one.

Custom hooks are functions whose names start with `use` and that call other hooks. They are how logic is reused:

```tsx
function useLocalStorage<T>(key: string, initial: T) {
  const [value, setValue] = useState<T>(() => {
    const raw = localStorage.getItem(key);
    return raw === null ? initial : (JSON.parse(raw) as T);
  });
  useEffect(() => { localStorage.setItem(key, JSON.stringify(value)); }, [key, value]);
  return [value, setValue] as const;
}
```

Each component that calls `useLocalStorage` gets its own state; a custom hook shares logic, not state.

</Level>

<Level name="Advanced">

The `use` prefix is not decoration; the lint rule uses it to know which functions follow hook rules. A function that calls no
hooks should not start with `use`. Custom hooks are the right home for effects: `useDebouncedValue`, `useOnlineStatus`,
`useProducts(query)`. Components then read like a description of what they need, not how it is fetched.

React 19's `use(promise)` and `use(context)` are an exception: `use` may be called conditionally, because it does not store
data by position in the same way. That is a deliberate, documented exception, not a loophole for other hooks.

</Level>

<Level name="Edge cases">

Hooks inside a `.map` over a list break as soon as the list length changes. Move the per-item logic into a child component that
calls the hook once, and render one child per item.

</Level>

<Level name="Corner cases">

A custom hook that returns a new object or function every render causes every consumer's effects and memoised children to rerun.
Stabilise returned functions with `useCallback` and returned objects with `useMemo` when consumers put them in dependency arrays.

</Level>

<Level name="Production level">

The hooks lint rules are errors in CI. Shared custom hooks live in one folder with tests using `renderHook` from Testing Library.

</Level>

<Level name="Mindset">

The rules are not arbitrary style; they follow from how React stores state. Knowing the mechanism makes the rules obvious.

</Level>

<Level name="System design">

Custom hooks are the unit of reusable behaviour in a React codebase, the way modules are in a backend. A good hook has a small,
typed interface and hides its effects.

</Level>

<Level name="Strategy">

I break the rules on purpose in a scratch component, read each error, then extract three custom hooks from the dashboard with
tests.

Done when the lint rule passes with no suppressions, I can explain the call-order mechanism from the figure, and three custom hooks
have `renderHook` tests.

</Level>

</Levels>

<Levels label="Phase 2, lists and keys">

<Level name="Beginner">

Lists render with `map`, and each item needs a `key`, a string or number that identifies that item among its siblings:

```tsx
<ul>
  {todos.map(t => (
    <li key={t.id}>{t.text}</li>
  ))}
</ul>
```

Without a key, React warns in the console:

```text
Warning: Each child in a list should have a unique "key" prop.
```

The key goes on the outermost element returned from the `map` (or on the fragment: `<Fragment key={t.id}>`), not on something
inside it.

Mistake: `key={index}`, or `key={Math.random()}`. The first breaks on reorder and delete (the figure); the second gives every item
a new identity on every render, so React destroys and recreates every row, losing focus and input state.

</Level>

<Level name="Intermediate">

Why keys matter, traced. Each todo row has an uncontrolled text input. I type "x" into the first row, then delete the first todo.
With index keys, React sees keys 0, 1, 2 become 0, 1: it thinks the last item was removed and updates the text of the first two.
The DOM input that held "x" is still at position 0, now labelled "B". With ID keys, React sees `a1` disappear, removes that row's
DOM, and B and C keep theirs. The <a href={withBase('/posts/react/03/')}>missing and unstable list keys</a> note reproduces this
with a sortable table.

Where do IDs come from? From the data (database IDs), or generated once when the item is created (`crypto.randomUUID()` in the
reducer), never during render.

</Level>

<Level name="Advanced">

A key is also a reset button for any component. Changing a component's key makes React treat it as a new component: state is
discarded and effects rerun.

```tsx
<ChatThread key={contactId} contactId={contactId} />
```

Switching contacts now clears the draft message automatically, with no effect needed. Keys only need to be unique among
siblings, not globally.

For long lists (thousands of rows), rendering every row is slow regardless of keys; virtualisation (`@tanstack/react-virtual`)
renders only the visible rows. Measure first: a few hundred simple rows are fine.

</Level>

<Level name="Edge cases">

Duplicate keys (two items with the same ID from a buggy API) make React drop or duplicate rows unpredictably and warn
`Encountered two children with the same key`. Fix the data, or combine fields into a key that is genuinely unique. Index keys are
acceptable for static lists that never reorder, filter or contain state, such as a fixed list of footer links.

</Level>

<Level name="Corner cases">

Filtering a list keeps keys stable (good) but optimistic items created before the server assigns an ID need a temporary client ID,
then a swap to the real ID. If the key changes at the swap, the row remounts and loses focus; keep a stable client key and store the
server ID separately.

</Level>

<Level name="Production level">

The lint rule `react/jsx-key` catches missing keys; review catches index keys on dynamic lists. Lists have empty states, and long
lists are paginated or virtualised.

</Level>

<Level name="Mindset">

A key answers "is this the same thing as last time?". Identity is a property of the data, not of where it sits on screen.

</Level>

<Level name="System design">

Stable identity runs through the whole stack: database primary keys, API IDs, cache keys, React keys. When identity is stable
everywhere, updates, caching and animations just work.

</Level>

<Level name="Strategy">

I reproduce the index-key bug with inputs in rows and a delete button, fix it with IDs, then use a key to reset a form when the
selected record changes.

Done when no dynamic list uses index or random keys, the reproduction shows the bug and the fix side by side, and the key-reset pattern
replaces at least one effect.

</Level>

</Levels>

#### Phase 2: Controlled forms

<Flow
  caption="A controlled input: React state is the single source of truth for what the field shows"
  steps={['User types "a"', 'onChange fires with e.target.value', 'setName("a")', 'Re-render: value="a"', 'Input shows "a"', 'Validation derived from state']}
/>

<Levels label="Phase 2, controlled forms">

<Level name="Beginner">

A controlled input gets its value from state and reports changes through `onChange`:

```tsx
function NameField() {
  const [name, setName] = useState('');
  return (
    <label>
      Name
      <input value={name} onChange={e => setName(e.target.value)} />
    </label>
  );
}
```

React state now decides what the field shows, so I can validate, transform or reset it from code. Wrapping the input in a
`label` (or using `htmlFor` and `id`) also names it for screen readers.

Mistake: `value={name}` with no `onChange`. The field becomes read-only and React warns:

```text
Warning: You provided a `value` prop to a form field without an `onChange` handler.
```

</Level>

<Level name="Intermediate">

A whole form with one state object, derived validation, and a real `form` element so Enter submits:

```tsx
type Fields = { title: string; price: string };

function ProductForm({ onSave }: { onSave: (p: { title: string; price: number }) => Promise<void> }) {
  const [fields, setFields] = useState<Fields>({ title: '', price: '' });
  const [touched, setTouched] = useState<Partial<Record<keyof Fields, boolean>>>({});
  const [status, setStatus] = useState<'idle' | 'saving' | 'error'>('idle');

  const errors = {
    title: fields.title.trim() === '' ? 'Title is required' : undefined,
    price: Number.isNaN(Number(fields.price)) || Number(fields.price) <= 0 ? 'Enter a price above 0' : undefined,
  };
  const valid = !errors.title && !errors.price;

  function update(e: React.ChangeEvent<HTMLInputElement>) {
    setFields(f => ({ ...f, [e.target.name]: e.target.value }));
  }

  async function handleSubmit(e: React.FormEvent) {
    e.preventDefault();
    setTouched({ title: true, price: true });
    if (!valid) return;
    setStatus('saving');
    try { await onSave({ title: fields.title.trim(), price: Number(fields.price) }); setStatus('idle'); }
    catch { setStatus('error'); }
  }

  return (
    <form onSubmit={handleSubmit} noValidate>
      <label htmlFor="title">Title</label>
      <input id="title" name="title" value={fields.title} onChange={update}
        onBlur={() => setTouched(t => ({ ...t, title: true }))}
        aria-invalid={touched.title && !!errors.title} aria-describedby="title-error" />
      {touched.title && errors.title && <p id="title-error" role="alert">{errors.title}</p>}
      {/* price field follows the same pattern */}
      <button type="submit" disabled={status === 'saving'}>{status === 'saving' ? 'Saving…' : 'Save'}</button>
      {status === 'error' && <p role="alert">Could not save. Try again.</p>}
    </form>
  );
}
```

Errors are derived, not stored. They show after a field is touched or on submit, not while the user is still typing the first
character. Input values are always strings; convert at submit.

</Level>

<Level name="Advanced">

Controlled is not always right. For simple forms, uncontrolled inputs read with `FormData` on submit are less code and fewer
renders:

```tsx
function handleSubmit(e: React.FormEvent<HTMLFormElement>) {
  e.preventDefault();
  const data = Object.fromEntries(new FormData(e.currentTarget));
}
```

For big forms, a library (React Hook Form) keeps inputs uncontrolled for speed and adds validation with a Zod schema, the same
schema the API uses in Phase 3. The <a href={withBase('/posts/react/05/')}>controlled inputs done wrong</a> note covers the
switch-between-modes bug and the cursor-jumping bug.

</Level>

<Level name="Edge cases">

`value={undefined}` makes an input uncontrolled; later setting a string makes it controlled, and React warns
`A component is changing an uncontrolled input to be controlled`. Initialise with `''`, never `undefined` or `null`. Number inputs
return strings and an empty string for invalid input; `type="number"` also changes on scroll wheel. Checkboxes use `checked`, not
`value`.

</Level>

<Level name="Corner cases">

Transforming input on every keystroke (forcing uppercase, formatting a phone number) moves the cursor to the end when the
transformed string differs, which is maddening in the middle of a value. Format on blur, or keep the raw value and display a formatted
version separately. Double submit: a fast double click sends two POSTs before `status` updates; disable the button on the first click
and make the server idempotent.

</Level>

<Level name="Production level">

Every field has a visible label, errors are linked with `aria-describedby` and announced, the first invalid field gets focus on submit,
the submit button cannot double-submit, and validation runs again on the server, because client validation is only for the user's
convenience.

</Level>

<Level name="Mindset">

A form is a conversation with the user. Tell them what is wrong, where, and how to fix it, at the moment it helps.

</Level>

<Level name="System design">

Sharing one schema between form and API keeps the rules in one place, and the server remains the authority. Forms are where the UI and
the backend contract meet.

</Level>

<Level name="Strategy">

I build the product form controlled by hand with touched state and derived errors, then rebuild it with React Hook Form and Zod, and
compare code and render counts.

Done when the form works with keyboard only, errors are announced by a screen reader, double submit is impossible, and both versions
pass the same tests.

</Level>

</Levels>

<Figure art={`

        <Nav>

<Levels label="Phase 2, context">

<Level name="Beginner">

Context passes a value deep into the tree without props at every level. Three parts: create it, provide it, read it.

```tsx
type Theme = 'light' | 'dark';
const ThemeContext = createContext<Theme>('light');

function App() {
  const [theme, setTheme] = useState<Theme>('light');
  return (
    <ThemeContext.Provider value={theme}>
      <Layout />
    </ThemeContext.Provider>
  );
}

function NavItem() {
  const theme = useContext(ThemeContext);
  return <a className={`nav-${theme}`}>Home</a>;
}
```

Good uses: the theme, the signed-in user, the locale. Mistake: putting everything in one global context because prop passing felt
tedious. Every reader re-renders on every change, and every component becomes coupled to a global.

</Level>

<Level name="Intermediate">

A custom provider and hook make context safe and readable:

```tsx
type AuthValue = { user: User | null; signIn: (u: User) => void; signOut: () => void };
const AuthContext = createContext<AuthValue | null>(null);

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const value = useMemo(() => ({ user, signIn: setUser, signOut: () => setUser(null) }), [user]);
  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used inside AuthProvider');
  return ctx;
}
```

The default `null` plus the throw turns "forgot the provider" into a clear error instead of `undefined` errors deep in a component.
`useMemo` on the value keeps its identity stable when the provider re-renders for unrelated reasons.

</Level>

<Level name="Advanced">

Every component that reads a context re-renders when the provider's value changes identity, even if it only uses one field. Fixes, in
order: split contexts by how often they change (`AuthUserContext` and `AuthActionsContext`, actions never change); keep fast-changing
values (a mouse position, a text field) out of context; and for genuinely shared, frequently updated client state, a store with
selectors (Zustand, or Redux as in <a href={withBase('/plans/redux/')}>the Redux plan</a>) that re-renders only components whose selected
slice changed.

Before context, try composition: if `Layout` takes `sidebar` and `main` as props (elements), `App` can create `<NavItem theme={theme} />`
itself and the middle layers never see `theme`.

</Level>

<Level name="Edge cases">

A component outside the provider silently gets the default value. A second provider deeper in the tree overrides the outer one for its
subtree, which is useful (a dark section in a light page) and confusing when accidental.

</Level>

<Level name="Corner cases">

`value={{ user, signOut }}` written inline creates a new object every render of the provider, so every reader re-renders whenever the
provider's parent renders, even when `user` did not change. React DevTools' "why did this render" shows "context changed" and that is
the clue; memoise the value.

</Level>

<Level name="Production level">

Contexts are few, each with a custom hook and a provider, and tests render components inside a test provider with known values.
Server data never goes into context by hand; the data library already shares it.

</Level>

<Level name="Mindset">

Context is a dependency injection tool, not a state manager. It answers "how does this value reach there", not "who owns it".

</Level>

<Level name="System design">

Global state is a cost paid by every component that touches it. Choosing between props, composition, context, URL and a store is the
front end's version of choosing module boundaries.

</Level>

<Level name="Strategy">

I add auth and theme contexts with custom hooks, measure renders with the Profiler before and after memoising and splitting, and
remove one context by switching to composition.

Done when each context has a reason, a hook and a test provider, and the Profiler shows a theme toggle does not re-render components
that do not use the theme.

</Level>

</Levels>

#### Phase 2: Memoization

<Flow
  caption="Memoization is a measurement-driven fix, not a default"
  steps={['Feel or see slowness', 'Profiler: record the interaction', 'Find the slow commit and the component', 'Ask why it rendered', 'Fix the cause (state placement, composition)', 'Only then memo, useMemo, useCallback', 'Profile again to confirm']}
/>

<Levels label="Phase 2, memoization">

<Level name="Beginner">

When a component renders, all its children render too, by default. Usually that is fast. Memoization skips work when inputs did not
change: `useMemo` caches a computed value, `useCallback` caches a function, and `React.memo` skips re-rendering a component whose props
are the same as last time.

```tsx
const sorted = useMemo(() => [...products].sort(byPrice), [products]);
const handleAdd = useCallback((id: string) => setCart(c => [...c, id]), []);
const ProductCard = memo(function ProductCard({ product, onAdd }: CardProps) { /* ... */ });
```

The plan's trap is cargo-cult `useMemo`: wrapping everything "for performance". Each memo costs memory, a dependency comparison and
readability, and wrong dependencies create stale values.

</Level>

<Level name="Intermediate">

How to measure. React DevTools, Profiler tab, record, type one character in the search box, stop. Each bar is a commit; each component
shows its render time and, with "Record why each component rendered" enabled, the reason:

```text
Commit 3   14.2 ms
  Catalog          0.4 ms   Hook 1 changed
  ProductList      0.3 ms   Parent rendered
  ProductCard x500 12.9 ms  Parent rendered
```

500 cards re-rendering on every keystroke is worth fixing. A commit under a couple of milliseconds is not.

</Level>

<Level name="Advanced">

`memo` only helps if props are actually stable. The trap inside the trap:

```tsx
<ProductCard product={p} onAdd={id => add(id)} />        // new function every render: memo never skips
<ProductCard product={p} onAdd={handleAdd} />            // stable with useCallback: memo skips
```

So `memo`, `useCallback` and `useMemo` usually come together, or not at all. Often a structural fix is better: move the search state into
`SearchBar` and the list's filtering below it so typing does not re-render the header and cart at all, or pass expensive subtrees as
`children` so they are created by a parent that did not re-render.

The React Compiler, where enabled, inserts this memoisation automatically, which makes hand-written memo even less necessary; the
measuring habit stays.

</Level>

<Level name="Edge cases">

`useMemo` is a performance hint, not a guarantee; React may discard the cache. Never put side effects or correctness logic in it.
Dependencies compared with `Object.is` mean an object prop built inline (`style={{ color }}`) defeats `memo` on every render.

</Level>

<Level name="Corner cases">

`useCallback` with an empty dependency array that reads state captures the first render's value forever, a stale closure. Use the updater
form of the setter (`setCart(c => ...)`) so the callback needs no state dependency, or include the dependency.

</Level>

<Level name="Production level">

Performance budgets for interactions (input responsiveness, INP), profiling before and after any memo in review, and a comment on
non-obvious memos stating what was measured.

</Level>

<Level name="Mindset">

Find out why something renders before deciding it should not. Most slowness is state in the wrong place, not missing memo.

</Level>

<Level name="System design">

Rendering cost scales with what re-renders times how expensive each render is. Architecture (state placement, composition, virtualisation)
changes the first factor; memo changes the second.

</Level>

<Level name="Strategy">

I make a deliberately slow list (500 cards with a costly render), profile, fix it first by moving state, then by memo, and record both
measurements.

Done when every memo in my code has a profiler measurement behind it, and I can read a Profiler recording and say why each component rendered.

</Level>

</Levels>

<Levels label="Phase 2, composition">

<Level name="Beginner">

Composition means building components by putting components inside each other, mainly through `children` and props that take elements.
A `Modal` does not need to know what is inside it:

```tsx
function Modal({ title, onClose, children }: { title: string; onClose: () => void; children: React.ReactNode }) {
  return (
    <div role="dialog" aria-modal="true" aria-labelledby="modal-title">
      <h2 id="modal-title">{title}</h2>
      {children}
      <button onClick={onClose}>Close</button>
    </div>
  );
}

<Modal title="Delete product?" onClose={close}>
  <p>This cannot be undone.</p>
  <Button variant="danger" onClick={confirm}>Delete</Button>
</Modal>
```

The plan's trap: abstracting a component before the second use. The first time, write it inline. The second time, notice. The third
time, extract with the shape both uses actually needed.

</Level>

<Level name="Intermediate">

Slots: when a component has more than one area for content, pass elements as named props.

```tsx
function PageLayout({ sidebar, header, children }: { sidebar: React.ReactNode; header: React.ReactNode; children: React.ReactNode }) {
  return (
    <div className="layout">
      <header>{header}</header>
      <nav aria-label="Sections">{sidebar}</nav>
      <main>{children}</main>
    </div>
  );
}

<PageLayout header={<UserMenu user={user} />} sidebar={<Filters />}>
  <ProductGrid />
</PageLayout>
```

`user` goes straight to `UserMenu`; `PageLayout` never sees it. That is how composition removes prop drilling.

</Level>

<Level name="Advanced">

Compound components share implicit state through a private context, giving callers flexible markup with a coherent API:

```tsx
const TabsContext = createContext<{ active: string; setActive: (id: string) => void } | null>(null);

function Tabs({ defaultTab, children }: { defaultTab: string; children: React.ReactNode }) {
  const [active, setActive] = useState(defaultTab);
  return <TabsContext.Provider value={{ active, setActive }}>{children}</TabsContext.Provider>;
}
function Tab({ id, children }: { id: string; children: React.ReactNode }) {
  const ctx = useContext(TabsContext)!;
  return <button role="tab" aria-selected={ctx.active === id} onClick={() => ctx.setActive(id)}>{children}</button>;
}
```

For complex accessible widgets (tabs, menus, comboboxes) a headless library (Radix, React Aria) provides behaviour and ARIA while I own
the styling; that is composition at library scale.

</Level>

<Level name="Edge cases">

`React.Children.map` and `cloneElement` to inject props into children work, but break when a caller wraps a child in a fragment or
another component. Context-based compound components are more robust.

</Level>

<Level name="Corner cases">

A component accepting both `children` and a `render` prop, or both a slot and a config prop for the same area, has two ways to do one
thing and will be used inconsistently. Pick one per area.

</Level>

<Level name="Production level">

Shared components have a gallery entry per variant, a documented composition API, and no prop that exists for a single caller.

</Level>

<Level name="Mindset">

Duplication is cheaper than the wrong abstraction. Wait until the pattern shows itself.

</Level>

<Level name="System design">

Composition keeps components closed for modification and open for extension: new uses arrive as new children, not new props, so the
shared component stays stable as the product grows.

</Level>

<Level name="Strategy">

I find one over-configured component in the dashboard, rebuild it with slots or compound parts, and fix one prop-drilling path with
composition instead of context.

Done when no shared component has a prop used by only one caller, and the layout no longer receives data it does not render.

</Level>

</Levels>
#### Phase 2: Accessibility

  caption="Accessibility in layers. Each layer is cheaper to get right than to retrofit."

<Levels label="Phase 2, accessibility">

<Level name="Beginner">

Accessibility means people using a keyboard, a screen reader, zoom, or other assistive technology can use the app. Most of it comes
free from the right HTML element. The plan's trap is a wall of `div`s with no landmarks:

```tsx
// wrong: a div pretending to be a button
<div className="btn" onClick={save}>Save</div>
// right
<button type="button" onClick={save}>Save</button>
```

The `div` cannot be reached with Tab, does nothing on Enter or Space, and a screen reader announces it as plain text. The `button`
does all three for free. Landmarks (`header`, `nav`, `main`, `footer`) and headings in order let screen-reader users jump around a page
the way sighted users scan it.

</Level>

<Level name="Intermediate">

The keyboard pass, as a procedure: unplug the mouse; press Tab from the address bar through the whole page; check every interactive
element gets a visible focus ring in a sensible order; operate each with Enter, Space, arrows and Escape; open and close every dialog
and menu. Write down every failure.

The screen-reader pass: VoiceOver on macOS (Cmd+F5) or NVDA on Windows. Navigate by headings (VO+Cmd+H or H), by landmarks, through
forms. Each control should announce a name, a role and a state:

```text
"Search, edit text"
"Sort by price, collapsed, button"
"Title is required, alert"
```

Icon-only buttons need a name: `<button aria-label="Remove Lamp from cart"><TrashIcon aria-hidden="true" /></button>`.

</Level>

<Level name="Advanced">

Focus management in a single-page app: when a route changes, move focus to the new page's `h1` (or announce the title), or keyboard
users stay focused on a link that no longer exists. A modal moves focus into itself on open, keeps Tab inside, closes on Escape, and
returns focus to the button that opened it on close. The native `dialog` element with `showModal()` does most of this.

ARIA's first rule is to not use ARIA if a native element does the job. Wrong ARIA is worse than none: `role="button"` on a `div`
promises keyboard behaviour that I then have to implement by hand.

</Level>

<Level name="Edge cases">

Content that appears asynchronously (search results count, "Saved", an error) is silent to screen readers unless it is in a live region
that existed before the change: `<p aria-live="polite">{count} results</p>`. Colour-only status (a red border for an error) fails for
colour-blind users; add text and an icon.

</Level>

<Level name="Corner cases">

`outline: none` in a CSS reset removes every focus ring. Use `:focus-visible` to show focus for keyboard users without showing it on
mouse clicks. Disabled buttons cannot be focused, so their tooltip explaining why is unreachable; prefer an enabled button that explains
the problem on click, or visible helper text.

</Level>

<Level name="Production level">

Automated checks (axe in Playwright tests, the Lighthouse accessibility audit) catch roughly the mechanical issues: missing names,
contrast, missing labels. They cannot judge whether the experience makes sense, so a manual keyboard and screen-reader pass happens before
each release of a significant UI change.

</Level>

<Level name="Mindset">

Accessibility is not a feature for a few users; it is whether the interface works. Keyboard and screen-reader users find the bugs that
everyone eventually hits.

</Level>

<Level name="System design">

Build accessibility into the design system's components (Button, Dialog, Field) once, and every page that uses them inherits it.
Retrofitting a hundred pages is the expensive alternative.

</Level>

<Level name="Strategy">

I do the keyboard and screen-reader passes on the dashboard and write each failure as an issue, fix them, add axe checks to the end-to-end
tests, and repeat the passes.

Done when the proof holds: a full keyboard pass and a screen-reader pass with no blocking issue, landmarks and heading order correct, and
axe reports zero violations on every page.

</Level>

</Levels>

#### Phase 2: Responsive CSS

<Figure art={`
  320px (phone)           768px (tablet)               1200px (desktop)
  +-----------+           +---------------------+      +-------+--------------------+
  | header    |           | header              |      | head  |                    |
  | [filter v]|           +--------+------------+      +-------+  grid: 4 columns   |
  | card      |           |filters | card card  |      |filters|  card card card .. |
  | card      |           |        | card card  |      |       |                    |
  | card      |           +--------+------------+      +-------+--------------------+
  one column, filters     two areas, 2 columns          sidebar + auto-fill grid
  in a disclosure
`} caption="One layout at three widths. Mobile first: the base CSS is the phone layout, and min-width queries add space." />

<Levels label="Phase 2, responsive CSS">

<Level name="Beginner">

Responsive design means one page works from a small phone to a wide monitor. Three foundations. The viewport meta tag so phones do
not pretend to be desktops: `<meta name="viewport" content="width=device-width, initial-scale=1">`. Fluid units (`%`, `rem`, `fr`)
instead of fixed pixel widths. Media queries for the points where the layout needs to change.

```css
.grid {
  display: grid;
  gap: 1rem;
  grid-template-columns: repeat(auto-fill, minmax(14rem, 1fr));
}
```

That one rule gives one column on a phone and as many 14rem-minimum columns as fit on a desktop, with no media query.

Mistake: designing at desktop width and squeezing it down. Start with the phone layout as the base CSS, then add with `min-width`.

</Level>

<Level name="Intermediate">

Mobile first, with layout areas:

```css
.layout { display: grid; grid-template-areas: "header" "filters" "main"; }
@media (min-width: 48rem) {
  .layout { grid-template-columns: 16rem 1fr; grid-template-areas: "header header" "filters main"; }
}
```

Flexbox for one dimension (a row of buttons that wraps), Grid for two (page layout, card grids). `clamp()` for fluid type that
scales between limits: `font-size: clamp(1rem, 0.9rem + 0.5vw, 1.25rem)`.

Testing: DevTools device toolbar at 320, 375, 768, 1024 and 1440 pixels, and dragging the width slowly to find where things break.
The breakpoints go where the content breaks, not at device names.

</Level>

<Level name="Advanced">

Container queries let a component respond to its own width instead of the viewport, so a `ProductCard` lays out differently in a narrow
sidebar and a wide grid on the same screen:

```css
.card-wrap { container-type: inline-size; }
@container (min-width: 28rem) { .card { display: grid; grid-template-columns: 8rem 1fr; } }
```

Images: `max-width: 100%; height: auto`, explicit `width` and `height` attributes so the browser reserves space (no layout shift),
`srcset` and `sizes` so phones download small files, and `loading="lazy"` below the fold.

</Level>

<Level name="Edge cases">

Long words and URLs overflow narrow containers: `overflow-wrap: anywhere`. A grid item containing a wide table or code block forces the
whole column wider because grid items default to `min-width: auto`; set `min-width: 0` on the item. Touch targets need about 44 by 44
CSS pixels.

</Level>

<Level name="Corner cases">

`100vh` on mobile browsers includes the area behind the address bar, so a full-height panel is cut off; `100dvh` uses the dynamic
viewport. Users zoom text to 200%: rem-based layouts reflow; pixel-based ones overlap.

</Level>

<Level name="Production level">

Visual regression screenshots at several widths in CI, no horizontal scroll at 320px as a checked rule, and Core Web Vitals (layout shift
especially) measured on real mobile devices.

</Level>

<Level name="Mindset">

The layout should adapt to the content and the space, not to a list of devices.

</Level>

<Level name="System design">

Layout primitives (Stack, Cluster, Grid, Sidebar) as small components or utility classes make responsive behaviour consistent across pages,
part of the design system next to tokens.

</Level>

<Level name="Strategy">

I build the dashboard mobile first, use auto-fill grids and one container query, and check each page at five widths and at 200% zoom.

Done when no page scrolls sideways at 320px, text zoom to 200% keeps everything usable, and images reserve their space.

</Level>

</Levels>

<Levels label="Phase 2, design tokens">

<Level name="Beginner">

Design tokens are named values for design decisions: colours, spacing, font sizes, radii, shadows. Instead of `#1a1a1a` in forty files,
there is one `--color-text`. In plain CSS they are custom properties:

```css
:root {
  --color-text: #1a1a1a;
  --color-surface: #ffffff;
  --color-border: #d4d4d4;
  --space-1: 0.25rem; --space-2: 0.5rem; --space-4: 1rem; --space-8: 2rem;
  --font-size-body: 1rem; --font-size-h1: 2rem;
  --radius: 6px;
}
.card { background: var(--color-surface); border: 1px solid var(--color-border); padding: var(--space-4); border-radius: var(--radius); }
```

Mistake: a token per one-off value (`--card-padding-left-on-tuesday`). A small scale (4, 8, 16, 32) forces consistency.

</Level>

<Level name="Intermediate">

Semantic names describe purpose, not appearance: `--color-danger`, not `--red`. That is what makes themes possible:

```css
[data-theme="dark"] {
  --color-text: #ededed;
  --color-surface: #141414;
  --color-border: #333;
}
```

Every component switches with no change to its CSS. A theme toggle sets `document.documentElement.dataset.theme`, and
`prefers-color-scheme` gives the default.

</Level>

<Level name="Advanced">

Tokens can be a source of truth beyond CSS: a JSON file transformed by a tool (Style Dictionary) into CSS variables, a TypeScript object
and design-tool variables, so design and code cannot drift. Contrast is checked at the token level: every text-on-surface pair meets 4.5:1
in every theme, so components cannot produce a failing pair.

</Level>

<Level name="Edge cases">

Custom properties are inherited and resolved at use time, so a token redefined on a parent changes descendants (useful for a dark section),
and an undefined token silently falls back to the property's initial value; give a fallback in critical places: `var(--color-text, #111)`.

</Level>

<Level name="Corner cases">

Theme flash: the page renders light, then JavaScript applies dark. Set the theme attribute in a tiny inline script in the `head` before the
body paints, reading from `localStorage` and `prefers-color-scheme`.

</Level>

<Level name="Production level">

A lint rule (stylelint) forbids raw colours outside the token file; the gallery shows every token; token changes are reviewed with screenshots.

</Level>

<Level name="Mindset">

Every raw value is a decision made in one place that the rest of the product does not know about. Tokens make decisions shared.

</Level>

<Level name="System design">

Tokens, then primitives (Button, Field, Stack), then patterns (forms, cards), then pages: a design system is layers, each using only the
layer below.

</Level>

<Level name="Strategy">

I extract every colour, space and size from the dashboard into about twenty-five tokens, add a dark theme, and check contrast for each pair.

Done when no component CSS contains a raw colour or spacing value, the dark theme works with no component changes, and every text pair passes
contrast.

</Level>

</Levels>

#### Phase 2: Loading, error and empty states

<Figure art={`
              fetch products
                    |
     +--------------+--------------+----------------+
     v              v              v                v
  loading         error          empty            success
  skeleton rows   "Couldn't load  "No products     the list
  aria-busy       products."      match 'xyz'."
                  [Try again]     [Clear filters]
     ^                |
     +---- retry -----+
`} caption="Every data-driven view has four states, and the happy path is only one of them." />

<Levels label="Phase 2, loading, error and empty states">

<Level name="Beginner">

The plan's goal is an interface that is not "a demo that only works on the happy path". Every view that loads data can be loading, failed,
empty or successful, and each needs designed UI. A union type makes impossible combinations unrepresentable:

```tsx
type State<T> =
  | { status: 'loading' }
  | { status: 'error'; error: Error }
  | { status: 'success'; data: T };

function ProductsView({ state, query, onRetry, onClear }: Props) {
  switch (state.status) {
    case 'loading': return <SkeletonList rows={6} />;
    case 'error':   return <ErrorPanel message="Couldn't load products." onRetry={onRetry} />;
    case 'success':
      if (state.data.length === 0) return <Empty message={`No products match "${query}".`} action={<button onClick={onClear}>Clear filters</button>} />;
      return <ProductList products={state.data} />;
  }
}
```

Mistake: `isLoading` and `error` and `data` as three separate states, which allows "loading and error at once" and a blank screen when
none is set.

</Level>

<Level name="Intermediate">

Each state, designed. Loading: a skeleton in the shape of the content (less layout shift than a spinner), shown only after a short delay
(a few hundred milliseconds) so fast responses do not flash. Error: what happened in plain words, what to do, a retry button, and the
technical details logged rather than shown. Empty: distinguish "nothing yet" (a first-run message with the action to create one) from
"nothing matches" (the query shown and a way to clear filters).

Testing the states: DevTools network throttling for loading, request blocking (right-click, Block request URL) for errors, and a test
account with no data for empty.

</Level>

<Level name="Advanced">

Refetching shows stale data, not a skeleton: keep the previous list visible with a subtle indicator while the new one loads. Data libraries
make this a flag (`placeholderData: keepPreviousData` in TanStack Query). React's `Suspense` with a data source that supports it lets a
parent declare the loading UI for a whole subtree, and an error boundary catches render errors in a subtree:

```tsx
<ErrorBoundary fallback={<ErrorPanel message="This section failed to load." />}>
  <Suspense fallback={<SkeletonList rows={6} />}>
    <Products query={q} />
  </Suspense>
</ErrorBoundary>
```

</Level>

<Level name="Edge cases">

Partial failure: the list loads but images fail; each image needs its own fallback. Pagination errors on page three should not wipe pages one
and two. A 401 is not a generic error; it should send the user to sign in.

</Level>

<Level name="Corner cases">

Offline: `navigator.onLine` and the `online` event can show a banner and retry when the connection returns. A mutation that fails after an
optimistic update must roll back the UI and say so, or the user believes the change was saved.

</Level>

<Level name="Production level">

Every data view's four states are in the component gallery, errors go to error tracking with context, and end-to-end tests cover the error and
empty paths with mocked responses.

</Level>

<Level name="Mindset">

Users spend more time in the non-happy states than designers expect. Design them first.

</Level>

<Level name="System design">

Consistent state components (Skeleton, ErrorPanel, Empty) are part of the design system, and a data layer that always returns a discriminated
state makes every view handle all four.

</Level>

<Level name="Strategy">

For every data view in the dashboard I list the four states, build each, and capture them in the gallery using throttling, blocking and an empty
account.

Done when no view can show a blank screen, every error offers a way forward, and the four states appear in the gallery for each data view.

</Level>

</Levels>

<Levels label="Phase 2, routing and the multi-page app">

<Level name="Beginner">

The build is a multi-page React app with routing. A client-side router (React Router) maps URLs to components without a full page reload:

```tsx
const router = createBrowserRouter([
  {
    path: '/', element: <Root />, errorElement: <ErrorPage />,
    children: [
      { index: true, element: <Dashboard /> },
      { path: 'products', element: <ProductsPage /> },
      { path: 'products/:id', element: <ProductDetail /> },
      { path: 'settings', element: <Settings /> },
      { path: '*', element: <NotFound /> },
    ],
  },
]);
```

`Root` renders the shared layout and an `<Outlet />` where the child page goes. Links use `<Link to="/products">`, which updates the URL
and renders without reloading. Mistake: `<a href>` for internal links, which reloads the whole app and loses state.

</Level>

<Level name="Intermediate">

Filters belong in the URL, so a filtered view survives reload, the back button works, and the link can be shared:

```tsx
function ProductsPage() {
  const [params, setParams] = useSearchParams();
  const q = params.get('q') ?? '';
  const sort = params.get('sort') ?? 'relevance';
  return <SearchBox value={q} onChange={v => setParams(p => { p.set('q', v); return p; }, { replace: true })} />;
}
```

`replace: true` while typing avoids a history entry per keystroke. Route params (`useParams().id`) are always strings and may not exist; validate
them and render `NotFound` for bad IDs.

</Level>

<Level name="Advanced">

Loaders fetch data per route before rendering (React Router data APIs, TanStack Router), which removes waterfall effects in components and
gives every route a loading and error boundary. Code splitting per route (`lazy`) keeps the initial bundle small. After navigation, move focus to
the new page's heading and update `document.title`, so screen-reader users know the page changed.

</Level>

<Level name="Edge cases">

Deploying a client-side-routed app to a static host: a reload on `/products/42` asks the server for that path, which does not exist as a file,
and returns 404. Configure the host to serve `index.html` for unknown paths (a rewrite rule). Scroll position: new pages should start at the top,
back navigation should restore position; routers provide `ScrollRestoration`.

</Level>

<Level name="Corner cases">

Unsaved form changes lost on navigation: block with a confirmation using the router's blocker API, and `beforeunload` for tab closes. A search
param that a user edits by hand (`?sort=evil`) must be validated against allowed values, not used blindly.

</Level>

<Level name="Production level">

Every route has a title, an error element, and a not-found path; the host rewrite rule is in the repository; deep links are tested end to end.

</Level>

<Level name="Mindset">

If a user would want to bookmark it, share it or go back to it, it belongs in the URL.

</Level>

<Level name="System design">

The route tree is the app's information architecture: nested layouts mirror nested navigation, and per-route loaders and code splitting make each
page independently fast.

</Level>

<Level name="Strategy">

I build the dashboard's routes with a root layout, URL-driven filters, a 404, per-route error elements and focus on navigation, then deploy and
test deep links.

Done when every filter state is shareable by URL, reload works on every route in production, and the back button always does what a user expects.

</Level>

</Levels>

#### Phase 2: The gate, why a component re-renders

<Flow
  caption="The four reasons a component renders, checked in this order"
  steps={['Is it the first render (mount)?', 'Did its own state change?', 'Did its parent render (and it is not memoised with equal props)?', 'Did a context it reads change?', 'Otherwise: it did not render']}
/>

<Levels label="Phase 2, Gate 2: re-renders, a stale closure and a derived-state bug">

<Level name="Beginner">

Gate 2: explain why a component re-renders, and fix a stale closure and a derived-state bug. A component renders for exactly four reasons, the
ones in the flow. Props changing is not a separate reason: props change because the parent rendered. So "why did `ProductCard` render?" is answered
by walking up: its parent rendered because the parent's state changed because the user typed.

I prove it with a render log:

```tsx
function ProductCard(props: CardProps) {
  console.log('render ProductCard', props.product.id);
  /* ... */
}
```

```text
type "l" in search
render Catalog
render ProductCard p1
render ProductCard p2
render ProductCard p3
```

</Level>

<Level name="Intermediate">

The stale closure, the case in the <a href={withBase('/posts/react/06/')}>stale closures note</a>:

```tsx
function Timer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setCount(count + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return <p>{count}</p>;
}
```

```text
0, 1, 1, 1, 1 ...
```

The interval's function was created during the first render and closed over that render's `count`, which is 0 forever. Every tick sets `0 + 1`.
Two fixes: the updater form `setCount(c => c + 1)`, which needs no captured value, or adding `count` to the dependencies (which restarts the
interval every second, worse here). The lint rule would have flagged the missing dependency.

</Level>

<Level name="Advanced">

The derived-state bug, as the gate might plant it:

```tsx
function Cart({ items }: { items: Item[] }) {
  const [total, setTotal] = useState(sum(items));
  return <p>Total ₹{total}</p>;
}
```

Adding an item to the cart does not change the total, because `useState` used `items` only on the first render. The fix deletes state:
`const total = sum(items)`. I explain it in the gate with the snapshot model: initial state is read once; render-time values are read every render.

</Level>

<Level name="Edge cases">

Strict Mode in development renders components twice to find impure renders, so a render log shows doubled lines; that is not a bug in my code.
React DevTools greys out duplicate logs from the second render.

</Level>

<Level name="Corner cases">

Setting state to the same value (`Object.is` equal) usually lets React bail out without rendering children, but it may still call the component
once more before bailing. Do not build logic on render counts.

</Level>

<Level name="Production level">

<Levels label="Phase 2, the README, the traps and the AI-era note">

<Level name="Beginner">

The README is part of the proof: what the app does, screenshots (phone and desktop, light and dark), how to run it in three commands, the live link,
and a short design rationale. The rationale is a few paragraphs: why these components, where state lives and why, the token scale, accessibility
decisions, and what I would change next.

```text
## Design rationale
State: filters live in the URL so views are shareable; server data in the query cache;
only form drafts and UI toggles use component state.
Tokens: a 4/8/16/32 spacing scale and 12 semantic colours, two themes, all pairs pass 4.5:1.
```

</Level>

<Level name="Intermediate">

The AI-era note: AI is good at scaffolding a component and not good at deciding who owns the state. My review checklist for generated
components: every `useState` (could it be derived? is it in the right component?), every `useEffect` (what external system? are dependencies
complete? is there cleanup?), every list key, every interactive element's semantics. Then I ask the model to critique, not to replace:

```text
Prompt: Critique this component. For each piece of state, say whether it could be
derived or should live elsewhere. For each effect, say whether it is needed. List
accessibility problems. Do not rewrite it.
```

</Level>

<Level name="Advanced">

Generated components often store derived values, fetch in effects without cleanup, use `div` buttons and index keys, exactly the plan's traps.
Reviewing them is good practice for the gate: each one is a planted bug.

</Level>

<Level name="Edge cases">

A model's critique can be wrong (suggesting `useMemo` everywhere, or an effect to sync state). I check each suggestion against the mental model and
the Profiler before accepting it.

</Level>

<Level name="Corner cases">

Generated code that passes my tests but fails the keyboard pass shows the limit of automated checks; the manual pass stays in the proof.

</Level>

<Level name="Production level">

The deployed app has no console errors or warnings (part of the proof), which I check in a production build, since development warnings differ.

</Level>

<Level name="Mindset">

Typing speed was never the bottleneck. Deciding where state lives, and noticing when it is wrong, is the skill this phase builds.

</Level>

<Level name="System design">

The front end built here becomes the client for Phase 3's API: the forms, states and routes already exist, so the backend phase replaces fake data
with real endpoints.

</Level>

<Level name="Strategy">

Write the README last week, with screenshots from the deployed app, and audit the code against the trap table before taking the gate.

Done when the README has screenshots and a rationale, the console is clean in production, every trap has evidence, and Gate 2 is passed cold.

</Level>
