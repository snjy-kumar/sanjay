#### Phase 2: Components and props

<Figure art={`

<Levels label="Phase 2, components and props">

<Level name="Beginner">

A component is a function that returns JSX, a description of UI. Props are its inputs, passed like
HTML attributes. Component names start with a capital letter.

```tsx
type CardProps = { title: string; price: number };
function ProductCard({ title, price }: CardProps) {
  return <article><h3>{title}</h3><p>₹{price}</p></article>;
}
export default function App() {
  return <ProductCard title="Notebook" price={120} />;
}
```

Mistake: `<productCard />` in lowercase renders an unknown HTML tag and React warns
`The tag <productCard> is unrecognized in this browser`. Fix: capitalise component names.

</Level>

<Level name="Intermediate">

`children` is a prop too, which makes wrapper components. Callbacks as props let children report
events. Conditional rendering uses `&&` or a ternary; lists use `map`.

```tsx
function Panel({ title, children }: { title: string; children: React.ReactNode }) {
  return <section aria-labelledby={title}><h2 id={title}>{title}</h2>{children}</section>;
}
<Panel title="Cart">{items.length ? <CartList items={items} /> : <p>Your cart is empty.</p>}</Panel>
```

</Level>

<Level name="Advanced">

JSX compiles to function calls (`jsx(ProductCard, { title, price })`) that produce plain objects
(elements). Props are read-only: a component must not mutate them. A component must be pure during
render: same props and state, same output, no side effects.

</Level>

<Level name="Edge cases">

`{count && <Badge />}` renders `0` when count is zero, because React renders numbers. Use
`count > 0 &&` spelled out, or a ternary. `undefined`, `null` and booleans render nothing.

</Level>

<Level name="Corner cases">

A prop that is an object created inline (`style={{ gap: 8 }}`) is a new object every render, which
defeats memoization of the child. Harmless usually, but it matters once memo is involved.

</Level>

<Level name="Production level">

Props are an API. Keep them few, name them for meaning (`onAdd`, not `handleClick2`), type them, and
document them in the gallery.

</Level>

<Level name="Mindset">

Think in trees: what does this part of the screen need to know, and who should tell it?

</Level>

<Level name="System design">

Component boundaries are module boundaries. A good split mirrors the product's nouns: a card, a list,
a filter bar.

</Level>

<Level name="Strategy">

Draw the component tree of the dashboard on paper before writing it. Done when every component has a
typed props list I can explain.

</Level>

</Levels>

#### Phase 2: State

<Flow
  caption="What setState actually does: it schedules a new render with a new value; the current render keeps its old one."
  steps={['Click', 'setCount(c => c + 1) queued', 'Handler finishes; count still old here', 'React re-renders', 'New render reads new count']}
/>

<Levels label="Phase 2, state">

<Level name="Beginner">

State is data a component remembers between renders. `useState` returns the current value and a setter;
calling the setter re-renders the component.

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Clicked {count} times</button>;
}
```

Mistake: a normal variable `let count = 0` that resets every render and never updates the screen. Fix:
`useState`.

</Level>

<Level name="Intermediate">

State updates are snapshots: inside a handler, `count` is the value from that render. Multiple updates
in one handler need the updater form. Objects and arrays are replaced, never mutated.

```tsx
setCount(count + 1); setCount(count + 1);       // adds 1
setCount((c) => c + 1); setCount((c) => c + 1); // adds 2
setTodos((ts) => [...ts, newTodo]);             // new array
```

</Level>

<Level name="Advanced">

React batches updates in a handler into one render. State is tied to a component's position in the
tree; moving or changing the type at that position resets it, and a `key` change resets it on purpose.
For complex transitions, `useReducer` keeps update logic in one pure function.

</Level>

<Level name="Edge cases">

`todos.push(x); setTodos(todos)` does nothing: same array reference, React bails out. Setting state to
the same value skips the re-render. `useState(expensive())` runs `expensive` every render; pass a
function `useState(() => expensive())`.

</Level>

<Level name="Corner cases">

Two inputs both reading `count`, plus an async handler that awaits before setting: the await resumes
with the old snapshot, so a second click in between is lost. Use the updater form. Conditional
rendering that swaps two components of the same type at the same spot keeps the state of the first,
surprising users with old form contents; give them different keys.

</Level>

<Level name="Production level">

Keep state minimal and close to where it is used. The <a href={withBase('/posts/react/04/')}>lifting state
too high</a> note shows the cost of the opposite: everything re-renders and props pass through layers
that do not care.

</Level>

<Level name="Mindset">

Ask "who owns this?" before "where do I put it?". The plan's AI note: models scaffold well and are bad
at deciding who owns the state.

</Level>

<Level name="System design">

State has kinds: UI state (open, selected), form state, server cache, URL state. Each has a better home
than a pile of `useState` calls, and Phase 2 meets them all.

</Level>

<Level name="Strategy">

Done when I can predict the output of the double `setCount` puzzle and explain snapshots without notes.

</Level>

</Levels>

#### Phase 2: Derived state

  ]}

/>

<Levels label="Phase 2, derived state">

<Level name="Beginner">

Derived state is a value computed from other state or props. It should be a plain variable in the
render, not its own `useState`. The <a href={withBase('/posts/react/01/')}>derived state note</a> is the
case study.

```tsx
const [todos, setTodos] = useState<Todo[]>([]);
const [filter, setFilter] = useState<Filter>('all');
const visible = todos.filter((t) => filter === 'all' || (filter === 'done') === t.done);
```

Mistake: `useState(todos.filter(...))`, which captures the first value only and goes stale.

</Level>

<Level name="Intermediate">

Store the minimal source: the selected id, not the selected object; the query, not the results.

```tsx
const [selectedId, setSelectedId] = useState<string | null>(null);
const selected = products.find((p) => p.id === selectedId) ?? null; // always fresh
```

</Level>

<Level name="Advanced">

Expensive derivations can use `useMemo`, but only after measuring. Resetting state when a prop changes
is done with a `key`, not an effect.

</Level>

<Level name="Edge cases">

A prop used as initial state (`useState(props.value)`) is read once; later prop changes are ignored.
Name it `initialValue` so the intent is clear.

</Level>

<Level name="Corner cases">

A stored "selected item" object plus an edit to that item in the list: the detail pane shows the old
copy. Storing the id fixes both the stale copy and the deleted-item case (it becomes `null`).

</Level>

<Level name="Production level">

Most "it shows the old value" bugs in React apps are duplicated state. The gate asks me to fix one.

</Level>

<Level name="Mindset">

One fact, one place. Everything else is a view.

</Level>

<Level name="System design">

Normalised data in a store with selectors is the same idea at app scale (the Redux plan), and database
views are the same idea in SQL.

</Level>

<Level name="Strategy">

Audit every `useState` in the app: could it be computed? Done when none could.

</Level>

</Levels>

#### Phase 2: Effects, and when not to use them

<Flow
  caption="Do I need an effect? Most paths end at no."
  steps={['Is it caused by a user event? put it in the handler', 'Is it computable from state? derive it', 'Is it resetting state on a prop change? use a key', 'Is it syncing with something outside React? effect']}
/>

<Levels label="Phase 2, effects and when not to use them">

<Level name="Beginner">

`useEffect` runs code after render to synchronise with something outside React: a subscription, a timer,
a non-React widget, the document title, a network request.

```tsx
useEffect(() => {
  document.title = `${count} items`;
}, [count]);
```

Mistake: an effect that watches state to respond to a click, the trap the plan names. See
<a href={withBase('/posts/react/02/')}>useEffect used as an event handler</a>. Fix: do it in the handler.

</Level>

<Level name="Intermediate">

Cleanup undoes the effect before the next run and on unmount. Data fetching in an effect needs a guard
against stale responses.

```tsx
useEffect(() => {
  const ctrl = new AbortController();
  setStatus('loading');
  fetch(`/api/products?q=${encodeURIComponent(query)}`, { signal: ctrl.signal })
    .then((r) => (r.ok ? r.json() : Promise.reject(new Error(`HTTP ${r.status}`))))
    .then((data) => { setProducts(data); setStatus('success'); })
    .catch((e) => { if (e.name !== 'AbortError') setStatus('error'); });
  return () => ctrl.abort();
}, [query]);
```

</Level>

<Level name="Advanced">

The dependency array lists every reactive value the effect reads; the lint rule
`react-hooks/exhaustive-deps` checks it. In development with Strict Mode, React mounts, unmounts and
mounts again, running effects twice, to expose missing cleanup. Effects run after paint;
`useLayoutEffect` runs before it, for measuring layout.

</Level>

<Level name="Edge cases">

An empty dependency array means "on mount" only, so it sees the first render's values forever. An
object or function dependency created in render changes every time, making the effect run every render.

</Level>

<Level name="Corner cases">

An effect that sets state it depends on, plus a new object each time: an infinite loop, with React
eventually warning `Maximum update depth exceeded`. Two effects syncing each other's state ping-pong.

</Level>

<Level name="Production level">

In real apps, server data is usually fetched with a data library or the framework's loader, which
handles caching, deduplication and races. Writing it by hand once teaches what those tools do.

</Level>

<Level name="Mindset">

Effects are an escape hatch. Each one should answer "what external system am I synchronising with?"

</Level>

<Level name="System design">

Server state belongs to a cache with invalidation, not to component state. That split is the start of
the caching ideas in Phase 4.

</Level>

<Level name="Strategy">

Review every effect dependency, as the plan's AI note says. Done when every effect in the app names its
external system and has cleanup where needed.

</Level>

</Levels>

#### Phase 2: The rules of hooks

<Figure art={`
  render 1            render 2 (if cond flipped)
  slot 0: useState    slot 0: useState
  slot 1: useEffect   slot 1: useMemo      <-- React thinks this is the effect
  slot 2: useMemo     slot 2: (missing)
  Hooks are matched by call order, so the order must never change.
`} caption="Why hooks cannot be conditional: React finds each hook's state by its position in the call order." />

<Levels label="Phase 2, the rules of hooks">

<Level name="Beginner">

Two rules: call hooks only at the top level of a component or custom hook (not in conditions, loops or
after an early return), and only from React functions.

```tsx
if (!user) return null;
const [tab, setTab] = useState('info'); // breaks the rule: after an early return
```

React reports `Rendered more hooks than during the previous render.` Fix: call hooks first, return
early after.

</Level>

<Level name="Intermediate">

Custom hooks are functions starting with `use` that call other hooks, a way to reuse stateful logic.

```tsx
function useLocalStorage<T>(key: string, initial: T) {
  const [value, setValue] = useState<T>(() => {
    try { return JSON.parse(localStorage.getItem(key) ?? '') as T; } catch { return initial; }
  });
  useEffect(() => { localStorage.setItem(key, JSON.stringify(value)); }, [key, value]);
  return [value, setValue] as const;
}
```

</Level>

<Level name="Advanced">

React stores hook state in a list on the component's fiber, indexed by call order, as the figure shows.
The lint rule `react-hooks/rules-of-hooks` catches violations statically.

</Level>

<Level name="Edge cases">

Hooks in a loop with a fixed length still violate the rule, and break as soon as the length changes.
Calling a custom hook conditionally breaks the same way.

</Level>

<Level name="Corner cases">

A component called as a function (`{Row(props)}`) instead of rendered (`<Row />`) merges its hooks into
the parent's list; a conditional call then breaks the parent.

</Level>

<Level name="Production level">

The lint rules run in the editor and CI. Custom hooks are where shared behaviour lives, tested on their
own.

</Level>

<Level name="Mindset">

Constraints with a clear reason are easier to keep. Know why the rule exists, not just the rule.

</Level>

<Level name="System design">

Custom hooks are the reuse unit of React apps, the way modules are in Phase 1.

</Level>

<Level name="Strategy">

Break the rule three ways and read each error. Done when I can explain the call-order diagram.

</Level>

</Levels>

#### Phase 2: Lists and keys

<Compare
  left="key = index"
  right="key = stable id"
  rows={[
    ['Delete row 1: row 2 inherits row 1 state', 'Each row keeps its own state'],
    ['Sort: inputs keep old text in new rows', 'Rows move with their data'],
    ['Insert at top: every row re-renders', 'Only the new row mounts'],
  ]}
  caption="Keys tell React which item is which between renders. An index describes a position, not an item."
/>

<Levels label="Phase 2, lists and keys">

<Level name="Beginner">

Rendering a list with `map` needs a `key` on each item: a stable, unique id. See
<a href={withBase('/posts/react/03/')}>missing and unstable list keys</a>.

```tsx
<ul>{todos.map((t) => <TodoRow key={t.id} todo={t} />)}</ul>
```

Without keys React warns `Each child in a list should have a unique "key" prop.`

</Level>

<Level name="Intermediate">

Keys must be stable across renders and unique among siblings. An index is acceptable only for a static
list that never reorders, filters or has per-row state.

</Level>

<Level name="Advanced">

Reconciliation compares children by key: same key, update in place; new key, mount; missing key,
unmount. Changing a key on purpose resets a component, a useful tool.

</Level>

<Level name="Edge cases">

Duplicate keys produce a warning and rows that update the wrong DOM. `Math.random()` as a key remounts
every row on every render, losing focus and state.

</Level>

<Level name="Corner cases">

Index keys plus a row with an uncontrolled input plus a delete: the text typed in the deleted row's
neighbour appears to jump. Two boundaries meet: position-based identity and DOM-held state.

</Level>

<Level name="Production level">

Ids come from the server or `crypto.randomUUID()`, never from render. Long lists get virtualisation, which
depends on stable keys.

</Level>

<Level name="Mindset">

Identity and position are different things.

</Level>

<Level name="System design">

Primary keys in Phase 3 are the same idea; the UI should use the database's identity.

</Level>

<Level name="Strategy">

Reproduce the index-key bug on purpose, then fix it. Done when every list has a data-derived key.

</Level>

</Levels>

#### Phase 2: Controlled forms

<Flow
  caption="A controlled input: React state is the single source; the DOM only displays it."
  steps={['User types', 'onChange(event)', 'setValue(event.target.value)', 'Re-render', 'input value = state']}
/>

<Levels label="Phase 2, controlled forms">

<Level name="Beginner">

A controlled input takes its `value` from state and reports changes through `onChange`. See
<a href={withBase('/posts/react/05/')}>controlled inputs done wrong</a>.

```tsx
const [name, setName] = useState('');
<label>Name <input value={name} onChange={(e) => setName(e.target.value)} /></label>
```

Mistake: `value` without `onChange` makes the input read-only, with a console warning about a `value`
prop without an `onChange` handler.

</Level>

<Level name="Intermediate">

A form with validation, submit handling and per-field errors, linked to inputs for screen readers.

```tsx
function onSubmit(e: React.FormEvent) {
  e.preventDefault();
  const errs: Record<string, string> = {};
  if (!form.email.includes('@')) errs.email = 'Enter an email address';
  setErrors(errs);
  if (Object.keys(errs).length === 0) save(form);
}
<input id="email" aria-invalid={!!errors.email} aria-describedby="email-err" ... />
{errors.email && <p id="email-err">{errors.email}</p>}
```

</Level>

<Level name="Advanced">

Uncontrolled inputs with `defaultValue` and `FormData` are fine when I only need values on submit.
Number inputs return strings; checkboxes use `checked`. Form libraries manage touched and dirty state
and validation schemas.

</Level>

<Level name="Edge cases">

Switching `value` from `undefined` to a string warns that a component is changing an uncontrolled input
to be controlled; initialise with `''`. A number field cleared by the user is `''`, not `0`.

</Level>

<Level name="Corner cases">

Formatting the value in `onChange` (adding commas) plus a cursor in the middle: the cursor jumps to the
end. Format on blur instead.

</Level>

<Level name="Production level">

Client validation is for the user's speed; the server validates again (Phase 3). Disable double submit,
show progress, and keep the user's input when the request fails.

</Level>

<Level name="Mindset">

Forms are where users and data meet; design the failure messages first.

</Level>

<Level name="System design">

Share one validation schema between client and server so the rules cannot drift.

</Level>

<Level name="Strategy">

Done when the dashboard's form validates, announces errors, survives a failed submit, and cannot submit
twice.

</Level>

</Levels>

#### Phase 2: Context

<Figure art={`
  <ThemeProvider value="dark">                 every consumer below
    <Layout>                                   re-renders when value
      <Sidebar>                                changes, even if the
        <ThemeToggle />   <-- useContext       components between
      </Sidebar>                               do not use it
      <Main> <Card /> </Main>   <-- useContext
    </Layout>
  </ThemeProvider>
`} caption="Context skips the props chain. Its cost: every consumer re-renders on every value change." />

<Levels label="Phase 2, context">

<Level name="Beginner">

Context passes a value to any descendant without threading props through each level. Good for the
theme, the current user, the locale.

```tsx
const ThemeContext = createContext<'light' | 'dark'>('light');
function ThemeToggle() { const theme = useContext(ThemeContext); return <span>{theme}</span>; }
<ThemeContext.Provider value="dark"><Layout /></ThemeContext.Provider>
```

</Level>

<Level name="Intermediate">

Wrap the context in a provider component and a custom hook that throws when used outside the provider.

```tsx
const AuthContext = createContext<Auth | null>(null);
export function useAuth() {
  const v = useContext(AuthContext);
  if (!v) throw new Error('useAuth must be used inside AuthProvider');
  return v;
}
```

</Level>

<Level name="Advanced">

Consumers re-render when the provider's `value` changes by reference. An inline object
(`value={{ user, logout }}`) is new every render, so memoize it or split state and actions into two
contexts.

</Level>

<Level name="Edge cases">

A consumer with no provider above gets the default value, silently. The throwing hook turns that into a
clear error.

</Level>

<Level name="Corner cases">

Fast-changing data (a text input's value) in a context near the root plus many consumers: every
keystroke re-renders the whole app.

</Level>

<Level name="Production level">

Context is for low-frequency, widely needed values. Passing everything through it is a known mistake,
which the React series covers in its later notes on context for every prop.

</Level>

<Level name="Mindset">

Prop drilling through two levels is fine. Reach for context when the drilling hurts, not before.

</Level>

<Level name="System design">

Server state goes to a cache, URL state to the router, global client state to context or a store such
as Redux (see <a href={withBase('/plans/redux/')}>the Redux plan</a>).

</Level>

<Level name="Strategy">

Done when the app uses context for theme and auth only, and the Profiler shows typing does not
re-render unrelated components.

</Level>

</Levels>

#### Phase 2: Memoization

<Flow
  caption="Measure first. Memoize only what the Profiler shows is slow, and only if its inputs are stable."
  steps={['Feels slow', 'Record in React Profiler', 'Find the expensive component', 'Stabilise its props', 'memo, useMemo or useCallback', 'Record again: faster?']}
/>

<Levels label="Phase 2, memoization">

<Level name="Beginner">

`useMemo` caches a computed value between renders; `useCallback` caches a function; `memo` skips
re-rendering a component when its props are unchanged.

```tsx
const sorted = useMemo(() => [...products].sort(byPrice), [products]);
const onAdd = useCallback((id: string) => addToCart(id), [addToCart]);
const Row = memo(function Row({ item }: { item: Item }) { return <li>{item.name}</li>; });
```

</Level>

<Level name="Intermediate">

Memoization only helps when the inputs are actually stable and the work is actually expensive. Wrapping
everything is the plan's named trap, cargo-cult `useMemo`, and the React series has a later note on it.

</Level>

<Level name="Advanced">

Dependencies compare with `Object.is`. A `memo` child receiving an inline arrow or object never skips.
The React Compiler can add memoization automatically where it is safe, which changes the manual
calculus but not the reasoning.

</Level>

<Level name="Edge cases">

`useMemo` with an empty dependency list caches the first value forever, a stale-value bug in disguise.

</Level>

<Level name="Corner cases">

`useCallback` on a handler plus a `memo` child plus a prop object created inline in the same render: the
callback is stable, the object is not, and the child re-renders anyway.

</Level>

<Level name="Production level">

Performance work starts with a number from the Profiler or the Performance panel, as rule 10 says:
measure before optimizing.

</Level>

<Level name="Mindset">

Memoization is a cache, and every cache needs a reason and an invalidation story.

</Level>

<Level name="System design">

The same trade appears in HTTP caches and database query caches in Phases 3 and 4.

</Level>

<Level name="Strategy">

Remove all memoization, profile, then add back only what the numbers justify. Done when each remaining
`useMemo` has a measured reason in a comment.

</Level>

</Levels>

<Levels label="Phase 2, composition">

<Level name="Beginner">

Composition builds UI by putting components inside other components with `children`, rather than adding
props for every variation.

```tsx
<Card>
  <Card.Header>Notebook</Card.Header>
  <p>₹120</p>
  <Card.Footer><Button>Add</Button></Card.Footer>
</Card>
```

</Level>

<Level name="Intermediate">

Slots: pass elements as named props (`icon={<SearchIcon />}`). Passing children also avoids prop
drilling: the parent that owns the data renders the deep child directly.

</Level>

<Level name="Advanced">

Compound components share implicit state through a private context (`Tabs`, `Tabs.List`, `Tabs.Panel`).
Render props and hooks share behaviour without fixing markup.

</Level>

<Level name="Edge cases">

`children` can be a string, an array, `null` or a fragment; code that inspects children breaks on some
of them. Avoid inspecting children.

</Level>

<Level name="Corner cases">

A compound component used outside its parent plus a missing context: throw a clear error, as the context
topic showed.

</Level>

<Level name="Production level">

The plan's trap: abstracting a component before the second use. Write it twice, then extract the shared
shape.

</Level>

<Level name="Mindset">

Duplication is cheaper than the wrong abstraction.

</Level>

<Level name="System design">

Design systems are built from small composable primitives plus documented patterns, not one component
per screen.

</Level>

<Level name="Strategy">

Done when the gallery's `Card`, `Tabs` and `Dialog` compose without boolean props that conflict.

</Level>

</Levels>

#### Phase 2: Accessibility

<Layers
  caption="Accessibility from the bottom up. Most of it is decided by the first layer."
  layers={[
    { name: 'Semantic HTML', note: 'button, a, label, headings, landmarks, lists' },
    { name: 'Keyboard', note: 'every action reachable with Tab, Enter, Space, Escape; visible focus' },
    { name: 'Names and states', note: 'labels, alt text, aria-expanded, aria-invalid, live regions' },
    { name: 'Perception', note: 'contrast, text resizing, motion, not colour alone' },
    { name: 'Testing', note: 'screen reader pass, axe, Lighthouse, a keyboard-only session' },
  ]}
/>

<Levels label="Phase 2, accessibility">

<Level name="Beginner">

Accessible means usable by people with different abilities and tools: screen readers, keyboards only,
magnification. Start with the right HTML element; it brings keyboard support and a role for free.

```tsx
<button onClick={toggle} aria-expanded={open} aria-controls="filters">Filters</button>
<div id="filters" hidden={!open}>...</div>
```

Mistake: `<div onClick>`, which a keyboard cannot reach. Fix: `button`.

</Level>

<Level name="Intermediate">

Every input has a label; images have alt text; headings form an outline; focus is visible; the page has
landmarks. Status changes that are not focused (saved, three results) go in a live region.

```tsx
<p role="status" aria-live="polite">{results.length} products found</p>
```

</Level>

<Level name="Advanced">

Focus management in single-page apps: after a route change, move focus to the new page's heading; when a
dialog opens, move focus into it, trap Tab inside, close on Escape and return focus to the opener. The
native `dialog` element with `showModal()` does most of this.

</Level>

<Level name="Edge cases">

An icon-only button with no text has no accessible name; screen readers say just "button". Add
`aria-label`. Placeholder text is not a label; it disappears when typing.

</Level>

<Level name="Corner cases">

A custom select built from divs plus a screen reader: no role, no state, no keyboard model. Use the
native select, or a tested library. ARIA added wrongly is worse than none.

</Level>

<Level name="Production level">

The plan's proof requires a keyboard and screen-reader pass. I run VoiceOver (macOS) or NVDA (Windows)
through the main journey and record what was confusing. Automated tools such as axe find about a third
of issues; the manual pass finds the rest.

</Level>

<Level name="Mindset">

Accessibility is a feature, not a chore: rule 11. It is also how search engines and tests see the page.

</Level>

<Level name="System design">

Accessible primitives in the design system make every screen accessible by default; Testing Library
queries by role, so accessible components are also the testable ones.

</Level>

<Level name="Strategy">

One full session per week with the mouse unplugged. Done when the main journey works by keyboard alone
and with a screen reader, and axe reports no violations.

</Level>

</Levels>

#### Phase 2: Responsive CSS

<Figure art={`
  phone (one column)     tablet (two)            desktop (sidebar + grid)
  +----------+           +---------+---------+   +------+-----+-----+-----+
  | filters  |           | filters | card    |   |      | card| card| card|
  | card     |           |         | card    |   | side | card| card| card|
  | card     |           +---------+---------+   | bar  |     |     |     |
  +----------+                                   +------+-----+-----+-----+
  grid-template-columns: repeat(auto-fill, minmax(16rem, 1fr))
`} caption="One grid rule adapts the catalog from one column to many, with no breakpoint for the cards themselves." />

<Levels label="Phase 2, responsive CSS">

<Level name="Beginner">

Responsive design makes one layout work on every screen. Start mobile-first: the narrow layout is the
default, wider screens add columns with media queries.

```css
.layout { display: grid; gap: 1rem; }
@media (min-width: 48rem) { .layout { grid-template-columns: 16rem 1fr; } }
.cards { display: grid; gap: 1rem; grid-template-columns: repeat(auto-fill, minmax(16rem, 1fr)); }
```

</Level>

<Level name="Intermediate">

Flexbox for one dimension (a toolbar), grid for two (a page). Relative units (`rem`, `%`, `ch`) and
`clamp()` for fluid type: `font-size: clamp(1rem, 0.9rem + 0.5vw, 1.25rem)`.

</Level>

<Level name="Advanced">

Container queries size a component by its container, not the viewport, so a card works in a sidebar and
a main column. Logical properties (`margin-inline`) support right-to-left languages.

```css
.card-wrap { container-type: inline-size; }
@container (min-width: 30rem) { .card { display: flex; } }
```

</Level>

<Level name="Edge cases">

Very long words, zoom at 200 percent, a phone in landscape, a 320 px wide screen, and user font size
changes. Fixed heights cut off text when fonts grow.

</Level>

<Level name="Corner cases">

`100vh` on mobile includes the area behind the browser's toolbar, so a full-height layout hides its
bottom button; `100dvh` fixes it. Sticky header plus an anchor link: the heading lands under the header
unless `scroll-margin-top` is set.

</Level>

<Level name="Production level">

Test on a real phone, not only device mode. Images get `width` and `height` to avoid layout shift, which
Phase 4 measures.

</Level>

<Level name="Mindset">

Design for the content, not for device names. Add a breakpoint where the layout breaks.

</Level>

<Level name="System design">

Layout primitives (stack, cluster, grid) in the design system keep pages consistent.

</Level>

<Level name="Strategy">

Done when every page works from 320 px to a wide desktop, at 200 percent zoom, with no horizontal scroll.

</Level>

</Levels>

#### Phase 2: Design tokens

<Layers
  caption="Tokens in three tiers. Components only use the top tier, so a theme change touches one file."
  layers={[
    { name: 'Component tokens', note: '--button-bg, --card-border: what a component uses' },
    { name: 'Semantic tokens', note: '--color-text, --color-surface, --space-2: meaning' },
    { name: 'Raw values', note: '#111, #fff, 0.5rem, IBM Plex Sans: the palette' },
  ]}
/>

<Levels label="Phase 2, design tokens">

<Level name="Beginner">

Design tokens are named values for colour, spacing, type and radius, kept in one place and used
everywhere. CSS custom properties are the simplest form.

```css
:root { --ink: #111; --paper: #fff; --muted: #666; --space-1: 0.25rem; --space-2: 0.5rem; --radius: 4px; }
.button { padding: var(--space-2); border-radius: var(--radius); color: var(--paper); background: var(--ink); }
```

Mistake: hard-coded `#333` in thirty files. Fix: one token, used thirty times.

</Level>

<Level name="Intermediate">

Semantic names (`--color-text`) over raw ones (`--grey-900`), so dark mode swaps values without touching
components.

```css
:root { --color-text: #111; --color-surface: #fff; }
[data-theme='dark'] { --color-text: #eee; --color-surface: #111; }
```

</Level>

<Level name="Advanced">

A spacing scale (4, 8, 12, 16, 24, 32) and a type scale reduce decisions. Tokens can be generated for
CSS, TypeScript and design tools from one JSON source.

</Level>

<Level name="Edge cases">

A token without a fallback in a context where it is undefined resolves to the property's initial value,
silently (`var(--x, #111)` adds a fallback).

</Level>

<Level name="Corner cases">

Dark mode plus contrast: a muted grey that passes on white fails on near-black. Check contrast for each
theme.

</Level>

<Level name="Production level">

This site is the example: monochrome tokens and IBM Plex, applied everywhere through variables.

</Level>

<Level name="Mindset">

Constrain choices so the interface is consistent without effort.

</Level>

<Level name="System design">

Tokens are the contract between design and code; a component library is not a design system without
them.

</Level>

<Level name="Strategy">

Done when `grep` finds no raw colour or spacing value outside the token file.

</Level>

</Levels>

#### Phase 2: Loading, error and empty states

<Figure art={`
              +---------+
   mount ---> | loading | --(slow > 300ms)--> show skeleton
              +----+----+
         ok   |         |  fail
   +----------+         +-----------+
   v                                v
  items.length = 0?            +---------+  retry
   yes -> EMPTY: say why,      |  error  | -------> loading
          offer an action      +---------+
   no  -> SUCCESS
`} caption="Four states, not one. Every data-backed view draws all four." />

<Levels label="Phase 2, loading, error and empty states">

<Level name="Beginner">

Every view that loads data has at least four states: loading, error, empty and success. The happy path
is only one of them.

```tsx
if (state.status === 'loading') return <p aria-busy="true">Loading products…</p>;
if (state.status === 'error') return <p role="alert">Could not load products. <button onClick={retry}>Try again</button></p>;
if (state.products.length === 0) return <p>No products match “{query}”. <button onClick={clear}>Clear search</button></p>;
return <ProductGrid products={state.products} />;
```

</Level>

<Level name="Intermediate">

Model the states as a discriminated union (Phase 1), so the compiler forces each one. Empty states say
why and what to do next.

</Level>

<Level name="Advanced">

Avoid flashes: delay the spinner by a few hundred milliseconds, keep the previous results visible while
refetching (stale state), and use skeletons that match the final layout. Error boundaries catch render
errors and show a fallback instead of a blank page.

</Level>

<Level name="Edge cases">

An error on page two of a list: keep page one visible. A filter that empties the list differs from a
truly empty account; they need different messages.

</Level>

<Level name="Corner cases">

Refetch in progress plus an error: show the stale data with an error banner, not an error screen that
hides what the user had.

</Level>

<Level name="Production level">

Most apps demo the success state and ship the others broken. The plan's goal is an interface "not a demo
that only works on the happy path"; these states are exactly that.

</Level>

<Level name="Mindset">

Design the unhappy paths first; they are what users remember.

</Level>

<Level name="System design">

API error shapes in Phase 3 should give the UI enough to choose a message.

</Level>

<Level name="Strategy">

Done when each data view shows all four states in the component gallery, triggered on demand.

</Level>

</Levels>

#### Phase 2: Routing and the multi-page app

<Figure art={`
  /                       Dashboard summary
  /products?q=pen&sort=   Catalog: search and filters live in the URL
  /products/:id           Detail page
  /products/new           Form
  /gallery                Component gallery
  *                       Not found
  <Layout> wraps them all: header, nav, <main>, footer
`} caption="The dashboard's routes. Anything a user might share or bookmark goes in the URL." />

<Levels label="Phase 2, routing and the multi-page app">

<Level name="Beginner">

The build is a multi-page React app, a dashboard or a catalog, with search, filters, forms and routing.
A client-side router maps URLs to components without full page reloads. With React Router:

```tsx
const router = createBrowserRouter([
  { path: '/', element: <Layout />, children: [
    { index: true, element: <Dashboard /> },
    { path: 'products', element: <Catalog /> },
    { path: 'products/:id', element: <ProductPage /> },
    { path: 'gallery', element: <Gallery /> },
    { path: '*', element: <NotFound /> },
  ] },
]);
```

</Level>

<Level name="Intermediate">

Search and filters belong in the URL so reload, back and share work.

```tsx
const [params, setParams] = useSearchParams();
const q = params.get('q') ?? '';
<input value={q} onChange={(e) => setParams({ q: e.target.value }, { replace: true })} />
```

</Level>

<Level name="Advanced">

Data loaders fetch before rendering a route, nested layouts keep shared UI mounted, and lazy routes split
the bundle. Frameworks such as Next.js or React Router's framework mode add server rendering.

</Level>

<Level name="Edge cases">

`/products/abc` for a missing id needs a not-found state, not a crash. A deep link opened fresh must load
its own data.

</Level>

<Level name="Corner cases">

A client-routed app on GitHub Pages plus a reload on `/products/1`: the static host returns 404 because
no file exists at that path. Use a hash router, a `404.html` fallback, or pre-render.

</Level>

<Level name="Production level">

Route changes announce themselves to screen readers (move focus to the `h1`), update the document title,
and scroll to top.

</Level>

<Level name="Mindset">

The URL is state, and the most shareable kind.

</Level>

<Level name="System design">

Route boundaries are natural code-splitting and data-loading boundaries.

</Level>

<Level name="Strategy">

Done when every page can be bookmarked, reloaded and shared, and the back button never surprises.

</Level>

</Levels>

<Level name="Beginner">

The proof asks for tests on five components. With Vitest and React Testing Library, render the
component, act like a user, assert on what is visible.

import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
it('adds a todo', async () => {
  render(<TodoApp />);

</Level>

#### Phase 2: The gate, why a component re-renders

<Flow
  caption="The four reasons a component re-renders. Gate 2 asks me to name which one applies."
  steps={['Its own state changed', 'Its parent re-rendered', 'A context it reads changed', 'A key change remounted it']}
/>

<Levels label="Phase 2, Gate 2: re-renders, a stale closure and a derived-state bug">

<Level name="Beginner">

Gate 2: explain why a React component re-renders. Pass: fix a stale closure and a derived-state bug. A
component re-renders when its state changes, its parent re-renders, or a context it uses changes. Props
changing is not the cause by itself; the parent re-rendering is.

</Level>

<Level name="Intermediate">

The stale closure, the case in the <a href={withBase('/posts/react/06/')}>stale closures note</a>:

```tsx
useEffect(() => {
  const id = setInterval(() => setSeconds(seconds + 1), 1000); // captured seconds = 0
  return () => clearInterval(id);
}, []);
// The counter sticks at 1.
// Fix: setSeconds((s) => s + 1)
```

</Level>

<Level name="Advanced">

The derived-state bug: a `filtered` list held in state and updated by an effect lags one render and
goes stale after an edit. Fix: compute it in render. React DevTools' Profiler "Why did this render?"
setting confirms each explanation.

</Level>

<Level name="Edge cases">

A component re-renders but the DOM does not change: render is not commit. Re-renders are cheap until
measured otherwise.

</Level>

<Level name="Corner cases">

A `memo` child still re-renders because a context it reads changed; memo only compares props.

</Level>

<Level name="Production level">

Most React performance and correctness bugs are one of these four reasons plus a closure.

</Level>

<Level name="Mindset">

Explain before fixing. A fix I cannot explain is a guess.

</Level>

<Level name="System design">

Knowing the re-render triggers decides where state lives in the tree.

</Level>

<Level name="Strategy">

Done when, given an unfamiliar component, I can say why it re-rendered, fix a stale closure and a
derived-state bug without notes, and confirm with the Profiler.

</Level>

</Levels>
