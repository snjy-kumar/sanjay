Five weeks to stop treating the machine as a black box. The primary book is
<a href={withBase('/books/computer-systems-a-programmers-perspective/')}>Computer Systems: A Programmer's Perspective</a>
with its labs, and <a href={withBase('/books/computer-organization-and-design/')}>Computer Organization and Design</a>
is the depth for how the hardware is built. Nand2Tetris is the hands-on
companion for gates and a CPU. The C from phase 1 comes back here as the
language that shows the machine. Below is the phase on the nine levels, how
I would learn it, the eleven concepts each on nine levels, the exercises and
the gate.

**The learning strategy, on nine levels**

<Levels label="Phase 5, computer architecture and C">

<Level name="Beginner">


A computer is a processor running instructions that read and write memory.
Numbers are bits of a fixed width. The smallest thing that works is a C
program, compiled, whose assembly I can read.


</Level>
<Level name="Intermediate">


Performance comes from how a program meets the machine: how its numbers are
stored, which instructions it becomes, how it walks memory through the
caches, and how the OS maps its addresses.


</Level>
<Level name="Advanced">


Each layer has exact rules: two's-complement wrap-around, IEEE rounding,
the calling convention, cache sets and lines, page tables, symbol
resolution. Most "mysterious" bugs and slowdowns are one of these rules.


</Level>
<Level name="Edge cases">


The boundaries are numeric: the largest integer, the smallest float, a
size that crosses a cache line or a page, an array exactly the size of the
cache.


</Level>
<Level name="Corner cases">


Two at once: signed and unsigned compared in one expression, false sharing
between two threads on one line, a page fault inside a hot loop.


</Level>
<Level name="Production level">


Every JavaScript performance cliff and memory limit sits on this layer: V8's
number representations, the heap inside virtual memory, the event loop
waiting on I/O and interrupts.


</Level>
<Level name="Mindset">


Measure before optimising, and explain the measurement with the machine. A
number without an explanation is luck.


</Level>
<Level name="System design">


Caches, pipelines, virtual memory and DMA are the same ideas I meet again
as CDNs, stream processors, container isolation and zero-copy networking.


</Level>
<Level name="Strategy">


Five weeks, CS:APP chapter by chapter with its labs, every claim measured
with `perf` or cachegrind. Done when I pass the gate: read assembly,
measure a cache-friendly loop, find a memory bug with ASan and Valgrind, and
explain virtual versus physical memory.

</Level>

</Levels>

**How I would learn it**

I would learn this phase by doing the CS:APP labs, with the chapters as
reading for each lab: Data Lab for integers and floats, Bomb Lab for
assembly, Cache Lab for caches. Each week ends with something that runs. I
would do the Nand2Tetris hardware projects for gates and the CPU, because
building an ALU from NAND gates teaches in an afternoon what a diagram does
not.

Every C file I write is built with `-Wall -Wextra -g
-fsanitize=address,undefined` during development, and run once under
Valgrind before I call it done. Every speed claim comes with `perf stat`
output. When I meet something that looks like magic in JavaScript, such as
`0.1 + 0.2`, a slow array of objects or a 32-bit wrap in a bitwise
operation, I explain it with this phase in the README.

**Concept 1 of 11: binary, hexadecimal, two's complement, overflow**

<Levels label="Binary, hexadecimal, two's complement and overflow">

<Level name="Beginner">


Binary is base 2; each hex digit is four bits, so `0xFF` is 255. In two's
complement, the top bit has a negative weight: in 8 bits, `0xFF` is −1.


</Level>
<Level name="Intermediate">


Negation is invert and add one. Unsigned arithmetic wraps modulo 2 to the w.
In C, signed overflow is undefined behaviour; in JavaScript, bitwise
operators work on 32-bit signed integers.

```c
#include <stdint.h>
#include <stdio.h>
int main(void) {
    uint8_t u = 255; u++;                 /* wraps to 0, defined */
    int32_t big = INT32_MAX;
    /* big + 1 is undefined behaviour: the compiler may assume it never happens */
    printf("%u %d\n", u, (int8_t)0xFF);   /* 0 -1 */
}
```


</Level>
<Level name="Advanced">


Sign extension copies the top bit when widening; truncation keeps the low
bits. The compiler uses the "no signed overflow" rule to simplify loops,
which is why an overflow check written as `x + 1 < x` can be deleted.


</Level>
<Level name="Edge cases">


- `INT_MIN / -1` and `-INT_MIN` overflow; `abs(INT_MIN)` is undefined.
- `(2 ** 31) | 0` in JavaScript is −2147483648.


</Level>
<Level name="Corner cases">


- `if (len - 1 < 0)` with an unsigned `len` of 0: `len - 1` wraps to a huge
  number and the check never fires.


</Level>
<Level name="Production level">


Size calculations that overflow allocate too little and are a classic
security hole; `__builtin_mul_overflow` or a check before multiplying fixes
it. 64-bit IDs must not pass through a JavaScript `number`.


</Level>
<Level name="Mindset">


Every integer has a range. Ask what happens at its edges before shipping.


</Level>
<Level name="System design">


Protocols fix integer widths and signedness per field, so two programs in
different languages agree on the bytes.


</Level>
<Level name="Strategy">


Do Data Lab and write a function that prints any integer's bits. Done when I
can predict each overflow case above without running it and catch the
undefined ones with `-fsanitize=undefined`.

</Level>

</Levels>

**Concept 2 of 11: floating point**

<Levels label="Floating point">

<Level name="Beginner">


A float is a sign, an exponent and a fraction, like scientific notation in
base 2. Most decimal fractions, 0.1 among them, have no exact binary form.


</Level>
<Level name="Intermediate">


`0.1 + 0.2` gives the nearest double to the true sum, which is not the
nearest double to 0.3, so `0.1 + 0.2 === 0.3` is false. Compare with a
tolerance, or work in integers.

```ts
0.1 + 0.2;                          // 0.30000000000000004
Number.isSafeInteger(2 ** 53 + 1);  // false
1e16 + 1 === 1e16;                  // true
```


</Level>
<Level name="Advanced">


A double has 53 bits of significand, about 15 to 17 decimal digits. Rounding
is to nearest, ties to even. Special values: ±0, ±Infinity, NaN, and
denormals for numbers very close to zero.


</Level>
<Level name="Edge cases">


- `NaN !== NaN`; `Object.is(NaN, NaN)` is true. `-0 === 0` but
  `Object.is(-0, 0)` is false.


</Level>
<Level name="Corner cases">


- Summing many small values into a large one loses the small ones; summing
  them first, or Kahan summation, keeps them.
- Addition is not associative, so a parallel sum differs from a serial one.


</Level>
<Level name="Production level">


Money in integer minor units (cents) or a decimal type, never floats. Display
with `toFixed` only at the edge, and never round twice.


</Level>
<Level name="Mindset">


A float is an approximation with a known error. Know the error budget.


</Level>
<Level name="System design">


JSON numbers are doubles in JavaScript, so a value that is exact in a
database can change on the way through an API.


</Level>
<Level name="Strategy">


Write a C program that prints a float's sign, exponent and fraction bits,
and check three values by hand. Done when I can explain `0.1 + 0.2` from the
bits.

</Level>

</Levels>

**Concept 3 of 11: gates, combinational and sequential logic, a simple CPU**

<Levels label="Gates, logic and a simple CPU">

<Level name="Beginner">


Gates compute Boolean functions: AND, OR, NOT, and NAND, from which all the
others can be built. Combinational logic has no memory: its output depends
only on its inputs.


</Level>
<Level name="Intermediate">


A full adder adds two bits and a carry; chaining them adds words. A
multiplexer picks one of its inputs. An ALU is adders and multiplexers
controlled by function bits.

```text
sum   = a XOR b XOR cin
carry = (a AND b) OR (cin AND (a XOR b))
```


</Level>
<Level name="Advanced">


Sequential logic adds state: a flip-flop holds a bit until the clock edge.
Registers are flip-flops; memory is many registers with an address decoder.
A CPU is an ALU, registers, memory and a control unit that fetches
instructions and sets the control bits.


</Level>
<Level name="Edge cases">


- A ripple-carry adder's delay grows with the word size, which is why fast
  adders look ahead at carries.


</Level>
<Level name="Corner cases">


- An input changing just before the clock edge: the flip-flop's setup time
  is violated and the value is uncertain, which is why designs synchronise
  inputs from other clocks.


</Level>
<Level name="Production level">


I will not design hardware, but the clock, the critical path and setup time
explain clock speeds, and the gates explain why bitwise operations are the
cheapest instructions.


</Level>
<Level name="Mindset">


Everything is built from something simpler. A CPU is NAND gates and a clock,
in layers.


</Level>
<Level name="System design">


Combinational versus sequential is pure functions versus state; the clock is
a synchronous system's global tick.


</Level>
<Level name="Strategy">


Do the Nand2Tetris hardware projects up to the CPU, reading COD's appendix A
alongside. Done when my CPU runs the course's test programs.

</Level>

</Levels>

**Concept 4 of 11: instruction sets, registers, addressing modes, assembly**

<Levels label="Instruction sets, registers, addressing and assembly">

<Level name="Beginner">


An instruction set is the list of operations a processor understands. x86-64
has sixteen general-purpose 64-bit registers; RISC-V has 32. Assembly is the
readable form of machine instructions.


</Level>
<Level name="Intermediate">


Addressing modes say where an operand is: a constant, a register, or memory
at an address computed from registers. In x86-64, `8(%rbp)` is "memory at
rbp plus 8", and `(%rdi,%rsi,4)` is "memory at rdi plus rsi times 4", an
array index in one operand.

```c
int get(int *a, long i) { return a[i]; }
/* gcc -O1:  movl (%rdi,%rsi,4), %eax
             ret                         */
```


</Level>
<Level name="Advanced">


The calling convention (System V on Linux x86-64) passes the first six
integer arguments in `rdi, rsi, rdx, rcx, r8, r9` and returns in `rax`. Some
registers are saved by the caller, some by the callee. The stack holds return
addresses, saved registers and locals that do not fit in registers.


</Level>
<Level name="Edge cases">


- Writing a 32-bit register (`eax`) zeroes the upper half of `rax`; writing
  `ax` does not.


</Level>
<Level name="Corner cases">


- At `-O0`, every variable lives on the stack, and the assembly looks
  nothing like the optimised version. Read optimised output to learn what
  ships, and `-Og` to learn with.


</Level>
<Level name="Production level">


Compiler Explorer and `objdump -d` are how I check that a hot loop was
vectorised or that a bounds check went away. Crash reports show addresses
and instructions.


</Level>
<Level name="Mindset">


The compiler is a translator I can check. When unsure, read its output.


</Level>
<Level name="System design">


The calling convention is the ABI that lets C, Rust and Node native addons
call each other.


</Level>
<Level name="Strategy">


Do Bomb Lab with gdb, and explain a compiler-generated listing of one of my C
functions line by line, which is one of the phase builds. Done when I can say
what a short function does from its assembly alone, the gate's first item.

</Level>

</Levels>

**Concept 5 of 11: fetch–decode–execute, pipelining, hazards, branch prediction**

<Levels label="Fetch–decode–execute, pipelining, hazards and branch prediction">

<Level name="Beginner">


The CPU repeats a cycle: fetch the instruction at the program counter,
decode it, execute it, access memory if needed, write the result, and move
to the next instruction.


</Level>
<Level name="Intermediate">


Pipelining overlaps the stages so several instructions are in flight at
once, one per stage. Throughput rises; each instruction's latency does not
fall.

<Flow caption="The classic five-stage pipeline" steps={["fetch", "decode and read registers", "execute", "memory access", "write back"]} />


</Level>
<Level name="Advanced">


Data hazards (an instruction needs a result not yet written) are solved by
forwarding, or by a stall when a load's result is needed at once. Control
hazards (a branch) are solved by prediction; a wrong guess flushes the
pipeline, costing around 15 to 20 cycles on modern cores.


</Level>
<Level name="Edge cases">


- A branch that always goes the same way costs almost nothing; a random one
  mispredicts about half the time.


</Level>
<Level name="Corner cases">


- Sorting data before a loop with a data-dependent `if` can make the loop
  several times faster, with the same instructions, purely from prediction.

```c
for (size_t i = 0; i < n; i++) if (a[i] >= 128) sum += a[i];
/* sorted a: predictable branch; random a: many mispredictions */
```


</Level>
<Level name="Production level">


Branchless code (conditional moves, arithmetic masks) helps on
unpredictable data; compilers do it when they can. Speculative execution
leaks (Spectre) come from this machinery.


</Level>
<Level name="Mindset">


Throughput and latency are different numbers. Ask which one matters.


</Level>
<Level name="System design">


Pipelines with hazards appear in CI, data pipelines and request processing;
stalls and flushes are the same problem.


</Level>
<Level name="Strategy">


Run the sorted-versus-random branch benchmark in C with `perf stat -e
branch-misses`, and trace a short loop through a five-stage pipeline on
paper. Done when the miss counts explain the time difference.

</Level>

</Levels>

**Concept 6 of 11: caches**

<Levels label="Caches">

<Level name="Beginner">


A cache is small fast memory holding recently used data. Programs that
reuse data (temporal locality) or use nearby data (spatial locality) hit
the cache.


</Level>
<Level name="Intermediate">


Data moves in lines, usually 64 bytes. An address splits into a tag, a set
index and an offset. A set-associative cache has several lines per set.
Write-back caches write a dirty line to memory only on eviction.

```c
/* ijk vs ikj matrix multiply: same work, different strides */
for (i = 0; i < n; i++) for (k = 0; k < n; k++) {
    double r = A[i][k];
    for (j = 0; j < n; j++) C[i][j] += r * B[k][j];   /* stride 1 */
}
```


</Level>
<Level name="Advanced">


Misses are cold, conflict or capacity. Associativity cuts conflicts; a
bigger cache cuts capacity misses; blocking (tiling) a loop keeps the
working set in cache.


</Level>
<Level name="Edge cases">


- A matrix whose row size is a power of two can map every row to the same
  sets and thrash.


</Level>
<Level name="Corner cases">


- False sharing: two threads write different variables in the same line,
  and coherence bounces the line between cores. Padding each variable to its
  own line fixes it.


</Level>
<Level name="Production level">


Arrays of numbers beat arrays of objects in JavaScript partly because of
locality; typed arrays are contiguous. Column stores in analytics databases
use the same idea.


</Level>
<Level name="Mindset">


The cost of a program is mostly the cost of moving data. Ask where the data
is.


</Level>
<Level name="System design">


Every cache in a system shares the vocabulary: lines or objects, hit rate,
eviction, write policy, coherence.


</Level>
<Level name="Strategy">


Write the plan's cache simulator for traces (configurable sets, lines and
block size, LRU), compare with cachegrind, and run the matrix multiply in
all six loop orders. Done when I can explain with a measurement why the
cache-friendly order is faster, the gate's second item.

</Level>

</Levels>

**Concept 7 of 11: the memory hierarchy**

<Levels label="The memory hierarchy">

<Level name="Beginner">


Registers, L1, L2, L3, main memory, SSD and disk: each level is bigger and
slower than the one above.


</Level>
<Level name="Intermediate">


Rough costs: a register in under a cycle, L1 in a few cycles, L3 in tens,
main memory in around a hundred, an SSD in tens of microseconds, a disk in
milliseconds. A miss at one level costs a trip to the next.


</Level>
<Level name="Advanced">


The memory mountain, read throughput against working-set size and stride,
shows each cache as a ridge and stride as a slope. Prefetchers detect
regular strides and fetch ahead, which is why sequential access is fast even
from memory.


</Level>
<Level name="Edge cases">


- A working set just larger than L2 runs at L3 speed: performance drops in
  steps, not smoothly.


</Level>
<Level name="Corner cases">


- Random access over a working set larger than the TLB's reach adds a page
  walk to every cache miss.


</Level>
<Level name="Production level">


Latency numbers decide architecture: a network round trip in a data centre
is microseconds to a millisecond, so one remote call costs more than
thousands of memory accesses.


</Level>
<Level name="Mindset">


Know the latency numbers to an order of magnitude; estimate before
building.


</Level>
<Level name="System design">


Caching tiers (in-process, Redis, database, object storage) mirror the
hardware hierarchy: each tier is bigger, slower and cheaper.


</Level>
<Level name="Strategy">


Write a pointer-chasing benchmark over working sets from 4 KB to 1 GB and
plot latency per access. Done when the plot shows the cache levels at sizes
that match my CPU's specification.

</Level>

</Levels>

**Concept 8 of 11: virtual memory, page tables, TLBs and the MMU**

<Levels label="Virtual memory, page tables, TLB and MMU">

<Level name="Beginner">


Each process sees its own virtual addresses. The MMU translates them to
physical addresses page by page, using page tables kept by the OS.


</Level>
<Level name="Intermediate">


With 4 KB pages, the low 12 bits are the offset and pass through; the rest
are the page number, translated through the page table. The TLB caches
recent translations.


</Level>
<Level name="Advanced">


x86-64 uses four (or five) levels of tables so unused regions need no
tables. A page fault calls the OS, which loads the page, maps it, or kills
the process with a segmentation fault. Copy-on-write lets `fork` share
pages until one side writes.


</Level>
<Level name="Edge cases">


- Dereferencing NULL faults because page 0 is unmapped on purpose.


</Level>
<Level name="Corner cases">


- A program can allocate more virtual memory than exists (overcommit) and be
  killed later, on first touch, by the OOM killer.


</Level>
<Level name="Production level">


Resident set size, not virtual size, is what a container's memory limit
counts. Huge pages cut TLB misses for large heaps, which databases and JVMs
use.


</Level>
<Level name="Mindset">


An address is a name the OS maps, not a place in RAM.


</Level>
<Level name="System design">


Process isolation, containers, `mmap`-based databases and shared memory
between processes all rest on this.


</Level>
<Level name="Strategy">


Write a C program that maps a file with `mmap`, forks, and shows
copy-on-write with `/proc/self/maps`, then draw a page-table walk on paper.
Done when I can explain virtual versus physical memory with the drawing, the
gate's last item.

</Level>

</Levels>

**Concept 9 of 11: compilation, linking, loading, static and dynamic libraries**

<Levels label="Compilation, linking, loading and libraries">

<Level name="Beginner">


`gcc` runs the preprocessor, the compiler, the assembler and the linker.
Each `.c` becomes a `.o` with a symbol table; the linker joins them into an
executable.


</Level>
<Level name="Intermediate">


```sh
gcc -c vec.c str.c                          # object files
ar rcs libmylib.a vec.o str.o               # static library
gcc -shared -fPIC vec.c str.c -o libmylib.so  # shared library
gcc main.c -L. -lmylib -o app               # link
```


</Level>
<Level name="Advanced">


Symbol resolution matches each undefined name to one definition. Relocation
fixes addresses. The loader maps the executable's segments into memory, and
the dynamic linker resolves shared-library symbols, lazily through the PLT.


</Level>
<Level name="Edge cases">


- Library order matters for static libraries: list a library after the
  objects that need it.


</Level>
<Level name="Corner cases">


- Two libraries defining the same symbol: the first one wins silently, and
  a function I thought I called is someone else's.


</Level>
<Level name="Production level">


"It works on my machine" is often a shared library version. `ldd`,
`LD_LIBRARY_PATH` and static builds in containers address it.


</Level>
<Level name="Mindset">


When a build fails, find which tool failed: preprocessor, compiler,
assembler or linker. Each has its own kind of error.


</Level>
<Level name="System design">


Static linking gives one self-contained file; dynamic linking gives shared
updates and smaller files. Container images make the same trade.


</Level>
<Level name="Strategy">


Build the phase's C dynamic array and string library as both a static and a
shared library and inspect them with `nm` and `readelf`. Done when I can fix
an "undefined reference" error by reasoning, not by searching.

</Level>

</Levels>

**Concept 10 of 11: I/O, interrupts, DMA and memory-mapped I/O**

<Levels label="I/O, interrupts, DMA and memory-mapped I/O">

<Level name="Beginner">


Devices are slow, so the CPU does not wait for them. A device raises an
interrupt when it has finished, and the CPU switches to a handler.


</Level>
<Level name="Intermediate">


Memory-mapped I/O puts device registers at physical addresses, so the CPU
talks to a device with ordinary loads and stores. DMA lets a device copy
data to or from memory without the CPU touching each byte.


</Level>
<Level name="Advanced">


An interrupt saves the current state, runs the kernel's handler, and
returns. System calls use a trap, a deliberate exception, to enter the
kernel. High-rate devices switch between interrupts and polling to avoid
an interrupt storm.


</Level>
<Level name="Edge cases">


- A read on a socket with no data blocks, or returns `EAGAIN` in
  non-blocking mode.


</Level>
<Level name="Corner cases">


- A DMA buffer cached by the CPU: the device writes memory while the cache
  holds stale data, so drivers must manage coherence or use uncached
  buffers.


</Level>
<Level name="Production level">


Node's event loop is built on this: the kernel signals readiness (epoll,
kqueue), and libuv runs callbacks. Zero-copy (`sendfile`) uses DMA to skip
user space.


</Level>
<Level name="Mindset">


Do not wait for slow things; ask to be told when they are done.


</Level>
<Level name="System design">


Event-driven servers, interrupt coalescing in network cards and batched
writes are the same trade: latency against overhead per event.


</Level>
<Level name="Strategy">


Read CS:APP's sections on exceptions and Unix I/O, run `strace` on a Node
HTTP server to see the system calls, and write a C program that reads a file
with `read` in a loop. Done when I can explain where an interrupt, a trap
and DMA happen in one request.

</Level>

</Levels>

**Concept 11 of 11: performance, profiling, perf and cachegrind**

<Levels label="Performance and profiling">

<Level name="Beginner">


Measure before optimising. A profiler shows where time goes; the answer is
rarely where I guessed.


</Level>
<Level name="Intermediate">


```sh
perf stat -e cycles,instructions,cache-misses,branch-misses ./app
perf record -g ./app && perf report
valgrind --tool=cachegrind ./app && cg_annotate cachegrind.out.*
```

`perf stat` gives counters; `perf record` gives a sampled profile;
cachegrind simulates the caches and attributes misses to lines.


</Level>
<Level name="Advanced">


Instructions per cycle tells me whether the CPU is busy or waiting.
Low IPC with many cache misses means memory-bound; many branch misses
means prediction. Fix the bound I have, not the one I imagine.


</Level>
<Level name="Edge cases">


- A benchmark that runs once measures cold caches and the loader. Warm up,
  repeat, and report the spread.


</Level>
<Level name="Corner cases">


- The optimiser deletes a benchmark loop whose result is unused; the
  measured time is zero and wrong. Use the result.


</Level>
<Level name="Production level">


Node has `--cpu-prof` and `--heap-prof`, and Linux `perf` works on Node with
`--perf-basic-prof`. The process is the same: measure, form a hypothesis,
change one thing, measure again.


</Level>
<Level name="Mindset">


No optimisation without a number before and after.


</Level>
<Level name="System design">


Production profiling (continuous profilers, flame graphs) is the same idea
across a fleet: sample everywhere, aggregate, find the hot path.


</Level>
<Level name="Strategy">


Profile my matrix multiply and my cache simulator with `perf` and
cachegrind, and write the before and after numbers for one change in the
README. Done when every speed claim in the phase has a measurement next to
it.

</Level>

</Levels>
