Three weeks under the syntax. I already write TypeScript every day; this phase is about what that
code stands on: where values live, how long they live, what a call does to the stack, and what
happens when a file, an input or an allocation goes wrong. The books are
<a href={withBase('/books/c-programming-a-modern-approach/')}>C Programming: A Modern Approach</a>, with
<a href={withBase('/books/the-c-programming-language/')}>The C Programming Language</a> as the terse
second read. The build is one CLI tool written twice, in C and in TypeScript.

#### Phase 1: how I would learn it

Each topic below gets the same treatment: read the King chapter, write a tiny C program that shows the
idea, write the TypeScript twin, and write down where the two differ. Then the idea goes into the
real tool. I pick a word-frequency counter, because it touches every topic: files, strings, a hash
table, errors, and a large input.

#### Phase 1: Values, types, variables, scope and lifetime

<Levels label="Phase 1, values, types, variables, scope and lifetime">

<Level name="Beginner">

A variable is a name for a place that holds a value of some type. In C the type fixes the size and
meaning of the bytes; in TypeScript the type exists only at compile time and the run-time value
carries its own tag.

</Level>

<Level name="Intermediate">

Scope is where a name is visible; lifetime is how long the place exists. A C local lives until its
block ends; a `static` local lives for the whole program; a `malloc` block lives until `free`. In
TypeScript, a closure keeps a local alive as long as the closure is reachable.

```ts
function counter() { let n = 0; return () => ++n; }  // n outlives the call
```

</Level>

<Level name="Advanced">

C has automatic, static, allocated and thread storage durations. Reading an uninitialised automatic
variable gives an indeterminate value. TypeScript's `let` has a temporal dead zone: the name exists
from the block's start but cannot be read before its declaration runs.

</Level>

<Level name="Edge cases">

Zero-length arrays are not allowed in standard C. A variable shadowed in an inner block hides the
outer one. A `const` object in TypeScript is still mutable inside.

</Level>

<Level name="Corner cases">

A closure created in a loop plus `var`: every closure sees the same variable and the last value. With
`let`, each iteration gets its own binding. Scope rules meet lifetime.

</Level>

<Level name="Production level">

Lifetime bugs are the top source of memory-safety vulnerabilities in C and of leaks in long-running
JavaScript (closures and listeners that keep large objects alive).

</Level>

<Level name="Mindset">

Every value has an owner and an end. Ask where it lives and when it dies.

</Level>

<Level name="System design">

Request-scoped, session-scoped and process-scoped state in a server are lifetimes at system scale.

</Level>

<Level name="Strategy">

For ten variables in my tool, write down scope, lifetime and where the storage lives. Done when the C
version's every variable has an answer and ASan agrees.

</Level>

</Levels>

#### Phase 1: Control flow, functions, recursion and iteration

<Levels label="Phase 1, control flow, functions, recursion and iteration">

<Level name="Beginner">

`if`, loops and function calls decide what runs next. A function takes arguments and returns a value.
Recursion is a function that calls itself on a smaller input.

</Level>

<Level name="Intermediate">

Any recursion can be written as a loop with an explicit stack, and tail recursion as a plain loop.
Choosing between them is a question of clarity and of stack depth.

```c
long fact_iter(int n) { long r = 1; while (n > 1) r *= n--; return r; }
long fact_rec(int n)  { return n <= 1 ? 1 : n * fact_rec(n - 1); }
```

</Level>

<Level name="Advanced">

Each call pushes a frame with arguments, locals and a return address; returning pops it. C passes
arguments by value. JavaScript does too, but the value of an object is a reference, so the callee can
mutate the caller's object.

</Level>

<Level name="Edge cases">

Recursion with no base case, or with a base case unreachable from some inputs, overflows the stack.
`fact` of 0 is 1. `fact` of 21 overflows a 64-bit `long`.

</Level>

<Level name="Corner cases">

Deep recursion plus large locals: each frame is big, so the stack runs out at a depth that would be
fine for a small frame. Depth meets frame size.

</Level>

<Level name="Production level">

Recursing over user-controlled structure (nested JSON, a directory tree) needs a depth limit or an
explicit stack, or a hostile input crashes the process.

</Level>

<Level name="Mindset">

Choose the form that makes the invariant obvious, then check the depth.

</Level>

<Level name="System design">

Recursive descent parsers, tree walkers and retry loops are the same choice at larger scale.

</Level>

<Level name="Strategy">

Write three functions both ways and measure the maximum depth before a crash. Done when I can predict
roughly where it overflows from the frame size and the stack limit.

</Level>

</Levels>

#### Phase 1: The stack and the heap; value and reference semantics

<Levels label="Phase 1, the stack and the heap; value and reference semantics">

<Level name="Beginner">

The stack holds function frames and is freed automatically on return. The heap holds blocks that live
until they are freed (in C) or unreachable (in JavaScript).

</Level>

<Level name="Intermediate">

A struct copied in C copies all its bytes; an object assigned in JavaScript copies a reference. Passing a
large struct by pointer avoids the copy and lets the callee change it.

</Level>

<Level name="Advanced">

`malloc` asks an allocator for a block, which may ask the operating system for more memory. A garbage
collector finds unreachable objects and reclaims them. Primitives in JavaScript behave like values;
objects behave like shared references.

</Level>

<Level name="Edge cases">

`malloc(0)` may return null or a unique pointer. `free(NULL)` is allowed and does nothing. A
`structuredClone` of an object with a function in it throws.

</Level>

<Level name="Corner cases">

A struct holding a pointer, copied by value and then freed through both copies: a double free. In
JavaScript, a shallow spread of an object with a nested array: both copies share the array.

```ts
const a = { tags: ['x'] };
const b = { ...a };
b.tags.push('y');   // a.tags is now ['x', 'y'] too
```

</Level>

<Level name="Production level">

Unexpected sharing causes the hardest bugs in UI state and caches. In C, every heap block needs one
clear owner who frees it.

</Level>

<Level name="Mindset">

Copy or share is a decision. Make it on purpose, and write it down.

</Level>

<Level name="System design">

Immutability, copy-on-write and ownership are system-level answers to the same question; Phase 3
returns to persistent structures.

</Level>

<Level name="Strategy">

Draw the stack and heap for my tool at three points in its run. Done when the drawing matches what
`gdb` shows.

</Level>

</Levels>

#### Phase 1: Pointers, addresses, arrays and pointer arithmetic

<Levels label="Phase 1, pointers, addresses, arrays and pointer arithmetic">

<Level name="Beginner">

A pointer holds an address. `&x` takes it, `*p` follows it, and `p + 1` points to the next element of
the same type.

</Level>

<Level name="Intermediate">

Arrays decay to pointers when passed, so functions take a pointer and a length. Strings are arrays of
`char` ending in a zero byte.

</Level>

<Level name="Advanced">

Pointer arithmetic is defined only inside one array and one past its end. `a[i]` is `*(a + i)`.
Comparing pointers into different objects is undefined. Typed arrays in JavaScript are the closest
twin: a view with an offset and a length over a buffer.

</Level>

<Level name="Edge cases">

A null pointer must not be followed. The one-past-the-end pointer can be compared but not read. An
empty string is a single zero byte.

</Level>

<Level name="Corner cases">

A dangling pointer to a freed block that happens to still hold the old data: the test passes, and
production, after the block is reused, does not. Lifetime meets aliasing.

</Level>

<Level name="Production level">

Bounds are the most common C vulnerability; pass lengths, check them, and run ASan in CI.

</Level>

<Level name="Mindset">

Draw the boxes before writing the line.

</Level>

<Level name="System design">

Zero-copy I/O, buffers and memory-mapped files are pointer arithmetic at system scale.

</Level>

<Level name="Strategy">

Implement `strlen`, `strcpy` with a bound, and a dynamic array with pointers only. Done when ASan is
clean on fuzzed input and I can draw each call.

</Level>

</Levels>

#### Phase 1: Input, output, files and process exit codes

<Levels label="Phase 1, input, output, files and process exit codes">

<Level name="Beginner">

Programs read from standard input or files and write to standard output. Errors go to standard error.
The exit code says whether it worked.

</Level>

<Level name="Intermediate">

The tool takes a path or reads standard input, streams line by line, and returns distinct codes for
usage errors, unreadable files and invalid input.

</Level>

<Level name="Advanced">

C streams are buffered; system calls are not. `fgets` handles long lines by returning partial ones.
In Node, `process.exitCode` lets pending writes finish where `process.exit()` may cut them off.

</Level>

<Level name="Edge cases">

An empty file, a file with no final newline, a missing file and a file that is a directory each need
a defined behaviour.

</Level>

<Level name="Corner cases">

Output to a closed pipe (`tool big.txt | head -1`): C gets `SIGPIPE` and dies, Node gets an `EPIPE`
error, and both must not report failure loudly in that normal case. Buffering meets the pipe closing.

</Level>

<Level name="Production level">

Exit codes and output format are an API for scripts and CI. Check the result of the final write and
`fclose`.

</Level>

<Level name="Mindset">

A tool is judged by how it behaves when things go wrong.

</Level>

<Level name="System design">

Unix pipelines, CI steps and container health checks all compose programs through exit codes and
streams.

</Level>

<Level name="Strategy">

Test each failure path from a shell script that checks exit codes. Done when every failure prints one
line to `stderr` and returns its own documented code.

</Level>

</Levels>

#### Phase 1: Errors as values, exceptions and crashes

<Levels label="Phase 1, errors as values, exceptions and crashes">

<Level name="Beginner">

Three ways to fail: return an error value (C's `-1` and `errno`, Go's `err`), throw an exception
(JavaScript), or crash (a segfault, an abort).

</Level>

<Level name="Intermediate">

C checks return values at every call; TypeScript can model results as values with a union type,
which makes the error path impossible to ignore.

```ts
type Result<T> = { ok: true; value: T } | { ok: false; error: string };
function parseCount(s: string): Result<number> {
  const n = Number(s);
  return Number.isInteger(n) && n >= 0 ? { ok: true, value: n } : { ok: false, error: `bad count: ${s}` };
}
```

</Level>

<Level name="Advanced">

Exceptions unwind the stack to the nearest handler; C has no unwinding, so every resource must be
released on every path. A segfault is the operating system stopping a process that touched memory it
does not own: a feature, not a punishment.

</Level>

<Level name="Edge cases">

`errno` is only meaningful right after a call that reported failure. A `catch` that swallows everything
hides bugs. A rejected promise with no handler terminates a Node process by default.

</Level>

<Level name="Corner cases">

An error inside error handling: cleanup code that itself fails, during an exception, hides the
original error. Two failures at once.

</Level>

<Level name="Production level">

Expected failures (bad input) are values with a message; unexpected ones (bugs) crash early with a
stack trace. Mixing them up gives either noise or silence.

</Level>

<Level name="Mindset">

Decide which failures are normal. Handle those; let the rest crash loudly.

</Level>

<Level name="System design">

Retries, circuit breakers and dead-letter queues are error handling at system scale.

</Level>

<Level name="Strategy">

Classify every failure in my tool as expected or a bug and handle each accordingly. Done when no
error path is silent and no expected failure prints a stack trace.

</Level>

</Levels>

#### Phase 1: Testing, debugging and reading a stack trace

<Levels label="Phase 1, testing, debugging and reading a stack trace">

<Level name="Beginner">

A test runs code on a known input and checks the output. A debugger stops the program to inspect it.
A stack trace lists the calls that led to an error.

</Level>

<Level name="Intermediate">

The tool's suite covers the gate's four cases: happy path, empty file, invalid input and a large file,
in both languages, run by `make check`.

</Level>

<Level name="Advanced">

Read a stack trace from the top for where, and down for why. `gdb` with a core file shows the state at
the crash; breakpoints, watchpoints and `bt` find the rest. Property-based tests generate inputs.

</Level>

<Level name="Edge cases">

Tests that only use small inputs miss the large-file case. A test that never fails proves nothing:
make it fail once.

</Level>

<Level name="Corner cases">

A flaky test caused by time or ordering plus a real bug: the real failure is dismissed as flake.

</Level>

<Level name="Production level">

CI runs tests and sanitizers on every push; a crash in production needs symbols to be readable.

</Level>

<Level name="Mindset">

Reproduce first, then fix, then add the test that would have caught it.

</Level>

<Level name="System design">

Tests are the feedback loop of every later system; debugging is how I learn what the system really
does.

</Level>

<Level name="Strategy">

Plant five bugs in the tool and find each with a test or the debugger. Done when I can debug a crash
with `gdb` and find a leak with Valgrind or ASan, the phase gate's words.

</Level>

</Levels>

#### Phase 1: Complexity: counting operations

<Levels label="Phase 1, complexity: counting operations">

<Level name="Beginner">

Count how many times the inner work runs as the input grows. A loop over `n` lines is linear; a loop
inside a loop over the same lines is quadratic.

</Level>

<Level name="Intermediate">

The word counter with a hash table is linear in the input; with a list searched for each word, it is
quadratic. A benchmark at sizes ten times apart shows the difference.

</Level>

<Level name="Advanced">

Big O ignores constants and small inputs; amortised cost averages occasional expensive steps, such as
a dynamic array doubling.

</Level>

<Level name="Edge cases">

Tiny inputs hide everything; the quadratic version is faster for ten words.

</Level>

<Level name="Corner cases">

String concatenation in a loop in C (`strcat` from the start each time) plus a large file is quadratic
hidden inside a library call.

</Level>

<Level name="Production level">

Most performance incidents are an accidental quadratic on input that grew. Benchmarks belong in the
repo.

</Level>

<Level name="Mindset">

Count, then measure. A claim without a number is a guess.

</Level>

<Level name="System design">

Capacity planning is complexity with constants; Phase 4 makes it rigorous.

</Level>

<Level name="Strategy">

Benchmark the tool at one, ten and a hundred megabytes. Done when the measured growth matches what
I predicted by counting.

</Level>

</Levels>

#### Phase 1: the gate

I can explain every line of the C version, including the lifetime of each allocation. The tests cover
the happy path, an empty file, invalid input and a large file. I can debug a crash with `gdb` and find
a leak with Valgrind or ASan. I check it by explaining the C tool line by line to an imagined reviewer,
out loud, with the code open and nothing else.
