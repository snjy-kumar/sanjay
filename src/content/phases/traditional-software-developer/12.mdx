Five weeks on one system, built properly. No new book is primary here: I go back to the book behind
the system I pick, and to that system's own papers and documentation. For a compiler that is
<a href={withBase('/books/crafting-interpreters/')}>Crafting Interpreters</a>; for a key-value store
it is the phase 10 reading and
<a href={withBase('/books/distributed-systems-tanenbaum-van-steen/')}>Distributed Systems</a>; the
security review leans on <a href={withBase('/books/security-engineering/')}>Security Engineering</a>.
After the capstone come the plan's two closing sections, retention and the AI policy, which are
strategies for every phase and so live here, at the end.

#### Phase 12: how I would learn it

I treat the capstone like a real project with a stranger as its user. Week 54 is design only: the
design doc, the first ADRs and the threat model, with no code beyond spikes. Weeks 55 to 57 are
build weeks, each ending with a benchmark run and a failure test. Week 58 is for evidence: the
security review, the postmortem, the README test on a clean machine and the write-up. I keep a
decision log from the first day, because the gate asks me to defend every choice and memory will not.

#### Phase 12: Choosing one system and going deep

<Levels label="Phase 12, choosing one system and going deep">

<Level name="Beginner">

The capstone is one system from the list, built far enough that it is real: it runs, it has users (even
if the user is me), and it fails in ways I understand.

</Level>

<Level name="Intermediate">

I choose by two questions: which phase do I understand least, and which system would I most enjoy
debugging at night. The second matters more; five weeks needs curiosity.

</Level>

<Level name="Advanced">

Depth means one feature taken all the way: recovery that survives a crash at any point, a planner
that picks the right index, a VM that collects its garbage. Breadth is the trap.

</Level>

<Level name="Edge cases">

A system too small to fail interestingly teaches nothing about failure. It needs state, concurrency or
untrusted input.

</Level>

<Level name="Corner cases">

A system too big to finish, plus a fixed deadline, ends with nothing working. Non-goals protect the
deadline.

</Level>

<Level name="Production level">

I scope like a team would: a minimum that runs end to end in week 55, then depth, never the other way.

</Level>

<Level name="Mindset">

The point is depth, not breadth. One thing understood completely beats six understood partly.

</Level>

<Level name="System design">

Whatever I pick connects back to two or three earlier phases. The capstone is the integration test of
the whole plan.

</Level>

<Level name="Strategy">

I write one paragraph per candidate system naming what it would teach me and what could sink it, then
pick. Done when the choice and its non-goals are the first ADR.

</Level>

</Levels>

#### Phase 12: The design doc: goals, non-goals, constraints and tradeoffs

<Levels label="Phase 12, the design doc">

<Level name="Beginner">

A design doc says what I am building and why, before I build it.

</Level>

<Level name="Intermediate">

Goals are what must be true at the end. Non-goals are what I deliberately will not do. Constraints are
fixed facts (time, language, hardware). Tradeoffs are the choices with their costs.

```md
## Goals
- Survive a crash at any write and recover all committed data.
## Non-goals
- Multi-node replication. SQL beyond SELECT, INSERT, UPDATE, DELETE.
## Tradeoffs
- Write-ahead log over shadow paging: simpler recovery, more write traffic.
```

</Level>

<Level name="Advanced">

Each tradeoff names the alternative I rejected and why. That is what the gate asks me to defend.

</Level>

<Level name="Edge cases">

A goal with no way to check it ("fast"). Every goal gets a number or a test.

</Level>

<Level name="Corner cases">

Two goals that conflict under one condition (durability and latency on every write). The doc states
which wins.

</Level>

<Level name="Production level">

The doc is short, in the repository, and updated when reality changes the plan.

</Level>

<Level name="Mindset">

Writing finds design bugs that code would find a week later and at higher cost.

</Level>

<Level name="System design">

The design doc is the parent of the ADRs, the threat model and the benchmark plan.

</Level>

<Level name="Strategy">

I write the doc in week 54 and ask a reviewer (a peer, or AI after my first draft) to find a missing
non-goal or an unchecked goal. Done when every goal has a test or number and every tradeoff names a
rejected alternative.

</Level>

</Levels>

#### Phase 12: An ADR for every decision I would otherwise forget

<Levels label="Phase 12, architecture decision records">

<Level name="Beginner">

An ADR is a short note recording one decision, its context and its consequences.

</Level>

<Level name="Intermediate">

I write one whenever I choose between real alternatives: a data structure, a protocol, a library, a
format.

</Level>

<Level name="Advanced">

ADRs are immutable once accepted. A changed decision gets a new ADR that supersedes the old one, so
the history of thinking survives.

</Level>

<Level name="Edge cases">

Trivial choices do not need ADRs. If I would not forget it or regret it, skip it.

</Level>

<Level name="Corner cases">

Two ADRs that each made sense alone and together imply something neither intended. Reading them as a
set in week 57 catches this.

</Level>

<Level name="Production level">

Numbered files in `docs/adr/`, linked from the design doc, written the day of the decision.

</Level>

<Level name="Mindset">

Future me has no context. Write for future me.

</Level>

<Level name="System design">

ADRs are how a system's architecture stays explainable after its authors move on.

</Level>

<Level name="Strategy">

I write an ADR the day of each real decision. Done when I can answer "why this and not that" for every
major part of the capstone by pointing to one.

</Level>

</Levels>

#### Phase 12: Tests, including property-based tests and failure tests

<Levels label="Phase 12, tests including property and failure tests">

<Level name="Beginner">

Tests prove the capstone does what the design doc promised.

</Level>

<Level name="Intermediate">

Unit tests for components, integration tests for paths, property tests for invariants (the index
always agrees with the table, the log always replays to the same state).

</Level>

<Level name="Advanced">

Failure tests break things on purpose: kill the process mid-write, drop packets, fill the disk, and
check the system recovers to a correct state.

```ts
for (let i = 0; i < 500; i++) {
  const db = await open(dir);
  await writeRandom(db, seed + i);
  crashAt(randomPoint(seed + i)); // simulate power loss
  const recovered = await open(dir);
  expect(await recovered.check()).toBe('consistent');
}
```

</Level>

<Level name="Edge cases">

A crash during recovery itself. Recovery must be restartable.

</Level>

<Level name="Corner cases">

A failure at the exact boundary between two operations (after the log write, before the data write)
is where most recovery bugs live.

</Level>

<Level name="Production level">

All tests seeded and reproducible; failing seeds saved as regression tests.

</Level>

<Level name="Mindset">

A system I have not seen fail is a system I do not understand.

</Level>

<Level name="System design">

Failure tests are the executable form of the failure matrix.

</Level>

<Level name="Strategy">

I write the invariants first, then the property and failure tests, then the code. Done when hundreds
of randomised crash runs end consistent and every found bug has a regression test.

</Level>

</Levels>

#### Phase 12: Benchmarks with numbers and a baseline

<Levels label="Phase 12, benchmarks with numbers and a baseline">

<Level name="Beginner">

A benchmark measures how fast or how much. Without a baseline, a number means nothing.

</Level>

<Level name="Intermediate">

The baseline is a known reference: a naive version of my own, or an established system on the same
workload (SQLite, Redis, `nginx`).

</Level>

<Level name="Advanced">

Report distributions, not averages: p50, p99, and throughput at a stated concurrency, on stated
hardware, with warm-up excluded.

</Level>

<Level name="Edge cases">

A benchmark that fits in cache measures the cache. Test with data larger than memory too.

</Level>

<Level name="Corner cases">

An optimisation that speeds up the benchmark and slows the real workload. Keep a realistic workload
beside the micro-benchmark.

</Level>

<Level name="Production level">

Benchmarks are scripted, in the repository, and run in CI or before each release to catch regressions.

</Level>

<Level name="Mindset">

Measure, do not guess. A cache is not fast; it is faster for this access pattern, by this much.

</Level>

<Level name="System design">

Numbers decide tradeoffs in the design doc. Where I guessed, I mark it and measure later.

</Level>

<Level name="Strategy">

I set the baseline in week 55 and rerun after each change. Done when the README has a table of my
numbers against the baseline with hardware and method stated.

</Level>

</Levels>

#### Phase 12: A security review and a threat model

<Levels label="Phase 12, security review and threat model">

<Level name="Beginner">

The security review asks what an attacker could do to my capstone and what stops them.

</Level>

<Level name="Intermediate">

I reuse phase 11's method: data-flow diagram, trust boundaries, STRIDE, and the OWASP checklist where
the system has a web or network surface.

</Level>

<Level name="Advanced">

Each capstone has its own threats: a database's query parser, a store's unauthenticated peer port, a
compiler's untrusted input, a proxy's request smuggling.

</Level>

<Level name="Edge cases">

Local-only tools still take untrusted input (files, network responses).

</Level>

<Level name="Corner cases">

A debug or admin endpoint added during the build week that survives to the demo.

</Level>

<Level name="Production level">

Findings become issues, fixes become tests, accepted risks are written with reasons.

</Level>

<Level name="Mindset">

The review is not a certificate. It is the list of what I know is wrong.

</Level>

<Level name="System design">

Security decisions appear in the ADRs like any other tradeoff.

</Level>

<Level name="Strategy">

I review in week 57 against the threat model from week 54 and update both. Done when every finding is
fixed with a test or accepted with a reason.

</Level>

</Levels>

#### Phase 12: A README a stranger can follow

<Levels label="Phase 12, a README a stranger can follow">

<Level name="Beginner">

The README says what the system is, how to install it, how to run it, and how to test it.

</Level>

<Level name="Intermediate">

Commands are copy-pasteable and in order. Requirements are stated with versions.

</Level>

<Level name="Advanced">

A README is tested like code: a CI job runs its quickstart in a clean container.

</Level>

<Level name="Edge cases">

A step that works only because something is already installed on my machine.

</Level>

<Level name="Corner cases">

A quickstart that runs, plus a default configuration that is insecure: the stranger succeeds and is
exposed.

</Level>

<Level name="Production level">

Quickstart, architecture overview, benchmarks, limits and known issues, with links to the design doc
and ADRs.

</Level>

<Level name="Mindset">

If a stranger cannot run it, it does not exist for anyone but me.

</Level>

<Level name="System design">

The README is the entry point to every other document.

</Level>

<Level name="Strategy">

I give the README to someone who has not seen the project, or a fresh container, and watch without
helping. Done when they run it and its tests with no questions, which is the gate.

</Level>

</Levels>

#### Phase 12: A postmortem: what broke, what I changed, what I would do differently

<Levels label="Phase 12, the capstone postmortem">

<Level name="Beginner">

The postmortem tells the story of the build honestly: what went wrong and what I learned.

</Level>

<Level name="Intermediate">

It covers at least one real failure, the timeline, the cause, the fix and the preventive action.

</Level>

<Level name="Advanced">

The best failure stories show a wrong mental model being corrected, not just a typo found.

</Level>

<Level name="Edge cases">

A build where nothing broke means I did not test hard enough. Break it on purpose.

</Level>

<Level name="Corner cases">

A failure caused by two of my own decisions interacting; that is the story worth telling.

</Level>

<Level name="Production level">

Blameless format, concrete numbers, and actions that are already done or scheduled.

</Level>

<Level name="Mindset">

The failure story is evidence of understanding. Hiding it hides what I learned.

</Level>

<Level name="System design">

What I would do differently becomes the first ADR of the next version.

</Level>

<Level name="Strategy">

I keep a bug log through the build and write the postmortem from it in week 58. Done when it has a
real failure, its cause, and a preventive action that is in the code.

</Level>

</Levels>

#### Phase 12: A demo or a public write-up

<Levels label="Phase 12, a demo or public write-up">

<Level name="Beginner">

The write-up explains the system to someone who did not build it.

</Level>

<Level name="Intermediate">

It covers the problem, the design, the hardest part, the numbers and the failure story.

</Level>

<Level name="Advanced">

A good write-up teaches one idea well, with a diagram, rather than listing every feature.

</Level>

<Level name="Edge cases">

Claims without numbers. Every claim of speed or correctness points to a benchmark or a test.

</Level>

<Level name="Corner cases">

A demo that works only on my machine at the moment of recording.

</Level>

<Level name="Production level">

The write-up links the repository, the README and the benchmarks; the demo uses the README's own
commands.

</Level>

<Level name="Mindset">

Teaching it is the final test of understanding it.

</Level>

<Level name="System design">

The write-up is the design doc rewritten after the fact, with what really happened.

</Level>

<Level name="Strategy">

I write it as the note I wish I had read before starting. Done when someone outside the project can
explain the hardest part back to me after reading it.

</Level>

</Levels>

#### Phase 12: the gate

A stranger runs the capstone from the README. I explain every design decision and the alternatives I
rejected, using the ADRs only as an index, not a script. I show numbers against a baseline, tests
including property and failure tests, and a failure story from the postmortem. And the core code is
mine: written by me first, with any AI help logged and rewritten.

#### Retention: keeping the core, beginner to strategy

The plan closes with how the core stays. These six practices run across every phase, not after them.

<Compare
  left="Practice"
  right="What I do"
  caption="The six retention practices from the plan, turned into a routine"
  rows={[
    ['Spaced repetition for facts', 'A small deck: complexity tables, system calls, TCP states, isolation levels. Ten minutes a day.'],
    ['Re-implementation for skills', 'Once a quarter, one structure or component from a blank file, compared with the old version.'],
    ['Teach-back for understanding', 'A note I wish I had read, without jargon. If I cannot write it, I do not know it.'],
    ['Interleaving for transfer', 'One old topic mixed into each new phase: B-trees with databases, queues with networks.'],
    ['Benchmarks for intuition', 'A number for every claim of fast, with the access pattern stated.'],
    ['A bug log for judgement', 'Symptom, cause, fix, rule. Re-read monthly for patterns.'],
  ]}
/>

<Levels label="Retention, keeping the core">

<Level name="Beginner">

Finishing a phase does not keep it. Using it does. Retention is a small, regular habit, not a review
week.

</Level>

<Level name="Intermediate">

Facts go into spaced repetition; skills are kept by rebuilding; understanding is kept by explaining.
Each kind of knowledge needs its own method.

</Level>

<Level name="Advanced">

Interleaving (mixing old topics into new work) is harder in the moment and better for transfer,
because recalling in a new context strengthens the memory more than rereading.

</Level>

<Level name="Edge cases">

A deck that grows past what I review daily turns into guilt. Keep it small and honest; delete cards I
no longer need.

</Level>

<Level name="Corner cases">

A rebuild that copies the old version from memory without understanding: it looks like retention and
is recall of text. Compare designs, not code.

</Level>

<Level name="Production level">

A calendar: daily cards, a monthly bug-log review, a quarterly rebuild, a note after each phase.

</Level>

<Level name="Mindset">

Forgetting is normal. The routine exists so forgetting is noticed and fixed early.

</Level>

<Level name="System design">

The study log, the bug log, the deck and the notes are one system. Each feeds the others.

</Level>

<Level name="Strategy">

I set up the deck and the bug log in phase 0 and keep them through phase 12. Done when, a quarter
after finishing, I can rebuild one phase's core component from a blank file and explain it without
notes.

</Level>

</Levels>

#### The AI policy, beginner to strategy

<Flow
  caption="Where AI enters the loop, and where it does not"
  steps={['First pass by me, no AI', 'Tests by me', 'AI critique and edge cases', 'I verify each suggestion', 'Retype what I accept', 'Log it', 'Closed-book gate, no AI']}
/>

<Levels label="The AI policy">

<Level name="Beginner">

AI is a tutor, a reviewer and a test generator. It does not write the first pass of a core
implementation.

</Level>

<Level name="Intermediate">

The order matters: I write, then I ask for critique, edge cases and tests, then I verify each
suggestion myself.

</Level>

<Level name="Advanced">

Accepted code is retyped, tested and explained. Code I cannot explain is not mine, however well it
runs.

</Level>

<Level name="Edge cases">

Autocomplete is AI too. In the first pass and at the gate, it is off.

</Level>

<Level name="Corner cases">

A suggestion that is correct for the common case and wrong at a boundary, accepted because the tests
I wrote did not cover that boundary. The delegation log catches it when I review what AI got wrong.

</Level>

<Level name="Production level">

A delegation log: what I asked, what it got wrong, what I learned. Reviewed with the bug log.

</Level>

<Level name="Mindset">

The gate is the moment I find out what I know. Help before it hides the answer.

</Level>

<Level name="System design">

The policy is a workflow with checkpoints: first pass, review, verification, gate. Each checkpoint
has a rule.

</Level>

<Level name="Strategy">

I keep the delegation log from phase 0 and read it before each gate. Done when every gate is passed
closed-book and the log shows AI used as a tool, with my own judgement on every accepted change.

</Level>

</Levels>
