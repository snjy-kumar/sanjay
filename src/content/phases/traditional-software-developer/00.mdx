Two weeks to make the next fourteen months cheap. Nothing here is computer science yet; all of it is
the setup that lets computer science happen without friction: a toolchain I trust, a Linux
environment I can see into, a repository that holds the evidence, and a study log that keeps me
honest. The books are <a href={withBase('/books/the-pragmatic-programmer/')}>The Pragmatic Programmer</a>
(chapters 1, 3 and 4) and, as optional depth, <a href={withBase('/books/the-devops-handbook/')}>The DevOps Handbook</a>
(Parts I and III), with MIT's Missing Semester for the tools.

#### Phase 0: how I would learn it

I would do it in the order the tools depend on each other, and I would not let myself read ahead
into Phase 1. The temptation in week one is to start on pointers; the setup is the point.

#### Phase 0: The C toolchain

<Levels label="Phase 0, the c toolchain">

<Level name="Beginner">

A compiler turns `hello.c` into an executable: `cc -std=c99 -Wall -Wextra -g hello.c -o hello`. `make`
remembers that command. `gdb` or `lldb` stops the program and shows its state. AddressSanitizer and
Valgrind report memory errors the program itself would hide.

</Level>

<Level name="Intermediate">

They combine into one loop: a makefile with a debug build (`-g -O0 -fsanitize=address,undefined`) and a
release build, a `test` target and a `check` target that runs warnings, tests and sanitizers together.

```make
CFLAGS = -std=c99 -Wall -Wextra -Werror -g -O0 -fsanitize=address,undefined
stats: stats.c
	$(CC) $(CFLAGS) $< -o $@
check: stats
	./stats testdata/small.txt
```

</Level>

<Level name="Advanced">

Underneath, `cc` runs the preprocessor, the compiler, the assembler and the linker. Sanitizers work by
instrumenting every memory access at compile time and checking it at run time, which is why they need
the flag at build time and slow the program down. Valgrind instead runs the unmodified binary on a
simulated CPU.

</Level>

<Level name="Edge cases">

An empty source file compiles to an object but does not link: no `main`. A program with no warnings
can still be wrong: the warnings are a floor. `-O2` can make a bug appear or vanish, because undefined
behaviour lets the optimiser assume it never happens.

</Level>

<Level name="Corner cases">

ASan and Valgrind together on one binary do not work: they both want to own memory. And a sanitizer
build on macOS versus Linux reports different leaks, because leak detection is not on everywhere by
default. Two tools meeting two platforms is a real corner.

</Level>

<Level name="Production level">

CI must build with the same flags I use locally, or a bug that the sanitizer would catch locally ships
anyway. The release build keeps warnings as errors and adds hardening flags later, in Phase 11.

</Level>

<Level name="Mindset">

A tool I have not seen catch a bug is a tool I do not trust. Prove each one with a planted error.

</Level>

<Level name="System design">

The toolchain is the bottom of the build system that every later phase depends on: the shell in Phase
6, the server in Phase 7 and the interpreter in Phase 9 all use this makefile's shape.

</Level>

<Level name="Strategy">

Write three broken programs, one out-of-bounds write, one use-after-free and one leak, and catch each
with the right tool. Done when each tool's report points at the planted line and I can read it.

</Level>

</Levels>

#### Phase 0: The Linux environment

<Levels label="Phase 0, the linux environment">

<Level name="Beginner">

A Linux environment where I can see processes, files and permissions: a VM, a container or WSL. `ps`,
`ls -l`, `chmod` and `/proc` show what the operating system is doing.

</Level>

<Level name="Intermediate">

A devcontainer or Dockerfile committed to the repo makes the environment reproducible: anyone, or me
in a year, gets the same compiler and tools with one command.

</Level>

<Level name="Advanced">

Everything is a file or a process. Permissions are bits per owner, group and others. A process has an
ID, a parent, open file descriptors and an exit status, all visible in `/proc`.

</Level>

<Level name="Edge cases">

A file I can read but not execute; a directory I can list but not enter (missing the `x` bit). A
script with Windows line endings fails with a confusing "not found".

</Level>

<Level name="Corner cases">

A bind-mounted folder from a host OS plus Linux permissions: files created inside the container are
owned by root on the host. Two systems' ideas of ownership meet.

</Level>

<Level name="Production level">

The environment a program runs in is part of the program: locale, time zone, file system case
sensitivity. Tests should pin them.

</Level>

<Level name="Mindset">

If I cannot see it, I cannot debug it. Choose environments that show me the system.

</Level>

<Level name="System design">

Containers here, operating systems in Phase 6 and deployment in Phase 11 are the same idea at three
depths: an isolated, reproducible place for a process to run.

</Level>

<Level name="Strategy">

Build the container, then explain every line of its file. Done when a fresh clone builds and tests
with one command inside it.

</Level>

</Levels>

#### Phase 0: The shell and the missing semester

<Levels label="Phase 0, the shell and the missing semester">

<Level name="Beginner">

The shell runs programs and connects them. Pipes send one program's output into another's input:
`cat log.txt | grep ERROR | wc -l`.

</Level>

<Level name="Intermediate">

Small scripts automate what I do twice: run all tests, regenerate a report, clean the build. Missing
Semester's lectures on the shell, scripting, data wrangling and debugging cover exactly this.

</Level>

<Level name="Advanced">

Exit codes connect programs: `0` is success, anything else failure, and `&&`, `||` and `set -e` act on
them. Quoting decides what the shell splits and expands; unquoted variables are the classic bug.

</Level>

<Level name="Edge cases">

A file name with a space breaks an unquoted loop. An empty glob expands to itself. A pipeline's exit
code is its last command's unless `set -o pipefail` is on.

</Level>

<Level name="Corner cases">

`set -e` plus a command inside an `if` or a pipeline: the failure is ignored, so a script that looks
strict is not. Strictness meets the exceptions to strictness.

</Level>

<Level name="Production level">

CI scripts are shell scripts. Every one I write starts with `set -euo pipefail` and quotes every
variable.

</Level>

<Level name="Mindset">

Automate the second time, not the tenth.

</Level>

<Level name="System design">

Pipelines of small programs are a system design: each does one thing, composed by a stable interface.
Phase 6 builds the shell itself.

</Level>

<Level name="Strategy">

Do the Missing Semester exercises for the shell, scripting and data wrangling. Done when my repo's
check script is strict, quoted, and fails loudly on a planted error.

</Level>

</Levels>

#### Phase 0: Git and the public repository

<Levels label="Phase 0, git and the public repository">

<Level name="Beginner">

Git records snapshots. `add`, `commit`, `log`, `diff` and `push` are enough to start. A public repo with
a README is where the plan's evidence lives.

</Level>

<Level name="Intermediate">

One repository for the whole plan, one directory per phase, each with a README, source, tests,
benchmarks and a "what I got wrong" section. Small commits whose messages say what changed and why.

</Level>

<Level name="Advanced">

A commit is a snapshot plus a pointer to its parent; a branch is a movable name for a commit. `bisect`
uses that history to find the commit that broke something in logarithmic steps.

</Level>

<Level name="Edge cases">

The first commit has no parent. An empty directory cannot be committed. A file once committed with a
secret stays in history after deletion.

</Level>

<Level name="Corner cases">

A secret committed, then deleted, then pushed to a public repo: it is public now, and rewriting history
does not un-leak it. Rotate the secret first.

</Level>

<Level name="Production level">

A `.gitignore` from day one, no build outputs committed, CI on every push, and a pre-commit secret
scan by Phase 11.

</Level>

<Level name="Mindset">

The repository is evidence. If it is not committed, it did not happen.

</Level>

<Level name="System design">

Version control is the first distributed system I use every day: clones, merges and conflicts are
replication and reconciliation, which Phase 10 returns to.

</Level>

<Level name="Strategy">

Set up the repo with its directory skeleton and CI, then use `git bisect` to find a planted bug in a
history of ten commits. Done when bisect names the commit without my help.

</Level>

</Levels>

#### Phase 0: The study log and the review rhythm

<Levels label="Phase 0, the study log and the review rhythm">

<Level name="Beginner">

A study log is a dated file: what I did, what broke, what I learned, what is next. One entry per
session, a few lines each.

</Level>

<Level name="Intermediate">

The plan's weekly rhythm is 60 percent implementation, 20 percent reading, 10 percent writing and 10
percent review. The log records which is which, so the ratio is visible instead of guessed.

</Level>

<Level name="Advanced">

Spaced repetition for facts and re-implementation for skills fight the forgetting curve. A monthly
synthesis says what I can now do, what is fuzzy and what I will revisit; a quarterly rebuild proves it.

</Level>

<Level name="Edge cases">

A week with no entry is information too: write "nothing" and why. A log that only records successes is
not a log.

</Level>

<Level name="Corner cases">

A busy week plus a skipped review: the review is what gets dropped first, and it is the part that makes
the rest stick. Protect it on the calendar.

</Level>

<Level name="Production level">

The log becomes interview stories and blog material; a "what I got wrong" section per phase is the
most valuable page in the repo.

</Level>

<Level name="Mindset">

Evidence beats intention. A plan is a guess; the log is data.

</Level>

<Level name="System design">

The log is my observability: the telemetry of a fourteen-month project, the same idea The DevOps
Handbook applies to a team.

</Level>

<Level name="Strategy">

Keep the log daily for the two weeks and write the first synthesis at the end. Done when the synthesis
can be written entirely from the log.

</Level>

</Levels>

#### Phase 0: The baseline programs

<Levels label="Phase 0, the baseline programs">

<Level name="Beginner">

A small C program that reads a file and prints statistics (lines, words, bytes, longest line), and the
same program in TypeScript.

</Level>

<Level name="Intermediate">

Both read from a file named on the command line or from standard input, print the same output, and
return a nonzero exit code with a message on `stderr` when the file is missing.

```ts
import { readFileSync } from 'node:fs';
const path = process.argv[2];
let text: string;
try { text = readFileSync(path ?? 0, 'utf8'); }
catch (e) { console.error(`stats: ${path}: ${(e as Error).message}`); process.exit(1); }
const lines = text.split('\n');
console.log(lines.length - (text.endsWith('\n') ? 1 : 0), text.split(/\s+/).filter(Boolean).length, Buffer.byteLength(text));
```

</Level>

<Level name="Advanced">

The two versions disagree on purpose: TypeScript decodes UTF-8 and counts characters, C counts bytes;
TypeScript reads the whole file into memory, C can stream. The list of "things I had to look up" is the
real output of the baseline.

</Level>

<Level name="Edge cases">

An empty file, a file without a final newline, a binary file and a very large file all produce
different answers or failures in the two versions.

</Level>

<Level name="Corner cases">

A large file plus reading it all into memory: the TypeScript version runs out of memory where the
streaming C version is fine. Size meets a design choice.

</Level>

<Level name="Production level">

Statistics tools are used in scripts; output format and exit codes are an interface. Changing either
breaks someone's pipeline.

</Level>

<Level name="Mindset">

Measure where I start, so that later I can see how far I came.

</Level>

<Level name="System design">

The baseline is a seed: Phase 1 rebuilds it properly as the tested CLI tool.

</Level>

<Level name="Strategy">

Write both versions without a tutorial, compare them on four nasty inputs, and record the lookups.
Done when both are committed, both pass `make check`, and the lookup list is in the log.

</Level>

</Levels>

#### Phase 0: exercises

- Plant one bug per tool (compiler warning, gdb, ASan, Valgrind, bisect) and catch it.
- Write the repo's `make check` and make CI run exactly that.
- Answer the exercises at the end of The Pragmatic Programmer's chapter 3 topics in the log.
- Compare the two baseline programs on an empty file, a file with no final newline, a binary file and
  a 1 GB file, and explain each difference.

#### Phase 0: the gate

A public repo with a README, a study log and two working baseline programs. I can compile, run,
debug and commit without following a tutorial. I check that by doing the whole loop, from a fresh
clone to a fixed planted bug to a green CI run, with no notes open.
