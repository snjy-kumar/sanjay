Seven weeks of turning problems into smaller problems. The primary book is
<a href={withBase('/books/the-algorithm-design-manual/')}>The Algorithm Design Manual</a>,
for how to model a problem and pick a technique, and
<a href={withBase('/books/introduction-to-algorithms/')}>Introduction to Algorithms</a> is
the depth, for the proofs. The phase 3 library is the toolbox: every
algorithm here runs on structures I already wrote. Below is the phase on the
nine levels, how I would learn it, the ten concepts each on nine levels,
the exercises and the gate.

**The learning strategy, on nine levels**

<Levels label="Phase 4, algorithms">

<Level name="Beginner">


An algorithm is a procedure that is correct on every input and has a cost I
can state. The smallest thing that works is brute force: try everything. The
rest of the phase is ways to avoid trying everything.


</Level>
<Level name="Intermediate">


Most problems match a pattern: sort first, binary search on the answer, two
pointers, BFS on a state graph, a greedy rule with a proof, or a DP over a
state I can name. Recognising the pattern is the skill.


</Level>
<Level name="Advanced">


Every algorithm comes with an invariant (why it is correct) and a recurrence
or a sum (why it costs what it costs). If I cannot state both, I do not yet
own the algorithm.


</Level>
<Level name="Edge cases">


Empty input, one element, all equal, already sorted, reversed, and the
maximum size. Those six inputs catch most wrong solutions.


</Level>
<Level name="Corner cases">


Two edges at once: an empty graph with a source vertex, duplicates at the
boundary of a binary search, a DP whose base case is also the answer.


</Level>
<Level name="Production level">


In production I call the library sort and the graph library, but I choose
which one, I know the inputs that make it slow, and I write the test that
proves it handles them.


</Level>
<Level name="Mindset">


Algorithms are not a list of tricks. They are ways of turning a problem into
a smaller one, and the plan says so in its first line for this phase.


</Level>
<Level name="System design">


Schedulers, routers, diff tools, search, build systems and query planners
are all one of these algorithms inside a larger system.


</Level>
<Level name="Strategy">


Thirty to forty problems across the patterns, each with the state, the
invariant, the complexity and one alternative written down, plus the five
builds. Done when I pass the gate: an unseen problem solved while
explaining my reasoning, and the named algorithms from a blank file.

</Level>

</Levels>

**How I would learn it**

I would work pattern by pattern, not problem by problem. For each pattern I
read Skiena's chapter for the idea and the war stories, solve three to five
problems on that pattern, and only then read the CLRS chapter for the proof.
Each problem gets a short note in the repository: the state, the invariant,
the complexity, and one alternative approach with why I did not take it.
That is the plan's rule, and it is what turns 35 problems into a method.

I would use CP-Algorithms when I need a clean reference implementation and
NeetCode's lists to pick problems by pattern, one source per topic. Every
solution runs against a brute force on small random inputs before I
trust it, because a wrong DP that passes three examples is the most common
failure in this phase.

No AI writes my solutions. After I solve one, I may ask for a different
approach and compare it with mine.

**Concept 1 of 10: complexity analysis**

<Levels label="Complexity analysis">

<Level name="Beginner">


Big-O bounds how cost grows from above, Ω from below, Θ both. Count the
basic steps as a function of input size and drop constants and lower terms.


</Level>
<Level name="Intermediate">


Nested loops over n give n squared; halving the range each step gives log n;
a loop inside a halving gives n log n. Space counts too: recursion depth is
memory.


</Level>
<Level name="Advanced">


Amortised analysis bounds a sequence (dynamic array push is amortised O(1)).
Expected cost averages over the algorithm's own randomness. Recurrences are
solved with the master method or a recursion tree.


</Level>
<Level name="Edge cases">


- O(n) with a huge constant can lose to O(n log n) with a tiny one at every
  size I will see.


</Level>
<Level name="Corner cases">


- Hidden costs inside one line: `arr.includes(x)` in a loop is O(n²);
  `str.slice()` in a recursion copies on every call.


</Level>
<Level name="Production level">


Complexity tells me what happens at ten times the data. Measurement tells me
what happens today. I need both in a performance review.


</Level>
<Level name="Mindset">


Before writing a solution, I say its complexity out loud and check that the
input size allows it: around 10^8 simple steps a second is the budget.


</Level>
<Level name="System design">


The growth rate of the hot path decides whether a service scales with
traffic or falls over at the next marketing push.


</Level>
<Level name="Strategy">


Predict the complexity of ten of my own functions, then time each at n and
2n. Done when my predicted ratios match the measured ones.

</Level>

</Levels>

**Concept 2 of 10: recursion, divide and conquer, and backtracking**

<Levels label="Recursion, divide and conquer, and backtracking">

<Level name="Beginner">


A recursive function solves a smaller version of its own problem and has a
base case that stops it. Divide and conquer splits into parts, solves each,
and combines. Backtracking builds a solution step by step and undoes a step
when it leads nowhere.


</Level>
<Level name="Intermediate">


```ts
function permutations<T>(xs: T[]): T[][] {
  const out: T[][] = [], cur: T[] = [], used = new Array(xs.length).fill(false);
  const go = () => {
    if (cur.length === xs.length) { out.push([...cur]); return; }
    for (let i = 0; i < xs.length; i++) {
      if (used[i]) continue;
      used[i] = true; cur.push(xs[i]); go(); cur.pop(); used[i] = false;
    }
  };
  go();
  return out;
}
```


</Level>
<Level name="Advanced">


Pruning makes backtracking practical: reject a partial solution as soon as it
cannot succeed. Ordering choices (most constrained first) shrinks the search
tree. Divide and conquer's cost comes from its recurrence.


</Level>
<Level name="Edge cases">


- Empty input: one empty permutation, not zero.
- Pushing `cur` instead of a copy: every result ends up as the same empty
  array.


</Level>
<Level name="Corner cases">


- Duplicates in the input with a permutation search: sort first and skip a
  value equal to the previous unused one, or the output repeats.


</Level>
<Level name="Production level">


Recursion depth is limited in JavaScript (roughly ten thousand frames,
engine-dependent); deep inputs need an explicit stack. Search with pruning
powers solvers, schedulers and type checkers.


</Level>
<Level name="Mindset">


Trust the recursive call: assume it works for the smaller input and only
check that I combine correctly.


</Level>
<Level name="System design">


Constraint solvers behind configuration tools and package managers' version
resolution are backtracking with clever pruning.


</Level>
<Level name="Strategy">


Solve permutations, subsets, n-queens and a sudoku with pruning, and count
nodes visited with and without each pruning rule. Done when I can explain
each count difference.

</Level>

</Levels>

**Concept 3 of 10: sorting**

<Levels label="Sorting">

<Level name="Beginner">


Insertion and selection sort are quadratic and simple. Merge sort and
quicksort are n log n. Heap sort is n log n in place. Counting and radix sort
are linear for small integer keys.


</Level>
<Level name="Intermediate">


Stable keeps equal keys in their original order (insertion, merge, counting,
radix). In-place uses constant extra memory (insertion, selection, heap,
quicksort's partitioning). Adaptive runs faster on nearly sorted input
(insertion, TimSort).

<Compare left="Property" right="Algorithms that have it" caption="Which sorts have which property" rows={[["Stable", "insertion, merge, counting, radix, TimSort"], ["In-place", "insertion, selection, heap, quicksort (stack aside)"], ["Adaptive", "insertion, TimSort"], ["Worst case n log n", "merge, heap, introsort"]]} />


</Level>
<Level name="Advanced">


No comparison sort beats n log n in the worst case (the decision-tree
bound). Library sorts are hybrids: TimSort finds runs and merges them;
introsort is quicksort that falls back to heapsort.


</Level>
<Level name="Edge cases">


- `[10, 9, 1].sort()` gives `[1, 10, 9]`: the default comparator compares
  strings. Always pass `(a, b) => a - b` for numbers.
- A comparator that is not consistent (returns random results) makes the
  output undefined.


</Level>
<Level name="Corner cases">


- `NaN` in a numeric sort: `a - b` is `NaN`, which breaks the comparator's
  contract, and the result is in an engine-dependent order.


</Level>
<Level name="Production level">


The library sort is the right answer almost always. Write my own only for a
known special case: integer keys (radix), external data (merge), or top-k
(a heap).


</Level>
<Level name="Mindset">


Know the properties, not just the names. "Is it stable?" is the question
that bites in multi-key sorts.


</Level>
<Level name="System design">


Database `ORDER BY` uses external merge sort when data does not fit in
memory; sorting is also the first step of many joins.


</Level>
<Level name="Strategy">


Build the plan's sorting benchmark: five algorithms on random, sorted,
reversed, many-duplicates and nearly sorted input. Done when I predict the
slowest cell of the table before running it.

</Level>

</Levels>

**Concept 4 of 10: binary search, lower and upper bound**

<Levels label="Binary search, lower and upper bound">

<Level name="Beginner">


Binary search halves a sorted range each step, finding a value in log n.


</Level>
<Level name="Intermediate">


Lower bound is the first index whose value is at least x; upper bound is the
first index whose value is greater than x. Together they find every copy of x.

```ts
function lowerBound(a: number[], x: number): number {
  let lo = 0, hi = a.length;           // invariant: answer in [lo, hi]
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (a[mid] < x) lo = mid + 1; else hi = mid;
  }
  return lo;
}
```


</Level>
<Level name="Advanced">


Binary search works on any monotone predicate, not only arrays: "the
smallest capacity that ships everything in d days" is a binary search on
the answer.


</Level>
<Level name="Edge cases">


- Empty array (returns 0), x smaller than all, x larger than all (returns
  length).


</Level>
<Level name="Corner cases">


- All elements equal to x: lower bound is 0 and upper bound is the length.
- Using `hi = a.length - 1` with `lo < hi` misses the last position; the
  half-open interval avoids it.


</Level>
<Level name="Production level">


Index lookups, `git bisect`, feature-flag rollouts by percentage and
searching sorted logs by timestamp are binary search.


</Level>
<Level name="Mindset">


Write the invariant first ("the answer is in lo to hi") and the loop
follows. Off-by-one bugs are invariant bugs.


</Level>
<Level name="System design">


`git bisect` is binary search over history to find the commit that broke the
build, the most useful algorithm in this phase for daily work.


</Level>
<Level name="Strategy">


Write lower bound, upper bound and binary search on the answer, and
property-test them against a linear scan on arrays full of duplicates. Done
when they pass on empty, single-element and all-equal arrays.

</Level>

</Levels>

**Concept 5 of 10: greedy algorithms**

<Levels label="Greedy algorithms">

<Level name="Beginner">


A greedy algorithm takes the best-looking choice at each step and never goes
back. It is fast, and it is correct only for some problems.


</Level>
<Level name="Intermediate">


Interval scheduling: sort by end time and take each interval that starts
after the last chosen one ends. Huffman coding: repeatedly merge the two
least frequent symbols.


</Level>
<Level name="Advanced">


Correctness needs a proof, usually an exchange argument: any optimal answer
can be changed step by step into the greedy one without getting worse.
Without that proof, a greedy is a heuristic.


</Level>
<Level name="Edge cases">


- Coin change with coins 1, 3 and 4 for amount 6: greedy takes 4, 1, 1;
  the best is 3, 3. Greedy works for some coin systems and not others.


</Level>
<Level name="Corner cases">


- Interval scheduling by shortest interval or by earliest start: both fail on
  small examples. I keep those counterexamples as tests.


</Level>
<Level name="Production level">


Schedulers, load balancers and compression use greedy rules. Where the rule
is not optimal, it needs a documented bound or a measured gap.


</Level>
<Level name="Mindset">


Before trusting a greedy, spend five minutes trying to break it with a small
input.


</Level>
<Level name="System design">


Cache eviction, bin packing of containers onto machines, and request
batching all start greedy and get refined.


</Level>
<Level name="Strategy">


Implement interval scheduling, Huffman coding and coin change, and find the
coin-change counterexample by comparing with a DP on all amounts up to 100.
Done when I can explain an exchange argument and a counterexample, which the
gate asks.

</Level>

</Levels>

**Concept 6 of 10: dynamic programming**

<Levels label="Dynamic programming">

<Level name="Beginner">


DP solves overlapping subproblems once and stores the answers. Fibonacci
with a memo is the first example; it turns exponential time into linear.


</Level>
<Level name="Intermediate">


The discipline the plan asks for: define the state in one sentence, then the
recurrence, then the base cases, then the order. Edit distance: `d[i][j]` is
the cost of turning the first i characters of a into the first j of b.

```ts
function editDistance(a: string, b: string): number {
  const d = Array.from({ length: a.length + 1 }, (_, i) =>
    Array.from({ length: b.length + 1 }, (_, j) => (i === 0 ? j : j === 0 ? i : 0)));
  for (let i = 1; i <= a.length; i++)
    for (let j = 1; j <= b.length; j++)
      d[i][j] = Math.min(d[i - 1][j] + 1, d[i][j - 1] + 1,
                         d[i - 1][j - 1] + (a[i - 1] === b[j - 1] ? 0 : 1));
  return d[a.length][b.length];
}
```


</Level>
<Level name="Advanced">


The shapes: 1D (house robber), 2D (LCS, edit distance), knapsack (items by
capacity), interval DP (best way to split a range, like matrix chain) and
bitmask DP (subsets of up to about 20 items, like a small travelling
salesperson).


</Level>
<Level name="Edge cases">


- Empty strings, capacity zero, a single item: the base row and column.


</Level>
<Level name="Corner cases">


- 0/1 knapsack in one dimension must loop capacity downwards, or an item is
  used twice; looping upwards gives the unbounded knapsack.


</Level>
<Level name="Production level">


Memory is n times m: two rows are enough when only the value is needed. Diff
tools, spell checkers and route planners with constraints use DP.


</Level>
<Level name="Mindset">


If I cannot say what one cell means, I am not ready to write the recurrence.


</Level>
<Level name="System design">


Memoisation across requests is caching; the hard parts are the same: the
key and when it goes stale.


</Level>
<Level name="Strategy">


Solve twelve DP problems across the five shapes, each state-first and
checked against brute force, and build the plan's LCS diff tool. Done when
the diff tool gives a minimal diff on real files.

</Level>

</Levels>

**Concept 7 of 10: graph algorithms**

<Levels label="Graph algorithms">

<Level name="Beginner">


BFS visits vertices in order of edge distance with a queue; DFS goes deep
with a stack or recursion. Both are O(V + E).


</Level>
<Level name="Intermediate">


Topological sort orders a DAG so every edge points forward. Connected
components come from repeated BFS or union–find. Dijkstra finds cheapest
paths with non-negative weights using a priority queue; A* adds a heuristic
that never overestimates.

<Flow caption="Picking a shortest-path algorithm" steps={["unweighted: BFS", "non-negative weights: Dijkstra, or A* with a good heuristic", "negative edges: Bellman–Ford", "all pairs on a small graph: Floyd–Warshall"]} />


</Level>
<Level name="Advanced">


Bellman–Ford relaxes every edge V − 1 times and detects negative cycles.
Floyd–Warshall is a V cubed DP over intermediate vertices. Prim and Kruskal
build minimum spanning trees from the cut property. SCCs come from two DFS
passes (Kosaraju) or one (Tarjan). Max flow pushes along augmenting paths
in a residual graph.


</Level>
<Level name="Edge cases">


- Disconnected graphs, unreachable targets, self-loops, and a source with
  no edges.


</Level>
<Level name="Corner cases">


- One negative edge and no negative cycle: Dijkstra's classic version
  returns a wrong distance. I keep a three-vertex example as a test.
- Recursive DFS on a 100,000-vertex path overflows the stack.


</Level>
<Level name="Production level">


Maps and routing use Dijkstra or A* with heavy precomputation; build tools
use topological sort; network monitoring uses connectivity; social features
use BFS to a small depth.


</Level>
<Level name="Mindset">


When a problem says "depends on", "reachable", "cheapest way" or
"connected", I draw the graph before I write code.


</Level>
<Level name="System design">


Task DAGs in CI and workflow engines are topological sorts; service
dependency graphs are checked for cycles the same way.


</Level>
<Level name="Strategy">


Implement BFS, iterative DFS, topological sort, Dijkstra, A*, Bellman–Ford,
Floyd–Warshall, Prim, Kruskal and SCC, and build the route planner on a small
grid map. Done when all shortest-path algorithms agree on random
non-negative graphs and A* expands fewer nodes than Dijkstra.

</Level>

</Levels>

**Concept 8 of 10: string algorithms**

<Levels label="String algorithms">

<Level name="Beginner">


Finding a pattern in a text naively tries every position, up to n times m.


</Level>
<Level name="Intermediate">


KMP precomputes the prefix function of the pattern, so after a mismatch it
continues without moving back in the text: O(n + m). Rabin–Karp compares a
rolling hash and verifies on a hit. A trie finds many words at once.

```ts
function kmpSearch(t: string, p: string): number[] {
  const pi = new Array(p.length).fill(0), out: number[] = [];
  for (let i = 1, k = 0; i < p.length; i++) {
    while (k && p[i] !== p[k]) k = pi[k - 1];
    if (p[i] === p[k]) k++; pi[i] = k;
  }
  for (let i = 0, k = 0; i < t.length; i++) {
    while (k && t[i] !== p[k]) k = pi[k - 1];
    if (t[i] === p[k]) k++;
    if (k === p.length) { out.push(i - k + 1); k = pi[k - 1]; }
  }
  return out;
}
```


</Level>
<Level name="Advanced">


A suffix array is the sorted list of all suffixes; with the LCP array it
finds repeated substrings and supports fast substring search. The plan asks
only for a preview.


</Level>
<Level name="Edge cases">


- Empty pattern, pattern longer than text, overlapping matches.


</Level>
<Level name="Corner cases">


- Unicode: JavaScript indexes UTF-16 code units, so an emoji pattern matches
  at code-unit positions, which need converting for display.


</Level>
<Level name="Production level">


`String.prototype.indexOf` is well optimised; I write KMP or Aho–Corasick
when matching many patterns or streaming text.


</Level>
<Level name="Mindset">


Precompute what a mismatch teaches so I never re-read input.


</Level>
<Level name="System design">


Search features choose between scanning, a trie for prefixes, and an
inverted index for words; each has a different build and query cost.


</Level>
<Level name="Strategy">


Build the plan's search tool: KMP for one pattern, a trie for a word list,
tested against `indexOf` on random small-alphabet text. Done when I can
compute a prefix function by hand.

</Level>

</Levels>

**Concept 9 of 10: randomized algorithms**

<Levels label="Randomized algorithms">

<Level name="Beginner">


A randomized algorithm uses random choices. Randomized quicksort picks a
random pivot so no input is reliably bad.


</Level>
<Level name="Intermediate">


Reservoir sampling keeps a uniform random sample of k items from a stream of
unknown length.

```ts
function reservoir<T>(stream: Iterable<T>, k: number): T[] {
  const r: T[] = []; let i = 0;
  for (const x of stream) {
    if (i < k) r.push(x);
    else { const j = Math.floor(Math.random() * (i + 1)); if (j < k) r[j] = x; }
    i++;
  }
  return r;
}
```


</Level>
<Level name="Advanced">


Las Vegas algorithms are always correct and their time is random
(randomized quicksort). Monte Carlo algorithms have a bounded time and may
be wrong with small probability (Miller–Rabin, Bloom filters). Repeating a
Monte Carlo test drives the error down.


</Level>
<Level name="Edge cases">


- A stream shorter than k: return all of it.


</Level>
<Level name="Corner cases">


- Seeding the random generator the same way on every server makes the
  "random" choices identical everywhere, which defeats jitter and load
  spreading.


</Level>
<Level name="Production level">


Random jitter on retries, random sampling of traces and logs, A/B test
assignment and hash seeds are randomized algorithms in production. Tests
need seeds to reproduce failures.


</Level>
<Level name="Mindset">


Randomness defends against an adversary I cannot predict, and it must be
reproducible when I debug.


</Level>
<Level name="System design">


Power-of-two-choices load balancing and consistent hashing rest on simple
probability arguments.


</Level>
<Level name="Strategy">


Write randomized quicksort and reservoir sampling, and check reservoir
uniformity with a chi-squared test over many runs. Done when I can explain
Monte Carlo versus Las Vegas with one example each.

</Level>

</Levels>

**Concept 10 of 10: NP-hardness**

<Levels label="NP-hardness">

<Level name="Beginner">


Some problems have no known algorithm that is fast for every input: the
travelling salesperson, graph colouring, scheduling with many constraints.
They are NP-hard.


</Level>
<Level name="Intermediate">


A reduction turns a known hard problem into mine in polynomial time. If I
could solve mine fast, I could solve the known one fast, so mine is at least
as hard. The direction matters: known to new.


</Level>
<Level name="Advanced">


Responses to a hard problem: exact search with pruning for small inputs, DP
when a parameter is small (bitmask DP), approximation with a guarantee
(vertex cover within 2), heuristics with no guarantee (local search,
simulated annealing), or an off-the-shelf solver.


</Level>
<Level name="Edge cases">


- Special cases are often easy: colouring with two colours is BFS; TSP on a
  tree is simple.


</Level>
<Level name="Corner cases">


- Subset sum is NP-complete yet has a DP that is fast when the target is
  small. Hardness is about the number of bits, not the size of the number.


</Level>
<Level name="Production level">


When a feature turns out to be NP-hard, I say so early and propose a
heuristic with a measured gap, instead of promising optimal.


</Level>
<Level name="Mindset">


The plan's phrase is "knowing when to stop looking for an exact polynomial
algorithm". That is the skill.


</Level>
<Level name="System design">


Container placement, delivery routing and timetabling run heuristics because
the exact problems are NP-hard.


</Level>
<Level name="Strategy">


Write one reduction on paper (3-SAT to independent set), and solve a small
scheduling problem exactly and with a greedy heuristic. Done when I can
report the gap and explain the reduction's direction.

</Level>

</Levels>
