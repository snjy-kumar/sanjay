**The learning strategy, on nine levels**

<Levels label="Phase 3, data structures">

<Level name="Beginner">


A data structure is a layout in memory plus the operations it makes cheap.
The smallest thing that works is an array and a loop. Everything else in the
phase is a different trade between what is cheap to do and what is expensive.


</Level>
<Level name="Intermediate">


Real programs combine structures: a hash map from key to a node in a linked
list is an LRU cache; a heap of indices into an array is a scheduler. The
skill is choosing a combination from the operations a feature needs.


</Level>
<Level name="Advanced">


Underneath, every structure is arrays and pointers. Arrays give locality and
indexing; pointers give cheap insertion and sharing. Costs come in kinds:
worst case, expected, amortised, and the constant factor of cache misses.


</Level>
<Level name="Edge cases">


Every structure has the same boundaries: empty, one item, full or at a
resize threshold, and duplicate keys. My tests start there.


</Level>
<Level name="Corner cases">


The bugs live where two boundaries meet: deleting the last item while a
resize happens, a tombstone at the exact load-factor limit, a rotation at the
root of a two-node tree.


</Level>
<Level name="Production level">


In production I mostly use the platform's `Array`, `Map` and `Set`, plus a
library for the rest. Knowing the internals tells me when they will be slow,
when they will use too much memory, and when an attacker can make them
slow.


</Level>
<Level name="Mindset">


The negative case is the real knowledge. For every structure I can say when
I would not use it.


</Level>
<Level name="System design">


Every database, cache and queue in a system is one of these structures with
persistence and concurrency added. Phase 8 is chapter 3 of Sedgewick on
disk.


</Level>
<Level name="Strategy">


Seven weeks, one structure or two a week, each written from a blank file with
a property test against a built-in and a benchmark number in the README.
Done when I pass the gate below: the structures from scratch without AI,
the explanations without notes, and one profiled number.

</Level>

</Levels>

**How I would learn it**

I would treat the phase as building one library, not studying twelve topics.
Every structure goes into the same repository with the same interface style
(`insert`, `delete`, `get`, `size`, iteration), a test file, a property test
against `Map`, `Set` or a sorted array, and a benchmark in one harness. The
README has one table per structure with the plan's five questions.

My loop per structure: read the Sedgewick section with the booksite open,
close the book, write it from a blank file in TypeScript, make the property
test pass, then read Weiss's chapter for the analysis and try to answer its
"why" questions before reading the answer. Anything I cannot explain becomes
a card in my study log. I visualise on VisuAlgo when a rotation or a probe
sequence does not make sense in my head.

I would not use AI to write any of the structures. I would use it, after the
fact, to review my README tables and argue with my complexity claims.

**Concept 1 of 12: arrays, dynamic arrays and strings**

<Levels label="Arrays, dynamic arrays and strings">

<Level name="Beginner">


An array is items side by side in memory, so reading item `i` is one address
calculation. A dynamic array keeps a capacity larger than its length and
copies into a bigger buffer when full.


</Level>
<Level name="Intermediate">


```ts
class DynArray<T> {
  private buf: (T | undefined)[] = new Array(1);
  private n = 0;
  push(x: T) {
    if (this.n === this.buf.length) this.resize(this.buf.length * 2);
    this.buf[this.n++] = x;
  }
  pop(): T | undefined {
    if (this.n === 0) return undefined;
    const x = this.buf[--this.n]; this.buf[this.n] = undefined;
    if (this.n > 0 && this.n === this.buf.length / 4) this.resize(this.buf.length / 2);
    return x;
  }
  private resize(cap: number) {
    const next = new Array(cap);
    for (let i = 0; i < this.n; i++) next[i] = this.buf[i];
    this.buf = next;
  }
}
```


</Level>
<Level name="Advanced">


Doubling makes push amortised O(1): the copies add up to less than 2n over n
pushes. Shrinking at a quarter, not a half, avoids thrashing. Strings in
JavaScript are immutable UTF-16 sequences, so building one by repeated `+=`
can copy, although engines use ropes to hide it.


</Level>
<Level name="Edge cases">


- Pop from empty, push into capacity zero, and a resize to exactly the
  current length.
- `"é".length` can be 1 or 2 depending on normalisation; emoji are two
  code units.


</Level>
<Level name="Corner cases">


- Shrinking to a quarter when the capacity is one: dividing gives zero. A
  minimum capacity fixes it.
- Clearing references on pop matters in a garbage-collected language: a
  stale slot keeps the object alive.


</Level>
<Level name="Production level">


V8 stores arrays of small integers, of doubles and of objects differently,
and a hole or a mixed type can switch an array to a slower representation.
Preallocating when the size is known avoids repeated growth.


</Level>
<Level name="Mindset">


Amortised cost is a promise over a sequence. A single push can still be slow,
and a latency-sensitive path has to know that.


</Level>
<Level name="System design">


Growable buffers sit under every log, socket buffer and serialiser. Picking
the growth factor trades memory for copies.


</Level>
<Level name="Strategy">


Write the dynamic array, count copies over a million pushes and pops, and
compare with the amortised bound. Done when my measured copies per operation
stay under two and I can explain why the quarter rule exists.

</Level>

</Levels>

**Concept 2 of 12: linked lists**

<Levels label="Linked lists">

<Level name="Beginner">


A linked list is nodes, each holding a value and a pointer to the next.
Inserting after a node I already hold is O(1); finding the node is O(n).


</Level>
<Level name="Intermediate">


Doubly linked lists add a `prev` pointer so a node can remove itself in O(1).
Circular lists link the tail back to the head. A sentinel node removes the
special cases for empty lists and the ends.

```ts
type Node<T> = { v: T; prev: Node<T>; next: Node<T> };
function remove<T>(n: Node<T>) { n.prev.next = n.next; n.next.prev = n.prev; }
```


</Level>
<Level name="Advanced">


Each node is a separate allocation, so walking a list misses the cache on
almost every step, while an array walks memory in order. That is why
arrays beat lists even for many insert-heavy workloads.


</Level>
<Level name="Edge cases">


- The empty list, a one-node list, and removing the head or the tail.


</Level>
<Level name="Corner cases">


- Removing the current node while iterating: keep the next pointer before
  removing, or the loop follows a dead link.
- A cycle introduced by a bug: a length count never ends. Floyd's tortoise
  and hare detects it.


</Level>
<Level name="Production level">


Lists earn their place where nodes are already held elsewhere: the LRU
cache's recency list, free lists in allocators, intrusive lists in kernels.


</Level>
<Level name="Mindset">


O(1) insert is only O(1) if I already have the node. Ask how I got it.


</Level>
<Level name="System design">


Intrusive lists (the pointers live inside the object) let one object sit on
several lists at once, as kernel structures do.


</Level>
<Level name="Strategy">


Write a sentinel doubly linked list and benchmark iteration against an array
of the same size. Done when the benchmark number is in my README and I can
say when a list is worse than an array, which is most of the time.

</Level>

</Levels>

**Concept 3 of 12: stacks, queues, deques and ring buffers**

<Levels label="Stacks, queues, deques and ring buffers">

<Level name="Beginner">


A stack is last in, first out (an array with push and pop). A queue is first
in, first out. A deque allows both ends. A ring buffer is a fixed array where
head and tail wrap around.


</Level>
<Level name="Intermediate">


In JavaScript, `Array.prototype.shift` is O(n) in the general case, so a
queue built on it gets slow; a ring buffer or two stacks gives O(1).

```ts
class Ring<T> {
  private b: (T | undefined)[]; private h = 0; private n = 0;
  constructor(cap: number) { this.b = new Array(cap); }
  push(x: T) { if (this.n === this.b.length) throw new Error('full');
    this.b[(this.h + this.n++) % this.b.length] = x; }
  shift() { if (!this.n) return undefined; const x = this.b[this.h];
    this.b[this.h] = undefined; this.h = (this.h + 1) % this.b.length; this.n--; return x; }
}
```


</Level>
<Level name="Advanced">


A growable ring buffer copies items in order from head to tail into the new
buffer, unwrapping them. Two stacks make a queue with amortised O(1)
operations by reversing one into the other when it runs out.


</Level>
<Level name="Edge cases">


- Full versus empty in a ring: head equals tail in both, so I track a count.


</Level>
<Level name="Corner cases">


- Growing a ring buffer while it is wrapped: a plain copy of the array keeps
  the wrap at the wrong place. The copy must start at head.


</Level>
<Level name="Production level">


Bounded queues give backpressure; unbounded ones turn a slow consumer into an
out-of-memory crash. Log buffers and audio buffers are rings that overwrite
the oldest item on purpose.


</Level>
<Level name="Mindset">


Every queue in a system needs a bound and a policy for when the bound is hit.


</Level>
<Level name="System design">


Message queues, the event loop's task queues and TCP's send buffer are this
concept at different scales.


</Level>
<Level name="Strategy">


Write a ring buffer and a two-stack queue, and property-test both against an
array used as a queue. Done when they pass at full, empty and after a
thousand wraps, and the benchmark shows `shift` losing at large sizes.

</Level>

</Levels>

**Concept 4 of 12: hash tables**

<Levels label="Hash tables">

<Level name="Beginner">


A hash table turns a key into an index with a hash function and stores the
value there, so lookups take expected constant time.


</Level>
<Level name="Intermediate">


Collisions are handled by chaining (a list per bucket) or open addressing
(probe the next slot). The load factor, items over slots, decides the cost,
and the table resizes to keep it low.

```ts
// linear probing lookup, keys as strings, null = empty, TOMB = deleted
function find(keys: (string | null | symbol)[], k: string, h: number): number {
  for (let i = h % keys.length, n = 0; n < keys.length; i = (i + 1) % keys.length, n++) {
    if (keys[i] === null) return -1;
    if (keys[i] === k) return i;
  }
  return -1;
}
```


</Level>
<Level name="Advanced">


Linear probing forms clusters but uses the cache well. Deletion in open
addressing needs tombstones or backward-shift deletion, because an emptied
slot would cut later probe chains. A good hash function spreads similar keys
apart; universal or keyed hashing defends against chosen inputs.


</Level>
<Level name="Edge cases">


- Delete then search for a key that was further along the same chain.
- Resizing must rehash every key, because the index depends on the table
  size.


</Level>
<Level name="Corner cases">


- A table full of tombstones: the load factor looks low but every miss scans
  the whole table. Count tombstones toward the resize trigger.


</Level>
<Level name="Production level">


Hash flooding sends many keys that collide to turn O(1) into O(n), which is
why engines randomise string hashing and use keyed hashes. A JavaScript
object used as a map also has prototype keys like `__proto__`; `Map` does
not.


</Level>
<Level name="Mindset">


"O(1)" is expected, under assumptions about the keys and the load factor.
State the assumption.


</Level>
<Level name="System design">


Sharding by hash, consistent hashing and partitioned caches are hash tables
across machines, with the same resize problem: rehashing moves data.


</Level>
<Level name="Strategy">


Write chaining and open-addressing tables with resizing and deletion, and
plot average probes against load factor. Done when a random-operations
property test against `Map` passes with heavy deletion.

</Level>

</Levels>

**Concept 5 of 12: trees and binary search trees**

<Levels label="Trees and binary search trees">

<Level name="Beginner">


A tree is nodes with children and no cycles. In a binary search tree, left
is smaller and right is larger, so search follows one path.


</Level>
<Level name="Intermediate">


Traversals: pre-order (node first), in-order (sorted order in a BST),
post-order (children first, used to free or evaluate), and level order
(breadth first, with a queue).

```ts
function* inorder<K>(n: { k: K; l?: any; r?: any } | undefined): Generator<K> {
  if (!n) return;
  yield* inorder(n.l); yield n.k; yield* inorder(n.r);
}
```


</Level>
<Level name="Advanced">


Every operation costs the height. Random inserts give height about 2 ln n on
average; sorted inserts give n. Deletion with two children replaces the
node with its successor (Hibbard deletion), and many deletions make the tree
lopsided.


</Level>
<Level name="Edge cases">


- Empty tree, single node, deleting the root.


</Level>
<Level name="Corner cases">


- Deleting a node with two children whose successor is its right child.
- A recursive traversal of a degenerate tree of 100,000 nodes overflows the
  stack; an explicit stack does not.


</Level>
<Level name="Production level">


Ordered maps power range queries: "all events between two times". Plain BSTs
are not used for that in production because of the degenerate case.


</Level>
<Level name="Mindset">


Shape is cost. Ask what input order gives the worst shape.


</Level>
<Level name="System design">


ASTs, DOM trees, file systems and org charts are trees; most code that walks
them is a traversal choice.


</Level>
<Level name="Strategy">


Write a BST with insert, delete, floor, ceiling and range, then insert a
million sorted keys and record the height. Done when deletions pass a
property test and the height number is in the README.

</Level>

</Levels>

**Concept 6 of 12: balanced trees (AVL, red–black, B-trees)**

<Levels label="Balanced trees">

<Level name="Beginner">


A balanced tree restructures itself on insert and delete so its height stays
O(log n) for any input order.


</Level>
<Level name="Intermediate">


AVL trees keep every node's two subtree heights within one, fixing
violations with single or double rotations. Red–black trees use colour rules
that allow a little more imbalance and fewer rotations. A left-leaning
red–black tree is the shortest version to write.


</Level>
<Level name="Advanced">


A red–black tree is a 2-3-4 (or 2-3) tree in disguise: a red link glues two
nodes into one multi-key node. A B-tree makes those nodes big on purpose, one
disk page each, so the height is a handful of levels for billions of keys.


</Level>
<Level name="Edge cases">


- Rotations at the root must update the root pointer.
- Double rotations (left-right and right-left) are the cases people forget.


</Level>
<Level name="Corner cases">


- AVL deletion can need a rotation at every level up to the root, unlike
  insertion, which needs at most one fix.


</Level>
<Level name="Production level">


Databases prefer B-trees because a disk or SSD reads whole pages: wide nodes
mean fewer reads. In memory, `std::map` and `TreeMap` are red–black trees.


</Level>
<Level name="Mindset">


An invariant you can check is worth more than a rotation you can remember.
I write `validate()` before `insert()`.


</Level>
<Level name="System design">


The phase 8 database index is a B+ tree. The choice between B-tree and LSM
tree is a read-versus-write trade at system level.


</Level>
<Level name="Strategy">


Write an AVL or left-leaning red–black tree with a validator run after every
random operation, and draw B-tree splits on paper. Done when ten thousand
random operations pass validation and I can explain to someone why databases
use B-trees, which the gate asks.

</Level>

</Levels>

**Concept 7 of 12: heaps and priority queues**

<Levels label="Heaps and priority queues">

<Level name="Beginner">


A binary heap is a complete tree stored in an array where each parent is
smaller (min-heap) than its children. The minimum is always at index 0.


</Level>
<Level name="Intermediate">


Insert appends and sifts up; pop-min swaps the last item to the root and
sifts down. Both are O(log n). Heapify builds a heap from an array in O(n).


</Level>
<Level name="Advanced">


Heapify is linear because most nodes are near the bottom and sift only a
short way. Heapsort is heapify plus n pops, in place, n log n, not stable,
and poor on cache.


</Level>
<Level name="Edge cases">


- Pop from an empty heap, and a heap of one.
- Equal priorities: heaps are not stable; add a sequence number to break
  ties if order matters.


</Level>
<Level name="Corner cases">


- Decrease-key needs the item's position, so an index map must be updated
  on every swap, including the swaps inside sift-down.


</Level>
<Level name="Production level">


Timers, schedulers, top-k queries and Dijkstra use priority queues. A heap of
millions of timers is why some runtimes use timer wheels instead.


</Level>
<Level name="Mindset">


Keep only the order I need. A heap is cheaper than a sorted array because it
promises less.


</Level>
<Level name="System design">


Job schedulers and rate limiters with deadlines are priority queues; at
scale, they become sorted sets in Redis.


</Level>
<Level name="Strategy">


Write a min-heap with an index map and decrease-key, and use it later in
phase 4's Dijkstra. Done when heapify plus pops sorts random arrays and
decrease-key passes a property test.

</Level>

</Levels>

**Concept 8 of 12: tries and radix trees**

<Levels label="Tries and radix trees">

<Level name="Beginner">


A trie stores strings by their characters, one level per character, so all
words with a prefix share a path. Lookup costs the length of the key, not the
number of keys.


</Level>
<Level name="Intermediate">


```ts
class Trie {
  private root: Map<string, any> = new Map();
  insert(w: string) {
    let n = this.root;
    for (const c of w) { if (!n.has(c)) n.set(c, new Map()); n = n.get(c); }
    n.set('$', true);
  }
  hasPrefix(p: string) {
    let n = this.root;
    for (const c of p) { n = n.get(c); if (!n) return false; }
    return true;
  }
}
```


</Level>
<Level name="Advanced">


A radix (compressed) trie merges chains of single-child nodes into one edge
labelled with a string, cutting memory. Ternary search tries keep three
pointers per node instead of a full alphabet.


</Level>
<Level name="Edge cases">


- The empty string as a key, and a word that is a prefix of another ("car",
  "cart"): the end marker is what tells them apart.


</Level>
<Level name="Corner cases">


- Deleting a word that is a prefix of another must remove only the end
  marker; deleting the longer word must prune nodes up to the shared prefix
  and no further.
- `for (const c of w)` iterates code points, while `w[i]` gives UTF-16 code
  units; mixing them breaks emoji keys.


</Level>
<Level name="Production level">


Autocomplete, router path matching in web frameworks, IP routing tables
(longest prefix match) and some key-value stores use tries or radix trees.


</Level>
<Level name="Mindset">


Sometimes the key's structure is the index. Look inside the key.


</Level>
<Level name="System design">


HTTP routers in Node frameworks use radix trees to match paths; IP routing
uses longest-prefix match on bits.


</Level>
<Level name="Strategy">


Write a trie with insert, delete and prefix search, then a compressed
version, and compare node counts on a word list. Done when deletion passes a
property test against a `Set` of strings.

</Level>

</Levels>

**Concept 9 of 12: graph representations**

<Levels label="Graph representations">

<Level name="Beginner">


A graph is vertices and edges. An adjacency list stores each vertex's
neighbours; an adjacency matrix is a V by V grid; an edge list is a plain
array of pairs.


</Level>
<Level name="Intermediate">


Lists suit sparse graphs (space V + E), matrices suit dense graphs and O(1)
edge checks (space V squared). Directed graphs store one direction;
undirected graphs store both. Weighted graphs store a weight with each edge.

```ts
type Graph = { n: number; adj: { to: number; w: number }[][] };
const addEdge = (g: Graph, u: number, v: number, w = 1, directed = false) => {
  g.adj[u].push({ to: v, w }); if (!directed) g.adj[v].push({ to: u, w });
};
```


</Level>
<Level name="Advanced">


Compressed sparse row (CSR) packs adjacency lists into two flat arrays,
which is far friendlier to the cache than arrays of objects.


</Level>
<Level name="Edge cases">


- Self-loops, parallel edges and isolated vertices.


</Level>
<Level name="Corner cases">


- An undirected self-loop added with the code above appears twice in the
  list, so a degree count is off by one unless I handle it.


</Level>
<Level name="Production level">


Social graphs, dependency graphs and road networks are too large for
matrices; they use lists or CSR, and graph databases add indexes.


</Level>
<Level name="Mindset">


Pick the representation from the queries: "is there an edge?" wants a
matrix or a hash set; "who are the neighbours?" wants a list.


</Level>
<Level name="System design">


Service dependency maps and build graphs are graphs; storing them as edge
lists in a table is the usual first step.


</Level>
<Level name="Strategy">


Implement all three representations behind one interface and convert between
them. Done when phase 4's BFS runs unchanged on each and I can state the
space of each for a given V and E.

</Level>

</Levels>

**Concept 10 of 12: union–find**

<Levels label="Union–find">

<Level name="Beginner">


Union–find keeps items in disjoint groups and answers "are these two in the
same group?" and "merge these groups".


</Level>
<Level name="Intermediate">


Each group is a tree with its root as the name. Union by rank (or size)
attaches the smaller tree under the larger. Path compression points nodes
at the root as find walks up.

```ts
const parent = Array.from({ length: n }, (_, i) => i), size = new Array(n).fill(1);
const find = (x: number): number => {
  while (parent[x] !== x) { parent[x] = parent[parent[x]]; x = parent[x]; }
  return x;
};
const union = (a: number, b: number) => {
  let [ra, rb] = [find(a), find(b)]; if (ra === rb) return;
  if (size[ra] < size[rb]) [ra, rb] = [rb, ra];
  parent[rb] = ra; size[ra] += size[rb];
};
```


</Level>
<Level name="Advanced">


With both optimisations, a sequence of operations costs close to constant
each: the inverse Ackermann function, at most 4 in practice.


</Level>
<Level name="Edge cases">


- Union of an item with itself; union of two items already together.


</Level>
<Level name="Corner cases">


- Union–find cannot split a group. Deleting an edge needs a different
  structure or a rebuild.


</Level>
<Level name="Production level">


Kruskal's MST, connected components in images, account merging and
percolation simulations use it.


</Level>
<Level name="Mindset">


Lazy work that is remembered becomes almost free.


</Level>
<Level name="System design">


Deduplicating user records into identities is union–find over "same email"
and "same phone" edges.


</Level>
<Level name="Strategy">


Write quick-find, quick-union and weighted with compression, and run
Sedgewick's doubling test on all three. Done when the measured ratios match
the expected growth for each.

</Level>

</Levels>

**Concept 11 of 12: applied structures (LRU, Bloom filter, skip list, segment tree, Fenwick tree)**

<Levels label="Applied structures">

<Level name="Beginner">


These are structures built for one job. An LRU cache evicts the least
recently used item; a Bloom filter answers "maybe present" or "definitely
not"; a skip list is a sorted list with express lanes; segment and Fenwick
trees answer range queries over an array that changes.


</Level>
<Level name="Intermediate">


LRU is a hash map from key to a node in a doubly linked list. In JavaScript,
a `Map` keeps insertion order, so delete and re-set moves a key to the end.

```ts
class LRU<K, V> {
  private m = new Map<K, V>();
  constructor(private cap: number) {}
  get(k: K) { if (!this.m.has(k)) return undefined;
    const v = this.m.get(k)!; this.m.delete(k); this.m.set(k, v); return v; }
  set(k: K, v: V) { this.m.delete(k); this.m.set(k, v);
    if (this.m.size > this.cap) this.m.delete(this.m.keys().next().value!); }
}
```


</Level>
<Level name="Advanced">


A Bloom filter sets k bits per item from k hashes; its false-positive rate
depends on bits per item and k. A Fenwick tree stores partial sums at
indices chosen by the lowest set bit, so prefix sums and updates are both
O(log n).


</Level>
<Level name="Edge cases">


- LRU with capacity 0 or 1.
- A Bloom filter cannot delete; a counting Bloom filter can, at more space.


</Level>
<Level name="Corner cases">


- Updating an existing key in an LRU at full capacity must not evict
  anything; the code above deletes first, so the size check is correct.


</Level>
<Level name="Production level">


LRU caches are everywhere; Bloom filters sit in front of disk lookups in
databases (LSM trees) and in CDNs; skip lists back Redis sorted sets.


</Level>

**Concept 12 of 12: immutability and persistent structures**

<Levels label="Immutability and persistent structures">

<Level name="Beginner">


An immutable structure never changes; an update returns a new version. A
persistent structure keeps old versions usable and shares most of their
memory with new ones.


</Level>
<Level name="Intermediate">


Path copying: updating a tree copies only the nodes on the path from the
root, and the new root shares every other subtree with the old one.

```ts
type T = { k: number; l?: T; r?: T } | undefined;
const insert = (t: T, k: number): T =>
  !t ? { k } : k < t.k ? { ...t, l: insert(t.l, k) }
     : k > t.k ? { ...t, r: insert(t.r, k) } : t;
```


</Level>
<Level name="Advanced">


Hash array mapped tries (HAMTs) give persistent maps with shallow, wide
nodes. Copying is O(log n) per update instead of O(n).


</Level>
<Level name="Edge cases">


- `Object.freeze` is shallow: nested objects stay mutable.
- Spreading an array to "copy" it is O(n) per update.


</Level>
<Level name="Corner cases">


- A persistent structure that holds old versions keeps their memory alive;
  undo history needs a limit.


</Level>
<Level name="Production level">


React state, Redux and many functional languages rely on immutability so a
change can be detected with a reference comparison. The cost is allocation.


</Level>
<Level name="Mindset">


The plan says immutability is a design choice, not a default. Use it where
sharing, undo or concurrency make it pay.


</Level>
<Level name="System design">


Event sourcing and append-only logs are immutability at system scale:
history is kept, and state is derived.


</Level>
<Level name="Strategy">


Write a persistent BST with path copying and measure allocations per insert
against a mutable one. Done when old versions stay correct after a thousand
updates and I can say where I would not use it.

</Level>

</Levels>
