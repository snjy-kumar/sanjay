Three weeks on judgement: how to change a system without breaking it, and how to keep it safe. The
engineering half follows *The Pragmatic Programmer*; the security half follows
<a href={withBase('/books/security-engineering/')}>Security Engineering</a>, with
<a href={withBase('/books/the-web-application-hackers-handbook/')}>The Web Application Hacker's Handbook</a>
and the PortSwigger Web Security Academy for the web attacks. Everything is applied to one codebase:
the capstone I am about to build, or the replicated store from phase 10 as its seed.

#### Phase 11: how I would learn it

This phase is less about new ideas and more about evidence. Each topic ends in an artefact in the
repository: a CI step, a test, a document, a finding. I alternate days: one day engineering practice
(Git, tests, CI, design, docs), the next day security (threat model, OWASP, auth, crypto, supply
chain). Security techniques are practised only on my own code and on labs built for practice.

#### Phase 11: Git workflows, small commits, code review and readable history

<Levels label="Phase 11, Git workflows, commits, review and history">

<Level name="Beginner">

A commit is a saved change with a message. Small commits that do one thing are easy to review,
revert and understand.

</Level>

<Level name="Intermediate">

Branches isolate work; a pull request asks for review before merging. A good message says why, not
only what.

```txt
Reject expired session tokens on refresh

Refresh accepted tokens past their idle timeout, so a stolen token
could be renewed forever. Check idle age before issuing a new one.
```

</Level>

<Level name="Advanced">

`git bisect` finds the commit that introduced a bug by binary search, which only works when every
commit builds and does one thing.

</Level>

<Level name="Edge cases">

A huge generated file or a formatting change mixed into a logic change makes review impossible.
Separate them.

</Level>

<Level name="Corner cases">

A rebase that rewrites commits other people already pulled: history changes under them. Rewrite only
what is not shared.

</Level>

<Level name="Production level">

Protected main branch, required review and green CI, and squash or rebase rules agreed by the team.
Secrets never committed; if they are, rotate them, because history keeps them.

</Level>

<Level name="Mindset">

History is documentation for my future self. Write it for someone debugging at night.

</Level>

<Level name="System design">

Branching strategy follows release strategy: trunk-based with feature flags for continuous delivery,
release branches for versioned software.

</Level>

<Level name="Strategy">

I find a bug in my capstone's history with `git bisect` and review my own last ten commits as a
stranger would. Done when every commit builds, does one thing and says why.

</Level>

</Levels>

#### Phase 11: Testing: unit, integration, end-to-end, property-based, fuzzing and the pyramid

<Levels label="Phase 11, testing">

<Level name="Beginner">

Tests run code and check results. Unit tests check one piece, integration tests check pieces
together, end-to-end tests check the whole system as a user would.

</Level>

<Level name="Intermediate">

Property-based tests generate many inputs and check a rule that must always hold.

```ts
import fc from 'fast-check';
fc.assert(fc.property(fc.array(fc.integer()), (xs) => {
  const s = sort(xs);
  return s.length === xs.length && s.every((v, i) => i === 0 || s[i - 1] <= v);
}));
```

</Level>

<Level name="Advanced">

Fuzzing feeds random or mutated input to find crashes; property tests find wrong answers. The pyramid
(many unit, fewer integration, few end-to-end) is a cost heuristic, not a law: some systems are best
tested mostly at integration level.

</Level>

<Level name="Edge cases">

Empty input, one element, the maximum size, duplicates, Unicode: the boundaries property tests find
first.

</Level>

<Level name="Corner cases">

Flaky tests from time, randomness or ordering: two sources of nondeterminism together make failures
that cannot be reproduced. Seed everything.

</Level>

<Level name="Production level">

Tests run in CI on every change, finish fast, and fail with messages that say what broke. A flaky
test is fixed or deleted, never ignored.

</Level>

<Level name="Mindset">

A test is a claim about behaviour. Ask what claim each test makes and whether it could fail.

</Level>

<Level name="System design">

Test seams come from design: code that takes its dependencies as parameters can be tested without
the network.

</Level>

<Level name="Strategy">

I add property tests to my capstone's core logic and a fuzz test to its input parsing, and mutate the
code to check the tests catch it. Done when a deliberate bug in each module fails at least one test.

</Level>

</Levels>

#### Phase 11: CI/CD: reproducible builds, caching, artifacts and gates

<Levels label="Phase 11, CI/CD">

<Level name="Beginner">

Continuous integration builds and tests every change automatically. Continuous delivery keeps the
result always ready to deploy.

</Level>

<Level name="Intermediate">

A pipeline is a series of steps; a gate is a step that must pass. Caching dependencies makes it fast;
an artifact is the built output that later steps deploy.

```yaml
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm test
      - run: npm audit --audit-level=high
```

</Level>

<Level name="Advanced">

Reproducible builds give the same output from the same input: pinned versions, locked dependencies,
no network surprises. The artifact that was tested is the one that is deployed.

</Level>

<Level name="Edge cases">

A cache that restores stale dependencies after the lockfile changed: key caches on the lockfile hash.

</Level>

<Level name="Corner cases">

A pipeline that runs untrusted pull-request code with secrets available: build convenience plus
credential exposure.

</Level>

<Level name="Production level">

Least-privilege CI tokens, pinned action versions, required checks on the main branch, and a rollback
path that is tested.

</Level>

<Level name="Mindset">

If it is not checked automatically, it will regress. Encode every lesson as a gate.

</Level>

<Level name="System design">

CI is production infrastructure: it holds secrets and produces what ships. It needs the same care.

</Level>

<Level name="Strategy">

I add a CI pipeline to my capstone and open a pull request that breaks an access check. Done when CI
blocks that change, which is part of the gate.

</Level>

</Levels>

#### Phase 11: Design patterns and their critics; modularity, boundaries and dependency direction

<Levels label="Phase 11, design patterns, modularity and dependency direction">

<Level name="Beginner">

A design pattern is a named, reusable solution shape: strategy, adapter, observer. Names help teams
talk about designs.

</Level>

<Level name="Intermediate">

Modules hide decisions behind interfaces. Dependencies should point toward stable, central code; the
core logic should not import the web framework or the database driver.

```ts
// core/ports.ts: the core defines what it needs
export interface OrderRepo { save(o: Order): Promise<void> }
// adapters/pg.ts: the outside implements it
export class PgOrderRepo implements OrderRepo { async save(o: Order) { /* SQL */ } }
```

</Level>

<Level name="Advanced">

Critics point out that many patterns patch missing language features (first-class functions make
strategy trivial) and that patterns applied by default add indirection without benefit.

</Level>

<Level name="Edge cases">

An interface with exactly one implementation forever is ceremony. Add it when a second use or a test
needs it.

</Level>

<Level name="Corner cases">

A circular dependency between two modules that each seemed fine alone: boundaries drawn without
looking at direction.

</Level>

<Level name="Production level">

I enforce dependency direction with a lint rule or a tool that fails CI on forbidden imports.

</Level>

<Level name="Mindset">

Use a pattern when it solves a problem I have, not one I might have.

</Level>

<Level name="System design">

The same idea scales up: services depend on contracts, not on each other's internals.

</Level>

<Level name="Strategy">

I draw my capstone's module dependency graph and remove every arrow pointing from core to
infrastructure. Done when a lint rule enforces it in CI.

</Level>

</Levels>

#### Phase 11: Documentation: READMEs, ADRs, runbooks and design docs

<Levels label="Phase 11, documentation">

<Level name="Beginner">

A README tells a stranger what the project is and how to run it. Without one, the project only works
for me.

</Level>

<Level name="Intermediate">

An ADR records one decision: context, decision, consequences. A runbook says what to do when an alert
fires. A design doc proposes a change before it is built.

```md
# ADR 7: Use Raft for metadata
Status: accepted
Context: leader election must survive one node failure.
Decision: Raft via my phase 10 implementation.
Consequences: three nodes minimum; writes need a majority.
```

</Level>

<Level name="Advanced">

Docs rot when they are far from code. Keep them in the repository, review them in pull requests, and
test the README's commands in CI.

</Level>

<Level name="Edge cases">

A runbook step that needs access the on-call person does not have. Test runbooks in game days.

</Level>

<Level name="Corner cases">

An ADR superseded without being marked: two decisions in the record, both looking current.

</Level>

<Level name="Production level">

Every alert links a runbook; every significant decision has an ADR; the README's quickstart is run
from a clean machine before each release.

</Level>

<Level name="Mindset">

Write for the reader who has none of my context and is in a hurry.

</Level>

<Level name="System design">

Design docs are where tradeoffs are argued before code is expensive to change.

</Level>

<Level name="Strategy">

I give my capstone's README to a clean container and follow it literally. Done when it runs without
my help, and the three biggest decisions so far have ADRs.

</Level>

</Levels>

#### Phase 11: Threat modelling: assets, trust boundaries, attackers and mitigations

<Levels label="Phase 11, threat modelling">

<Level name="Beginner">

A threat model lists what I protect, who might attack it, how, and what stops them.

</Level>

<Level name="Intermediate">

Draw a data-flow diagram; mark trust boundaries where data crosses from less trusted to more trusted;
at each boundary ask about spoofing, tampering, repudiation, information disclosure, denial of service
and elevation of privilege (STRIDE).

</Level>

<Level name="Advanced">

Threat trees break one harm into the paths that reach it. Ranking by impact and likelihood decides
order of work.

</Level>

<Level name="Edge cases">

Assets that are not data: availability, reputation, the CI system, the signing key.

</Level>

<Level name="Corner cases">

Two low-risk weaknesses on one path (a verbose error and a missing rate limit) that combine into
account enumeration at scale.

</Level>

<Level name="Production level">

The model lives in the repository, is reviewed when architecture changes, and every finding links to
a fix or an accepted-risk note.

</Level>

<Level name="Mindset">

Think like the opponent, then act like the owner: every threat gets a decision.

</Level>

<Level name="System design">

Threat modelling belongs in design review, before code, when mitigations are cheapest.

</Level>

<Level name="Strategy">

I write my capstone's threat model with a diagram, STRIDE per boundary and one threat tree. Done when
it has real findings, each fixed or accepted with a reason, which is the gate.

</Level>

</Levels>

#### Phase 11: OWASP: injection, access control, XSS, CSRF, SSRF, deserialisation and dependency risk

<Levels label="Phase 11, OWASP risks">

<Level name="Beginner">

The OWASP Top 10 lists the most common serious web risks. It is a checklist for where to look first.

</Level>

<Level name="Intermediate">

Injection: input becomes code; fix with parameters. Broken access control: missing ownership checks.
XSS: input becomes script; fix with encoding and CSP. CSRF: another site sends requests as the user;
fix with SameSite and tokens. SSRF: the server fetches attacker URLs; fix with allow lists.

</Level>

<Level name="Advanced">

Insecure deserialisation turns data into objects with behaviour. In JavaScript the cousin is
prototype pollution: merging untrusted JSON into objects can set `__proto__`.

```ts
const safe = Object.assign(Object.create(null), JSON.parse(body)); // no prototype to pollute
```

</Level>

<Level name="Edge cases">

Allow lists for SSRF that check the hostname but not where it resolves.

</Level>

<Level name="Corner cases">

A dependency with a known vulnerability in a function I never call, flagged by an audit: risk depends
on reachability, not presence.

</Level>

<Level name="Production level">

Each class has a test in CI: injection payloads, cross-user access attempts, an XSS payload, a
cross-origin post, an internal URL.

</Level>

<Level name="Mindset">

Most web bugs are data crossing into code or identity crossing into another user's data. Look for
those two crossings.

</Level>

<Level name="System design">

Framework defaults handle most of these. Every escape hatch (raw SQL, raw HTML, disabled CSRF) needs a
review comment.

</Level>

<Level name="Strategy">

I self-review my capstone against the OWASP Top 10 using the WAHH methodology, with PortSwigger labs
for each class. Done when every item is marked tested, not applicable or found, with evidence.

</Level>

</Levels>

#### Phase 11: Authentication and authorisation: sessions, tokens, OAuth and RBAC

<Levels label="Phase 11, authentication and authorisation">

<Level name="Beginner">

Authentication answers who you are. Authorisation answers what you may do. Confusing them is a common
bug.

</Level>

<Level name="Intermediate">

Sessions keep state on the server and give the browser an opaque ID. Tokens such as JWTs carry signed
claims. OAuth lets a user grant an app limited access without sharing a password; OpenID Connect adds
login on top.

</Level>

<Level name="Advanced">

RBAC grants permissions by role; attribute-based control adds conditions (owner, tenant, time). Most
apps need both: a role check and an ownership check.

```ts
function canEdit(user: User, doc: Doc) {
  return user.role === 'admin' || (user.role === 'editor' && doc.teamId === user.teamId);
}
```

</Level>

<Level name="Edge cases">

A JWT with `alg: none` or a verifier that accepts any algorithm. Pin the algorithm.

</Level>

<Level name="Corner cases">

A role revoked while a long-lived token still carries it. Short token life plus a server-side check
for sensitive actions.

</Level>

<Level name="Production level">

Use a vetted auth library or provider, keep tokens in `HttpOnly` cookies, check authorisation in one
central place on every request, and log denials.

</Level>

<Level name="Mindset">

Every request is a new question: who is this, and may they do this to this object?

</Level>

<Level name="System design">

Identity at the edge, authorisation near the data. Services pass identity along, and each decides for
its own data.

</Level>

<Level name="Strategy">

I write the access matrix for my capstone and generate a test per cell. Done when every cell passes
and removing any check fails a test.

</Level>

</Levels>

#### Phase 11: Cryptography basics: hashing, salting, encryption, signatures and TLS

<Levels label="Phase 11, cryptography basics">

<Level name="Beginner">

A hash is a fingerprint of data. Encryption hides data from anyone without the key. A signature proves
who wrote something and that it was not changed.

</Level>

<Level name="Intermediate">

Passwords get a slow, salted hash (scrypt, bcrypt, Argon2), never a fast hash and never encryption.
Symmetric encryption uses one shared key; asymmetric uses a public and private pair.

</Level>

<Level name="Advanced">

TLS uses asymmetric crypto to authenticate the server and agree a key, then symmetric authenticated
encryption for the data. Certificates bind a public key to a name.

</Level>

<Level name="Edge cases">

A salt reused for every user, or a predictable one, lets attackers precompute.

</Level>

<Level name="Corner cases">

Encrypting with a correct algorithm but reusing a nonce, or checking a signature with a key taken from
the message itself.

</Level>

<Level name="Production level">

High-level library APIs only, keys in a secrets manager, rotation planned, TLS everywhere with
modern settings.

```ts
import { createSign, createVerify } from 'node:crypto';
const sig = createSign('sha256').update(payload).sign(privateKey);
const ok = createVerify('sha256').update(payload).verify(publicKey, sig);
```

</Level>

<Level name="Mindset">

Use crypto, do not design it. My job is to pick the right primitive and protect the keys.

</Level>

<Level name="System design">

Every key needs an owner, a location, a rotation plan and a blast radius if leaked.

</Level>

<Level name="Strategy">

I list every crypto use in my capstone with primitive, library call, key location and rotation. Done
when every row is complete and none is hand-rolled.

</Level>

</Levels>

#### Phase 11: Supply chain: lockfiles, audits, provenance and reproducible builds

<Levels label="Phase 11, supply chain">

<Level name="Beginner">

My app runs code from hundreds of packages I did not write. Each one is a way in.

</Level>

<Level name="Intermediate">

A lockfile pins exact versions and integrity hashes. `npm ci` installs exactly that. An audit checks
those versions against known vulnerabilities.

</Level>

<Level name="Advanced">

Provenance records where and how a package was built, so I can check it came from its source repo.
Install scripts run arbitrary code at install time, which is a common attack path.

</Level>

<Level name="Edge cases">

A typosquatted package one letter off a popular name.

</Level>

<Level name="Corner cases">

A trusted maintainer's account is taken over and a patch release ships malware: the version range I
allowed accepts it automatically.

</Level>

<Level name="Production level">

`npm ci` in CI, audits as a gate, a bot for update pull requests, review of new dependencies, and
install scripts disabled where possible.

</Level>

<Level name="Mindset">

Every dependency is a hire. Would I give this person commit access?

</Level>

<Level name="System design">

Reproducible builds plus signed artifacts let me prove what is running came from what was reviewed.

</Level>

<Level name="Strategy">

I run a dependency audit on my capstone, remove what I do not need, and make the audit a CI gate.
Done when high-severity findings block the build and each existing finding is fixed or justified.

</Level>

</Levels>

#### Phase 11: Incident response: detect, contain, eradicate, recover and learn

<Levels label="Phase 11, incident response">

<Level name="Beginner">

An incident is something going wrong in production that hurts users. Response is a practised
sequence, not improvisation.

</Level>

<Level name="Intermediate">

Detect (an alert fires), contain (stop the spread), eradicate (remove the cause), recover (restore
service), learn (postmortem with actions).

</Level>

<Level name="Advanced">

Blameless postmortems ask how the system allowed the mistake, which finds fixes; asking who made it
finds only someone to blame.

```md
## Postmortem: expired certificate on the replica port
Impact: 14 minutes of failed writes.
Cause: certificate renewal covered the public port only.
Preventive action: renew all ports from one job; alert 14 days before expiry.
```

</Level>

<Level name="Edge cases">

An incident at the moment nobody is watching. Alerts must reach a person.

</Level>

<Level name="Corner cases">

Containment that destroys evidence, such as restarting a compromised server before capturing its
state.

</Level>

<Level name="Production level">

Severity levels, one incident lead, a written timeline during the incident, and action items with
owners and dates.

</Level>

<Level name="Mindset">

Every incident is paid-for information. Waste it and it will be paid for again.

</Level>

<Level name="System design">

Feature flags, rollback and isolation are containment tools designed in before they are needed.

</Level>

<Level name="Strategy">

I run a game day: break my capstone on purpose, respond with the runbook, and write the postmortem.
Done when it has a preventive action that I then implement and test, which is part of the gate.

</Level>

</Levels>

#### Phase 11: exercises

- Add a CI pipeline to the capstone and prove it blocks a change that removes an access check.
- Write the capstone threat model: data-flow diagram, trust boundaries, STRIDE per boundary, one threat tree.
- Run a dependency audit and make it a gate.
- Self-review against the OWASP Top 10 with evidence for each item.
- Run a game day, cause an incident on purpose, and write the postmortem with a preventive action.
- Add property tests to the core logic and a fuzz test to input parsing.

#### Phase 11: the gate

I show three artefacts: a threat model with real findings, a CI pipeline that blocks a bad change
(demonstrated with a pull request that it rejects), and a postmortem with a preventive action that
is now in the code. Then, without notes, I explain the security tradeoffs in my capstone: where
trust boundaries are, which risks I accepted and why.
