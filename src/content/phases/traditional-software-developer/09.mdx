#### Phase 9: Finite automata, regular expressions and regular languages

<Levels label="Phase 9, finite automata, regular expressions and regular languages">

<Level name="Beginner">

A finite automaton reads input one character at a time, moving between a fixed set of states, and
accepts or rejects at the end. A regular expression describes the same set of strings in text.

</Level>

<Level name="Intermediate">

Every regular expression becomes an NFA (Thompson's construction), and every NFA becomes a DFA (the
subset construction). Simulating the NFA directly, tracking a set of states, runs in time linear in
the input.

```ts
type NFA = { start: number; accept: number; edges: Map<number, Array<[string | null, number]>> };
function step(nfa: NFA, states: Set<number>, c: string): Set<number> {
  const next = new Set<number>();
  for (const s of states) for (const [label, to] of nfa.edges.get(s) ?? []) if (label === c) next.add(to);
  return closure(nfa, next); // follow the empty (null) edges
}
```

</Level>

<Level name="Advanced">

Regular languages are exactly what finite memory can recognise. The pumping lemma shows the limit:
balanced parentheses need a counter that grows, so no regex recognises them.

</Level>

<Level name="Edge cases">

The empty string, the empty language and an expression like `a*` that matches nothing at all are
three different things, and an engine must treat each correctly.

</Level>

<Level name="Corner cases">

Backreferences plus a backtracking engine: the feature takes the language beyond regular and the
engine can take exponential time on a pattern like `(a+)+b`.

</Level>

<Level name="Production level">

A user-supplied regex run on a backtracking engine is a denial-of-service risk. I limit input size,
avoid nested quantifiers, or use a linear-time engine for untrusted patterns.

</Level>

<Level name="Mindset">

Ask how much memory a problem needs. "Finite" versus "grows with the input" decides which tool fits.

</Level>

<Level name="System design">

Lexers, input validators, routers and log parsers are all automata. Choosing a regex where a parser
is needed is a design bug.

</Level>

<Level name="Strategy">

I build a regex engine from NFAs in TypeScript with concatenation, alternation, star and grouping,
and time it against `RegExp` on `(a+)+b`. Done when it passes my tests and I can explain the timing
difference.

</Level>

</Levels>

#### Phase 9: Context-free grammars, derivations, ambiguity and parsing

<Levels label="Phase 9, context-free grammars, derivations, ambiguity and parsing">

<Level name="Beginner">

A context-free grammar is a set of rules that build sentences from smaller pieces. Unlike a regex,
a rule can refer to itself, which is what nesting needs.

</Level>

<Level name="Intermediate">

A derivation applies rules step by step; the parse tree records which rules were used. One grammar
for arithmetic, written by precedence levels:

```txt
expression := term ( ( "+" | "-" ) term )*
term       := factor ( ( "*" | "/" ) factor )*
factor     := NUMBER | "(" expression ")"
```

</Level>

<Level name="Advanced">

A grammar is ambiguous if one sentence has two parse trees. `1 - 2 - 3` with a rule like
`e := e "-" e` has two, and they compute different answers. Layering by precedence and choosing an
associativity removes it.

</Level>

<Level name="Edge cases">

Empty productions and the empty input: a grammar that allows nothing must still give a clear
answer when there is nothing.

</Level>

<Level name="Corner cases">

The dangling else: `if a if b x else y` is ambiguous where two optional parts meet. Languages pick a
rule (the else binds to the nearest if) and the parser must implement exactly that.

</Level>

<Level name="Production level">

Real grammars (JSON, SQL subsets, config formats) are where I meet this. I write the grammar down
before the parser, so the parser can be checked against something.

</Level>

<Level name="Mindset">

The grammar is the specification. If I cannot write it down, I do not know what my parser accepts.

</Level>

<Level name="System design">

Every format a system accepts has a grammar, written or not. Unwritten grammars are where two
parsers disagree and security bugs live.

</Level>

<Level name="Strategy">

I write the grammar for my interpreter's language before any parser code, then show both parse
trees for an ambiguous sentence under a naive version. Done when the final grammar has one tree for
every test sentence.

</Level>

</Levels>

#### Phase 9: Turing machines, computability, the halting problem and decidability

<Levels label="Phase 9, Turing machines, computability, the halting problem and decidability">

<Level name="Beginner">

A Turing machine is a finite automaton with an unlimited tape it can read and write. It is the
simplest model that can compute anything a computer can.

</Level>

<Level name="Intermediate">

A problem is decidable if some program always halts with the right yes or no. The halting problem
(does this program halt on this input?) is not.

</Level>

<Level name="Advanced">

The proof: suppose `halts(p, x)` exists. Build `trouble(p)` that loops forever if `halts(p, p)` is
true and halts otherwise. Then `trouble(trouble)` halts exactly when it does not. The assumption was
wrong.

```ts
declare function halts(program: string, input: string): boolean; // cannot exist
function trouble(p: string) { if (halts(p, p)) for (;;) {} }
```

</Level>

<Level name="Edge cases">

For a specific program on a specific input, halting can often be decided. Undecidable means no single
program decides it for all inputs.

</Level>

<Level name="Corner cases">

Recognisable but not decidable: I can confirm halting by running the program and waiting, but I can
never confirm non-halting that way. Two answers, one of which may never come.

</Level>

<Level name="Production level">

Linters, type checkers and static analysers face this limit. They either reject some correct
programs or accept some wrong ones; none is perfect. Timeouts are the practical answer for running
untrusted code.

</Level>

<Level name="Mindset">

Some questions have no algorithm. Knowing that saves me from building a tool that cannot exist.

</Level>

<Level name="System design">

Turing-complete configuration (templates with loops, build files with scripts) inherits the halting
problem. A less powerful format is often the safer design.

</Level>

<Level name="Strategy">

I write a Turing machine simulator and run a machine for a to the n, b to the n. Then I explain the
halting proof in three plain sentences, closed-book. Done when someone who has not studied it
follows my explanation.

</Level>

</Levels>

#### Phase 9: Complexity classes: P, NP, NP-complete, reductions and what hard means

<Levels label="Phase 9, complexity classes, reductions and what hard means">

<Level name="Beginner">

P is problems solvable in polynomial time. NP is problems whose answers can be checked in polynomial
time. Whether they are the same is open.

</Level>

<Level name="Intermediate">

A reduction turns problem A into problem B. If B is easy, A is easy; if A is hard, B is hard.
NP-complete problems are the hardest in NP: every NP problem reduces to them.

</Level>

<Level name="Advanced">

Checking a certificate is easy even when finding one is not:

```ts
// Verify a subset-sum certificate in linear time.
const verify = (nums: number[], pick: number[], target: number) =>
  pick.every((i) => i >= 0 && i < nums.length) && new Set(pick).size === pick.length &&
  pick.reduce((s, i) => s + nums[i], 0) === target;
```

</Level>

<Level name="Edge cases">

Pseudo-polynomial: subset sum has a dynamic-programming solution fast when the numbers are small.
Hardness depends on how the input is measured.

</Level>

<Level name="Corner cases">

A reduction written in the wrong direction proves nothing. Showing my problem reduces to an
NP-complete one only says it is no harder.

</Level>

<Level name="Production level">

Scheduling, packing and routing problems at work are often NP-hard. I reach for heuristics,
approximations, solvers or limits on input size instead of exact search.

</Level>

<Level name="Mindset">

Hard is about the worst case as input grows. Many hard problems are easy on the inputs I actually
have.

</Level>

<Level name="System design">

When a feature needs an NP-hard optimisation, I put a time budget on it and accept a good answer
over the best.

</Level>

<Level name="Strategy">

I time brute force, the DP and the verifier for subset sum as the input grows and plot the results.
Done when I can define NP-complete exactly and point to the curve that shows the difference.

</Level>

</Levels>

#### Phase 9: Lexing: tokens, regular expressions and a hand-written lexer

<Levels label="Phase 9, lexing">

<Level name="Beginner">

A lexer turns characters into tokens: numbers, names, operators, strings. The parser works on
tokens, not characters.

</Level>

<Level name="Intermediate">

A hand-written lexer is a loop over characters with a switch on the current one, a lookahead for
two-character operators, and a table for keywords.

```ts
switch (c) {
  case '=': return add(match('=') ? 'EQUAL_EQUAL' : 'EQUAL');
  case '"': return string();
  default: if (isDigit(c)) return number(); if (isAlpha(c)) return identifier();
}
```

</Level>

<Level name="Advanced">

Maximal munch: the lexer takes the longest token that matches, which is why `>=` is one token, not
two. A lexer is a DFA written by hand.

</Level>

<Level name="Edge cases">

End of input in the middle of a string or comment must produce a clear error with a line number.

</Level>

<Level name="Corner cases">

A keyword that is also a valid prefix of a name (`or` and `orchid`): longest match plus a keyword
table decides correctly only if the table lookup comes after the whole name is read.

</Level>

<Level name="Production level">

Every token carries its position for error messages. A lexer that never throws on random bytes is a
fuzz test I run before anything else.

</Level>

<Level name="Mindset">

Separate concerns: the lexer knows characters, the parser knows structure. Mixing them makes both
harder.

</Level>

<Level name="System design">

Editors, formatters and syntax highlighters reuse lexers. Error tolerance matters more there than in
a compiler.

</Level>

<Level name="Strategy">

I write the Lox scanner in TypeScript with tests per token type and a fuzz test of random bytes.
Done when both pass and every error names its line.

</Level>

</Levels>

#### Phase 9: Parsing: recursive descent, Pratt parsing, precedence and error recovery

<Levels label="Phase 9, parsing">

<Level name="Beginner">

Recursive descent writes one function per grammar rule. Each function calls the functions for the
rules inside it.

</Level>

<Level name="Intermediate">

Precedence lives in which function calls which: `term` calls `factor`, so multiplication binds
tighter. A loop inside each function gives left associativity.

</Level>

<Level name="Advanced">

Pratt parsing attaches a binding power to each operator and parses expressions in one function. New
operators become table entries.

```ts
function expr(minBp: number): Expr {
  let left = prefix(next());
  for (;;) {
    const op = peek(); const [lbp, rbp] = infixBp(op) ?? [-1, -1];
    if (lbp < minBp) break;
    next(); left = { kind: 'binary', op, left, right: expr(rbp) };
  }
  return left;
}
```

</Level>

<Level name="Edge cases">

Right-associative operators (assignment, exponent) need the right binding power one lower, or `a = b
= c` parses wrongly.

</Level>

<Level name="Corner cases">

An error inside a nested expression inside a statement: recovery must skip to a safe point
(synchronise at the next statement) without reporting a cascade of fake errors.

</Level>

<Level name="Production level">

Good error messages decide whether a language is usable. I report the expected token, the found
token and the position, and I keep parsing to report more than one error.

</Level>

<Level name="Mindset">

A parser is a direct translation of the grammar. When they differ, the grammar is the one to trust.

</Level>

<Level name="System design">

Language servers need parsers that recover and produce partial trees, because the code is broken
while being typed.

</Level>

<Level name="Strategy">

I write the recursive-descent parser for statements and a Pratt parser for expressions, and test a
table of thirty expressions with precedence and associativity. Done when the table passes and three
syntax errors in one file give three good messages.

</Level>

</Levels>

#### Phase 9: Abstract syntax trees and semantic analysis

<Levels label="Phase 9, abstract syntax trees and semantic analysis">

<Level name="Beginner">

An AST keeps the structure of the program and drops the punctuation. `(1 + 2) * 3` becomes a
multiply node with an add node inside.

</Level>

<Level name="Intermediate">

In TypeScript, a discriminated union is a natural AST, and `switch` on `kind` with a `never` check
makes missing cases a compile error.

```ts
type Expr =
  | { kind: 'num'; value: number }
  | { kind: 'var'; name: string }
  | { kind: 'binary'; op: string; left: Expr; right: Expr };
function never(x: never): never { throw new Error(String(x)); }
```

</Level>

<Level name="Advanced">

Semantic analysis checks what the grammar cannot: names are declared before use, `return` is inside a
function, a variable is not read in its own initialiser. The resolver computes how far up the scope
chain each name lives.

</Level>

<Level name="Edge cases">

Shadowing: an inner variable with the same name as an outer one. The resolver must pick the right
one at each use.

</Level>

<Level name="Corner cases">

A closure that captures a variable which is later shadowed in the enclosing scope. Without a resolver,
a dynamic lookup returns the wrong variable.

</Level>

<Level name="Production level">

Each node keeps its source position so later errors still point at code.

</Level>

<Level name="Mindset">

Parsing answers "is it well formed"; analysis answers "does it make sense". Keep them separate.

</Level>

<Level name="System design">

Linters, bundlers and codemods all work on ASTs. Knowing the shape of one makes those tools
readable.

</Level>

<Level name="Strategy">

I write the resolver and a test that fails before it (the closure-capture bug) and passes after.
Done when that test is green and an unhandled node kind fails the TypeScript build.

</Level>

</Levels>

#### Phase 9: Type checking: rules, inference, and checking versus guessing

<Levels label="Phase 9, type checking">

<Level name="Beginner">

A type checker rejects programs that would misuse values, such as adding a number to a function,
before they run.

</Level>

<Level name="Intermediate">

Typing rules are written per node: if the left and right are numbers, `+` gives a number. The checker
walks the AST applying them.

```ts
function check(e: Expr, env: Map<string, Type>): Type {
  switch (e.kind) {
    case 'num': return 'number';
    case 'var': { const t = env.get(e.name); if (!t) throw new Error(`unbound ${e.name}`); return t; }
    case 'binary': {
      const l = check(e.left, env), r = check(e.right, env);
      if (l !== 'number' || r !== 'number') throw new Error(`${e.op} needs numbers`);
      return 'number';
    }
  }
}
```

</Level>

<Level name="Advanced">

Inference finds types without annotations by generating constraints and solving them (unification).
Checking verifies a type I wrote; inference derives one. Guessing is neither: a checker that "tries"
without rules is unsound.

</Level>

<Level name="Edge cases">

Empty collections: the type of `[]` is unknown until something constrains it.

</Level>

<Level name="Corner cases">

Recursive functions with inferred types need the function's own type in scope while checking its
body, before that type is known.

</Level>

<Level name="Production level">

TypeScript is deliberately unsound in places (`any`, bivariant method parameters, casts). Knowing
where lets me decide where runtime validation is still needed.

</Level>

<Level name="Mindset">

A type is a promise the checker can verify. If it cannot verify it, it is a comment.

</Level>

<Level name="System design">

Types at module boundaries plus validation at system boundaries: the checker covers code I compile,
validation covers data I receive.

</Level>

<Level name="Strategy">

I write a checker for a small ML-like language with numbers, booleans, functions and `let`, then add
inference for `let`. Done when I can explain, for ten rejected programs, which rule rejected each.

</Level>

</Levels>

#### Phase 9: Intermediate representations, bytecode and a stack machine

<Levels label="Phase 9, intermediate representations, bytecode and a stack machine">

<Level name="Beginner">

Bytecode is a compact list of instructions for a virtual machine. A stack machine keeps
intermediate values on a stack: push two numbers, then `ADD` pops both and pushes the sum.

</Level>

<Level name="Intermediate">

The compiler walks the AST and emits instructions; constants go in a pool and are loaded by index.

```txt
1 + 2 * 3   =>   CONST 1, CONST 2, CONST 3, MUL, ADD
```

</Level>

<Level name="Advanced">

IRs sit between the AST and the machine. Stack bytecode is easy to generate; register-based and SSA
forms are easier to optimise. Each IR makes some transformations simple.

</Level>

<Level name="Edge cases">

A constant pool that overflows its index size (256 constants with one-byte operands) needs a wide
instruction.

</Level>

<Level name="Corner cases">

A jump whose offset does not fit in its operand, inside a loop body that also grew a constant: two
limits hit in one function.

</Level>

<Level name="Production level">

A disassembler is the first tool I build, because every VM bug is debugged by reading bytecode.

</Level>

<Level name="Mindset">

Each representation exists to make one job easy. Ask which job before choosing one.

</Level>

<Level name="System design">

V8, the JVM and WebAssembly all use bytecode or IRs. Reading their output (`node --print-bytecode`)
connects this phase to code I ship.

</Level>

<Level name="Strategy">

I build the chunk, the disassembler and the VM loop in C, then trace a program's stack by hand
before running it. Done when my predicted stack matches the trace at every step.

</Level>

</Levels>

#### Phase 9: Optimisation: constant folding, dead code elimination and inlining

<Levels label="Phase 9, optimisation">

<Level name="Beginner">

An optimiser rewrites a program to do the same thing faster. Constant folding computes `2 * 3` at
compile time.

</Level>

<Level name="Intermediate">

Dead code elimination removes code whose result is never used or that can never run. Inlining
replaces a call with the function's body.

```ts
function fold(e: Expr): Expr {
  if (e.kind !== 'binary') return e;
  const l = fold(e.left), r = fold(e.right);
  if (l.kind === 'num' && r.kind === 'num' && e.op === '*') return { kind: 'num', value: l.value * r.value };
  return { ...e, left: l, right: r };
}
```

</Level>

<Level name="Advanced">

Optimisations enable each other: inlining exposes constants, folding exposes dead branches. Compilers
run passes in a deliberate order, often more than once.

</Level>

<Level name="Edge cases">

Folding must follow runtime semantics exactly: integer overflow, floating point rounding and division
by zero must give the same result as running the code.

</Level>

<Level name="Corner cases">

Removing "dead" code that had a side effect (a call that logs) changes behaviour. Purity has to be
known before deleting.

</Level>

<Level name="Production level">

Measure before and after. An optimisation that does not move a benchmark is complexity with no
benefit.

</Level>

<Level name="Mindset">

Correctness first, then measure, then optimise the hot path only.

</Level>

<Level name="System design">

Bundlers do these passes on JavaScript (tree shaking is dead code elimination across modules).

</Level>

<Level name="Strategy">

I add constant folding and dead branch removal to my compiler and benchmark before and after. Done
when the numbers are recorded and the full test suite still passes.

</Level>

</Levels>

#### Phase 9: Code generation, calling conventions and a first look at JIT

<Levels label="Phase 9, code generation, calling conventions and JIT">

<Level name="Beginner">

Code generation turns an IR into instructions for a real or virtual machine.

</Level>

<Level name="Intermediate">

A calling convention fixes where arguments go, who saves which registers, and where the return value
lands. In my VM, a call frame records the function, its instruction pointer and its stack window.

</Level>

<Level name="Advanced">

A JIT compiles hot bytecode to machine code at run time, using what it has observed (types seen,
branches taken) to specialise. If an assumption breaks, it deoptimises back to the interpreter.

</Level>

<Level name="Edge cases">

Deep recursion overflows the frame stack. The VM must report it as a language error, not crash.

</Level>

<Level name="Corner cases">

A function that is hot and polymorphic: the JIT's type assumption fails repeatedly and it keeps
deoptimising, slower than never compiling.

</Level>

<Level name="Production level">

In Node, keeping object shapes and argument types consistent keeps V8 on its fast path. That is a
calling-convention lesson applied to JavaScript.

</Level>

<Level name="Mindset">

Every abstraction has a cost model. Know roughly what a call costs in the runtime I use.

</Level>

<Level name="System design">

Interpreters start fast; compilers run fast. Tiered runtimes use both, and that tradeoff appears in
any system with warm-up.

</Level>

<Level name="Strategy">

I implement calls and frames in my VM and compare its speed with the tree-walker on a recursive
benchmark. Done when both numbers are recorded and I can explain where the difference comes from.

</Level>

</Levels>

#### Phase 9: Garbage collection: reference counting, tracing and generational collectors

<Levels label="Phase 9, garbage collection">

<Level name="Beginner">

A garbage collector frees memory the program can no longer reach, so I never call `free`.

</Level>

<Level name="Intermediate">

Reference counting frees an object when its count reaches zero. Tracing (mark and sweep) starts from
roots (stack, globals), marks everything reachable and frees the rest.

</Level>

<Level name="Advanced">

Generational collectors rely on most objects dying young: collect the young area often and cheaply,
the old area rarely. V8 does this.

</Level>

<Level name="Edge cases">

Reference counting leaks cycles: two objects pointing at each other never reach zero.

</Level>

<Level name="Corner cases">

A collection triggered in the middle of allocating an object whose pointer is not yet on the stack
frees it. Stress mode (collect on every allocation) finds this.

</Level>

<Level name="Production level">

Memory leaks in JavaScript are references kept alive by mistake: listeners, caches, closures. A heap
snapshot shows the retaining path.

</Level>

<Level name="Mindset">

Reachability, not use, decides lifetime. If something is reachable, it lives.

</Level>

<Level name="System design">

Pause times matter for latency-sensitive services. Collector choice and allocation rate are part of
performance design.

</Level>

<Level name="Strategy">

I write mark-sweep for my VM and run the whole test suite with stress GC and AddressSanitizer on.
Done when it passes and I can explain one missing-root bug I found.

</Level>

</Levels>

#### Phase 9: the gate

Closed-book, no AI, no search: I write a recursive-descent parser and an interpreter for a small
expression-and-statement language from a blank file, with tests. Then I explain, out loud or in
writing, why the halting problem is undecidable, what my type checker rejects and why, and how an
interpreter differs from a compiler. If any explanation needs notes, I go back to the matching
section above and try again a week later.
