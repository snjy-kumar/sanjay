Four weeks of the grammar of computer science. Every later phase leans on this one: invariants and
induction for data structures, counting and recurrences for algorithms, modular arithmetic for hashing
and security, probability for benchmarks and distributed systems, graphs for networks. The primary
book is <a href={withBase('/books/mathematics-for-computer-science/')}>Mathematics for Computer Science</a>
with the MIT 6.042J lectures; <a href={withBase('/books/discrete-mathematics-and-its-applications/')}>Rosen</a>
is the reference beside it, and the source for Boolean algebra and matrices.

#### Phase 2: how I would learn it

Proofs on paper, everything else in code. Each week I write proofs into a notebook without looking,
check them against the text, and compute whatever can be computed: truth tables, the modular toolkit,
simulations, a graph checker. When a proof and a program agree, I understand the idea twice.

#### Phase 2: Propositional and predicate logic

<Levels label="Phase 2, propositional and predicate logic">

<Level name="Beginner">

Propositions are true or false and combine with and, or, not, implies. Truth tables decide every
formula. Predicates add variables and the quantifiers "for all" and "there exists".

</Level>

<Level name="Intermediate">

Every `if` is a formula; De Morgan's laws rewrite guards safely. A truth-table generator checks any
rewrite exhaustively.

```ts
const vars = ['a', 'b'];
const rows = [...Array(1 << vars.length).keys()].map(i => vars.map((_, j) => Boolean((i >> j) & 1)));
const equiv = (f: (...x: boolean[]) => boolean, g: (...x: boolean[]) => boolean) => rows.every(r => f(...r) === g(...r));
equiv((a, b) => !(a && b), (a, b) => !a || !b);   // true
```

</Level>

<Level name="Advanced">

Negation swaps quantifiers: not every request is authorised means some request is not. Implication is
false only when the premise is true and the conclusion false.

</Level>

<Level name="Edge cases">

For all over an empty set is true; there exists over an empty set is false. `[].every` and `[].some`
agree.

</Level>

<Level name="Corner cases">

Short-circuit evaluation plus a side effect: `a() && b()` is a logical and, but `b` may not run at all.

</Level>

<Level name="Production level">

Authorisation rules and feature flags are formulas; test their truth tables.

</Level>

<Level name="Mindset">

Translate English into logic before reasoning; ambiguity hides in the English.

</Level>

<Level name="System design">

SAT solvers, policy engines and query planners operate on formulas.

</Level>

<Level name="Strategy">

Translate five requirements into predicate logic and negate them. Done when each negation, read back in
English, is the real failure case.

</Level>

</Levels>

#### Phase 2: Proof techniques

<Levels label="Phase 2, proof techniques">

<Level name="Beginner">

A direct proof goes from assumptions to conclusion. Contradiction assumes the opposite and reaches the
impossible. Induction proves a base case and a step.

</Level>

<Level name="Intermediate">

Strong induction assumes every smaller case. A recurrence like `T(n) = 2T(n/2) + n` is proved by
guessing `T(n)` at most `c n log n` and checking the step.

</Level>

<Level name="Advanced">

Ordinary induction, strong induction and the well ordering principle are equivalent; loop invariants
are induction over iterations.

</Level>

<Level name="Edge cases">

The base case must be the domain's first element; a step valid only from 2 upward needs base cases at
1 and 2.

</Level>

<Level name="Corner cases">

The "all horses are the same colour" fallacy: a step that fails at exactly one size plus a base case
just below it.

</Level>

<Level name="Production level">

Code review of a tricky loop is an informal invariant proof. Assertions make it executable.

</Level>

<Level name="Mindset">

A proof says what is true for every input under its assumptions, and nothing outside them.

</Level>

<Level name="System design">

Distributed protocol safety is proved by invariants over state transitions; this is where that starts.

</Level>

<Level name="Strategy">

Write ten proofs I can explain without looking, including one recurrence by induction. Done when I can
present each from a blank page.

</Level>

</Levels>

#### Phase 2: Sets, relations, functions, cardinality and countability

<Levels label="Phase 2, sets, relations, functions, cardinality and countability">

<Level name="Beginner">

Sets, ordered pairs, relations and functions are the vocabulary. A function maps each input to exactly
one output.

</Level>

<Level name="Intermediate">

Injective, surjective, bijective. Database keys are injective functions; joins compose relations.

</Level>

<Level name="Advanced">

Equivalence relations partition; partial orders order dependencies. Two sets have the same cardinality
if a bijection exists; the reals are uncountable, by diagonalisation.

</Level>

<Level name="Edge cases">

The empty set is a subset of every set; the power set of `n` elements has `2^n` members.

</Level>

<Level name="Corner cases">

A "function" that sometimes returns two rows or none is a relation pretending; that mismatch is a
duplicate-key or missing-row bug.

</Level>

<Level name="Production level">

Data models are mathematical data types; name them before writing the schema.

</Level>

<Level name="Mindset">

Ask: set, sequence, function or relation?

</Level>

<Level name="System design">

Undecidability, from countability, explains why perfect static analysis cannot exist.

</Level>

<Level name="Strategy">

Classify ten functions from my code. Done when each classification survives a counterexample search.

</Level>

</Levels>

#### Phase 2: Combinatorics

<Levels label="Phase 2, combinatorics">

<Level name="Beginner">

Sum and product rules; permutations order, combinations do not.

</Level>

<Level name="Intermediate">

`n choose k` counts subsets; the division rule removes the orderings I did not want.

</Level>

<Level name="Advanced">

Pigeonhole proves collisions must exist; inclusion-exclusion fixes overlaps; bijections count hard sets
via easy ones.

</Level>

<Level name="Edge cases">

Choosing zero is one way; `0!` is 1; choosing more than `n` is zero ways.

</Level>

<Level name="Corner cases">

Ordered selection plus overlapping categories: both overcounts at once.

</Level>

<Level name="Production level">

Key-space sizes, collision guarantees and exhaustive test feasibility are counting.

</Level>

<Level name="Mindset">

Count two ways; the answers must agree.

</Level>

<Level name="System design">

Hash width, ID formats and sharding rest on counting arguments.

</Level>

<Level name="Strategy">

Check every counting formula against brute-force enumeration for small `n`. Done when they agree.

</Level>

</Levels>

#### Phase 2: Probability

<Levels label="Phase 2, probability">

<Level name="Beginner">

A sample space, events, and probabilities that sum to 1. Conditional probability shrinks the world to
the condition.

</Level>

<Level name="Intermediate">

Bayes with a concrete example: a test that catches 99 percent of a 1-in-1000 condition with a 1
percent false alarm rate gives about a 9 percent chance after a positive result. Monty Hall: switching
wins two times in three.

```ts
function simulate(trials: number): { p: number; lo: number; hi: number } {
  let wins = 0;
  for (let t = 0; t < trials; t++) {
    const car = Math.floor(Math.random() * 3), pick = Math.floor(Math.random() * 3);
    if (pick !== car) wins++;            // switching wins exactly when the first pick was wrong
  }
  const p = wins / trials, se = Math.sqrt((p * (1 - p)) / trials);
  return { p, lo: p - 1.96 * se, hi: p + 1.96 * se };
}
```

</Level>

<Level name="Advanced">

Expectation is linear; variance adds for independent variables; the law of large numbers says sample
averages converge; Chebyshev and the central limit theorem size the interval.

</Level>

<Level name="Edge cases">

Zero successes collapse the simple interval to a point; use a Wilson interval for proportions near 0
or 1.

</Level>

<Level name="Corner cases">

Dependent samples plus an independence assumption give an interval far too narrow.

</Level>

<Level name="Production level">

Benchmarks and A/B tests need intervals; base rates decide whether alerts are worth it.

</Level>

<Level name="Mindset">

Write the sample space; never trust intuition about conditional probability.

</Level>

<Level name="System design">

Sampling, canaries, Bloom filters and retries are probability in production.

</Level>

<Level name="Strategy">

Simulate Monty Hall and the birthday paradox with confidence intervals. Done when each interval
contains the exact value and I can say what the 95 percent means.

</Level>

</Levels>

#### Phase 2: Number theory

<Levels label="Phase 2, number theory">

<Level name="Beginner">

Divisibility, primes, remainders, the gcd by Euclid's algorithm.

</Level>

<Level name="Intermediate">

The extended gcd gives modular inverses; fast exponentiation squares and multiplies.

```ts
function modexp(b: bigint, e: bigint, m: bigint): bigint {
  let r = 1n; b %= m;
  for (; e > 0n; e >>= 1n) { if (e & 1n) r = (r * b) % m; b = (b * b) % m; }
  return r;
}
```

</Level>

<Level name="Advanced">

Euler's theorem makes RSA work: encrypting with `e` and decrypting with `d`, where `e d` is 1 modulo
phi(n), returns the message.

</Level>

<Level name="Edge cases">

`gcd(a, 0)` is `a`; a number sharing a factor with the modulus has no inverse; anything modulo 1 is 0.

</Level>

<Level name="Corner cases">

JavaScript's `%` with negative numbers plus `number` precision above 2 to the 53: two silent errors.
Normalise and use `bigint`.

</Level>

<Level name="Production level">

Never use textbook RSA for real; use vetted libraries.

</Level>

<Level name="Mindset">

Reduce early; big numbers stay small.

</Level>

<Level name="System design">

Hashing, sharding and public key cryptography sit on modular arithmetic.

</Level>

<Level name="Strategy">

Build the toolkit and a toy RSA round trip, tested against brute force. Done when modexp is right for
random inputs and the round trip works.

</Level>

</Levels>

#### Phase 2: Graphs and trees

<Levels label="Phase 2, graphs and trees">

<Level name="Beginner">

Vertices and edges; degree, paths, connectivity. A tree is connected and acyclic.

</Level>

<Level name="Intermediate">

The graph checker: connected components, cycle detection, bipartiteness by 2-colouring in a BFS.

</Level>

<Level name="Advanced">

Bipartite exactly when there is no odd cycle; a tree on `n` vertices has `n - 1` edges; colouring is
hard in general.

</Level>

<Level name="Edge cases">

One vertex is connected; an empty graph is bipartite; components need an outer loop over all vertices.

</Level>

<Level name="Corner cases">

A disconnected graph whose second component has an odd cycle fools a checker that starts only at
vertex 0.

</Level>

<Level name="Production level">

Recursion depth on long path graphs overflows the stack; use an explicit queue.

</Level>

<Level name="Mindset">

See the graph in the problem.

</Level>

<Level name="System design">

Networks, dependencies and social systems are graphs; Phases 3, 4 and 7 build on this.

</Level>

<Level name="Strategy">

Build the checker and test it against brute force on random small graphs. Done when it handles
disconnected graphs and I can prove the odd-cycle theorem.

</Level>

</Levels>

#### Phase 2: Recurrences and asymptotic notation

<Levels label="Phase 2, recurrences and asymptotic notation">

<Level name="Beginner">

A recurrence defines a cost from smaller costs; big O, Omega and Theta describe growth.

</Level>

<Level name="Intermediate">

Hanoi is `2^n - 1` moves; merge sort is about `n log n`.

</Level>

<Level name="Advanced">

Linear recurrences by characteristic roots; divide-and-conquer recurrences by the master theorem or
Akra-Bazzi.

</Level>

<Level name="Edge cases">

Initial conditions decide constants; floors and ceilings rarely change growth.

</Level>

<Level name="Corner cases">

Overlapping subproblems plus naive recursion: exponential time. Memoise.

</Level>

<Level name="Production level">

Accidental exponential recursion and hidden quadratics are real incidents.

</Level>

<Level name="Mindset">

Guess the form, then prove it.

</Level>

<Level name="System design">

The recurrence says where the cost of divide and conquer sits.

</Level>

<Level name="Strategy">

Prove one recurrence by induction and match it against an operation counter. Done when counts and
formula agree exactly for small inputs.

</Level>

</Levels>

#### Phase 2: Boolean algebra, gates and hardware

<Levels label="Phase 2, boolean algebra, gates and hardware">

<Level name="Beginner">

AND, OR, NOT on bits; NAND alone is enough to build everything.

</Level>

<Level name="Intermediate">

A half adder is XOR plus AND; chaining full adders gives a ripple-carry adder.

</Level>

<Level name="Advanced">

Sum-of-products from truth tables; Karnaugh maps minimise. Phase 5 builds on this toward a CPU.

</Level>

<Level name="Edge cases">

A function of zero inputs is a constant; don't-cares can be set either way.

</Level>

<Level name="Corner cases">

Gate delays plus logic: glitches the truth table does not show.

</Level>

<Level name="Production level">

Masks and flags in code are Boolean algebra on words.

</Level>

<Level name="Mindset">

Hardware is logic you can hold.

</Level>

<Level name="System design">

From gates to ALU to CPU is the path Nand2Tetris walks, which Phase 5 picks up.

</Level>

<Level name="Strategy">

Simulate a 4-bit ripple-carry adder from gate functions. Done when it adds all 256 pairs correctly.

</Level>

</Levels>

#### Phase 2: Linear algebra basics

<Levels label="Phase 2, linear algebra basics">

<Level name="Beginner">

Vectors are lists of numbers; matrices transform them. The dot product measures alignment.

</Level>

<Level name="Intermediate">

Matrix multiplication composes transformations; adjacency-matrix powers count walks in a graph.

</Level>

<Level name="Advanced">

Rotations and scalings are matrices; an eigenvector is a direction a transformation only stretches.
That is the preview the plan asks for.

</Level>

<Level name="Edge cases">

Dimensions must match; the zero vector has no direction.

</Level>

<Level name="Corner cases">

Floating-point products are not exactly associative; reordering changes the last digits.

</Level>

<Level name="Production level">

Graphics, ranking and machine learning run on these operations; numeric libraries handle stability.

</Level>

<Level name="Mindset">

Think of a matrix as a function on vectors.

</Level>

<Level name="System design">

PageRank-style ranking is an eigenvector of a graph's transition matrix.

</Level>

<Level name="Strategy">

Implement dot product, matrix multiply and power iteration for the top eigenvector of a small matrix.
Done when power iteration converges to the known answer.

</Level>

</Levels>
