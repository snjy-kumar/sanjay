What it is
</h2>
<p><code>any</code> opts a value out of checking in both directions. You can read any property, call it, and pass it anywhere, and you can assign anything to it. It compiles, it ships, and it removes the reason to use TypeScript on that path. The usual excuse is local: one <code>any</code> to unblock a feature. The property that does not exist is then a runtime error three files later, often spelled wrong, like <code>nmae</code>, which <code>any</code> will not catch.</p>
<p><code>any</code> is contagious. A function that returns it turns the caller’s variables into <code>any</code> the moment they are used as <code>any</code>. A function that accepts it accepts a mistake from honest code. <code>unknown</code> is the opposite default: you can hold the value, but you cannot touch it until a check narrows it. A real interface is what you use once you do know the shape. A parse at the boundary — hand-written checks, or a schema library if you already depend on one — is how <code>unknown</code> becomes that interface.</p>
<p>This is not a moral rule about a forbidden keyword. It is cost. <code>any</code> in a core model is technical debt with a short name, because every downstream signature quietly degrades to JavaScript.</p>
<p>An API handler in a personal project maps <code>res.data.items</code> to names for a list view. Typed as <code>any</code>, the map compiles with <code>i.nmae</code>. The list renders blanks. The same <code>any</code> is passed into a save function that expected a <code>User</code>, so a partial object is written through. Replacing the parameter with <code>unknown</code> forces one parser. After that parser, <code>item.name</code> is a string and the typo is a compile error.</p>
</section>

Old
</h2>
<p><strong>Wrong approach: <code>any</code> to unblock</strong></p>
<p><strong>Best case.</strong> A type you delete the same hour, isolated in a scratch file, never exported, never stored. Or a third-party callback typed <code>any</code> that you immediately narrow into a local <code>unknown</code> variable and parse. The keyword does not escape.</p>
<p><strong>Worst case.</strong> Core models are <code>any</code>. Typos compile. Refactors do not fail. A function annotated <code>any</code> accepts a number where a <code>User</code> belongs and returns a value every caller treats as checked. You are maintaining JavaScript with an extra compile step.</p>
<p>Before: the list view and the logger both take <code>any</code> so the feature can ship.</p>

<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M7 2.15 11.7 7 7 11.85 2.3 7z"/></svg>
New
</h2>
<p><strong>Right approach: <code>unknown</code>, then a real type</strong></p>
<p><strong>Best case.</strong> JSON, request bodies, and document dumps stay <code>unknown</code> until one function checks them. The rest of the app takes <code>Item</code> or <code>User</code>. <code>item.nmae</code> fails at compile time. Callers of <code>handle</code> get <code>string[]</code> and cannot pass the raw payload onward.</p>
<p><strong>Worst case.</strong> A parser full of casts (<code>as Item</code>) wearing the costume of <code>unknown</code>. The parameter type looks careful and the body repeats <code>any</code>’s mistake one assertion at a time. <code>unknown</code> only helps if the narrowing is a real check: <code>typeof</code>, <code>in</code>, <code>Array.isArray</code>, or a schema that returns a typed value.</p>
<p>After: <code>unknown</code> in, <code>string[]</code> out, and the typo cannot hide.</p>

<section class="section" id="when">
<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M3.6 2.4v9.2"/><path d="M3.6 6.4h4.35"/><path d="M7.95 6.4 11.15 3.5"/><path d="M7.95 6.4 11.15 9.3"/></svg>
When to use which
</h2>
<p>Turn on <code>noImplicitAny</code> so the shortcut has to be typed on purpose. Ban <code>any</code> on exported functions and on models that other modules import; a lint rule such as <code>no-explicit-any</code> is the mechanical version of that ban. Where a type is genuinely not known yet — <code>JSON.parse</code>, <code>response.json()</code>, a request body — store <code>unknown</code> and parse once into a named type. Do not “fix” an error by annotating <code>any</code> or by prefixing the expression with <code>as any</code>. If you need a temporary escape in a migration, keep it in one function at the edge and give it a comment that names the replacement type. Replace one <code>any</code> in a core model before adding a new one.</p>
<div class="when">
<div class="when-row"><span>JSON, a request body, or a document dump</span><span class="when-choice">unknown</span></div>
<div class="when-row"><span>A shape you already know</span><span class="when-choice">named type</span></div>
<div class="when-row"><span>An exported function or shared model</span><span class="when-choice">no any</span></div>
<div class="when-row"><span>A temporary escape while migrating</span><span class="when-choice">one edge function</span></div>
</div>
