What it is
</h2>
<p><code>interface</code> and <code>type</code> both name a shape, so it is easy to swap them per file and treat the choice as taste. The code still compiles. What you lose is a rule you can apply when the shape is not a plain object.</p>
<p>An interface describes an object (or a callable or construct signature) and can be extended or merged by another declaration with the same name. A type alias can name almost any type: a union, an intersection, a primitive, a tuple, a mapped type, or a function. You cannot write a string-literal union as an interface without stuffing it into a dummy object, and that dummy object is how a finite set quietly becomes “some string field.”</p>
<p>Neither keyword is more professional. The useful split in application code is: <code>interface</code> for object shapes you expect to extend (component props, API models), <code>type</code> for unions, function aliases, and compositions built with utilities. Pick that rule once per codebase and keep it, including when you are the only reviewer.</p>
<p>A post card in a personal project needs props, a publish status, and a click handler. Props are an object you might extend with an optional <code>href</code> later. Status is three strings, not an object. The handler is a function type reused by the card and by a keyboard shortcut. Modeling status as <code>interface Status { value: string }</code> throws away the finite set. Mixing <code>type PostCardProps</code> in one file and <code>interface PostCardProps</code> in another just creates churn.</p>
</section>

Old
</h2>
<p><strong>Wrong approach: no rule, unions forced into objects</strong></p>
<p><strong>Best case.</strong> A tiny file where every alias is a flat object and you never extend it. <code>interface</code> and <code>type</code> behave alike, so the mix does not hurt yet.</p>
<p><strong>Worst case.</strong> Status, role, and route names all become <code>{ value: string }</code> or a bare <code>string</code> because an interface could not hold the union. Call sites lose autocomplete. A second <code>interface User</code> in the same scope merges fields you did not mean to add. Separate modules do not merge just because the name matches; a global, a namespace, or a second declaration in the same file does. Reviews argue the keyword instead of the data.</p>
<p>Before: one file uses a type for props, the next uses an interface, and the status union has been flattened so it will fit anywhere.</p>

New
</h2>
<p><strong>Right approach: interface for objects, type for the rest</strong></p>
<p><strong>Best case.</strong> Props and API models use <code>interface</code> and <code>extends</code>. Unions, handlers, and utility compositions use <code>type</code>. A new teammate — or you, six months later — can tell why a declaration was written that way without a comment war.</p>
<p><strong>Worst case.</strong> You follow the rule so rigidly that a one-off union of two object shapes becomes awkward, or you export an interface that then merges with a dependency’s interface of the same name. The rule is a default, not a ban on <code>type</code> for objects. If a public object type must not merge, a type alias is the safer export.</p>
<p>After: props stay extendable objects, status is a union, and the handler has a real alias.</p>

<section class="section" id="when">
<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M3.6 2.4v9.2"/><path d="M3.6 6.4h4.35"/><path d="M7.95 6.4 11.15 3.5"/><path d="M7.95 6.4 11.15 9.3"/></svg>
When to use which
</h2>
<p>Write the rule at the top of the types module, then stop relitigating it. Use <code>interface</code> for component props and for object models you <code>extend</code>. Use <code>type</code> the moment you need a union, a tuple, a mapped type, or a function signature. Reach for <code>extends</code> on interfaces and intersections or utilities on type aliases. Do not wrap a union in an object just to keep using <code>interface</code>. If a type is part of a public export and accidental declaration merging would be bad, prefer <code>type</code>.</p>
<div class="when">
<div class="when-row"><span>Object shape you expect to extend</span><span class="when-choice">interface</span></div>
<div class="when-row"><span>Union, tuple, mapped type, or function</span><span class="when-choice">type</span></div>
<div class="when-row"><span>Public export that must not merge</span><span class="when-choice">type</span></div>
</div>
</section>
