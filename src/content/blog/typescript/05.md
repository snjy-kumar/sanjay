What it is
</h2>
<p>An array type <code>number[]</code> means “zero or more numbers, order does not change the type of each slot.” That is correct for a list of scores. It is the wrong model for a coordinate, where index 0 is latitude, index 1 is longitude, and a third number is not a plan.</p>
<p>A tuple fixes the length and the type at each position: <code>[number, number]</code> or <code>[string, number]</code>. Extra elements, missing elements, and a string in the latitude slot fail to assign. Arrays say the length may grow. Tuples say the shape is part of the contract. If the positions have names that readers must remember, an object is often clearer than either — the point of the tuple is a short, ordered pair, not a secret struct.</p>
<p>A map pin in a personal project is stored as <code>[lat, lng]</code> because that is the order a small helper already expects, and a chart series is a list of <code>[label, value]</code> pairs such as <code>["views", 120]</code> before those records grow enough fields to deserve an object. Typing both as <code>number[]</code> or <code>(string | number)[]</code> lets a third coordinate through and lets the label and the value swap places.</p>
</section>

Old
</h2>
<p><strong>Wrong approach: an array wherever there is a list</strong></p>
<p><strong>Best case.</strong> The array really is a list: search results, tags, log lines. Length changes, and every element means the same thing. A tuple would fight the domain.</p>
<p><strong>Worst case.</strong> You meant a coordinate. <code>push</code> adds a third number, a bug swaps latitude and longitude, both still type-check, and the pin is simply wrong on the map. A pair typed as <code>(string | number)[]</code> makes you narrow on every read.</p>

<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M7 2.15 11.7 7 7 11.85 2.3 7z"/></svg>
New
</h2>
<p><strong>Right approach: a tuple when position is the API</strong></p>
<p><strong>Best case.</strong> <code>[number, number]</code> rejects a third value and a non-number. Destructuring names the positions at the use site. Helpers that talk to a library expecting <code>[lat, lng]</code> stay honest without a class.</p>
<p><strong>Worst case.</strong> An eight-element tuple with no labels. Callers pass arguments in the wrong order and the types still line up because too many slots share a type. At that size, switch to an object. Tuples also widen in unannotated literals sometimes (<code>as const</code> or an explicit annotation fixes inference). A tuple does not validate a runtime array from JSON; you still parse length and types before asserting the tuple.</p>
<p>After: both helpers take a fixed pair. The distance function cannot be called with a 3D point by accident. The formatter knows which side is text.</p>

When to use which
</h2>
<p>Use <code>T[]</code> when the length is allowed to change and every index has the same meaning. Use a tuple for pairs and other short fixed records: coordinates, <code>[string, number]</code> entries, a function that returns <code>[value, error]</code>. Prefer an object once the positions need names to be readable. Annotate the tuple (or use <code>as const</code> for a literal you do not intend to widen). At a JSON boundary, check <code>Array.isArray</code>, length, and element types, then return the tuple type — do not cast a raw array.</p>
<div class="when">
<div class="when-row"><span>Length may change and every index means the same thing</span><span class="when-choice">array</span></div>
<div class="when-row"><span>A short fixed pair</span><span class="when-choice">tuple</span></div>
<div class="when-row"><span>Positions need names to stay readable</span><span class="when-choice">object</span></div>
<div class="when-row"><span>A JSON array at the boundary</span><span class="when-choice">parse, then tuple</span></div>
</div>
