What it is
</h2>
<p><code>null</code>, <code>undefined</code>, and an optional property all feel like “no value.” They are three different absences, and collapsing them with <code>|| ""</code> or <code>|| "N/A"</code> hides which one you had.</p>
<p>With <code>strictNullChecks</code>, <code>null</code> and <code>undefined</code> are not members of <code>string</code> unless you add them. An optional property <code>name?: string</code> means the caller may omit the key; a read of it is <code>string | undefined</code>. Writing <code>name: string | undefined</code> means the key is part of the object and the value may be <code>undefined</code>. Writing <code>name: string | null</code> means the key is present and <code>null</code> is an intentional empty, which is how a lot of JSON APIs say “the user cleared this” or “it was never set” if you have agreed on that meaning. <code>""</code> is a fourth state: present, and blank.</p>
<p>Under <code>exactOptionalPropertyTypes</code>, the split gets sharper on the way in. An optional property does not accept an explicit <code>undefined</code> unless <code>undefined</code> is in its type. Without that flag, assigning <code>undefined</code> to an optional property is allowed, so the difference is easier to miss. Reading still cannot tell “omitted” from “set to undefined” unless you check <code>in</code> or <code>hasOwn</code>.</p>
<p>The question to ask before picking a default is: is this absence a valid state, or a bug? Valid absence gets a type and a branch. A bug fails at the boundary instead of being painted over with <code>"N/A"</code>.</p>
<p>A profile screen in React. The API returns <code>bio: null</code> when the person has never written one, and <code>bio: ""</code> when they saved an empty bio on purpose. A presentational row takes <code>bio?: string</code> so the parent can omit the row’s text entirely. The old helper <code>profile.bio || "N/A"</code> shows “N/A” for <code>null</code>, for <code>undefined</code>, and for <code>""</code>, so support cannot tell “not set” from “set to empty,” and a real bug — the field missing because a select forgot it — looks like a normal profile.</p>
</section>

Old

<p><strong>Wrong approach: one fallback for every absence</strong></p>
<p><strong>Best case.</strong> The product truly wants the same placeholder for missing, null, and blank, and you have checked that no other falsy value can appear. <code>||</code> is then a display choice, not a parser. Even then, <code>??</code> is usually the operator you meant if <code>""</code> should stay visible, because <code>||</code> treats <code>""</code> as missing.</p>
<p><strong>Worst case.</strong> A dropped field, a JSON <code>null</code>, and a user-entered empty string all render “N/A”. A bug in the query looks like an empty profile. <code>||</code> also collapses the number <code>0</code> if this pattern is copied onto a count. The UI cannot show “not set” versus “cleared.”</p>

New
</h2>
<p><strong>Right approach: one type per meaning</strong></p>
<p><strong>Best case.</strong> <code>null</code> renders “Not set,” <code>""</code> renders “Empty,” and a missing optional prop skips the row. <code>strictNullChecks</code> forces each call site to decide. Invalid data that should have been a string fails in the parser instead of becoming a placeholder.</p>
<p><strong>Worst case.</strong> You model three absences the product does not actually distinguish, and every call site grows branches that all do the same thing. Or you turn on <code>exactOptionalPropertyTypes</code> in a large repo without fixing call sites that pass explicit <code>undefined</code>. Match the type to a real product difference; do not add null only to look careful.</p>
<p>After: the API type keeps null, the props type uses omission for “no row,” and the adapter is the only place that maps one to the other.</p>

<section class="section" id="when">
<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M3.6 2.4v9.2"/><path d="M3.6 6.4h4.35"/><path d="M7.95 6.4 11.15 3.5"/><path d="M7.95 6.4 11.15 9.3"/></svg>
When to use which
</h2>
<p>Turn on <code>strictNullChecks</code> if it is not already on; without it, <code>null</code> and <code>undefined</code> flow into every type and this distinction is fiction. Use <code>?:</code> when a React prop or object key may be omitted. Use <code>| undefined</code> when the key should exist. Use <code>| null</code> when the backend intentionally sends null, and document that meaning next to the type. Compare with <code>=== null</code> and <code>=== undefined</code>, not truthiness. Prefer <code>??</code> over <code>||</code> when empty string or zero is real data. If absence is a bug, throw or reject at the boundary and keep the inner type non-null.</p>
<div class="when">
<div class="when-row"><span>The caller may omit the key</span><span class="when-choice">optional property</span></div>
<div class="when-row"><span>The key should exist</span><span class="when-choice">string | undefined</span></div>
<div class="when-row"><span>The backend sends intentional null</span><span class="when-choice">string | null</span></div>
<div class="when-row"><span>Empty string or zero is real data</span><span class="when-choice">??</span></div>
<div class="when-row"><span>Absence is a bug</span><span class="when-choice">reject at the boundary</span></div>
</div>
