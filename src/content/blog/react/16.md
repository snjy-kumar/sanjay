What it is
</h2>
<p>This note closes the React series. The fifteen pages before it represent the core mental models I rely on every day: deriving state rather than synchronizing it in effects, reserving <code>useEffect</code> for external synchronization rather than user events, keeping list keys stable across renders, and lifting state only as far as necessary.</p>
<p>The later notes tackle architectural seams. Avoid giant form state bags by trusting the browser’s native <code>FormData</code>. Favor component composition with <code>children</code> over twenty-prop monolithic wrappers. Abort in-flight network requests on unmount to eliminate race conditions. Respect the distinction between visible UI state and silent internal refs.</p>
<p>Like the close of the TypeScript series, this page compresses the entire journey into a clean wrong-vs-right reference. The code you write after absorbing these habits is almost always less code than the versions they replace—cleaner, faster, and far easier to reason about.</p>
<p>Whenever I review a React component, these are the invariants I check first.</p>

Old
</h2>
<p><strong>Wrong approach: fighting React's render model with artificial synchronization</strong></p>
<p><strong>Best case.</strong> Code that runs adequately on fast developer machines, hiding timing glitches and flash-of-old-content bugs.</p>
<p><strong>Worst case.</strong> Cascading effect renders, infinite loops, stale closures in click handlers, and unmounted state warnings.</p>

New
</h2>
<p><strong>Right approach: embrace pure components, derived values, and native web standards</strong></p>
<p><strong>Best case.</strong> Predictable rendering: what you see is a pure function of props and state. Changes propagate instantly without race conditions.</p>
<p><strong>Worst case.</strong> Learning to let go of old mental habits from early React versions. The resulting simplicity is immediate.</p>
<p>After: plain variable assignment during render.</p>
