What it is
</h2>
<p>I read a call above a declaration and assumed JavaScript had moved the whole line to the top of the file. It had not. Hoisting is a story about how bindings are created during the setup of a scope. It is not a rearrangement of the source I see.</p>
<p><code>var name</code> is created for the whole function and initialized to <code>undefined</code>, so a read before the line yields <code>undefined</code> rather than a reference error. <code>let</code> and <code>const</code> are created for the block too, but they stay uninitialized until their line runs. A read in that temporal dead zone throws <code>ReferenceError</code>. A function declaration is initialized with the function, so a call earlier in the same scope can succeed.</p>
<p>Those are three different behaviors. Saying “it is hoisted” hides which one I mean. <code>console.log(name)</code> before <code>var name = &quot;Sanjay&quot;</code> logs <code>undefined</code>. The same read before <code>let count = 1</code> throws.</p>
<p>I declare before I use. The runtime rules still matter when I debug someone else’s file, including my own from last month. I separate what is in scope, what is initialized, and what is actually callable.</p>
</section>

Old

<p><strong>Best case.</strong> A function declaration I call from the bottom of a short file, and I know declarations are initialized, not merely created.</p>
<p><strong>Worst case.</strong> I log a <code>var</code> and think the value was never assigned, when it was assigned later. Or I touch a <code>let</code> in the dead zone and the throw looks unrelated to order.</p>

New
</h2>
<p><strong>Right approach: initialize a binding before any read, and name the rule when you are debugging</strong></p>
<p><strong>Best case.</strong> A glance down the function shows the value before it is used. There is no dead zone and no <code>undefined</code> pretending to be “not hoisted.”</p>
<p><strong>Worst case.</strong> A style rule so rigid that I cannot explain a legacy <code>var</code> bug. I still want the three-way distinction in my head when I read old code.</p>
<p>After: both names are initialized, then logged.</p>

<section class="section" id="when">
<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M3.6 2.4v9.2"/><path d="M3.6 6.4h4.35"/><path d="M7.95 6.4 11.15 3.5"/><path d="M7.95 6.4 11.15 9.3"/></svg>
When to use which
</h2>
<p>Write bindings before their first read. When debugging, ask which keyword created the binding. <code>var</code> can be <code>undefined</code>. <code>let</code> and <code>const</code> can throw. A function declaration can be called earlier in the same scope. None of these is a reason to scramble the file.</p>
<div class="when">
<div class="when-row"><span>New code</span><span class="when-choice">declare, then use</span></div>
<div class="when-row"><span>A var read that prints undefined</span><span class="when-choice">it may be uninitialized, not missing</span></div>
<div class="when-row"><span>A let or const read that throws</span><span class="when-choice">temporal dead zone</span></div>
<div class="when-row"><span>A function called above its declaration</span><span class="when-choice">function declarations are initialized</span></div>
</div>
</section>
