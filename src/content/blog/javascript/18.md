<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><circle cx="7" cy="7" r="4.75"/><path d="M7 6.35v3.45"/><path d="M7 4.4v.02" stroke-width="1.8"/></svg>
What it is
</h2>
<p>A config field set to <code>null</code> skipped my default and later broke a string operation. I had written <code>const { theme = &quot;light&quot; } = config</code>. The default applies when the property is missing or present with the value <code>undefined</code>. <code>null</code> is a present value. The variable became <code>null</code>, and a later <code>theme.toUpperCase()</code> threw.</p>
<p>The same rule holds for parameters: <code>function paint(theme = &quot;light&quot;)</code> replaces <code>undefined</code> only. A caller who passes <code>null</code> gets <code>null</code>. Defaults are not a general “empty” cleaner.</p>
<p>I decide which absences share a fallback. If only <code>undefined</code> means “not provided,” the destructuring default is exact. If <code>null</code> means the same thing in this config, I take the property and then apply <code>??</code>. <code>&quot;&quot;</code> and <code>0</code> stay intact under <code>??</code>, which matters when an empty string is a real theme name or a real count.</p>
<p>Defaults are policy. I write the policy in the expression instead of expecting <code>=</code> to mean “anything empty.”</p>
</section>

Old
</h2>
<p><strong>Wrong approach: a destructuring default as a cleanup for every empty value</strong></p>
<p><strong>Best case.</strong> The only missing signal you use is <code>undefined</code> or a missing key. <code>null</code> never appears. The default matches the data.</p>
<p><strong>Worst case.</strong> <code>null</code> skips the default and crashes in a string method, or <code>false</code> is replaced because you used <code>||</code> and a deliberate off switch disappears.</p>
<p>Before: <code>= &quot;light&quot;</code> looks like it covers a null theme. It does not.</p>

<h2>

New
</h2>
<p><strong>Right approach: apply ?? when null and undefined share a fallback</strong></p>
<p><strong>Best case.</strong> <code>themeOf({ theme: null })</code> and <code>themeOf({})</code> return <code>&quot;light&quot;</code>. <code>themeOf({ theme: &quot;&quot; })</code> returns <code>&quot;&quot;</code> if I want blank to stay blank, or I add a separate check if blank is also invalid.</p>
<p><strong>Worst case.</strong> <code>??</code> keeping <code>NaN</code> or an unexpected number. The operator only covers nullish values. I still validate the union of themes I accept.</p>
<p>After: null takes the fallback on purpose, in a separate expression from the property read.</p>

<section class="section" id="when">
<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M3.6 2.4v9.2"/><path d="M3.6 6.4h4.35"/><path d="M7.95 6.4 11.15 3.5"/><path d="M7.95 6.4 11.15 9.3"/></svg>
When to use which
</h2>
<p>Use a destructuring or parameter default for <code>undefined</code>. Use <code>??</code> when <code>null</code> should join that fallback. Use an explicit check when empty string, zero, or false needs its own decision. Do not stack <code>||</code> on top unless every falsy value is truly invalid.</p>
<div class="when">
<div class="when-row"><span>Missing property or undefined</span><span class="when-choice">default in the pattern</span></div>
<div class="when-row"><span>null means missing too</span><span class="when-choice">??</span></div>
<div class="when-row"><span>Empty string is invalid</span><span class="when-choice">check after the fallback</span></div>
<div class="when-row"><span>false is a real choice</span><span class="when-choice">do not use ||</span></div>
</div>
</section>
