<h2>

What it is
</h2>
<p>Typing in a search box fired a request for every character. Slower responses arrived out of order, and an earlier query painted over a later one. The input felt busy because I had tied network work to the raw input event.</p>
<p>Debouncing waits until the calls stop for a gap, then runs once with the latest value. Each new input clears the previous timer. A 300ms pause is a common starting point for search. It is not a law. A control that must react immediately, such as a button that submits, should not be debounced.</p>
<p>The timer limits how often I start work. It does not cancel work already running. I copy the input value before the wait, and when the timer fires I pass an <code>AbortController</code> so a newer query can abort the older fetch. Debounce is frequency. Abort is correctness.</p>
<p>I use the same pattern for resize and for validation that is expensive to run per key. I do not debounce the text the user sees. The input updates immediately. Only the expensive follow-up waits.</p>
</section>

New
</h2>
<p><strong>Right approach: reset a timer, then run once with the latest value, and cancel stale async work</strong></p>
<p><strong>Best case.</strong> Typing stays instant because the input is not waiting. One search runs after a quiet 300ms, and the previous fetch is aborted.</p>
<p><strong>Worst case.</strong> A debounce so long the UI feels stuck, or a debounce on the only feedback the user has. I shorten the wait or update a local hint immediately and debounce only the request.</p>
<p>After: each keystroke replaces the timer. The network call sees the value captured for that pause.</p>

<section class="section" id="when">
<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M3.6 2.4v9.2"/><path d="M3.6 6.4h4.35"/><path d="M7.95 6.4 11.15 3.5"/><path d="M7.95 6.4 11.15 9.3"/></svg>
When to use which
</h2>
<p>Debounce work that should wait for a pause: search requests, expensive validation, resize layout. Do not debounce direct feedback. Pair a debounced request with abort or a generation token so an older response cannot win. Clear the timer on teardown so a removed input does not fire into a gone page.</p>
<div class="when">
<div class="when-row"><span>Search or remote validation</span><span class="when-choice">debounce, then abort stale calls</span></div>
<div class="when-row"><span>Filtering a tiny local list</span><span class="when-choice">run it, or debounce if you measured jank</span></div>
<div class="when-row"><span>A submit button</span><span class="when-choice">do not debounce</span></div>
<div class="when-row"><span>The input’s own text</span><span class="when-choice">update immediately</span></div>
</div>
</section>
