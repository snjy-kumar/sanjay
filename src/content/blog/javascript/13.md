<h2>

What it is
</h2>
<p>A failed request became an unhandled rejection because I assumed <code>await</code> turned errors into a return value. It does not. <code>await</code> pauses until the promise settles. Fulfillment becomes the value. Rejection throws at that line. If nobody catches it, the rejection surfaces as an unhandled promise error and my spinner may never stop.</p>
<p><code>async</code> functions always return a promise. A <code>throw</code> inside one rejects that promise. <code>try/catch</code> around <code>await</code> catches that rejection in the same way it catches a synchronous throw. <code>finally</code> runs on both paths, which is where I hide a spinner.</p>
<p>HTTP is a second failure mode. <code>fetch</code> rejects on network failure, not on a 404 or a 500. <code>response.ok</code> is the check for status. I throw my own error for a bad status so the <code>catch</code> handles both kinds of failure.</p>
<p><code>await</code> improves the reading order. It does not add a failure policy. Every async boundary I ship has a catch I can show in the UI and a finally that clears the in-between state.</p>
</section>

Old
</h2>
<p><strong>Wrong approach: await a fetch and assume failure comes back as data</strong></p>
<p><strong>Best case.</strong> The request succeeds and the caller remembers to catch. Nothing in the function itself shows that contract.</p>
<p><strong>Worst case.</strong> A 500 still calls <code>response.json()</code> on an error page, or a network rejection is unhandled and the spinner stays up.</p>
<p>Before: there is no try, no status check, and no cleanup.</p>

New
</h2>
<p><strong>Right approach: try around await, check response.ok, and clear UI state in finally</strong></p>
<p><strong>Best case.</strong> Network errors and bad statuses reach <code>showError</code>. The spinner hides on every exit. The caller receives <code>null</code> instead of an unhandled rejection.</p>
<p><strong>Worst case.</strong> A catch that swallows the error and returns an empty list, so failure looks like “no notes.” I return a distinct failure or rethrow after showing it.</p>
<p>After: both failure kinds are caught, and cleanup is not duplicated.</p>

<section class="section" id="when">
<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M3.6 2.4v9.2"/><path d="M3.6 6.4h4.35"/><path d="M7.95 6.4 11.15 3.5"/><path d="M7.95 6.4 11.15 9.3"/></svg>
When to use which
</h2>
<p>Put <code>try/catch</code> at the boundary that knows how to tell a person. Check <code>response.ok</code> before reading a success body. Use <code>finally</code> for spinners and locks. Let the error propagate only when a caller above has the UI for it.</p>
<div class="when">
<div class="when-row"><span>A network failure</span><span class="when-choice">fetch rejects, catch it</span></div>
<div class="when-row"><span>An HTTP error status</span><span class="when-choice">response.ok, then throw</span></div>
<div class="when-row"><span>A spinner or a lock</span><span class="when-choice">finally</span></div>
<div class="when-row"><span>A caller that already catches</span><span class="when-choice">rethrow after local cleanup</span></div>
</div>
</section>
