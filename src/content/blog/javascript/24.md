What it is
</h2>
<p>A resize path in a personal project read <code>offsetHeight</code> after every style write. The page stuttered. Some layout reads flush pending style changes so the number is up to date. If I write, read, write, read inside a loop, the browser recalculates layout on each read. That pattern is layout thrashing. The cost is the order, not only the number of elements.</p>
<p><code>offsetHeight</code>, <code>offsetWidth</code>, and <code>getBoundingClientRect</code> are the reads I watch. Setting <code>style.width</code> or a class is a write. Reads that happen together can share one flush. Writes that happen after the reads can share the next frame. Interleaving them throws the batching away.</p>
<p>I measure first, into an array, and then write. If the work is visual and repeats, I schedule it with <code>requestAnimationFrame</code> so it lines up with rendering, and I keep the handler from doing anything else heavy. I do not read layout from a scroll listener on every event unless I have no other API for the fact I need.</p>
<p>When a measurement and a write depend on each other per item, I still separate the passes if I can. If I cannot, I know I am paying for a forced layout and I keep the list short.</p>
</section>

Old
</h2>
<p><strong>Wrong approach: read layout in the same loop that writes style</strong></p>
<p><strong>Best case.</strong> One element, one write, one read, on a rare event. The forced layout is real and too small to feel.</p>
<p><strong>Worst case.</strong> A list of hundreds, on resize or scroll, stutters because each read flushes the write from the previous item.</p>
<p>Before: write and read alternate inside the loop.</p>

New
</h2>
<p><strong>Right approach: collect measurements, then apply writes</strong></p>
<p><strong>Best case.</strong> The read loop does not invalidate layout for the next read. The write loop does not ask for geometry. A frame can contain one flush instead of one per item.</p>
<p><strong>Worst case.</strong> Batching reads that include a write I hid in a helper. The helper still forces layout. I keep measurement functions free of style changes.</p>
<p>After: heights are captured, then styles are set.</p>

<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M3.6 2.4v9.2"/><path d="M3.6 6.4h4.35"/><path d="M7.95 6.4 11.15 3.5"/><path d="M7.95 6.4 11.15 9.3"/></svg>
When to use which
</h2>
<p>Group layout reads, then group DOM writes. Use <code>requestAnimationFrame</code> for repeated visual work. Prefer a transform or a class to a per-item readback when you can. If a read must see a write, do the write, then read once, not once per sibling.</p>
<div class="when">
<div class="when-row"><span>You need sizes before changing them</span><span class="when-choice">read pass, then write pass</span></div>
<div class="when-row"><span>Repeated visual updates</span><span class="when-choice">requestAnimationFrame</span></div>
<div class="when-row"><span>One read after one intentional write</span><span class="when-choice">accept a single flush</span></div>
<div class="when-row"><span>Scroll math you can replace</span><span class="when-choice">an observer or a CSS approach</span></div>
</div>
</section>
