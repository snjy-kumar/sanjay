What it is
</h2>
<p>I expected a zero-millisecond timer to run before a promise callback. The printed order was the opposite. “Async” is not one queue, and a delay of <code>0</code> is a minimum wait until a timer task, not a promise to run immediately.</p>
<p>The current synchronous turn finishes first, including the lines after I scheduled the callback. Then the engine drains the microtask queue: promise reactions and <code>queueMicrotask</code>. Then it may run one timer or other macrotask, such as the <code>setTimeout</code> I scheduled. A long synchronous loop blocks both queues. Nothing in them runs until that loop returns.</p>
<p>So <code>console.log(&quot;A&quot;)</code>, schedule a microtask, schedule a timeout, <code>console.log(&quot;B&quot;)</code> prints <code>A</code>, then <code>B</code>, then the microtask, then the timer. I write that order down when timing matters instead of reasoning from the word async.</p>
<p>Promise callbacks are microtasks even though <code>fetch</code> itself waits on the network. Once the response arrives, the <code>.then</code> or the code after <code>await</code> is queued as a microtask, not as a timer.</p>
</section>

Old

<p><strong>Wrong approach: treat setTimeout(fn, 0) as run this next, before any promise</strong></p>
<p><strong>Best case.</strong> There is no microtask queued, and the call stack is about to empty. The timer runs soon. “Next line” was still the wrong description.</p>
<p><strong>Worst case.</strong> I hide a promise chain behind a 0ms timer to “wait for the DOM,” and a microtask from another library runs in between and sees a half-updated page. Or a long loop starves the timer and the UI freezes anyway.</p>
<p>Before: the timeout is assumed to beat the promise because it was scheduled first.</p>

New
</h2>
<p><strong>Right approach: finish the synchronous turn, drain microtasks, then take a timer task</strong></p>
<p><strong>Best case.</strong> I can predict A, B, M, T from the queues instead of from the order of the schedule calls. A bug in ordering becomes a diagram, not a mystery.</p>
<p><strong>Worst case.</strong> Stuffing <code>queueMicrotask</code> recursively. Microtasks drain completely before the next timer or paint, so an unbounded microtask chain stalls the page the way a long loop does.</p>
<p>After: the log names the queue. Sync work is the two console lines. The callbacks are scheduled, not run, by those lines.</p>

<section class="section" id="when">
<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M3.6 2.4v9.2"/><path d="M3.6 6.4h4.35"/><path d="M7.95 6.4 11.15 3.5"/><path d="M7.95 6.4 11.15 9.3"/></svg>
When to use which
</h2>
<p>When order matters, name the queue. Synchronous code runs now. Promise continuations and <code>queueMicrotask</code> run before timers. <code>setTimeout(fn, 0)</code> waits until after the microtask checkpoint. Do not use a timer to paper over a microtask ordering bug you have not drawn yet.</p>
<div class="when">
<div class="when-row"><span>Work that must finish before any callback</span><span class="when-choice">write it synchronously</span></div>
<div class="when-row"><span>After the current turn, before timers</span><span class="when-choice">queueMicrotask or a promise</span></div>
<div class="when-row"><span>After a delay, or after paint-sized work</span><span class="when-choice">setTimeout or requestAnimationFrame</span></div>
<div class="when-row"><span>A long loop</span><span class="when-choice">it blocks every queue</span></div>
</div>
</section>
