What it is
</h2>
<p>A price total in a personal project became <code>&quot;105&quot;</code> instead of <code>15</code>. One operand came from an input. DOM input values are strings. <code>&quot;10&quot; + 5</code> concatenates, because <code>+</code> means addition only when neither side prefers string conversion. The bug then spread into sorting, where <code>&quot;105&quot;</code> and <code>15</code> are not in numeric order.</p>
<p>Other operators coerce differently. <code>&quot;10&quot; * 5</code> is <code>50</code>, because multiplication converts to numbers. That inconsistency is why a total can look fine in one line and wrong in the next. I do not rely on it.</p>
<p>I normalize once, at the edge, with <code>Number(input.value)</code>. Then I ask <code>Number.isFinite</code>. <code>Number(&quot;&quot;)</code> is <code>0</code>, <code>Number(&quot;10px&quot;)</code> is <code>NaN</code>, and <code>Number(&quot; &quot;)</code> is <code>0</code>. <code>isFinite</code> catches <code>NaN</code> and also rejects <code>Infinity</code>. The rest of the calculation stays numeric, boring, and reviewable.</p>
<p>I do not sprinkle <code>Number()</code> through the middle of the file. One conversion, one validation, then math.</p>
</section>

New
</h2>
<p><strong>Right approach: convert once with Number and refuse non-finite results</strong></p>
<p><strong>Best case.</strong> <code>totalFromInput(&quot;10&quot;)</code> is 15. A blank string is rejected before conversion, and <code>totalFromInput(&quot;n/a&quot;)</code> fails <code>Number.isFinite</code> instead of adding <code>NaN</code>.</p>
<p><strong>Worst case.</strong> Trusting <code>Number.isFinite</code> alone. <code>Number(&quot;&quot;)</code> is <code>0</code>, which is finite, so a blank field becomes a total of 5. <code>parseInt(&quot;10px&quot;, 10)</code> would quietly keep 10; <code>Number(&quot;10px&quot;)</code> is <code>NaN</code>, which this check rejects.</p>
<p>After: addition only sees a finite number. Empty input is rejected before <code>Number</code>, because <code>Number(&quot;&quot;)</code> is <code>0</code> and would otherwise pass <code>isFinite</code>.</p>

<h2>

When to use which
</h2>
<p>Convert at the boundary where strings enter: inputs, query params, JSON fields that should have been numbers. Use <code>Number.isFinite</code> afterward. Prefer explicit <code>Number</code> over relying on <code>*</code> or <code>/</code> to coerce. Do not use <code>parseInt</code> unless you want truncation and have set a radix.</p>
<div class="when">
<div class="when-row"><span>Both values are already numbers</span><span class="when-choice">+ is addition</span></div>
<div class="when-row"><span>A DOM input or query string</span><span class="when-choice">Number at the edge</span></div>
<div class="when-row"><span>Empty string should not become 0</span><span class="when-choice">reject trim before Number</span></div>
<div class="when-row"><span>An integer prefix like 10px</span><span class="when-choice">do not use parseInt to paper over it</span></div>
</div>
</section>
