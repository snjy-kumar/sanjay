What it is
</h2>
<p>I debugged a missing method by staring at a class declaration. The behavior did not live on the instance. JavaScript objects delegate property lookup along a prototype chain. <code>class</code> writes the constructor and puts methods on <code>Constructor.prototype</code>. It does not replace that model.</p>
<p><code>new Job()</code> creates an object whose internal prototype is <code>Job.prototype</code>. <code>job.run</code> is found by walking that link. <code>Object.hasOwn(job, &quot;run&quot;)</code> is false. <code>Object.hasOwn(Job.prototype, &quot;run&quot;)</code> is true. Every instance shares one function, which is why instances stay smaller and why mutating the prototype is visible to all of them.</p>
<p>Own properties are the fields assigned in the constructor or with <code>job.id = ...</code>. Methods and inherited defaults are not own properties. <code>hasOwn</code> versus <code>in</code> is the difference: <code>in</code> walks the chain.</p>
<p>I use <code>class</code> when I want a readable constructor and a stable set of methods. I still picture the prototype chain when identity, <code>instanceof</code>, or a “missing” method surprises me. A function constructor with <code>Job.prototype.run = ...</code> is the same mechanism written out.</p>

<p><strong>Worst case.</strong> You clone with <code>Object.assign({}, job)</code> and the methods disappear. Or you compare <code>job.run === other.run</code> and misunderstand why it is true: there is one shared function.</p>

New
</h2>
<p><strong>Right approach: treat methods as prototype properties, whether you wrote class or an assignment</strong></p>
<p><strong>Best case.</strong> <code>job.run()</code> delegates. Instances do not each carry a copy of the function. <code>instanceof Job</code> follows the same chain.</p>
<p><strong>Worst case.</strong> Editing <code>Job.prototype</code> at runtime as a patch. Every instance sees the edit, including ones I forgot about. I change the class instead of patching the prototype from a call site.</p>
<p>After: the lookup path is the thing I test, not a copied own property.</p>

<section class="section" id="when">
<h2>
<svg class="ico" width="14" height="14" viewBox="0 0 14 14" aria-hidden="true" fill="none" stroke="#111" stroke-width="1.25" stroke-linecap="round" stroke-linejoin="round"><path d="M3.6 2.4v9.2"/><path d="M3.6 6.4h4.35"/><path d="M7.95 6.4 11.15 3.5"/><path d="M7.95 6.4 11.15 9.3"/></svg>
When to use which
</h2>
<p>Use <code>class</code> for most new constructors. Remember methods live on the prototype. Put per-instance data on <code>this</code> inside the constructor. Use <code>Object.hasOwn</code> when you mean an own field, and <code>instanceof</code> or <code>Object.getPrototypeOf</code> when you are debugging delegation.</p>
<div class="when">
<div class="when-row"><span>A constructor with shared methods</span><span class="when-choice">class or prototype assignment</span></div>
<div class="when-row"><span>Data that differs per instance</span><span class="when-choice">own properties</span></div>
<div class="when-row"><span>Did this object define the field?</span><span class="when-choice">Object.hasOwn</span></div>
<div class="when-row"><span>Does it inherit the field?</span><span class="when-choice">walk the prototype, or use in</span></div>
</div>
</section>
