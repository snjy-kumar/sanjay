Automated accessibility checkers are useful and limited. They find a
missing `alt`, a contrast failure, a label that points nowhere. They cannot
tell whether the tab order makes sense, whether a dialog returns focus to
where it came from, or whether "Read more" means anything when a screen
reader lists twelve of them. Those need a person to use the screen the way
some people have to. This note is a pass I can run on any screen in about
twenty minutes: keyboard first, then a screen reader, then contrast, then
the composite widgets where most failures hide.

## Before you start

After this note you will be able to:

- run a keyboard pass and find focus that is lost, hidden, trapped or out
  of order;
- explain an element's accessible name, role and state, and predict the
  name from markup;
- compute a contrast ratio and know which threshold applies;
- build a toolbar or tab list with roving tabindex, and manage focus in a
  dialog;
- write down a pass as a checklist that someone else can repeat.

What you should already know: the semantic elements and landmarks from
[note one](/sanjay/posts/ui/01/) and the field wiring from
[note five](/sanjay/posts/ui/05/). This note uses both and adds the
interaction layer.

Reading time: about 30 minutes, longer if you run the pass on a real screen
alongside, which is the point.

## The keyboard pass

### In one sentence

Put the mouse away and use the screen with Tab, Shift+Tab, Enter, Space,
the arrow keys and Escape, watching where focus is at every moment.

### The idea

Many people use a keyboard or something that behaves like one: people with
motor impairments, switch users, screen-reader users, and power users who
prefer it. If something cannot be done with a keyboard, it cannot be done
by them. The keyboard pass is the cheapest accessibility test there is, and
it needs no tools.

Four things to watch for:

1. **Reachability.** Every interactive thing can be reached with Tab.
   Custom controls built from `div`s often cannot.
2. **Visibility.** Focus is always visible. A stylesheet that removes the
   outline (`outline: none`) with no replacement leaves keyboard users
   guessing where they are.
3. **Order.** Focus moves in an order that matches the visual and reading
   order. CSS that reorders content visually (flex `order`, grid placement)
   does not change the tab order, which follows the DOM.
4. **No traps.** Focus never gets stuck. The only acceptable trap is a
   modal dialog, which holds focus deliberately and releases it on close.

Also check the keys each control should respond to: Enter on links and
buttons, Space on buttons and checkboxes, arrows inside radio groups,
menus and tabs, Escape to close anything that opened.

### Worked example

The simple example is a skip link. On a page with a long navigation, a
keyboard user has to Tab through every nav link to reach the content on
every page. A skip link is the first focusable element, hidden until
focused:

```html
<a class="skip" href="#main">Skip to content</a>
<!-- header and nav -->
<main id="main" tabindex="-1">…</main>
```

```css
.skip { position: absolute; left: -9999px; }
.skip:focus { left: 1rem; top: 1rem; }
```

The first Tab shows it; Enter jumps to `main`. The `tabindex="-1"` makes
`main` focusable by script and by the link, without adding it to the tab
order, which helps some browsers move focus there reliably.

The realistic example is a card whose whole surface is clickable, built as
a `div` with an `onclick`. With a keyboard, it cannot be reached. The fix
that keeps the large target is a real link on the card's title, stretched
over the card with a pseudo-element, so the card has one focusable element
with a sensible name, and the whole card is still clickable.

### Common mistake

The common mistake is `tabindex` with a positive value, such as
`tabindex="3"`, to "fix" the order. Positive values pull elements ahead of
everything else in the page, and the order becomes a manual list that
breaks with every change. Fix the DOM order instead. Use only `0` (in the
normal order) and `-1` (focusable by script, not by Tab).

The other common one is removing focus outlines because they look bad on
mouse click. The `:focus-visible` selector shows the outline for keyboard
focus and usually not for mouse clicks, which solves the original
complaint without hurting anyone.

### In real systems

Teams that take this seriously put a keyboard pass in the definition of
done for any new screen, and add end-to-end tests that drive key presses,
such as Tab to a button and press Enter. Browser testing tools can assert
which element has focus after each key, which catches regressions in
dialogs and menus that would otherwise only be found by a user.

## Names, roles and states

### In one sentence

A screen reader announces each control by its **name**, **role** and
**state**, and the name is computed from the markup in a fixed order of
precedence, so I can predict what will be heard before I hear it.

### The idea

Note one introduced the accessibility tree: the browser's second tree, in
which each meaningful node has a role, a name and states. A screen reader
reads that tree. When it focuses a control, it says something like "Close,
button" or "Dark mode, switch, off". If the name is empty, it says just
"button", and the person has to guess.

The **accessible name** is computed in an order of precedence, defined in a
W3C specification. Much simplified:

1. `aria-labelledby`: the text of the elements whose ids it lists.
2. `aria-label`: the string in the attribute.
3. The native label: a `label` for an input, `alt` for an image, the
   `legend` for a fieldset, the caption for a table.
4. For controls whose name comes from content, such as buttons and links,
   their text content, including the `alt` of images inside.
5. Last resorts: the `title` attribute, and for inputs the `placeholder`.

The earlier sources win. A button with an `aria-label` and visible text is
named by the `aria-label`, which is a trap: if the two disagree, voice
control users who say the visible text cannot activate it. Keep the visible
text inside the name.

**Roles** come from elements (`button`, `link`, `checkbox`) or, for custom
controls, from the `role` attribute. **States** come from native properties
(`disabled`, `checked`) or from ARIA attributes (`aria-expanded`,
`aria-pressed`, `aria-selected`, `aria-current`), which must be kept in
sync by the code.

### Worked example

A deliberately simplified name computation, enough to predict the common
cases:

```js
// a11y.mjs
export function accessibleName(el, doc) {
  if (el.attrs['aria-labelledby']) {
    return el.attrs['aria-labelledby'].split(' ').map((id) => text(doc[id])).join(' ').trim();
  }
  if (el.attrs['aria-label']?.trim()) return el.attrs['aria-label'].trim();
  if (el.tag === 'input' && el.labelledByFor) return text(el.labelledByFor);
  if (el.tag === 'img') return el.attrs.alt ?? '';
  if (['button', 'a'].includes(el.tag)) return text(el) || (el.attrs.title ?? '');
  return el.attrs.title ?? el.attrs.placeholder ?? ''; // last resorts
}
```

The `text` helper joins text children, uses `alt` for images, and skips
anything marked `aria-hidden="true"`. Run on seven common cases:

```text
icon button, svg only        -> ""
icon button with aria-label  -> "Close"
button with img alt          -> "Search"
link "read more"             -> "Read more"
dialog labelled by title     -> "Delete note"
input with label             -> "Email address"
input, placeholder only      -> "Email"
```

The first line is the most common real failure: an icon button whose SVG
is hidden from assistive technology and which has no other name. The link
line is a quieter one: "Read more" is a name, but a screen-reader user who
pulls up a list of links hears "Read more" twelve times. The last line
shows that a placeholder can supply a name as a last resort, but it is
still a poor label for the reasons in note five.

To run this pass, use the screen reader that comes with the system:
VoiceOver on macOS and iOS, Narrator on Windows, TalkBack on Android, or
the free NVDA on Windows. Learn five commands: start and stop, read next,
next heading, next link or control, and activate. That is enough to find
most problems.

### Common mistake

The common mistake is adding ARIA to fix something native HTML already
does. `<div role="button" tabindex="0">` needs key handlers for Enter and
Space, a disabled state, and focus styles, all by hand. A `button` has all
of them. The first rule of ARIA, as its own authors put it, is roughly:
if a native element does the job, use it.

The second mistake is ARIA states that are set once and never updated: a
menu button with `aria-expanded="false"` hard-coded, even when the menu is
open. A wrong state is worse than no state, because it is believed.

### In real systems

Browser dev tools have an accessibility panel that shows the computed name,
role and states for the selected element, and a full accessibility tree
view. That turns "what will be announced" from a guess into a lookup.
Automated checkers such as axe, run in end-to-end tests, catch missing
names and invalid ARIA on every build, which leaves the human pass for the
problems only a human can judge.

## Contrast and colour

### In one sentence

Text needs enough contrast with its background to be read by people with
low vision and in bad light, and the WCAG contrast ratio gives a number to
check against fixed thresholds.

### The idea

WCAG defines contrast as a ratio of the **relative luminance** of the
lighter colour to the darker one, each plus 0.05, so the ratio runs from
1:1 (identical) to 21:1 (black on white). Relative luminance converts each
sRGB channel to a linear value and weights green most, red less and blue
least, roughly matching how bright each looks to the eye.

The thresholds at level AA:

- **4.5:1** for normal text.
- **3:1** for large text, which WCAG defines as at least 18 point, or 14
  point bold (around 24 and 18.7 CSS pixels).
- **3:1** for the visible parts of controls and for focus indicators
  against adjacent colours, so a light grey input border on white may fail
  even though the text inside passes.

Level AAA raises the text thresholds to 7:1 and 4.5:1. Contrast is also
one of the two rules about colour; the other is that **colour is never the
only signal**, which is why errors in note five have text, not just a red
border.

### Worked example

```js
// contrast.mjs
const channel = (c) => { c /= 255; return c <= 0.04045 ? c / 12.92 : ((c + 0.055) / 1.055) ** 2.4; };
const luminance = (hex) => {
  const [r, g, b] = hex.match(/\w\w/g).map((h) => channel(parseInt(h, 16)));
  return 0.2126 * r + 0.7152 * g + 0.0722 * b;
};
export const ratio = (a, b) => {
  const [hi, lo] = [luminance(a), luminance(b)].sort((x, y) => y - x);
  return (hi + 0.05) / (lo + 0.05);
};
```

Five pairs, including this site's ink and muted greys on its paper colour:

```text
#111111 on #f7f7f5: 17.60:1  normal text AA pass, large text AA pass
#6b6b6b on #f7f7f5: 4.97:1  normal text AA pass, large text AA pass
#999999 on #ffffff: 2.85:1  normal text AA fail, large text AA fail
#767676 on #ffffff: 4.54:1  normal text AA pass, large text AA pass
#777777 on #ffffff: 4.48:1  normal text AA fail, large text AA pass
```

The last two lines are the instructive pair. `#767676` on white just
passes; `#777777`, one step lighter on each channel, just fails. Nobody can
see that difference, which is why contrast is measured, not judged by eye.
The popular light grey `#999999` fails even for large text.

### Common mistake

The common mistake is checking text contrast and forgetting everything
else: placeholder text, disabled-looking but enabled controls, input
borders, icons that carry meaning, and the focus ring. A focus ring that is
a pale blue on white can fail the 3:1 rule, which makes the keyboard pass
fail for low-vision users even when the outline technically exists.

Another is checking against the wrong background: text on a photo or a
gradient has a different contrast at every point. Put a solid or
semi-opaque layer behind it.

### In real systems

In a token system, contrast is checked once per pair of semantic tokens,
not once per screen: `color.muted` on `color.surface`, `color.text` on
`color.surface-raised`, and so on for each theme. A small script like the
one above, run over every text-and-background token pair in every theme,
catches a failing dark theme before any screen is built.

### Check yourself

</details>

<details>
<summary>2. Why check contrast at the token level?</summary>

## Composite widgets and managed focus

### In one sentence

A group of related controls, such as a toolbar, tab list or menu, should be
one Tab stop with arrow keys inside it, and anything that opens on top of
the page should move focus in, keep it there, and give it back on close.

### The idea

If every button in a twelve-button toolbar is a Tab stop, a keyboard user
presses Tab twelve times to get past it. The ARIA Authoring Practices
describe the expected pattern: the group is one stop, and arrow keys move
within it. The standard way to build that is **roving tabindex**:

- exactly one item in the group has `tabindex="0"`, the rest have `-1`;
- arrow keys move focus to the next or previous item, and move the `0`
  with it;
- Home and End jump to the first and last items;
- Tab leaves the group, and coming back lands on the item that was last
  active.

Dialogs need **managed focus**. When a modal opens, focus moves into it,
usually to the first control or the heading. While it is open, Tab cycles
inside it and the rest of the page is inert. Escape closes it. On close,
focus returns to the control that opened it. Miss the last step and the
keyboard user is dropped at the top of the page.

### Worked example

Roving tabindex for a four-button toolbar, printing the focused item and
every item's tabindex after each key:

```js
// roving.mjs
function toolbar(labels) {
  let active = 0;
  const render = () => labels.map((l, i) => `${l}[${i === active ? 0 : -1}]`).join(' ');
  const key = (k) => {
    if (k === 'ArrowRight') active = (active + 1) % labels.length;
    if (k === 'ArrowLeft') active = (active - 1 + labels.length) % labels.length;
    if (k === 'Home') active = 0;
    if (k === 'End') active = labels.length - 1;
    return `${k.padEnd(10)} focus ${labels[active].padEnd(6)} tabindex: ${render()}`;
  };
  return { render, key };
}
```

Output:

```text
start      focus Bold   tabindex: Bold[0] Italic[-1] Link[-1] Code[-1]
ArrowRight focus Italic tabindex: Bold[-1] Italic[0] Link[-1] Code[-1]
ArrowRight focus Link   tabindex: Bold[-1] Italic[-1] Link[0] Code[-1]
End        focus Code   tabindex: Bold[-1] Italic[-1] Link[-1] Code[0]
ArrowRight focus Bold   tabindex: Bold[0] Italic[-1] Link[-1] Code[-1]
ArrowLeft  focus Code   tabindex: Bold[-1] Italic[-1] Link[-1] Code[0]
Home       focus Bold   tabindex: Bold[0] Italic[-1] Link[-1] Code[-1]
```

At every step exactly one item has `0`. The right arrow wraps from Code to
Bold; whether a toolbar wraps is a design choice, and the APG allows
either. In a browser, each step also calls `.focus()` on the new item.

For dialogs, the modern native answer is the `dialog` element opened with
`showModal()`. It moves focus inside, makes the rest of the page inert,
closes on Escape, and has a backdrop. Returning focus on close is still
worth doing explicitly in many setups: store the opener, and call
`opener.focus()` in the close handler.

### Common mistake

The common mistake is building a menu or tab list as a row of independent
buttons with no arrow-key support, and then adding ARIA roles like
`role="menu"` or `role="tablist"`. The roles promise screen-reader users
the arrow-key behaviour; without it, the widget is worse than plain
buttons. Either implement the pattern fully, or use plain buttons and
links with no composite role.

### In real systems

Most teams do not hand-build these widgets more than once. Headless
component libraries implement the APG patterns, with roving tabindex,
typeahead, focus return and the right ARIA, and design systems style them.
Hand-building one, as in this note, is how to know whether the library is
doing it right, and how to test it.

## From beginner to strategy

<Levels label="A keyboard and screen-reader pass">
<Level name="Beginner" depth={3}>

At the beginner level, run the keyboard pass on every screen you build.
Tab through it, check that every control is reachable, that focus is
always visible, and that Escape closes what opened. Use native elements so
most of this works without effort.

A worked example: a modal built from `div`s cannot be closed with Escape
and leaves focus behind it. Replacing it with `dialog` and `showModal()`
fixes three issues in one change.

The mistake at this level is `outline: none` in a reset stylesheet. Keep
the outline, or replace it with a visible `:focus-visible` style.

</Level>
<Level name="Intermediate" depth={3}>

At the intermediate level, add the screen-reader pass and the contrast
check. Learn five commands of one screen reader. Check every control's
name, role and state in the dev tools accessibility panel, and every token
pair's contrast with a script.

A worked example: a theme toggle built as a button with only an icon. The
pass reveals "button", with no name and no state. Adding
`aria-label="Dark mode"` and `aria-pressed` gives "Dark mode, toggle
button, pressed".

The mistake at this level is testing with the screen reader as if it were
a visual check, glancing at the screen. Turn the screen off or look away,
and listen.

</Level>
<Level name="Advanced" depth={3}>

At the advanced level, build composite widgets to the APG patterns: roving
tabindex, typeahead in long lists, `aria-activedescendant` where focus must
stay on an input (as in a combobox), and correct focus return for every
overlay.

A worked example: a search combobox. Focus stays in the input while arrow
keys move a highlighted option, which is exposed through
`aria-activedescendant` pointing at the option's id. Roving tabindex would
move focus out of the input and break typing.

The mistake at this level is mixing the two techniques in one widget, so
focus and the announced active item disagree.

</Level>
<Level name="Edge cases" depth={3}>

Single boundaries:

- **Focus on a removed element.** Deleting a list item while it is focused
  drops focus to the body. Move focus to the next item, or the list
  heading, before removing it.
- **A sticky header covering focus.** Tabbing down a long page, the
  focused element scrolls under a fixed header. `scroll-padding-top` on
  the scroll container keeps it visible; WCAG 2.2 has a criterion about
  focus not being obscured.
- **Content that appears on hover.** A tooltip that only appears on hover
  is invisible to keyboard users. Show it on focus as well, and let Escape
  dismiss it.
- **Zoom to 200 percent.** Text and controls must still work; a fixed
  height container that clips text at zoom fails people who rely on it.

</Level>
<Level name="Corner cases" depth={3}>

Two boundaries at once:

- **A modal opened from inside a menu.** The menu closes when the dialog
  opens, so the opener no longer exists when the dialog closes. Return
  focus to the menu button instead.
- **Roving tabindex plus a disabled item.** Arrow keys should either skip
  disabled items or focus them with `aria-disabled`; the APG discusses
  both, and the choice should be consistent across the system.
- **A live region plus a route change in a single-page app.** The page
  changes without a load, so nothing is announced and focus stays on the
  clicked link. Move focus to the new page's `h1`, or announce the new
  title in a live region.

</Level>
<Level name="Production level" depth={3}>

In production, accessibility is a check in every build and a pass in every
release. Automated tests with an engine such as axe run in CI and fail on
new violations. End-to-end tests drive the keyboard through critical
journeys: sign in, the main task, checkout. A human pass with a screen
reader happens for new components and major screens.

Issues are tracked like bugs, with severity from the keyboard layers above:
a trap or an unreachable feature blocks release, an unclear name does not.

The mistake in production is an accessibility audit once a year, with a
long report that ages faster than it is fixed. Small, continuous checks
beat a large, rare one.

</Level>
<Level name="Mindset" depth={3}>

The mindset is that the keyboard and the screen reader are first-class
ways to use the product, not edge cases. Some people use nothing else, and
many more use them some of the time: with a broken trackpad, in bright
sun, with a sleeping child on one arm.

So I test the way I would test on a phone: routinely, early, as part of
building, not as a final gate. The cost of a fix is lowest while the
component is fresh in my head.

The mistake in mindset is aiming for a checker's green tick. The tick
means the automated rules pass, which is a floor. The question is whether
a person can finish the task.

</Level>
<Level name="System design" depth={3}>

At the system level, accessibility lives in the design system. Tokens
guarantee contrast for every pair in every theme. The Field component wires
labels and errors. The Button forces a name when it has only an icon.
Dialog, Menu, Tabs and Combobox implement the APG patterns once. Product
screens compose these, and most of the work is already done.

## Questions people ask

**Which screen reader should I test with?** The one on the system you have,
first. VoiceOver on a Mac or iPhone, Narrator or NVDA on Windows, TalkBack
on Android. Different readers behave differently, so important flows are
worth checking in two.

**Is an automated checker enough?** No. Automated tools find a meaningful
share of issues, such as missing names and contrast failures, but not
whether the order makes sense or a dialog returns focus. Use both.

**Should every icon have alt text?** Icons that carry meaning need a name;
decorative icons next to text should be hidden with `aria-hidden="true"`,
or they are read twice.

**What about `tabindex="0"` on non-interactive elements?** Avoid it. Tab
stops on text that cannot be activated slow keyboard users down. Make
scrollable regions focusable only when they are not otherwise reachable.

**Do I need ARIA at all?** For native controls, rarely. For composite
widgets and live updates, yes: roles, states and live regions have no
native equivalent in those cases.

**How do I write the pass down so someone else can repeat it?** As a short
table per screen: the journey (for example "change the theme and save"),
the keys pressed, what was announced, and each issue with its layer from
the keyboard diagram and the fix. The table is also the regression test: the
next person runs the same journey and compares. I keep mine next to the
component or screen it covers, so it changes when the screen changes.

**What about mobile screen readers?** They work by swiping and tapping
rather than Tab, but they read the same accessibility tree. Names, roles,
states and landmarks matter just as much. Touch targets also need to be
large enough to hit; WCAG 2.2 has a minimum target size criterion for
pointer targets, with exceptions for inline links in text.

**How long should a pass take?** For one screen, keyboard and screen reader
together, about twenty minutes once the five screen-reader commands are
familiar. The first few take longer, mostly because of learning the
reader, and that time is paid back on every later screen.

## Key takeaways

- A keyboard pass finds unreachable, invisible, out-of-order and trapped
  focus; it needs no tools.
- Every control is announced by name, role and state; the name comes from
  `aria-labelledby`, `aria-label`, native labels, content, then last
  resorts.
- Keep visible text inside the accessible name.
- Contrast is a measured ratio: 4.5:1 for normal text, 3:1 for large text,
  controls and focus indicators.
- Composite widgets are one Tab stop with arrow keys inside; overlays move
  focus in and give it back.
- Native elements first; ARIA only where nothing native fits, and kept in
  sync.

## Glossary

- **Focus**: the element that receives keyboard input.
- **Tab order**: the sequence in which Tab moves focus, following the DOM.
- **Focus trap**: a place focus cannot leave; deliberate only in modals.
- **Accessible name**: the text a screen reader announces to identify a
  control.
- **Role**: what kind of thing a node is, such as button or link.
- **State**: a changing property of a node, such as expanded or pressed.
- **Relative luminance**: the brightness of a colour on a linear scale from
  0 (black) to 1 (white), as WCAG defines it.
- **Contrast ratio**: (lighter luminance + 0.05) / (darker luminance +
  0.05).
- **Roving tabindex**: keeping exactly one item of a group at
  `tabindex="0"` and moving it with arrow keys.
- **APG**: the ARIA Authoring Practices Guide, the W3C's collection of
  widget patterns.
- **Inert**: content that cannot be focused or interacted with.

## Practice

**Warm-up.** Run the keyboard pass on any screen you built, and write down
every issue with the layer it belongs to.

**Build.** Run the contrast script over every text and background token
pair in your site, in every theme. Fix any failure in the tokens, not in
the screens.

**Stretch.** Build a tab list to the APG pattern with roving tabindex,
Home and End, `aria-selected` and panels connected by
`aria-controls`. Test it with the keyboard and a screen reader, and
compare it with a headless library's version.
