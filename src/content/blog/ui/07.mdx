Responsive design used to mean a stylesheet with a breakpoint for phones,
one for tablets and one for desktops, and a lot of guessing about which
device was which. Modern CSS lets most layouts adapt on their own: flexbox
shares space along a line, grid fits as many columns as there is room for,
container queries let a component change shape based on the space it was
given, and `clamp()` makes sizes fluid between two limits. This note
explains each by running its arithmetic in a few lines of JavaScript, so
the browser's behaviour stops being a surprise.

## Before you start

After this note you will be able to:

- explain how flexbox turns flex-basis, flex-grow and flex-shrink into
  final sizes, and predict them;
- choose between flexbox and grid for a given layout;
- write a card grid with `auto-fill` and `minmax()` that needs no media
  query, and work out how many columns it will have;
- make a component respond to its container's width with a container
  query;
- set fluid type and spacing with `clamp()` and know its limits.

What you should already know: the box model, `display`, and CSS custom
properties from [note two](/sanjay/posts/ui/02/), since spacing values in
layouts should come from tokens.

Reading time: about 30 minutes, plus ten for the scripts.

## Start from content

### In one sentence

The most robust responsive layout is the one CSS already does: block
elements stacking and inline text wrapping, with a maximum width, so only
the parts that genuinely need a layout get one.

### The idea

Normal flow is responsive by default. Paragraphs fill their container's
width and wrap. Blocks stack. Images with `max-width: 100%` shrink to fit.
A page of text with a sensible `max-width` on its column and some padding
works on a phone and a wide monitor without a single media query.

Layout tools are for the places where flow is not enough: a row of
buttons, a sidebar next to content, a grid of cards. Each of those should
be expressed in terms of **content and constraints**, not devices: "cards
at least 220 pixels wide, as many per row as fit", not "three columns on
tablets".

The words for this are **intrinsic** and **extrinsic** sizing. An intrinsic
size comes from content: `min-content` is the narrowest a box can be
without overflow (the longest word), `max-content` is how wide it would be
with no wrapping. An extrinsic size comes from outside: a fixed width, a
percentage. Responsive layouts lean on intrinsic sizes and use extrinsic
ones as limits.

A good reading column is the simplest example of both:

```css
.prose {
  max-width: 68ch;          /* limit: about 68 characters per line */
  margin-inline: auto;      /* centred when there is room */
  padding-inline: var(--space-4);
}
```

The `ch` unit is the width of the "0" character, so the limit scales with
the font. Below 68 characters' width, the column is simply as wide as the
screen minus padding.

### Worked example

The simple example is the column above: no media query, readable at every
width.

The realistic example is the layout of this site's note pages: a left rail,
the text column and a right overview. On a wide screen all three sit side
by side. On a narrow one, the rails move out of the way and the text column
takes the width. The text column itself never needs to know which case it
is in, because it is a flow column with a maximum width; only the outer
arrangement changes.

### Common mistake

The common mistake is device breakpoints: `@media (max-width: 768px)`
because 768 was a tablet width once. Devices change; content does not. The
breakpoint that matters is where **this** content stops fitting, which is
found by resizing the browser slowly until the layout looks wrong, and
putting the breakpoint there, ideally in `em` or `rem` so it follows the
user's font size.

### In real systems

Real stylesheets keep media queries for page-level changes (showing a
navigation drawer, hiding a rail) and use flow, flexbox, grid and container
queries for everything inside. Spacing comes from tokens, so a layout
change never invents a new pixel value. Testing covers a narrow width, a
wide one, and 200 percent zoom, which together catch most responsive
bugs.

## Flexbox: sharing space on a line

### In one sentence

Flexbox lays items along one axis, starts each at its flex-basis, then
hands out leftover space by flex-grow or takes away missing space by
flex-shrink weighted by size.

### The idea

A flex container puts its children in a row (or a column). For each item,
the browser starts from its **flex-basis**: a length, or `auto`, which
means the item's width or its content size. It adds up the bases and the
gaps and compares the total with the container:

- If there is **positive free space**, each item grows by its share of
  `flex-grow`. Two items with `flex-grow: 1` and one with `2` split the
  space 1:1:2.
- If there is **negative free space**, items shrink. Each one's share of
  the shrinking is its `flex-shrink` **multiplied by its flex-basis**, so
  a wide item gives up more pixels than a narrow one with the same shrink
  factor. That is what keeps proportions roughly sane.

The shorthand `flex: 1` sets grow 1, shrink 1 and basis `0%`. Because the
basis is zero, all the space is free space, and items with equal grow end
up equal, regardless of content. `flex: auto` uses basis `auto`, so items
start at their content size and share only the leftover; they end up
unequal.

The real algorithm also clamps items to their min and max sizes and
re-runs the distribution for the rest, which matters in the common mistake
below. The simplified version is enough to predict most layouts.

### Worked example

```js
// flex.mjs (simplified: one line, no min/max clamping)
export function flex(container, items, gap = 0) {
  const basisSum = items.reduce((s, i) => s + i.basis, 0) + gap * (items.length - 1);
  const free = container - basisSum;
  if (free >= 0) {
    const grow = items.reduce((s, i) => s + i.grow, 0);
    return { free, sizes: items.map((i) => i.basis + (grow ? (free * i.grow) / grow : 0)) };
  }
  // shrinking is weighted by shrink x basis, so big items give up more
  const scaled = items.reduce((s, i) => s + i.shrink * i.basis, 0);
  return { free, sizes: items.map((i) => i.basis + (free * i.shrink * i.basis) / scaled) };
}
```

Four layouts:

```text
sidebar 240 + main grow, 1000px    free  760 -> 240.0, 760.0
grow 1,1,1, bases 100/200/300, 900 free  300 -> 200.0, 300.0, 400.0
same items, 450px: shrink          free -150 -> 75.0, 150.0, 225.0
flex: 1 (basis 0), 900px           free  900 -> 300.0, 300.0, 300.0
```

Line one is the classic sidebar: a fixed 240 that neither grows nor
shrinks, and a main area that takes everything else. Line two shows grow
adding equal amounts (100 each) on top of unequal bases, so the items stay
unequal. Line three shows shrink taking 25, 50 and 75 pixels, in
proportion to the bases, so all three end at 75 percent of their basis.
Line four is `flex: 1`: zero bases, so equal grow gives equal widths.

### Common mistake

The common mistake is a flex item that refuses to shrink and overflows its
container: typically a main area containing a long URL or a code block.
The cause is the clamping step the simplified version skipped. A flex
item's default minimum width is `auto`, which for most items means its
min-content width, so it will not shrink below its longest word or its
widest child. The fix is `min-width: 0` on the item (or `overflow: hidden`
or `auto`), which lets it shrink and its content wrap or scroll.

### In real systems

Flexbox is the right tool for one-dimensional arrangements: toolbars,
button rows, a label and a value, a header with a logo and navigation, a
media object with an image and text. With `flex-wrap: wrap`, items move to
a new line when there is no room, which makes small responsive groups
without a media query. The `gap` property spaces items without margins on
the first or last child.

One flexbox pattern is worth knowing by heart because it gives a
breakpoint-free switch between a row and a stack. Give each item
`flex: 1 1 15rem` inside a wrapping container. While the container can
hold every item at 15rem or more, they sit in one row and share the extra
space. When it cannot, items wrap onto new lines, and each line's items
grow to fill it. A two-item "sidebar" layout follows the same idea: the
sidebar gets `flex: 1 1 15rem`, the main area `flex: 999 1 0` with a
`min-width` of about half the container, so the main area takes almost
all the free space, and when it would drop below its minimum, the two
items wrap onto separate lines. The arithmetic is exactly the grow and shrink rules in the
script, plus wrapping, and it needs no media query at all.

Equal, because `flex: 1` sets the basis to zero, so all space is shared by

unequal. (A minimum-content clamp can still override this for very long
words.)

</details>

<details>
<summary>2. Why does a main column with a long URL overflow instead of shrinking?</summary>

Its automatic minimum width is its min-content width, the URL's width.
Setting `min-width: 0` lets it shrink.

</details>

## Grid: rows, columns and auto-fill

### In one sentence

Grid defines rows and columns on the container and places items into them,
and `repeat(auto-fill, minmax(MIN, 1fr))` fits as many columns of at least
MIN as the space allows, with no media query.

### The idea

Flexbox works item by item along a line; grid works from the container,
which defines **tracks** (columns and rows) and places items into the
cells they form. That makes grid the tool for two-dimensional layouts and
for anything that should line up in columns across rows.

The `fr` unit is a fraction of the free space in the grid after fixed
tracks and gaps. `minmax(220px, 1fr)` is a track that is at least 220
pixels and at most one fraction.

The responsive trick is `repeat(auto-fill, …)`. Instead of a number of
columns, the browser computes how many tracks of the minimum size fit:

```text
columns = floor((width + gap) / (min + gap))
```

then `1fr` stretches them to fill the row. Resize the container, and the
column count changes at exactly the widths where one more minimum-width
column fits. `auto-fit` is the same except that, when there are fewer
items than columns, empty tracks collapse and the items stretch across the
whole row.

### Worked example

```js
// grid.mjs
export function autoFill(width, min, gap) {
  const columns = Math.max(1, Math.floor((width + gap) / (min + gap)));
  return { columns, track: (width - gap * (columns - 1)) / columns };
}
```

For `repeat(auto-fill, minmax(220px, 1fr))` with a 16-pixel gap:

```text
  320px container -> 1 columns of 320.0px
  600px container -> 2 columns of 292.0px
  760px container -> 3 columns of 242.7px
 1000px container -> 4 columns of 238.0px
 1280px container -> 5 columns of 243.2px
```

One column on a phone, five on a wide screen, and the cards are never
narrower than 220 pixels. The CSS is one line:

```css
.cards {
  display: grid;
  gap: var(--space-4);
  grid-template-columns: repeat(auto-fill, minmax(min(220px, 100%), 1fr));
}
```

The `min(220px, 100%)` guards the case the script hides with
`Math.max(1, …)`: a container narrower than 220 pixels. Without it, the
single column would stay 220 wide and overflow.

The realistic example is a page layout with named areas:

```css
.page {
  display: grid;
  grid-template-columns: minmax(0, 1fr);
  grid-template-areas: "header" "main" "aside";
}
@media (min-width: 60rem) {
  .page {
    grid-template-columns: 15rem minmax(0, 1fr);
    grid-template-areas: "header header" "aside main";
  }
}
```

The same elements, rearranged by changing the template, with one media
query at the width where a sidebar fits. `minmax(0, 1fr)` is the grid
version of `min-width: 0`: it lets the main column shrink below its
content's minimum.

### Common mistake

The common mistake is `1fr` columns that overflow. A `1fr` track has a
minimum of `auto`, the content's min-content size, so a wide image or a
long word in one cell widens the track and pushes the grid past its
container. `minmax(0, 1fr)` fixes it, at the cost of letting the content
overflow its cell instead, which then needs wrapping or scrolling.

### In real systems

Grid handles most page-level layout: header, navigation, main, aside,
footer, rearranged by template areas at one or two widths. Card lists and
galleries use auto-fill. Forms use grid to line up labels and inputs.
`subgrid` lets a nested element use its parent's tracks, so the titles and
footers of cards in one row line up even when their content differs.

## Container queries and fluid values

### In one sentence

A container query lets a component change its layout based on the width
of the element that contains it, and `clamp()` lets sizes grow smoothly
between a minimum and a maximum.

### The idea

Media queries ask about the viewport. That is the wrong question for a
component. A card might be in a wide main column on one page and a narrow
sidebar on another, on the same screen. A media query sees the same
viewport in both places and gives the same layout; the card in the sidebar
breaks.

A **container query** asks about the nearest ancestor that is declared a
container. The ancestor opts in:

```css
.card-slot { container-type: inline-size; }

.card { display: grid; gap: var(--space-2); }
@container (min-width: 30rem) {
  .card { grid-template-columns: 8rem 1fr; } /* image beside text */
}
```

In a slot wider than 30rem, the card puts its image beside the text; in a
narrower slot, it stacks. The card's CSS knows nothing about pages or
devices. Container query units such as `cqi` (one percent of the
container's inline size) size things relative to the container in the
same way `vw` does for the viewport.

`clamp(MIN, PREFERRED, MAX)` returns the preferred value, kept between the
two limits. With a preferred value that mixes `rem` and `vw`, type and
spacing grow with the viewport, but never below a readable minimum or
above a sensible maximum.

### Worked example

`font-size: clamp(1rem, 0.875rem + 0.5vw, 1.25rem)` at six viewport
widths, with 1rem as 16 pixels:

```js
// clamp.mjs
const clamp = (min, value, max) => Math.min(Math.max(value, min), max);
for (const vw of [320, 400, 768, 1024, 1440, 1920]) {
  const preferred = 14 + 0.005 * vw; // 0.875rem + 0.5vw in px
  console.log(`viewport ${String(vw).padStart(4)}px: preferred ${preferred.toFixed(2)}px -> font-size ${clamp(16, preferred, 20).toFixed(2)}px`);
}
```

```text
viewport  320px: preferred 15.60px -> font-size 16.00px
viewport  400px: preferred 16.00px -> font-size 16.00px
viewport  768px: preferred 17.84px -> font-size 17.84px
viewport 1024px: preferred 19.12px -> font-size 19.12px
viewport 1440px: preferred 21.20px -> font-size 20.00px
viewport 1920px: preferred 23.60px -> font-size 20.00px
```

The size is 16 up to a 400-pixel viewport, grows smoothly to 20 by 1200
pixels, and stays there. No breakpoints, no jumps.

The `rem` part of the preferred value matters. A pure `vw` font size
ignores the user's font settings and does not grow with browser zoom in
the way text should, which is an accessibility failure. Mixing in `rem`
keeps part of the size tied to the user's preference.

### Common mistake

The common mistake is forgetting the containment side effect.
`container-type: inline-size` makes the element's inline size independent
of its contents, so a container that relied on its content for its width,
such as a shrink-wrapped flex item, can collapse to zero. Containers
should be elements whose width comes from outside: a grid cell, a column, a
slot with a defined width.

Another is querying the element itself. A container query applies to
descendants of the container, not the container, so the card cannot be its
own container; wrap it, or make the slot the container.

### In real systems

Container queries are supported in all current major browsers, and they
change how component libraries are written: a component ships its own
responsive behaviour, and pages only decide how much space to give it.
Fluid type scales, built from a few `clamp()` values in tokens, replace
the old per-breakpoint font sizes. Media queries remain for things that
really are about the viewport or the user: page layout, and preferences
such as `prefers-reduced-motion` and `prefers-color-scheme`.

## From beginner to strategy

<Levels label="Responsive CSS: flexbox, grid and container queries">
<Level name="Beginner" depth={3}>

At the beginner level, let flow do the work and add layout only where it
is needed. Set a maximum width on text, make images `max-width: 100%`, use
flexbox with `gap` and `flex-wrap` for rows of things, and test by
dragging the browser narrower and wider.

A worked example: a header with a logo and five links that overflows on a
phone. `display: flex; flex-wrap: wrap; gap: var(--space-2)` lets the
links wrap under the logo with no media query.

The mistake at this level is fixed widths in pixels on containers. Use
maximum widths, and let things be narrower.

</Level>
<Level name="Intermediate" depth={3}>

At the intermediate level, choose the tool by the shape of the layout:
flexbox for lines, grid for tables and pages. Use auto-fill grids for card
lists and named template areas for page layouts. Place breakpoints where
content breaks, in `rem`.

A worked example: a product list with a filter sidebar. Grid template
areas put the sidebar beside the list above 60rem and above it below. The
list inside is an auto-fill grid that needs no breakpoint of its own.

The mistake at this level is using grid for everything, including button
rows that should simply wrap, or flexbox for card grids whose rows should
line up.

</Level>
<Level name="Advanced" depth={3}>

At the advanced level, predict sizes. Know how flex distributes free
space, how the automatic minimum clamps items, how `fr` tracks resolve, and
when `minmax(0, 1fr)` or `min-width: 0` is needed. Use container queries
for components and `clamp()` for fluid type and spacing.

A worked example: a dashboard card with a chart that overflows its grid
cell. The cause is the chart's intrinsic width setting the track's
minimum. `minmax(0, 1fr)` on the column and a chart that sizes to its
container fix it.

The mistake at this level is debugging layout by trying values. Open the
browser's flex or grid inspector, read the computed sizes, and compare
them with the arithmetic.

</Level>
<Level name="Edge cases" depth={3}>

Single boundaries:

- **A container narrower than the grid minimum.** `minmax(220px, 1fr)` in
  a 200-pixel container overflows. Use `min(220px, 100%)`.
- **Very long words or URLs.** They set min-content widths. Use
  `overflow-wrap: anywhere` on text that may contain them.
- **Zoom at 400 percent.** A 1280-pixel window behaves like a 320-pixel
  one, and WCAG expects content to reflow without two-dimensional
  scrolling. The same narrow layout covers both.
- **Empty grid cells.** Auto-fill keeps empty tracks, which can look like a
  missing card. Use auto-fit when a short list should stretch.

</Level>
<Level name="Corner cases" depth={3}>

Two boundaries at once:

- **A container query plus an intrinsically sized container.** The
  container collapses because its width can no longer come from content.
  Give it a width from its parent.
- **`flex: 1` plus a long word.** Equal widths are expected, but the
  automatic minimum makes the item with the long word wider. `min-width:
  0` restores equality.
- **Fluid type plus a container query.** A heading sized with `vw` inside a
  narrow sidebar card is as large as in the main column. Size it with
  `cqi` in the card's container instead.

</Level>
<Level name="Production level" depth={3}>

In production, responsive behaviour is tested, not eyeballed. Visual
regression tests run at a narrow, a medium and a wide width, and at 200
percent zoom. Layout spacing and fluid sizes come from tokens. Components
carry their own container queries, so a page can drop them into any slot.

Performance matters too: layout that depends on JavaScript measuring
elements causes shifts and costs time; CSS layout runs in the browser's
layout engine with no script.

The mistake in production is a component that only works at the width it
was designed in, discovered when another team puts it in a sidebar.

</Level>
<Level name="Mindset" depth={3}>

The mindset is to describe constraints and let the browser solve them.
"At least 220 pixels, as many as fit" is a constraint; "three columns at
1024" is a solution for one case. Constraints keep working for widths
nobody tested.

So I ask what each part of the layout needs from its space, write that
down in CSS terms, and let flow, flex and grid do the arithmetic. I only
reach for a breakpoint when the content itself demands a different
arrangement.

The mistake in mindset is designing for devices. There are too many, they
change every year, and the user's window is not their device anyway.

</Level>
<Level name="System design" depth={3}>

At the system level, layout responsibilities are split. Pages own the
macro layout: the grid areas, which slot gets how much space, and the one
or two media queries that change it. Components own their micro layout,
through flexbox, grid and container queries on their own width. Tokens own
the spacing and fluid type scale.

A concrete design: a `Stack` and a `Cluster` primitive for vertical and
wrapping horizontal spacing, a `Grid` primitive with an auto-fill minimum
prop, and a convention that every slot in a page layout is a container.
Product components assume nothing about the viewport.

The mistake at this level is components with viewport media queries
inside them, which tie them to page layouts they cannot see.

</Level>
<Level name="Strategy" depth={3}>

How I learn this and how I know I have. I rebuild one page of my site
from flow upward: text first, then a flex header, then a grid for the
lists, then container queries for the cards, then `clamp()` for headings.

## Questions people ask

**Flexbox or grid?** Flexbox when items sit on a line and their own sizes
should drive the result. Grid when the container should define columns
that items line up in. Many layouts use both: grid for the page, flexbox
inside each part.

**Are media queries obsolete?** No. They remain the right tool for
viewport-level layout and for user preferences. Container queries replace
them inside components.

**What unit should breakpoints use?** `rem` or `em`, so they respond to
the user's font size. Container query thresholds in `rem` behave the same
way.

**How many breakpoints does a page need?** As few as the content needs.
Often one or two for the page layout, and none inside components.

**Is `clamp()` safe for font sizes?** Yes, if the preferred value includes
a `rem` part and the maximum is not more than about two and a half times
the minimum, so zoom still enlarges text enough. Check at 200 percent zoom.

**What about logical properties like `margin-inline`?** Use them. They
describe spacing relative to the writing direction, so `padding-inline`
means left and right in English and still means the start and end of a
line in a right-to-left language. They cost nothing and make a layout
correct for more languages without a second stylesheet. Flexbox and grid
already work this way: `justify-content: start` follows the writing
direction, not the left edge.

**Why does my layout jump when a web font loads?** The fallback font and
the web font have different widths, so line breaks and intrinsic sizes
change when the font swaps in. That is a responsive problem in disguise:
the layout responded to new content. Matching the fallback's metrics, or
reserving space for elements whose size depends on text, reduces the
shift. Images have a simpler fix: `width` and `height` attributes, so the
browser knows the aspect ratio before the file arrives.

**How do I debug a layout I did not write?** Open the browser's layout
inspector, which overlays grid lines, track sizes, flex free space and
gaps. Read the computed values of `flex-basis`, `min-width` and the grid
template for the element that misbehaves, and run the arithmetic from this
note on them. Most surprises come from one of three places: an automatic
minimum size, a basis that is not what the shorthand suggested, or a
percentage resolved against a different box than expected.

## Key takeaways

- Normal flow is already responsive; add layout only where it is needed.
- Flexbox starts from flex-basis and shares free space by grow, or missing
  space by shrink times basis.
- `flex: 1` means a zero basis and equal shares; `min-width: 0` lets a flex
  item shrink below its content.
- `repeat(auto-fill, minmax(min(MIN, 100%), 1fr))` fits as many columns as
  there is room for, with no media query.
- Container queries let a component respond to its own space; media
  queries are for the viewport and user preferences.
- `clamp()` makes sizes fluid between limits; include `rem` in the
  preferred value.

## Glossary

- **Normal flow**: the default layout, where blocks stack and inline
  content wraps.
- **Intrinsic size**: a size that comes from content, such as min-content
  and max-content.
- **Flex-basis**: an item's starting size before growing or shrinking.
- **Free space**: the container size minus all bases and gaps; positive is
  shared by grow, negative by shrink.
- **Track**: a column or row in a grid.
- **fr unit**: a fraction of the grid's free space.
- **auto-fill / auto-fit**: repeat as many tracks as fit; auto-fit also
  collapses empty ones.
- **Container query**: a style rule conditioned on an ancestor container's
  size.
- **cqi**: one percent of the query container's inline size.
- **clamp()**: a CSS function that returns a value kept between a minimum
  and a maximum.

## Practice

**Warm-up.** Take a page you built and remove every media query. Write down
what breaks, and at what width.

**Build.** Extend the flex script to clamp items to a `min` and re-run the
distribution for the rest, as the browser does. Test it on a case where
one item cannot shrink below its content.

**Stretch.** Build a card that is stacked below 30rem and side by side
above, using a container query, and place it in a main column, a sidebar
and a three-column grid on one page. Then add a fluid heading inside it
using `cqi` and `clamp()`.
