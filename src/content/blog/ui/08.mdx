A folder called `components` with a button, a card and a dialog in it is
useful. It is not yet a design system. The difference shows up a few
months later, when the button has three local copies, the card has been
restyled in two screens with inline overrides, nobody knows whether the
dialog may be changed, and a "small fix" to its padding repaints every
page. A design system is the components plus everything that keeps them
used, consistent and safe to change. This note, the last in the series,
covers those other parts, with a script that measures drift and one that
decides a version bump from an API change.

## Before you start

After this note you will be able to:

- name the parts of a design system beyond the components, and say what
  each one is for;
- measure adoption and drift in a codebase with a small scanner, and read
  its numbers sensibly;
- decide whether a component change is a patch, a minor or a major
  version, from a diff of its API;
- run a deprecation that does not break anyone on the day it ships;
- set up a contribution path so the system grows from real needs instead
  of guesses.

What you should already know: the earlier notes in this series, especially
[tokens](/sanjay/posts/ui/02/) and [component APIs](/sanjay/posts/ui/03/),
and the basic idea of semantic versioning: major, minor and patch.

Reading time: about 30 minutes, plus ten for the scripts.

## More than components

### In one sentence

A design system is a product whose users are the people building other
products, and it includes the decisions, the documentation and the process
around the components, not only the components.

### The idea

The component library is the most visible part, because it is the part
people import. But it rests on things below it and is held together by
things around it:

- **Principles.** A few sentences about what the interface values, such as
  "content first, chrome second" or "every action can be undone or
  confirmed". They settle arguments that no component can.
- **Tokens.** The named decisions from note two: colour, spacing, type,
  radius, motion. They make the components consistent with each other.
- **Components.** The controls and patterns, with APIs designed as in
  note three, accessibility built in as in note six.
- **Patterns.** Arrangements of components for recurring tasks: a form
  with a summary of errors, an empty state, a confirmation for a
  destructive action, a settings page. Patterns are often documentation and
  examples rather than code.
- **Documentation.** For each component: what it is for, when not to use
  it, every variant rendered, the props, accessibility notes, and a few
  do and do-not examples.
- **Process.** How a change is proposed, reviewed, versioned, released and
  announced, and who decides.

Take away any of these and the library degrades in a predictable way.
Without tokens, components drift visually. Without documentation, people
cannot find the right component and build their own. Without process,
changes either never happen or happen without warning.

### Worked example

The simple example is a team of two with a shared button. The "system" is
the button, a tokens file, and an agreement that new buttons use it. That
is enough at that size; the process is a conversation.

The realistic example is the same button a year later, used by four teams
in three products. Someone needs a "ghost" style. Without a system around
the library, they copy the button into their product and add it. With
one, they read the docs, see that ghost is not there, open a request,
and the system team either adds it (a minor release) or explains which
existing variant covers the case. The second path is slower that day and
much faster over a year, because there is still one button.

### Common mistake

The common mistake is building the library first and the rest never. A
team extracts twenty components in a burst, publishes a package, and moves
on. Nobody documents when to use the card versus the panel, nobody owns
reviews, and the first breaking change is shipped as a patch. Within a
year, product teams treat the package as optional, and the drift the next
section measures begins.

### In real systems

Large public design systems from governments and big software companies
publish all these layers openly, and reading two of them side by side is a
quick education. They differ in style, but every one has principles,
tokens, components with usage guidance, patterns, accessibility notes and
a contribution model. That shared shape is the strongest evidence that the
extra layers are not optional.

### Check yourself

<details>
<summary>1. What is the difference between a component and a pattern?</summary>

A component is one reusable part, such as a button or input. A pattern is
a recurring arrangement of parts for a task, such as a form with an error
summary, often documented as guidance and examples rather than shipped as
one component.

</details>

<details>
<summary>2. Why are principles part of a design system?</summary>

They settle decisions no component covers, so teams make consistent
choices in new situations without a meeting.

</details>

## Adoption and drift

### In one sentence

Adoption is how much of the product's interface goes through the system,
and drift is every place it goes around it, and both can be measured with
a scanner over the source.

### The idea

A design system's success is not its component count. It is whether the
product's screens use it. Two numbers capture most of that:

- **Adoption.** Of all the interface elements of a kind (buttons, inputs,
  cards), how many come from the system? A raw `<button>` with local
  classes is not adopted; a `<Button>` is.
- **Drift.** Of the adopted ones, how many are bent: a `className` or
  `style` that overrides the look, a hard-coded colour next to them, a
  wrapper that changes behaviour. Drift is adoption in name only.

Neither number is a target to maximise blindly. Some raw elements are
fine, such as a native `button` inside a third-party widget. Some
overrides are layout, such as a margin, which most systems allow. The
numbers are a map of where to look, and the most useful output is the
**list of places**, sorted by count, not the percentage.

Drift is also information. A cluster of overrides on the same component,
all making the same change, is a feature request nobody filed. Three teams
removing the button's border radius is the system being told something.

### Worked example

A toy scanner over three files, counting system components, raw
equivalents, overridden system components and raw values:

```js
// drift.mjs (excerpt)
const systemTags = /<(Button|Card|Input|Dialog)\b/g;
const rawTags = /<(button|input|dialog)\b|className="card"/g;
const overrides = /<(Button|Card)[^>]*\b(className|style)=/g;
const rawValues = /#[0-9a-f]{3,6}\b|padding: \d+/gi;

for (const [file, src] of Object.entries(files)) {
  const sys = (src.match(systemTags) ?? []).length;
  const raw = (src.match(rawTags) ?? []).length;
  const ovr = (src.match(overrides) ?? []).length;
  const vals = (src.match(rawValues) ?? []).length;
  // print one line per file, then the total adoption
}
```

Its output:

```text
settings/Page.tsx    system 3  raw 1  overridden 0  raw values 1
billing/Invoice.tsx  system 2  raw 1  overridden 1  raw values 1
notes/List.tsx       system 3  raw 0  overridden 0  raw values 0
adoption: 8 of 10 components from the system (80%)
```

The settings page has a raw red `button` with inline padding: a "danger"
button built by hand, which suggests the author did not find the danger
intent. Billing has a hand-made card with a hard-coded red, and a system
button with a class that removes its rounding: drift. The notes list is
clean. Counted this way, compound parts such as `Card.Header` count as
system components too, which is a choice; a real scanner would report
them separately.

Regular expressions over source are crude, and a real scanner parses the
code (an abstract syntax tree) so that it sees imports, props and
components renamed on import. But even the crude version produces the
thing that matters: a list of files and lines to go and read.

### Common mistake

The common mistake is turning the adoption number into a goal for product
teams, with a dashboard and a target. Teams then wrap raw elements in thin
system-named components to move the number, and the scanner is satisfied
while the product drifts further. Use the numbers to decide where the
system team should look and help, not to grade the teams using it.

### In real systems

Production setups run the scanner in CI and post the diff on pull
requests: "this change adds two raw buttons and one override". That
timing, at review, is when a fix costs least. Lint rules can flag imports
of raw elements where a system component exists, and a weekly report of
the top drift clusters gives the system team its backlog.

### Check yourself

<details>
<summary>1. What is the difference between adoption and drift?</summary>

Adoption counts how many elements come from the system. Drift counts how
many of those are overridden or bent, so they use the system in name but
not in look or behaviour.

</details>

<details>
<summary>2. Eleven teams override the same prop in the same way. What does that suggest?</summary>

A missing variant, or an existing one that the documentation does not
show for that case. It is a feature request, and the system should
respond to it.

</details>

## Change: versions and deprecations

### In one sentence

A design system is a dependency, so every change is versioned by its
effect on callers, and anything that would break them goes through a
deprecation with a warning, a replacement and a deadline.

### The idea

Semantic versioning gives three levels, by the effect on whoever depends
on the package:

- **Patch**: no API change. A bug fix, an internal refactor, a style fix
  that matches the documented look.
- **Minor**: an addition that existing callers can ignore. A new optional
  prop, a new variant value, a new component.
- **Major**: anything that can break an existing caller. A removed or
  renamed prop or value, a prop that becomes required, a changed default.

For components, there is one category that semver tools cannot see: a
**visual or behavioural change with no API change**. The button's padding
grows; the dialog now closes on outside click. The API diff is empty, so a
tool says patch, but every screen changes. Systems handle this by policy:
any change to a documented look or behaviour is announced, and big ones
are treated as major even though the types did not change.

A **deprecation** turns one major change into two easy steps. In a minor
release, the old prop keeps working, a development warning names the
replacement, and the docs mark it deprecated. Callers move at their own
pace, often with a codemod. In the next major release, the old prop is
removed, and nobody is surprised.

### Worked example

A script that diffs two prop specifications and decides the bump:

```js
// semver.mjs
export function bump(before, after) {
  const reasons = [];
  let level = 'patch';
  const raise = (to, why) => {
    reasons.push(`${to}: ${why}`);
    if (to === 'major' || (to === 'minor' && level === 'patch')) level = to;
  };
  for (const [prop, spec] of Object.entries(before)) {
    const next = after[prop];
    if (!next) { raise('major', `removed prop ${prop}`); continue; }
    if (!spec.required && next.required) raise('major', `${prop} became required`);
    for (const v of spec.values ?? []) if (!(next.values ?? []).includes(v)) raise('major', `removed ${prop}="${v}"`);
    for (const v of next.values ?? []) if (!(spec.values ?? []).includes(v)) raise('minor', `added ${prop}="${v}"`);
    if (spec.default !== next.default) raise('major', `default of ${prop} changed ${spec.default} -> ${next.default}`);
  }
  for (const [prop, spec] of Object.entries(after)) {
    if (!(prop in before)) raise(spec.required ? 'major' : 'minor', `added ${spec.required ? 'required' : 'optional'} prop ${prop}`);
  }
  return { level, reasons };
}
```

Five changes to the button from note three, whose v1 has `intent`
(primary, secondary, danger; default secondary) and `size` (sm, md, lg;
default md):

```text
add a ghost intent         -> minor minor: added intent="ghost"
add optional icon prop     -> minor minor: added optional prop icon
drop size lg               -> major major: removed size="lg"
default size md -> sm      -> major major: default of size changed md -> sm
no API change (CSS fix)    -> patch 
```

The default change is the instructive line. Nothing was removed and no
type changed, yet every `<Button>` with no `size` prop renders smaller. The
script calls it major, which is right. The last line is the blind spot:
the script says patch, and only a visual regression test and a human can
say whether the "CSS fix" changed something callers relied on.

### Common mistake

The common mistake is the patch-release default change: "the medium button
looked too big, I made small the default". Every product upgrades its
patch versions automatically, and every screen changes size overnight. A
default is part of the API. Changing it is major, and it is usually better
done by deprecation: keep the default, add a warning when the prop is
omitted, and change it in the next major.

### In real systems

Real systems publish a changelog per release, written for the people
upgrading: what changed, why, and what to do. They ship codemods for
mechanical renames. They run visual regression tests across every
component story, so a "CSS fix" that moves anything is caught and either
reverted or announced. Many keep a migration guide per major version.

### Check yourself

<details>
<summary>1. A new optional prop and a new variant value: what bump?</summary>

Minor. Existing callers are unaffected, because they do not pass the new
prop or value.

</details>

<details>
<summary>2. Why is changing a default a major change?</summary>

Every caller that omitted the prop relied on the old default, so their
rendering changes even though their code did not.

</details>

## Contribution and ownership

### In one sentence

A design system needs an owner who says yes and no, and a path by which
product teams turn a real need into a system change, so the system grows
from evidence instead of guesses.

### The idea

Two failure modes bracket a system's governance. In the first, a central
team decides everything and accepts nothing from outside. Product teams
wait, give up, and build locally. In the second, anyone can add anything.
The system fills with one-off components and near-duplicates, and its
consistency is gone.

The workable middle has three parts:

1. **An owner.** A person or small team responsible for the system's
   quality, with the authority to say no and the obligation to explain
   why. Ownership can be part-time on a small team; it cannot be nobody.
2. **A contribution path.** A product team with a need first checks the
   docs, then opens a short proposal: the problem, where it appears, what
   they tried. The owner decides whether it is a new variant, a new
   component, a pattern, or a local solution that should stay local.
3. **A bar for inclusion.** Something goes into the system when it is
   needed in more than one place, fits the principles and tokens, has a
   designed API, and has documentation and accessibility checks. "Rule of
   three" is a common heuristic: wait until a need appears in three places
   before generalising.

Local components are not failures. A product component that only one
screen needs should stay in that product. The system is for what is
shared.

### Worked example

The simple example is a proposal for a "stat" component: a large number
with a label, used on two dashboards. The owner asks for the third use.
Until it appears, both dashboards keep a local component, built from
system tokens and the `Text` primitive, so they stay visually consistent.
When the third use appears, the three local versions are compared, and the
system version is designed from what they have in common.

The realistic example is a contribution that changes an existing
component: a team needs the dialog to support a scrollable body. They open
a proposal with screenshots of three places it is needed. The owner agrees,
the team writes the change with the system's tests and docs, the owner
reviews the API, and it ships as a minor release. The team got its feature,
and every other product got it too.

### Common mistake

The common mistake is treating the system team as a service desk that
builds every request. The backlog grows, response times grow with it, and
teams stop asking. Contributions from product teams, reviewed by the owner,
scale far better, and they keep the system close to real use.

The other mistake is accepting contributions without the bar: a component
merged with no docs, no accessibility check and an API shaped by one
screen. It will be a breaking change waiting to happen.

### In real systems

Mature systems publish their contribution model: what kinds of changes
they accept, the proposal template, review expectations and release
cadence. They hold regular office hours, keep a public roadmap, and credit
contributors in release notes. The owner's most important output is often
not code but decisions, written down where people can find them.

### Check yourself

<details>
<summary>1. A component is needed on one screen only. Should it go in the system?</summary>

Usually not. Keep it local, built from system tokens and primitives, and
revisit when the need appears in more places.

</details>

<details>
<summary>2. Why is a central team that builds every request a problem?</summary>

It becomes a bottleneck. Teams wait, give up and build locally, which is
the drift the system was meant to prevent. Reviewed contributions scale
better.

</details>

## From beginner to strategy

<Levels label="A component library is not a design system">
<Level name="Beginner" depth={3}>

At the beginner level, a design system for one project is a tokens file, a
handful of components that read it, and a page that shows them. Write the
page: each component, each variant, one sentence on when to use it. That
page is documentation, and it is what turns a folder into something other
people can use.

A worked example: my own site. Its tokens are the custom properties for
ink, muted, line and the IBM Plex fonts; its components are the diagram
components these notes use; its documentation is the note guide. That is
a small design system, and the guide is what keeps new notes consistent.

The mistake at this level is building components nobody asked for, in
anticipation. Extract from real use.

</Level>
<Level name="Intermediate" depth={3}>

At the intermediate level, the system becomes a package with versions and
a changelog. Changes follow semver, with defaults treated as API. A simple
scanner reports raw elements and overrides, and you read its list
regularly.

A worked example: the drift scan shows six hand-made confirmation dialogs.
Instead of six fixes, the system adds a confirmation pattern to the docs,
using the existing dialog and button, and the six are replaced over a
month.

The mistake at this level is publishing without a changelog. Callers
cannot upgrade safely if they cannot see what changed.

</Level>
<Level name="Advanced" depth={3}>

At the advanced level, change is automated where it can be. The API diff
decides the minimum bump in CI. Visual regression tests catch look
changes the types cannot. Deprecations ship with development warnings and
codemods. The scanner parses code properly and runs on pull requests.

A worked example: a rename of `intent` to `tone` across the library. A
minor release accepts both and warns on `intent`; a codemod rewrites
calls; the scanner tracks remaining uses; the next major removes `intent`.

The mistake at this level is automating the bump and trusting it fully.
The script's blind spot, a visual change with no API change, is exactly
the change that surprises people most.

</Level>
<Level name="Edge cases" depth={3}>

Single boundaries:

- **A security or accessibility fix that changes behaviour.** A dialog
  that did not trap focus now does. Technically a behaviour change; ship it
  as a fix, announce it clearly, because the old behaviour was a bug.
- **A product pinned to an old major.** It still needs a critical fix.
  Decide in advance how many majors get fixes, and for how long.
- **Two products with conflicting needs.** One wants denser tables, the
  other more spacing. A density setting, as a token layer, can serve both
  without a fork.
- **A component that should be deleted.** Nobody uses it, per the
  scanner. Deprecate and remove it in the next major; dead components
  still cost maintenance.

</Level>
<Level name="Corner cases" depth={3}>

Two boundaries at once:

- **A token rename plus a pinned product.** The token package renames
  `color.muted`; a product on the old component version reads the old
  name. Ship the old name as an alias for a full major cycle.
- **A deprecation plus third-party wrappers.** Another team wraps the
  button in their own component and passes props through. The
  deprecation warning fires inside the wrapper, far from the real caller.
  Include the component stack in the warning.
- **A contribution plus an urgent product deadline.** The team cannot wait
  for review. Let them ship locally with the system's tokens, with an
  agreement to contribute it back; track it, so local does not become
  permanent.

</Level>
<Level name="Production level" depth={3}>

In production, a design system runs like any other platform product. It
has an owner, a roadmap, a release cadence, a changelog, a support
channel, and measures: adoption and drift per product, time from proposal
to release, and the number of local forks.

The build checks tokens (resolver and contrast), components (types, unit
tests, accessibility engine, visual regression) and the API diff. Docs
are generated from the same source as the components, so they cannot
disagree on props.

The mistake in production is measuring the system by its own output,
components shipped, rather than by its users' outcomes: consistency in
products, speed of building new screens, and accessibility issues avoided.

</Level>
<Level name="Mindset" depth={3}>

The mindset is that a design system is a product with internal users. Its
users have deadlines, other priorities, and the option to ignore it. It
has to be easier to use than to avoid, which means good docs, quick
answers, safe upgrades, and saying yes to real needs.

So I treat drift as feedback, proposals as user research, and breaking
changes as costs I impose on other people's time. A change that is
convenient for the system and painful for every product is a bad change.

The mistake in mindset is thinking of the system as a set of rules to
enforce. Rules without help produce workarounds.

</Level>
<Level name="System design" depth={3}>

At the system level, the design system is a layered dependency graph:
tokens at the bottom, primitives and controls on them, patterns on those,
and products on top. Each layer is versioned, and products pin versions.
Dependencies point down only.

A concrete design: a tokens package, a components package that depends on
it, a docs site generated from both, a scanner and an API-diff check in
CI, and a contribution template. A rebrand is a major of the tokens
package. A new variant is a minor of the components package. Products
upgrade on their schedule, with codemods for majors.

The mistake at this level is one giant package containing tokens,
components and product-specific pieces, so every change is a release of
everything and products cannot take a token update without a component
upgrade.

</Level>
<Level name="Strategy" depth={3}>

How I learn this and how I know I have. I take the components I built in
this series and turn them into a small system: a tokens file, the button,
field, card and dialog, a docs page per component with variants rendered
and when-to-use notes, and a changelog.

Then I run the two scripts: the drift scanner over my own site, and the
semver bump on a few real changes I want to make. I make one change by
deprecation, with a warning and a codemod, and remove it a version later.

Done when: every shared component has docs, a version and a changelog; I
can say what the bump for any change is and why; and the drift scan lists
nothing I cannot explain.

</Level>
</Levels>

## Questions people ask

**When does a project need a design system?** When more than one person or
more than one product builds interface with the same look, or when the
same component has been copied a second time. Before that, tokens and a
few shared components are enough.

**Should I adopt a public design system instead of building one?** Often,
yes, especially for internal tools. A public system brings tested
components, accessibility work and documentation. The trade-off is
looking like everyone else and following someone else's change schedule.
Many teams adopt a headless library and build their own tokens and styles
on top.

**Who should own the design system?** Someone with both design and
engineering judgement, or a pair. The owner needs the authority to say no
and the time to review contributions.

**How do I get teams to adopt it?** Make it easier than the alternative:
good docs, quick help, safe upgrades and fixes to real complaints. Use the
drift list to find teams having trouble and help them, rather than
reporting them.

**Is Storybook a design system?** It is a tool for documenting and testing
components, and a good home for part of the documentation layer. The
system is the decisions, components, docs and process together.

## Key takeaways

- A design system is principles, tokens, components, patterns,
  documentation and process; the library is one layer.
- Adoption is how much of the product uses the system; drift is where it
  is bent or bypassed. Report the list of places, not just the
  percentage.
- Drift clusters are feature requests and documentation gaps.
- Version every change by its effect on callers; a changed default is
  major.
- Visual and behavioural changes with no API change need visual tests and
  clear announcements.
- Deprecate before removing: warning, replacement, codemod, then the major.
- Give the system an owner and a contribution path, and keep one-off
  components local.

## Glossary

- **Design system**: the principles, tokens, components, patterns,
  documentation and process that keep an interface consistent and
  changeable.
- **Component library**: the code package of reusable components; one
  part of a design system.
- **Pattern**: a documented, recurring arrangement of components for a
  task.
- **Adoption**: the share of interface elements that come from the system.
- **Drift**: places where system components are overridden or bypassed.
- **Semantic versioning**: major, minor and patch numbers that describe the
  effect of a release on callers.
- **Deprecation**: marking an API as going away, with a warning and a
  replacement, before removing it.
- **Codemod**: a script that rewrites source code automatically, used for
  mechanical migrations.
- **Visual regression test**: a test that compares screenshots of
  components before and after a change.
- **Rule of three**: a heuristic to generalise only once a need appears in
  three places.

## Practice

**Warm-up.** Pick one component you share across screens. Write its docs
page: what it is for, when not to use it, every variant, and the props.

**Build.** Point the drift scanner at a real codebase you own, adjusting
the patterns to its components. Sort the findings by count and fix the
top cluster by changing docs or the component, not the callers.

**Stretch.** Extend the semver script to read prop types from a
TypeScript declaration file instead of a hand-written spec, and run it in
CI so a pull request that needs a major bump says so before it merges.
