The first thing a browser does with my markup is not paint it. It builds two
trees from it: the DOM, which scripts see, and the accessibility tree, which
screen readers, voice control and a lot of search tooling see. Which element I
choose decides what goes into the second tree. This note is about choosing
well: semantic elements, landmarks, and a heading outline with exactly one
`h1`, plus a small script that checks all three.

## Before you start

After this note you will be able to:

- explain what "semantic" means in terms of the accessibility tree, not in
  terms of taste;
- pick the right element for a control, a region and a heading, and say what
  each one gives you for free;
- lay out a page with landmarks that a screen reader user can jump between;
- write a heading outline that starts at one `h1` and never skips a level;
- audit a built page for all of the above with a script, and know what the
  script cannot see.

What you should already know: basic HTML (elements, attributes, nesting) and
enough JavaScript to read a 20-line script. The React note on
[controlled inputs](/sanjay/posts/react/05/) helps for the form examples but
is not required.

Reading time: about 30 minutes, longer if you run the audit script against
your own pages, which I recommend.

## Semantic elements: meaning, not looks

### In one sentence

A semantic element is one whose name tells the browser what the thing *is*,
so the browser can tell everyone else, and a `div` with a class tells it
nothing.

### The idea

HTML has two kinds of element. Some carry meaning: `button`, `a`, `nav`,
`main`, `h2`, `ul`, `label`, `table`. Others carry none: `div` and `span`
exist only to group things for styling or scripting. A sighted mouse user
cannot tell the two kinds apart once CSS has run, because a `div` can be made
to look like anything. That is exactly why the difference is easy to miss.

The difference shows up in the **accessibility tree**. That is a second tree
the browser builds next to the DOM, with one node per meaningful thing. Each
node has a **role** (what it is: button, link, heading, list), a **name**
(what it is called: "Save", "Home"), and **states** (pressed, expanded,
checked, disabled). Assistive technology, meaning screen readers, voice
control, switch devices and braille displays, reads this tree, not the
pixels.

A semantic element fills in role, name and states without extra work. A
`button` gets the role button, takes its name from its text, is in the tab
order, fires `click` on Enter and on Space, and reports `disabled` when it
is disabled. A `div` gets no role at all. It is a generic container, so the
reader announces its text as plain text and moves on.

That is the whole argument for semantic HTML in one paragraph: the element is
an API contract with the browser. Pick the right element and the browser does
the accessibility work. Pick a `div` and you have signed up to rebuild that
work by hand, and you will miss some of it.

### Worked example

The simple case first: a clickable thing that saves a draft.

```html
<!-- looks like a button, is a div -->
<div class="btn" onclick="save()">Save</div>

<!-- is a button -->
<button type="button" onclick="save()">Save</button>
```

With a mouse, both work. Now use only the keyboard. The `div` is not in the
tab order, so Tab skips it; there is no way to reach it. A screen reader
announces "Save" as text, with no hint that it does anything. The `button` is
reached by Tab, announced as "Save, button", and pressing Enter or Space
runs `save()`.

The realistic case is what happens when someone notices the `div` is broken
and patches it. To match the `button`, the `div` needs a role, a tab stop and
keyboard handling:

```html
<div class="btn" role="button" tabindex="0"
     onclick="save()"
     onkeydown="if (event.key === 'Enter') save()">Save</div>
```

This is still wrong in three ways. Space does not activate it, and a real
button activates on Space when the key is released, not pressed. It has no
disabled state that a reader understands; adding a `disabled` attribute to a
`div` does nothing. And inside a form it does not submit, while a real
`button` with `type="submit"` does. Each fix is another line, and every line
is a place for the next bug. The element that already does all of it is one
word long.

### Common mistake

The common mistake is choosing the element by how it should look. A heading
is chosen because the text should be big, so the page gets an `h3` where an
`h2` belongs, or a `div class="title"` where a heading belongs. A link is
used for an action because it should look like text, so "Delete" becomes an
`a href="#"`.

The fix is a rule I apply before writing any markup: **choose by what it
does, then style it to look right**. A thing that navigates to another
address is a link. A thing that does something on this page is a button. A
thing that names the section below it is a heading, at the level that matches
the outline. CSS can make any of them look like any other.

### In real systems

In a real codebase the mistake usually lives in a shared component, which
multiplies it. A `Card` component that makes the whole card clickable with a
`div` and an `onClick` breaks every card on every page. A design system
`Link` that renders a `button` when it has no `href` breaks "open in a new
tab" and the browser's history for every caller.

Search engines read the same structure. A crawler follows `a href` links; it
does not run click handlers on `div` elements. The site's own rule in
`AGENTS.md` says "Real links only" for exactly this reason. Semantic markup
is one of the few changes that helps accessibility, search and maintenance at
the same time.

## Landmarks: the regions of a page

### In one sentence

Landmarks are the handful of page regions (banner, navigation, main,
complementary, content info) that a screen reader lists so a user can jump
straight to the part they want.

### The idea

A sighted user takes in a page's layout at a glance: the header across the
top, the menu, the main column, a sidebar, the footer. A screen reader user
gets the page as a stream, one thing after another. Without help, reaching
the article means listening through the whole header and menu first, on
every page.

Landmarks are that help. Certain elements map to **landmark roles**, and
screen readers offer a list of them and a key to jump between them. The
mapping is:

| Element | Landmark role | Notes |
|---|---|---|
| `header` | banner | only when it is not inside `article`, `aside`, `main`, `nav` or `section` |
| `nav` | navigation | label it when there is more than one |
| `main` | main | exactly one visible per page |
| `aside` | complementary | content related to, but separate from, the main content |
| `footer` | contentinfo | same scoping rule as `header` |
| `section` | region | only when it has an accessible name |
| `form` | form | only when it has an accessible name |
| `search` | search | the newer element for a search area |

Two rules carry most of the value. There is **exactly one `main`**, holding
the content that is unique to this page. And when the same landmark appears
twice, each one gets a **label**, so the list reads "navigation, Site" and
"navigation, On this page" instead of two identical entries.

Landmarks also give sighted keyboard users something, indirectly. A "Skip to
content" link at the top of the page, pointing at `main`, lets them skip the
menu with one keypress. That link is only reliable when there is one obvious
`main` to point at.

### Worked example

The simple version is a blog page with a header, a menu, the note and a
footer:

```html
<header>
  <a href="/sanjay/">Notes</a>
  <nav aria-label="Site">
    <a href="/sanjay/posts/">Series</a>
    <a href="/sanjay/path/">Path</a>
  </nav>
</header>
<main id="content">
  <h1>Semantic HTML, landmarks and one h1</h1>
  ...
</main>
<footer>Written by hand, built with Astro.</footer>
```

A screen reader's landmark list for this page has four entries: banner,
navigation "Site", main, content info. Jumping to main lands on the `h1`,
which is what the user wanted.

The realistic version is this site's note layout. It has a rail on the left
with the series list and the published notes, the note in the middle, and an
overview of the note's sections on the right. That is three navigation areas
and two side regions. Each one is labelled, so the list stays readable:

### Common mistake

There are two common mistakes, and they pull in opposite directions.

The first is **no landmarks**: every region is a `div`, so the landmark list
is empty and the only way through the page is linear. The fix is mechanical:
swap the outer `div` elements for `header`, `nav`, `main`, `aside` and
`footer`.

The second is **too many landmarks**. Every card becomes a `section` with an
`aria-label`, every widget becomes a region, and the landmark list grows to
thirty entries, which is as useless as none. A landmark is for a region a
user would want to jump to from anywhere on the page. A card in a grid is
not that; it is content inside `main`. The fix is to keep landmarks to the
page's big regions, usually five to eight, and use headings for everything
inside them.

### In real systems

Landmarks usually live in one layout component, so they are fixed once and
stay fixed. The risks come from composition. A layout that renders `main`
and a page component that renders another `main` inside it produces two. A
modal dialog rendered next to `main` is fine; a second app shell mounted by a
micro-frontend is not.

Single-page apps add a navigation problem. When the route changes, the
content inside `main` is swapped, but focus stays on the link that was
clicked, and a screen reader may announce nothing. Good routers move focus
to the new page's `h1` or to `main`, and update the document title, so the
user knows the page changed.

### Check yourself

<details>
<summary>1. A page has two nav elements with no labels. What does the user hear, and what is the fix?</summary>

Two entries that both say "navigation", so they cannot tell which is the
site menu and which is the table of contents. Give each an `aria-label`
("Site", "On this page"), or an `aria-labelledby` that points at a visible
heading.

</details>

<details>
<summary>2. Is a header element inside an article a banner landmark?</summary>

No. A `header` is only the banner landmark when it is scoped to the page,
not inside `article`, `aside`, `main`, `nav` or `section`. Inside an article
it is just that article's header.

</details>

## Headings: an outline with one h1

### In one sentence

Headings turn a page into an outline a reader can skim and jump through, so
the outline should start at one `h1` that names the page and go down one
level at a time.

### The idea

Headings are the most used navigation tool on the web for screen reader
users. A reader can list every heading, or press a key to jump to the next
one, or to the next `h2`. That only works if the heading levels mean
something. An `h2` should be a main section of the page, an `h3` a part of
that section, and so on.

The **`h1`** names the page. It usually matches, or nearly matches, the
document `title`. The rule this site follows is exactly one `h1` per page,
and `npm run check` fails the build if a page has zero or two. To be honest
about it, one `h1` is a convention and not a WCAG requirement, and search
engines cope with more than one. I keep it because it forces a decision:
what is this page *about*? A page that cannot answer with one heading
usually has a structure problem.

The second rule is **no skipped levels on the way down**. Going from `h2` to
`h4` leaves the reader wondering where the missing `h3` went. Going back up
any number of levels is fine: after an `h4`, the next main section is an
`h2`.

One idea that sounds right but does not work is the "outline algorithm",
where every `section` would start its own heading scope and an `h1` inside a
section would count as a lower level. Browsers never implemented it for
assistive technology, and it was removed from the HTML standard. An `h1` is
an `h1` wherever it sits. Use the real levels.

### Worked example

The simple example is a note with three sections, one of them with two
parts:

```html
<h1>Semantic HTML, landmarks and one h1</h1>
  <h2>Semantic elements</h2>
  <h2>Landmarks</h2>
    <h3>Labelling two navs</h3>
    <h3>Skip links</h3>
  <h2>Headings</h2>
```

(The indentation is only for reading; HTML does not care.) The outline a
reader gets is exactly the table of contents a sighted reader sees.

The realistic example is a page built from components, where each component
picks its own heading level. A `Card` that always uses `h3` is fine on a page
where cards sit under an `h2`. Put the same card directly under the `h1`, or
inside a sidebar that has its own `h2` and `h3`, and the outline breaks. The
fix is a heading-level prop, or a context that tracks the current depth, so
the component asks "what level am I at?" instead of hard-coding it.

### Common mistake

The common mistake is using heading levels for size. "This needs to be
smaller" turns an `h2` into an `h4`, and the outline skips. Or "this needs to
stand out" turns a sentence into a heading, and the outline fills with
headings that do not head anything.

The fix has two halves. Choose the level from the outline, then set the size
with CSS: a class, or a rule on `.sidebar h2`. And only make something a
heading if it names the content that follows it. A call to action, a quote
or a price is not a heading, however big it is.

### In real systems

In a content site the risk is the content itself. Writers paste text with
their own heading levels into a template that already has an `h1`, so every
page gets two. Markdown makes this easy: a `#` line is an `h1`. This site's
guides say "never write a `#` heading" in a note body for that reason, and
the build check catches it if someone does.

In an app the risk is the component tree. Dashboards built from widgets
often have no `h1` at all, or one `h2` per widget with nothing above it. A
visually hidden `h1` that names the screen ("Billing, invoices") is a
legitimate fix when the design has no visible title.

</details>

</details>

## Auditing the structure with a script

### In one sentence

A short script can read built HTML and check the outline and the landmarks
on every build, so structure stops depending on someone remembering.

### The idea

Structure decays. A page is correct when it is written, then a component
changes, a writer pastes a heading, a layout gains a second `main`. Nobody
notices, because nothing *looks* wrong. The fix for invisible regressions is
a check that runs every time.

The script below is deliberately small. It pulls the headings and the
landmark elements out of an HTML string with regular expressions and applies
four rules: one `h1`, the first heading is an `h1`, no downward skips, one
`main`, and labels on repeated `nav` elements. A real parser would be more
robust, and this site's `scripts/check-build.mjs` does the `h1` part on every
build, but the small version shows the whole idea in one screen.

### Worked example

The audit function:

```js
// audit.mjs
const LANDMARK_TAGS = { header: 'banner', nav: 'navigation', main: 'main',
  aside: 'complementary', footer: 'contentinfo' };

export function audit(html) {
  const problems = [];
  const headings = [...html.matchAll(/<h([1-6])[^>]*>(.*?)<\/h\1>/gs)]
    .map((m) => ({ level: Number(m[1]), text: m[2].replace(/<[^>]+>/g, '').trim() }));
  const h1s = headings.filter((h) => h.level === 1).length;
  if (h1s !== 1) problems.push(`${h1s} h1 elements, expected exactly 1`);
  if (headings[0] && headings[0].level !== 1)
    problems.push(`the first heading is h${headings[0].level}, expected h1`);
  for (let i = 1; i < headings.length; i++) {
    const jump = headings[i].level - headings[i - 1].level;
    if (jump > 1) problems.push(`"${headings[i].text}" jumps from h${headings[i - 1].level} to h${headings[i].level}`);
  }
  const landmarks = [...html.matchAll(/<(header|nav|main|aside|footer)\b([^>]*)>/g)]
    .map((m) => ({ role: LANDMARK_TAGS[m[1]], label: m[2].match(/aria-label="([^"]*)"/)?.[1] }));
  const mains = landmarks.filter((l) => l.role === 'main').length;
  if (mains !== 1) problems.push(`${mains} main landmarks, expected exactly 1`);
  const navs = landmarks.filter((l) => l.role === 'navigation');
  if (navs.length > 1 && navs.some((n) => !n.label))
    problems.push(`${navs.length} nav landmarks, and not all have a label`);
  return { headings, landmarks, problems };
}
```

Run against two small pages, a `div` soup and the semantic version of the
same content, it prints:

```text
--- div soup
outline: h3 Why it matters | h1 Landmarks
landmarks: (none)
  x the first heading is h3, expected h1
  x 0 main landmarks, expected exactly 1
--- semantic
outline: h1 Semantic HTML | h2 Why it matters | h2 Landmarks | h3 Labelling two navs
landmarks: banner, navigation "Site", main, navigation "On this page", contentinfo
  ok
```

The `div` soup has exactly one `h1`, so a check that only counted `h1`
elements would have passed it. The "first heading" rule is what catches a
page that opens on an `h3` and puts its `h1` halfway down.

### Common mistake

The common mistake is trusting the script too far. It reads the markup, not
the accessibility tree, so it cannot see a `role="main"` on a `div`, a
heading hidden with `display: none`, an `aria-label` that says something
unhelpful, or a name computed from an image's `alt`. It also cannot tell
whether the `h1` describes the page.

The fix is to treat the script as a floor, not a verdict. It catches the
regressions that happen silently. A real pass with a keyboard and a screen
reader, which the sixth note in this series walks through, catches the rest.

### In real systems

In a real pipeline this kind of check runs after the build, on the HTML that
will actually ship, not on the source. That matters for frameworks: the
source may never contain the word `main`, because a layout component adds
it. Checking `dist/` checks what the user gets. This site does exactly that:
`npm run build` writes `dist/`, and `npm run check` reads every HTML file in
it.

Browser-based tools go further. Axe, Lighthouse and the browsers' own
accessibility panels read the real accessibility tree after CSS and scripts
have run. They are slower and need a browser, so a common split is a cheap
markup check on every build and a browser audit in CI on a handful of key
pages.

</details>

## From beginner to strategy

<Levels label="Semantic HTML, landmarks and one h1">
<Level name="Beginner" depth={3}>

At the beginner level, the whole note is one habit: before writing a tag,
ask what the thing *does*, and pick the element that does that. A thing that
goes somewhere is an `a` with an `href`. A thing that does something here is
a `button`. A thing that names a section is a heading. A list of similar
things is a `ul` or an `ol`.

A worked example: a newsletter sign-up box. It has a title, a sentence, an
email field and a submit button. The beginner version is four `div`
elements. The semantic version is an `h2` for the title, a `p` for the
sentence, a `label` and an `input type="email"` for the field, and a
`button type="submit"` inside a `form`. Nothing about how it looks has to
change.

The mistake at this level is thinking semantics is extra work. It is less
work: the `button` is shorter than the `div` with a role, a tab stop and two
key handlers. The fix is to notice when you are adding ARIA or key handlers
to a `div`, and ask which element already does that.

</Level>
<Level name="Intermediate" depth={3}>

At the intermediate level you build whole pages and components, so structure
becomes a property of the composition, not of one tag. The layout owns the
landmarks: one `header`, one labelled `nav`, one `main`, an `aside` if there
is one, one `footer`. Pages own their `h1`. Components own nothing above
their own section's level.

A worked example is a heading-level prop. A `Section` component takes a
`level` of 2 to 6 and renders the matching element, and the page passes the
level it needs. Rendered under the `h1` it gets `level={2}`; rendered inside
a sidebar section it gets `level={3}`. The outline stays correct without the
component knowing where it lives.

The mistake at this level is the component that hard-codes `h3` because it
looked right on the first page that used it. The fix is the prop, with a
sensible default, and the audit script in the build to catch the page where
the default is wrong.

</Level>
<Level name="Advanced" depth={3}>

At the advanced level you know the exact rules underneath. Every element has
an **implicit ARIA role** defined by the HTML-to-ARIA mapping: `button` is
button, `a` *with* `href` is link (without `href` it is generic), `header`
is banner only when it is scoped to the body, `section` is region only when
it has an accessible name. The **accessible name** is computed by a defined
algorithm that checks `aria-labelledby`, then `aria-label`, then native
labelling (a `label` element, an image's `alt`, a table's `caption`), then
the content, then `title`.

A worked example of why this matters: an icon-only button with an SVG and no
text has no name, so a reader says "button" and nothing else. Adding
`aria-label="Close"` gives it a name. Adding `title="Close"` also gives it a
name, but only as the last resort, and the tooltip is unreliable on touch.
Visible text, visually hidden if necessary, is the most robust choice.

The mistake at this level is adding ARIA on top of an element that already
has the semantics, such as `role="button"` on a `button` or
`role="navigation"` on a `nav`. It is redundant at best. At worst,
`role="presentation"` on a meaningful element removes its meaning. The first
rule of ARIA is to not use it when a native element does the job.

</Level>
<Level name="Edge cases" depth={3}>

Single boundaries, each with what happens:

- **A page with no visible title.** A dashboard opens on a grid of widgets.
  There is no `h1`, so the outline starts at `h2`. Fix: a visually hidden
  `h1` naming the screen, using a "visually hidden" class that keeps it in
  the accessibility tree, not `display: none`, which removes it.
- **A link with no `href`.** `a` without `href` has no link role and is not
  focusable. It is a placeholder, not a link. If it is meant to act, it is a
  button; if it is meant to go somewhere, give it the address.
- **An empty heading.** A heading with an icon and no text appears in the
  heading list as an empty entry. Give the icon an accessible name or put
  text in the heading.
- **A table used for layout.** A reader announces rows and columns that
  mean nothing. Use CSS grid for layout, and keep tables for tabular data.

</Level>
<Level name="Corner cases" depth={3}>

Two boundaries at once:

- **A modal dialog on a page with `main`.** The dialog is outside `main`, so
  the landmark list does not include it, and focus has to be moved into it
  by script. A native `dialog` element opened with `showModal()` makes the
  rest of the page inert, which handles both: the reader cannot wander out,
  and focus is managed.
- **A repeated `nav` that is also hidden on mobile.** The mobile menu and
  the desktop menu are two `nav` elements, one hidden with CSS at each
  width. Hidden with `display: none`, the hidden one leaves the tree and
  there is only one landmark at a time, which is fine. Hidden by moving it
  off-screen, both stay in the tree, the reader hears two navigations, and
  one of them cannot be seen.
- **A client-side route change inside an `h1`-per-page app.** Old page and
  new page both have an `h1`. If the new one is rendered before the old one
  is removed, there are briefly two, and a focus move to "the `h1`" may land
  on the wrong one. Render, then move focus once the old content is gone.

</Level>
<Level name="Production level" depth={3}>

In production, structure has to survive many authors, many components and
many deploys. Three things keep it alive.

First, **checks on the built output**. This site's build check counts `h1`
elements on every page, resolves every internal link, and requires a
canonical URL, a title and a description. A failing check blocks the
deploy, so a regression never ships quietly.

Second, **a layout that owns the landmarks**. When every page goes through
one or two layouts, the landmarks are written once and reviewed once. A page
that needs a different shell gets a new layout, not a second `main` inside
the old one.

Third, **browser audits on the pages that matter most**: the home page, a
typical article, a form. Run Axe or Lighthouse in CI against a preview
deploy and fail on new violations. The mistake here is gating on a total
score, which hides a new failure behind an unrelated improvement. Gate on
"no new violations of these rules" instead.

</Level>
<Level name="Mindset" depth={3}>

The mindset this note teaches is that **markup is an interface**, and the
browser is its most important consumer. Everyone who does not see the screen
the way I do, whether a screen reader, a crawler, a voice assistant, a
reader mode or a translation tool, gets my page through that interface.

The habit that comes from it reaches beyond HTML. When I design a function,
a component or an API, I ask what it *means* before what it *looks like*.
A function named for its effect is easier to call correctly than one named
for its implementation, for the same reason a `button` is easier to use
correctly than a `div`.

The mistake in mindset is treating accessibility as a separate pass done at
the end by someone else. Done that way, it is expensive, because the
structure has to be undone. Done from the first tag, it costs nothing.

</Level>
<Level name="System design" depth={3}>

At the system level, semantic structure is a cross-cutting concern, like
logging or security. It needs an owner, a place in the architecture, and a
check.

Take this site as the concrete system. Content lives in Markdown and MDX
collections. Layouts (`BaseLayout`, `PostLayout`, `ChapterLayout`) own the
document shell, the landmarks and the one `h1`. Content files are forbidden
from writing an `h1`. Components that render headings take their level from
the place they are used. A build script checks the output. Each layer has
one job, and the structure rule sits at the layer that can enforce it.

The mistake at this level is spreading responsibility so thinly that no
layer owns it: the CMS lets writers choose any heading, components hard-code
levels, and the layout adds its own. The fix is to write down which layer
owns which part of the structure and to check it at the end of the pipeline.

</Level>
<Level name="Strategy" depth={3}>

How I learn this and how I know I have. I start by auditing pages I did not
write: open a site I use daily, list its headings and landmarks in the
browser's accessibility panel, and write down what is wrong. Then I do the
same to my own pages. The mistakes I find in other people's pages train my
eye for my own.

Then I build the audit script from this note and run it against my built
site. Next I turn on a screen reader (VoiceOver on a Mac, NVDA on Windows)
and navigate one page using only the landmark and heading keys. Hearing a
missing label is more convincing than reading about it.

Done when: every page on my site passes the script, I can name the implicit
role of the ten most common elements without looking, and I can navigate my
own note page by landmarks and headings to any section in under five
keypresses.

</Level>
</Levels>

## Questions people ask

**Is one `h1` per page a rule or a preference?** It is a convention, and the
build check on this site enforces it. WCAG requires headings that describe
their content and a structure a program can read; it does not count `h1`
elements. One `h1` is the simplest way to meet that, and it forces the page
to have one clear subject.

**Should every section be a `section` element?** No. A `section` without an
accessible name is just a generic grouping, and with a name it becomes a
region landmark. Use `section` when the content has a heading and is a real
part of the document; use `div` for styling wrappers.

**Do I still need ARIA?** Sometimes: for widgets HTML has no element for,
such as tabs, tree views and comboboxes, and for labelling, such as
`aria-label` on a second `nav`. Reach for a native element first and ARIA
second.

**Does semantic HTML help SEO?** It helps crawlers understand the page's
structure and follow its links. Headings tell a crawler what each part is
about. It is not a ranking trick; it is making the page legible to a
machine.

**What about `b` and `strong`, `i` and `em`?** `strong` and `em` carry
emphasis that some screen readers can convey; `b` and `i` are for styling
conventions without extra importance. Choose by meaning, as with everything
else here.

## Key takeaways

- The element you choose decides the role, name and states in the
  accessibility tree.
- Choose by what a thing does, then style it to look right.
- A thing that navigates is a link; a thing that acts on this page is a
  button.
- Use five to eight landmarks: one `main`, and a label on every repeated
  role.
- One `h1` names the page; headings go down one level at a time and up
  freely.
- Never pick a heading level for its size; CSS sets the size.
- Check the built HTML on every build, and do a real keyboard and screen
  reader pass for what a script cannot see.

## Glossary

- **Semantic element**: an element whose name carries meaning the browser
  exposes, such as `button` or `nav`.
- **Accessibility tree**: the tree of roles, names and states the browser
  builds from the DOM for assistive technology.
- **Role**: what a node is, such as button, link, heading or navigation.
- **Accessible name**: what a node is called, computed from labels, content
  and attributes.
- **State**: a changeable property such as pressed, expanded or disabled.
- **Landmark**: a page region a screen reader can list and jump to.
- **Banner, navigation, main, complementary, content info**: the landmark
  roles of `header`, `nav`, `main`, `aside` and `footer`.
- **Heading outline**: the tree the headings form, from the `h1` down.
- **Skip link**: a link at the top of the page that jumps to `main`.
- **ARIA**: attributes that add or change roles, names and states when
  native HTML cannot.
- **Visually hidden**: CSS that hides content from sight but keeps it in
  the accessibility tree.

## Practice

**Warm-up.** Take one page you wrote and list its headings and landmarks by
hand from the source. Mark every skipped level, every unlabelled repeated
`nav`, and every `div` that has a click handler.

**Build.** Copy the audit function from this note, point it at every HTML
file in your `dist/` folder, and make it exit with a non-zero code when it
finds a problem. Add it to your build. Then extend it to flag `a` elements
without `href` and `img` elements without `alt`.

**Stretch.** Turn on a screen reader and navigate your page using only the
landmark and heading keys. Write down the three places where what you hear
does not match what you see, and fix each one with the most native element
you can.
