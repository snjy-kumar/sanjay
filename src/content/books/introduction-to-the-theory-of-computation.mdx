## Why this book

This is the optional depth for phase 9 of the
<a href={withBase('/plans/traditional-software-developer/')}>traditional core</a>, theory
and compilers. *Crafting Interpreters* shows how a language becomes a
machine; this book shows what any machine can and cannot do. The plan's
phase-9 gate asks me to explain why the halting problem is undecidable and
what "hard" means; this is the book that makes those explanations exact.

It is a proof book. There is no code in it. My job is to turn each
definition into something I can run, and each proof into something I can
explain to a developer without the notation.

## How I would learn it

I would read Sipser the way I read a specification: slowly, with a pen,
one definition at a time. For every definition I write a small program
that makes it concrete, because I trust what I can run: an automaton
simulator, a grammar, a Turing machine simulator, a verifier. For every
proof I write a three-sentence version in plain language and check it
against the book. If I cannot write that version, I have not understood
the proof yet. When a proof does not land on first read, the MIT 18.404J
lectures are the second voice, and I do the exercises that have published
solutions first, to calibrate.

I would not try to finish the book in phase 9. Chapters 1, 2, 4, 5 and 7
are the ones the gate needs. The rest stays on the shelf until a later
problem makes me want them, which, with distributed systems next, will
happen sooner than I expect.

## Before the parts

### 0. Introduction

**Covers:** Automata, computability and complexity as three questions; the
mathematical vocabulary (sets, sequences, functions, relations, graphs,
strings, languages, boolean logic); definitions, theorems and proofs; and
three kinds of proof: construction, contradiction and induction.

<Levels label="Chapter 0, Introduction">
<Level name="Beginner">

A *language* in this book is just a set of strings. "Is this string in the
set?" is the question every machine in the book answers.

</Level>
<Level name="Intermediate">

Problems become languages: "is this number prime?" becomes "is this string
in the set of encodings of primes?". That encoding step is what lets one
theory cover parsing, graphs and arithmetic.

</Level>
<Level name="Advanced">

A proof by construction builds the object; contradiction assumes the
opposite and derives nonsense; induction proves a base case and a step.
Every later proof in the book is one of these three, often nested.

</Level>
<Level name="Edge cases">

The empty string is not the empty language. A language containing only
the empty string has one member; the empty language has none.

</Level>
<Level name="Corner cases">

Infinite sets of different sizes: the set of all strings is countable,
the set of all languages is not. That gap is why undecidable problems
must exist, before any specific one is found.

</Level>
<Level name="Production level">

A precise definition of the input set is the start of every good parser,
validator and API schema. "What exactly is a valid input?" is chapter 0's
question in production clothes.

</Level>
<Level name="Mindset">

Definitions first. Most confusion in this book is skipping a definition
and guessing.

</Level>
<Level name="System design">

Encoding problems as membership questions is how type checkers, query
validators and schema validators are specified: a set of accepted inputs.

</Level>
<Level name="Strategy">

This overlaps with phase 2. I would skim it, redo the induction proofs
from memory, and move on in a day. Done when I can write three induction proofs from memory and say what a language is in one sentence.

</Level>
</Levels>

## Part One: Automata and Languages

### 1. Regular Languages

**Covers:** Finite automata and their formal definition, designing automata, the
regular operations, nondeterminism and the equivalence of NFAs and DFAs,
closure under union, concatenation and star, regular expressions and
their equivalence with automata, and nonregular languages with the
pumping lemma.

```ts
// A DFA for binary strings with an even number of 1s.
type State = 'even' | 'odd';
const delta: Record<State, Record<'0' | '1', State>> = {
  even: { '0': 'even', '1': 'odd' },
  odd: { '0': 'odd', '1': 'even' },
};
const accepts = (s: string) =>
  [...s].reduce<State>((q, c) => delta[q][c as '0' | '1'], 'even') === 'even';
```

          0                 0
        ┌───┐             ┌───┐
        v   │      1      v   │
   ──> (even) ──────────> (odd)
       ((acc))  <──────────
                    1
`} caption="Two states are enough: the machine remembers only parity." />

<Levels label="Chapter 1, Regular Languages">
<Level name="Beginner">

A finite automaton reads a string one symbol at a time, moving between a
fixed number of states. If it ends in an accepting state, the string is
in the language.

</Level>
<Level name="Intermediate">

An NFA may have several possible next states and empty moves; it accepts
if *any* path accepts. Every NFA can be converted to a DFA by tracking the
set of states it could be in (the subset construction).

</Level>
<Level name="Advanced">

Regular expressions, NFAs and DFAs describe exactly the same languages.
Thompson's construction turns a regex into an NFA; that is how I will
build the phase-9 regex engine.

</Level>
<Level name="Edge cases">

The subset construction can blow up: an NFA with n states may need up to
2^n DFA states. "Strings whose fifth-last symbol is 1" is the standard
example.

</Level>
<Level name="Corner cases">

Balanced parentheses are not regular: the pumping lemma shows any long
enough string can be pumped out of balance. A regex cannot validate
nesting, which is why parsing HTML with a regex fails.

</Level>
<Level name="Production level">

Most real "regex" engines (backtracking ones in JavaScript, Python, Java)
add backreferences and are no longer finite automata. They can take
exponential time on patterns like `(a+)+$`, which is catastrophic
backtracking, a real denial-of-service bug. Automaton-based engines (RE2,
Rust's `regex`) guarantee linear time by refusing those features.

</Level>
<Level name="Mindset">

A finite machine has finite memory. If a problem needs to count without
bound, no regex will do.

</Level>
<Level name="System design">

Lexers, protocol state machines, input validation and UI states are all
finite automata. Drawing the states first prevents impossible states in
code.

</Level>
<Level name="Strategy">

Build a regex engine in TypeScript: parse the regex, Thompson-construct an
NFA, simulate it with a set of states. Then time it against
`RegExp` on `(a+)+$` with a long non-matching input. Done when my regex engine passes its tests and the timing against `RegExp` on a pathological pattern is in my log.

</Level>
</Levels>

### 2. Context-Free Languages

**Covers:** Context-free grammars, designing them, ambiguity, Chomsky normal form,
pushdown automata and their equivalence with grammars, the pumping lemma
for context-free languages, and (new in the third edition) deterministic
context-free languages, DPDAs and LR(k) parsing.

```text
E → E + T | T
T → T * F | F
F → ( E ) | num
```

<Levels label="Chapter 2, Context-Free Languages">
<Level name="Beginner">

A grammar is a set of rewrite rules. Starting from the start symbol and
applying rules produces every string in the language. Programming
languages are mostly described this way.

</Level>
<Level name="Intermediate">

A pushdown automaton is a finite automaton with a stack. The stack is
exactly the memory needed for nesting, so PDAs recognise the same
languages grammars generate.

</Level>
<Level name="Advanced">

Ambiguity is a property of the grammar, not the language: the same
language can have an ambiguous and an unambiguous grammar. Some languages
are inherently ambiguous and have no unambiguous grammar at all.

</Level>
<Level name="Edge cases">

Deciding whether an arbitrary grammar is ambiguous is undecidable. Parser
generators report conflicts for the grammars they cannot handle instead.

</Level>
<Level name="Corner cases">

`a^n b^n c^n` is not context-free: one stack cannot match three counts.
Real languages have context-sensitive rules (declare before use, types)
that are checked after parsing, not by the grammar.

</Level>
<Level name="Production level">

Deterministic context-free languages are what LR parsers handle in linear
time. Recursive descent handles the LL subset; Pratt parsing handles
operator precedence without rewriting the grammar.

</Level>
<Level name="Mindset">

The grammar is the specification of syntax. When a parser and a grammar
disagree, the grammar is the source of truth.

</Level>
<Level name="System design">

Splitting syntax (context-free, the parser) from semantics
(context-sensitive, later passes) is the reason compilers have a resolver
and a type checker separate from the parser.

</Level>
<Level name="Strategy">

Take the grammar above, show the two parse trees an ambiguous version
produces for `1 + 2 * 3`, then write the recursive-descent parser that
follows the unambiguous one. Done when I can show both parse trees of an ambiguous expression and my parser follows the unambiguous grammar.

</Level>
</Levels>

## Part Two: Computability Theory

### 3. The Church–Turing Thesis

**Covers:** Turing machines and their formal definition, examples, variants
(multitape, nondeterministic, enumerators) and their equivalence, Hilbert's
problems, and the definition of an algorithm.

<Compare left="Machine" right="Memory it has" rows={[["DFA / NFA", "a fixed number of states"], ["Pushdown automaton", "states plus one stack"], ["Turing machine", "states plus an unbounded read/write tape"], ["Real computer", "a very large but finite tape, which is why it behaves like a Turing machine for practical purposes"]]} caption="The book's hierarchy of machines, by memory." />

<Levels label="Chapter 3, The Church–Turing Thesis">
<Level name="Beginner">

A Turing machine has a tape it can read, write and move along in both
directions. It can accept, reject, or run forever.

</Level>
<Level name="Intermediate">

Adding tapes or nondeterminism does not let a Turing machine solve more
problems, only (sometimes) solve them faster. Robustness to these changes
is evidence the model captures "computation".

</Level>
<Level name="Advanced">

The Church–Turing thesis is not a theorem: it is the claim that the
informal idea of an algorithm equals what a Turing machine can do. Every
reasonable model found since agrees.

</Level>
<Level name="Edge cases">

A recogniser may loop forever on strings not in the language; a decider
always halts. The difference between them is the whole of chapter 4.

</Level>
<Level name="Corner cases">

Simulating a nondeterministic machine deterministically requires
breadth-first search of its branches; depth-first could follow an
infinite branch and never find an accepting one.

</Level>
<Level name="Production level">

"Turing complete" shows up in surprising places: SQL with recursive CTEs,
TypeScript's type system, CSS with HTML input, spreadsheet formulas. It
means "can loop forever", which is why type checkers and query engines add
depth limits.

</Level>
<Level name="Mindset">

Models are tools. The Turing machine is not how computers work; it is the
simplest thing that computes everything they can.

</Level>
<Level name="System design">

Choosing a deliberately non-Turing-complete language (configuration
formats, regular expressions, Datalog, eBPF's verifier-constrained
programs) buys guaranteed termination.

</Level>
<Level name="Strategy">

Write a Turing machine simulator in TypeScript and a machine that
recognises `a^n b^n`. Then find one type-level TypeScript example that
hits the compiler's recursion limit, and explain why the limit exists. Done when my Turing machine simulator accepts exactly the strings of the form a^n b^n in my tests.

</Level>
</Levels>

### 4. Decidability

**Covers:** Decidable problems about regular and context-free languages, the
diagonalisation method, the undecidability of the acceptance problem for
Turing machines, and a language that is not even Turing-recognisable.

```ts
// The shape of the halting argument, as code that cannot exist.
declare function halts(program: string, input: string): boolean; // suppose it existed
function paradox(program: string) {
  if (halts(program, program)) { while (true) {} } // loop if it would halt
  return; // halt if it would loop
}
// paradox(source of paradox) halts exactly when it does not. So `halts` cannot exist.
```

<Levels label="Chapter 4, Decidability">
<Level name="Beginner">

A problem is decidable if some program always answers it correctly and
always halts. "Does this DFA accept this string?" is decidable: run it.

</Level>
<Level name="Intermediate">

"Does this Turing machine accept this input?" is not decidable. The proof
assumes a decider exists and builds a machine that does the opposite of
whatever the decider predicts about it.

</Level>
<Level name="Advanced">

That is diagonalisation, the same idea that proves the real numbers are
uncountable: list every candidate, then construct something that differs
from each one somewhere.

</Level>
<Level name="Edge cases">

Acceptance is *recognisable* (simulate and wait), just not decidable. Its
complement is not even recognisable; that is the book's example of a
language beyond every Turing machine.

</Level>
<Level name="Corner cases">

Emptiness is decidable for context-free grammars but equality of two
context-free grammars is not. Similar-sounding questions land on
different sides of the line.

</Level>
<Level name="Production level">

Every static analyser, linter and type checker is either incomplete
(misses some bugs) or unsound (reports some false bugs) or both. It is a
consequence of this chapter, not a lack of effort by the tool authors.

</Level>
<Level name="Mindset">

"Can a tool always detect X?" Before building it, ask if X is a property of
what a program *does*. If so, the answer is no, and the design must
choose its approximation.

</Level>
<Level name="System design">

Timeouts are the engineering answer to undecidability: since I cannot know
if a job will finish, I bound how long I wait. Phase 10 builds on exactly
this.

</Level>
<Level name="Strategy">

Explain the halting proof to someone in three sentences without notation,
then write it in my study log. That explanation is a phase-9 gate item. Done when I can explain the halting proof in three plain sentences, closed-book.

</Level>
</Levels>

### 5. Reducibility

**Covers:** Undecidable problems from language theory, reductions via computation
histories, the Post Correspondence Problem as a simple undecidable
problem, and mapping reducibility with computable functions.

<Flow steps={["Known hard problem A", "Computable translation f", "Problem B", "If B were solvable, A would be too", "So B is unsolvable"]} caption="The direction of a reduction: from the known hard problem to the new one." />

<Levels label="Chapter 5, Reducibility">
<Level name="Beginner">

To show a new problem is unsolvable, show that solving it would let me
solve one already known to be unsolvable.

</Level>
<Level name="Intermediate">

A mapping reduction is a computable function that turns instances of A
into instances of B with the same answer. If A reduces to B, B is at
least as hard as A.

</Level>
<Level name="Advanced">

Computation histories, the full sequence of a machine's configurations,
let undecidability spread to problems that look nothing like machines,
such as tile-matching puzzles (PCP) and grammar questions.

</Level>
<Level name="Edge cases">

The direction matters. Reducing a new problem *to* a hard one proves
nothing about the new problem's hardness.

</Level>
<Level name="Corner cases">

Rice's theorem (in the problems) generalises everything: any nontrivial
property of the language a program recognises is undecidable. "Does this
function ever return null?" is one.

</Level>
<Level name="Production level">

Reductions are how engineers argue about difficulty too: "this feature is
as hard as general cache invalidation" is an informal reduction that ends
a design debate faster than any benchmark.

</Level>
<Level name="Mindset">

Hardness transfers. Recognising a known-hard problem in disguise saves
weeks.

</Level>
<Level name="System design">

Reductions in the other direction are how I reuse solvers: turn
scheduling into SAT, dependency resolution into SAT, routing into
shortest paths.

</Level>
<Level name="Strategy">

Write out one reduction in plain words with the direction arrow drawn,
and check the direction with someone else's explanation. Done when I can write one reduction with the direction stated correctly and explain why the direction matters.

</Level>
</Levels>

### 6. Advanced Topics in Computability Theory

**Covers:** The recursion theorem and self-reference, decidability of logical
theories (one decidable, one not), Turing reducibility, and a definition
of information through minimal description length.

<Levels label="Chapter 6, Advanced Topics in Computability Theory">
<Level name="Beginner">

A program can obtain its own source code. A quine, a program that prints
itself, is the friendly version of that fact.

</Level>
<Level name="Intermediate">

The recursion theorem makes "a machine that refers to itself" a legal
construction, which shortens many undecidability proofs.

</Level>
<Level name="Advanced">

Some logical theories are decidable (arithmetic with only addition) and
some are not (arithmetic with addition and multiplication). Expressive
power and decidability trade off.

</Level>
<Level name="Edge cases">

Turing reducibility allows asking an oracle many questions, which is
weaker as a hardness tool than a single mapping.

</Level>
<Level name="Corner cases">

Kolmogorov complexity, the length of the shortest description of a
string, is itself uncomputable. "Most compressible" has no algorithm.

</Level>
<Level name="Production level">

SMT solvers used for verification work in decidable fragments of logic
for exactly this reason. Staying inside them is a design constraint.

</Level>
<Level name="Mindset">

More expressive is not always better. A less powerful language can come
with guarantees.

</Level>
<Level name="System design">

Self-reference is behind bootstrapped compilers and the "trusting trust"
attack, where a compiler inserts a backdoor into its own future builds.

</Level>
<Level name="Strategy">

Optional for the phase. I would write a quine in JavaScript, read 6.1,
and leave 6.2–6.4 for later. Done when I have written a working quine and can say in a sentence what the recursion theorem allows.

</Level>
</Levels>

## Part Three: Complexity Theory

### 7. Time Complexity

**Covers:** Measuring complexity, big-O and small-o, analysing algorithms and model
dependence, the class P with examples, the class NP and verifiers,
P versus NP, NP-completeness, polynomial-time reductions, the Cook–Levin
theorem, and further NP-complete problems such as vertex cover,
Hamiltonian path and subset sum.

```ts
// NP in one function: checking a certificate is fast, even if finding one is not.
function verifySubsetSum(nums: number[], target: number, pickIdx: number[]): boolean {
  return new Set(pickIdx).size === pickIdx.length &&
    pickIdx.every((i) => i >= 0 && i < nums.length) &&
    pickIdx.reduce((s, i) => s + nums[i], 0) === target;
}
```

<Levels label="Chapter 7, Time Complexity">
<Level name="Beginner">

P is the set of problems solvable in polynomial time. NP is the set whose
"yes" answers can be *checked* in polynomial time given a hint, called a
certificate.

</Level>
<Level name="Intermediate">

NP-complete problems are the hardest in NP: every NP problem reduces to
each of them. SAT was first (Cook–Levin); others follow by reduction.

</Level>
<Level name="Advanced">

P versus NP asks whether checking is fundamentally easier than finding.
Nobody knows. Almost everyone believes P ≠ NP, and much of cryptography
relies on related assumptions.

</Level>
<Level name="Edge cases">

Subset sum is NP-complete but has a pseudo-polynomial dynamic program:
fast when the numbers are small. Size of the input means number of
*bits*, not the magnitude of the numbers.

</Level>
<Level name="Corner cases">

NP-hard does not mean every instance is hard. SAT solvers routinely solve
industrial instances with millions of variables, and fail on small
crafted ones.

</Level>
<Level name="Production level">

When I recognise an NP-complete problem in a feature (scheduling, packing,
routing with constraints), I stop looking for an exact fast algorithm and
choose: a heuristic, an approximation, a solver, or a smaller problem.

</Level>
<Level name="Mindset">

"Hard" has a precise meaning. Use it precisely, and do not call a problem
NP-hard without a reduction.

</Level>
<Level name="System design">

Package managers solve dependency resolution, which is NP-complete in
general. Lockfiles exist partly so the hard search runs once.

</Level>
<Level name="Strategy">

Write the subset-sum verifier above, a brute-force solver and the
pseudo-polynomial DP. Time all three as the input grows and plot the
numbers in my log. Done when the verifier, brute force and DP for subset sum are timed and plotted, and I can define NP-complete exactly.

</Level>
</Levels>

### 8. Space Complexity

**Covers:** Savitch's theorem, the class PSPACE, PSPACE-completeness (TQBF and
generalised games), the classes L and NL, NL-completeness, and NL equal
to coNL.

<Levels label="Chapter 8, Space Complexity">
<Level name="Beginner">

Space complexity counts memory instead of steps. Memory can be reused;
time cannot, so space is the more forgiving resource.

</Level>
<Level name="Intermediate">

PSPACE contains NP: a polynomial-space machine can try every certificate
one after another, reusing the same memory.

</Level>
<Level name="Advanced">

Savitch's theorem shows nondeterminism helps less for space than it seems
to for time: nondeterministic space s can be simulated in space s².

</Level>
<Level name="Edge cases">

Logarithmic space (L) means the machine can hold a few pointers into the
input but not a copy of it. Graph reachability in directed graphs is the
NL-complete example.

</Level>
<Level name="Corner cases">

Optimal play in generalised games (like a generalised geography game) is
PSPACE-complete, which is why perfect play in many games is out of reach
even though each position is small.

</Level>
<Level name="Production level">

Streaming algorithms are log-space thinking in practice: process data
larger than memory with a few counters, sketches or pointers.

</Level>
<Level name="Mindset">

Ask "how much do I need to remember?" as often as "how many steps?".

</Level>
<Level name="System design">

Memory budgets, not CPU, are often the binding constraint in databases
and stream processors. Space-efficient algorithms decide what fits on one
machine.

</Level>
<Level name="Strategy">

Optional. I would read 8.1–8.3 for PSPACE and leave L and NL until a
project needs them. Done when I can explain why NP is inside PSPACE without notes.

</Level>
</Levels>

### 9. Intractability

**Covers:** Hierarchy theorems for time and space, exponential-space completeness,
relativisation and the limits of diagonalisation, and circuit complexity.

<Levels label="Chapter 9, Intractability">
<Level name="Beginner">

Some problems are provably not in P: given more time, a machine can
always solve strictly more problems. That is the time hierarchy theorem.

</Level>
<Level name="Intermediate">

The hierarchy theorems use diagonalisation again, now with a budget: build
a machine that differs from every machine running within the smaller
budget.

</Level>
<Level name="Advanced">

Relativisation shows diagonalisation alone cannot settle P versus NP,
because there are oracle worlds where P equals NP and others where it
does not.

</Level>
<Level name="Edge cases">

Problems proven to need exponential time are natural, not contrived: the
book's example is equivalence of certain regular expressions with
exponentiation.

</Level>
<Level name="Corner cases">

Circuit complexity measures the size of a boolean circuit per input
length. A family of small circuits can exist without any uniform
algorithm producing them.

</Level>
<Level name="Production level">

Knowing a problem is provably intractable ends the search for a clever
exact algorithm. The work shifts to restricting inputs.

</Level>
<Level name="Mindset">

Proof techniques have limits too. Knowing why a method fails is part of
knowing the method.

</Level>
<Level name="System design">

Circuit models connect to hardware from phase 5 and to how
cryptographers reason about attackers with fixed resources.

</Level>
<Level name="Strategy">

Optional. Read 9.1 for the hierarchy theorem and its proof idea; skim the
rest. Done when I can state the time hierarchy theorem and its diagonal idea in plain words.

</Level>
</Levels>

### 10. Advanced Topics in Complexity Theory

**Covers:** Approximation algorithms, probabilistic algorithms and the class BPP
(with primality testing as the example), alternation, interactive proof
systems, parallel computation, and cryptography (one-way functions and
trapdoor functions).

<Levels label="Chapter 10, Advanced Topics in Complexity Theory">
<Level name="Beginner">

When the exact answer is too expensive, settle for an approximately
optimal one with a guarantee, or a randomised algorithm that is right with
high probability.

</Level>
<Level name="Intermediate">

BPP is the class of problems solvable in polynomial time by a randomised
algorithm with bounded error. Repeating the algorithm drives the error
down exponentially.

</Level>
<Level name="Advanced">

Interactive proofs let a weak verifier be convinced by a powerful prover;
they are the ancestors of zero-knowledge proofs.

</Level>
<Level name="Edge cases">

Approximation guarantees differ wildly: vertex cover has a simple
2-approximation; some NP-hard problems cannot be approximated within any
constant factor unless P = NP.

</Level>
<Level name="Corner cases">

Cryptography needs problems that are hard *on average*, not just in the
worst case. NP-hardness alone does not give a secure scheme.

</Level>
<Level name="Production level">

Randomised primality testing (Miller–Rabin) is what real RSA key
generation uses, which ties back to phase 2's number theory and forward to
phase 11's cryptography.

</Level>
<Level name="Mindset">

Probability is an engineering tool. An error rate of 2^-128 is not
"maybe wrong", it is more reliable than the hardware.

</Level>
<Level name="System design">

Parallel complexity (NC) asks which problems speed up with more
processors. Some problems are inherently sequential, which caps what
adding machines can do.

</Level>
<Level name="Strategy">

Implement Miller–Rabin in TypeScript with `bigint`, test it against known
primes and Carmichael numbers, and connect it to my phase 2 RSA demo. Done when Miller–Rabin passes against known primes and Carmichael numbers in my tests.

</Level>
</Levels>

## Misreadings to avoid

- **"Undecidable means very hard."** No. It means no algorithm exists at
  all, however slow.
- **"NP means not polynomial."** It means nondeterministic polynomial:
  verifiable in polynomial time.
- **"My regex engine is a finite automaton."** Only if it has no
  backreferences and does not backtrack.
- **"Turing complete is a feature."** For a config language or a type
  system, it is usually a liability.
- **"NP-hard problems cannot be solved in practice."** Many instances can;
  the guarantee is about the worst case.

## Done with this book when

- I can explain, without notation, why the halting problem is undecidable and what NP-complete means: the phase 9 gate.
- I can convert a regular expression to an NFA and an NFA to a DFA, and my regex engine passes its tests.
- I can show a language is not regular, and find and remove an ambiguity in a grammar.
- I can write a mapping reduction in the right direction and say what Rice's theorem rules out.
- I can explain why checking a certificate is easier than finding one, with my timed subset-sum experiment as evidence.
