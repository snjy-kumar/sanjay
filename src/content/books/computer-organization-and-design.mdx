## Why this book

This is the depth book for <a href={withBase('/plans/traditional-software-developer/#strategy-5')}>phase 5, computer architecture and C</a>.
<a href={withBase('/books/computer-systems-a-programmers-perspective/')}>Computer Systems: A Programmer's Perspective</a>
is the primary book and explains the machine from the programmer's side.
Patterson and Hennessy explain it from the designer's side: how an
instruction set is chosen, how a datapath is wired, how a pipeline and a
cache are built. I open it when CS:APP tells me what happens and I want to
know how.

The book comes in several editions for different instruction sets (MIPS,
ARM and RISC-V). I follow the RISC-V edition, second edition, because RISC-V
is small, open and clean enough to read in full. The publisher's contents
list gives the chapter and appendix titles, which this page follows. It does
not list sections, so the topics under each chapter are described from the
chapter's subject in my own words, not from a verified section list.

## How I would learn it

I read CS:APP's chapter on a topic first, then the matching chapter here.
The pairs are: CS:APP chapter 2 with chapter 3 here, CS:APP 3 with chapter 2,
CS:APP 4 with chapter 4, and CS:APP 6 and 9 with chapter 5. Appendix A comes
before chapter 4, because a datapath makes no sense until gates and
flip-flops do.

The book's own examples are RISC-V assembly, and I would write and run them
in a RISC-V simulator rather than read them. I would also use the free
Nand2Tetris course that the plan names alongside: building gates, an ALU and
a small CPU in its hardware language is the hands-on version of appendix A
and chapter 4.

For each chapter I would answer the in-chapter self-check questions before
reading on, and draw the datapath or the cache by hand before trusting my
understanding of it.

## The chapters

### 1. Computer Abstractions and Technology

**Covers:** The layers from applications down to hardware, the parts of a computer, how
chips are made, how performance is defined and measured, the power wall,
the switch from single processors to multiprocessors, and the fallacies and
pitfalls around performance numbers.

<Levels label="Chapter 1, Computer Abstractions and Technology">

<Level name="Beginner">


A computer is input, output, memory, a datapath and control. Software layers
(applications, system software, the instruction set) sit on top of it, and
each hides the one below.


</Level>
<Level name="Intermediate">


CPU time is instructions times cycles per instruction (CPI) times seconds per
cycle. A change that lowers one can raise another: a compiler may emit fewer
instructions that each take more cycles.

```text
CPU time = instruction count × CPI × clock period
         = 2e9 instructions × 1.5 cycles × (1 / 3e9 Hz) = 1.0 s
```


</Level>
<Level name="Advanced">


Dynamic power grows with capacitance, the square of voltage, and frequency.
When voltage could no longer drop, clock speeds stopped climbing around the
mid-2000s, and the industry turned to multiple cores. Amdahl's law limits
what more cores give.


</Level>
<Level name="Edge cases">


- MIPS (millions of instructions per second) as a metric: a machine can run
  more instructions per second and still finish later.


</Level>
<Level name="Corner cases">


- A benchmark that fits in cache on one machine and not on another:
  "faster processor" and "faster for my workload" disagree.


</Level>
<Level name="Production level">


Benchmarks need a fixed workload, repeated runs and a stated metric. A
single "it feels faster" run of a Node script means nothing.


</Level>
<Level name="Mindset">


Performance is a product of terms. Ask which term a change moves.


</Level>
<Level name="System design">


The power wall is why servers scale out instead of up, and why cloud pricing
is per core.


</Level>
<Level name="Strategy">


Compute CPU time for three made-up machines and rank them, then measure
instruction count and cycles for a C loop with `perf stat`. Done when I can
derive CPI from the measured numbers.

</Level>

</Levels>

### 2. Instructions: Language of the Computer

**Covers:** The RISC-V instruction set: operations and operands, registers, memory
operands and immediates, signed and unsigned numbers, how instructions are
encoded, logical operations, decisions and loops, procedures and the stack,
characters and strings, addressing for wide immediates and branches, how
C compiles, links and loads into RISC-V, and a comparison with other
instruction sets.

<Levels label="Chapter 2, Instructions: Language of the Computer">

<Level name="Beginner">


An instruction set is the contract between software and hardware. RISC-V
has 32 integer registers, `x0` to `x31`, with `x0` always zero. Arithmetic
works on registers; only loads and stores touch memory.

```asm
# a[i] = b + c, with a in x10, i in x11, b in x12, c in x13
add  x5, x12, x13       # t = b + c
slli x6, x11, 3         # offset = i * 8
add  x6, x10, x6        # address = a + offset
sd   x5, 0(x6)          # store the doubleword
```


</Level>
<Level name="Intermediate">


Every instruction is 32 bits, in a few fixed formats (register, immediate,
store, branch, upper immediate, jump), so the fields line up and decoding is
simple. Branches compare two registers and jump relative to the program
counter.


</Level>
<Level name="Advanced">


Procedure calls follow a convention: arguments in `a0` to `a7`, the return
address in `ra`, saved registers the callee must preserve, and a stack
pointer in `sp`. Large constants take two instructions (`lui` then `addi`).
The design principles are simplicity, regularity and making the common case
fast.


</Level>
<Level name="Edge cases">


- `x0` swallows writes: `add x0, x1, x2` does nothing, which is how a
  no-op is encoded.
- Immediates are 12 bits and sign-extended, so a constant like 2048 does not
  fit in one `addi`.


</Level>
<Level name="Corner cases">


- Loading a 32-bit constant whose low 12 bits have the top bit set: `addi`
  sign-extends, so `lui` must be given the upper part plus one. Assemblers
  do this for `li`; hand-written code gets it wrong.


</Level>
<Level name="Production level">


Reading compiler output for an ISA is a debugging skill, and RISC-V's is the
cleanest to start with. WebAssembly is also a small, regular instruction set
that compilers target, with similar design choices.


</Level>
<Level name="Mindset">


An instruction set is an API. Small and regular beats clever.


</Level>
<Level name="System design">


The ISA is a stable boundary: hardware can change completely underneath it,
and software keeps running, the same reason public APIs are versioned.


</Level>
<Level name="Strategy">


Hand-compile three small C functions (a sum loop, string length, a recursive
factorial) to RISC-V, run them in a simulator, and compare with `gcc -O1`
for a RISC-V target. Done when my calling convention matches the compiler's.

</Level>

</Levels>

### 3. Arithmetic for Computers

**Covers:** Addition and subtraction with overflow, multiplication, division, floating
point (IEEE 754, its formats, addition and multiplication, rounding),
subword parallelism, and the fallacies around computer arithmetic.

<Levels label="Chapter 3, Arithmetic for Computers">

<Level name="Beginner">


Hardware adds binary numbers with chains of full adders. Subtraction is
adding the two's complement. Overflow is a result too big for the word.


</Level>
<Level name="Intermediate">


Multiplication is repeated shift-and-add; faster multipliers add the partial
products in a tree. Division is repeated shift-and-subtract. RISC-V does not
trap on integer overflow: software has to check, with an extra branch.


</Level>
<Level name="Advanced">


Floating point is sign, exponent with a bias, and fraction with an implied
leading 1. Adding two floats means aligning exponents, adding, normalising
and rounding, with guard and round bits to round correctly. Subword
parallelism (SIMD) splits a wide register into lanes to add many small
numbers at once.


</Level>
<Level name="Edge cases">


- Denormals: tiny numbers lose the implied 1 and gradually lose precision,
  and some processors handle them much more slowly.
- Division by zero: a trap for integers on some machines, infinity for
  floats.


</Level>
<Level name="Corner cases">


- Adding a tiny float to a huge one: the tiny one is shifted away entirely,
  so `1e16 + 1 === 1e16` in JavaScript.
- `(a + b) + c` and `a + (b + c)` differ in floating point, so parallel sums
  are not reproducible without care.


</Level>
<Level name="Production level">


Overflow checks are a security property in size calculations. Numerical
code accumulates in higher precision or uses compensated (Kahan) summation.


</Level>
<Level name="Mindset">


Arithmetic in hardware is approximate and finite. Precision is something I
budget.


</Level>
<Level name="System design">


The same 64-bit floats move between JavaScript, JSON, databases and GPUs,
and each boundary can round or reject values.


</Level>
<Level name="Strategy">


Build a 4-bit adder in Nand2Tetris or on paper, then write a float-adding
function in C on the raw bits and compare it with the hardware. Done when
mine agrees on random inputs, including signs and rounding.

</Level>

</Levels>

### 4. The Processor

**Covers:** Logic design conventions, building a datapath, a simple implementation of
RISC-V, an overview of pipelining, a pipelined datapath and its control,
data hazards with forwarding and stalls, control hazards and branch
prediction, exceptions, parallelism through instructions, and real
processors. The online companion adds a multicycle implementation.

<Levels label="Chapter 4, The Processor">

<Level name="Beginner">


A processor is a datapath (registers, an ALU, memories, the program counter)
and control that tells it what to do for each instruction. A single-cycle
version does one instruction per long clock cycle.


<Figure caption="A single-cycle datapath, simplified. Control picks the multiplexer inputs." art={`
  +----+   +--------+   +-----------+   +-----+   +--------+
  | PC |-->| instr  |-->| registers |-->| ALU |-->|  data  |
  +----+   | memory |   +-----------+   +-----+   | memory |
     ^     +--------+         ^                    +--------+
     |                        |                        |
     +---- PC + 4 or branch   +------ write back ------+
`} />


</Level>
<Level name="Intermediate">


Pipelining splits the datapath into five stages (fetch, decode, execute,
memory, write back) with registers between them, so each stage works on a
different instruction. The clock gets faster; each instruction still takes
five steps.


</Level>
<Level name="Advanced">


Forwarding sends an ALU result straight to the next instruction's input. A
load followed by a use still needs a one-cycle stall. Branches are
predicted; a dynamic predictor learns each branch's history, and a wrong
guess flushes the instructions fetched after it. Multiple issue and
out-of-order execution find more parallelism among instructions.


</Level>
<Level name="Edge cases">


- A store followed by a load of the same address: the pipeline must not
  reorder them.
- An exception in the middle of the pipeline: earlier instructions finish,
  later ones are cancelled.


</Level>
<Level name="Corner cases">


- A branch that depends on a value just loaded: a load-use stall and a
  control hazard together, the costliest case in a simple pipeline.


</Level>
<Level name="Production level">


Branchy code on unpredictable data is slow: sorting the input first can
speed up a loop several times. Compilers turn branches into conditional
moves for this reason, and I can see it in the assembly.


</Level>
<Level name="Mindset">


Overlap work, then handle the dependencies that overlap creates. That is
pipelining, and it is also most concurrency design.


</Level>
<Level name="System design">


Speculation with rollback is the processor's version of optimistic
concurrency. Spectre showed that rolled-back speculation can still leak
through caches.


</Level>
<Level name="Strategy">


Build the Nand2Tetris CPU, then draw the five-stage pipeline for a short
RISC-V loop and mark every forward, stall and flush. Done when I can
predict the cycles for the loop and explain a branch-prediction benchmark
I ran in C.

</Level>

</Levels>

### 5. Large and Fast: Exploiting Memory Hierarchy

**Covers:** Locality, memory technologies (SRAM, DRAM, flash, disk), the basics of
caches, measuring and improving cache performance with associativity and
multilevel caches, dependable memory, virtual machines, virtual memory with
page tables and the TLB, a common framework for the hierarchy, controlling
a cache with a finite-state machine, cache coherence for multiprocessors,
and real memory hierarchies. The companion adds RAID and more on cache
controllers.

<Levels label="Chapter 5, Large and Fast: Exploiting Memory Hierarchy">

<Level name="Beginner">


Programs touch a small part of memory at a time, so a small fast cache
holding that part makes all of memory look fast. A hit is found in the
cache; a miss goes to the next level.


</Level>
<Level name="Intermediate">


Average memory access time is hit time plus miss rate times miss penalty.
Bigger lines exploit spatial locality but raise the miss penalty.
Associativity lowers conflict misses at the cost of a slower lookup.

```c
/* cache simulator core: decode an address into tag, set and offset */
uint64_t offset = addr & ((1u << b) - 1);
uint64_t set    = (addr >> b) & ((1u << s) - 1);
uint64_t tag    = addr >> (s + b);
```


</Level>
<Level name="Advanced">


Write-through sends every write to the next level (with a write buffer);
write-back writes a dirty line only when evicted. Virtual memory is the same
idea one level down, with pages as lines and disk as the next level, and the
TLB as a cache of the page table. Coherence protocols (such as MSI and its
relatives) keep each core's cached copy of a line consistent.


</Level>
<Level name="Edge cases">


- A cold cache at startup: every first access misses, so short benchmarks
  measure misses, not steady state.
- A virtually indexed cache and two virtual addresses for one physical page
  (aliasing).


</Level>
<Level name="Corner cases">


- Two cores writing different words in one line: coherence invalidates the
  line on every write, false sharing, and the program slows with no shared
  variable.


</Level>
<Level name="Production level">


Hit rate is the number that matters for every cache, from L1 to a CDN.
Error-correcting memory (dependable memory in this chapter) is why server
RAM is ECC.


</Level>
<Level name="Mindset">


One framework, where can a block go, how is it found, what is replaced, what
happens on a write, describes every cache I will ever meet.


</Level>
<Level name="System design">


The four questions apply directly to Redis, a CDN and a database buffer
pool, and coherence is the hardware version of cache invalidation across
servers.


</Level>
<Level name="Strategy">


Write the plan's cache simulator with configurable sets, lines and block
size, LRU replacement and write-back, and check it against cachegrind on the
matrix-multiply traces. Done when my simulator's miss counts match within a
few percent.

</Level>

</Levels>

### 6. Parallel Processors from Client to Cloud

**Covers:** Why parallel programming is hard, SISD, MIMD, SIMD, SPMD and vector
processing, hardware multithreading, multicore and shared memory, GPUs,
clusters and warehouse-scale computers, and the networks between processors,
with benchmarks and the roofline performance model.

<Levels label="Chapter 6, Parallel Processors from Client to Cloud">

<Level name="Beginner">


Since single cores stopped getting much faster, more speed comes from doing
things in parallel: several cores, wide vector units, GPUs, and many machines.


</Level>
<Level name="Intermediate">


Flynn's categories sort machines by instruction and data streams: one
instruction on many data (SIMD) is vectors and GPUs; many instructions on
many data (MIMD) is multicore. Shared-memory multicores need coherence and
synchronisation.


</Level>
<Level name="Advanced">


The roofline model plots attainable performance against arithmetic
intensity (operations per byte from memory): below the ridge a kernel is
memory-bound, above it compute-bound. Warehouse-scale computers treat a whole
data centre as one machine, where power and failures are design inputs.


</Level>
<Level name="Edge cases">


- One thread on a many-core machine: the speed-up is one, however many cores
  are there.


</Level>
<Level name="Corner cases">


- Strong scaling hits Amdahl's limit while weak scaling (a bigger problem
  per core) keeps going; a benchmark has to say which it measures.


</Level>
<Level name="Production level">


Most server workloads are memory- or I/O-bound, so more cores help less than
expected. The roofline tells me which kind of fix to look for.


</Level>
<Level name="Mindset">


Parallel speed-up is earned by removing dependencies and data movement, not
by adding hardware.


</Level>
<Level name="System design">


Warehouse-scale computing is the bridge to phase 10, distributed systems:
failure is normal, and the network is part of the computer.


</Level>
<Level name="Strategy">


Parallelise the matrix multiply with threads, measure the speed-up for 1 to
N cores, and plot it against a roofline for my machine. Done when I can say
whether the kernel is memory- or compute-bound and why.

</Level>

</Levels>

## The appendices

Appendix A, the basics of logic design, covers gates, truth tables,
combinational logic, multiplexers, an ALU, clocks, flip-flops, registers and
memory elements, finite-state machines and an introduction to hardware
description languages; it is the reading for the phase's "gates,
combinational and sequential logic" bullet, and I would do it alongside
Nand2Tetris. Appendix B is on graphics and computing GPUs, C on mapping
control to hardware, and D surveys other RISC architectures. B to D are for
looking things up, not part of phase 5.

## Misreadings to avoid

- "RISC-V is a niche choice, so this is not about real machines." The
  principles are the same on x86 and ARM; RISC-V just hides less.
- "Clock speed is performance." Instruction count and CPI matter as much.
- "Pipelining makes each instruction faster." It improves throughput; each
  instruction's latency stays about the same or grows.
- "Bigger caches are always better." Bigger means slower to search; levels
  exist because of that trade-off.
- "Parallel hardware means parallel speed-up." Dependencies and memory
  bandwidth decide it.
