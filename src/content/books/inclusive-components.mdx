## Why this book

Phase 2 of the <a href={withBase('/plans/software-ai-developer/')}>software AI developer</a> roadmap is the
frontend phase, and its gate starts with a main flow that works with the keyboard alone. I can build a toggle, a
menu or a modal that looks right. What I cannot yet do reliably is build one that works for someone using a screen
reader, a switch device, a zoomed screen or only a keyboard. This book takes twelve components every product needs
and builds each one so it works for everyone, explaining why each attribute is there.

It is short, practical and opinionated: it usually starts with the simplest HTML that works and adds ARIA and
script only when they earn their place. That fits the phase, which also asks for a documented, tested
design-system component. Each chapter here is a candidate for that component.

## How I would learn it

I read one chapter, then build the component from an empty file without looking, then test it four ways: keyboard
only, with VoiceOver or NVDA, at 400% zoom, and with an automated checker (axe). Whatever I got wrong goes into a
`notes.md` next to the component. Then I write the component a second time in my phase 2 app's framework and
add tests with Testing Library queries by role, so the tests fail if the accessibility breaks.

Every chapter below climbs the same nine levels: what it is, how it combines, what happens underneath, the edges,
the corners where two edges meet, what changes in production, the habit of thought, where it sits in a larger
system, and how I would learn it and know I have. The output for a component is often what the accessibility tree
or a screen reader exposes, so that is what I show; exact announcements vary between screen readers.

## What I learn from it

- When to use a native element, and when ARIA is needed and which roles, states and properties.
- Toggle buttons with `aria-pressed`, and when a switch or a checkbox is the better choice.
- Dynamic lists: headings, labelling, empty states and focus after adding or deleting.
- The difference between true application menus and navigation, and building a menu button.
- Tooltips that describe and toggletips that reveal, without hiding content on hover.
- Theme switching that respects `prefers-color-scheme` and keeps contrast.
- Tabs, collapsible sections and sliders built by progressive enhancement from plain content.
- Live regions for notifications, and why they must exist before the message is inserted.
- Data tables with captions, header scope, sorting state and responsive overflow.
- Modal dialogs: focus moved in, trapped, returned, with Escape and an inert background.
- Cards with one primary link and a whole-card click area that does not break text selection.

## The chapters

### 1. Toggle Buttons

**Covers:** Changing state versus changing label, `aria-pressed`, the switch role, checkbox-based toggles, labelling, and toggles that change what other content shows.

<Compare left="Toggle button" right="Switch" rows={[
  ['button with aria-pressed', 'button with role="switch" and aria-checked'],
  ['announced as pressed or not pressed', 'announced as on or off'],
  ['label stays the same', 'label stays the same'],
  ['fits a setting inside a toolbar', 'fits a settings list'],
]} caption="Two honest ways to expose an on and off state. Changing the label instead is the dishonest third way." />

<Levels label="Chapter 1, Toggle Buttons">

<Level name="Beginner">

A toggle button has a fixed label and a state. `aria-pressed` exposes the state, and a real `button` brings keyboard
support for free.

```html
<button type="button" aria-pressed="false">Notify by email</button>
<script>
  const b = document.querySelector("[aria-pressed]");
  b.addEventListener("click", () => b.setAttribute("aria-pressed", String(b.getAttribute("aria-pressed") !== "true")));
</script>
```

```
accessibility tree: button "Notify by email", toggle, not pressed
after a click:      button "Notify by email", toggle, pressed
```

Mistake: a `div` with a click handler, which is not focusable and has no role. Fix: a `button`.

</Level>

<Level name="Intermediate">

Style from the state, not from a separate class, so the visual and the accessible state cannot drift apart.

```css
[aria-pressed="true"] { background: #000; color: #fff; }
[aria-pressed="true"]::after { content: " (on)"; }
```

Mistake: toggling the label between "Mute" and "Unmute" while also setting `aria-pressed`, so a screen reader hears
"Unmute, pressed", which means the opposite. Fix: change the label or the state, never both.

</Level>

<Level name="Advanced">

The checkbox alternative: an `input type="checkbox"` styled as a switch keeps form submission, label clicking and the
checked state with no script at all. A `role="switch"` on a button gives on and off semantics with
`aria-checked`.

```html
<label><input type="checkbox" role="switch" checked> Dark mode</label>
```

```
accessibility tree: switch "Dark mode", on
```

</Level>

<Level name="Edge cases">

A toggle with only an icon has no accessible name. Fix: visually hidden text or `aria-label`, and never a name that
describes the icon ("speaker") rather than the action ("Mute").

```
axe: Buttons must have discernible text (button-name)
```

</Level>

<Level name="Corner cases">

A toggle that also shows and hides a panel needs `aria-expanded` and `aria-controls`, not `aria-pressed`. Using both on
one button gives two conflicting states. Fix: decide whether the button sets a setting (pressed) or reveals content
(expanded), and use only that one.

</Level>

<Level name="Production level">

In a design system the toggle is a component with a fixed label prop and a `pressed` prop, and the tests query it by
role and state.

```js
const b = screen.getByRole("button", { name: "Notify by email", pressed: false });
await user.click(b);
expect(screen.getByRole("button", { name: "Notify by email", pressed: true })).toBeTruthy();
```

</Level>

<Level name="Mindset">

Accessible state is a contract with people I cannot see. If the visual state and the announced state can disagree,
one day they will.

</Level>

<Level name="System design">

Settings toggles often save to a server. The button shows the new state at once (optimistic), the request goes out,
and on failure the state reverts with an announced error. The state machine is the same for every user.

</Level>

<Level name="Strategy">

I build the button, switch and checkbox versions and test each with a screen reader. Done when my component's tests
query by role and pressed state and fail if `aria-pressed` is removed.

</Level>

</Levels>

### 2. A Todo List

**Covers:** Headings and list structure, labelling the add field, adding items, empty states, deleting items and managing focus afterwards, and announcing changes.

<Flow steps={['type a task', 'press Enter or Add', 'item appended to the list', 'announce "added"', 'field cleared, focus stays in the field']} caption="Adding an item. Each step has a keyboard and a screen-reader version, and the focus never gets lost." />

<Levels label="Chapter 2, A Todo List">

<Level name="Beginner">

A todo list is a heading, a real list and a labelled form. Native elements do most of the work.

```html
<h2 id="todos-label">My todo list</h2>
<ul aria-labelledby="todos-label"></ul>
<form>
  <label for="add-todo">Add a todo item</label>
  <input id="add-todo" type="text">
  <button>Add</button>
</form>
```

```
accessibility tree: list "My todo list", 0 items
```

Mistake: a placeholder instead of a label, which disappears on typing and is often not read. Fix: a `label`.

</Level>

<Level name="Intermediate">

Each item is a checkbox with a label and a delete button whose name includes the item, so a list of "Delete"
buttons is distinguishable.

```html
<li>
  <input type="checkbox" id="todo-1"><label for="todo-1">Pick up kids</label>
  <button aria-label="delete Pick up kids">Delete</button>
</li>
```

Mistake: ten buttons all named "Delete". Fix: put the item's text into each delete button's accessible name.

</Level>

<Level name="Advanced">

Deleting removes the focused button, so focus falls back to `body` and keyboard users lose their place. The fix is to
move focus somewhere meaningful, such as the list heading made focusable with `tabindex="-1"`.

```js
function remove(li) {
  li.remove();
  heading.focus(); // heading has tabindex="-1"
  status.textContent = "Pick up kids deleted";
}
```

</Level>

<Level name="Edge cases">

The empty state: an empty `ul` is announced as an empty list or not at all. Fix: show a message of my own, such as "Nothing to do yet, add your first task
above", in a `p` when the list is empty, and keep the list
element present for structure.

</Level>

<Level name="Corner cases">

Adding an empty or whitespace-only item. With `required`, the browser shows a native error; with script validation, the
error must be tied to the field and announced.

```html
<input id="add-todo" required aria-describedby="add-error">
<p id="add-error" role="status"></p>
```

Fix: trim the value and reject it with a visible, announced message, without moving focus away from the field.

</Level>

<Level name="Production level">

In production the list is long and synced. I would announce additions and deletions through one polite live region,
debounce announcements when bulk actions run, and keep the item ID stable so focus can return to the right row after
a re-render.

</Level>

<Level name="Mindset">

Every action that removes something removes it from under someone's focus. I always ask "where is focus now?"

</Level>

<Level name="System design">

The todo list is the CRUD screen in miniature. Every admin table, comment thread and cart in my apps has the same
add, label, delete and focus problems, so solving it once in a shared component solves it everywhere.

</Level>

<Level name="Strategy">

I build it with keyboard-only testing first, then add the live region. Done when I can add, check and delete three items
with only the keyboard and a screen reader, and always know where focus is.

</Level>

</Levels>

### 3. Menus & Menu Buttons

**Covers:** The difference between navigation and true menus, the ARIA menu role and its keyboard expectations, menu buttons with `aria-haspopup` and `aria-expanded`, choosing an item, and closing the menu.

<Compare left="Navigation" right="Application menu" rows={[
  ['nav with a list of links', 'role="menu" with role="menuitem"'],
  ['Tab moves between links', 'arrow keys move, Tab leaves'],
  ['links go to pages', 'items perform actions'],
  ['what most websites need', 'what desktop-style apps need'],
]} caption="The chapter's main point: most 'menus' on websites are navigation, and should not use the menu role." />

<Levels label="Chapter 3, Menus & Menu Buttons">

<Level name="Beginner">

Site navigation is a `nav` with a list of links. It needs no ARIA.

```html
<nav aria-label="Main">
  <ul><li><a href="/">Home</a></li><li><a href="/about/">About</a></li></ul>
</nav>
```

```
accessibility tree: navigation "Main", list 2 items, link "Home", link "About"
```

Mistake: adding `role="menu"` to navigation, which tells screen readers to expect arrow-key behaviour that is not
there. Fix: no menu role on navigation.

</Level>

<Level name="Intermediate">

A disclosure for a navigation submenu: a button with `aria-expanded` shows and hides a list of links.

```html
<button aria-expanded="false" aria-controls="products">Products</button>
<ul id="products" hidden>...</ul>
```

Mistake: opening on hover only, so keyboard and touch users never reach it. Fix: open on click and keep hover as an
enhancement.

</Level>

<Level name="Advanced">

A true menu button (`aria-haspopup="true"`) opens a `role="menu"`. The keyboard contract: Enter or Space or Down opens
and focuses the first item; arrows move; Escape closes and returns focus to the button; choosing an item closes the
menu.

```js
menu.addEventListener("keydown", (e) => {
  const items = [...menu.querySelectorAll('[role="menuitem"]')];
  const i = items.indexOf(document.activeElement);
  if (e.key === "ArrowDown") items[(i + 1) % items.length].focus();
  if (e.key === "ArrowUp") items[(i - 1 + items.length) % items.length].focus();
  if (e.key === "Escape") { close(); button.focus(); }
});
```

</Level>

<Level name="Edge cases">

Clicking outside the menu, or tabbing out of it, must close it. Without that, an open menu covers content and keeps
`aria-expanded="true"` while invisible to the user.

Fix: close on `focusout` when the new focus is outside the menu, and on a click outside it.

</Level>

<Level name="Corner cases">

A menu inside a scrolling container near the bottom of the screen: opening it below cuts it off, and focus moves to an
item the user cannot see. Fix: position it to fit the viewport (flip upward), and scroll the focused item into view.

</Level>

<Level name="Production level">

Menus in a design system come with a documented keyboard contract and tests for each key. Choosing an item should
announce the result ("Sorted by date"), and the button should show the current choice in its accessible name.

</Level>

<Level name="Mindset">

ARIA roles are promises about behaviour. If I use the menu role, I owe the arrow keys.

</Level>

<Level name="System design">

A shared menu component is one of the highest-leverage pieces of a design system: one correct implementation, used
by dozens of screens, removes a whole class of accessibility bugs from the product.

</Level>

<Level name="Strategy">

I build a navigation disclosure and a true menu button and write keyboard tests for both. Done when the menu passes
every key in its contract and the navigation uses no menu roles at all.

</Level>

</Levels>

### 4. Tooltips & Toggletips

**Covers:** What tooltips are for, labelling versus describing, `aria-describedby`, inclusive hover and focus behaviour, toggletips that reveal information on click, and live regions for the toggletip content.

<Compare left="Tooltip" right="Toggletip" rows={[
  ['shows on hover and focus', 'shows on click'],
  ['adds a short description to a control', 'is a button that reveals information'],
  ['aria-describedby or aria-labelledby', 'live region content inserted on click'],
  ['never interactive content', 'can be dismissed with Escape'],
]} caption="A tooltip describes something else; a toggletip is the thing the user clicks to learn more." />

<Levels label="Chapter 4, Tooltips & Toggletips">

<Level name="Beginner">

A tooltip is a short label or description for a control, shown on hover and on focus.

```html
<button aria-describedby="notify-tip">Notify</button>
<div role="tooltip" id="notify-tip">Notifications will be sent by email</div>
```

```
accessibility tree: button "Notify", description "Notifications will be sent by email"
```

Mistake: a tooltip on hover only, so keyboard users never see it. Fix: show it on focus too.

</Level>

<Level name="Intermediate">

For an icon-only button, the tooltip is the label, so `aria-labelledby` points at it. Then the visible tooltip and the
accessible name are the same text.

Mistake: both `aria-label` and a tooltip with different text. Fix: one source of truth, the tooltip, referenced by
`aria-labelledby`.

</Level>

<Level name="Advanced">

A toggletip is a button (often an "i" icon) that inserts its information into a live region when clicked, so the
screen reader announces it.

```html
<button type="button" aria-label="more info" data-toggletip-content="This clears your history">i</button>
<span role="status"></span>
```

```js
btn.addEventListener("click", () => {
  status.textContent = "";
  setTimeout(() => { status.textContent = btn.dataset.toggletipContent; }, 100);
});
```

The empty-then-fill makes repeat clicks announce again.

</Level>

<Level name="Edge cases">

Escape must dismiss a tooltip without moving focus, and a tooltip must stay visible while the pointer moves onto it,
so zoomed-in users can read it. Those are the WCAG 1.4.13 rules for content on hover or focus.

</Level>

<Level name="Corner cases">

Putting a link or a button inside a tooltip: it disappears when focus leaves the trigger, so the link cannot be
reached. Fix: interactive content goes in a toggletip or a dialog, never in a tooltip.

</Level>

<Level name="Production level">

In production, tooltips should be rare. Every one is a sign the interface might need a clearer label. The component
should handle placement, Escape, hover persistence and touch (where hover does not exist).

</Level>

<Level name="Mindset">

If the information matters, it should be visible, not hidden behind a hover.

</Level>

<Level name="System design">

Help text is content. In a large product it belongs in the same localisation and content system as the rest of the
interface, not hard-coded in a tooltip prop.

</Level>

<Level name="Strategy">

I build a tooltip and a toggletip and test both by keyboard, screen reader and touch. Done when every tooltip in my app
is reachable by focus, dismissible with Escape, and contains no interactive content.

</Level>

</Levels>

### 5. A Theme Switcher

**Covers:** Offering a dark theme, inverting colours with a CSS filter and its pitfalls, respecting `prefers-color-scheme`, a switch for the theme, persisting the choice, and keeping images and contrast right.

<Flow steps={['read saved choice', 'else read prefers-color-scheme', 'set data-theme on html before paint', 'user toggles switch', 'save choice and update']} caption="Choosing a theme. The saved choice beats the system preference, and the theme is applied before the first paint." />

<Levels label="Chapter 5, A Theme Switcher">

<Level name="Beginner">

A theme switcher is a switch that changes a whole page's colour scheme. The simplest version uses CSS custom
properties and one attribute on `html`.

```css
:root { --bg: #fff; --fg: #111; }
[data-theme="dark"] { --bg: #111; --fg: #eee; }
body { background: var(--bg); color: var(--fg); }
```

Mistake: hard-coded colours scattered through the CSS, so the dark theme misses half the page. Fix: every colour
through a custom property.

</Level>

<Level name="Intermediate">

The control is a switch, and the system preference is the default.

```html
<button role="switch" aria-checked="false" id="dark">Dark theme</button>
```

```js
const prefersDark = matchMedia("(prefers-color-scheme: dark)").matches;
const saved = localStorage.getItem("theme");
const dark = saved ? saved === "dark" : prefersDark;
document.documentElement.dataset.theme = dark ? "dark" : "light";
```

```
accessibility tree: switch "Dark theme", on (when the system is dark)
```

</Level>

<Level name="Advanced">

The chapter's quick trick is `filter: invert(100%)` on the root, with images and videos inverted back. It works with
almost no CSS, but it inverts brand colours and shadows too, so a token-based theme is the robust version.

```css
:root[data-theme="dark"] { filter: invert(100%) hue-rotate(180deg); }
:root[data-theme="dark"] img, :root[data-theme="dark"] video { filter: invert(100%) hue-rotate(180deg); }
```

Mistake: forgetting the images, so photos look like negatives. Fix: invert them back, or use the token approach.

</Level>

<Level name="Edge cases">

The flash of the wrong theme: a script at the end of `body` sets the theme after the first paint, so dark-mode users
see a white flash. Fix: a tiny inline script in `head` that sets `data-theme` before anything renders.

</Level>

<Level name="Corner cases">

The user's saved choice conflicts with a later system change: they chose light, then switched the OS to dark at night.
Should the page follow? Fix: offer three states (light, dark, system), store "system" as its own choice, and listen to
the media query's `change` event only in that state.

</Level>

<Level name="Production level">

Both themes need contrast checking (4.5:1 for body text), `color-scheme: light dark` so form controls and scrollbars
match, and visual regression tests for both. `forced-colors` mode (Windows high contrast) must still work, so
information is never carried by background colour alone.

</Level>

<Level name="Mindset">

A theme is an accessibility feature before it is a style. Some users need dark, some need light, and some need the
system to decide.

</Level>

<Level name="System design">

In a design system, themes are a layer of tokens (semantic names like `--surface` and `--text`) mapped to raw values per
theme. Components only use semantic tokens, so a new theme is a new mapping, not a rewrite.

</Level>

<Level name="Strategy">

I build the filter version, then the token version, and compare them. Done when my app has light, dark and system
themes with no flash, passes contrast in both, and works in forced-colors mode.

</Level>

</Levels>

### 6. Tabbed Interfaces

**Covers:** When tabs are appropriate, progressive enhancement from a table of contents and sections, the `tablist`, `tab` and `tabpanel` roles, arrow-key navigation, the roving tabindex, and focus on the panel.

<Figure art={`
  without script:                   with script:
  +---------------------------+     +---------+---------+---------+
  | - Section 1 (link)        |     | [Tab 1] |  Tab 2  |  Tab 3  |  tablist
  | - Section 2 (link)        |     +---------+---------+---------+
  | - Section 3 (link)        |     |                             |
  +---------------------------+     |  panel 1 (tabpanel)         |
  | Section 1 heading + text  |     |  Tab enters the panel,      |
  | Section 2 heading + text  |     |  arrows move between tabs   |
  | Section 3 heading + text  |     +-----------------------------+
`} caption="Progressive enhancement: a working page of linked sections becomes tabs only when the script runs." />

<Levels label="Chapter 6, Tabbed Interfaces">

<Level name="Beginner">

Start with content that works without script: a list of links to sections on the same page.

```html
<ul><li><a href="#section1">Section 1</a></li><li><a href="#section2">Section 2</a></li></ul>
<section id="section1"><h2>Section 1</h2>...</section>
<section id="section2"><h2>Section 2</h2>...</section>
```

Mistake: building tabs whose content is invisible when the script fails. Fix: the base HTML must be complete.

</Level>

<Level name="Intermediate">

The script adds roles and hides inactive panels.

```js
ul.setAttribute("role", "tablist");
links.forEach((a, i) => {
  a.setAttribute("role", "tab");
  a.setAttribute("aria-selected", String(i === 0));
  a.tabIndex = i === 0 ? 0 : -1;
  panels[i].setAttribute("role", "tabpanel");
  panels[i].hidden = i !== 0;
});
```

```
accessibility tree: tablist, tab "Section 1" selected 1 of 2, tab "Section 2" 2 of 2
```

</Level>

<Level name="Advanced">

The roving tabindex: only the selected tab is in the tab order. Left and Right move between tabs, and Tab moves into
the panel, so a keyboard user does not have to tab through every tab.

```js
tablist.addEventListener("keydown", (e) => {
  const i = tabs.indexOf(document.activeElement);
  const next = e.key === "ArrowRight" ? i + 1 : e.key === "ArrowLeft" ? i - 1 : null;
  if (next === null) return;
  switchTab(tabs[(next + tabs.length) % tabs.length]);
});
```

Mistake: every tab with `tabindex="0"`. Fix: roving tabindex.

</Level>

<Level name="Edge cases">

A panel with no focusable content: Tab skips it and jumps past the whole component. Fix: `tabindex="0"` on the panel
(or `-1` and focus it from the tab with Down), so its content can be reached and read.

</Level>

<Level name="Corner cases">

A deep link to `#section3` when the page loads with tabs enabled: the hash points at a hidden panel, so nothing
appears to happen. Fix: on load, if the hash matches a panel, select that tab, and update the hash on switching
without jumping the scroll.

</Level>

<Level name="Production level">

On small screens, tabs often become an accordion. In production I would keep one data model and render either, with
the same tests by role. Tabs whose panels load data need a loading state announced inside the panel.

</Level>

<Level name="Mindset">

Not everything that looks like tabs should be tabs. If the content is long or people need to compare sections, a
plain page with headings is better.

</Level>

<Level name="System design">

Tabs are a view-switching pattern. In an app, routes often do the same job better, because they give each view a URL,
history and a page title.

</Level>

<Level name="Strategy">

I build the progressive tabs and test them with and without script. Done when the tabs pass the keyboard contract, the
deep link opens the right tab, and the page still works with script disabled.

</Level>

</Levels>

### 7. Collapsible Sections

**Covers:** Disclosure buttons inside headings, `aria-expanded`, hiding with `hidden`, progressive enhancement, a reusable web component version, and the native `details` element.

<Flow steps={['heading with a button inside', 'button aria-expanded="false"', 'click or Enter or Space', 'aria-expanded="true", content hidden removed', 'heading structure unchanged']} caption="A collapsible section keeps the heading as a heading and puts the button inside it." />

<Levels label="Chapter 7, Collapsible Sections">

<Level name="Beginner">

The pattern: a button inside the heading toggles the content after it.

```html
<h2><button aria-expanded="false">My section</button></h2>
<div hidden>
  <p>Content</p>
</div>
```

```
accessibility tree: heading level 2, button "My section", collapsed
```

Mistake: a clickable heading with no button, which is not focusable and not announced as interactive. Fix: a
`button` inside the heading.

</Level>

<Level name="Intermediate">

The script flips the state and the content's `hidden` together.

```js
btn.addEventListener("click", () => {
  const expanded = btn.getAttribute("aria-expanded") === "true";
  btn.setAttribute("aria-expanded", String(!expanded));
  content.hidden = expanded;
});
```

Mistake: a button that wraps the heading, which removes heading semantics. Fix: heading outside, button inside.

</Level>

<Level name="Advanced">

The chapter wraps the pattern in a web component, so authors write plain headings and content and the component
adds the button and state. With shadow DOM, the light DOM content stays accessible through slots.

```html
<toggle-section open>
  <h2>My section</h2>
  <p>Content</p>
</toggle-section>
```

</Level>

<Level name="Edge cases">

The native `details` and `summary` elements give a disclosure with no script. Their limits: the `summary` cannot be a
heading in the document outline in every screen reader, and styling the marker needs `::marker` or
`list-style: none`.

</Level>

<Level name="Corner cases">

Find in page against hidden content: `hidden` content is not searchable, so a user searching for a word in a collapsed
section finds nothing. Fix: `hidden="until-found"` where supported, which reveals the section when the browser finds
a match, with a `beforematch` event to update `aria-expanded`.

</Level>

<Level name="Production level">

For long FAQ pages I would add "expand all", keep the state in the URL for sharing, and make sure printing expands
everything (`@media print`).

</Level>

<Level name="Mindset">

Hiding content is a cost to the user, not a free tidy-up. Collapse only what most people do not need.

</Level>

<Level name="System design">

Disclosure is the base of accordions, menus and navigation. One tested disclosure primitive in the design system can
power all of them.

</Level>

<Level name="Strategy">

I build the heading-button version, the web component and a `details` version, and compare them by screen reader.
Done when my component keeps the heading level and passes find-in-page.

</Level>

</Levels>

### 8. A Content Slider

**Covers:** Whether to have a slider at all, a scrollable list with scroll snapping, making it focusable and labelled, hiding off-screen slides from interaction, previous and next buttons, and no autoplay.

<Figure art={`
  region "Gallery" (tabindex=0, arrow keys scroll)
  +-----------------------------------------------------+
  | [ slide 1 visible ] [ slide 2 visible ] [ slide 3 ]  -> scroll-snap
  +-----------------------------------------------------+
            ^ interactive        ^ interactive   ^ inert until in view
  [ < previous ]                                 [ next > ]
`} caption="A slider as a scrollable, labelled region. Off-screen slides are not reachable by Tab until they scroll into view." />

<Levels label="Chapter 8, A Content Slider">

<Level name="Beginner">

The simplest slider is a list in a scrollable container. Browsers scroll it with touch, trackpad and keyboard.

```html
<section aria-label="Gallery" tabindex="0" class="slider">
  <ul><li><img src="1.jpg" alt="..."></li><li><img src="2.jpg" alt="..."></li></ul>
</section>
```

```css
.slider ul { display: flex; overflow-x: auto; scroll-snap-type: x mandatory; }
.slider li { scroll-snap-align: start; flex: 0 0 80%; }
```

Mistake: no `tabindex` on the scrolling region, so keyboard users cannot scroll it. Fix: `tabindex="0"` and a label.

</Level>

<Level name="Intermediate">

`IntersectionObserver` marks slides as visible or not, so links in off-screen slides are taken out of the tab order.

```js
const io = new IntersectionObserver((entries) => {
  for (const e of entries) e.target.inert = !e.isIntersecting;
}, { root: slider, threshold: 0.99 });
slides.forEach((s) => io.observe(s));
```

Mistake: Tab lands on a link in an off-screen slide and the slider jumps. Fix: `inert` on hidden slides.

</Level>

<Level name="Advanced">

Previous and next buttons scroll by one slide width with `scrollBy`, and are optional, because the region already
scrolls. With `scroll-behavior: smooth` they animate, except under `prefers-reduced-motion`.

```css
@media (prefers-reduced-motion: no-preference) { .slider ul { scroll-behavior: smooth; } }
```

</Level>

<Level name="Edge cases">

Autoplay. Content that moves on its own for more than five seconds needs a pause control (WCAG 2.2.2), and autoplay
moves content away from people who read slowly. Fix: no autoplay.

</Level>

<Level name="Corner cases">

Right-to-left languages: `scrollLeft` is negative or reversed depending on the browser, and "next" points left. Fix:
use logical properties, `scrollBy` with a sign from `getComputedStyle(slider).direction`, and test with
`dir="rtl"`.

</Level>

<Level name="Production level">

Every image needs real alt text, lazy loading (`loading="lazy"`) and fixed dimensions to avoid layout shift. Sliders on
a home page are often where Lighthouse and CLS fail; I measure before and after.

</Level>

<Level name="Mindset">

Before building a slider, ask whether a grid of the same items would serve people better. Usually it would.

</Level>

<Level name="System design">

A slider is a viewport over a list. The same model (a list, a window, lazy loading) is a virtualised list in a big
dashboard.

</Level>

<Level name="Strategy">

I build the scroll-snap slider with inert slides and test it by touch, keyboard and screen reader. Done when there is
no autoplay, no layout shift and no focus on an off-screen slide.

</Level>

</Levels>

### 9. Notifications

**Covers:** Live regions, `role="status"` and `role="alert"`, polite versus assertive, having the region in the page before inserting messages, toast messages, and when not to notify.

<Flow steps={['live region exists, empty', 'something happens', 'message text inserted', 'screen reader announces it', 'message stays readable or is cleared']} caption="A live region announces changes to its content, so it must already exist before the message arrives." />

<Levels label="Chapter 9, Notifications">

<Level name="Beginner">

A live region announces new text without moving focus.

```html
<div role="status" id="status"></div>
<script>document.querySelector("#status").textContent = "Saved";</script>
```

```
screen reader: "Saved" (polite, after the current speech)
```

Mistake: creating the live region and its message at the same moment, so nothing is announced. Fix: the empty region
is in the page from the start.

</Level>

<Level name="Intermediate">

`role="status"` is polite and waits; `role="alert"` is assertive and interrupts. Errors that block progress may justify
`alert`; everything else is `status`.

Mistake: every message as an alert, so the screen reader keeps cutting off what the user was reading. Fix: polite by
default.

</Level>

<Level name="Advanced">

Announcing the same message twice: setting the same text again does not change the DOM, so nothing is announced.

```js
function announce(msg) {
  status.textContent = "";
  requestAnimationFrame(() => { status.textContent = msg; });
}
```

`aria-atomic="true"` makes the whole region read when any part changes.

</Level>

<Level name="Edge cases">

Toasts that vanish after three seconds fail people who read slowly or use magnification. Fix: keep messages until
dismissed, or a long timeout that pauses on hover and focus, and a history somewhere the user can reread.

</Level>

<Level name="Corner cases">

A notification that contains an action ("Undo"): the live region announces the text, but the button is somewhere
focus is not. A keyboard user cannot reach it before it disappears. Fix: do not put the only path to an action in a
toast; offer undo where the action happened too, and do not auto-dismiss toasts with actions.

</Level>

<Level name="Production level">

One app-wide announcer (a polite and an assertive region, mounted once) avoids competing regions. Batch bursts of
updates ("3 messages received") rather than announcing each.

</Level>

<Level name="Mindset">

Every notification interrupts someone. I notify about what the user needs to know now, and nothing else.

</Level>

<Level name="System design">

The announcer is a shared service in the frontend architecture, like logging: components call `announce()` and never
touch live regions directly.

</Level>

<Level name="Strategy">

I build an announcer module and wire it to save, error and undo flows. Done when each is announced once, at the right
politeness, and no action is reachable only through a toast.

</Level>

</Levels>

### 10. Data Tables

**Covers:** Real table markup, captions, header cells and scope, sortable columns with `aria-sort`, buttons in headers, making a table responsive with a scrollable region, and the card layout for small screens.

<Figure art={`
  table, caption "Monthly sales"
  +--------------+----------------+-------------+
  | Product (th) | [Units v] (th) | Price (th)  |   column headers, scope="col"
  |              | aria-sort=desc |             |
  +--------------+----------------+-------------+
  | Lamp (th)    | 120            | 40          |   row header, scope="row"
  | Desk (th)    | 80             | 200         |
  +--------------+----------------+-------------+
`} caption="A data table's structure: a caption, column and row headers, and a sort button inside the sorted column's header." />

<Levels label="Chapter 10, Data Tables">

<Level name="Beginner">

Tabular data goes in a `table` with a `caption` and `th` cells, so screen readers can announce headers as the user
moves between cells.

```html
<table>
  <caption>Monthly sales</caption>
  <tr><th scope="col">Product</th><th scope="col">Units</th></tr>
  <tr><th scope="row">Lamp</th><td>120</td></tr>
</table>
```

```
screen reader in the Units column of Lamp: "Lamp, Units, 120"
```

Mistake: a grid of `div`s that looks like a table. Fix: a `table`.

</Level>

<Level name="Intermediate">

Sortable columns: a button inside the header, and `aria-sort` on the `th`.

```html
<th scope="col" aria-sort="descending"><button>Units</button></th>
```

Mistake: `aria-sort` on every column. Fix: only on the sorted one; the others have none.

</Level>

<Level name="Advanced">

A wide table on a small screen: wrap it in a scrollable, focusable, labelled region so keyboard users can scroll it.

```html
<div role="region" aria-labelledby="sales-caption" tabindex="0" style="overflow-x: auto">
  <table><caption id="sales-caption">Monthly sales</caption>...</table>
</div>
```

</Level>

<Level name="Edge cases">

`display: block` or `display: flex` on table elements can remove table semantics in some browsers, so CSS for a
responsive layout breaks the screen-reader experience. Fix: keep table display, or restore the roles
(`role="table"`, `role="row"`, `role="cell"`) explicitly.

</Level>

<Level name="Corner cases">

A sorted table that is also paginated and filtered: sorting changes the rows, the focus stays on the header button,
and the user hears nothing. Fix: announce "Sorted by units, descending, page 1 of 4" through the status region, and
sort on the server so page 1 means the same thing for everyone.

</Level>

<Level name="Production level">

Large tables need sticky headers, virtualisation and server-side sort and filter. Virtualisation removes rows from the
DOM, so `aria-rowcount` and `aria-rowindex` keep the position honest.

</Level>

<Level name="Mindset">

Tables are for data people compare across rows and columns. If no one compares, it is a list.

</Level>

<Level name="System design">

The table component is where frontend and API meet: sort, filter and page parameters become query strings and
indexes. I design those together, not separately.

</Level>

<Level name="Strategy">

I build a sortable, scrollable table and test it with a screen reader's table navigation. Done when headers are announced
in every cell, sorting is announced, and the table scrolls by keyboard at 320 pixels wide.

</Level>

</Levels>

### 11. Modal Dialogs

**Covers:** When to use a modal, the `dialog` role and `aria-modal`, moving focus into the dialog, trapping it, closing with Escape and the close button, returning focus, making the background inert, and the native `dialog` element.

<Flow steps={['trigger button clicked', 'background made inert', 'focus moved into the dialog', 'Tab stays inside, Escape closes', 'focus returned to the trigger']} caption="A modal dialog's focus life cycle. Getting in and getting back out are as important as what is inside." />

<Levels label="Chapter 11, Modal Dialogs">

<Level name="Beginner">

The native `dialog` element with `showModal()` handles focus, Escape and the inert background.

```html
<button id="open">Delete account</button>
<dialog id="confirm" aria-labelledby="confirm-title">
  <h2 id="confirm-title">Delete your account?</h2>
  <form method="dialog"><button value="cancel">Cancel</button><button value="ok">Delete</button></form>
</dialog>
<script>open.onclick = () => confirm.showModal();</script>
```

```
accessibility tree: dialog "Delete your account?", modal
```

Mistake: a `div` overlay with no role, no focus management and no Escape. Fix: `dialog` with `showModal`.

</Level>

<Level name="Intermediate">

Returning focus: when the dialog closes, focus goes back to the button that opened it, so keyboard users continue where
they were. Native `dialog` does this in current browsers; a custom dialog must store and restore `document.activeElement`.

Mistake: focus jumps to the top of the page after closing. Fix: restore it to the trigger.

</Level>

<Level name="Advanced">

A custom modal must trap focus: Tab from the last control goes to the first, and the rest of the page is `inert`.

```js
function openModal(dialog) {
  const trigger = document.activeElement;
  document.querySelector("main").inert = true;
  dialog.hidden = false;
  dialog.querySelector("[autofocus], button").focus();
  return () => { dialog.hidden = true; document.querySelector("main").inert = false; trigger.focus(); };
}
```

</Level>

<Level name="Edge cases">

A dialog taller than the screen at 200% zoom: if it is `position: fixed` with no scrolling, the bottom buttons are
unreachable. Fix: `max-height: 100vh` (or `100dvh`) and `overflow: auto` on the dialog.

</Level>

<Level name="Corner cases">

A dialog opened from inside another dialog, or a toast appearing while a modal is open: inert backgrounds and focus
restore must nest, or closing the inner dialog returns focus to an inert element. Fix: a stack of open dialogs, each
restoring the previous one's state.

</Level>

<Level name="Production level">

In production: confirmation dialogs focus the least destructive option, forms in dialogs keep their data if closed by
accident, and dialogs are never opened automatically on page load. Tests assert focus in, focus trap, Escape and focus
return.

</Level>

<Level name="Mindset">

A modal takes over someone's whole screen. It has to earn that, and it has to give the screen back exactly as it was.

</Level>

<Level name="System design">

Dialogs in a design system are one primitive (focus management, inert, Escape) with many skins: confirm, form, image
viewer. The primitive is tested once.

</Level>

<Level name="Strategy">

I build a native dialog and a custom one and test both with keyboard and screen reader. Done when focus goes in, stays in
and comes back, at every zoom level.

</Level>

</Levels>

### 12. Cards

**Covers:** Card content order and headings, one primary link, making the whole card clickable with a pseudo-element, keeping text selectable, secondary links in a card, and image alt text.

<Figure art={`
  article (card)
  +--------------------------------+
  | img (decorative or alt text)   |
  | h3 > a "Card title" ------------+--  a::after covers the whole card
  | p summary text                 |    (position: absolute; inset: 0)
  | small "by Author" (z-index up)  |    secondary links sit above it
  +--------------------------------+
`} caption="A whole-card click area made from the heading link, with secondary links raised above it." />

<Levels label="Chapter 12, Cards">

<Level name="Beginner">

A card is a small article: a heading with a link, a summary and maybe an image. The heading link is the card's
primary action.

```html
<article class="card">
  <img src="lamp.jpg" alt="">
  <h3><a href="/lamp/">Desk lamp</a></h3>
  <p>A warm light for late reading.</p>
</article>
```

```
accessibility tree: article, heading level 3, link "Desk lamp"
```

Mistake: wrapping the whole card in one `a`, so screen readers read every word in the card as the link name. Fix: link
the heading only.

</Level>

<Level name="Intermediate">

The whole card becomes clickable with a pseudo-element on the link that covers the card.

```css
.card { position: relative; }
.card h3 a::after { content: ""; position: absolute; inset: 0; }
```

Mistake: a JavaScript click handler on the card, which breaks middle click and open in new tab. Fix: the pseudo-element
trick, which keeps a real link.

</Level>

<Level name="Advanced">

Secondary links ("by Author") must sit above the pseudo-element with `position: relative; z-index: 1`, or the covering
link swallows their clicks.

</Level>

<Level name="Edge cases">

Text selection: with the covering pseudo-element, users cannot select the summary text to copy it. Fix: the chapter's
alternative, a click handler on the card that follows the link only if no text is selected, with the real link kept for
keyboards and screen readers.

```js
card.addEventListener("click", () => { if (!getSelection().toString()) link.click(); });
```

</Level>

<Level name="Corner cases">

An image placed before the heading in the source for visual order: screen-reader users meet an image with no context.
Fix: heading first in source order, image moved visually with flexbox `order` or grid placement. But a large visual
and source order mismatch breaks keyboard order, so keep it small.

</Level>

<Level name="Production level">

Card grids are long; each card needs the same heading level, so the page's outline stays sane. Focus styles must show
on the whole card (`:focus-within`), and images need fixed dimensions to avoid layout shift.

</Level>

<Level name="Mindset">

A card's markup should read well with no CSS at all. If it does, it will read well in every assistive technology.

</Level>

<Level name="System design">

Cards are the most-reused UI unit in a product: search results, feeds, dashboards. A single accessible card component
fixes all of them at once.

</Level>

<Level name="Strategy">

I build a card with a whole-card link, a secondary link and selectable text. Done when middle click works, text can be
selected, and a screen reader's links list shows one sensible link per card.

</Level>

</Levels>

## Misreadings to avoid

- "Add ARIA to make it accessible." Native elements first; ARIA only adds meaning, never behaviour.
- "Accessibility is for screen readers." Keyboard, zoom, motion, contrast and cognitive load matter as much.
- "Passing axe means accessible." Automated checks catch a fraction of issues; the keyboard and a screen reader catch
  the rest.
- "These are the only correct implementations." The book shows one good path for each, with reasons. The reasons are
  the lesson.
- "Progressive enhancement is old-fashioned." It is what keeps the tabs and sliders working when script fails.
