## Why this book

This is the first book of the <a href={withBase('/plans/traditional-software-developer/')}>traditional core</a>:
phase 1, programming from first principles. It is also the book behind the memory lens of the
<a href={withBase('/plans/underrated-fundamentals/')}>underrated fundamentals</a>. I write TypeScript every
day, and the runtime hides almost everything this book is about: where a value lives, how long it lives,
and what happens when I read past the end of it. C hides none of that.

King's book teaches C89 and C99 side by side, with programs and exercises in every chapter, and it is
the gentler of the two C books the plan names. Kernighan and Ritchie's book is the shorter reference I
keep next to it.

## How I would learn it

I would not read it cover to cover in one go. Phase 1 is three weeks (weeks 3 to 5), and its gate is a
command-line tool in C whose every allocation I can explain. So I read the chapters that tool needs first,
with a compiler open, and come back to the rest when a later phase asks for them.

My loop for each chapter: read it once quickly, type the book's programs instead of reading them, break
each one on purpose, then do the exercises I would get wrong. Everything builds with
`-std=c99 -Wall -Wextra -fsanitize=address,undefined`, because the sanitizers turn silent undefined
behaviour into a report I can read. When a chapter has a JavaScript or TypeScript twin, I write both and
compare what each language makes easy and what it hides, which is the point of the phase.

## Basic features of C

### 1. Introducing C

**Covers:** Where C came from, how it was standardised, and what it is good and bad at.


<Levels label="Chapter 1, Introducing C">

<Level name="Beginner">

C is a small, compiled language from the early 1970s, built to write Unix. The standards I care about are C89 and C99, which this edition covers. The smallest thing that works is not a program yet; it is knowing that C trusts me completely.

</Level>

<Level name="Intermediate">

The trade-offs come as a set: C is fast, portable and close to the machine, and it is terse, permissive and short on safety nets. Every later chapter is one of those strengths with its matching risk attached.

</Level>

<Level name="Advanced">

Portable means the same source compiles on many machines, not that it behaves the same on all of them. The standard leaves some behaviour implementation-defined (documented per compiler) and some undefined (anything may happen). Knowing which is which is most of what separates a C programmer from someone typing C.

</Level>

<Level name="Edge cases">

Code that looks finished can depend on things the standard does not promise: the size of an `int`, the sign of a plain `char`, the order arguments are evaluated in. It compiles cleanly and works on my laptop, which proves nothing.

</Level>

<Level name="Corner cases">

Two dialects meet: a C89-only compiler rejects a `//` comment or a declaration after a statement, both fine in C99. The same file is valid or invalid depending on a compiler flag, so I always pin `-std=c99` (or later) on purpose.

</Level>

<Level name="Production level">

In production, C is the language under everything I use: the kernel, the database, the JavaScript engine. The habit to take in is tooling from day one: warnings on (`-Wall -Wextra`), sanitizers in debug builds, and a fixed standard version.

</Level>

<Level name="Mindset">

C teaches me that the machine is not an abstraction I am protected from. Coming from TypeScript, the mindset shift is from "the runtime will catch it" to "I am the runtime".

</Level>

<Level name="System design">

Where C sits in a system: it is the layer other languages call into (Node add-ons, Python extensions, SQLite). Choosing C is choosing control over safety for one boundary, and keeping that boundary small.

</Level>

<Level name="Strategy">

I read this chapter fast, then set up the toolchain properly: one compiler, warnings as errors, AddressSanitizer on. I know I am done when I can explain undefined versus implementation-defined behaviour with one example of each.

</Level>

</Levels>

### 2. C Fundamentals

**Covers:** The shape of a program: directives, functions, statements, comments, variables, assignment, reading input, constants, identifiers and layout.


<Flow steps={['source.c', 'preprocessor', 'compiler', 'object file', 'linker', 'executable']} caption="From source to a running program: the preprocessor expands directives, the compiler makes object code, the linker joins it with the libraries." />

<Levels label="Chapter 2, C Fundamentals">

<Level name="Beginner">

A C program is preprocessing directives plus functions, and execution starts in `main`. The smallest program:

```c
#include <stdio.h>

int main(void) {
  printf("hello\n");
  return 0;
}
```

</Level>

<Level name="Intermediate">

Variables have a type and must be declared before use. Assignment copies a value. A macro like `#define FREEZING_PT 32.0f` is text substitution, not a variable. Compile, link and run are separate steps, and an error message tells me which step failed.

</Level>

<Level name="Advanced">

`return 0` from `main` is the exit status the shell sees. An uninitialised local variable holds whatever bits were there; reading it is undefined behaviour, not "zero". Identifiers are case-sensitive, and names starting with an underscore and a capital letter are reserved.

</Level>

<Level name="Edge cases">

Integer division truncates: `5 / 9 * (f - 32)` is always zero, because `5 / 9` is zero before anything is multiplied. Writing `5.0f / 9.0f` fixes it. This is the first bug every C learner writes.

</Level>

<Level name="Corner cases">

`main` without a return reaches the end and returns 0 in C99, but not in C89, where the status is garbage. The same source has a different exit status depending on the standard.

</Level>

<Level name="Production level">

Exit status matters the moment a program runs in a script or CI: a non-zero return is how failure is reported. Layout and naming are for the next reader; compilers do not care, reviewers do.

</Level>

<Level name="Mindset">

The compiler is a strict reader, not an enemy. I read every warning as a question about my intent, and answer it in the code.

</Level>

<Level name="System design">

The compile pipeline is a small system of its own, and the one every C build tool automates. When a build breaks, I locate which stage failed before reading the error.

</Level>

<Level name="Strategy">

I type every example instead of pasting, and break each on purpose to read the error it gives. Done when I can predict whether a mistake is a compile, link or run-time error.

</Level>

</Levels>

### 3. Formatted Input/Output

**Covers:** `printf` and `scanf`: conversion specifications, field widths and precision, escape sequences, and how `scanf` matches input against its format.


<Levels label="Chapter 3, Formatted Input/Output">

<Level name="Beginner">

`printf("%d items at %.2f\n", n, price)` prints values through conversion specifications. `scanf("%d", &n)` reads into the address of `n`; forgetting the `&` is the classic mistake.

</Level>

<Level name="Intermediate">

A specification can carry flags, a width and a precision: `%5d` right-aligns in five columns, `%-5d` left-aligns, `%.3f` gives three decimals, `%e` and `%g` choose scientific or shortest form.

</Level>

<Level name="Advanced">

`scanf` is a pattern matcher: whitespace in the format matches any amount of whitespace in the input, other characters must match exactly, and a conversion stops at the first character that cannot belong to it. It returns how many items it stored.

</Level>

<Level name="Edge cases">

The format and the argument types must agree. `printf("%d", 3.0)` is undefined behaviour, not a conversion. With `scanf`, `%f` writes a `float` and `%lf` a `double`, while for `printf` both print with `%f`.

</Level>

<Level name="Corner cases">

Input that does not match leaves the unread characters in the stream, so the next `scanf` reads the same bad characters again. A loop that calls `scanf` without checking the return value spins forever on one typo.

</Level>

<Level name="Production level">

Real programs check every `scanf` return value, or read a whole line with `fgets` and parse it separately, which is easier to recover from. Formatted output with user data never uses that data as the format string.

</Level>

<Level name="Mindset">

I/O is where my program meets the world, and the world is not well-formed. Validate at the edge, then trust inside.

</Level>

<Level name="System design">

The format string is a tiny interpreted language with no type checking. Compilers warn about mismatches with `-Wformat`; in a system, that check is the only thing between a typo and a memory error.

</Level>

<Level name="Strategy">

I write a small input parser that survives bad input: letters where numbers go, an empty line, end of file. Done when it never hangs and never reads an uninitialised value.

</Level>

</Levels>

### 4. Expressions

**Covers:** Arithmetic operators, precedence and associativity, assignment and compound assignment, increment and decrement, evaluation order, and expression statements.


<Compare left="Defined" right="Undefined" rows={[['i++;  a[i] = i;', 'a[i] = i++;'], ['j = i + 1; i = j;', 'i = i++ + 1;'], ['x = f(); y = g(); z = x + y;', 'z = f() + g();  /* fine, but order unspecified */']]} caption="Change a variable once, read it after the sequence point. The last row is legal but the call order is not promised." />

<Levels label="Chapter 4, Expressions">

<Level name="Beginner">

Operators: `+ - * / %`, with the usual precedence. Assignment is itself an expression that yields the value assigned, which is why `a = b = 0` works.

</Level>

<Level name="Intermediate">

Compound assignment (`+=`) and increment (`i++`, `++i`) are shorthand with side effects. Prefix yields the new value, postfix the old one. Associativity breaks ties between equal-precedence operators: `-` groups left, `=` groups right.

</Level>

<Level name="Advanced">

Precedence decides grouping, not order of evaluation. In `f() + g()` either function may run first. A sequence point (end of a full expression, `&&`, `||`, comma operator) is where side effects are guaranteed complete.

</Level>

<Level name="Edge cases">

`%` with negative operands: C99 says division truncates toward zero, so `-7 / 2` is `-3` and `-7 % 2` is `-1`. In C89 the result was implementation-defined. Dividing by zero is undefined.

</Level>

<Level name="Corner cases">

`i = i++ + 1` and `a[i] = i++` modify and read `i` without a sequence point between, which is undefined behaviour. It is not "one of two answers"; the compiler may assume it never happens.

</Level>

<Level name="Production level">

In review I reject any expression that changes a variable and reads it elsewhere in the same statement. Clear code is one side effect per statement; the optimiser makes it just as fast.

</Level>

<Level name="Mindset">

Precedence tables are something I look up, not memorise. When I need the table to read a line, I add parentheses so the next reader does not.

</Level>

<Level name="System design">

Unspecified evaluation order is what lets compilers reorder work. The same freedom shows up later in concurrency and in distributed systems: if order matters, I must say so.

</Level>

<Level name="Strategy">

I write ten expressions mixing `++` and assignment and predict each one, then check with a compiler and `-Wsequence-point`. Done when I can spot undefined ones on sight.

</Level>

</Levels>

### 5. Selection Statements

**Covers:** Relational, equality and logical operators, `if` and `else`, the conditional operator, Boolean values in C89 and C99, and `switch`.


<Levels label="Chapter 5, Selection Statements">

<Level name="Beginner">

Conditions are integers: zero is false, anything else is true. `if (x > 0) ... else ...` picks a branch; relational operators yield 1 or 0.

</Level>

<Level name="Intermediate">

`&&` and `||` short-circuit, so `if (p != NULL && p->ok)` is safe. The conditional operator `c ? a : b` is an expression. `switch` jumps to a matching integer `case` label and falls through unless I `break`.

</Level>

<Level name="Advanced">

C99 adds `_Bool` and `<stdbool.h>` with `bool`, `true`, `false`. Assigning any non-zero value to a `_Bool` stores 1. An `else` binds to the nearest unmatched `if`, whatever the indentation says.

</Level>

<Level name="Edge cases">

`if (x = 0)` assigns and is always false; it compiles, and only a warning saves me. `0 < x < 10` parses as `(0 < x) < 10`, which is always true.

</Level>

<Level name="Corner cases">

Fallthrough plus a missing `break` in the last case before a new one added later: the old last case starts running into the new case. Intended fallthrough needs a comment so nobody "fixes" it.

</Level>

<Level name="Production level">

Production `switch` statements on an enum get a `default` that reports the impossible case, so a new value added elsewhere is caught when it first appears, not weeks later.

</Level>

<Level name="Mindset">

Branches are where bugs hide in plain sight. I write the condition I mean, then read it as the compiler will.

</Level>

<Level name="System design">

A `switch` over a closed set of states is a state machine. In larger systems I want that set closed and checked; TypeScript's exhaustive `switch` over a union is the same idea with a compiler behind it.

</Level>

<Level name="Strategy">

I write a small menu-driven program with nested `if`s and a `switch`, then turn on `-Wimplicit-fallthrough` and `-Wparentheses`. Done when the warnings are clean and every case is intentional.

</Level>

</Levels>

### 6. Loops

**Covers:** `while`, `do`, and `for`, the comma operator, exiting with `break`, `continue` and `goto`, and the null statement.


<Levels label="Chapter 6, Loops">

<Level name="Beginner">

Three loops: `while` tests first, `do ... while` runs once then tests, `for (init; test; step)` keeps the control in one line. Use the loop whose shape matches the problem.

</Level>

<Level name="Intermediate">

`break` leaves the innermost loop or `switch`; `continue` skips to the next iteration; `goto` jumps to a label in the same function. The comma operator lets a `for` header update two variables.

</Level>

<Level name="Advanced">

In C99 a `for` can declare its counter (`for (int i = 0; ...)`), scoped to the loop. Any of the three header parts may be empty; `for (;;)` is an infinite loop that only `break` or `return` ends.

</Level>

<Level name="Edge cases">

Off-by-one: `for (i = 0; i <= n; i++)` runs n + 1 times. With an unsigned counter, `for (unsigned i = n; i >= 0; i--)` never ends, because an unsigned value is always at least zero.

</Level>

<Level name="Corner cases">

A stray semicolon after the header, `for (i = 0; i < n; i++);`, makes the null statement the body. The block below it runs once, after the loop, with `i` equal to `n`.

</Level>

<Level name="Production level">

Long-running loops need an exit I can prove: a bounded counter, a timeout, or an end-of-input check. The one acceptable `goto` in production C is a jump to shared cleanup code at the end of a function.

</Level>

<Level name="Mindset">

I write loops by stating the invariant first: what is true at the top of every iteration. Then the boundaries follow from it.

</Level>

<Level name="System design">

An event loop, a retry loop and a polling loop are all `while` loops with a policy attached. The policy (backoff, limit, cancellation) is the system design; the loop is just the carrier.

</Level>

<Level name="Strategy">

I write each loop shape twice, once with a deliberate off-by-one, and test both boundaries: zero iterations and the maximum. Done when I check the empty case first, by habit.

</Level>

</Levels>

### 7. Basic Types

**Covers:** Integer types, floating types, character types, reading and writing them, type conversion (implicit and casts), `typedef`, and `sizeof`.


<Figure art={`
  int  -1      : 11111111 11111111 11111111 11111111
  as unsigned : 4294967295
  compared    : -1 < 1u   ->  4294967295 < 1  ->  false
`} caption="The same 32 bits, read signed and unsigned. A mixed comparison converts the signed side." />

<Levels label="Chapter 7, Basic Types">

<Level name="Beginner">

The integer types are `short`, `int`, `long` (and C99 `long long`), each signed or unsigned; the floating types are `float`, `double`, `long double`; a `char` is a small integer that holds a character code.

</Level>

<Level name="Intermediate">

Mixed arithmetic converts operands to a common type (the usual arithmetic conversions). Assignment converts to the target type. A cast, `(double) total / count`, converts one operand on purpose. `typedef` names a type; `sizeof` gives its size in bytes.

</Level>

<Level name="Advanced">

The standard fixes minimum ranges, not sizes: an `int` is at least 16 bits. Signed overflow is undefined; unsigned arithmetic wraps modulo 2 to the n. Floating values follow IEEE 754 on almost every machine I will meet, which C itself does not require.

</Level>

<Level name="Edge cases">

Comparing signed and unsigned: `-1 < 1u` is false, because `-1` converts to a huge unsigned value. `sizeof` returns an unsigned type, so `if (i < sizeof a - 10)` misbehaves when the array is small.

</Level>

<Level name="Corner cases">

Whether a plain `char` is signed is implementation-defined, so a byte of 0xFF read into `char` and compared with `EOF` behaves differently across compilers. That is why `getchar` returns `int`.

</Level>

<Level name="Production level">

Real code uses fixed-width types (`int32_t`, `uint8_t`) for data on disk and on the wire, and `size_t` for sizes and indexes. Money is never a `float`.

</Level>

<Level name="Mindset">

Every value has a range. When I write arithmetic, I ask what the largest input is, and whether the result still fits.

</Level>

<Level name="System design">

Types are part of every protocol and file format. In a system the hard bugs are at the boundary: a 64-bit length read as 32 bits, or a signed byte treated as unsigned.

</Level>

<Level name="Strategy">

I write a program that prints the limits from `<limits.h>` and `<float.h>` on my machine, then trigger each conversion surprise above. Done when I can explain each surprising line without running it.

</Level>

</Levels>

### 8. Arrays

**Covers:** One-dimensional arrays, subscripting, initialisation, designated initialisers, `sizeof` on arrays, multidimensional arrays, constant arrays and C99 variable-length arrays.


<Levels label="Chapter 8, Arrays">

<Level name="Beginner">

An array is a fixed number of elements of one type in a row: `int a[10];`. Elements are `a[0]` to `a[9]`. A brace initialiser fills them; anything left over is zero.

</Level>

<Level name="Intermediate">

`sizeof a / sizeof a[0]` gives the length, but only where the array itself is in scope. Two-dimensional arrays are arrays of arrays, stored row by row. C99 designated initialisers (`[5] = 1`) set chosen elements.

</Level>

<Level name="Advanced">

There is no bounds checking: `a[10]` reads whatever is next in memory, and writing it corrupts that memory. Subscripting is defined in terms of pointer arithmetic, which chapter 12 makes explicit.

</Level>

<Level name="Edge cases">

Arrays cannot be assigned (`a = b` does not compile) or compared with `==` meaningfully. A variable-length array sized from input with a zero or negative size is undefined, and a huge one overflows the stack with no error to catch.

</Level>

<Level name="Corner cases">

`int a[] = {1, 2, 3};` lets the compiler count, but passed to a function the size is lost and `sizeof` inside reports the pointer size. The same expression gives different answers inside and outside.

</Level>

<Level name="Production level">

Real code passes the length with the array, every time, and checks indexes from outside input. Variable-length arrays are often banned in production style guides because stack size is not checked.

</Level>

<Level name="Mindset">

An array is memory with a shape I promise to respect. The compiler will not keep that promise for me.

</Level>

<Level name="System design">

Contiguous memory is why arrays are fast: one cache line holds several neighbours. Row-by-row layout decides whether a loop over a matrix is quick or slow, which comes back in the systems books.

</Level>

<Level name="Strategy">

I write a fixed-size buffer program, then build it with `-fsanitize=address` and step one past the end on purpose. Done when I always pass a length and I know the sanitizer's report on sight.

</Level>

</Levels>

### 9. Functions

**Covers:** Defining and calling functions, declarations (prototypes), arguments and array arguments, the `return` statement, program termination, and recursion.


<Figure art={`
  stack (grows down)
  +---------------------+
  | main:  n = 3        |
  +---------------------+
  | fact(3): ret addr   |
  +---------------------+
  | fact(2): ret addr   |
  +---------------------+
  | fact(1): returns 1  |  <- top of stack
  +---------------------+
`} caption="One frame per call. Each frame is gone once its call returns, and anything pointing into it is left dangling." />

<Levels label="Chapter 9, Functions">

<Level name="Beginner">

A function has a return type, a name, parameters and a body. A declaration (prototype) before the call tells the compiler the types, so the call can be checked.

</Level>

<Level name="Intermediate">

Arguments are passed by value: the function gets a copy. To change the caller's variable, pass its address (chapter 11). An array argument arrives as a pointer to its first element, so the length goes in a separate parameter.

</Level>

<Level name="Advanced">

Each call gets a stack frame for its parameters and locals, gone when it returns. `exit(status)` ends the whole program from anywhere; `return` from `main` does the same. Recursion is a function calling itself, with a frame per level.

</Level>

<Level name="Edge cases">

A function declared with `()` in C89-style C accepts any arguments unchecked; `(void)` means none. Falling off the end of a non-`void` function and using the result is undefined.

</Level>

<Level name="Corner cases">

Returning the address of a local variable compiles and may even seem to work, until the next call reuses that stack space. The pointer is valid at the `return` and dangling one line later.

</Level>

<Level name="Production level">

Deep recursion on untrusted input (a nested JSON document, a deep tree) overflows the stack and crashes. In production I bound the depth or rewrite as a loop with an explicit stack.

</Level>

<Level name="Mindset">

A function is a contract: what it needs, what it returns, what it changes. I write the prototype first and the body second.

</Level>

<Level name="System design">

The call stack is the first resource limit I meet. Every larger system has the same shape: a bounded resource, an input that grows, and a limit nobody checked.

</Level>

<Level name="Strategy">

I write a recursive function, an iterative twin, and a test with input deep enough to crash the recursive one. Done when I can draw the stack frames for three calls by hand.

</Level>

</Levels>

### 10. Program Organization

**Covers:** Local and external variables, blocks, scope, storage duration, and how to organise a single-file program.


<Levels label="Chapter 10, Program Organization">

<Level name="Beginner">

A local variable lives inside a function; an external (global) variable lives outside every function and is visible from its declaration onward. A block is any `{ ... }`, and it can declare its own variables.

</Level>

<Level name="Intermediate">

Scope is where a name is visible; storage duration is how long the object lives. A `static` local keeps its value between calls. An inner declaration hides an outer one with the same name.

</Level>

<Level name="Advanced">

Automatic storage (locals) is created per call; static storage (globals and `static` locals) exists for the whole run and is zero-initialised. The order in a single file is: directives, types, globals, prototypes, `main`, then the other functions.

</Level>

<Level name="Edge cases">

A local without an initialiser holds garbage, while a global without one is zero. Moving a variable from file scope into a function changes its starting value without changing a character of its declaration.

</Level>

<Level name="Corner cases">

Shadowing plus a `static` local: the inner variable is the one updated, the outer is untouched, and a recursive function's `static` counter is shared across every level, not one per frame.

</Level>

<Level name="Production level">

Global mutable state is the first thing that makes a C program impossible to test or to run on two threads. I keep it `static` to one file and give it a small set of functions.

</Level>

<Level name="Mindset">

Smallest scope, shortest life. A variable I cannot see cannot break my code.

</Level>

<Level name="System design">

File-level organisation is the seed of module design: what is public, what is private, and who owns each piece of state. Chapter 15 turns it into headers and source files.

</Level>

<Level name="Strategy">

I refactor one long single-file program so every variable has the smallest scope it can. Done when it has no global I cannot justify in one sentence.

</Level>

</Levels>

## Advanced features of C

### 11. Pointers

**Covers:** Pointer variables, the address and indirection operators, pointer assignment, pointers as arguments, and pointers as return values.


<Figure art={`
   x                p
  +-----+          +---------+
  |  5  |  <-------| &x      |
  +-----+          +---------+
  addr 0x1000      holds 0x1000

  *p = 7   writes into x
  p  = &y  changes only p
`} caption="A pointer is a box that holds the address of another box. Writing through it changes the box it points at." />

<Levels label="Chapter 11, Pointers">

<Level name="Beginner">

A pointer holds an address. `int *p = &x;` makes `p` point at `x`; `*p` is `x` itself, so `*p = 5` changes `x`.

</Level>

<Level name="Intermediate">

Passing `&x` lets a function change the caller's variable, which is how `scanf` works and how a function returns two results. `const int *p` promises not to change what `p` points at.

</Level>

<Level name="Advanced">

Pointer assignment `q = p` copies the address, so both point at the same object; `*q = *p` copies the value. A pointer has a type, so `*p` knows how many bytes to read and how to read them.

</Level>

<Level name="Edge cases">

Dereferencing an uninitialised pointer or a null pointer is undefined behaviour. `int *p, q;` declares one pointer and one `int`, because the `*` binds to the name, not the type.

</Level>

<Level name="Corner cases">

Returning a pointer to a local variable (chapter 9) and keeping a pointer into an array that is later resized (chapter 17) are the same bug: the address outlives the object.

</Level>

<Level name="Production level">

In production, every pointer has an owner and a lifetime I can name. Null checks go at the boundary where a pointer can first be null, not sprinkled everywhere.

</Level>

<Level name="Mindset">

A pointer is a name for a place, not a value. The question for every pointer is: what does it point at right now, and who keeps that alive?

</Level>

<Level name="System design">

References in every higher-level language are pointers without the arithmetic. Shared mutable state through two references is the same aliasing problem, in JavaScript objects and in distributed caches.

</Level>

<Level name="Strategy">

I draw boxes and arrows for every pointer exercise before I run it. Done when my drawing predicts the output, including the swap function done wrong and done right.

</Level>

</Levels>

### 12. Pointers and Arrays

**Covers:** Pointer arithmetic and pointer comparison, combining `*` and `++` to walk arrays, using an array name as a pointer, pointers into multidimensional arrays, and C99 pointers to compound literals and variable-length arrays.


<Figure art={`
  a:  [ 10 ][ 20 ][ 30 ][ 40 ]  .
        ^           ^           ^
        p           p + 2       a + 4 (one past the end: compare, never read)
`} caption="Pointer arithmetic counts in elements. One past the end is a legal place to point, and an illegal place to read." />

<Levels label="Chapter 12, Pointers and Arrays">

<Level name="Beginner">

Adding 1 to a pointer moves it one element, not one byte: if `p = &a[0]`, then `p + 2` is `&a[2]`. `*(p + i)` and `p[i]` are the same thing.

</Level>

<Level name="Intermediate">

A loop can walk an array with a pointer: `for (p = a; p < a + n; p++) sum += *p;`. Subtracting two pointers into the same array gives the distance in elements. An array name used in an expression becomes a pointer to its first element.

</Level>

<Level name="Advanced">

The array name is not a pointer variable: `a++` does not compile, and `sizeof a` is the whole array. For a 2D array, `a[i]` is a pointer to row `i`, and `int (*row)[N]` is a pointer to a whole row.

</Level>

<Level name="Edge cases">

A pointer may point one past the last element (for loop bounds), but must never be dereferenced there. Comparing or subtracting pointers into different arrays is undefined.

</Level>

<Level name="Corner cases">

`*p++` increments the pointer and reads the old element; `(*p)++` increments the element. One pair of parentheses changes which object is modified.

</Level>

<Level name="Production level">

Production code walks buffers with an explicit end pointer or a length and never trusts a terminator from outside input. Most memory-safety CVEs in C are pointer arithmetic past a bound nobody checked.

</Level>

<Level name="Mindset">

Index and pointer are two notations for one idea. I pick the one that makes the bounds easiest to see.

</Level>

<Level name="System design">

Slices, views and cursors (a `Uint8Array` over an `ArrayBuffer`, a Go slice) are a pointer plus a length. Carrying the length with the pointer is the design fix C left to me.

</Level>

<Level name="Strategy">

I rewrite three array functions from index style to pointer style and back, under AddressSanitizer. Done when I can read `*p++` style loops as fast as `for` loops.

</Level>

</Levels>

### 13. Strings

**Covers:** String literals, string variables (character arrays versus character pointers), reading and writing strings, accessing characters, the C string library, string idioms, arrays of strings, and command-line arguments.


<Figure art={`
  char s[6] = "hello";

  +---+---+---+---+---+----+
  | h | e | l | l | o | \\0 |
  +---+---+---+---+---+----+
    0   1   2   3   4   5

  strlen(s) == 5   sizeof s == 6
`} caption="Five characters take six bytes. The terminator is the length." />

<Levels label="Chapter 13, Strings">

<Level name="Beginner">

A C string is an array of `char` ending in a null character `'\0'`. `char s[6] = "hello";` needs six bytes: five letters plus the terminator.

</Level>

<Level name="Intermediate">

`<string.h>` gives `strlen`, `strcpy`, `strcat`, `strcmp` and friends; none of them knows the size of the destination. An array of strings is usually an array of pointers to `char`, which can be ragged.

</Level>

<Level name="Advanced">

A string literal is stored in memory I must not modify: `char *p = "abc"; p[0] = 'x';` is undefined, while `char s[] = "abc";` is a modifiable copy. `strlen` walks to the terminator each time it is called, so it is O(n).

</Level>

<Level name="Edge cases">

`strcpy` into a buffer too small writes past it, and `strncpy` does not always add a terminator. A string exactly the size of the buffer has no room for the `'\0'`.

</Level>

<Level name="Corner cases">

A missing terminator plus `printf("%s")` reads until it finds a zero byte somewhere in memory, printing garbage or crashing. Calling `strlen` in a loop condition on a string that grows turns a linear loop into a quadratic one.

</Level>

<Level name="Production level">

Production code uses length-carrying buffers or `snprintf`, which always terminates and reports how much it wanted to write. Every copy has a destination size beside it.

</Level>

<Level name="Mindset">

A string in C is a convention, not a type. Code is correct only if every function keeps the convention.

</Level>

<Level name="System design">

Strings are the main thing a program receives from outside. Length-prefixed strings (JavaScript, most protocols) exist because the terminator design leaves nothing to stop an overflow.

</Level>

<Level name="Strategy">

I write my own `strlen`, `strcpy` and a safe copy with a size argument, then fuzz them with random lengths under the sanitizer. Done when the safe version cannot be made to overflow.

</Level>

</Levels>

### 14. The Preprocessor

**Covers:** How the preprocessor works, simple and parameterised macros, the `#` and `##` operators, predefined macros and C99 variadic macros, conditional compilation, and `#error`, `#line` and `#pragma`.


<Flow steps={['source.c', '#include pasted', '#define replaced', '#if lines dropped', 'translation unit', 'compiler']} caption="The preprocessor rewrites text, then the compiler sees one translation unit. gcc -E shows that unit." />

<Levels label="Chapter 14, The Preprocessor">

<Level name="Beginner">

The preprocessor edits the source text before the compiler sees it: `#include` pastes a file, `#define` replaces names, `#if` keeps or drops lines.

</Level>

<Level name="Intermediate">

Parameterised macros look like functions: `#define MAX(a, b) ((a) > (b) ? (a) : (b))`. `#` turns an argument into a string literal, `##` pastes two tokens. `#ifdef` and `#ifndef` choose code per platform or build, and include guards stop a header being pasted twice.

</Level>

<Level name="Advanced">

Macros work on tokens, not values or types: no type checking, no scope, no single evaluation of arguments. Predefined macros like `__FILE__`, `__LINE__` and C99 `__func__` support logging and assertions.

</Level>

<Level name="Edge cases">

`#define SQUARE(x) x * x` gives `SQUARE(a + 1)` as `a + 1 * a + 1`. Every parameter and the whole body need parentheses.

</Level>

<Level name="Corner cases">

`MAX(i++, j)` evaluates `i++` twice when `i` is larger. A macro can be correctly parenthesised and still wrong because of side effects in the arguments.

</Level>

<Level name="Production level">

Production code keeps macros for what only the preprocessor can do: include guards, conditional compilation and `__FILE__` logging. For everything else, `static inline` functions and `enum` constants are type-checked.

</Level>

<Level name="Mindset">

The preprocessor is a text editor run by the build, not a part of the language. When something looks impossible, I read the expanded output with `gcc -E`.

</Level>

<Level name="System design">

Conditional compilation is how one codebase serves many platforms, and how feature flags worked before runtime config. Too many `#if` branches mean some branch is never compiled, and so never tested.

</Level>

<Level name="Strategy">

I write the broken `SQUARE` and `MAX` macros, view the `-E` output, then replace them with inline functions. Done when I can predict the expansion of any macro by hand.

</Level>

</Levels>

### 15. Writing Large Programs

**Covers:** Source files, header files, sharing macros, types, functions and variables across files, protecting headers, dividing a program into files, and building it with makefiles.


<Layers layers={[{ name: 'main.c', note: 'includes stack.h, calls push and pop' }, { name: 'stack.h', note: 'the interface: prototypes and types' }, { name: 'stack.c', note: 'the implementation: static helpers stay private' }, { name: 'linker', note: 'joins main.o and stack.o into one program' }]} caption="A module in C: the header is what other files may use, the source file is everything else." />

<Levels label="Chapter 15, Writing Large Programs">

<Level name="Beginner">

A large program is split into `.c` source files and `.h` header files. A header holds declarations that several source files share; each source file is compiled separately.

</Level>

<Level name="Intermediate">

A header shares macro definitions, type definitions and function prototypes. A shared variable is defined in exactly one `.c` file and declared `extern` in the header. A makefile rebuilds only what changed.

</Level>

<Level name="Advanced">

Each `.c` file plus its included headers is a translation unit. The linker resolves names across units: external linkage by default for functions, internal linkage for `static` ones. Include guards (`#ifndef FOO_H`) make a header safe to include twice.

</Level>

<Level name="Edge cases">

Defining (not just declaring) a variable in a header gives each including file its own definition, and the link fails with duplicate symbols, or on some toolchains silently merges them.

</Level>

<Level name="Corner cases">

A header that includes another header which includes the first: guards stop infinite pasting, but whichever header is read first sees the other half-defined, so a type is used before it exists.

</Level>

<Level name="Production level">

Production C has one header per module, the public interface only, with everything else `static` in the source. Builds use dependency tracking (`-MMD`) so a header change rebuilds what uses it.

</Level>

<Level name="Mindset">

A header is a promise to other files. I keep it as small as I can and change it as rarely as I can.

</Level>

<Level name="System design">

Header and source is interface and implementation: the same split as a TypeScript module's exports, a package's public API, or a service's contract. Small interfaces are cheap to change behind.

</Level>

<Level name="Strategy">

I split one of my single-file programs into three modules with a makefile and break the build three ways: a missing prototype, a duplicate definition, a stale object. Done when I can name the stage of each failure.

</Level>

</Levels>

### 16. Structures, Unions, and Enumerations

**Covers:** Structure variables and types, nested arrays and structures, unions, and enumerations.


<Figure art={`
  struct { char c; int n; char d; }     sizeof = 12 (typical)
  +---+-------+---------------+---+-------+
  | c |  pad  |       n       | d |  pad  |
  +---+-------+---------------+---+-------+

  struct { int n; char c; char d; }     sizeof = 8 (typical)
  +---------------+---+---+-------+
  |       n       | c | d |  pad  |
  +---------------+---+---+-------+
`} caption="The same three fields in a different order. Padding keeps each member aligned; the exact sizes depend on the platform." />

<Levels label="Chapter 16, Structures, Unions, and Enumerations">

<Level name="Beginner">

A `struct` groups named fields of different types: `struct part { int number; char name[25]; };`. Members are read with `.`, or with `->` through a pointer.

</Level>

<Level name="Intermediate">

Structures can be assigned, passed and returned by value (copied whole), nested, and kept in arrays. C99 designated initialisers set fields by name. `typedef struct { ... } Part;` names the type.

</Level>

<Level name="Advanced">

The compiler may add padding between members for alignment, so `sizeof` a struct can exceed the sum of its fields. A `union` overlays its members in the same memory; an `enum` names integer constants.

</Level>

<Level name="Edge cases">

Structs cannot be compared with `==`, and comparing with `memcmp` also compares the padding bytes, whose values are unspecified. A union read through a member other than the one last written gives reinterpreted bits.

</Level>

<Level name="Corner cases">

Copying a struct that contains a pointer copies the pointer, not what it points at: two structs now share one buffer, and freeing one leaves the other dangling.

</Level>

<Level name="Production level">

Production code does not write a struct's raw bytes to a file or socket, because padding and byte order differ across machines; it serialises field by field. A tagged union (an `enum` tag plus a `union`) is the safe way to store one of several shapes.

</Level>

<Level name="Mindset">

A struct is a decision about what belongs together. When I cannot name the struct, the fields probably do not belong together.

</Level>

<Level name="System design">

A tagged union in C is a discriminated union in TypeScript, written by hand with no checker. Data layout decisions (padding, order) matter again in caches, file formats and wire protocols.

</Level>

<Level name="Strategy">

I print `sizeof` and `offsetof` for a few structs, reorder fields to remove padding, and build a tagged union with a `switch` over its tag. Done when I can predict a struct's size before printing it.

</Level>

</Levels>

### 17. Advanced Uses of Pointers

**Covers:** Dynamic storage allocation, dynamically allocated strings and arrays, deallocating storage and the dangling-pointer problem, linked lists, pointers to pointers, pointers to functions, and C99 restricted pointers and flexible array members.


<Figure art={`
  head
   |
   v
  +----+---+    +----+---+    +----+------+
  | 10 | *-+--->| 20 | *-+--->| 30 | NULL |
  +----+---+    +----+---+    +----+------+

  delete 20:  first->next = second->next;  free(second);
`} caption="A linked list in heap memory. Deleting a node is one pointer update and one free, in that order." />

<Levels label="Chapter 17, Advanced Uses of Pointers">

<Level name="Beginner">

`malloc(n)` returns a pointer to `n` bytes on the heap, or a null pointer if it fails; `free(p)` gives them back. `calloc` zeroes the memory; `realloc` resizes it.

</Level>

<Level name="Intermediate">

Dynamic arrays and strings are sized at run time: `int *a = malloc(n * sizeof *a);`. A linked list is nodes that each hold a pointer to the next; insertion and deletion change pointers, not elements. A pointer to a pointer lets a function change the caller's pointer, for example the head of a list.

</Level>

<Level name="Advanced">

Function pointers let code be passed as data: `qsort` takes a comparison function. `restrict` (C99) promises the compiler two pointers do not alias, enabling optimisation. A flexible array member lets a struct end in an array sized at allocation.

</Level>

<Level name="Edge cases">

`malloc(0)` may return null or a unique pointer; either is legal. `realloc` may move the block, so `p = realloc(p, n)` loses the original pointer if it fails. Every `malloc` result is checked.

</Level>

<Level name="Corner cases">

Freeing a node, then reading `node->next` to continue the loop, reads freed memory: save the next pointer first. Two pointers into one block, freed through both, is a double free, which corrupts the allocator.

</Level>

<Level name="Production level">

In production every allocation has exactly one owner responsible for freeing it, failure paths free what they allocated, and leak checks (`valgrind`, LeakSanitizer) run in CI.

</Level>

<Level name="Mindset">

Manual memory is bookkeeping. Most bugs come not from forgetting the rules, but from not knowing who owns a pointer at a given line.

</Level>

<Level name="System design">

Ownership is the design question every runtime answers differently: garbage collection in JavaScript, borrow checking in Rust, reference counting in Swift. C makes me answer it explicitly, so I understand the other answers.

</Level>

<Level name="Strategy">

I build a linked list and a growable array from scratch, with insert, delete and free-all, and run them under AddressSanitizer and LeakSanitizer. Done when both run clean through a randomised test of a thousand operations.

</Level>

</Levels>

### 18. Declarations

**Covers:** Declaration syntax, storage classes, type qualifiers, declarators (including complicated ones), initialisers, and C99 inline functions.


<Levels label="Chapter 18, Declarations">

<Level name="Beginner">

A declaration is specifiers (`static`, `const`, `int`) followed by declarators (`*p`, `a[10]`, `f(void)`). It says what a name is and, sometimes, sets aside storage for it.

</Level>

<Level name="Intermediate">

Storage classes are `auto`, `static`, `extern` and `register`. Qualifiers are `const`, `volatile` and C99 `restrict`. `static` at file scope means "private to this file"; inside a function it means "lives for the whole run".

</Level>

<Level name="Advanced">

Declarators read inside out: start at the name, go right through `[]` and `()`, then left through `*`. `int *a[10]` is an array of ten pointers; `int (*a)[10]` is a pointer to an array of ten. A function returning a pointer to a function needs a `typedef` to stay readable.

</Level>

<Level name="Edge cases">

`const int *p` is a pointer to a constant `int`; `int *const p` is a constant pointer to an `int`. Initialisers for static storage must be constant expressions; automatic ones may be any expression.

</Level>

<Level name="Corner cases">

A C99 `inline` function in a header with no `extern` declaration in exactly one source file leaves no out-of-line definition, so the program fails to link the moment the compiler decides not to inline.

</Level>

<Level name="Production level">

Production code uses `typedef` to name function-pointer and array types, `const` everywhere a value should not change, and `static` on everything that is not part of the module interface.

</Level>

<Level name="Mindset">

If I cannot read a declaration aloud, I rewrite it until I can. Clarity in declarations is clarity about ownership and mutability.

</Level>

<Level name="System design">

`const` and `static` are the language's way to state intent: what can change, and who can see it. Every larger design has the same two questions about every piece of state.

</Level>

<Level name="Strategy">

I translate twenty declarations to English and back, including function pointers, then check them with `cdecl`. Done when the complicated ones read without the tool.

</Level>

</Levels>

### 19. Program Design

**Covers:** Modules, cohesion and coupling, information hiding, abstract data types, a stack ADT, encapsulation in C, and design issues for abstract data types.


<Layers layers={[{ name: 'caller', note: 'holds a Stack; calls push, pop, destroy' }, { name: 'stack.h', note: 'typedef struct stack_type *Stack; prototypes' }, { name: 'stack.c', note: 'struct stack_type defined here, and only here' }]} caption="An abstract data type in C: the caller can hold the handle but cannot see inside it." />

<Levels label="Chapter 19, Program Design">

<Level name="Beginner">

A module is a set of related services behind an interface. In C that is a header plus a source file. A good module has high cohesion (its parts belong together) and low coupling (it depends little on others).

</Level>

<Level name="Intermediate">

Information hiding keeps the representation private: other files see functions, not fields. An abstract data type is a type whose operations are public and whose representation is not, like a stack with `push`, `pop` and `is_empty`.

</Level>

<Level name="Advanced">

C's tool for this is an incomplete type: the header declares `typedef struct stack_type *Stack;` and only the source file defines the struct. Users can hold a `Stack` but cannot read its fields. The stack can then change from an array to a linked list without callers recompiling their logic.

</Level>

<Level name="Edge cases">

Errors in an ADT need a policy: return an error code, call a handler, or terminate. Popping an empty stack has to do something defined, and the interface must say what.

</Level>

<Level name="Corner cases">

An ADT that is generic over element type in C needs `void *` (losing type checking) or macros (losing readability); each instance that stores pointers must also say who frees the elements, not just the stack.

</Level>

<Level name="Production level">

Production C libraries (SQLite, libcurl) are built exactly this way: opaque handles, a create and destroy pair, every function taking the handle first, and a documented error convention.

</Level>

<Level name="Mindset">

Design is choosing what to hide. The interface I expose is the part I can never easily change.

</Level>

<Level name="System design">

Opaque handles are the C form of a service API: callers depend on operations, not storage. The same reasoning drives module boundaries in a large TypeScript app and service boundaries in a distributed one.

</Level>

<Level name="Strategy">

I build a stack ADT twice, array-backed and list-backed, behind one unchanged header, with one test file that runs against both. Done when swapping the implementation needs no change outside one file.

</Level>

</Levels>

### 20. Low-Level Programming

**Covers:** Bitwise operators, using them to access bits and bit-fields, bit-fields in structures, machine-dependent types, unions as multiple views of data, pointers as addresses, and the `volatile` qualifier.


<Figure art={`
  x          = 0b1011 0010
  1u << 3    = 0b0000 1000
  x | mask   = 0b1011 1010   set bit 3
  x & ~mask  = 0b1011 0010   clear bit 3
  x ^ mask   = 0b1011 1010   toggle bit 3
`} caption="Set, clear and toggle one bit with a mask. Unsigned operands keep every shift defined." />

<Levels label="Chapter 20, Low-Level Programming">

<Level name="Beginner">

The bitwise operators are `& | ^ ~ << >>`. `x & 1` tests the lowest bit; `x | (1u << n)` sets bit `n`; `x & ~(1u << n)` clears it.

</Level>

<Level name="Intermediate">

Bit masks pack several flags or small fields into one integer. Bit-fields in a struct (`unsigned mode: 3;`) let the compiler do the masking. XOR toggles bits and undoes itself, which the book uses for a small encryption example.

</Level>

<Level name="Advanced">

How bit-fields are laid out is implementation-defined. A union can give two views of the same bytes. A pointer can be set to a fixed address to reach hardware, and `volatile` tells the compiler every read and write must really happen.

</Level>

<Level name="Edge cases">

Shifting by the width of the type or more, or shifting a negative value left, is undefined. Right-shifting a negative signed value is implementation-defined (arithmetic or logical).

</Level>

<Level name="Corner cases">

`1 << 31` on a 32-bit `int` overflows a signed value, which is undefined; `1u << 31` is fine. The same mask is safe or unsafe depending on one letter.

</Level>

<Level name="Production level">

Production code does bit work on unsigned fixed-width types, uses named masks instead of magic numbers, and never relies on bit-field layout for file formats or hardware registers it must share across compilers.

</Level>

<Level name="Mindset">

At this level a value is just bits, and I decide what they mean. Writing the meaning down is the whole job.

</Level>

<Level name="System design">

Flags in one integer show up everywhere: Unix file permissions, protocol headers, feature bitmaps, database null bitmaps. Endianness and layout are what make them portable or not.

</Level>

<Level name="Strategy">

I write a set of bit helpers (set, clear, toggle, test, count bits) on `uint32_t` with tests at bit 0 and bit 31. Done when I can read a hex mask and say which bits it touches without converting it on paper.

</Level>

## The standard C library

### 21. The Standard Library

**Covers:** Using the library, the restrictions on names it uses, functions hidden by macros, an overview of the C89 and C99 headers, and `<stddef.h>` and `<stdbool.h>`.


<Levels label="Chapter 21, The Standard Library">

<Level name="Beginner">

The standard library is a set of headers, each declaring related functions, types and macros: `<stdio.h>` for I/O, `<string.h>` for strings, `<stdlib.h>` for allocation and conversion, and so on.

</Level>

<Level name="Intermediate">

Including a header gives the prototypes so calls are type-checked. `<stddef.h>` defines `size_t`, `ptrdiff_t`, `NULL` and `offsetof`; `<stdbool.h>` gives `bool`. C99 adds headers such as `<stdint.h>` and `<complex.h>`.

</Level>

<Level name="Advanced">

Some library functions may also be macros, so `getc` may evaluate its argument more than once. `#undef name` or `(name)(args)` forces the real function. Names the library uses, including any starting with an underscore and a capital, are reserved for it.

</Level>

<Level name="Edge cases">

Defining my own function named `index`, `log` or `exit` collides with the library on some systems; it compiles, then links against the wrong one or fails.

</Level>

<Level name="Corner cases">

A header I did not include, used anyway, worked in C89 by implicit declaration as returning `int`, so `malloc` without `<stdlib.h>` truncated a 64-bit pointer to 32 bits. C99 removed implicit declarations; old code still hits it with old flags.

</Level>

<Level name="Production level">

Production code includes exactly what it uses, never relies on one header including another, and reaches for the standard library before writing its own version of anything.

</Level>

<Level name="Mindset">

Read the library before writing the function. Most problems I am about to solve have a tested answer in a header.

</Level>

<Level name="System design">

The standard library is the smallest platform API C promises everywhere. Everything else (POSIX, Windows, an embedded SDK) is a separate, larger contract, chosen per system.

</Level>

<Level name="Strategy">

I go header by header with a one-line note on what each is for, and write a ten-line program per header. Done when for any task I know which header to open first.

</Level>

</Levels>

### 22. Input/Output

**Covers:** Streams, file pointers, standard streams and redirection, text and binary files, file operations, formatted I/O, character I/O, line I/O, block I/O, file positioning and string I/O.


<Layers layers={[{ name: 'my program', note: 'fprintf, fputs, fwrite' }, { name: 'stdio buffer', note: 'in memory; flushed when full, on newline (terminal), or fflush' }, { name: 'operating system', note: 'write() system call, kernel page cache' }, { name: 'disk', note: 'durable only after the kernel writes it' }]} caption="Where written bytes really are. Each layer can hold them before passing them on." />

<Levels label="Chapter 22, Input/Output">

<Level name="Beginner">

All I/O in `<stdio.h>` goes through streams: a `FILE *` from `fopen`, or the standard streams `stdin`, `stdout` and `stderr`. `fclose` flushes and closes.

</Level>

<Level name="Intermediate">

There are four levels: formatted (`fprintf`, `fscanf`), character (`fgetc`, `fputc`), line (`fgets`, `fputs`) and block (`fread`, `fwrite`). `fseek` and `ftell` move around a file; `sprintf` and `sscanf` do formatted I/O on strings.

</Level>

<Level name="Advanced">

Streams are buffered: output collects in memory and is written when the buffer fills, on a newline for an interactive terminal, or on `fflush`. Text mode may translate line endings on some systems; binary mode never does.

</Level>

<Level name="Edge cases">

`while (!feof(fp))` runs one extra time, because end of file is only detected after a read fails; check the read's return value instead. `fgets` keeps the newline, and a line longer than the buffer arrives in pieces.

</Level>

<Level name="Corner cases">

A program that writes to `stdout`, then crashes, loses output still in the buffer, while `stderr` (unbuffered) already printed. Error messages appear before the output they came after.

</Level>

<Level name="Production level">

Production I/O checks every return value, including `fclose`, which is where a full disk is often first reported. Output files are written to a temporary name and renamed when complete, so a crash never leaves half a file.

</Level>

<Level name="Mindset">

Every I/O call can fail, and the failure is information. I treat a return value as part of the answer, not noise.

</Level>

<Level name="System design">

Buffering is a throughput-versus-latency trade-off, the same one in network sockets, database write-ahead logs and log shippers. Knowing when data is really written is the base of durability.

</Level>

<Level name="Strategy">

I write a file copy tool three ways (character, line, block), time each on a large file, and make each handle a missing file and a full disk cleanly. Done when all three report every failure correctly.

</Level>

</Levels>

### 23. Library Support for Numbers and Character Data

**Covers:** `<float.h>` and `<limits.h>`, the `<math.h>` functions (C89 and C99), `<ctype.h>` character handling, and the `<string.h>` string functions in full.


<Levels label="Chapter 23, Library Support for Numbers and Character Data">

<Level name="Beginner">

`<limits.h>` gives the ranges of integer types (`INT_MAX`), `<float.h>` the properties of floating types (`DBL_EPSILON`). `<math.h>` has `sqrt`, `pow`, `sin` and the rest; `<ctype.h>` has `isdigit`, `toupper` and similar tests.

</Level>

<Level name="Intermediate">

`<string.h>` has copying (`memcpy`, `strcpy`), concatenation, comparison (`strcmp`, `memcmp`), searching (`strchr`, `strstr`, `strtok`) and `memset` and `strlen`. C99 adds math functions for classification and rounding, like `isnan`, `round` and `fma`.

</Level>

<Level name="Advanced">

Math functions report domain and range errors through `errno` and special values (NaN, infinity). Floating-point equality is fragile: compare with a tolerance scaled to the values. `memcpy` assumes no overlap; `memmove` handles it.

</Level>

<Level name="Edge cases">

`isdigit(c)` on a negative `char` value (any byte above 127 where `char` is signed) is undefined; cast to `unsigned char` first. `strtok` modifies its input and keeps hidden state, so it cannot parse two strings at once.

</Level>

<Level name="Corner cases">

`memcpy` with overlapping source and destination may work on one machine and corrupt data on another, depending on how the library copies. `0.1 + 0.2 == 0.3` is false in C exactly as it is in JavaScript, for the same IEEE reason.

</Level>

<Level name="Production level">

Production code uses `memmove` when in doubt, `strtol` instead of `atoi` (so errors are detectable), and integer cents for money. Character classification in a real product needs a locale or a Unicode library, which `<ctype.h>` is not.

</Level>

<Level name="Mindset">

Numbers in a computer are approximations with rules. I learn the rules once and stop being surprised.

</Level>

<Level name="System design">

Floating-point behaviour is shared by every language on the machine: JavaScript numbers are C `double`s. A bug found here is understood in the browser too.

</Level>

<Level name="Strategy">

I write tests for the edge cases above (negative chars, overlapping copies, float comparison, `strtol` with bad input). Done when each test explains in its name what it guards against.

</Level>

</Levels>

### 24. Error Handling

**Covers:** `<assert.h>` diagnostics, `<errno.h>` and `perror`/`strerror`, `<signal.h>` signal handling, and `<setjmp.h>` nonlocal jumps.


<Compare left="Programmer error" right="Runtime error" rows={[['index past the end I computed', 'file not found'], ['null where my contract forbids it', 'malloc returns NULL'], ['assert(); fix the code', 'check, report, recover or exit cleanly']]} caption="Assertions are for bugs in my code. Everything the world can cause is checked and handled." />

<Levels label="Chapter 24, Error Handling">

<Level name="Beginner">

`assert(expr)` stops the program with a message if `expr` is false. Library functions report errors by return value, and many also set `errno` to a code that `perror` or `strerror` turns into text.

</Level>

<Level name="Intermediate">

`errno` is only meaningful right after a call that failed; set it to zero before a call that does not signal failure in its return value (like `strtol`). Signals (`SIGINT`, `SIGSEGV`) are asynchronous events a program can catch with `signal`.

</Level>

<Level name="Advanced">

`setjmp` saves the current execution context and `longjmp` returns to it from deep in the call stack, skipping the frames between. It is C's closest thing to exceptions, with no cleanup of the skipped frames.

</Level>

<Level name="Edge cases">

`assert` disappears when `NDEBUG` is defined, so `assert(fp = fopen(...))` stops opening the file in release builds. A successful library call may also change `errno`, so it cannot be read later.

</Level>

<Level name="Corner cases">

A signal handler that calls `printf` or `malloc` can deadlock or corrupt state if the signal arrives inside those same functions; only async-signal-safe actions (setting a `volatile sig_atomic_t` flag) are safe. Locals changed between `setjmp` and `longjmp` are indeterminate unless `volatile`.

</Level>

<Level name="Production level">

Production C has one error convention per codebase, checks every call, frees resources on every error path, and uses `assert` only for programmer errors, never for input errors.

</Level>

<Level name="Mindset">

Errors are part of the interface. I design the failure path with the same care as the success path, because it runs exactly when things are worst.

</Level>

<Level name="System design">

Error codes, exceptions, result types and crash-and-restart supervisors are different answers to one question: who handles this failure, and where. In TypeScript I choose between `throw` and returning a result type for the same reason.

</Level>

<Level name="Strategy">

I take one of my programs and audit every call that can fail, writing down what happens on each failure. Done when no failure path leaks memory or a file handle.

</Level>

</Levels>

### 25. International Features

**Covers:** `<locale.h>` and locale categories, multibyte and wide characters, digraphs and trigraphs, universal character names, and C99 wide-character headers.


<Levels label="Chapter 25, International Features">

<Level name="Beginner">

A locale sets the cultural rules a program follows: decimal point, currency, character classification. `setlocale(LC_ALL, "")` adopts the user's locale; by default every C program starts in the plain "C" locale.

</Level>

<Level name="Intermediate">

Multibyte characters (like UTF-8) take a varying number of bytes; wide characters (`wchar_t`) take a fixed number. Functions convert between the two (`mbstowcs`, `wcstombs`). `<wchar.h>` and `<wctype.h>` provide wide versions of the string and classification functions.

</Level>

<Level name="Advanced">

Locale categories can be set separately (`LC_NUMERIC`, `LC_CTYPE`, `LC_TIME`). Trigraphs and digraphs are alternate spellings of `#`, `[` and others for keyboards without them; universal character names write any Unicode character as `\u` followed by hex digits.

</Level>

<Level name="Edge cases">

After `setlocale`, `printf("%f")` may print a comma as the decimal point, so a CSV writer suddenly emits broken files on a German machine. `strlen` on UTF-8 counts bytes, not characters.

</Level>

<Level name="Corner cases">

The size of `wchar_t` is 16 bits on Windows and 32 on most Unix systems, so a character outside the Basic Multilingual Plane is one `wchar_t` on Linux and two on Windows, and code that counts them is wrong on one platform.

</Level>

<Level name="Production level">

Production code keeps data formats locale-independent (parse and print machine data in the "C" locale), uses UTF-8 end to end, and does real text work (case folding, segmentation) with a Unicode library.

</Level>

<Level name="Mindset">

Text is not bytes. The moment a program talks to people, I ask which characters, which language and which rules.

</Level>

<Level name="System design">

Internationalisation is a system concern: storage, APIs, logs and UI all have to agree on an encoding. Most text bugs are two components each correct about a different encoding.

</Level>

<Level name="Strategy">

I write a program that prints a number and a non-ASCII string under two locales and counts characters in UTF-8 correctly. Done when I can say where the encoding is decided at each step.

</Level>

</Levels>

### 26. Miscellaneous Library Functions

**Covers:** `<stdarg.h>` variable arguments, the general utilities in `<stdlib.h>` (conversion, random numbers, communication with the environment, searching and sorting, integer arithmetic), and `<time.h>`.


<Levels label="Chapter 26, Miscellaneous Library Functions">

<Level name="Beginner">

`<stdarg.h>` lets a function take a variable number of arguments, like `printf`: `va_start`, `va_arg`, `va_end`. `<stdlib.h>` has `strtol`, `strtod`, `rand`, `qsort`, `bsearch`, `getenv`, `system` and `exit`. `<time.h>` has `time`, `clock`, `localtime` and `strftime`.

</Level>

<Level name="Intermediate">

A variadic function needs some way to know how many arguments there are and their types: a count, a format string or a sentinel. `qsort` and `bsearch` take a comparison function pointer. `atexit` registers cleanup to run at exit.

</Level>

<Level name="Advanced">

Variadic arguments get default promotions: `float` arrives as `double`, `char` and `short` as `int`. `rand` is a small pseudo-random generator with implementation-defined quality. `time_t` is an arithmetic type of unspecified meaning; `difftime` subtracts two times portably.

</Level>

<Level name="Edge cases">

A comparison function written as `return a - b;` overflows for large values of opposite sign and sorts wrongly; compare explicitly. `va_arg` with the wrong type is undefined, and nothing checks it.

</Level>

<Level name="Corner cases">

`localtime` returns a pointer to a static buffer shared across calls, so two calls in one `printf` print the same time twice. `rand() % n` is biased when `n` does not divide the generator's range.

</Level>

<Level name="Production level">

Production code never uses `rand` for anything security-related, uses the platform's monotonic clock to measure durations (wall-clock time can jump), and validates `getenv` values like any other input.

</Level>

<Level name="Mindset">

Every convenience function has a hidden contract: shared state, promotions, bias. I read the contract before the convenience.

</Level>

<Level name="System design">

Time is a distributed-systems problem in miniature: wall-clock versus monotonic, time zones, and two readings that cannot be compared directly. That comes back in phase 10.

</Level>

<Level name="Strategy">

I write a variadic `sum_ints(count, ...)`, a correct `qsort` comparator, and a timer that uses `clock` and `time` for the right jobs. Done when the comparator is overflow-safe and tested at the extremes.

</Level>

</Levels>

### 27. Additional C99 Support for Mathematics

**Covers:** `<stdint.h>` integer types and limits, `<inttypes.h>` format macros, complex numbers and `<complex.h>`, type-generic math in `<tgmath.h>`, and the floating-point environment in `<fenv.h>`.


<Levels label="Chapter 27, Additional C99 Support for Mathematics">

<Level name="Beginner">

`<stdint.h>` gives integer types of exact or minimum width: `int32_t`, `uint8_t`, `int_least16_t`, `intmax_t`, with their limits (`INT32_MAX`). `<inttypes.h>` gives the matching `printf` and `scanf` format macros.

</Level>

<Level name="Intermediate">

Printing an `int64_t` portably is `printf("%" PRId64 "\n", x)`. C99 adds complex numbers as a real type: `double complex z = 1.0 + 2.0 * I;`, with `<complex.h>` functions like `cabs` and `csqrt`. `<tgmath.h>` picks the right math function for the argument type.

</Level>

<Level name="Advanced">

`<fenv.h>` exposes the floating-point environment: status flags (overflow, division by zero, inexact), rounding modes, and functions to test and clear them. The `FENV_ACCESS` pragma tells the compiler the program reads or changes that environment.

</Level>

<Level name="Edge cases">

The exact-width types are optional: a platform without an 8-bit byte has no `uint8_t`, while the `least` and `fast` variants always exist. `printf("%ld", x)` for an `int64_t` works on Linux and breaks on Windows, where `long` is 32 bits.

</Level>

<Level name="Corner cases">

Changing the rounding mode without `FENV_ACCESS ON` lets the compiler fold constants at compile time with the default mode, so the run-time mode change seems to do nothing for some expressions and work for others.

</Level>

<Level name="Production level">

Production code uses `<stdint.h>` types for every on-disk and on-wire field, `PRId64`-style macros for printing them, and checks floating-point status flags in numeric code where silent overflow would be wrong.

</Level>

<Level name="Mindset">

Exactness is a choice I write down. When the width or the rounding matters, the type says so.

</Level>

<Level name="System design">

Fixed-width integers are the vocabulary of every binary protocol and file format, and of the typed arrays in JavaScript. The floating-point environment is shared process state, like a global that every thread can change.

</Level>

<Level name="Strategy">

I write a binary record reader with `<stdint.h>` types that prints with `<inttypes.h>` macros, and a small program that triggers and reads each floating-point flag. Done when it builds and prints identically with `-m32` and `-m64`.

</Level>

</Levels>

## Misreadings to avoid

- "It compiled and it ran, so it is correct." Undefined behaviour can do anything, including work today.
- "An array is a pointer." An array decays to a pointer in most expressions, but `sizeof` and `&` see the array.
- "A string has a length." A C string has a terminator; its length is something you compute.
- "`free` makes the pointer null." It does not. The pointer keeps its old value and now points at nothing.
- "C is just low-level JavaScript." C has no runtime to catch mistakes. The habits transfer; the safety nets do not.
