## Why this book

This is the primary book for <a href={withBase('/plans/traditional-software-developer/#strategy-3')}>phase 3, data structures</a>
of the traditional core. It is the book I would keep open beside the
from-scratch library, because every structure in it comes with an API, a
working implementation, a cost model and an experiment that checks the cost
model. That last part is why it is on the spine: it treats performance as a
hypothesis to test, not a fact to memorise.

The book's code is Java. I do not need to write Java to use it. I read the
Java, then write the structure again in TypeScript, which is the language
the plan picks for this phase. The examples on this page are TypeScript.

## How I would learn it

I would not read this book front to back. I would read one section, close
it, and write the structure in TypeScript from a blank file with a test file
open beside it. Then I would open the booksite's Java and compare: what did
they do that I did not, and why? The differences go in the README's "what I
got wrong" section.

The part I would slow down for is 3.3. Red–black trees are where most people
memorise rotations and forget them a month later. I would draw the 2-3 tree
first, every time, and only then the red–black tree it encodes. If I cannot
draw the 2-3 tree, I do not understand the rotation.

Every structure gets a property-based test against `Map`, `Set` or a sorted
array, and one benchmark with a number in the README. The video lectures on
the booksite and the free Coursera course are a good second pass for the
sections that do not stick, but one source per topic is the rule, so they are
for review, not for a first read.

## Chapters 3 and 4: symbol tables and graphs

### 3. Searching

**Covers:** The sections are 3.1 Symbol Tables, 3.2 Binary Search Trees, 3.3 Balanced
Search Trees, 3.4 Hash Tables and 3.5 Applications.

- **Symbol tables.** Put a key with a value, get the value for a key. An
  ordered symbol table also answers min, max, floor, ceiling, rank and range
  queries. Sequential search in a linked list and binary search in a sorted
  array are the two baselines.
- **Binary search trees.** Each node's left subtree holds smaller keys and
  its right subtree larger ones. Fast on random input, a linked list on
  sorted input. Hibbard deletion replaces a node with its successor.
- **Balanced search trees.** 2-3 trees keep perfect balance by allowing nodes
  with two keys. Left-leaning red–black trees encode a 2-3 tree as a binary
  tree, using rotations and colour flips.
- **Hash tables.** Turn the key into an array index. Separate chaining keeps a
  list per slot; linear probing walks to the next free slot. Both need a good
  hash function and resizing.
- **Applications.** Sets, deduplication, dictionary lookup, indexes and
  inverted indexes, and sparse vectors.

<Compare left="Ordered symbol table (red–black BST)" right="Hash table" caption="Choosing between the two implementations in the chapter" rows={[["get, put: about lg N, guaranteed", "get, put: constant on average, with a good hash"], ["keeps keys in order", "keys in no useful order"], ["min, max, floor, rank, range queries", "no ordered operations"], ["needs a compare function", "needs hash and equality that agree"], ["no resizing pause", "resizing copies every key"]]} />

<Levels label="Chapter 3, Searching">

<Level name="Beginner">


A JavaScript `Map` is a symbol table. A BST is the simplest one I can build
that also keeps keys in order:

```ts
type Node<K, V> = { key: K; val: V; left?: Node<K, V>; right?: Node<K, V>; size: number };

function get<K, V>(x: Node<K, V> | undefined, key: K, cmp: (a: K, b: K) => number): V | undefined {
  while (x) {
    const c = cmp(key, x.key);
    if (c === 0) return x.val;
    x = c < 0 ? x.left : x.right;
  }
  return undefined;
}
```


</Level>
<Level name="Intermediate">


Keeping a `size` field in every node turns the BST into an ordered symbol
table: `rank(key)` (how many keys are smaller) and `select(k)` (the k-th
smallest key) both walk one path. For hashing, the chapter's two methods
differ in what happens on a collision: chaining appends to a list in the
slot, linear probing tries the next slot. Linear probing must resize before
the table gets near full, because clusters grow and merge.


</Level>
<Level name="Advanced">


A 2-3 tree grows at the root, not at the leaves, which is why every path from
the root to a leaf has the same length. The left-leaning red–black tree is a
2-3 tree in disguise: a red link glues two nodes into one 3-node. Three local
moves keep it valid on insert: rotate left when a right link is red, rotate
right when two left links in a row are red, flip colours when both children
are red. The height stays at most about 2 lg N. For hashing, the analysis
assumes uniform hashing; under that assumption a search in linear probing
touches about 1.5 slots on a hit when the table is half full.


</Level>
<Level name="Edge cases">


- `put` with an existing key replaces the value, it does not add a second
  node.
- `delete` of a node with two children: Hibbard deletion is correct but makes
  a random tree less balanced over many deletes.
- Deleting from a linear-probing table cannot just empty a slot, because that
  breaks the probe chain for keys after it. The book reinserts the rest of the
  cluster.
- `floor` of a key smaller than every key returns nothing; decide how.


</Level>
<Level name="Corner cases">


- Keys inserted in sorted order turn an unbalanced BST into a linked list of
  height N. This is the normal case for timestamps and auto-increment ids.
- A hash and an equality that disagree (two equal keys with different hashes)
  give a table that loses entries.
- A mutable key changed after insertion is now in the wrong slot or the
  wrong subtree, and no lookup will find it.
- An attacker who knows the hash function can send keys that all collide.
  Language runtimes randomise their string hash seeds for this reason.


</Level>
<Level name="Production level">


Most production lookups are hash tables (`Map`, `Set`, a Redis hash). Ordered
trees win when the query is a range: "all orders between two timestamps",
"the next scheduled job". In databases the ordered structure is a B-tree,
covered in chapter 6, because a disk page holds hundreds of keys and a
binary tree would read one page per level. Resizing a large hash table is a
latency spike, which is why some systems resize incrementally.


</Level>
<Level name="Mindset">


The question is never "which is fastest", it is "which operations do I
need". If I need order, I pay for a tree. If I need only equality, I take the
hash table and its assumptions, and I write those assumptions down.


</Level>
<Level name="System design">


An index is a symbol table from a key to the place a record lives. An
inverted index maps each word to the documents that contain it, which is the
core of a search engine. A cache is a symbol table with an eviction policy.
Choosing a tree or a hash table for an index decides which queries the system
can answer cheaply for its whole life.


</Level>
<Level name="Strategy">


Build the BST with size fields, then the left-leaning red–black tree, then a
linear-probing hash table with resizing and correct deletion. Property-test
all three against `Map` with random operations. Benchmark inserting a
million sorted keys into the plain BST and the red–black tree, and record the
heights. Done when I can draw the three red–black fix-ups from
memory and say which 2-3 tree move each one mirrors.


</Level>

</Levels>


### 4. Graphs

**Covers:** The sections are 4.1 Undirected Graphs, 4.2 Directed Graphs, 4.3 Minimum
Spanning Trees and 4.4 Shortest Paths.

- **Undirected graphs.** The adjacency-list representation, depth-first
  search for paths and connected components, breadth-first search for
  shortest paths in edge count, and detection of cycles and bipartiteness.
- **Directed graphs.** Reachability, cycle detection, topological order on a
  directed acyclic graph, and strong components with Kosaraju–Sharir.
- **Minimum spanning trees.** The cut property: the lightest edge crossing
  any cut belongs to some MST. Prim grows one tree; Kruskal adds the lightest
  edges that do not form a cycle, using union–find.
- **Shortest paths.** Edge relaxation, Dijkstra for non-negative weights,
  the topological-order algorithm for acyclic graphs (which also gives
  longest paths and critical paths), and Bellman–Ford for negative weights
  and negative-cycle detection.

  │    │        adj[1] = [0, 3]
  2 ── 3        adj[2] = [0, 3]
                adj[3] = [1, 2]
  each edge is stored twice, once at each end
`} />

<Levels label="Chapter 4, Graphs">

<Level name="Beginner">


A graph is a set of vertices and the edges between them. The adjacency list is
the default representation: for each vertex, the list of its neighbours.

```ts
const adj: number[][] = Array.from({ length: 4 }, () => []);
function addEdge(v: number, w: number) { adj[v].push(w); adj[w].push(v); }
```

BFS from a source visits vertices in order of distance in edges, so the first
time it reaches a vertex is along a shortest path.


</Level>
<Level name="Intermediate">


DFS and BFS are the same loop with a different container: a stack (or
recursion) for DFS, a queue for BFS. Topological sort is the reverse of the
DFS postorder. Dijkstra is BFS with a priority queue keyed by distance.

```ts
function bfs(adj: number[][], s: number) {
  const dist = new Array(adj.length).fill(Infinity);
  const queue = [s]; dist[s] = 0;
  for (let head = 0; head < queue.length; head++) {
    const v = queue[head];
    for (const w of adj[v]) if (dist[w] === Infinity) { dist[w] = dist[v] + 1; queue.push(w); }
  }
  return dist;
}
```

Using an index into the array instead of `queue.shift()` keeps it linear;
`shift` is linear per call in the worst case.


</Level>
<Level name="Advanced">


Every shortest-path algorithm in the chapter is "relax edges until no edge
can be relaxed", differing only in the order. Dijkstra relaxes in order of
distance, which is correct only because non-negative weights mean a vertex's
distance is final when it leaves the priority queue. The acyclic algorithm
relaxes in topological order, which is linear and allows negative weights.
Bellman–Ford relaxes every edge V−1 times, and a relaxation in round V
proves a negative cycle. The MST algorithms are all instances of the greedy
rule from the cut property.


</Level>
<Level name="Edge cases">


- A disconnected graph: run the search from every unvisited vertex.
- Self-loops and parallel edges: the adjacency list stores them; decide
  whether the problem allows them.
- Recursive DFS on a path of a million vertices overflows the call stack in
  JavaScript. Write the iterative version.
- Dijkstra with a zero-weight edge is fine; with a negative one it is wrong.


</Level>
<Level name="Corner cases">


- A negative cycle makes "shortest path" undefined for every vertex it can
  reach. Bellman–Ford must report it, not return a number.
- Equal edge weights give more than one MST; tests must check the total
  weight, not a specific edge set.
- Topological sort on a graph with a cycle must fail loudly. A build tool that
  silently picks an order is a bug.
- An unweighted graph run through Dijkstra works, but BFS is simpler and
  faster.


</Level>
<Level name="Production level">


Graphs are everywhere I already work: module imports (a cycle is a build
error), task dependencies (topological order), package resolution, social
connections, routing. The production questions are size and freshness: does
the graph fit in memory, how often does it change, and is the answer allowed
to be slightly stale? Route planners precompute heavily because running a
plain Dijkstra on a continent per request is too slow.


</Level>
<Level name="Mindset">


Before choosing an algorithm, I name the graph: directed or not, weighted or
not, negative weights or not, cycles or not, dense or sparse. Those five
answers pick the algorithm almost by themselves.


</Level>
<Level name="System design">


A dependency graph is how a build system decides what to rebuild, how a
package manager installs in order, and how a scheduler runs jobs. A cycle
detector is a safety check in all three. Bellman–Ford's negative-cycle check
is the textbook arbitrage detector. Kruskal with union–find is also a
clustering algorithm: stop before the last k−1 edges and the components are
k clusters.


</Level>
<Level name="Strategy">


Implement the graph type, iterative DFS, BFS, topological sort with cycle
detection, Kruskal with my union–find, Dijkstra with my heap, and
Bellman–Ford. Feed them the book's small test graphs from the booksite and
compare outputs. Then build the plan's route planner on a small road graph. Done
when I can say why Dijkstra fails on a negative edge with a
three-vertex counterexample.


</Level>

</Levels>

## Chapters 5 and 6: strings and the wider context

### 5. Strings

**Covers:** The sections are 5.1 String Sorts, 5.2 Tries, 5.3 Substring Search, 5.4
Regular Expressions and 5.5 Data Compression.

- **String sorts.** LSD radix sort for fixed-length keys, MSD radix sort for
  variable-length keys, and three-way string quicksort, which handles long
  common prefixes well. They use characters as array indexes instead of
  comparing whole strings.
- **Tries.** An R-way trie branches on each character, so search cost depends
  on the key length, not the number of keys. A ternary search trie uses far
  less space. Both support prefix queries.
- **Substring search.** Brute force, Knuth–Morris–Pratt (never back up in
  the text, using a precomputed automaton), Boyer–Moore (scan the pattern
  from the right and skip) and Rabin–Karp (compare rolling hashes).
- **Regular expressions.** A regular expression compiles to a
  nondeterministic finite automaton, and grep simulates it by tracking the
  set of states it could be in.
- **Data compression.** Run-length coding, Huffman codes built greedily from
  frequencies, and LZW, which builds a dictionary of substrings as it reads.

<Levels label="Chapter 5, Strings">

<Level name="Beginner">


A trie stores strings by their characters: the path from the root spells the
key. Looking up a word costs one step per character, however many words are
stored.

```ts
type Trie = { end?: boolean; next: Map<string, Trie> };
function insert(t: Trie, word: string) {
  for (const ch of word) {
    if (!t.next.has(ch)) t.next.set(ch, { next: new Map() });
    t = t.next.get(ch)!;
  }
  t.end = true;
}
```


</Level>
<Level name="Intermediate">


KMP is the one to understand deeply. When a mismatch happens after matching
part of the pattern, the matched part is already known, so the text pointer
never needs to move back. The book builds this as a deterministic finite
automaton; the common variant is the failure (prefix) function:

```ts
function prefixFunction(p: string): number[] {
  const pi = new Array(p.length).fill(0);
  for (let i = 1, k = 0; i < p.length; i++) {
    while (k > 0 && p[i] !== p[k]) k = pi[k - 1];
    if (p[i] === p[k]) k++;
    pi[i] = k;
  }
  return pi; // pi[i] = longest proper prefix of p[0..i] that is also a suffix
}
```


</Level>
<Level name="Advanced">


KMP guarantees linear time in the text plus the pattern. Boyer–Moore is often
sublinear in practice because it can skip ahead by the pattern length.
Rabin–Karp is a Monte Carlo algorithm if it trusts a hash match, and a Las
Vegas one if it checks each match. The regular-expression NFA simulation runs
in time proportional to the text length times the pattern length, with no
exponential blow-up. Huffman coding is optimal among prefix-free codes for
known symbol frequencies, proved by an exchange argument.


</Level>
<Level name="Edge cases">


- The empty pattern matches at position 0; decide and test it.
- A pattern longer than the text matches nowhere.
- Overlapping matches: "aa" in "aaaa" occurs three times, and a search that
  skips past each match finds only two.
- Huffman on an input with one distinct symbol needs a code of at least one
  bit, not zero.


</Level>
<Level name="Corner cases">


- JavaScript strings are UTF-16. `for...of` iterates code points, indexing
  iterates code units, and a trie built one way will not find keys searched
  the other way. Emoji and many scripts expose this.
- Unicode normalisation: "é" can be one code point or two. Two equal-looking
  keys can be different strings.
- Backtracking regex engines (including JavaScript's) can take exponential
  time on patterns like `(a+)+$` with a crafted input. The NFA simulation in
  the book cannot.


</Level>
<Level name="Production level">


Autocomplete is a trie or a sorted array with prefix search. Log search and
`grep` are substring search at scale. Regular-expression denial of service
(ReDoS) is a real class of outage. Compression is in every HTTP response
(gzip, Brotli), and its cost is CPU traded for bandwidth. In production I
almost never write KMP; I need to know when the library's choice will be slow
and when a regex is the wrong tool.


</Level>
<Level name="Mindset">


Strings are not just arrays of letters. Their alphabet size, their encoding
and their shared prefixes are the structure that the fast algorithms exploit.
Asking "what is the alphabet and how long are the keys?" comes first.


</Level>
<Level name="System design">


A search box is a stack of this chapter: a trie or prefix index for
suggestions, an inverted index for documents, a regex or substring search for
filters, and compression on the wire. Putting user-supplied regular
expressions into a backtracking engine is a design decision with a security
cost.


</Level>
<Level name="Strategy">


Implement the trie, KMP, Rabin–Karp and Huffman coding. Build the plan's
string search tool: KMP for one pattern, a trie for many words. Test it with
Unicode input on purpose. Done when I can compute the prefix
function of "ababaca" by hand and explain what each value lets the search
skip.


</Level>

</Levels>


### 6. Context

**Covers:** The booksite lists the chapter as under construction online; the printed
chapter connects the book's ideas to other fields. Its programs cover event-
driven simulation, B-trees, suffix arrays, maximum flow and minimum cut,
bipartite matching, linear programming, and intractability.

- **Event-driven simulation.** A priority queue of future events, processed
  in time order, instead of ticking a clock.
- **B-trees.** A balanced search tree whose nodes are disk pages holding many
  keys, so a search reads very few pages.
- **Suffix arrays.** Sort all suffixes of a text, then answer substring and
  longest-repeated-substring questions with binary search.
- **Network flow.** Ford–Fulkerson augmenting paths, and the max-flow min-cut
  theorem.
- **Reductions and intractability.** Solving one problem by transforming it
  into another, and the problems no one knows how to solve quickly.

<Levels label="Chapter 6, Context">

<Level name="Beginner">


A B-tree is the answer to "why do databases not use binary trees?". Reading
a disk page is slow and a page holds hundreds of keys, so each node should be
a whole page with hundreds of children. A tree of a billion keys is then only
a few levels deep.


</Level>
<Level name="Intermediate">


A suffix array for "banana" is the start positions of its suffixes in sorted
order: a, ana, anana, banana, na, nana. Any substring is a prefix of some
suffix, so binary search over the sorted suffixes finds every occurrence.


</Level>
<Level name="Advanced">


The max-flow min-cut theorem says the most that can flow from source to sink
equals the smallest total capacity of edges whose removal separates them.
Many problems reduce to it: bipartite matching, project selection, image
segmentation. A reduction turns a new problem into a solved one, which is the
habit the chapter is really teaching.


</Level>
<Level name="Edge cases">


- A B-tree node that splits at the root is how the tree grows taller; every
  leaf stays at the same depth.
- A suffix array of a text with many repeats takes longer to build with a
  naive sort, because comparisons are long.


</Level>
<Level name="Corner cases">


- Ford–Fulkerson with irrational capacities may not terminate; with integer
  capacities it does, and choosing shortest augmenting paths bounds the
  number of rounds.
- A reduction proves hardness only in the right direction: reducing a known
  hard problem to mine shows mine is hard, not the other way round.


</Level>
<Level name="Production level">


Every relational database index I will touch in phase 8 is a B-tree or a
B+-tree. Suffix arrays and their relatives sit inside full-text search and
genome tools. Flow and matching show up in assignment problems: matching
drivers to riders or reviewers to papers.


</Level>
<Level name="Mindset">


Context is the point: the structures in chapters 1–5 are not exercises, they
are parts of real systems. When I meet a new problem, the first question is
which old problem it reduces to.


</Level>
<Level name="System design">


Event-driven simulation is how I would test a scheduler or a queueing system
without waiting for real time. A B-tree is the storage engine decision. A
reduction to flow or linear programming lets a team use a solver instead of
writing a bespoke algorithm.


</Level>
<Level name="Strategy">


Read this chapter last and lightly. Write a small in-memory B-tree with
splits, because phase 8 needs it, and a naive suffix array for the
longest-repeated-substring problem. Done when I can explain in
two minutes why a B-tree's height grows so slowly.


</Level>

</Levels>

## Misreadings to avoid

- **Chapter 1.** "Amortised" does not mean "average over random inputs". It is a worst-case guarantee over any sequence of operations.
- **Chapter 1.** The doubling test predicts growth, not absolute time. A different machine shifts the constant, not the exponent.
- **Chapter 1.** Path compression alone is not the whole story; the bound in the book comes from combining it with weighting.
- **Chapter 2.** "Quicksort is N log N." Only in expectation, and only with a random pivot or a shuffle.
- **Chapter 2.** "Heapsort is the best because its worst case is N log N." It has poor locality, so it is usually slower than quicksort on real hardware.
- **Chapter 2.** "Stability does not matter if the output is sorted." It decides what happens to equal keys, which matters as soon as records carry more than the key, such as sorting by city after sorting by name.
- **Chapter 3.** "Hash tables are O(1)." On average, under an assumption about the hash function, with resizing amortised. The worst case is linear.
- **Chapter 3.** "A red–black tree is perfectly balanced." Its black height is; the real height can be up to about twice the best possible.
- **Chapter 3.** "BSTs are obsolete." Ordered operations are the reason they exist.
- **Chapter 4.** "DFS finds shortest paths." Only BFS does, and only in edge count.
- **Chapter 4.** "Dijkstra works on any weighted graph." Not with negative weights.
- **Chapter 4.** "An MST gives shortest paths." It minimises total edge weight, not the distance between two vertices.
- **Chapter 5.** "Tries are always memory-hungry." The R-way trie is; the ternary search trie and compressed (radix) tries are not.
- **Chapter 5.** "Regex is a string search." It is an automaton, and the engine type decides whether it can blow up.
