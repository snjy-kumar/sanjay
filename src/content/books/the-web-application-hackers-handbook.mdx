## Why this book

This is the optional depth for phase 11 of the
<a href={withBase('/plans/traditional-software-developer/')}>traditional core</a>,
software engineering and security, and it sits on the reference shelf of the
<a href={withBase('/plans/software-ai-developer/')}>software AI developer</a> plan.
*Security Engineering* gives me the system view; this book gives me the
attacker's method against the thing I actually build every day, a web
application.

The second edition is from 2011, so some technology in it is dated (Java
applets, Flash, Silverlight). The method is not: map the application,
find where it trusts the client, and test every one of those trusts. I
read it as a defender. Every technique here I try only against my own
applications or against deliberately vulnerable practice labs, never
against a system I do not own.

## How I would learn it

I would pair every chapter with the matching topic in PortSwigger's free
Web Security Academy, which is current and has a lab for nearly every
attack class in the book. Read the chapter, do the labs, then go back to
my own capstone and look for the same bug. I keep the book's methodology
chapter open the whole time as the checklist.

For every attack I write the defence as a test in my capstone: a request
that should be refused, asserted in CI. The book is finished for me when
the self-review against the OWASP Top 10 that phase 11 asks for is a list
of tests, not a list of opinions.

## The 21 chapters

### 1. Web Application (In)security

**Covers:** How web applications evolved, why they are so often insecure, and the core problem behind it: users can submit arbitrary input.

<Levels label="Chapter 1, Web Application (In)security">
<Level name="Beginner">

A web application runs on a server and takes requests from anyone. Everything in a request is chosen by the sender.

</Level>
<Level name="Intermediate">

The core problem is that the client is not under my control. Hidden fields, headers, cookies and the order of requests are all input.

</Level>
<Level name="Advanced">

The security perimeter moved: it used to be the network firewall, now it is the application's own code, because the application must accept traffic from the internet to work.

</Level>
<Level name="Edge cases">

An internal admin app reached only through a VPN still trusts every employee's browser, and every browser extension in it.

</Level>
<Level name="Corner cases">

A feature built quickly, plus an assumption that "only our frontend calls this", is how most vulnerabilities ship.

</Level>
<Level name="Production level">

I assume every endpoint will be called directly with hostile values, by tools such as `curl` or an intercepting proxy, not only by my UI.

</Level>
<Level name="Mindset">

The frontend is a convenience for honest users. The server is the only place a rule is enforced.

</Level>
<Level name="System design">

APIs, background jobs fed by user data and third-party webhooks are all part of the web attack surface.

</Level>
<Level name="Strategy">

I list every endpoint in my capstone and mark which ones trust anything about the client. Done when each such trust is removed or has a written reason.

</Level>
</Levels>

### 2. Core Defense Mechanisms

**Covers:** The defences every application needs: handling user access, handling user input, handling attackers, and managing the application.

<Flow steps={["Receive request", "Authenticate", "Authorise", "Validate input", "Process", "Encode output", "Log"]} caption="The core defences as a request passes through. Each step is a place to stop an attack." />

<Levels label="Chapter 2, Core Defense Mechanisms">
<Level name="Beginner">

Four jobs: control who gets in and what they can do, handle input safely, deal with attackers when they appear, and protect the admin side.

</Level>
<Level name="Intermediate">

Input handling has approaches: reject known bad, accept known good, sanitise, safe data handling and semantic checks. Accepting known good is the strongest.

```ts
import { z } from 'zod';
const Body = z.object({ email: z.string().email(), age: z.number().int().min(13).max(120) });
const body = Body.parse(await req.json()); // throws on anything else
```

</Level>
<Level name="Advanced">

Validate at the boundary, then encode for each output context: HTML, SQL, shell, URL. Validation and encoding solve different problems and both are needed.

</Level>
<Level name="Edge cases">

Canonicalisation: `%2e%2e%2f` is `../` after decoding. Validate after decoding, once, or decode twice and be fooled.

</Level>
<Level name="Corner cases">

Input validated in one service and used in another that decodes it again combines two correct steps into a bypass.

</Level>
<Level name="Production level">

Handling attackers means logging security events, alerting on them and reacting: lock an account, block an IP, raise a ticket.

</Level>
<Level name="Mindset">

Defence in depth: assume each layer will sometimes fail, and make sure the next one catches it.

</Level>
<Level name="System design">

Admin interfaces are part of the application and often the weakest part. They need the same controls, and usually more.

</Level>
<Level name="Strategy">

I check each request path in my capstone against the flow above. Done when every endpoint has authentication, authorisation, schema validation and output encoding, with a test for each.

</Level>
</Levels>

### 3. Web Application Technologies

**Covers:** The technologies an attacker must understand: HTTP, web functionality on the server and the client, state and sessions, and encoding schemes.

<Levels label="Chapter 3, Web Application Technologies">
<Level name="Beginner">

HTTP is text requests and responses: a method, a path, headers and a body. Cookies add state to a stateless protocol.

</Level>
<Level name="Intermediate">

Encodings layer up: URL encoding, HTML entities, Base64, Unicode. An attacker uses them to slip input past filters.

</Level>
<Level name="Advanced">

Methods have meanings: GET should be safe and idempotent. A GET that changes state can be triggered by an image tag on another site.

</Level>
<Level name="Edge cases">

Header and parameter duplication: two `id` parameters may be read differently by the proxy and the app.

</Level>
<Level name="Corner cases">

A CDN that caches by path, plus an app that varies the response by a header, can serve one user's page to another.

</Level>
<Level name="Production level">

I set cookies with `HttpOnly`, `Secure` and `SameSite`, and I know exactly which headers my CDN uses as cache keys.

</Level>
<Level name="Mindset">

Read the raw request. Frameworks hide HTTP, and attacks live in what is hidden.

</Level>
<Level name="System design">

Every hop (browser, CDN, load balancer, app) parses HTTP. Differences between their parsers are an attack class of their own.

</Level>
<Level name="Strategy">

I watch my capstone's traffic in the browser's network tab and a local intercepting proxy for an hour. Done when I can explain every header on a login request and its response.

</Level>
</Levels>

### 4. Mapping the Application

**Covers:** Finding the attack surface: enumerating content and functionality, analysing the application, and identifying the entry points for user input and the server-side technologies.

<Levels label="Chapter 4, Mapping the Application">
<Level name="Beginner">

Before testing, map: every page, endpoint, parameter and function. Unmapped code is untested code.

</Level>
<Level name="Intermediate">

Mapping combines browsing through a proxy, crawling, reading JavaScript bundles for API routes, and guessing common paths.

</Level>
<Level name="Advanced">

Each entry point gets a note: what input it takes, what it does with it, what technology handles it. That table drives the rest of the test.

</Level>
<Level name="Edge cases">

Hidden routes: old API versions, debug endpoints and admin paths that are not linked but still answer.

</Level>
<Level name="Corner cases">

A source map shipped to production, plus an unlinked admin route, hands an attacker the map and the door.

</Level>
<Level name="Production level">

I generate my route list from the code (the router table or OpenAPI spec) and compare it to what a crawler finds. Differences are findings.

</Level>
<Level name="Mindset">

The attacker's map is better than mine unless I make mine first.

</Level>
<Level name="System design">

An up-to-date API specification is a security artefact. It is the inventory every other review relies on.

</Level>
<Level name="Strategy">

I build an entry-point table for my capstone: route, method, parameters, auth required. Done when it matches the router exactly and lives in the repository.

</Level>
</Levels>

### 5. Bypassing Client-Side Controls

**Covers:** Why controls in the browser cannot be trusted: data sent through the client (hidden fields, cookies, URL parameters), capturing user data in forms and scripts, and handling client-side data securely.

<Compare left="Client-side check" right="Server-side check" rows={[["maxlength on an input", "Length validated on the server"], ["Price in a hidden field", "Price looked up by product ID"], ["Button hidden for non-admins", "Role checked in the handler"]]} caption="Every left-hand check is a hint. Only the right-hand column is a control." />

<Levels label="Chapter 5, Bypassing Client-Side Controls">
<Level name="Beginner">

Anything in the browser can be changed by the user: hidden fields, disabled buttons, JavaScript checks.

</Level>
<Level name="Intermediate">

A client-side check improves usability; the server must repeat it. A price, a role or a discount sent from the client is a value the attacker chooses.

</Level>
<Level name="Advanced">

Opaque data (encoded or encrypted tokens) can still be replayed, swapped between users or tampered with if the server does not bind and verify it.

</Level>
<Level name="Edge cases">

Negative quantities and zero prices: a client that only offers 1 to 10 does not stop a request with -5.

</Level>
<Level name="Corner cases">

A signed token that is valid but issued for another user or another purpose: valid signature plus wrong context.

</Level>
<Level name="Production level">

The server looks up every authoritative value (price, owner, role) itself. Client-sent values are requests, never facts.

```ts
const product = await db.product.findUniqueOrThrow({ where: { id: body.productId } });
const total = product.priceCents * body.qty; // never body.price
```

</Level>
<Level name="Mindset">

If the browser can see it, the user can change it.

</Level>
<Level name="System design">

Thin clients, authoritative servers. In single-page apps the API is the real application.

</Level>
<Level name="Strategy">

I replay my capstone's checkout and settings requests with edited values from an intercepting proxy. Done when every edit is rejected by the server and a test covers each.

</Level>
</Levels>

### 6. Attacking Authentication

**Covers:** How login fails: authentication technologies, design flaws (weak passwords, brute force, verbose failure messages, password change and recovery, "remember me", impersonation), implementation flaws, and securing authentication.

<Levels label="Chapter 6, Attacking Authentication">
<Level name="Beginner">

Authentication proves who a user is. Its weak points are guessing, stealing and the side doors such as recovery.

</Level>
<Level name="Intermediate">

Brute force and credential stuffing are stopped by rate limits, lockout or delays, breached-password checks and a second factor.

</Level>
<Level name="Advanced">

Verbose failures ("no such user" against "wrong password") enumerate accounts. Recovery flows with guessable questions or long-lived links are bypasses.

</Level>
<Level name="Edge cases">

Multi-step logins that let the second step be reached without the first.

</Level>
<Level name="Corner cases">

A password change that does not end other sessions, plus a stolen session, keeps the attacker in after the victim "fixes" it.

</Level>
<Level name="Production level">

I use a vetted library or provider, hash with a slow function, return one generic failure, rate-limit by account and by IP, and expire recovery tokens quickly and after one use.

</Level>
<Level name="Mindset">

Every way into an account is the login. Recovery, "remember me" and support are all authentication.

</Level>
<Level name="System design">

Authentication belongs in one service or library, not reimplemented per route. Passkeys move the secret out of the server entirely.

</Level>
<Level name="Strategy">

I test my capstone's login, recovery and password change against each flaw in this chapter. Done when each flaw has a test that proves it is not present.

</Level>
</Levels>

### 7. Attacking Session Management

**Covers:** Sessions as the key to every request after login: the need for state, weaknesses in token generation, weaknesses in token handling, and securing session management.

<Levels label="Chapter 7, Attacking Session Management">
<Level name="Beginner">

After login, a session token stands in for the password. Whoever holds it is the user.

</Level>
<Level name="Intermediate">

Tokens must be unpredictable (from a secure random source), sent only over TLS, and stored in cookies the page's scripts cannot read.

```ts
import { randomBytes } from 'node:crypto';
const token = randomBytes(32).toString('base64url');
```

</Level>
<Level name="Advanced">

Session fixation: the attacker sets a token before login and the server keeps it after. Issue a new token at login.

</Level>
<Level name="Edge cases">

Logout that only clears the cookie but leaves the server session valid.

</Level>
<Level name="Corner cases">

A JWT with no server-side revocation, plus a long expiry, plus a stolen token, gives an attacker weeks.

</Level>
<Level name="Production level">

I rotate tokens at login and privilege change, expire idle sessions, invalidate on logout server-side, and set `HttpOnly`, `Secure` and `SameSite` on the cookie.

</Level>
<Level name="Mindset">

A session token is a password with a timer. Treat it with the same care.

</Level>
<Level name="System design">

Server-side sessions are easy to revoke; stateless tokens are easy to scale. The choice decides how fast I can respond to theft.

</Level>
<Level name="Strategy">

I test that my capstone issues a new token at login, kills it at logout, and expires it when idle. Done when all three have tests that pass.

</Level>
</Levels>

### 8. Attacking Access Controls

**Covers:** Broken access control: common vulnerabilities (unprotected functions, identifier-based functions, multistage functions, static files, platform misconfiguration, insecure methods), attacking access controls, and securing them.

<Levels label="Chapter 8, Attacking Access Controls">
<Level name="Beginner">

Access control decides whether this user may do this action on this object. Missing checks are the most common serious web bug.

</Level>
<Level name="Intermediate">

Insecure direct object references: changing `/invoices/1001` to `/invoices/1002` shows someone else's invoice if ownership is not checked.

```ts
const inv = await db.invoice.findFirst({ where: { id, ownerId: session.userId } });
if (!inv) return notFound(); // same answer for missing and forbidden
```

</Level>
<Level name="Advanced">

Vertical escalation reaches admin functions; horizontal escalation reaches another user's data. Both are tested by replaying one user's requests with another's session.

</Level>
<Level name="Edge cases">

Static files (exports, uploads) served without any check because they are "just files".

</Level>
<Level name="Corner cases">

A multi-step flow that checks permission on step one but not on step three, called directly.

</Level>
<Level name="Production level">

Deny by default, central authorisation, ownership in every query, and a test matrix of roles against endpoints.

</Level>
<Level name="Mindset">

Every request carries an ID. For each one ask: whose is this, and did I check?

</Level>
<Level name="System design">

Row-level security in the database is a second line behind application checks.

</Level>
<Level name="Strategy">

I run every capstone endpoint with a second user's session and IDs from the first user. Done when every attempt fails and the run is part of CI.

</Level>
</Levels>

### 9. Attacking Data Stores

**Covers:** Injection into the stores behind an application: interpreted contexts, bypassing a login, SQL injection, NoSQL injection, XPath injection, and LDAP injection.

<Compare left="Built by string" right="Parameterised" rows={[["SELECT ... WHERE email = ' + email + '", "SELECT ... WHERE email = $1, with email passed separately"], ["Input becomes code", "Input stays data"]]} caption="Injection is data crossing into code. Parameters keep it on the data side." />

<Levels label="Chapter 9, Attacking Data Stores">
<Level name="Beginner">

Injection happens when input is pasted into a query and changes its meaning. Parameterised queries stop it.

</Level>
<Level name="Intermediate">

SQL injection can read data, change it, or bypass logins. Error messages and timing let attackers extract data even when results are not shown.

</Level>
<Level name="Advanced">

NoSQL stores have their own injection: in MongoDB, an object such as `{ "$ne": null }` sent where a string was expected changes the query.

</Level>
<Level name="Edge cases">

Identifiers cannot be parameters: a sort column from the user must be checked against an allow list.

</Level>
<Level name="Corner cases">

Data stored safely, then later concatenated into a query by a reporting job: second-order injection.

</Level>
<Level name="Production level">

I use an ORM or parameterised queries everywhere, validate types at the boundary so objects cannot arrive where strings are expected, and give the app's database user only the rights it needs.

</Level>
<Level name="Mindset">

Never build code from data. Wherever strings become queries, commands or templates, stop and parameterise.

</Level>
<Level name="System design">

Least-privilege database accounts limit what a successful injection can do.

</Level>
<Level name="Strategy">

I search my capstone for every raw query and every place user input reaches a query builder. Done when none concatenates input and a test sends injection payloads to each.

</Level>
</Levels>

### 10. Attacking Back-End Components

**Covers:** Injection into the systems behind the app: OS commands, file paths, XML interpreters, back-end HTTP requests, mail services, and other back-end interfaces.

<Levels label="Chapter 10, Attacking Back-End Components">
<Level name="Beginner">

Applications pass user input to other systems: the shell, the file system, XML parsers, mail servers, other HTTP services. Each can be injected.

</Level>
<Level name="Intermediate">

Path traversal: `../../etc/passwd` as a file name. Command injection: `; rm -rf` appended to an argument passed to a shell.

```ts
import { execFile } from 'node:child_process';
execFile('convert', [inputPath, outputPath]); // no shell, arguments as a list
```

</Level>
<Level name="Advanced">

XML external entities make a parser read local files or call internal URLs. Server-side request forgery makes the server fetch an attacker-chosen URL, often an internal one.

</Level>
<Level name="Edge cases">

A URL that resolves to a public address at check time and an internal one at fetch time (DNS rebinding).

</Level>
<Level name="Corner cases">

SSRF to a cloud metadata endpoint combines a fetch feature with cloud credentials, and becomes account takeover of the infrastructure.

</Level>
<Level name="Production level">

No shell, resolved and normalised paths checked against a base directory, XML parsers with external entities off, and an egress allow list for server-side fetches.

</Level>
<Level name="Mindset">

Every interpreter my code talks to is an injection target. List them.

</Level>
<Level name="System design">

Outbound network policy is an SSRF control: services that do not need the internet should not reach it.

</Level>
<Level name="Strategy">

I list every interpreter and outbound request in my capstone. Done when each has a safe API or an allow list, and a test sends a traversal or SSRF payload to it.

</Level>
</Levels>

### 11. Attacking Application Logic

**Covers:** Flaws in the application's own reasoning, shown through a series of real-world style examples, and how to avoid logic flaws.

<Levels label="Chapter 11, Attacking Application Logic">
<Level name="Beginner">

Logic flaws are bugs in what the application does, not in how it handles input. No scanner finds them, because each is unique.

</Level>
<Level name="Intermediate">

Examples include skipping a step in a checkout, applying a discount twice, or changing a quantity after a price was approved.

</Level>
<Level name="Advanced">

They come from assumptions the developer made about how users move through the app: order, timing, repetition.

</Level>
<Level name="Edge cases">

The first and last items, empty carts, zero amounts and maximum values break assumptions about the normal case.

</Level>
<Level name="Corner cases">

Two parallel requests that each pass a "once only" check (a coupon, a free trial) because the check and the update are not atomic.

</Level>
<Level name="Production level">

I model important flows as explicit state machines on the server and reject transitions that are not allowed.

```ts
type Order = 'cart' | 'priced' | 'paid' | 'shipped';
const next: Record<Order, Order[]> = { cart: ['priced'], priced: ['paid', 'cart'], paid: ['shipped'], shipped: [] };
```

</Level>
<Level name="Mindset">

Write down every assumption a flow makes about the user, then try to break each one.

</Level>
<Level name="System design">

Business rules that matter (payments, quotas, entitlements) belong in one server-side module with its own tests.

</Level>
<Level name="Strategy">

I write the assumptions of my capstone's most valuable flow and a test that violates each. Done when every test is refused by the server.

</Level>
</Levels>

### 12. Attacking Users: Cross-Site Scripting

**Covers:** Cross-site scripting: the kinds of XSS (reflected, stored, DOM-based), what an attacker does with it, delivery mechanisms, finding and exploiting it, and preventing it.

<Levels label="Chapter 12, Attacking Users: Cross-Site Scripting">
<Level name="Beginner">

XSS is attacker-supplied script running in another user's browser on my site, with that user's session and permissions.

</Level>
<Level name="Intermediate">

Reflected XSS bounces input straight back; stored XSS saves it for every viewer; DOM-based XSS happens entirely in client code that writes untrusted data into the page.

</Level>
<Level name="Advanced">

The fix is context-aware output encoding. HTML body, attributes, URLs and script contexts each need different encoding; a framework that escapes by default covers the common ones.

```tsx
<p>{comment}</p>                                    // escaped by React
<div dangerouslySetInnerHTML={{ __html: comment }} /> // not escaped: XSS
```

</Level>
<Level name="Edge cases">

`href` values starting with `javascript:` pass HTML escaping and still run script. URLs need scheme checks.

</Level>
<Level name="Corner cases">

Markdown rendered to HTML, then sanitised, then edited by a later transform that reintroduces raw HTML: three safe steps in the wrong order.

</Level>
<Level name="Production level">

Escape by default, sanitise any HTML I must accept with a maintained sanitiser, set a strict Content Security Policy, and keep session cookies `HttpOnly`.

</Level>
<Level name="Mindset">

Every place data meets markup is a boundary. Know which context the data lands in.

</Level>
<Level name="System design">

CSP is the second line: even if an injection slips through, inline script without a nonce does not run.

</Level>
<Level name="Strategy">

I grep my capstone for every raw-HTML sink and every user-controlled URL. Done when each is removed or sanitised, a CSP blocks inline script, and an XSS payload test fails to execute.

</Level>
</Levels>

### 13. Attacking Users: Other Techniques

**Covers:** Attacks on users beyond XSS: inducing user actions (request forgery, UI redress), capturing data cross-domain, the same-origin policy revisited, other client-side injection, local privacy attacks, attacking browsers, and man-in-the-middle attacks.

<Levels label="Chapter 13, Attacking Users: Other Techniques">
<Level name="Beginner">

Cross-site request forgery makes a logged-in user's browser send a request to my site from another site. The browser attaches the cookies.

</Level>
<Level name="Intermediate">

Defences: `SameSite` cookies, anti-CSRF tokens for state-changing requests, and checking the `Origin` header. Clickjacking is stopped by forbidding framing.

</Level>
<Level name="Advanced">

The same-origin policy limits what a page can read from another origin, not what it can send. CORS relaxes reading, so a loose CORS policy undoes the protection.

</Level>
<Level name="Edge cases">

A GET endpoint that changes state is CSRF-able through an image tag, even with tokens on POST forms.

</Level>
<Level name="Corner cases">

CORS that reflects any origin with credentials allowed: a misconfiguration plus cookies gives any site read access to user data.

</Level>
<Level name="Production level">

I set `SameSite=Lax` or `Strict`, require a CSRF token or a custom header for mutations, send `frame-ancestors 'none'` in CSP, and allow-list CORS origins explicitly.

</Level>
<Level name="Mindset">

Ask what another website can make a user's browser do to mine.

</Level>
<Level name="System design">

Browser security headers are configuration of the user's browser as a defence. They belong in one shared middleware.

</Level>
<Level name="Strategy">

I build a small hostile page locally that tries to post to my capstone and to frame it. Done when both fail and the headers that stop them are tested.

</Level>
</Levels>

### 14. Automating Customized Attacks

**Covers:** Using automation for enumerating identifiers, harvesting data and fuzzing, the barriers to automation (session handling, CAPTCHAs), and how attackers get around them.

<Levels label="Chapter 14, Automating Customized Attacks">
<Level name="Beginner">

Many attacks are the same request repeated with different values: guessing IDs, trying passwords, sending payloads.

</Level>
<Level name="Intermediate">

A short script that loops over IDs and records response sizes finds which ones exist. Response differences are the signal.

</Level>
<Level name="Advanced">

Fuzzing sends unexpected values (long strings, special characters, wrong types) to every parameter and watches for errors and anomalies.

</Level>
<Level name="Edge cases">

A rate limit per IP is no limit against requests spread over many addresses.

</Level>
<Level name="Corner cases">

A CAPTCHA on login but not on the password-reset endpoint: automation moves to the unprotected path.

</Level>
<Level name="Production level">

I fuzz my own API in CI with property-based tests and a schema-aware fuzzer, and rate-limit by account as well as by IP.

```ts
import fc from 'fast-check';
fc.assert(fc.asyncProperty(fc.string(), async (s) => {
  const r = await api.post('/search', { q: s });
  return r.status === 200 || r.status === 400; // never 500
}));
```

</Level>
<Level name="Mindset">

Assume anything a person can do once, a script will do a million times.

</Level>
<Level name="System design">

Abuse prevention (bot detection, quotas, anomaly alerts) is a system that sits in front of every expensive or sensitive endpoint.

</Level>
<Level name="Strategy">

I add a property-based fuzz test to my capstone's input-handling endpoints. Done when it runs in CI and has found, and I have fixed, at least one real crash or 500.

</Level>
</Levels>

### 15. Exploiting Information Disclosure

**Covers:** What applications give away: exploiting error messages, gathering published information, using inference, and preventing information leakage.

<Levels label="Chapter 15, Exploiting Information Disclosure">
<Level name="Beginner">

Error messages, stack traces and debug pages tell attackers about the code, the database and the versions in use.

</Level>
<Level name="Intermediate">

Differences in responses leak facts: whether a user exists, whether a file exists, which branch of code ran.

</Level>
<Level name="Advanced">

Published information (old pages, comments in HTML, source maps, public repositories) often reveals internal paths and secrets.

</Level>
<Level name="Edge cases">

A debug mode left on in production, flipped by an environment variable nobody set.

</Level>
<Level name="Corner cases">

A generic error page for users, plus the full stack trace in a response header added by middleware.

</Level>
<Level name="Production level">

Generic errors to clients, detail in server logs with a correlation ID, secret scanning on the repository, and no source maps published unless intended.

```ts
app.onError((err, c) => {
  const id = crypto.randomUUID();
  log.error({ id, err });
  return c.json({ error: 'Something went wrong', id }, 500);
});
```

</Level>
<Level name="Mindset">

Every byte I return is read by an attacker. Return what the user needs and nothing more.

</Level>
<Level name="System design">

Error handling, logging and secret scanning together form the disclosure control. Each covers what the others miss.

</Level>
<Level name="Strategy">

I trigger every error path I can find in my capstone and read the raw responses. Done when none shows a stack trace, a query or a version, and secret scanning runs in CI.

</Level>
</Levels>

### 16. Attacking Native Compiled Applications

**Covers:** Memory-safety bugs reachable through a web application: buffer overflows, integer vulnerabilities, format string vulnerabilities, and how to find them.

<Levels label="Chapter 16, Attacking Native Compiled Applications">
<Level name="Beginner">

Some web apps call native code (image libraries, parsers, old components) where a long input can overflow memory.

</Level>
<Level name="Intermediate">

Buffer overflows write past an array; integer overflows make a size calculation wrap; format string bugs let input control a `printf`. This connects back to phase 1's C work.

</Level>
<Level name="Advanced">

Overflows can corrupt control data and run attacker code. Modern mitigations make it harder, not impossible.

</Level>
<Level name="Edge cases">

Exactly the buffer size plus one: the classic off-by-one that drops the terminator.

</Level>
<Level name="Corner cases">

A size check done in a signed type that a negative input passes, followed by an unsigned copy.

</Level>
<Level name="Production level">

In a Node app, native risk lives in dependencies such as image processors. I keep them patched, run them on limited input sizes, and isolate them where I can.

</Level>
<Level name="Mindset">

A memory-safe language at the top does not make the whole stack memory-safe.

</Level>
<Level name="System design">

Risky parsers run in a sandboxed worker or a separate service with few permissions.

</Level>
<Level name="Strategy">

I list the native modules in my capstone's dependency tree. Done when each is patched, size-limited at the input, and I know what it would reach if it were compromised.

</Level>
</Levels>

### 17. Attacking Application Architecture

**Covers:** Weaknesses that come from how the application is deployed: tiered architectures and their trust between tiers, and shared hosting and application service providers.

<Levels label="Chapter 17, Attacking Application Architecture">
<Level name="Beginner">

Applications are split into tiers: web, application, database. Each tier often trusts the one in front of it completely.

</Level>
<Level name="Intermediate">

If the web tier is compromised and the database trusts it fully, the attacker has the database.

</Level>
<Level name="Advanced">

Shared hosting and multi-tenant platforms put many customers on one system. Isolation between them is the architecture's main security property.

</Level>
<Level name="Edge cases">

A shared cache or temp directory between tenants on the same host.

</Level>
<Level name="Corner cases">

A tier that was internal, made reachable by a new feature, still trusting all its callers.

</Level>
<Level name="Production level">

Each tier authenticates its callers and has its own least-privilege credentials. A web tier compromise should not grant admin on the database.

</Level>
<Level name="Mindset">

Trust between components is a decision, not a default. Write it down.

</Level>
<Level name="System design">

This is the architecture view of the threat model: trust boundaries drawn on the deployment diagram.

</Level>
<Level name="Strategy">

I draw my capstone's tiers with the credential each uses. Done when no tier has more rights than it needs and the diagram is in the threat model.

</Level>
</Levels>

### 18. Attacking the Application Server

**Covers:** Weaknesses in the server under the app: vulnerable configurations, vulnerable server software, and web application firewalls.

<Levels label="Chapter 18, Attacking the Application Server">
<Level name="Beginner">

The server software under my app has its own defaults, admin pages and bugs.

</Level>
<Level name="Intermediate">

Default credentials, directory listings, sample apps and verbose banners are configuration bugs, not code bugs.

</Level>
<Level name="Advanced">

Web application firewalls block known patterns. They help against noise and fail against attacks shaped to avoid their rules.

</Level>
<Level name="Edge cases">

An old server version exposed by a forgotten staging host.

</Level>
<Level name="Corner cases">

A WAF in front of the app and a different parser in the app: the payload the WAF sees is not the one the app runs.

</Level>
<Level name="Production level">

I build container images from minimal bases, patch them on a schedule, turn off listings and banners, and treat the WAF as one layer, not the defence.

</Level>
<Level name="Mindset">

The platform is part of my attack surface even if someone else wrote it.

</Level>
<Level name="System design">

Infrastructure as code makes configuration reviewable and repeatable, which is a security property.

</Level>
<Level name="Strategy">

I scan my capstone's container image and running headers. Done when there are no high-severity findings and no banner reveals a version.

</Level>
</Levels>

### 19. Finding Vulnerabilities in Source Code

**Covers:** Code review for security: approaches to review, signatures of common vulnerabilities, the Java, ASP.NET, PHP, Perl and JavaScript platforms, database code components, and tools for browsing code.

<Levels label="Chapter 19, Finding Vulnerabilities in Source Code">
<Level name="Beginner">

Reading code finds bugs that testing from outside misses, because I can see every path.

</Level>
<Level name="Intermediate">

Start from sources (request data) and sinks (queries, shell, HTML, file paths), and trace between them.

</Level>
<Level name="Advanced">

Each platform has its dangerous APIs. In Node: `eval`, `child_process.exec`, raw SQL strings, `innerHTML` and unsafe deserialisation.

```sh
rg -n "exec\(|eval\(|innerHTML|dangerouslySetInnerHTML|\$queryRawUnsafe" src
```

</Level>
<Level name="Edge cases">

A sink reached only through an error path that tests never take.

</Level>
<Level name="Corner cases">

A source in one service and a sink in another, joined by a queue: the trace crosses a boundary review tools do not follow.

</Level>
<Level name="Production level">

I run static analysis in CI for known patterns and do a manual source-to-sink review of every new endpoint at code review.

</Level>
<Level name="Mindset">

Review the data's journey, not the file's lines.

</Level>
<Level name="System design">

Security review is part of the pull-request process: a checklist for anything that touches auth, input or output.

</Level>
<Level name="Strategy">

I do a source-to-sink review of my capstone's five riskiest endpoints. Done when each has a written trace and every finding is fixed or recorded.

</Level>
</Levels>

### 20. A Web Application Hacker's Toolkit

**Covers:** The tools of the trade: web browsers, integrated testing suites (intercepting proxies, spiders, fuzzers), standalone vulnerability scanners, and other tools.

<Levels label="Chapter 20, A Web Application Hacker's Toolkit">
<Level name="Beginner">

The main tool is an intercepting proxy: it sits between the browser and the server and lets me see and change every request.

</Level>
<Level name="Intermediate">

Proxies come with repeaters, fuzzers and spiders. Browser developer tools cover much of the same ground for my own apps.

</Level>
<Level name="Advanced">

Automated scanners find known patterns quickly and miss logic and access-control bugs, which need a person.

</Level>
<Level name="Edge cases">

A scanner run without a logged-in session tests only the login page.

</Level>
<Level name="Corner cases">

A scanner that submits forms against a real environment and sends real emails or creates real orders.

</Level>
<Level name="Production level">

I run scanners against a test environment with seeded accounts, never production, and treat their output as leads to verify.

</Level>
<Level name="Mindset">

Tools amplify judgement; they do not replace it.

</Level>
<Level name="System design">

A dynamic scan in CI against a preview deployment catches regressions in headers and obvious injections.

</Level>
<Level name="Strategy">

I proxy my capstone through a local intercepting proxy and run one authenticated scan against a test deployment. Done when every finding is verified as real or false and recorded.

</Level>
</Levels>

### 21. A Web Application Hacker's Methodology

**Covers:** The full testing method as a checklist: map the content, analyse the application, test client-side controls, authentication, session handling, access controls, input-based vulnerabilities, function-specific and logic flaws, shared hosting, the server, and miscellaneous checks.

<Flow steps={["Map", "Analyse", "Client controls", "Authentication", "Sessions", "Access control", "Input", "Logic", "Server", "Report"]} caption="The order the methodology tests in. Each stage feeds the next." />

<Levels label="Chapter 21, A Web Application Hacker's Methodology">
<Level name="Beginner">

The methodology turns the whole book into an ordered checklist. Following it means not forgetting a class of bug.

</Level>
<Level name="Intermediate">

Mapping comes first because every later test needs the list of entry points.

</Level>
<Level name="Advanced">

The checklist is a minimum. Logic flaws need understanding of what the application is for, which no list gives.

</Level>
<Level name="Edge cases">

Areas that are hard to reach (multi-step flows, admin functions, file uploads) are the ones skipped and the ones that fail.

</Level>
<Level name="Corner cases">

</Level>
<Level name="Production level">

</Level>
<Level name="Mindset">

Method beats talent. A complete checklist done honestly finds more than clever guesses.

</Level>
<Level name="System design">

The methodology maps onto the OWASP Top 10 and onto the CI gates: each class of bug has a test and a place in the pipeline.

</Level>
<Level name="Strategy">

I run the methodology against my capstone as the phase 11 self-review. Done when every stage has evidence and every finding has a fix or a written decision.

</Level>

## Misreadings to avoid

- "This is a book for attackers." It is the defender's best map of what to test.
- "It is from 2011, so it is out of date." The technologies changed; the classes of bug did not.
- "A scanner covers this." Scanners miss access control and logic, the two most damaging classes.
- "Frameworks fix all of it." Frameworks fix the defaults; every escape hatch reopens the bug.
- "I can practise on any site." Only on my own apps and on labs built for it.

## Done with this book when

- My capstone has an OWASP Top 10 self-review with evidence for each item: part of the phase 11 build.
- Every endpoint has tests for authentication, authorisation, input validation and output encoding.
- A CI step blocks a change that removes an access check or introduces a raw-HTML sink.
- I can explain injection, XSS, CSRF, SSRF and broken access control with an example and a fix for each.
- I have done the matching PortSwigger Academy labs for every chapter phase 11 needs first.
