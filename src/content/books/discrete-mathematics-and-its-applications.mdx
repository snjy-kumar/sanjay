## Why this book

The <a href={withBase('/plans/traditional-software-developer/')}>traditional core</a> lists Rosen as
the optional depth for Phase 2, discrete mathematics. MIT's text is the primary book; Rosen is the
encyclopaedia beside it, with many worked examples and exercises, and with two topics the phase needs
that the MIT text leaves out: Boolean algebra and logic gates, and matrices. The
<a href={withBase('/plans/traditional-software-developer/#strategy-2')}>Phase 2 strategy</a> uses it
that way.

The chapter list below follows the publisher's contents for the eighth edition. I describe each
chapter's topics in my own words and do not cite section or page numbers.

## How I would learn it

I do not read Rosen front to back. I read the matching Rosen chapter when the MIT chapter is hard, to
see the same idea explained more slowly, and I take its exercises when I need more practice than the
proof notebook gives me. Chapters 2 (matrices) and 12 (Boolean algebra) I read in full, because the
phase needs them and the MIT text does not have them.

## The chapters

### 1. The Foundations: Logic and Proofs

**Covers:** Propositional logic and its applications, propositional equivalences, predicates and quantifiers, nested quantifiers, rules of inference, and an introduction to proofs and proof methods and strategy.

<Levels label="Chapter 1, The Foundations: Logic and Proofs">

<Level name="Beginner">

Propositions are combined with not, and, or, implies and iff; truth tables decide their value.
Predicates take arguments, and quantifiers say "for all" and "there exists".

</Level>

<Level name="Intermediate">

Nested quantifiers are where meaning hides: "every request has a handler" is for all requests, there
exists a handler; swap them and it says one handler serves every request. Rules of inference, such as
modus ponens, chain statements into arguments.

</Level>

<Level name="Advanced">

Equivalence laws (De Morgan, distribution, contrapositive) rewrite formulas without changing truth.
Proof methods: direct, by contrapositive, by contradiction, by cases, and existence proofs that
either build the object or show it must exist.

</Level>

<Level name="Edge cases">

Universal statements over an empty domain are true; existential ones are false. An implication with a
false premise is true.

</Level>

<Level name="Corner cases">

Negating a nested quantifier with a conditional inside: "not (for all x, P implies Q)" becomes "there
exists x with P and not Q". Two boundaries, the quantifier flip and the implication's negation, in one
step.

</Level>

<Level name="Production level">

Access rules, validation and query filters are quantified formulas. A wrong quantifier order in a
SQL `NOT EXISTS` or an `every`/`some` swap is a real bug that tests on small data miss.

</Level>

<Level name="Mindset">

Translate English into logic before reasoning about it. Ambiguity lives in the English.

</Level>

<Level name="System design">

Policy engines, type checkers and database query planners all manipulate logical formulas.

</Level>

<Level name="Strategy">

Translate ten requirements from my own projects into predicate logic and negate each. Done when every
negation, turned back into English, describes the real failure case.

</Level>

</Levels>

### 2. Basic Structures: Sets, Functions, Sequences, Sums, and Matrices

**Covers:** Sets and set operations, functions, sequences and summations, cardinality of sets, and matrices.

<Levels label="Chapter 2, Basic Structures: Sets, Functions, Sequences, Sums, and Matrices">

<Level name="Beginner">

Sets, functions, sequences and sums are the nouns of discrete maths. A matrix is a rectangular table
of numbers with rules for adding and multiplying.

</Level>

<Level name="Intermediate">

Set operations are `Set` operations: union, intersection, difference. Matrix multiplication combines
rows of one with columns of the other; the adjacency matrix of a graph, multiplied by itself, counts
two-step walks. This is the first piece of the phase's linear algebra.

```ts
const matmul = (a: number[][], b: number[][]) =>
  a.map(row => b[0].map((_, j) => row.reduce((s, x, k) => s + x * b[k][j], 0)));
```

</Level>

<Level name="Advanced">

Countable and uncountable sets are distinguished by bijections and diagonal arguments. Matrix
multiplication is associative but not commutative; the identity matrix is its neutral element.

</Level>

<Level name="Edge cases">

The empty set has cardinality zero and is a subset of every set. Multiplying an `m` by `n` matrix by a
`p` by `q` one needs `n` to equal `p`.

</Level>

<Level name="Corner cases">

Floating-point matrix products are not exactly associative: reordering a long product changes the
last digits, so two correct programs disagree slightly. Non-commutativity plus rounding.

</Level>

<Level name="Production level">

Matrices are the data layout of graphics, machine learning and recommendation. Summation formulas give
the cost of loops.

</Level>

<Level name="Mindset">

Know the shape before the operation: types for sets, dimensions for matrices.

</Level>

<Level name="System design">

A dense matrix and an adjacency list are two representations of one graph; the choice is a memory
and speed trade that phase 3 makes.

</Level>

<Level name="Strategy">

Implement set operations and matrix multiply, then use matrix powers to count walks in a small graph.
Done when the walk counts match a brute-force enumeration.

</Level>

</Levels>

### 3. Algorithms

**Covers:** Algorithms and their properties, the growth of functions with big-O, big-Omega and big-Theta, and the complexity of algorithms.

<Levels label="Chapter 3, Algorithms">

<Level name="Beginner">

An algorithm is a finite, precise sequence of steps that solves a problem. Searching and sorting are
the first examples.

</Level>

<Level name="Intermediate">

Big-O bounds growth from above, Omega from below, Theta both. Counting the comparisons in linear and
binary search gives `n` and about `log n`.

</Level>

<Level name="Advanced">

Growth classes order themselves: constant, logarithmic, linear, `n log n`, polynomial, exponential,
factorial. Worst case, average case and best case are different questions. Greedy algorithms are
simple and only sometimes optimal.

</Level>

<Level name="Edge cases">

For tiny `n`, a "slower" algorithm can win. An algorithm on empty input should do nothing gracefully.

</Level>

<Level name="Corner cases">

Greedy coin change works for some coin systems and fails for others; the algorithm is correct only
together with an assumption about the input.

</Level>

<Level name="Production level">

A quadratic step on user-sized input is the common performance incident. Measure the input sizes you
actually see.

</Level>

<Level name="Mindset">

State the input size and the operation being counted before claiming a complexity.

</Level>

<Level name="System design">

Complexity tells me which part of a system will fall over first as it grows.

</Level>

<Level name="Strategy">

Count the operations of three algorithms by hand, then benchmark them at sizes ten times apart. Done
when the measured growth matches the prediction.

</Level>

</Levels>

### 4. Number Theory and Cryptography

**Covers:** Divisibility and modular arithmetic, integer representations and algorithms, primes and greatest common divisors, solving congruences, applications of congruences, and cryptography.

<Levels label="Chapter 4, Number Theory and Cryptography">

<Level name="Beginner">

Modular arithmetic is clock arithmetic. Integers can be written in any base; binary and hexadecimal
are the ones I meet daily.

</Level>

<Level name="Intermediate">

Fast modular exponentiation squares and multiplies over the binary digits of the exponent. Congruences
power check digits, hashing and pseudo-random number generators.

</Level>

<Level name="Advanced">

Euclid's algorithm and its extended form give gcds and inverses; the Chinese remainder theorem solves
systems of congruences; Fermat's little theorem underlies primality tests. RSA combines them.

</Level>

<Level name="Edge cases">

Zero has no inverse; a number sharing a factor with the modulus has none either. Base conversion of 0
must output "0", not an empty string.

</Level>

<Level name="Corner cases">

Negative numbers plus `%` in JavaScript give negative remainders; a modular inverse computed from them
is wrong unless normalised.

</Level>

<Level name="Production level">

Never deploy textbook RSA. Use vetted libraries with padding, constant-time operations and secure
randomness.

</Level>

<Level name="Mindset">

Big problems become small when reduced modulo something.

</Level>

<Level name="System design">

Hash tables, checksums, ISBNs, IDs and TLS all use this chapter.

</Level>

<Level name="Strategy">

Implement base conversion, modexp and the Chinese remainder theorem in TypeScript with `bigint`. Done
when each matches brute force on random small inputs.

</Level>

</Levels>

### 5. Induction and Recursion

**Covers:** Mathematical induction, strong induction and well-ordering, recursive definitions and structural induction, recursive algorithms, and program correctness.

<Levels label="Chapter 5, Induction and Recursion">

<Level name="Beginner">

Induction proves a statement for all natural numbers from a base case and a step. Recursion defines
things in terms of smaller versions of themselves.

</Level>

<Level name="Intermediate">

A recursive algorithm is proved correct by induction on input size. The same structure proves merge
sort sorts and binary search finds.

</Level>

<Level name="Advanced">

Program correctness uses preconditions, postconditions and loop invariants: partial correctness says
the answer is right if the program stops; termination is proved separately.

</Level>

<Level name="Edge cases">

The base case must match the domain. A recursive function's base case must be reachable from every
input.

</Level>

<Level name="Corner cases">

Partial correctness plus non-termination: a loop that is "correct whenever it stops" and never stops on
one input. Both proofs are needed.

</Level>

<Level name="Production level">

Assertions in code are executable invariants. Recursion over untrusted input needs a depth bound.

</Level>

<Level name="Mindset">

Correctness is an argument, not a feeling.

</Level>

<Level name="System design">

Contracts and invariants are how large codebases stay correct as people change them.

</Level>

<Level name="Strategy">

Write pre- and postconditions and a loop invariant for three functions in my repo, as assertions.
Done when each assertion has survived a property-based test run.

</Level>

</Levels>

### 6. Counting

**Covers:** The basics of counting, the pigeonhole principle, permutations and combinations, binomial coefficients and identities, generalised permutations and combinations, and generating permutations and combinations.

<Levels label="Chapter 6, Counting">

<Level name="Beginner">

Sum rule, product rule, permutations and combinations: how many ways can it happen?

</Level>

<Level name="Intermediate">

Counting with repetition (stars and bars) and with indistinguishable objects. Pascal's triangle
organises the binomial coefficients.

</Level>

<Level name="Advanced">

The pigeonhole principle, including its generalised form, proves existence by counting. Algorithms that
generate every permutation or combination in order make counting checkable.

</Level>

<Level name="Edge cases">

Choosing zero is one way; choosing more than available is zero ways.

</Level>

<Level name="Corner cases">

Counting with both repetition and order restrictions at once is where formulas get misapplied; check
with enumeration.

</Level>

<Level name="Production level">

Exhaustive tests are only possible when the count is small; counting tells me when to switch to
random or property-based testing.

</Level>

<Level name="Mindset">

Count before enumerating; enumerate to check the count.

</Level>

<Level name="System design">

Key spaces, ID formats and combinatorial test design are counting.

</Level>

<Level name="Strategy">

Write a generator for all `k`-combinations and compare its output size with the formula. Done when
they agree for every small `n` and `k`.

</Level>

</Levels>

### 7. Discrete Probability

**Covers:** An introduction to discrete probability, probability theory, Bayes' theorem, and expected value and variance.

<Levels label="Chapter 7, Discrete Probability">

<Level name="Beginner">

For equally likely outcomes, probability is favourable over total. Events combine with union,
intersection and complement.

</Level>

<Level name="Intermediate">

Conditional probability and independence; Bayes' theorem for updating a belief given evidence, with a
spam filter as a natural example.

</Level>

<Level name="Advanced">

Expectation is linear; variance measures spread; Chebyshev bounds how far a variable strays from its
mean.

</Level>

<Level name="Edge cases">

An event that cannot happen has probability zero; conditioning on it is undefined.

</Level>

<Level name="Corner cases">

A low base rate plus a fairly accurate test gives mostly false positives.

</Level>

<Level name="Production level">

Alerting, ranking and A/B testing are applied probability; base rates decide alert fatigue.

</Level>

<Level name="Mindset">

Write the sample space; distrust intuition.

</Level>

<Level name="System design">

Probabilistic data structures (Bloom filters, skip lists) trade certainty for speed.

</Level>

<Level name="Strategy">

Simulate a Bayes example and compare with the formula. Done when the simulated posterior sits inside
its confidence interval around the exact value.

</Level>

</Levels>

### 8. Advanced Counting Techniques

**Covers:** Applications of recurrence relations, solving linear recurrence relations, divide-and-conquer algorithms and recurrence relations, generating functions, inclusion-exclusion, and applications of inclusion-exclusion.

<Levels label="Chapter 8, Advanced Counting Techniques">

<Level name="Beginner">

A recurrence relation counts something in terms of smaller counts: Fibonacci, Hanoi, bit strings
without two consecutive zeros.

</Level>

<Level name="Intermediate">

Dynamic programming evaluates a recurrence bottom-up and stores the results.

</Level>

<Level name="Advanced">

Linear homogeneous recurrences with constant coefficients are solved through the characteristic
equation; divide-and-conquer recurrences by a master-theorem style result; inclusion-exclusion counts
derangements and onto functions.

</Level>

<Level name="Edge cases">

Initial conditions decide the constants; wrong ones give a formula off by a constant forever.

</Level>

<Level name="Corner cases">

Repeated characteristic roots change the solution's form; overlapping subproblems make naive
recursion exponential.

</Level>

<Level name="Production level">

Recursive code without memoisation is the classic exponential surprise.

</Level>

<Level name="Mindset">

Find the recurrence first, then decide how to compute it.

</Level>

<Level name="System design">

Caching layers are memoisation at system scale.

</Level>

<Level name="Strategy">

Solve three recurrences by formula, then check each against a memoised program. Done when they agree
for the first fifty terms.

</Level>

</Levels>

### 9. Relations

**Covers:** Relations and their properties, n-ary relations and their applications, representing relations, closures of relations, equivalence relations, and partial orderings.

<Levels label="Chapter 9, Relations">

<Level name="Beginner">

A relation is a set of pairs. Properties: reflexive, symmetric, antisymmetric, transitive.

</Level>

<Level name="Intermediate">

`n`-ary relations are database tables, and the operations on them, selection, projection and join, are
relational algebra.

</Level>

<Level name="Advanced">

Transitive closure answers reachability, computed with Warshall's algorithm. Equivalence relations
partition a set; partial orders and Hasse diagrams describe dependencies and topological sorting.

</Level>

<Level name="Edge cases">

The empty relation is symmetric and transitive but not reflexive on a nonempty set.

</Level>

<Level name="Corner cases">

A relation can be both symmetric and antisymmetric (only self-pairs); a "both" case breaks naive
classifiers.

</Level>

<Level name="Production level">

SQL is relational algebra; a join written wrong multiplies rows.

</Level>

<Level name="Mindset">

See tables as relations and joins as composition.

</Level>

<Level name="System design">

Phase 8's databases are this chapter in production.

</Level>

<Level name="Strategy">

Implement transitive closure and test whether relations from my data are equivalences or partial
orders. Done when the checker agrees with hand analysis on ten examples.

</Level>

</Levels>

### 10. Graphs

**Covers:** Graphs and graph models, terminology and special types, representations and isomorphism, connectivity, Euler and Hamilton paths, shortest-path problems, planar graphs, and graph coloring.

<Levels label="Chapter 10, Graphs">

<Level name="Beginner">

A graph is vertices and edges, directed or not, weighted or not. Adjacency lists and matrices store
them.

</Level>

<Level name="Intermediate">

Connectivity, Euler paths (every edge once) and Hamilton paths (every vertex once) sound alike and are
completely different in difficulty.

</Level>

<Level name="Advanced">

Dijkstra's algorithm finds shortest paths with non-negative weights. Planarity and Euler's formula,
and colouring, round out the chapter.

</Level>

<Level name="Edge cases">

A graph with one vertex is connected; a disconnected graph has no Euler path covering all edges.

</Level>

<Level name="Corner cases">

Dijkstra plus a negative edge gives wrong answers silently.

</Level>

<Level name="Production level">

Routing, social graphs and dependency analysis are graph problems at scale.

</Level>

<Level name="Mindset">

Model the problem as a graph before choosing the algorithm.

</Level>

<Level name="System design">

Maps, networks and service dependencies are graphs; phase 4 makes them fast.

</Level>

<Level name="Strategy">

Build the phase 2 graph checker and add Dijkstra. Done when it handles disconnected graphs and rejects
negative weights with a clear error.

</Level>

</Levels>

### 11. Trees

**Covers:** Introduction to trees, applications of trees, tree traversal, spanning trees, and minimum spanning trees.

<Levels label="Chapter 11, Trees">

<Level name="Beginner">

A tree is a connected graph with no cycles; a rooted tree has a parent for every vertex but the root.

</Level>

<Level name="Intermediate">

Binary search trees, decision trees, prefix codes (Huffman) and game trees are applications.

</Level>

<Level name="Advanced">

Preorder, inorder and postorder traversals; spanning trees by DFS or BFS; minimum spanning trees by
Prim's and Kruskal's algorithms.

</Level>

<Level name="Edge cases">

The empty tree and the single node are the base cases.

</Level>

<Level name="Corner cases">

Equal edge weights mean several minimum spanning trees; tests that expect one exact tree fail.

</Level>

<Level name="Production level">

Tree depth decides performance and stack use; unbalanced trees degrade to lists.

</Level>

<Level name="Mindset">

Trees are recursion made into data.

</Level>

<Level name="System design">

File systems, the DOM, indexes and routing tables are trees.

</Level>

<Level name="Strategy">

Implement traversals and Kruskal's algorithm. Done when the MST weight matches brute force on small
random graphs.

</Level>

</Levels>

### 12. Boolean Algebra

**Covers:** Boolean functions, representing Boolean functions, logic gates, and minimisation of circuits.

<Levels label="Chapter 12, Boolean Algebra">

<Level name="Beginner">

Boolean algebra works on 0 and 1 with AND, OR and NOT. Every Boolean function can be built from them,
and even from NAND alone.

</Level>

<Level name="Intermediate">

Sum-of-products form turns a truth table into a formula; gates turn the formula into a circuit. A
half adder is an XOR and an AND.

```ts
const halfAdder = (a: 0 | 1, b: 0 | 1) => ({ sum: (a ^ b) as 0 | 1, carry: (a & b) as 0 | 1 });
```

</Level>

<Level name="Advanced">

Karnaugh maps and the Quine-McCluskey method minimise circuits. This is the bridge from logic to
hardware, which phase 5 continues.

</Level>

<Level name="Edge cases">

A function of zero variables is a constant. Don't-care conditions can be set either way to simplify.

</Level>

<Level name="Corner cases">

Two gates switching at slightly different times can glitch, a hazard that the logic alone does not
show. Timing meets logic.

</Level>

<Level name="Production level">

Bit manipulation in code is Boolean algebra on words; flags and masks are its everyday use.

</Level>

<Level name="Mindset">

Hardware is logic you can hold.

</Level>

<Level name="System design">

CPUs, FPGAs and feature-flag evaluation all reduce to Boolean functions.

</Level>

<Level name="Strategy">

Build a ripple-carry adder from simulated gates in TypeScript. Done when it adds every pair of 4-bit
numbers correctly.

</Level>

</Levels>

### 13. Modeling Computation

**Covers:** Languages and grammars, finite-state machines with output, finite-state machines with no output, language recognition, and Turing machines.

<Levels label="Chapter 13, Modeling Computation">

<Level name="Beginner">

A grammar generates strings; a finite-state machine recognises them. Regular expressions describe the
same languages as finite-state machines.

</Level>

<Level name="Intermediate">

A tokenizer is a finite-state machine. A vending machine or a protocol is one with output.

</Level>

<Level name="Advanced">

Some languages, like balanced brackets, need more than finite memory. Turing machines model all
computation and lead to undecidability.

</Level>

<Level name="Edge cases">

The empty string is a valid input and must be accepted or rejected deliberately.

</Level>

<Level name="Corner cases">

Nested brackets plus a regular expression: no regex in the formal sense can match arbitrary nesting.

</Level>

<Level name="Production level">

State machines make UI flows and protocols testable; regex backtracking can take exponential time on
crafted input.

</Level>

<Level name="Mindset">

Model the states first; the code follows.

</Level>

<Level name="System design">

Parsers, protocol handlers and workflow engines are machines from this chapter; phase 9 builds one.

</Level>

<Level name="Strategy">

Implement a finite-state machine for a small tokenizer and test it on hostile input. Done when every
input is accepted or rejected in linear time.

</Level>

</Levels>

## The back matter

The book closes with appendices on axioms for the real numbers and integers, exponential and
logarithmic functions, and pseudocode, plus answers to odd-numbered exercises. The answers are the
reason I use its exercises: I can check my work without a teacher.

## Misreadings to avoid

- "Bigger book, better book." Rosen is wide; MIT's text is deeper on proofs and probability. Use each
  for what it is good at.
- "Reading the worked examples is practising." Doing the exercises is practising.
- "Boolean algebra is only for hardware people." Every mask, flag and condition in code is Boolean
  algebra.
- "Greedy works because it worked on the example." It works only with an assumption about the input.
