## Why this book

This is the reference book for phase 7 of the <a href={withBase('/plans/traditional-software-developer/')}>traditional core</a>,
networks. Kurose and Ross explain why the protocols are designed the way they are; this book shows what they
actually do on the wire, header field by header field, with real packet traces. When a capture shows me
something I cannot explain, this is where I look.

The second edition, by Kevin Fall building on W. Richard Stevens's original, covers IPv4 and IPv6 side by side
and adds chapters on firewalls and NAT, DHCP and security. I read it as a reference, not cover to cover, but
I read the TCP chapters (12 to 17) in full.

## How I would learn it

The book's method is the trace: run a tool, capture the packets, explain every field. I copy that method
with `tcpdump`, Wireshark, `ping`, `traceroute`, `dig`, `ss` and `ip` on my own machine and a couple of VMs,
so every chapter ends with a capture I made and annotated myself, not one I read.

## Architecture and addressing

### 1. Introduction
**Covers:** Architectural principles of the Internet, layering, the protocols of the TCP/IP suite, multiplexing and encapsulation, standards bodies and RFCs, and implementations.

<Levels label="Chapter 1, Introduction">

<Level name="Beginner">

The Internet is built on packet switching and best-effort delivery: IP moves packets with no guarantees, and everything else is built on top. Protocols are layered so each solves one problem.

</Level>

<Level name="Intermediate">

Encapsulation wraps data in headers layer by layer; demultiplexing uses fields in each header (EtherType, protocol number, port) to hand data upwards to the right protocol.

</Level>

<Level name="Advanced">

The end-to-end argument puts reliability in the hosts, not the network, which keeps routers simple. RFCs define the protocols; implementations differ in details the RFCs leave open.

</Level>

<Level name="Edge cases">

A protocol number or port nobody listens on gets an ICMP error or a TCP reset, which is how the stack says "nothing here".

</Level>

<Level name="Corner cases">

Middleboxes that read or rewrite higher-layer headers violate the layering, which makes new protocols hard to deploy (ossification); QUIC encrypts its headers partly to avoid this.

</Level>

<Level name="Production level">

When debugging, read the RFC and then check what the implementation actually does.

</Level>

<Level name="Mindset">

The design of the Internet is a set of choices about where functions live. Ask where a function lives before asking how it works.

</Level>

<Level name="System design">

The end-to-end argument applies to applications too: only the endpoints can confirm a business operation completed.

</Level>

<Level name="Strategy">

I would capture one HTTP request and label every header and the demultiplexing field in each. Done when I can follow the bytes from Ethernet to HTTP.

</Level>
</Levels>

### 2. The Internet Address Architecture
**Covers:** IPv4 and IPv6 address structure and notation, classful history, subnetting, CIDR and aggregation, special-use addresses, address allocation, unicast, multicast and anycast, and IPv6 address formats.

<Levels label="Chapter 2, The Internet Address Architecture">

<Level name="Beginner">

An IPv4 address is 32 bits, written as four decimal numbers; an IPv6 address is 128 bits, written in hexadecimal groups. A prefix length says how many leading bits name the network.

</Level>

<Level name="Intermediate">

Subnetting splits a network into smaller ones by extending the prefix. CIDR replaced the old fixed classes so routes can be aggregated into larger blocks, keeping routing tables small.

</Level>

<Level name="Advanced">

Special ranges exist for private networks, loopback, link-local and documentation. IPv6 interfaces have several addresses at once (link-local, global, temporary).

</Level>

<Level name="Edge cases">

The first and last addresses of an IPv4 subnet are traditionally the network and broadcast addresses and cannot be assigned to hosts (with exceptions such as /31 point-to-point links).

</Level>

<Level name="Corner cases">

Overlapping private ranges between two networks that need to be connected, such as two VPCs both using `10.0.0.0/16`, cannot be routed without NAT or renumbering.

</Level>

<Level name="Production level">

Plan address space before building networks; renumbering later is expensive. Many cloud peering problems are overlapping CIDRs.

</Level>

<Level name="Mindset">

Addresses carry structure; reading the structure answers most routing questions.

</Level>

<Level name="System design">

IP address management and VPC design start here.

</Level>

<Level name="Strategy">

I would write a TypeScript subnet calculator that handles IPv4 and checks overlaps, and read my machine's IPv6 addresses with `ip -6 addr`. Done when I can plan non-overlapping subnets for three environments.

</Level>
</Levels>

## Link, ARP and IP

### 3. Link Layer
**Covers:** Ethernet and the IEEE 802 standards, full duplex, power saving, autonegotiation and flow control, bridges and switches, wireless LANs (Wi-Fi), the Point-to-Point Protocol, loopback, MTU and path MTU, tunneling basics, and attacks on the link layer.

<Levels label="Chapter 3, Link Layer">

<Level name="Beginner">

The link layer carries frames between machines on the same network. Ethernet frames have source and destination MAC addresses, a type field and a checksum.

</Level>

<Level name="Intermediate">

Switches learn which MAC addresses are on which ports and forward frames only there. Wi-Fi uses its own frame formats and acknowledgements. The MTU is the largest payload a link carries, 1500 bytes on standard Ethernet.

</Level>

<Level name="Advanced">

VLAN tags, link aggregation and spanning tree change how frames flow; tunnels (GRE, VXLAN) carry one link layer inside another, reducing the effective MTU.

</Level>

<Level name="Edge cases">

Jumbo frames on one side of a link and standard frames on the other cause large packets to be dropped silently.

</Level>

<Level name="Corner cases">

A tunnel inside a tunnel shrinks the MTU twice, and if ICMP is filtered, path MTU discovery fails and only large transfers hang.

</Level>

<Level name="Production level">

MTU problems are a classic cause of "small requests work, big ones hang" in VPNs and container overlays.

</Level>

<Level name="Mindset">

Know the size limits of each hop, not just the endpoints.

</Level>

<Level name="System design">

Overlay networks in Kubernetes and the cloud are tunnels; their MTU settings matter.

</Level>

<Level name="Strategy">

I would find my path MTU to a remote host with `ping -M do -s` and capture Ethernet frames with VLAN tags in a VM bridge. Done when I can explain an MTU-related hang.

</Level>
</Levels>

### 4. ARP: Address Resolution Protocol
**Covers:** How ARP maps IPv4 addresses to MAC addresses, the ARP cache, frame format, proxy ARP, gratuitous ARP and address conflict detection, and ARP attacks.

<Levels label="Chapter 4, ARP: Address Resolution Protocol">

<Level name="Beginner">

To send an IP packet on a local network, a host needs the destination's MAC address. ARP broadcasts "who has this IP?" and the owner replies.

</Level>

<Level name="Intermediate">

Replies are cached for a while; `ip neigh` shows the cache. Packets to other networks go to the gateway's MAC address.

</Level>

<Level name="Advanced">

Gratuitous ARP announces a host's own mapping, used after failover to move an address to a new machine. Address conflict detection checks no one else uses an address.

</Level>

<Level name="Edge cases">

The first packet to a new neighbour waits for ARP, adding latency to the first connection.

</Level>

<Level name="Corner cases">

A failover that moves an IP without a gratuitous ARP leaves neighbours sending to the old machine until their cache entries expire.

</Level>

<Level name="Production level">

ARP spoofing can redirect local traffic; switches and cloud networks add protections. In the cloud, ARP is often answered by the virtual network itself.

</Level>

<Level name="Mindset">

Every name needs a lookup, and every lookup needs a cache and a way to go stale.

</Level>

<Level name="System design">

Virtual IP failover with keepalived relies on gratuitous ARP.

</Level>

<Level name="Strategy">

I would flush the ARP cache, ping a neighbour, and capture the request and reply. Done when I can describe each field of an ARP packet.

</Level>
</Levels>

### 5. The Internet Protocol (IP)
**Covers:** The IPv4 and IPv6 headers, IPv6 extension headers, IP forwarding, mobile IP, host processing of datagrams, and attacks involving IP.

<Levels label="Chapter 5, The Internet Protocol (IP)">

<Level name="Beginner">

IP carries packets between hosts across networks. Each header has source and destination addresses, a time-to-live, and the protocol of the payload.

</Level>

<Level name="Intermediate">

Routers forward using the longest prefix match in their routing table and decrement the TTL; a packet whose TTL reaches zero is dropped with an ICMP message.

</Level>

<Level name="Advanced">

The IPv4 header has a checksum and fragmentation fields; IPv6 drops the checksum, moves options and fragmentation into extension headers, and uses a hop limit and flow label.

</Level>

<Level name="Edge cases">

A host with several interfaces may answer from a different address than the one it received on, confusing firewalls (the strong versus weak host model).

</Level>

<Level name="Corner cases">

Spoofed source addresses combined with services that reply with large responses give reflection and amplification attacks.

</Level>

<Level name="Production level">

`ip route` and `ip rule` explain where a host sends traffic; policy routing and multiple interfaces are common in servers.

</Level>

<Level name="Mindset">

Each router decides locally with only its table; the path is the sum of local decisions.

</Level>

<Level name="System design">

Traffic engineering, multi-homing and anycast all depend on how IP forwarding works.

</Level>

<Level name="Strategy">

I would read my routing table, add a route in a VM, and watch the TTL drop with `traceroute`. Done when I can explain how traceroute uses TTL and ICMP.

</Level>
</Levels>

## Configuration and middleboxes

### 6. System Configuration: DHCP and Autoconfiguration
**Covers:** DHCP, its message flow, options and relaying, stateless address autoconfiguration in IPv6, DHCPv6, PPP over Ethernet, and attacks involving configuration.

<Levels label="Chapter 6, System Configuration: DHCP and Autoconfiguration">

<Level name="Beginner">

DHCP gives a joining host an address, a gateway and DNS servers automatically, with a lease that expires.

</Level>

<Level name="Intermediate">

The flow is discover, offer, request, acknowledge; relays forward DHCP across networks. IPv6 hosts can configure themselves from router advertisements (SLAAC) or use DHCPv6.

</Level>

<Level name="Advanced">

Leases are renewed halfway through their life. Options carry dozens of settings, from DNS search domains to boot servers.

</Level>

<Level name="Edge cases">

Two DHCP servers on one network hand out conflicting configurations; one rogue server can redirect a whole office.

</Level>

<Level name="Corner cases">

A short lease with a DHCP server outage makes hosts drop their addresses mid-work.

</Level>

<Level name="Production level">

In the cloud, DHCP is provided by the platform; in data centres it boots machines over the network.

</Level>

<Level name="Mindset">

Configuration is a protocol too, with its own failure modes.

</Level>

<Level name="System design">

Service discovery is the application-level version of DHCP.

</Level>

<Level name="Strategy">

I would release and renew a lease with `dhclient` in a VM and capture the four messages. Done when I can explain every option in the acknowledgement.

</Level>
</Levels>

### 7. Firewalls and Network Address Translation (NAT)
**Covers:** Packet-filtering and proxy firewalls, NAT and its behaviours, NAT traversal with STUN, TURN and ICE, configuring packet filters and NAT, NAT for IPv4 and IPv6 coexistence, and attacks.

<Levels label="Chapter 7, Firewalls and Network Address Translation (NAT)">

<Level name="Beginner">

A firewall decides which packets may pass. NAT rewrites addresses and ports so many private hosts share one public address.

</Level>

<Level name="Intermediate">

Stateful firewalls track connections so replies are allowed automatically. NAT keeps a table mapping private address and port pairs to public ones.

</Level>

<Level name="Advanced">

NAT behaviours differ in how mappings are created and filtered; peer-to-peer applications use STUN to learn their public mapping, TURN to relay when direct paths fail, and ICE to try both.

</Level>

<Level name="Edge cases">

Idle connections through NAT or a stateful firewall are dropped when the mapping times out, so long-lived connections need keepalives.

</Level>

<Level name="Corner cases">

Two hosts behind symmetric NATs cannot connect directly at all; only a relay works.

</Level>

<Level name="Production level">

Connection drops after a few minutes of idleness are usually a NAT or firewall timeout. Security groups and `iptables` or `nftables` rules are daily tools.

</Level>

<Level name="Mindset">

State in the middle of the network is fragile. Design for it to disappear.

</Level>

<Level name="System design">

WebRTC, VPNs and multiplayer games are built around NAT traversal.

</Level>

<Level name="Strategy">

I would set up NAT and a stateful filter in a VM with `nftables` and watch `conntrack` entries come and go. Done when I can explain why an idle connection died.

</Level>
</Levels>

## Control and group traffic

### 8. ICMPv4 and ICMPv6: Internet Control Message Protocol
**Covers:** ICMP message formats, error messages (unreachable, packet too big, time exceeded, parameter problem), query messages (echo), neighbour discovery in IPv6, and attacks.

<Levels label="Chapter 8, ICMPv4 and ICMPv6: Internet Control Message Protocol">

<Level name="Beginner">

ICMP carries error reports and diagnostics for IP. `ping` uses echo request and reply; `traceroute` uses time-exceeded errors.

</Level>

<Level name="Intermediate">

Errors include part of the original packet so the sender can match them. "Packet too big" and "fragmentation needed" drive path MTU discovery.

</Level>

<Level name="Advanced">

In IPv6, ICMPv6 also does neighbour discovery (replacing ARP) and router discovery, so blocking it breaks the network.

</Level>

<Level name="Edge cases">

ICMP errors are rate-limited, so traceroute can show missing hops that are actually fine.

</Level>

<Level name="Corner cases">

Filtering all ICMP looks secure and breaks path MTU discovery, which only shows on large transfers.

</Level>

<Level name="Production level">

Allow the ICMP types the network needs; do not blanket-block.

</Level>

<Level name="Mindset">

Error messages are part of the protocol. Blocking them hides problems instead of stopping them.

</Level>

<Level name="System design">

Health checks and network monitoring use ICMP, and cloud firewalls often block it by default.

</Level>

<Level name="Strategy">

I would capture ping, traceroute and a "packet too big" error. Done when I can explain how each tool reads the replies.

</Level>
</Levels>

### 9. Broadcasting and Local Multicasting (IGMP and MLD)
**Covers:** Broadcast, multicast addressing and delivery, IGMP and MLD for group membership, and attacks.

<Levels label="Chapter 9, Broadcasting and Local Multicasting (IGMP and MLD)">

<Level name="Beginner">

Broadcast sends to every host on a network; multicast sends to hosts that joined a group.

</Level>

<Level name="Intermediate">

Hosts join multicast groups with IGMP (IPv4) or MLD (IPv6); switches can snoop these messages to forward multicast only where needed.

</Level>

<Level name="Advanced">

Multicast addresses map to special MAC addresses so network cards can filter in hardware.

</Level>

<Level name="Edge cases">

Broadcasts do not cross routers, which limits their reach to one network.

</Level>

<Level name="Corner cases">

Many cloud networks do not support multicast at all, breaking software that discovers peers with it.

</Level>

<Level name="Production level">

Service discovery like mDNS uses local multicast; clustering software that relies on it needs a different mode in the cloud.

</Level>

<Level name="Mindset">

Know the delivery model your environment supports.

</Level>

<Level name="System design">

Gossip protocols over unicast replace multicast in most distributed systems.

</Level>

<Level name="Strategy">

I would watch mDNS traffic on my local network with Wireshark. Done when I can explain which group and port it uses.

</Level>
</Levels>

## UDP and DNS

### 10. User Datagram Protocol (UDP) and IP Fragmentation
**Covers:** The UDP header and checksum, IP fragmentation and reassembly, path MTU discovery with UDP, maximum datagram sizes, UDP server design, and attacks.

<Levels label="Chapter 10, User Datagram Protocol (UDP) and IP Fragmentation">

<Level name="Beginner">

UDP sends independent datagrams with ports and a checksum and nothing else: no connection, no retransmission, no ordering.

</Level>

<Level name="Intermediate">

A datagram larger than the path MTU is fragmented by IP; losing any fragment loses the whole datagram.

</Level>

<Level name="Advanced">

The checksum covers a pseudo-header with addresses. Servers handle each datagram independently and must manage their own state per client.

</Level>

<Level name="Edge cases">

A zero-length datagram is valid and delivered as an empty message.

</Level>

<Level name="Corner cases">

Fragmented datagrams under loss lose far more data than unfragmented ones, and many firewalls drop fragments entirely.

</Level>

<Level name="Production level">

DNS, QUIC, video and games use UDP; keep datagrams under the MTU to avoid fragmentation.

</Level>

<Level name="Mindset">

UDP gives you the network as it is. Every guarantee you want, you build.

</Level>

<Level name="System design">

QUIC is a reliable, secure transport built on UDP, which shows how far this goes.

</Level>

<Level name="Strategy">

I would send UDP datagrams larger than the MTU and capture the fragments. Done when I can show one lost fragment losing the whole datagram.

</Level>
</Levels>

### 11. Name Resolution and the Domain Name System (DNS)
**Covers:** The DNS namespace and name servers, caching, the protocol and message format, resource record types, dynamic updates, zone transfers, sort lists and other tricks, and attacks.

<Levels label="Chapter 11, Name Resolution and the Domain Name System (DNS)">

<Level name="Beginner">

DNS turns names into addresses through a hierarchy: the root, top-level domains and authoritative servers. Resolvers cache answers for their TTL.

</Level>

<Level name="Intermediate">

Record types include A, AAAA, CNAME, MX, NS, TXT, SRV and SOA. A recursive resolver walks the hierarchy for the client; the client asks only the resolver.

</Level>

<Level name="Advanced">

DNS uses UDP for most queries and TCP for large responses and zone transfers. Negative answers are cached too, for a time set in the SOA record.

</Level>

<Level name="Edge cases">

A CNAME cannot sit at the zone apex beside other records, which is why providers invent alias records.

</Level>

<Level name="Corner cases">

Lowering a TTL just before a migration does nothing for resolvers that already cached the old, long TTL; lower it at least one old TTL in advance.

</Level>

<Level name="Production level">

DNS failures cause a large share of outages; monitor resolution and expiry of domains and records.

</Level>

<Level name="Mindset">

Caches make DNS fast and make changes slow. Plan changes around TTLs.

</Level>

<Level name="System design">

Service discovery, load balancing with DNS and CDN steering all build on this chapter.

</Level>

<Level name="Strategy">

I would trace a lookup with `dig +trace`, read each record type for a domain, and time cached versus uncached queries. Done when I can explain every line of `dig` output.

</Level>
</Levels>

## TCP

### 12. TCP: The Transmission Control Protocol (Preliminaries)
**Covers:** An introduction to reliable delivery (ARQ, windows, retransmission), the TCP service, and the TCP header and its encapsulation in IP.

<Levels label="Chapter 12, TCP: The Transmission Control Protocol (Preliminaries)">

<Level name="Beginner">

TCP gives a reliable, ordered byte stream over IP's unreliable packets, between two ports on two hosts.

</Level>

<Level name="Intermediate">

Reliability comes from sequence numbers, acknowledgements and retransmission; a sliding window lets several segments be in flight.

</Level>

<Level name="Advanced">

The header carries ports, sequence and acknowledgement numbers, flags (SYN, ACK, FIN, RST, PSH, URG and ECN bits), the window and options.

</Level>

<Level name="Edge cases">

Sequence numbers count bytes, not segments, so a SYN and a FIN each consume one sequence number.

</Level>

<Level name="Corner cases">

Sequence numbers wrap around on fast links, and timestamps protect against old segments being mistaken for new ones.

</Level>

<Level name="Production level">

The header fields are exactly what you read in a capture, so knowing them speeds up every network debugging session.

</Level>

<Level name="Mindset">

Reliability is a set of rules about numbers. Learn the numbers and the rules follow.

</Level>

<Level name="System design">

Every protocol on top of TCP inherits its byte-stream model and its head-of-line blocking.

</Level>

<Level name="Strategy">

I would annotate the header of one captured segment field by field. Done when I can read any segment in Wireshark without the decoded view.

</Level>
</Levels>

### 13. TCP Connection Management
**Covers:** Connection establishment and termination, TCP options (MSS, window scaling, timestamps, SACK), path MTU discovery with TCP, state transitions including TIME_WAIT, reset segments, how TCP servers operate, and attacks on connection management.

<Levels label="Chapter 13, TCP Connection Management">

<Level name="Beginner">

TCP opens with a three-way handshake (SYN, SYN-ACK, ACK) and closes with FIN segments from each side.

</Level>

<Level name="Intermediate">

Options negotiated in the SYN set the maximum segment size, window scaling, timestamps and selective acknowledgements.

</Level>

<Level name="Advanced">

The state machine has states like SYN_SENT, ESTABLISHED, FIN_WAIT_1 and 2, CLOSE_WAIT, LAST_ACK and TIME_WAIT. TIME_WAIT lasts twice the maximum segment lifetime to absorb late segments.

</Level>

<Level name="Edge cases">

A RST closes a connection immediately; a connection attempt to a closed port gets a RST back.

</Level>

<Level name="Corner cases">

A pile of CLOSE_WAIT sockets means the application never closed its side, a bug in the app, not the network.

</Level>

<Level name="Production level">

SYN floods exhaust half-open connection state; SYN cookies defend against them. TIME_WAIT is normal and only a problem with huge numbers of short connections.

</Level>

<Level name="Mindset">

Read the state, then find who is responsible for the next move.

</Level>

<Level name="System design">

Connection pooling and keep-alive exist to avoid paying the handshake and TIME_WAIT for every request.

</Level>

<Level name="Strategy">

I would watch connections move through states with `ss -tan` while opening and closing from each side, and create a CLOSE_WAIT leak on purpose. Done when I can diagnose that leak from `ss` output.

</Level>
</Levels>

### 14. TCP Timeout and Retransmission
**Covers:** Estimating the round-trip time and setting the retransmission timeout, timer-based retransmission, fast retransmit, selective acknowledgements, spurious timeouts, packet reordering and duplication, and attacks.

<Levels label="Chapter 14, TCP Timeout and Retransmission">

<Level name="Beginner">

If an acknowledgement does not arrive in time, TCP resends the data.

</Level>

<Level name="Intermediate">

The retransmission timeout is computed from a smoothed RTT and its variation; each timeout doubles it (exponential backoff). Three duplicate acknowledgements trigger fast retransmit without waiting.

</Level>

<Level name="Advanced">

Selective acknowledgements tell the sender exactly which blocks arrived, so only missing ones are resent. Algorithms detect spurious retransmissions and undo their effects.

</Level>

<Level name="Edge cases">

A timeout early in a connection uses a conservative initial value, making the first loss expensive.

</Level>

<Level name="Corner cases">

Reordering on a multipath network looks like loss and triggers needless fast retransmits.

</Level>

<Level name="Production level">

Retransmissions show as tail latency; `ss -ti` and Wireshark's analysis flags show them.

</Level>

<Level name="Mindset">

Timeouts are guesses based on measurements. Make the guess adaptive.

</Level>

<Level name="System design">

Application retries with exponential backoff and jitter copy this design.

</Level>

<Level name="Strategy">

I would add loss and delay with `tc netem` and watch retransmissions and RTO growth in a capture. Done when I can point out a fast retransmit and a timeout retransmit.

</Level>
</Levels>

### 15. TCP Data Flow and Window Management
**Covers:** Interactive and bulk data, delayed acknowledgements, the Nagle algorithm, flow control and window management, the silly window syndrome, large buffers and auto-tuning, urgent data, and attacks.

<Levels label="Chapter 15, TCP Data Flow and Window Management">

<Level name="Beginner">

The receiver advertises a window: how many more bytes it can accept. The sender never has more unacknowledged data than that.

</Level>

<Level name="Intermediate">

Delayed acknowledgements wait briefly to combine acks; Nagle's algorithm holds small segments while data is unacknowledged, to avoid flooding the network with tiny packets.

</Level>

<Level name="Advanced">

Window scaling allows windows larger than 64 KB, needed for fast long-distance links. Receivers avoid advertising tiny windows (silly window syndrome). Buffers auto-tune to the connection's needs.

</Level>

<Level name="Edge cases">

A zero window stops the sender; window probes check when it reopens.

</Level>

<Level name="Corner cases">

Nagle combined with delayed acks adds a delay of tens of milliseconds to request-response protocols that write in two pieces; `TCP_NODELAY` fixes it.

</Level>

<Level name="Production level">

Throughput is at most window divided by RTT, so long-distance transfers need big windows. Latency-sensitive services set `TCP_NODELAY`.

</Level>

<Level name="Mindset">

Two reasonable optimisations can combine into a bad one. Test them together.

</Level>

<Level name="System design">

Back-pressure in streaming systems is flow control at the application layer.

</Level>

<Level name="Strategy">

I would reproduce the Nagle and delayed-ack interaction with a small client and server and fix it with `TCP_NODELAY`. Done when I can measure the delay disappearing.

</Level>
</Levels>

### 16. TCP Congestion Control
**Covers:** Classic congestion control (slow start, congestion avoidance, fast recovery), evolution through NewReno and SACK, CUBIC and other high-speed variants, delay-based approaches, buffer bloat, active queue management and ECN, sharing with other flows, and attacks.

<Levels label="Chapter 16, TCP Congestion Control">

<Level name="Beginner">

Congestion control keeps TCP from sending more than the network can carry. The congestion window limits data in flight alongside the receiver's window.

</Level>

<Level name="Intermediate">

Slow start doubles the window each round trip until loss or a threshold; congestion avoidance grows it by about one segment per round trip and cuts it on loss.

</Level>

<Level name="Advanced">

Linux uses CUBIC by default, which grows the window as a cubic function of time since the last loss; delay-based and model-based algorithms react to rising RTT instead of loss. ECN lets routers mark packets instead of dropping them.

</Level>

<Level name="Edge cases">

A new connection starts small, so short transfers finish before reaching full speed.

</Level>

<Level name="Corner cases">

Large router buffers (buffer bloat) delay loss signals, so loss-based algorithms fill the queues and latency soars for everyone sharing the link.

</Level>

<Level name="Production level">

Congestion control choice and queue management matter for high-throughput and latency-sensitive services; most applications only need to reuse connections.

</Level>

<Level name="Mindset">

A shared resource needs every user to back off. Fairness is a protocol, not a hope.

</Level>

<Level name="System design">

Rate limiting and adaptive concurrency limits in services borrow congestion control ideas.

</Level>

<Level name="Strategy">

I would plot the congestion window from `ss -ti` during a transfer with added loss. Done when I can point out slow start, avoidance and a loss response in my plot.

</Level>

### 17. TCP Keepalive
**Covers:** What keepalive does, its timers and probes, and attacks involving keepalives.

<Levels label="Chapter 17, TCP Keepalive">

<Level name="Beginner">

Keepalive sends a probe on an idle connection to check that the other side is still there.

</Level>

<Level name="Intermediate">

After a long idle period (two hours by default on Linux), TCP sends probes; if enough go unanswered, the connection is closed.

</Level>

<Level name="Advanced">

The timers are configurable per socket. Keepalive detects a dead peer or a broken path, not an unresponsive application.

</Level>

<Level name="Edge cases">

A peer that rebooted answers a probe with a reset, closing the connection quickly.

</Level>

<Level name="Corner cases">

The default two-hour timer is far longer than typical NAT and firewall idle timeouts, so connections die in the middle before keepalive ever runs.

</Level>

<Level name="Production level">

Set keepalive intervals below middlebox timeouts for long-lived connections, or use application-level heartbeats.

</Level>

<Level name="Mindset">

Silence is ambiguous. Decide how you will tell idle from dead.

</Level>

<Level name="System design">

Database connection pools and message brokers use keepalives and heartbeats to detect dead connections.

</Level>

<Level name="Strategy">

I would set short keepalive timers on a socket and capture the probes. Done when I can show a connection closed by failed probes.

## Security

### 18. Security: EAP, IPsec, TLS, DNSSEC, and DKIM
**Covers:** Basic security principles and cryptography, certificates and public-key infrastructure, EAP for network access, IPsec, TLS, DNSSEC, DKIM for email, and attacks on security protocols.

<Levels label="Chapter 18, Security: EAP, IPsec, TLS, DNSSEC, and DKIM">

<Level name="Beginner">

Security protocols add confidentiality, integrity and authentication at different layers: EAP for joining networks, IPsec at the IP layer, TLS above TCP, DNSSEC for DNS answers, DKIM for email.

</Level>

<Level name="Intermediate">

Certificates bind public keys to names, signed by certificate authorities; clients verify the chain to a trusted root.

</Level>

<Level name="Advanced">

TLS negotiates algorithms, authenticates the server (and optionally the client), and derives session keys. DNSSEC signs records so resolvers can verify answers, but does not encrypt them.

</Level>

<Level name="Edge cases">

A certificate chain missing an intermediate works in browsers that cached it and fails in other clients.

</Level>

<Level name="Corner cases">

DNSSEC protects answers from forgery but a misconfigured signature makes a domain fail to resolve for validating resolvers, an outage caused by security.

</Level>

<Level name="Production level">

Automate certificate renewal, monitor expiry, and know which layer protects which traffic.

</Level>

<Level name="Mindset">

Each protocol protects one thing at one layer. Know what is still exposed.

</Level>

<Level name="System design">

Email deliverability (DKIM, SPF, DMARC), service mesh mTLS and VPNs are all this chapter applied.

</Level>

<Level name="Strategy">

I would inspect a certificate chain with `openssl`, check DNSSEC with `dig +dnssec`, and read a DKIM header from an email I received. Done when I can explain what each one proves.

</Level>

## Misreadings to avoid

- "The trace shows how it works everywhere." It shows how one implementation behaved; check the RFC and your own kernel.
- "TIME_WAIT is a problem to remove." It protects new connections from old segments; reduce the number of connections instead.
- "Blocking ICMP is safer." It breaks path MTU discovery and IPv6 neighbour discovery.
- "Keepalive keeps connections alive." It detects dead ones, and its default timer is too slow for most middleboxes.
- "A bigger buffer is always better." Oversized buffers cause buffer bloat and latency.
