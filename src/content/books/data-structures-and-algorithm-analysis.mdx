## Why this book

This is the optional depth for <a href={withBase('/plans/traditional-software-developer/#strategy-3')}>phase 3, data structures</a>.
Where <a href={withBase('/books/algorithms-sedgewick-wayne/')}>Sedgewick and Wayne</a> teach
by experiment, Weiss teaches by analysis: no structure appears without its
running time, and the later chapters go past what the phase requires into
amortised analysis and the structures that need it.

The plan names the book without a language. There are C++, Java and C
editions with the same overall shape. I follow the C++ fourth edition's
table of contents here because the publisher lists it section by section. My
examples are in TypeScript, the language of the phase, with C where memory
layout is the point.

## How I would learn it

I would use Weiss to check my understanding, not to build it the first time.
After writing a structure from Sedgewick, I would read Weiss's chapter and
try to answer its analysis questions before reading the answers: why is
buildHeap linear, why does quadratic probing need a prime size, why does AVL
deletion need more than one rotation. Every question I cannot answer goes
in the study log as a card.

I would do the easier exercises for each chapter I read and leave the
hardest for a second pass. The C++
details in chapter 1 I would read once, then come back to in phase 5, when C
memory makes them concrete.

This book is depth, not the spine. During phase 3 I read chapters 3 to 6 and
8 alongside Sedgewick, one chapter per structure, to get the analysis that
Sedgewick measures. Chapters 7, 9 and 10 are a second view during phase 4.
Chapters 11 and 12 are for after the phase 3 gate, when the library exists
and I want to know what else could replace each part.

## Chapters 1 and 2: foundations

### 1. Programming: A General Overview

**Covers:** The chapter covers what the book is about, a mathematics review (exponents,
logarithms, series, modular arithmetic, and the proof techniques the book
calls "the P word"), recursion, C++ classes, C++ details (pointers, lvalues,
rvalues and references, parameter and return passing, `std::swap` and
`std::move`, the "Big-Five"), templates, and a matrix class.

<Levels label="Chapter 1, Programming: A General Overview">

<Level name="Beginner">


Three pieces of maths carry the whole book: logarithms (how many times can I
halve N?), geometric series (1 + 2 + 4 + ... + N is less than 2N) and proof
by induction. Recursion needs a base case and progress towards it on every
call.


</Level>
<Level name="Intermediate">


The four rules of recursion in the chapter come down to: a base case, making
progress, believing the recursive call works, and never solving the same
subproblem twice in separate calls. The last rule is the seed of dynamic
programming in chapter 10. Naive Fibonacci breaks it:

```ts
const fib = (n: number): number => (n < 2 ? n : fib(n - 1) + fib(n - 2)); // exponential
```


</Level>
<Level name="Advanced">


The C++ sections are about who owns memory. An lvalue has an address, an
rvalue is a temporary, and move semantics let a container steal a
temporary's buffer instead of copying it. The Big-Five (destructor, copy
constructor, move constructor, copy assignment, move assignment) are the
operations a class must get right if it owns a resource. TypeScript hides
all of this behind the garbage collector, which is exactly why reading it
once is useful.


</Level>
<Level name="Edge cases">


- `log` of zero or a negative number is undefined; analysis assumes N ≥ 1.
- Modular arithmetic with a negative left operand: `-7 % 3` is `-1` in C,
  C++ and JavaScript, not `2`.
- A recursive function with no reachable base case overflows the stack.


</Level>
<Level name="Corner cases">


- A copy constructor that copies a pointer instead of the buffer gives two
  objects that free the same memory. This is the classic double free.
- Self-assignment (`a = a`) in a hand-written copy assignment can free the
  buffer before copying from it.
- A moved-from object is valid but unspecified; using it afterwards is a
  bug that compiles cleanly.


</Level>
<Level name="Production level">


In production C++ the rule is to let standard containers own memory and to
write none of the Big-Five if possible. In TypeScript, the same idea is
immutability by default and explicit copies (`structuredClone`, spread) when
a value crosses a boundary.


</Level>
<Level name="Mindset">


Analysis starts with mathematics, not with a stopwatch. Weiss wants me to
know what the answer should be before I measure it, which is the opposite
order from Sedgewick and a useful second view.


</Level>
<Level name="System design">


Ownership is a system-level idea too: which service owns a record, which one
may delete it, and who frees a resource on failure. The Big-Five are the
same questions asked about one object.


</Level>
<Level name="Strategy">


Skim the C++ unless I am writing C++. Do the maths review exercises on
logarithms and series by hand, since every later analysis uses them. Write
memoised Fibonacci and compare call counts with the naive version.


Done when I can prove the geometric series bound by induction and explain why a copy that shares a buffer double frees.

</Level>

</Levels>

### 2. Algorithm Analysis

**Covers:** Mathematical background (the definitions of O, Ω, Θ and little-o), the model
of computation, what to analyse, running-time calculations with general
rules, four solutions to the maximum subsequence sum problem, logarithms in
running times, and the limits of worst-case analysis.

<Levels label="Chapter 2, Algorithm Analysis">

<Level name="Beginner">


Big-O is an upper bound on growth, Ω a lower bound, Θ both. A loop of N
iterations doing constant work is O(N); two nested loops over N are O(N²).


</Level>
<Level name="Intermediate">


The maximum subsequence sum problem is the chapter's set piece: the same
answer in cubic, quadratic, N log N (divide and conquer) and linear time.

```ts
function maxSubSum(a: number[]): number {
  let best = 0, here = 0; // the empty subsequence counts as 0
  for (const x of a) {
    here = Math.max(0, here + x);
    best = Math.max(best, here);
  }
  return best;
}
```


</Level>
<Level name="Advanced">


An algorithm is O(log N) when constant work cuts the problem by a constant
fraction: binary search, Euclid's algorithm (the remainder at least halves
every two steps) and fast exponentiation. Worst-case analysis can be too
pessimistic, and average-case analysis needs an input distribution that may
not match reality, which is the chapter's closing caution.


</Level>
<Level name="Edge cases">


- If all numbers are negative, the linear algorithm above returns 0 because it
  allows the empty subsequence. A version that must return a real element
  needs a different start.
- Big-O hides constants; for small N a quadratic algorithm can win.


</Level>
<Level name="Corner cases">


- Two variables: an algorithm that is O(N + M) is not O(N) when M can be
  much larger than N.
- Logarithm bases do not matter inside O, but they matter in a real time
  estimate.


</Level>
<Level name="Production level">


In production the "N" is often not the obvious one: the number of tenants,
the size of the largest customer, the number of retries. Analysis is how I
notice the quadratic loop before the biggest customer finds it.


</Level>
<Level name="Mindset">


Four algorithms for one problem is the lesson: the first correct answer is
rarely the best one, and finding the linear one starts with asking what
information the slow one recomputes.


</Level>
<Level name="System design">


Capacity planning is asymptotic analysis with real constants: requests per
second times work per request, and how both grow as the data does.


</Level>
<Level name="Strategy">


Implement all four maximum subsequence sum algorithms, test them against
each other on random arrays, and time them at doubling sizes. Explain why the
linear one is correct with a loop invariant.


Done when all four versions agree on 1,000 random arrays and my timings show the cubic, quadratic, N log N and linear growth.

</Level>

</Levels>

## Chapters 3 to 6: the core structures

### 3. Lists, Stacks, and Queues

**Covers:** Abstract data types, the list ADT (array and linked versions), `vector` and
`list` in the standard library with iterators, implementations of both, the
stack ADT and its applications, and the queue ADT with an array (circular)
implementation.

<Levels label="Chapter 3, Lists, Stacks, and Queues">

<Level name="Beginner">


A list ADT is a sequence with insert, remove and find. An array makes
indexing constant and insertion in the middle linear; a linked list makes
insertion at a known node constant and indexing linear.


</Level>
<Level name="Intermediate">


The stack applications are the useful part: balancing brackets, evaluating
postfix expressions, converting infix to postfix, and the call stack itself.

```ts
function balanced(s: string): boolean {
  const pairs: Record<string, string> = { ')': '(', ']': '[', '}': '{' };
  const stack: string[] = [];
  for (const ch of s) {
    if ('([{'.includes(ch)) stack.push(ch);
    else if (ch in pairs && stack.pop() !== pairs[ch]) return false;
  }
  return stack.length === 0;
}
```


</Level>
<Level name="Advanced">


The array queue is circular: `front` and `back` wrap around with modulo, so
the queue never shifts elements. That is a ring buffer, the plan's
"stacks, queues, deques, and ring buffers" in one idea. Iterator invalidation
is the advanced point: erasing from a `vector` invalidates iterators after
the erased position; erasing from a `list` invalidates only the erased one.


</Level>
<Level name="Edge cases">


- A circular queue must tell "full" from "empty" when `front === back`. Keep
  a count or leave one slot unused.
- Removing the only node of a doubly linked list must update both head and
  tail.


</Level>
<Level name="Corner cases">


- Removing items from an array while iterating forward skips the element
  after each removal. Iterate backwards or build a new array.
- A sentinel (header and tail) node removes most special cases from a
  linked list, at the cost of two extra nodes.


</Level>
<Level name="Production level">


A ring buffer is how logs, audio, network cards and metrics windows hold a
fixed amount of recent data without allocation. Linked lists in production
are mostly intrusive lists inside kernels and allocators, or the order list
in an LRU cache.


</Level>
<Level name="Mindset">


"When is a linked list worse than an array?" Nearly always for scanning,
because of cache locality. The ADT is the same; the cost depends on memory
layout, which phase 5 will make concrete.


</Level>
<Level name="System design">


A queue between producer and consumer is the basic decoupling tool in a
system. Its capacity and its policy when full (block, drop, reject) are
design decisions, not implementation details.


</Level>
<Level name="Strategy">


Implement a doubly linked list with sentinels, a ring buffer queue, and the
bracket checker. Benchmark summing a million numbers in an array and in a
linked list and write the ratio down.


Done when the ring buffer passes a property test against an array-backed queue, including the full and empty states.

</Level>

</Levels>

### 4. Trees

**Covers:** Preliminaries and traversals, binary trees and expression trees, the binary
search tree (contains, findMin and findMax, insert, remove, average-case
analysis), AVL trees with single and double rotations, splay trees, tree
traversals revisited, B-trees, and sets and maps in the standard library.

<Figure caption="An AVL single rotation (right rotation at k2)" art={`
        k2                k1
       /  \\              /  \\
      k1   Z    ──▶     X    k2
     /  \\                   /  \\
    X    Y                 Y    Z
  X got too tall; Y changes parent; the order X < k1 < Y < k2 < Z is kept
`} />

<Levels label="Chapter 4, Trees">

<Level name="Beginner">


A tree is nodes with children and one root. Preorder visits a node before
its children, postorder after, inorder between the left and right subtree.
An inorder walk of a binary search tree gives the keys in sorted order.


</Level>
<Level name="Intermediate">


An expression tree has operators inside and operands at the leaves. A
postorder walk evaluates it; building one from a postfix expression uses a
stack of subtrees. BST removal of a node with two children replaces it with
the smallest key in its right subtree, then removes that key.


</Level>
<Level name="Advanced">


An AVL tree keeps the heights of every node's two subtrees within one of
each other. An insert can break this at one point on the path; a single
rotation fixes an outside insertion (left-left or right-right) and a double
rotation fixes an inside one (left-right or right-left). A splay tree makes
no balance promise per operation; it rotates each accessed node to the root,
and the guarantee is amortised: M operations cost O(M log N). A B-tree of
order M stores between M/2 and M children per internal node, so its height
is about log base M/2 of N.


</Level>
<Level name="Edge cases">


- Removing the root, a leaf, and a node with one child are three different
  paths in the code. Test each.
- Duplicate keys: decide whether to reject, count, or keep a list per node.
- AVL deletion can need rotations at several levels on the way up, not just
  one; the fourth edition includes the deletion code.


</Level>
<Level name="Corner cases">


- The average-case BST depth of about 1.39 lg N assumes random insertion
  order and no deletions; repeated deletions with the successor rule skew
  the tree.
- A splay tree turns read operations into writes, which hurts concurrency
  and cache behaviour.


</Level>
<Level name="Production level">


AVL trees appear where lookups dominate; red–black trees (chapter 12) where
updates are frequent. B-trees are the default on disk. Language standard
maps (`std::map`, Java's `TreeMap`) are red–black trees.


</Level>
<Level name="Mindset">


Balance is a promise about the worst case. Each balanced tree makes a
different promise (strict height, loose height, amortised), and choosing
one is choosing which promise the system needs.


</Level>
<Level name="System design">


A file system directory, a database index and a DOM are trees. The decision
to store a tree in memory, in pages on disk, or flattened into rows changes
which of these algorithms apply.


</Level>
<Level name="Strategy">


Implement the BST, then AVL insert and delete, with a check function that
verifies the balance property after every operation in a property test. Draw
all four rotation cases on paper before writing them.


Done when a property test of 10,000 random inserts and deletes never finds a node out of AVL balance.

</Level>

</Levels>

### 5. Hashing

**Covers:** The general idea, hash functions, separate chaining, hash tables without
linked lists (linear probing, quadratic probing, double hashing), rehashing,
hash tables in the standard library, worst-case constant access (perfect,
cuckoo and hopscotch hashing), universal hashing, and extendible hashing.

<Levels label="Chapter 5, Hashing">

<Level name="Beginner">


A hash function maps a key to a table index. A collision is two keys with the
same index. The load factor is the number of keys divided by the table size;
performance depends on keeping it bounded.


</Level>
<Level name="Intermediate">


Open addressing stores everything in the array. Linear probing tries `h`,
`h+1`, `h+2`; quadratic probing tries `h+1`, `h+4`, `h+9`; double hashing
steps by a second hash. Quadratic probing with a prime table size at most
half full is guaranteed to find an empty slot.

```ts
function strHash(s: string, size: number): number {
  let h = 0;
  for (let i = 0; i < s.length; i++) h = (h * 31 + s.charCodeAt(i)) >>> 0; // keep 32 bits
  return h % size;
}
```


</Level>
<Level name="Advanced">


Universal hashing picks the hash function at random from a family, so no
fixed input is bad for every choice. Cuckoo hashing gives each key two
possible slots and evicts the occupant to its other slot on insert, so
lookups check at most two places. Hopscotch hashing keeps each key within a
small neighbourhood of its home slot. Extendible hashing is for disk: a
directory of pointers to buckets that split one at a time.


</Level>
<Level name="Edge cases">


- Deleting in open addressing needs a tombstone ("deleted" marker) or a
  reinsert of the cluster; emptying the slot breaks lookups.
- Rehashing must reinsert every key with the new size, not copy slots.
- Cuckoo insertion can cycle; the fix is to rehash with new functions.


</Level>
<Level name="Corner cases">


- Tombstones accumulate: a table with many deletes is full of markers and
  slow, even with few live keys.
- A hash of a floating-point key: `0` and `-0` are equal but have different
  bits; `NaN` is not equal to itself.


</Level>
<Level name="Production level">


Standard hash maps (`unordered_map`, JavaScript `Map`) handle this for me,
but I still choose keys. In distributed systems the same idea becomes
consistent hashing, so that adding a server moves few keys. Seeded hashes
protect against collision flooding.


</Level>
<Level name="Mindset">


A hash table's speed is a bet on the hash function and the input. Universal
hashing is the habit of making that bet explicit and random rather than
implicit and fixed.


</Level>
<Level name="System design">


Extendible hashing and consistent hashing both answer "how do I grow without
moving everything?", which is the question behind database sharding and
cache clusters.


</Level>
<Level name="Strategy">


Implement linear and quadratic probing with tombstones and rehashing.
Measure probe counts at load factors 0.25, 0.5, 0.75 and 0.9. Then build a
small cuckoo table and watch an insertion cycle happen.


Done when my probe-count table matches the expected trend and deletes never lose a key in a property test.

</Level>

</Levels>

### 6. Priority Queues (Heaps)

**Covers:** The model, simple implementations, the binary heap (structure property,
heap-order property, insert, deleteMin, buildHeap), applications (selection
and event simulation), d-heaps, leftist heaps, skew heaps, binomial queues,
and priority queues in the standard library.

<Levels label="Chapter 6, Priority Queues (Heaps)">

<Level name="Beginner">


A priority queue supports insert and deleteMin. A binary heap is a complete
binary tree stored in an array where every parent is at most its children.


</Level>
<Level name="Intermediate">


Insert percolates up; deleteMin moves the last element to the root and
percolates down. buildHeap from N items is linear, not N log N, because most
nodes are near the bottom and move only a short way.

```ts
function siftDown(h: number[], i: number, n = h.length) {
  for (let c = 2 * i + 1; c < n; i = c, c = 2 * i + 1) {
    if (c + 1 < n && h[c + 1] < h[c]) c++;
    if (h[i] <= h[c]) break;
    [h[i], h[c]] = [h[c], h[i]];
  }
}
const heapify = (h: number[]) => { for (let i = (h.length >> 1) - 1; i >= 0; i--) siftDown(h, i); };
```


</Level>
<Level name="Advanced">


A binary heap cannot merge two heaps quickly. Leftist heaps, skew heaps and
binomial queues can, in O(log N). A d-heap with more children per node makes
inserts cheaper and deletes more expensive, and has better cache behaviour.


</Level>
<Level name="Edge cases">


- deleteMin on an empty heap.
- Duplicate priorities: a heap is not stable, so equal priorities come out in
  no particular order. Add a sequence number if order matters.


</Level>
<Level name="Corner cases">


- Changing an item's priority needs its position in the heap: an indexed
  priority queue keeps a map from item to index. Dijkstra needs this or lazy
  deletion.
- Zero-based and one-based indexing give different child formulas. Mixing
  them is the most common heap bug.


</Level>
<Level name="Production level">


Timers in event loops, job schedulers, top-k queries and Dijkstra all run on
heaps. Lazy deletion (leave stale entries, skip them on pop) is the usual
production trick.


</Level>
<Level name="Mindset">


The heap gives up full order for partial order and gets cheaper operations.
Asking for less is often the fastest optimisation.


</Level>
<Level name="System design">


An event-driven simulator, a rate limiter's next-allowed time and a
scheduler's run queue are all priority queues. Their correctness under equal
priorities is a design decision.


</Level>
<Level name="Strategy">


Implement a binary heap with linear buildHeap and an indexed version with
decrease-key. Prove to myself that buildHeap is linear by summing the node
heights.


Done when heapify plus N pops returns sorted output on random input and decrease-key keeps the heap valid.

</Level>

</Levels>

## Chapters 7 and 8: using the structures

### 7. Sorting

**Covers:** Insertion sort, the lower bound for simple (adjacent-swap) sorts, Shellsort,
heapsort, mergesort, quicksort (pivot choice, partitioning, small arrays,
analysis, and quickselect), the general and decision-tree lower bounds,
adversary lower bounds, bucket sort and radix sort, and external sorting.

<Levels label="Chapter 7, Sorting">

<Level name="Beginner">


Insertion sort is simple and fast on small or nearly sorted input. An
inversion is a pair out of order; any sort that swaps only adjacent items
must remove every inversion one at a time, so it needs Ω(N²) on average.


</Level>
<Level name="Intermediate">


Median-of-three pivoting and a cutoff to insertion sort for small subarrays
are the chapter's practical quicksort. Quickselect partitions once and
recurses into one side only, giving expected linear time for the k-th
smallest.


</Level>
<Level name="Advanced">


A decision tree with N! leaves has height at least lg(N!), which is Ω(N log
N): that is the lower bound for comparison sorting. Radix sort escapes it by
not comparing; it reads digits. External sorting creates sorted runs that fit
in memory, then merges them with a multiway merge; replacement selection
makes the runs longer than memory on average.


</Level>
<Level name="Edge cases">


- Quicksort with every key equal: the partition must stop on equal keys, or
  it goes quadratic.
- Radix sort on negative numbers or floats needs a key transform first.


</Level>
<Level name="Corner cases">


- Median-of-three is defeated by crafted "median-of-three killer" inputs;
  introsort switches to heapsort when recursion gets too deep.
- Shellsort's running time depends on the gap sequence, and its exact
  average-case complexity for good sequences is still not fully known.


</Level>
<Level name="Production level">


Library sorts are hybrids: introsort in many C++ libraries, TimSort in
Python, Java (for objects) and V8. External merge sort is how databases sort
results bigger than memory.


</Level>
<Level name="Mindset">


Lower bounds tell me when to stop optimising. If a sort compares, N log N is
the floor; going below it needs a different model.


</Level>
<Level name="System design">


A database `ORDER BY` on a large table spills to disk and runs this
chapter's external sort. An index avoids that sort entirely, which is often
the real fix.


</Level>
<Level name="Strategy">


Write quicksort with median-of-three, a cutoff and correct equal-key
handling; write quickselect; write an LSD radix sort. Add them to the
phase 4 sorting benchmark.


Done when my quicksort stays fast on all-equal input and quickselect agrees with sorting on random arrays.

</Level>

</Levels>

### 8. The Disjoint Sets Class

**Covers:** Equivalence relations, the dynamic equivalence problem, the basic forest
structure, smart union (by size and by height or rank), path compression,
the worst case for union-by-rank with path compression, and an application
(maze generation).

<Levels label="Chapter 8, The Disjoint Sets Class">

<Level name="Beginner">


A disjoint-set structure keeps items in groups. `find` returns a group's
representative; `union` merges two groups. An equivalence relation
(reflexive, symmetric, transitive) is exactly what it models.


</Level>
<Level name="Intermediate">


```ts
class DSU {
  parent: number[]; rank: number[];
  constructor(n: number) { this.parent = [...Array(n).keys()]; this.rank = new Array(n).fill(0); }
  find(x: number): number {
    while (this.parent[x] !== x) { this.parent[x] = this.parent[this.parent[x]]; x = this.parent[x]; } // path halving
    return x;
  }
  union(a: number, b: number): boolean {
    let ra = this.find(a), rb = this.find(b);
    if (ra === rb) return false;
    if (this.rank[ra] < this.rank[rb]) [ra, rb] = [rb, ra];
    this.parent[rb] = ra;
    if (this.rank[ra] === this.rank[rb]) this.rank[ra]++;
    return true;
  }
}
```


</Level>
<Level name="Advanced">


With both union by rank and path compression, M operations on N items cost
O(M α(M, N)), where α is the inverse Ackermann function. The fourth
edition's proof uses a recursive decomposition. α is at most 4 or 5 for any
input that could exist, which is why the structure is "practically
constant".


</Level>
<Level name="Edge cases">


- `union(x, x)` must not change ranks.
- Path compression with recursion can overflow the stack on a long chain
  built before compression; path halving is iterative.


</Level>
<Level name="Corner cases">


- Union–find cannot split groups. If edges are deleted, it is the wrong
  structure.
- Rank is an upper bound on height once compression runs, not the height.


</Level>
<Level name="Production level">


Kruskal's MST, connected components on a stream of edges, merging duplicate
user accounts, and type inference (unification) all use it.


</Level>
<Level name="Mindset">


The analysis is famously hard, the code is ten lines. A simple structure can
hide a deep result; I can use it without proving it, but I should know the
bound.


</Level>
<Level name="System design">


Entity resolution in a data pipeline is union–find over "these two records
are the same" signals, often run in batches.


</Level>
<Level name="Strategy">


Implement it, then build the chapter's maze generator: knock down random
walls between cells in different sets until all cells connect.


Done when the maze generator always produces exactly one path between any two cells.

</Level>

</Levels>

## Chapters 9 and 10: algorithms on top

### 9. Graph Algorithms

**Covers:** Definitions and representation, topological sort, shortest paths
(unweighted, Dijkstra, negative edge costs, acyclic graphs, all-pairs),
network flow with a simple maximum-flow algorithm, minimum spanning trees
(Prim and Kruskal), applications of depth-first search (undirected graphs,
biconnectivity, Euler circuits, directed graphs, strong components), and an
introduction to NP-completeness.

<Levels label="Chapter 9, Graph Algorithms">

<Level name="Beginner">


A graph is vertices and edges. Use an adjacency list unless the graph is
dense. Topological sort orders a directed acyclic graph so every edge points
forward; the chapter's version repeatedly removes a vertex with no incoming
edges (Kahn's algorithm).


</Level>
<Level name="Intermediate">


```ts
function topoSort(n: number, edges: [number, number][]): number[] | null {
  const indeg = new Array(n).fill(0), adj: number[][] = Array.from({ length: n }, () => []);
  for (const [u, v] of edges) { adj[u].push(v); indeg[v]++; }
  const q = [...Array(n).keys()].filter((v) => indeg[v] === 0), order: number[] = [];
  for (let i = 0; i < q.length; i++) {
    order.push(q[i]);
    for (const w of adj[q[i]]) if (--indeg[w] === 0) q.push(w);
  }
  return order.length === n ? order : null; // null: there is a cycle
}
```


</Level>
<Level name="Advanced">


Biconnectivity uses DFS numbering and "low" values to find articulation
points: vertices whose removal disconnects the graph. Euler circuits exist
when every vertex has even degree and the graph is connected. Strong
components come from two DFS passes. The NP-completeness section separates
problems with known polynomial algorithms from those like the travelling
salesperson and Hamiltonian cycle.


</Level>
<Level name="Edge cases">


- The root of a DFS tree is an articulation point only if it has two or more
  DFS children.
- Kahn's algorithm with several zero in-degree vertices has more than one
  valid order; tests must accept any valid one.


</Level>
<Level name="Corner cases">


- Euler circuit (every edge once) is easy; Hamiltonian cycle (every vertex
  once) is NP-complete. The two sound alike.
- Negative edges with no negative cycle: Dijkstra is still wrong; the
  chapter's queue-based Bellman–Ford is right.


</Level>
<Level name="Production level">


Articulation points are single points of failure in a network. Topological
sort runs every build and every migration ordering. Max flow is how capacity
across a network is reasoned about.


</Level>
<Level name="Mindset">


Many graph problems are DFS plus one extra number per vertex. Learning DFS
deeply pays off more than memorising ten algorithms.


</Level>
<Level name="System design">


Finding single points of failure in a service dependency graph is the
biconnectivity algorithm applied to architecture.


</Level>

### 10. Algorithm Design Techniques

**Covers:** Greedy algorithms (a scheduling problem, Huffman codes, approximate bin
packing), divide and conquer (its running time, closest points, selection,
arithmetic improvements), dynamic programming (tables instead of recursion,
ordering matrix multiplications, optimal binary search trees, all-pairs
shortest paths), randomised algorithms (random number generators, skip
lists, primality testing), and backtracking (turnpike reconstruction and
games).

<Levels label="Chapter 10, Algorithm Design Techniques">

<Level name="Beginner">


Greedy makes the locally best choice and never revisits it. Divide and
conquer splits, solves and combines. Dynamic programming solves overlapping
subproblems once and stores them. Backtracking tries choices and undoes them
on failure.


</Level>
<Level name="Intermediate">


Bin packing shows greedy as an approximation: first fit decreasing uses at
most about 11/9 of the optimal number of bins plus a small constant. A skip
list is a randomised linked list with express lanes, giving expected
logarithmic search without rotations.


</Level>
<Level name="Advanced">


The master theorem bounds recurrences of the form T(N) = aT(N/b) + Θ(N^k).
The linear-time selection algorithm (median of medians) shows divide and
conquer can give a worst-case guarantee where randomisation gives only an
expected one. Minimax with alpha–beta pruning is backtracking for games.


</Level>
<Level name="Edge cases">


- Closest pair with duplicate points has distance zero.
- Random number generators: a linear congruential generator with bad
  parameters has short cycles and visible patterns.


</Level>
<Level name="Corner cases">


- Greedy coin change works for some coin systems and fails for others, for
  example coins 1, 3 and 4 making 6.
- A primality test that is probabilistic can be wrong; the chapter's test has
  a bounded error per trial, so repeated trials make it negligible.


</Level>
<Level name="Production level">


Skip lists are the ordered set inside Redis sorted sets. Randomised
algorithms are everywhere in load balancing and sampling. Use a
cryptographic random source when the randomness protects anything.


</Level>
<Level name="Mindset">


The technique is a lens: before writing code, I ask which of the five
techniques the problem's structure invites.


</Level>
<Level name="System design">


Approximation is a design choice. A scheduler that packs containers onto
machines uses bin-packing heuristics because the exact problem is hard.


</Level>

## Chapters 11 and 12: depth

### 11. Amortized Analysis

**Covers:** An unrelated puzzle to show the idea, then amortised bounds for binomial
queues, skew heaps, Fibonacci heaps (cutting nodes, lazy merging, the
operations and the proof), and splay trees.

<Levels label="Chapter 11, Amortized Analysis">

<Level name="Beginner">


Amortised analysis bounds the total cost of a sequence of operations, so an
occasional expensive one is paid for by many cheap ones. The doubling array
from phase 3 is the first example.


</Level>
<Level name="Intermediate">


The potential method stores "prepaid" work in a potential function of the
data structure. Amortised cost is actual cost plus the change in potential.
If potential never drops below its start, total amortised cost bounds total
actual cost.


</Level>
<Level name="Advanced">


Fibonacci heaps get amortised constant insert and decrease-key, and
logarithmic delete-min, by being lazy: they merge trees only on delete-min
and cut nodes on decrease-key, with a "mark" rule that keeps trees bushy.
That is what makes Dijkstra O(E + V log V) in theory.


</Level>
<Level name="Edge cases">


- An amortised bound says nothing about one operation's latency. A single
  splay or resize can be slow.


</Level>
<Level name="Corner cases">


- Fibonacci heaps have large constants and poor locality; in practice a
  binary or pairing heap is usually faster.


</Level>
<Level name="Production level">


Latency-sensitive systems care about the worst single operation, so they
use incremental resizing or structures with worst-case bounds even when the
amortised bound is better elsewhere.


</Level>
<Level name="Mindset">


"Expensive sometimes" and "expensive on average" are different claims. I
should say which one I mean.


</Level>
<Level name="System design">


Garbage collection pauses and hash table resizes are amortised costs that
show up as tail latency in a service.


</Level>
<Level name="Strategy">


Read this after phase 3's gate. Redo the dynamic array proof with the
potential method, then read the splay tree proof once.


Done when I can write the potential function for the doubling array and show that each push costs a constant amount amortised.

</Level>

<Levels label="Chapter 12, Advanced Data Structures and Implementation">

<Level name="Beginner">

## Misreadings to avoid

- "Analysis replaces measurement." A bound says how cost grows; only a
  benchmark says what the constant is on my machine.
- "AVL trees are always better than red–black trees." AVL is more tightly
  balanced, so lookups are a little shorter and updates rotate more. The
  workload decides.
- "A hash table is O(1)." Expected O(1), under a good hash function and a
  bounded load factor. The worst case is linear.
- "Amortised means average over random input." Amortised is a guarantee
  over any sequence of operations; no probability is involved.
- "Advanced structures are what real code uses." Most production code uses a
  dynamic array, a hash map and a sorted array. Chapter 12 is for knowing
  when that stops being enough.
- "The C++ is the point." The language is the vehicle; the analysis is what
  transfers to TypeScript.
