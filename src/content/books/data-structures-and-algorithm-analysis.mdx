## Why this book

This is the optional depth for <a href={withBase('/plans/traditional-software-developer/#strategy-3')}>phase 3, data structures</a>.
Where <a href={withBase('/books/algorithms-sedgewick-wayne/')}>Sedgewick and Wayne</a> teach
by experiment, Weiss teaches by analysis: no structure appears without its
running time, and the later chapters go past what the phase requires into
amortised analysis and the structures that need it.

The plan names the book without a language. There are C++, Java and C
editions with the same overall shape. I follow the C++ fourth edition's
table of contents here because the publisher lists it section by section. My
examples are in TypeScript, the language of the phase, with C where memory
layout is the point.

## How I would learn it

I would use Weiss to check my understanding, not to build it the first time.
After writing a structure from Sedgewick, I would read Weiss's chapter and
try to answer its analysis questions before reading the answers: why is
buildHeap linear, why does quadratic probing need a prime size, why does AVL
deletion need more than one rotation. Every question I cannot answer goes
in the study log as a card.

Each chapter now has its own page below, written as a full chapter: every
section of the book taught from first principles in TypeScript, with traces,
proofs walked line by line, the common mistake, where it shows up in real
systems, and the nine levels from beginner to strategy. I read the page, then
the book's chapter, then do the exercises.

I would do the easier exercises for each chapter I read and leave the
hardest for a second pass. The C++
details in chapter 1 I would read once, then come back to in phase 5, when C
memory makes them concrete.

This book is depth, not the spine. During phase 3 I read chapters 3 to 6 and
8 alongside Sedgewick, one chapter per structure, to get the analysis that
Sedgewick measures. Chapters 7, 9 and 10 are a second view during phase 4.
Chapters 11 and 12 are for after the phase 3 gate, when the library exists
and I want to know what else could replace each part.

## What I learn from it

- [ ] Chapter 1: use exponents, logarithms, series, modular arithmetic and induction; write recursion that obeys the four rules; explain C++ ownership, the Big-Five and templates.
- [ ] Chapter 2: define O, Ω, Θ and little-o; count running time with the general rules; solve maximum subsequence sum four ways; spot logarithmic algorithms.
- [ ] Chapter 3: build a growable array, a sentinel doubly linked list with iterators, stacks and a circular queue; use stacks for brackets, postfix and infix conversion.
- [ ] Chapter 4: traverse trees; build expression trees; implement BST contains, insert and remove; write all four AVL rotations; explain splaying, B-trees and ordered maps.
- [ ] Chapter 5: design hash functions; build separate chaining and open addressing tables with rehashing; explain perfect, cuckoo, hopscotch, universal and extendible hashing.
- [ ] Chapter 6: build a binary heap with linear buildHeap; use heaps for selection and simulation; explain d-heaps, leftist, skew and binomial heaps.
- [ ] Chapter 7: write and analyse insertion sort, Shellsort, heapsort, mergesort, quicksort and quickselect; prove the comparison lower bounds; sort by radix and externally.
- [ ] Chapter 8: implement union–find with smart union and path compression; explain the log-star and inverse Ackermann bounds; generate a maze.
- [ ] Chapter 9: represent graphs; topologically sort; find shortest paths, maximum flows and spanning trees; use DFS for biconnectivity, Euler circuits and strong components; explain NP-completeness.
- [ ] Chapter 10: recognise and apply greedy, divide and conquer, dynamic programming, randomised and backtracking designs.
- [ ] Chapter 11: use the potential method on binomial queues, skew heaps, Fibonacci heaps and splay trees.
- [ ] Chapter 12: implement top-down splay and red–black trees, treaps, suffix arrays, k-d trees and pairing heaps.

## Misreadings to avoid

- "Analysis replaces measurement." A bound says how cost grows; only a
  benchmark says what the constant is on my machine.
- "AVL trees are always better than red–black trees." AVL is more tightly
  balanced, so lookups are a little shorter and updates rotate more. The
  workload decides.
- "A hash table is O(1)." Expected O(1), under a good hash function and a
  bounded load factor. The worst case is linear.
- "Amortised means average over random input." Amortised is a guarantee
  over any sequence of operations; no probability is involved.
- "Advanced structures are what real code uses." Most production code uses a
  dynamic array, a hash map and a sorted array. Chapter 12 is for knowing
  when that stops being enough.
- "The C++ is the point." The language is the vehicle; the analysis is what
  transfers to TypeScript.

## Done with this book when

- Every structure in my phase 3 library has a stated bound in its README,
  and I can derive it rather than quote it.
- My AVL tree and hash tables pass property tests against `Map`, including
  deletes.
- I can explain why buildHeap is linear, why quadratic probing needs a prime
  table size, and what α means in union–find.
- I can answer the phase 3 gate questions: when a hash table beats a
  balanced tree, why a B-tree suits disk, and what an LRU cache is made of.
