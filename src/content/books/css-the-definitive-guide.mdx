## Why this book

Phase 2 of the <a href={withBase('/plans/software-ai-developer/')}>software AI developer</a> roadmap asks for a
frontend with no layout shift, a Lighthouse score of 95 or more and a design-system component I can defend. I write
CSS every week, mostly by trying things until the page looks right. That works until a specificity fight, a
collapsing margin or a grid item that refuses to shrink eats an afternoon. This book is the reference that explains
why: every property, how values are computed, and how the cascade decides.

It is a reference, not a tutorial, and the fifth edition covers modern CSS: custom properties, logical properties,
flexbox, grid, container queries and cascade layers. I do not read it cover to cover in one go. I read the
foundations properly, then each layout and text chapter when my phase 2 app needs it.

## How I would learn it

For each chapter I keep a scratch HTML file and DevTools open. I read a section, write the smallest example, and
predict the computed value before checking it in the Computed panel. When my prediction is wrong I write down why.
Then I apply the chapter to my phase 2 app: one real component restyled with what I just learned, and a Lighthouse
and layout-shift check before and after.

## What I learn from it

- How style sheets attach to documents, and how the browser parses and applies them.
- Every selector type, including `:is()`, `:where()`, `:has()` and the pseudo-elements.
- Specificity, inheritance, the cascade, origins, importance and cascade layers.
- Values and units: lengths, percentages, `calc()`, custom properties, colours and viewport units.
- The box model, block and inline formatting, margin collapsing and logical properties.
- Backgrounds, gradients, floats and every positioning scheme, including sticky.
- Flexbox and grid in depth, plus table layout.
- Fonts, font loading, text properties, line height, white space and writing modes.
- Lists, counters and generated content.
- Transforms, transitions, animations and `prefers-reduced-motion`.
- Filters, blending, clipping and masking.
- At-rules: media queries, container queries, `@supports` and paged media.

## Foundations

### 1. CSS Fundamentals

**Covers:** Where CSS came from, how elements are displayed (replaced and nonreplaced, block and inline), linking style sheets, `@import`, the `style` element and attribute, rule structure, vendor prefixes, white space and comments, and how media and feature queries fit.

<Flow steps={['HTML parsed into DOM', 'style sheets fetched and parsed', 'rules matched to elements', 'cascade picks one value per property', 'layout', 'paint']} caption="From markup to pixels. Each chapter in the foundations explains one step of the middle three." />

<Levels label="Chapter 1, CSS Fundamentals">

<Level name="Beginner">

A rule is a selector and a block of declarations. A style sheet attaches with `link`, `style` or the `style` attribute.

```html
<link rel="stylesheet" href="site.css">
<style>h1 { color: maroon; font-size: 2rem; }</style>
```

```
computed: h1 color rgb(128, 0, 0), font-size 32px (with a 16px root)
```

Mistake: a missing semicolon between declarations, so the next one is swallowed. Fix: end every declaration with `;`.

</Level>

<Level name="Intermediate">

Invalid declarations are dropped individually, not the whole rule. That forgiving parse is how fallbacks work.

```css
.box { width: 50%; width: min(50%, 40rem); }
```

Old browsers drop the second line and keep the first. Mistake: one invalid selector in a selector list drops the whole
rule. Fix: use `:is()`, which is forgiving, or separate rules.

</Level>

<Level name="Advanced">

`@import` must come before every other rule except `@charset` and `@layer` statements, and it blocks: the browser
discovers the imported file only after downloading the first.

```
DevTools: the @import rule is ignored when placed after other rules
```

Fix: `link` elements in HTML for parallel downloads, or a build step that inlines the imports.

</Level>

<Level name="Edge cases">

Replaced elements (`img`, `video`, form controls) have content outside the document's styling, so pseudo-elements
like `::before` do not render on an `img`, and their intrinsic size drives layout.

</Level>

<Level name="Corner cases">

`display` changes the box but not the element: `display: block` on a `span` makes a block box, but the `span` is still
not allowed to contain block content in HTML terms, and `display: contents` removes the box and, in older browsers,
the element's accessibility role. Fix: choose the right element for meaning, and use `display` only for layout.

</Level>

<Level name="Production level">

Ship CSS that is small, cached and not render-blocking beyond what the first screen needs: one hashed stylesheet,
critical styles inline, and `media` attributes on print styles so they do not block rendering.

</Level>

<Level name="Mindset">

CSS is declarative. I say what should be true, and the browser decides how. Fighting that ends in `!important`.

</Level>

<Level name="System design">

CSS architecture is about where styles live: global, per component, or utility classes. Each choice trades cascade
power for predictability, and the book's foundations are what let me make that choice deliberately.

</Level>

<Level name="Strategy">

I build a page with `link`, `style` and inline styles and predict which wins. Done when I can explain every computed
value on my app's main heading from the Styles panel.

</Level>

</Levels>

### 2. Selectors

**Covers:** Element, universal, class and ID selectors, attribute selectors (presence, exact, partial and case-insensitive), grouping, descendant, child and sibling combinators, and the structure of the document tree.

<Figure art={`
  article          "article p"   any p inside article   (descendant)
   +-- h2          "article > p" only direct children   (child)
   +-- p   <-- h2 + p     the p right after h2          (next sibling)
   +-- p   <-- h2 ~ p     every later sibling p         (subsequent sibling)
   +-- div
        +-- p  <-- matched by "article p", not by "article > p"
`} caption="The four combinators on one small tree." />

<Levels label="Chapter 2, Selectors">

<Level name="Beginner">

Selectors choose elements: by type, class, ID or attribute.

```css
p { margin-block: 1em; }
.warning { color: darkred; }
#main { max-width: 60rem; }
a[href^="https://"] { text-decoration-style: dotted; }
```

Mistake: `.warning.large` (both classes on one element) confused with `.warning .large` (a descendant). Fix: the
space is a combinator.

</Level>

<Level name="Intermediate">

Combinators express relationships, and grouping applies one block to many selectors.

```css
h2 + p { margin-block-start: 0; }
nav > ul > li { display: inline-block; }
h1, h2, h3 { line-height: 1.2; }
```

Mistake: long descendant chains like `.page .content .card .title`. Fix: a class on the element itself.

</Level>

<Level name="Advanced">

Attribute operators: `[a="x"]` exact, `[a~="x"]` one word in a space-separated list, `[a|="en"]` `en` or `en-`
prefix, `[a^=]` starts, `[a$=]` ends, `[a*=]` contains, and the `i` flag for case-insensitive values.

```css
a[href$=".pdf" i]::after { content: " (PDF)"; }
```

```
matches: report.PDF and report.pdf
```

</Level>

<Level name="Edge cases">

IDs must be unique, but CSS matches every element with the ID anyway, so a duplicate ID styles two elements without
complaint, while `getElementById` returns only the first. Fix: classes for styling, IDs for anchors and ARIA references.

</Level>

<Level name="Corner cases">

Selectors match right to left: the browser starts from the rightmost part. `div *` matches every element inside any
`div`, and in a large DOM a universal selector at the end of a chain is costly when combined with frequent style
recalculation. Fix: keep the rightmost part specific (a class).

</Level>

<Level name="Production level">

In a component system I select by class almost always, avoid IDs and element selectors inside components, and keep
specificity flat so overrides are predictable.

</Level>

<Level name="Mindset">

A selector is a query over the document tree. A good one says what the element is, not where it happens to be.

</Level>

<Level name="System design">

Naming conventions (BEM, CSS modules, utility classes) are selector strategies for teams. They exist to make
selectors local, so one team's change cannot restyle another team's component.

</Level>

<Level name="Strategy">

I play a selector game: write selectors for given elements in a sample tree and check them with
`document.querySelectorAll`. Done when every selector in my app is one or two classes deep.

</Level>

</Levels>

### 3. Pseudo-Class and -Element Selectors

**Covers:** Combining pseudo-classes, structural pseudo-classes (`:first-child`, `:nth-child()`, `:nth-of-type()`, `:empty`, `:root`), location and user-action pseudo-classes, UI state pseudo-classes, `:not()`, `:is()`, `:where()`, `:has()`, and the pseudo-elements `::before`, `::after`, `::first-line`, `::first-letter`, `::marker`, `::placeholder`, `::selection` and others.

<Compare left="Pseudo-class" right="Pseudo-element" rows={[
  ['a state or position of a real element', 'a part of an element, or a generated box'],
  ['one colon: :hover, :nth-child(2)', 'two colons: ::before, ::first-line'],
  ['adds to specificity like a class', 'adds to specificity like an element'],
  ['many per selector', 'one per selector, at the end'],
]} caption="Pseudo-classes select elements in a state; pseudo-elements create or select parts that are not elements." />

<Levels label="Chapter 3, Pseudo-Class and -Element Selectors">

<Level name="Beginner">

Pseudo-classes select elements in a state or position; pseudo-elements select parts of them.

```css
a:hover, a:focus-visible { text-decoration-thickness: 2px; }
li:nth-child(odd) { background: #f4f4f4; }
.required::after { content: " *"; }
```

Mistake: `:focus` styling that shows a ring on every mouse click. Fix: `:focus-visible`.

</Level>

<Level name="Intermediate">

`:is()` groups, `:where()` groups with zero specificity, `:not()` excludes, `:has()` selects by what an element
contains.

```css
:where(h1, h2, h3) { margin-block: 0 0.5em; }
.card:has(img) { grid-template-rows: auto 1fr; }
label:has(+ input:invalid) { color: darkred; }
```

Mistake: expecting `:where()` overrides to win. They have no specificity, so any later class beats them. Fix: use
`:where()` for defaults and `:is()` when the rule must hold.

</Level>

<Level name="Advanced">

`:nth-child(An+B of S)` counts only elements matching S; `:nth-of-type` counts by element type.

```css
li:nth-child(2 of .visible) { font-weight: bold; }
```

```
In a list where the first li is hidden (not .visible), the second visible item is bold, not the second li.
```

</Level>

<Level name="Edge cases">

`:empty` matches only elements with no children at all, including no white space text, so `<p> </p>` is not empty.
And `::before` content is not in the DOM, so it is not selectable and screen readers may or may not read it.

Fix: never put essential information in generated content.

</Level>

<Level name="Corner cases">

`:has()` with a relative selector that changes often, such as `body:has(input:focus)`, forces the browser to
re-evaluate styles for large parts of the page on every focus change. Fix: anchor `:has()` to the smallest container
that needs it.

</Level>

<Level name="Production level">

Form validation styling with `:invalid` shows errors before the user types anything. In production I use
`:user-invalid` (or a class set after the first blur) so errors appear only after interaction.

</Level>

<Level name="Mindset">

Pseudo-classes let CSS react to state without script. Every state I can express in CSS is a state I do not have to
synchronise in JavaScript.

</Level>

<Level name="System design">

`:has()` changes component boundaries: a parent can now style itself by its children. That is powerful and couples
the parent to its children's markup, so I document it as part of the component's contract.

</Level>

<Level name="Strategy">

I rebuild a form's validation and a striped table using only pseudo-classes. Done when the form shows errors only after
interaction and the table stripes survive filtered rows with `of S`.

</Level>

</Levels>

### 4. Specificity and the Cascade

**Covers:** Specificity calculation, declarations and specificity, the universal selector and combinators, ID and attribute selectors, inline styles, importance, inheritance, the cascade with origins and importance, cascade layers, sorting by order, and non-CSS presentational hints.

<Flow steps={['origin and importance', 'context (shadow DOM)', 'inline style', 'cascade layer', 'specificity', 'order of appearance']} caption="How the cascade picks a winner, top to bottom. Specificity is only the fifth question asked." />

<Levels label="Chapter 4, Specificity and the Cascade">

<Level name="Beginner">

When two rules set the same property, the more specific selector wins; at equal specificity, the later one wins.

```css
p { color: black; }        /* 0,0,1 */
.note { color: navy; }     /* 0,1,0 */
#intro { color: green; }   /* 1,0,0 */
```

```
<p id="intro" class="note"> computes to green
```

Mistake: adding an ID to win a fight. Fix: lower the other rule's specificity instead.

</Level>

<Level name="Intermediate">

Inheritance passes some properties (colour, font, line height) from parent to child; box properties (border, margin)
do not inherit. Inherited values have no specificity at all, so any rule that targets the child beats them.

```css
#nav { color: white; }
a { color: blue; }
```

```
links inside #nav are blue: the a rule targets them directly, the white is only inherited
```

</Level>

<Level name="Advanced">

Cascade layers order whole groups of rules before specificity is even considered.

```css
@layer reset, base, components, utilities;
@layer utilities { .mt-0 { margin-top: 0; } }
@layer components { #hero .title { margin-top: 2rem; } }
```

```
.mt-0 wins: the utilities layer beats the components layer, whatever the selectors
```

Unlayered styles beat every layer for normal declarations.

</Level>

<Level name="Edge cases">

`!important` reverses layer order: an important declaration in an earlier layer beats an important one in a later
layer, and important user-agent and user styles beat author ones. That is how user accessibility styles can win.

</Level>

<Level name="Corner cases">

`:is()` takes the specificity of its most specific argument, so `:is(#a, .b) p` has ID specificity even when matching
through `.b`. A harmless-looking selector suddenly beats everything. Fix: `:where()` for groupings that should not
add weight.

</Level>

<Level name="Production level">

In a large codebase I set up layers once (reset, base, components, utilities), keep specificity flat inside each, and
ban `!important` outside utilities. Third-party CSS goes into its own low layer.

</Level>

<Level name="Mindset">

When styles fight, I ask which step of the cascade decides, instead of adding weight and hoping.

</Level>

<Level name="System design">

Layers are the CSS architecture tool for teams: they encode "utilities beat components beat base" in the language
itself, instead of in naming conventions people forget.

</Level>

<Level name="Strategy">

I compute specificity for twenty selectors by hand and check them in DevTools, then refactor one stylesheet into
layers. Done when my app has no `!important` and no ID selectors in component styles.

</Level>

</Levels>

### 5. Values and Units

**Covers:** Keywords and global keywords (`inherit`, `initial`, `unset`, `revert`, `revert-layer`), strings, URLs, numbers, percentages, distances (absolute, font-relative and viewport units), `calc()`, `min()`, `max()`, `clamp()`, attribute values, colours (named, RGB, HSL, HWB, Lab, LCH, `color()`), angles, times, frequencies, ratios, position values, custom properties, and specified, computed and used values.

<Flow steps={['declared value', 'cascaded value', 'specified value', 'computed value', 'used value', 'actual value']} caption="How a value travels from the style sheet to the screen. DevTools' Computed panel shows the computed value, and layout uses the used value." />

<Levels label="Chapter 5, Values and Units">

<Level name="Beginner">

Values have types: lengths, percentages, numbers, colours, keywords. Relative units scale with something else.

```css
html { font-size: 100%; }    /* usually 16px */
h1 { font-size: 2rem; }      /* 32px */
.lead { font-size: 1.25em; } /* relative to the parent's font size */
```

Mistake: `px` font sizes everywhere, which ignore the user's browser font setting. Fix: `rem` for type.

</Level>

<Level name="Intermediate">

`clamp()` and `calc()` combine units, and custom properties make values reusable.

```css
:root { --space: 1rem; }
h1 { font-size: clamp(1.75rem, 1.2rem + 2vw, 3rem); margin-block-end: calc(var(--space) * 2); }
```

```
computed at 1000px wide: font-size 39.2px, between the 28px minimum and the 48px maximum
```

Mistake: `calc(1rem+2vw)` without spaces, which is invalid. Fix: spaces around `+` and `-`.

</Level>

<Level name="Advanced">

Custom properties are inherited and substituted at computed-value time, so an invalid value is caught late: the
declaration becomes invalid at computed-value time and falls back to `inherit` or `initial`, not to the previous
declaration.

```css
.box { --w: red; width: 10rem; width: var(--w); }
```

```
computed width: auto (the initial value), not 10rem
```

</Level>

<Level name="Edge cases">

`100vh` on mobile includes the area behind the address bar, so a full-height hero is cut off. Fix: `100dvh` (dynamic)
or `100svh` (small), with `100vh` as a fallback before it.

</Level>

<Level name="Corner cases">

A percentage padding is relative to the containing block's width, even for top and bottom padding, which is how the old
aspect-ratio hack worked. Combined with `box-sizing: border-box` and a percentage height, the results surprise. Fix:
`aspect-ratio` for ratios.

</Level>

<Level name="Production level">

A design system defines its scales (space, type, colour) as custom properties with semantic names. Colours move to
`oklch()` for predictable lightness, with fallbacks where needed.

</Level>

<Level name="Mindset">

Every number in CSS is relative to something. I always ask "relative to what?" before I write a unit.

</Level>

<Level name="System design">

Tokens are values with names, owned by the design system and consumed by every component. Changing a token is a
system-wide change, so tokens need versioning like an API.

</Level>

<Level name="Strategy">

I build a type and space scale with `clamp()` and custom properties and check computed values at three widths. Done
when no component in my app uses a raw `px` value for type or spacing.

</Level>

</Levels>

## Misreadings to avoid

- "It is a reference, so I can skip the foundations." Every later chapter assumes the cascade and computed values.
- "Specificity decides everything." Origin, importance and layers are asked first.
- "The longest selector wins." Specificity counts IDs, then classes, then types; length does not matter.
