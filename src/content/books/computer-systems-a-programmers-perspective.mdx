## Why this book

This is the primary book for <a href={withBase('/plans/traditional-software-developer/#strategy-5')}>phase 5, computer architecture and C</a>
of the traditional core, and it comes back in the
<a href={withBase('/plans/underrated-fundamentals/')}>underrated fundamentals</a> for the
memory and performance lenses. Its title is the reason I picked it over a
hardware book: it explains the machine from the side of the person writing
the program. Every chapter answers a question I have hit as a JavaScript
developer without knowing the answer, such as why `0.1 + 0.2` is not `0.3`,
why one loop order is ten times faster than another, or what a segfault
actually is.

<a href={withBase('/books/computer-organization-and-design/')}>Computer Organization and Design</a>
is the depth book: it explains the same machine from the hardware designer's
side. I read CS:APP first, and open Patterson and Hennessy when I want to
know how a pipeline or a cache is built.

The examples are C and x86-64 assembly, the book's own languages, with
JavaScript or TypeScript beside them when the contrast teaches something.

## How I would learn it

The labs are the book. The CS:APP site publishes the labs that go with the
book (Data Lab, Bomb Lab, Attack Lab, Architecture Lab, Cache Lab,
Performance Lab, Shell Lab, Malloc Lab and Proxy Lab), and I would treat each
chapter as reading for a lab, not the other way round. I read a chapter with
a terminal open, compile every example with `gcc -Og` and look at the output
of `objdump -d`, and do the practice problems inside the chapter as I go,
because their answers are at the chapter's end and tell me straight away if
I have misread something.

Phase 5 is five weeks, so I would not do every lab. Data Lab, Bomb Lab and
Cache Lab map exactly onto the phase's build and gate. Malloc Lab, Shell Lab
and Proxy Lab belong to phase 6 (operating systems) and phase 7
(networking), and I would come back to chapters 8, 10, 11 and 12 then.

Every C file in the phase is built with `-Wall -Wextra -g
-fsanitize=address,undefined`, and every claim about speed is measured with
`perf stat` or cachegrind, never assumed.

## What I learn from it

Each chapter has its own page, linked in the contents below. One line per
chapter of what I can do once I have worked through it:

- [ ] **1, A Tour of Computer Systems:** follow `hello.c` from source text to pixels on a terminal, naming every layer, and use Amdahl's law on a real profile.
- [ ] **2, Representing and Manipulating Information:** read a hex dump, explain byte order, two's complement, signed and unsigned conversion, overflow, shifts, and IEEE 754 bit by bit.
- [ ] **3, Machine-Level Representation of Programs:** read `gcc -Og` x86-64 for arithmetic, branches, loops, switches, calls, arrays and structs, draw a stack frame and explain a buffer overflow and its defences.
- [ ] **4, Processor Architecture:** explain an instruction set as a contract, trace Y86-64 instructions through the six SEQ stages and the five-stage pipeline, and resolve data and control hazards.
- [ ] **5, Optimizing Program Performance:** measure cycles per element, remove the blockers a compiler cannot remove (aliasing, calls, memory traffic), and use unrolling and multiple accumulators to reach the latency and throughput bounds.
- [ ] **6, The Memory Hierarchy:** explain locality, cache lines, sets, tags and associativity, simulate a cache by hand, and reorder loops for spatial locality.
- [ ] **7, Linking:** explain symbols, strong and weak resolution, static libraries and their order, relocation, ELF executables, shared libraries, PIC with the GOT and PLT, and interpositioning.
- [ ] **8, Exceptional Control Flow:** explain exceptions, processes and context switches, and use `fork`, `execve`, `waitpid` and signal handlers without races.
- [ ] **9, Virtual Memory:** translate a virtual address through a TLB and a four-level page table, explain page faults, `mmap`, copy-on-write, and write a working allocator.
- [ ] **10, System-Level I/O:** handle short counts, explain the descriptor, open-file and v-node tables, redirection, and when to use Unix I/O versus standard I/O.
- [ ] **11, Network Programming:** build a sockets client and server with `getaddrinfo`, speak HTTP by hand, and explain how a tiny web server serves static and dynamic content.
- [ ] **12, Concurrent Programming:** compare processes, I/O multiplexing and threads for a server, reason about shared variables with progress graphs, use semaphores and mutexes, and find races and deadlocks.

The book's Appendix A, on error handling and the capitalised wrapper
functions, is short; I cover it inside chapter 8's section on system call
error handling. I keep the habit of checking every call and drop the habit
of exiting: in a library, return the error instead.

## Misreadings to avoid

- "This is a hardware book." It is about the machine as the programmer sees
  it; the hardware detail is there to explain program behaviour.
- "x86-64 is the point." The ideas (calling conventions, stacks, caches,
  virtual memory) transfer to ARM and RISC-V.
- "The compiler will optimise it." Only what it can prove safe; aliasing and
  function calls block it.
- "Caches are a hardware concern." Data layout in my code decides the hit
  rate.
- "JavaScript developers do not need this." Every V8 performance cliff,
  every memory limit and every event-loop stall is explained here.
- "Defences make overflows harmless." Canaries and ASLR raise the cost of an
  attack; they do not fix the bug.

## Done with this book when

- My C dynamic array and string library builds clean with sanitizers and
  passes its tests under Valgrind.
- My cache simulator matches cachegrind on a few traces, and my
  matrix-multiply table shows the loop orders I predicted.
- I can explain an assembly listing of my own code line by line.
- I can pass the phase 5 gate: read assembly, measure a cache-friendly loop,
  find a bug with ASan or Valgrind, and explain virtual versus physical
  memory.
