## Why this book

This is the primary book for <a href={withBase('/plans/traditional-software-developer/#strategy-5')}>phase 5, computer architecture and C</a>
of the traditional core, and it comes back in the
<a href={withBase('/plans/underrated-fundamentals/')}>underrated fundamentals</a> for the
memory and performance lenses. Its title is the reason I picked it over a
hardware book: it explains the machine from the side of the person writing
the program. Every chapter answers a question I have hit as a JavaScript
developer without knowing the answer, such as why `0.1 + 0.2` is not `0.3`,
why one loop order is ten times faster than another, or what a segfault
actually is.

<a href={withBase('/books/computer-organization-and-design/')}>Computer Organization and Design</a>
is the depth book: it explains the same machine from the hardware designer's
side. I read CS:APP first, and open Patterson and Hennessy when I want to
know how a pipeline or a cache is built.

The examples are C and x86-64 assembly, the book's own languages, with
JavaScript or TypeScript beside them when the contrast teaches something.

## How I would learn it

The labs are the book. The CS:APP site publishes the labs that go with the
book (Data Lab, Bomb Lab, Attack Lab, Architecture Lab, Cache Lab,
Performance Lab, Shell Lab, Malloc Lab and Proxy Lab), and I would treat each
chapter as reading for a lab, not the other way round. I read a chapter with
a terminal open, compile every example with `gcc -Og` and look at the output
of `objdump -d`, and do the practice problems inside the chapter as I go,
because their answers are at the chapter's end and tell me straight away if
I have misread something.

Phase 5 is five weeks, so I would not do every lab. Data Lab, Bomb Lab and
Cache Lab map exactly onto the phase's build and gate. Malloc Lab, Shell Lab
and Proxy Lab belong to phase 6 (operating systems) and phase 7
(networking), and I would come back to chapters 8, 10, 11 and 12 then.

Every C file in the phase is built with `-Wall -Wextra -g
-fsanitize=address,undefined`, and every claim about speed is measured with
`perf stat` or cachegrind, never assumed.

## Chapter 1: the tour

### 1. A Tour of Computer Systems

**Covers:** Following one hello-world program through the system: information as bits
in context, compilation, the hardware that runs it, caches and the storage
hierarchy, the operating system's processes, threads, virtual memory and
files, networks, Amdahl's law, concurrency and parallelism, and the
importance of abstractions.

<Levels label="Chapter 1, A Tour of Computer Systems">

<Level name="Beginner">


A program is bytes. The same bytes are text in an editor, instructions to
the CPU, or a number, depending on what reads them. `hello.c` goes through
the preprocessor, the compiler, the assembler and the linker to become an
executable file.


</Level>
<Level name="Intermediate">


Running it means the shell asks the OS to load it; the CPU fetches its
instructions from memory; `printf` ends in a system call that writes to the
terminal. Caches exist because the processor is much faster than main
memory.


</Level>
<Level name="Advanced">


The OS gives each program three illusions: a process (the CPU to itself),
virtual memory (all of memory to itself) and files (every device as a
sequence of bytes). Amdahl's law bounds the speed-up from improving one
part: if a part takes a fraction α of the time and gets k times faster, the
whole thing speeds up by 1 over ((1 − α) + α/k).


</Level>
<Level name="Edge cases">


- A program that does nothing still costs a process, a page table and a
  loader run. Startup time is real.
- A program that produces no output still produces an exit status.


</Level>
<Level name="Corner cases">


- Amdahl with k going to infinity: even an infinitely fast part leaves the
  rest, so a 90% part caps the speed-up at ten.


</Level>
<Level name="Production level">


Node itself is a C++ program going through exactly this: loaded, linked
against libc and V8, running in a process with virtual memory, writing with
system calls. When it is slow, these layers are where the time goes.


</Level>
<Level name="Mindset">


Every abstraction I use is built from the layer below it, and it leaks. The
book's aim is that I can look one layer down when it does.


</Level>
<Level name="System design">


Amdahl's law is the first question in any optimisation or scaling plan:
what fraction of the time is the part I want to improve?


</Level>
<Level name="Strategy">


Compile hello.c with `gcc -save-temps` and open each intermediate file, then
run it under `strace`. Done when I can name each stage from source to
system call and use Amdahl's law on a profile of my own code.

</Level>

</Levels>

## Part I — Program Structure and Execution

### 2. Representing and Manipulating Information

**Covers:** How data is stored: hexadecimal, word sizes, byte order, strings and code as
bytes, Boolean algebra and bit-level operations, logical and shift
operations, unsigned and two's-complement integers and conversions between
them, extension and truncation, integer addition, negation, multiplication
and division by powers of two, and IEEE 754 floating point with its
rounding and operations.

<Levels label="Chapter 2, Representing and Manipulating Information">

<Level name="Beginner">


Everything is bits. A byte is eight. Hex writes four bits per digit, so a
32-bit number is eight hex digits. An unsigned integer of w bits holds 0 to
2 to the w minus 1. Two's complement gives the top bit a negative weight, so
an 8-bit value runs from −128 to 127.


</Level>
<Level name="Intermediate">


Byte order decides how a multi-byte number sits in memory: x86 is little
endian, the least significant byte first.

```c
#include <stdio.h>
int main(void) {
    int x = 0x01234567;
    unsigned char *p = (unsigned char *)&x;
    for (size_t i = 0; i < sizeof x; i++) printf("%02x ", p[i]);
    printf("\n");   /* prints 67 45 23 01 on x86-64 */
}
```

In JavaScript, a `DataView` makes the same choice explicit with its
`littleEndian` argument.


</Level>
<Level name="Advanced">


Integer arithmetic is arithmetic modulo 2 to the w. Unsigned overflow wraps
and is defined in C; signed overflow is undefined behaviour, which lets the
compiler assume it never happens. Floating point stores a sign, an exponent
and a fraction; 0.1 has no exact binary form, so `0.1 + 0.2` rounds to a
neighbour of 0.3.

```ts
0.1 + 0.2 === 0.3;              // false
Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON;  // true
(2 ** 31) | 0;                  // -2147483648: bitwise ops use 32-bit ints
```


</Level>
<Level name="Edge cases">


- The minimum two's-complement value has no positive twin: `-INT_MIN`
  overflows, and `abs(INT_MIN)` is undefined.
- Shifting by the word size or more is undefined in C; JavaScript masks the
  count to five bits, so `1 << 32` is 1.
- Floats have +0 and −0, infinities and NaN, and `NaN !== NaN`.


</Level>
<Level name="Corner cases">


- Comparing signed and unsigned in C converts the signed value: `-1 &lt;
  0u` is false. A loop `for (unsigned i = n - 1; i >= 0; i--)` never ends.
- Large integers above 2 to the 53 in a JavaScript `number` lose their low
  bits, so IDs from a 64-bit database column must be strings or `bigint`.
- Floating-point addition is not associative: summing a big array in a
  different order gives a different answer.


</Level>
<Level name="Production level">


Money is never a float: use integer cents or a decimal type. Size
calculations (`n * sizeof(T)`) can overflow and allocate too little, a
classic security bug; check before multiplying.


</Level>
<Level name="Mindset">


Numbers in a computer are finite. Ask "what is the range, and what happens
at its edge?" before trusting arithmetic.


</Level>
<Level name="System design">


Wire formats and file formats fix width and byte order for every field.
Protocols say "network byte order" (big endian) because two machines must
agree.


</Level>
<Level name="Strategy">


Do Data Lab, then write a small program that prints the bit pattern of any
float and check it against the IEEE rules by hand. Done when I can explain
`0.1 + 0.2`, `-1 < 0u` and `abs(INT_MIN)` without running them.

</Level>

</Levels>

### 3. Machine-Level Representation of Programs

**Covers:** x86-64 assembly as the compiler produces it: program encodings, data formats,
operands and data movement, push and pop, `lea`, arithmetic and logic,
condition codes, jumps, conditional moves, loops and switch statements,
procedures and the run-time stack, arrays, structures, unions and alignment,
pointers, using gdb, buffer overflows and the defences against them,
variable-size stack frames, and floating-point code.

<Levels label="Chapter 3, Machine-Level Representation of Programs">

<Level name="Beginner">


The compiler turns C into instructions that move data between registers and
memory and do arithmetic. `gcc -Og -S file.c` shows the assembly;
`objdump -d` shows it for a compiled file.

```c
long sum(long *a, long n) {
    long s = 0;
    for (long i = 0; i < n; i++) s += a[i];
    return s;
}
```

Compiled with `gcc -Og`, it becomes something close to this (the exact
output varies with the compiler version):

```asm
sum:                      # a in %rdi, n in %rsi
    movl  $0, %eax        # s = 0
    movl  $0, %edx        # i = 0
.L3:
    cmpq  %rsi, %rdx      # compare i with n
    jge   .L1
    addq  (%rdi,%rdx,8), %rax   # s += a[i]
    addq  $1, %rdx
    jmp   .L3
.L1:
    ret                   # result in %rax
```


</Level>
<Level name="Intermediate">


Arguments arrive in `%rdi`, `%rsi`, `%rdx`, `%rcx`, `%r8`, `%r9`, and the
result leaves in `%rax`. The addressing mode `(%rdi,%rdx,8)` computes
`a + i*8`, which is how array indexing becomes one instruction. Conditions set
flags, and jumps read them.


</Level>
<Level name="Advanced">


`call` pushes the return address on the stack and `ret` pops it. Local
arrays live in the stack frame, below the return address. A write past the
end of a local buffer overwrites the return address, which is how a buffer
overflow takes control. Stack canaries, non-executable stacks and address
randomisation are the defences.


</Level>
<Level name="Edge cases">


- `lea` does address arithmetic without touching memory, so compilers use
  it for plain arithmetic like `x*3 + 4`.
- Struct fields are padded to their alignment; `sizeof` a struct can be
  larger than the sum of its fields.


</Level>
<Level name="Corner cases">


- A `gets` into a stack buffer with a canary and ASLR: the overflow is
  detected at return, but only after it has already corrupted the frame.
  Defences limit damage; they do not make unsafe code safe.
- Recursion without a base case runs off the end of the stack into a
  guard page: a segfault, the same thing as a JavaScript "Maximum call stack
  size exceeded" one level down.


</Level>
<Level name="Production level">


Reading assembly is how I check that a hot loop got vectorised, that a bounds
check was removed, or what a crash address means in a core dump. V8's
optimising compiler emits machine code too, and `--print-opt-code` shows it.


</Level>
<Level name="Mindset">


The compiler is a translator I can check. When I doubt what my code does,
I read what it became.


</Level>
<Level name="System design">


Calling conventions are the contract that lets code from different
compilers and languages call each other: Node's native addons, FFI and
WebAssembly all rely on one.


</Level>
<Level name="Strategy">


Do Bomb Lab with gdb, then explain an assembly listing of my own C function
line by line, as the phase build asks. Done when I can read a function's
assembly and say where each local variable lives.

</Level>

</Levels>

### 4. Processor Architecture

**Covers:** A processor designed from scratch: the Y86-64 instruction set, logic design
and the hardware control language HCL, a sequential implementation (SEQ),
the principles of pipelining, a pipelined implementation (PIPE) with data
and control hazards and exception handling, and performance analysis.

<Levels label="Chapter 4, Processor Architecture">

<Level name="Beginner">


A processor runs instructions in stages: fetch the instruction, decode it
and read registers, execute in the ALU, access memory, write back the
result, and update the program counter. Y86-64 is the book's small
x86-like instruction set for building one.


</Level>
<Level name="Intermediate">


A sequential processor does all stages for one instruction per clock cycle,
so the cycle is as long as the slowest path. Pipelining puts registers
between stages so five instructions are in flight at once, one per stage.

<Flow caption="One instruction through the pipeline" steps={["fetch", "decode", "execute", "memory", "write back"]} />


</Level>
<Level name="Advanced">


Hazards break the overlap. A data hazard is an instruction needing a result
not yet written; forwarding passes it straight from a later stage. A
load-use hazard still needs a one-cycle stall. A control hazard is a branch
whose outcome is unknown; the processor predicts and, if wrong, cancels the
fetched instructions.


</Level>
<Level name="Edge cases">


- An instruction that faults in the middle of the pipeline must not let
  later instructions change state: exceptions must be precise.


</Level>
<Level name="Corner cases">


- A mispredicted branch followed by a load-use hazard and a return: the
  control logic must decide which bubble wins, which is where processor bugs
  live.


</Level>
<Level name="Production level">


Branch misprediction is why sorted data makes some loops faster, and why
branchless code (conditional moves) sometimes wins. Modern CPUs are deeply
pipelined, out of order and superscalar, but these hazards remain the
vocabulary.


</Level>
<Level name="Mindset">


Throughput and latency are different. A pipeline does not make one
instruction faster; it lets more finish per second.


</Level>
<Level name="System design">


Pipelining is everywhere above the hardware: HTTP pipelining, CI stages,
stream processing. The same hazards (dependencies, stalls, flushes) apply.


</Level>
<Level name="Strategy">


Trace three short Y86-64 programs through PIPE on paper, marking every
forward and stall, then run them in the book's simulator. Done when I can
predict the cycle count of a small loop and explain each stall.

</Level>

</Levels>

### 5. Optimizing Program Performance

**Covers:** Making code faster on a modern processor: what stops a compiler optimising,
measuring in cycles per element, removing loop inefficiencies, unneeded
procedure calls and memory references, how out-of-order processors work,
loop unrolling, multiple accumulators, reassociation, register spilling,
branch prediction penalties, load and store performance, and profiling.

<Levels label="Chapter 5, Optimizing Program Performance">

<Level name="Beginner">


First choose the right algorithm. Then remove obvious waste from loops, such
as calling `strlen` in the loop condition, which makes a linear loop
quadratic.

```c
/* quadratic: strlen runs every iteration */
for (size_t i = 0; i < strlen(s); i++) s[i] = tolower(s[i]);
/* linear */
for (size_t i = 0, n = strlen(s); i < n; i++) s[i] = tolower(s[i]);
```


</Level>
<Level name="Intermediate">


The compiler cannot move code it cannot prove safe. Two pointers that might
alias the same memory force it to reload from memory each time; accumulating
into a local variable fixes it. Cycles per element (CPE) measures a loop's
cost independently of n.


</Level>
<Level name="Advanced">


An out-of-order processor runs independent operations in parallel, so a
single accumulator chain is bound by the latency of one add. Unrolling with
several accumulators, or reassociating `(acc * a[i]) * a[i+1]` into `acc *
(a[i] * a[i+1])`, breaks the chain and approaches the throughput bound.


</Level>
<Level name="Edge cases">


- Unrolling by k needs a cleanup loop for the last n mod k items.
- Reassociating floating-point code changes the result, so compilers will
  not do it without `-ffast-math`.


</Level>
<Level name="Corner cases">


- Too many accumulators: they spill out of registers to the stack and the
  loop gets slower again.


</Level>
<Level name="Production level">


Profile first. `perf record` and `perf report` show where time goes; the
fix is rarely where I guessed. Most JavaScript performance work is the same
loop-invariant hoisting and allocation avoidance, applied to the engine's
rules.


</Level>
<Level name="Mindset">


Measure, change one thing, measure again. Performance work without numbers is
guessing.


</Level>
<Level name="System design">


The critical path idea, latency of a dependency chain versus throughput of
independent work, is the same one that sizes connection pools and parallel
requests.


</Level>
<Level name="Strategy">


Take the book's combine-style loop over a vector, apply each optimisation in
turn, and record CPE with `perf stat` after each. Done when my table shows
the latency bound, then the throughput bound, and I can explain both.

</Level>

</Levels>

### 6. The Memory Hierarchy

**Covers:** Storage technologies (RAM, disks, solid-state disks), locality, the memory
hierarchy and caching in it, cache memories (direct-mapped, set associative,
fully associative), issues with writes, real cache hierarchies and their
performance, and writing cache-friendly code, including the memory mountain
and rearranging loops for locality.

<Levels label="Chapter 6, The Memory Hierarchy">

<Level name="Beginner">


Fast memory is small and expensive; big memory is slow and cheap. So
computers stack them: registers, L1, L2, L3 caches, main memory, then SSD
or disk. Programs with good locality, reusing recent data (temporal) or
nearby data (spatial), run mostly from the fast levels.

<Layers caption="The memory hierarchy, fastest and smallest at the top" layers={[{"name": "Registers", "note": "a few hundred bytes, inside the CPU, no delay"}, {"name": "L1 cache", "note": "tens of KB per core, a few cycles"}, {"name": "L2 cache", "note": "hundreds of KB to a few MB, around ten cycles"}, {"name": "L3 cache", "note": "shared, several MB, tens of cycles"}, {"name": "Main memory (DRAM)", "note": "gigabytes, around a hundred cycles"}, {"name": "SSD and disk", "note": "terabytes, microseconds to milliseconds"}]} />


</Level>
<Level name="Intermediate">


A cache holds lines (often 64 bytes). An address splits into tag, set
index and block offset. A direct-mapped cache has one line per set; a set
associative cache has E lines per set, which reduces conflict misses.

```c
/* row-major walk: stride 1, good spatial locality */
for (int i = 0; i < N; i++) for (int j = 0; j < N; j++) sum += a[i][j];
/* column walk: stride N, a miss on almost every access for large N */
for (int j = 0; j < N; j++) for (int i = 0; i < N; i++) sum += a[i][j];
```


</Level>
<Level name="Advanced">


Misses are cold (first touch), conflict (two addresses fighting for one set)
or capacity (the working set is too big). Writes are write-through or
write-back, with write-allocate or not. The memory mountain plots read
throughput against working-set size and stride, showing each cache level
as a ridge. Matrix multiply's six loop orders differ several times over in
speed because of their strides.


</Level>
<Level name="Edge cases">


- Arrays whose size is a power of two can map rows onto the same sets and
  thrash a cache that the working set would otherwise fit.


</Level>
<Level name="Corner cases">


- Two threads writing different variables in the same cache line: false
  sharing. The line bounces between cores, and the program slows down with
  no shared data at all.


</Level>
<Level name="Production level">


Data layout decides speed: arrays of structs versus structs of arrays, typed
arrays in JavaScript versus arrays of objects, column stores in analytics
databases. The same O(n) loop can differ ten times in speed.


</Level>
<Level name="Mindset">


Memory access, not arithmetic, is usually the cost. Ask where the data is.


</Level>
<Level name="System design">


Every cache in a system (CDN, Redis, the page cache, the CPU cache) has the
same vocabulary: hit rate, working set, eviction, write policy.


</Level>
<Level name="Strategy">


Do Cache Lab: write the cache simulator, then run my matrix multiply in all
six loop orders under `perf stat -e cache-misses` and cachegrind. Done when
I can predict the fastest and slowest orders before measuring, which is the
phase 5 gate.

</Level>

</Levels>

## Part II — Running Programs on a System

### 7. Linking

**Covers:** How separately compiled files become one program: compiler drivers, static
linking, relocatable object files and their symbols and symbol tables,
symbol resolution, static libraries, relocation, executable object files,
loading, dynamic linking with shared libraries, loading them at run time,
position-independent code, library interpositioning, and the tools for
looking at object files.

<Levels label="Chapter 7, Linking">

<Level name="Beginner">


Each `.c` file compiles to an object file with code, data and a symbol
table: the names it defines and the names it needs. The linker joins
objects, matches each needed name to one definition, and writes an
executable.

```sh
gcc -c main.c util.c          # two .o files
nm util.o                     # T = defined function, U = undefined
gcc main.o util.o -o app      # the linker resolves the symbols
```


</Level>
<Level name="Intermediate">


A static library (`.a`) is an archive of objects; the linker copies in only
the members that resolve something still undefined, scanning left to right.
A shared library (`.so`) is linked at load time or run time by the dynamic
linker, so many programs share one copy in memory.


</Level>
<Level name="Advanced">


Relocation patches addresses in the code once the final layout is known.
Position-independent code reaches globals through a table (the GOT) and
calls other libraries' functions through stubs (the PLT), so a shared
library can be loaded at any address. `dlopen` loads a library while the
program runs, which is how plugins work.


</Level>
<Level name="Edge cases">


- Library order on the command line matters: `gcc -lm main.o` can fail where
  `gcc main.o -lm` works, because the library was scanned before anything
  needed it.
- `static` on a global makes the symbol local to its file.


</Level>
<Level name="Corner cases">


- Two files each defining an uninitialised global with the same name: older
  toolchains merged them silently (common symbols) and newer GCC rejects
  them by default. Different types for the "same" variable corrupt memory
  without any error under the old rules.


</Level>
<Level name="Production level">


"Works on my machine" is often a different shared library version.
`ldd`, `LD_LIBRARY_PATH` and `LD_PRELOAD` (interpositioning) are the tools.
Node native addons are shared libraries loaded with `dlopen`, which is why
they must be rebuilt for each Node ABI.


</Level>
<Level name="Mindset">


A build is a pipeline of separate tools with contracts between them. When it
fails, find which tool failed.


</Level>
<Level name="System design">


Static versus dynamic linking is a deployment choice: self-contained
binaries (Go, containers built `FROM scratch`) versus shared, patchable
libraries.


</Level>
<Level name="Strategy">


Build my C string library as both a `.a` and a `.so`, link a program against
each, and inspect them with `nm`, `objdump` and `readelf`. Done when I can
explain an "undefined reference" error and fix it without searching.

</Level>

</Levels>

### 8. Exceptional Control Flow

**Covers:** Exceptions (interrupts, traps, faults and aborts), processes, handling
system-call errors, process control with fork, execve and waitpid, signals,
nonlocal jumps, and tools for manipulating processes.

<Levels label="Chapter 8, Exceptional Control Flow">

<Level name="Beginner">


Control flow normally goes from one instruction to the next. Exceptions jump
elsewhere: an interrupt from a device, a trap for a system call, a fault
such as a page fault, or an abort on a hardware error.


</Level>
<Level name="Intermediate">


`fork` creates a copy of the process; it returns twice, 0 in the child and
the child's pid in the parent. `execve` replaces the program in the current
process. `waitpid` reaps a finished child.

```c
pid_t pid = fork();
if (pid == 0) { execlp("ls", "ls", "-l", (char *)NULL); _exit(127); }
int status;
waitpid(pid, &status, 0);
```


</Level>
<Level name="Advanced">


Signals are software interrupts delivered to a process: `SIGINT` from
Ctrl+C, `SIGCHLD` when a child ends, `SIGSEGV` on a bad memory access. A
handler can run between any two instructions of the main program, so it may
only call async-signal-safe functions.


</Level>
<Level name="Edge cases">


- `fork` can fail (too many processes); check for −1.
- A child that exits and is never waited for stays as a zombie.


</Level>
<Level name="Corner cases">


- Signals do not queue: two `SIGCHLD`s arriving while one is blocked are
  seen as one, so a handler must reap in a loop until no child is left.
- Calling `printf` in a signal handler can deadlock if the main program was
  inside `printf` when the signal arrived.


</Level>
<Level name="Production level">


Process managers, shells, container runtimes and Node's `child_process`
are built on these calls. Graceful shutdown on `SIGTERM` is a production
requirement for any service.


</Level>
<Level name="Mindset">


Anything can happen between two instructions. Code that handles
asynchronous events must be written with that in mind.


</Level>
<Level name="System design">


Kubernetes sends `SIGTERM`, waits, then `SIGKILL`. A service that ignores the
first signal loses in-flight requests.


</Level>
<Level name="Strategy">


Write a tiny shell that runs commands, handles Ctrl+C for the foreground job
and reaps background jobs, then do Shell Lab in phase 6. Done when no zombie
is left after a stress test of a hundred background jobs.

</Level>

</Levels>

### 9. Virtual Memory

**Covers:** Physical and virtual addressing, address spaces, VM as a tool for caching,
memory management and protection, address translation with the TLB and
multi-level page tables, the Core i7 and Linux memory systems, memory
mapping, dynamic memory allocation (implicit and explicit free lists,
segregated lists, coalescing), garbage collection, and common memory bugs in
C.

<Levels label="Chapter 9, Virtual Memory">

<Level name="Beginner">


Every process sees its own virtual address space. The hardware (the MMU)
translates each virtual address to a physical one, page by page, using page
tables the OS maintains.


</Level>
<Level name="Intermediate">


A virtual address splits into a page number and an offset. The page table
maps the page number to a physical frame. The TLB caches recent
translations, because walking the table on every access would be far too
slow.

<Figure caption="A 4 KB page: the low 12 bits pass through, the rest are translated." art={`
 virtual address  [ virtual page number      | offset (12 bits) ]
                              |                        |
                     TLB / page table                  |
                              v                        v
 physical address [ physical frame number    | offset (12 bits) ]
`} />


</Level>
<Level name="Advanced">


x86-64 uses four levels of page tables, so most of the address space needs
no table at all. A page fault happens when a page is not in memory; the OS
loads it and retries the instruction. `mmap` maps a file or anonymous
memory into the address space, and `fork` shares pages copy-on-write.
`malloc` manages a heap inside this space with free lists, splitting and
coalescing blocks.


</Level>
<Level name="Edge cases">


- Reading address 0: the zero page is unmapped on purpose, so a null
  pointer dereference faults instead of reading garbage.
- `malloc(0)` may return NULL or a unique pointer; both are allowed.


</Level>
<Level name="Corner cases">


- Freeing a block twice corrupts the allocator's free list, and the crash
  happens later in an unrelated `malloc`. AddressSanitizer catches it at
  the second `free`.
- Overcommit: Linux can promise more memory than exists, so `malloc`
  succeeds and the process is killed later by the OOM killer when it touches
  the pages.


</Level>
<Level name="Production level">


Resident set size versus virtual size, page faults, swapping and the OOM
killer explain most "out of memory" incidents. In Node, the V8 heap lives in
this virtual space, and `--max-old-space-size` is a limit V8 sets on itself
inside it.


</Level>
<Level name="Mindset">


An address is a name, not a location. The OS decides where it really is.


</Level>
<Level name="System design">


Memory-mapped files are how databases (LMDB, and the page cache under
Postgres) avoid copying. Container memory limits are cgroup limits on this
system.


</Level>
<Level name="Strategy">


Write a small allocator with an implicit free list and coalescing, run it
under AddressSanitizer and Valgrind, and later do Malloc Lab. Done when I can
explain the difference between virtual and physical memory with a page table
drawn on paper, which is the phase 5 gate.

</Level>

</Levels>

## Part III — Interaction and Communication between Programs

### 10. System-Level I/O

**Covers:** Unix I/O, files, opening and closing, reading and writing, robust reading and
writing with the book's Rio package, file metadata, directories, sharing
files, I/O redirection, and standard I/O, with advice on which to use.

<Levels label="Chapter 10, System-Level I/O">

<Level name="Beginner">


In Unix, a file is a sequence of bytes, and devices, pipes and sockets look
like files too. `open` returns a small integer, the file descriptor;
`read` and `write` move bytes; `close` releases it.


</Level>
<Level name="Intermediate">


`read` can return fewer bytes than asked (a short count) at end of file, on
a pipe or on a socket. Robust code loops until it has what it needs.

```c
ssize_t read_full(int fd, void *buf, size_t n) {
    size_t left = n; char *p = buf;
    while (left > 0) {
        ssize_t r = read(fd, p, left);
        if (r < 0) { if (errno == EINTR) continue; return -1; }
        if (r == 0) break;                 /* end of file */
        left -= r; p += r;
    }
    return n - left;
}
```


</Level>
<Level name="Advanced">


The kernel keeps three tables: a descriptor table per process, an open-file
table (with the current offset) and a v-node table. `dup2` points one
descriptor at another's open file, which is how a shell redirects output.
Standard I/O (`fopen`, `printf`) adds a user-space buffer on top.


</Level>
<Level name="Edge cases">


- A read of 0 bytes means end of file, not an error.
- A write to a pipe whose reader has gone raises `SIGPIPE`.


</Level>
<Level name="Corner cases">


- Mixing `printf` and `write` on the same descriptor: the buffered output
  comes out later, in the wrong order. A `fork` with unflushed buffers
  prints the buffer twice.


</Level>
<Level name="Production level">


Node's streams handle short reads and backpressure for me; Unix I/O is what
they are built on. "Too many open files" is a descriptor leak.


</Level>
<Level name="Mindset">


The happy path is a full read. Robust code is written for the short one.


</Level>
<Level name="System design">


Everything-is-a-file is why pipes, redirection and Unix tools compose. It is
the original plugin interface.


</Level>
<Level name="Strategy">


Write `cat` and `cp` with plain Unix I/O and the short-count loop, and test
them on pipes. Done when they behave the same as the real tools on a pipe,
an empty file and a file larger than memory.

</Level>

</Levels>

### 11. Network Programming

**Covers:** The client-server model, networks, the global IP internet (addresses, domain
names, connections), the sockets interface, web servers, and the small Tiny
web server.

<Levels label="Chapter 11, Network Programming">

<Level name="Beginner">


A server waits for connections; a client opens one. An IP address names a
host and a port names a program on it. A socket is a file descriptor for a
network connection.


</Level>
<Level name="Intermediate">


The server calls `socket`, `bind`, `listen` and `accept`; the client calls
`socket` and `connect`. `getaddrinfo` turns names into addresses for both
IPv4 and IPv6. Then both sides read and write like files.


</Level>
<Level name="Advanced">


HTTP is text over this connection: a request line, headers, a blank line, a
body. A small web server serves static files and runs programs for dynamic
content, which is what the book's Tiny server does.


</Level>
<Level name="Edge cases">


- Port numbers below 1024 need privileges on most systems.
- Addresses are in network byte order, big endian.


</Level>
<Level name="Corner cases">


- A client that connects and never sends anything ties up an iterative
  server forever, which is why chapter 12 follows.


</Level>
<Level name="Production level">


Every Node HTTP server is this loop under libuv. Timeouts, keep-alive and
limits on header size exist because of the corner case above.


</Level>
<Level name="Mindset">


The network is a file that can be slow, partial or gone at any moment.


</Level>
<Level name="System design">


Phase 7 builds on this. Proxy Lab ties it to caching and concurrency.


</Level>
<Level name="Strategy">


Write an echo server and a tiny static HTTP server in C, and talk to both
with `curl` and `nc`. Done when the server survives a client that connects
and sends nothing, which needs a timeout.

</Level>

</Levels>

### 12. Concurrent Programming

**Covers:** Concurrency with processes, with I/O multiplexing, and with threads; shared
variables; synchronising threads with semaphores; prethreading; using
threads for parallelism; and other issues: thread safety, reentrancy,
library functions, races and deadlocks.

<Levels label="Chapter 12, Concurrent Programming">

<Level name="Beginner">


A server that handles one client at a time is stuck behind slow ones.
Concurrency handles many at once: separate processes, threads, or one
thread watching many sockets with `select` or `epoll`.


</Level>
<Level name="Intermediate">


Threads share memory, so two threads updating one counter without a lock
lose updates: `cnt++` is a load, an add and a store, and the steps
interleave.

```c
static long cnt = 0;
static sem_t mutex;              /* sem_init(&mutex, 0, 1) at start */
void *worker(void *arg) {
    for (long i = 0; i < 1000000; i++) {
        sem_wait(&mutex); cnt++; sem_post(&mutex);
    }
    return NULL;
}
```


</Level>
<Level name="Advanced">


Semaphores give mutual exclusion and also schedule shared resources, as in
producer-consumer buffers. A function is thread-safe if it is correct when
called from many threads; it is reentrant if it shares no state at all.
Deadlock needs a cycle of threads each holding a lock the next one wants;
locking in a fixed global order prevents it.


</Level>
<Level name="Edge cases">


- One thread: races disappear, which is why the bug passes every test on a
  laptop.


</Level>
<Level name="Corner cases">


- A lock that protects a counter but not the check before it: "check then
  act" still races. The whole sequence must be atomic.
- A thread-unsafe library function (`strtok`, `rand`) called from two
  threads, inside code that otherwise locks correctly.


</Level>
<Level name="Production level">


Node is single-threaded for JavaScript, which is why the event loop is I/O
multiplexing, the second model in this chapter. Worker threads with
`SharedArrayBuffer` and `Atomics` bring the shared-memory problems back.


</Level>
<Level name="Mindset">


Assume every interleaving will happen eventually. Design so that each one is
correct.


</Level>
<Level name="System design">


Process-per-request, thread-per-request and the event loop are the three
server models, and every web server picks one or mixes them.


</Level>
<Level name="Strategy">


Write the counter with and without the lock, run each a hundred times, and
record how often the result is wrong. Then build Proxy Lab in phase 7. Done
when I can name the race in a piece of concurrent code and fix it.

</Level>

</Levels>

## Misreadings to avoid

- "This is a hardware book." It is about the machine as the programmer sees
  it; the hardware detail is there to explain program behaviour.
- "x86-64 is the point." The ideas (calling conventions, stacks, caches,
  virtual memory) transfer to ARM and RISC-V.
- "The compiler will optimise it." Only what it can prove safe; aliasing and
  function calls block it.
- "Caches are a hardware concern." Data layout in my code decides the hit
  rate.
- "JavaScript developers do not need this." Every V8 performance cliff,
  every memory limit and every event-loop stall is explained here.
- "Defences make overflows harmless." Canaries and ASLR raise the cost of an
  attack; they do not fix the bug.
