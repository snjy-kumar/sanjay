## Why this book

This is the depth book for <a href={withBase('/plans/traditional-software-developer/#strategy-4')}>phase 4, algorithms</a>
of the traditional core. <a href={withBase('/books/the-algorithm-design-manual/')}>The Algorithm Design Manual</a>
is the primary book: it teaches me how to recognise and model a problem.
CLRS is where I go when I need the proof: why Dijkstra is correct, why the
master method gives the bound it gives, why a red–black tree stays balanced.

It is a reference, not a cover-to-cover read. At more than thirty chapters it
covers far more than the phase needs. I read the chapters a phase 4 build
touches, and treat the rest as a map of what exists. The book writes its
algorithms in pseudocode; my examples are TypeScript, the phase's language.

## How I would learn it

I would never open CLRS first. For each phase 4 topic I solve problems with
Skiena's framing, write the code, and only then open the CLRS chapter to read
the proof. Reading a proof of an algorithm I have already implemented is a
different experience from reading it cold: every invariant maps to a line I
wrote, and every case in the proof maps to a test I should have.

For each chapter I read, I write the loop invariant or the key lemma in my
own words at the top of my implementation, as a comment, and then try to
break it with a property test. I do a handful of the exercises at the end of
each section, the ones whose answers I cannot guess, and skip the
problems at the chapter ends on the first pass.

Phase 4 is seven weeks (weeks 17 to 23). CLRS fills in behind Skiena, one
proof-level chapter per topic, and stays on the desk for the rest of the
roadmap.

## Part I — Foundations

### 1. The Role of Algorithms in Computing

**Covers:** What an algorithm is, the kinds of problems algorithms solve, and why
algorithms are a technology in their own right: a better algorithm can beat a
faster machine.

<Levels label="Chapter 1, The Role of Algorithms in Computing">

<Level name="Beginner">


An algorithm is a well-defined procedure that takes an input and produces an
output, and it is correct if it halts with the right output for every input
instance. Sorting is the standard first example.


</Level>
<Level name="Intermediate">


Efficiency is the second question after correctness. Insertion sort grows
roughly with n squared, merge sort with n log n. On a million items the gap
is so large that a slow machine running merge sort beats a fast machine
running insertion sort.


</Level>
<Level name="Advanced">


The "instance" is the unit of correctness. A procedure that is right on most
instances is a heuristic. Problems the chapter points at, such as shortest
paths, matching strings and hard problems with no known efficient solution,
return in later parts.


</Level>
<Level name="Edge cases">


- An empty input is an instance too. "Correct for every instance" includes
  it.
- An algorithm that never halts on some instance is not correct, even if
  its answers are right when it does halt.


</Level>
<Level name="Corner cases">


- Small n with a large constant: for ten items, insertion sort is often
  faster than merge sort, which is why real sorts switch to it for small
  slices.


</Level>
<Level name="Production level">


Hardware gets faster by constant factors; algorithms change the growth
rate. When a service slows down as data grows, the first question is the
growth rate of the hot path, not the instance type.


</Level>
<Level name="Mindset">


Treat algorithms as technology I choose, the same way I choose a database.


</Level>
<Level name="System design">


Every system has a few hot loops whose growth rate decides how it scales.
Finding them is the first step of capacity planning.


</Level>
<Level name="Strategy">


Read it once quickly. Then time insertion sort against `Array.prototype.sort`
from 10 to a million items and plot it. Done when I can explain the crossover
point on my own machine.

</Level>

</Levels>

### 2. Getting Started

**Covers:** Insertion sort, loop invariants as a way to prove a loop correct, the RAM
model for analysing running time, and merge sort as the first divide and
conquer algorithm.

<Levels label="Chapter 2, Getting Started">

<Level name="Beginner">


Insertion sort keeps a sorted prefix and inserts the next item into it.

```ts
function insertionSort(a: number[]): number[] {
  for (let i = 1; i < a.length; i++) {
    const key = a[i];
    let j = i - 1;
    while (j >= 0 && a[j] > key) { a[j + 1] = a[j]; j--; }
    a[j + 1] = key;
  }
  return a;
}
```


</Level>
<Level name="Intermediate">


A loop invariant is a statement true before each iteration. For insertion
sort: the prefix before `i` holds the original prefix's items, sorted. I
prove it holds at the start (initialisation), stays true (maintenance), and
gives the answer when the loop ends (termination).


</Level>
<Level name="Advanced">


The RAM model counts each simple step as constant time. Insertion sort's
worst case, reversed input, does about n squared over 2 comparisons; its
best case, sorted input, does n minus 1. Merge sort's recurrence, two halves
plus a linear merge, solves to n log n.


</Level>
<Level name="Edge cases">


- Empty array and single item: the loop body never runs, and the invariant
  still holds.
- Equal keys: using `>` rather than `>=` keeps insertion sort stable.


</Level>
<Level name="Corner cases">


- Merge sort on an odd length: the halves differ by one, and the
  off-by-one in the midpoint is the classic bug. Writing `mid = lo + ((hi -
  lo) >> 1)` avoids overflow in languages with fixed integers.


</Level>
<Level name="Production level">


Real library sorts (TimSort, introsort, pdqsort) use insertion sort for small
runs. Its best case on nearly sorted data is why it survives.


</Level>
<Level name="Mindset">


A loop invariant is a contract with myself. If I cannot state one, I do not
know what my loop does.


</Level>
<Level name="System design">


Merge sort's shape, split, solve, merge, is the shape of external sorting
and of map-reduce: sort chunks that fit in memory, then merge them.


</Level>
<Level name="Strategy">


Write insertion and merge sort with the invariant as a comment, then a
property test against `sort`. Done when I can state the three parts of the
invariant proof for both, without notes.

</Level>

</Levels>

### 3. Characterizing Running Times

**Covers:** O, Ω and Θ notation, the less common little-o and little-ω, the precise
definitions behind them, and the standard functions: polynomials,
exponentials, logarithms, factorials and iterated logarithms.

<Levels label="Chapter 3, Characterizing Running Times">

<Level name="Beginner">


Big-O is an upper bound on growth, Ω a lower bound, and Θ both. "Merge sort
is Θ(n log n)" says its running time grows exactly like n log n, ignoring
constants.


</Level>
<Level name="Intermediate">


The definitions have constants: f is O(g) if there are c and n0 such that f
is at most c times g for every n at least n0. So 3n² + 100n is O(n²) with
c = 4 and a large enough n0.


</Level>
<Level name="Advanced">


Little-o is strict: n is o(n²) but n² is not o(n²). Logarithms of different
bases differ by a constant, so the base disappears inside O. Factorials grow
faster than exponentials, and the iterated logarithm grows so slowly it is at
most 5 for any input a computer will see.


</Level>
<Level name="Edge cases">


- O is an upper bound, so "insertion sort is O(n³)" is true and useless.
- A worst-case bound says nothing about the best case.


</Level>
<Level name="Corner cases">


- Two functions can be incomparable: n and n raised to (1 + sin n) is
  neither O nor Ω of the other. Asymptotic order is not total.


</Level>
<Level name="Production level">


When someone says "this is O(n)", I ask: worst case, expected or amortised,
and with what constant? An O(n) scan over a contiguous array often beats an
O(log n) tree walk over scattered pointers for the sizes production sees.


</Level>
<Level name="Mindset">


Notation is a way to throw away detail on purpose. I should know which
detail I threw away.


</Level>
<Level name="System design">


Latency budgets are constants, and asymptotics hide constants. Both matter;
asymptotics decide what happens at ten times the load.


</Level>
<Level name="Strategy">


Sort twenty functions by growth on paper, then check by evaluating them at
large n in a script. Done when I can prove one O and one Ω claim from the
definitions with explicit constants.

</Level>

</Levels>

### 4. Divide-and-Conquer

**Covers:** Matrix multiplication by divide and conquer, Strassen's algorithm, and the
three ways to solve recurrences: substitution, the recursion tree and the
master method, with a proof of the master theorem for continuous
recurrences and the Akra–Bazzi method for uneven splits.

<Levels label="Chapter 4, Divide-and-Conquer">

<Level name="Beginner">


Divide and conquer splits a problem into smaller copies, solves them
recursively, and combines the answers. The running time is a recurrence:
`T(n) = a·T(n/b) + f(n)`.


</Level>
<Level name="Intermediate">


The master method compares f(n) with n raised to log base b of a. Merge sort
has a = 2, b = 2, f(n) = n: they match, so T is n log n. Binary search has a
= 1, b = 2, f constant: T is log n.


</Level>
<Level name="Advanced">


Strassen multiplies two n-by-n matrices with seven recursive products
instead of eight, giving roughly n to the 2.81 instead of n cubed. The
recursion tree shows where the work is: at the leaves, at the root, or
evenly across levels, which are the master method's three cases.


</Level>
<Level name="Edge cases">


- The master method does not cover every recurrence. `T(n) = 2T(n/2) + n
  log n` falls between cases in the basic form and needs the extended case
  or a recursion tree.


</Level>
<Level name="Corner cases">


- Floors and ceilings: real recurrences split into ⌊n/2⌋ and ⌈n/2⌉. The
  chapter shows they do not change the asymptotic answer, but my code's base
  case must handle both sizes.
- Strassen's constant and its numerical stability make it slower than the
  plain loop below a crossover size.


</Level>
<Level name="Production level">


BLAS libraries use blocked, cache-aware loops far more than Strassen. The
asymptotic winner is not always the deployed one.


</Level>
<Level name="Mindset">


When I see recursion, I write the recurrence before I write the code.


</Level>
<Level name="System design">


Divide and conquer is how parallel work is shaped: fork the halves, join the
results. The recurrence's critical path is the parallel running time.


</Level>
<Level name="Strategy">


Solve ten recurrences with the master method and check three with a recursion
tree drawn by hand. Done when I can say which case applies on sight and why
`T(n) = T(n/3) + T(2n/3) + n` is still n log n.

</Level>

</Levels>

### 5. Probabilistic Analysis and Randomized Algorithms

**Covers:** The hiring problem, indicator random variables, randomized algorithms, and
further probabilistic analysis built on indicator variables.

<Levels label="Chapter 5, Probabilistic Analysis and Randomized Algorithms">

<Level name="Beginner">


Probabilistic analysis averages cost over a distribution of inputs. A
randomized algorithm puts the randomness inside the algorithm, so the
expected cost holds for every input.


</Level>
<Level name="Intermediate">


An indicator random variable is 1 if an event happens and 0 if not. Its
expected value is the event's probability, and expectations add even when the
events are dependent. That one trick solves most expected-cost questions.

```ts
// Fisher–Yates: every permutation equally likely
function shuffle<T>(a: T[]): T[] {
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
}
```


</Level>
<Level name="Advanced">


In the hiring problem, the expected number of hires over a random order is
the harmonic number, about ln n. The birthday paradox says about the square
root of n items are enough for a likely collision among n slots, which is
why hash collisions arrive sooner than intuition says.


</Level>
<Level name="Edge cases">


- `Math.floor(Math.random() * i)` instead of `i + 1` gives Sattolo's
  algorithm: only cyclic permutations, not a uniform shuffle.
- `Math.random()` is not cryptographic. Shuffling for a lottery needs
  `crypto.getRandomValues`.


</Level>
<Level name="Corner cases">


- Sorting by a random comparator (`sort(() => Math.random() - 0.5)`) is not
  uniform and depends on the engine's sort.


</Level>
<Level name="Production level">


Randomising input order defends against adversarial worst cases: quicksort
on attacker-chosen data, hash flooding. Seeded randomness makes failures
reproducible.


</Level>
<Level name="Mindset">


When the worst case comes from the input, move the randomness into the
algorithm, where the adversary cannot see it.


</Level>
<Level name="System design">


Random jitter in retries, random load balancing (power of two choices) and
consistent hashing all rest on the expectation arguments here.


</Level>
<Level name="Strategy">


Write the correct shuffle and two broken ones, then a chi-squared test over a
million shuffles of three items. Done when the test passes for the correct
one and fails for both broken ones.

</Level>

</Levels>

## Part II — Sorting and Order Statistics

### 6. Heapsort

**Covers:** Binary heaps, maintaining the heap property, building a heap in linear time,
heapsort, and priority queues.

<Levels label="Chapter 6, Heapsort">

<Level name="Beginner">


A max-heap is an array viewed as a complete binary tree where every parent is
at least as large as its children. The children of index `i` are `2i + 1`
and `2i + 2` with zero-based indexing.


</Level>
<Level name="Intermediate">


Sift-down restores the property at one node in O(log n). Building a heap
calls it from the last parent to the root. Heapsort builds a heap, then
repeatedly swaps the root to the end and sifts down.

```ts
function siftDown(a: number[], i: number, n: number) {
  for (;;) {
    const l = 2 * i + 1, r = l + 1;
    let m = i;
    if (l < n && a[l] > a[m]) m = l;
    if (r < n && a[r] > a[m]) m = r;
    if (m === i) return;
    [a[i], a[m]] = [a[m], a[i]];
    i = m;
  }
}
```


</Level>
<Level name="Advanced">


Building a heap is linear, not n log n: most nodes are near the bottom and
sift down only a short way, and the sum of heights over all nodes is O(n).
A priority queue adds insert (sift up) and increase-key on top.


</Level>
<Level name="Edge cases">


- One-based indexing in the book's pseudocode versus zero-based in
  TypeScript: the child formulas change.
- A heap of size 0 or 1 is already valid.


</Level>
<Level name="Corner cases">


- Increase-key needs to know where an item lives in the array. Without an
  index map from item to position, it is O(n) to find it.


</Level>
<Level name="Production level">


Heapsort is in-place with an n log n worst case, which is why introsort falls
back to it, but its jumps across the array make it cache-unfriendly. Timers,
schedulers and Dijkstra use heaps as priority queues more than as sorts.


</Level>
<Level name="Mindset">


The surprising linear bound teaches me to sum the real costs rather than
multiply the worst case by n.


</Level>
<Level name="System design">


Top-k queries, job schedulers and event simulators are priority queues. In
Node, a timer wheel or heap sits under `setTimeout`.


</Level>
<Level name="Strategy">


Write a heap with an index map and decrease-key, then use it in Dijkstra.
Done when a property test against a sorted array passes for a million random
operations.

</Level>

</Levels>

### 7. Quicksort

**Covers:** The partition procedure, quicksort's performance in the best, worst and
balanced cases, a randomized version, and its analysis.

<Levels label="Chapter 7, Quicksort">

<Level name="Beginner">


Quicksort picks a pivot, partitions the array into items smaller and larger
than it, and sorts both sides recursively, in place.


</Level>
<Level name="Intermediate">


The book uses Lomuto partition: one index sweeps the array and swaps smaller
items to the front. Picking a random pivot makes the expected time n log n on
every input.


</Level>
<Level name="Advanced">


The analysis counts comparisons with indicator variables: items i and j are
compared only if one of them is the first pivot chosen from the range between
them, with probability 2 over (j − i + 1). Summing gives about 2n ln n.


</Level>
<Level name="Edge cases">


- Already sorted input with a last-element pivot: worst case, n squared.
- Many equal keys: two-way partition degenerates. Three-way partition
  (Dutch national flag) fixes it.


</Level>
<Level name="Corner cases">


- Sorted input of equal keys: both problems at once. Recursion depth
  becomes n, and an unbounded recursion overflows the stack. Recursing on
  the smaller side and looping on the larger bounds the depth at log n.


</Level>
<Level name="Production level">


V8 uses TimSort for `Array.prototype.sort`; C++ standard libraries use
introsort, quicksort that switches to heapsort when the recursion is too deep.
Adversarial inputs exist for deterministic pivot rules.


</Level>
<Level name="Mindset">


An expected bound is only as good as the randomness behind it. Who controls
the input?


</Level>
<Level name="System design">


Partition is the core of quickselect, of database partitioning around a
split key, and of building balanced k-d trees.


</Level>
<Level name="Strategy">


Write Lomuto, Hoare and three-way partition, and benchmark all three on
random, sorted and all-equal input. Done when no input in the benchmark makes
my final version quadratic or overflow the stack.

</Level>

</Levels>

### 8. Sorting in Linear Time

**Covers:** The comparison-sort lower bound by decision trees, counting sort, radix sort
and bucket sort.

<Levels label="Chapter 8, Sorting in Linear Time">

<Level name="Beginner">


Any sort that only compares items needs about n log n comparisons in the
worst case. Sorts that look at the keys themselves, such as counting sort,
can be faster.


</Level>
<Level name="Intermediate">


Counting sort counts occurrences of each key in a range 0 to k, takes prefix
sums, and places items, in O(n + k). It is stable, which is what radix sort
needs: sort by the least significant digit first, then the next, and so on.

```ts
function countingSort(a: number[], k: number): number[] {
  const count = new Array(k + 1).fill(0);
  for (const x of a) count[x]++;
  for (let i = 1; i <= k; i++) count[i] += count[i - 1];
  const out = new Array(a.length);
  for (let i = a.length - 1; i >= 0; i--) out[--count[a[i]]] = a[i];
  return out;
}
```


</Level>
<Level name="Advanced">


A decision tree for n items has n factorial leaves, one per order, so its
height is at least log of n factorial, which is about n log n. Bucket sort
is linear in expectation only when the input is spread uniformly.


</Level>
<Level name="Edge cases">


- Counting sort with a huge k (32-bit keys) needs a huge count array; radix
  sort with a byte per pass fixes that.
- Negative numbers need an offset or a sign-aware pass.


</Level>
<Level name="Corner cases">


- Radix sort on floats: their bit patterns sort correctly only after
  flipping the sign bit for positives and all bits for negatives.


</Level>
<Level name="Production level">


Radix sort is used for large arrays of fixed-size integer keys, on GPUs and
in database engines. For general objects with a comparator, comparison sorts
remain the default.


</Level>
<Level name="Mindset">


A lower bound is about a model. Leave the model, and the bound no longer
applies.


</Level>
<Level name="System design">


Bucketing by key range is how data is sharded and how histograms are built.
Skewed keys break bucket sort and sharding in the same way.


</Level>
<Level name="Strategy">


Implement counting, LSD radix and bucket sort, and add them to the phase 4
benchmark with uniform and skewed inputs. Done when I can explain each line of
the decision-tree argument and the benchmark shows bucket sort degrading on
skew.

</Level>

</Levels>

### 9. Medians and Order Statistics

**Covers:** Minimum and maximum, selection in expected linear time, and selection in
worst-case linear time.

<Levels label="Chapter 9, Medians and Order Statistics">

<Level name="Beginner">


The i-th order statistic is the i-th smallest item. The median is the
middle one. Sorting finds it in n log n; selection finds it in linear time.


</Level>
<Level name="Intermediate">


Randomized select partitions like quicksort but recurses only into the side
that holds the answer, which gives expected linear time. Finding min and max
together needs only about 3n/2 comparisons, by comparing items in pairs.

```ts
function select(a: number[], k: number): number {
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    const p = a[lo + Math.floor(Math.random() * (hi - lo + 1))];
    let i = lo, j = hi;
    while (i <= j) {
      while (a[i] < p) i++;
      while (a[j] > p) j--;
      if (i <= j) { [a[i], a[j]] = [a[j], a[i]]; i++; j--; }
    }
    if (k <= j) hi = j; else if (k >= i) lo = i; else return a[k];
  }
  return a[lo];
}
```


</Level>
<Level name="Advanced">


The worst-case linear algorithm picks its pivot as the median of medians of
groups of five, which guarantees a constant fraction is discarded each round.
The constant is large, so it is mostly a theoretical result.


</Level>
<Level name="Edge cases">


- k out of range, an empty array, and k on the boundaries (min and max).
- Even length: "the median" is two values; decide which, or average them.


</Level>
<Level name="Corner cases">


- All-equal input with a two-way partition makes randomized select
  quadratic, the same trap as quicksort.


</Level>
<Level name="Production level">


C++'s `nth_element` is introselect. Percentiles over a stream use sketches
(t-digest) because exact selection needs the data in memory.


</Level>
<Level name="Mindset">


Do not sort when I only need one position.


</Level>
<Level name="System design">


p50, p95 and p99 latency are order statistics. At scale they come from
approximate sketches merged across machines.


</Level>
<Level name="Strategy">


Write randomized select and check it against sorting on random arrays,
including all-equal ones. Done when I can explain why groups of five work and
groups of three do not.

</Level>

</Levels>

## Part III — Data Structures

### 10. Elementary Data Structures

**Covers:** Simple array-based structures (arrays, matrices, stacks and queues), linked
lists, and representing rooted trees.

<Levels label="Chapter 10, Elementary Data Structures">

<Level name="Beginner">


A stack is last in, first out; a queue is first in, first out. Both fit in an
array. A linked list stores each item in a node with a pointer to the next.


</Level>
<Level name="Intermediate">


A queue in an array is a ring: head and tail indices wrap around with modulo.
A doubly linked list with a sentinel node removes every special case for the
empty list and the ends.

```ts
class Ring<T> {
  private buf: (T | undefined)[]; private head = 0; private size = 0;
  constructor(cap: number) { this.buf = new Array(cap); }
  push(x: T) {
    if (this.size === this.buf.length) throw new Error('full');
    this.buf[(this.head + this.size++) % this.buf.length] = x;
  }
  shift(): T | undefined {
    if (this.size === 0) return undefined;
    const x = this.buf[this.head]; this.buf[this.head] = undefined;
    this.head = (this.head + 1) % this.buf.length; this.size--;
    return x;
  }
}
```


</Level>
<Level name="Advanced">


Matrices are stored row-major or column-major, and the choice decides which
loop order walks memory in sequence. Trees with any number of children can
be stored as left-child, right-sibling, so each node needs only two pointers.


</Level>
<Level name="Edge cases">


- Ring buffer full versus empty: head equals tail in both, so I track a
  size, or leave one slot unused.
- Popping an empty stack: underflow, which must be an error or an
  `undefined`, never a silent garbage read.


</Level>
<Level name="Corner cases">


- Removing the only node of a doubly linked list without a sentinel: head
  and tail both have to change. The sentinel makes it one code path.


</Level>
<Level name="Production level">


Ring buffers sit under logging, audio, network queues and Node streams.
Linked lists lose to arrays on modern hardware for most workloads, because
following pointers misses the cache.


</Level>
<Level name="Mindset">


Sentinels and invariants remove special cases. Fewer branches, fewer bugs.


</Level>
<Level name="System design">


Bounded queues are backpressure. An unbounded queue between two services is a
memory leak waiting for a slow consumer.


</Level>
<Level name="Strategy">

### 11. Hash Tables

**Covers:** Direct-address tables, hash tables with chaining, hash functions (static and
random), open addressing, and practical considerations such as memory
hierarchies and designing fast hash functions.

<Levels label="Chapter 11, Hash Tables">

<Level name="Beginner">


A hash table maps a key to a slot with a hash function, so lookups take
expected constant time. Collisions, two keys in one slot, are handled by
chaining (a list per slot) or open addressing (probe for another slot).


</Level>
<Level name="Intermediate">


The load factor, items over slots, controls the cost. Chaining degrades
gracefully as it grows; open addressing needs it kept well below 1 and
resizes before then.


</Level>
<Level name="Advanced">


A fixed hash function has inputs that all collide. Choosing the function at
random from a universal family bounds the expected collisions for any input.
Linear probing is fast in practice because the probes are adjacent in
memory, despite clustering.


</Level>
<Level name="Edge cases">


- Deleting from open addressing: emptying the slot breaks later probe
  chains. Use a tombstone, or backward-shift deletion with linear probing.
- A table of size 0 or a load factor that never triggers a resize.


</Level>
<Level name="Corner cases">


- Many tombstones and a resize at the same time: the table is "full" of
  deleted slots, lookups probe forever, and the fix is to rehash into a
  fresh table, not to grow.


</Level>
<Level name="Production level">


Hash flooding, an attacker sending keys that collide, turns constant-time
maps into linear ones. Keyed hashes (SipHash) and randomised seeds defend
against it. JavaScript engines randomise string hash seeds for the same
reason.


</Level>
<Level name="Mindset">


"Constant time" always has an asterisk: expected, under assumptions about the
keys. Know the assumption.


</Level>
<Level name="System design">


Consistent hashing, sharding by hash, caches and Bloom filters all start
here. Hashing decides where data lives in a cluster as well as in an array.


</Level>
<Level name="Strategy">


Write chaining and linear-probing tables with resizing, and measure probe
counts as the load factor rises. Done when a property test with random
inserts and deletes never disagrees with `Map`.

</Level>

### 12. Binary Search Trees

**Covers:** What a BST is, querying it (search, minimum, maximum, successor), and
insertion and deletion.

<Levels label="Chapter 12, Binary Search Trees">

<Level name="Beginner">


In a binary search tree, every key in a node's left subtree is smaller and
every key in its right subtree is larger. An in-order walk visits the keys in
sorted order.


</Level>
<Level name="Intermediate">


Search, insert, min, max and successor all walk one path from the root, so
they cost the height of the tree.


</Level>
<Level name="Advanced">


Deletion has three cases: no children, one child, or two, where the node is
replaced by its successor. The book's transplant helper moves a subtree into
another's place and keeps the parent pointers right.


</Level>
<Level name="Edge cases">


- Deleting the root, and deleting from an empty tree.
- Duplicate keys: decide whether they go left, right, or into a count.


</Level>
<Level name="Corner cases">


- Deleting a node with two children whose successor is its own right child:
  the successor has no left subtree to splice, a separate case in the code.


</Level>
<Level name="Production level">


Inserting sorted keys into a plain BST builds a linked list of height n. Real
ordered maps use balanced trees, or B-trees on disk.


</Level>
<Level name="Mindset">


A structure's cost is its shape. Ask what input makes the worst shape.


</Level>
<Level name="System design">


Ordered indexes support range queries ("all orders between two dates")

### 13. Red-Black Trees

**Covers:** The properties of red–black trees, rotations, insertion and deletion.

<Levels label="Chapter 13, Red-Black Trees">

<Level name="Beginner">


A red–black tree colours each node red or black, with rules that keep the
longest path no more than twice the shortest. So the height stays O(log n).


</Level>
<Level name="Intermediate">


The rules: the root and the leaves (nil) are black, a red node has black
children, and every path from a node down to a leaf has the same number of
black nodes. Insert adds a red node, then fixes any red–red violation with
recolouring and at most two rotations.

<Figure caption="A left rotation at x. The in-order sequence a, x, b, y, c stays the same." art={`
     x                 y
    / \\               / \\
   a   y     ==>     x   c
      / \\           / \\
     b   c         a   b
`} />


</Level>
<Level name="Advanced">


Deletion is the hard part: removing a black node breaks the black-height
rule, and the fix-up walks up the tree through four cases. Rotations keep
the in-order order and change only local pointers, so each is O(1).


</Level>
<Level name="Edge cases">


- Inserting into an empty tree: the new node becomes a black root.
- A shared nil sentinel: its parent pointer is written during deletion, so
  it is not safe to share across threads.


</Level>
<Level name="Corner cases">


- Deleting the last node, or a node whose replacement is the nil sentinel,
  while the fix-up runs at the root.


</Level>
<Level name="Production level">


Red–black trees sit under C++ `std::map`, Java's `TreeMap` and the Linux
kernel's scheduler and memory maps. They are chosen for bounded update cost,
not fastest lookups.


</Level>
<Level name="Mindset">


Invariants are what make "balanced" checkable. A validator that checks the
rules after every operation finds bugs faster than reading the code.


</Level>
<Level name="System design">


Balanced trees in memory, B-trees on disk, and LSM trees for write-heavy
loads: the same ordered-map contract with different costs.


</Level>
<Level name="Strategy">

run after each operation in a random test. Done when ten thousand random

## Part IV — Advanced Design and Analysis Techniques

### 14. Dynamic Programming

**Covers:** Rod cutting, matrix-chain multiplication, the elements of dynamic programming
(optimal substructure and overlapping subproblems), longest common
subsequence, and optimal binary search trees.

<Levels label="Chapter 14, Dynamic Programming">

<Level name="Beginner">


Dynamic programming solves a problem by solving smaller versions once each
and storing the answers. It applies when the answer is built from optimal
answers to subproblems, and the same subproblems come up again and again.


</Level>
<Level name="Intermediate">


The steps: define the subproblem in a sentence, write the recurrence, choose
an order that computes smaller subproblems first, then rebuild the solution
from stored choices. LCS is the standard example.

```ts
function lcs(a: string, b: string): string {
  const n = a.length, m = b.length;
  const L = Array.from({ length: n + 1 }, () => new Array(m + 1).fill(0));
  for (let i = 1; i <= n; i++)
    for (let j = 1; j <= m; j++)
      L[i][j] = a[i - 1] === b[j - 1] ? L[i - 1][j - 1] + 1
                                      : Math.max(L[i - 1][j], L[i][j - 1]);
  let i = n, j = m, out = '';
  while (i && j) {
    if (a[i - 1] === b[j - 1]) { out = a[i - 1] + out; i--; j--; }
    else if (L[i - 1][j] >= L[i][j - 1]) i--; else j--;
  }
  return out;
}
```


</Level>
<Level name="Advanced">


Optimal substructure must be proved, usually by cut and paste: if the
optimal solution used a worse subsolution, swapping in the better one would
improve it. Top-down memoisation and bottom-up tables compute the same thing;
bottom-up avoids recursion depth and often allows keeping only two rows.


</Level>
<Level name="Edge cases">


- Empty strings, a rod of length 0, and a chain of one matrix: the base
  cases, which the table's first row and column must encode.
- Ties when rebuilding the answer: LCS is not unique; pick a rule and test
  for it.


</Level>
<Level name="Corner cases">


- Longest simple path does not have optimal substructure: subpaths of a
  longest path can share vertices. DP that looks right silently gives wrong
  answers there.
- Two-row space optimisation loses the table needed to rebuild the
  solution; Hirschberg's divide-and-conquer trick recovers it.


</Level>
<Level name="Production level">


`diff`, spell checkers (edit distance), sequence alignment in biology, and
query planners choosing join orders all run DP. Memory, n times m cells,
is what breaks first on large inputs.


</Level>
<Level name="Mindset">


Define the state first. If I cannot say in one sentence what a cell of the
table means, I am not ready to write the recurrence.


</Level>
<Level name="System design">


Caching is DP across requests: the same subproblem answered once and
reused. The questions are the same: what is the key, and when is it stale?


</Level>
<Level name="Strategy">


Do rod cutting, LCS, edit distance, 0/1 knapsack and matrix chain, each
written state-first, each checked against brute force on small inputs. Done
when my phase 4 LCS diff tool works on real files.

</Level>

### 15. Greedy Algorithms

**Covers:** An activity-selection problem, the elements of the greedy strategy (the
greedy-choice property and optimal substructure), Huffman codes, and offline
caching.

<Levels label="Chapter 15, Greedy Algorithms">

<Level name="Beginner">


A greedy algorithm makes the locally best choice at each step and never
reconsiders. It is right only when that local choice can be proved to lead
to a global optimum.


</Level>
<Level name="Intermediate">


Activity selection: sort by finish time and take each activity that starts
after the last one taken. Huffman coding repeatedly merges the two least
frequent symbols, using a priority queue.


</Level>
<Level name="Advanced">


The proof is an exchange argument: take any optimal solution, swap its first
choice for the greedy one, and show it is no worse. Offline caching, evicting
the item needed furthest in the future, is optimal, but needs to know the
future.


</Level>
<Level name="Edge cases">


- Coin change with denominations 1, 3 and 4: greedy gives 4 + 1 + 1 for 6,
  but 3 + 3 is better. Greedy is correct for some coin systems only.
- Huffman with a single symbol: the code needs at least one bit.


</Level>
<Level name="Corner cases">


- Activities that end exactly when another starts, plus ties in finish
  time: the comparison and the sort's stability both affect the answer.


</Level>
<Level name="Production level">


Greedy algorithms are fast and simple, so they are everywhere: schedulers,
compression (Huffman in DEFLATE), routing heuristics. Where they are not
optimal, they need a stated approximation bound or a test with the known bad
case.


</Level>
<Level name="Mindset">


Greedy is a claim that needs a proof. Without one, it is a heuristic.


</Level>
<Level name="System design">


Furthest-in-future eviction is the ideal that LRU and its variants try to
approximate. It is the yardstick for any cache policy.


</Level>
<Level name="Strategy">


Implement activity selection, Huffman and a coin-change greedy, and find the
counterexample for the non-canonical coins by brute force. Done when I can
write the exchange argument for activity selection from memory.

</Level>

### 16. Amortized Analysis

**Covers:** Aggregate analysis, the accounting method, the potential method, and dynamic
tables.

<Levels label="Chapter 16, Amortized Analysis">

<Level name="Beginner">


Amortised analysis bounds the total cost of a sequence of operations, so an
occasional expensive one is paid for by many cheap ones. A dynamic array's
push is amortised O(1) even though some pushes copy everything.


</Level>
<Level name="Intermediate">


Aggregate: add up the total and divide. Accounting: overcharge cheap
operations and store the credit for later. Potential: define a function of
the structure's state and charge each operation its real cost plus the
change in potential.


</Level>
<Level name="Advanced">


For a table that doubles when full and halves when a quarter full, the
potential is built from the gap between twice the size and the capacity.
Halving at a half instead of a quarter allows a sequence that alternates
grow and shrink at the boundary, costing linear time per operation.


</Level>
<Level name="Edge cases">


- The first push into an empty table of capacity 0: grow to 1, not to 0
  times 2.


</Level>
<Level name="Corner cases">


- Push and pop alternating exactly at the resize threshold: the thrashing
  case the quarter rule exists to prevent.


</Level>
<Level name="Production level">


Amortised is not worst case. A latency-sensitive path (an audio callback, a
request with a tight deadline) can still hit the expensive step; incremental
resizing spreads it out.


</Level>
<Level name="Mindset">


Look at sequences, not single operations. Many costs only make sense over
time.


</Level>
<Level name="System design">


Garbage collection pauses, log compaction and hash-table rehashing are
amortised costs. Systems either accept the spike or do the work
incrementally.


</Level>
<Level name="Strategy">


Write a dynamic array with grow and shrink, count element copies over a
million random operations, and prove the bound with a potential function.
Done when the measured copies per operation stay below my proven constant.

</Level>

### 18. B-Trees

**Covers:** The definition of B-trees, basic operations (search and insert), and deleting
a key.

<Levels label="Chapter 18, B-Trees">

<Level name="Beginner">


A B-tree is a balanced search tree whose nodes hold many keys and have many
children. One node fits one disk page, so a lookup reads only a few pages.


</Level>
<Level name="Intermediate">


With minimum degree t, every node except the root has between t − 1 and
2t − 1 keys. Insert splits a full node on the way down, so the insert never
has to back up. The tree grows at the root.


</Level>
<Level name="Advanced">


The height is about log base t of n. With t in the hundreds, a billion keys
fit in a tree of height three or four. Deletion keeps nodes from getting too
small by borrowing from a sibling or merging with one, again on the way down.


</Level>
<Level name="Edge cases">


- Splitting the root: the only way the tree gets taller.
- Deleting from a node at the minimum key count.


</Level>
<Level name="Corner cases">


- Deleting a key from an internal node whose children are both at minimum:
  merge them first, then delete, and the root can shrink away.


</Level>
<Level name="Production level">


Almost every relational database index is a B+ tree, the variant that keeps
all keys in the leaves and links the leaves for range scans. Page size,
fill factor and write amplification are the production questions.


</Level>
<Level name="Mindset">


Design for the slow medium. When a disk read costs a million times a
comparison, count reads, not comparisons.


</Level>
<Level name="System design">


This is phase 8's foundation: indexes, range queries, and why random UUID
primary keys spread inserts across pages.


</Level>

### 19. Data Structures for Disjoint Sets

**Covers:** Disjoint-set operations, a linked-list representation, disjoint-set forests,
and the analysis of union by rank with path compression.

<Levels label="Chapter 19, Data Structures for Disjoint Sets">

<Level name="Beginner">


A disjoint-set structure (union–find) keeps items in groups and answers two
questions: which group is this item in, and merge these two groups.


</Level>
<Level name="Intermediate">


Each group is a tree with a root as its name. Find follows parents to the
root; union links one root under the other.

```ts
const parent: number[] = [], rank: number[] = [];
function find(x: number): number {
  while (parent[x] !== x) { parent[x] = parent[parent[x]]; x = parent[x]; }
  return x;
}
function union(a: number, b: number) {
  let ra = find(a), rb = find(b);
  if (ra === rb) return;
  if (rank[ra] < rank[rb]) [ra, rb] = [rb, ra];
  parent[rb] = ra;
  if (rank[ra] === rank[rb]) rank[ra]++;
}
```


</Level>
<Level name="Advanced">


Union by rank keeps trees shallow; path compression flattens them. Together
the cost per operation is the inverse Ackermann function, which is at most 4
for any practical n. The proof is one of the hardest in the book.


</Level>
<Level name="Edge cases">


- Union of an item with itself, or with an item already in its set: must be
  a no-op.


</Level>
<Level name="Corner cases">


- Recursive path compression on a long chain before any compression has
  happened can overflow the stack; the iterative halving above avoids it.


</Level>
<Level name="Production level">


Kruskal's MST, connected components in image processing, type inference
(unification) and network connectivity checks all use union–find.


</Level>
<Level name="Mindset">


Lazy work, done only when asked and remembered afterwards, can be almost
free.


</Level>
<Level name="System design">


Grouping events into sessions, merging duplicate user accounts, and
clustering alerts are union–find problems at the application level.


</Level>
<Level name="Strategy">

Done when Kruskal on my phase 4 graph uses it, and I can say what α(n)

### 20. Elementary Graph Algorithms

**Covers:** Representations of graphs, breadth-first search, depth-first search,
topological sort, and strongly connected components.

<Levels label="Chapter 20, Elementary Graph Algorithms">

<Level name="Beginner">


A graph is vertices and edges. An adjacency list stores each vertex's
neighbours and suits sparse graphs; an adjacency matrix suits dense ones.
BFS explores in rings of distance; DFS goes deep first and backtracks.


</Level>
<Level name="Intermediate">


BFS with a queue gives shortest paths by edge count. DFS records discovery
and finish times; sorting vertices by decreasing finish time gives a
topological order of a DAG.

```ts
function topoSort(n: number, adj: number[][]): number[] {
  const state = new Uint8Array(n), out: number[] = [];
  const visit = (u: number) => {
    if (state[u] === 1) throw new Error('cycle');
    if (state[u] === 2) return;
    state[u] = 1;
    for (const v of adj[u]) visit(v);
    state[u] = 2; out.push(u);
  };
  for (let u = 0; u < n; u++) visit(u);
  return out.reverse();
}
```


</Level>
<Level name="Advanced">


DFS classifies edges as tree, back, forward and cross. A back edge means a
cycle. Strongly connected components come from two DFS passes: one on the
graph to get finish times, one on the reversed graph in decreasing finish
order.


</Level>
<Level name="Edge cases">


- Disconnected graphs: BFS or DFS from one source misses vertices, so loop
  over all vertices.
- Self-loops and parallel edges in the input.


</Level>
<Level name="Corner cases">


- Recursive DFS on a long path (a linked-list-shaped graph of 100,000
  vertices) overflows the JavaScript stack. An explicit stack is needed, and
  getting finish times right with it takes care.


</Level>
<Level name="Production level">


Build systems, package managers and spreadsheet recalculation are topological
sorts. Cycle detection with a clear error naming the cycle is the
user-facing feature.


</Level>
<Level name="Mindset">


Most problems with "depends on", "reachable" or "connected" in them are graph
problems. Draw the graph first.


</Level>
<Level name="System design">


Dependency graphs of services, task DAGs in workflow engines (Airflow,

</Level>
<Level name="Strategy">

### 21. Minimum Spanning Trees

**Covers:** Growing a minimum spanning tree with the cut property, and the algorithms of

<Levels label="Chapter 21, Minimum Spanning Trees">

<Level name="Beginner">


A minimum spanning tree connects every vertex of a weighted, undirected graph
with the least total edge weight and no cycles.


</Level>
<Level name="Intermediate">


Kruskal sorts edges by weight and adds each one that joins two different

always adding the cheapest edge leaving it, using a priority queue.


</Level>

</Level>
<Level name="Edge cases">

</Level>
<Level name="Corner cases">

</Level>
<Level name="Production level">


Network design, clustering (cut the heaviest MST edges to get k clusters) and
approximation algorithms for TSP use MSTs.


</Level>
<Level name="Mindset">


A local rule (the cheapest safe edge) plus a structural lemma (the cut
property) gives a global optimum. That is what a correct greedy looks like.


</Level>
<Level name="System design">


Laying cable or fibre between sites, and building a cheap backbone between

### 22. Single-Source Shortest Paths

**Covers:** The Bellman–Ford algorithm, shortest paths in DAGs, Dijkstra's algorithm,
difference constraints, and proofs of the shortest-path properties.

<Levels label="Chapter 22, Single-Source Shortest Paths">

<Level name="Beginner">


Find the cheapest path from one source to every vertex. Relaxation is the
basic step: if going through u makes the path to v cheaper, update v.


</Level>
<Level name="Intermediate">


Dijkstra uses a priority queue and settles the closest unsettled vertex each
step; it needs non-negative weights. Bellman–Ford relaxes every edge V − 1
times and handles negative weights. A DAG needs one pass in topological
order.

```ts
function dijkstra(adj: [number, number][][], s: number): number[] {
  const dist = new Array(adj.length).fill(Infinity); dist[s] = 0;
  const pq: [number, number][] = [[0, s]];       // use a real heap in practice
  while (pq.length) {
    pq.sort((a, b) => a[0] - b[0]);
    const [d, u] = pq.shift()!;
    if (d > dist[u]) continue;                   // stale entry
    for (const [v, w] of adj[u])
      if (d + w < dist[v]) { dist[v] = d + w; pq.push([dist[v], v]); }
  }
  return dist;
}
```


</Level>
<Level name="Advanced">


Dijkstra's proof: when a vertex is taken from the queue, its distance is
final, because any other path would have to leave the settled set through an
edge that cannot make it cheaper if weights are non-negative. Bellman–Ford
detects a negative cycle with one extra pass: if anything still relaxes, a
cycle exists.


</Level>
<Level name="Edge cases">


- Unreachable vertices keep distance Infinity; print them clearly.
- Zero-weight edges are fine for Dijkstra.


</Level>
<Level name="Corner cases">


- One negative edge and no negative cycle: the textbook Dijkstra, which
  never revisits a settled vertex, gives a wrong answer. Three vertices show
  it: s to a costs 2, s to b costs 3, b to a costs −2. The lazy version above
  happens to recover here, by re-queueing a, but can then take exponential
  time on other graphs.
- A negative cycle reachable from the source makes "shortest" undefined for
  every vertex reachable from the cycle.


</Level>
<Level name="Production level">


Routing (maps, network protocols like OSPF), game pathfinding with A*, and
currency arbitrage detection (a negative cycle in log prices) are this
chapter.


</Level>
<Level name="Mindset">


Know the algorithm's precondition. Dijkstra is fast because it assumes
something; violating it gives confident wrong answers.


</Level>
<Level name="System design">


Difference constraints, solved as shortest paths, schedule tasks with
"at least" and "at most" gaps, which is how some build and layout engines
place things.


</Level>
<Level name="Strategy">


Write Dijkstra with my heap, Bellman–Ford and DAG shortest paths, and run
all three on random non-negative graphs. Done when they agree, and my
three-vertex counterexample breaks Dijkstra exactly as predicted.

</Level>

### 23. All-Pairs Shortest Paths

**Covers:** Shortest paths and matrix multiplication, the Floyd–Warshall algorithm, and

<Levels label="Chapter 23, All-Pairs Shortest Paths">

<Level name="Beginner">


All-pairs finds the shortest path between every pair of vertices, as a V by
V table.


</Level>
<Level name="Intermediate">


Floyd–Warshall tries each vertex k as an intermediate stop: the best path
from i to j either avoids k or goes through it.

```ts
for (let k = 0; k < n; k++)
  for (let i = 0; i < n; i++)
    for (let j = 0; j < n; j++)
      if (d[i][k] + d[k][j] < d[i][j]) d[i][j] = d[i][k] + d[k][j];
```


</Level>
<Level name="Advanced">


It is V cubed time and V squared space, with a tiny constant. Johnson's
algorithm reweights edges with Bellman–Ford so they are non-negative, then
runs Dijkstra from every vertex, which is faster on sparse graphs.


</Level>
<Level name="Edge cases">


- The diagonal starts at 0; a negative value on it after the run means a
  negative cycle.


</Level>
<Level name="Corner cases">


- Putting the k loop inside instead of outside gives wrong answers that
  look plausible. The order of the loops is the algorithm.


</Level>
<Level name="Production level">


V cubed limits Floyd–Warshall to a few thousand vertices. Road networks use
precomputation schemes (contraction hierarchies) instead.


</Level>
<Level name="Mindset">


The DP state is "paths using only the first k vertices as stops". Once that
sentence is right, the three lines follow.


</Level>
<Level name="System design">


Precomputing all pairs is a cache trade: space and build time for instant
queries, and a rebuild when an edge changes.


</Level>
<Level name="Strategy">


Implement Floyd–Warshall with path reconstruction and check it against V
runs of Dijkstra. Done when I can explain why k must be the outer loop.

</Level>

### 24. Maximum Flow

**Covers:** Flow networks, the Ford–Fulkerson method, and maximum bipartite matching.

<Levels label="Chapter 24, Maximum Flow">

<Level name="Beginner">


A flow network has edges with capacities, a source and a sink. Maximum flow
is the most that can travel from source to sink without exceeding any
capacity.


</Level>
<Level name="Intermediate">


Ford–Fulkerson repeatedly finds an augmenting path in the residual graph,
which includes reverse edges for undoing flow, and pushes as much as the
path allows. Using BFS to find the path (Edmonds–Karp) bounds the running
time at V E squared.


</Level>
<Level name="Advanced">


The max-flow min-cut theorem: the maximum flow equals the capacity of the
smallest cut separating source from sink. Bipartite matching becomes a flow
problem with unit capacities.


</Level>
<Level name="Edge cases">


- Source equals sink, or no path at all: the flow is zero.


</Level>
<Level name="Corner cases">


- Irrational capacities can make plain Ford–Fulkerson fail to terminate;
  with integer capacities it terminates, and the max flow is integral.


</Level>
<Level name="Production level">


Assignment problems, image segmentation, airline scheduling and network
reliability are max flow or min cut in disguise.


</Level>
<Level name="Mindset">


Reverse edges are the clever part: let the algorithm change its mind.


</Level>
<Level name="System design">


The minimum cut is the bottleneck of a pipeline. Finding it tells me which
link to upgrade.


</Level>
<Level name="Strategy">


Write Edmonds–Karp on an adjacency matrix, then use it for a bipartite
matching of people to tasks. Done when I can find the min cut from the final
residual graph.

</Level>

### 25. Matchings in Bipartite Graphs

**Covers:** Maximum bipartite matching revisited, the stable-marriage problem, and the
Hungarian algorithm for the assignment problem.

<Levels label="Chapter 25, Matchings in Bipartite Graphs">

<Level name="Beginner">


A matching pairs vertices so no vertex is used twice. In a bipartite graph,
vertices are on two sides and edges only cross between them.


</Level>
<Level name="Intermediate">


Augmenting paths grow a matching one pair at a time; Hopcroft–Karp finds
many at once. Gale–Shapley stable matching has one side propose in order of
preference until no pair would rather be together than with their partners.


</Level>
<Level name="Advanced">


The Hungarian algorithm finds a minimum-cost perfect matching on a weighted
bipartite graph, using labels on vertices to keep track of which edges are
"tight" enough to use.


</Level>
<Level name="Edge cases">


- Unequal sides: some vertices stay unmatched; a perfect matching does not
  exist.


</Level>
<Level name="Corner cases">


- In stable matching, the proposing side gets its best stable partner and
  the other side its worst. Who proposes is a policy choice, not a detail.


</Level>
<Level name="Production level">


Medical residency matching, school choice, ride assignment and ad auctions
use these algorithms.


</Level>
<Level name="Mindset">


An algorithm's "optimal" depends on who it is optimal for.


</Level>
<Level name="System design">


Matching services pair supply with demand under constraints. Fairness is a
property of the algorithm I pick.

### 26. Parallel Algorithms

**Covers:** The basics of fork-join parallelism, parallel matrix multiplication, and
parallel merge sort.

<Levels label="Chapter 26, Parallel Algorithms">

<Level name="Beginner">


Fork-join parallelism spawns subtasks that may run at the same time and
waits for them to finish. Divide-and-conquer algorithms parallelise
naturally.


</Level>
<Level name="Intermediate">


Work is the total cost on one processor; span is the length of the longest
chain of dependent steps. Parallelism is work divided by span: the most
speed-up extra processors can give.


</Level>
<Level name="Advanced">


A greedy scheduler runs in at most work over P plus span. Parallel merge sort
needs a parallel merge, because a serial merge makes the span linear and kills
the speed-up.


</Level>
<Level name="Edge cases">


- Tasks so small that spawning them costs more than doing them: a serial
  cutoff below some size is needed.


</Level>
<Level name="Corner cases">


- Two parallel strands writing the same location: a determinacy race,
  giving different results run to run.


</Level>
<Level name="Production level">


In JavaScript, worker threads and the browser's Web Workers are the
fork-join tools; data must be copied or shared through `SharedArrayBuffer`.


</Level>
<Level name="Mindset">


Ask for the span before adding cores. Amdahl's law is the span talking.


</Level>
<Level name="System design">


Map-reduce and parallel query execution split work by the same model: total
work, critical path, and the cost of combining.


</Level>
<Level name="Strategy">


Compute work and span for merge sort with a serial and a parallel merge. Done
when I can predict the speed-up ceiling before running a parallel version in
worker threads.

### 27. Online Algorithms

**Covers:** Waiting for an elevator, maintaining a search list, and online caching,
analysed by competitive ratio.

<Levels label="Chapter 27, Online Algorithms">

<Level name="Beginner">


An online algorithm gets its input one piece at a time and must decide
without seeing the future. Its competitive ratio compares it with the best
offline algorithm that does see the future.


</Level>
<Level name="Intermediate">


Waiting for an elevator versus taking the stairs is the ski-rental problem:
wait as long as the stairs would take, then walk, and you never pay more than
about twice the best choice. Move-to-front keeps a list in a good order
without knowing the future requests.


</Level>
<Level name="Advanced">


For caching, LRU is k-competitive for a cache of size k against the
furthest-in-future optimum, and no deterministic policy does better.
Randomised marking policies do better in expectation.


</Level>
<Level name="Edge cases">


- A cache of size one: every policy behaves the same.


</Level>
<Level name="Corner cases">


- A cyclic access pattern one item larger than the cache: LRU misses every
  time, while the optimum misses rarely.


</Level>
<Level name="Production level">


Cache eviction, autoscaling and "retry or give up" decisions are online
problems. The adversarial input for LRU is a real workload: a full table
scan.


</Level>
<Level name="Mindset">


When I cannot know the future, bound how badly I can do against someone who
does.


</Level>
<Level name="System design">


Scan-resistant caches (LRU-K, 2Q, ARC) exist because of the cyclic worst case
above.


</Level>
<Level name="Strategy">

### 28. Matrix Operations

**Covers:** Solving systems of linear equations with LUP decomposition, inverting

<Levels label="Chapter 28, Matrix Operations">

A system of linear equations is a matrix times a vector of unknowns equals a

</Level>
<Level name="Intermediate">

</Level>

<Level name="Production level">

<Level name="Mindset">


Floating point turns exact algebra into approximate computation. Phase 5

<Level name="System design">


Linear regression in a metrics dashboard and ML training both sit on these

### 29. Linear Programming

**Covers:** Linear programming formulations and the algorithms that solve them,
formulating problems as linear programs, and duality.

<Levels label="Chapter 29, Linear Programming">

<Level name="Beginner">


A linear program maximises or minimises a linear function subject to linear
inequalities. Many scheduling and resource problems fit this shape.


</Level>
<Level name="Intermediate">


Shortest paths and max flow can both be written as linear programs. The
feasible region is a convex polytope, and an optimum sits at a corner.


</Level>
<Level name="Advanced">


Duality: every LP has a dual whose optimum equals the primal's, which gives a
certificate that a solution is optimal. The simplex method walks corner to
corner and is fast in practice, though exponential in the worst case;
interior-point methods are polynomial.


</Level>
<Level name="Edge cases">


- Infeasible programs (no point satisfies the constraints) and unbounded
  ones (the objective grows forever).


</Level>
<Level name="Corner cases">


- Requiring integer variables turns LP into integer programming, which is
  NP-hard. Rounding an LP answer is not the same thing.


</Level>
<Level name="Production level">


Solvers (GLPK, HiGHS, commercial ones) do this. My job is to model the
problem correctly.


</Level>
<Level name="Mindset">


Modelling a problem as an LP is often the whole job; the solver is a library
call.


</Level>
<Level name="System design">


Capacity planning, ad budget allocation and supply chains are LPs inside
larger systems.


</Level>

### 30. Polynomials and the FFT

**Covers:** Representing polynomials by coefficients and by point values, the discrete
Fourier transform and the fast Fourier transform, and FFT circuits.

<Levels label="Chapter 30, Polynomials and the FFT">

<Level name="Beginner">


Multiplying two polynomials of degree n the school way costs n squared. The
FFT does it in n log n.


</Level>
<Level name="Intermediate">


The trick is changing representation: evaluate both at enough points,
multiply point by point, and interpolate back. Choosing complex roots of unity
as the points makes evaluation divide and conquer.


</Level>
<Level name="Advanced">


The FFT recurrence is T(n) = 2T(n/2) + n, so n log n. The same transform
multiplies big integers and computes convolutions.


</Level>
<Level name="Edge cases">


- Sizes that are not a power of two: pad with zeros.


</Level>
<Level name="Corner cases">


- Floating-point rounding when multiplying big integers by FFT: results must
  be rounded back, and large inputs need a number-theoretic transform.


</Level>
<Level name="Production level">


Audio, image compression, signal processing and big-number libraries use FFT
implementations tuned far beyond the textbook.


</Level>
<Level name="Mindset">


When an operation is expensive in one representation, change representation.


</Level>
<Level name="System design">


Representation changes are a system tool too: column stores, compressed

</Level>

### 31. Number-Theoretic Algorithms

**Covers:** Elementary number theory, the greatest common divisor, modular arithmetic,
solving modular linear equations, the Chinese remainder theorem, powers of an
element, the RSA public-key cryptosystem, and primality testing.

<Levels label="Chapter 31, Number-Theoretic Algorithms">

<Level name="Beginner">


Euclid's algorithm finds the greatest common divisor by repeated remainders.

```ts
const gcd = (a: bigint, b: bigint): bigint => (b === 0n ? a : gcd(b, a % b));
function modPow(b: bigint, e: bigint, m: bigint): bigint {
  let r = 1n; b %= m;
  for (; e > 0n; e >>= 1n, b = (b * b) % m) if (e & 1n) r = (r * b) % m;
  return r;
}
```


</Level>
<Level name="Intermediate">


Extended Euclid also finds modular inverses. Fast exponentiation by squaring
computes powers mod m in log e steps. The Chinese remainder theorem rebuilds
a number from its remainders modulo coprime moduli.


</Level>
<Level name="Advanced">


RSA: choose two large primes, publish their product and an exponent, keep
the inverse exponent secret. Encryption and decryption are modular powers.
Miller–Rabin tests primality probabilistically.


</Level>
<Level name="Edge cases">


- `%` in JavaScript keeps the sign of the dividend: `-7 % 3` is `-1`. Modular
  arithmetic needs `((a % m) + m) % m`.
- Numbers above 2 to the 53 lose precision as `number`; use `bigint`.


</Level>
<Level name="Corner cases">


- A modular inverse does not exist when the number and the modulus share a
  factor; extended Euclid reveals it with a gcd above 1.


</Level>
<Level name="Production level">


Never implement RSA for real use: textbook RSA without padding is insecure,
and timing leaks keys. Use the platform's crypto library.


</Level>
<Level name="Mindset">


Correct maths is not secure code. Side channels and padding are part of the
algorithm in practice.


</Level>
<Level name="System design">


TLS, signatures and hash-based IDs rest on this chapter; phase 7 and the
security phase return to it.


</Level>
<Level name="Strategy">


Write gcd, extended gcd, modPow and Miller–Rabin with `bigint`, and a
toy RSA round trip clearly marked unsafe. Done when the round trip works and

### 32. String Matching

**Covers:** The naive string-matching algorithm, Rabin–Karp, matching with finite
automata, Knuth–Morris–Pratt, and suffix arrays.

<Levels label="Chapter 32, String Matching">

<Level name="Beginner">


Find every place a pattern of length m occurs in a text of length n. The
naive method tries every shift, costing up to n times m.


</Level>
<Level name="Intermediate">


KMP precomputes, for each prefix of the pattern, the longest proper prefix
that is also a suffix. On a mismatch, it shifts by that much instead of
starting over, so it never moves backwards in the text.

```ts
function prefixFunction(p: string): number[] {
  const pi = new Array(p.length).fill(0);
  for (let i = 1, k = 0; i < p.length; i++) {
    while (k > 0 && p[i] !== p[k]) k = pi[k - 1];
    if (p[i] === p[k]) k++;
    pi[i] = k;
  }
  return pi;
}
```


</Level>
<Level name="Advanced">


Rabin–Karp compares rolling hashes and checks real matches on a hit, which
suits searching for many patterns. A suffix array sorts all suffixes of the
text; with the LCP array it answers substring and repeat queries quickly.


</Level>
<Level name="Edge cases">


- Empty pattern: matches at every position, or is an error; decide.
- Overlapping matches ("aa" in "aaaa" occurs three times).


</Level>
<Level name="Corner cases">


- Rabin–Karp with a weak hash and adversarial text: many false hits, and the
  verification makes it n times m again.
- JavaScript strings are UTF-16: "characters" outside the basic plane are
  two code units, so match on code units or code points consistently.


</Level>
<Level name="Production level">


`grep`, editors and intrusion detection use variants (Boyer–Moore,
Aho–Corasick). Full-text search uses inverted indexes, and suffix arrays
appear in compression and bioinformatics.


</Level>
<Level name="Mindset">


Precompute what a failure teaches me, so I never re-read the same input.


</Level>
<Level name="System design">


Search features choose between scanning (simple, no index) and indexing
(fast queries, build and storage cost).


</Level>
<Level name="Strategy">


Implement naive, KMP and Rabin–Karp and a naive suffix array, and test all on
random text with a tiny alphabet. Done when I can compute the prefix function
of a pattern by hand and my phase 4 search tool uses KMP.

</Level>

### 34. NP-Completeness

**Covers:** Polynomial time, polynomial-time verification, NP-completeness and
reducibility, NP-completeness proofs, and a set of NP-complete problems.

<Levels label="Chapter 34, NP-Completeness">

<Level name="Beginner">


P is the class of problems solvable in polynomial time. NP is the class whose
yes-answers can be checked in polynomial time given a certificate. Nobody
knows whether they are equal.


</Level>
<Level name="Intermediate">


A problem is NP-complete if it is in NP and every NP problem reduces to it.
To show a new problem is NP-hard, reduce a known NP-complete problem to it:
known to new, never the other way.


</Level>
<Level name="Advanced">


The chain starts at circuit satisfiability and runs through SAT, 3-CNF-SAT,
clique, vertex cover, Hamiltonian cycle, travelling salesperson and subset
sum. Each reduction is a polynomial transformation that preserves yes and no
answers.


</Level>
<Level name="Edge cases">


- NP-hard is about the worst case over all inputs. A specific input family
  (trees, small k, bounded weights) can be easy.


</Level>
<Level name="Corner cases">


- Subset sum has a pseudo-polynomial DP, polynomial in the numeric value of
  the target but not in its number of bits. "NP-complete" and "fast in
  practice" can both be true.


</Level>
<Level name="Production level">


When a product requirement turns out to be NP-hard (optimal scheduling,
packing, routing), the response is an approximation, a heuristic, a solver
or a smaller problem, not a promise of optimality.


</Level>
<Level name="Mindset">


Recognising a hard problem early saves weeks. The reduction is the
argument.


</Level>
<Level name="System design">


Schedulers, bin-packing in container orchestrators and route planners all
choose heuristics because of this chapter.


</Level>
<Level name="Strategy">


Write the reductions from 3-SAT to clique and from clique to vertex cover on
paper. Done when I can explain the direction of a reduction to someone else
and say what I would ship instead of an exact solver.

</Level>

### 35. Approximation Algorithms

**Covers:** The vertex-cover problem, the travelling-salesperson problem, the set-covering
problem, randomization and linear programming, and the subset-sum problem.

<Levels label="Chapter 35, Approximation Algorithms">

<Level name="Beginner">


An approximation algorithm runs in polynomial time and guarantees a
solution within a stated factor of optimal.


</Level>
<Level name="Intermediate">


Vertex cover: take any uncovered edge and add both its ends. The result is
at most twice the optimum. For TSP with the triangle inequality, walking an
MST gives a tour at most twice optimal.


</Level>
<Level name="Advanced">


Greedy set cover is within a logarithmic factor, and that is essentially the
best possible. Subset sum has a fully polynomial-time approximation scheme:
any accuracy, at a cost that grows as the accuracy tightens.


</Level>
<Level name="Edge cases">


- TSP without the triangle inequality cannot be approximated within any
  constant factor unless P equals NP.


</Level>
<Level name="Corner cases">


- An approximation factor is a worst case. On real inputs the gap is often
  much smaller, which a benchmark against an exact solver on small inputs
  shows.


</Level>
<Level name="Production level">


Ship approximations with the guarantee documented, and measure the real gap
on representative data.


</Level>
<Level name="Mindset">


A provable "good enough" beats an unprovable "optimal".


</Level>
<Level name="System design">


Placement, packing and route planning in production systems are
approximation algorithms with tuning on top.


</Level>
<Level name="Strategy">


Implement the vertex-cover and MST-tour approximations and compare them with
brute force on small graphs. Done when I can state each guarantee and the
measured gap.

</Level>

## Misreadings to avoid

- "CLRS is the book to learn algorithms from first." It is the reference for
  proofs. A design-first book and practice problems come first.
- "Pseudocode is ready to paste." The book indexes arrays from 1 and leaves
  out overflow, recursion depth and error handling.
- "If it is in CLRS, it is what production uses." Libraries use tuned
  hybrids: TimSort, introsort, B+ trees, Swiss tables.
- "Asymptotic bounds decide everything." Constants and memory layout decide
  most real comparisons at production sizes.
- "NP-hard means I cannot solve it." It means no known algorithm is fast on
  every input; real inputs are often tractable.
- "Reading the proof is enough." Writing the code and a property test is
  what shows I understood it.
