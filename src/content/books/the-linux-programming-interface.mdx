## Why this book

This is the optional depth book for phase 6 of the <a href={withBase('/plans/traditional-software-developer/')}>traditional core</a>,
operating systems. Operating Systems: Three Easy Pieces explains why the kernel works the way it does; this
book is the exact contract of every system call and library function a Linux program uses, with the rules,
the error cases and the portability notes. It is the book I keep open when `strace` shows me a call I do not
fully understand.

It is long, and it is a reference as much as a tutorial. I would not read it front to back. I would read the
chapters each phase 6 project needs, and dip into the rest as later phases (networking, databases,
distributed systems) send me back to a call.

## How I would learn it

Every chapter here comes with small example programs. My loop is: read the chapter, write my own small
program that uses the calls, run it under `strace`, then read the man page for each call and find one rule
the chapter mentioned that the man page states differently or more precisely. Node's `fs`, `child_process`,
`net` and `worker_threads` modules are thin layers over these calls, so for most chapters I also write the
Node version and check in `strace` that it makes the calls I expect.

## Background

### 1. History and Standards
**Covers:** Where UNIX and Linux came from, and the standards (POSIX, the Single UNIX Specification, C) that define what a portable program can rely on.

<Levels label="Chapter 1, History and Standards">

<Level name="Beginner">

Linux is a UNIX-like kernel; together with GNU tools and a C library it forms the systems I use. Standards say which calls exist and how they behave.

</Level>

<Level name="Intermediate">

POSIX and the Single UNIX Specification describe the interface; Linux implements most of it and adds its own calls. Feature-test macros choose which definitions a program sees.

</Level>

<Level name="Advanced">

A call can be standard, a Linux extension, or present on Linux with subtly different behaviour; the man page's "Conforming to" (now "Standards") section says which.

</Level>

<Level name="Edge cases">

A program that compiles on Linux may fail on macOS because it used a Linux-only call such as `epoll`.

</Level>

<Level name="Corner cases">

The same call name can differ between the kernel and the C library wrapper, and between glibc and musl, so a container built on Alpine can behave differently from one built on Debian.

</Level>

<Level name="Production level">

Portability matters most for libraries and tools; for a service that only ever runs on Linux it is a choice, and it should be a written one.

</Level>

<Level name="Mindset">

Know which contract you depend on: the standard, the kernel, or the library.

</Level>

<Level name="System design">

Runtimes like Node and libuv exist partly to hide these differences across platforms.

</Level>

<Level name="Strategy">

I would check three calls I use (`epoll_wait`, `sendfile`, `posix_spawn`) for which standard defines them. Done when I can say which of my programs would run on macOS unchanged.

</Level>
</Levels>

### 2. Fundamental Concepts
**Covers:** A tour of the ideas the rest of the book builds on: the kernel, the shell, users and groups, the file hierarchy, file I/O, programs and processes, memory mappings, IPC, signals, threads, sessions, pseudoterminals, time and /proc.

<Levels label="Chapter 2, Fundamental Concepts">

<Level name="Beginner">

The kernel manages resources; programs ask it for things with system calls. Everything else in the book is a closer look at one item in this tour.

</Level>

<Level name="Intermediate">

Files, processes, users, signals and IPC interact: a process runs as a user, opens files with permissions, receives signals, and talks to other processes.

</Level>

<Level name="Advanced">

Many resources are reached through file descriptors, which is why "everything is a file" is a useful, if incomplete, slogan.

</Level>

<Level name="Edge cases">

Some things are not files at all (threads, most signals), and some files are not storage (`/proc`, `/dev/null`).

</Level>

<Level name="Corner cases">

A process has a real, effective and saved user ID, and the difference only matters when privileges change, which is exactly when bugs are dangerous.

</Level>

<Level name="Production level">

`/proc` is the first place to look when a production process misbehaves: its open files, memory maps, limits and status.

</Level>

<Level name="Mindset">

Learn the vocabulary first; the details attach to it.

</Level>

<Level name="System design">

Container runtimes are assembled from these pieces: processes, namespaces, file systems, users, signals.

</Level>

<Level name="Strategy">

I would explore `/proc/self` for a running shell and name what each entry shows. Done when I can explain ten entries without looking them up.

</Level>
</Levels>

### 3. System Programming Concepts
**Covers:** How system calls and library functions differ, the C library, error handling with errno, the book's example conventions, and portability issues.

<Levels label="Chapter 3, System Programming Concepts">

<Level name="Beginner">

A system call enters the kernel; a library function is ordinary code that may or may not make system calls. `fopen` is a library function; `open` is a system call.

</Level>

<Level name="Intermediate">

System calls report failure by returning -1 and setting `errno`; programs must check every return value and print `strerror(errno)` or use `perror`.

</Level>

<Level name="Advanced">

A system call goes through a C library wrapper that puts arguments in registers, executes the trap instruction and converts the kernel's negative return into -1 and errno.

</Level>

<Level name="Edge cases">

Some calls can legitimately return -1 on success (`getpriority`), so errno must be cleared first and checked after.

</Level>

<Level name="Corner cases">

errno is per-thread, but a signal handler that makes a call can overwrite it in the middle of the interrupted code; handlers must save and restore it.

</Level>

<Level name="Production level">

Unchecked return values are the most common cause of silent failures in system code; every call gets a check.

</Level>

<Level name="Mindset">

Every call can fail. Handle the failure where it happens, with the reason.

</Level>

<Level name="System design">

Node turns errno values into error codes like `ENOENT` and `EACCES`; knowing them makes Node errors readable.

</Level>

<Level name="Strategy">

I would write a tiny wrapper that prints the call name and `strerror` on failure, then trigger `ENOENT`, `EACCES` and `EBADF` on purpose. Done when I can predict the errno for a failing call before running it.

</Level>
</Levels>

## Files and processes

### 4. File I/O: The Universal I/O Model
**Covers:** The four core calls (open, read, write, close), file descriptors, and why the same calls work on files, pipes, terminals and devices.

<Levels label="Chapter 4, File I/O: The Universal I/O Model">

<Level name="Beginner">

`open` gives a file descriptor, a small integer; `read` and `write` move bytes through it; `close` releases it. Descriptors 0, 1 and 2 are standard input, output and error.

</Level>

<Level name="Intermediate">

The same four calls work on regular files, pipes, sockets, terminals and devices, which is what makes small Unix tools composable.

</Level>

<Level name="Advanced">

`open` flags choose access mode and behaviour (`O_CREAT`, `O_EXCL`, `O_TRUNC`, `O_APPEND`); the mode argument sets permissions for new files, filtered by the umask. `lseek` moves the offset and can create holes.

</Level>

<Level name="Edge cases">

`read` can return fewer bytes than asked (a short read) without an error, especially from pipes, sockets and terminals; 0 means end of file.

</Level>

<Level name="Corner cases">

Seeking past the end and writing creates a file with a hole: its size is large, its disk use small, and reading the hole returns zeros.

</Level>

<Level name="Production level">

Every I/O loop must handle short reads and writes. A forgotten `close` leaks descriptors until `EMFILE`.

</Level>

<Level name="Mindset">

One interface for many kinds of things is worth more than a perfect interface for each.

</Level>

<Level name="System design">

Streams in Node are this model with back-pressure added.

</Level>

<Level name="Strategy">

I would write my own `cp` with `open`, `read` and `write` that handles short writes and holes. Done when it copies a sparse file and keeps it sparse.

</Level>
</Levels>

### 5. File I/O: Further Details
**Covers:** Atomicity, fcntl and open file status flags, how descriptors relate to open files, dup, positional I/O, scatter-gather I/O, truncation, non-blocking I/O, large files and /dev/fd.

<Levels label="Chapter 5, File I/O: Further Details">

<Level name="Beginner">

Two processes writing to a file can interleave badly unless the operation is atomic. `O_APPEND` makes "seek to end and write" one step.

</Level>

<Level name="Intermediate">

`dup` and `dup2` make another descriptor for the same open file; this is how a shell sets up redirection. `pread` and `pwrite` read and write at an offset without moving the shared offset.

</Level>

<Level name="Advanced">

There are three layers: per-process descriptors point to system-wide open file descriptions (offset, status flags), which point to inodes. `dup` shares the description; opening the file again creates a new one.

</Level>

<Level name="Edge cases">

`O_CREAT` with `O_EXCL` atomically creates a file only if it does not exist, the basis of lock files.

</Level>

<Level name="Corner cases">

Two descriptors from `dup` share an offset, but the close-on-exec flag belongs to each descriptor, not to the shared description.

</Level>

<Level name="Production level">

Log files opened with `O_APPEND` by several processes stay intact line by line for reasonably small writes on local file systems; on network file systems that promise weakens.

</Level>

<Level name="Mindset">

Draw the three tables when descriptors confuse you.

</Level>

<Level name="System design">

Zero-downtime restarts pass listening descriptors to a new process; this is the model that makes it work.

</Level>

<Level name="Strategy">

I would write a program that demonstrates shared and separate offsets with `dup` versus a second `open`. Done when I can draw the three tables for any shell redirection.

</Level>
</Levels>

### 6. Processes
**Covers:** Processes and programs, process IDs, the memory layout of a process, virtual memory, the stack, command-line arguments, the environment, and nonlocal gotos.

<Levels label="Chapter 6, Processes">

<Level name="Beginner">

A process is an instance of a running program with an ID and a parent ID. Its memory has text, initialized data, uninitialized data (bss), heap and stack.

</Level>

<Level name="Intermediate">

`main` receives `argc` and `argv`; the environment is a list of `NAME=value` strings reached with `getenv` and `setenv`. Each function call adds a stack frame.

</Level>

<Level name="Advanced">

Virtual memory gives each process its own layout; `/proc/PID/maps` shows it. `setjmp` and `longjmp` jump across stack frames, skipping normal returns.

</Level>

<Level name="Edge cases">

Arguments and environment share a limited space, so very long command lines fail with `E2BIG`.

</Level>

<Level name="Corner cases">

`longjmp` out of a signal handler or into a function that has returned is undefined; optimised local variables may not keep their values across it.

</Level>

<Level name="Production level">

Environment variables are the usual way to configure services, and they are visible to anyone who can read `/proc/PID/environ` with the right permissions, so secrets there need care.

</Level>

<Level name="Mindset">

The process is a container of state. Know what is in it and who can see it.

</Level>

<Level name="System design">

The twelve-factor config pattern is the environment list used as an interface.

</Level>

<Level name="Strategy">

I would print the addresses of each memory segment and compare them with `/proc/self/maps`. Done when every address falls in the region I predicted.

</Level>
</Levels>

### 7. Memory Allocation
**Covers:** Allocating on the heap with brk, sbrk, malloc and free, how malloc is implemented, debugging allocators, and allocating on the stack with alloca.

<Levels label="Chapter 7, Memory Allocation">

<Level name="Beginner">

`malloc` returns heap memory; `free` returns it. Underneath, the heap grows with `brk` and `sbrk`, and large blocks come from `mmap`.

</Level>

<Level name="Intermediate">

`calloc` zeroes memory, `realloc` resizes it and may move it, and `memalign`-style calls give aligned blocks.

</Level>

<Level name="Advanced">

malloc keeps free lists of blocks with headers; freeing rarely shrinks the heap, so process memory often does not drop after freeing. glibc's environment knobs and debugging hooks help find misuse.

</Level>

<Level name="Edge cases">

`realloc` to a larger size can return a different pointer; keeping the old pointer is a use-after-free.

</Level>

<Level name="Corner cases">

`realloc` failing returns NULL and leaves the old block valid, so `p = realloc(p, n)` leaks on failure.

</Level>

<Level name="Production level">

Memory that does not return to the OS after a spike is normal allocator behaviour, not always a leak; per-thread arenas can multiply it.

</Level>

<Level name="Mindset">

Measure resident memory over time, not after one free.

</Level>

<Level name="System design">

Node's heap, the V8 garbage collector and native buffers sit on top of this allocator.

</Level>

<Level name="Strategy">

I would allocate and free in patterns and watch the program break with `sbrk(0)`. Done when I can explain why freed memory did not shrink the heap.

</Level>
</Levels>

### 8. Users and Groups
**Covers:** The password, shadow password and group files, and the functions that read user and group information.

<Levels label="Chapter 8, Users and Groups">

<Level name="Beginner">

Users and groups are numbers (UID, GID) with names stored in `/etc/passwd` and `/etc/group`. Password hashes live in `/etc/shadow`.

</Level>

<Level name="Intermediate">

`getpwnam` and `getgrnam` look up users and groups; they consult the configured name services, not only the files.

</Level>

<Level name="Advanced">

The name service switch can pull users from LDAP or other sources, so lookups can be slow or fail on network problems.

</Level>

<Level name="Edge cases">

A UID with no name in `/etc/passwd` is still valid; tools show the number.

</Level>

<Level name="Corner cases">

Inside a container with a user namespace, UID 0 can map to an unprivileged UID on the host, so the same number means different things.

</Level>

<Level name="Production level">

Running services as dedicated unprivileged users limits the damage a bug can do.

</Level>

<Level name="Mindset">

Identity is a number; names are a lookup that can fail.

</Level>

<Level name="System design">

Container images should run as non-root users with fixed UIDs so mounted volumes keep working.

</Level>

<Level name="Strategy">

I would write `id` with `getpwuid` and `getgrouplist`. Done when it matches the real `id` output.

</Level>
</Levels>

### 9. Process Credentials
**Covers:** Real, effective and saved user and group IDs, file-system IDs, supplementary groups, and the calls that change them.

<Levels label="Chapter 9, Process Credentials">

<Level name="Beginner">

Each process has a real UID (who started it) and an effective UID (whose permissions it uses). Usually they are the same.

</Level>

<Level name="Intermediate">

A set-user-ID program runs with the file owner's effective UID; `passwd` uses this to edit the shadow file.

</Level>

<Level name="Advanced">

The saved set-user-ID lets a program drop privileges temporarily and regain them; `setuid`, `seteuid` and `setresuid` have subtly different rules for privileged and unprivileged callers.

</Level>

<Level name="Edge cases">

`setuid` called by root changes all three IDs permanently, which is the right way to drop privileges for good.

</Level>

<Level name="Corner cases">

Dropping the user ID while keeping supplementary groups leaves the process with group permissions it should not have; drop groups first.

</Level>

<Level name="Production level">

Privileged programs should drop privileges as early as possible and check that the drop succeeded.

</Level>

<Level name="Mindset">

Privilege is something to hold briefly and verify after releasing.

</Level>

<Level name="System design">

Services binding to port 80 used to start as root and drop privileges; capabilities and socket activation now avoid it.

</Level>

<Level name="Strategy">

I would write a small set-UID test program in a VM and print all three IDs at each step of dropping. Done when I can predict the IDs after each call.

</Level>
</Levels>

### 10. Time
**Covers:** Calendar time, converting between time representations, time zones, locales, updating the system clock, the software clock, and process time.

<Levels label="Chapter 10, Time">

<Level name="Beginner">

Calendar time is seconds since the Epoch (1 January 1970 UTC). `time` and `gettimeofday` return it; `localtime` and `strftime` turn it into readable text.

</Level>

<Level name="Intermediate">

Time zones are applied when converting, controlled by the `TZ` variable and the zone database. Process time (`times`, `clock`) measures CPU used, not wall time.

</Level>

<Level name="Advanced">

The system clock can be stepped or slewed; `adjtime` slews gradually. Wall time is not monotonic.

</Level>

<Level name="Edge cases">

Local times in a daylight-saving transition can be skipped or repeated, so converting a local time back to calendar time is ambiguous.

</Level>

<Level name="Corner cases">

Measuring a duration with wall-clock time breaks when the clock is stepped mid-measurement; use a monotonic clock.

</Level>

<Level name="Production level">

Store and log times in UTC and convert at the edges.

</Level>

<Level name="Mindset">

There are several clocks. Pick the one whose promise matches the question.

</Level>

<Level name="System design">

Distributed systems cannot trust wall clocks for ordering, which is where logical clocks come from.

</Level>

<Level name="Strategy">

I would print the same instant in three time zones and measure a duration across a manual clock change with both clocks. Done when the monotonic measurement stays right.

</Level>
</Levels>

### 11. System Limits and Options
**Covers:** Finding implementation limits and optional features at compile time and at run time with sysconf, pathconf and fpathconf.

<Levels label="Chapter 11, System Limits and Options">

<Level name="Beginner">

Systems have limits (maximum path length, open files, argument size). Some are fixed at compile time, others queried at run time.

</Level>

<Level name="Intermediate">

`sysconf` returns system-wide limits; `pathconf` returns limits that can differ per file system.

</Level>

<Level name="Advanced">

Some limits are indeterminate and the calls return -1 without setting errno, so the program must pick a sensible fallback.

</Level>

<Level name="Edge cases">

`PATH_MAX` is not a true limit; paths can be longer than it through relative paths.

</Level>

<Level name="Corner cases">

A limit read once at startup can change while the program runs (resource limits can be raised or lowered).

</Level>

<Level name="Production level">

Hard-coded buffer sizes based on assumed limits are a common source of truncation bugs.

</Level>

<Level name="Mindset">

Ask the system instead of assuming.

</Level>

<Level name="System design">

Containers and cgroups add their own limits on top of the kernel's, and `sysconf` may not report them.

</Level>

<Level name="Strategy">

I would print ten limits with `sysconf` and `pathconf` on two file systems. Done when I can explain one that differs.

</Level>
</Levels>

### 12. System and Process Information
**Covers:** The /proc file system, information about processes and the system, and the uname call.

<Levels label="Chapter 12, System and Process Information">

<Level name="Beginner">

`/proc` is a virtual file system: reading its files asks the kernel for information about processes and the system.

</Level>

<Level name="Intermediate">

`/proc/PID/status`, `fd/`, `maps` and `limits` describe one process; `/proc/meminfo`, `cpuinfo` and `loadavg` describe the system.

</Level>

<Level name="Advanced">

Many files are generated at read time, so reading them repeatedly gives fresh values, and some are writable to change kernel settings (`/proc/sys`).

</Level>

<Level name="Edge cases">

A process can exit between listing `/proc` and reading its files, so tools must handle vanishing entries.

</Level>

<Level name="Corner cases">

Inside a container, `/proc` shows the container's processes but some system-wide files still show the host's totals, which confuses memory-reporting tools.

</Level>

<Level name="Production level">

`top`, `ps` and most monitoring agents are readers of `/proc`.

</Level>

<Level name="Mindset">

When a tool's output is confusing, read the file it reads.

</Level>

<Level name="System design">

Observability agents scrape `/proc` and cgroup files to build host metrics.

</Level>

<Level name="Strategy">

I would write a tiny `ps` that lists PID, command and resident memory from `/proc`. Done when it survives processes disappearing during the scan.

</Level>
</Levels>

## File systems

### 13. File I/O Buffering
**Covers:** The two layers of buffering (the kernel's buffer cache and stdio's user-space buffers), controlling each, fsync and friends, direct I/O, and mixing library and system calls.

<Levels label="Chapter 13, File I/O Buffering">

<Level name="Beginner">

`write` copies data into the kernel's buffer cache and returns; the kernel writes it to disk later. stdio adds its own buffer in the process on top.

</Level>

<Level name="Intermediate">

`fflush` moves stdio's buffer into the kernel; `fsync` and `fdatasync` move the kernel's buffers to the device. `setvbuf` picks full, line or no buffering.

</Level>

<Level name="Advanced">

Buffer size changes throughput a lot: tiny writes cost a system call each. `O_DIRECT` bypasses the buffer cache with strict alignment rules; `posix_fadvise` hints the access pattern.

</Level>

<Level name="Edge cases">

stdout is line-buffered on a terminal and fully buffered into a pipe, so a program's output order can change when piped.

</Level>

<Level name="Corner cases">

Mixing `printf` and `write` on the same descriptor reorders output, because one is buffered in the process and the other is not; forking with a full stdio buffer prints it twice.

</Level>

<Level name="Production level">

Databases call `fsync` (or `fdatasync`) at commit; a missing one loses committed data on power loss, and a fake one (a drive that caches) does too.

</Level>

<Level name="Mindset">

Know which buffer your data is in at every moment.

</Level>

<Level name="System design">

The durability promise of every database is built on exactly these calls.

</Level>

<Level name="Strategy">

I would time copying a file with buffer sizes from 1 byte to 1 MiB, then add `fsync` per write. Done when I can explain the shape of both curves.

</Level>
</Levels>

### 14. File Systems
**Covers:** Devices, disks and partitions, file systems and inodes, the virtual file system, journaling, the single directory hierarchy, mounting and unmounting, tmpfs, and file system statistics.

<Levels label="Chapter 14, File Systems">

<Level name="Beginner">

A disk is split into partitions, each holding a file system. Mounting attaches a file system at a directory in the single tree.

</Level>

<Level name="Intermediate">

An ext-style file system has a boot block, a superblock, an inode table and data blocks. The virtual file system layer lets one set of calls work on every file system type.

</Level>

<Level name="Advanced">

`mount` takes flags (read-only, no set-UID, no exec) and can bind-mount a directory elsewhere; mount namespaces give processes different trees. Journaling file systems recover quickly after crashes.

</Level>

<Level name="Edge cases">

Running out of inodes gives "No space left on device" while `df` shows free space; `df -i` shows why.

</Level>

<Level name="Corner cases">

Mounting over a non-empty directory hides its files until unmount, and processes with files open there keep using them.

</Level>

<Level name="Production level">

tmpfs lives in memory and swap; filling it uses RAM. Container volumes are bind mounts.

</Level>

<Level name="Mindset">

The tree is assembled from many file systems; know which one a path lives on.

</Level>

<Level name="System design">

Container images are layered file systems mounted together.

</Level>

<Level name="Strategy">

## Signals and timers

### 20. Signals: Fundamental Concepts
**Covers:** What signals are, the signal types and default actions, changing dispositions with signal and sigaction, sending signals, signal masks and pending signals.

<Levels label="Chapter 20, Signals: Fundamental Concepts">

<Level name="Beginner">

A signal is a notification sent to a process: Ctrl-C sends SIGINT, `kill` sends SIGTERM by default. Each signal has a default action: terminate, dump core, ignore, stop or continue.

</Level>

<Level name="Intermediate">

A process can ignore a signal, catch it with a handler, or accept the default. SIGKILL and SIGSTOP cannot be caught or ignored.

</Level>

<Level name="Advanced">

Each thread has a signal mask of blocked signals; blocked signals stay pending until unblocked. Standard signals are not queued, so several of the same signal can arrive as one.

</Level>

<Level name="Edge cases">

Sending signal 0 checks whether a process exists and can be signalled, without sending anything.

</Level>

<Level name="Corner cases">

Signals sent while blocked collapse to one, so counting signals to count events is wrong.

</Level>

<Level name="Production level">

Services must handle SIGTERM for a graceful shutdown; containers send SIGTERM, then SIGKILL after a timeout.

</Level>

<Level name="Mindset">

A signal says "something happened", not "this many things happened".

</Level>

<Level name="System design">

Graceful shutdown in Kubernetes is SIGTERM, a grace period and SIGKILL, so every service needs a handler.

</Level>

<Level name="Strategy">

I would write a program that catches SIGINT and SIGTERM and shuts down cleanly, then send it signals with `kill`. Done when it cleans up on SIGTERM and dies immediately on SIGKILL.

### 21. Signals: Signal Handlers
**Covers:** Designing signal handlers: reentrancy and async-signal-safe functions, global variables and sig_atomic_t, ways to leave a handler, alternate signal stacks, and interrupted system calls.

<Levels label="Chapter 21, Signals: Signal Handlers">

<Level name="Beginner">

A signal handler runs in the middle of whatever the program was doing, so it must be short and careful.

</Level>

<Level name="Intermediate">

The safest handler sets a `volatile sig_atomic_t` flag and returns; the main loop checks it. Only async-signal-safe functions may be called inside a handler, and `printf` and `malloc` are not among them.

</Level>

<Level name="Advanced">

A signal can interrupt a slow system call, which then fails with `EINTR` unless the handler was installed with `SA_RESTART`. An alternate stack lets a handler run even after a stack overflow.

</Level>

<Level name="Edge cases">

Calling `malloc` in a handler while the main code was inside `malloc` can deadlock or corrupt the heap.

</Level>

<Level name="Corner cases">

A handler that changes errno breaks the interrupted code's error check unless it saves and restores errno.

</Level>

<Level name="Production level">

The self-pipe trick, or `signalfd`, turns signals into readable events for an event loop.

</Level>

<Level name="Mindset">

Do the least possible in an interrupt; defer the real work.

</Level>

<Level name="System design">

Node handles signals by converting them into events on the loop, which is the self-pipe idea.

<Levels label="Chapter 22, Signals: Advanced Features">

<Level name="Beginner">

<Level name="Intermediate">

<Level name="Mindset">

<Levels label="Chapter 23, Timers and Sleeping">

<Level name="Beginner">

`sleep` and `nanosleep` pause a process; `alarm` and `setitimer` send a signal after a delay.

<Level name="Intermediate">

## Process lifecycle

### 24. Process Creation
**Covers:** fork, exit, wait and execve in overview, how fork works, file sharing between parent and child, vfork, and race conditions after fork.

<Levels label="Chapter 24, Process Creation">

<Level name="Beginner">

`fork` creates a child process that is a copy of the parent. Both continue from the same point; the return value tells them apart.

</Level>

<Level name="Intermediate">

The child inherits copies of open descriptors that share open file descriptions with the parent, so they share offsets.

</Level>

<Level name="Advanced">

Fork uses copy-on-write, so the copy is cheap until either side writes. `vfork` shares memory until the child execs, which is faster and dangerous.

</Level>

<Level name="Edge cases">

Which process runs first after fork is not defined; code that assumes an order has a race.

</Level>

<Level name="Corner cases">

A parent that writes to a shared descriptor while its child does produces interleaved output, and forked stdio buffers can print twice.

</Level>

<Level name="Production level">

Fork in a large-memory process can still be slow because page tables must be copied; `posix_spawn` avoids it.

</Level>

<Level name="Mindset">

After fork there are two programs. Decide what each one owns.

</Level>

<Level name="System design">

Pre-fork worker models (older web servers, some language runtimes) are built on this.

</Level>

<Level name="Strategy">

I would write a program that forks, has both sides write to one file, and synchronise them with a pipe. Done when the output order is the one I chose.

### 25. Process Termination
**Covers:** Terminating a process with _exit and exit, what happens on termination, exit handlers, and the interaction between fork, stdio buffers and _exit.

<Levels label="Chapter 25, Process Termination">

<Level name="Beginner">

A process ends by calling `exit`, returning from `main`, or being killed by a signal. The exit status is a small number its parent can read.

</Level>

<Level name="Intermediate">

`exit` runs registered exit handlers and flushes stdio buffers, then calls `_exit`, which enters the kernel directly.

</Level>

<Level name="Advanced">

On termination the kernel closes descriptors, releases memory, sends SIGCHLD to the parent, and keeps a zombie entry for the status.

</Level>

<Level name="Edge cases">

Only the low 8 bits of the exit status survive, so `exit(256)` looks like success.

</Level>

<Level name="Corner cases">

A forked child that calls `exit` flushes a copy of the parent's buffers and runs the parent's exit handlers; children should usually call `_exit`.

</Level>

<Level name="Production level">

Exit codes are an interface: scripts, CI and supervisors read them. Use 0 for success and documented non-zero codes for failures.

</Level>

<Level name="Mindset">

How a program ends is part of its contract.

</Level>

<Level name="System design">

Container exit codes (137 for SIGKILL) follow the 128-plus-signal convention shells use.

<Level name="Mindset">

<Level name="System design">

A mutex makes sure only one thread at a time runs a critical section.

<Level name="Intermediate">

Signals can be directed at a thread or the process; a common design blocks signals in all threads and has one thread accept them with `sigwait`.

</Level>

<Level name="Advanced">

Linux uses NPTL, a one-to-one model: each thread is a kernel task. Calling fork in a threaded program copies only the calling thread; exec in any thread replaces all of them.

</Level>

<Level name="Edge cases">

A process-directed signal is delivered to any thread that does not block it, which might be the busiest one.

</Level>

<Level name="Corner cases">

Forking a threaded program and continuing without exec risks deadlock on locks held by threads that no longer exist; `pthread_atfork` is the partial fix.

</Level>

<Level name="Production level">

Set thread stack sizes deliberately when creating many threads, and handle signals in one place.

</Level>

<Level name="Mindset">

Combine features one at a time and check the documented interactions.

</Level>

<Level name="System design">

Runtimes with green threads or async tasks exist partly to avoid the costs and traps of one-to-one threads.

</Level>

<Level name="Strategy">

I would build a threaded program with a dedicated signal thread using `sigwait`. Done when Ctrl-C shuts all threads down cleanly.

### 35. Process Priorities and Scheduling
**Covers:** Nice values, realtime scheduling policies, and CPU affinity.

<Levels label="Chapter 35, Process Priorities and Scheduling">

<Level name="Beginner">

The nice value (from -20 to 19) hints how much CPU a process should get compared with others; higher is nicer, so less CPU.

</Level>

<Level name="Intermediate">

Realtime policies (SCHED_FIFO, SCHED_RR) always run ahead of normal processes. `sched_setaffinity` limits which CPUs a process may use.

<Level name="Corner cases">

</Level>

<Level name="Production level">

Background jobs (backups, indexing) run with a high nice value and `ionice`; latency-sensitive services may pin to cores.

</Level>

<Level name="Mindset">

</Level>

<Level name="System design">

Kubernetes CPU requests and limits map to scheduler weights and quotas.

POSIX message queues carry messages with priorities; the highest priority message is received first.

</Level>

<Level name="Intermediate">

Attributes set the maximum message count and size. `mq_notify` delivers a signal or starts a thread when a message arrives on an empty queue.

<Level name="Advanced">

<Level name="Edge cases">

Receiving with a buffer smaller than the maximum message size fails, even if the actual message is small.

</Level>

<Level name="Corner cases">

Notification is one-shot and only fires on the transition from empty, so a program that does not re-register misses later messages.

</Level>

<Level name="Production level">

Useful for local priority messaging; for anything that crosses machines, a broker is used instead.

</Level>

<Level name="Mindset">

Notification APIs usually fire on transitions, not on states. Re-check the state.

</Level>

<Level name="System design">

Priority queues in job systems behave like this, with the same starvation risks.

</Level>

<Level name="Strategy">

I would build a priority job queue with two producers and one consumer. Done when high-priority jobs always go first.

</Level>
</Levels>

### 53. POSIX Semaphores
**Covers:** Named semaphores, semaphore operations, unnamed semaphores, comparison with Pthreads mutexes, and limits.

<Levels label="Chapter 53, POSIX Semaphores">

<Level name="Beginner">

A POSIX semaphore is a counter: `sem_wait` decrements or blocks, `sem_post` increments.

</Level>

<Level name="Intermediate">

Named semaphores are shared by name between processes; unnamed ones live in memory shared by threads or processes.

</Level>

<Level name="Advanced">

Semaphores can be posted by any thread, unlike mutexes, which makes them good for signalling between processes.

</Level>

<Level name="Edge cases">

`sem_wait` can be interrupted by a signal and fail with `EINTR`.

</Level>

<Level name="Corner cases">

A process that dies after `sem_wait` leaves the count reduced forever, since POSIX semaphores have no undo.

</Level>

<Level name="Production level">

Mutexes are better for mutual exclusion in threads; semaphores for counting resources and cross-process signalling.

</Level>

<Level name="Mindset">

Use the primitive whose meaning matches the problem.

</Level>

<Level name="System design">

Connection pools and worker limits are counting semaphores.

</Level>

<Level name="Strategy">

I would limit concurrent workers across processes to three with a named semaphore. Done when no more than three ever run.

</Level>
</Levels>

### 54. POSIX Shared Memory
**Covers:** Creating, using and removing shared memory objects, and comparison with other shared memory APIs.

<Levels label="Chapter 54, POSIX Shared Memory">

<Level name="Beginner">

`shm_open` creates a named shared memory object; `ftruncate` sets its size; `mmap` maps it into each process.

</Level>

<Level name="Intermediate">

It combines the file model with mmap: an object is a file in a memory file system.

</Level>

<Level name="Advanced">

Compared with System V, it uses ordinary descriptors and naming; compared with mapping a regular file, it avoids disk writes.

</Level>

<Level name="Edge cases">

Forgetting `ftruncate` leaves a zero-size object, and touching the mapping raises SIGBUS.

</Level>

<Level name="Corner cases">

Objects persist until unlinked, so a crashed program leaves memory in use in `/dev/shm`.

</Level>

<Level name="Production level">

Container runtimes limit `/dev/shm` size, which breaks programs (browsers, some databases) that expect more.

</Level>

<Level name="Mindset">

Shared memory is a file you never write to disk.

</Level>

<Level name="System design">

High-performance local data paths (video, ML inference) share buffers this way.

</Level>

<Level name="Strategy">

I would port my ring buffer to POSIX shared memory and semaphores. Done when it runs and cleans up `/dev/shm` on exit.

</Level>
</Levels>

### 55. File Locking
**Covers:** Advisory locking with flock and fcntl record locks, mandatory locking, the /proc/locks file, running one instance of a program, and older techniques.

<Levels label="Chapter 55, File Locking">

<Level name="Beginner">

File locks let processes coordinate access to a file. Most Unix locks are advisory: they only work if every program checks them.

</Level>

<Level name="Intermediate">

`flock` locks a whole file; `fcntl` locks byte ranges and is the one POSIX defines. Locks can be shared (read) or exclusive (write).

</Level>

<Level name="Advanced">

`fcntl` locks belong to the process and the inode, so closing any descriptor to the file releases all the process's locks on it. Deadlocks between record locks are detected and reported.

</Level>

<Level name="Edge cases">

A lock file with a PID inside is a common single-instance trick, and a stale PID after a crash breaks it unless the lock is a real lock.

</Level>

<Level name="Corner cases">

A library that opens and closes the same file silently drops the application's `fcntl` locks; Linux added open file description locks to fix this.

</Level>

<Level name="Production level">

Locks over network file systems are unreliable; distributed coordination needs a proper service.

</Level>

<Level name="Mindset">

Advisory locks are agreements. Make sure every party has signed.

</Level>

<Level name="System design">

SQLite's concurrency is built on file locks, which is why it struggles on network shares.

</Level>

<Level name="Strategy">

I would make a program run as a single instance with `fcntl` locks and test it with a crash. Done when a new instance starts after the old one dies.

</Level>
</Levels>

## Sockets

### 56. Sockets: Introduction
**Covers:** The sockets model, creating sockets, binding addresses, generic address structures, stream sockets, datagram sockets.

<Levels label="Chapter 56, Sockets: Introduction">

<Level name="Beginner">

A socket is an endpoint for communication. A server creates a socket, binds an address, listens and accepts; a client creates one and connects.

</Level>

<Level name="Intermediate">

Stream sockets (TCP) give reliable byte streams over connections; datagram sockets (UDP) send separate messages without connections.

</Level>

<Level name="Advanced">

Addresses are passed through a generic `sockaddr` structure cast from family-specific ones. `accept` returns a new socket per connection while the listening socket keeps listening.

</Level>

<Level name="Edge cases">

Binding to a port in use fails with `EADDRINUSE`, often right after a restart, because old connections linger.

</Level>

<Level name="Corner cases">

A stream socket has no message boundaries: two writes can arrive as one read, or one write as two.

</Level>

<Level name="Production level">

Every server must frame its messages (length prefix or delimiter), because TCP will not.

</Level>

<Level name="Mindset">

A stream is bytes, not messages. Define your own boundaries.

</Level>

<Level name="System design">

Node's `net` module wraps exactly these calls.

</Level>

<Level name="Strategy">

I would write a TCP echo server and client in C and in Node, then break framing by sending two messages quickly. Done when my framed version always splits them right.

</Level>
</Levels>

### 57. Sockets: UNIX Domain
**Covers:** UNIX domain socket addresses, stream and datagram sockets in the UNIX domain, permissions, socketpair, and the Linux abstract namespace.

<Levels label="Chapter 57, Sockets: UNIX Domain">

<Level name="Beginner">

UNIX domain sockets connect processes on the same machine through a path in the file system.

</Level>

<Level name="Intermediate">

They support stream and datagram types, and `socketpair` makes a connected pair for parent and child.

</Level>

<Level name="Advanced">

Permissions on the socket file control who can connect. They can pass file descriptors and credentials between processes. Linux also has an abstract namespace with no file.

</Level>

<Level name="Edge cases">

The socket file stays after the server exits, so the next bind fails until it is removed.

</Level>

<Level name="Corner cases">

Datagram UNIX sockets are reliable and ordered, unlike UDP, which surprises people who assume datagram means lossy.

</Level>

<Level name="Production level">

Docker, PostgreSQL and many local services use UNIX sockets; they are faster than TCP on localhost and permissioned by the file system.

</Level>

<Level name="Mindset">

Local communication deserves a local mechanism.

</Level>

<Level name="System design">

Sidecars and service meshes talk to apps over UNIX sockets.

</Level>

<Level name="Strategy">

I would pass a file descriptor from one process to another over a UNIX socket. Done when the receiver reads a file it never opened.

</Level>
</Levels>

### 58. Sockets: Fundamentals of TCP/IP Networks
**Covers:** Internets, networking protocols and layers, the data-link layer, the network layer (IP), IP addresses, the transport layer, and RFCs.

<Levels label="Chapter 58, Sockets: Fundamentals of TCP/IP Networks">

<Level name="Beginner">

Networks are built in layers: link, network (IP), transport (TCP, UDP) and application.

</Level>

<Level name="Intermediate">

IP delivers packets between hosts by address, without guarantees. TCP adds connections, ordering, reliability and flow control; UDP adds only ports and a checksum.

</Level>

<Level name="Advanced">

Ports pick out the process on a host. Protocols are specified in RFCs, which are the final word on behaviour.

</Level>

<Level name="Edge cases">

IPv4 addresses are scarce, which is why NAT and IPv6 exist.

</Level>

<Level name="Corner cases">

A TCP connection is identified by four values (two addresses, two ports), so one server port serves many clients at once.

</Level>

<Level name="Production level">

Most production network trouble is in the layers below the application: DNS, MTU, firewalls.

</Level>

<Level name="Mindset">

Learn the layers so you know which one to blame.

</Level>

<Level name="System design">

This chapter is the bridge to phase 7, where the networking books go much deeper.

</Level>

<Level name="Strategy">

I would capture a TCP connection with `tcpdump` and label each layer's header. Done when I can name every field I see.

</Level>
</Levels>

### 59. Sockets: Internet Domains
**Covers:** Internet domain sockets, network byte order, data representation, internet socket addresses, host and service conversion, getaddrinfo and getnameinfo, an example client and server, and obsolete APIs.

<Levels label="Chapter 59, Sockets: Internet Domains">

<Level name="Beginner">

Internet sockets use IPv4 or IPv6 addresses and ports. Numbers on the wire use big-endian network byte order.

</Level>

<Level name="Intermediate">

`getaddrinfo` turns a host name and service into a list of addresses to try; `getnameinfo` goes the other way. These replace the old `gethostbyname`.

</Level>

<Level name="Advanced">

A client should try each address `getaddrinfo` returns until one connects, to work over both IPv4 and IPv6. Data sent between machines needs a defined representation, not raw structs.

</Level>

<Level name="Edge cases">

Forgetting `htons` on a port number sends it byte-swapped on little-endian machines.

</Level>

<Level name="Corner cases">

A host with an IPv6 address that does not actually route makes a naive client hang before falling back to IPv4; "happy eyeballs" races the two.

</Level>

<Level name="Production level">

Never send C structs over the network: padding, byte order and sizes differ between machines.

</Level>

<Level name="Mindset">

The wire format is a contract separate from your in-memory format.

</Level>

<Level name="System design">

Serialization formats (JSON, Protocol Buffers) exist to make this contract explicit.

</Level>

<Level name="Strategy">

I would write a client that resolves a name with `getaddrinfo` and connects over IPv4 or IPv6. Done when it works against a dual-stack and an IPv4-only server.

</Level>
</Levels>

### 60. Sockets: Server Design
**Covers:** Iterative and concurrent servers, an iterative UDP echo server, a concurrent TCP echo server, other server designs, and the inetd super-server.

<Levels label="Chapter 60, Sockets: Server Design">

<Level name="Beginner">

An iterative server handles one client at a time; a concurrent server handles many, with a process or thread per client.

</Level>

<Level name="Intermediate">

A concurrent TCP server forks or starts a thread for each accepted connection and keeps accepting.

</Level>

<Level name="Advanced">

Other designs pre-fork or pre-thread a pool, or use one process with multiplexed I/O. `inetd` starts a server per connection on demand.

</Level>

<Level name="Edge cases">

A process per connection cannot handle thousands of connections cheaply.

</Level>

<Level name="Corner cases">

A forking server that does not reap children fills the process table with zombies under load.

</Level>

<Level name="Production level">

Modern servers combine an event loop per core with a pool for blocking work.

</Level>

<Level name="Mindset">

The server design follows from the number of clients and the cost of each.

</Level>

<Level name="System design">

Node is one event loop per process; the `cluster` module or multiple processes use more cores.

</Level>

<Level name="Strategy">

I would write iterative, forking and threaded echo servers and load-test each. Done when I can show where each one stops scaling.

</Level>

### 61. Sockets: Advanced Topics
**Covers:** Partial reads and writes, shutdown, socket-specific I/O calls, sendfile, getting addresses, a closer look at TCP and its states, monitoring sockets with netstat, tcpdump, socket options, SO_REUSEADDR, inherited options, and TCP versus UDP.

<Levels label="Chapter 61, Sockets: Advanced Topics">

<Level name="Beginner">

Socket reads and writes may move fewer bytes than asked, so every I/O must loop.

</Level>

<Level name="Intermediate">

`shutdown` closes one direction of a connection; `sendfile` copies a file to a socket without passing through user space.

</Level>

<Level name="Advanced">

TCP connections move through states (LISTEN, ESTABLISHED, FIN_WAIT, TIME_WAIT and more); `ss` or `netstat` shows them. `SO_REUSEADDR` lets a server rebind while old connections are in TIME_WAIT.

</Level>

<Level name="Edge cases">

Closing a socket with unread data can reset the connection instead of closing it gracefully.

</Level>

<Level name="Corner cases">

The side that closes first enters TIME_WAIT; a client making many short connections can run out of local ports.

</Level>

<Level name="Production level">

Set `SO_REUSEADDR` on listening sockets, set timeouts, and watch connection states during incidents.

</Level>

<Level name="Mindset">

A connection has a life cycle. Know which state it is in.

</Level>

<Level name="System design">

Load balancers, proxies and connection pools are designed around TIME_WAIT and keep-alive.

</Level>

<Level name="Strategy">

I would watch a connection's states with `ss` while opening and closing from each side. Done when I can predict which side ends up in TIME_WAIT.

## Terminals and I/O models

### 62. Terminals
**Covers:** Terminal attributes and special characters, flags, I/O modes, line speed, line control, window size, and identifying terminals.

<Levels label="Chapter 62, Terminals">

<Level name="Beginner">

A terminal driver sits between the keyboard and a program, handling line editing, echo and special keys like Ctrl-C.

</Level>

<Level name="Intermediate">

In canonical mode input arrives a line at a time with editing; in noncanonical (raw) mode each key arrives at once. `tcgetattr` and `tcsetattr` change the mode.

</Level>

<Level name="Advanced">

Special characters (interrupt, end of file, erase) are configurable. Programs like editors switch to raw mode and must restore it on exit.

</Level>

<Level name="Edge cases">

A program that crashes in raw mode leaves the terminal unusable until `reset`.

</Level>

<Level name="Corner cases">

Window-size changes arrive as SIGWINCH, which interrupts blocking reads.

</Level>

<Level name="Production level">

Command-line tools should check `isatty` to decide on colour and prompts, and behave plainly when piped.

</Level>

<Level name="Mindset">

A terminal is a device with its own rules, not just a text stream.

</Level>

<Level name="System design">

Interactive CLIs in Node use raw mode through the same driver.

</Level>

<Level name="Strategy">

I would write a tiny program that reads keys in raw mode and restores the terminal on every exit path. Done when Ctrl-C and a crash both leave my terminal working.

### 63. Alternative I/O Models
**Covers:** Nonblocking I/O, I/O multiplexing with select and poll, signal-driven I/O, the epoll API, waiting on signals and descriptors together, and when each model fits.

<Levels label="Chapter 63, Alternative I/O Models">

<Level name="Beginner">

Blocking I/O waits for one descriptor at a time. To serve many connections, a program needs to know which descriptors are ready.

</Level>

<Level name="Intermediate">

`select` and `poll` take a list of descriptors and report which are ready; `epoll` keeps the list in the kernel and scales to many descriptors.

</Level>

<Level name="Advanced">

Readiness can be level-triggered (reported while ready) or edge-triggered (reported once per change). Edge-triggered use requires nonblocking descriptors and reading until `EAGAIN`.

</Level>

<Level name="Edge cases">

`select` has a fixed maximum descriptor number, which a busy server can exceed.

</Level>

<Level name="Corner cases">

Edge-triggered with a partial read leaves data unread and never reported again, so the connection stalls.

</Level>

<Level name="Production level">

Every high-performance Linux server, including Node's libuv, Nginx and Redis, is built on epoll.

</Level>

<Level name="Mindset">

Ask "what is ready" instead of waiting on one thing.

</Level>

<Level name="System design">

The event loop is the core of Node; this chapter is how it works underneath.

</Level>

<Level name="Strategy">

I would write an epoll echo server in level-triggered then edge-triggered mode. Done when the edge-triggered version handles large messages without stalling.

</Level>

## Misreadings to avoid

- "A short read means an error." It means fewer bytes were ready. Loop until done or until read returns 0.
- "`write` means it is on disk." It means the kernel has it; `fsync` and the device decide the rest.
- "Signals are a messaging system." Standard signals are not queued and carry no data; use a pipe or socket for messages.
- "A thread-safe function is safe in a signal handler." Thread-safe and async-signal-safe are different promises.
- "UNIX file locks protect a file." They are advisory; a program that ignores them is not stopped.
- "TCP sends my messages." TCP sends bytes; message boundaries are mine to add.
