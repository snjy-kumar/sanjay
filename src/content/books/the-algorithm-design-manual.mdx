## Why this book

This is the primary book for <a href={withBase('/plans/traditional-software-developer/#strategy-4')}>phase 4, algorithms</a>.
The plan says algorithms are ways of turning a problem into a smaller one,
and that is what Skiena's book is about. Part I teaches design: how to model
a problem, analyse it, and pick a technique. Part II, the Hitchhiker's Guide
to Algorithms, is a catalogue of about seventy-five classic problems, each
with what to do when you meet it in practice. I use Part I to learn and Part
II to look things up for the rest of my working life.

The chapter list below follows Springer's table of contents for the third
edition. Section topics are described in my own words. The book's code is in
C; my examples are TypeScript, the phase's language.

## How I would learn it

I would read the war stories first in each chapter. They are where Skiena
shows the design process going wrong and then right on a real problem, and
they make the technique memorable. Then the technique sections, then the
exercises.

For the 30–40 problems the plan asks for, I would pick them by chapter:
five for divide and conquer, five for graphs, eight for DP, and so on. For
each I write the plan's four lines (the state, the invariant, the
complexity, one alternative) before the code. If a problem takes more than
an hour, I look at the catalogue entry for its model, not the solution.

The catalogue I would treat like documentation. Every time a later phase
raises a problem (a scheduler in phase 6, routing in phase 7, an index in
phase 8), I look it up and note the entry in that phase's README.

## Part I — Practical Algorithm Design

### 1. Introduction to Algorithm Design

**Covers:** What an algorithm is (a procedure that is correct for every instance), why
"obvious" heuristics fail, with a robot tour and a job-selection problem,
reasoning about correctness, demonstrating incorrectness with a
counterexample, induction and recursion, modelling a problem with standard
combinatorial objects, proof by contradiction, and estimation.

<Levels label="Chapter 1, Introduction to Algorithm Design">

<Level name="Beginner">


An algorithm must be correct on every input, not on the examples I tried. A
heuristic that works on the examples is not an algorithm until it is proved.


</Level>
<Level name="Intermediate">


The job-selection problem is the key example: given intervals, choose as many
non-overlapping ones as possible. "Shortest first" and "earliest start
first" both fail on small counterexamples; "earliest finish first" is
correct.

```ts
function maxJobs(jobs: [start: number, end: number][]): number {
  let count = 0, lastEnd = -Infinity;
  for (const [s, e] of [...jobs].sort((a, b) => a[1] - b[1])) {
    if (s >= lastEnd) { count++; lastEnd = e; }
  }
  return count;
}
```


</Level>
<Level name="Advanced">


Modelling is the advanced skill: most problems are a permutation, a subset,
a tree, a graph, a set of points, a polygon or a string in disguise. Naming
the object points straight to the catalogue in Part II. Induction proves
recursive algorithms correct; contradiction proves that something cannot
exist.


</Level>
<Level name="Edge cases">


- Intervals that touch (one ends at 5, the next starts at 5): decide whether
  that counts as overlap, and use `>=` or `>` to match.
- Zero jobs, one job, and every job identical.


</Level>
<Level name="Corner cases">


- A good counterexample is small and specific. If I cannot find one with
  three or four items, I try the extremes: all equal, all nested, all
  disjoint.


</Level>
<Level name="Production level">


Most production "algorithms" are heuristics nobody proved. The habit from
this chapter is to know which ones they are, and to write a test with the
counterexample that would break them.


</Level>
<Level name="Mindset">


Hunting for counterexamples is the core mindset. Before trusting a greedy
idea, I spend five minutes trying to break it.


</Level>
<Level name="System design">


Estimation (the chapter's last section) is the back-of-the-envelope skill
behind capacity planning: how many requests, how many bytes, how long.


</Level>
<Level name="Strategy">


For every new problem in the phase, write the model first ("this is a set of
intervals"), then attempt a counterexample to the first idea. Keep a page of
counterexamples I have found.


Done when I have a written counterexample for two plausible but wrong job-selection rules.

</Level>

</Levels>

### 2. Algorithm Analysis

**Covers:** The RAM model, best, worst and average case, Big-O, growth rates and
dominance, adding and multiplying functions, reasoning about selection sort,
insertion sort, string matching and matrix multiplication, summations,
logarithms and their uses (binary search, trees, bits, fast exponentiation),
and some advanced analysis.

<Levels label="Chapter 2, Algorithm Analysis">

<Level name="Beginner">


The RAM model counts simple operations as one step each. Big-O keeps the
fastest-growing term and drops constants. The usual ladder is 1, log n, n,
n log n, n², 2ⁿ, n!.


</Level>
<Level name="Intermediate">


Logarithms appear whenever something halves: binary search, the height of a
balanced tree, the number of bits in n. Fast exponentiation squares instead
of multiplying n times:

```ts
function power(a: bigint, n: bigint, mod: bigint): bigint {
  let result = 1n;
  for (a %= mod; n > 0n; n >>= 1n, a = (a * a) % mod) if (n & 1n) result = (result * a) % mod;
  return result;
}
```


</Level>
<Level name="Advanced">


Dominance is about limits: f dominates g when g/f goes to zero. Summations
turn loops into formulas: a loop of i from 1 to n doing i work is about
n²/2. Average-case analysis needs a distribution; worst case needs a proof
that no input is worse.


</Level>
<Level name="Edge cases">


- `n = 0` and `n = 1` in every formula.
- BigInt is needed for modular exponentiation with large moduli in
  JavaScript, because `number` loses precision past 2^53.


</Level>
<Level name="Corner cases">


- A string-matching loop that compares up to m characters at each of n
  positions is O(nm), even though most comparisons stop early in practice.


</Level>
<Level name="Production level">


Knowing the ladder lets me reject designs early: anything exponential in a
user-controlled number is a denial-of-service risk.


</Level>
<Level name="Mindset">


Analyse before running. If the analysis and the benchmark disagree, one of
them is wrong, and finding which is the lesson.


</Level>
<Level name="System design">


The ladder maps to real limits: about 10⁸ simple operations per second on
one core is a useful rough number for deciding what n a design can handle.


</Level>
<Level name="Strategy">


Do the chapter's exercises on ordering functions by growth. Write fast
exponentiation and binary search from memory.


Done when I can sort a list of ten functions by growth without notes and my fast exponentiation matches BigInt `**` on random inputs.

</Level>

</Levels>

### 3. Data Structures

**Covers:** Contiguous versus linked structures, stacks and queues, dictionaries, binary
search trees and balance, priority queues, hashing (collisions, duplicate
detection, other tricks, canonicalisation, compaction), and specialised
structures.

<Levels label="Chapter 3, Data Structures">

<Level name="Beginner">


Contiguous (arrays) or linked (pointers) is the first choice for any
structure. Arrays are compact and cache-friendly; linked structures grow and
splice without copying.


</Level>
<Level name="Intermediate">


Canonicalisation is a hashing trick worth stealing: to group anagrams, hash
the sorted letters, so "listen" and "silent" share a key.

```ts
const groups = new Map<string, string[]>();
for (const w of words) {
  const key = [...w].sort().join('');
  groups.set(key, [...(groups.get(key) ?? []), w]);
}
```


</Level>
<Level name="Advanced">


The chapter frames choices as dictionary operations (search, insert, delete,
min, max, successor, predecessor) and shows each structure's costs for each.
Specialised structures (strings, geometry, graphs, sets) are previewed for
Part II.


</Level>
<Level name="Edge cases">


- Duplicate detection with a hash can produce false matches if I store only
  the hash; keep the value to confirm.


</Level>
<Level name="Corner cases">


- Canonical forms must really be canonical: "Listen" and "silent" differ by
  case unless the key lower-cases first.


</Level>
<Level name="Production level">


Deduplication by content hash is how backups, Git and CDNs save storage.
Compaction (storing a big string once and referencing it) is how interning
saves memory.


</Level>
<Level name="Mindset">


A data structure choice is a table of operations and costs. I fill in the
table before choosing.


</Level>
<Level name="System design">


Content-addressed storage (Git's object store) is hashing as a system design.


</Level>
<Level name="Strategy">


Connect this chapter to the phase 3 library: for each structure I built,
fill in the dictionary-operations table.


Done when every structure in my phase 3 README has a filled-in operations table.

</Level>

</Levels>

### 4. Sorting

**Covers:** Applications of sorting, the pragmatics (order, keys, comparison functions),
heapsort through heaps, mergesort, quicksort and randomisation, distribution
sort through bucketing, and lower bounds.

<Levels label="Chapter 4, Sorting">

<Level name="Beginner">


Sorting turns many problems into easy ones: once sorted, duplicates are
adjacent, the median is in the middle, and binary search works.


</Level>
<Level name="Intermediate">


Use sorting as a preprocessing step: closest pair in one dimension, finding
whether two sets intersect, the mode, the convex hull. The pragmatics matter:
ascending or descending, which field is the key, what to do on ties.


</Level>
<Level name="Advanced">


Randomised quicksort's expected cost is O(n log n) for every input, because
the randomness is in the algorithm, not the data. Bucketing beats the
comparison lower bound when the key distribution is known and roughly
uniform.


</Level>
<Level name="Edge cases">


- Bucket sort on a skewed distribution puts everything in one bucket and
  degrades to its inner sort.


</Level>
<Level name="Corner cases">


- Sorting objects by a key computed from them (such as a lower-cased name)
  recomputes the key on every comparison unless I precompute it.


</Level>
<Level name="Production level">


"Sort, then scan" is often the simplest correct solution and fast enough.
The library sort is almost always right.


</Level>
<Level name="Mindset">


When a problem feels hard, ask whether it is easy on sorted input.


</Level>
<Level name="System design">


Sort-merge joins in databases and sorted string tables in storage engines are
this chapter at scale.


</Level>
<Level name="Strategy">


Solve five problems with "sort first" as the key idea. Add bucket sort to the
sorting benchmark with uniform and skewed inputs.


Done when I have solved five problems where sorting first was the key idea, and the benchmark shows bucket sort degrading on skewed input.

</Level>

</Levels>

### 5. Divide and Conquer

**Covers:** Binary search and variants (counting occurrences, one-sided search, roots),
recurrence relations and how to solve divide-and-conquer recurrences, fast
multiplication, largest subrange and closest pair, parallel algorithms and
their pitfalls, and convolution.

<Levels label="Chapter 5, Divide and Conquer">

<Level name="Beginner">


Binary search halves the range each step. The variants the plan names,
lower bound and upper bound, find the first position where a key could go
and the first position past it.

```ts
function lowerBound(a: number[], x: number): number {
  let lo = 0, hi = a.length; // answer is in [lo, hi]
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (a[mid] < x) lo = mid + 1; else hi = mid;
  }
  return lo;
}
// count of x = upperBound(a, x) - lowerBound(a, x)
```


</Level>
<Level name="Intermediate">


One-sided binary search finds a boundary in an unbounded sequence by
doubling until it overshoots, then searching back. Binary search on the
answer works for any monotone yes-or-no question: "can I ship all packages
in D days with capacity C?"


</Level>
<Level name="Advanced">


The master theorem solves T(n) = aT(n/b) + f(n) by comparing f(n) with
n^(log_b a). Karatsuba multiplication uses three recursive multiplications
instead of four, giving about n^1.585. Convolution via the FFT multiplies
polynomials in n log n.


</Level>
<Level name="Edge cases">


- `(lo + hi) / 2` overflows in fixed-width integers; `lo + (hi - lo) / 2`
  does not.
- Empty array, all elements equal, the target smaller than everything or
  larger than everything.


</Level>
<Level name="Corner cases">


- An off-by-one loop condition (`lo <= hi` with `hi = mid`) loops forever.
  Pick one invariant (half-open or closed) and keep it everywhere.


</Level>
<Level name="Production level">


`git bisect` is binary search over history. Binary search on the answer
appears in capacity planning and in tuning a parameter against a test.


</Level>
<Level name="Mindset">


Write the invariant first ("the answer is in [lo, hi)"), then the code
follows. Most binary search bugs are an unstated invariant.


</Level>
<Level name="System design">


Parallel divide and conquer (map, then reduce) is how batch data systems
work. The pitfalls section is the reminder that splitting work has overhead.


</Level>
<Level name="Strategy">


Implement lower bound, upper bound and binary search on the answer, and test
them against a linear scan on random arrays with duplicates.


Done when lower and upper bound pass a property test against a linear scan on arrays full of duplicates.

</Level>

</Levels>

### 6. Hashing and Randomized Algorithms

**Covers:** A probability review, balls and bins and the coupon collector, why hashing
is a randomised algorithm, Bloom filters, the birthday paradox and perfect
hashing, minwise hashing, efficient string matching, primality testing, and
where random numbers come from.

<Levels label="Chapter 6, Hashing and Randomized Algorithms">

<Level name="Beginner">


A randomised algorithm uses coin flips. A Las Vegas algorithm is always
correct and its time is random (randomised quicksort). A Monte Carlo
algorithm has bounded time and may be wrong with small probability (a
primality test).


</Level>
<Level name="Intermediate">


A Bloom filter answers "definitely not in the set" or "probably in the set"
with a bit array and k hash functions. Reservoir sampling, from the plan,
keeps a uniform random sample of k items from a stream of unknown length:

```ts
function reservoir<T>(stream: Iterable<T>, k: number): T[] {
  const sample: T[] = []; let i = 0;
  for (const x of stream) {
    if (i < k) sample.push(x);
    else { const j = Math.floor(Math.random() * (i + 1)); if (j < k) sample[j] = x; }
    i++;
  }
  return sample;
}
```


</Level>
<Level name="Advanced">


Balls and bins explains hash table behaviour: with n keys in n slots, the
fullest slot has about log n / log log n keys. The coupon collector needs
about n ln n draws to see all n values. The birthday paradox says collisions
appear after about the square root of the table size. Minwise hashing
estimates the similarity of two sets from small signatures.


</Level>
<Level name="Edge cases">


- A Bloom filter cannot delete without counters; removing bits breaks other
  keys.
- Reservoir sampling with k greater than the stream length returns the whole
  stream.


</Level>
<Level name="Corner cases">


- `Math.random()` is not cryptographically secure. Tokens and keys need
  `crypto.getRandomValues`.
- A Bloom filter's false-positive rate rises past its design as it fills;
  size it for the final count.


</Level>
<Level name="Production level">


Bloom filters skip disk reads in storage engines, minhash finds near-duplicate
documents, and the birthday bound is why IDs need enough random bits.


</Level>
<Level name="Mindset">


Randomness is a tool for beating adversaries and for summarising data too
big to keep. The question is always which kind of failure I can tolerate.


</Level>
<Level name="System design">


Probabilistic structures trade exactness for memory: Bloom filters,
HyperLogLog, count-min sketches. Each is a decision about acceptable error.


</Level>
<Level name="Strategy">


Implement a Bloom filter and measure its false-positive rate against the
formula. Implement reservoir sampling and check uniformity with a
simulation, which connects back to phase 2's probability.


Done when my measured false-positive rate is within a few percent of the formula and the reservoir sample passes a uniformity check.

</Level>

</Levels>

### 7. Graph Traversal

**Covers:** Flavours of graphs, data structures for graphs, breadth-first search and its
applications (connected components, two-colouring), depth-first search and
its applications (cycles, articulation vertices), DFS on directed graphs,
topological sorting and strongly connected components, with war stories.

<Levels label="Chapter 7, Graph Traversal">

<Level name="Beginner">


Graphs can be undirected or directed, weighted or not, simple or with
multi-edges, sparse or dense, explicit or implicit. Naming the flavour comes
first.


</Level>
<Level name="Intermediate">


Two-colouring with BFS tests bipartiteness: colour the start, colour each
neighbour the opposite, and fail on an edge between same colours. DFS edge
types (tree, back, forward, cross) are what make cycle detection and
topological sort work: a back edge means a cycle.


</Level>
<Level name="Advanced">


Articulation vertices come from DFS by tracking, for each vertex, the
earliest ancestor its subtree can reach by one back edge. Strongly connected
components need either two DFS passes or Tarjan's single pass with a stack.


</Level>
<Level name="Edge cases">


- Implicit graphs (game states, word ladders) are generated on the fly; the
  visited set is the memory cost.
- Disconnected graphs need an outer loop over all vertices.


</Level>
<Level name="Corner cases">


- A recursive DFS on a deep graph overflows the stack in JavaScript; convert
  to an explicit stack early.
- Undirected DFS must not treat the edge back to the parent as a cycle.


</Level>
<Level name="Production level">


Crawlers are BFS, dependency resolvers are DFS with cycle detection, and
garbage collectors are graph traversal from roots.


</Level>
<Level name="Mindset">


BFS and DFS are not two algorithms to memorise; they are the two orders in
which to explore, and most graph algorithms are one of them plus a little
bookkeeping.


</Level>
<Level name="System design">


A web crawler's frontier is a BFS queue with politeness rules; its visited
set becomes a distributed problem at scale.


</Level>
<Level name="Strategy">


Implement BFS, iterative DFS with entry and exit times, bipartiteness,
topological sort and Tarjan's SCC. Solve one implicit-graph problem, such as
a word ladder.


Done when iterative DFS handles a 100,000-vertex path without a stack overflow and my SCCs match a brute-force reachability check.

</Level>

</Levels>

### 8. Weighted Graph Algorithms

**Covers:** Minimum spanning trees (Prim, Kruskal with union–find, variations), shortest
paths (Dijkstra and all-pairs), network flows and bipartite matching,
randomised min-cut, and designing graphs rather than algorithms.

<Levels label="Chapter 8, Weighted Graph Algorithms">

<Level name="Beginner">


Dijkstra finds shortest paths from one source when weights are non-negative,
always expanding the closest unfinished vertex.


</Level>
<Level name="Intermediate">


```ts
function dijkstra(adj: [to: number, w: number][][], s: number): number[] {
  const dist = new Array(adj.length).fill(Infinity); dist[s] = 0;
  const pq: [number, number][] = [[0, s]]; // use a real heap in practice
  while (pq.length) {
    pq.sort((a, b) => a[0] - b[0]);
    const [d, v] = pq.shift()!;
    if (d > dist[v]) continue; // stale entry: lazy deletion
    for (const [w, c] of adj[v]) if (d + c < dist[w]) { dist[w] = d + c; pq.push([dist[w], w]); }
  }
  return dist;
}
```

The sort-based queue keeps the example short; the phase 3 heap makes it
O((V + E) log V).


</Level>
<Level name="Advanced">


Floyd–Warshall computes all pairs in V³ with three nested loops over an
intermediate vertex. Network flow models many assignment problems;
bipartite matching is flow with unit capacities. The chapter's lesson
"design graphs, not algorithms" means building the right graph so a standard
algorithm solves the problem.


</Level>
<Level name="Edge cases">


- Unreachable vertices keep distance Infinity; the caller must handle it.
- Floyd–Warshall detects a negative cycle when a diagonal entry goes
  negative.


</Level>
<Level name="Corner cases">


- A* (from the plan) is Dijkstra with a heuristic; it is correct only if the
  heuristic never overestimates the remaining distance.
- Bellman–Ford is needed for negative edges; Dijkstra silently gives wrong
  answers.


</Level>
<Level name="Production level">


Routing, network design and assignment all reduce to this chapter. Real
route planners precompute (contraction hierarchies) because per-query
Dijkstra is too slow at continental scale.


</Level>
<Level name="Mindset">


The modelling trick is the important one: if I can turn the problem into a
graph with the right weights, the algorithm is already written.


</Level>
<Level name="System design">


Matching riders to drivers or tasks to workers is bipartite matching or
min-cost flow, usually solved approximately and in batches.


</Level>
<Level name="Strategy">


Implement Dijkstra with my heap, Bellman–Ford, Floyd–Warshall, Prim and
Kruskal, then build the plan's route planner with Dijkstra and A* on a grid
and compare nodes expanded.


Done when Dijkstra, Bellman–Ford and Floyd–Warshall agree on random non-negative graphs and A* expands fewer nodes than Dijkstra on the grid.

</Level>

</Levels>

### 9. Combinatorial Search

**Covers:** Backtracking, search-space pruning, sudoku, war stories on covering
chessboards, best-first search, and the A* heuristic.

<Levels label="Chapter 9, Combinatorial Search">

<Level name="Beginner">


Backtracking builds a solution one choice at a time and undoes the last
choice when it leads nowhere. Generating all subsets or permutations is the
basic form.


</Level>
<Level name="Intermediate">


```ts
function permutations<T>(items: T[]): T[][] {
  const out: T[][] = [], used = new Array(items.length).fill(false), cur: T[] = [];
  const go = () => {
    if (cur.length === items.length) { out.push([...cur]); return; }
    for (let i = 0; i < items.length; i++) if (!used[i]) {
      used[i] = true; cur.push(items[i]); go(); cur.pop(); used[i] = false;
    }
  };
  go(); return out;
}
```


</Level>
<Level name="Advanced">


Pruning is what makes backtracking usable: cut a branch as soon as it cannot
lead to a solution (or a better one). For sudoku, choosing the most
constrained square next is far faster than going in order. Best-first and A*
order the search by an estimate of how promising each state is.


</Level>
<Level name="Edge cases">


- Duplicates in the input give duplicate permutations unless I skip equal
  items at the same depth.


</Level>
<Level name="Corner cases">


- Forgetting to copy `cur` when recording a solution records a reference
  that is later emptied.


</Level>
<Level name="Production level">


Constraint solvers, schedulers and configuration tools use backtracking with
heavy pruning, or hand the problem to a SAT or constraint solver.


</Level>
<Level name="Mindset">


Exponential search is fine when the search space is small or the pruning is
strong. Measure the nodes visited.


</Level>
<Level name="System design">


When a product needs "find a valid schedule", the design choice is between a
hand-written search, a solver library, and a heuristic that is good enough.


</Level>
<Level name="Strategy">


Write subsets, permutations and an n-queens solver; then a sudoku solver,
first naive and then most-constrained-first, and count nodes visited in each.


Done when the most-constrained-first sudoku solver visits far fewer nodes than the naive one on the same puzzles, with the counts written down.

</Level>

</Levels>

### 10. Dynamic Programming

**Covers:** Caching versus computation, approximate string matching (edit distance),
longest increasing subsequence, the partition problem, parsing context-free
grammars, the limits of dynamic programming, and war stories.

<Levels label="Chapter 10, Dynamic Programming">

<Level name="Beginner">


Dynamic programming is recursion plus a table. The plan's rule is to define
the state before writing the recurrence: what exactly does `dp[i][j]` mean?


</Level>
<Level name="Intermediate">


Edit distance: `dp[i][j]` is the cost of turning the first `i` characters of
`a` into the first `j` characters of `b`.

```ts
function editDistance(a: string, b: string): number {
  const dp = Array.from({ length: a.length + 1 }, (_, i) => [i, ...new Array(b.length).fill(0)]);
  for (let j = 1; j <= b.length; j++) dp[0][j] = j;
  for (let i = 1; i <= a.length; i++)
    for (let j = 1; j <= b.length; j++)
      dp[i][j] = Math.min(
        dp[i - 1][j] + 1,                                  // delete
        dp[i][j - 1] + 1,                                  // insert
        dp[i - 1][j - 1] + (a[i - 1] === b[j - 1] ? 0 : 1), // match or substitute
      );
  return dp[a.length][b.length];
}
```


</Level>
<Level name="Advanced">


A problem suits DP when it has optimal substructure and overlapping
subproblems, and when the subproblems can be ordered (left to right, by
length, by subset). The limits section matters: DP needs a small number of
states, and the state must not depend on the path taken. Reconstructing the
solution, not just its cost, needs a parent table or a backward walk.


</Level>
<Level name="Edge cases">


- Empty strings: edit distance to "" is the other string's length.
- Longest increasing subsequence: strict or non-strict changes the
  comparison and the answer.


</Level>
<Level name="Corner cases">


- Memory: a 10,000 by 10,000 table of numbers is hundreds of megabytes. Keep
  two rows when only the cost is needed.
- Bitmask DP (from the plan) is only possible up to about 20 items, because
  the state space is 2ⁿ.


</Level>
<Level name="Production level">


Diff tools, spell checkers, DNA alignment and text layout (line breaking)
are DP. The plan's diff tool uses LCS, a sibling of edit distance.


</Level>
<Level name="Mindset">


The hard part is the state, not the code. If I cannot say in one sentence
what a table cell means, I am not ready to write the recurrence.


</Level>
<Level name="System design">


DP often becomes a precomputed table in a system: a cost matrix, a cached
route, a pricing grid. Its size is the design constraint.


</Level>
<Level name="Strategy">


For each DP problem in my 30–40, write the state sentence, the recurrence,
the base cases, the order of evaluation and the complexity before code. Do
knapsack, LCS, edit distance, LIS, an interval DP and a bitmask DP.


Done when I have written the state sentence and recurrence for six DP problems before coding them, and each passes against a brute force on small inputs.

</Level>

</Levels>

### 11. NP-Completeness

**Covers:** Problems and reductions, elementary reductions, satisfiability, creative
reductions, the art of proving hardness, P versus NP, and war stories.

<Levels label="Chapter 11, NP-Completeness">

<Level name="Beginner">


A reduction turns problem A into problem B, so a fast algorithm for B gives
one for A. NP-complete problems are those every NP problem reduces to; no
polynomial algorithm is known for any of them.


</Level>
<Level name="Intermediate">


The direction matters: to show my problem is hard, I reduce a known hard
problem (3-SAT, vertex cover, Hamiltonian cycle) to mine. Showing mine
reduces to a hard one proves nothing about mine.


</Level>
<Level name="Advanced">


The chapter builds a family tree of reductions from satisfiability. The art
of proving hardness is picking the right source problem and building gadgets
that translate its structure.


</Level>
<Level name="Edge cases">


- Special cases of NP-complete problems are often easy: 2-SAT is
  polynomial, vertex cover on trees is linear.


</Level>
<Level name="Corner cases">


- Pseudo-polynomial algorithms (knapsack in n times W) are fast only when
  the numbers are small; they do not contradict NP-hardness.


</Level>
<Level name="Production level">


Recognising hardness saves weeks. If the problem is NP-hard, I reach for
approximation, heuristics, small sizes or a solver.


</Level>
<Level name="Mindset">


"Knowing when to stop looking for an exact polynomial algorithm", in the
plan's words, is a professional skill.


</Level>
<Level name="System design">


Scheduling, packing, routing with constraints and test-set minimisation are
usually NP-hard in their exact form; the design picks a tractable version.


</Level>
<Level name="Strategy">


Do three reductions by hand: 3-SAT to vertex cover, vertex cover to
independent set, Hamiltonian cycle to travelling salesperson.


Done when I can explain each of the three reductions on paper, in the right direction, without notes.

</Level>

</Levels>

### 12. Dealing with Hard Problems

**Covers:** Approximation algorithms (vertex cover, Euclidean TSP, maximum acyclic
subgraph, set cover), heuristic search (random sampling, local search,
simulated annealing, genetic algorithms), war stories, and quantum
computing.

<Levels label="Chapter 12, Dealing with Hard Problems">

<Level name="Beginner">


When exact is too slow, accept a guaranteed approximation or a good
heuristic. A 2-approximation for vertex cover: take both ends of any
uncovered edge until none is left.


</Level>
<Level name="Intermediate">


Local search starts from a solution and makes small improving changes (swap
two cities in a tour). Simulated annealing sometimes accepts worse moves,
with a probability that falls over time, to escape local optima.


</Level>
<Level name="Advanced">


Approximation guarantees are proofs of a ratio to the optimum; heuristics
have no guarantee but often do better in practice. Greedy set cover achieves
a logarithmic ratio, which is essentially the best possible unless P = NP.


</Level>
<Level name="Edge cases">


- Simulated annealing with too fast a cooling schedule becomes plain local
  search.


</Level>
<Level name="Corner cases">


- A heuristic tuned on one input distribution can be poor on another.
  Benchmark on the real one.


</Level>
<Level name="Production level">


Delivery routing, container placement and ad allocation run heuristics with
monitoring of solution quality, not exact algorithms.


</Level>
<Level name="Mindset">


Good enough, measured, beats perfect, unfinished.


</Level>
<Level name="System design">


A system with a heuristic at its core needs a quality metric and a fallback,
because the heuristic will sometimes be bad.


</Level>
<Level name="Strategy">


Implement the vertex-cover 2-approximation, greedy set cover, and simulated
annealing for TSP on random points; plot tour length against iterations.


Done when my annealed tours are measurably shorter than the greedy start on random points.

</Level>

</Levels>

## Misreadings to avoid

- "The catalogue is for reading." Part II is for looking things up when a
  project raises a problem. Reading it cover to cover teaches little.
- "If a greedy rule works on my examples, it is correct." Chapter 1's lesson
  is that plausible heuristics fail; find a counterexample or a proof.
- "Dynamic programming is memoisation." Memoisation is one way to evaluate a
  recurrence. The work is defining the state and the recurrence.
- "NP-complete means impossible." It means no known polynomial algorithm for
  every input. Small inputs, special structure, heuristics and approximation
  often work well.
- "Big-O is the whole story." The book stresses constant factors and real
  inputs; a linear scan over a small array beats a clever structure.
- "War stories are anecdotes." They are worked examples of modelling, which is
  the skill the book is really about.
