## Why this book

This is the primary book for <a href={withBase('/plans/traditional-software-developer/#strategy-4')}>phase 4, algorithms</a>.
The plan says algorithms are ways of turning a problem into a smaller one,
and that is what Skiena's book is about. Part I teaches design: how to model
a problem, analyse it, and pick a technique. Part II, the Hitchhiker's Guide
to Algorithms, is a catalogue of about seventy-five classic problems, each
with what to do when you meet it in practice. I use Part I to learn and Part
II to look things up for the rest of my working life.

The chapter list follows Springer's table of contents for the third edition,
and the section headings on each chapter page follow the book's printed
contents. Each chapter has its own page, written in my own words with my own
examples. The book's code is in C; mine is TypeScript, the phase's language,
run in Node.

## How I would learn it

I would read the war stories first in each chapter. They are where Skiena
shows the design process going wrong and then right on a real problem, and
they make the technique memorable. Then the technique sections, then the
exercises.

For the 30–40 problems the plan asks for, I would pick them by chapter:
five for divide and conquer, five for graphs, eight for DP, and so on. For
each I write the plan's four lines (the state, the invariant, the
complexity, one alternative) before the code. If a problem takes more than
an hour, I look at the catalogue entry for its model, not the solution.

The catalogue I would treat like documentation. Every time a later phase
raises a problem (a scheduler in phase 6, routing in phase 7, an index in
phase 8), I look it up and note the entry in that phase's README.

## What I learn from it

Chapter by chapter, one line each. Each line is what I should be able to do
after that chapter's page.

- [ ] **1. Introduction to Algorithm Design:** break a plausible heuristic with a minimal counterexample, prove a greedy rule by exchange, model a problem as a standard object, and estimate.
- [ ] **2. Algorithm Analysis:** use the RAM model and Big Oh, order functions by growth, analyse loops with summations, and use logarithms (binary search, trees, fast exponentiation).
- [ ] **3. Data Structures:** choose between contiguous and linked structures, implement stacks, queues, dictionaries, binary search trees and priority queues, and use hashing tricks such as canonicalisation.
- [ ] **4. Sorting:** use sorting as a tool, write heapsort, mergesort and quicksort, explain randomisation and bucketing, and the comparison lower bound.
- [ ] **5. Divide and Conquer:** write binary search variants, solve divide-and-conquer recurrences, and use fast multiplication, closest pair and convolution.
- [ ] **6. Hashing and Randomized Algorithms:** reason with probability, balls and bins and the birthday paradox, and build Bloom filters, minhash, string hashing and primality tests.
- [ ] **7. Graph Traversal:** represent graphs, run BFS and DFS, and use them for components, two-colouring, cycles, articulation vertices, topological sort and strongly connected components.
- [ ] **8. Weighted Graph Algorithms:** build minimum spanning trees with union–find, shortest paths, network flow and matching, and design graphs instead of algorithms.
- [ ] **9. Combinatorial Search:** write backtracking with pruning, solve sudoku, and use best-first search and A*.
- [ ] **10. Dynamic Programming:** define a state, write the recurrence, and solve edit distance, LIS, partition and parsing problems, knowing when DP is correct and efficient.
- [ ] **11. NP-Completeness:** do reductions in the right direction, and recognise satisfiability, vertex cover, clique and Hamiltonian cycle as hard.
- [ ] **12. Dealing with Hard Problems:** use approximation algorithms, local search and simulated annealing, and know what quantum computing does and does not change.
- [ ] **13. How to Design Algorithms:** use the design checklist on a new problem.
- [ ] **14–22. The Hitchhiker's Guide:** look up a problem in the catalogue, recognise its entry, and find a well-maintained implementation.

## Misreadings to avoid

- "The catalogue is for reading." Part II is for looking things up when a
  project raises a problem. Reading it cover to cover teaches little.
- "If a greedy rule works on my examples, it is correct." Chapter 1's lesson
  is that plausible heuristics fail; find a counterexample or a proof.
- "Dynamic programming is memoisation." Memoisation is one way to evaluate a
  recurrence. The work is defining the state and the recurrence.
- "NP-complete means impossible." It means no known polynomial algorithm for
  every input. Small inputs, special structure, heuristics and approximation
  often work well.
- "Big-O is the whole story." The book stresses constant factors and real
  inputs; a linear scan over a small array beats a clever structure.
- "War stories are anecdotes." They are worked examples of modelling, which is
  the skill the book is really about.

## Done with this book when

- I have solved 30 to 40 problems across sorting, search, greedy, DP and
  graphs, and for each I wrote the model before the code.
- My phase 4 builds work: the sorting benchmark, the Dijkstra and A* route
  planner, the LCS diff, the greedy and DP scheduler, and the KMP and trie
  search.
- For a new problem I can name its catalogue entry, a technique, and a
  counterexample to the first greedy idea that comes to mind.
- I can explain to someone else why a problem is NP-hard by a reduction in
  the right direction, and what I would do about it in practice.
