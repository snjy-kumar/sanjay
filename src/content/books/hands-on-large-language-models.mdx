## Part I, Understanding Language Models

### 1. An Introduction to Large Language Models

**Covers:** What language AI is and its recent history (bag-of-words, dense embeddings, attention, encoder-only and decoder-only transformers), what "large" means, how LLMs are trained, what they are useful for, responsible use, running with limited resources, proprietary versus open models, and generating a first piece of text.

  { when: 'the transformer', what: 'Attention only, in parallel; scales with data and compute.' },

<Levels label="Chapter 1, An Introduction to Large Language Models">

<Level name="Beginner">

Language AI is software that understands or produces language. Early methods
counted words (bag-of-words), which ignores order and meaning. Embeddings
represent each word as a vector so similar words sit close together. Attention
lets a model weigh which other words matter for each word. The transformer is
built entirely on attention, and from it come two families: representation
models that turn text into vectors (encoder-only, like BERT), and generative
models that continue text (decoder-only, like GPT).

```py
from transformers import pipeline
gen = pipeline("text-generation", model="a-small-open-instruct-model", device_map="auto")
print(gen([{"role": "user", "content": "Write one line about tokenizers."}], max_new_tokens=30)[0]["generated_text"][-1]["content"])
```

Common mistake: thinking "LLM" means only chatbots. Fix: representation models
power search, classification and clustering, and are often the better tool.

</Level>

<Level name="Intermediate">

Training has stages. Pretraining (language modelling) learns from huge amounts of
text by predicting tokens; the result is a base model. Fine-tuning adapts it to a
task or to following instructions. A representation model is pretrained with a
masked objective (guess the hidden word) and fine-tuned for classification or
embeddings. "Large" is a moving target; it is less about a parameter count and
more about general capability.

```py
# bag-of-words, to feel what is lost
from collections import Counter
print(Counter("the dog bit the man".split()) == Counter("the man bit the dog".split()))  # True
```

Proprietary models are accessed by API: strong and easy, but my data leaves my
machine and the model can change. Open models run locally: private and
controllable, but I need hardware and must handle serving.

Common mistake: choosing a proprietary API for data I am not allowed to send
out. Fix: decide the data boundary first, then the model.

</Level>

<Level name="Advanced">

Underneath, the two families differ in what each token can see. An encoder lets
every token attend to every other token in both directions, which is ideal for
understanding a whole input. A decoder lets each token attend only to earlier
tokens (a causal mask), which is what allows generating one token at a time.
Encoder-decoder models (like T5) encode an input and decode an output.

<Compare left="Encoder-only (representation)" right="Decoder-only (generative)" rows={[
  ['sees the whole input both ways', 'sees only earlier tokens'],
  ['output: a vector per token or per text', 'output: the next token, repeatedly'],
  ['good for search, classification, clustering', 'good for generation, instructions, chat'],
  ['small and fast', 'larger and slower'],
]} caption="The two transformer families this book uses. Most tasks in Part II can use either; the choice is cost and fit." />

Running with limited resources means quantised models and small models, which
the book uses so its code runs on one consumer GPU.

Common mistake: using a big generative model to classify a million short texts.
Fix: an embedding model plus a small classifier, at a fraction of the cost.

</Level>

<Level name="Edge cases">

One boundary each. A model too large for my GPU: loading fails with an
out-of-memory error. A prompt in a language the model barely saw: fluent-looking
nonsense. A base model without instruction tuning: it continues my question
instead of answering it.

```text
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 2.00 GiB
```

Common mistake: sending chat-style instructions to a base model. Fix: use an
instruct model, or format the prompt as text the base model would continue.

</Level>

<Level name="Corner cases">

Two boundaries meet. A small open model plus a long input: it fits the memory but
not the context window, so the input is silently truncated. Responsible use plus
an open model: no provider filter sits in front, so safety checks are entirely my
job.

Common mistake: assuming an open model has the same guardrails as an API. Fix:
add my own input and output checks.

</Level>

<Level name="Production level">

In production the choice between an API and an open model is a trade of
capability, cost at volume, latency, privacy and operations. Responsible
development means checking for bias, being transparent that content is generated,
avoiding harmful content, and respecting intellectual property and data rules.

```ts
// the same interface for either: my code does not care which is behind it
interface TextModel { generate(prompt: string, opts?: { maxTokens?: number }): Promise<string>; }
```

Common mistake: coupling the app to one provider's SDK everywhere. Fix: one
interface, swappable implementations.

</Level>

<Level name="Mindset">

Intuition first. The habit this book teaches is to picture what the model is
doing (vectors moving, attention weighing tokens) before using it, so its
behaviour stops being surprising.

Common mistake: memorising library calls without a picture. Fix: draw the data
flow for each example.

</Level>

<Level name="System design">

Representation and generative models are components with different costs.
Systems usually combine them: an encoder for retrieval, a decoder for the answer.

<Flow steps={['text', 'encoder: embeddings', 'vector index', 'retrieve relevant text', 'decoder: generate answer']} caption="The common shape: a representation model finds, a generative model writes." />

Common mistake: one generative model for every step. Fix: use the cheapest model
that does each step well.

</Level>

<Level name="Strategy">

I run one small open instruct model locally and one API model on the same five
prompts, and write down speed, cost and output quality. Done when I can explain
encoder versus decoder in terms of attention masks, and have a working local
generation script.

</Level>

</Levels>

### 2. Tokens and Embeddings

**Covers:** How tokenizers prepare input, word versus subword versus character versus byte tokens, comparing trained tokenizers and their properties; token embeddings and contextualised word embeddings; text embeddings for whole sentences and documents; word embeddings beyond LLMs, word2vec and contrastive training; and embeddings for recommendation systems.

<Flow steps={['"unbelievable!"', 'tokenizer', '["un", "believ", "able", "!"]', 'ids [403, 18292, 540, 0]', 'embedding lookup', 'vectors, one per token']} caption="From text to vectors. The token ids here are illustrative; each tokenizer has its own vocabulary." />

<Levels label="Chapter 2, Tokens and Embeddings">

<Level name="Beginner">

Models do not read characters; they read tokens, pieces of text from a fixed
vocabulary. A tokenizer splits text into tokens and maps each to an id. The model
holds an embedding (a vector) for every token in its vocabulary, and the first
thing it does is look up those vectors.

```py
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("a-small-open-model")
ids = tok("Tokenizers split text.")["input_ids"]
print(ids, tok.convert_ids_to_tokens(ids))
```

Common mistake: counting words to estimate cost or context. Fix: count tokens with
the model's own tokenizer.

</Level>

<Level name="Intermediate">

Tokenizers come in kinds. Word tokens cannot handle new words. Character tokens
handle anything but make sequences long. Subword tokens (byte-pair encoding,
WordPiece, SentencePiece) are the common middle: frequent words are one token,
rare words split into pieces. Byte-level tokens fall back to raw bytes so nothing
is unknown. Trained tokenizers differ in how they treat capitals, spaces, code
indentation, digits, emoji and other languages, and that shapes what the model
is good at.

```py
for name in ["tokenizer-a", "tokenizer-b", "tokenizer-c"]:
    t = AutoTokenizer.from_pretrained(name)
    for s in ["    return x", "12345678", "नमस्ते दुनिया"]:
        print(name, repr(s), len(t(s)["input_ids"]))
```

Common mistake: assuming all tokenizers split code or Hindi the same way. Fix:
measure tokens per character for my own text on each candidate.

</Level>

<Level name="Advanced">

Token embeddings are static: one vector per vocabulary entry. After the
transformer layers, each token's vector is contextualised: "bank" in "river
bank" and "bank account" ends up with different vectors. A text embedding for a
whole sentence is produced by a model trained for that purpose, often by pooling
token vectors (mean, or a special token). Word2vec showed the idea underneath:
train vectors so words that appear in similar contexts are close, using
contrastive training (pull true neighbour pairs together, push random pairs
apart).

```py
from sentence_transformers import SentenceTransformer, util
m = SentenceTransformer("a-sentence-embedding-model")
a, b, c = m.encode(["deploy failed", "the release broke", "lunch is ready"])
print(float(util.cos_sim(a, b)), float(util.cos_sim(a, c)))  # high, low
```

The same trick works beyond language: treat playlists as sentences and songs as
words, and word2vec learns song embeddings for recommendations.

Common mistake: averaging token embeddings from a generative model and calling it
a sentence embedding. Fix: use a model trained to produce text embeddings.

</Level>

<Level name="Edge cases">

One boundary each. An empty string: zero tokens, or only special tokens, and the
embedding is meaningless. A very long document: truncated at the model's maximum
sequence length without warning. A misspelling: splits into odd subwords and its
embedding drifts from the correct word. Numbers: split into chunks that make
arithmetic hard.

```py
print(m.max_seq_length)   # e.g. 256 tokens: anything after that is ignored
```

Common mistake: embedding whole documents with a 256-token model. Fix: chunk first,
embed chunks.

</Level>

<Level name="Corner cases">

Two boundaries meet. Truncation plus a document whose key point is at the end:
the embedding represents the introduction only. A multilingual query plus an
English-only embedding model: the query and the right document end up far apart.
Song embeddings plus a new song: no co-occurrence data, no vector (cold start).

Common mistake: mixing embeddings from two different models in one index. Fix:
one model per index; re-embed everything when changing it.

</Level>

<Level name="Production level">

In production the tokenizer decides cost and limits: price per token, maximum
context, and how chunks are measured. The embedding model is a versioned
dependency of the index: change it and every stored vector is invalid.

```ts
type IndexMeta = { embeddingModel: string; dims: number; createdAt: string };
if (meta.embeddingModel !== CURRENT_MODEL) throw new Error('index built with a different embedding model, re-embed');
```

Common mistake: upgrading the embedding model for queries only. Fix: store the
model id with the index and refuse to mix.

</Level>

<Level name="Mindset">

Everything the model knows about text, it knows through tokens and vectors. The
habit is to look at the tokens when behaviour is strange: many failures (spelling,
counting letters, arithmetic) are tokenisation, not reasoning.

Common mistake: blaming the model's intelligence for a tokenisation artefact. Fix:
print the tokens.

</Level>

<Level name="System design">

<Figure art={`

                                      |
                                transformer layers
                                      |
                        contextual token vectors --> pool --> text embedding
                                                                 |
                                                       vector index / classifier
`} caption="Where each kind of embedding comes from. Search and classification use the pooled text embedding at the end." />

Common mistake: treating the tokenizer as a detail. Fix: pin it with the model;

</Level>

<Level name="Strategy">

I tokenise a sample of my notes, a TypeScript file and a Hindi paragraph with
three tokenizers and tabulate tokens per character, then embed twenty note titles

many tokens a text costs and explain why two sentences are close in embedding
space.

</Level>

### 3. Looking Inside Large Language Models

**Covers:** The inputs and outputs of a trained transformer, the components of the forward pass, choosing a token from the distribution, parallel processing and context size, caching keys and values, inside the transformer block, and recent improvements: more efficient attention, the modern block, rotary positional embeddings and other experiments.

<Figure art={`
 tokens --> embeddings (+ position) --> [ block 1 ] --> ... --> [ block N ]
                                         |  attention  |        |
                                         |  feedforward|        v
                                                         LM head: one score
                                                         per vocab token
                                                               |
                                                       softmax -> sample -> next token
                                                               (append, repeat)
`} caption="The forward pass. Only the last position's scores are used to choose the next token." />

<Levels label="Chapter 3, Looking Inside Large Language Models">

<Level name="Beginner">

A generative model takes a list of tokens and outputs, for the next position, a
score for every token in its vocabulary. It picks one (decoding), appends it, and
runs again. Inside, the input goes through a stack of transformer blocks; each
block has an attention layer and a feedforward layer. At the end a language
modelling head turns the last vector into vocabulary scores.

```py
import torch
out = model(**tok("The capital of France is", return_tensors="pt"))
next_id = int(out.logits[0, -1].argmax())
print(tok.decode(next_id))   # " Paris"
```

Common mistake: thinking the model generates a whole sentence at once. Fix: it
generates one token per forward pass; the loop is in the decoding code.

</Level>

<Level name="Intermediate">

Choosing the next token: greedy decoding always takes the top score; sampling
draws from the softmax distribution, shaped by temperature and top-p. Tokens are
processed in parallel during the forward pass, each in its own stream through
the blocks, which is why the context size (the number of streams) is a hard limit.

Generation would repeat a lot of work, because each step recomputes earlier
tokens. The key-value cache stores each layer's keys and values for past tokens,
so each new step only computes the new token.

```py
import time
for use_cache in [True, False]:
    t = time.time(); model.generate(**inputs, max_new_tokens=100, use_cache=use_cache)
    print(use_cache, round(time.time() - t, 2))
# True 1.9   False 6.8   (numbers vary by hardware)
```

Common mistake: disabling the cache to save memory without seeing the speed cost.
Fix: measure both and size the cache deliberately.

</Level>

<Level name="Advanced">

Inside the attention layer, each token's vector is projected into a query, a key
and a value. Each query is compared with the keys of the positions it may see
(dot products, scaled), softmaxed into weights, and used to average the values.
Several heads do this in parallel, each learning a different kind of relevance.
The feedforward layer then transforms each position independently, and is where
much of the model's stored knowledge sits. Residual connections and normalisation
keep the deep stack trainable.

```py
import torch, math
q, k, v = torch.randn(4, 8), torch.randn(4, 8), torch.randn(4, 8)   # 4 tokens, dim 8
scores = q @ k.T / math.sqrt(8)
mask = torch.triu(torch.ones(4, 4), 1).bool()
scores[mask] = float("-inf")                       # causal: no peeking ahead
out = torch.softmax(scores, -1) @ v
print(out.shape)                                   # torch.Size([4, 8])
```

Recent improvements: attention variants that share keys and values across heads
(multi-query and grouped-query attention) to shrink the cache, local or sparse
attention for long inputs, hardware-aware attention kernels, pre-normalisation,
and rotary positional embeddings, which encode position by rotating query and key
vectors so relative distance shows up in their dot product.

Common mistake: forgetting the scaling by the square root of the dimension when
implementing attention. Fix: without it, softmax saturates and gradients vanish.

</Level>

<Level name="Edge cases">

One boundary each. A sequence of exactly the context length: the next token has
no room. A single-token input: attention has only itself to look at. Logits with
two tokens tied at the top: greedy decoding depends on tie-breaking. A token the
model never saw in training (a rare byte): its embedding is barely trained.

```py
probs = torch.softmax(torch.tensor([3.0, 3.0, 1.0]), 0)
print(probs)  # tensor([0.4683, 0.4683, 0.0634])  -> greedy picks index 0 by convention
```

Common mistake: assuming greedy decoding is the "true" answer. Fix: treat it as one
choice among close alternatives, and check margins.

</Level>

<Level name="Corner cases">

Two boundaries meet. A long context plus the KV cache: memory grows linearly with
tokens and batch size, so long chats evict other users. Grouped-query attention
plus a model converted from multi-head: quality may drop if it was not trained
that way. Rotary embeddings plus contexts longer than training: positions beyond
the trained range behave poorly unless the model was extended for them.

Common mistake: setting a context length beyond what the model was trained on.
Fix: use the documented maximum, or a model trained or adapted for longer context.

</Level>

<Level name="Production level">

In production these internals are the cost model. Prefill processes the whole
prompt in parallel; decode is one token per step with the cache. Memory is
weights plus cache. Attention variants and cache sharing are why some models are
cheaper to serve at long context.

```ts
// a rough serving budget from internals, in bytes
const kvPerToken = 2 * layers * kvHeads * headDim * 2; // keys and values, 16-bit
const maxConcurrent = Math.floor((gpuBytes - weightBytes) / (kvPerToken * avgContextTokens));
```

Common mistake: sizing a GPU by weights alone. Fix: add the cache for the expected
number of concurrent requests and their context.

</Level>

<Level name="Mindset">

A transformer is a stack of simple, repeated operations. The habit is to reason
about behaviour from the mechanism: causal masks explain why it cannot revise
earlier tokens, the cache explains memory growth, attention explains why context
placement matters.

Common mistake: treating the model as an oracle. Fix: picture the forward pass.

</Level>

<Level name="System design">

Common mistake: choosing a model without looking at its attention variant and

</Level>

<Level name="Strategy">

I implement single-head causal attention in about twenty lines of PyTorch, check
it against a library layer on random input, then time generation with and without
the cache. Done when I can draw a transformer block from memory and explain where
the KV cache memory goes with numbers.

</Level>

## Part II, Using Pretrained Language Models

### 4. Text Classification

**Covers:** Classifying the sentiment of movie reviews with representation models (choosing a model, using a task-specific model, supervised classification on embeddings, zero-shot classification without labels) and with generative models (a text-to-text transformer, and a chat model as a classifier).

<Figure art={`
                    do I have labelled data?
                     /                  \\
                   yes                   no
                    |                     |
     is there a task-specific        zero-shot: embed the labels
     model for this exact task?      and pick the nearest, or
       /            \\                 prompt a generative model
     yes             no
      |               |
  use it as is   embeddings + a small classifier
                 (fast, cheap, strong baseline)
`} caption="Choosing a classification approach. Embeddings plus logistic regression is the baseline everything else must beat." />

<Levels label="Chapter 4, Text Classification">

<Level name="Beginner">

Text classification assigns a label to a text: positive or negative, billing or
bug. Three easy routes exist. Use a model already fine-tuned for the task. Embed
texts with an embedding model and train a small classifier on the vectors. Or ask
a generative model to pick a label.

```py
from sentence_transformers import SentenceTransformer
from sklearn.linear_model import LogisticRegression
m = SentenceTransformer("a-sentence-embedding-model")
X_train, X_test = m.encode(train_texts), m.encode(test_texts)
clf = LogisticRegression(max_iter=1000).fit(X_train, train_labels)
print(clf.score(X_test, test_labels))   # e.g. 0.85
```

Common mistake: reaching for a chat model to classify thousands of texts. Fix:
embeddings plus a classifier first; it is fast and often as good.

</Level>

<Level name="Intermediate">

Choosing a representation model means looking at what it was trained on, its
size, its languages, and benchmark results for the task type. A task-specific
model (for example, one fine-tuned on reviews) can be used directly, but only if
its domain matches mine. Evaluation uses precision, recall, F1 and accuracy per
class, read together in a classification report.

Without labels, zero-shot classification embeds descriptions of each label
("a negative movie review") and assigns each text to the most similar label
description.

```py
from sklearn.metrics.pairwise import cosine_similarity
labels = ["a ticket about billing", "a ticket about a bug", "a ticket about account access"]
L = m.encode(labels)
pred = cosine_similarity(m.encode(test_texts), L).argmax(1)
```

Common mistake: label descriptions that are one word. Fix: a short descriptive
phrase per label, and test a few phrasings.

</Level>

<Level name="Advanced">

Generative models classify through prompting. An encoder-decoder text-to-text
model can be asked "Is the following sentence positive or negative?" and outputs
the label as text. A chat model can do the same with a system prompt and an
output format. This is flexible (new labels need no training) but slower, more
expensive, and needs output parsing.

```ts
const r = await callModel([
  { role: 'system', content: 'Label the review as 1 (positive) or 0 (negative). Output only the digit.' },
  { role: 'user', content: review },
]);
const label = r.text.trim() === '1' ? 1 : r.text.trim() === '0' ? 0 : null; // null = unparseable, count it
```

The comparison that matters is accuracy against cost and latency per item, on my
data.

Common mistake: ignoring unparseable outputs when computing accuracy. Fix: count
them as errors and report the parse failure rate.

</Level>

<Level name="Edge cases">

One boundary each. A sarcastic review ("great, it broke on day one"): sentiment
models often get it wrong. A very short text ("ok"): little signal. A text longer
than the model's maximum length: truncated, so the verdict comes from the opening.
A class with ten training examples.

```py
from sklearn.metrics import classification_report
print(classification_report(y_test, y_pred))   # read the per-class rows, not just accuracy
```

Common mistake: reporting only accuracy on imbalanced labels. Fix: per-class
precision and recall.

</Level>

<Level name="Corner cases">

Two boundaries meet. Zero-shot plus overlapping labels ("billing" and "refund"):
texts sit equally close to both, and the argmax is a coin toss. A task-specific
model plus a domain shift: a model trained on movie reviews applied to support
tickets is confident and wrong. A chat model plus a label it refuses to assign
(for a sensitive topic).

Common mistake: trusting a model's high confidence outside its training domain.
Fix: a small labelled sample from my domain to check it.

</Level>

<Level name="Production level">

In production classification needs a confidence threshold and a fallback: below
it, route to a human or an "other" class. The classifier, its embedding model and
its threshold are versioned together. I watch the predicted class distribution
for shifts.

```py
proba = clf.predict_proba(X)
pred = [labels[p.argmax()] if p.max() >= 0.6 else "needs_review" for p in proba]
```

Common mistake: forcing every input into a class. Fix: an explicit "needs review"
outcome.

</Level>

<Level name="Mindset">

Use the smallest model that does the job, and prove it with a baseline. The habit
is to compare three routes on the same test set before choosing.

Common mistake: picking the most impressive route. Fix: a table of accuracy, cost
and latency per route.

</Level>

  ['output is always a valid label', 'output must be parsed and validated'],

Common mistake: staying on the expensive route after labels have accumulated. Fix:
use the generative labels to train the cheap classifier.

</Level>

<Level name="Strategy">

I label 300 of my synthetic tickets, then compare a zero-shot embedding
classifier, embeddings plus logistic regression, and a chat model prompt, on
accuracy, per-class recall, cost and latency. Done when the table exists and I
have chosen a route with a reason.

</Level>

</Levels>

### 5. Text Clustering and Topic Modeling

**Covers:** A common clustering pipeline on a corpus of arXiv abstracts (embed documents, reduce dimensions, cluster, inspect clusters), and topic modelling with BERTopic as a modular framework, including adding a representation block and a text generation block to name topics.

<Flow steps={['documents', 'embed (sentence model)', 'reduce dimensions (UMAP)', 'cluster (HDBSCAN)', 'describe clusters (c-TF-IDF)', 'optional: rerank keywords, LLM names the topic']} caption="The clustering and topic pipeline. Each block can be swapped without changing the others." />

<Levels label="Chapter 5, Text Clustering and Topic Modeling">

<Level name="Beginner">

Clustering groups similar texts without labels. The pipeline: embed every
document, reduce the vectors to a few dimensions so distances are meaningful, run
a clustering algorithm, and read samples from each cluster to see what it means.
Topic modelling goes one step further and describes each cluster with keywords
or a label.

```py
from umap import UMAP
from hdbscan import HDBSCAN
E = m.encode(abstracts, show_progress_bar=True)
R = UMAP(n_components=5, min_dist=0.0, metric="cosine", random_state=42).fit_transform(E)
labels = HDBSCAN(min_cluster_size=50).fit_predict(R)
print(len(set(labels)) - (1 if -1 in labels else 0), "clusters;", (labels == -1).sum(), "outliers")
```

Common mistake: running k-means on raw high-dimensional embeddings. Fix: reduce
dimensions first, and consider a density-based method that allows outliers.

</Level>

<Level name="Intermediate">

Dimensionality reduction (UMAP, or PCA) keeps neighbourhood structure while
dropping to a handful of dimensions; a separate 2D reduction is used only for
plotting. Density-based clustering (HDBSCAN) finds clusters of any shape and
marks points that belong nowhere as outliers (label minus one), instead of
forcing them into a cluster.

BERTopic builds topics on top: it joins each cluster's documents and uses a
class-based TF-IDF to find words that are frequent in this cluster and rare in
others.

```py
from bertopic import BERTopic
topic_model = BERTopic(embedding_model=m, umap_model=UMAP(n_components=5), hdbscan_model=HDBSCAN(min_cluster_size=50))
topics, _ = topic_model.fit_transform(abstracts, E)
print(topic_model.get_topic_info().head())
```

Common mistake: interpreting the 2D plot as the clustering. Fix: cluster in the
5D reduction; the 2D plot is only a picture.

</Level>

<Level name="Advanced">

The framework is modular: each step is a block. The representation block can be
improved by reranking the c-TF-IDF keywords with embedding similarity
(KeyBERT-style), or by maximal marginal relevance to make keywords diverse. A
text generation block sends a few representative documents and keywords to an
LLM and asks for a short topic label, called once per topic rather than once per
document, which keeps cost low.

```py
prompt = """I have a topic with these documents:
[DOCUMENTS]
Keywords: [KEYWORDS]
Give a short label for this topic."""
# the generation block fills the placeholders per topic, not per document
```

Common mistake: calling an LLM for every document to "find topics". Fix: cluster
cheaply, then call the LLM once per cluster.

</Level>

<Level name="Edge cases">

One boundary each. A tiny corpus (50 documents): `min_cluster_size` of 50 yields
zero clusters. A huge outlier share: half the documents labelled minus one. Near
duplicate documents: they form a tight fake cluster. Very short texts: embeddings
carry little meaning.

```py
print((labels == -1).mean())   # 0.48 -> lower min_cluster_size or reduce outliers after fitting
```

Common mistake: treating outliers as noise to delete. Fix: inspect them; they are
often the interesting, rare documents.

</Level>

<Level name="Corner cases">

Two boundaries meet. UMAP randomness plus a small corpus: different seeds give
different clusters, and conclusions change between runs. LLM topic labels plus
mixed clusters: the LLM writes a confident label for a cluster that is really two
topics. c-TF-IDF plus a domain stopword ("model" in an ML corpus): every topic's
top word is the same.

Common mistake: trusting one run. Fix: fix the seed, then check stability across
a few seeds.

</Level>

<Level name="Production level">

In production topic models are for exploration and monitoring (what are users
asking about this week?), not hard decisions. New documents are assigned to
existing topics; topics are refit periodically and compared with the previous
set. Labels need a human pass before they appear in a dashboard.

```py
new_topics, _ = topic_model.transform(new_docs)
print(Counter(new_topics).most_common(5))   # what grew this week
```

Common mistake: refitting from scratch and losing comparability. Fix: keep the old
model to assign, refit on a schedule, and map old topics to new.

</Level>

<Level name="Mindset">

Clustering is a lens, not a truth. The habit is to read documents from every
cluster before naming anything.

Common mistake: believing a tidy plot. Fix: sample ten documents per cluster.

</Level>

<Level name="System design">

<Layers layers={[
  { name: 'Generation', note: 'LLM labels per topic (optional)' },
  { name: 'Representation', note: 'c-TF-IDF, keyword reranking, diversity' },
  { name: 'Clustering', note: 'HDBSCAN or k-means' },
  { name: 'Reduction', note: 'UMAP or PCA' },
  { name: 'Embedding', note: 'sentence embedding model' },
]} caption="BERTopic as Lego blocks. Each layer can be replaced; the cost lives mostly in embedding and generation." />

Common mistake: re-embedding the corpus every time I tweak clustering. Fix: cache
embeddings and iterate on the blocks above.

</Level>

<Level name="Strategy">

I cluster all my notes and commit messages, inspect outliers, and label topics
with an LLM, then compare the labels with my own reading. Done when I can explain
each block's job, the result is stable across three seeds, and the topic list
matches my own sense of what I write about.

</Level>

</Levels>

### 6. Prompt Engineering

**Covers:** Using text generation models (choosing and loading one, controlling output with sampling parameters), the basic ingredients of a prompt and instruction-based prompting, advanced techniques (complex prompts, in-context examples, chain prompting), reasoning (chain-of-thought, self-consistency, tree-of-thought), and output verification (examples, grammar-constrained sampling).

<Figure art={`
  instruction  : what to do
  context      : background the model needs
  persona      : who it should act as
  audience     : who reads the output
  tone         : how it should sound
  format       : the exact shape of the output
  data         : the input to work on
  examples     : a few input -> output pairs
`} caption="The ingredients of a prompt. Not every prompt needs all of them, but each missing one is a guess the model makes for me." />

<Levels label="Chapter 6, Prompt Engineering">

<Level name="Beginner">

A text generation model is controlled by its prompt and by sampling settings:
temperature (randomness) and top-p (how much of the distribution is kept). A
prompt starts with an instruction and the data; adding context, a format and
examples makes the output more predictable. Chat models expect a template with
roles, which the tokenizer's chat template applies.

```py
msgs = [{"role": "user", "content": "Summarise in one sentence: " + note}]
print(tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True))
```

Common mistake: sending raw text to a chat model without its template. Fix: use
the chat template so the model sees the format it was trained on.

</Level>

<Level name="Intermediate">

Instruction-based prompting covers common tasks: classification, summarisation,
extraction, question answering. Being specific, stating the format, and putting
the instruction at the start or end (models attend best there) helps. In-context
learning adds examples: one-shot or few-shot. Chain prompting splits a task into
steps, each prompt feeding the next, such as name then slogan then sales pitch
for a product.

```ts
const name = (await callModel([{ role: 'user', content: `Name for a product that ${desc}. Output the name only.` }])).text;
const slogan = (await callModel([{ role: 'user', content: `Slogan for ${name}, which ${desc}. One line.` }])).text;
```

Common mistake: one prompt that asks for everything at once. Fix: chain small
prompts, each testable.

</Level>

<Level name="Advanced">

Reasoning techniques spend more tokens to get better answers. Chain-of-thought
asks the model to reason step by step before answering, either with examples of
reasoning or with a simple instruction. Self-consistency samples several reasoned
answers at a non-zero temperature and takes the majority. Tree-of-thought
explores several intermediate steps, evaluates them, and continues the promising
ones.

```py
answers = [extract_final(generate(cot_prompt, temperature=0.7)) for _ in range(5)]
print(Counter(answers).most_common(1))   # majority answer and its count
```

Output verification makes outputs usable: examples of the exact format, a
validator that rejects bad output, or grammar-constrained sampling, where a
grammar (for example, a JSON schema) restricts which tokens can be sampled at
each step, so the output is always valid.

Common mistake: using self-consistency at temperature 0. Fix: the samples are
identical then; diversity needs temperature.

</Level>

<Level name="Edge cases">

One boundary each. Temperature very high: incoherent text. A prompt so long the
instruction sits in the middle: ignored. Chain-of-thought on a simple lookup:
slower and sometimes worse. A few-shot set with a wrong example: copied.

```py
gen(prompt, temperature=2.0, max_new_tokens=30)  # word salad: a useful thing to see once
```

Common mistake: assuming more reasoning is always better. Fix: measure CoT against
direct answers on my eval set.

</Level>

<Level name="Corner cases">

Two boundaries meet. Constrained sampling plus a schema that forces a value: the
model must output something for every field, so it invents one. Chain prompting
plus an early error: step one's mistake flows through every later step.
Self-consistency plus open-ended answers: answers are all different strings, so
there is no majority to take.

Common mistake: chains without checks between steps. Fix: validate each step's
output before passing it on.

</Level>

<Level name="Production level">

In production prompts are templates with versions; reasoning tokens are a cost
and latency line item; constrained output is preferred wherever the result is
parsed by code. The visible reasoning should not be shown to users as if it were
a faithful explanation.

```py
from pydantic import BaseModel
class Ticket(BaseModel):
    category: str
    order_id: str | None
# constrain generation to Ticket's JSON schema, then validate with Ticket.model_validate_json
```

Common mistake: parsing free-form output with regexes. Fix: constrained decoding
or a schema validator with retries.

</Level>

<Level name="Mindset">

A prompt is an interface. The habit is to design it for the model's strengths
(clear instructions, examples, room to reason) and to verify the output instead of
hoping.

Common mistake: polishing wording endlessly. Fix: structure and verification
matter more than adjectives.

</Level>

<Level name="System design">

<Flow steps={['template + ingredients', 'optional: reasoning (CoT, self-consistency)', 'constrained or free generation', 'validate', 'next chain step or final output']} caption="Prompting as a pipeline step with verification. Reasoning and constraints are dials, set per step." />

Common mistake: the same expensive reasoning prompt for every step. Fix: reason
only where the eval shows it helps.

</Level>

<Level name="Strategy">

I take one task (extract action items from a note) and try instruction only,
few-shot, chain-of-thought, self-consistency and grammar-constrained JSON, scored
on 30 notes. Done when I have a table of accuracy, validity and token cost for
each technique and have chosen one for production.

</Level>

</Levels>

### 7. Advanced Text Generation Techniques and Tools

**Covers:** Loading quantised models through LangChain; chains (a prompt template as a single link, chains of several prompts); memory for conversations (full buffer, windowed buffer, summary); and agents (step-by-step reasoning as their driver, and ReAct in LangChain).

<Compare left="Memory type" right="Trade-off" rows={[
  ['full conversation buffer', 'complete, but grows until it overflows the context'],
  ['windowed buffer (last k turns)', 'bounded, forgets early facts'],
  ['running summary', 'bounded and long-lived, costs a model call, loses detail'],
]} caption="Three ways to give a chat model memory. Each is a choice about what to forget." />

<Levels label="Chapter 7, Advanced Text Generation Techniques and Tools">

<Level name="Beginner">

Frameworks like LangChain wrap common patterns: a model loader, a prompt
template, a chain that connects them, memory that keeps conversation history, and
agents that let a model call tools. A quantised model file (such as a GGUF file)
lets a large model run on modest hardware.

```py
from langchain_core.prompts import PromptTemplate
prompt = PromptTemplate.from_template("Write a title for this note:\n{note}")
chain = prompt | llm
print(chain.invoke({"note": note_text}))
```

Common mistake: learning the framework before the pattern. Fix: write the same
chain in plain code once, then use the framework if it saves time.

</Level>

<Level name="Intermediate">

A chain with several prompts passes one step's output into the next step's
template: write a story title, then a character description using the title,
then the story using both. Memory gives a stateless model the illusion of
remembering: the history is inserted into each new prompt. A windowed buffer
keeps the last k exchanges; a summary memory asks the model to summarise the
conversation so far and keeps the summary.

```ts
// a windowed buffer in plain code
const history: Msg[] = [];
function remember(m: Msg, k = 6) { history.push(m); while (history.length > k * 2) history.shift(); }
```

Common mistake: a full buffer in a long chat. Fix: a window or summary, sized to
the context and the cost budget.

</Level>

<Level name="Advanced">

Agents are driven by step-by-step reasoning. In the ReAct pattern the model
writes a thought, chooses an action (a tool with input), receives an
observation, and repeats until it writes a final answer. The framework parses
each step and runs the tool. The loop is only as good as the parsing, the tool
descriptions and the stopping rule.

<Figure art={`
  Thought: I need today's exchange rate.
  Action: search["USD to INR rate"]
  Observation: 1 USD = 83.2 INR (source ...)
  Thought: Now compute 120 * 83.2.
  Action: calculator["120 * 83.2"]
  Observation: 9984
  Final Answer: About 9,984 INR.
`} caption="A ReAct trace. The model writes the thoughts and actions; the framework runs the tools and writes the observations." />

```py
agent = create_react_agent(llm, tools, react_prompt)
executor = AgentExecutor(agent=agent, tools=tools, max_iterations=5, handle_parsing_errors=True)
```

Common mistake: no iteration limit. Fix: a maximum number of steps and a parsing
error handler.

</Level>

<Level name="Edge cases">

One boundary each. A summary memory that drops a key fact (the user's order
number). A tool that returns an error string: the agent reads it as data. An
agent whose output does not match the expected format: the parser fails. A
quantised model too small to follow the ReAct format.

```text
OutputParserException: Could not parse LLM output: `I think the answer is...`
```

Common mistake: using a tiny local model for agents. Fix: agents need a model
strong enough to follow the format reliably; test format adherence first.

</Level>

<Level name="Corner cases">

Two boundaries meet. Summary memory plus a correction ("no, my order is 4417, not
4471"): the summary keeps the wrong number if the summariser misses the
correction. An agent plus a tool that has side effects plus a retry: the action
runs twice. Memory plus multiple users: history from one session leaks into
another through a shared object.

Common mistake: a module-level memory object in a web server. Fix: memory keyed by
session id, stored outside the process.

</Level>

<Level name="Production level">

In production frameworks are a convenience, not an architecture. I keep the
prompts, tools and memory policy in my own code, log every step, and make tools
idempotent. Memory is stored per user with retention limits.

```ts
await store.set(`mem:${sessionId}`, JSON.stringify(history), { ttlSeconds: 86_400 }); // retention is a policy choice
```

Common mistake: hiding agent steps inside a framework with no tracing. Fix: trace
every thought, action and observation.

</Level>

<Level name="Mindset">

Every framework feature is a pattern I could write myself. The habit is to
understand the pattern so I can debug it when the framework hides the failure.

Common mistake: debugging by changing framework options at random. Fix: print the
exact prompt the framework sent.

</Level>

<Level name="System design">

<Layers layers={[
  { name: 'Agent loop', note: 'reasoning, tool choice, stop condition' },
  { name: 'Tools', note: 'search, calculator, my APIs, with schemas and limits' },
  { name: 'Memory', note: 'buffer, window or summary, per session' },
  { name: 'Chains', note: 'templates linked step to step' },
  { name: 'Model I/O', note: 'local quantised model or API' },
]} caption="The layers a framework provides. Each can be replaced by plain code when the framework gets in the way." />

Common mistake: letting the framework own state. Fix: state in my database, the
framework only orchestrates.

</Level>

<Level name="Strategy">

I build a note assistant twice, once with a framework and once in plain
TypeScript: a two-step chain, a windowed memory, and a ReAct agent with a search
and a calculator tool and a five-step limit. Done when both versions pass the
same ten conversations and I can print the exact prompt of every step.

</Level>

### 8. Semantic Search and Retrieval-Augmented Generation

**Covers:** Semantic search with language models (dense retrieval, reranking, retrieval evaluation metrics) and retrieval-augmented generation (from search to RAG, grounded generation with an API, RAG with local models, advanced RAG techniques, and RAG evaluation).

<Figure art={`
   query --> embed --> nearest chunks (top 50) --> reranker --> top 5
                         (dense, fast)            (cross-encoder,
                                                   slow, accurate)
                                                        |
                                    prompt: question + top 5, cite [n]
                                                        |
                                               grounded answer
`} caption="Two-stage retrieval then generation. The reranker reads query and chunk together, which is why it is more accurate and too slow to run on everything." />

<Levels label="Chapter 8, Semantic Search and Retrieval-Augmented Generation">

<Level name="Beginner">

Semantic search finds text by meaning, not by matching words. Dense retrieval
embeds every chunk and the query, and returns the nearest chunks. RAG takes those
chunks and asks a generative model to answer using them, with citations.

```py
import faiss, numpy as np
E = m.encode(chunks, normalize_embeddings=True).astype("float32")
index = faiss.IndexFlatIP(E.shape[1]); index.add(E)
q = m.encode(["how do I roll back a deploy?"], normalize_embeddings=True).astype("float32")
scores, ids = index.search(q, 3)
print([chunks[i][:60] for i in ids[0]])
```

Common mistake: forgetting to normalise vectors before inner-product search.
Fix: normalise, so inner product equals cosine similarity.

</Level>

<Level name="Intermediate">

Chunking decides what a retrievable unit is: by sentence, paragraph, fixed
token count with overlap, or by document structure (headings). Reranking takes
the top candidates from a fast retriever (dense, keyword, or both) and reorders
them with a cross-encoder that reads query and chunk together and outputs a
relevance score.

```py
from sentence_transformers import CrossEncoder
ce = CrossEncoder("a-cross-encoder-reranker")
cands = [chunks[i] for i in ids[0][:50]]
order = np.argsort(-ce.predict([(query, c) for c in cands]))
top = [cands[i] for i in order[:5]]
```

Retrieval evaluation needs queries with known relevant chunks. Mean average
precision rewards putting relevant results at the top; recall at k asks whether
the relevant chunk appears at all; nDCG weights by rank.

Common mistake: judging retrieval by reading a few results. Fix: a labelled query
set and a metric.

</Level>

<Level name="Advanced">

Grounded generation puts the retrieved chunks into the prompt with an
instruction to answer only from them and to cite. With local models, the same
pipeline runs with a quantised generator and a local embedding model, fully
private. Advanced techniques: query rewriting (turn a chatty question into a
search query), multi-query (search several rewrites and merge), multi-hop (answer
a question that needs facts from two documents by retrieving in steps), query
routing (choose which index to search), and agentic RAG (the model decides when
and what to retrieve).

```ts
const rewritten = (await callModel([
  { role: 'system', content: 'Rewrite the last user message as a standalone search query. Output only the query.' },
  ...history,
])).text;
```

RAG evaluation scores the answer on fluency, perceived utility, citation recall
(are claims supported by cited chunks) and citation precision (does each citation
support its claim); automated judges help, with the usual calibration.

Common mistake: evaluating RAG only by answer quality. Fix: score retrieval and
citations separately.

</Level>

<Level name="Edge cases">

One boundary each. A query with an exact identifier (`E1042`) that dense
retrieval misses. A question with no answer in the corpus. A chunk that is only a
heading. A corpus with many near-duplicate chunks, which fill the top five with
the same text.

```py
seen, unique = set(), []
for c in top_candidates:
    key = c[:200]
    if key not in seen: seen.add(key); unique.append(c)
```

Common mistake: no "not found" path. Fix: a score threshold and unanswerable
questions in the eval set.

</Level>

<Level name="Corner cases">

Two boundaries meet. Reranking plus a permission filter applied after reranking:
the best chunk is forbidden and is removed, but the reranker's budget was spent
on it. Query rewriting plus an ambiguous follow-up: the rewrite picks the wrong
referent and retrieval looks perfect for the wrong question. A local model plus
long retrieved context: the model's small context window truncates the chunks.

Common mistake: logging the user's question but not the rewritten query. Fix: log
both, so bad retrieval can be traced to a bad rewrite.

</Level>

<Level name="Production level">

In production the index has an ingestion pipeline with updates and deletes,
stores chunk source and version, and filters by permission at query time.
Latency is split into embedding, search, rerank and generation. Every answer
records the chunk ids it used.

```ts
log.info('rag', { q, rewritten, retrieved: ids, reranked: topIds, cited: citations, ms: { embed, search, rerank, gen } });
```

Common mistake: a reranker on the hot path with no timeout. Fix: a timeout that
falls back to the retriever's order.

</Level>

<Level name="Mindset">

Search quality is most of RAG quality. The habit is to evaluate and improve
retrieval before touching the generation prompt.

Common mistake: switching to a bigger generator to fix missing facts. Fix: check
whether the right chunk was retrieved.

</Level>

<Level name="System design">

<Flow steps={['ingest: parse, chunk, embed, index', 'query: rewrite', 'retrieve: dense + keyword', 'filter: permissions', 'rerank', 'generate with citations', 'evaluate: retrieval and citations']} caption="A full RAG system. Filtering by permission belongs inside retrieval, before any model reads the chunks." />

Common mistake: one global index for all tenants. Fix: tenant filters or separate
indexes.

</Level>

<Level name="Strategy">

I build semantic search over my notes, label 50 queries with their relevant
chunks, measure recall at 5 and MAP with and without a reranker, then add grounded
generation and score citation precision on 30 answers. Done when retrieval metrics
are measured, the reranker's gain is known, and every answer is traceable to its
chunks.

</Level>

</Levels>

### 9. Multimodal Large Language Models

**Covers:** Transformers for vision; multimodal embedding models (CLIP, how it creates shared text-image embeddings, OpenCLIP); making text generation models multimodal (BLIP-2 bridging the modality gap, preprocessing inputs), with use cases for image captioning and multimodal chat-based prompting.

<Figure art={`
   image --> patches --> vision encoder --+
                                          +--> shared space: matching pairs close,
   text  --> tokens  --> text encoder   --+    mismatched pairs far (contrastive)
   BLIP-2: frozen vision encoder --> small bridge (Q-Former) --> frozen LLM
`} caption="Two ways to join images and text: a shared embedding space (CLIP), or a bridge that feeds image features into a language model (BLIP-2)." />

<Levels label="Chapter 9, Multimodal Large Language Models">

<Level name="Beginner">

A multimodal model works with more than text, most often images. A vision
transformer cuts an image into patches and treats each patch like a token. CLIP
trains an image encoder and a text encoder together so that an image and its
caption land close in the same vector space. That lets me search images with
text, or classify images by comparing them with label descriptions.

```py
from PIL import Image
from sentence_transformers import SentenceTransformer, util
clip = SentenceTransformer("a-clip-model")
img = clip.encode(Image.open("screenshot.png"))
txt = clip.encode(["an error dialog", "a login form", "a chart"])
print(util.cos_sim(img, txt))   # highest score = best description
```

Common mistake: comparing an image embedding with an embedding from a different
text model. Fix: both sides must come from the same multimodal model.

</Level>

<Level name="Intermediate">

CLIP is trained contrastively on image-caption pairs: in each batch, the true
pairs are pulled together and all other pairings are pushed apart. OpenCLIP is an
open implementation with models trained on public data. Images need
preprocessing (resize, crop, normalise) to the size the vision encoder expects.

To make a text generator see images, BLIP-2 keeps a pretrained vision encoder and
a pretrained LLM frozen and trains a small bridge between them that turns image
features into soft visual tokens the LLM can read. This is cheap compared with
training a multimodal model from scratch.

```py
inputs = processor(images=Image.open("chart.png"), text="Question: what does this chart show? Answer:", return_tensors="pt")
print(processor.decode(model.generate(**inputs, max_new_tokens=40)[0], skip_special_tokens=True))
```

Common mistake: sending a huge image and expecting fine detail. Fix: the
preprocessor resizes it; crop the region that matters first.

</Level>

<Level name="Advanced">

Underneath, the "modality gap" is that image features and text embeddings live in
different spaces. BLIP-2's bridge (a querying transformer) learns a fixed set of
query vectors that attend to the image features and output a small number of
vectors projected into the LLM's embedding space. Training happens in stages:
first align the bridge with text, then connect it to the LLM.

Use cases: captioning (describe an image), visual question answering, and
multimodal chat where an image and a conversation go in together.

Common mistake: assuming a multimodal chat model "reads" text in images reliably.
Fix: for dense text in screenshots, test against plain OCR and measure.

</Level>

<Level name="Edge cases">

One boundary each. An image with tiny text: lost at the model's input resolution.
A synthetic diagram unlike training photos: weak captions. A label description
that is one word ("dog") versus a phrase ("a photo of a dog"): CLIP zero-shot
accuracy changes. A transparent PNG: the alpha channel is dropped and the image
looks different.

```py
img = Image.open("icon.png").convert("RGB")  # be explicit about the conversion
```

Common mistake: loading images without converting the mode. Fix: convert to RGB
and check the preprocessed tensor shape.

</Level>

<Level name="Corner cases">

Two boundaries meet. Multimodal input plus prompt injection: text drawn inside an
image ("ignore your instructions") reaches the model as instructions. Image
search plus personal photos: embeddings of faces enable searches the users never
agreed to.

Common mistake: treating image content as trusted. Fix: anything inside an image
is untrusted input, exactly like retrieved text.

</Level>

<Level name="Production level">

In production images are large inputs: they cost more tokens or compute, take
longer to upload and process, and carry privacy risks (faces, documents, location
metadata). I strip metadata, limit size, and decide retention.

```ts
const stripped = await sharp(buffer).rotate().resize({ width: 1024, withoutEnlargement: true }).toBuffer(); // drops EXIF by default
```

Common mistake: storing uploaded images forever with their metadata. Fix: strip
metadata and set retention.

</Level>

<Level name="Mindset">

Every modality becomes tokens and vectors. The habit is to ask how an image is
turned into what the model reads, and what is lost on the way.

Common mistake: assuming the model sees what I see. Fix: look at the preprocessed
input.

</Level>

<Level name="System design">

<Compare left="Shared embedding (CLIP)" right="Bridge into an LLM (BLIP-2 style)" rows={[

  ['fast, one vector per image', 'slower, generates text'],
  ['no generation', 'generation, with the LLM\'s strengths and risks'],

Common mistake: a generative multimodal model for image search. Fix: CLIP-style
embeddings and a vector index.

</Level>

<Level name="Strategy">

If my phase 8 feature handles screenshots, I index 200 screenshots with a CLIP
model, measure text-to-image search on 30 queries, and compare captions from a
multimodal model with my own. Done when I know the search recall, the caption
failure modes, and have one injection-in-image test that the system resists.

</Level>

## Part III, Training and Fine-Tuning Language Models

### 10. Creating Text Embedding Models

**Covers:** What embedding models are, contrastive learning, SBERT, creating an embedding model (generating contrastive examples, training, in-depth evaluation, loss functions), fine-tuning an embedding model (supervised, Augmented SBERT), and unsupervised learning with TSDAE, including domain adaptation.

<Figure art={`
   anchor:   "how do I roll back a release?"
   positive: "revert the deploy to the previous version"     pull together
   negative: "the release notes are on the wiki"             push apart
   in-batch: every other pair's positive is a free negative
`} caption="Contrastive training in one picture. The model learns what 'similar' means from which pairs it is told belong together." />

<Levels label="Chapter 10, Creating Text Embedding Models">

<Level name="Beginner">

An embedding model turns text into a vector such that similar texts get close
vectors. What "similar" means depends on training. Contrastive learning teaches
it with pairs: examples that should be close (anchor and positive) and examples
that should be far (negatives). SBERT is the standard recipe: a BERT-like encoder
in a siamese setup, so each sentence is embedded independently and compared by
cosine similarity.

```py
from sentence_transformers import InputExample
train = [InputExample(texts=["roll back the release", "revert the deploy"], label=1.0),
         InputExample(texts=["roll back the release", "office lunch menu"], label=0.0)]
```

Common mistake: assuming a general embedding model knows my domain's meaning of
"similar". Fix: test it on pairs from my domain before relying on it.

</Level>

<Level name="Intermediate">

Contrastive examples come from labelled data (natural language inference pairs:
entailment as positive, contradiction as negative), from structure (a question
and its accepted answer, a title and its body), or from mining. Training uses a
loss function: cosine similarity loss regresses on a similarity score; multiple
negatives ranking loss treats each anchor's positive as the right answer among
all positives in the batch, which gives many negatives for free and favours
larger batches.

```py
from sentence_transformers import SentenceTransformer, losses
from torch.utils.data import DataLoader
model = SentenceTransformer("a-small-bert-like-model")
dl = DataLoader(pairs, batch_size=64, shuffle=True)
loss = losses.MultipleNegativesRankingLoss(model)
model.fit(train_objectives=[(dl, loss)], epochs=1, warmup_steps=100)
```

Common mistake: a tiny batch size with in-batch negatives. Fix: larger batches
give more and harder negatives.

</Level>

<Level name="Advanced">

Hard negatives matter: a negative that is obviously unrelated teaches little; one
that is topically close but wrong teaches the boundary. Evaluation goes beyond a
single number: semantic textual similarity correlation, retrieval metrics on my
queries, and broad benchmarks of many tasks (such as MTEB), which show whether
gains on one task cost others.

Fine-tuning a pretrained embedding model on domain pairs usually beats training
from scratch. Augmented SBERT helps when labelled pairs are few: a cross-encoder
trained on the small gold set labels many more unlabelled pairs (silver data),
and the bi-encoder trains on gold plus silver.

```py
# silver labels from a cross-encoder trained on the small gold set
silver = [(a, b, float(ce.predict([(a, b)])[0])) for a, b in candidate_pairs]
```

TSDAE is unsupervised: corrupt a sentence by deleting words, encode it, and train
a decoder to reconstruct the original from the embedding. It adapts a model to a
domain's vocabulary with no labels.

Common mistake: random negatives only. Fix: mine hard negatives from the current
model's top results that are not true matches.

</Level>

<Level name="Edge cases">

One boundary each. A "negative" that is actually a positive (a duplicate question
with different wording): the model is trained to push apart things that match. A
very short anchor ("deploy"): ambiguous. Pairs that are all from one subtopic: the
model learns that subtopic and nothing else. Zero labelled pairs: TSDAE or
structure-derived pairs.

```py
false_negs = [n for n in mined_negs if cos(model.encode(anchor), model.encode(n)) > 0.9]
print(len(false_negs), "suspicious negatives to review")
```

Common mistake: trusting mined negatives blindly. Fix: review the closest ones;
some are true matches.

</Level>

<Level name="Corner cases">

Two boundaries meet. Domain fine-tuning plus general queries: retrieval on my
domain improves while general similarity gets worse, so a mixed corpus suffers.
Silver labels plus a weak cross-encoder: its mistakes become training data at
scale. A new embedding model plus an existing index: every stored vector must be
recomputed, which is a migration, not a deploy.

Common mistake: evaluating only on the domain set after fine-tuning. Fix: also run
a general set to catch regressions.

</Level>

<Level name="Production level">

In production a custom embedding model is a versioned artefact, and changing it
means re-embedding the corpus, ideally into a new index built in parallel and
switched atomically. I keep a retrieval eval set and run it on every candidate.

```ts
await buildIndex({ model: 'notes-embed@v2', target: 'notes_v2' });
if ((await evalRecall('notes_v2')) >= (await evalRecall('notes_v1')) + 0.02) await alias.point('notes', 'notes_v2');
```

Common mistake: re-embedding in place. Fix: build a new index, evaluate, then
switch an alias.

</Level>

<Level name="Mindset">

Similarity is defined by the training data, not by the model. The habit is to ask
"similar for what task?" and build pairs that encode that answer.

Common mistake: chasing benchmark rankings for embedding models. Fix: my own
retrieval set decides.

</Level>

<Level name="System design">

<Flow steps={['pairs: labelled, structural, mined', 'hard negatives', 'train or fine-tune (MNRL)', 'evaluate: domain + general', 'new index in parallel', 'switch alias']} caption="The life of a custom embedding model, from pairs to production index." />

Common mistake: no rollback for the index. Fix: keep the old index until the new
one has served real traffic.

</Level>

<Level name="Strategy">

I build 2,000 pairs from my notes (heading and section body as positives), mine
hard negatives, fine-tune a small embedding model, and compare recall at 5 with
the base model on my 50 labelled queries plus a general set. Done when I know
whether fine-tuning helped my retrieval by a measured margin and did not break
general similarity.

</Level>

</Levels>

### 11. Fine-Tuning Representation Models for Classification

**Covers:** Supervised classification by fine-tuning a pretrained BERT model and freezing layers; few-shot classification with SetFit; continued pretraining with masked language modelling; and named-entity recognition (preparing token-level data and fine-tuning).

<Layers layers={[
  { name: 'Classification head', note: 'always trained' },
  { name: 'Top encoder layers', note: 'task-specific features: train these' },
  { name: 'Middle layers', note: 'train if data allows' },
  { name: 'Bottom layers and embeddings', note: 'general language: freeze first' },
]} caption="Which layers to freeze. Training more layers gives more accuracy and costs more compute and data." />

<Levels label="Chapter 11, Fine-Tuning Representation Models for Classification">

<Level name="Beginner">

Instead of training a classifier on frozen embeddings (chapter 4), I can
fine-tune the whole representation model with a classification head on top, so
the model's internal features adapt to the task. This usually gives higher
accuracy when labelled data exists.

```py
from transformers import AutoModelForSequenceClassification, Trainer, TrainingArguments
model = AutoModelForSequenceClassification.from_pretrained("a-bert-like-model", num_labels=2)
args = TrainingArguments("out", learning_rate=2e-5, per_device_train_batch_size=16, num_train_epochs=1)
Trainer(model=model, args=args, train_dataset=tok_train, eval_dataset=tok_test).train()
```

Common mistake: a learning rate like 1e-3 for fine-tuning. Fix: small rates
(around 2e-5) for pretrained transformers.

</Level>

<Level name="Intermediate">

Freezing layers trades accuracy for speed: freeze the embeddings and lower
blocks, train the top blocks and the head. SetFit handles few-shot
classification: it fine-tunes a sentence embedding model contrastively on pairs
generated from a handful of labelled examples per class (same class as positive,
different class as negative), then trains a simple head. It works with eight or
sixteen examples per class.

```py
from setfit import SetFitModel, Trainer as SetFitTrainer
model = SetFitModel.from_pretrained("a-sentence-embedding-model")
trainer = SetFitTrainer(model=model, train_dataset=eight_per_class, eval_dataset=test)
trainer.train(); print(trainer.evaluate())
```

Common mistake: dismissing fine-tuning because labels are scarce. Fix: SetFit
generates many pairs from few labels.

</Level>

<Level name="Advanced">

Continued pretraining runs the original masked language modelling objective on
my domain's unlabelled text before fine-tuning, so the model learns domain words
and usage. Named-entity recognition classifies each token (person, organisation,
product), which needs token-level labels aligned with subword tokens: when a word
splits into several tokens, label the first and mark the rest to be ignored in
the loss.

```py
def align(word_ids, word_labels):
    out, prev = [], None
    for w in word_ids:
        out.append(-100 if w is None or w == prev else word_labels[w]); prev = w
    return out   # -100 is ignored by the loss
```

Common mistake: giving every subword the word's label, which double-counts. Fix:
label the first subword and ignore the rest, consistently in training and
evaluation.

</Level>

<Level name="Edge cases">

One boundary each. One class with two examples in SetFit: pairs are few and
unbalanced. Text longer than 512 tokens: truncated. An entity that spans a line
break or a hyphen. A dataset where one class is 95 percent.

```py
tok_train = train.map(lambda b: tok(b["text"], truncation=True, max_length=256), batched=True)
```

Common mistake: forgetting truncation and hitting a shape error on a long text.
Fix: set truncation and a maximum length explicitly, and know what is cut.

</Level>

<Level name="Corner cases">

Two boundaries meet. Continued pretraining plus a small domain corpus: the model
overfits it and forgets general language. NER plus a tokenizer change: label
alignment silently shifts when the tokenizer splits words differently. Freezing
layers plus a domain far from pretraining: the frozen lower layers never adapt,
capping accuracy.

Common mistake: switching base models without regenerating aligned labels. Fix:
alignment is part of preprocessing, rerun per tokenizer.

</Level>

<Level name="Production level">

In production a fine-tuned classifier is small and fast, which is its main
advantage over prompting a generative model. It needs a versioned model, a
threshold, per-class monitoring, and a retraining pipeline as labels accumulate.

```py
model.save_pretrained("models/ticket-clf@v3"); tok.save_pretrained("models/ticket-clf@v3")  # tokenizer travels with the model
```

Common mistake: saving the model but not the tokenizer. Fix: always save both
together.

</Level>

<Level name="Mindset">

Representation models are the workhorses. The habit is to reach for a fine-tuned
small model whenever the task is fixed and repeated, and keep generative models
for open-ended work.

Common mistake: assuming bigger generative models beat a fine-tuned small one on
a narrow task. Fix: compare them on the same test set.

</Level>

<Level name="System design">

<Compare left="Few labels" right="Many labels" rows={[
  ['SetFit or prompting', 'full fine-tuning'],
  ['continued pretraining helps a lot', 'helps less'],
  ['freeze more layers', 'train more layers'],
  ['generative labels can bootstrap', 'human labels refine'],

Common mistake: one approach for every data size. Fix: choose by labels available
and move up as they grow.

</Level>

<Level name="Strategy">

On my ticket set I compare a frozen-embedding classifier, SetFit with 8 examples
per class, and full fine-tuning with all labels, then train a small NER model to
extract order ids and product names. Done when the comparison table exists and the
NER model's per-entity F1 is measured with correct subword alignment.

</Level>

### 12. Fine-Tuning Generation Models

**Covers:** The three LLM training steps (pretraining, supervised fine-tuning, preference tuning); supervised fine-tuning, full and parameter-efficient; instruction tuning with QLoRA (templating, quantisation, LoRA and training configuration, training, merging weights); evaluating generative models (word-level metrics, benchmarks, leaderboards, automated and human evaluation); and preference tuning with reward models and with DPO.

<Flow steps={['pretrained base model', 'SFT on instruction data (QLoRA)', 'merge adapter', 'preference data: chosen vs rejected', 'DPO (or reward model + RL)', 'evaluate: benchmarks, judge, humans']} caption="The fine-tuning path for a generative model. Each stage needs its own data and its own evaluation." />

<Levels label="Chapter 12, Fine-Tuning Generation Models">

<Level name="Beginner">

A chat model is built in three steps: pretraining on lots of text (a base model
that continues text), supervised fine-tuning on instruction and response pairs (a
model that follows instructions), and preference tuning on which of two responses
people prefer (a model that answers the way people like). I can repeat the last
two on a small model with my own data.

```py
example = [{"role": "user", "content": "Summarise: the deploy failed because the env var was missing."},
           {"role": "assistant", "content": "Deploy failed: missing environment variable."}]
text = tok.apply_chat_template(example, tokenize=False)  # the template the model will train on
```

Common mistake: training on raw prompt and response text without the chat
template. Fix: apply the template so training matches how the model is used.

</Level>

<Level name="Intermediate">

Full fine-tuning updates every weight and needs a lot of memory. Parameter-
efficient fine-tuning updates a small set: adapters, or LoRA, which learns two
small low-rank matrices per chosen weight matrix. QLoRA loads the base model in
4-bit and trains LoRA adapters on top, which fits a few-billion-parameter model on
one consumer GPU.

```py
from peft import LoraConfig
from transformers import BitsAndBytesConfig
bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_compute_dtype="bfloat16")
lora = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05, target_modules=["q_proj", "k_proj", "v_proj", "o_proj"], task_type="CAUSAL_LM")
```

After training, the adapter can be merged into the base weights for simpler
serving.

Common mistake: targeting only one projection with a tiny rank and concluding
LoRA does not work. Fix: target the attention projections (and often the
feedforward ones) and compare a few ranks.

</Level>

<Level name="Advanced">

Training configuration matters: learning rate and schedule, batch size with
gradient accumulation, number of epochs, and sequence length. Evaluating a
generative model is hard: word-level metrics (perplexity, ROUGE, BLEU) miss
quality; benchmarks measure general skills and can be contaminated; leaderboards
aggregate benchmarks; automated evaluation uses a strong model as a judge; human
evaluation, including pairwise comparison, remains the reference.

Preference tuning can use a reward model, trained to score a prompt and response
so preferred responses score higher, followed by reinforcement learning (PPO) to
maximise the reward. DPO skips the reward model: it trains directly on chosen and
rejected pairs, increasing the likelihood of the chosen response relative to a
reference model. It is simpler and more stable to run.

```py
pref = {"prompt": "Explain a race condition in one sentence.",
        "chosen": "Two operations interleave so the result depends on timing.",
        "rejected": "It is when code runs fast."}
```

Common mistake: preference data where "chosen" is only longer, not better. Fix:
pairs that differ in the quality I want, checked by hand.

</Level>

<Level name="Edge cases">

One boundary each. One epoch too many: the model memorises responses and repeats
them verbatim. A sequence length shorter than my examples: responses are cut, and
the model learns to stop mid-sentence. A dataset in the wrong template: the model
learns to output template tokens as text. DPO with a high beta or learning rate:
outputs collapse into short, safe answers.

```py
lens = [len(tok(t)["input_ids"]) for t in texts]
print(max(lens), sum(l > 1024 for l in lens))  # how many examples a 1024 cut would truncate
```

Common mistake: not checking example lengths before choosing the sequence length.
Fix: measure and set it to cover nearly all examples.

</Level>

<Level name="Corner cases">

Two boundaries meet. QLoRA training plus merging into a 4-bit base: merging
adapters into quantised weights loses precision; merge into a higher-precision
copy instead. SFT on a narrow task plus general use: the model gets better at my
task and worse at following other instructions. A judge model plus preference
data from the same model: the tuned model learns the judge's taste, not users'.

Common mistake: evaluating the merged model with a different template than
training. Fix: the same chat template from training to serving.

</Level>

<Level name="Production level">

In production a fine-tuned generator is an artefact with base model, data,
adapter, merge settings and eval results recorded. It is compared against the
best prompted baseline on the eval set, with cost and latency. It needs a
re-training plan when the base model is upgraded, because adapters do not
transfer across base models.

```yaml
artifact: notes-assistant-dpo@v1
base: open-instruct-3b@2025-02
sft: notes-sft@v4 (1,200 pairs), qlora r=16
dpo: notes-pref@v2 (600 pairs), beta=0.1
eval: { judge_win_rate_vs_prompted: 0.58, n: 200, human_check: 50 }
```

Common mistake: shipping a fine-tune that only beats the base model, not the best
prompt. Fix: the prompted baseline is the bar.

</Level>

<Level name="Mindset">

Fine-tuning a generator is changing behaviour with data. The habit is to be
precise about the behaviour, collect data that shows exactly it, and measure
against the cheapest alternative.

Common mistake: fine-tuning for knowledge. Fix: retrieval for facts, fine-tuning
for behaviour.

</Level>

<Level name="System design">

<Figure art={`

                                                   +--> merge (fp16) --> serve
  preference pairs --> DPO from A -----> adapter B -+         |
                                                          eval gate:
                                         benchmarks + judge + human sample
                                         vs best prompted baseline
`} caption="Where each dataset enters and where the gate sits. Nothing is served without beating the prompted baseline." />

Common mistake: no eval gate between training and serving. Fix: an automated

</Level>

<Level name="Strategy">

After phase 8, I instruction-tune a small model with QLoRA on 1,000 of my own
note summaries, then run DPO on 300 preference pairs I check by hand, and compare

Done when the comparison shows a measured win or loss with sample sizes, and I
can say whether to keep the fine-tune.

</Level>

## Misreadings to avoid

- **"LLM means a chatbot."** Half the book is representation models, which are
  often the cheaper and better tool for search and classification.
- **"Embeddings capture meaning."** They capture the similarity their training
  pairs defined; my domain may need different pairs.
- **"RAG is a prompt pattern."** It is search first; retrieval metrics come
  before prompt tweaks.
- **"Fine-tuning is how you add knowledge."** It shapes behaviour; retrieval
  supplies facts.
- **"The code is the lesson."** The pictures are: tokens, vectors, attention,
  pipelines. Libraries change; the mechanisms do not.
