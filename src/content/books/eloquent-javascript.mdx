## Why this book

This is one of the two primary books for phase 1 of the
<a href={withBase('/plans/software-ai-developer/')}>software AI developer</a> roadmap, core programming
from first principles. The phase says it plainly: I am not here to learn syntax, I am here to learn what the
runtime is doing when the syntax succeeds. I already write JavaScript and TypeScript every day, which is
exactly why I need a book that starts from values and builds up to a working language, a browser game and a
Node server. The habits I skipped when I learned JavaScript by shipping are the habits this book teaches.

It is free online, it has runnable exercises in every chapter, and its five project chapters (a robot, a
programming language, a platform game, a pixel editor and a skill-sharing site) are the closest thing to the
phase's "build" requirement in any JavaScript book. *You Don't Know JS Yet* is the other primary book; I use
this one for breadth and projects, and that one for the language's exact rules.

## How I would learn it

I read it in the browser with a second tab open on the book's own code sandbox and a terminal running Node 22.
For each chapter I read once quickly, then retype every example instead of pasting it, then do every exercise
before looking at any solution. When an exercise passes on the first try I make it fail on purpose: an empty
array, a `null`, a string where a number was expected. That is where the nine levels below come from.

Every chapter also gets a TypeScript pass: I port the chapter's main example to strict TypeScript and write
down what the compiler caught that JavaScript allowed. The project chapters get their own repository folder
with tests, because the phase gate (a router, a JSON parser and a rate limiter from scratch, plus explaining
the event loop) needs exactly the muscles those projects build.

Every chapter below climbs the same nine levels: what it is, how it combines, what happens underneath, the

## What I learn from it

- How every JavaScript value is one of a small set of types, and how operators coerce between them.
- Bindings, scope, closures and recursion, and how the call stack makes them work.
- Arrays, objects, mutation versus identity, and JSON as a data boundary.
- Higher-order functions as the way to abstract over actions, not just values.
- Prototypes, classes, getters, symbols and the iterator protocol.
- Modelling state as values that are replaced, not changed, in the robot project.
- Strict mode, testing, debugging, exceptions, `finally` and assertions.
- Regular expressions: syntax, groups, flags, `lastIndex`, Unicode and parsing with them.
- Modules: ES modules versus CommonJS, packages, and the design of small interfaces.
- Callbacks, promises, `async` functions, generators and the event loop, including its ordering rules.
- How a programming language works, by building a parser, an evaluator and a scope model.
- The browser: the DOM tree, events, propagation, timers, layout, styles from script and the canvas.
- HTTP, forms, `fetch`, local storage and the file input.
- Node.js: modules, the file system, an HTTP server, streams, and a long-polling application.

## Part 1, Language

### Introduction

**Covers:** What programming is, why JavaScript, how code and data look in the book, and how to run the examples.

<Flow steps={['idea', 'program text', 'engine parses', 'engine runs', 'output or effect']} caption="A program is text an engine turns into behaviour. Every later chapter is a step in that pipeline." />

<Levels label="Introduction">

<Level name="Beginner">

A program is precise text that tells a computer what to do, and JavaScript is the language every browser and
Node runs. The smallest thing that works is one line:

```js
console.log("hello, world");
// hello, world
```

Mistake: treating the browser console as the program. Fix: save the line in `hello.js` and run `node hello.js`,
so a file is the unit of work from day one.

</Level>

<Level name="Intermediate">

The book's examples show expressions together with the output they produce. I copy that discipline: every snippet
in my notes has its expected output written next to it, so I can tell exactly when my mental model is wrong.

```js
let total = 0;
for (let i = 1; i <= 10; i++) total += i;
console.log(total); // 55
```

Mistake: reading examples without predicting their output first. Fix: write the prediction, then run it.

</Level>

<Level name="Advanced">

JavaScript is standardised as ECMAScript. Browsers and Node implement the same core language and add their own
host APIs: the DOM in one, the file system in the other. Knowing which line is language and which is host is the
first real skill. `Math.max` is language; `document` and `process` are host.

```js
console.log(typeof globalThis.document); // "undefined" in Node, "object" in a browser
```

Mistake: assuming a global exists everywhere. Fix: check the environment, or reach globals through `globalThis`.

</Level>

<Level name="Edge cases">

An old engine fails on new syntax before a single line runs, because parsing fails first:

```
SyntaxError: Unexpected token '?'
```

That error on `a ?? b` means the engine predates nullish coalescing. Mistake: debugging the logic. Fix: check
`node --version` and the build target first.

</Level>

<Level name="Corner cases">

A script and a module are parsed differently. In a module, top-level `await` works and top-level `this` is
`undefined`; in a classic script, top-level `await` is a syntax error and `this` is the global object. The same
file means two things depending on how it is loaded. Fix: choose modules (`"type": "module"` or `.mjs`) and stay
there.

</Level>

<Level name="Production level">

For other people, "it works in my console" means nothing. Code runs on their browser version, their locale, their
slow phone. The production habit from day one: a pinned Node version (`.nvmrc` or `engines`), a lint step, and a
test that runs in CI.

</Level>

<Level name="Mindset">

Programming is managing complexity with precise language. The computer is literal and patient; I should be
literal and patient too, and stop guessing.

</Level>

<Level name="System design">

JavaScript sits at the edge of most systems I build: it renders the UI, validates the form and often runs the API.
One language on both sides makes the boundary between them (what runs where, what is trusted) the main design
decision.

</Level>

<Level name="Strategy">

I set up a folder per chapter with a `package.json`, a test runner and a `notes.md`. Done when I can run any example
from the book in both Node and the browser and say which lines are language and which are host.

</Level>

</Levels>

### 1. Values, Types, and Operators

**Covers:** Numbers, strings, booleans, `null` and `undefined`, the operators on them, and automatic type conversion.

<Figure art={`
  value
   +-- number ...... 13, -0, 0.1, NaN, Infinity
   +-- bigint ...... 13n
   +-- string ...... "half of 100 is 50"
   +-- boolean ..... true, false
   +-- undefined
   +-- null
   +-- symbol ...... Symbol("id")
   +-- object ...... everything else (arrays, functions, dates)
`} caption="The value types: seven primitives and one object type. typeof reports a function as 'function' and null as 'object'." />

<Levels label="Chapter 1, Values, Types, and Operators">

<Level name="Beginner">

Every value has a type. Numbers are 64-bit floats, strings are text, booleans are `true` or `false`, and two values
mean "nothing": `undefined` (never set) and `null` (set to nothing on purpose).

```js
console.log(typeof 42, typeof "42", typeof true, typeof undefined);
// number string boolean undefined
```

Mistake: expecting `typeof null` to be `"null"`. It prints `"object"`, an old bug kept for compatibility. Fix: test
with `value === null`.

</Level>

<Level name="Intermediate">

Operators combine values: arithmetic (`+ - * / % **`), comparison, logical (`&&`, `||`, `!`) and the conditional
`a ? b : c`. Logical operators return one of their operands, not a boolean, which is why they work for defaults.

```js
console.log(null || "user"); // user
console.log("" || "user");   // user, because "" is falsy
console.log("" ?? "user");   // "" because ?? only skips null and undefined
```

Mistake: `count || 10` when `count` can legitimately be `0`. Fix: `count ?? 10`.

</Level>

<Level name="Advanced">

Numbers are IEEE 754 doubles: integers are exact up to 2 to the 53rd, and decimal fractions are approximations.
Automatic conversion follows fixed rules: `+` prefers strings if either side is a string, the other arithmetic
operators convert to numbers, and `==` runs a conversion algorithm that `===` skips.

```js
console.log(0.1 + 0.2);                   // 0.30000000000000004
console.log("5" + 1, "5" - 1);            // 51 4
console.log(Number.MAX_SAFE_INTEGER + 2); // 9007199254740992, off by one
```

Mistake: adding money as floats. Fix: store integer cents, and use `BigInt` for counts beyond 2 to the 53rd.

</Level>

<Level name="Edge cases">

`NaN` is the only value not equal to itself, and `-0` equals `0` under `===`.

```js
console.log(NaN === NaN, Number.isNaN(NaN)); // false true
console.log(0 === -0, Object.is(0, -0));     // true false
console.log(1 / -0);                         // -Infinity
```

Mistake: `if (x === NaN)`, which is always false. Fix: `Number.isNaN(x)`, never the global `isNaN`, which converts
first (`isNaN("abc")` is `true`).

</Level>

<Level name="Corner cases">

Two conversions meet when `==` compares an object with a primitive: the object becomes a primitive first, then the
comparison converts again.

```js
console.log([] == false);  // true: [] -> "" -> 0, and false -> 0
console.log([0] == false); // true
console.log([] == []);     // false: two different objects
```

The empty array is truthy (`if ([])` runs) and yet loosely equal to `false`. Mistake: reasoning about `==` from
truthiness. Fix: `===` everywhere, and convert explicitly with `Number()` or `String()`.

</Level>

<Level name="Production level">

Production bugs from this chapter: form inputs (every `input.value` is a string, so `"2" + 1` is `"21"`), JSON numbers
above 2 to the 53rd (IDs from other systems silently lose digits), and money in floats. The habits: parse at the
boundary with `Number()` and check `Number.isFinite`, keep large IDs as strings, and turn on the `eqeqeq` lint rule.

</Level>

<Level name="Mindset">

A type is a contract about what a value can do. JavaScript checks that contract late and quietly, so I make it
explicit: in my head first, in TypeScript second.

</Level>

<Level name="System design">

Every system boundary (HTTP, a database driver, `localStorage`) hands me strings or loosely typed JSON. The design
decision is where conversion happens: once, at the edge, with a validator, so the inside of the system only ever
sees the types it expects.

</Level>

<Level name="Strategy">

I write a table of 20 expressions mixing types, predict each result, then run them. Done when I get every row right
and can explain why `[] + {}` is `"[object Object]"` from the conversion rules rather than from memory.

</Level>

</Levels>

### 2. Program Structure

**Covers:** Expressions and statements, bindings, the environment, functions as values, control flow with `if`, `while`, `do`, `for` and `switch`, `break` and `continue`, naming and comments.

<Flow steps={['check condition', 'true: run body', 'run update', 'back to condition', 'false: leave loop']} caption="A loop is a condition checked before every pass. The update step is the one that gets forgotten, and then the loop never ends." />

<Levels label="Chapter 2, Program Structure">

<Level name="Beginner">

An expression produces a value; a statement does something. A binding (`let`, `const`) gives a value a name.

```js
const name = "Sanjay";
let count = 0;
count = count + 1;
console.log(`${name}: ${count}`); // Sanjay: 1
```

Mistake: `const` for something I later reassign. The error is `TypeError: Assignment to constant variable.` Fix:
`let` for values that change, `const` for everything else.

</Level>

<Level name="Intermediate">

Conditions and loops combine into real programs: FizzBuzz, a chessboard, a triangle of hashes. The chapter's
exercises are exactly this shape.

```js
for (let n = 1; n <= 15; n++) {
  let out = "";
  if (n % 3 === 0) out += "Fizz";
  if (n % 5 === 0) out += "Buzz";
  console.log(out || n);
}
```

Mistake: an `else if` chain that tests `% 3` before the combined case, so 15 prints only "Fizz". Fix: build the
string, or test the combined case first.

</Level>

<Level name="Advanced">

`const` makes the binding constant, not the value: `const list = []; list.push(1)` is fine. `let` and `const` are
block-scoped; `var` is function-scoped. `switch` compares with `===` and falls through until a `break`.

```js
switch ("2") {
  case 2: console.log("number"); break;
  case "2": console.log("string");
}
// string
```

Mistake: expecting `switch` to coerce the way `==` does. Fix: normalise the type before the switch.

</Level>

<Level name="Edge cases">

Loop boundaries: `i <= arr.length` reads one past the end and gets `undefined`, silently.

```js
const arr = [1, 2, 3];
for (let i = 0; i <= arr.length; i++) console.log(arr[i]);
// 1 2 3 undefined
```

Fix: `i < arr.length`, or better `for (const x of arr)`. A `while` whose body never changes the condition hangs the
tab with no error at all.

</Level>

<Level name="Corner cases">

A missing `break` plus a `return` in a later case: execution falls into the next case's side effects before it
reaches the return. Two features (fall-through and early exit) interact, and the bug only shows for one input. Fix:
one exit per case, and the `no-fallthrough` lint rule.

</Level>

<Level name="Production level">

In production, structure is for the reader: short functions, shallow nesting, and names that say what a value is
rather than its type (`unpaidInvoices`, not `arr2`). The chapter's advice on naming and comments is the same advice
code review gives.

</Level>

<Level name="Mindset">

A program is read far more often than it is written. Every control-flow choice is a choice about how easily the next
person can follow the path.

</Level>

<Level name="System design">

Control flow is where business rules live. In a larger system I want each rule's branching in one place (a function
or a lookup table), not copied across handlers, because copied conditions drift apart.

</Level>

<Level name="Strategy">

I do every exercise in the chapter twice: once with loops, once with array methods after chapter 5. Done when my
chessboard works for any size, including 0 and 1, with no off-by-one.

</Level>

</Levels>

### 3. Functions

**Covers:** Defining functions, bindings and scopes, nested scope, functions as values, declaration notation, arrow functions, the call stack, optional arguments, closure, recursion, growing functions, and functions and side effects.

<Figure art={`
  call stack (grows down)            heap
  +----------------------+          +----------------------+
  | main                 |          | closure environment  |
  +----------------------+          |   factor = 2         |
  | multiplier(2)        | -------> +----------------------+
  +----------------------+                    ^
  returns twice = n => n * factor             |
  multiplier's frame is gone, but twice still points here
`} caption="A closure: the inner function keeps a reference to the environment it was created in, after the outer call has returned." />

<Levels label="Chapter 3, Functions">

<Level name="Beginner">

A function is a value that wraps a piece of program. Call it with arguments and get a return value.

```js
const square = (x) => x * x;
function power(base, exponent = 2) {
  let result = 1;
  for (let i = 0; i < exponent; i++) result *= base;
  return result;
}
console.log(square(12), power(2, 10)); // 144 1024
```

Mistake: forgetting `return` in a block-bodied arrow, so it returns `undefined`. Fix: a concise body
`(x) => x * x`, or an explicit `return`.

</Level>

<Level name="Intermediate">

Closures let a function remember where it was born. A function that returns a function is the basis of counters,
memoisation and configuration.

```js
function multiplier(factor) {
  return (n) => n * factor;
}
const twice = multiplier(2);
console.log(twice(5)); // 10
```

Mistake: believing `factor` is copied. It is referenced: if something changes it later, the closure sees the new
value. Fix: treat captured variables as shared state.

</Level>

<Level name="Advanced">

Each call creates a new environment and pushes a frame on the call stack. Recursion reuses one function with a new
environment per call; too deep, and the stack overflows.

```js
function depth(n) { return depth(n + 1); }
try { depth(0); } catch (e) { console.log(e instanceof RangeError, e.message); }
// true Maximum call stack size exceeded
```

Function declarations are hoisted (callable before their line); arrow functions bound with `const` are not. Mistake:
recursion over 100,000-element inputs. Fix: an explicit stack or a loop.

</Level>

<Level name="Edge cases">

Too few arguments become `undefined`, too many are ignored, and defaults apply only for `undefined`, not `null`.

```js
function greet(name = "friend") { return `hi ${name}`; }
console.log(greet(), greet(undefined), greet(null)); // hi friend hi friend hi null
```

Fix: decide whether `null` means "use the default", and normalise with `name ?? "friend"` inside.

</Level>

<Level name="Corner cases">

Closures in a loop plus `var`: every callback shares the one function-scoped binding.

```js
const fns = [];
for (var i = 0; i < 3; i++) fns.push(() => i);
console.log(fns.map((f) => f())); // [ 3, 3, 3 ]
```

With `let`, each iteration gets a fresh binding and the output is `[ 0, 1, 2 ]`. Fix: never use `var`.

</Level>

<Level name="Production level">

Side effects make functions hard to test and reuse. In production code I keep pure functions (same input, same
output) as most of the codebase and push the few that touch the network or disk to the edges. Memory leaks often come
from closures holding large objects alive, such as a handler that captured a whole response body.

</Level>

<Level name="Mindset">

A function is a name for an idea. If I cannot name it, the idea is not clear yet. The chapter's "growing functions"
section is the habit: write the code, notice the repetition, then name the function.

</Level>

<Level name="System design">

Closures are how JavaScript does encapsulation without classes: modules, React hooks and middleware all rely on them.
A factory that returns closures is a dependency-injection point: the outer arguments are configuration, the inner
function is behaviour.

</Level>

<Level name="Strategy">

I write `min`, recursive `isEven` and `countChar` from the exercises, then a memoised Fibonacci with a closure cache.
Done when I can draw the call stack and closure environments for `multiplier` on paper, and `isEven(-1)` no longer
overflows.

</Level>

</Levels>

### 4. Data Structures: Objects and Arrays

**Covers:** The weresquirrel journal, data sets, properties, methods, objects, mutability, computing correlation, array loops, further arrayology, strings and their properties, rest parameters, the `Math` object, destructuring, optional property access and JSON.

<Figure art={`
  const a = { x: 1 };     const b = a;     const c = { x: 1 };

   a ---+
        +---->  { x: 1 }  <---- b          a === b   true
                                           a === c   false
   c -------->  { x: 1 }                   same content, different object
`} caption="Identity versus content. Two bindings can point at one object; two objects with the same content are still two values." />

<Levels label="Chapter 4, Data Structures: Objects and Arrays">

<Level name="Beginner">

Arrays hold ordered values; objects hold named properties. Bindings point at them.

```js
const day = { events: ["work", "pizza"], squirrel: false };
day.events.push("running");
console.log(day.events.length, day["squirrel"]); // 3 false
```

Mistake: a typo like `day.event` reads `undefined` with no error. Fix: TypeScript, or `Object.hasOwn(day, key)` when
the key is dynamic.

</Level>

<Level name="Intermediate">

The chapter's journal example computes a correlation (the phi coefficient) between an event and an outcome over a
list of days. The shape is the everyday one: loop over records, count into a small table, compute.

```js
function tableFor(event, journal) {
  const table = [0, 0, 0, 0];
  for (const { events, squirrel } of journal) {
    let index = 0;
    if (events.includes(event)) index += 1;
    if (squirrel) index += 2;
    table[index] += 1;
  }
  return table;
}
```

Mistake: mutating the journal while analysing it. Fix: read-only loops that return new values.

</Level>

<Level name="Advanced">

Objects compare by identity, not content; strings and numbers compare by value. Spread copies one level deep;
`structuredClone` copies deeply. JSON can hold only plain data: no functions, no `undefined`, no `Date` (it becomes a
string), no `Map`, and `NaN` becomes `null`.

```js
console.log(JSON.stringify({ when: new Date(0), skip: undefined, n: NaN }));
// {"when":"1970-01-01T00:00:00.000Z","n":null}
```

Mistake: expecting `JSON.parse(JSON.stringify(x))` to round-trip. Fix: a schema that revives dates explicitly.

</Level>

<Level name="Edge cases">

Arrays have holes and surprising lengths: `new Array(3)` has length 3 and no elements, and `arr[10] = 4` on a
three-element array makes the length 11.

```js
const arr = [1, 2, 3];
arr[10] = 4;
console.log(arr.length, arr[5]);       // 11 undefined
console.log([, 1].map((x) => x * 2));  // [ <1 empty item>, 2 ]
```

Fix: never write past the end on purpose; build arrays with `push` or `Array.from({ length: n }, fn)`.

</Level>

<Level name="Corner cases">

Destructuring defaults meet `null`:

```js
const user = { profile: null };
const { profile: { name = "anon" } = {} } = user;
// TypeError: Cannot read properties of null (reading 'name')
```

The default `= {}` applies only to `undefined`, and `profile` is `null`. Fix:
`const name = user.profile?.name ?? "anon";`.

</Level>

<Level name="Production level">

Shared mutable objects cause the hardest production bugs: a cached config object one request mutates and the next
request reads. The habits: freeze shared constants with `Object.freeze`, copy before changing, and validate every JSON
payload against a schema at the boundary.

</Level>

<Level name="Mindset">

Before every mutation I ask: who else holds a reference to this? That one question prevents most aliasing bugs.

</Level>

<Level name="System design">

JSON is the common language between my services, my database's JSON columns and my front end. Its limits (no dates,
no big integers, no cycles) are design constraints: ISO strings for dates and strings for 64-bit IDs, decided once in
the API contract.

</Level>

<Level name="Strategy">

I write `range`, `sum`, `reverseArray`, `reverseArrayInPlace`, the list helpers and `deepEqual` from the exercises, then
test `deepEqual` against `NaN`, `null`, arrays versus objects and cycles. Done when it handles each of those, and I can
say which ones it deliberately does not.

</Level>

</Levels>

### 5. Higher-order Functions

**Covers:** Abstraction, abstracting repetition, higher-order functions, the script data set, filtering arrays, transforming with `map`, summarising with `reduce`, composability, strings and character codes, and recognising text.

<Flow steps={['array of records', 'filter: keep some', 'map: transform each', 'reduce: fold into one value']} caption="The pipeline the chapter builds. Each step takes a function that says what to do with one element." />

<Levels label="Chapter 5, Higher-order Functions">

<Level name="Beginner">

A higher-order function takes a function as an argument or returns one. `filter`, `map` and `reduce` are the three I
use every day.

```js
const nums = [1, 2, 3, 4, 5];
console.log(nums.filter((n) => n % 2).map((n) => n * 10).reduce((a, b) => a + b, 0));
// 90
```

Mistake: `reduce` with no initial value on an empty array throws
`TypeError: Reduce of empty array with no initial value`. Fix: always pass the initial value.

</Level>

<Level name="Intermediate">

The chapter uses a data set of writing systems with their Unicode ranges and asks which script a piece of text is
written in: filter, group and count, then pick the largest group.

```js
function countBy(items, groupName) {
  const counts = new Map();
  for (const item of items) {
    const name = groupName(item);
    counts.set(name, (counts.get(name) ?? 0) + 1);
  }
  return counts;
}
console.log(countBy([1, 2, 3, 4, 5], (n) => n > 2)); // Map(2) { false => 2, true => 3 }
```

Mistake: grouping into a plain object, where a key like `"__proto__"` misbehaves. Fix: a `Map`, or `Map.groupBy`.

</Level>

<Level name="Advanced">

Strings are UTF-16: characters outside the Basic Multilingual Plane, like most emoji, take two code units. `length`
and indexing count code units; `for...of` and `codePointAt` work in code points.

```js
const s = "🐴👟";
console.log(s.length, [...s].length); // 4 2
console.log(s.codePointAt(0), s.charCodeAt(0)); // 128052 55357
```

Mistake: trimming user text with `slice(0, 10)` and cutting an emoji in half. Fix: `Array.from(s).slice(0, 10).join("")`,
or `Intl.Segmenter` for whole graphemes.

</Level>

<Level name="Edge cases">

`map` passes three arguments (value, index, array), which surprises functions with optional parameters:

```js
console.log(["1", "2", "3"].map(parseInt)); // [ 1, NaN, NaN ]
```

`parseInt` receives the index as its radix. Fix: `map((s) => parseInt(s, 10))` or `map(Number)`. Also, `forEach`
cannot be stopped with `break`; use `for...of` or `some` when I need to stop early.

</Level>

<Level name="Corner cases">

A callback that mutates the array being iterated: `filter` and `map` fix the length when they start, so pushed
elements are skipped and removed ones shift the rest. The output depends on the order of two rules. Fix: never mutate
inside a higher-order callback; build a new array.

</Level>

<Level name="Production level">

Each step of a chain allocates an intermediate array. For ten items that is nothing; for a million rows in a Node
report it is memory pressure and garbage-collection pauses. I measure first, then fuse steps into one loop only where
the profiler points.

</Level>

<Level name="Mindset">

Abstract over actions, not only values. Two loops that differ in one line are a function argument waiting to be
named.

</Level>

<Level name="System design">

Higher-order functions are the shape of middleware, retry wrappers, React render props and every `withX(handler)` in a
codebase. They are how I add cross-cutting behaviour (logging, auth, timing) without editing every handler.

</Level>

<Level name="Strategy">

I do the flattening, your-own-loop, `every` and dominant writing direction exercises, then rewrite chapter 4's journal
analysis with only `filter`, `map` and `reduce`. Done when I can implement `map`, `filter` and `reduce` myself with the
same callback arguments the built-ins pass.

### 6. The Secret Life of Objects

**Covers:** Abstract data types, methods, prototypes, classes, private properties, overriding derived properties, maps, polymorphism, getters, setters and statics, symbols, the iterator interface, inheritance and the `instanceof` operator.

<Figure art={`
  rabbit --[[Prototype]]-->  Rabbit.prototype --> Object.prototype --> null

  rabbit.speak()      found on Rabbit.prototype

<Levels label="Chapter 6, The Secret Life of Objects">

<Level name="Beginner">

An object can carry methods, and `this` inside a method is the object it was called on. A class is a template for
objects that share methods.

```js
class Rabbit {
  constructor(type) { this.type = type; }
  speak(line) { return `The ${this.type} rabbit says '${line}'`; }
}
console.log(new Rabbit("white").speak("hi")); // The white rabbit says 'hi'
```

Mistake: calling a class without `new`:
`TypeError: Class constructor Rabbit cannot be invoked without 'new'`.

</Level>

<Level name="Intermediate">

Private fields, getters, setters and static methods turn a class into an abstract data type with a small public
interface.

```js
class Temperature {
  #celsius = 0;
  get fahrenheit() { return this.#celsius * 1.8 + 32; }
  set fahrenheit(f) { this.#celsius = (f - 32) / 1.8; }
  static fromFahrenheit(f) { const t = new Temperature(); t.fahrenheit = f; return t; }
}
console.log(Temperature.fromFahrenheit(212).fahrenheit); // 212
```

Mistake: exposing the internal field so callers can set invalid states. Fix: private fields, and validation in the
setter.

</Level>

<Level name="Advanced">

`this` is decided at the call site, not where the function is written. A method pulled off its object loses `this`;
an arrow function has no `this` of its own and uses the enclosing one. Class bodies are strict, so the lost `this` is
`undefined`, not the global object.

```js
const r = new Rabbit("black");
const speak = r.speak;
try { speak("x"); } catch (e) { console.log(e.message); }
// Cannot read properties of undefined (reading 'type')
```

Fix: `r.speak.bind(r)` or an arrow wrapper at the point where the method is passed along.

</Level>

<Level name="Edge cases">

A plain object used as a dictionary has inherited keys:

```js
const ages = { Boris: 39 };
console.log("toString" in ages, Object.hasOwn(ages, "toString")); // true false
console.log(new Map([["Boris", 39]]).has("toString"));           // false
```

Fix: a `Map` for dictionaries with user-controlled keys, or `Object.create(null)`.

</Level>

<Level name="Corner cases">

Iteration meets mutation: a custom iterator over a class's internal array while the caller adds elements inside the
`for...of`. Depending on how `next` reads the length, the loop either picks up new elements or never ends. Fix:
iterate a snapshot, or document that mutation during iteration is not allowed.

```js
class Group {
  #items = [];
  add(x) { if (!this.#items.includes(x)) this.#items.push(x); }
  *[Symbol.iterator]() { yield* [...this.#items]; } // iterate a snapshot
}
```

</Level>

<Level name="Production level">

Deep inheritance trees become the hardest code to change, because every base-class method is a contract all
subclasses silently rely on. I prefer composition and keep inheritance to one level for real is-a relationships.
`instanceof` fails across realms (an array from an iframe or a worker), so at boundaries I use `Array.isArray` and
duck typing.

</Level>

<Level name="Mindset">

An interface is a promise. The polymorphism section is the core habit: code against what an object can do
(`toString`, `Symbol.iterator`), not against what it is.

</Level>

<Level name="System design">

Encapsulation is how a module protects its invariants from the rest of the system. A class with private fields and a
small API is the same design move, at a smaller scale, as a service with a narrow HTTP interface.

</Level>

<Level name="Strategy">

I build the `Vec` class, the `Group` class with its iterator, and the borrowing-a-method exercise, then port them to
TypeScript with `implements Iterable`. Done when I can draw the prototype chain that explains why `rabbit.hasOwnProperty`

### 7. Project: A Robot

**Covers:** Meadowfield's roads, the task, persistent data, simulation, the mail truck's route, pathfinding, and the exercises on measuring and improving robots.

<Figure art={`
  state  = { place: "Post Office", parcels: [p1, p2, p3] }
     |
     |  state.move("Alice's House")   returns a NEW state
     v
  state' = { place: "Alice's House", parcels: [p2, p3] }

  the old state is untouched: easy to compare, replay and test
`} caption="The robot never mutates the world. Each move returns a new state, so any two states can be compared." />

<Levels label="Chapter 7, Project: A Robot">

<Level name="Beginner">

A robot delivers parcels around a small village graph. The state is where the robot is and which parcels are left;
a move returns a new state rather than changing the old one.

```js
class VillageState {
  constructor(place, parcels) { this.place = place; this.parcels = parcels; }
  move(dest) {
    const parcels = this.parcels
      .map((p) => (p.place !== this.place ? p : { place: dest, address: p.address }))
      .filter((p) => p.place !== p.address);
    return new VillageState(dest, parcels);
  }
}
```

Mistake: pushing into `this.parcels` inside `move`. Fix: always return a new state; the old one must stay valid.

</Level>

<Level name="Intermediate">

The roads are a list of strings turned into an adjacency map, and then robots of increasing intelligence are tried:
a random walker, a fixed mail-truck route, and a goal-oriented robot that plans a path to each parcel.

```js
function buildGraph(edges) {
  const graph = Object.create(null);
  const add = (from, to) => (graph[from] ??= []).push(to);
  for (const [from, to] of edges.map((r) => r.split("-"))) { add(from, to); add(to, from); }
  return graph;
}
```

Mistake: adding each road in one direction only. Fix: roads are undirected, so add both.

</Level>

<Level name="Advanced">

The goal-oriented robot uses breadth-first search. BFS explores places in order of distance, so the first time it
reaches the target the route is a shortest one.

```js
function findRoute(graph, from, to) {
  const work = [{ at: from, route: [] }];
  for (let i = 0; i < work.length; i++) {
    const { at, route } = work[i];
    for (const place of graph[at]) {
      if (place === to) return [...route, place];
      if (!work.some((w) => w.at === place)) work.push({ at: place, route: [...route, place] });
    }
  }
}
```

Mistake: depth-first search, which finds a valid but long route. Fix: a queue (BFS) for unweighted shortest paths.

</Level>

<Level name="Edge cases">

Boundaries: zero parcels (the robot should stop at once), a parcel already at its address, and an unreachable place,
where BFS returns `undefined`.

```js
console.log(findRoute(buildGraph(["A-B"]), "A", "Z")); // undefined
```

Fix: treat `undefined` as "cannot deliver" and report it, instead of crashing on `route[0]`.

</Level>

<Level name="Corner cases">

Randomness meets measurement: comparing two robots on different random tasks compares noise. Fix: generate the 100
tasks once and run both robots on the same ones, then compare the average number of steps.

</Level>

<Level name="Production level">

The production lesson is persistence. Immutable state makes undo, replay, time-travel debugging and safe concurrent
readers easy, at the cost of allocation. Redux reducers, React state and event-sourced backends all apply this
chapter; structural sharing (copy only the changed path) keeps the cost down when state is large.

</Level>

<Level name="Mindset">

Model the world as values, and change as functions from one value to the next. Then behaviour is something I test by
comparing values.

</Level>

<Level name="System design">

The robot is a tiny planner: state, actions, a goal and a search. That is the loop of a job scheduler or an agent that
plans tool calls, and the same failure (an unreachable goal) needs the same answer: detect it and stop.

</Level>

<Level name="Strategy">

I build all three robots, then the measuring-a-robot, robot-efficiency and persistent-group exercises. Done when my
robot beats the goal-oriented one on the same 100 tasks and I can say why.

</Level>

### 8. Bugs and Errors

**Covers:** Language strictness, types, testing, debugging, error propagation, exceptions, cleaning up after exceptions, selective catching and assertions.

<Flow steps={['throw', 'unwind the call stack', 'nearest try/catch', 'finally blocks run', 'or uncaught: the program stops']} caption="An exception jumps out of every function between the throw and the nearest catch, running each finally on the way." />

<Levels label="Chapter 8, Bugs and Errors">

<Level name="Beginner">

Bugs are the gap between what I meant and what I wrote. Strict mode, which is automatic in modules and classes, turns
some silent mistakes into errors.

```js
"use strict";
function f() { counter = 1; }
try { f(); } catch (e) { console.log(e.name, e.message); }
// ReferenceError counter is not defined
```

Without strict mode the same code silently creates a global. Fix: write modules, which are strict by default.

</Level>

<Level name="Intermediate">

Errors travel either as special return values or as exceptions. Exceptions let deep code fail without every caller
checking.

```js
class InputError extends Error {}
function promptDirection(input) {
  const d = input.toLowerCase();
  if (d === "left" || d === "right") return d;
  throw new InputError(`Invalid direction: ${input}`);
}
try { promptDirection("up"); }
catch (e) { if (e instanceof InputError) console.log(e.message); else throw e; }
// Invalid direction: up
```

Mistake: a bare `catch` that swallows everything, including my own typos. Fix: catch selectively and rethrow the rest.

</Level>

<Level name="Advanced">

`finally` runs whether the `try` returns, throws or finishes, so it is the place for cleanup. A `return` in
`finally` overrides the earlier return or throw.

```js
function f() { try { throw new Error("boom"); } finally { return "finally wins"; } }
console.log(f()); // finally wins, and the error is lost
```

Fix: never `return` from `finally`; use it only to release resources.

</Level>

<Level name="Edge cases">

Throwing something that is not an `Error` loses the stack trace:

```js
try { throw "oops"; } catch (e) { console.log(typeof e, e.stack); } // string undefined
```

Fix: throw `Error` objects or subclasses, and wrap a lower-level error with `new Error("msg", { cause: err })`.

</Level>

<Level name="Corner cases">

An exception halfway through a multi-step change leaves state half changed. The chapter's money-transfer example is
exactly this: money leaves one account and the error fires before it arrives. Fix: compute the whole new state first
and commit it in one step, or track progress and undo it in `finally`.

```js
function transfer(from, to, amount, getAccount) {
  let progress = 0;
  try {
    from.balance -= amount; progress = 1;
    getAccount(to).balance += amount; progress = 2; // may throw
  } finally {
    if (progress === 1) from.balance += amount;     // undo the half-done step
  }
}
```

</Level>

<Level name="Production level">

In production errors must reach a person: one top-level handler that logs with context and a correlation ID, an
error-tracking service, and a split between expected errors (bad input, a 400) and bugs (a 500 and an alert).
Assertions catch impossible states in development; they do not replace validation.

</Level>

<Level name="Mindset">

An error message is a note to a future me at 2 a.m.: what failed, with which input, and what to do next.

</Level>

<Level name="System design">

Error handling is a contract between layers. A repository throws `NotFoundError`, the service decides what it means,
and the HTTP layer maps it to a status code. The design decision is which layer translates which error, written down
once.

</Level>

<Level name="Strategy">

I do the retry exercise (a multiply that fails a fifth of the time) and the locked-box exercise with `finally`, then add
a test suite to chapter 7's robot. Done when I debug a failing test from its stack trace and one breakpoint, without
adding `console.log`.

</Level>

</Levels>

### 9. Regular Expressions

**Covers:** Creating a regular expression, testing for matches, sets of characters, international characters, repeating parts, grouping, matches and groups, the `Date` class, boundaries and look-ahead, choice patterns, the mechanics of matching, backtracking, `replace`, greed, dynamically creating regexes, `search`, `lastIndex`, looping over matches, parsing an INI file, and code units and characters.

<Figure art={`
  /\\b(\\d+) (pig|cow|chicken)s?\\b/

  word boundary --> one or more digits --> a space
     --> "pig" | "cow" | "chicken"  (tried left to right)
     --> optional "s" --> word boundary --> match
  on any failure: backtrack to the last choice and try the next branch
`} caption="A regex as a flow. The engine walks the pattern left to right and backtracks into alternatives when a step fails." />

<Levels label="Chapter 9, Regular Expressions">

<Level name="Beginner">

A regular expression describes a pattern of characters. `test` asks whether it matches; `exec` and `match` return
the match and its groups.

```js
console.log(/abc/.test("abcde")); // true
console.log("2026-10-23".match(/(\d+)-(\d+)-(\d+)/).slice(1)); // [ '2026', '10', '23' ]
```

Mistake: an unescaped dot, so `/1.5/` matches `"105"`. Fix: `/1\.5/`.

</Level>

<Level name="Intermediate">

Groups, named groups and `replace` with a function do real parsing work. The chapter ends by parsing an INI file line
by line.

```js
function parseINI(text) {
  const result = {};
  let section = result;
  for (const line of text.split(/\r?\n/)) {
    let m;
    if ((m = line.match(/^(\w+)=(.*)$/))) section[m[1]] = m[2];
    else if ((m = line.match(/^\[(.*)\]$/))) section = result[m[1]] = {};
    else if (!/^\s*(;|$)/.test(line)) throw new Error(`Line '${line}' is not valid.`);
  }
  return result;
}
console.log(parseINI("name=Vasilis\n[address]\ncity=Tessaloniki"));
// { name: 'Vasilis', address: { city: 'Tessaloniki' } }
```

Mistake: splitting on `"\n"`, which breaks on Windows line endings. Fix: `/\r?\n/`.

</Level>

<Level name="Advanced">

The engine is a backtracking matcher. Greedy quantifiers take as much as they can and give back; lazy ones (`*?`) take
as little as they can. Nested quantifiers over the same characters can make backtracking exponential.

```js
console.log("<a><b>".match(/<.*>/)[0]);  // <a><b>
console.log("<a><b>".match(/<.*?>/)[0]); // <a>
```

Mistake: `/(a+)+$/` on user input; thirty `a`s followed by `!` takes seconds (catastrophic backtracking). Fix: no
nested quantifiers over overlapping characters.

</Level>

<Level name="Edge cases">

The `g` and `y` flags make a regex stateful through `lastIndex`:

```js
const re = /a/g;
console.log(re.test("a"), re.test("a")); // true false
```

The second call starts at index 1, fails and resets. Fix: no `g` flag on a regex used with `test`, and `matchAll` for
loops. Also `\w` is ASCII-only: `/\w/.test("é")` is `false`, while `/\p{L}/u.test("é")` is `true`.

</Level>

<Level name="Corner cases">

A regex built from user input, with the `g` flag, reused in a loop: special characters in the input change the
pattern, and the shared `lastIndex` skips matches. Fix: escape the input, build the regex once per use, iterate with
`matchAll`.

```js
const escape = (s) => s.replace(/[\\^$.*+?()[\]{}|]/g, "\\$&");
const name = "dea+hl[]rd";
console.log(new RegExp(escape(name), "i").test("Hello DEA+HL[]RD")); // true
```

</Level>

<Level name="Production level">

Regex in production has two dangers: ReDoS, where a crafted input blocks the event loop and every request on that Node
process stalls, and patterns nobody dares change. The habits: test patterns against hostile inputs, use a parser for
structured formats (`URL` for URLs, a date library for dates), and name the groups in long patterns.

</Level>

<Level name="Mindset">

A regex is a small program. It deserves tests, names and a limit on how clever it is allowed to be.

</Level>

<Level name="System design">

Validation patterns sit at system boundaries. The design question is where they live: in one shared module used by
client and server, so the two never disagree about what a valid slug or phone number is.

</Level>

<Level name="Strategy">

I do the regexp golf, quoting style and numbers-again exercises, then write an arithmetic tokenizer with `y`-flag
regexes. Done when I can explain why my number pattern rejects `"."` and `"1e"` but accepts `"-1.5e-3"`.

</Level>

</Levels>

### 10. Modules

**Covers:** Modular programs, ES modules, packages, CommonJS modules, building and bundling, and module design.

<Layers layers={[
  { name: 'application code', note: 'imports only what it uses' },
  { name: 'my modules', note: 'each with a small export list' },
  { name: 'packages from npm', note: 'versioned, locked, in node_modules' },
  { name: 'runtime built-ins', note: 'node:fs, fetch, URL' },
]} caption="A program as layers of modules. Each layer should depend only on the layers below it." />

<Levels label="Chapter 10, Modules">

<Level name="Beginner">

A module is a file with its own scope that exports some bindings and imports others.

```js
// math.js
export const add = (a, b) => a + b;
// main.js
import { add } from "./math.js";
console.log(add(2, 3)); // 5
```

Mistake: leaving off the `.js` extension in Node's ES modules, which fails with `ERR_MODULE_NOT_FOUND`. Fix: write the
full relative path.

</Level>

<Level name="Intermediate">

Packages bundle modules with a `package.json` and a version and are installed from npm. A real program combines its
own modules, packages and built-ins, and the dependency graph is the program's real shape.

```json
{ "name": "ini-parser", "version": "1.0.0", "type": "module", "exports": "./index.js" }
```

Mistake: importing a package's internal file. With an `exports` map it fails with `ERR_PACKAGE_PATH_NOT_EXPORTED`. Fix:
import only the public entry points.

</Level>

<Level name="Advanced">

ES module imports are live bindings resolved before any code runs, so imports are hoisted and cycles are possible.
CommonJS `require` is an ordinary function call that returns `module.exports` as it is at that moment.

```js
// counter.js
export let count = 0;
export const inc = () => { count++; };
// main.js
import { count, inc } from "./counter.js";
inc();
console.log(count); // 1, because the imported binding is live
```

With CommonJS and `const { count } = require("./counter")`, the same code prints `0`: a copy was taken at require
time.

</Level>

<Level name="Edge cases">

Circular imports: A imports B, B imports A, and B reads one of A's exports at the top level before A has run.

```
ReferenceError: Cannot access 'config' before initialization
```

Fix: move the shared value into a third module, or read it lazily inside a function.

</Level>

<Level name="Corner cases">

A package that ships both an ESM and a CommonJS build, loaded once in each format by two different dependencies: two
copies of the module, two copies of its state, and `instanceof` checks between them fail. This is the dual package
hazard. Fix: one format, or state kept outside the package.

</Level>

<Level name="Production level">

The module graph is also the bundle and the attack surface: every dependency is code I ship and trust. Lockfiles,
`npm ci`, a small dependency count and a bundle analyser are the habits. Tree shaking only works with ES modules and
files without side effects.

</Level>

<Level name="Mindset">

A module's export list is its contract. Exporting less is a feature, because every export is something I promise not
to break.

</Level>

<Level name="System design">

Module boundaries are where a monolith can later be split. If modules talk only through their exports, any one of them
can become a package or a service without rewriting its callers.

</Level>

<Level name="Strategy">

### 11. Asynchronous Programming

**Covers:** Asynchronicity, callbacks, promises, failure, the crow examples (Carla, and breaking in), async functions, generators, a corvid art project, the event loop and asynchronous bugs.

<Figure art={`
   call stack          microtask queue           task queue
  +-----------+       +------------------+      +-----------------+
  | script    |       | promise reactions|      | setTimeout cb   |
  +-----------+       | await resumption |      | I/O callbacks   |
       |              +------------------+      +-----------------+
       v                  ^ run ALL of these         ^ then take ONE
   stack empty -----------+--------------------------+   and repeat
`} caption="The event loop: run the script, drain every microtask, take one task, drain microtasks again, and repeat." />

<Levels label="Chapter 11, Asynchronous Programming">

<Level name="Beginner">

Asynchronous code starts work now and handles the result later, without blocking. A promise is a value that settles
later; `await` waits for it inside an `async` function.

```js
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
async function main() {
  console.log("start");
  await wait(100);
  console.log("100 ms later");
}
main();
```

Mistake: using an `async` function's return value as if it were the result. It is a `Promise`. Fix: `await` it.

</Level>

<Level name="Intermediate">

Real programs run several things at once and combine them: `Promise.all` waits for all and fails fast,
`Promise.allSettled` waits for all regardless, `Promise.race` and `Promise.any` take the first to settle or succeed.

```js
const results = await Promise.allSettled([Promise.resolve(1), Promise.reject(new Error("no"))]);
console.log(results.map((r) => r.status)); // [ 'fulfilled', 'rejected' ]
```

Mistake: `await` inside a `for` loop over independent requests, so they run one after another. Fix: start them all,
then `await Promise.all(...)`.

</Level>

<Level name="Advanced">

The ordering rule: synchronous code runs to completion, then every microtask (promise callbacks and `await`
continuations), then one task (a timer, an I/O callback), then microtasks again.

```js
setTimeout(() => console.log("timeout"), 0);
Promise.resolve().then(() => console.log("microtask"));
console.log("sync");
// sync
// microtask
// timeout
```

An `async` function always returns a promise, and a `throw` inside it becomes a rejection. Generators (`function*`)
pause and resume; the chapter shows they are how async functions can be built.

</Level>

<Level name="Edge cases">

An unhandled rejection crashes a current Node process:

```
node:internal/process/promises: triggerUncaughtException
Error: no
```

Fix: every promise is awaited inside a `try` or ends with a `catch`, and the process has an `unhandledRejection` handler
that logs and exits cleanly.

</Level>

<Level name="Corner cases">

The chapter's async bug: two operations read shared state, `await`, then write it back.

```js
let total = 0;
async function add(n) { const t = total; await wait(10); total = t + n; }
await Promise.all([add(1), add(2)]);
console.log(total); // 2, not 3
```

Both read `0` before either writes. Single-threaded does not mean race-free. Fix: no shared read held across an
`await`, or serialise the updates through a queue.

</Level>

<Level name="Production level">

In production, async code needs timeouts (`AbortSignal.timeout` on every `fetch`), cancellation, bounded concurrency
(not 10,000 parallel requests) and backpressure. A long synchronous loop blocks every request on a Node server, so CPU
work moves to a worker thread.

```js
const res = await fetch(url, { signal: AbortSignal.timeout(5000) });
```

</Level>

<Level name="Mindset">

Concurrency without threads is still concurrency. Every `await` is a point where the world can change under me.

</Level>

<Level name="System design">

The event loop is the scheduling model of the whole Node backend: one thread, many requests in flight, each yielding at
I/O. Designing for it means nothing blocking on the request path, and a worker pool or queue for slow work.

</Level>

<Level name="Strategy">

I do the quiet-times, real-promises and building-`Promise.all` exercises, then write my own `promiseAll` and a
concurrency-limited `mapLimit`. Done when I can predict the output order of any mix of timers, promises and `await`,
and explain it with the diagram above. That is the phase 1 gate's event-loop item.

</Level>

</Levels>

### 12. Project: A Programming Language

**Covers:** Building Egg: parsing into a syntax tree, the evaluator, special forms, the environment, functions, compilation, and cheating.

<Flow steps={['source text', 'parser', 'syntax tree', 'evaluate(node, scope)', 'value']} caption="A tiny language in four steps. The parser turns text into a tree; the evaluator walks the tree with a scope." />

<Levels label="Chapter 12, Project: A Programming Language">

<Level name="Beginner">

Egg has one kind of syntax: everything is an expression, and application looks like `do(define(x, 10), print(x))`. The
parser turns that text into a tree of plain objects.

```js
// parse("+(a, 10)") returns
// { type: "apply", operator: { type: "word", name: "+" },
//   args: [ { type: "word", name: "a" }, { type: "value", value: 10 } ] }
```

Mistake: trying to parse with one giant regex. Fix: a recursive parser that reads one expression, then checks for an
argument list after it.

</Level>

<Level name="Intermediate">

The evaluator takes a tree node and a scope. Special forms (`if`, `while`, `do`, `define`, `fun`) receive their
arguments unevaluated, so they decide what to run.

```js
function evaluate(expr, scope) {
  if (expr.type === "value") return expr.value;
  if (expr.type === "word") {
    if (expr.name in scope) return scope[expr.name];
    throw new ReferenceError(`Undefined binding: ${expr.name}`);
  }
  const { operator, args } = expr;
  if (operator.type === "word" && operator.name in specialForms) {
    return specialForms[operator.name](args, scope);
  }
  const op = evaluate(operator, scope);
  if (typeof op === "function") return op(...args.map((a) => evaluate(a, scope)));
  throw new TypeError("Applying a non-function.");
}
```

Mistake: evaluating `if`'s arguments before choosing a branch, so both branches run. Fix: special forms.

</Level>

<Level name="Advanced">

Scopes are objects linked by prototypes: `Object.create(scope)` makes a child scope that sees its parent. `fun` makes a
closure by capturing the scope where it was defined, which is lexical scope, the model JavaScript itself uses.

Mistake (the `set` exercise): assigning in the local scope creates a new binding instead of updating the outer one.
Fix: walk up with `Object.getPrototypeOf` until the binding is found, and throw a `ReferenceError` if it never is.

</Level>

<Level name="Edge cases">

Parser boundaries: an empty program, an unclosed parenthesis, a trailing comma and comments. Each should produce a
clear `SyntaxError` with a position, not a crash.

```
SyntaxError: Expected ',' or ')'
```

Fix: the parser keeps track of the remaining text and reports what it expected.

</Level>

<Level name="Corner cases">

Recursion in the evaluator meets recursion in the program: a deeply recursive Egg function overflows the JavaScript
stack sooner than the same function in JavaScript, because each Egg call is several JavaScript calls. Fix: a step limit
that turns overflow into an Egg error, or an evaluator with an explicit stack.

</Level>

<Level name="Production level">

Config formats, template languages, query builders and rule engines are all small languages. In production they need
error messages with line numbers, a sandbox (no access to the host's globals) and a step or time budget, so one user's
program cannot hang the server.

</Level>

<Level name="Mindset">

Languages are not magic. A parser and an evaluator are a few hundred lines, and knowing that makes every compiler
error, linter and bundler something I can reason about.

</Level>

<Level name="System design">

An interpreter is a pipeline with a clean data structure in the middle. Compilers, linters, formatters and codemods
share that design: a front end that builds a tree, and back ends that read it.

</Level>

<Level name="Strategy">

I build Egg, then the arrays, closure, comments and fixing-scope exercises. Done when Egg runs a recursive `fib` and a
closure counter and reports a clear error for an unclosed parenthesis. This feeds the phase 1 gate's JSON parser.

</Level>

</Levels>

### 13. JavaScript and the Browser

**Covers:** Networks and the internet, the web, HTML, HTML and JavaScript, the sandbox, and compatibility and the browser wars.

<Flow steps={['type a URL', 'DNS lookup', 'TCP and TLS', 'HTTP request', 'HTML parsed', 'scripts run']} caption="What happens between a URL and running JavaScript. Every step can fail, and each failure looks different in dev tools." />

<Levels label="Chapter 13, JavaScript and the Browser">

<Level name="Beginner">

The browser fetches an HTML document over HTTP, parses it into a page and runs the scripts it finds. A script tag is
the smallest bridge from HTML to JavaScript.

```html
<!doctype html>
<h1>Hi</h1>
<script type="module">document.querySelector("h1").textContent = "Hello";</script>
```

Mistake: a classic script in the head that queries elements not yet parsed and gets `null`. Fix: `type="module"` or
`defer`, which run after parsing.

</Level>

<Level name="Intermediate">

The web is protocols layered on one another: IP moves packets, TCP makes a reliable stream, TLS secures it and HTTP
carries requests and responses. The browser is a client for all of them and an application runtime at once.

Mistake: assuming a slow page means slow JavaScript. Fix: open the network panel first; most slowness is waiting.

</Level>

<Level name="Advanced">

The sandbox: scripts can only reach what the same-origin policy allows. An origin is scheme, host and port. A script
from `https://a.com` cannot read responses from `https://b.com` unless `b.com` sends CORS headers.

```
Access to fetch at 'https://b.com/api' from origin 'https://a.com' has been blocked by CORS policy
```

Mistake: trying to fix CORS in the client. Fix: CORS is configured on the server that owns the resource.

</Level>

<Level name="Edge cases">

Pages opened from `file://` have odd rules: module scripts and `fetch` of local files fail. Fix: always serve the page
from a local server (`npx serve` or `python3 -m http.server`).

</Level>

<Level name="Corner cases">

A page served over HTTPS loading a script over plain HTTP: mixed content is blocked and the page silently loses that
script. The secure-context rule and the loading rule meet. Fix: HTTPS everywhere, and a Content Security Policy with
violation reporting so the block is visible.

</Level>

<Level name="Production level">

The browser is a varied and hostile environment: different versions, extensions that inject scripts, slow networks and
small screens. The habits: progressive enhancement (the HTML works before the script), a CSP, feature detection over
browser sniffing (the lesson of the browser wars), and testing on a real phone.

</Level>

<Level name="Mindset">

The browser is a runtime I do not control. I write for it as for any untrusted client: assume nothing, and check
everything that matters on the server.

</Level>

<Level name="System design">

The browser is the outermost tier of a web system. Whatever runs there can be read and edited by the user, so business
rules and authorisation live on the server; the browser gets presentation and convenience checks.

</Level>

<Level name="Strategy">

I trace one page load in the network panel and write down every request and why it happened. Done when I can explain
every request my phase 2 app makes, which is a phase 2 gate item.

<Levels label="Chapter 14, The Document Object Model">

<Level name="Beginner">

The DOM is the browser's live tree of the page. I find nodes and change them.

```js

link.textContent = "read it here";
link.setAttribute("href", "/book/");
```

Mistake: `el.innerHTML = userInput`, which runs injected markup. Fix: `textContent` for text, and `createElement` to

</Level>

<Level name="Intermediate">

Building UI from data means creating nodes in a loop and attaching them once.

```js
function table(rows) {
  const t = document.createElement("table");

    const tr = t.insertRow();
```

Mistake: appending to the live document inside the loop, forcing repeated layout. Fix: build off-document, then

<Level name="Advanced">

`childNodes` and `getElementsByTagName` return live collections that change as the document changes, while

```js
const live = document.body.getElementsByTagName("p");
```

<Level name="Edge cases">

Whitespace between tags becomes text nodes, so `firstChild` is often not the element I expect.

</Level>

<Level name="Corner cases">

Animation meets layout reads: a `requestAnimationFrame` loop that writes `style.left` and reads `offsetWidth` for each

everything, and animate `transform` instead of `left`.

</Level>

<Level name="Production level">

DOM work is the main cost of a UI. Frameworks batch it for me; without one I batch it myself. Accessibility lives here
too: semantic elements (`button`, not a clickable `div`) bring keyboard and screen-reader support for free.

</Level>

<Level name="Mindset">

The page is output. I render the DOM from state; I do not keep my state in the DOM.

</Level>

<Level name="System design">

Every UI framework is a strategy for keeping the DOM in sync with state: React diffs a virtual tree, Svelte compiles

</Level>

<Level name="Strategy">

### 15. Handling Events

**Covers:** Event handlers, events and DOM nodes, event objects, propagation, default actions, key events, pointer events, scroll events, focus events, the load event, events and the event loop, timers and debouncing.

<Flow steps={['capture: window down to target', 'at the target', 'bubble: target up to window', 'default action unless prevented']} caption="An event travels down to its target and bubbles back up. Handlers on ancestors see it on the way up." />

<Levels label="Chapter 15, Handling Events">

<Level name="Beginner">

An event handler is a function the browser calls when something happens.

```js
const button = document.querySelector("button");
button.addEventListener("click", (event) => console.log("clicked", event.target));
```

Mistake: `addEventListener("click", handler())`, which calls the handler once, immediately. Fix: pass the function,
not its result.

</Level>

<Level name="Intermediate">

Event delegation: one handler on a parent uses `event.target` to find which child was hit, and it covers children
added later.

```js
list.addEventListener("click", (e) => {
  const item = e.target.closest("li[data-id]");
  if (item) select(item.dataset.id);
});
```

Mistake: using `e.target` directly when the click lands on a `span` inside the item. Fix: `closest`.

</Level>

<Level name="Advanced">

`stopPropagation` stops bubbling; `preventDefault` stops the browser's default action (following a link, submitting a
form). Passive listeners promise never to call `preventDefault`, so scrolling stays smooth. Handlers run as tasks on the
event loop, so a slow handler freezes the page.

Mistake: `return false` from an `addEventListener` handler, which does nothing. Fix: `event.preventDefault()`.

</Level>

<Level name="Edge cases">

Key events: `key` is the character produced (`"a"`, `"A"`, `"Enter"`) and `code` the physical key (`"KeyA"`). Holding a
key repeats `keydown` with `event.repeat` set. Input methods for Hindi or Japanese fire key events in the middle of
composing a character.

```js
input.addEventListener("keydown", (e) => {
  if (e.key === "Enter" && !e.isComposing) submit();
});
```

</Level>

<Level name="Corner cases">

Touch and mouse together: a tap fires pointer events, touch events and then emulated mouse events, so a handler on
both `touchstart` and `click` runs twice. Fix: pointer events for both input types, handled once.

</Level>

<Level name="Production level">

Debouncing and throttling keep high-frequency events (scroll, resize, input) from flooding the page or the API.

```js
function debounce(fn, ms) {
  let id;
  return (...args) => { clearTimeout(id); id = setTimeout(() => fn(...args), ms); };
}
search.addEventListener("input", debounce((e) => query(e.target.value), 250));
```

Single-page apps must also remove listeners on teardown, for example with an `AbortSignal` in the listener options, or
they leak.

</Level>

<Level name="Mindset">

Events are the user talking, and every handler is a reply. Keyboard and screen-reader users are talking too.

</Level>

<Level name="System design">

The event model is publish and subscribe inside the page. The same pattern scales out to message queues and webhooks:
producers emit, consumers subscribe, nobody calls anybody directly.

</Level>

<Level name="Strategy">

I do the balloon, mouse trail and tabs exercises, with the tabs fully keyboard accessible. Done when my phase 2 app's
main flow works with the keyboard alone, which is the first phase 2 gate item.

</Level>

</Levels>

### 16. Project: A Platform Game

**Covers:** The game, the technology, levels, reading a level, actors, drawing, motion and collision, actor updates, tracking keys and running the game.

<Flow steps={['read input', 'update state by elapsed time', 'resolve collisions', 'draw the state', 'next animation frame']} caption="The game loop. State is updated by elapsed time and then drawn; drawing never changes state." />

<Levels label="Chapter 16, Project: A Platform Game">

<Level name="Beginner">

The game turns a text level plan into a grid of walls, lava and coins, plus moving actors: the player, coins and lava.

```js
const plan = `
......#
.@..o.#
#######`;
const rows = plan.trim().split("\n").map((line) => [...line]);
console.log(rows[1][1]); // @
```

Mistake: hard-coding the level size. Fix: derive width and height from the plan.

</Level>

<Level name="Intermediate">

Each actor has an `update(time, state, keys)` that returns a new actor; the state's `update` combines them and checks
collisions. The loop runs on `requestAnimationFrame` with the time since the last frame.

```js
function runAnimation(frameFunc) {
  let last = null;
  function frame(time) {
    if (last != null) {
      const step = Math.min(time - last, 100) / 1000;
      if (frameFunc(step) === false) return;
    }
    last = time;
    requestAnimationFrame(frame);
  }
  requestAnimationFrame(frame);
}
```

Mistake: a fixed move per frame, so the game runs twice as fast on a 120 Hz screen. Fix: speed times elapsed time.

</Level>

<Level name="Advanced">

Collision against the grid checks every cell the actor's box overlaps. The player moves one axis at a time, so a wall
stops horizontal motion without cancelling a jump.

Mistake: moving on both axes and then checking, which makes the player stick to walls. Fix: move and test x, then y.

</Level>

<Level name="Edge cases">

When the tab is hidden, frames stop; when it comes back, the first step can be seconds long and the player falls
through the floor. That is why the loop caps each step at 100 ms.

</Level>

<Level name="Corner cases">

A long step combined with high speed lets an actor jump from one side of a thin wall to the other in a single update,
so the overlap check never fires (tunnelling). Fix: cap the step and split fast movement into sub-steps.

</Level>

<Level name="Production level">

Real-time interfaces (games, editors, live dashboards) need a stable loop, input decoupled from rendering and a way to
pause. Separating update from draw also makes the state testable without a screen.

</Level>

<Level name="Mindset">

Separate what is true (state) from how it looks (drawing), so either can change without breaking the other.

</Level>

<Level name="System design">

The game is a small model-view split with a fixed-step simulation. Multiplayer games and collaborative editors scale
the same idea with a server that holds the authoritative state.

</Level>

<Level name="Strategy">

I build the game, then the game-over, pausing and monster exercises. Done when Escape pauses without leaking frames, and
a test runs ten seconds of simulated time with no DOM.

</Level>

<Levels label="Chapter 17, Drawing on Canvas">

<Level name="Beginner">

A canvas is a bitmap I draw on through a 2D context.

```js
const cx = document.querySelector("canvas").getContext("2d");
cx.fillStyle = "black";
cx.fillRect(10, 10, 100, 50);
```

Mistake: sizing the canvas with CSS only, so it is stretched and blurry. Fix: set the `width` and `height` attributes,

</Level>

<Level name="Intermediate">

Paths combine lines and curves; a pie chart is arcs drawn from the centre.

```js
let angle = -0.5 * Math.PI;
for (const { count } of results) {

  cx.arc(100, 100, 100, angle, angle + slice);
```

Mistake: no `beginPath`, so every fill repaints all the earlier slices. Fix: one path per shape.

</Level>

<Level name="Advanced">

Transformations (`translate`, `scale`, `rotate`) change the coordinate system for everything drawn afterwards. `save`

Mistake: transforming without `save` and `restore`, so everything drawn later is rotated too. Fix: always pair them.

</Level>

<Level name="Edge cases">

Images draw only after they load; `drawImage` on an unloaded image draws nothing and throws nothing.

```js
const img = new Image();

```

</Level>

<Level name="Corner cases">

High-DPI scaling plus a sprite flip: applying the `devicePixelRatio` scale and the mirror in the wrong order mirrors the
whole scene. Fix: scale once at setup, then `save`, flip, draw and `restore` per sprite.

</Level>

<Level name="Production level">

Canvas content is invisible to screen readers and search engines, so charts in production need a data table or a text
summary beside them. Large canvases are expensive on phones, so redraw only what changed.

</Level>

<Level name="Mindset">

Choose the drawing technology by what must stay true afterwards. Events, text, accessibility: DOM or SVG. Thousands of

</Level>

<Level name="System design">

In a dashboard, choosing SVG or canvas decides how charts scale with data size, how they are tested and whether they
work with assistive technology. It is an architecture decision, not a styling one.

### 18. HTTP and Forms

**Covers:** The protocol, browsers and HTTP, `fetch`, HTTP sandboxing, appreciating HTTP, security and HTTPS, form fields, focus, disabled fields, the form as a whole, text fields, checkboxes and radio buttons, select fields, file fields, and storing data client-side.

<Flow steps={['user input', 'client validation (for speed)', 'submit with fetch', 'server validation (the truth)', 'success, or field errors shown']} caption="A form round trip. The server's validation is the one that counts; the client's only saves a round trip." />

<Levels label="Chapter 18, HTTP and Forms">

<Level name="Beginner">

HTTP is requests (method, path, headers, body) and responses (status, headers, body). `fetch` sends requests from
script; forms send them from HTML.

```js
const res = await fetch("/api/notes", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ title: "hi" }),
});
console.log(res.status, await res.json());
```

Mistake: expecting `fetch` to reject on a 404 or a 500. It rejects only when the network fails. Fix: check `res.ok`.

</Level>

<Level name="Intermediate">

A form with real feedback: handle `submit`, prevent the default, send with `fetch` and show errors next to the fields.

```js
form.addEventListener("submit", async (e) => {
  e.preventDefault();
  const button = form.querySelector("button");
  button.disabled = true;
  try {
    const data = Object.fromEntries(new FormData(form));
    const res = await fetch(form.action, { method: "POST", body: JSON.stringify(data) });
    if (!res.ok) showErrors(await res.json());
  } finally {
    button.disabled = false;
  }
});
```

Mistake: disabling the button and never re-enabling it after an error. Fix: `finally`.

</Level>

<Level name="Advanced">

Methods carry meaning: GET is safe and cacheable, PUT and DELETE are idempotent, POST is neither. Status codes are the
contract: 2xx success, 3xx redirect, 4xx the client's fault, 5xx the server's. Disabled fields are not submitted; read-only
fields are.

</Level>

<Level name="Edge cases">

Field boundaries: a number input's `value` is a string, and `""` when empty or invalid; an unchecked checkbox is absent
from the form data; a multi-select needs `getAll`; a file input gives `File` objects read asynchronously.

```js
console.log(new FormData(form).get("agree")); // null when the box is unchecked
console.log(await fileInput.files[0].text()); // the file's contents
```

</Level>

<Level name="Corner cases">

Double submission on a slow network: two clicks, two POSTs, two orders. Disabling the button helps only if the second
click is not already in flight. Fix: an idempotency key created when the form loads, sent with the request and enforced
by the server.

</Level>

<Level name="Production level">

Client-side storage has limits and risks: `localStorage` is synchronous, small (a few megabytes), readable by any script
on the origin (never a token store) and can be cleared at any time. Every form needs server validation, CSRF protection
for cookie-authenticated requests, and errors linked to fields with `aria-describedby`.

</Level>

<Level name="Mindset">

The client is a convenience and the server is the truth. Every check I write in the browser, I write again where it
cannot be skipped.

</Level>

<Level name="System design">

The request and response cycle is the seam between frontend and backend. Designing it means choosing resource names,
methods, error shapes and idempotency once for the whole system, not once per form.

</Level>

<Level name="Strategy">

I do the content negotiation, JavaScript workbench and Conway's Game of Life exercises. Done when my phase 2 form
handles empty, invalid, slow, failed and double-submitted cases, each with a visible state.

</Level>

### 19. Project: A Pixel Art Editor

**Covers:** Components, the state, DOM building, the canvas, the application, drawing tools, saving and loading, undo history, drawing with it, and why this is so hard.

<Flow steps={['user action', 'dispatch(action)', 'new state = update(state, action)', 'every component syncState(state)', 'DOM and canvas updated']} caption="The editor's one-way data flow. Components never change state directly; they dispatch actions." />

<Levels label="Chapter 19, Project: A Pixel Art Editor">

<Level name="Beginner">

The editor is built from components: objects with a `dom` property and a `syncState(state)` method. The whole
application state is one object: the picture, the current tool and the current colour.

```js
const state = { tool: "draw", color: "#000000", picture: Picture.empty(60, 30, "#f0f0f0") };
```

Mistake: each component keeping its own copy of the colour, so the picker and the canvas disagree. Fix: one state
object, passed down.

</Level>

<Level name="Intermediate">

Updating is `dispatch(action)`: a new state is computed and pushed to every component. The picture is immutable, so
`draw` returns a new `Picture`.

```js
function updateState(state, action) {
  return { ...state, ...action };
}
let s = updateState(state, { color: "#ff0000" });
console.log(state.color, s.color); // #000000 #ff0000
```

Mistake: mutating `state.picture.pixels` in place, so nothing knows to redraw and undo has nothing to go back to. Fix:
new objects for changed data.

</Level>

<Level name="Advanced">

Undo comes almost free with immutable state: keep a list of earlier pictures and pop on undo. Grouping matters: one
drag is one undo step, not one per pixel, so a new history entry is pushed only if enough time has passed since the
last.

Mistake: pushing every intermediate picture onto the history, so undo walks back one pixel at a time. Fix: time-based
or gesture-based grouping.

</Level>

<Level name="Edge cases">

Pointer boundaries: dragging off the canvas, a mouse button released outside the window, touches with two fingers and
coordinates on a canvas scaled by CSS. Fix: pointer capture (`setPointerCapture`) and coordinates computed from
`getBoundingClientRect` scaled to the picture size.

</Level>

<Level name="Corner cases">

Flood fill on a large picture with a recursive implementation overflows the stack:

```
RangeError: Maximum call stack size exceeded
```

And a fill with the colour already under the cursor loops forever if "visited" is tracked by colour. Fix: an explicit
queue and a visited set by position.

</Level>

<Level name="Production level">

Saving and loading touch the outside world: loading an image file reads untrusted data that may be enormous, saving
uses `toDataURL` and a download link. Real editors also need keyboard shortcuts that do not fire inside text inputs,
autosave and redraws that touch only changed pixels.

</Level>

<Level name="Mindset">

The chapter's closing question, why this is so hard, is the point. UI is state over time plus many inputs, and the
discipline of one-way data flow is what keeps it understandable.

</Level>

<Level name="System design">

This is the architecture of Redux and of React with a reducer, built by hand: a store, actions, a pure update function
and views that render from state. Having built it, the frameworks are a choice, not a mystery.

</Level>

<Level name="Strategy">

I build the editor, then the keyboard bindings, efficient drawing, circles and proper lines exercises. Done when undo
groups a drag into one step and redraw touches only the pixels that changed.

</Level>

Node runs JavaScript outside the browser, with access to files, processes and the network.

<Level name="Intermediate">

A minimal HTTP server, the start of every Node backend.

```js
import { createServer } from "node:http";
createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain" });
  res.end(`You asked for ${req.url}\n`);
}).listen(8000);
```

```
$ curl localhost:8000/hello
You asked for /hello
```

Mistake: forgetting `res.end`, so the client hangs until it times out. Fix: every path through a handler ends the
response.

</Level>

<Level name="Advanced">

Streams move data in chunks with backpressure: `pipeline(readable, transform, writable)` handles errors and
cleanup for me.

```js
import { createReadStream, createWriteStream } from "node:fs";
import { createGzip } from "node:zlib";
import { pipeline } from "node:stream/promises";
await pipeline(createReadStream("big.log"), createGzip(), createWriteStream("big.log.gz"));
```

Mistake: `a.pipe(b)` with no error handler, so a failed read leaves the file open. Fix: `pipeline`.

</Level>

<Level name="Edge cases">

The file server's path handling: `GET /../../etc/passwd` resolved naively escapes the served directory.

```js
import { resolve, sep } from "node:path";
const base = process.cwd();
function safePath(url) {
  const path = resolve(base, decodeURIComponent(new URL(url, "http://x").pathname).slice(1));
  if (path !== base && !path.startsWith(base + sep)) throw Object.assign(new Error("Forbidden"), { status: 403 });
  return path;
}
```

The `+ sep` matters: without it, `/srv/app-secrets` passes a check for `/srv/app`.

</Level>

<Level name="Corner cases">

Encoded traversal plus symbolic links: `%2e%2e%2f` decodes to `../`, and a symlink inside the served directory can
point outside it, so a string check on the resolved path passes. Fix: decode once, resolve, then `fs.realpath` and check
again.

</Level>

<Level name="Production level">

A production Node server needs: no blocking calls on the request path, graceful shutdown on `SIGTERM` (stop accepting,
finish in-flight requests), body size limits, timeouts, structured logs and an exit on unhandled errors so the process
manager restarts it cleanly.

</Level>

<Level name="Mindset">

Node is the same language with different powers. In the browser the risk is the user's data; on the server it is
everyone's data and the machine itself.

</Level>

<Level name="System design">

One Node process handles many connections on one thread; to use more cores, run several processes behind a load
balancer. That is also why session state belongs in a shared store, not in process memory.

</Level>

<Levels label="Chapter 21, Project: Skill-Sharing Website">

<Level name="Beginner">

The site lets people propose talks and comment on them, with every open browser updating live. The server keeps the
talks in memory and exposes them over a small JSON API.

```
GET    /talks
PUT    /talks/Unituning
DELETE /talks/Unituning
POST   /talks/Unituning/comments
```

Mistake: using the raw title in the URL. Fix: `encodeURIComponent` on the client and decode on the server.

</Level>

<Level name="Intermediate">

The server is a small router: a list of method and regex pairs mapped to handlers.

```js
class Router {
  #routes = [];
  add(method, url, handler) { this.#routes.push({ method, url, handler }); }
  async resolve(request, context) {
    const { pathname } = new URL(request.url, "http://d");
    for (const { method, url, handler } of this.#routes) {
      const match = url.exec(pathname);
      if (match && request.method === method) {
        return handler(context, ...match.slice(1).map(decodeURIComponent), request);
      }
    }
    return null;
  }
}
```

Mistake: a regex without `^` and `$`, so `/talks/x/comments` also matches the talk route. Fix: anchor every pattern.
This is the phase 1 gate's router.

</Level>

<Level name="Advanced">

Long polling: the client sends `If-None-Match` with the last version it saw and `Prefer: wait=90`; the server answers at
once if the version is stale, otherwise parks the request until a change or the timeout, then replies `304`.

Mistake: never cleaning up parked requests when clients disconnect. Fix: remove them on the response's `close` event.

</Level>

<Level name="Edge cases">

Two people edit or delete the same talk at once: last write wins, and a comment can arrive for a talk that was just
deleted. Fix: return `404` for comments on missing talks, and an ETag check (`If-Match`) for updates.

</Level>

<Level name="Corner cases">

The client's long-poll loop after the server restarts: the version counter resets to a lower number, the client's
`If-None-Match` never matches again, and it receives a full response on every poll forever. Fix: version tags that
cannot repeat (a boot ID plus a counter).

</Level>

<Level name="Production level">

In production I would add persistence (the disk persistence exercise), validation of every body, rate limits on writes
and a proxy timeout longer than the poll wait. Today I would probably use Server-Sent Events or WebSockets, but long
polling still works through every proxy, which is why it is worth knowing.

</Level>

<Level name="Mindset">

A whole product is just the book's chapters put together: data, functions, modules, async, the DOM, HTTP and Node. If I
can build this, I can build the shape of most web apps.

</Level>

<Level name="System design">

The design is a single stateful server with clients polling for changes. To scale it, state moves to a database, change
notifications go through pub and sub (Redis or Postgres `LISTEN`), and any server can answer any poll.

</Level>

<Level name="Strategy">

I build it, then do the disk persistence and comment field resets exercises. Done when the server survives a restart
without losing talks, two browsers stay in sync, and the router has tests for every route.

</Level>

</Levels>

## Misreadings to avoid

- "It is a beginner book, so I can skim it." The project chapters, Egg especially, are harder than most tutorials.
- "Read the chapter, skip the exercises." The exercises are the book; the prose is the setup for them.
- "Async is just syntax." Chapter 11 is about ordering and shared state, and the bugs are about ordering.
- "Frameworks make chapters 14 to 19 obsolete." Every framework is built on the DOM, events and one-way data flow
  shown here.
- "Node is browser JavaScript on a server." Same language, different threats: files, processes and other users.
