## Why this book

Phase 10 of the
<a href={withBase('/plans/software-ai-developer/')}>software AI developer roadmap</a>
pairs this book with *Fundamentals of Software Architecture*. Fundamentals gives
the vocabulary; this one goes into the decisions that have no clean answer: how
to split a system, who owns which data, how to keep data consistent across
services, how to coordinate workflows, and how to analyse a trade-off when no
best practice applies. Phase 10's failure matrix and data ownership exercises are

The book follows a fictional team, the Sysops Squad, as they break apart a
monolithic support-ticket system, and each chapter ends with ADRs from their

### 1. What Happens When There Are No "Best Practices"?

**Covers:** Why the book calls these the hard parts, timeless advice, why data matters, architectural decision records, architecture fitness functions, architecture versus design, and the introduction to the Sysops Squad saga.

<Compare left="Best practice exists" right="No best practice" rows={[
  ['one known good answer', 'several options, each with costs'],
  ['look it up', 'analyse trade-offs in context'],
  ['decided once', 'decided per system, recorded, revisited'],
]} caption="The book's premise. Most hard architecture problems sit in the right column." />

<Levels label="Chapter 1, What Happens When There Are No Best Practices">

<Level name="Beginner">

Many architecture problems are new to each organisation: nobody has solved exactly
this split, with this data, with this team. There is no best practice to look up,
only options with costs. The book's tool is trade-off analysis: find the options,
find what they trade, and pick the least worst for this context. It calls them
the hard parts both because they are difficult and because they are foundational,
hard to change later.

```md
Question: one database or a database per service for tickets and customers?
Options: shared DB (simple, coupled) | split DB (independent, distributed consistency)
Context decides: transaction needs, team boundaries, scaling differences
```

Common mistake: searching for the industry standard answer. Fix: list options and
trade-offs in my context.

</Level>

<Level name="Intermediate">

Data is central: in distributed systems, the hardest decisions are about where
data lives and who owns it, because data outlives code. ADRs record each decision
and its trade-offs. Fitness functions check that the architecture keeps its
characteristics, so decisions are governed, not just written. Architecture versus
design is a spectrum: architecture decisions are structural and hard to reverse.

```ts
// a fitness function from the Sysops Squad style: no service writes another's tables
test('ticket tables are written only by the ticket service', () => {
  expect(writersOf('ticket.*')).toEqual(['ticket-service']);
});
```

Common mistake: ADRs without fitness functions. Fix: each important decision gets
a check where possible.

</Level>

<Level name="Advanced">

Timeless advice means learning the method, not the answer: the technologies in
any example will change, but the way to analyse coupling, data and workflow
trade-offs carries over. The Sysops Squad saga gives a running example: a support
ticketing system for an electronics retailer, a monolith in trouble, and a team
deciding how to break it apart.

Common mistake: treating the Sysops Squad decisions as prescriptions. Fix: copy
the reasoning, not the outcome.

</Level>

<Level name="Edge cases">

One boundary each. A decision that does have a best practice (use TLS): do not
over-analyse it. A decision with one dominant constraint (a regulation): the
analysis is short. A decision nobody owns: it gets made by default.

Common mistake: analysis paralysis on easy decisions. Fix: reserve deep
trade-off analysis for structural, hard-to-reverse ones.

</Level>

<Level name="Corner cases">

Two boundaries meet. A decision about data plus team politics: data ownership is
also an organisational decision. A fitness function plus a decision that changed:
the old check blocks the new design until updated.

Common mistake: stale fitness functions. Fix: when an ADR is superseded, update
its checks in the same change.

</Level>

<Level name="Production level">

In production I keep an ADR per hard decision with options, trade-offs and the
decision, plus a fitness function and a revisit condition. That is the book's
pattern and the one I follow throughout.

```md
ADR-H1 Keep one database during extraction
Trade-offs: + transactions stay local, + no data migration now; - schema coupling remains
Check: per-service DB roles. Revisit: when ticket load needs separate scaling.
```

Common mistake: decisions without revisit conditions. Fix: always add one.

</Level>

<Level name="Mindset">

No silver bullets. The habit is to expect trade-offs in every structural choice
and to make them explicit.

Common mistake: believing the last project's answer applies here. Fix: rerun
the analysis.

</Level>

<Level name="System design">

<Flow steps={['hard decision, no best practice', 'list options', 'find coupling points and trade-offs', 'decide least worst', 'ADR + fitness function', 'revisit condition']} caption="The working loop the whole book applies, chapter after chapter." />

Common mistake: skipping the fitness function step. Fix: governance makes the
decision stick.

</Level>

<Level name="Strategy">

I list three hard decisions my capstone faces if it ever splits into services and
write one ADR now in the book's style. Done when the ADR has two options, their
trade-offs, a decision, a fitness function and a revisit condition.

</Level>

</Levels>

## Part I, Pulling Things Apart

### 2. Discerning Coupling in Software Architecture

**Covers:** Architecture versus design and trade-off analysis, architecture quanta (independently deployable, high functional cohesion, high static coupling, dynamic quantum coupling), and the Sysops Squad saga on understanding quanta.

<Figure art={`
  static coupling: what a service needs to start (DB, libraries, broker)
  dynamic coupling: how services talk at runtime

        communication      consistency       coordination
        sync | async       atomic | eventual  orchestrated | choreographed
            \\                  |                    /
             +------ eight combinations (chapter 12) +
`} caption="Static coupling defines a quantum; three dynamic dimensions describe how quanta interact." />

<Levels label="Chapter 2, Discerning Coupling in Software Architecture">

<Level name="Beginner">

Two parts are coupled if a change in one might require a change in the other. An
architecture quantum is an independently deployable artefact with high functional
cohesion, high static coupling and synchronous dynamic coupling. Static coupling is
what it is wired to at deploy time (its database, frameworks, a broker); dynamic
coupling is how it communicates at runtime.

```md
Ticket service quantum:
  static: Node 22, ticket DB, message broker, auth library
  dynamic: sync call to customer service for profile (joins the quantum while waiting)
```

Common mistake: drawing quanta by deploy unit alone. Fix: include databases and
synchronous calls.

</Level>

<Level name="Intermediate">

Dynamic coupling has three dimensions. Communication: synchronous (caller waits)
or asynchronous (caller continues). Consistency: atomic (all-or-nothing) or
eventual. Coordination: orchestrated (a coordinator drives it) or choreographed
(each service reacts). Each combination has different coupling, complexity and
scalability.

```ts
type Dynamic = { comm: 'sync' | 'async'; consistency: 'atomic' | 'eventual'; coordination: 'orchestrated' | 'choreographed' };
const ticketAssign: Dynamic = { comm: 'async', consistency: 'eventual', coordination: 'orchestrated' };
```

Common mistake: choosing sync versus async without considering consistency and
coordination. Fix: decide all three together.

</Level>

<Level name="Advanced">

Static coupling is easiest to see through dependencies: a shared database puts
services in one quantum no matter how they deploy. A shared broker does not
necessarily, as long as the services do not wait on each other. A user
interface shared by several services can couple them too. Dynamic coupling
shifts: a synchronous call merges the characteristics of caller and callee for
the call's duration.

Common mistake: thinking a message broker couples everything. Fix: it is
infrastructure; what couples is waiting and shared data.

</Level>

<Level name="Edge cases">

One boundary each. A service with no database: its quantum is just itself and
what it calls synchronously. A batch job that reads another service's tables: a
hidden static coupling. A sync call with a fallback: weaker coupling, still
coupling.

Common mistake: forgetting batch jobs and reports when mapping coupling. Fix:
check database access logs.

</Level>

<Level name="Corner cases">

Two boundaries meet. Async communication plus atomic consistency: the hardest
combination to implement, because nothing waits yet everything must commit
together. Choreography plus a shared database: services react independently but
remain one quantum.

Common mistake: async plus atomic expectations without a plan. Fix: relax to
eventual consistency, or use synchronous orchestration.

</Level>

<Level name="Production level">

In production I map quanta from traces (synchronous paths) and database access
(shared tables), and record the three dynamic dimensions for each important
workflow.

```md
Workflow       comm   consistency  coordination
create ticket  sync   atomic       orchestrated
assign expert  async  eventual     orchestrated
survey         async  eventual     choreographed
```

Common mistake: assuming every workflow has the same dynamics. Fix: a row per
workflow.

</Level>

<Level name="Mindset">

Coupling is the thing to manage. The habit is to name the kind of coupling before
judging it.

Common mistake: "decoupled" as a binary. Fix: describe static and three dynamic
dimensions.

</Level>

<Level name="System design">

<Compare left="Static coupling" right="Dynamic coupling" rows={[
  ['deploy-time wiring', 'runtime interaction'],
  ['defines the quantum', 'describes interaction between quanta'],
  ['seen in dependencies and data', 'seen in traces and messages'],
]} caption="Two views of coupling. Both are needed to understand a distributed system." />

Common mistake: only one view. Fix: draw both.

</Level>

<Level name="Strategy">

I draw the quanta of my capstone as if split into three services and fill the

### 3. Architectural Modularity

**Covers:** Modularity drivers (maintainability, testability, deployability, scalability, availability and fault tolerance), and the Sysops Squad saga on creating a business case for breaking apart the monolith.

<Flow steps={['business problem', 'modularity driver', 'measurable target', 'business case', 'decomposition']} caption="Why to break a system apart. Without a driver and a target, it is a rewrite looking for a reason." />

<Levels label="Chapter 3, Architectural Modularity">

<Level name="Beginner">

Breaking a monolith apart needs a reason the business recognises. The drivers:
maintainability (changes are easier and safer), testability (smaller scope to
test), deployability (deploy parts independently, more often, with less risk),
scalability and elasticity (scale the part that needs it), and availability and
fault tolerance (one part failing does not take down the rest).

```md
Driver: deployability. Today: one deploy a fortnight, 2-hour freeze, 30% rollback rate.
Target: ticket service deploys daily, rollback under 5 minutes.
```

Common mistake: "microservices are modern" as the business case. Fix: a driver
with a measured baseline and a target.

</Level>

<Level name="Intermediate">

Each driver maps to something measurable. Maintainability: change lead time,
files touched per change. Testability: test suite duration, coverage of changed
code. Deployability: deploy frequency, failure rate. Scalability: throughput per
instance, cost at peak. Fault tolerance: blast radius of incidents.

```sh
# files touched per change, a maintainability signal
git log --since=90.days --pretty=format: --name-only | grep -v '^$' | wc -l
git log --since=90.days --oneline | wc -l
```

Common mistake: claiming maintainability will improve without a baseline. Fix:
measure before the split.

</Level>

<Level name="Advanced">

Drivers interact. Splitting helps deployability and fault tolerance but adds
network cost, which hurts performance; it helps scalability of one part but
complicates data consistency. A business case should name the driver, the
expected improvement, and the new costs.

Common mistake: a business case with benefits only. Fix: list the operational and
consistency costs alongside.

</Level>

<Level name="Edge cases">

One boundary each. A monolith that is slow only in one module: extract that one.
A monolith that fails because of one bad dependency: isolate it. A monolith that
is fine except for team friction: modularise in place first.

Common mistake: splitting everything for one module's problem. Fix: extract the
module with the driver.

</Level>

<Level name="Corner cases">

Two boundaries meet. Fault tolerance plus synchronous calls: if the split
services call each other synchronously, a failure still cascades. Scalability
plus a shared database: services scale, the database does not.

Common mistake: splitting the code but keeping sync calls and one database. Fix:
the driver must survive the coupling analysis.

</Level>

<Level name="Production level">

In production the business case becomes a set of before and after metrics,
checked after each extraction.

```md
After extracting tickets (8 weeks):
deploys/week 0.5 -> 6 | rollback time 120 min -> 4 min | cross-service incidents 0
New cost: +1 on-call rotation, +$140/month infra
```

Common mistake: never checking whether the split delivered. Fix: a review with
the same metrics.

</Level>

<Level name="Mindset">

Modularity serves a business goal. The habit is to state which driver I am
pursuing and how I will know it worked.

Common mistake: modularity as an aesthetic. Fix: drivers and numbers.

</Level>

<Level name="System design">

<Layers layers={[
  { name: 'Business outcome', note: 'faster fixes, fewer outages, lower cost at peak' },
  { name: 'Modularity driver', note: 'deployability, fault tolerance, scalability' },
  { name: 'Metric', note: 'deploy frequency, blast radius, cost per request' },

Common mistake: starting at the bottom layer. Fix: start at the outcome.

</Level>

<Level name="Strategy">

I write a one-page business case for extracting one module of my capstone, with a
driver, baseline metrics from my repo, a target and new costs. Done when the page
would convince a skeptical reviewer, or I decide not to split.

</Level>

### 4. Architectural Decomposition

**Covers:** Whether a codebase is decomposable (afferent and efferent coupling, abstractness and instability, distance from the main sequence), component-based decomposition, tactical forking, and the Sysops Squad saga on choosing a decomposition approach.

<Compare left="Component-based decomposition" right="Tactical forking" rows={[
  ['refactor components, then extract', 'clone the monolith, delete what each service does not need'],
  ['works when components are well defined', 'works for a big ball of mud'],
  ['cleaner result, slower start', 'fast start, leftover dead code'],
]} caption="Two decomposition approaches. The codebase's structure decides which one fits." />

<Levels label="Chapter 4, Architectural Decomposition">

<Level name="Beginner">

Before splitting, check whether the codebase is decomposable. If components have
clear boundaries and manageable coupling, refactor and extract them
(component-based decomposition). If it is a big ball of mud, tactical forking may
be faster: copy the whole codebase for each new service and delete what that
service does not need.

```sh
# a rough coupling check: how many modules import each module?
npx madge --json src | node -e "const g=JSON.parse(require('fs').readFileSync(0));const ca={};for(const[k,v]of Object.entries(g))for(const d of v)ca[d]=(ca[d]||0)+1;console.log(Object.entries(ca).sort((a,b)=>b[1]-a[1]).slice(0,5))"
```

Common mistake: starting extraction without measuring coupling. Fix: analyse the
codebase first.

</Level>

<Level name="Intermediate">

Metrics help judge decomposability: afferent coupling (incoming), efferent
coupling (outgoing), abstractness, instability, and distance from the main
sequence. Components far from the main sequence (concrete and stable, or abstract
and unstable) are hard to extract.

```ts
function distance(ca: number, ce: number, abstractTypes: number, totalTypes: number) {
  const I = ce / (ca + ce), A = abstractTypes / totalTypes;
  return Math.abs(A + I - 1);
}
console.log(distance(12, 1, 0, 20).toFixed(2)); // 0.92: concrete and stable, in the zone of pain
```

Common mistake: extracting the most depended-on component first. Fix: start
with low-coupling components.

</Level>

<Level name="Advanced">

Tactical forking: clone, then delete. It avoids untangling everything up front
but leaves dead code, duplicated logic and shared data to clean up later. It is
honest about the starting point: when nothing is cleanly separable, deleting is
easier than extracting.

```md
Fork 1: ticket service, delete reporting, billing, survey code
Fork 2: reporting service, delete ticket workflow, billing, survey code
Then: remove dead code in each, split data by chapter 6.
```

Common mistake: forking and never cleaning up. Fix: plan the cleanup as part of
the migration.

</Level>

<Level name="Edge cases">

One boundary each. A codebase with no folders: no components to measure. A god
class used by everything: blocks component-based decomposition. A small monolith:
maybe no decomposition needed.

Common mistake: decomposing a small, healthy monolith. Fix: check the business
case from chapter 3 first.

</Level>

<Level name="Corner cases">

Two boundaries meet. Tactical forking plus shared data: both forks still use one
database, so data is the real coupling left. Component-based decomposition plus a
deadline: refactoring takes time before any extraction shows value.

Common mistake: underestimating the data step. Fix: plan data decomposition
alongside code.

</Level>

<Level name="Production level">

In production I run coupling metrics in CI during a decomposition to watch
progress and stop regressions.

```js
if (distance(ca, ce, a, t) > 0.7) console.warn('component drifting into the zone of pain');
```

Common mistake: one-off analysis. Fix: track metrics through the migration.

</Level>

<Level name="Mindset">

Measure, then choose the approach. The habit is to accept the codebase as it is
and pick the decomposition that fits it.

Common mistake: forcing component-based decomposition on a ball of mud. Fix:
tactical forking when untangling would take longer than deleting.

</Level>

<Level name="System design">

<Flow steps={['measure coupling and structure', 'decomposable?', 'yes: component-based patterns (ch 5)', 'no: tactical forking', 'split data (ch 6)', 'tune granularity (ch 7)']} caption="Choosing a decomposition path. Both paths end at data and granularity." />

Common mistake: skipping data. Fix: the data path is the long one.

</Level>

<Level name="Strategy">

I compute instability, abstractness and distance for each module of my capstone
and decide which decomposition approach I would use. Done when the metrics table
exists and the choice is written with its reason.

</Level>

### 5. Component-Based Decomposition Patterns

**Covers:** The six patterns: identify and size components, gather common domain components, flatten components, determine component dependencies, create component domains, and create domain services, each with a description, fitness functions and a Sysops Squad saga episode.

<Flow steps={['identify and size', 'gather common domain', 'flatten', 'determine dependencies', 'create component domains', 'create domain services']} caption="The six patterns in order. Each prepares the codebase for the next." />

<Levels label="Chapter 5, Component-Based Decomposition Patterns">

<Level name="Beginner">

Component-based decomposition follows six patterns in order. Identify and size
components (find them and measure their size, often by statement count). Gather
common domain components (find duplicated domain logic). Flatten components
(remove components nested inside others). Determine component dependencies (map
who uses whom). Create component domains (group components into domains). Create
domain services (extract each domain as a service).

```ts
// identify and size: statements per component (a rough proxy by lines)
const sizes = Object.fromEntries(components.map((c) => [c, countStatements(`src/${c}`)]));
const mean = Object.values(sizes).reduce((a, b) => a + b) / components.length;
```

Common mistake: extracting services before sizing components. Fix: size first,
so oversized components are split before extraction.

</Level>

<Level name="Intermediate">

Sizing uses statements rather than files, and flags components far above or below
the mean (by standard deviation). Gathering common domain components finds
logic like "notification" scattered in several places and consolidates it.
Flattening removes orphaned classes in a parent namespace when the namespace also
has child namespaces, so each component is a leaf.

```ts
const sd = Math.sqrt(Object.values(sizes).reduce((s, x) => s + (x - mean) ** 2, 0) / components.length);
for (const [c, s] of Object.entries(sizes)) if (Math.abs(s - mean) > 2 * sd) console.log('outlier', c, s);
```

Common mistake: components nested inside components. Fix: flatten so every
component is a leaf namespace.

</Level>

<Level name="Advanced">

Determining dependencies shows whether the codebase is feasible to split:
components with many incoming dependencies are hard to move. Component domains
group related components (ticketing, reporting, customer) and are reflected in
namespaces. Creating domain services moves each domain into a separately
deployed service, usually as a step towards service-based architecture.

Each pattern has fitness functions to keep the work from regressing.

```ts
test('every component belongs to a domain namespace', () => {
  for (const c of components) expect(c).toMatch(/^(ticket|customer|report|admin)\//);
});
```

Common mistake: creating domain services while components still cross domains.
Fix: finish component domains first.

</Level>

<Level name="Edge cases">

One boundary each. A component that belongs to two domains: split it. A tiny
component under the mean: merge it. A shared component (notifications) that every
domain uses: a candidate for a shared service or library (chapter 8).

Common mistake: duplicate domain logic left in place. Fix: gather it before
extracting.

</Level>

<Level name="Corner cases">

Two boundaries meet. Flattening plus active development: namespaces change under
the team's feet, so coordinate. Domain services plus a shared database: services
are separate but data is not, which is fine as an intermediate step.

Common mistake: treating shared database as failure. Fix: it is a valid stage;
split data later if drivers demand.

</Level>

<Level name="Production level">

In production the patterns run over weeks with fitness functions in CI, so each
step holds while the team keeps delivering features.

```yaml
ci-decomposition:
  - component-size-outliers: warn
  - no-nested-components: error
  - domain-namespace-rule: error
  - cross-domain-deps-max: 3
```

Common mistake: a decomposition branch that lives for months. Fix: small steps on
main, guarded by checks.

</Level>

<Level name="Mindset">

Incremental and governed. The habit is to move one step at a time and lock it in
with a check.

Common mistake: a big-bang restructure. Fix: patterns in order, each guarded.

</Level>

<Level name="System design">

<Layers layers={[
  { name: 'Domain services', note: 'separately deployed, one per domain' },
  { name: 'Component domains', note: 'namespaces grouping related components' },
  { name: 'Flattened components', note: 'leaf namespaces, sized and deduplicated' },
  { name: 'Monolith code', note: 'as found' },
]} caption="The patterns build upward. Skipping a layer leaves the next one unstable." />

Common mistake: jumping from monolith to domain services. Fix: build each layer.

</Level>

<Level name="Strategy">

I apply the first four patterns to my capstone as an analysis: component sizes

analysis is in my design doc and one fitness function from it runs in CI.

</Level>

### 6. Pulling Apart Operational Data

**Covers:** Data decomposition drivers (disintegrators: change control, connection management, scalability, fault tolerance, architectural quanta, database type optimisation; integrators: data relationships, database transactions), decomposing monolithic data in five steps, selecting a database type, and the Sysops Squad saga on polyglot databases.

<Flow steps={['analyse DB, create data domains', 'assign tables to domains', 'separate connections per domain', 'move schemas to separate servers', 'switch over']} caption="Five steps from one monolithic database to separate ones. Each step is reversible until the last." />

<Levels label="Chapter 6, Pulling Apart Operational Data">

<Level name="Beginner">

Splitting a database needs reasons, and there are forces on both sides.
Disintegrators push to split: change control (a schema change breaks many
services), connection management (too many services exhaust connections),
scalability, fault tolerance (the shared database is a single point of failure),
architectural quanta (the shared database merges quanta), and database type
optimisation (some data fits another kind of store). Integrators push to keep data
together: relationships (foreign keys, joins) and transactions.

```md
tickets + customers:
  disintegrators: separate scaling (tickets 50x more writes), change control
  integrators: FK from ticket to customer, create-ticket transaction reads customer
```

Common mistake: splitting data because the code was split. Fix: weigh
disintegrators against integrators per table group.

</Level>

<Level name="Intermediate">

The five-step process. 1: analyse the database and create data domains (groups
of tables that belong together). 2: assign tables to data domains, ideally as
schemas. 3: separate database connections so each service connects only to its
domain's schema. 4: move schemas to separate database servers. 5: switch over.
Cross-domain joins and foreign keys must be removed along the way.

```sql
CREATE SCHEMA ticketing; CREATE SCHEMA customer;
ALTER TABLE public.ticket SET SCHEMA ticketing;
ALTER TABLE public.customer SET SCHEMA customer;
-- step 3: per-service roles
CREATE ROLE ticket_svc LOGIN; GRANT USAGE ON SCHEMA ticketing TO ticket_svc;
```

Common mistake: moving to separate servers before connections are separated. Fix:
step 3 first; it reveals hidden cross-domain access.

</Level>

<Level name="Advanced">

Cross-domain foreign keys become references by id with application-level
checks. Cross-domain joins become API calls, replicated data, or a read model
(chapter 10). Transactions spanning domains become distributed workflows
(chapters 9 and 12). Selecting a database type per domain: relational,
key-value, document, column family, graph, NewSQL, cloud native, time series,
each rated on ease of learning, ease of data modelling, scalability, availability,
consistency, programming language support, product maturity, SQL support and
community.

```sql
-- before: FK across domains
ALTER TABLE ticketing.ticket DROP CONSTRAINT ticket_customer_fk;
-- after: the ticket service validates customer_id via the customer API on create
```

Common mistake: polyglot persistence by default. Fix: change database type only
when a domain's access pattern clearly fits another store.

</Level>

<Level name="Edge cases">

One boundary each. A table used by every domain (reference data such as
countries): replicate it rather than own it centrally. A table with mixed columns
from two domains: split the table. A view joining domains: becomes a read model.

Common mistake: forcing reference data into one owner's API. Fix: replicate
read-only reference data.

</Level>

<Level name="Corner cases">

Two boundaries meet. Dropping a foreign key plus concurrent deletes: a customer is
deleted while a ticket references it, so orphans appear. Separate servers plus a
report that joined everything: the report breaks at switch-over.

Common mistake: discovering cross-domain queries at switch-over. Fix: step 3's
per-schema roles make them fail early in testing.

</Level>

<Level name="Production level">

In production each step ships separately, with monitoring of query errors and
connection counts, and a rollback plan until step 5.

```sh
# find queries that touch two schemas (Postgres, from logs)
grep -E "ticketing\.[a-z_]+.*customer\.[a-z_]+" postgres.log | sort | uniq -c | sort -rn | head
```

Common mistake: switch-over without a dry run. Fix: a staging switch-over with
production-like data.

</Level>

<Level name="Mindset">

Data is the hard part. The habit is to analyse data coupling before code
coupling, because data outlives services.

Common mistake: code-first decomposition with data as an afterthought. Fix: data
domains early.

</Level>

<Level name="System design">

<Compare left="Disintegrators" right="Integrators" rows={[
  ['change control, connections', 'data relationships'],
  ['scalability, fault tolerance', 'database transactions'],
  ['quanta, database type fit', 'strong enough to outweigh several splitters'],
]} caption="Forces on a data split. The integrators are few but strong." />

Common mistake: ignoring transactions. Fix: a strong transactional need often
outweighs several disintegrators.

</Level>

<Level name="Strategy">

I group my capstone's tables into data domains, move them to schemas with per-
module roles, and list every cross-schema foreign key and join. Done when the
roles are in place, the list is complete, and each item has a planned
replacement.

### 7. Service Granularity

**Covers:** Granularity disintegrators (service scope and function, code volatility, scalability and throughput, fault tolerance, security, extensibility), granularity integrators (database transactions, workflow and choreography, shared code, data relationships), finding the right balance, and the Sysops Squad saga on ticket assignment and customer registration granularity.

<Figure art={`
  disintegrators (split)            integrators (merge)
  scope and function   --+     +--  database transactions
  code volatility      --+     +--  workflow and choreography
  scalability          --+-- ? +--  shared code
  fault tolerance      --+     +--  data relationships
  security             --+
  extensibility        --+
`} caption="Granularity as a balance of forces. The right size is where the strongest forces on each side meet." />

<Levels label="Chapter 7, Service Granularity">

<Level name="Beginner">

Granularity is the size of a service. Too coarse and parts with different needs
are stuck together; too fine and services must constantly coordinate. Six
disintegrators argue for splitting: different scope and function, different code
volatility (one part changes weekly, another yearly), different scalability or
throughput, fault tolerance (isolate a crash-prone part), security (isolate
sensitive data), and extensibility (a part that will grow with variants).

```md
Notification service: email, SMS, push in one service?
Scope: all "notify the customer" -> cohesive
Volatility: SMS rules change weekly -> split SMS?
Scalability: email 100k/day, SMS 1k/day -> similar enough
```

Common mistake: splitting by noun (one service per entity). Fix: split by
disintegrators.

</Level>

<Level name="Intermediate">

Four integrators argue for keeping together: database transactions (the parts
must commit atomically), workflow and choreography (they talk constantly to do one
job), shared code (they share a lot of domain logic), and data relationships
(their data is intertwined).

```ts
// a workflow integrator signal: calls per user action between two candidate services
const calls = trace.spans.filter((s) => s.from === 'profile' && s.to === 'credentials').length;
console.log(calls); // 6 per registration: strong integrator
```

Common mistake: splitting services that must share a transaction. Fix: keep them
together or accept a saga with its costs.

</Level>

<Level name="Advanced">

Finding the balance means writing both lists for a candidate split and weighing
them with the business: "if we split, customer registration is no longer atomic;
is a partially registered customer acceptable?" Security as a disintegrator often
wins: isolating credit card data shrinks the compliance scope, even if it costs
a transaction.

```md
Customer registration: profile + credit card + password
Disintegrator: security (card data to its own service, limits PCI scope)
Integrator: transaction (registration must be atomic)
Decision: split card data; registration orchestrated with compensation on failure
```

Common mistake: architects deciding alone on consistency. Fix: ask the business
whether eventual consistency is acceptable here.

</Level>

<Level name="Edge cases">

One boundary each. A part with high volatility but tiny size: maybe a plug-in, not
a service. A part needing different security but sharing a transaction. A part
that fails often because of a third-party API: fault tolerance argues to isolate
it.

Common mistake: splitting only on volatility. Fix: weigh it against the
integrators.

</Level>

<Level name="Corner cases">

Two boundaries meet. Extensibility plus shared code: variants share most logic,
so splitting duplicates it. Fault tolerance plus workflow: isolating a part that
is in every workflow's synchronous path does not improve fault tolerance.

Common mistake: isolating a part that is still called synchronously by all.
Fix: isolation needs async or a fallback to help.

</Level>

<Level name="Production level">

In production granularity decisions are ADRs listing the disintegrators and
integrators, with a revisit condition, because the forces change over time.

```md
ADR-H7 Ticket assignment and routing stay in one service
Integrators: workflow (assign then route every time), shared data
Disintegrators considered: volatility (routing rules change monthly) - not enough
Revisit if: routing gets a separate scaling need.
```

Common mistake: granularity fixed forever. Fix: revisit when forces shift.

</Level>

<Level name="Mindset">

Size by forces, not by rules. The habit is to write both lists for every split or
merge.

Common mistake: "services should be small". Fix: services should be the size the
forces say.

</Level>

<Level name="System design">

<Compare left="Too fine" right="Too coarse" rows={[
  ['chatty workflows, sagas everywhere', 'mixed scaling and change rates'],
  ['many deploy units to operate', 'larger blast radius'],
  ['shared code duplicated', 'security scope too wide'],
]} caption="Two failure modes of granularity. The forces lists help avoid both." />

Common mistake: fixing one by creating the other. Fix: change one boundary at a
time.

</Level>

<Level name="Strategy">

I pick two candidate splits in my capstone and write disintegrators and
integrators for each, then decide. Done when both decisions are ADRs and one of
them asks a business question about consistency.

</Level>

</Levels>

### 8. Reuse Patterns

**Covers:** Code replication, shared libraries (dependency management and change control, versioning strategies), shared services (change risk, performance, scalability, fault tolerance), sidecars and the service mesh, and the Sysops Squad saga on common infrastructure logic and shared domain functionality.

<Compare left="Shared library" right="Shared service" rows={[
  ['compile-time binding, versioned', 'runtime binding, one version live'],
  ['no network cost', 'network latency and failure'],
  ['change needs consumer upgrades', 'change is instant, and risky for all'],
  ['scales with each consumer', 'must scale for all consumers'],
]} caption="The central reuse trade-off. Replication and sidecars complete the set of options." />

<Levels label="Chapter 8, Reuse Patterns">

<Level name="Beginner">

When several services need the same code, there are four options. Code
replication: copy it into each service (no coupling, but fixes must be applied
everywhere). Shared library: package it and version it. Shared service: run it
once and call it remotely. Sidecar: for operational code (logging, metrics, mTLS),
run it alongside each service, often managed by a service mesh.

```ts
// replication is fine for tiny, stable helpers
export const slug = (s: string) => s.toLowerCase().trim().replace(/[^a-z0-9]+/g, '-');
```

Common mistake: a shared service for a five-line helper. Fix: replicate or
library for small stable code.

</Level>

<Level name="Intermediate">

Shared libraries need dependency management: versioning lets each consumer upgrade
when ready, at the cost of several versions in use. Fine-grained libraries (one
per concern) reduce change impact but multiply dependencies; coarse-grained ones
simplify dependencies but force unrelated upgrades. Deprecation policy limits how
many old versions stay supported.

```json
{ "dependencies": { "@sysops/validation": "^2.3.0", "@sysops/formatting": "1.x" } }
```

Common mistake: unversioned shared libraries (always latest). Fix: semantic
versioning and a deprecation window.

</Level>

<Level name="Advanced">

Shared services trade change control for runtime risk: a bug in a shared service
breaks every consumer at once. They also add latency, need to scale for all
consumers, and are a fault tolerance risk. Sidecars and a service mesh suit
operational coupling: consistent infrastructure behaviour without sharing domain
code. Domain code is usually better replicated or in a library than in a shared
service.

```yaml
# sidecar concerns, not domain logic
sidecar: { logging: otel, metrics: prometheus, mtls: on, retries: { max: 2 } }
```

Common mistake: putting domain logic in a sidecar. Fix: sidecars for operational
concerns only.

</Level>

<Level name="Edge cases">

One boundary each. A security fix in a shared library: every consumer must
upgrade, fast. A shared service down: all consumers degrade. Replicated code that
diverges: two services now calculate tax differently.

Common mistake: replicating code with business rules that must stay identical.
Fix: a library or service for rules that must match.

</Level>

<Level name="Corner cases">

Two boundaries meet. Shared library plus polyglot services: one library per
language, kept in sync. Shared service plus a hot path: added latency on every
request.

Common mistake: assuming a shared service is "reuse for free". Fix: count the
network calls it adds per request.

</Level>

<Level name="Production level">

In production I choose per piece of shared code and write it down.

```md
reuse map
slug/formatting  -> replicate (tiny, stable)
validation rules -> library @sysops/validation (versioned, polyglot not needed)
pricing          -> shared service (changes often, must be consistent)
logging/mTLS     -> sidecar
```

Common mistake: one reuse strategy for everything. Fix: a reuse map.

</Level>

<Level name="Mindset">

Reuse is coupling. The habit is to ask what coupling each reuse option creates
before reaching for it.

Common mistake: reuse as an automatic good. Fix: sometimes duplication is the
cheaper coupling.

</Level>

<Level name="System design">

<Layers layers={[
  { name: 'Shared service', note: 'runtime coupling: frequently changing shared behaviour' },
  { name: 'Shared library', note: 'compile-time coupling: stable shared domain code' },
  { name: 'Sidecar / mesh', note: 'operational coupling: logging, security, traffic' },
  { name: 'Replication', note: 'no coupling: tiny, stable helpers' },
]} caption="Reuse options from most to least coupled. Choose the lowest that meets the need." />

Common mistake: starting at the top. Fix: start at the bottom.

</Level>

<Level name="Strategy">

I write a reuse map for my capstone's shared code and move one piece to the right
option. Done when the map exists and one change is committed with its reason.

</Level>

</Levels>

### 9. Data Ownership and Distributed Transactions

**Covers:** Assigning data ownership (single ownership, common ownership, joint ownership with the table split, data domain, delegate and service consolidation techniques), summary of data ownership, distributed transactions, eventual consistency patterns (background synchronisation, orchestrated request-based, event-based), and the Sysops Squad saga on data ownership for ticket processing.

<Figure art={`
  single ownership:  [svc A] writes T          -> A owns T
  common ownership:  [A][B][C][D] all write T  -> a dedicated service owns T
  joint ownership:   [A][B] write T            -> table split | data domain | delegate | consolidate
`} caption="Three ownership situations. The owner is the only service that writes the table." />

<Levels label="Chapter 9, Data Ownership and Distributed Transactions">

<Level name="Beginner">

Data ownership means the service that writes a table owns it. Three cases.
Single ownership: one service writes it, so it owns it. Common ownership: most
services write it (an audit log), so a dedicated service owns it and others send
it data. Joint ownership: a few services write it, which needs one of four
techniques.

```ts
// common ownership: services send audit entries, only the audit service writes
await bus.publish('audit.entry', { actor, action: 'ticket.closed', ticketId, at: new Date().toISOString() });
```

Common mistake: several services writing one table after a split. Fix: decide an
owner for every table.

</Level>

<Level name="Intermediate">

Joint ownership techniques. Table split: split the table so each service owns its
columns (the product table becomes product and inventory). Data domain: services
share a schema and both write it (simple, but keeps them coupled). Delegate: one
service owns the table, the other asks it to write (by API or message), choosing
whether the owner is the service whose domain it is or the one that writes most.
Service consolidation: merge the two services.

```sql
-- table split: catalog owns product, inventory owns stock
CREATE TABLE catalog.product (id uuid PRIMARY KEY, name text, description text);
CREATE TABLE inventory.stock (product_id uuid PRIMARY KEY, on_hand int);
```

Common mistake: data domain sharing as a permanent solution. Fix: use it only
when the other techniques cost more.

</Level>

<Level name="Advanced">

Splitting data breaks ACID transactions across services. Distributed transactions
lose atomicity, consistency, isolation and sometimes durability guarantees across
the whole. Eventual consistency patterns restore agreement over time.
Background synchronisation: a separate process reconciles data periodically
(simple, slow, couples to all databases). Orchestrated request-based: a service
orchestrates updates to all services during the request (fast consistency,
complex error handling). Event-based: the owner publishes an event and others
update themselves (decoupled, fast, but error handling is harder).

```ts
// event-based: customer service owns customer; others listen
bus.subscribe('customer.unsubscribed', async (e) => {
  await db.update(subscriptions).set({ active: false }).where(eq(subscriptions.customerId, e.customerId));
});
```

Common mistake: assuming distributed transactions behave like local ones. Fix:
pick an eventual consistency pattern and design its errors.

</Level>

<Level name="Edge cases">

One boundary each. An event lost: the subscriber never updates. Background sync
during a partial failure: half the records reconcile. An orchestrator that crashes
mid-request: some services updated, some not.

Common mistake: no reconciliation for missed events. Fix: a periodic check as a
backstop.

</Level>

<Level name="Corner cases">

Two boundaries meet. Delegate technique plus high write volume: the owning service
becomes a bottleneck. Event-based consistency plus a user who reads immediately:
stale data seen.

Common mistake: delegating writes to an owner that cannot handle the load. Fix:
measure write rates before choosing the owner.

</Level>

<Level name="Production level">

In production I keep an ownership table and a consistency pattern per shared
fact, with monitoring for divergence.

```md
table            owner      writers via        consistency
ticket           ticketing  -                  local
customer         customer   -                  local
customer_subs    customer   events to survey   event-based, nightly reconcile
audit_log        audit      events from all    event-based
```

Common mistake: no ownership table. Fix: one row per table.

</Level>

<Level name="Mindset">

One writer per table. The habit is to ask "who owns this?" for every table and
"how do others learn about changes?" for every shared fact.

Common mistake: avoiding the ownership question. Fix: ask it at split time.

</Level>

<Level name="System design">

<Compare left="Background sync" right="Event-based" rows={[
  ['simple, independent of services', 'decoupled through events'],
  ['slow to converge', 'fast to converge'],
  ['couples to all databases', 'needs reliable publishing and handlers'],
]} caption="Two eventual consistency patterns. Orchestrated request-based sits between them with faster consistency and harder errors." />

Common mistake: one pattern for everything. Fix: choose per fact by how fast
consistency is needed.

</Level>

<Level name="Strategy">

I build the ownership table for my capstone with a technique for each jointly
owned table and a consistency pattern for each shared fact. Done when every table
has one owner and one shared fact uses events with a reconciliation backstop in
code.

</Level>

</Levels>

### 10. Distributed Data Access

**Covers:** The interservice communication pattern, column schema replication, the replicated caching pattern, the data domain pattern, and the Sysops Squad saga on data access for ticket assignment.

<Compare left="Pattern" right="Main trade-off" rows={[
  ['interservice communication', 'simple, but adds latency and runtime coupling'],
  ['column schema replication', 'fast local reads, but data can be stale and governance is hard'],
  ['replicated caching', 'fast in-memory reads, but memory limits and start-up dependency'],
  ['data domain', 'direct shared access, but couples services through the schema'],
]} caption="Four ways for a service to read data it does not own." />

<Levels label="Chapter 10, Distributed Data Access">

<Level name="Beginner">

After a split, a service often needs data it does not own (ticket assignment
needs expert profiles). Four patterns. Interservice communication: call the
owner's API. Column schema replication: copy the needed columns into my own
database and keep them updated. Replicated caching: keep an in-memory copy,
replicated from the owner. Data domain: share a schema between the services.

```ts
// interservice communication
const expert = await (await fetch(`http://experts/experts/${id}`)).json();
```

Common mistake: calling the owner's API inside a loop. Fix: batch, or use another
pattern for heavy reads.

</Level>

<Level name="Intermediate">

Interservice communication is simple and always fresh but adds latency, couples
availability, and loads the owner. Column schema replication gives local, fast
reads but the copy can be stale and someone must keep it in sync (usually
events). Replicated caching (an in-memory data grid) gives very fast reads with
the owner as the only writer, but data must fit in memory and the reader may
depend on the owner at start-up.

```ts
// column replication kept fresh by events
bus.subscribe('expert.updated', (e) => db.insert(expertCopy).values({ id: e.id, skills: e.skills }).onConflictDoUpdate({ target: expertCopy.id, set: { skills: e.skills } }));
```

Common mistake: replicated columns with no freshness monitoring. Fix: track the
lag between owner and copy.

</Level>

<Level name="Advanced">

The data domain pattern shares tables between services in one schema: no
latency, no sync, but it re-couples the services and blurs ownership. It suits
cases where data is tightly shared and the services are close. The choice depends
on read volume, freshness needs, data size and fault tolerance.

```md
Ticket assignment needs expert skills on every assignment (high read rate, small data, minutes of staleness OK)
-> replicated cache or column replication, not an API call per assignment
```

Common mistake: interservice calls for high-volume reads. Fix: replicate when
staleness is acceptable.

</Level>

<Level name="Edge cases">

One boundary each. An owner that is down: interservice calls fail, replicas still
work. A replica after a missed event: stale forever without reconciliation. Data
too large for memory: replicated caching is out.

Common mistake: assuming caches start warm. Fix: plan start-up when the owner is
unavailable.

</Level>

<Level name="Corner cases">

Two boundaries meet. Column replication plus a schema change at the owner: the
copy's sync breaks. Replicated caching plus many readers: every write replicates
to every reader.

Common mistake: owners changing event schemas without notice. Fix: versioned
events and contract tests (chapter 13).

</Level>

<Level name="Production level">

In production each cross-service read has a recorded pattern, a freshness target
and a monitor.

```yaml
reads:
  - consumer: assignment, data: expert.skills, pattern: column-replication, freshness: 5m, monitor: replica_lag_seconds
  - consumer: billing, data: customer.address, pattern: interservice, timeout_ms: 300
```

Common mistake: cross-service reads discovered by accident. Fix: list them.

</Level>

<Level name="Mindset">

Reading others' data is a design decision. The habit is to choose a pattern by
volume, freshness and failure tolerance.

Common mistake: the API call as the only option. Fix: four patterns, chosen per
read.

</Level>

<Level name="System design">

<Flow steps={['need data I do not own', 'how fresh?', 'how much and how often?', 'can I work if the owner is down?', 'choose pattern', 'monitor freshness']} caption="Choosing a data access pattern as a short set of questions." />

Common mistake: skipping the "owner down" question. Fix: ask it every time.

</Level>

<Level name="Strategy">

For my capstone's split design, I list each cross-service read and choose a
pattern with freshness and failure behaviour. Done when every read has a pattern
and one replicated read is implemented with a lag metric.

</Level>

### 11. Managing Distributed Workflows

**Covers:** Orchestration communication style, choreography communication style (workflow state management: front controller, stateless choreography, stamp coupling), trade-offs between orchestration and choreography, and the Sysops Squad saga on managing workflows.

<Compare left="Orchestration" right="Choreography" rows={[
  ['central workflow state', 'state spread across services'],
  ['easy error handling and recovery', 'error handling is hard'],
  ['orchestrator is a coupling point and bottleneck', 'highly decoupled, scales well'],
  ['good for complex workflows', 'good for simple, high-volume flows'],
]} caption="The coordination trade-off. Workflow complexity is the main deciding factor." />

<Levels label="Chapter 11, Managing Distributed Workflows">

<Level name="Beginner">

A workflow that spans services needs coordination. Orchestration: a dedicated
orchestrator calls each service in turn and handles errors. Choreography: each
service does its part and tells the next (by event or call); there is no central
coordinator.

```ts
// orchestration
async function placeTicket(t: Ticket) {
  const saved = await tickets.create(t);
  const expert = await assignment.assign(saved.id);
  await notify.customer(saved.customerId, `Assigned to ${expert.name}`);
}
```

Common mistake: choreography for a workflow with many error paths. Fix:
orchestrate complex workflows.

</Level>

<Level name="Intermediate">

Orchestration gives centralised workflow state, easy error handling, and
recoverability, at the cost of responsiveness (everything goes through one
service), fault tolerance (the orchestrator is critical), and coupling.
Choreography gives responsiveness, scalability and fault tolerance, but workflow
state and error handling are spread out, and recovery is hard.

```ts
// choreography: each service reacts
bus.subscribe('ticket.created', async (e) => bus.publish('ticket.assigned', await assignment.assign(e.id)));
bus.subscribe('ticket.assigned', (e) => notify.customer(e.customerId, 'Assigned'));
```

Common mistake: assuming choreography is always more scalable and therefore
better. Fix: weigh error handling and state needs.

</Level>

<Level name="Advanced">

In choreography, who knows the workflow's state? Options. Front controller: the
first service in the chain owns the state and others report back to it.
Stateless choreography: nobody stores state; to know where a ticket is, query each
service. Stamp coupling: pass the workflow state in the message itself, so each
service sees and updates it.

```ts
// stamp coupling: the message carries workflow state
type TicketMsg = { id: string; status: 'created' | 'assigned' | 'routed' | 'completed'; history: { step: string; at: string }[] };
```

Common mistake: stateless choreography with users asking "where is my ticket?".
Fix: a front controller or stamp coupling.

</Level>

<Level name="Edge cases">

One boundary each. A step that fails in choreography: who notices? A workflow with
one step: no coordination needed. A workflow where a step can be retried later:
choreography with a retry queue is fine.

Common mistake: no timeout on a workflow. Fix: a deadline after which someone (the
orchestrator or front controller) acts.

</Level>

<Level name="Corner cases">

Two boundaries meet. Orchestration plus high volume: the orchestrator must scale
horizontally, needing durable state. Stamp coupling plus large state: messages
grow, and every service sees fields it does not need.

Common mistake: unbounded state in messages. Fix: keep stamp state small or keep
a reference to stored state.

</Level>

<Level name="Production level">

In production orchestrators are often workflow engines with durable state,
retries and visibility. Choreographed flows need tracing across messages and a
way to see stuck workflows.

```yaml
stuck-detector: tickets with status in (created, assigned) and updated_at older than 30m -> alert
```

Common mistake: choreography with no stuck-workflow detection. Fix: a query or
monitor for workflows past their deadline.

</Level>

<Level name="Mindset">

Choose coordination per workflow. The habit is to rate each workflow's complexity
and error needs before picking a style.

Common mistake: one style for the whole system. Fix: both styles, each where it
fits.

</Level>

<Level name="System design">

<Flow steps={['list the workflow steps', 'count error paths', 'need central state?', 'volume and responsiveness', 'orchestrate or choreograph', 'how state is visible']} caption="Choosing coordination for one workflow." />

Common mistake: deciding before listing error paths. Fix: errors first.

</Level>

<Level name="Strategy">

I design one capstone workflow both ways, list error paths and state visibility for
each, and choose. Done when both designs and the decision are in my design doc
with the reason.

</Level>

</Levels>

### 12. Transactional Sagas

**Covers:** The eight transactional saga patterns (Epic, Phone Tag, Fairy Tale, Time Travel, Fantasy Fiction, Horror Story, Parallel, Anthology), state management and eventual consistency (saga state machines), techniques for managing sagas, and the Sysops Squad saga on atomic transactions and compensating updates.

<Figure art={`
  name              communication  consistency  coordination
  Epic              sync           atomic       orchestrated
  Phone Tag         sync           atomic       choreographed
  Fairy Tale        sync           eventual     orchestrated
  Time Travel       sync           eventual     choreographed
  Fantasy Fiction   async          atomic       orchestrated
  Horror Story      async          atomic       choreographed
  Parallel          async          eventual     orchestrated
  Anthology         async          eventual     choreographed
`} caption="The eight sagas are the eight combinations of chapter 2's three dynamic coupling dimensions." />

<Levels label="Chapter 12, Transactional Sagas">

<Level name="Beginner">

A saga is a distributed workflow that has to keep data consistent across services.
The book names the eight combinations of communication (sync or async),
consistency (atomic or eventual) and coordination (orchestrated or choreographed).
The Epic saga is the familiar one: synchronous, atomic, orchestrated, like a
monolith's transaction spread over services, with compensating updates on
failure.

```ts
// Epic saga: orchestrator calls each service; on failure, compensate in reverse
const done: Array<() => Promise<void>> = [];
try {
  await tickets.create(t);   done.push(() => tickets.delete(t.id));
  await billing.reserve(t);  done.push(() => billing.release(t.id));
  await assign.expert(t);
} catch (e) { for (const undo of done.reverse()) await undo().catch(log); throw e; }
```

Common mistake: assuming compensation makes it truly atomic. Fix: other requests
can see intermediate states; compensation is not isolation.

</Level>

<Level name="Intermediate">

Each saga trades coupling, complexity, responsiveness and scalability. Sync and
atomic (Epic, Phone Tag) are easiest to reason about but couple tightly and scale
poorly. Eventual consistency (Fairy Tale, Time Travel, Parallel, Anthology)
loosens coupling and improves scale. Async with atomic (Fantasy Fiction, Horror
Story) is the hardest: asking for all-or-nothing while not waiting. The Horror
Story (async, atomic, choreographed) is the name for the worst combination:
everything spread out and still expected to commit together.

```ts
type Saga = { comm: 'sync' | 'async'; consistency: 'atomic' | 'eventual'; coordination: 'orchestrated' | 'choreographed' };
const isHorror = (s: Saga) => s.comm === 'async' && s.consistency === 'atomic' && s.coordination === 'choreographed';
```

Common mistake: drifting into the Horror Story by adding async messaging to an
atomic workflow. Fix: relax to eventual (Anthology) or add an orchestrator.

</Level>

<Level name="Advanced">

State management: an eventually consistent saga needs a state machine so the
system knows where each instance is and what to do on failure. Each state lists
its allowed transitions; failures move to explicit states rather than vanishing.
Techniques: track saga state in the orchestrator or in a saga table, annotate
code or events with the saga they belong to, and design compensations or
alternative paths for each step.

```ts
type State = 'CREATED' | 'ASSIGNED' | 'ACCEPTED' | 'COMPLETED' | 'NO_EXPERT' | 'REASSIGN';
const next: Record<State, State[]> = {
  CREATED: ['ASSIGNED', 'NO_EXPERT'], ASSIGNED: ['ACCEPTED', 'REASSIGN'], REASSIGN: ['ASSIGNED', 'NO_EXPERT'],
  ACCEPTED: ['COMPLETED'], COMPLETED: [], NO_EXPERT: ['CREATED'],
};
const move = (s: State, to: State) => { if (!next[s].includes(to)) throw new Error(`${s} -> ${to} not allowed`); return to; };
```

Common mistake: eventual consistency with no state machine. Fix: explicit
states, transitions and failure states.

</Level>

<Level name="Edge cases">

One boundary each. A compensation that fails (refund service down): needs its
own retry and alert. A step that cannot be undone (an email sent): needs a
follow-up action instead. A saga that times out halfway: needs a defined state.

Common mistake: compensations that are assumed to succeed. Fix: retry
compensations and alert when they fail.

</Level>

<Level name="Corner cases">

Two boundaries meet. Parallel saga plus ordering requirements: async steps finish
in any order, so later steps must not assume order. Epic saga plus a slow service:
the user waits for the slowest step, and every service holds resources meanwhile.

Common mistake: treating an orchestrated async saga as ordered. Fix: model order
in the state machine.

</Level>

<Level name="Production level">

In production each saga has its pattern name, state machine, compensations,
timeouts and a dashboard of instances by state.

```sql
SELECT state, count(*) FROM saga_instances WHERE type = 'ticket' GROUP BY state;
-- NO_EXPERT growing? alert
```

Common mistake: sagas with no visibility. Fix: a saga table and a dashboard.

</Level>

<Level name="Mindset">

Name the saga before building it. The habit is to place each workflow in the
eight-pattern table and accept its trade-offs consciously.

Common mistake: building a saga accidentally. Fix: classify it on the three
dimensions first.

</Level>

<Level name="System design">

<Flow steps={['workflow across services', 'choose comm, consistency, coordination', 'name the saga', 'state machine and compensations', 'timeouts and alerts', 'dashboard']} caption="From workflow to running saga. Classification comes before code." />

Common mistake: compensations designed after an incident. Fix: design them with
the state machine.

</Level>

<Level name="Strategy">

I build one saga for my capstone (Fairy Tale: sync, eventual, orchestrated) with a
state machine, compensations, a timeout and a failure injected in the middle. Done
when a test shows the failure leads to a defined state and the compensations run.

</Level>

</Levels>

### 13. Contracts

**Covers:** Strict versus loose contracts (trade-offs, contracts in microservices), stamp coupling (over-coupling via stamp coupling, bandwidth, stamp coupling for workflow management), and the Sysops Squad saga on managing ticketing contracts.

<Compare left="Strict contract" right="Loose contract" rows={[
  ['schema enforced, exact types', 'name-value pairs, few rules'],
  ['early, clear errors', 'tolerant to change'],
  ['every change versions the contract', 'consumers break silently on meaning changes'],
  ['good for high-trust, critical data', 'good for decoupled, evolving services'],
]} caption="Contract strictness as a spectrum. Loose contracts need consumer-driven tests to stay safe." />

<Levels label="Chapter 13, Contracts">

<Level name="Beginner">

A contract is the format of data exchanged between parts. Strict contracts
(typed schemas, exact fields) catch errors early but force versioning on every
change. Loose contracts (simple name-value pairs, JSON with few rules) tolerate
change but let mistakes slip through.

```ts
import { z } from 'zod';
const TicketCreated = z.object({ id: z.string().uuid(), customerId: z.string(), priority: z.enum(['low', 'high']) }).strict();
TicketCreated.parse({ id: 'x', customerId: 'c', priority: 'high' }); // throws: invalid uuid
```

Common mistake: strict contracts everywhere in a system of many services. Fix:
strict where correctness matters most, looser elsewhere.

</Level>

<Level name="Intermediate">

Loose contracts in microservices pair well with consumer-driven contracts: each
consumer writes tests of what it needs from the provider, and the provider runs
them in its CI. The provider can change freely as long as no consumer's needs
break.

```ts
// consumer-driven contract: survey service needs only id and customerId
test('ticket.completed has what survey needs', () => {
  const msg = sampleFromProvider('ticket.completed');
  expect(msg).toEqual(expect.objectContaining({ id: expect.any(String), customerId: expect.any(String) }));
});
```

Common mistake: loose contracts with no tests. Fix: consumer-driven contract
tests run by the provider.

</Level>

<Level name="Advanced">

Stamp coupling is passing a large data structure when the receiver needs only
part of it. It over-couples (the receiver depends on fields it does not use, and
changes to them may break it) and wastes bandwidth. It is useful in one case:
workflow management, where a message carries the workflow state (chapter 11).

```ts
// over-coupled: send the whole customer for one field
await wishlist.update({ customer: fullCustomerRecord });
// better: send what is needed
await wishlist.update({ customerId: c.id, name: c.name });
```

Common mistake: sending full records "in case". Fix: send what the receiver
needs, unless stamp coupling is deliberate for workflow state.

</Level>

<Level name="Edge cases">

One boundary each. An optional field added: fine for loose contracts. A field
renamed: breaks everyone. A field's meaning changed with the same name: breaks
silently. An enum value added: strict consumers fail.

Common mistake: changing a field's meaning without renaming. Fix: new field,
deprecate the old one.

</Level>

<Level name="Corner cases">

Two boundaries meet. Strict contracts plus independent deploys: provider and
consumers must support two versions during a migration. Stamp coupling plus a
large fleet of consumers: bandwidth multiplies.

```ts
const bytes = 4_000, msgsPerSec = 200, consumers = 6;
console.log((bytes * msgsPerSec * consumers / 1e6).toFixed(1), 'MB/s'); // 4.8 MB/s for data mostly unused
```

Common mistake: ignoring bandwidth of large messages. Fix: compute it.

</Level>

<Level name="Production level">

In production contracts are versioned, stored in a registry, and checked by
consumer-driven tests in the provider's CI.

```yaml
contracts:
  ticket.created: { version: 3, schema: schemas/ticket-created.v3.json, consumers: [assignment, survey, analytics] }
```

Common mistake: contracts in people's heads. Fix: a registry and tests.

</Level>

<Level name="Mindset">

Contracts are coupling you choose. The habit is to choose strictness per
boundary and protect loose contracts with tests.

Common mistake: one strictness for all. Fix: per boundary.

</Level>

<Level name="System design">

<Flow steps={['identify boundary', 'how critical is the data?', 'strict or loose', 'consumer-driven tests', 'version and register', 'deprecate safely']} caption="Designing a contract from choice to evolution." />

Common mistake: no deprecation plan. Fix: versions with dates.

</Level>

<Level name="Strategy">

I write one strict contract (payment events) and one loose contract with a
consumer-driven test (survey events) in my capstone. Done when both run in CI and
a breaking change fails the consumer's test.

</Level>

</Levels>

### 14. Managing Analytical Data

**Covers:** Previous approaches (the data warehouse, the data lake), the data mesh (definition, data product quantum, data mesh, coupling and architecture quantum, when to use it), and the Sysops Squad saga on data mesh.

<Figure art={`
  data warehouse:  sources --ETL--> central schema --> reports
  data lake:       sources --raw--> central storage --> analysts transform later
  data mesh:       [domain svc + data product quantum] x N --> consumers across domains
`} caption="Three generations of analytical data. The mesh moves ownership back to domains." />

<Levels label="Chapter 14, Managing Analytical Data">

<Level name="Beginner">

Operational data serves the system; analytical data serves decisions. A data
warehouse copies data from operational systems into one central, carefully
modelled schema (ETL), which is consistent but slow to change and centrally owned.
A data lake stores raw data centrally and transforms it later, which is flexible
but often becomes hard to find and trust.

```sql
-- warehouse-style fact table
CREATE TABLE fact_ticket (ticket_id uuid, opened_at timestamptz, closed_at timestamptz, expert_id uuid, customer_region text);
```

Common mistake: analytics queries on operational databases. Fix: separate
analytical stores.

</Level>

<Level name="Intermediate">

The data mesh is a decentralised approach: domains own their analytical data and
publish it as data products. Its principles: domain ownership, data as a product,
a self-serve data platform, and federated governance. A data product quantum (DPQ)
is an analytical data product deployed alongside a domain service, with its own
interfaces.

```ts
// a data product quantum interface for the ticketing domain (sketch)
export const ticketDataProduct = {
  name: 'ticketing.closed_tickets_daily',
  schema: { date: 'date', region: 'text', closed: 'int', median_hours: 'float' },
  freshness: 'daily by 02:00',
  owner: 'ticketing team',
};
```

Common mistake: a data product with no owner. Fix: the domain team owns it like
any service.

</Level>

<Level name="Advanced">

A DPQ is coupled to its domain service (it reads the service's data, usually
asynchronously) but is its own quantum for consumers. Consumers combine DPQs from
several domains. Data mesh suits organisations with many domains and teams, and
fits well with microservices; it is overkill for a small system with one team.

Common mistake: data mesh for a small team. Fix: a simple warehouse or read
replica until the domain count demands more.

</Level>

<Level name="Edge cases">

One boundary each. A domain with no analytical consumers: no DPQ needed. A
cross-domain metric (revenue per ticket): needs an aggregate data product. A
schema change in the domain service: the DPQ must absorb it without breaking
consumers.

Common mistake: exposing operational schema as the data product. Fix: a stable,
documented product schema.

</Level>

<Level name="Corner cases">

Two boundaries meet. Federated governance plus inconsistent definitions ("active
customer" differs by domain): agree on shared definitions. Data products plus
privacy: domain teams must apply the same privacy rules.

Common mistake: each domain defining shared terms its own way. Fix: federated
governance with a glossary.

</Level>

<Level name="Production level">

In production data products have SLAs (freshness, completeness), schema versions,
lineage and access control, monitored like services.

```yaml
data_product: ticketing.closed_tickets_daily
sla: { freshness: "02:00 IST", completeness: ">= 99.5%" }
monitors: [late_partition, row_count_drop_20pct]
```

Common mistake: analytical data with no monitoring. Fix: SLAs and alerts.

</Level>

<Level name="Mindset">

Analytical data is a product. The habit is to give it owners, interfaces and
quality targets.

Common mistake: analytics as someone else's problem. Fix: domains own their data
products.

</Level>

<Level name="System design">

<Compare left="Warehouse or lake" right="Data mesh" rows={[
  ['central team owns', 'domain teams own'],
  ['central schema or raw storage', 'data products per domain'],
  ['simple for few domains', 'scales with many domains'],
]} caption="Choosing an analytical approach by organisation size and domain count." />

Common mistake: choosing by trend. Fix: by domain count and team structure.

</Level>

<Level name="Strategy">

I define one data product for my capstone (daily notes created and searched) with
schema, freshness and owner, and build it as a nightly job. Done when it runs,
meets its freshness target and has one monitor.

</Level>

</Levels>

### 15. Build Your Own Trade-Off Analysis

**Covers:** Finding entangled dimensions (coupling, analysing coupling points, assessing trade-offs), trade-off techniques (qualitative versus quantitative analysis, MECE lists, the out-of-context trap, modelling relevant domain cases, preferring bottom line over overwhelming evidence, avoiding snake oil and evangelism), and the Sysops Squad saga epilogue.

<Flow steps={['find what is entangled', 'analyse coupling points', 'list options (MECE)', 'model real domain scenarios', 'compare qualitatively', 'state the bottom line']} caption="The book's method for trade-off analysis, usable on problems it never covers." />

<Levels label="Chapter 15, Build Your Own Trade-Off Analysis">

<Level name="Beginner">

The book ends by teaching its method. First, find the entangled dimensions: what
is coupled to what, and where the coupling points are. Second, analyse each
coupling point's options. Third, assess the trade-offs and pick the least worst.

```md
Question: should notifications be a separate service?
Coupling points: shared customer data (static), sync call from tickets (dynamic)
Options: in-process module | separate service with sync API | separate service via events
```

Common mistake: comparing options before finding coupling points. Fix: coupling
first.

</Level>

<Level name="Intermediate">

Techniques. Qualitative analysis is usually more realistic than quantitative,
because architecture rarely has exact numbers; compare options relative to each
other. MECE lists (mutually exclusive, collectively exhaustive) make sure options
do not overlap and none is missing. The out-of-context trap: a trade-off table
with generic criteria misleads; weight criteria by this context.

```md
              in-process   sync service   event service
coupling      high         medium         low
consistency   immediate    immediate      eventual
complexity    low          medium         high
fits context? yes (one team, low volume)
```

Common mistake: a generic pros and cons list. Fix: criteria weighted by the
actual context.

</Level>

<Level name="Advanced">

Model relevant domain cases: walk through real scenarios (a ticket created during
a notification outage) for each option instead of reasoning abstractly. Prefer
the bottom line over overwhelming evidence: stakeholders need a clear
recommendation with its main trade-off, not fifty pages. Avoid snake oil and
evangelism: be wary of anyone (including myself) who presents an option with no
downsides.

```md
Scenario: notification service down for 10 minutes
in-process: tickets fail if notification throws -> need try/catch
sync service: ticket creation fails or waits -> needs fallback
event service: tickets succeed; notifications delayed -> acceptable
Bottom line: events, because ticket creation must not depend on notifications.
```

Common mistake: overwhelming stakeholders with analysis. Fix: one-line bottom
line, the details attached.

</Level>

<Level name="Edge cases">

One boundary each. Options that overlap (not MECE): the comparison double-counts.
A scenario nobody has seen: model it anyway if it is plausible. A trade-off where
all options are bad: pick the least worst and record why.

Common mistake: missing the "do nothing" option. Fix: always include it.

</Level>

<Level name="Corner cases">

Two boundaries meet. Qualitative analysis plus a quantitative stakeholder: give
the few numbers that exist and be clear what is judgement. Evangelism plus my own
favourite technology: my own bias is the hardest to spot.

Common mistake: trusting my own enthusiasm. Fix: ask someone to argue the other
side.

</Level>

<Level name="Production level">

In production the method is how ADRs are written: coupling points, MECE options,
scenarios, a qualitative table, the bottom line, and the decision.

```md
ADR template (hard parts style)
Coupling points / Options (MECE, incl. do nothing) / Scenarios / Trade-off table / Bottom line / Decision / Fitness function
```

Common mistake: ADRs that skip scenarios. Fix: at least two real scenarios per
option.

</Level>

<Level name="Mindset">

The method outlasts the examples. The habit is to apply this loop to any hard
decision, in any technology.

Common mistake: remembering the book's answers. Fix: remember its method.

</Level>

<Level name="System design">

<Layers layers={[
  { name: 'Bottom line', note: 'one sentence: what and the main trade-off' },
  { name: 'Trade-off table', note: 'qualitative, weighted by context' },
  { name: 'Scenarios', note: 'real domain cases walked through each option' },
  { name: 'Options and coupling points', note: 'MECE, including do nothing' },
]} caption="A trade-off analysis as layers. Stakeholders read the top; reviewers check the rest." />

Common mistake: presenting the bottom layer first. Fix: lead with the bottom line.

</Level>

<Level name="Strategy">

I take one open question in my capstone and write a full trade-off analysis with
the template above, then present the bottom line to a peer in one minute. Done
when the ADR is in the repo and the peer can name the main trade-off.

</Level>

</Levels>

## Misreadings to avoid

- **"There is a right way to split a monolith."** The book's point is that each
  split is a trade-off analysis in context.
- **"Microservices fix data problems."** Splitting services makes data the
  hardest part: ownership, transactions and access.
- **"Sagas give distributed transactions."** They give coordination with
  compensation; intermediate states are visible.
- **"Choreography is always better."** It wins on scale and decoupling, and loses
  on state and error handling.
- **"The Sysops Squad's answers are the lesson."** The method is the lesson; the
  answers belong to their context.
