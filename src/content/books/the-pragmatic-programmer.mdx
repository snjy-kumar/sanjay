## Why this book

This is the primary book for Phase 0 of the <a href={withBase('/plans/traditional-software-developer/')}>traditional core</a>,
and it comes back in Phase 11, when the subject is judgment. It does not teach
computer science. It teaches the habits that make the next fourteen months
stick: plain text, version control, a debugger, a daybook, failing loudly, and
taking responsibility for what I ship. The
<a href={withBase('/plans/traditional-software-developer/#strategy-0')}>Phase 0 strategy</a>
leans on it directly.

The other plans cite it too, which is a good sign: it is the one book that is
about the developer rather than about a technology.

## How I would learn it

Not cover to cover. In Phase 0 I read chapters 1, 3 and 4, because they are
about the setup and the study system: ownership, the tools, and failing loudly.
The rest I read one topic a week, alongside whatever phase I am in, and only
when that phase gives me a place to apply it.

- **One topic, one change.** After each topic I make one concrete change to my
  study repository and write the commit message as the lesson. Adding a `make
  check` target that runs the tests, the warnings and the sanitizers is the
  starter-kit topic applied.
- **Do the exercises in writing.** Most topics end with short exercises; I
  answer them in the daybook before reading the possible answers at the back.
- **Keep a disagreement list.** Some advice depends on context. When I
  disagree, I write down why and what evidence would change my mind. That is
  the pragmatism the book is named for.
- **Re-read in Phase 11.** The second read is where it pays off.

I know I am done with the first pass when the Phase 0 gate is met using the
habits from chapters 1, 3 and 4, without a tutorial open.

## What I learn from it

Every chapter has its own page, linked in the contents below. One line per
chapter of what I take from it:

- **Chapter 1, A Pragmatic Philosophy (topics 1–7):** own my career and my results, offer options instead of excuses, fix or board up broken windows, start change small, watch for slow decline against a fixed baseline, agree the quality bar with users, run a knowledge portfolio, and plan communication for its audience.
- **Chapter 2, A Pragmatic Approach (topics 8–15):** judge design by how easy it is to change, keep each piece of knowledge in one place, keep components independent, keep decisions reversible, build tracer bullets end to end, prototype to answer one question, write in the domain's language, and estimate with units and a model.
- **Chapter 3, The Basic Tools (topics 16–22):** keep knowledge in plain text, use the shell fluently, know my editor, put everything in version control, debug by method, script text transformations, and keep an engineering daybook.
- **Chapter 4, Pragmatic Paranoia (topics 23–27):** state preconditions, postconditions and invariants, crash early instead of limping on, assert what cannot happen, release every resource I acquire, and take small steps so feedback arrives in time.
- **Chapter 5, Bend, or Break (topics 28–32):** reduce coupling, handle events with state machines, observers, pub/sub and streams, think in transformations, prefer interfaces, delegation and mixins to inheritance, and move configuration out of code.
- **Chapter 6, Concurrency (topics 33–36):** find work that does not need to be ordered, treat shared mutable state as the source of concurrency bugs, isolate state in actors and processes, and coordinate through blackboards.
- **Chapter 7, While You Are Coding (topics 37–44):** listen to unease, program deliberately rather than by coincidence, estimate algorithm speed, refactor continuously, use tests to design code, test properties with generated input, think like an attacker, and name things well.
- **Chapter 8, Before the Project (topics 45–48):** discover requirements through feedback, separate policy from requirement, find the real constraints of a hard puzzle, work together with pairs and mobs, and apply agility as a loop rather than a process.
- **Chapter 9, Pragmatic Projects (topics 49–53):** build teams that own quality, avoid copying practices without their context, set up version control, regression tests and full automation, delight users by meeting their real expectations, and sign my work.

## Misreadings to avoid

- **"DRY means no repeated lines."** It means no repeated knowledge. Repeated
  lines with different reasons to change should stay repeated.
- **"Good-enough means low quality."** It means the quality bar is chosen with
  the user, explicitly.
- **"Crash early means crash the server."** It means stop the failing unit of
  work before it corrupts state.
- **"Tracer bullets and prototypes are the same."** One is kept, one is thrown
  away.
- **"The book is a rulebook."** It is a set of heuristics with reasons. When the
  reason does not apply, neither does the rule.
