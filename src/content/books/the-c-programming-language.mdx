## Why this book

The <a href={withBase('/plans/traditional-software-developer/')}>traditional core</a> names this as the
alternative C book for phase 1, programming from first principles. It is short, dense and old, and it
was written by the people who made the language. I read
<a href={withBase('/books/c-programming-a-modern-approach/')}>King's book</a> for the exercises and the
gentle path, and I keep this one next to it as the compact statement of how C thinks.

It is also a model of technical writing. Every chapter is a few pages of explanation and then a real
program that uses it: a word counter, a sort, a hash table lookup, a memory allocator. That is the
shape of the phase 1 gate too: a small tool, every line explained. The
<a href={withBase('/plans/traditional-software-developer/#strategy-1')}>phase 1 strategy</a> leans on it
as the second read of each idea.

The book describes ANSI C (C89). The C I compile today is C99 or C11 or later, so I note where a
later standard changed something, and I never take its code as a security example: it predates most
of what we now know about buffer overflows.

## How I would learn it

I read it after the matching King chapter, not before. King explains; Kernighan and Ritchie compress.
Reading the compressed version after the explanation is a test: if a paragraph here surprises me, I
did not really understand the King chapter.

Each chapter, I type every program, compile it with `-std=c99 -Wall -Wextra -pedantic
-fsanitize=address,undefined`, and fix whatever the modern compiler complains about. Then I do two or
three exercises, the ones that change the program rather than the ones that repeat it. Where a
program reads input, I feed it an empty file, a file with no final newline, and a very long line,
because those are the phase 1 gate's cases.

## The chapters

### 1. A Tutorial Introduction

**Covers:** A fast tour of the whole language through small programs: printing, variables and
arithmetic, loops, symbolic constants, character input and output, arrays, functions, arguments by
value, character arrays, and external variables.

<Levels label="Chapter 1, A Tutorial Introduction">

<Level name="Beginner">

The smallest C program is a `main` that calls `printf` and returns. The chapter moves straight on to
programs that do something: convert a temperature table, copy input to output, count characters,
words and lines. The point is to see the whole language once before learning any part properly.

```c
#include <stdio.h>

int main(void) {
    int c;
    while ((c = getchar()) != EOF)
        putchar(c);
    return 0;
}
```

</Level>

<Level name="Intermediate">

The pieces combine into a state machine. A word counter is a loop over characters with one bit of
state: am I inside a word or not. That pattern, a loop plus a little state, is half of all text
processing, and it is exactly what the phase 1 tool needs.

```c
#include <stdio.h>
#include <ctype.h>

int main(void) {
    long lines = 0, words = 0, chars = 0;
    int c, in_word = 0;
    while ((c = getchar()) != EOF) {
        chars++;
        if (c == '\n') lines++;
        if (isspace(c)) in_word = 0;
        else if (!in_word) { in_word = 1; words++; }
    }
    printf("%ld %ld %ld\n", lines, words, chars);
    return 0;
}
```

</Level>

<Level name="Advanced">

Why is `c` an `int` and not a `char`? `getchar` returns every possible byte value plus one more,
`EOF`, which is negative. A `char` cannot hold all of those, so storing the result in a `char`
either never sees `EOF` (if `char` is unsigned) or mistakes a real byte for it (if it is signed).
Arguments are passed by value: a function gets a copy, so changing a parameter changes nothing in
the caller. Arrays are the exception that is not really an exception: what gets copied is a pointer
to the first element.

</Level>

<Level name="Edge cases">

An empty input: the loop body never runs and every count is zero, which is correct. Input with no
final newline: the line count is one less than a person would say. A file that is one enormous
word: the counter still works, because it never stores the word. The book's line-reading function
has a fixed-size buffer; a line longer than it is silently split.

</Level>

<Level name="Corner cases">

The byte `0xFF` in a file read into a signed `char` becomes `-1`, which on most machines equals
`EOF`: an empty-looking file meets a real byte, and the program stops early. And `isspace` given a
negative `char` value that is not `EOF` is undefined behaviour, so a non-ASCII byte plus a signed
`char` plus a `ctype` call is a crash waiting for the right input. Cast to `unsigned char` first.

</Level>

<Level name="Production level">

Real tools are run in pipelines. That means a nonzero exit code on failure, errors on `stderr` not
`stdout`, and checking that the final write actually succeeded: `printf` into a closed pipe or a full
disk fails, and a tool that ignores it reports success with missing output. The book's early programs
skip this to stay short; mine do not.

</Level>

<Level name="Mindset">

See the whole thing once, badly, then go back. The tutorial is deliberately incomplete. Learning a
system by building the smallest end-to-end version first is the same move as a tracer bullet.

</Level>

<Level name="System design">

`getchar` and `putchar` make every program a filter: bytes in, bytes out, composable with any other
filter through a pipe. The Unix pipeline is a system design built from that one interface, and
streaming over input instead of loading it is what lets the tool handle the large-file test.

</Level>

<Level name="Strategy">

Type the chapter's programs, then rewrite the word counter in TypeScript reading from `stdin` and
compare the two outputs on the same files. Done when both versions agree on an empty file, a file
without a final newline, a binary file and a 1 GB file, and I can explain any difference.

</Level>

</Levels>

### 2. Types, Operators, and Expressions

**Covers:** Names, the basic data types and their sizes, constants, declarations, arithmetic,
relational and logical operators, type conversions, increment and decrement, bitwise operators,
assignment operators, the conditional expression, and precedence and order of evaluation.

<Levels label="Chapter 2, Types, Operators, and Expressions">

<Level name="Beginner">

C has a handful of basic types: `char`, `int`, `float`, `double`, with `short`, `long`, `signed` and
`unsigned` as qualifiers. Their sizes are not fixed by the language, only their minimum ranges. A
constant has a type too: `10` is an `int`, `10L` a `long`, `10.0` a `double`, `'a'` an `int`.

</Level>

<Level name="Intermediate">

Expressions mix types, and C converts them by rules rather than by intent. Bitwise operators turn an
`unsigned` into a small set: masks, flags, packing. A real program uses them for permission bits, for
a bitset of seen characters, or to test whether a number is a power of two.

```c
/* is x a power of two? true for 1, 2, 4, ...; false for 0 */
int is_pow2(unsigned x) { return x != 0 && (x & (x - 1)) == 0; }
```

</Level>

<Level name="Advanced">

The usual arithmetic conversions decide the type of `a + b`: small integers are promoted to `int`,
then the operands are brought to a common type. When a signed and an unsigned operand of the same
rank meet, the signed one is converted to unsigned. Precedence decides grouping, not order: in
`f() + g()` the language does not say which call runs first, and `i = i++ + 1` modifies `i` twice
without a sequence point, which is undefined.

</Level>

<Level name="Edge cases">

`INT_MAX + 1` is undefined behaviour for signed types and wraps for unsigned ones. Shifting by the
width of the type or more is undefined. Integer division truncates toward zero since C99; in C89 the
direction for negative operands was implementation-defined. `char` may be signed or unsigned.

</Level>

<Level name="Corner cases">

`-1 < 0u` is false: the `-1` becomes the largest `unsigned`. Put that inside a loop bound and an
empty array plus an unsigned length gives a loop that runs four billion times.

```c
size_t n = 0;
for (int i = 0; i < n - 1; i++) { /* n - 1 is SIZE_MAX: runs "forever" */ }
```

</Level>

<Level name="Production level">

Compile with `-Wall -Wextra -Wconversion -Wsign-compare` and treat the warnings as errors. Use
`<stdint.h>` types where the width matters, `size_t` for sizes and indexes, and check arithmetic
that comes from input before doing it, not after it overflowed.

</Level>

<Level name="Mindset">

Types in C describe storage, not intent. JavaScript has one `number`; TypeScript adds intent at
compile time and erases it. C keeps the storage at run time and lets me get the intent wrong.

</Level>

<Level name="System design">

Integer widths and signedness are part of every file format and network protocol. A length field
read as signed, then compared and used as a size, is the shape of many real vulnerabilities.

</Level>

<Level name="Strategy">

Write a table of twenty small expressions mixing `char`, `int`, `unsigned` and `long`, predict each
result and type, then check with a program that prints them. Done when I predict all twenty and can
name the rule behind each one.

</Level>

</Levels>

### 3. Control Flow

**Covers:** Statements and blocks, `if`-`else`, `else`-`if` chains, `switch`, `while` and `for`
loops, `do`-`while`, `break` and `continue`, and `goto` with labels.

<Levels label="Chapter 3, Control Flow">

<Level name="Beginner">

A statement ends with a semicolon; braces group statements into a block. `if`, `while`, `for` and
`switch` work much as they do in JavaScript, because JavaScript took them from C.

</Level>

<Level name="Intermediate">

Binary search is the chapter's kind of program: a loop with two indexes that close in on an answer.
Writing it correctly means stating the loop invariant: the target, if present, is always between
`low` and `high`.

```c
int bsearch_int(int x, const int v[], int n) {
    int low = 0, high = n - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (x < v[mid]) high = mid - 1;
        else if (x > v[mid]) low = mid + 1;
        else return mid;
    }
    return -1;
}
```

</Level>

<Level name="Advanced">

`switch` jumps to a matching `case` label and then falls through every later case until a `break`.
That is a computed jump, not a chain of `if`s, and compilers can turn a dense switch into a jump
table. `goto` is legal and occasionally right: jumping forward to one cleanup block at the end of a
function that acquired several resources.

</Level>

<Level name="Edge cases">

An empty array (`n == 0`): `high` starts at `-1`, the loop never runs, and the search correctly
fails. A one-element array exercises the `mid` arithmetic once. The dangling `else` binds to the
nearest `if`, whatever the indentation says.

</Level>

<Level name="Corner cases">

`(low + high) / 2` overflows when both are near `INT_MAX`, a bug that sat in widely used library
code for years; `low + (high - low) / 2` does not. Large array plus signed index arithmetic is a
corner most tests never reach.

</Level>

<Level name="Production level">

Fall-through is the classic control-flow bug; compilers warn with `-Wimplicit-fallthrough`. A loop
that reads input needs a bound or a timeout. One cleanup path per function makes leaks visible in
review.

</Level>

<Level name="Mindset">

A loop is correct because of its invariant, not because it passed three tests. State it in a
comment and check it at the boundaries.

</Level>

<Level name="System design">

Control flow is where an error path lives. Every early return in C is a place a resource may leak;
the single-exit cleanup pattern is the manual version of `finally`, `defer` and destructors.

</Level>

<Level name="Strategy">

Write binary search from a blank file, then test it against a linear search on random arrays,
including empty and one-element ones. Done when it passes ten thousand random cases and I can state
its invariant.

</Level>

</Levels>

### 4. Functions and Program Structure

**Covers:** The basics of functions, functions returning non-integers, external variables, scope
rules, header files, static variables, register variables, block structure, initialization,
recursion, and the C preprocessor.

<Levels label="Chapter 4, Functions and Program Structure">

<Level name="Beginner">

A function has a declared return type and parameter types. A prototype declares it before use so
the compiler can check calls. Larger programs split into several `.c` files, each compiled on its
own, with shared declarations in a header.

</Level>

<Level name="Intermediate">

The chapter's calculator is a real program structure: a main loop, a stack in one file, a tokenizer
in another, and `static` to keep each file's internals private. That is modules, before modules.

```c
/* stack.h */
void push(double);
double pop(void);

/* stack.c */
#include "stack.h"
#define MAXVAL 100
static int sp = 0;          /* private to this file */
static double val[MAXVAL];
void push(double f) { if (sp < MAXVAL) val[sp++] = f; }
double pop(void) { return sp > 0 ? val[--sp] : 0.0; }
```

</Level>

<Level name="Advanced">

Scope (where a name is visible) and storage duration (how long the object lives) are different
things. A `static` local has block scope and static duration: it keeps its value across calls.
`extern` declares without defining. The preprocessor runs first and only on text: `#include` pastes
a file, `#define` substitutes tokens.

</Level>

<Level name="Edge cases">

A function called without a prototype in C89 is assumed to return `int`, so a function returning
`double` called that way returns garbage; C99 removed implicit declarations. Recursion with no
base case exhausts the stack.

</Level>

<Level name="Corner cases">

A macro argument with a side effect, used twice: `#define SQUARE(x) ((x) * (x))` with `SQUARE(i++)`
increments twice and is undefined. Macro plus side effect is two hazards meeting. Use an `inline`
function instead.

</Level>

<Level name="Production level">

Headers need include guards. Every global is shared state that tests cannot isolate; keep them
`static` and few. Deep recursion on user-controlled input is a denial of service; make it iterative
or bound the depth.

</Level>

<Level name="Mindset">

A file is a module and `static` is `private`. The interface is the header; everything else is an
implementation I am free to change.

</Level>

<Level name="System design">

Separate compilation and linking are why large C programs build incrementally and why a header
change rebuilds everything. Every later module system made a different trade on the same problem.

</Level>

<Level name="Strategy">

Split the phase 1 tool into three files with headers and a makefile. Done when changing one `.c`
file rebuilds only that file and nothing outside a header is visible to the other files.

</Level>

</Levels>

### 5. Pointers and Arrays

**Covers:** Pointers and addresses, pointers as function arguments, the relationship between pointers
and arrays, address arithmetic, character pointers and functions, pointer arrays, multi-dimensional
arrays, command-line arguments, pointers to functions, and complicated declarations.

<Figure art={`
  int a[4] = {10, 20, 30, 40};   int *p = &a[1];

  address  1000   1004   1008   1012
          +------+------+------+------+
     a    |  10  |  20  |  30  |  40  |
          +------+------+------+------+
                    ^             ^
                    p             p + 2   (moves 2 * sizeof(int) bytes)
`} caption="Pointer arithmetic counts elements, not bytes: p + 2 skips two ints." />

<Levels label="Chapter 5, Pointers and Arrays">

<Level name="Beginner">

A pointer holds an address. `&x` takes the address of `x`; `*p` follows a pointer. Passing `&x` to a
function is how C lets the function change the caller's variable.

```c
void swap(int *a, int *b) { int t = *a; *a = *b; *b = t; }
```

</Level>

<Level name="Intermediate">

`a[i]` is defined as `*(a + i)`. An array name in most expressions becomes a pointer to its first
element, which is why functions receive arrays as pointers and need a separate length. Command-line
arguments arrive as `argv`, an array of pointers to strings.

</Level>

<Level name="Advanced">

Arithmetic on a pointer is only defined within one array, plus one past its end. Function pointers
let a sort take a comparison, which is how `qsort` is generic. Declarations read from the name
outward: `int *(*f)(char *)` is a pointer to a function taking `char *` and returning `int *`.

</Level>

<Level name="Edge cases">

`sizeof a` inside the function that declared the array gives the array size; `sizeof a` on a
parameter gives a pointer size. A null pointer must never be followed. The one-past-the-end pointer
may be compared but never read.

</Level>

<Level name="Corner cases">

A pointer to a local variable, returned from the function: the address is valid inside and dangling
the moment the function returns. The code often still prints the right value in a test, because the
stack has not been reused yet, and fails later. Lifetime plus aliasing is the corner.

```c
int *bad(void) { int x = 42; return &x; }   /* dangling: never do this */
```

</Level>

<Level name="Production level">

String functions in this chapter copy without bounds; real code passes and checks sizes, uses
`snprintf`, and runs under AddressSanitizer in tests. Every pointer parameter's contract says
whether it may be null and who owns what it points to.

</Level>

<Level name="Mindset">

Draw the boxes. A pointer bug is almost always visible on paper before it is visible in a debugger.

</Level>

<Level name="System design">

Ownership, who frees what and when, is a design decision that a C API must document and that Rust
makes the compiler check. JavaScript's garbage collector removes the question; the cost is that I
stop seeing it.

</Level>

<Level name="Strategy">

Implement `strlen`, `strcpy`, `strcmp` and a `qsort` comparator with pointers only, then test them
under ASan. Done when I can draw memory for each call and ASan reports nothing on hostile inputs.

</Level>

</Levels>

### 6. Structures

**Covers:** Basics of structures, structures and functions, arrays of structures, pointers to
structures, self-referential structures, table lookup, `typedef`, unions, and bit-fields.

<Levels label="Chapter 6, Structures">

<Level name="Beginner">

A `struct` groups named fields into one value. `p.x` reads a field; `pp->x` reads it through a
pointer. Structures can be copied, passed and returned by value.

</Level>

<Level name="Intermediate">

The chapter builds a binary tree of words and a hash table for name lookup: self-referential
structs that point to more of themselves. That is the first real data structure, and the phase 1
word-frequency counter is the same program.

```c
struct node {
    char *word;
    int count;
    struct node *next;   /* chain in one hash bucket */
};
```

</Level>

<Level name="Advanced">

The compiler may put padding between fields to align them, so `sizeof` a struct can be larger than
the sum of its fields, and field order changes the size. A union overlays its members in one piece
of storage. Bit-fields pack small integers but their layout is implementation-defined.

</Level>

<Level name="Edge cases">

An empty table: every lookup misses and nothing crashes. A key not found must return a clear "not
found", not a garbage node. Copying a struct that holds a pointer copies the pointer, not what it
points to.

</Level>

<Level name="Corner cases">

A shallow copy plus two `free` calls: two structs share one string, each frees it, and the second
free is a double free. Copy semantics plus ownership is the corner that bites in every language with
references.

</Level>

<Level name="Production level">

A hash table fed adversarial keys degrades to a list; real ones resize and use a seeded hash. Writing
a struct straight to a file bakes in padding and byte order; serialise field by field.

</Level>

<Level name="Mindset">

Data first. Once the structure is right, the functions that walk it are short.

</Level>

<Level name="System design">

Structs are the in-memory side of every record format, row and message. The decision between
pointers to shared data and embedded copies shows up again in databases and in distributed systems.

</Level>

<Level name="Strategy">

Build the word-frequency counter with a chained hash table that grows. Done when it counts a 100 MB
file correctly, frees every node, and Valgrind reports zero leaks.

</Level>

</Levels>

### 7. Input and Output

**Covers:** Standard input and output, formatted output with `printf`, variable-length argument
lists, formatted input with `scanf`, file access, error handling with `stderr` and `exit`, line input
and output, and miscellaneous library functions.

<Levels label="Chapter 7, Input and Output">

<Level name="Beginner">

`printf` formats to standard output; `fopen`, `fgets` and `fclose` work with files; `fprintf(stderr,
...)` reports errors. A program ends with `exit(0)` for success and a nonzero status for failure.

</Level>

<Level name="Intermediate">

The chapter's `cat` is the template for every file tool: open each file named on the command line,
copy it, report and skip the ones that fail, and exit nonzero if any failed.

```c
FILE *fp = fopen(path, "r");
if (fp == NULL) {
    fprintf(stderr, "%s: %s: %s\n", prog, path, strerror(errno));
    status = 1;
}
```

</Level>

<Level name="Advanced">

A `FILE` is buffered: writes collect in memory until a newline, a full buffer, `fflush` or `fclose`.
Variadic functions like `printf` read their arguments by trusting the format string; a mismatched
type is undefined. `scanf` returns how many items it matched, which is the only way to know it
worked.

</Level>

<Level name="Edge cases">

A file that ends without a newline: `fgets` still returns the last line. A line longer than the
buffer: `fgets` returns a partial line with no newline, and the rest comes on the next call. A
missing file: `fopen` returns null and sets `errno`.

</Level>

<Level name="Corner cases">

Output to a full disk: `printf` succeeds into the buffer, and the failure only appears at `fclose`.
A program that ignores the result of `fclose` exits 0 having lost data. Buffering plus an error
that arrives late is the corner.

</Level>

<Level name="Production level">

Never pass user input as a format string. Check every I/O return value, including `fclose`. Prefer
`fgets` plus parsing over `scanf`, which leaves bad input in the stream.

</Level>

<Level name="Mindset">

A tool is judged by how it fails. The error message names the program, the file and the reason.

</Level>

<Level name="System design">

Standard input, output, error and the exit status are the whole interface a command-line program
offers to a shell, a script or CI. Getting them right is what makes a tool composable.

</Level>

<Level name="Strategy">

Give the phase 1 tool this chapter's error handling and test each failure: missing file, unreadable
file, long line, full output. Done when every failure prints one clear line to `stderr` and returns
a distinct nonzero exit code.

</Level>

</Levels>

### 8. The UNIX System Interface

**Covers:** File descriptors, low-level I/O with `read` and `write`, `open`, `creat`, `close` and
`unlink`, random access with `lseek`, an implementation of `fopen` and `getc`, listing directories,
and a storage allocator.

<Flow
  steps={['fopen / fgets (library, buffered)', 'read / write (system call)', 'kernel file table', 'file system', 'disk']}
  caption="The standard library sits on top of system calls; this chapter opens the lower layer."
/>

<Levels label="Chapter 8, The UNIX System Interface">

<Level name="Beginner">

Underneath `FILE *` is a small integer, a file descriptor. `0`, `1` and `2` are standard input,
output and error. `read` and `write` move bytes between a descriptor and a buffer.

</Level>

<Level name="Intermediate">

The chapter rebuilds `fopen` and `getc` on top of `read`, showing what buffering is: one large
`read`, then many cheap calls served from memory. It ends with a `malloc` built from a free list.

</Level>

<Level name="Advanced">

Every `read` is a system call: a switch into the kernel, which is far more expensive than a function
call, which is why the buffered library exists. The allocator keeps free blocks in a circular list
with a header holding each block's size, and coalesces neighbours when they are freed.

</Level>

<Level name="Edge cases">

`read` returns 0 at end of file and may return fewer bytes than asked even before the end. `write`
may write fewer bytes than asked. `malloc(0)` may return null or a unique pointer.

</Level>

<Level name="Corner cases">

A short read plus a signal: `read` interrupted by a signal returns `-1` with `errno` set to `EINTR`,
and a loop that treats that as a real error fails at random. Partial transfers plus interrupts is
why robust I/O loops exist.

</Level>

<Level name="Production level">

Real allocators handle threads, alignment, fragmentation and hostile frees. The book's version is
for understanding. Descriptors leak just like memory; a server that does not close them stops
accepting connections.

</Level>

<Level name="Mindset">

Every abstraction is a layer I can open. When something is slow or strange, go one layer down.

</Level>

<Level name="System design">

The buffered library over unbuffered system calls is the same trade as a cache over a database:
fewer expensive operations, at the cost of data that has not reached its destination yet.

</Level>

<Level name="Strategy">

In phase 6, write a `cat` with `read` and `write` only, measure it against the buffered version with
different buffer sizes, then trace both with `strace`. Done when I can explain the timing difference
from the system call counts.

</Level>

</Levels>

Appendix A is the reference manual: the grammar and exact rules of the language, which I use to
settle arguments about what is defined. Appendix B summarises the standard library, header by header.
Appendix C lists what changed from the first edition. I keep A and B open while writing C, the way I
keep MDN open for JavaScript, and I check anything important against the current standard, because
the language has moved since 1988.

## Misreadings to avoid

- "Short means simple." The book is short because it is dense; every paragraph carries a rule.
- "The code is a security model." It is a teaching model from 1988; its string handling is unsafe by
  today's standards.
- "ANSI C is current C." C99, C11 and later added `//` comments, `stdint.h`, `bool`, designated
  initialisers and much more.
- "Undefined behaviour means a crash." It means the language makes no promise at all, including that
  the program looks fine today.
- "K&R or King." They do different jobs: one explains, one compresses. Use both.
