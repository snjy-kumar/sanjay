#### Across every phase: the project ladder

**Covers:** the eight projects, one per phase from 0 to 7, each with a scope and acceptance criteria, each
the evidence the next one stands on.

<Levels label="Across every phase, the project ladder">

<Level name="Beginner">

The projects are the curriculum and the notes are the by-product. Each phase has exactly one project with
an acceptance line I can check: a public URL with Lighthouse at 95 or more and no console errors; a vanilla
app that adds, deletes, filters, searches and persists with no framework; a React app with a keyboard pass
and five tested components; a full-stack app where two users cannot read each other's data; a hardened app
where a red build blocks a bad change; a RAG feature with a 30-question eval; a maintainer agent with ten
runs and zero unapproved writes; a product with ten users and three iterations.

```md
## Ladder status (README of my portfolio repo)
| # | Project        | Live | Repo | Acceptance                         | Met |
| 1 | Static page    | url  | url  | Lighthouse 95+, no console errors  | yes |
| 2 | Vanilla app    | url  | url  | add/delete/filter/search/persist   | yes |
| 3 | React app      | url  | url  | keyboard pass, 5 component tests   | ... |
```

Common mistake: starting project 6 because RAG is exciting while project 4's isolation test does not exist.
Fix: the plan's rule, do not skip a rung.

</Level>

<Level name="Intermediate">

The rungs are not separate apps that get thrown away. Projects 4 to 8 can be the same codebase growing: the
full-stack app from phase 3 is hardened in phase 4, gets the RAG feature in phase 5, the agent maintains its
repository in phase 6, and it becomes the product in phase 7. That is how real systems grow, and it means
every later rung inherits the tests and CI of the earlier ones.

Each project is deployed and linked from the portfolio, and each acceptance line becomes a test or a
check where it can: Lighthouse in CI for rung 1, an isolation test for rung 4, the eval in CI for rung 6.

</Level>

<Level name="Advanced">

Acceptance criteria are written before building, not after. Writing them after lets the criteria drift to
match whatever got built. I copy the plan's line into the project's README on day one, then add my own
measurable details (which five components, which journey the end-to-end test covers).

```ts
// rung 4's acceptance, as a test
test('user B cannot read user A\u2019s record', async () => {
  const a = await signUp('a@example.test'); const b = await signUp('b@example.test');
  const rec = await createRecord(a, { title: 'private' });
  const res = await getRecord(b, rec.id);
  expect(res.status).toBe(404);   // not 403: do not even confirm it exists
});
```

</Level>

<Level name="Edge cases">

- A project that meets acceptance but nobody can run from the README: not met. Running from the README on a
  clean machine is an implicit criterion of every rung.
- A rung redone after a gap of months: re-run its acceptance; things rot (expired keys, dead free tiers).

</Level>

<Level name="Corner cases">

- Projects 4 to 8 in one codebase, and a later change breaks an earlier rung's acceptance (the RAG feature
  slows the page below the Lighthouse score). The earlier acceptance checks stay in CI, so the ladder
  defends itself.

</Level>

<Level name="Production level">

Every rung is deployed, monitored at least with an uptime check, and has a README with how to run, how to
test and what it proves. Free tiers sleep or expire, so I check the links monthly.

</Level>

<Level name="Mindset">

The ladder is the point: each rung is the evidence for the next. Evidence beats intention.

</Level>

<Level name="System design">

</Level>

<Level name="Strategy">

Keep the ladder status table in the portfolio README and update it at each gate. Done when all eight rows

#### Across every phase: the weekly operating system

**Covers:** how ten to fifteen hours a week are split between learning, building, writing and review, and
the note loop that turns work into notes.

<Compare
  left="Block"
  right="What happens (hours)"
  caption="The plan's week, as a routine I can put in a calendar"
  rows={[
    ['Learn', '4 to 5: one concept, one chapter, one exercise'],
    ['Build', '5 to 6: the current project, one shippable slice'],
    ['Write', '2: the log entry and the note'],
    ['Review', '1: the week, the diff, the next single outcome'],
  ]}
/>

<Levels label="Across every phase, the weekly operating system">

<Level name="Beginner">

A sample day is 90 minutes: one concept, one commit, one log line. A sample week ends with something
deployed, even if it is small. The structure matters more than the hours, because it removes the daily
question of what to do.

```md
## 2026-W43 log
Mon 90m  concept: reranking. read docs, ran 3 queries by hand. commit: rerank behind flag
Tue 90m  build: rerank eval run. recall@5 numbers in table. log: flat scores bug
Wed 90m  write: log -> draft note "reranking is a second opinion"
...
Sun 60m  review: shipped rerank flag; next single outcome: refusal threshold from data
```

Common mistake: spending all fifteen hours on learning because building feels slow. Fix: the build block
comes first in the week.

</Level>

<Level name="Intermediate">

The note loop is the same as this site's: do the work; write the raw log (what broke, what I tried, the
gotcha); promote it into a note with a claim, code, the old way, the new way, when to use which, a practice
exercise and sources; ship it. The note is proof I understood it; the log is proof it happened.

</Level>

<Level name="Advanced">

Monthly and quarterly rhythms sit on top: every month, publish one artefact and update the portfolio;
every quarter, run a gate and delete one thing (a dependency, a note that no longer teaches, a habit that
is not working). Deletion keeps the system light enough to keep running.

</Level>

<Level name="Edge cases">

- A week with only five hours: keep the shape, shrink each block. One concept, one commit, one log line.
- A week lost entirely: the review block next week says so, and the calendar moves, not the gates.

</Level>

<Level name="Corner cases">

- A hard bug eating the whole build block for two weeks: that is learning too, so it goes into the log and
  probably becomes the best note of the month. Time-box it with a written hypothesis per session.

</Level>

<Level name="Production level">

The log lives in the repository next to the work, dated, so the evidence is in the same history as the
code.

</Level>

<Level name="Mindset">

Consistency beats intensity. Ninety minutes a day for a year is the plan; heroic weekends are not.

</Level>

<Level name="System design">

<Flow
  caption="The note loop"
  steps={['do the work', 'raw log: what broke, what I tried', 'note: claim, code, old way, new way', 'practice exercise and sources', 'ship it']}
/>

</Level>

<Level name="Strategy">

Put the four blocks in the calendar for four weeks before changing anything. Done when four consecutive
weeks each ended with something deployed and a review entry naming the next single outcome.

</Level>

</Levels>

#### Across every phase: how to learn, not just what

**Covers:** the five techniques that do most of the work (build first, explain in a note, spaced review,
interleaving, a bug log) and what deliberate practice means.

<Layers
  caption="The five techniques, and what each one keeps"
  layers={[
    { name: 'Build first, read second', note: 'motivation and the right questions' },
    { name: 'Explain it in a note', note: 'understanding: if I cannot write the rule, I do not own it' },
    { name: 'Space the review', note: 'retention: a day, a week, a month' },
    { name: 'Interleave', note: 'transfer: mixed topics, like real work' },
    { name: 'Keep a bug log', note: 'judgment: error, cause, fix, rule' },
  ]}
/>

<Levels label="Across every phase, how to learn">

<Level name="Beginner">

Read enough to start, then build, and let the bug teach the rest. When it works, write the rule in my own
words. If I cannot, I do not own it yet. Then come back to it after a day, a week and a month.

```md
## bug log entry
error:  "Cannot read properties of undefined (reading 'map')"
cause:  fetch result not loaded on first render; items was undefined
fix:    initial state [] and a loading state
rule:   every async value has three states: loading, error, data. Render all three.
```

Common mistake: rereading notes and feeling fluent. Rereading is recognition, not recall. Fix: close the
notes and rebuild the thing.

</Level>

<Level name="Intermediate">

Spaced review is cheap if it is scheduled: each note gets three review dates when it is written. A review
is a small re-implementation or an explanation from memory, not a reread.

Interleaving means mixing a language exercise, a UI bug and a database query in the same week. It feels
slower and works better, because choosing which tool fits is part of the skill.

</Level>

<Level name="Advanced">

Deliberate practice is working at the edge of my ability, with feedback, on a task that resembles the real
thing. Watching a tutorial is not practice. Rebuilding a feature from memory is. The feedback comes from
tests, evals, review and users.

</Level>

<Level name="Edge cases">

- A topic I will rarely use (a sorting algorithm I never implement at work): one note and one review, not
  three.

</Level>

<Level name="Corner cases">

- Build first on a topic where a mistake is costly (auth, payments): read the security guidance first,
  then build. Build-first has limits, and the plan's security checklist is one of them.

</Level>

<Level name="Production level">

The bug log is the highest-value file I keep. I reread it monthly for patterns; a repeated cause becomes a
lint rule, a test, or a note.

</Level>

<Level name="Mindset">

Learning is something I do, not something that happens to me while I watch.

</Level>

<Level name="System design">

<Flow
  caption="One concept through the five techniques"
  steps={['build a small thing', 'hit the bug, log it', 'write the rule as a note', 'review at day 1, 7, 30', 'mix it into next week']}
/>

</Level>

<Level name="Strategy">

Start the bug log on day one; give every note three review dates. Done when the bug log has thirty entries
and I can rebuild three earlier features from memory.

</Level>

</Levels>

#### Across every phase: assessment gates

**Covers:** the eight gates that prove a phase is done, passed without notes and then again with AI, where I
explain every line and trade-off.

<Figure art={`
  gate  task                              pass
  1     todo app from scratch, no framework  works, persists, explain every function
  2     why does a component re-render?      fix stale closure + derived-state bug
  3     design a multi-user schema           auth, authz, migrations, isolation test
  4     make a failing test pass             add CI, find a security bug, flame graph
  5     build a RAG feature                  measure retrieval and generation; refusal
  6     build a tool-using agent             approval gate, trace, budget, kill switch
  7     ship to ten users                    three iterations and a postmortem
  8     present three case studies           a stranger can say what I'd be trusted with
`} caption="The plan's gates. Failing one sends me back, not forward." />

<Levels label="Across every phase, assessment gates">

<Level name="Beginner">

A phase is done when I can pass its gate without notes. Not when the weeks are up, and not when I have read
everything. The gate is a task with a pass condition, so it is checkable.

Common mistake: moving on because the calendar says so. Fix: the plan's rule, if I cannot pass a gate, the
next phase will not fix it. Go back.

</Level>

<Level name="Intermediate">

Each gate has two halves. First without AI and without notes, to prove I own it. Then the AI-assisted
version: use the model, then explain every line and every trade-off it produced. The second half is the job
as it is now; the first half is what makes the second half safe.

</Level>

<Level name="Advanced">

I run gates as a timed session and record what I could not do. Gate 2, for example: given a component with
a stale closure and a derived-state bug, I explain why it re-renders, find both bugs and fix them, with the
clock running.

```tsx
// gate 2 practice: two bugs to find
function Counter({ items }: { items: string[] }) {
  const [count, setCount] = useState(0);
  const [total, setTotal] = useState(items.length);       // derived state: goes stale when items change
  useEffect(() => {
    const id = setInterval(() => setCount(count + 1), 1000); // stale closure: count is always 0 here
    return () => clearInterval(id);
  }, []);
  return <p>{count} / {total}</p>;
}
// fixes: const total = items.length;  and  setCount(c => c + 1)
```

</Level>

<Level name="Edge cases">

- Passing a gate by luck (the bug I happened to have seen): retake with a different instance of the task.

</Level>

<Level name="Corner cases">

- Passing the no-AI half but failing to explain the AI half (it used an API I do not know): not passed. The
  explanation is the gate.

</Level>

<Level name="Production level">

Each gate attempt is a dated log entry with the result and what I go back to. Gates are rerun once a
quarter, which doubles as spaced review.

</Level>

<Level name="Mindset">

Gates are kind: they tell me exactly what to fix before it costs me in a job.

</Level>

<Level name="System design">

<Flow
  caption="A gate attempt"
  steps={['task, timed, no notes', 'pass?', 'no: list gaps, go back', 'yes: AI-assisted version', 'explain every line', 'log result, next phase']}
/>

</Level>

<Level name="Strategy">

Write each gate's task down at the start of its phase. Done when all eight gates are logged as passed, both
halves, with dates.

</Level>

</Levels>

#### Across every phase: the AI-era split

**Covers:** what to delegate to AI, what to keep for myself, what to verify every time, and the six rules
that keep the split honest.

<Compare
  left="Delegate to AI"
  right="Keep for myself, and verify every time"
  caption="The plan's three columns, read across: delegate the left, keep the middle, verify the right"
  rows={[
    ['Boilerplate and scaffolding', 'Keep: problem framing and scope. Verify: the diff, line by line'],
    ['First drafts and refactors', 'Keep: data model and state ownership. Verify: behaviour, not just compilation'],
    ['Test generation', 'Keep: auth and security boundaries. Verify: tests actually assert something'],
    ['Error explanations', 'Keep: trade-offs and naming. Verify: citations and sources'],
    ['Documentation summaries', 'Keep: UX and accessibility. Verify: performance and cost'],
    ['Translation between languages', 'Keep: final review and merge. Verify: privacy and secrets'],
  ]}
/>

<Levels label="Across every phase, the AI-era split">

<Level name="Beginner">

AI is a junior pair with infinite patience and no accountability. I hand it work a junior could do with
review, I keep the decisions that need ownership, and I verify everything it produces before it ships.

The six rules: never merge code I cannot explain; never ship an AI feature without an eval; keep a
model-free path for critical flows; log prompts, model versions and costs for anything user-facing; treat
model output as untrusted input; if a deterministic script can do it, use the script.

</Level>

<Level name="Intermediate">

"Verify the diff, line by line" in practice: I read the generated diff as if a stranger wrote it, run it,
and check one edge input by hand. "Tests actually assert something": I break the code on purpose and see a
test fail.

```ts
// A generated test that asserts nothing useful:
test('formatPrice works', () => { expect(formatPrice(10)).toBeDefined(); });
// A test that would catch a real bug:
test('formatPrice rounds half up to two places', () => { expect(formatPrice(10.005)).toBe('10.01'); });
// Note: 10.005 is not exactly representable in floating point, which is why this test is worth having.
```

</Level>

<Level name="Advanced">

"Keep a model-free path for critical flows" means sign-in, payment and data export work if the model
provider is down or wrong. The RAG feature degrades to search results; the agent's absence leaves the
deterministic scripts running.

</Level>

<Level name="Edge cases">

- A refactor across fifty files generated in seconds: too big to verify line by line. Ask for it in slices
  I can review, each with tests passing.

</Level>

<Level name="Corner cases">

- AI-generated code that touches a "keep" column item (an auth check inside a scaffold): the scaffold is
  delegated, the auth line is mine. I rewrite that part by hand.

</Level>

<Level name="Production level">

For user-facing AI, the log line per call holds the prompt version, model, tokens and cost, and the eval runs
in CI. That is rules 2 and 4 made mechanical.

</Level>

<Level name="Mindset">

AI made the first draft cheap. It did not make judgment cheap. The split is how I keep doing the
expensive part myself.

</Level>

<Level name="System design">

<Flow
  caption="An AI-assisted change"
  steps={['I frame the task', 'AI drafts', 'I read the diff', 'tests and evals run', 'I check one edge by hand', 'I can explain it?', 'merge']}
/>

</Level>

<Level name="Strategy">

Tag each commit in a month as hand-written or AI-drafted and reviewed, and check the review notes. Done when
every AI-drafted commit has a test that would fail without it, and I can explain any line chosen at random.

</Level>

</Levels>

## Week review: rules

fix the cause and add a test. Most "random" bugs stop being random at the reproduce step.

<Level name="Production level">

The rules become automation where they can: CI enforces tests (rule 5), Lighthouse and axe enforce parts of
rule 11, the eval enforces rule 7 for AI features.

</Level>

<Level name="Mindset">

Rules are cheaper than willpower. Write them once, check them weekly.

</Level>

<Levels label="Across every phase, the first 30 days">

<Level name="Beginner">

Week 1 ends with a public URL. Five Git commands are enough: `init`, `add`, `commit`, `push`, `status`.
Week 2 is the language in tiny pieces, ending with a page where a button changes some text.

```html
<p id="msg">Hello</p>
<button id="btn" type="button">Change</button>
<script>
  document.getElementById('btn').addEventListener('click', () => {
    document.getElementById('msg').textContent = 'Changed at ' + new Date().toLocaleTimeString();
  });
</script>
```

Common mistake: a script in the `head` that runs before the elements exist, giving `TypeError: Cannot read
properties of null (reading 'addEventListener')`. Fix: script at the end of the body, or `defer`.

</Level>

<Level name="Intermediate">

Week 3 is the vanilla todo app: an array of objects as the state, a render function that draws it, event
handlers that change the state and call render. Week 4 adds the network: fetch a public API and render all
three states.

```js
async function load() {
  render({ status: 'loading' });
  try {
    const res = await fetch('https://api.example.com/items');
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    const items = await res.json();
    render(items.length ? { status: 'data', items } : { status: 'empty' });
  } catch (err) {
    render({ status: 'error', message: err.message });
  }
}
```
