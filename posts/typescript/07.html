The `any` trap

3 October 2026

The mistake and the right approach

any opts a value out of checking in both directions. You can read any property, call it, and pass it anywhere, and you can assign anything to it. It compiles, it ships, and it removes the reason to use TypeScript on that path. The usual excuse is local: one any to unblock a feature. The property that does not exist is then a runtime error three files later, often spelled wrong, like nmae, which any will not catch.

any is contagious. A function that returns it turns the caller’s variables into any the moment they are used as any. A function that accepts it accepts a mistake from honest code. unknown is the opposite default: you can hold the value, but you cannot touch it until a check narrows it. A real interface is what you use once you do know the shape. A parse at the boundary — hand-written checks, or a schema library if you already depend on one — is how unknown becomes that interface.

This is not a moral rule about a forbidden keyword. It is cost. any in a core model is technical debt with a short name, because every downstream signature quietly degrades to JavaScript.

A concrete use case

An API handler in a personal project maps res.data.items to names for a list view. Typed as any, the map compiles with i.nmae. The list renders blanks. The same any is passed into a save function that expected a User, so a partial object is written through. Replacing the parameter with unknown forces one parser. After that parser, item.name is a string and the typo is a compile error.

Code that shows the scenario

Both the response and each item are any. The misspelling is legal. So is passing the result to a function that wanted strings.

function handle(res: any) {
  return res.data.items.map((item: any) => item.nmae);
}

function shout(names: string[]): string {
  return names.join(", ");
}

shout(handle({})); // compiles; throws when data or items is missing

unknown does not allow the property access. The parser is the only door.

type Item = { name: string };

type Payload = { items: Item[] };

function parsePayload(raw: unknown): Payload {
  if (typeof raw !== "object" || raw === null || !("data" in raw)) {
    throw new Error("missing data");
  }
  const data = raw.data;
  if (typeof data !== "object" || data === null || !("items" in data)) {
    throw new Error("missing items");
  }
  if (!Array.isArray(data.items)) throw new Error("items is not an array");
  return {
    items: data.items.map((item) => {
      if (typeof item !== "object" || item === null || !("name" in item)) {
        throw new Error("item.name missing");
      }
      if (typeof item.name !== "string") throw new Error("item.name");
      return { name: item.name };
    }),
  };
}

function handle(res: unknown): string[] {
  const data = parsePayload(res);
  return data.items.map((item) => item.name);
}

A typed model beats any when you already know the shape. unknown is for the gap before you know.

type User = { id: string; name: string };

function greet(user: User): string {
  return "Hello " + user.name;
}

const loose: any = { id: 1 };
greet(loose); // allowed, and wrong

const held: unknown = { id: 1 };
// greet(held); // error: unknown is not User

Best case and worst case

Wrong approach: any to unblock

Best case. A type you delete the same hour, isolated in a scratch file, never exported, never stored. Or a third-party callback typed any that you immediately narrow into a local unknown variable and parse. The keyword does not escape.

Worst case. Core models are any. Typos compile. Refactors do not fail. A function annotated any accepts a number where a User belongs and returns a value every caller treats as checked. You are maintaining JavaScript with an extra compile step.

Right approach: unknown, then a real type

Best case. JSON, request bodies, and document dumps stay unknown until one function checks them. The rest of the app takes Item or User. item.nmae fails at compile time. Callers of handle get string[] and cannot pass the raw payload onward.

Worst case. A parser full of casts (as Item) wearing the costume of unknown. The parameter type looks careful and the body repeats any’s mistake one assertion at a time. unknown only helps if the narrowing is a real check: typeof, in, Array.isArray, or a schema that returns a typed value.

Old implementation vs new implementation

Before: the list view and the logger both take any so the feature can ship.

function itemNames(res: any): any {
  return res.data.items.map((item: any) => item.nmae);
}

function logNames(res: any) {
  console.log(itemNames(res).join(", "));
}

After: unknown in, string[] out, and the typo cannot hide.

function itemNames(res: unknown): string[] {
  return parsePayload(res).items.map((item) => item.name);
}

function logNames(res: unknown): void {
  console.log(itemNames(res).join(", "));
}

The best way to do it in practice

Turn on noImplicitAny so the shortcut has to be typed on purpose. Ban any on exported functions and on models that other modules import; a lint rule such as no-explicit-any is the mechanical version of that ban. Where a type is genuinely not known yet — JSON.parse, response.json(), a request body — store unknown and parse once into a named type. Do not “fix” an error by annotating any or by prefixing the expression with as any. If you need a temporary escape in a migration, keep it in one function at the edge and give it a comment that names the replacement type. Replace one any in a core model before adding a new one.
