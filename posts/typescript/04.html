null/undefined + optional props

30 September 2026 · about 6 min · Published

What it is

null, undefined, and an optional property all feel like “no value.” They are three different absences, and collapsing them with || "" or || "N/A" hides which one you had.

With strictNullChecks, null and undefined are not members of string unless you add them. An optional property name?: string means the caller may omit the key; a read of it is string | undefined. Writing name: string | undefined means the key is part of the object and the value may be undefined. Writing name: string | null means the key is present and null is an intentional empty, which is how a lot of JSON APIs say “the user cleared this” or “it was never set” if you have agreed on that meaning. "" is a fourth state: present, and blank.

Under exactOptionalPropertyTypes, the split gets sharper on the way in. An optional property does not accept an explicit undefined unless undefined is in its type. Without that flag, assigning undefined to an optional property is allowed, so the difference is easier to miss. Reading still cannot tell “omitted” from “set to undefined” unless you check in or hasOwn.

The question to ask before picking a default is: is this absence a valid state, or a bug? Valid absence gets a type and a branch. A bug fails at the boundary instead of being painted over with "N/A".

A profile screen in React. The API returns bio: null when the person has never written one, and bio: "" when they saved an empty bio on purpose. A presentational row takes bio?: string so the parent can omit the row’s text entirely. The old helper profile.bio || "N/A" shows “N/A” for null, for undefined, and for "", so support cannot tell “not set” from “set to empty,” and a real bug — the field missing because a select forgot it — looks like a normal profile.

One union of absences, one default. The label cannot report what happened.

Model the backend field as intentional null, and handle blank text separately.

5function bioLabel(bio: string | null): string {


6  if (bio === null) return "Not set";


7  if (bio.length === 0) return "Empty";


8  return bio;

Optional props are a different contract. Omitting caption means “do not render the line.” A required key that may be undefined is a value the parent must pass, even when the value is undefined.

Old

Wrong approach: one fallback for every absence

Best case. The product truly wants the same placeholder for missing, null, and blank, and you have checked that no other falsy value can appear. || is then a display choice, not a parser. Even then, ?? is usually the operator you meant if "" should stay visible, because || treats "" as missing.

Worst case. A dropped field, a JSON null, and a user-entered empty string all render “N/A”. A bug in the query looks like an empty profile. || also collapses the number 0 if this pattern is copied onto a count. The UI cannot show “not set” versus “cleared.”

Before: the component props and the API model share one muddy field, and the view papered over it.

before.ts 
1type ProfileCardProps = {


2  bio?: string | null;


3};


4


5function ProfileCard(props: ProfileCardProps): string {


6  return props.bio || "N/A";


7}

New

Right approach: one type per meaning

Best case. null renders “Not set,” "" renders “Empty,” and a missing optional prop skips the row. strictNullChecks forces each call site to decide. Invalid data that should have been a string fails in the parser instead of becoming a placeholder.

Worst case. You model three absences the product does not actually distinguish, and every call site grows branches that all do the same thing. Or you turn on exactOptionalPropertyTypes in a large repo without fixing call sites that pass explicit undefined. Match the type to a real product difference; do not add null only to look careful.

After: the API type keeps null, the props type uses omission for “no row,” and the adapter is the only place that maps one to the other.

after.ts 
1type ApiProfile = {


2  bio: string | null;


3};


4


5type ProfileCardProps = {


6  title: string;


7  bio?: string;


8};


9


10function toCardProps(api: ApiProfile, title: string): ProfileCardProps {


11  if (api.bio === null || api.bio.length === 0) {


12    return { title };


13  }


14  return { title, bio: api.bio };


15}


16


17function ProfileCard(props: ProfileCardProps): string {


18  if (props.bio === undefined) return props.title;


19  return props.title + ": " + props.bio;


20}

When to use which

Turn on strictNullChecks if it is not already on; without it, null and undefined flow into every type and this distinction is fiction. Use ?: when a React prop or object key may be omitted. Use | undefined when the key should exist. Use | null when the backend intentionally sends null, and document that meaning next to the type. Compare with === null and === undefined, not truthiness. Prefer ?? over || when empty string or zero is real data. If absence is a bug, throw or reject at the boundary and keep the inner type non-null.
