interface vs type

28 September 2026

The mistake and the right approach

interface and type both name a shape, so it is easy to swap them per file and treat the choice as taste. The code still compiles. What you lose is a rule you can apply when the shape is not a plain object.

An interface describes an object (or a callable or construct signature) and can be extended or merged by another declaration with the same name. A type alias can name almost any type: a union, an intersection, a primitive, a tuple, a mapped type, or a function. You cannot write a string-literal union as an interface without stuffing it into a dummy object, and that dummy object is how a finite set quietly becomes “some string field.”

Neither keyword is more professional. The useful split in application code is: interface for object shapes you expect to extend (component props, API models), type for unions, function aliases, and compositions built with utilities. Pick that rule once per codebase and keep it, including when you are the only reviewer.

A concrete use case

A post card in a personal project needs props, a publish status, and a click handler. Props are an object you might extend with an optional href later. Status is three strings, not an object. The handler is a function type reused by the card and by a keyboard shortcut. Modeling status as interface Status { value: string } throws away the finite set. Mixing type PostCardProps in one file and interface PostCardProps in another just creates churn.

Code that shows the scenario

This compiles, and it is the wrong tool. The union is gone. Any string is a status.

interface Status {
  value: string;
}

function publish(status: Status) {
  if (status.value === "live") return;
  // "archived", "LIVE", and "ship it" all type-check
}

The split that matches the work: an interface for the object, type aliases for the union and the function.

interface PostCardProps {
  title: string;
  published: boolean;
}

type Status = "draft" | "live" | "archived";
type Handler = (id: string) => Promise<void>;

interface PostCardPropsWithLink extends PostCardProps {
  href: string;
}

Declaration merging is the other real difference. Two interfaces with the same name combine. Two type aliases with the same name are an error. That is helpful for extending a model on purpose, and harmful when two files merge an interface by accident.

interface User {
  id: string;
}

interface User {
  name: string;
}

const user: User = { id: "u_1", name: "Ada" };

type Id = string;
// type Id = number;  // Duplicate identifier

Best case and worst case

Wrong approach: no rule, unions forced into objects

Best case. A tiny file where every alias is a flat object and you never extend it. interface and type behave alike, so the mix does not hurt yet.

Worst case. Status, role, and route names all become { value: string } or a bare string because an interface could not hold the union. Call sites lose autocomplete. A second interface User in the same scope merges fields you did not mean to add. Separate modules do not merge just because the name matches; a global, a namespace, or a second declaration in the same file does. Reviews argue the keyword instead of the data.

Right approach: interface for objects, type for the rest

Best case. Props and API models use interface and extends. Unions, handlers, and utility compositions use type. A new teammate — or you, six months later — can tell why a declaration was written that way without a comment war.

Worst case. You follow the rule so rigidly that a one-off union of two object shapes becomes awkward, or you export an interface that then merges with a dependency’s interface of the same name. The rule is a default, not a ban on type for objects. If a public object type must not merge, a type alias is the safer export.

Old implementation vs new implementation

Before: one file uses a type for props, the next uses an interface, and the status union has been flattened so it will fit anywhere.

type PostCardProps = {
  title: string;
  published: boolean;
};

interface Status {
  value: string;
}

const onSave: any = async (id) => {
  await fetch("/api/posts/" + id, { method: "POST" });
};

After: props stay extendable objects, status is a union, and the handler has a real alias.

interface PostCardProps {
  title: string;
  published: boolean;
}

type Status = "draft" | "live" | "archived";

interface Post extends PostCardProps {
  id: string;
  status: Status;
}

type Handler = (id: string) => Promise<void>;

const onSave: Handler = async (id) => {
  const res = await fetch("/api/posts/" + id, { method: "POST" });
  if (!res.ok) throw new Error("save failed");
};

The best way to do it in practice

Write the rule at the top of the types module, then stop relitigating it. Use interface for component props and for object models you extend. Use type the moment you need a union, a tuple, a mapped type, or a function signature. Reach for extends on interfaces and intersections or utilities on type aliases. Do not wrap a union in an object just to keep using interface. If a type is part of a public export and accidental declaration merging would be bad, prefer type.
