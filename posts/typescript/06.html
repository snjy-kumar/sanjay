Typing functions properly

2 October 2026 · about 5 min · Published

What it is

Annotating a variable is local. Annotating a function is a contract every call site inherits. The expensive early habit is function save(data) { ... } — under noImplicitAny that is an error; with the flag off, data is any — or writing an explicit return of any “just for now” and never coming back.

Type the parameters first. If the return expression is obvious, let TypeScript infer it: a function that returns post.title does not need you to write : string unless you want to lock it. For a public helper used in more than one place, write the return type anyway. The annotation is what you meant to return. Inference is what you happened to return. When they disagree, you want the error at the helper, not at a distant caller.

A return annotation is not a validator. return res.json() as Promise<Post> makes the checker treat the body as Post without looking at it. fetch’s json() is Promise<any>. The honest contract types the inputs, types the promised output, checks res.ok, and parses the JSON into that output. The assertion is a hole you can see; it is not the design.

Two personal-project helpers share a save path: a React form and a small Node script. The first version was save(data) returning whatever fetch produced. One caller passed { name } and the other passed { title }. Both compiled. The route wanted title. The script then read saved.id off a value that was still any, so a missing id was a runtime crash instead of a type error at the helper.

The code

No parameter type, no return type. Callers guess, and a typo in the body is invisible if any leaks in.

untyped.ts 
1async function save(data) {


2  const res = await fetch("/api/posts", {


3    method: "POST",


4    body: JSON.stringify(data),


5  });


6  return res.json();


7}

A reusable helper states its input and its promised output. Inference is enough for the tiny local function next to it.

annotated.ts 
1type SaveInput = { title: string };


2type Saved = { id: string };


3


4function titleOf(input: SaveInput) {


5  return input.title; // inferred string


6}


7


8async function save(data: SaveInput): Promise<Saved> {


9  const res = await fetch("/api/posts", {


10    method: "POST",


11    headers: { "content-type": "application/json" },


12    body: JSON.stringify(data),


13  });


14  if (!res.ok) throw new Error("failed to save");


15  return parseSaved(await res.json());


16}

The cast compiles and still does not check the payload. Parsing is what makes the return annotation true.

parse.ts 
1function parseSaved(raw: unknown): Saved {


2  if (typeof raw !== "object" || raw === null) {


3    throw new Error("saved: expected an object");


4  }


5  if (!("id" in raw) || typeof raw.id !== "string" || raw.id.length === 0) {


6    throw new Error("saved: expected id");


7  }


8  return { id: raw.id };


9}


10


11async function fetchPost(id: string): Promise<Saved> {


12  const res = await fetch("/api/posts/" + id);


13  if (!res.ok) throw new Error("failed");


14  return parseSaved(await res.json());


15}

Old

Wrong approach: untyped parameters and any returns

Best case. A function used once, directly under the call, with data built in that same block, deleted when the experiment ends. You never cross a file boundary.

Worst case. save is imported in several places. Each caller invents a shape. res.json() returns any, so saved.id.toUpperCase type-checks even when the server returned { error }. The bug shows up as a thrown method call on undefined, far from the fetch.

Before: the helper documents nothing, and the caller asserts its way out.

before.ts 
1async function fetchPost(id) {


2  const res = await fetch("/api/posts/" + id);


3  return res.json();


4}


5


6async function show(id) {


7  const post: any = await fetchPost(id);


8  return post.title;


9}

New

Right approach: parameters typed, public returns annotated

Best case. SaveInput rejects a payload without title at every call site. Promise<Saved> means a refactor that returns the raw Response fails in save, not in the form. titleOf stays inferred because the expression is the type. Autocomplete on the result is the real id.

Worst case. You annotate a lie. Promise<Post> plus as Promise<Post> looks like a contract and is only a cast. Callers trust it. The server changes the body and TypeScript stays green. An explicit return type helps only if the value you return was actually checked or built from checked pieces.

After: id is a string, the promise is Post, and title is only read after parsePost has checked it.

after.ts 
1type Post = { id: string; title: string };


2


3function parsePost(raw: unknown): Post {


4  if (typeof raw !== "object" || raw === null) throw new Error("post");


5  if (!("id" in raw) || typeof raw.id !== "string") throw new Error("post.id");


6  if (!("title" in raw) || typeof raw.title !== "string") throw new Error("post.title");


7  return { id: raw.id, title: raw.title };


8}


9


10async function fetchPost(id: string): Promise<Post> {


11  const res = await fetch("/api/posts/" + id);


12  if (!res.ok) throw new Error("failed");


13  return parsePost(await res.json());


14}


15


16async function show(id: string): Promise<string> {


17  const post = await fetchPost(id);


18  return post.title;


19}

When to use which

Enable noImplicitAny so an untyped parameter is a mistake you see immediately. Type every parameter on exported functions. Let local, obvious returns be inferred. Annotate return types on helpers you import from more than one module, and on anything async whose payload crosses I/O — then make the returned value satisfy that annotation by parsing, not by as. Check res.ok before reading the body. Keep Response inside the helper so callers receive the domain type, not the transport type.

A helper used in more than one placetype the parameters
A local return that is obviousinfer it
An async payload that crosses I/Oannotate and parse
The caller should not see the transportreturn the domain type

Practice

Type save so the argument must have a title, and so the function returns a promise of an object with a string id. Do not return the JSON unchecked.

exercise.ts 
1async function save(data) {


2  const res = await fetch("/api/posts", {


3    method: "POST",


4    body: JSON.stringify(data),


5  });


6  return res.json();


7}
