Union types

29 September 2026

The mistake and the right approach

If a value has four real states, string says it has infinitely many. Typos type-check. A status of "sucess" sails through, and the UI has a branch for a state that does not exist in the product plus no branch for one that does.

A union lists the members you actually handle: "idle" | "loading" | "error" | "success". Assigning anything else is an error. A switch that returns on each member starts failing the compile when a member is added and a case is forgotten, which is the compiler complaining with better memory than yours. Autocomplete offers the real set instead of every string you have typed this year.

That is not an advanced trick. It is how you stop describing a finite fact as an open primitive. When each state also carries different data — a message only on error, a post only on success — the same idea gets stricter as a discriminated union, so those fields cannot appear together by accident. Start with the literal union if the payload is shared; split the object if the fields are not.

A concrete use case

A fetch panel on a personal project shows one of four labels: waiting, loading, failed, done. The first version stored status: string and optional data and error on the same object. A typo in a setter left the panel blank. Another path set both data and error, and the UI rendered a successful post with an error banner under it.

Code that shows the scenario

The wide status accepts the typo. Nothing in the type system notices.

type State = {
  status: string;
  data?: string;
  error?: string;
};

const broken: State = { status: "sucess", data: "hello", error: "nope" };

function label(state: State): string {
  if (state.status === "success") return "Done";
  if (state.status === "error") return "Failed";
  return "Unknown";
}

A closed union makes the typo an error and makes a missing case visible. assertNever turns “we added a state” into a compile error at the switch.

type Status = "idle" | "loading" | "error" | "success";

function assertNever(value: never): never {
  throw new Error("unexpected status: " + String(value));
}

function label(status: Status): string {
  switch (status) {
    case "idle":
      return "Waiting";
    case "loading":
      return "Loading";
    case "error":
      return "Failed";
    case "success":
      return "Done";
    default:
      return assertNever(status);
  }
}

// label("sucess"); // not assignable to Status

If data and error cannot both be meaningful, do not leave them as parallel optionals. Tie each field to the status that owns it.

type Post = { id: string; title: string };

type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "error"; message: string }
  | { status: "success"; data: Post };

function titleOf(state: RequestState): string {
  switch (state.status) {
    case "success":
      return state.data.title;
    case "error":
      return state.message;
    case "idle":
    case "loading":
      return "";
    default:
      return assertNever(state);
  }
}

Best case and worst case

Wrong approach: string for a finite set

Best case. Every writer of the field is a constant you control, the tests spell the same four words, and nobody typos them. The bug is latent, not visible.

Worst case. "sucess" and "SUCCESS" both compile. The default branch hides a new state. Optional data and error are set together, so the UI tells two stories. A rename of one status does not touch the other files.

Right approach: a union of the real options

Best case. New states do not compile until every switch handles them. Call sites get autocomplete. Impossible combinations are not representable, so the blank-screen class of bugs moves to compile time.

Worst case. You union together states that are not exhaustive in the real system — the server can still send "queued" — and then a parser you do not have throws only at runtime. A union models what you decided to accept. Untrusted strings still need a parse step into that union, or the outside world will hand you a value the type pretends cannot exist.

Old implementation vs new implementation

Before: one object, open status, fields that can all be present.

type PanelState = {
  status: string;
  data?: Post;
  error?: string;
};

function PanelText(state: PanelState): string {
  if (state.data) return state.data.title;
  if (state.error) return state.error;
  return state.status;
}

After: the status is a union, and the text helper has nowhere to forget a member.

type PanelState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "error"; message: string }
  | { status: "success"; data: Post };

function PanelText(state: PanelState): string {
  switch (state.status) {
    case "idle":
      return "Waiting";
    case "loading":
      return "Loading";
    case "error":
      return state.message;
    case "success":
      return state.data.title;
    default:
      return assertNever(state);
  }
}

The best way to do it in practice

Search for fields whose comments list the allowed strings, and replace the comment with a union. Switch on that union without a catch-all string compare; put assertNever in the default so a new member fails the build. Parse external input into the union once. If two fields cannot be true together, split them into separate union members instead of optional properties on one object. Do not use a union for genuinely open text.
