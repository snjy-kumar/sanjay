Basic types treated too casually

27 September 2026

The mistake and the right approach

A string, a number, and a boolean are real types. They are also very wide. Treating them as labels — write the primitive, move on — lets values through that look typed and still mean the wrong thing at runtime.

Three failures show up as soon as a form or an API is involved. An “empty” text field is still a string: "". An id that looks numeric is often a string from JSON ("42"), and the reverse happens too. And true is not "true". Boolean("false") is true, because any non-empty string is truthy. Number("n/a") is NaN, and NaN is a number, so a typed age field accepts it. An empty numeric field is a different trap: Number("") is 0, which also type-checks and is still the wrong age.

The correction is to make the type say what the value is allowed to be, then refuse everything else at the boundary. A status that is only ever draft or published should be "draft" | "published", not string. A value that can be empty should say which kind of empty is legal: a blank string, null, or a missing property are different states. Checks such as typeof and Number.isNaN belong where untrusted input enters, not three components later.

A concrete use case

A small publishing screen in a personal project: title input, a status control, an age or “years using the tool” number, and an “active” flag that one backend sends as a boolean and another sends as the strings "true" and "false". The loose model compiles. The published record then has status "yes", an id you cannot safely concatenate, and an age of NaN that renders as blank in one view and breaks a sort in another.

Code that shows the scenario

This assignment type-checks. Every field is the primitive you asked for, and every field is still wrong for the product.

type User = {
  id: string;
  status: string;
  age: number;
  active: boolean;
};

const saved: User = {
  id: "42",
  status: "yes",
  age: Number("n/a"),      // NaN, which is a number
  active: Boolean("false"), // true, because "false" is a non-empty string
};

Tighten the known set, and parse at the edge so NaN and stringly booleans fail before they are stored.

type Status = "draft" | "published";

type User = {
  id: string;
  status: Status;
  age: number;
  active: boolean;
};

function parseAge(value: unknown): number {
  if (typeof value !== "number" || Number.isNaN(value)) {
    throw new Error("age must be a real number");
  }
  return value;
}

function parseActive(value: unknown): boolean {
  if (value === true || value === "true") return true;
  if (value === false || value === "false") return false;
  throw new Error("active must be boolean or 'true' | 'false'");
}

function parseStatus(value: unknown): Status {
  if (value === "draft" || value === "published") return value;
  throw new Error("unknown status");
}

A third case: the empty title. "" is a successful string. If a missing title is a bug, reject it. If a draft may have no title yet, put that in the type on purpose instead of hoping a later if (title) remembers.

function requireTitle(value: string): string {
  if (value.trim() === "") throw new Error("title is empty");
  return value;
}

type Draft = { title: string | null; status: "draft" };

Best case and worst case

Wrong approach: primitives as labels

Best case. A one-off script whose fields really are free text, a count you already sanitized, and a boolean you set yourself in the same function. The wide types happen to match the data because nothing untrusted touches them.

Worst case. The form ships. Status "yes" misses every branch that looks for "published". The id "42" gets added to another id or sent to a path that expected a number. Boolean("false") marks a paused account active. NaN sorts and compares in ways that are hard to see in a log.

Right approach: precise types and a boundary parse

Best case. Illegal status strings do not assign. parseAge throws on NaN and on numeric strings you forgot to convert. parseActive accepts both JSON booleans and the legacy string form, and nothing else. Call sites after the parse use User without guessing.

Worst case. You invent a giant union for a field that really is open-ended prose, or you throw on empty drafts that the product allows. Precision still has to match the domain. A closed union for a closed set is the win; a closed union for a comment body is noise.

Old implementation vs new implementation

Before: the save path trusts the form object because the type already said string and number.

function saveUser(input: User): User {
  return input;
}

After: the save path accepts unknown form state and returns a User only after each field has been read deliberately.

type UserInput = {
  id: unknown;
  status: unknown;
  age: unknown;
  active: unknown;
  title: unknown;
};

function saveUser(input: UserInput, title: string): User {
  if (typeof input.id !== "string" || input.id.length === 0) {
    throw new Error("id must be a non-empty string");
  }
  requireTitle(title);
  return {
    id: input.id,
    status: parseStatus(input.status),
    age: parseAge(input.age),
    active: parseActive(input.active),
  };
}

The best way to do it in practice

Keep primitives where the set is actually open: a title, a free-text bio, a count you computed locally. As soon as a field has a known shape — a lifecycle, an enum from the API, a flag that crosses a JSON boundary — name that shape. Put the parsers next to the model, call them once where data enters, and let the rest of the app take the parsed type. Prefer Number.isNaN or Number.isFinite over a truthiness check for numbers. Never coerce flags with Boolean(string). If empty is legal, decide whether you mean "", null, or an optional property, and type only that.
